Change Feed & Global Distribution

The change feed is how you build anything reactive on Cosmos. Global distribution is the reason to choose it at all.

🔴 Advanced ⭐ Senior-level 🔥 Must know
Quick revision
  • The change feed is a persistent, ordered log of changes per partition. Not a queue — you can re-read it.
  • Ordering is guaranteed within a logical partition only, never globally.
  • The default feed doesn't include deletes. Use soft deletes with TTL, or the all-versions mode.
  • The lease container tracks progress and distributes work across instances.
  • At-least-once delivery — handlers must be idempotent.
  • Multi-region writes mean conflicts, and you choose the resolution policy.
  • Strong consistency is incompatible with multi-region writes.

The change feed 🔥 Must know

In simple terms

Every insert and update to a container is recorded in a persistent, ordered log. You can read that log from any point — the beginning, now, or a saved position.

It isn't a message queue. The log persists, so multiple independent consumers can read it at their own pace, and you can replay history.

PropertyDetail
OrderingGuaranteed within a logical partition. No global ordering
ContentThe latest version of each changed item, not every intermediate version
DeletesNot included in the default (latest-version) mode
RetentionAs long as the data exists — it's derived from the items themselves
DeliveryAt-least-once. Handlers must be idempotent
CostReading it consumes RU from the container's budget
Two properties that cause real design mistakes

1. Deletes are invisible. The default change feed shows inserts and updates only. So a downstream search index or cache built on the change feed will never remove anything — deleted items live on forever in your derived stores.

The standard fix is a soft delete: set isDeleted: true plus a short TTL. The update appears in the feed so consumers can remove it, and TTL cleans up the item afterwards for free. There's also an all versions and deletes mode which does surface deletes, with a limited retention window.

2. Only the latest version appears. If an item is updated three times before your consumer reads the feed, you see the final state once — not three events. So the change feed tells you what something is now, not what happened to it. Any logic that depends on the sequence of intermediate states won't work, and that's a genuine architectural constraint versus a real event log.

The change feed processor 🔥 Must know

var processor = container
    .GetChangeFeedProcessorBuilder<Order>("order-projections", HandleChangesAsync)
    .WithInstanceName(Environment.MachineName)     // must be unique per instance
    .WithLeaseContainer(leaseContainer)            // separate container for progress
    .WithMaxItems(100)
    .WithPollInterval(TimeSpan.FromSeconds(1))
    .WithStartTime(DateTime.MinValue.ToUniversalTime())   // from the beginning
    .Build();

await processor.StartAsync();

async Task HandleChangesAsync(
    ChangeFeedProcessorContext ctx,
    IReadOnlyCollection<Order> changes,
    CancellationToken ct)
{
    foreach (var order in changes)
    {
        // MUST be idempotent - this can be called twice for the same item
        await UpsertProjectionAsync(order, ct);
    }
    // Returning without throwing checkpoints the lease.
    // Throwing means the batch is retried - so partial work must be safe.
}
ComponentRole
Lease containerStores one lease document per partition range, holding the continuation position and owner
Instance nameIdentifies this consumer. Must be unique per running instance
Processor nameIdentifies the logical consumer. Different names = independent progress
CheckpointingAutomatic when the delegate returns without throwing
Senior signal — how the lease container gives you scale-out for free

Leases are how the processor distributes work. Each physical partition range has a lease document; an instance acquires leases it can handle and renews them.

Start a second instance and it acquires some of the leases from the first — work rebalances automatically. If an instance dies, its leases expire and another picks them up, resuming from the checkpointed position. No coordination code, no leader election.

Two consequences worth stating. Parallelism is bounded by the number of partition ranges — running 20 instances against 4 ranges means 16 sit idle, so scaling consumers past the partition count does nothing. And the lease container needs its own throughput; under-provisioning it throttles the processor itself, which looks like the consumer being mysteriously slow.

Also: a different processor name gives an entirely independent consumer. That's how you run a search-index projection and an analytics pipeline off the same container without them interfering — each has its own leases and its own position.

Idempotency isn't optional here

Checkpointing happens after the delegate returns. So if the process dies mid-batch, the whole batch is redelivered — items already handled will be handled again.

That's at-least-once delivery, and it's the correct trade: the alternative would be checkpointing first and losing changes on a crash.

So handlers must be safe to run twice. Upserts are naturally idempotent; "increment a counter" is not, and needs either a version check or a separate dedupe record. This is the same requirement as idempotent message consumers.

With Azure Functions

[Function("ProjectOrders")]
public async Task Run(
    [CosmosDBTrigger(
        databaseName: "shop",
        containerName: "orders",
        Connection = "CosmosConnection",
        LeaseContainerName = "leases",
        CreateLeaseContainerIfNotExists = true,
        MaxItemsPerInvocation = 100)]
    IReadOnlyList<Order> changes,
    FunctionContext ctx)
{
    foreach (var order in changes) await UpsertProjectionAsync(order);
}

The trigger wraps the same processor, so all the same rules apply — idempotency, lease container throughput, partition-bounded parallelism. It's the least-code option, and it hides the lease mechanics, which is worth understanding anyway when something goes wrong.

Senior signal — the change feed solves the dual-write problem

The classic dual-write problem: write to the database, then publish an event. If the publish fails, the data changed and nothing downstream knows.

The change feed inverts it. You write only to Cosmos, and the event stream is derived from the committed data. There's nothing to keep in sync because there's one write.

That's effectively a built-in outbox with no table to maintain and no publisher to run — genuinely one of Cosmos's better features, and the same argument as MongoDB change streams.

The honest limitation: because only the latest version appears, it gives you state changed notifications rather than a true event log. If downstream consumers need semantic events — "order cancelled" versus "order shipped" — you either infer them from the state, or write explicit event documents to a separate container and put the change feed on that instead. The second is usually cleaner.

Global distribution 🔥 Must know

In simple terms

Adding a region is a checkbox. Cosmos replicates the data and the SDK routes reads to the nearest region.

The interesting decision is whether those regions can accept writes.

Single-region writesMulti-region writes
Writes go toOne primary regionAny region
Write latencyCross-region for distant usersLocal everywhere
ConflictsImpossiblePossible — you must handle them
Strong consistencyAvailableNot available
CostBaselineRoughly 2× RU
Write availability on region lossNeeds failoverContinues elsewhere
Remember this

Multi-region writes buy local write latency and write availability, and cost you conflict handling, Strong consistency, and roughly double the RU.

Single-region writes with multi-region reads is the more common and often better configuration — most applications read far more than they write, so you get local read latency without any of the conflict complexity.

Enabling multi-region writes because it sounds more capable is a real and common mistake.

Conflict resolution

PolicyBehaviourUse when
Last Writer Wins (default) Highest value of _ts, or a numeric property you nominate, wins Independent updates where losing one is acceptable
Custom (stored procedure) Your merge logic runs server-side You can genuinely merge — set union, additive counters
Custom (manual) Conflicts land in a conflicts feed for the application to resolve Conflicts need human or domain judgement
Last Writer Wins silently discards data

It's the default and it's the least safe. Two regions update the same item; the one with the later timestamp wins and the other update is gone — no error, no notification, nothing in a log by default.

For a user profile edit that's probably fine. For a shopping cart, one region's added item vanishes. For a balance or a counter, you've lost a transaction.

Worse, clock skew between regions means "later" isn't strictly reliable — _ts has second-level granularity, so simultaneous updates resolve arbitrarily.

If losing an update matters, don't use the default. Either nominate a version property you control, use a custom merge procedure, or take manual resolution and handle the conflicts feed.

Senior signal — design so conflicts can't happen

The strongest answer isn't a resolution policy, it's avoiding the situation.

Partition by region affinity. If a user's data is only ever written from their home region — which is usually true — two regions never write the same item and conflicts don't arise. That's free, and it makes the policy question moot for most of your data.

Model as append-only where you can. Two regions each inserting a new event document with distinct ids cannot conflict. Conflicts only happen on updates to the same item. So an event-sourced or ledger-style shape sidesteps the problem entirely, and you derive current state from the events.

"I'd design so the same item isn't written from two regions" is a much better answer than any conflict policy — because every policy is a choice about which data to lose or how much complexity to accept.

Failover 🔴 Advanced

MechanismDetail
Automatic failoverCosmos promotes the next region by your configured priority. No application change
Manual failoverYou trigger it. Used for testing and planned maintenance
Availability zonesZone-redundancy within a region. Costs more, protects against a datacentre failure
Failover priorityThe order regions are promoted. Configure deliberately
Automatic failover can lose recent writes

With single-region writes and anything short of Strong consistency, replication to other regions is asynchronous. So an unplanned regional failover can lose whatever hadn't replicated — typically a small window, but non-zero.

Bounded staleness is the level that gives you a stated guarantee on that window, which is why it exists. Strong eliminates it and costs 2× read RU plus cross-region write latency.

A planned manual failover is graceful and doesn't lose data — which is why it's worth using manual failover in a game day to test that your application handles a region change, rather than discovering the behaviour during a real incident.

new CosmosClientOptions
{
    // Preferred read regions, in order. The SDK fails over automatically
    // and routes reads to the first available.
    ApplicationPreferredRegions = new List<string>
    {
        Regions.WestEurope,
        Regions.NorthEurope
    }
}
Set the preferred region, always

Without ApplicationRegion or ApplicationPreferredRegions, the SDK uses the account's default write region — which may be on another continent from the compute.

That's a silent, permanent latency penalty on every read: a service in West Europe reading from an account whose primary is East US pays 80–100ms per read for no reason.

It's one line of configuration and it's frequently missing, because everything works — just slowly.

Key takeaways
  • The change feed is a persistent log, ordered within a logical partition only.
  • Deletes aren't in the default feed — soft delete plus TTL, or the all-versions mode.
  • Only the latest version appears, so it's state-change notification, not an event log.
  • The lease container gives automatic scale-out and resumption; provision it properly.
  • Parallelism is bounded by partition range count.
  • A different processor name gives an independent consumer.
  • At-least-once delivery — handlers must be idempotent.
  • The change feed removes the dual-write problem.
  • Multi-region writes cost conflict handling, Strong consistency and ~2× RU.
  • Last Writer Wins silently discards updates. Don't default into it.
  • Better: partition by region affinity, or model append-only, so conflicts can't occur.
  • Always set the preferred region on the client.

Common mistakes

  • Expecting deletes in the change feed, so derived stores grow forever.
  • Expecting every intermediate version when only the latest appears.
  • Non-idempotent change feed handlers.
  • An under-provisioned lease container, throttling the processor.
  • Duplicate instance names, so instances fight over leases.
  • Scaling consumers beyond the partition count and expecting more throughput.
  • Enabling multi-region writes without needing them, then hitting conflicts.
  • Leaving Last Writer Wins on data where losing an update matters.
  • Assuming Strong consistency works with multi-region writes.
  • Not setting the preferred region, paying cross-continent latency silently.
  • Never testing a failover.

Interview questions

Advanced / scenario

You need to maintain a search index and a summary view from a Cosmos container. How? ⭐ Senior-level
How I'd answer

"The change feed, with two independent processors — and that second point is the one people miss."

"A change feed consumer is identified by its processor name, and each name gets its own set of leases and its own position. So I'd run one processor called something like search-index and another called summary-view. They read the same feed completely independently — if the search indexer falls behind or fails, the summary view keeps going, and I can replay one without touching the other."

"Why the change feed rather than dual writes: with dual writes, the application writes to Cosmos and then to the search index, and if the second call fails they diverge silently with no recovery mechanism. It also puts the burden on every code path that writes, so one forgotten path is a permanent inconsistency. The change feed derives the event stream from the committed data — one write, nothing to keep in sync."

"Implementation details that matter."

"Idempotency is mandatory. Checkpointing happens after the handler returns, so a crash mid-batch redelivers the whole batch. For a search index that's naturally fine — indexing the same document twice is idempotent. For the summary view it depends: if it's an upsert of a computed projection, fine. If it's 'increment a counter', that will double-count on redelivery, so I'd either recompute from source rather than increment, or keep a processed-version marker on the summary document."

"Deletes need handling explicitly. This is the trap — the default change feed contains inserts and updates only, not deletes. So a search index built naively on it never removes anything and slowly fills with items that no longer exist. The fix is a soft delete: set isDeleted: true with a short TTL. The update appears in the feed so consumers can remove the entry, and TTL cleans up the item afterwards using spare RU. There's also an all-versions-and-deletes mode, with a shorter retention window."

"Provision the lease container. It's a real container consuming RU, and under-provisioning it throttles the processor — which presents as the consumer being inexplicably slow, and it's not an obvious place to look."

"Scale-out is bounded by partition ranges. The lease mechanism distributes work per partition range, so running 20 instances against 4 ranges leaves 16 idle. Worth knowing before concluding that more replicas will fix a backlog."

"Monitor lag. I'd track the gap between the newest change and the consumer's position, and alert on it — because a stalled consumer means the search index and summary quietly drift from reality, and nothing errors."

"For the summary view specifically, the payoff is worth naming: it turns an expensive cross-partition aggregate — which would cost hundreds of RU on every page load and get worse as partitions split — into a 1 RU point read. That's usually the strongest argument for building it at all."

"On hosting: Azure Functions with a Cosmos DB trigger is the least-code option and wraps the same processor. I'd use it unless I needed finer control over batching or error handling, in which case a hosted service with the processor builder directly. Either way I'd want a replay path — the ability to reset a lease and rebuild from the beginning — because schema changes to the index will need it."

What they're really checking
  • Do you know separate processor names give independent consumers?
  • Do you catch that deletes aren't in the feed?
  • Do you require idempotency and know which operations aren't?
  • Do you know the lease container needs throughput?
  • Do you monitor lag and plan for replay?
Weak answers
  • Red flag: dual writes from the application.
  • Red flag: one processor doing both jobs, coupling their failures.
  • Red flag: no plan for deletes.
Likely follow-ups
  • How would you rebuild the index from scratch?
  • How do you make a counter update idempotent?
  • What if ordering across partitions mattered?
Should you enable multi-region writes? ⭐ Senior-level
How I'd answer

"Usually no, and I'd want a specific reason — because it sounds like a straightforward upgrade and it changes the correctness model of the application."

"What you gain: local write latency everywhere, and write availability if a region is lost — no failover needed, other regions keep accepting writes."

"What you give up is more significant than people expect."

"Conflicts become possible, and you have to decide what happens. The default is Last Writer Wins, which is the least safe option: two regions update the same item, the later timestamp wins, and the other update is silently discarded — no error, nothing logged by default. For a profile edit that's tolerable. For a shopping cart, someone's added item vanishes. For a counter or balance, you've lost a transaction. And _ts has second-level granularity with clock skew between regions, so 'later' isn't strictly reliable for near-simultaneous updates."

"Strong consistency becomes unavailable. That's not a Cosmos limitation, it's CAP arithmetic — you can't have linearizability while independent regions accept writes without coordinating."

"Roughly double the RU cost."

"So the question I'd ask is: do users actually write from multiple regions? Most applications read far more than they write. Multi-region reads with single-region writes gets you local read latency — which is what users experience — with zero conflict complexity and normal cost. That's the configuration I'd default to, and it covers most global deployments."

"I'd enable multi-region writes when write latency is genuinely a product requirement for geographically distributed users, or when write availability during a full regional outage is a hard requirement — a system that must keep accepting orders even if a region is gone."

"And if I do enable it, the design work is making conflicts impossible rather than resolvable."

"Region affinity in the partitioning: if a user's data is only ever written from their home region — which is usually naturally true — two regions never write the same item, so conflicts don't arise regardless of the policy."

"Append-only modelling: conflicts only occur on updates to the same item. Two regions each inserting a new document with distinct ids cannot conflict. So an event or ledger shape, with current state derived from the entries, sidesteps the problem entirely — and that's often the right model for globally-distributed data anyway."

"Where I genuinely can't avoid concurrent updates to one item, I'd use a custom merge procedure if the data can be merged — set union, additive counters — or manual resolution with the conflicts feed if it needs domain judgement. What I wouldn't do is leave Last Writer Wins on data where losing an update matters, which is the common failure."

What they're really checking
  • Do you default to no, with reasons?
  • Do you know Last Writer Wins loses data silently?
  • Do you know Strong is unavailable, and why?
  • Do you distinguish multi-region reads from writes?
  • Do you design conflicts out rather than resolving them?
Weak answers
  • Red flag: "yes, for high availability" with no conflict discussion.
  • Red flag: not knowing conflicts are possible.
  • Red flag: assuming Strong consistency still works.
Likely follow-ups
  • Write a custom conflict resolution procedure.
  • How would you detect that conflicts are occurring?
  • What's the RPO on an unplanned regional failover?
