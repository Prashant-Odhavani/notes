Modelling, Cost & Comparisons

How to shape data for the RU model, how to keep the bill under control, and when something else is the better choice.

🔴 Advanced ⭐ Senior-level 💡 Good to know
Quick revision
  • Model for the access pattern, same as any document store — but here the cost is measured, so the incentive is sharper.
  • Denormalize aggressively. There are no cross-container joins at all.
  • Single-container design with a type discriminator is a legitimate and common pattern.
  • Keep documents small. RU scales with size on reads and writes.
  • 2 MB item limit, 20 GB per logical partition. Both hard.
  • Cost control = fewer RU per operation, not a smaller RU/s number.
  • Cosmos is usually more expensive than the alternatives. Know when it's worth it.

Modelling for the RU model 🔥 Must know

The one rule

Shape documents so that your most frequent operation is a point read — partition key plus id, ~1 RU.

Everything else is a compromise away from that.

DecisionGuidance
EmbedBounded, owned, read together. Same rules as MongoDB
ReferenceUnbounded or independently queried — but remember there's no join, so plan how you'll resolve it
DenormalizeMore aggressively than in MongoDB, because $lookup has no equivalent
Duplicate documentsStoring the same data twice under different partition keys is a legitimate technique
Keep items smallRU scales with bytes. A 100 KB read is ~10 RU, not 1
Senior signal — duplicating a document under two partition keys

In a relational database, storing the same row twice is a bug. Here it can be the correct design.

Suppose messages need to be read by conversation and by recipient. One partition key can't serve both — whichever you choose, the other access path is a cross-partition fan-out that gets worse as you grow.

So you write the message twice: once partitioned by conversationId, once by recipientId. Both reads are single-partition. The write costs 2× RU, and the change feed can maintain the second copy so the application only writes once.

The reasoning: reads are usually far more frequent than writes, so paying double on write to make every read cheap is normally the right trade. Being able to justify deliberate duplication — rather than treating it as something to avoid — is a genuine senior signal in any RU-billed or access-pattern-driven store.

When single-container is right

Use it when entity types share a partition key and are read together — a tenant's customers, orders and settings on one screen. It's also how you get a transactional batch across types, since those are scoped to a single logical partition.

Don't when types have genuinely different partition keys, very different indexing needs, or wildly different volumes — putting a high-volume telemetry stream in the same container as low-volume reference data means one indexing policy and one throughput allocation serving two incompatible workloads.

Watch the 20 GB implication: with /tenantId as the key, everything for a tenant shares that budget. A hierarchical key is usually the answer if that's a risk.

Transactional batch 🟡 Intermediate

var batch = container.CreateTransactionalBatch(new PartitionKey(tenantId));

batch.CreateItem(order);
foreach (var line in lines) batch.CreateItem(line);
batch.PatchItem(customer.Id, new[]
{
    PatchOperation.Increment("/orderCount", 1)
});

var response = await batch.ExecuteAsync();
if (!response.IsSuccessStatusCode)
{
    // The whole batch failed. Inspect per-operation results to find out why.
}
Remember this

Transactional batch is atomic within one logical partition only.

There is no cross-partition transaction in Cosmos — none, at any consistency level. So the partition key isn't just a performance decision, it's your transaction boundary.

That's a stronger constraint than MongoDB, which does have multi-document transactions across shards (slowly). If two things must change atomically in Cosmos, they must share a partition key — or you need a saga.

Batch limits

100 operations, 2 MB total. Beyond that you need multiple batches — which means you've lost atomicity across them, so design the unit of work to fit.

Also worth knowing: batch is atomic but not isolated from concurrent readers in the way a relational transaction is. It's a single-partition atomic operation, not a general transaction mechanism.

Reference data 🟡 Intermediate

ApproachUse when
Embed a copy in each documentSmall, rarely changes — a currency code, a country name
Duplicate into every partitionNeeded alongside partition data; keeps reads single-partition
Separate container + application cacheLarger reference sets read frequently. Cache in memory, refresh periodically
Integrated cacheHot reads at 0 RU without application caching
The pragmatic answer for lookup data

A container of a few hundred reference items read on every request is a waste of RU no matter how it's indexed.

Load it into memory at startup and refresh on a timer, or subscribe to its change feed to invalidate. That's zero RU per request and the data is typically stale by seconds at most, which for reference data is irrelevant.

Reaching for in-process caching before RU optimisation is often the bigger win, and it's easy to overlook when you're focused on the database.

Cost control ⭐ Senior-level

The framing that matters

Cost control in Cosmos means reducing RU per operation, not provisioning a smaller number.

Provisioning less than you need just moves the problem to throttling. The real lever is making each operation cheaper — then the same workload needs less throughput.

LeverImpactEffort
Point reads instead of queries1 RU vs 3–5+Low
Partition key in every queryAvoids × partition countLow
Tune the indexing policyDirectly cuts write RULow
Project fields, not SELECT *RU scales with bytesLow
TTL instead of delete jobsUses spare RU — freeLow
Autoscale below ~66% utilisationStops paying for idle headroomLow
Reserved capacity (1 or 3 years)Substantial discount on steady loadLow — a commitment, not a change
Integrated cacheRepeat reads at 0 RUMedium
Analytical store for reportingRemoves analytics from RU entirelyMedium
Change-feed-maintained read modelsExpensive query → 1 RU readHigh
Fix the partition keyEnds hot-partition throttlingHigh — container migration
Senior signal — reserved capacity is the forgotten lever

Everyone reaches for query tuning. Reserved capacity — committing to a baseline RU/s for one or three years — is a discount you get for signing a form, with no engineering work and no risk to correctness.

For a production workload with a predictable floor, that's usually the largest single saving available and the cheapest to obtain. You can still autoscale above the reserved baseline.

Mentioning it shows you think about cost as an engineering and commercial problem, which is exactly the framing a senior role expects.

Where the bill usually comes from

In my experience the unexpected costs are, in order: cross-partition queries that were fine at launch and got worse as partitions split; default indexing policies on write-heavy containers with large documents; analytics running against the transactional container; and over-provisioned autoscale maximums, where the 10% floor means you never pay less than a tenth of a number someone picked optimistically.

All four are invisible without logging RequestCharge — which is why that's the first thing to instrument.

Senior signal — the sharpest distinction between Cosmos and Mongo

People treat them as interchangeable document stores. Two differences matter in practice.

Cosmos has no cross-partition transactions at all. MongoDB does, since 4.2 for sharded clusters — slow, but available. So in Cosmos the partition key is your transaction boundary, and that's a much harder constraint on modelling. Anything that must change atomically has to share a partition key.

Cosmos has no cross-document join. MongoDB's $lookup is inefficient but it exists, so you can defer a modelling decision. In Cosmos there's no fallback, so denormalization isn't an optimisation — it's the only option, and the design has to be right earlier.

That's why "Cosmos requires knowing your access patterns up front, more than Mongo does" is the accurate framing, and it explains why the partition key decision carries so much weight.

Key takeaways
  • Shape data so the most frequent operation is a ~1 RU point read.
  • Denormalize more aggressively than in MongoDB — there's no join fallback.
  • Duplicating a document under two partition keys is a legitimate design, maintained by the change feed.
  • Single-container with a type discriminator is common and needs a type filter everywhere.
  • Transactional batch is atomic within one logical partition — that's your transaction boundary.
  • There are no cross-partition transactions at all.
  • Cache reference data in the application; RU per request for lookups is waste.
  • Cost control means fewer RU per operation, not a smaller provisioned number.
  • Reserved capacity is the largest zero-effort saving on steady load.
  • Cosmos is usually the most expensive option — justify it with global distribution and latency.

Common mistakes

  • Normalising as in SQL, then discovering there are no joins.
  • Refusing to duplicate data, so a key access path is a permanent fan-out.
  • Expecting cross-partition transactions.
  • Single-container design without a type filter on every query.
  • Large documents, paying RU on size for every read and write.
  • Reference lookups per request instead of an in-process cache.
  • Provisioning less RU/s as a cost fix, converting cost into throttling.
  • Never considering reserved capacity.
  • Choosing Cosmos for a single-region CRUD app.
  • Assuming Cosmos and MongoDB are interchangeable.

Interview questions

Advanced / scenario

Messages must be read by conversation and by recipient. How do you model that? ⭐ Senior-level
How I'd answer

"This is the classic two-access-path problem, and in Cosmos it can't be solved with indexing — because a secondary index still doesn't tell the router which partition to go to. So the answer is storing the message twice."

"One copy partitioned by conversationId, one by recipientId. Both reads become single-partition. If I picked only one key, the other access path would be a cross-partition fan-out — and crucially that would get worse over time as data grows and Cosmos splits into more physical partitions, with nothing in the code changing."

"I know duplicating data sounds wrong coming from a relational background. Here it's the correct design, and the justification is the read/write ratio: messages are read far more often than they're written. Paying 2× RU on write to make every read 1 RU is a good trade when reads outnumber writes by an order of magnitude — which for messaging they do."

"For keeping the copies consistent, I wouldn't have the application write both. I'd write the canonical copy — partitioned by conversationId, since that's the primary access path — and use the change feed to maintain the recipient-partitioned copy. That way there's one write from the application's perspective, no dual-write problem, and if the projection falls behind it catches up rather than diverging permanently."

"The change feed handler must be idempotent, which an upsert naturally is."

"Two design details I'd get right."

"The second copy can be a projection, not a full copy. The recipient view probably needs sender, preview text, timestamp and read status — not the full body. So it can be much smaller, which reduces both the storage and the RU cost of maintaining it. Only duplicate the fields that view needs."

"Deletes need handling. The change feed doesn't surface deletes by default, so a deleted message would persist in the recipient copy forever. Soft delete with a short TTL: the update appears in the feed so the projection can remove its copy, and TTL cleans up the original for free."

"I'd also consider the alternative: a single copy with a synthetic composite key, if one access path is much rarer. If reading by recipient is only used for a notifications screen loaded occasionally, a cross-partition query there might be acceptable and simpler than maintaining a projection. I'd want the actual call rates before committing to the duplication — it's real complexity, and worth it only if both paths are genuinely hot."

"And I'd note this is a case where DynamoDB would be more ergonomic — a Global Secondary Index does exactly this duplication for you, managed by the platform. In Cosmos you build it yourself with the change feed. Same pattern, more code."

What they're really checking
  • Are you comfortable duplicating data deliberately?
  • Do you justify it with the read/write ratio?
  • Do you use the change feed rather than dual writes?
  • Do you handle deletes?
  • Do you check whether both paths are actually hot?
Weak answers
  • Red flag: "add a secondary index" — it doesn't solve partition routing.
  • Red flag: accepting a cross-partition query on a hot path.
  • Red flag: dual writes from the application.
Likely follow-ups
  • What if a message is edited?
  • How would you detect the projection drifting?
  • How does DynamoDB's GSI differ from this?
Your Cosmos bill tripled in three months with no traffic increase. Investigate. ⭐ Senior-level
How I'd answer

"No traffic increase but tripled cost points at something that scales with data volume rather than request volume — and there's a specific mechanism for that in Cosmos."

"My leading hypothesis: cross-partition queries getting more expensive as partitions split. A cross-partition query costs roughly base × partition count. At launch with one physical partition it's indistinguishable from a targeted query. As data grows Cosmos splits — one partition becomes three, becomes eight — and that same unchanged query now costs eight times more and its latency is the slowest partition's. Nothing in the code changed, the traffic didn't change, and the bill tripled. That's exactly this signature."

"To confirm I'd log RequestCharge per operation type and compare against whatever baseline exists, and check the physical partition count over time in the metrics."

"Other candidates, in the order I'd check them."

"Autoscale maximum raised and never lowered. The floor is 10% of the maximum, so if someone bumped the max to 50,000 RU/s during an incident, the account now never bills below 5,000 RU/s even overnight. That's a very common cause and trivial to fix."

"Document size growth. RU scales with bytes. If documents are accumulating an array — an audit trail, an event history — then every read and write of them costs proportionally more over time. And with the default indexing policy, every property of every array element is indexed, so write cost grows too. That's two multipliers from one modelling problem."

"Data volume with no TTL. If nothing expires, storage grows and queries scan more. Adding TTL is cheap because expiry uses leftover RU rather than provisioned throughput."

"A new consumer nobody counted. A change feed processor, a reporting job, a dashboard, a data export — all consume RU from the same container budget. Worth checking what was deployed in that window."

"Multi-region or consistency changes. Adding a region multiplies cost. Enabling multi-region writes roughly doubles RU. Someone moving the account default to Strong doubles read RU. Any of those could have been a well-intentioned change with an unexamined bill impact."

"How I'd actually work it: Azure Cost Analysis broken down by container to see where the increase is, then RequestCharge logging on that container's operations to see which operations. Cost Analysis first, because it narrows the search from an account to a container in minutes."

"Then the fixes, cheapest first: lower the autoscale maximum if that's it; add the partition key to queries that can have it; tune the indexing policy; add TTL. If a genuinely cross-partition query is on a hot path, build a change-feed-maintained read model so it becomes a 1 RU point read."

"And I'd put monitoring in place so this doesn't recur silently — a budget alert on the account, plus tracking RU per operation type as a metric. The reason it went unnoticed for three months is that nothing was watching, and in Cosmos cost and performance are the same signal: the same query that tripled the bill is also on its way to throttling other features with 429s."

What they're really checking
  • Do you know cross-partition cost grows with partition count?
  • Do you know the autoscale 10% floor?
  • Do you connect document growth to both read and write cost?
  • Do you start from Cost Analysis rather than guessing?
  • Do you add monitoring so it doesn't recur?
Weak answers
  • Red flag: "reduce the provisioned RU/s" — converts cost into throttling.
  • Red flag: no systematic diagnosis.
  • Red flag: not knowing cost can rise with data volume alone.
Likely follow-ups
  • How do you attribute cost per tenant?
  • What would you alert on?
  • How do you migrate a container to a new partition key?
