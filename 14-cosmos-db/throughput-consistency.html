Throughput & Consistency

RU/s is the currency of Cosmos DB. Consistency is the one dial no other mainstream database exposes this explicitly.

🟡 Intermediate 🔴 Advanced 🔥 Must know
Quick revision
  • 1 RU ≈ a point read of a 1 KB item. Writes cost roughly 5× a read of the same item.
  • Exceeding provisioned RU/s gives HTTP 429, with a retry-after header.
  • The SDK retries 429s automatically. Don't write your own retry.
  • Provisioned for steady load, autoscale for spiky, serverless for intermittent and small.
  • Autoscale costs 1.5× per RU but scales 10:1, so it wins when utilisation is under ~66%.
  • Five consistency levels. Session is the default and usually correct.
  • Stronger consistency costs more RU on reads — consistency is billed.

Request Units 🔥 Must know

In simple terms

An RU is a normalised unit of work covering CPU, memory and IOPS together. Every operation has a measured RU cost, and you provision RU per second.

The reference point: a point read of a 1 KB item costs 1 RU. Everything else is relative to that.

OperationTypical costNote
Point read (pk + id), 1 KB1 RUThe cheapest possible read. Always prefer this
Point read, 100 KB~10 RUScales with item size
Create / replace, 1 KB~5 RUWrites maintain every indexed path

Patch (partial update)~5 RU, often lessCheaper than replace on large items

Cross-partition queryMultiplies by partition countThe main source of unexpected cost
COUNT(*) across partitionsCan be hundreds or thousandsScans everything
Stored procedureSum of its operations, plus overheadRarely worth it
The mental model

Writes cost about 5× reads, because every indexed path is maintained.

Which gives a Cosmos-specific optimisation with no equivalent elsewhere: excluding paths from the indexing policy directly reduces write cost. On a write-heavy container that's often the single biggest saving available.

Covered on the indexing page.

Every response tells you what it cost
var response = await container.ReadItemAsync<Order>(id, new PartitionKey(tenantId));
logger.LogInformation("{RU} RU", response.RequestCharge);

// Queries: accumulate across pages, since each page is charged
double total = 0;
using var iterator = container.GetItemQueryIterator<Order>(query);
while (iterator.HasMoreResults)
{
    var page = await iterator.ReadNextAsync();
    total += page.RequestCharge;
}

RequestCharge is the single most useful diagnostic in Cosmos. A lookup you expected to be 1 RU costing 200 RU means it's a cross-partition query — and nothing else in the response tells you that.

Note the query case: each page is charged separately, so a single logical query returning 1,000 items across 10 pages has 10 charges to add up. Measuring only the first page understates the cost badly.

Senior signal — the autoscale break-even

Autoscale costs 1.5× per RU but scales down to 10% of the maximum. So the arithmetic:

If average utilisation is below about 66%, autoscale is cheaper — you're paying 1.5× for the RU you use, but you're not paying for idle headroom. Above that, provisioned wins because the 1.5× premium exceeds what you'd save.

So the question isn't "is autoscale better?", it's "what's our average utilisation against peak?" A workload at a steady 80% should be provisioned. One that idles overnight and spikes during business hours should be autoscale.

Being able to state that break-even is a strong signal, because most people treat autoscale as either obviously good or obviously more expensive.

Two limits that catch people

Autoscale's floor is 10% of the maximum. Set the max to 20,000 RU/s and you never pay less than 2,000 RU/s, even at 3am with zero traffic. So an unnecessarily high maximum has a real, permanent cost.

Serverless is capped at 5,000 RU/s and one region. Excellent for dev/test and genuinely intermittent workloads, and it cannot be your production database if you need multi-region — which is the main reason to use Cosmos at all. Migrating from serverless to provisioned means a new account, not a setting change.

Throttling and 429s 🔥 Must know

What actually happens

Exceed your RU/s and Cosmos returns HTTP 429 Too Many Requests with a x-ms-retry-after-ms header telling you exactly how long to wait.

It's not an error condition in the usual sense — it's flow control. A small number of 429s is normal and means you're using the capacity you paid for.

new CosmosClientOptions
{
    // The SDK retries automatically, honouring retry-after
    MaxRetryAttemptsOnRateLimitedRequests = 9,
    MaxRetryWaitTimeOnRateLimitedRequests = TimeSpan.FromSeconds(30)
}

// Only if you need to react to exhausted retries
try { await container.CreateItemAsync(item, new PartitionKey(pk)); }
catch (CosmosException ex) when (ex.StatusCode == HttpStatusCode.TooManyRequests)
{
    // All retries used. Shed load, queue it, or surface backpressure.
    logger.LogWarning("Throttled after retries, retry-after {Ms}ms", ex.RetryAfter?.TotalMilliseconds);
}
Don't write your own retry loop

The SDK's retry respects the retry-after value the service supplies, which is calculated from actual capacity. A hand-rolled exponential backoff either waits too long (adding latency) or too little (adding load to a service that's already telling you to slow down).

Worse, a custom retry on top of the SDK's gives you multiplicative retries — 9 SDK attempts × 3 of yours is 27 requests for one logical operation, which turns a brief throttle into retry amplification.

Configure the SDK's limits and let it do the work.

Persistent 429s meanFix
Genuinely under-provisionedRaise RU/s, or switch to autoscale
A hot partitionFix the partition key. More RU/s won't help
Expensive queriesCross-partition fan-out, or missing index coverage
A bulk job competing with live trafficThrottle the job, or run it against a separate container
The diagnostic that distinguishes them

429s while overall RU consumption is low means a hot partition, not under-provisioning. Check Normalized RU Consumption per partition key range — if one is at 100% and the rest are near zero, adding throughput is money wasted.

429s with overall consumption near 100% means you're genuinely at capacity, and either the queries are too expensive or you need more RU/s.

Same symptom, opposite fixes. Getting this wrong is how teams end up paying for 10× the throughput they need while still being throttled.

The five consistency levels 🔥 Must know

LevelGuaranteeRead RULatency
Strong Always the latest committed write. Linearizable 2× Highest — waits for a quorum
Bounded staleness At most K versions or T seconds behind 2× High
Session (default) Read-your-own-writes within a session 1× Low
Consistent prefix Never see writes out of order; may be behind 1× Low
Eventual No ordering guarantee at all 1× Lowest
Remember this

Session is the default, and it's the right answer for most applications.

It gives read-your-own-writes — the guarantee users actually notice — at eventual-consistency cost and latency. That's the combination that matters: users care that their change appears, not that someone else's does instantly.

And note Strong and Bounded staleness cost 2× RU on reads. Consistency is literally billed here, which is unusual and worth knowing.

Think of it this way

Strong — everyone reads from the single master copy. Correct, and there's a queue.

Session — you always see your own edits immediately; other people's may take a moment to reach you.

Consistent prefix — you may be reading an older revision, but never a scrambled one: you'll never see chapter 3 before chapter 2.

Eventual — you get whichever copy is nearest, in whatever state it's in.

How Session consistency works 🔴 Advanced

The mechanism

Every write returns a session token. The SDK sends it with subsequent reads, and a replica that hasn't caught up to that token waits rather than returning stale data.

The token is held by the CosmosClient instance — which is why the client must be a singleton, and why session consistency silently breaks across process boundaries.

// Service A writes and captures the token
var response = await container.CreateItemAsync(order, new PartitionKey(tenantId));
string token = response.Headers.Session;

// Pass it to service B (header, message property, whatever the transport is)
// Service B supplies it, so its read is guaranteed to see the write
var read = await container.ReadItemAsync<Order>(
    order.Id, new PartitionKey(tenantId),
    new ItemRequestOptions { SessionToken = token });
The distributed read-your-own-writes gap

Session consistency is scoped to a client instance. So:

  • A new CosmosClient per request means a new session each time — no read-your-own-writes at all, and this is invisible until it isn't.
  • Two services have separate sessions. Service A writes, service B reads, and B can miss it.
  • Scaled-out instances behind a load balancer have separate sessions. The write hits instance 1 and the follow-up read hits instance 3, which never saw the token.

The fix is to propagate the session token explicitly, as above. That's the answer to "how do you guarantee read-your-own-writes across services?" — and most people don't know the token can be passed around, so they reach for Strong consistency instead and pay 2× RU plus latency for something Session already provides.

Choosing a level

RequirementLevel
General application dataSession
Financial balances, stock counts, anything you act on irreversiblyStrong — but note it constrains multi-region writes
Dashboards, analytics, feedsEventual — cheapest and fastest
Event or audit ordering matters, freshness doesn'tConsistent prefix
"No more than 5 seconds stale", with a guaranteeBounded staleness
Senior signal — the multi-region constraint on Strong

Strong consistency requires a write quorum across regions, so every write pays inter-region latency — potentially hundreds of milliseconds for geographically distant regions.

And it's incompatible with multi-region writes. You can have globally-distributed writes or Strong consistency, not both. That's not a Cosmos limitation so much as CAP arithmetic — you cannot have linearizability and independent regional write acceptance simultaneously.

So "we'll use Strong to be safe" quietly gives up the main reason you chose Cosmos. The better answer is Session globally, with Strong scoped to the specific operations that genuinely need it — the level is configurable per request, downwards from the account default.

Note the direction: a request can weaken consistency below the account default, never strengthen it. So the account default should be the strongest level any operation needs.

The analytical store is the answer to "reporting is eating our RU"

Azure Synapse Link maintains a column-oriented copy of your data, updated automatically from the change feed, billed on storage and scan — not RU.

So analytical queries stop competing with your transactional workload for throughput, which is otherwise one of the most common causes of production throttling.

It's a checkbox per container plus a small storage cost, and it's the structurally correct answer rather than trying to make aggregations cheap in RU. Same reasoning as keeping reporting off the OLTP primary.

Key takeaways
  • 1 RU = a 1 KB point read. Writes ≈ 5× because every indexed path is maintained.
  • Log RequestCharge — and accumulate it across query pages.
  • 429 is flow control with a retry-after. Let the SDK retry; never stack your own.
  • 429s at low overall utilisation mean a hot partition, not under-provisioning.
  • Autoscale is cheaper below ~66% average utilisation; its floor is 10% of max.
  • Serverless caps at 5,000 RU/s and one region.
  • Session is the default and gives read-your-own-writes at eventual-consistency cost.
  • Session is scoped to a client instance — propagate the token across services.
  • Strong and Bounded staleness cost 2× read RU.
  • Strong is incompatible with multi-region writes.
  • Consistency can be weakened per request, never strengthened.
  • Analytical store removes reporting from the RU budget.

Common mistakes

  • Custom retry logic on top of the SDK's, causing retry amplification.
  • Adding RU/s to fix a hot partition.
  • Never logging RequestCharge, so cost is invisible until the invoice.
  • Measuring only the first page of a query's RU cost.
  • Strong consistency "to be safe", doubling read cost and blocking multi-region writes.
  • A CosmosClient per request, silently losing session consistency.
  • Assuming session consistency spans services.
  • An unnecessarily high autoscale maximum, so the 10% floor is expensive.
  • Serverless for production, then discovering the region and RU caps.
  • Analytics against the transactional container.
  • Explicit delete jobs where TTL is free.

Interview questions

Intermediate

What happens when you exceed provisioned throughput? 🔥 Must know
How I'd answer

"Cosmos returns HTTP 429 with an x-ms-retry-after-ms header saying exactly how long to wait. That's the key difference from a relational database — you don't get a slow query, you get a rejected request."

"It's worth framing 429 as flow control rather than an error. A small number of them is normal and means you're actually using the capacity you're paying for. Zero 429s ever probably means you're over-provisioned."

"The SDK retries automatically, honouring the retry-after value, so most 429s never surface to application code. I'd configure MaxRetryAttemptsOnRateLimitedRequests and the wait time, and specifically not write my own retry — the service tells you how long to wait based on real capacity, which a generic exponential backoff can't know. And a custom retry layered on the SDK's gives multiplicative attempts: nine SDK retries times three of mine is 27 requests for one operation, which turns a brief throttle into retry amplification."

"If 429s are persistent, that's a real problem, and the diagnosis splits two ways."

"If overall RU consumption is near 100%, I'm genuinely at capacity — so either the queries are too expensive or I need more throughput."

"If overall consumption is low but I'm still throttled, that's a hot partition. Provisioned RU/s are divided evenly across physical partitions, so with 30,000 RU/s across three partitions each gets 10,000. One hot partition-key value throttles at 10,000 while 20,000 sits unused. Adding RU/s does not help — it adds capacity to partitions that weren't busy. I'd check Normalized RU Consumption per partition key range to confirm, because overall averages hide it entirely."

"Getting that distinction wrong is how teams end up paying for ten times the throughput they need and still being throttled."

"Other common causes: expensive cross-partition queries, or a bulk import competing with live traffic — for that I'd throttle the job or run it against a separate container so it can't starve user requests."

"And on handling exhausted retries in the application: at that point I'd shed load or apply backpressure rather than failing the user request outright — queue the write if it can be asynchronous, or return a clear 503 with a retry-after of my own so callers behave sensibly."

What they're really checking
  • Do you know it's 429 with a retry-after, not a slowdown?
  • Do you know the SDK handles it and yours shouldn't?
  • Can you distinguish under-provisioning from a hot partition?
  • Do you know adding RU/s doesn't fix a hot partition?
Likely follow-ups
  • How would you find the hot partition?
  • Provisioned or autoscale for a spiky workload?
  • How do you stop a bulk job throttling live traffic?

Advanced / scenario

Which consistency level would you choose, and why? ⭐ Senior-level
How I'd answer

"Session as the account default, and I'd weaken or strengthen specific operations from there. That's usually the right answer and I'd explain why rather than just naming it."

"Session gives read-your-own-writes, which is the guarantee users actually notice. Someone updates their profile and immediately sees the new value. They genuinely don't care whether another user's change from 200ms ago has propagated. And it costs the same read RU as Eventual — 1×, whereas Strong and Bounded staleness are 2×. So you get the guarantee that matters at the cheaper price point."

"The mechanism is worth knowing because it has a sharp edge: every write returns a session token, and the SDK sends it with subsequent reads so a replica that hasn't caught up waits rather than returning stale data. But that token lives on the CosmosClient instance."

"Which means session consistency silently breaks in three situations. If you create a client per request, there's no shared session at all. If two services are involved, service A writes and service B can miss it. And if you're scaled out, the write hits instance 1 while the follow-up read hits instance 3, which never saw the token."

"The fix most people don't know: you can propagate the session token explicitly — capture it from the write response, pass it in a header or a message property, and supply it via ItemRequestOptions.SessionToken on the read. That gives cross-service read-your-own-writes without upgrading consistency. A lot of teams reach for Strong instead and pay double RU plus latency for something Session already provides."

"Where I'd go stronger: operations I act on irreversibly. A balance check before a transfer, a stock count before dispatch. There I'd use Strong on that specific read, because acting on stale data has real consequences."

"But I'd flag the cost properly: Strong requires a write quorum across regions, so every write pays inter-region latency — and it's incompatible with multi-region writes entirely. That's CAP arithmetic, not a Cosmos quirk. So 'we'll use Strong to be safe' quietly gives up the main reason you chose Cosmos in the first place."

"Where I'd go weaker: dashboards, analytics, activity feeds, search results — Eventual, cheapest and lowest latency. And Consistent prefix for anything where ordering matters but freshness doesn't, like an audit trail: you may be a little behind, but you'll never see events out of order."

"Bounded staleness I'd use when there's an actual stated requirement — 'no more than five seconds stale' — because it's the only level that gives you a guarantee you can put in a contract."

"One directional detail: consistency can be weakened per request but never strengthened above the account default. So the account default has to be the strongest level any operation needs, and everything else relaxes from there. That's the opposite of what people assume and it affects how you set the default."

What they're really checking
  • Do you default to Session and know why it's the right trade?
  • Do you know Strong and Bounded cost 2× read RU?
  • Do you know session tokens are per client, and can be propagated?
  • Do you know Strong blocks multi-region writes?
  • Do you know consistency can only be weakened per request?
Weak answers
  • Red flag: "Strong, to be safe" with no cost awareness.
  • Red flag: "Eventual, it's a NoSQL database."
  • Red flag: not knowing Session is the default.
Likely follow-ups
  • How do you get read-your-own-writes across two services?
  • What breaks if you enable multi-region writes?
  • How does Bounded staleness differ from Eventual in practice?
