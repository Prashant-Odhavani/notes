Azure Cosmos DB

Two decisions determine whether a Cosmos project succeeds: the partition key and the RU budget. Almost everything else is detail.

🟡 Intermediate ⭐ Senior-level

What makes it different 🔥 Must know

In simple terms

Cosmos DB is a globally-distributed, horizontally-partitioned database where you pay for throughput, not for queries.

Every operation costs a measured number of Request Units. You provision RU/s per second. Exceed it and you get throttled — HTTP 429 — not a slow query.

The mental shift from SQL Server

In SQL Server, an inefficient query is slow.

In Cosmos DB, an inefficient query is expensive — and once you hit your provisioned limit, it throttles everything else too.

So cost and performance are the same conversation here. A badly-designed query doesn't just perform poorly, it shows up on the invoice and can take down unrelated features.

Senior signal — the indexing default is backwards, deliberately

Every other database indexes nothing until you ask. Cosmos indexes every property by default.

That's a sensible default for a system where you may not know the query patterns yet — reads are never accidentally catastrophic. But it means writes cost more RU than they need to, because every indexed path is maintained on every write.

So on a write-heavy container, tuning the indexing policy to exclude paths you never filter on is a direct, measurable cost reduction. That's a Cosmos-specific optimisation with no equivalent elsewhere, and a good thing to raise.

The two decisions that matter 🔥 Must know

DecisionGet it wrong and
Partition key Hot partitions throttle while the rest idles, queries fan out across every partition, and a single logical partition hits its 20 GB ceiling. Changing it means migrating the container.
Throughput model Either you over-provision and pay for idle capacity, or you under-provision and get throttled under load
The partition key is effectively permanent

You cannot change a container's partition key. The fix is creating a new container and migrating every item — which means dual writes, a backfill, and a cutover.

MongoDB added reshardCollection in 5.0; Cosmos has no equivalent. So the partition key genuinely is a design-time decision you have to get right, and it deserves proportionate attention up front.

The Mongo API is a compatibility layer, not MongoDB

It speaks the MongoDB wire protocol, so existing drivers and tools connect. Underneath it's Cosmos — so you get Cosmos partitioning, RU billing and consistency levels, not Mongo's.

Practical consequences: feature coverage lags real MongoDB, some aggregation stages and operators are unsupported, and performance characteristics differ because the RU model is doing the work underneath.

It's a migration path, not a destination. For new development, use the NoSQL API — you get the change feed, the full SDK, and features as they ship. Choosing the Mongo API for a greenfield project is a decision worth questioning.

When Cosmos is the right choice ⭐ Senior-level

Good fitPoor fit
Global, multi-region with low latency everywhere — this is the genuine differentiator Relational data with complex ad-hoc queries — use SQL
Predictable, key-based access at very high scale Unknown or changing query patterns — the partition key locks you in
Guaranteed single-digit-millisecond reads backed by an SLA Reporting and analytics — expensive per RU; use the analytical store or a warehouse
Serverless / event-driven — pairs naturally with Functions and the change feed Cost-sensitive small workloads — a small SQL database or Postgres is cheaper
Spiky traffic with autoscale or serverless Heavy cross-partition aggregation
Senior signal — the honest cost position

Cosmos is frequently more expensive than a relational database for the same workload, and the difference is often large.

What you're paying for is global distribution, guaranteed latency and elastic scale. If you need those, it's excellent value. If you have one region and moderate traffic, you're paying for capabilities you aren't using — and Azure SQL or Postgres Flexible Server will cost a fraction.

"We chose Cosmos because it scales" is a weak answer. "We chose Cosmos because we serve users in four regions and need sub-20ms reads in all of them, and we accept the RU cost for that" is a strong one.

The reverse is equally valid: recommending against Cosmos for a single-region CRUD application is usually the correct senior call.

The .NET side 🟡 Intermediate

// Singleton - the client owns connections and caches routing metadata
builder.Services.AddSingleton(_ => new CosmosClient(
    connectionString,
    new CosmosClientOptions
    {
        // Direct mode over TCP: lower latency than Gateway. The default for the SDK.
        ConnectionMode      = ConnectionMode.Direct,
        ApplicationRegion   = Regions.WestEurope,   // read from the nearest region
        // Let the SDK handle 429s; it respects the retry-after header
        MaxRetryAttemptsOnRateLimitedRequests = 9,
        MaxRetryWaitTimeOnRateLimitedRequests = TimeSpan.FromSeconds(30),
        SerializerOptions   = new CosmosSerializationOptions
        {
            PropertyNamingPolicy = CosmosPropertyNamingPolicy.CamelCase
        }
    }));
DetailWhy
CosmosClient as a singletonIt caches partition routing metadata and pools connections. Per-request creation is slow and exhausts sockets
ConnectionMode.DirectTCP straight to the partition. Gateway mode is HTTPS via a proxy — needed behind restrictive firewalls, slower
ApplicationRegionReads go to the nearest region. Getting this wrong means cross-continent latency on every read
SDK retry on 429Built in and respects retry-after. Don't write your own
Always check RequestChargeEvery response carries its RU cost. This is your primary diagnostic
Log the RU charge in development
var response = await container.ReadItemAsync<Order>(id, new PartitionKey(tenantId));
logger.LogInformation("Read {Id} cost {RU} RU", id, response.RequestCharge);

This is the Cosmos equivalent of logging EF Core's SQL — and arguably more important, because RU charge is both the performance signal and the cost signal.

A point read is ~1 RU. If a lookup is costing 200 RU, it's doing a cross-partition query and you'd never know from the response itself.

Why would you choose Cosmos DB over Azure SQL? 🔥 Must know
How I'd answer

"I'd want a specific reason, because for a typical business application my default is still Azure SQL — it's cheaper, the team probably knows it, and relational constraints do real work."

"The genuine reasons to pick Cosmos:"

"Multi-region with low latency everywhere. This is the real differentiator. Adding a region is a checkbox, and reads are served locally with an SLA on latency. Doing that with Azure SQL means geo-replication with a read-only secondary and considerably more engineering — and you don't get multi-region writes at all."

"Guaranteed latency at scale. Cosmos has an SLA on latency, throughput and consistency, not just availability. For a system where p99 read latency is a product requirement, that's meaningful."

"Elastic, spiky throughput. Autoscale or serverless handles traffic that varies by an order of magnitude without provisioning for peak."

"Predictable key-based access at very high volume — session stores, device state, user profiles, event ingestion."

"Where I'd stay with Azure SQL: relational data with ad-hoc queries, because Cosmos charges per RU and cross-partition aggregation is expensive. Multi-entity invariants — 'total allocations must not exceed budget' is a constraint SQL enforces and Cosmos can't. Reporting. And anything where the query patterns aren't settled yet, because the partition key is effectively permanent — there's no resharding, so changing it means migrating the container."

"On cost I'd be direct: Cosmos is usually more expensive for the same workload, often substantially. You're paying for global distribution, guaranteed latency and elastic scale. If you need those it's good value; if you're single-region with moderate traffic you're paying for capabilities you aren't using."

"So 'we chose Cosmos because it scales' is a weak justification. 'We serve users in four regions and need sub-20ms reads in all of them' is a real one. And honestly, recommending against Cosmos for a single-region CRUD app is usually the right call — that's the answer I'd expect a senior engineer to be comfortable giving."

"One thing worth adding: they're not mutually exclusive. A common shape is Azure SQL for transactional core data and Cosmos for a globally-distributed read surface, session state or event ingestion — kept in sync with the change feed."

What they're really checking
  • Do you know global distribution is the actual differentiator?
  • Are you honest about cost?
  • Do you know the partition key is permanent?
  • Would you recommend against it when appropriate?
Weak answers
  • Red flag: "it's NoSQL so it scales better" with no mechanism.
  • Red flag: "it's schemaless so we can move faster."
  • Red flag: no awareness of the cost model.
Likely follow-ups
  • What's a Request Unit?
  • How would you pick a partition key?
  • What happens when you exceed provisioned throughput?
