Architecture & Partitioning

The most important page in this section. The partition key can't be changed, and it determines cost, latency and scale ceiling.

🟡 Intermediate 🔴 Advanced 🔥 Must know
Quick revision
  • Logical partition = all items sharing one partition-key value. Hard limit 20 GB and 10,000 RU/s.
  • Physical partition = the actual storage/compute unit. Cosmos manages these; you never see them directly.
  • A point read (partition key + id) is ~1 RU. Everything else costs more.
  • Queries without the partition key fan out across every physical partition.
  • Hot partition = one key value taking disproportionate traffic. It throttles while the rest idles.
  • Synthetic keys combine fields to raise cardinality.
  • Hierarchical keys (up to 3 levels) solve the 20 GB problem without losing routing.

The resource hierarchy 🟢 Beginner

LevelWhat it is
AccountThe billing and global-distribution boundary. Regions are configured here
DatabaseA namespace. Can hold shared throughput for its containers
ContainerThe unit that matters. Has a partition key, an indexing policy and throughput. Equivalent to a table or collection
ItemA JSON document. Max 2 MB
Container throughput vs database throughput

Container-level throughput is dedicated — that container's RU/s are guaranteed and isolated.

Database-level (shared) throughput is pooled across all containers in the database. Cheaper when you have many small containers, and it means one busy container can starve the others — the noisy-neighbour problem, same as an elastic pool.

Practical rule: shared throughput for many low-traffic containers, dedicated for anything with meaningful or unpredictable load.

Logical vs physical partitions 🔥 Must know

In simple terms

A logical partition is all the items that share one partition-key value. If the key is tenantId, then everything for tenant-acme is one logical partition.

A physical partition is real storage and compute. Cosmos assigns logical partitions to physical ones by hashing the key, and splits physical partitions automatically as data grows.

Logical partitionPhysical partition
Defined byYour partition-key valueCosmos, automatically
Storage limit20 GB — hard50 GB
Throughput limit10,000 RU/s10,000 RU/s
Can be splitNoYes, automatically
You control itYesNo
The 20 GB limit is the one that ends projects

A logical partition cannot be split. All items with the same partition-key value must fit in 20 GB, on one physical partition.

So if you partition orders by tenantId and one tenant grows past 20 GB, writes for that tenant start failing. Not slowing — failing. And you can't fix it by adding throughput or scaling anything, because the constraint is per logical partition.

The only fixes are migrating to a new container with a different key, or having chosen a hierarchical key up front.

This is why "will any single key value exceed 20 GB in the lifetime of this system?" is the first question to ask about a partition key — before distribution, before query routing.

How throughput is actually divided

Provisioned RU/s are split evenly across physical partitions. With 30,000 RU/s across 3 physical partitions, each gets 10,000.

Which means a hot partition throttles at 10,000 RU/s even though you provisioned 30,000. The other 20,000 are sitting on partitions with no traffic.

That's the mechanism behind hot partitions, and it's why people are baffled to see 429s while the portal shows overall RU consumption at 35%. Knowing this explains the symptom.

Choosing a partition key 🔥 Must know

Four requirements, in priority order
  1. No single value can approach 20 GB. A hard failure, so it comes first.
  2. High cardinality — many distinct values, so data and traffic spread.
  3. Even access distribution — no value taking a disproportionate share of requests.
  4. Present in your queries — otherwise every read fans out across all partitions.

Requirements 2 and 4 often pull in opposite directions. Resolving that tension is the design work.

CandidateVerdict
/id Maximum distribution, and every query that isn't a point read fans out. Good for pure key-value access
/tenantId Good if tenants are small and numerous. Dangerous with a few large tenants — 20 GB and hot-partition risk
/userId Usually good — high cardinality, naturally bounded per user, and in most queries
/country Bad. Low cardinality and hugely uneven
/status Bad. A handful of values, and items move between partitions as status changes
/date Bad for writes — today's partition takes every write while historical ones idle
/deviceId Good for telemetry — high cardinality, and queries are usually per device
A partition key value is immutable

You cannot update an item's partition-key value. Changing it means delete and re-insert, which isn't atomic across partitions.

So never partition by something that changes — status, assignedTo, currentStage. A workflow item that moves through states would have to be deleted and recreated on every transition, and a failure between the two loses it.

Partition by something intrinsic and permanent: which tenant it belongs to, which user, which device.

Synthetic partition keys ⭐ Senior-level

The problem they solve

Sometimes no single field works. tenantId has too few distinct values and some tenants are huge; id distributes perfectly but makes every query fan out.

A synthetic key is a field you compute and store, combining values to get the cardinality you need while keeping routing.

public class TelemetryItem
{
    [JsonPropertyName("id")]
    public string Id { get; set; } = Guid.NewGuid().ToString();

    public string TenantId { get; set; } = null!;
    public DateTime Timestamp { get; set; }

    // Stored synthetic key: "acme-2024-06"
    // Bounds each logical partition to one tenant-month, and queries for a
    // tenant's data in a known month stay single-partition.
    [JsonPropertyName("pk")]
    public string PartitionKey => $"{TenantId}-{Timestamp:yyyy-MM}";
}
StrategyExampleGets you
Concatenate fieldstenantId + "-" + categoryHigher cardinality, still routable if both are known
Add a time buckettenantId + "-" + yyyyMMBounds partition growth — the 20 GB fix
Add a random suffixtenantId + "-" + rand(0..9)Spreads a hot key across 10 partitions — but reads now fan out to all 10
Hash suffix from the idtenantId + "-" + (hash(id) % 10)Same spread, and deterministic so a point read still works
Senior signal — deterministic beats random suffixes

The random-suffix trick is widely cited and has a real flaw: once the suffix is random, you can no longer compute an item's partition key from its identity. So a point read becomes a fan-out query across all N suffixes — you've traded a 1 RU read for an N-partition query.

Deriving the suffix deterministically from the item's own id — hash(id) % 10 — gives the same write distribution while keeping point reads at 1 RU, because the reader can recompute the same suffix.

Making that distinction unprompted is a strong signal, because it shows you're thinking about the read path rather than just fixing the hot partition.

Hierarchical partition keys ⭐ Senior-level

In simple terms

Cosmos supports up to three levels of partition key — /tenantId, /userId, /sessionId.

The 20 GB limit then applies to the full key combination, not the first level. So one tenant can hold far more than 20 GB in total, as long as no single tenant-user-session combination does.

await database.CreateContainerIfNotExistsAsync(new ContainerProperties
{
    Id = "events",
    PartitionKeyPaths = new List<string> { "/tenantId", "/userId", "/sessionId" }
});

// Full key: a point-read-class single-partition operation
var pk = new PartitionKeyBuilder()
    .Add(tenantId).Add(userId).Add(sessionId)
    .Build();

// PREFIX key: routed to the subset of partitions holding that tenant's data,
// NOT a full fan-out across the container
var prefix = new PartitionKeyBuilder().Add(tenantId).Build();
var query = container.GetItemQueryIterator<Event>(
    "SELECT * FROM c WHERE c.type = 'login'",
    requestOptions: new QueryRequestOptions { PartitionKey = prefix });
Senior signal — this resolves the multi-tenant dilemma

The classic bind: partition by tenantId and queries route beautifully, but a large tenant hits 20 GB. Partition by id and it scales forever, but every tenant query fans out.

A hierarchical key /tenantId/userId gets both. The limit applies per tenant-user combination so a tenant can be terabytes; and because tenantId is the prefix, a tenant-scoped query is routed to just that tenant's partitions rather than the whole container.

This is the current best answer to "how would you model multi-tenant data in Cosmos?", and a lot of material predates it — so knowing it exists is genuinely differentiating.

The constraint: you must query by a prefix, left to right. Querying by userId alone still fans out, because it isn't a prefix of the key.

Hot partitions 🔥 Must know

Think of it this way

Ten supermarket checkouts, and everyone queues at one of them.

You've paid for ten. Throughput is one checkout's worth. The other nine stand idle while customers complain about the wait.

SymptomWhat it means
429s while overall RU usage is lowThe classic hot-partition signature. One partition is at its share of the limit
Uneven Normalized RU Consumption in metricsThe direct measurement. Look for one partition near 100%
Storage skew across partitionsHot from a data-volume perspective; heading for 20 GB
Remember this

Throughput is divided evenly across physical partitions, regardless of where the traffic goes.

So 100,000 RU/s across 10 physical partitions means each gets 10,000. A single hot key throttles at 10,000 while 90,000 goes unused.

Adding RU/s does not fix a hot partition — it just adds capacity to partitions that weren't busy. This is the single most common Cosmos misunderstanding.

Item ids and uniqueness 🟡 Intermediate

RuleDetail
id is unique per logical partitionNot container-wide. Two partitions can hold the same id
A point read needs bothPartition key and id. That's the ~1 RU operation
Unique keysEnforce uniqueness on other fields — also scoped to the logical partition
id must be a stringMax 1023 bytes, and can't contain /, \, #, ?
There is no global uniqueness

Both id and unique-key constraints are enforced within a logical partition only.

So "email must be unique across all users" is not enforceable unless email is the partition key. If you partition by tenantId, you get uniqueness per tenant — which may be exactly right for a B2B product, and is wrong if you needed it globally.

The workaround is a separate container partitioned by the value you need unique, holding a reservation item you insert first. That's more moving parts, so it's worth checking whether per-tenant uniqueness actually satisfies the requirement before building it.

TTL 💡 Good to know

// Container default: -1 means "TTL enabled but no default expiry"
var props = new ContainerProperties("events", "/tenantId")
{
    DefaultTimeToLive = -1
};

// Per-item override, in seconds
public class Event
{
    [JsonPropertyName("ttl")]
    public int? TimeToLive { get; set; } = 60 * 60 * 24 * 30;   // 30 days
}
TTL deletes are cheap, and that matters

TTL deletion uses leftover RU rather than your provisioned budget. So expiring old data is effectively free, whereas issuing millions of explicit deletes would cost real RU and could throttle live traffic.

That makes TTL the right answer for event data, sessions, caches and audit logs — set it at write time and never write a cleanup job.

Two caveats: deletion is best-effort, so it may lag under sustained load; and setting the container default to -1 rather than a number is what enables per-item control, which is the form you usually want.

Key takeaways
  • Logical partition = one partition-key value. 20 GB and 10,000 RU/s, both hard, and it can't be split.
  • Throughput divides evenly across physical partitions, so a hot key throttles below your provisioned total.
  • Adding RU/s does not fix a hot partition.
  • Partition-key priority: 20 GB safety, cardinality, even access, then query routing.
  • Never partition on a mutable field — key values are immutable.
  • Synthetic keys raise cardinality; derive suffixes deterministically to keep point reads.
  • Hierarchical keys apply the 20 GB limit to the full combination and route on prefixes — the multi-tenant answer.
  • id and unique keys are scoped to the logical partition. No global uniqueness.
  • A point read needs partition key plus id, and costs ~1 RU.
  • TTL uses spare RU, so expiry is effectively free.

Common mistakes

  • Partitioning by a low-cardinality field such as status, type or country.
  • Partitioning by a mutable field, requiring delete-and-recreate on change.
  • Not asking whether any key value could reach 20 GB.
  • Adding RU/s to fix a hot partition.
  • Random synthetic suffixes, destroying point reads.
  • Assuming id is globally unique.
  • Assuming a unique key is container-wide.
  • Partitioning by date, so all writes hit one partition.
  • Not knowing hierarchical keys exist and choosing between routing and scale.
  • Explicit delete jobs where TTL would be free.

Interview questions

Intermediate

What's the difference between a logical and a physical partition? 🔥 Must know
How I'd answer

"A logical partition is all the items sharing one partition-key value — so if the key is tenantId, everything for tenant-acme is one logical partition. That's defined by my data and my key choice."

"A physical partition is actual storage and compute. Cosmos hashes partition-key values to assign logical partitions to physical ones, and splits physical partitions automatically as data or throughput grows. I don't control or see them directly."

"The distinction matters because of where the limits sit."

"A logical partition has a hard 20 GB limit and cannot be split. All items with the same key value must fit on one physical partition. So if one tenant grows past 20 GB, writes for that tenant start failing — not slowing, failing — and no amount of scaling fixes it, because the constraint is per logical partition. The only remedies are migrating to a new container with a different key, or having chosen a hierarchical key up front."

"The throughput consequence is the one that confuses people most. Provisioned RU/s are divided evenly across physical partitions. So with 30,000 RU/s across three physical partitions, each gets 10,000. If one partition-key value takes most of the traffic, it throttles at 10,000 while 20,000 RU/s sits unused on quiet partitions."

"That's why you can see 429s in production while the portal shows overall RU consumption at 35% — which looks like a bug until you know how throughput is allocated. And it's why adding RU/s doesn't fix a hot partition: you're adding capacity to partitions that weren't busy."

"For diagnosis I'd look at Normalized RU Consumption per partition key range in Azure Monitor. Overall averages hide this completely; per-partition is where you see one at 100% and the rest near zero."

What they're really checking
  • Do you know the 20 GB limit is per logical partition and unsplittable?
  • Do you know throughput divides evenly across physical partitions?
  • Can you explain 429s at low overall utilisation?
  • Do you know which metric to look at?
Likely follow-ups
  • What happens when a logical partition reaches 20 GB?
  • How do you fix a hot partition?
  • How would you change a partition key on a live container?

Advanced / scenario

Design the partition key for a multi-tenant SaaS where tenants range from 10 users to 50,000. ⭐ Senior-level
How I'd answer

"The tenant size range is the whole problem, so I'd start there. Uniform tenants would make tenantId the obvious answer; a 5,000-times spread means the obvious answer breaks at the top end."

"Let me rule out the two simple options first, because each fails in an instructive way."

"/tenantId alone routes queries perfectly — nearly every query in a SaaS is already tenant-scoped, so every read would be single-partition. But a 50,000-user tenant will exceed the 20 GB logical partition limit, and at that point writes for my largest and most valuable customer start failing. It's also a hot-partition risk: that tenant is capped at 10,000 RU/s regardless of what I provision overall."

"/id distributes perfectly and scales forever, and every tenant-scoped query becomes a cross-partition fan-out. That's expensive in RU and the latency becomes the slowest partition's. I'd have solved scale by making the common case bad."

"So my answer is a hierarchical partition key: /tenantId/userId."

"That resolves both. The 20 GB limit applies to the full combination, so a tenant can hold terabytes as long as no single tenant-user pair exceeds 20 GB — which for per-user data is a comfortable bound. And because tenantId is the prefix, a tenant-scoped query is routed to just that tenant's partitions rather than the entire container. Per-user queries supply the full key and are effectively single-partition."

"The constraint I'd state: queries must use a left-to-right prefix. Querying by userId alone still fans out, because that isn't a prefix. So I'd want to confirm the access patterns are tenant-first — in a SaaS they almost always are, since you need tenant scoping for data isolation anyway."

"Two additions I'd make."

"Consider giving the very largest tenants their own container. If one tenant is 40% of the data and traffic, a dedicated container with its own provisioned throughput isolates them — both so they can't throttle everyone else, and so their cost is attributable. That's a routing lookup in the application, and it's the same reasoning as graduating a tenant out of an elastic pool."

"Enforce tenant scoping structurally. Every query must include the tenant, and because it's the partition key that's both a correctness requirement and a performance one — a query missing it is simultaneously a cross-tenant data leak and a fan-out. I'd centralise that in the repository layer so a single query can't omit it."

"One thing I'd flag as a limitation: unique keys are scoped to the logical partition. So 'email must be unique' means unique per tenant-user combination here, which is almost certainly not what's wanted. If global email uniqueness is a requirement, that needs a separate container partitioned by email holding reservation items. Worth surfacing early, because it's the kind of requirement that appears late and is awkward to retrofit."

"And I'd say plainly: get this right now. Cosmos has no resharding — unlike MongoDB 5.0 — so changing the partition key means a new container, dual writes, a backfill and a cutover. It's worth spending real time on this decision at design time."

What they're really checking
  • Do you identify tenant size variance as the core problem?
  • Do you know why both simple options fail?
  • Do you know hierarchical partition keys?
  • Do you know the prefix constraint?
  • Do you consider isolating the largest tenants?
  • Do you catch the uniqueness scoping issue?
Weak answers
  • Red flag: /tenantId with no mention of 20 GB.
  • Red flag: /id with no mention of fan-out cost.
  • Red flag: "we can change it later."
Likely follow-ups
  • How would you migrate if you did get it wrong?
  • How do you enforce global email uniqueness?
  • What if queries were mostly per-user rather than per-tenant?
