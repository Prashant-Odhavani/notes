Indexing & Query Execution

Cosmos indexes everything by default, which makes reads safe and writes expensive. Tuning that is a direct cost saving.

🟡 Intermediate 🔴 Advanced 🔥 Must know
Quick revision
  • Everything is indexed by default. Safe reads, expensive writes.
  • Excluding unqueried paths reduces write RU — the main Cosmos-specific optimisation.
  • A point read is ~1 RU; the same item fetched by query costs several times more.
  • Composite indexes are needed for multi-property ORDER BY.
  • Cross-partition queries fan out and multiply RU by partition count.
  • Continuation tokens, not OFFSET. Offset still reads what it skips.
  • SELECT * costs more — RU scales with returned bytes.

Point reads vs queries 🔥 Must know

// POINT READ - ~1 RU. Direct lookup by partition key + id.
var order = await container.ReadItemAsync<Order>(
    id: "order-123",
    partitionKey: new PartitionKey("tenant-acme"));

// QUERY for the same item - ~3-5 RU. Goes through the query engine.
var query = new QueryDefinition("SELECT * FROM c WHERE c.id = @id")
    .WithParameter("@id", "order-123");
var iterator = container.GetItemQueryIterator<Order>(query,
    requestOptions: new QueryRequestOptions { PartitionKey = new PartitionKey("tenant-acme") });
Remember this

If you know the partition key and the id, use ReadItemAsync.

A point read bypasses the query engine entirely — it's a direct key lookup. Same result, a fraction of the RU, and lower latency.

Querying by id is one of the most common avoidable costs in Cosmos codebases, because the query version looks more familiar to anyone coming from SQL.

Cross-partition queries 🔥 Must know

// TARGETED - one partition
var iterator = container.GetItemQueryIterator<Order>(
    new QueryDefinition("SELECT * FROM c WHERE c.status = @s").WithParameter("@s", "open"),
    requestOptions: new QueryRequestOptions
    {
        PartitionKey = new PartitionKey(tenantId)      // this is the important line
    });
// No PartitionKey supplied and no partition key in the WHERE clause
var iterator = container.GetItemQueryIterator<Order>(
    new QueryDefinition("SELECT * FROM c WHERE c.status = 'open'"));
// RU cost multiplies by partition count. Latency = the slowest partition.

Cross-partition queries get worse over time

This is what makes them insidious. At launch with one physical partition, a cross-partition query is indistinguishable from a targeted one — same cost, same latency.

As data grows, Cosmos splits into more physical partitions. The same query now costs proportionally more RU and its latency becomes the maximum across all of them. Nothing in the code changed.

So a query that was fine in testing and fine for the first six months degrades steadily and inexplicably. That's why "does this query include the partition key?" is a review question, not just a tuning one.

You can bound the damage with MaxConcurrency and MaxItemCount on QueryRequestOptions, but that limits parallelism rather than fixing the fan-out.

Indexing policy ⭐ Senior-level

The default, and why it's backwards

Cosmos indexes every property, at every nesting level, unless you say otherwise. Every other database indexes nothing by default.

That's a good default for reads — nothing is ever accidentally a full scan. But every indexed path is maintained on every write, so writes cost more RU than they need to.

{
  "indexingMode": "consistent",
  "includedPaths": [ { "path": "/*" } ],
  "excludedPaths": [ { "path": "/\"_etag\"/?" } ]
}
{
  "indexingMode": "consistent",
  "includedPaths": [
    { "path": "/tenantId/?" },
    { "path": "/status/?" },
    { "path": "/createdAt/?" },
    { "path": "/customer/email/?" }
  ],
  "excludedPaths": [
    { "path": "/*" },                        // exclude everything else
    { "path": "/payload/*" },                // large nested blob, never filtered
    { "path": "/auditTrail/*" }              // array we only ever read whole
  ],
  "compositeIndexes": [
    [ { "path": "/status", "order": "ascending" },
      { "path": "/createdAt", "order": "descending" } ]
  ]
}
Senior signal — this is a cost optimisation with no equivalent elsewhere

On a write-heavy container with large nested documents, switching from "/*" to an explicit include list is frequently a large reduction in write RU — because you stop maintaining index entries for fields nobody ever filters on.

The biggest wins are large nested objects and arrays. An auditTrail array with 200 entries generates index entries for every property of every element on every write, and if you only ever read it as a whole, all of that is wasted.

The trade-off to state honestly: an excluded path cannot be filtered on. If someone later needs to query it, you must add it back and Cosmos reindexes the container — which is online but consumes RU while it runs. So this is an optimisation for containers whose access patterns have settled, not for something still in flux.

"I'd index the paths we filter on and exclude the rest" is a specific, quantifiable answer to "how would you reduce Cosmos costs?" — much stronger than "reduce RU/s".

Path syntaxMeans

/customer/*Everything under customer, recursively
/lines/[]/sku/?sku in every element of the lines array

Indexing mode: consistent vs none

"indexingMode": "consistent" updates the index synchronously with the write. That's the default and almost always what you want.

"none" disables indexing entirely — point reads still work (they don't use the index), but queries can't. The legitimate use is a bulk import: set it to none, load the data cheaply, then switch back to consistent and let it index once. That can cut the RU cost of a large migration substantially.

There's also a lazy mode, which is deprecated and shouldn't be used — it gave no consistency guarantee on query results.

Composite indexes

SELECT * FROM c
WHERE c.tenantId = @tenant
ORDER BY c.status ASC, c.createdAt DESC
Remember this

A multi-property ORDER BY requires a composite index. Without one the query fails — it doesn't just run slowly.

And the composite index must match the order and direction. An index defined as (status ASC, createdAt DESC) serves that exact ordering and its complete reverse — (status DESC, createdAt ASC) — but not other combinations.

Single-property ORDER BY works with the default range index, which is why this only bites when you add a second sort field.

Pagination 🔥 Must know

    {

Continuation tokens have two practical constraints

They can be large — up to a few KB, especially for cross-partition queries where the token encodes progress through every partition. That's too big for a URL query string in some cases, so you may need to return it in a response body or header. The ResponseContinuationTokenLimitInKb option can cap it, at the cost of some efficiency.

They're opaque and version-bound. Don't parse them, don't store them long-term, and don't assume one survives an SDK upgrade. They're for immediate next-page use.

Also: an empty page with a non-null token is normal on cross-partition queries — it means "no results from this batch, keep going". Treating a null result set as "end of data" is a bug; the token being null is the only end-of-data signal.

The integrated cache is underused

A dedicated gateway with an integrated cache serves repeat reads from memory at 0 RU. For read-heavy workloads with hot items — product catalogues, configuration, reference data — that can be a large saving.

Requirements: the client must use Gateway connection mode (not Direct), and you set a staleness window via DedicatedGatewayRequestOptions.MaxIntegratedCacheStaleness.

The trade is Gateway mode's slightly higher latency versus Direct, plus the cost of the dedicated gateway. So it wins when the hit rate is high, and it's worth measuring rather than assuming.

var iterator = container.GetItemQueryIterator<Order>(query,
    requestOptions: new QueryRequestOptions { PopulateIndexMetrics = true });

var page = await iterator.ReadNextAsync();
logger.LogInformation("RU {RU}, index metrics: {Metrics}",
    page.RequestCharge, page.IndexMetrics);
// IndexMetrics tells you which indexes were used and which were RECOMMENDED
// but missing - the closest equivalent to a missing-index suggestion.
PopulateIndexMetrics is the diagnostic to know

It reports which index the query used, and — more usefully — which composite index it would have benefited from. That's the Cosmos equivalent of SQL Server's missing-index DMV.

Same caveat applies: treat it as evidence about which queries are struggling, not a list to apply verbatim, because every index you add costs write RU.

Enable it in development and for investigation, not permanently — it adds overhead.

Query patterns to avoid 🔴 Advanced

PatternProblemInstead
COUNT(*) for a UI badge Scans every matching item, every page load Maintain a counter document, updated by the change feed
WHERE CONTAINS(c.name, 'x') Cannot use an index — scans the partition Azure AI Search, or store a normalised prefix field
JOIN across containers Not supported — Cosmos JOIN is intra-document only Denormalize, or two queries
ORDER BY on a cross-partition query Every partition sorts, then merges Scope to a partition, or pre-sort with a synthetic key
Large IN lists Can fan out across partitions Parallel point reads, or ReadManyItemsAsync
ReadManyItemsAsync for batch lookups
var keys = new List<(string id, PartitionKey pk)>
{
    ("order-1", new PartitionKey("tenant-a")),
    ("order-2", new PartitionKey("tenant-b"))
};
var results = await container.ReadManyItemsAsync<Order>(keys);

This batches point reads efficiently across partitions — much cheaper than a query with a large IN clause, and cheaper than N separate round trips.

It's the right answer when you have a list of ids and their partition keys, which happens constantly when resolving references between denormalized documents.

JOIN in Cosmos means something different

Cosmos SQL has a JOIN keyword, and it only joins within a single document — it flattens nested arrays, closer to CROSS APPLY over an array than a relational join.

There is no cross-container or cross-document join at all. So relationships are resolved by denormalizing the fields you need, or by issuing a second query.

That's a real constraint on modelling, and it's why the extended reference pattern is even more important here than in MongoDB — where at least $lookup exists as a fallback.

Key takeaways
  • Point read (partition key + id) is ~1 RU. Never query by id.
  • Always supply the partition key, or the query fans out and multiplies RU.
  • Cross-partition queries degrade over time as partitions split — nothing in the code changes.
  • Everything is indexed by default; excluding unqueried paths cuts write RU.
  • An excluded path can't be filtered on, and re-adding it triggers a reindex.
  • indexingMode: none during a bulk import, then switch back.
  • Multi-property ORDER BY requires a matching composite index or it fails.
  • Continuation tokens, not OFFSET. A null token is the only end-of-data signal.
  • Project specific fields — RU scales with returned bytes.
  • PopulateIndexMetrics tells you which composite index would help.
  • No cross-container joins. Denormalize, or use ReadManyItemsAsync.

Common mistakes

  • Querying by id instead of a point read.
  • Omitting the partition key from queries that could include it.
  • Leaving the default /* indexing policy on a write-heavy container.
  • Indexing large nested arrays nobody filters on.
  • SELECT * when three fields are needed.
  • OFFSET pagination, paying for everything skipped.
  • Treating an empty page as end-of-data instead of checking the token.
  • Storing continuation tokens long-term.
  • COUNT(*) on every page load.
  • Expecting cross-container joins to exist.
  • Never logging RequestCharge, so cost is invisible.

Interview questions

Intermediate

How would you reduce the RU cost of a Cosmos container? 🔥 Must know
How I'd answer

"I'd start by measuring, because RU cost is invisible unless you look. Every response carries a RequestCharge, so I'd log it in development and check the expensive operations — accumulating across pages for queries, since each page is charged separately and measuring only the first page badly understates the cost."

"Then, roughly in order of impact:"

"Point reads instead of queries. If I know the partition key and the id, ReadItemAsync is about 1 RU. The same item fetched with SELECT * FROM c WHERE c.id = @id goes through the query engine and costs three to five times more. Querying by id is extremely common because it looks familiar coming from SQL, and it's pure waste."

"Make sure queries include the partition key. Without it the query fans out to every physical partition and the RU multiplies by the partition count. What makes this particularly nasty is that it gets worse over time — at launch with one physical partition it's indistinguishable from a targeted query, and as data grows and Cosmos splits, the same unchanged code costs proportionally more and its latency becomes the slowest partition's."

"Tune the indexing policy. This is the Cosmos-specific one with no equivalent elsewhere. Cosmos indexes every property by default, and writes cost about 5× reads precisely because every indexed path is maintained on every write. So switching from /* to an explicit include list — just the paths we actually filter on — directly reduces write RU. The biggest wins are large nested objects and arrays: an audit-trail array with 200 entries generates index entries for every property of every element, and if we only ever read it whole, all of that is wasted."

"I'd state the trade-off honestly: an excluded path can't be filtered on, and adding it back triggers a container reindex which consumes RU. So it's right for containers whose access patterns have settled, not something still in flux."

"Project only the fields needed. RU scales with returned bytes, so SELECT c.id, c.total beats SELECT * on large documents."

"Replace cross-partition aggregates. A COUNT(*) for a UI badge scans everything matching, on every page load. Maintaining a counter document updated by the change feed turns that into a 1 RU point read."

"TTL instead of delete jobs, because TTL deletion uses leftover RU rather than my provisioned budget — expiry is effectively free, where millions of explicit deletes cost real RU and can throttle live traffic."

"Two structural options beyond query tuning. The integrated cache serves repeat reads at 0 RU, which is significant for hot reference data — it needs Gateway connection mode and a dedicated gateway. And the analytical store via Synapse Link moves reporting off the RU budget entirely, billed on storage and scan instead. If analytics is what's consuming throughput, that's the structurally correct fix rather than trying to make aggregations cheap."

"And on the provisioning side: if average utilisation is below roughly 66%, autoscale is cheaper than provisioned despite the 1.5× per-RU premium, because you stop paying for idle headroom."

What they're really checking
  • Do you measure first?
  • Do you know point reads vs queries?
  • Do you know the indexing policy affects write cost?
  • Do you know cross-partition cost grows over time?
  • Do you know about the analytical store and integrated cache?
Likely follow-ups
  • What's the downside of excluding paths?
  • How would you maintain that counter document?
  • When is autoscale cheaper?

Advanced / scenario

A list endpoint costs 800 RU per call and the team wants to raise throughput. What do you do? ⭐ Senior-level
How I'd answer

"800 RU for a list endpoint is very high, so I'd push back on raising throughput and find out what it's actually doing first. Adding RU/s here would be paying monthly for a bug."

"I'd get the query and check PopulateIndexMetrics, which tells me which indexes were used and which composite index would have helped. Then I'd look for four specific things."

"Is it cross-partition? That's the most likely explanation for 800 RU. If the query doesn't include the partition key it fans out to every physical partition and the cost multiplies. If this is a tenant-scoped list and the partition key is tenantId, supplying it should collapse the cost dramatically — and it's a one-line change."

"Is it doing SELECT *? RU scales with returned bytes. If the documents are large and the list only displays five fields, projecting just those can cut it substantially."

"Is it using OFFSET? Cosmos still reads and charges for skipped items, so a deep page is expensive. Continuation tokens make it constant-cost."

"Is there a COUNT for a total? An exact count across partitions is often more expensive than the page itself, and it's frequently there just to render 'showing 20 of 1,432'."

"My expectation is that fixing those gets it to a small fraction of 800 RU. If it's still high after that, the question becomes structural."

"Is the container modelled for this query? If the list is a genuinely important screen and the query can't be made single-partition — because it legitimately spans tenants, say — then the answer isn't tuning, it's maintaining a purpose-built read document. A single document per tenant holding the list projection, updated by the change feed, turns an 800 RU fan-out into a 1 RU point read. That's the Cosmos version of a read model."

"Is it the same list repeatedly? If many users request identical data, the integrated cache serves it at 0 RU. Needs Gateway mode and a dedicated gateway, but for a hot list endpoint the arithmetic usually works."

"Is it actually a reporting query? If the endpoint is really analytics wearing a list's clothing — aggregations, arbitrary filters, large ranges — it belongs in the analytical store via Synapse Link, which is billed on storage and scan rather than RU. That removes it from the throughput budget completely."

"The framing I'd bring to the team: in Cosmos, cost and performance are the same conversation. An 800 RU endpoint isn't just expensive — once it's called frequently it consumes the throughput budget and starts throttling unrelated features with 429s. So this is a reliability issue, not only a billing one, and raising RU/s postpones it rather than fixing it."

"I'd also want to know the call rate before deciding urgency. 800 RU called twice a day is irrelevant; 800 RU called 50 times a second is 40,000 RU/s and the dominant cost in the account. Same query, completely different priority."

What they're really checking
  • Do you refuse to just raise throughput?
  • Do you check cross-partition first — the most likely cause?
  • Do you know PopulateIndexMetrics?
  • Do you reach for a change-feed-maintained read document?
  • Do you connect RU cost to throttling other features?
  • Do you ask about call rate?
Weak answers
  • Red flag: "increase RU/s."
  • Red flag: no mention of the partition key.
  • Red flag: treating it purely as a cost problem, not a reliability one.
Likely follow-ups
  • How would you keep that read document consistent?
  • What if the list genuinely must span all tenants?
  • How do you show a total count cheaply?
