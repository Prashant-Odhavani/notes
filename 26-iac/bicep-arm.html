Bicep & ARM

Azure-native, no state file to manage, and day-one support for new services. The trade is that it only does Azure.

🟡 Intermediate 🔴 Advanced 💡 Good to know
Quick revision
  • Bicep compiles to ARM JSON. Same engine, far better language.
  • No state file — Azure's resource graph is the state.
  • Incremental mode is the default, and what you almost always want.
  • Complete mode deletes anything not in the template. Be very careful.
  • what-if is Bicep's equivalent of a plan.
  • Four scopes: resource group, subscription, management group, tenant.
  • existing references something you don't own.
  • Deployment stacks give lifecycle management, closer to Terraform.

ModulesNested/linked templates, awkwardFirst-class module
Relationship—Compiles to ARM JSON; identical runtime behaviour
Bicep is a language, not a different engine

Bicep transpiles to ARM JSON and Azure Resource Manager executes it. So anything ARM can do, Bicep can do, and the deployment semantics — modes, scopes, idempotency — are identical.

Which means you never need to write ARM JSON by hand for new work, and az bicep decompile converts existing templates. Reading generated JSON is occasionally useful for debugging an obscure error message that references the compiled output.

The most practically valuable difference is inferred dependencies. In ARM you write dependsOn arrays by hand, and getting them wrong produces intermittent deployment failures that depend on timing — the worst kind of bug. Bicep derives ordering from symbolic references, so referring to storageAccount.id creates the dependency automatically.

You can still write dependsOn explicitly for an ordering that isn't expressed by a reference, and needing to is usually a sign the template is fighting something.

A Bicep template worth reading 🔥 Must know

targetScope = 'resourceGroup'

@description('Environment name, used in resource naming')
@allowed(['dev', 'test', 'prod'])
param environment string

@description('Deployment location')
param location string = resourceGroup().location

@minLength(3)
@maxLength(11)
param appName string

@secure()                                  // never logged, never in deployment history output
param sqlAdminPassword string

// Computed values - not parameters, so callers cannot get them wrong
var resourceSuffix = '${appName}-${environment}'
var isProd = environment == 'prod'
var tags = {
  environment: environment
  application: appName
  managedBy: 'bicep'
}

resource logAnalytics 'Microsoft.OperationalInsights/workspaces@2023-09-01' = {
  name: 'log-${resourceSuffix}'
  location: location
  tags: tags
  properties: {
    retentionInDays: isProd ? 90 : 30
    sku: { name: 'PerGB2018' }
  }
}

resource plan 'Microsoft.Web/serverfarms@2023-12-01' = {
  name: 'plan-${resourceSuffix}'
  location: location
  tags: tags
  sku: {
    name: isProd ? 'P1v3' : 'B1'
    capacity: isProd ? 3 : 1
  }
  properties: { reserved: true }           // Linux
}

resource app 'Microsoft.Web/sites@2023-12-01' = {
  name: 'app-${resourceSuffix}'
  location: location
  tags: tags
  identity: { type: 'SystemAssigned' }
  properties: {
    serverFarmId: plan.id                  // this reference creates the dependency
    httpsOnly: true
    siteConfig: {
      linuxFxVersion: 'DOTNETCORE|9.0'
      minTlsVersion: '1.2'
      ftpsState: 'Disabled'
      alwaysOn: isProd
      healthCheckPath: '/health/ready'
      appSettings: [
        { name: 'ASPNETCORE_ENVIRONMENT', value: isProd ? 'Production' : 'Development' }
        { name: 'APPLICATIONINSIGHTS_CONNECTION_STRING', value: appInsights.properties.ConnectionString }
      ]
    }
  }
}

resource appInsights 'Microsoft.Insights/components@2020-02-02' = {
  name: 'appi-${resourceSuffix}'
  location: location
  tags: tags
  kind: 'web'
  properties: {
    Application_Type: 'web'
    WorkspaceResourceId: logAnalytics.id
  }
}

// Diagnostics as a child of the app - an extension resource
resource diagnostics 'Microsoft.Insights/diagnosticSettings@2021-05-01-preview' = {
  scope: app
  name: 'send-to-log-analytics'
  properties: {
    workspaceId: logAnalytics.id
    logs: [{ categoryGroup: 'allLogs', enabled: true }]
    metrics: [{ category: 'AllMetrics', enabled: true }]
  }
}

output appPrincipalId string = app.identity.principalId
output appHostname string = app.properties.defaultHostName
Senior signal — @secure() and what it does and doesn't do

@secure() on a parameter means the value is excluded from deployment history and logs. Without it, a password passed as a parameter is visible in the deployment record in the portal, permanently, to anyone with read access to the resource group.

That's a real leak and an easy one to create — and unlike a Terraform state file, deployment history isn't something people think to lock down.

What it doesn't do: protect the value in transit from wherever you got it, or stop it being echoed by a pipeline that logs its own variables.

The better pattern is not to pass secrets at all. A parameter file can reference a Key Vault secret directly, so the value goes from vault to ARM without appearing in a pipeline variable or a parameter file. And where the resource supports it, use managed identity so no secret exists — the app above has a system-assigned identity for exactly that reason.

Same conclusion as everywhere: the best secret handling is not having a secret.

Modules and scopes 🟡 Intermediate

targetScope = 'subscription'               // this template creates resource groups

param environment string
param location string = 'uksouth'

resource rg 'Microsoft.Resources/resourceGroups@2024-03-01' = {
  name: 'rg-orders-${environment}'
  location: location
}

// A module is a separate deployment, scoped where you say
module app './modules/web-app.bicep' = {
  name: 'app-deployment'                   // the DEPLOYMENT name, not the resource name
  scope: rg                                // deploy into the group created above
  params: {
    environment: environment
    location: location
    appName: 'orders'
  }
}

// Reference something owned by another team - read only, never modified
resource sharedVnet 'Microsoft.Network/virtualNetworks@2024-01-01' existing = {
  name: 'vnet-shared-${environment}'
  scope: resourceGroup('rg-platform-network')
}

// Deploy many similar things with a loop
module regionalApps './modules/web-app.bicep' = [for region in ['uksouth', 'ukwest']: {
  name: 'app-${region}'
  scope: rg
  params: {
    environment: environment
    location: region
    appName: 'orders'
  }
}]

output vnetId string = sharedVnet.id
output appHostname string = app.outputs.appHostname

managementGroupPolicies and RBAC across many subscriptions
tenantManagement groups themselves
The existing keyword is the ownership boundary

existing declares a reference to a resource this template does not manage. You get its properties and its id; you can't create, modify or delete it.

That's how you handle shared infrastructure cleanly. A platform team owns the virtual network and the Key Vault; your template references them as existing and deploys into them.

It's the same distinction as Terraform's data versus resource, and the same hazard if you get it wrong: two templates both declaring the same resource will each reset it to their own definition, and it flaps between them on every deployment.

One thing to know: existing is resolved at deployment time, so if the resource doesn't exist the deployment fails — which is usually the behaviour you want, since silently proceeding without it would be worse.

Deployment modes 🔥 Must know

ModeBehaviourUse
Incremental (default) Creates or updates what's in the template. Leaves everything else alone Almost always this
Complete Deletes any resource in the group that isn't in the template Rarely, and only where the template is the sole owner of the group
Complete mode is a loaded gun, and it's also the only way to get cleanup

Complete mode makes the resource group match the template exactly — which means anything not in the template is deleted. Including things another team created, things added during an incident, and things you forgot were there.

Run a partial template in complete mode against a shared resource group and you delete production resources. It's the most destructive thing in this toolchain.

But there's a real tension here, because incremental mode never removes anything. Delete a resource from your Bicep file and it stays in Azure, forever, unmanaged and still billing. That's the main lifecycle weakness compared with Terraform, which deletes what you remove from the configuration.

So you get one of two uncomfortable positions: incremental and orphans accumulate, or complete and a mistake is catastrophic.

Deployment stacks are the answer to that. A stack tracks the resources it manages, so removing something from the template removes it from Azure — scoped to the stack rather than the whole resource group. That's Terraform-like lifecycle management without a state file you have to look after, and it's what to reach for when orphaned resources become a real problem.

Until then, the pragmatic position: incremental mode always, with periodic auditing for orphans.

what-if, the plan equivalent 🔥 Must know

# Preview: what would change. Bicep's equivalent of terraform plan.
az deployment group what-if \
  --resource-group rg-orders-prod \
  --template-file main.bicep \
  --parameters main.prod.bicepparam

# Deploy. Incremental is the default.
az deployment group create \
  --resource-group rg-orders-prod \
  --template-file main.bicep \
  --parameters main.prod.bicepparam \
  --name "orders-$(git rev-parse --short HEAD)"    # traceable deployment name

# Deployment stacks - manages lifecycle, so removals actually delete
az stack group create \
  --name orders \
  --resource-group rg-orders-prod \
  --template-file main.bicep \
  --parameters main.prod.bicepparam \
  --action-on-unmanage deleteResources \
  --deny-settings-mode denyWriteAndDelete       # blocks portal changes to stack resources

# Lint and build locally
az bicep lint --file main.bicep
az bicep build --file main.bicep
what-if is less precise than a Terraform plan, and you should know why

what-if compares your template against Azure's current state and reports Create, Delete, Modify, Ignore or NoChange per resource. It's genuinely useful and worth running on every pull request.

It's less exact than terraform plan for a structural reason: Terraform has a state file recording what it last set, so it knows the difference between "I set this" and "Azure defaulted it". Bicep has no such record and must infer from the live resource.

In practice that shows up as noisy output — properties reported as changing when they aren't meaningfully, particularly on resources with many server-set defaults. Some resource providers implement the what-if API better than others.

So it's a strong signal for deletes and creates — which are the operations you care most about — and less reliable on the detail of modifications. That's fine as long as you know it, and it means the review focus is the same as with Terraform: look for deletions first.

Two habits that help. Use a traceable deployment name — the git SHA — so the deployment history maps to a commit. And note that deployment history is capped at 800 per resource group; exceeding it causes deployment failures, so long-lived groups need history pruning.

Parameter files 🟡 Intermediate

using './main.bicep'                       // typed against the template - errors on mismatch

param environment = 'prod'
param appName = 'orders'
param location = 'uksouth'

// Pull the secret from Key Vault at deployment time.
// The value never appears in this file, in a pipeline variable, or in logs.
param sqlAdminPassword = getSecret(
  '00000000-0000-0000-0000-000000000000',  // subscription
  'rg-platform-secrets',                    // resource group
  'kv-platform-prod',                       // vault
  'sql-admin-password'                      // secret name
)
.bicepparam over JSON parameter files

The .bicepparam format is typed against the template through using. So a misspelled parameter name, a missing required parameter or a wrong type is caught before deployment, in the editor.

With JSON parameter files, those mistakes surface as a deployment failure — after you've triggered a pipeline and waited.

The more valuable feature is getSecret, which references a Key Vault secret directly. ARM retrieves it at deployment time, so the value never touches the parameter file, a pipeline variable, or a log.

That's cleaner than the usual approach of storing the secret as a pipeline variable and passing it through, which puts it in a second system and in the pipeline's own logs if anything echoes it. It does require the deploying identity to have read access to the vault, which is the right place for that permission to live anyway.

Where Bicep genuinely wins ⭐ Senior-level

Bicep advantageWhy
No state to manageNothing to store, lock, back up, corrupt or leak
Day-one support for new servicesIt's the ARM API; no provider needs updating
Preview and unusual featuresAvailable immediately, including undocumented properties
Microsoft supportSupported directly, and used by Azure's own documentation
Azure Verified ModulesMicrosoft-maintained modules following the Cloud Adoption Framework
No extra credentialsUses Azure RBAC directly, with no separate tool identity
Senior signal — the provider-lag argument is the strongest one

Terraform reaches Azure through the azurerm provider, which is a layer that has to be written. A new Azure service, a new property, or a preview feature isn't available until someone implements and releases it — and that can be weeks or months.

When it isn't there, your options are unpleasant: wait, or use azapi, or shell out to the CLI from a null_resource. All of which mean the thing you're doing is no longer really Terraform.

Bicep is the ARM API, so if Azure supports it, Bicep supports it — today, including preview features and properties that aren't in any provider yet.

That's the argument that carries weight for Azure-only work, alongside no state file, which removes an entire operational concern: no backend to configure, no locking to get right, no plaintext secrets in a storage container, and no possibility of the "we lost the state file" incident.

Terraform's counter-arguments are equally real and worth stating in the same breath: multi-cloud, a far larger module and provider ecosystem (including Entra, GitHub, Datadog and anything else in the estate), better lifecycle management, a more precise plan, and portable skills — a Terraform engineer is useful anywhere.

The honest summary: Azure-only and want the least operational overhead → Bicep. Multi-cloud, or already invested in Terraform → Terraform. Both are defensible; a candidate who insists one is simply better usually hasn't run the other in production.

Key takeaways
  • Bicep compiles to ARM JSON — same engine, better language, no hand-written JSON needed.
  • Dependencies are inferred from references, removing a class of ordering bug.
  • @secure() keeps values out of deployment history — but prefer no secret at all.
  • Use getSecret in a .bicepparam so secrets never touch the pipeline.
  • Four scopes; subscription scope is what creates resource groups.
  • existing is the ownership boundary — read, don't manage.
  • Incremental mode always; complete mode deletes anything absent.
  • Incremental never removes, so orphans accumulate.
  • Deployment stacks give real lifecycle management without a state file.
  • what-if is noisier than a Terraform plan — trust it most on deletes.
  • Deployment history caps at 800 per resource group.
  • Bicep's strongest arguments: no state, and no provider lag.

Common mistakes

  • Complete mode on a shared resource group, deleting other people's resources.
  • Never auditing for orphans left behind by incremental mode.
  • Secrets as plain parameters without @secure(), visible in history.
  • Secrets in a parameter file instead of a Key Vault reference.
  • Declaring a shared resource rather than referencing it with existing.
  • Not running what-if before deploying.
  • Hand-written dependsOn where a reference would do.
  • Hardcoded locations and names instead of parameters and variables.
  • Deployment history unpruned, eventually hitting the 800 limit.
  • Generic deployment names, so history can't be traced to a commit.
  • Writing ARM JSON by hand for new work.

Terraform or Bicep for a new Azure project? 🔥 Must know
How I'd answer

"Both are good, so I'd decide on three questions rather than a preference: is it Azure-only, what does the team already know, and how much operational overhead do we want to own?"

"The case for Bicep — and the strongest single point is no state file. That removes a whole operational category: no backend to configure, no locking to get right, no plaintext secrets sitting in a storage container, and no possibility of the 'we lost the state file' incident where Terraform no longer knows anything it created. Azure's resource graph is the state."

"Second, no provider lag. Terraform reaches Azure through the azurerm provider, which is a layer someone has to write. A new service or a preview property isn't available until it's implemented and released — sometimes months. Then you're waiting, or using azapi, or shelling out to the CLI, at which point it isn't really Terraform any more. Bicep is the ARM API, so if Azure supports it, Bicep supports it today."

"Third, it's Microsoft-supported, Azure's own documentation uses it, and Azure Verified Modules give you maintained modules aligned to the Cloud Adoption Framework."

"The case for Terraform — multi-cloud, obviously, but more practically a much larger provider ecosystem. Real infrastructure isn't only Azure resources: it's Entra app registrations, GitHub repositories and permissions, Datadog monitors, Cloudflare DNS. Terraform manages all of that in one workflow; Bicep manages Azure and you need something else for the rest."

"Then better lifecycle management. This is Bicep's real weakness: incremental mode — which is the default and what you should use — never deletes anything. Remove a resource from your template and it stays in Azure, unmanaged and still billing. Terraform deletes what you remove from the configuration. Complete mode exists in Bicep and it's dangerous, because it deletes everything in the resource group that isn't in the template, including other teams' resources."

"Deployment stacks address that — they track what they manage, so removals actually delete, scoped to the stack. That's a genuine improvement and it's newer, so it's worth checking maturity for the specific resources involved."

"Also, terraform plan is more precise than what-if, and the reason is structural: Terraform's state records what it last set, so it can distinguish 'I configured this' from 'Azure defaulted it'. Bicep has to infer from the live resource, so what-if is noisier on modifications. It's reliable on creates and deletes, which are what matter most in review."

"And portable skills. A Terraform engineer is useful in any cloud; Bicep knowledge is Azure-specific."

"My recommendation would be: Azure-only, small team, want minimal operational overhead → Bicep. The absence of state management is worth a lot, and the tooling is good. Multi-cloud, or managing non-Azure resources, or the team already knows Terraform → Terraform."

"The one thing I'd push back on is using both. It happens — Terraform for the platform, Bicep for applications — and it means two toolchains, two skill sets, and ambiguity about which owns what. If it has to happen, the ownership boundary must be explicit, with each tool referencing the other's resources read-only: existing in Bicep, data in Terraform. Two tools both believing they own a resource is a genuinely nasty failure — each apply reverts the other and the resource flaps."
