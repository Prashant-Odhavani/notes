IaC in Production

The tool matters less than the pipeline around it. This page is about the parts that keep it trustworthy.

🔴 Advanced ⭐ Senior-level
Quick revision
  • Plan on the pull request, apply after approval — applying the saved plan.
  • OIDC federation, not a service principal secret. No credential to rotate.
  • Humans get read-only in the portal. The pipeline holds write.
  • Scheduled drift detection, alerting on any difference.
  • A documented break-glass path — emergencies happen anyway.
  • Policy as code so insecure configuration fails the build.
  • Split state by blast radius, not by tidiness.
  • Same definition, different parameters across environments.

The pipeline 🔥 Must know

name: infrastructure

on:
  pull_request:
    paths: ['infra/**']
  push:
    branches: [main]
    paths: ['infra/**']

permissions:
  id-token: write          # required for OIDC - this is what replaces a secret
  contents: read
  pull-requests: write     # to post the plan as a comment

jobs:
  plan:
    runs-on: ubuntu-latest
    environment: production-plan          # read-only credentials
    steps:
      - uses: actions/checkout@v4

      - uses: azure/login@v2
        with:                             # NO client secret anywhere
          client-id: ${{ vars.AZURE_CLIENT_ID }}
          tenant-id: ${{ vars.AZURE_TENANT_ID }}
          subscription-id: ${{ vars.AZURE_SUBSCRIPTION_ID }}

      - uses: hashicorp/setup-terraform@v3
        with:
          terraform_version: 1.9.8        # pinned, like the providers

      - run: terraform init
        working-directory: infra/envs/prod

      - run: terraform validate
        working-directory: infra/envs/prod

      # Security and policy scanning BEFORE anything is applied
      - uses: bridgecrewio/checkov-action@master
        with:
          directory: infra
          soft_fail: false                # findings fail the build

      - name: Plan
        run: terraform plan -out=tf.plan -input=false
        working-directory: infra/envs/prod

      - uses: actions/upload-artifact@v4
        with:
          name: tf-plan
          path: infra/envs/prod/tf.plan   # THIS artefact is what gets applied

  apply:
    needs: plan
    if: github.ref == 'refs/heads/main'
    runs-on: ubuntu-latest
    environment: production               # requires a human approval
    steps:
      - uses: actions/checkout@v4
      - uses: azure/login@v2
        with:
          client-id: ${{ vars.AZURE_CLIENT_ID }}
          tenant-id: ${{ vars.AZURE_TENANT_ID }}
          subscription-id: ${{ vars.AZURE_SUBSCRIPTION_ID }}
      - uses: hashicorp/setup-terraform@v3
        with:
          terraform_version: 1.9.8
      - uses: actions/download-artifact@v4
        with: { name: tf-plan, path: infra/envs/prod }
      - run: terraform init
        working-directory: infra/envs/prod
      # Apply the REVIEWED plan, not a freshly computed one
      - run: terraform apply -input=false -auto-approve tf.plan
        working-directory: infra/envs/prod
Senior signal — the plan artefact is what makes the approval mean something

The important structural detail is that the plan job saves a plan file and the apply job applies that exact file.

If apply recomputes its own plan, the approval was for a different set of operations than the one that runs. State may have changed, someone may have made a portal change, another apply may have run. So the approval degrades into "I approve of the general idea."

Applying the saved plan means the reviewed operations are the executed operations — and if reality has moved, the apply fails rather than doing something different. Failing is the correct outcome there.

Two supporting details worth naming. The plan job uses a read-only identity, so a pull request from anywhere can safely produce a plan without any ability to change infrastructure — which matters because plan runs on untrusted input. And apply is gated by a GitHub environment (or an Azure DevOps approval), so the human gate is enforced by the platform rather than by convention.

One caution on plan output: a plan can contain sensitive values. Posting it verbatim as a pull request comment on a public repository leaks them, so redact or restrict where plans are published.

OIDC instead of secrets 🔥 Must know

Service principal secretOIDC federated credential
StoredIn the CI system, as a secretNothing is stored
ExpiryExpires; deployment breaks when it doesTokens are per-run and short-lived
RotationA recurring manual taskNothing to rotate
If leakedUsable by anyone, from anywhereUseless — bound to repo, branch and environment
ScopeWhatever it was grantedConstrained by the federation subject
Senior signal — the binding is what makes it strong, not the absence of a secret

The obvious benefit is that there's no credential to store or rotate. The stronger property is what the trust is bound to.

A federated credential names a subject: this repository, this branch or this environment, from this issuer. So a token minted for repo:org/infra:environment:production is only issued to a workflow run that genuinely meets those conditions — checked by Entra against GitHub's signed token, not asserted by the workflow.

Which means even a fully compromised CI configuration in another repository cannot obtain it. A leaked client secret, by contrast, works from anywhere until someone notices.

Two things to get right. Federate on the environment, not just the repository, or any branch in that repo can request production credentials — which defeats the approval gate you just built. And keep the plan identity separate from the apply identity: Reader for plan, Contributor for apply. Plan runs on pull requests, including from forks in some configurations, so it should never hold write access.

Same reasoning as managed identity for applications: the best credential is one that doesn't exist.

Senior signal — without read-only humans, IaC is advisory

This is the point that separates a team that uses IaC from one that relies on it.

If engineers have Contributor in production, then IaC is a convention people follow when convenient. Under pressure someone will click, because clicking is faster — and that's a completely rational choice for the individual in that moment. Drift then accumulates, the repository stops matching reality, and people stop trusting it.

Reader for humans, write for the pipeline makes the code the only path. Not because people are untrustworthy, but because it removes the temptation entirely and keeps the repository authoritative.

The necessary companion is a break-glass path, and this is where a lot of well-intentioned policies fail. During a genuine incident someone may need to change something now. If there's no sanctioned way, they'll find an unsanctioned one — a shared account, a standing exemption — and you've lost both the control and the audit trail.

So: an elevation group activated through PIM, time-bound to a few hours, requiring a justification, alerting the team on activation, and with a mandatory follow-up to reconcile the code. That's the mature position — plan for the emergency instead of forbidding it.

Drift detection 🔥 Must know

name: drift-detection

on:
  schedule:
    - cron: '0 6 * * *'      # every morning, before anyone deploys
  workflow_dispatch:

permissions:
  id-token: write
  contents: read
  issues: write

jobs:
  detect:
    strategy:
      fail-fast: false        # check every environment even if one drifts
      matrix:
        env: [dev, test, prod]
    runs-on: ubuntu-latest
    environment: ${{ matrix.env }}-plan     # READ-ONLY identity
    steps:
      - uses: actions/checkout@v4
      - uses: azure/login@v2
        with:
          client-id: ${{ vars.AZURE_CLIENT_ID }}
          tenant-id: ${{ vars.AZURE_TENANT_ID }}
          subscription-id: ${{ vars.AZURE_SUBSCRIPTION_ID }}
      - uses: hashicorp/setup-terraform@v3

      - run: terraform init
        working-directory: infra/envs/${{ matrix.env }}

      # -detailed-exitcode: 0 = no changes, 2 = changes present, 1 = error
      - name: Detect drift
        id: drift
        continue-on-error: true
        run: terraform plan -detailed-exitcode -input=false -no-color
        working-directory: infra/envs/${{ matrix.env }}

      - name: Raise an issue if drift found
        if: steps.drift.outcome == 'failure'
        uses: actions/github-script@v7
        with:
          script: |
            github.rest.issues.create({
              owner: context.repo.owner,
              repo: context.repo.repo,
              title: `Infrastructure drift detected in ${{ matrix.env }}`,
              labels: ['drift', 'infrastructure'],
              body: 'A scheduled plan found differences. Review the run log.'
            })
The value is timing, not detection

Drift gets discovered eventually — the next time someone runs a plan. The problem is when: usually mid-deployment, when someone is trying to ship something unrelated and now has to decide, under time pressure, whether an unexpected change in the plan is safe to apply.

A nightly check moves that discovery to a quiet morning, with context still fresh about whatever happened yesterday.

It also catches the more dangerous case: drift that IaC would silently revert. An emergency firewall rule added during an incident will be removed by the next apply, at some unrelated moment, with no obvious connection to anything. That's how an outage returns weeks later, and it's genuinely hard to diagnose.

Two implementation details. Use -detailed-exitcode, which returns 2 specifically for "changes present", so you can distinguish drift from an error. And route the alert somewhere with an owner — an issue or a channel message. A nightly job that fails quietly is worse than none, because it creates the impression of coverage.

For Bicep the equivalent is a scheduled what-if, with the caveat that it's noisier on modifications, so tune what you alert on or you'll train people to ignore it.

Senior signal — Azure Policy is the layer that can't be bypassed

CI checks are excellent and they share one weakness: they only see changes that go through CI. A portal change, a CLI command, another team's pipeline — none of it is scanned.

Azure Policy evaluates at the resource-manager level, so it applies to every creation path. A deny effect makes a non-compliant resource impossible to create, whoever is creating it and however. deployIfNotExists can add diagnostics settings automatically so nothing is deployed without telemetry.

That's the difference between a rule that's checked and a rule that's enforced — and it's the same structural-not-procedural principle that runs through this whole part of the handbook.

So the layers complement each other. CI scanning gives fast, specific feedback in the pull request where the fix is cheap and the author has context. Azure Policy is the backstop that holds regardless of path. Neither replaces the other: policy alone gives you a deployment failure with a cryptic message; CI alone gives you a rule people can route around.

One practical note: start policies in audit mode. Turning on deny across an existing estate will block legitimate deployments in ways nobody predicted. Audit first, look at what's non-compliant, fix or exempt deliberately, then enforce.

PrincipleWhy
Same definition, different parametersIf dev and prod are different code, dev tests nothing
Separate state per environmentA dev mistake cannot reach production
Separate subscriptionsQuota isolation, clean cost attribution, a real boundary
Promote through environmentsThe same commit reaches prod having passed test
Split state by blast radiusNetworking changes rarely; apps change daily
Parity has limits, and pretending otherwise wastes money

"Dev should be identical to production" is the ideal and it's rarely affordable. Zone-redundant Premium plans, geo-replicated databases and a full AKS cluster per environment is a serious bill.

The useful distinction is between structural parity and capacity parity.

Structure must match: the same resource types, the same networking topology, the same identity and authentication model, the same TLS and firewall configuration. These are where behavioural differences hide — if dev uses a connection string and prod uses managed identity, dev never tests the thing most likely to break.

Capacity can differ: SKU sizes, instance counts, redundancy tier, retention periods. A B1 plan in dev and P1v3 in prod is fine; both are App Service and behave the same way.

The differences worth being nervous about are the ones that change semantics: single-instance dev versus multi-instance prod hides every local-state bug, and a serverless database tier can behave differently under load. Running at least two instances even in dev is a cheap way to close the most damaging gap.

And keep the differences in a parameter file rather than in conditionals. A tfvars file is readable; count = var.environment == "prod" ? 3 : 1 scattered through the code means production's actual shape can only be discovered by mentally evaluating expressions.

Testing infrastructure code 🔴 Advanced

LevelWhat it verifiesCost
validate and lintIt parses and is internally consistentSeconds
Static analysisSecurity and convention rulesSeconds

Ephemeral environmentIt actually deploys and worksMinutes, and real money
Plan assertions are the best value

Deploying to a real environment is the only way to know something truly works, and it's slow and costs money — so it isn't a per-pull-request check.

Asserting against the JSON plan gets you most of the way in seconds. terraform show -json gives a machine-readable description of every intended change, so you can assert mechanically: no resource is being deleted, every storage account has HTTPS-only enabled, no SQL server permits public network access, everything carries the required tags.

That catches the mistakes that actually happen, in the pull request, where the fix is cheap.

For modules, which are consumed repeatedly and where a bug multiplies, terraform test is worth the investment — including a real apply against a throwaway resource group for the important ones.

What I'd be sceptical about is elaborate testing of root configurations. They change constantly, and the honest test is deploying to a real environment and promoting the same commit through it — which the pipeline already does. Effort is better spent on plan assertions plus fast, safe rollback.

A word on Pulumi

Pulumi lets you define infrastructure in C#, which is genuinely appealing to a .NET team: real types, real tests, real refactoring tools, and the language you already know.

The counterargument is the one that decides it for most teams: a general-purpose language invites general-purpose complexity. HCL and Bicep are constrained, and that constraint keeps infrastructure definitions readable by people who didn't write them — including operations staff and auditors.

With C# available, someone will eventually add a class hierarchy, a factory and some LINQ, and the infrastructure becomes a program you must execute mentally to understand what it deploys.

Worth knowing it exists and being able to articulate that trade. In practice the ecosystem and hiring pool for Terraform and Bicep are much larger, which matters more than language preference.

Key takeaways
  • Save the plan as an artefact and apply that file, so the approval means something.
  • Plan identity read-only, apply identity write, both separate.
  • OIDC federation on the environment — no secret, and bound to repo and environment.
  • Reader for humans in production; otherwise IaC is advisory.
  • A PIM break-glass path with alerting and mandatory reconciliation.
  • Nightly drift detection with -detailed-exitcode, alerting an owner.
  • CI scanning for fast feedback; Azure Policy as the unbypassable backstop.
  • Start policies in audit mode before denying.
  • Structural parity across environments; capacity can differ.
  • Two instances even in dev, to surface local-state bugs.
  • Differences in parameter files, not conditionals.
  • Plan assertions are the best-value test; module tests for reused code.
  • Terraform for multi-cloud and ecosystem; Bicep for Azure-only and no state.

Common mistakes

  • Apply recomputing its own plan, so the approval covered something else.
  • One identity for plan and apply, giving write access to pull request runs.
  • A service principal secret in CI instead of OIDC.
  • OIDC federated on the repository only, so any branch can reach production.
  • Developers with Contributor in production, so drift is inevitable.
  • No break-glass path, so emergencies happen unsanctioned.
  • No drift detection, so drift is found mid-deployment.
  • A drift job that fails quietly, creating false confidence.
  • Policy set to deny immediately, blocking legitimate work.
  • Different code per environment, so dev tests nothing.
  • Single-instance dev, hiding every scale-out bug.
  • Environment conditionals scattered through the code.
  • Plan output with secrets posted publicly.

"I'd design it around one question: can someone change production without a reviewed plan? If the answer is yes anywhere, the rest is decoration."

"On a pull request, the pipeline runs validate, lint, security scanning and a plan. The plan is posted as a comment and saved as an artefact."

"That artefact is the important part. Apply must apply the saved plan, not compute a fresh one. Applying the saved file means the reviewed operations are the executed operations, and if reality has shifted the apply fails, which is the correct outcome."

"The plan job uses a read-only identity. Plan runs on pull requests, which is semi-untrusted input, so it must have no ability to change anything. Apply uses a separate identity with Contributor scoped to its own resource groups."

"Authentication is OIDC federation, not a service principal secret. No credential stored, nothing to rotate, and nothing to leak. "On merge to main, apply runs behind a GitHub environment with required reviewers, so the human gate is enforced by the platform rather than by convention."

"Promotion: the same commit applied to dev, then test, then production, with the same modules and only tfvars differing. If environments are different code, dev tests nothing."

"Nightly drift detection per environment, using the read-only identity and -detailed-exitcode so I can distinguish drift from error, raising an issue when it finds anything. Someone changed a production setting in the portal. What do you do? ⭐ Senior-level
How I'd answer

"I'd separate two things: dealing with this instance, and the fact that it was possible. The second one matters more."

"On the instance. First, find out what changed and why. The activity log gives me the resource, the change, the identity and the timestamp. Then I'd talk to whoever made it — not to blame them, but because the reason determines the response."

"If it was a correct emergency fix — say a firewall rule opened during an incident — then the change is right and the code is wrong. So I bring it into the definition and confirm the plan goes quiet. The urgent part here is that the next apply would silently revert it, possibly during an unrelated deployment weeks later, and the outage comes back with no obvious connection to anything. That's genuinely hard to diagnose, so reconciling promptly isn't tidiness — it's preventing a future incident."

"If it was wrong or accidental, then running apply reverts it, which is the tool working as intended. I'd still check the plan carefully first, because Azure sometimes implements a property change by replacing the resource, and the code diff won't show that — only the plan will."

"If it's ambiguous — someone changed a setting because they believed it was needed and nobody is sure — I'd treat the code as the source of truth and make the change properly through a pull request, so the reasoning is recorded. That's the whole point of the repository."

"Now the more important half."

"Why did they have write access? If engineers hold Contributor in production, then IaC is a convention people follow when convenient. Under pressure someone will click, and that's rational for the individual. I'd move humans to Reader — enough to diagnose, not to change — with write held by the pipeline identity."

"Was there a sanctioned way to do it urgently? If not, that's my finding. A pipeline that takes twenty minutes with a required approval is unusable at three in the morning during an outage, so people will route around it. Forbidding the manual change without providing an alternative just makes it undocumented."

"So I'd want a break-glass path: a PIM-activated elevation, time-bound to a few hours, requiring a justification, alerting the team on activation, and with a mandatory reconciliation task afterwards. Then an emergency change is visible, attributable and followed up, rather than discovered by accident."

"How long did it take to notice? If the answer is 'we found out when a deployment behaved oddly', I'd add scheduled drift detection — a nightly plan that raises an issue on any difference. That moves discovery to a quiet morning with the context still fresh."

"For rules that must never be violated, regardless of route — public network access, TLS version, missing encryption — I'd use Azure Policy in deny mode. CI checks only see changes that go through CI; policy applies at the resource-manager level, so it stops a portal change too. That's the only layer that genuinely can't be bypassed."

"The framing I'd bring: drift's real cost is loss of trust in the repository. One manual change is usually harmless. The damage is that the definition no longer describes reality, so people stop believing it — and once they stop believing it, they stop using it, and you're back to portal changes with extra ceremony. Protecting that trust is what all of the above is actually for."

What they're really checking
  • Do you investigate before reverting?
  • Do you know an apply will silently revert it later?
  • Do you check the plan for replacement before applying?
  • Do you treat the access as the real problem?
  • Do you provide a break-glass path rather than just forbidding?
  • Do you reach for Azure Policy for unbypassable rules?
Weak answers
  • Red flag: immediately running apply to revert it.
  • Red flag: treating it as a discipline problem only.
  • Red flag: no mechanism to detect it next time.
Likely follow-ups
  • How do you make an urgent change safely at 3am?
  • What if the drifted resource can't be changed back without downtime?
  • Which rules would you put in deny mode first?
