Terraform

Powerful, cloud-agnostic, and the state file is yours to look after. Most Terraform problems are state problems.

Providers and versions 🔥 Must know

terraform {
  required_version = "~> 1.9"          # allow 1.9.x, not 1.10

  required_providers {
    azurerm = {
      source  = "hashicorp/azurerm"
      version = "~> 4.0"                # allow 4.x, not 5.0
    }
    azuread = {
      source  = "hashicorp/azuread"
      version = "~> 3.0"
    }
  }

  # Remote state - see the next section
  backend "azurerm" {
    resource_group_name  = "rg-tfstate"
    storage_account_name = "sttfstateprod"
    container_name       = "tfstate"
    key                  = "orders/prod.tfstate"
    use_azuread_auth     = true          # no storage key needed
  }
}

provider "azurerm" {
  features {
    resource_group {
      # Refuse to delete a resource group that still contains resources
      prevent_deletion_if_contains_resources = true
    }
  }
  subscription_id = var.subscription_id   # be explicit; do not rely on CLI context
}
Unpinned versions mean the same code produces different infrastructure

Without a version constraint, terraform init takes the latest provider. So a pipeline run today and the same commit run next month can behave differently — new defaults, renamed attributes, changed behaviour.

That breaks the core promise of IaC: the same definition producing the same result. And it breaks it in the most annoying way — an unrelated deployment suddenly shows unexpected changes in the plan, and nobody changed anything.

Pin with ~> so patch and minor updates flow but a major version bump is deliberate. Major provider versions do contain breaking changes — azurerm 4.0 changed several defaults and required explicit subscription ids.

And commit .terraform.lock.hcl. That pins the exact provider versions and their checksums, so every machine and every pipeline run uses identical binaries. It's the same reasoning as committing packages.lock.json, and it's frequently gitignored by mistake.

One more thing worth doing: prevent_deletion_if_contains_resources. It makes an accidental resource-group deletion fail instead of quietly taking everything inside it — a very cheap safety net for the single most destructive mistake available.

RequirementWhy
Remote backendLocal state can't be shared, and is lost with the machine

State holds secrets in plaintext

Anything Terraform knows is in the state file, unredacted. A generated password, a storage account key it read to configure something, a connection string, a certificate.

Marking a variable sensitive = true only hides it from console output. It is still plaintext in state.

So the state container needs to be treated as a credential store: encryption at rest, no public access, RBAC limited to the pipeline identity, and diagnostic logging so you know who read it. Giving every engineer read access to state is equivalent to giving them the secrets.

The better pattern is to not have Terraform generate or handle secrets at all. Create an empty Key Vault secret, let the application or a separate process populate it, and have Terraform reference it rather than know its value. And use managed identity wherever possible so there's no secret to manage — which removes the problem rather than protecting against it.

count versus for_each 🔥 Must know

# count: resources are addressed by INDEX
resource "azurerm_storage_account" "bad" {
  count = length(var.names)             # [0] [1] [2]
  name  = var.names[count.index]
}
# Remove the FIRST name from the list and Terraform sees:
#   [0] name changes  -> REPLACE
#   [1] name changes  -> REPLACE
#   [2] no longer exists -> DESTROY
# One removal destroys and recreates everything after it.


# for_each: resources are addressed by KEY
resource "azurerm_storage_account" "good" {
  for_each = toset(var.names)           # ["alpha"] ["beta"] ["gamma"]
  name     = each.value
}
# Remove "alpha" and Terraform sees:
#   ["alpha"] destroyed
#   ["beta"], ["gamma"] untouched


# for_each over a map gives per-item configuration too
resource "azurerm_linux_web_app" "apps" {
  for_each = {
    orders   = { sku = "P1v3", always_on = true  }
    reports  = { sku = "S1",   always_on = false }
  }

  name                = "app-${each.key}-${var.environment}"
  service_plan_id     = azurerm_service_plan.plans[each.key].id
  site_config { always_on = each.value.always_on }
}
Senior signal — index-based addressing is the bug

This is the most commonly hit Terraform footgun, and explaining why is what demonstrates understanding.

With count, a resource's identity in state is its position: module.x.resource[1]. Remove an item from the middle of the list and everything after it shifts down. Terraform compares state to configuration by address, sees different attributes at each address, and concludes those resources must be replaced.

So removing one item from a list of ten can destroy and recreate nine resources. On storage accounts or databases that's data loss, from what looked like a trivial change.

With for_each, identity is a stable key: module.x.resource["beta"]. Removing "alpha" affects only "alpha".

So for_each unless you specifically want N identical copies where position is meaningless — and even then, keys are usually clearer.

The related trap: for_each keys must be known at plan time. Keying on a value computed from another resource gives "Invalid for_each argument", and the fix is to key on something static — a name from a variable — rather than a generated id.

Modules 🟡 Intermediate

module "orders_api" {
  source = "../../modules/web-app"      # or a registry / git ref with a version

  name                = "orders-api"
  environment         = var.environment
  resource_group_name = azurerm_resource_group.main.name
  location            = var.location

  sku                 = var.app_sku
  min_instances       = var.min_instances
  key_vault_id        = azurerm_key_vault.main.id
  app_settings        = { OrdersDb__Timeout = "30" }

  tags = local.common_tags
}

# Consume outputs rather than reaching into the module's internals
resource "azurerm_role_assignment" "orders_kv" {
  scope                = azurerm_key_vault.main.id
  role_definition_name = "Key Vault Secrets User"
  principal_id         = module.orders_api.principal_id
}
Modules for reuse, not for tidiness

The common mistake is wrapping every resource in a module because it feels organised. That adds indirection with no benefit: every value must be threaded through variables and outputs, plans become harder to read, and refactoring means moving state.

A module is worth creating when the same shape is deployed more than once — several environments, several similar services, or a pattern your organisation wants to standardise (a web app that always has diagnostics, managed identity and the right TLS settings).

For a single deployment, separate .tf files in one configuration gives you organisation with none of the cost. Terraform concatenates them, so network.tf, compute.tf, data.tf is a perfectly good structure.

When you do publish modules, version them and reference a version rather than a branch. A module referenced by branch changes under consumers without warning, which is the same problem as an unpinned provider.

And keep the interface narrow. A module with forty variables that pass straight through to the resource isn't an abstraction — it's the resource with extra steps, and its consumers get no simplification at all.

Environments ⭐ Senior-level

ApproachHowVerdict
Directory per environment envs/dev, envs/prod, each with its own backend key and tfvars The safe default for production
Workspaces One configuration, terraform workspace select prod Convenient, risky — see below
Terragrunt or similar A wrapper generating backend config per environment Good at scale; another tool to learn
Separate repositories Strong isolation Configuration drifts between them over time
Workspaces put production one forgotten command away

Workspaces share one configuration and one backend, distinguished by state key. Which means the currently selected workspace is ambient state on your machine or your pipeline.

Forget to switch, run apply, and you've applied dev's intent to production. There's no confirmation step that names the environment — the plan just shows changes, and they look plausible.

They also encourage conditionals — count = terraform.workspace == "prod" ? 1 : 0 — which accumulate until the configuration is hard to reason about and production's shape is only discoverable by mentally evaluating expressions.

A directory per environment avoids both. The backend key is written down rather than selected, so running in the wrong place requires being in the wrong directory — which is far more visible than a forgotten workspace. Differences are expressed as explicit tfvars files, which are readable.

The cost is some duplication of root-module wiring, and that's what shared modules are for. It's a good trade: duplication you can see beats cleverness you can't.

Workspaces are fine for genuinely ephemeral things — a per-pull-request environment — where the blast radius is nil.

The operations that matter 🔥 Must know

terraform init -upgrade                    # providers per constraints; updates lock file
terraform fmt -recursive                   # formatting, in CI as a check
terraform validate                         # syntax and internal consistency

terraform plan -out=tf.plan                # ALWAYS save the plan
terraform show -json tf.plan | jq '...'    # machine-readable, for policy checks
terraform apply tf.plan                    # apply exactly what was reviewed

# Bring an existing resource under management (no changes made to it)
terraform import azurerm_resource_group.main /subscriptions/.../resourceGroups/rg-prod

# Rename or move a resource WITHOUT destroying it - use a moved block, not state mv
# moved {
#   from = azurerm_linux_web_app.api
#   to   = module.orders_api.azurerm_linux_web_app.this
# }

terraform state list                       # what Terraform believes it owns
terraform state show azurerm_key_vault.main
terraform state rm azurerm_storage_account.old   # FORGET it - does not delete it

terraform plan -refresh-only               # detect drift without proposing changes
terraform force-unlock LOCK_ID             # only after confirming nothing is running
Senior signal — apply the saved plan, not a fresh one

Running terraform apply with no plan file makes Terraform compute a new plan and apply that. Which means what gets applied may not be what was reviewed — state can have changed, someone may have made a portal change, or another apply may have run in between.

Saving with -out and applying that file guarantees the reviewed operations are the executed operations. If reality has moved, the apply fails rather than doing something different, which is exactly the behaviour you want.

In a pipeline that maps naturally: plan on pull request, publish the plan as an artefact, apply that artefact after approval. The approval then means something specific rather than "I approve of the general idea."

Two related habits. terraform show -json makes the plan machine-readable, so a policy check can fail the build on any delete action against a protected resource type — mechanical rather than relying on a reviewer's attention. And moved blocks instead of state mv: a refactor expressed in code, reviewed, and applied by the pipeline, rather than someone running a state-mutating command by hand.

Three commands to be careful with

state rm makes Terraform forget a resource without deleting it. Useful when handing ownership to another team, and dangerous because the resource now exists with nothing managing it. Anything you remove should be recorded somewhere.

force-unlock breaks a state lock. Sometimes necessary after a pipeline is killed mid-run — and if you use it while an apply is genuinely still running, you get concurrent writes and corrupted state. Confirm nothing is running first, always.

-target applies to one resource. Occasionally the right tool for recovering from a broken state, and it produces a partial apply where dependencies weren't evaluated. HashiCorp documents it as exceptional use, and a plan that needs targeting usually indicates a dependency problem worth fixing instead.

Worth knowing the pattern: these are all recovery tools. Reaching for them routinely means something upstream — module structure, state layout, ownership boundaries — is wrong.

Data sources versus resources: who owns it

A resource is something Terraform creates and controls. A data source is something it only reads.

That distinction is how you handle shared infrastructure. If a platform team owns the virtual network, your configuration should reference it as a data source — you read its id and deploy into it, without any ability to modify or destroy it.

Declaring it as a resource in two configurations is the real hazard: both believe they own it, and they fight — each apply reverting the other's changes, with the resource flapping between two definitions.

So exactly one configuration owns each resource, and everyone else reads. Getting that boundary explicit early avoids a class of problem that's very hard to untangle later.

OpenTofu, briefly

Terraform's licence changed from MPL to BSL in 2023, which prompted a fork: OpenTofu, under the Linux Foundation and MPL-licensed.

It's a drop-in replacement for practical purposes, and the ecosystems have started to diverge on newer features.

Worth knowing exists because it may come up as a question about licensing awareness, and because some organisations have adopted it specifically to avoid the BSL. It doesn't change anything about how you write configuration.

Common mistakes

  • Unpinned provider versions, so the same commit behaves differently over time.
  • Gitignoring the lock file.
  • Local state in a team, or a remote backend with no locking.
  • Broad read access to state, which is read access to secrets.
  • count over a list, so removing an item recreates the rest.
  • Everything wrapped in modules for a single deployment.
  • Module references by branch rather than version.
  • Workspaces for production, one forgotten switch from disaster.
  • apply without a saved plan, so the reviewed plan isn't what runs.
  • Not reading the plan for destroy and replace.
  • state mv by hand instead of a reviewed moved block.
  • Two configurations declaring the same resource, fighting over it.
  • Routine use of -target to work around dependency problems.

Interview questions

Intermediate

What is Terraform state, and how do you manage it for a team? 🔥 Must know
How I'd answer

"State is Terraform's record of what it created and how — a mapping from the resources in your configuration to the real resources in Azure, plus their last-known attributes."

"It needs that record to decide what to do. Without it, it can't distinguish 'this should be created' from 'this exists and I made it' from 'this exists and someone else owns it'. And it's how Terraform knows to delete something you removed from the configuration — that's a capability plain scripts don't have."

"For a team, the requirements are fairly firm."

"A remote backend — Azure Storage or Terraform Cloud. Local state can't be shared and is lost with the machine, and 'the state is on Dave's laptop' is a genuine failure mode."

"State locking. Two applies at once produce a state file that matches neither reality nor either intent, and that's harder to fix than either change. The azurerm backend uses blob leases, so it's automatic once you're using it — which is one reason to prefer a proper backend over a plain file share."

"Versioning and soft delete on the container, because state corruption happens and the recovery path is a previous version."

"Restricted access, and this is the point people miss: state contains secrets in plaintext. Any generated password, any key Terraform read, any connection string. Marking a variable sensitive only hides it from console output — it's still plaintext in state. So read access to state is effectively read access to those secrets, and it should be limited to the pipeline identity rather than granted to everyone."

"Which leads to a design preference: try not to have Terraform handle secrets at all. Create an empty Key Vault secret and let something else populate it, and use managed identity wherever possible so there's no secret to store. That removes the problem instead of guarding it."

"Separate state per environment, so a mistake in dev cannot reach production. I'd do that with a directory per environment and a distinct backend key, rather than workspaces — because a workspace is ambient state, and forgetting to switch means applying dev's intent to production with nothing naming the environment in the plan."

"And I'd scope state by blast radius and change frequency. One enormous state file means every plan touches everything, plans get slow, and unrelated changes contend for the same lock. Splitting — networking separately from applications, since networking changes rarely — limits what any one apply can damage. The cost is cross-state references, which is what data sources or remote state outputs are for."

"On failure recovery, the commands worth knowing are terraform import to bring an existing resource under management, state rm to make Terraform forget one without deleting it, and force-unlock for a stuck lock — with the caveat that using force-unlock while an apply is genuinely running causes exactly the corruption you were avoiding."

"The framing I'd offer: the state file is production infrastructure. Losing it is a serious incident — Terraform no longer knows anything it created, the next apply tries to recreate everything, and recovery means importing resources by hand. It deserves backup, access control and monitoring like anything else critical."

What they're really checking
  • Can you explain why state is necessary at all?
  • Do you know locking prevents concurrent corruption?
  • Do you know state contains plaintext secrets?
  • Do you separate state per environment, and why not workspaces?
  • Do you think about blast radius when sizing state?
Weak answers
  • Red flag: "it's a file that tracks resources" and nothing more.
  • Red flag: committing state to Git.
  • Red flag: unaware that secrets are in state.
Likely follow-ups
  • What happens if you lose the state file?
  • How would you split one large state?
  • How do you reference a resource in another state?

Advanced

A plan shows your production database will be destroyed and recreated. What now? ⭐ Senior-level
How I'd answer

"First: I don't apply it. And I'd say that plainly, because the correct first action is to stop, not to investigate while the pipeline is waiting on an approval."

"Then I'd find out which attribute is forcing replacement. The plan tells you — Terraform annotates the specific line with # forces replacement. That one line is the whole diagnosis."

"The usual causes, and they're all mundane:"

"A change to an immutable property. Some attributes can't be altered after creation — a resource's name, its location, sometimes a SKU family or a network configuration. Azure has no update operation for them, so the only way to reach the declared state is delete and create."

"A drifted value being corrected. Someone changed something in the portal that happens to be immutable, so Terraform now sees a difference it can only resolve by replacing."

"A provider upgrade changing behaviour — a default that shifted, or an attribute that's now handled differently. This is why pinning versions matters, and why a major provider bump gets its own pull request rather than riding along with something else."

"A refactor. Renaming a resource or moving it into a module changes its address, and Terraform reads that as 'the old one is gone, create a new one'. Nothing about the infrastructure actually changed."

"What I'd do depends on which it is."

"If it's a refactor, that's the easy one — a moved block tells Terraform the resource's address changed without touching the resource. In older versions that was state mv; the moved block is better because it's in code, reviewed, and applied by the pipeline rather than run by hand."

"If it's drift, I'd decide which side is right. If the portal change was correct, bring it into the configuration so the plan goes quiet. If it wasn't, then replacement might be genuinely required — and that's a planned maintenance operation, not a deployment."

"If it's a genuinely immutable property that must change, then this is a migration, and I'd treat it as one: provision the new resource alongside the old, migrate the data, verify, cut over, and decommission afterwards. Never a single apply. That's usually create_before_destroy in the lifecycle block, plus real steps for the data — and for a database the data movement dominates the plan, not the Terraform."

"If it's a provider upgrade, I'd revert the upgrade, verify the plan is clean, then upgrade separately and read the changelog. Isolating the variable is worth the extra cycle."

"Then the more important half: this shouldn't have been possible to apply by accident, so I'd fix the guardrails."

"prevent_destroy in a lifecycle block on the database. Then a plan that would destroy it errors instead of proceeding. It's slightly inconvenient when you genuinely want to replace something, and that inconvenience is the point."

"An Azure resource lock as a second layer, so even something outside Terraform can't delete it."

"Automated plan inspection. terraform show -json makes the plan machine-readable, so CI can fail the build on any delete action against a protected resource type. That's mechanical rather than depending on a reviewer noticing — and a reviewer scanning a 200-line plan at 5pm will miss it."

"Plan output posted to the pull request, with a required check on destructive operations. The plan is the review artefact, not the code diff — a one-line variable change can produce a destroy, and nothing in the diff hints at it."

"And the structural point: state stored where it can't be corrupted, and backups verified, because the mitigation of last resort for any destructive infrastructure change is a restore. If I can't say confidently when the database was last successfully restored — not backed up, restored — then that's the real finding here."

What they're really checking
  • Do you stop rather than investigate mid-apply?
  • Do you know the plan names the forcing attribute?
  • Do you know moved blocks for refactors?
  • Do you treat a genuine replacement as a migration?
  • Do you add prevent_destroy and automated plan checks?
  • Do you mention verified restores?
Weak answers
  • Red flag: applying it because the plan said so.
  • Red flag: using -target to skip the database.
  • Red flag: fixing this instance with no guardrail added.
Likely follow-ups
  • How would you migrate a database that genuinely must be replaced?
  • How do you enforce no-destroy in CI?
  • What does create_before_destroy do, and when does it not help?
