Infrastructure as Code

The point isn't automation. It's that infrastructure becomes something you can review, test and reason about — and that nobody can change it by clicking.

🟡 Intermediate 🔥 Must know
Quick revision
  • Declarative: describe the end state. The tool works out the steps.
  • State is how the tool knows what it created and what changed.
  • Drift is reality diverging from the declaration — usually a manual change.
  • Idempotent: applying the same definition twice changes nothing the second time.
  • Immutable: replace rather than modify in place.
  • Plan before apply, always. The plan is the review artefact.
  • The real value is review and reproducibility, not speed.

"It automates provisioning" is the usual answer and it's the weakest of the benefits. Most teams provision infrastructure rarely, so the time saved is modest.

The properties that actually matter:

Infrastructure changes become reviewable. Opening a firewall port or removing a backup policy arrives as a diff with an author and a reason, and someone else looks at it. That's a control you cannot achieve with portal access, and it catches the changes that cause incidents.

It's reproducible. Standing up an identical environment stops being a project. Which makes realistic testing possible, and makes disaster recovery a procedure rather than an improvisation.

It's the documentation, and it can't go stale — because it's what's actually deployed.

It eliminates snowflakes. The server nobody dares touch because someone configured something by hand three years ago and left.

Framing it that way — governance and reproducibility, with automation as a side effect — is the more senior read, and it's what makes the case to people who don't provision anything themselves.

Declarative versus imperative 🔥 Must know

ImperativeDeclarative
You writeThe stepsThe desired end state
Exampleaz webapp create ...A Terraform or Bicep resource block
Run twiceFails or duplicatesSecond run is a no-op
Handles partial stateYou write the checksThe tool reconciles
Deleting somethingYou must remember to script itRemove it from the definition
Good forOne-off operations, glueAnything you'll maintain
Think of it this way

Imperative is a recipe: heat the pan, add the oil, add the onions. Run it twice and you have two pans of onions — or an error because the pan is already hot.

Declarative is a photograph of the finished dish. The tool compares the photo to what's on the counter and does whatever is needed to match. Compare again and there's nothing to do.

Which is why declarative scales to real infrastructure: you don't have to know the current state to write a correct change.

The property that matters most: removal

The difference people underestimate is what happens when something should stop existing.

With scripts, deleting a resource means writing a deletion script — and remembering that it exists at all. In practice it doesn't happen, so orphaned resources accumulate: storage accounts nobody uses, public IPs still billing, network rules nobody can justify keeping.

Declaratively, you delete the block and the tool removes the resource, because the definition is the complete statement of what should exist. Anything not in it shouldn't be there.

That's also the property that makes IaC an audit tool: if it isn't in the repository, it shouldn't exist — so anything unaccounted for is worth investigating. You can't say that with scripts.

It's also the property that makes IaC dangerous, which is why plan matters so much. The same mechanism that cleans up orphans will happily delete a production database if you remove the wrong block.

State 🔥 Must know

Why a tool needs it

To decide what to change, the tool must know what it created and how. That record is state.

Without it, the tool can't tell "this resource should be created" from "this resource exists and I made it" from "this exists and someone else owns it."

ApproachWhere state livesConsequence
Terraform An explicit state file you must store and lock Full lifecycle control, including deletion. The state file is critical infrastructure
Bicep / ARM Azure itself — the resource graph is the state Nothing to manage or lose. Less control over deletion semantics
Kubernetes / GitOps The cluster's etcd, reconciled continuously Drift is corrected automatically, not just detected
Terraform's state file is production infrastructure

This is the single biggest operational difference between Terraform and Bicep, and it's worth being precise about.

Lose the state file and Terraform no longer knows anything it created. The next apply tries to create everything again — and fails on name conflicts, or worse, creates duplicates alongside the originals. Recovery means importing every resource by hand.

Two people applying at once without locking produces a corrupted state that doesn't match reality, which is harder to fix than either individual change.

State contains secrets. Generated passwords, connection strings and keys are stored in plaintext in the state file — so it needs the same protection as a credential store, not just a bucket.

So the non-negotiables: a remote backend (Azure Storage or Terraform Cloud) with state locking, versioning and soft delete on the container, encryption at rest, and access restricted to the pipeline identity rather than to every engineer.

Bicep avoids this entire category because Azure's own resource graph is the state. There's nothing to store, lock, back up or leak. That's a genuine advantage, and the trade is that you get less control over lifecycle — Bicep is weaker at knowing when to remove something.

Drift 🔥 Must know

What it is

Reality no longer matches the definition. Almost always because someone changed something directly — in the portal, with the CLI, or via an automated process outside IaC.

Why drift happensWhat to do about it
An emergency fix during an incidentExpected. Reconcile afterwards, don't pretend it won't happen
Someone has portal write accessRemove it — read-only for humans, write for the pipeline
Another tool or team manages part of itMake ownership explicit; use data sources rather than resources
Azure adds or changes a defaultPin versions; expect occasional plan noise
Nobody ever runs a planScheduled drift detection
Senior signal — the dangerous part of drift is silence

A single manual change is usually harmless in itself. The damage is what it does to trust.

Once the definition doesn't match reality, the next apply will revert that change — possibly during an unrelated deployment, weeks later, with no obvious connection. That's how an emergency firewall rule quietly disappears and an outage returns.

Worse, people stop believing the repository. And once nobody trusts it, they stop using it, and you're back to portal changes with extra ceremony.

So the practices that matter: scheduled drift detection — a nightly plan that alerts on any diff, so drift is found in hours rather than at the worst moment. Read-only portal access for humans, with the pipeline identity holding write permission, so drift becomes difficult rather than merely discouraged. And an explicit break-glass path: a documented way to make an emergency change with elevated access, logged, and a required follow-up to reconcile the code.

That last one is the mature position. Pretending emergency changes won't happen guarantees they happen undocumented. Planning for them keeps the repository trustworthy.

Idempotency and immutability 🟡 Intermediate

PropertyMeansWhy it matters
Idempotent Applying twice has the same effect as once A failed run can be retried safely
Immutable Changes replace rather than modify in place No accumulated state; the new thing is exactly as defined
Immutable infrastructure, and where it stops

The immutable approach — build a new VM image or container image and replace the running instance rather than patching it — removes configuration drift entirely at that layer. There's no long-lived machine to accumulate hand-edits, and every instance is byte-identical.

That's why containers fit IaC so naturally: the image is the immutable artefact, and deployment replaces rather than updates.

It doesn't apply everywhere. Stateful resources can't be replaced casually — a database holds data, so "delete and recreate" is not available. That's the distinction worth carrying: immutable for compute, careful in-place change for data.

Which is exactly where IaC needs the most care. A parameter change that Azure implements by replacing a resource is fine for an App Service and catastrophic for a SQL database. The plan output tells you which — if you read it, and reading it properly is the discipline the whole workflow depends on.

The workflow 🔥 Must know

  write / change definition
        |
        v
  validate + lint        syntax, policy rules, security checks
        |
        v
  PLAN                   what WOULD change - posted to the pull request
        |
        v
  review                 a human reads the plan, not just the code diff
        |
        v
  APPLY                  pipeline identity only, never a laptop
        |
        v
  drift detection        scheduled plan; alert on any difference
The plan is the review artefact, not the code

A code diff shows what someone wrote. The plan shows what will actually happen, and they can differ dramatically.

A one-line change to a parameter can produce a plan containing -/+ destroy and then create replacement on a database. Nothing in the diff hints at that. You only see it in the plan.

So the practice is to post the plan into the pull request and require someone to read it — specifically looking for destroy and replace operations. That's the single highest-value habit in IaC, and it's what turns "we use Terraform" into "we use Terraform safely."

Two supports worth having. Policy checks in CI — Checkov, tfsec, Azure Policy — so "public network access enabled" is caught mechanically rather than depending on a reviewer noticing. And resource locks or prevent_destroy on genuinely irreplaceable resources, so an accidental deletion fails rather than succeeding.

Structural, not procedural — the same principle as everywhere else. A rule the tooling enforces beats a rule people are asked to remember.

Key takeaways
  • The value is review, reproducibility and governance — automation is a side effect.
  • Declarative means you don't need to know the current state to write a correct change.
  • Removal is the property scripts don't give you: delete the block, the resource goes.
  • State is how a tool knows what it owns.
  • Terraform's state file is critical infrastructure and contains secrets.
  • Bicep avoids state entirely because Azure's resource graph is the state.
  • Drift's real cost is loss of trust in the repository.
  • Scheduled drift detection plus read-only portal access for humans.
  • Plan an explicit break-glass path — emergencies will happen.
  • Immutable for compute; careful in-place change for data.
  • Read the plan for destroy and replace operations — the code diff won't show them.
  • Policy checks and resource locks make safety structural.

Interview questions

Intermediate

Why use Infrastructure as Code rather than the portal? 🔥 Must know
How I'd answer

"I'd put automation last, because it's the weakest of the benefits — most teams provision infrastructure rarely, so the time saved isn't the point."

"The strongest reason is reviewability. With IaC, opening a firewall port or removing a backup policy arrives as a pull request with an author, a reason and a reviewer. In the portal it's a click nobody sees. That's a genuine control, and it catches exactly the changes that cause incidents — particularly security-relevant ones where the person making the change doesn't realise the implication."

"Second, reproducibility. Standing up an identical environment stops being a project. Which makes realistic testing practical, and turns disaster recovery from an improvisation into a procedure you can rehearse."

"Third, it's documentation that can't go stale, because it's what's actually deployed. The question 'why is this configured like that?' becomes answerable with git blame — usually the hardest question to answer about inherited infrastructure."

"Fourth, no snowflakes. No server nobody dares touch because someone configured something by hand years ago and left."

"There's a property worth calling out specifically: declarative IaC handles removal. With scripts you have to remember to write a deletion script, so in practice orphaned resources accumulate — storage accounts nobody uses, public IPs still billing. Declaratively you delete the block and the resource goes, because the definition is the complete statement of what should exist. That's also what makes it an audit tool: if it isn't in the repository, it shouldn't exist."

"I'd be honest about the costs, because they're real. There's a learning curve, and simple changes take longer than a click. State management is a genuine operational concern with Terraform. And drift becomes a new problem you have to manage — someone makes a portal change during an incident, and now the code lies."

"On drift specifically, the mature position is that emergency manual changes will happen, so I'd plan for them: a documented break-glass path with elevated access, logged, and a required follow-up to reconcile the code. Pretending they won't happen just guarantees they happen undocumented."

"And I'd pair IaC with read-only portal access for humans, with write permission held by the pipeline identity. Otherwise IaC is advisory — a convention people follow when convenient. That's the difference between using it and relying on it, and it's the same structural-not-procedural principle that applies to any control."

"Where I wouldn't insist on it: genuinely throwaway exploration. Clicking around to learn a service is fine. The rule is that anything that lives becomes code, and anything long-lived created by hand gets imported."

What they're really checking
  • Do you lead with governance rather than automation?
  • Do you value reproducibility for testing and DR?
  • Do you know declarative handles removal?
  • Are you honest about the costs and about drift?
  • Do you restrict portal write access?
Weak answers
  • Red flag: "it's faster" as the main argument.
  • Red flag: no awareness of drift or state.
  • Red flag: claiming manual changes simply won't happen.
Likely follow-ups
  • Someone changed a setting in the portal. What now?
  • How do you bring existing resources under IaC?
  • Who should be allowed to run apply?
