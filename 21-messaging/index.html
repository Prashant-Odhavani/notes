Messaging Patterns In Depth

Queues look simple until you meet ordering, duplicates and poison messages. All three arrive in production, not in testing.

🟡 Intermediate 🔴 Advanced 🔥 Must know
Quick revision
  • Queue = one consumer gets each message (competing consumers). Topic = every subscriber gets a copy (fan-out).
  • Delivery is at-least-once. Duplicates are guaranteed, not exceptional.
  • A dead-letter queue is mandatory — and so is monitoring it.
  • Ordering costs throughput, because it forces serial processing per group.
  • Scaling consumers breaks global ordering. You can only order within a partition.
  • A poison message blocks its partition unless you handle it.
  • Publish via an outbox, or you'll lose messages on commit failures.

Queue or topic 🔥 Must know

The distinction

A queue delivers each message to exactly one consumer. Add consumers and you process faster — they compete for messages. That's for work.

A topic delivers a copy to every subscription. Add a subscriber and it gets everything. That's for notification.

QueueTopic / pub-sub

More consumers meansHigher throughputMore copies delivered
Producer knows consumersImplicitly one logical consumerNo — it just publishes

Command or event — the naming tells you which to use

A command is an instruction to one recipient: SendInvoice, ChargeCard. Imperative, one handler, queue.

An event is a statement of fact: OrderPlaced, PaymentReceived. Past tense, any number of interested parties, topic.

If you find yourself publishing SendEmailEvent to a topic, the name is telling you the design is confused — that's a command wearing an event's clothes, and the publisher has taken on knowledge of what should happen.

Senior signal — events invert the dependency

With commands, the sender decides what happens. Adding "also award loyalty points when an order is placed" means changing the order service to send another command.

With events, the order service publishes OrderPlaced and is finished. Loyalty subscribes. Adding a fifth reaction touches nothing in the publisher — so the dependency points from the reactor to the event, not from the publisher to every reactor.

That's genuine decoupling and it's the strongest argument for event-driven design. The cost is that nobody knows the full set of consequences of placing an order — which is a real operational problem when debugging, and why an event catalogue matters.

The nuance: events should describe what happened in the domain, not what should happen next. If your event is OrderPlacedSoSendEmail, you've coupled the publisher to the consumer's purpose and lost the benefit.

Delivery guarantees 🔥 Must know

GuaranteeMeansReality
At-most-onceNever duplicated, may be lostFire-and-forget. Acceptable for metrics

Exactly-onceNever lost, never duplicatedNot achievable at the transport level
Why exactly-once delivery is impossible

A consumer processes a message and crashes before its acknowledgement reaches the broker.

The broker now cannot distinguish "processed but unacknowledged" from "never processed". It has two choices: redeliver (risking a duplicate) or don't (risking loss). There is no third option — the information needed to decide doesn't exist anywhere.

Brokers choose redelivery, because losing messages is worse. So at-least-once is the honest guarantee, and any product advertising exactly-once is doing deduplication somewhere and calling it delivery.

What you can achieve is at-least-once delivery plus idempotent processing, which produces an exactly-once effect. That's what exactly-once always means in practice, and being precise about it is a strong signal — it's the same ambiguous timeout problem as HTTP.

public async Task ConsumeAsync(OrderPlaced msg, CancellationToken ct)
{
    await using var tx = await _db.Database.BeginTransactionAsync(ct);

    // Unique constraint on MessageId is what makes this correct
    _db.ProcessedMessages.Add(new ProcessedMessage(msg.MessageId, DateTime.UtcNow));

    try
    {
        await _db.SaveChangesAsync(ct);
    }
    catch (DbUpdateException) when (IsUniqueViolation)
    {
        return;                     // already processed - acknowledge and move on
    }

    await DoTheWorkAsync(msg, ct);  // the work
    await _db.SaveChangesAsync(ct);
    await tx.CommitAsync(ct);       // dedupe record and work commit TOGETHER
}
The detail that makes it correct

The dedupe record and the work must commit in the same transaction.

If you record the message id and commit, then do the work separately, a crash between them leaves the message marked processed but the work never done. You've converted duplicate delivery into lost work, which is strictly worse — and it's silent.

Also: prune the dedupe table. It grows forever otherwise. A TTL slightly longer than the broker's maximum redelivery window is sufficient.

Retries and dead-letter queues 🔥 Must know

Two kinds of failure, two responses

Transient — a network blip, a timeout, a throttled dependency. Retrying works.

Permanent — malformed payload, a referenced entity that doesn't exist, a business rule violation. Retrying will never work.

Treating the second as the first is how you get a message retried ten thousand times.

LayerPurposeTypical
Immediate retryMomentary blips3 attempts, milliseconds apart
Delayed retryA dependency that needs timeExponential backoff with jitter, minutes
Dead-letter queueGive up; preserve the messageAfter retries are exhausted
 
public async Task ConsumeAsync(ConsumeContext<ChargeCard> ctx)
{
    try
    {
        await _payments.ChargeAsync(ctx.Message, ctx.CancellationToken);
    }
    catch (HttpRequestException)          // transient - let the retry policy work
    {
        throw;
    }
    catch (CardDeclinedException ex)      // PERMANENT - retrying is pointless
    {
        _logger.LogWarning(ex, "Card declined for {OrderId}", ctx.Message.OrderId);
        await ctx.Publish(new PaymentFailed(ctx.Message.OrderId, ex.Reason));
        return;                           // acknowledge - do NOT retry or dead-letter
    }
}
Senior signal — a DLQ nobody monitors is a silent data-loss mechanism

Every guide says "use a dead-letter queue". Far fewer mention that an unmonitored DLQ is worse than no DLQ.

Messages arrive there, nobody notices, and the business consequence surfaces weeks later — orders never fulfilled, invoices never sent. The system reported no errors, because dead-lettering is the designed error path.

So a DLQ needs three things: an alert on depth greater than zero — not a threshold, because any dead letter is by definition unhandled; enough context to diagnose, meaning the original message plus the exception and the trace id; and a documented replay path, because the whole point is that these messages can be reprocessed after a fix.

The replay path is the one that's usually missing. Teams dead-letter diligently for a year, then discover they have no tooling to resubmit and have to write it during an incident.

Poison messages block their partition

In an ordered stream — a Service Bus session, a Kafka partition — the consumer cannot skip a message without breaking ordering. So a message that always fails blocks everything behind it, indefinitely.

One malformed order stalls every subsequent order for that customer. The queue depth grows and nothing progresses.

Options, and each is a real trade-off: dead-letter it and continue, accepting an ordering gap; park the whole partition and alert, preserving order at the cost of availability; or fail the consumer and force intervention.

Most systems choose dead-letter-and-continue, which means you've chosen availability over strict ordering — and that should be a deliberate decision, since it can leave the downstream state inconsistent in a way that needs reconciliation.

Knowing that ordering and poison-message handling are in direct tension is a strong signal.

Ordering 🔥 Must know

The fundamental tension

Ordering requires serial processing. Throughput requires parallel processing.

You cannot have both globally. What you can have is ordering within a partition, parallelism across partitions.

So the design question is: what is the smallest scope that genuinely needs ordering? Usually one entity — one order, one account, one device.

// Azure Service Bus: SessionId groups messages for ordered, single-consumer processing
await sender.SendMessageAsync(new ServiceBusMessage(payload)
{
    SessionId = order.Id.ToString(),      // all messages for this order, in order
    MessageId = eventId.ToString()        // for deduplication
});

// Kafka: the partition key does the same job
await producer.ProduceAsync("orders", new Message<string, string>
{
    Key = order.Id.ToString(),            // same key -> same partition -> ordered
    Value = payload
});
Ordering scopeThroughputVerdict
Global — every message in orderOne consumer, everAlmost never a real requirement
Per entity — per order, per accountParallel across entitiesUsually the right answer
NoneMaximumFine if handlers are commutative
Senior signal — design so ordering doesn't matter

Ordering is expensive: it caps parallelism, and it creates the poison-message blocking problem. So the better question is often whether you need it at all.

Techniques that remove the requirement: include a version or sequence number and have the consumer ignore anything older than what it has already applied — so out-of-order arrival is handled rather than prevented. Make handlers commutative, so order genuinely doesn't affect the outcome. Or send state rather than deltas — "the order is now Shipped" is order-independent, where "increment the status" isn't.

That last one is the most useful reframing. SetQuantity(5) is idempotent and order-independent; AddQuantity(2) is neither. Choosing state-based messages over delta-based ones eliminates a whole category of problem.

"I'd try to make ordering unnecessary before paying for it" is a stronger answer than describing how to configure sessions.

Publishing reliably 🔥 Must know

await _db.SaveChangesAsync(ct);                    // database committed
await _bus.Publish(new OrderPlaced(order.Id), ct); // if THIS fails...

// The order exists and nothing downstream knows. No email, no fulfilment,
// no inventory update. And no error the user sees.
//
// Reversing the order is no better: publish then save means consumers can
// react to an order that was never persisted.
// Both the entity and the message go into the SAME transaction
_db.Orders.Add(order);
_db.OutboxMessages.Add(OutboxMessage.For(new OrderPlaced(order.Id)));
await _db.SaveChangesAsync(ct);      // atomic - both or neither

// A background relay reads unsent outbox rows, publishes them,
// and marks them sent. At-least-once, which is why consumers dedupe.
The outbox is the answer to "how do you not lose messages?"

There is no way to make a database commit and a broker publish atomic — they're separate systems, and 2PC is the option nobody wants.

The outbox sidesteps it: the message becomes part of the database transaction, so it can't be lost if the commit succeeds. A relay publishes it afterwards, retrying until the broker accepts.

The consequence is at-least-once publishing — the relay might publish and crash before marking it sent — so consumers must be idempotent. Which they had to be anyway.

In .NET, MassTransit has a transactional outbox that handles the relay, the retries and the deduplication. Hand-rolling it is straightforward but the details — ordering of relay dispatch, cleanup, and avoiding double-publish under concurrent relays — are easy to get subtly wrong.

Practical details 🟡 Intermediate

ConcernGuidance

Versioning A new message type (OrderPlacedV2) rather than changing V1, with both published during transition

The claim-check pattern, and why message size matters

Brokers have hard limits — Service Bus is 256KB on standard tiers, 1MB on premium; Kafka defaults to 1MB.

More importantly, large messages are slow to move and expensive to retry. A 5MB message retried three times is 15MB of traffic for one logical operation, and it occupies broker storage.

Claim check: write the payload to blob storage, put the reference in the message. The message stays small, the payload is fetched only if needed, and retries cost almost nothing.

The trade-off is a second failure mode — the blob might be missing or expired — so lifecycle needs thought: the blob must outlive the maximum redelivery window plus the DLQ retention period, or a replayed message will find nothing.

Trace context does not cross the broker automatically

This is the observability gap that catches people. HTTP calls propagate traceparent automatically; a message publish does not, unless the library adds it.

So without it, the trace ends at "published a message" and the consumer's work appears as an unrelated root trace. Correlating them means matching timestamps and guessing — precisely where the hard bugs live, because asynchronous flows are the ones you can't reason about by reading code.

MassTransit and the Azure SDKs handle this now, but it's worth verifying on a real trace rather than assuming. Publish a message, consume it, and confirm both spans appear under one trace id.

Key takeaways
  • Queue for work (one consumer), topic for notification (all subscribers).
  • Commands go to queues, events to topics — the naming reveals the design.
  • Events invert the dependency; the cost is nobody knowing all the consequences.
  • At-least-once is the real guarantee. Exactly-once is at-least-once plus idempotency.
  • Dedupe record and work must commit in one transaction, or duplicates become lost work.
  • Separate transient from permanent failures — retrying a declined card never helps.
  • An unmonitored DLQ is silent data loss. Alert on depth > 0 and build the replay path.
  • A poison message blocks its partition; ordering and availability are in tension.
  • Order within a partition, parallelise across them. Global ordering is rarely a real requirement.
  • Better still: send state not deltas, so ordering stops mattering.
  • Publish via an outbox — a database commit and a broker publish can't be atomic.
  • Claim check for large payloads; verify trace context crosses the broker.

Common mistakes

  • A topic where a queue was needed, so work is done N times.
  • Command-shaped events — SendEmailEvent — coupling publisher to consumer.
  • Non-idempotent consumers, so redelivery duplicates side effects.
  • Dedupe key committed separately from the work.
  • Retrying permanent failures until the retry limit.
  • No dead-letter queue, so failures vanish.
  • A DLQ nobody monitors.
  • No replay tooling for dead-lettered messages.
  • Global ordering when per-entity would do, capping throughput.
  • Scaling consumers without realising ordering is lost.
  • Dual writes instead of an outbox.
  • Large payloads inline rather than a claim check.
  • Trace context not propagated through the broker.

Interview questions

Intermediate

How do you handle a message that keeps failing? 🔥 Must know
How I'd answer

"The first thing is to distinguish transient from permanent failure, because they need opposite responses and conflating them is the usual bug."

"Transient — a network blip, a timeout, a throttled dependency. Retrying works, so I'd use immediate retries for momentary problems and delayed retries with exponential backoff and jitter for a dependency that needs time to recover."

"Permanent — a malformed payload, a referenced entity that doesn't exist, a declined card. Retrying will never succeed. So retrying a declined card ten times just wastes ten attempts and delays telling anyone. The correct handling is to acknowledge the message and publish a failure event so the saga or the user can respond."

"That's the distinction I'd write into the consumer explicitly — catch the permanent exceptions, handle them, and let everything else propagate to the retry policy."

"For genuine exhaustion, the message goes to a dead-letter queue — it's preserved rather than lost, and can be reprocessed after a fix."

"But the point I'd emphasise is that an unmonitored DLQ is worse than no DLQ. Messages arrive, nobody notices, and the business impact surfaces weeks later — orders never fulfilled, invoices never sent. And there's no error anywhere, because dead-lettering is the designed error path."

"So a DLQ needs three things. An alert on depth greater than zero — not a threshold, because any dead letter is by definition unhandled. Enough context to diagnose: the original message, the exception, and the trace id so I can find the full distributed trace. And a documented replay path, which is the one usually missing — teams dead-letter diligently for a year, then discover during an incident that they have no tooling to resubmit."

"The harder case is a poison message in an ordered stream — a Service Bus session or a Kafka partition. There the consumer can't skip it without breaking ordering, so a message that always fails blocks everything behind it indefinitely. One malformed order stalls every subsequent order for that customer."

"There's no free answer. Dead-letter it and continue, accepting an ordering gap. Park the whole partition and alert, preserving order at the cost of availability. Or fail the consumer and force intervention. Most systems choose dead-letter-and-continue — which means choosing availability over strict ordering, and that should be a deliberate decision, because it can leave downstream state inconsistent in a way needing reconciliation."

"And the preventative point: validate at the boundary. A message that can't be deserialised or fails schema validation should be dead-lettered on the first attempt rather than retried — it's permanently broken, and retrying it three times just delays the inevitable while blocking the partition."

What they're really checking
  • Do you separate transient from permanent?
  • Do you know retrying a business failure is pointless?
  • Do you insist on DLQ monitoring and a replay path?
  • Do you know a poison message blocks an ordered partition?
  • Do you recognise the ordering/availability trade-off?
Weak answers
  • Red flag: "retry until it works".
  • Red flag: a DLQ with no monitoring.
  • Red flag: no awareness of partition blocking.
Likely follow-ups
  • How would you build the replay tooling?
  • How do you avoid re-dead-lettering on replay?
  • What if the poison message is one of a million per hour?

Advanced

You need messages processed in order, but you also need throughput. How? ⭐ Senior-level
How I'd answer

"These are in direct tension: ordering requires serial processing, throughput requires parallel processing. You can't have both globally, so the design work is finding the smallest scope that genuinely needs ordering."

"My first question would be what actually needs to be ordered, because 'we need ordering' is almost always narrower than it sounds. Global ordering across all messages is very rarely a real requirement — usually it's per entity: messages for one order, one account, one device."

"If it's per entity, the answer is partition by that entity. In Service Bus that's a SessionId; in Kafka it's the partition key. Same key means same partition means ordered delivery to a single consumer — and different keys process in parallel."

"So with a thousand orders you get ordering within each order and a thousand-way parallelism across them. That's the answer that satisfies both requirements, and it scales with entity count rather than being capped."

"Two constraints to be honest about. Throughput is bounded by partition count, and in Kafka you can't easily reduce partitions later, so that's a capacity decision made upfront. And a hot key still serialises — if one account generates most of the traffic, that partition is your bottleneck and adding consumers won't help, because you can't split a single key."

"The bigger point I'd make though: I'd first try to make ordering unnecessary, because it's expensive beyond the throughput cost — it also creates the poison-message blocking problem, where one permanently-failing message stalls everything behind it."

"Three ways to remove the requirement."

"Send state rather than deltas. This is the most useful reframing. SetQuantity(5) is order-independent and idempotent — applying it twice or out of sequence gives the same result. AddQuantity(2) is neither. So designing messages as facts about current state rather than increments eliminates the whole category of problem."

"Include a version or sequence number and have the consumer ignore anything older than what it has already applied. That handles out-of-order arrival rather than preventing it, so you keep full parallelism."

"Make handlers commutative where the domain allows it, so order genuinely doesn't affect the outcome."

"So my order of preference: design so ordering doesn't matter; if it does, partition by the entity that needs it; and only consider global ordering if there's a genuine domain requirement — at which point I'd want to understand it properly, because it means one consumer forever and that's a hard ceiling."

"One practical detail: scaling consumers on a plain queue silently breaks ordering. If a team adds instances to clear a backlog without realising the queue wasn't partitioned, they've introduced a subtle correctness bug to fix a throughput problem — and it won't be obvious until something processes out of sequence."

What they're really checking
  • Do you know ordering and throughput are fundamentally in tension?
  • Do you narrow the ordering scope to the entity?
  • Do you know about session ids and partition keys?
  • Do you try to eliminate the requirement first?
  • Do you know state-vs-delta messages matter?
  • Do you know hot keys still serialise?
Weak answers
  • Red flag: "use one consumer" with no partitioning idea.
  • Red flag: claiming you can have both globally.
  • Red flag: no awareness that scaling consumers breaks ordering.
Likely follow-ups
  • What if one entity produces 80% of the traffic?
  • How do you choose the partition count?
  • What happens to ordering when a consumer restarts?
