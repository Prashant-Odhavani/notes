Versioning, OpenAPI & Error Handling

The parts of an API that matter after it ships: how you change it without breaking clients, and how you report failure usefully.

🟡 Intermediate ⭐ Senior-level
Quick revision
  • Adding an optional field is safe. Removing or renaming one is a breaking change.
  • Version in the URL for public APIs — visible, cacheable, easy to route.
  • Every version you support is code you maintain. Version the endpoint, not the whole API, where you can.
  • One global exception handler — never try/catch in every action.
  • ProblemDetails (RFC 7807) is the standard error shape. Use it rather than inventing one.
  • Never leak stack traces to clients. Return a correlation ID they can quote instead.

What actually breaks a client 🔥 Must know

In simple terms

A change is breaking if an existing client that worked yesterday stops working today.

That's a lower bar than people assume — and it depends on how tolerant the client's deserializer is.

ChangeBreaking?Why
Add an optional response field✅ SafeMost deserializers ignore unknown fields
Add an optional request field✅ SafeOld clients just don't send it
Add a required request field❌ BreakingOld clients don't send it and now fail validation
Remove or rename a response field❌ BreakingClients reading it get null or throw
Change a type (int → string)❌ BreakingDeserialization fails
Add an enum value⚠️ Usually breakingStrict clients throw on an unknown value
Make validation stricter❌ BreakingRequests that worked now get 400
Change a status code❌ BreakingClients branch on status
Change default sort order or pagination⚠️ Subtly breakingClients relying on order silently get wrong results
The enum one catches everyone

Adding Refunded to an OrderStatus enum feels additive. But a client whose generated model is a strict enum will throw on a value it's never seen.

Two defences: serialise enums as strings so at least the value is self-describing, and document that clients must tolerate unknown values. If you can't rely on that, adding an enum value is a versioned change.

Versioning strategies 🔥 Must know

StrategyLooks likeProsCons
URL path /api/v2/orders Visible, cacheable, trivial to route and test in a browser Arguably not "RESTful" — the resource didn't change
Query string /api/orders?api-version=2 Easy to add later; keeps one path Easy to omit accidentally; messier caching
Custom header X-Api-Version: 2 Clean URLs Invisible; can't be tested from a browser address bar
Media type Accept: application/vnd.acme.v2+json Most technically correct — versions the representation Awkward for clients; poor tooling support
What to actually pick

URL path versioning, for anything with external consumers.

It loses a purity argument and wins on everything practical: you can see it in a log, share a URL that works, and route it at a gateway without inspecting headers.

builder.Services.AddApiVersioning(options =>
{
    options.DefaultApiVersion = new ApiVersion(1, 0);
    options.AssumeDefaultVersionWhenUnspecified = true;
    options.ReportApiVersions = true;      // advertises supported versions in a response header
})
.AddApiExplorer(options =>
{
    options.GroupNameFormat = "'v'VVV";
    options.SubstituteApiVersionInUrl = true;
});
[ApiController]
[Route("api/v{version:apiVersion}/orders")]
public sealed class OrdersController : ControllerBase
{
    [HttpGet, MapToApiVersion("1.0")]
    public async Task<IActionResult> GetV1() { /* old shape */ }

    [HttpGet, MapToApiVersion("2.0")]
    public async Task<IActionResult> GetV2() { /* new shape */ }

    // Unversioned - shared by both, no duplication
    [HttpDelete("{id:guid}")]
    public async Task<IActionResult> Cancel(Guid id) { /* ... */ }
}
Senior signal — the real cost of versioning

Every supported version is code you maintain, test and secure. Two versions doubles your test matrix; a bug fix has to be applied to both.

So the strong answer isn't "here's how to add v2" — it's how to avoid needing one: additive changes, tolerant readers, serialising enums as strings, and never removing a field until telemetry shows nobody reads it.

And when you do version, have a deprecation plan from day one: announce it, measure who still uses the old version, contact them, then remove it. A v1 that lives forever because nobody measured usage is the actual failure.

Global exception handling 🔥 Must know

[HttpGet("{id:guid}")]
public async Task<IActionResult> Get(Guid id)
{
    try
    {
        var order = await _repo.GetAsync(id);
        return Ok(order);
    }
    catch (Exception ex)
    {
        _logger.LogError(ex, "Failed");
        return StatusCode(500, ex.Message);      // and it leaks internals
    }
}

Three problems: it's repeated in every action, it's inconsistent because each one is written slightly differently, and ex.Message can expose connection strings, file paths or schema details.

public sealed class GlobalExceptionHandler(
    ILogger<GlobalExceptionHandler> log,
    IProblemDetailsService problemDetails) : IExceptionHandler
{
    public async ValueTask<bool> TryHandleAsync(
        HttpContext context, Exception exception, CancellationToken ct)
    {
        // The trace id is what the user quotes and what you search on
        var traceId = context.TraceIdentifier;

        log.LogError(exception, "Unhandled exception. TraceId {TraceId}", traceId);

        var (status, title) = exception switch
        {
            NotFoundException      => (StatusCodes.Status404NotFound, "Resource not found"),
            ValidationException    => (StatusCodes.Status400BadRequest, "Validation failed"),
            ConcurrencyException   => (StatusCodes.Status409Conflict, "The resource was modified"),
            UnauthorizedException  => (StatusCodes.Status403Forbidden, "Not permitted"),
            _                      => (StatusCodes.Status500InternalServerError, "An error occurred")
        };

        context.Response.StatusCode = status;

        return await problemDetails.TryWriteAsync(new ProblemDetailsContext
        {
            HttpContext = context,
            ProblemDetails = new ProblemDetails
            {
                Status = status,
                Title  = title,
                // NOTE: no exception message, no stack trace
                Extensions = { ["traceId"] = traceId }
            }
        });
    }
}

// Program.cs
builder.Services.AddExceptionHandler<GlobalExceptionHandler>();
builder.Services.AddProblemDetails();

app.UseExceptionHandler();      // FIRST in the pipeline
Production trap — leaking internals in errors

Returning ex.Message or a stack trace to a client is an information disclosure vulnerability. A SqlException message can contain a server name, a database name and column names — enough to help someone attack you.

The pattern is: log everything, return almost nothing. Give the client a stable title and a traceId. When they report a problem, that ID takes you straight to the full detail in your logs.

And check your Development configuration isn't accidentally deployed — the developer exception page is deliberately verbose and must never run in production.

Why ProblemDetails rather than a custom shape

{
  "type": "https://api.example.com/errors/insufficient-stock",
  "title": "Insufficient stock",
  "status": 409,
  "detail": "SKU-1234 has 2 units available, 5 requested.",
  "instance": "/api/v1/orders",
  "traceId": "0HN7A2QK9M3PL:00000003"
}
FieldPurpose
typeA stable URI identifying the error kind. Clients branch on this, not on the message
titleShort human-readable summary. Stable per type
statusThe HTTP status, repeated in the body
detailSpecifics for this occurrence — safe to show a user
traceIdCorrelates to your logs. The single most useful extension

The value of type is that it gives clients something stable to program against. If they branch on title or detail, then improving your error wording becomes a breaking change.

Don't use exceptions for expected outcomes

In simple terms

An exception should mean something went wrong that we didn't plan for.

"Payment declined" and "out of stock" are planned outcomes. They're results, not exceptions.

public async Task<Result<Order>> PlaceAsync(CreateOrder cmd, CancellationToken ct)
{
    if (!await _stock.IsAvailableAsync(cmd.Sku, cmd.Quantity, ct))
        return Result.Failure<Order>(OrderErrors.InsufficientStock);   // not a throw

    // ...
}

Two reasons this matters. Exceptions are slow — throwing is orders of magnitude more expensive than returning a value, and a declined-payment path can be high volume. And it keeps your error metrics honest: if declines throw, your exception rate spikes during a normal busy period and you can't tell real failures from business outcomes.

OpenAPI 🟡 Intermediate

[HttpGet("{id:guid}")]
[ProducesResponseType<OrderResponse>(StatusCodes.Status200OK)]
[ProducesResponseType(StatusCodes.Status404NotFound)]
[ProducesResponseType<ProblemDetails>(StatusCodes.Status409Conflict)]
public async Task<IActionResult> Get(Guid id, CancellationToken ct) { /* ... */ }
app.MapGet("/api/orders/{id:guid}",
    async Task<Results<Ok<OrderResponse>, NotFound>> (Guid id, IOrderRepository repo, CancellationToken ct)
        => await repo.GetAsync(id, ct) is { } o
            ? TypedResults.Ok(OrderResponse.From(o))
            : TypedResults.NotFound());

That's a genuine advantage of TypedResults: the possible responses are in the signature, so the documentation can't drift from the code.

Swashbuckle vs the built-in generator

.NET 9 ships a built-in OpenAPI document generator (AddOpenApi / MapOpenApi), and the project templates no longer include Swashbuckle by default.

The built-in generator produces the document; it doesn't include the Swagger UI. If you want the interactive page you add a UI package separately. Worth verifying against current docs — this area is actively changing.

Don't expose Swagger UI publicly in production

It documents every endpoint, parameter and model — a complete map of your attack surface, and often an interactive client for it.

Either restrict it to non-production, or put it behind authentication. Publishing the OpenAPI document to consumers is fine and useful; publishing an unauthenticated interactive console usually isn't.

Key takeaways
  • Additive changes are safe; removals, renames, type changes and stricter validation are not.
  • Adding an enum value is usually breaking. Serialise enums as strings.
  • URL path versioning wins on practicality. Version the endpoint, not the whole API.
  • Every version is maintenance. Have a deprecation plan before you create v2.
  • One global exception handler, registered first in the pipeline.
  • Log everything, return a title plus a traceId. Never a stack trace.
  • Use ProblemDetails, and give clients a stable type to branch on.
  • Expected business outcomes are results, not exceptions.

Common mistakes

  • Returning ex.Message to clients — information disclosure.
  • try/catch in every action, inconsistently.
  • Exception handler registered late, so it misses earlier middleware.
  • Throwing for expected outcomes like a declined payment — slow, and it pollutes error metrics.
  • Inventing a custom error shape instead of ProblemDetails.
  • Clients branching on the error message, so rewording it breaks them.
  • Creating v2 for an additive change that didn't need it.
  • Supporting v1 forever because nobody measured who uses it.
  • Public Swagger UI in production.

Interview questions

How would you version a public API? ⭐ Senior-level
How I'd answer

"I'd use URL path versioning — /api/v1/orders — for anything with external consumers. There's a purist argument that the resource didn't change so the URL shouldn't, and media-type versioning is more technically correct. But path versioning wins on everything practical: it's visible in logs, you can share a URL that works, you can route it at a gateway without inspecting headers, and it caches cleanly."

"The more important part of the answer is avoiding versions in the first place, because every version I support is code I maintain, test and secure. Two versions doubles the test matrix and means every bug fix gets applied twice."

"So I'd design for additive change. New fields are optional. Enums serialise as strings and clients are told to tolerate unknown values. I don't remove a response field until telemetry shows nobody reads it. And I'd version the endpoint rather than the whole API where possible — if only one response shape changed, only that endpoint needs a v2, and everything else stays shared."

"When a breaking change is genuinely unavoidable, I'd have the deprecation plan before shipping v2: announce it with a date, advertise supported versions in a response header, instrument usage per version so I know who's still on v1, contact those consumers, then remove it. The failure mode I've seen is a v1 that lives for five years because nobody ever measured whether it was still used."

"One more thing I'd mention: for internal service-to-service APIs I'd push much harder on not versioning at all, and instead using tolerant readers plus expand-and-contract — add the new field, migrate consumers, then remove the old one. You control both sides, so you can coordinate."

What they're really checking
  • Can you pick a strategy and justify it against the alternatives?
  • Do you treat versioning as a cost to be avoided rather than a feature?
  • Do you have a deprecation plan, and do you measure usage?
Weak answers
  • Red flag: listing the four strategies with no recommendation.
  • Red flag: no mention of the maintenance cost or deprecation.
Likely follow-ups
  • Which changes are breaking and which aren't?
  • Is adding an enum value breaking?
  • How would you find out who's still calling v1?
How do you handle errors in a Web API? 🔥 Must know
How I'd answer

"One global exception handler rather than try/catch in every action. In .NET 8 that's IExceptionHandler registered with AddExceptionHandler, and UseExceptionHandler goes first in the pipeline so it wraps everything below it."

"The handler maps exception types to status codes — not found to 404, validation to 400, concurrency conflict to 409, everything else to 500 — and returns ProblemDetails, which is the RFC 7807 standard shape. I'd use that rather than inventing one, because clients and tooling already understand it."

"The rule I'd emphasise is log everything, return almost nothing. Never send a stack trace or the exception message to a client — a SqlException message can include the server name, database name and column names, which is genuine information disclosure. Instead I return a stable title and a traceId. When a user reports a problem they quote the ID and it takes me straight to the full detail in the logs."

"I'd also give each error kind a stable type URI, so clients branch on that rather than on the message text. Otherwise improving the wording of an error becomes a breaking change."

"And a design point: I wouldn't use exceptions for expected outcomes. A declined payment or an out-of-stock item is a planned business result, so it returns a result object, not a throw. Two reasons — throwing is expensive and those paths can be high volume, and it keeps error metrics honest. If declines throw, my exception rate spikes on a busy day and I can't distinguish real failures from normal business."

What they're really checking
  • Global handler rather than scattered try/catch?
  • Do you know not to leak exception details, and why?
  • Do you know ProblemDetails and the value of a stable type?
  • Bonus: exceptions vs expected outcomes.
Weak answers
  • Red flag: returning ex.Message or the stack trace.
  • Red flag: try/catch in every controller action.
  • Red flag: always returning 500 regardless of cause.
Likely follow-ups
  • Where exactly in the pipeline does the handler go, and why there?
  • How does the client correlate an error with your logs?
  • 400 or 422 for a business rule violation?
