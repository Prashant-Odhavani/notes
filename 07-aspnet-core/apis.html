Controllers, Minimal APIs & Binding

How data gets from an HTTP request into your method parameters — and the binding mistake that's actually a security vulnerability.

🟡 Intermediate 🔥 Must know
Quick revision
  • Model binding fills your parameters from the route, query string, body, headers and form.
  • Simple types bind from route/query by default; complex types bind from the body.
  • Over-posting (mass assignment) is the real risk: binding straight to an entity lets a caller set fields you never exposed.
  • [ApiController] gives automatic 400s on validation failure and ProblemDetails responses.
  • Filters are for cross-cutting concerns per endpoint; middleware is for cross-cutting concerns per request.
  • Prefer TypedResults over Results — you get the status codes in OpenAPI for free.

Model binding 🔥 Must know

In simple terms

Model binding is the framework reading the raw HTTP request and filling in your method parameters for you.

You never parse the query string or deserialize the body by hand.

SourceBound by default fromExplicit attribute
Route valuesSimple types matching a route parameter name[FromRoute]
Query stringSimple types not matched by the route[FromQuery]
Body (JSON)Complex types[FromBody]
HeadersNever automatically[FromHeader]
Form fieldsComplex types on form posts[FromForm]
DI containerRegistered services[FromServices]
 
// GET /api/orders/3f2a.../lines?page=2&size=50
[HttpGet("/api/orders/{orderId:guid}/lines")]
public async Task<IActionResult> GetLines(
    Guid orderId,                     // from the route
    int page,                         // from the query string
    int size,                         // from the query string
    [FromHeader(Name = "X-Tenant")] string tenant,
    CancellationToken ct)             // supplied by the framework
{ /* ... */ }
One body parameter only

A request has one body, so you can bind one complex type from it. Two [FromBody] parameters is a runtime error.

If you need several things, wrap them in one request object — which you should be doing anyway, per the over-posting section below.

Over-posting — a binding bug that's a security hole 🔥 Must know

public class Order
{
    public Guid Id { get; set; }
    public string CustomerId { get; set; } = "";
    public decimal Total { get; set; }
    public OrderStatus Status { get; set; }      // internal
    public bool IsInternalTestOrder { get; set; } // internal
    public decimal DiscountApplied { get; set; }  // internal!
}

[HttpPost("/api/orders")]
public async Task<IActionResult> Create(Order order) { /* ... */ }

The client controls the whole JSON body. So they can send:

{
  "customerId": "acme",
  "total": 100.00,
  "status": "Paid",
  "discountApplied": 99.99,
  "isInternalTestOrder": true
}

Nothing is malformed. The binder does exactly what it's designed to do. Your order is now marked paid with a 99.99 discount, and it never went near a payment provider.

Remember this

Never bind a request body directly to an entity.

Bind to a request DTO containing only the fields a caller is allowed to set, then map.

// The contract: exactly what a caller may send. Nothing else exists to set.
public sealed record CreateOrderRequest(
    [property: Required] string CustomerId,
    [property: MinLength(1)] IReadOnlyList<OrderLineRequest> Lines);

[HttpPost("/api/orders")]
public async Task<IActionResult> Create(CreateOrderRequest request, CancellationToken ct)
{
    // Status, discount and totals are decided HERE, by the domain - not by the caller.
    var order = Order.Create(request.CustomerId, request.Lines);
    await _repo.AddAsync(order, ct);
    return CreatedAtAction(nameof(Get), new { id = order.Id }, OrderResponse.From(order));
}

Two benefits beyond security. The DTO documents the contract, so OpenAPI shows callers exactly what's accepted. And it decouples your API from your database schema — you can rename an entity property without breaking clients.

Validation 🔥 Must know

public sealed class CreateCustomerRequest
{
    [Required, EmailAddress]
    public string Email { get; init; } = "";

    [Required, StringLength(100, MinimumLength = 2)]
    public string Name { get; init; } = "";

    [Range(18, 120)]
    public int Age { get; init; }
}

With [ApiController] on the controller, a failed validation returns 400 automatically, formatted as ProblemDetails with the field errors — you write no code for it.

{
  "type": "https://tools.ietf.org/html/rfc7231#section-6.5.1",
  "title": "One or more validation errors occurred.",
  "status": 400,
  "errors": {
    "Email": [ "The Email field is not a valid e-mail address." ],
    "Age": [ "The field Age must be between 18 and 120." ]
  }
}

Where validation belongs

Request validation checks the shape — required fields, formats, ranges. It answers "is this a well-formed request?"

It does not replace domain invariants. "Total must equal the sum of the lines" or "cannot ship an unpaid order" belong in the domain object, where they can't be bypassed by another code path — see encapsulation.

A rule that only exists in a request validator is a rule that a background job or an admin tool will violate.

Returning results 🟡 Intermediate

app.MapGet("/api/orders/{id:guid}",
    async Task<Results<Ok<OrderResponse>, NotFound>> (
        Guid id, IOrderRepository repo, CancellationToken ct) =>
{
    var order = await repo.GetAsync(id, ct);
    return order is null
        ? TypedResults.NotFound()
        : TypedResults.Ok(OrderResponse.From(order));
});

The Results<Ok<T>, NotFound> return type declares the possible responses, so OpenAPI generates accurate documentation with no [ProducesResponseType] attributes. With plain IResult the framework has no idea what you might return.

SituationReturn
Read succeeded200 Ok(dto)
Created something201 Created + a Location header
Accepted for later processing202 Accepted + a status URL
Succeeded, nothing to return204 NoContent
Malformed request400 BadRequest
Not found or not yours404 NotFound
Business rule violated409 Conflict or 422
Why 404 for "not yours"

Returning 403 for a record that belongs to another tenant confirms that the record exists, which lets an attacker enumerate valid IDs.

404 leaks nothing. See resource authorization.

Filters 🟡 Intermediate

In simple terms

Middleware runs for every request, before routing decides anything.

Filters run around a specific endpoint, and they know which endpoint it is and what the bound arguments are.

Use middleware whenUse a filter when
It applies to every requestIt applies to some endpoints
You need it before routing (HTTPS redirect, CORS)You need the model-bound arguments
It's transport-levelIt's application-level
Examples: correlation ID, compression, exception handlingExamples: audit logging with the entity ID, per-action caching
 
public sealed class AuditFilter(ILogger<AuditFilter> log) : IEndpointFilter
{
    public async ValueTask<object?> InvokeAsync(
        EndpointFilterInvocationContext context, EndpointFilterDelegate next)
    {
        // Filters can see the BOUND arguments - middleware cannot
        var request = context.Arguments.OfType<CreateOrderRequest>().FirstOrDefault();
        log.LogInformation("Creating order for {CustomerId}", request?.CustomerId);

        return await next(context);
    }
}

app.MapPost("/api/orders", CreateOrder).AddEndpointFilter<AuditFilter>();

That's the distinction that matters: the filter can read CreateOrderRequest.CustomerId because binding has already happened. Middleware would have to parse the body itself — and consuming the body stream would break the endpoint.

Controllers vs minimal APIs, concretely 🟡 Intermediate

// Controller
[ApiController]
[Route("api/orders")]
public sealed class OrdersController(IOrderRepository repo) : ControllerBase
{
    [HttpGet("{id:guid}")]
    [ProducesResponseType<OrderResponse>(200)]
    [ProducesResponseType(404)]
    public async Task<IActionResult> Get(Guid id, CancellationToken ct)
    {
        var order = await repo.GetAsync(id, ct);
        return order is null ? NotFound() : Ok(OrderResponse.From(order));
    }
}

// Minimal API
app.MapGet("/api/orders/{id:guid}",
    async Task<Results<Ok<OrderResponse>, NotFound>> (
        Guid id, IOrderRepository repo, CancellationToken ct) =>
{
    var order = await repo.GetAsync(id, ct);
    return order is null ? TypedResults.NotFound() : TypedResults.Ok(OrderResponse.From(order));
});

Note that the minimal version needs no [ProducesResponseType] attributes — the return type carries that information.

Keeping minimal APIs organised

The failure mode is forty endpoints in Program.cs. Group them into extension methods per feature:

// Features/Orders/OrderEndpoints.cs
public static class OrderEndpoints
{
    public static void MapOrderEndpoints(this WebApplication app)
    {
        var group = app.MapGroup("/api/orders")
                       .RequireAuthorization()
                       .WithTags("Orders");

        group.MapGet("/{id:guid}", GetOrder);
        group.MapPost("/", CreateOrder);
    }
}

// Program.cs stays one line per feature
app.MapOrderEndpoints();

That gives you minimal-API brevity with controller-like discoverability.

Key takeaways
  • Simple types bind from route/query, complex types from the body. One body parameter only.
  • Never bind the body to an entity — over-posting lets callers set internal fields.
  • Request DTOs make the contract explicit and decouple the API from the schema.
  • [ApiController] gives automatic 400 + ProblemDetails on validation failure.
  • Request validation checks shape; domain invariants belong in the domain.
  • Filters see bound arguments; middleware doesn't. That's how you choose.
  • TypedResults documents your status codes automatically.
  • Return 404, not 403, for records that aren't the caller's.

Common mistakes

  • Binding to EF entities — over-posting, and it couples your API to your schema.
  • Returning entities directly, leaking internal fields and creating circular references in JSON.
  • Validation rules only in the request validator, so other code paths bypass them.
  • Reading the body in middleware without enabling buffering, so the endpoint gets nothing.
  • Returning 200 with an error object instead of a proper status code.
  • Forgetting CancellationToken on the action signature.
  • Route constraints used as validation, giving 404 where 400 was intended.
  • All minimal API endpoints in Program.cs.

Interview questions

What is over-posting and how do you prevent it? 🔥 Must know
How I'd answer

"Over-posting — sometimes called mass assignment — is when you bind a request body directly to an entity, and the caller sets properties you never intended to expose."

"The concrete example: an Order entity with Status and DiscountApplied properties. If the endpoint takes Order as its parameter, a client can post JSON that sets status to Paid and discount to 99.99. Nothing is malformed — the binder is doing exactly what it's designed to do. You've just let the client decide fields the business logic owns."

"The fix is a request DTO containing only what a caller may legitimately send — CustomerId and the lines, say. Status and discount are then decided by the domain, and there's literally no property for the client to set."

"That has two other benefits worth mentioning. It documents the contract, so OpenAPI shows callers exactly what's accepted. And it decouples the API from the database schema — I can rename an entity property without it becoming a breaking API change."

"I'd do the same on the way out. Returning entities directly leaks internal fields, and with EF it also risks serializing navigation properties into circular references or accidentally triggering lazy loads during serialization."

"If for some reason I couldn't introduce a DTO, the older mitigation is a binding include list — [Bind(nameof(Order.CustomerId))] — but that's a denylist-by-omission and easy to get wrong when someone adds a property. The DTO is the structural fix."

What they're really checking
  • Do you know this is a security issue, not a style preference?
  • Can you give a concrete exploitable example?
  • Do you apply the same reasoning to responses?
Weak answers
  • Red flag: not knowing the term or the risk.
  • Red flag: "validate the input" — validation doesn't stop a caller setting a field that passes validation.
Likely follow-ups
  • Where should mapping between DTO and entity live?
  • How do you avoid writing three near-identical classes per endpoint?
  • What goes wrong if you return EF entities from an API?
When would you use a filter instead of middleware?
How I'd answer

"The deciding factor is whether I need to know which endpoint is running and what its arguments are."

"Middleware runs before routing has necessarily resolved an endpoint, and it only sees the raw HttpContext. That's right for transport-level concerns that apply to everything — exception handling, HTTPS redirection, CORS, response compression, adding a correlation ID."

"Filters run around a specific endpoint, after model binding. So they can see the bound arguments and the endpoint metadata. That's what you need for application-level concerns — audit logging that includes the customer ID from the request, per-action caching, or a validation filter."

"The concrete example: if I want to log the customer ID on order creation, a filter can just read it from the bound CreateOrderRequest. Middleware would have to read and parse the body itself — and if it consumes the request stream without enabling buffering, the endpoint then gets an empty body. That's a real bug people hit."

"There's also a scope difference: middleware applies to every request whether you want it to or not, whereas a filter can be attached per endpoint or per route group. So if something applies to some endpoints, a filter is the honest choice rather than middleware with a path check."

"For minimal APIs the mechanism is IEndpointFilter; for controllers it's the fuller filter pipeline with action, result and exception filters."

What they're really checking
  • Do you know filters see bound arguments and middleware doesn't?
  • Do you know the request-body-stream trap?
  • Do you consider scope — all requests vs some endpoints?
Likely follow-ups
  • How do you read the request body in middleware safely?
  • What's the order of the controller filter types?
  • Where would you put a global exception handler — middleware or filter?
