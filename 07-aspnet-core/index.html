ASP.NET Core

The web framework. Built directly on the platform features from the previous section — so if DI and hosting are clear, this is mostly about the request pipeline.

🟡 Intermediate 🔥 Must know
Quick revision
  • A request flows through a pipeline of middleware, in registration order, and back out again.
  • Order matters and mis-ordering rarely errors — it just behaves subtly wrong.
  • Kestrel is the web server. Behind IIS/nginx it's a reverse proxy setup; it can also be public-facing.
  • Minimal APIs and controllers are two front ends over the same routing and binding. Not a performance choice.
  • Everything scoped is scoped per request — which is why the DI material came first.
  • The framework gives you validation, auth, rate limiting and health checks. Don't hand-roll them.

What happens to a request 🔥 Must know

In simple terms

A request enters at the server, passes down through a stack of middleware, reaches your endpoint, and then the response passes back up through the same stack.

  HTTP request
       │
  ┌────▼──────────────────────────────────────────┐
  │ Kestrel  (parses HTTP, TLS, connection limits)│
  └────┬──────────────────────────────────────────┘
       │
  ┌────▼───────────────┐
  │ Exception handler  │  ── wraps everything below it
  ├────────────────────┤
  │ HTTPS redirect     │
  ├────────────────────┤
  │ Static files       │  ── may short-circuit here
  ├────────────────────┤
  │ Routing            │  ── decides WHICH endpoint
  ├────────────────────┤
  │ CORS               │
  ├────────────────────┤
  │ Authentication     │  ── who are you?
  ├────────────────────┤
  │ Authorization      │  ── may you do this?
  ├────────────────────┤
  │ Rate limiting      │
  ├────────────────────┤
  │ Your endpoint      │  ── controller action or minimal API handler
  └────────────────────┘
       │
  response travels back UP through each layer

Two properties of that diagram cause most ASP.NET Core bugs:

  1. Any layer can short-circuit. Static files returns a file and never calls what's below. Authorization can return 403 and stop.
  2. Code runs on the way out too. Anything after await next() executes as the response unwinds — which is how response logging and timing work.

That's the Chain of Responsibility pattern, and the ordering rules are covered in detail on the pipeline page.

Senior signal

Saying "I'd use the built-in rate limiter rather than writing one, because getting the algorithm and the partitioning right is the hard part and it's already solved" reads much better than describing a hand-rolled solution.

The corollary matters too: know where the built-in thing stops being enough. The built-in rate limiter is per-instance, so across three replicas you need a distributed store.

Minimal APIs or controllers? 🟡 Intermediate

A question that comes up in most .NET interviews now, and where the expected answer has shifted.

Minimal APIsControllers
Introduced.NET 6Since the beginning
BoilerplateVery littleA class per group of endpoints
FiltersEndpoint filters (.NET 7+)Full action/result/exception filter pipeline
Model bindingSame underlying systemSame underlying system
DiscoverabilityCan sprawl unless organised deliberatelyConvention makes it obvious where things live
Best forFocused APIs, microservices, vertical slicesLarge APIs with lots of shared cross-cutting behaviour
The honest answer

Performance is not the differentiator. They share routing, binding and the pipeline; minimal APIs have a marginal edge that almost never matters.

Choose on organisation: how many endpoints, how much shared behaviour, and how the team navigates the codebase.

Common mistake with minimal APIs

Putting every endpoint in Program.cs. It's fine for a demo and unusable at forty endpoints.

Group them into extension methods per feature — app.MapOrderEndpoints() — with each feature in its own file. That gives you the brevity of minimal APIs with the discoverability of controllers, and it lines up with vertical slice architecture.

Warm-up interview question

Walk me through what happens when a request hits an ASP.NET Core API. 🔥 Must know
How I'd answer

"Kestrel accepts the connection and parses the HTTP request — that's the actual web server. In production it's often behind IIS or nginx as a reverse proxy, though it can be public-facing."

"Then a HttpContext is created and passed into the middleware pipeline. Each piece of middleware gets the context plus a delegate for the rest of the pipeline, so it can do work, call the next one, and then do more work as the response comes back out."

"A typical order is exception handling first so it wraps everything, then HTTPS redirection, static files, routing, CORS, authentication, authorization, rate limiting, and finally the endpoint."

"Along the way a DI scope is created for the request — that's what makes scoped services scoped, and it's disposed when the response completes. That's also why injecting a DbContext works cleanly per request and why capturing it in a singleton breaks."

"At the endpoint, model binding populates parameters from the route, query string and body, validation runs, and the handler executes. The result gets written to the response, which then unwinds back up through the middleware — so anything after await next() runs on the way out."

"The part I'd emphasise is that ordering is load-bearing and mis-ordering usually doesn't throw. Put authorization before authentication and it silently fails to find an identity. Put exception handling too late and your custom error format doesn't apply to anything above it."

What they're really checking
  • Do you know it's a pipeline, and that it's bidirectional?
  • Do you connect the request scope to DI lifetimes?
  • Do you know mis-ordering fails silently?
Weak answers
  • Red flag: "the controller handles it" — skips the whole pipeline.
  • Red flag: no mention of middleware or ordering.
Likely follow-ups
  • What breaks if authentication comes after authorization?
  • Where would you add rate limiting, and why there?
  • What's the difference between Use, Run and Map?
