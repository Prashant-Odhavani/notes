Performance & Resilience

The framework features that keep an API up under load — and the HttpClient mistake that appears in more production incidents than any other .NET bug.

🟡 Intermediate 🔴 Advanced 🔥 Must know
Quick revision
  • Never new HttpClient() per request. Use IHttpClientFactory. This is the classic .NET production bug.
  • A static HttpClient fixes socket exhaustion but breaks DNS changes — the factory handles both.
  • Timeouts first, then retry with jitter, then a circuit breaker. Order matters.
  • Built-in rate limiting (.NET 7+) is per-instance. Across replicas you need a shared store.
  • Health checks: liveness = am I alive; readiness = can I serve traffic. They must be different endpoints.
  • Most "slow API" problems are database or blocking calls, not framework overhead.

HttpClient — the classic bug 🔥 Must know

public async Task<Price> GetPriceAsync(string sku)
{
    using var client = new HttpClient();          // new client per call
    return await client.GetFromJsonAsync<Price>($"/prices/{sku}");
}
Why this fails

Disposing an HttpClient doesn't immediately free its socket. The connection sits in TIME_WAIT for up to four minutes.

Under load you create sockets faster than the OS releases them, run out of ports, and start getting SocketException — "only one usage of each socket address is normally permitted".

Why this bug is so nasty

The using statement looks correct. It's the responsible thing to do with an IDisposable, so it survives code review easily.

And it works perfectly in development and in light testing. It only fails under sustained load — often first appearing as intermittent failures a few minutes into a load test or a traffic spike.

Why a static client isn't the answer either

private static readonly HttpClient Client = new();   // lives forever

This does solve socket exhaustion — connections are pooled and reused. But a long-lived HttpClient caches DNS resolution at the connection level and never picks up DNS changes.

So when the service you're calling fails over to a new IP — a deployment, a load balancer change, an Azure failover — your app keeps calling the old address until it's restarted. That's a genuinely difficult outage to diagnose, because everything else recovered and only your service didn't.

// Program.cs
builder.Services.AddHttpClient<IPricingClient, PricingClient>(client =>
{
    client.BaseAddress = new Uri("https://pricing.internal/");
    client.Timeout = TimeSpan.FromSeconds(3);          // ALWAYS set this
});

// Injected and used normally
public sealed class PricingClient(HttpClient client) : IPricingClient
{
    public async Task<Price?> GetAsync(string sku, CancellationToken ct) =>
        await client.GetFromJsonAsync<Price>($"prices/{sku}", ct);
}
What the factory actually does

It pools the underlying message handlers (which own the sockets) and rotates them on a lifetime — two minutes by default.

So sockets get reused (no exhaustion) but handlers are periodically replaced (DNS refreshes). That's why it's the answer rather than either extreme.

Common mistake

The injected HttpClient is cheap and meant to be short-lived — don't cache it in a static field or hold it beyond the consuming service's lifetime. Doing so defeats the handler rotation and reintroduces the DNS problem.

Retry, timeout and circuit breaker 🔥 Must know

The patterns themselves — and why ordering matters — are covered in resilience patterns. Here's how you wire them up in ASP.NET Core.

builder.Services.AddHttpClient<IPricingClient, PricingClient>(c =>
{
    c.BaseAddress = new Uri("https://pricing.internal/");
})
.AddStandardResilienceHandler(options =>
{
    // Per-attempt timeout
    options.AttemptTimeout.Timeout = TimeSpan.FromSeconds(2);

    // Retry with exponential backoff AND jitter
    options.Retry.MaxRetryAttempts = 3;
    options.Retry.UseJitter = true;

    // Stop hammering a dependency that's clearly down
    options.CircuitBreaker.FailureRatio = 0.5;
    options.CircuitBreaker.MinimumThroughput = 20;

    // Bounds the WHOLE operation, including retries
    options.TotalRequestTimeout.Timeout = TimeSpan.FromSeconds(10);
});

Two details worth understanding rather than copying:

  • Two timeouts, deliberately. AttemptTimeout bounds each try; TotalRequestTimeout bounds all of them together. Without the total, three retries at two seconds each can exceed what the caller will wait for — so you do work nobody receives.
  • MinimumThroughput stops false trips. Without it, two failures during a quiet period is a 100% failure rate, and the breaker opens on a healthy dependency.
Retry is only safe if the operation is idempotent

A timeout means you don't know whether the request succeeded — it may have completed and only the response was lost.

Retrying a GET is fine. Retrying a payment authorisation without an idempotency key can charge the customer twice. The standard handler retries by default on transient failures, so for non-idempotent operations you must either supply an idempotency key or disable retry for that client.

Rate limiting 🟡 Intermediate

builder.Services.AddRateLimiter(options =>
{
    options.RejectionStatusCode = StatusCodes.Status429TooManyRequests;

    // Partition by tenant, not globally - one heavy tenant shouldn't
    // consume everyone else's quota.
    options.AddPolicy("per-tenant", context =>
        RateLimitPartition.GetTokenBucketLimiter(
            partitionKey: context.User.FindFirst("tenant_id")?.Value ?? "anonymous",
            factory: _ => new TokenBucketRateLimiterOptions
            {
                TokenLimit = 100,
                TokensPerPeriod = 20,
                ReplenishmentPeriod = TimeSpan.FromSeconds(1),
                QueueLimit = 0                     // reject rather than queue
            }));

    // Tell well-behaved clients when to come back
    options.OnRejected = async (ctx, ct) =>
    {
        if (ctx.Lease.TryGetMetadata(MetadataName.RetryAfter, out var retryAfter))
            ctx.HttpContext.Response.Headers.RetryAfter =
                ((int)retryAfter.TotalSeconds).ToString();
        await ValueTask.CompletedTask;
    };
});

app.UseRateLimiter();      // after UseAuthentication, so the tenant claim exists

The limitation to state in an interview

The built-in rate limiter holds state in memory, per instance. With three replicas, a limit of 100 becomes an effective 300 — and it's uneven, depending on how the load balancer distributes requests.

For a genuine global limit you need shared state (Redis) or enforcement at the gateway. Knowing that boundary is more valuable than knowing the configuration syntax.

Production trap — caching per-user data globally

If a response depends on who's asking and you cache it without varying by user, the first caller's data gets served to everyone else. That's a data leak caused by a performance optimisation.

Rule: if the response varies by user or tenant, either VaryByValue on that claim, or don't cache it at the response level — cache the expensive data further down instead.

Health checks 🔥 Must know

In simple terms

Liveness — "am I alive?" If this fails, restart me.

Readiness — "can I serve traffic?" If this fails, stop sending me requests but don't restart me.

builder.Services.AddHealthChecks()
    .AddCheck("self", () => HealthCheckResult.Healthy(), tags: ["live"])
    .AddDbContextCheck<AppDbContext>("database", tags: ["ready"])
    .AddCheck<RedisHealthCheck>("cache", tags: ["ready"]);

// Liveness: no dependencies. Only fails if the process is broken.
app.MapHealthChecks("/health/live", new HealthCheckOptions
{
    Predicate = check => check.Tags.Contains("live")
});

// Readiness: includes dependencies.
app.MapHealthChecks("/health/ready", new HealthCheckOptions
{
    Predicate = check => check.Tags.Contains("ready")
});
Production trap — the restart loop

If your liveness probe checks the database, and the database has a brief outage, Kubernetes concludes every pod is dead and restarts them all.

Now you have a restart storm on top of a database problem — and restarting doesn't fix a database outage, so the pods keep failing. You've turned a degradation into a full outage.

Liveness must not check dependencies. Only readiness should.

Kestrel limits 🔴 Advanced 💡 Good to know

builder.WebHost.ConfigureKestrel(options =>
{
    options.Limits.MaxConcurrentConnections = 1000;
    options.Limits.MaxRequestBodySize = 10 * 1024 * 1024;        // 10 MB
    options.Limits.RequestHeadersTimeout = TimeSpan.FromSeconds(30);

    // Slowloris defence: require a minimum data rate
    options.Limits.MinRequestBodyDataRate =
        new MinDataRate(bytesPerSecond: 100, gracePeriod: TimeSpan.FromSeconds(10));
});

MaxRequestBodySize is the one people hit: the default is around 30 MB, and a large upload fails with a 413 that isn't obviously about a limit. Raise it deliberately for upload endpoints rather than globally — a global increase makes you easier to exhaust.

Remember this

In a typical ASP.NET Core app, framework overhead is not your bottleneck.

It's a database round trip, a missing index, or a blocking call. Profile before optimising anything else.

Key takeaways
  • new HttpClient() per request → socket exhaustion. Static → stale DNS. IHttpClientFactory → both solved.
  • Always set an HttpClient timeout. The default is 100 seconds.
  • Two timeouts: per attempt and total. Retry needs jitter and idempotency.
  • Circuit breakers need MinimumThroughput or they trip spuriously.
  • Built-in rate limiting is per instance. Partition by tenant, and know the multi-replica limit.
  • Never cache a per-user response globally.
  • Liveness must not check dependencies, or a DB blip becomes a restart storm.
  • Slowness is almost always the database or a blocking call.

Common mistakes

  • using var client = new HttpClient() — looks correct, exhausts sockets.
  • No HttpClient timeout, so a hung dependency holds a request for 100 seconds.
  • Retry without idempotency on a payment or order submission.
  • Retry without jitter, so all clients retry in synchronised waves.
  • Circuit breaker with no minimum throughput, tripping at 3am on two failures.
  • Global rate limit instead of per-tenant, letting one client consume the quota.
  • Caching authenticated responses without varying by user.
  • Liveness probe that checks the database — restart storms.
  • Raising MaxRequestBodySize globally instead of per endpoint.

Interview questions

What's wrong with using var client = new HttpClient()? 🔥 Must know
How I'd answer

"It causes socket exhaustion, and the frustrating part is that it looks like correct code — it's an IDisposable in a using, which is exactly what you're taught to do."

"The problem is that disposing an HttpClient doesn't release its socket immediately. The connection goes into TIME_WAIT for up to four minutes. Under sustained load you create sockets faster than the OS reclaims them, run out of ephemeral ports, and start getting SocketException. And it only shows up under load — development and light testing look fine."

"The obvious fix, a static HttpClient, solves that but introduces a different bug: a long-lived client caches DNS at the connection level and never picks up changes. So when the service you're calling fails over to a new IP, your app keeps calling the old one until it's restarted. That's a nasty outage because everything else recovered and only you didn't."

"So the answer is IHttpClientFactory. It pools the underlying message handlers, which own the sockets, and rotates them on a lifetime — two minutes by default. Sockets get reused so there's no exhaustion, and handlers get replaced so DNS refreshes. It solves both ends of the trade-off."

"Two things I'd add. The injected HttpClient is cheap and meant to be short-lived — caching it in a static field defeats the handler rotation. And I'd always set an explicit timeout, because the default is 100 seconds, which under load means a hung dependency holds request threads long enough to exhaust the thread pool."

What they're really checking
  • Do you know the socket/TIME_WAIT mechanism?
  • Do you know the static-client DNS problem — the detail that shows real experience?
  • Do you mention the default timeout?
Weak answers
  • Red flag: "you should reuse it" with no mechanism.
  • Red flag: "make it static" with no mention of DNS.
Likely follow-ups
  • How would you add retry and a circuit breaker to that client?
  • What's the handler lifetime and why does it exist?
  • How would you diagnose socket exhaustion in production?
How would you add rate limiting to a multi-tenant API?
How I'd answer

"I'd use the built-in rate limiter from .NET 7 rather than writing one, partitioned per tenant rather than globally. A global limit means one heavy tenant consumes everyone else's quota, which is the noisy-neighbour problem."

"For the algorithm I'd default to a token bucket. It allows a reasonable burst — clients often legitimately send a batch — while enforcing a sustained rate. A fixed window lets a client send double the limit across a window boundary, which is a real gap."

"Placement matters: it goes after authentication in the pipeline, because I need the tenant claim to build the partition key. Before auth I'd only have the IP, which is much less useful and wrong behind a proxy."

"On rejection I'd return 429 with a Retry-After header. Without it, well-behaved clients guess, and they usually guess too aggressively — which keeps you overloaded."

"The limitation I'd state explicitly is that the built-in limiter keeps state in memory per instance. With three replicas a limit of 100 becomes an effective 300, distributed unevenly depending on the load balancer. For a genuine global limit you need shared state in Redis, or you enforce it at the gateway — API Management or similar — which is usually the better place because it rejects traffic before it reaches your compute."

"I'd also want per-tenant limits to be configurable, because in a real SaaS the plan tier usually determines the quota — so the limit has to come from tenant configuration rather than a constant."

What they're really checking
  • Do you partition per tenant rather than globally?
  • Do you know the per-instance limitation?
  • Do you return Retry-After?
Likely follow-ups
  • How would you implement a distributed rate limit with Redis?
  • Should rate limiting live in the app or the gateway?
  • How do you handle a legitimate burst from a big customer?
How should health checks be set up for Kubernetes? ⭐ Senior-level
How I'd answer

"Two separate endpoints, because liveness and readiness answer different questions and have different consequences."

"Liveness is 'is this process alive?' If it fails, Kubernetes restarts the pod. So it must check only the process itself — no database, no cache, no downstream services. Essentially it returns 200 if the app is running."

"Readiness is 'can this pod serve traffic?' If it fails, the pod is removed from the load balancer but not restarted. That's where dependency checks belong — database, cache, whatever you can't function without."

"The reason this distinction matters is a specific failure I'd want to avoid. If the liveness probe checks the database and the database has a thirty-second blip, Kubernetes concludes every pod is dead and restarts all of them. Now you have a restart storm on top of a database problem — and restarting doesn't fix a database outage, so they keep failing. You've converted a brief degradation into a full outage."

"A couple of refinements. I'd add a startup probe for apps with slow initialisation, so a long warm-up isn't mistaken for a liveness failure. And I'd make readiness fail during shutdown — the host's ApplicationStopping event is the hook — so the pod is drained from the load balancer before it stops accepting connections. Otherwise you get failed requests on every deployment."

"And I'd keep the checks cheap. A readiness probe running every few seconds that executes a real query adds meaningful load and can itself become the problem. A connectivity check is usually enough."

What they're really checking
  • Do you know liveness must not check dependencies? That's the discriminating detail.
  • Can you describe the restart-storm failure?
  • Bonus: startup probes and draining on shutdown.
Weak answers
  • Red flag: one /health endpoint checking everything.
  • Red flag: not knowing the difference in what Kubernetes does with each.
Likely follow-ups
  • What should happen to readiness during a rolling deployment?
  • How do you avoid the probe itself loading the database?
  • What if a dependency is optional — degrade or fail readiness?
