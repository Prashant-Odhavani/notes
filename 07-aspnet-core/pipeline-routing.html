Middleware, Pipeline & Routing

The most asked ASP.NET Core topic, because getting the order wrong produces bugs that don't throw — they just quietly misbehave.

🟡 Intermediate 🔥 Must know
Quick revision
  • Middleware runs in registration order on the way in, and reverse order on the way out.
  • Each component gets the context plus next — it can pass along, modify, or short-circuit.
  • Exception handling first. It can only catch what's registered below it.
  • Authentication before authorization. You can't check permissions before you know who it is.
  • UseRouting before anything that depends on which endpoint was matched.
  • Once the response has started, you cannot change headers or status. That's the "Headers are read-only" error.

How the pipeline works 🔥 Must know

In simple terms

Each piece of middleware is handed the request and a function representing "everything after me".

It can do work before calling that function, after calling it, or refuse to call it at all.

Think of it this way

Airport security. You pass through check-in, then bag drop, then passport control, then the gate. Each stage can process you and send you on — or stop you entirely.

On the way back from your flight, you pass through the same stages in reverse. That's the response unwinding.

app.Use(async (context, next) =>
{
    // ---- on the way IN ----
    var sw = Stopwatch.StartNew();

    await next(context);          // hand off to everything below

    // ---- on the way OUT ----
    logger.LogInformation("{Path} took {Ms}ms", context.Request.Path, sw.ElapsedMilliseconds);
});

That single example shows why the pipeline is bidirectional: the timing only works because code after next() runs once the response is ready.

{
    admin.UseMiddleware<AdminAuditMiddleware>();   // only for /admin/*
    admin.Run(async ctx => await ctx.Response.WriteAsync("admin"));

// UseWhen adds middleware but rejoins the main pipeline afterwards
app.UseWhen(ctx => ctx.Request.Path.StartsWithSegments("/api"),
    api => api.UseMiddleware<ApiKeyMiddleware>());

The order that matters 🔥 Must know

var app = builder.Build();

// 1. FIRST - it can only catch exceptions from middleware BELOW it
app.UseExceptionHandler("/error");

// 2. Before anything writes a response
app.UseHsts();
app.UseHttpsRedirection();

// 3. Cheap short-circuit - don't run auth for a CSS file
app.UseStaticFiles();

// 4. Decides WHICH endpoint - anything below can now read endpoint metadata
app.UseRouting();

// 5. Before auth: a rejected CORS preflight must not need credentials
app.UseCors();

// 6. Who are you?  ...then...  may you do this?
app.UseAuthentication();
app.UseAuthorization();

// 7. After auth, so limits can be per-user rather than per-IP
app.UseRateLimiter();

// 8. Terminal - executes the matched endpoint
app.MapControllers();

app.Run();
RuleWhat breaks if you get it wrong
Exception handling firstExceptions from middleware above it are unhandled — generic 500, no ProblemDetails, no correlation ID in the log
Authentication before authorizationAuthorization sees no identity, so every authenticated endpoint returns 401 even with a valid token
Routing before authorizationEndpoint-specific policies ([Authorize(Policy=...)]) can't be read, so they don't apply
Static files before authDeliberate — it avoids running auth for assets. But it means static files are public. If they must be protected, move it below auth
CORS before authA preflight OPTIONS request carries no credentials, so auth would reject it and the browser blocks the real request
Rate limiting after authLets you limit per user or tenant rather than per IP — much more useful
Why this is dangerous rather than just wrong

Mis-ordering almost never throws. The app starts, most requests work, and the failure is specific and subtle:

Authorization before authentication → valid tokens rejected, but only on protected endpoints.
Exception handler too late → your error format applies to most errors but not all.
Static files after auth → suddenly every image request runs a database-backed auth check.

That's why the pipeline block deserves careful review rather than being appended to.

Writing custom middleware 🟡 Intermediate

Two forms. The class form is preferred for anything non-trivial.

public sealed class TenantResolutionMiddleware(RequestDelegate next)
{
    // Note: this class is effectively a SINGLETON - constructed once.
    // Per-request dependencies must be parameters on InvokeAsync, not the constructor.
    public async Task InvokeAsync(HttpContext context, ITenantContext tenantContext)
    {
        var host = context.Request.Host.Host;
        var tenant = TenantFromHost(host);

        if (tenant is null)
        {
            context.Response.StatusCode = StatusCodes.Status404NotFound;
            return;                          // short-circuit: nothing below runs
        }

        tenantContext.Set(tenant);
        await next(context);
    }
}

// Registered as:  app.UseMiddleware<TenantResolutionMiddleware>();
The middleware DI trap

Middleware classes are instantiated once, at startup. So a constructor parameter is captured for the app's lifetime — injecting a scoped service there is a captive dependency.

Put per-request dependencies on InvokeAsync, which is called per request and resolved from the request scope. Singletons and IOptions are fine in the constructor.

(Factory-based middleware via IMiddleware is created per request, so its constructor can take scoped services — but then it must be registered in DI explicitly.)

The "response has already started" error 🔴 Advanced

app.Use(async (context, next) =>
{
    await next(context);                              // endpoint writes the response

    context.Response.StatusCode = 500;                // InvalidOperationException
    context.Response.Headers["X-Custom"] = "value";   // headers already sent
});

Once the first byte is flushed, the status line and headers are already on the wire. You cannot change them.

Two consequences worth knowing:

  • Check before writing. if (!context.Response.HasStarted) — that's how the built-in exception handler decides whether it can still produce an error response.
  • This is why an exception thrown late gives a broken response rather than a clean 500. If the endpoint streamed half a JSON document and then threw, the client gets truncated JSON with a 200 status. That's a genuinely nasty failure mode, and it's an argument for buffering small responses or validating before you start writing.

Endpoint routing 🟡 Intermediate

In simple terms

UseRouting works out which endpoint matches. The endpoint isn't executed until the end of the pipeline.

That gap is deliberate: it lets middleware in between read the endpoint's metadata and act on it.

That's why [Authorize(Policy = "AdminOnly")] works — the authorization middleware, sitting between routing and execution, can see the policy attached to the matched endpoint.

app.MapGet("/orders/{id:guid}", GetOrder);              // must parse as a Guid
app.MapGet("/orders/{page:int:min(1)}", GetOrderPage);  // int, at least 1
app.MapGet("/files/{*path}", GetFile);                  // catch-all, includes slashes

// Constraints are for ROUTING, not validation.
// A non-Guid id gives 404 (no route matched), not 400.
Constraints vs validation

A route constraint decides whether a route matches. If it doesn't match, the client gets 404, not 400.

That's usually what you want for an obviously malformed URL, but it's worth being deliberate: if you'd rather return "400 Bad Request — id must be a GUID", bind it as a string and validate. Otherwise a typo in an ID looks identical to a deleted resource.

Route groups (.NET 7+)

var orders = app.MapGroup("/api/orders")
                .RequireAuthorization("OrdersPolicy")
                .WithTags("Orders")
                .AddEndpointFilter<ValidationFilter>();

orders.MapGet("/{id:guid}", GetOrder);
orders.MapPost("/", CreateOrder);
orders.MapDelete("/{id:guid}", CancelOrder);

This is what makes minimal APIs viable at scale — the shared concerns are declared once rather than repeated per endpoint.

Key takeaways
  • Registration order = execution order in, reverse order out.
  • Exception handling first; authentication before authorization; routing before both.
  • Mis-ordering fails silently — review the pipeline block, don't append to it.
  • Static files before auth means static files are public. Decide deliberately.
  • CORS before auth, so preflight requests aren't rejected.
  • Middleware constructors are singleton-scoped — per-request dependencies go on InvokeAsync.
  • You can't change status or headers after the response has started.
  • Routing matches early and executes late, which is what lets middleware read endpoint metadata.

Common mistakes

  • UseAuthorization before UseAuthentication — valid tokens get 401.
  • Exception handler registered late, so it misses errors from earlier middleware.
  • Scoped service in a middleware constructor — captive dependency.
  • Forgetting await next(), silently ending the request with a 200 and an empty body.
  • Writing to the response then calling next(), then hitting "response already started".
  • Reading the request body without enabling buffering — it's a forward-only stream, so the endpoint then sees nothing.
  • Using route constraints as validation and getting 404 where you wanted 400.
  • Putting business logic in middleware — it applies to every request and is hard to test.

Interview questions

Why does middleware order matter? Give examples. 🔥 Must know
How I'd answer

"Because each piece of middleware wraps everything registered after it, and any of them can short-circuit. So position determines both what a component can see and whether it runs at all."

"The clearest example is exception handling. It has to be first, because it can only catch exceptions thrown by middleware below it. Register it third and anything that throws in the first two gets an unhandled 500 with none of your error formatting or correlation ID."

"Authentication before authorization is the other classic. Authentication establishes who the caller is; authorization checks what they may do. Reverse them and authorization sees an unauthenticated user, so every protected endpoint returns 401 even with a perfectly valid token."

"Routing needs to come before authorization too, because policies are attached to endpoints as metadata. If routing hasn't run, there's no matched endpoint, so [Authorize(Policy = ...)] has nothing to read."

"A subtler one is CORS before authentication. A browser preflight is an OPTIONS request with no credentials, so if auth runs first it rejects the preflight and the browser blocks the real request — which presents as a confusing CORS error when the actual cause is ordering."

"And I'd flag static files deliberately. Putting it before auth is normal, because you don't want a database-backed auth check for every CSS file — but it does mean those files are public. If they need protecting, it has to move below auth."

"The thing that makes this worth reviewing carefully is that mis-ordering almost never throws. The app starts, most requests work, and you get a narrow, confusing failure."

What they're really checking
  • Can you give the reason for each ordering rule, not just the sequence?
  • Do you know it fails silently?
  • Bonus: the CORS preflight and static-files trade-offs.
Weak answers
  • Red flag: reciting the order from the template with no reasoning.
  • Red flag: "order doesn't really matter as long as they're all there."
Likely follow-ups
  • Where would you put rate limiting, and why?
  • What happens if middleware doesn't call next?
  • How would you add a correlation ID to every log line?
Write middleware that logs every request's duration. What do you have to be careful about?
How I'd answer

"The structure is: start a stopwatch, await next(context), then log after it returns — because that's the point at which the response has been produced. The bidirectional nature of the pipeline is what makes this possible at all."

"Things I'd be careful about. First, where I register it — near the top, so it measures the whole pipeline rather than a fraction of it. Though above the exception handler means I'd need my own try/finally to make sure the log still happens when something throws."

"Second, use a finally. If the endpoint throws, I still want the timing — a slow failing request is exactly the case I care about."

"Third, dependency injection. The middleware class is constructed once, so a scoped dependency in the constructor is a captive dependency. ILogger<T> is a singleton so it's fine there, but anything per-request goes on InvokeAsync."

"Fourth, don't touch the response after it's started. If I wanted to add a timing header I'd have to set it before calling next, or use OnStarting — because once bytes are flushed, headers are read-only."

"And I'd log it as structured data — path, status code and elapsed milliseconds as separate fields — so it's queryable rather than a string I'd have to parse."

"Honestly though, I'd check first whether I need this at all. ASP.NET Core has UseHttpLogging, and the built-in metrics plus OpenTelemetry already emit request duration with far better dimensionality. I'd rather configure that than hand-roll it."

What they're really checking
  • Do you know code after next() runs on the way out?
  • Do you use finally so failures are measured too?
  • Do you know the middleware DI lifetime trap?
  • Bonus: knowing the framework already does this.
Likely follow-ups
  • How would you add a response header from middleware?
  • How do you read the request body in middleware without breaking the endpoint?
  • Where does this sit relative to the exception handler?
