Background & Hosted Services

Work that happens outside a request. Simple to start, and there are four specific traps that bite in production.

🟡 Intermediate 🔴 Advanced 🔥 Must know
Quick revision
  • BackgroundService is registered as a singleton — so create a DI scope per unit of work.
  • An unhandled exception in ExecuteAsync stops the whole host. Catch inside the loop.
  • Honour the cancellation token, or the platform kills you mid-work.
  • With multiple instances, your job runs on every one. Plan for that.
  • Don't block startup: heavy work in StartAsync delays the app becoming ready.
  • For request-triggered background work, use a Channel, not fire-and-forget Task.Run.

The shape of a background service 🟢 Beginner

public class OrderProcessor(AppDbContext db) : BackgroundService
{
    protected override async Task ExecuteAsync(CancellationToken ct)
    {
        while (true)
        {
            var pending = await db.Orders.Where(o => !o.Processed).ToListAsync();
            foreach (var o in pending) Process(o);
            await Task.Delay(10_000);
        }
    }
}

Three problems, all of which show up in production rather than development:

  1. Injected DbContext. The service is a singleton, so this context lives for the lifetime of the app — accumulating tracked entities, returning stale data, and eventually throwing.
  2. No exception handling. One transient database failure throws out of ExecuteAsync and takes down the entire host, including your API.
  3. Cancellation ignored. while (true) and an unparameterised Task.Delay mean shutdown waits, then the process is killed mid-work.
public sealed class OrderProcessor(
    IServiceScopeFactory scopeFactory,
    ILogger<OrderProcessor> log) : BackgroundService
{
    private static readonly TimeSpan Interval = TimeSpan.FromSeconds(10);

    protected override async Task ExecuteAsync(CancellationToken ct)
    {
        while (!ct.IsCancellationRequested)
        {
            try
            {
                await ProcessBatchAsync(ct);
            }
            catch (OperationCanceledException) when (ct.IsCancellationRequested)
            {
                break;                                  // normal shutdown
            }
            catch (Exception ex)
            {
                // Log and continue - do NOT let this escape
                log.LogError(ex, "Order processing batch failed");
            }

            try
            {
                await Task.Delay(Interval, ct);
            }
            catch (OperationCanceledException) { break; }
        }

        log.LogInformation("Order processor stopped cleanly");
    }

    private async Task ProcessBatchAsync(CancellationToken ct)
    {
        // A fresh scope per batch: fresh DbContext, disposed at the end
        using var scope = scopeFactory.CreateScope();
        var db = scope.ServiceProvider.GetRequiredService<AppDbContext>();

        var pending = await db.Orders
            .Where(o => !o.Processed)
            .Take(50)                                   // bounded batch
            .ToListAsync(ct);

        foreach (var order in pending)
        {
            ct.ThrowIfCancellationRequested();          // check between items
            order.MarkProcessed();
        }

        await db.SaveChangesAsync(ct);
    }
}
Production trap — one failure takes down the API

Since .NET 6, an unhandled exception in ExecuteAsync stops the host by default. So a background job that fails once will take your web API offline.

You can change that with HostOptions.BackgroundServiceExceptionBehavior, but the right answer is to handle exceptions in the loop. Swallowing at the batch level and continuing is almost always what you want — with an alert on the error rate so silent failure doesn't become permanent.

Where to put the scope boundary 🟡 Intermediate

In simple terms

One scope per unit of work you'd want to succeed or fail together.

Scope per…BehaviourUse when
Whole service lifetime❌ Same as injecting the context. Don'tNever
Loop iteration / batchOne transaction per batch; all-or-nothingBatch processing where partial success is fine to retry
Individual itemOne transaction per item; failures isolatedMessage processing, where one bad item mustn't block the rest

The trade-off: per-batch is fewer scopes and fewer round trips, but one poison record fails the whole batch — and if you retry the batch, it fails again forever. Per-item is more overhead but isolates failures, which is why message consumers work that way.

Graceful shutdown 🔥 Must know

The sequence when the platform stops your app:

  1. SIGTERM arrives (Kubernetes, Azure, Ctrl+C).
  2. The host triggers ApplicationStopping; the API stops accepting new requests.
  3. The token passed to ExecuteAsync is cancelled.
  4. StopAsync is called on each hosted service.
  5. The host waits up to ShutdownTimeout (default 30s), then kills what's left.
public override async Task StopAsync(CancellationToken ct)
{
    log.LogInformation("Draining: waiting for the current batch");

    // Let in-flight work finish, but respect the caller's timeout
    await _currentBatch.WaitAsync(ct);

    await base.StopAsync(ct);
}
Production trap — timeout mismatch with Kubernetes

Kubernetes sends SIGTERM, waits terminationGracePeriodSeconds (default 30), then SIGKILL.

If your .NET ShutdownTimeout is longer than that, Kubernetes kills you mid-drain — and you lose exactly the in-flight work you were trying to protect.

Set the .NET timeout below the grace period, and make sure work checks cancellation often enough to actually stop inside it. A batch that takes 60 seconds and never checks the token can't be drained gracefully no matter what the timeouts say.

The multi-instance problem ⭐ Senior-level

In simple terms

Your background service runs in every instance of your app.

Three replicas means the job runs three times, concurrently. Nobody tells you this — it just starts happening when you scale out.

Whether that's a problem depends on the work:

Work typeMultiple instances?Why
Consuming a queue✅ GoodCompeting consumers — each message goes to one instance, and you get throughput
Polling a table with a claim✅ FineIf you atomically claim rows, instances don't collide
"Send the daily summary email"❌ BadThree emails per customer
Regenerating a shared cache⚠️ WastefulSame work three times; usually harmless

The options, in order of how much I'd reach for them:

  1. Make the work claim-based. A conditional UPDATE that claims rows means instances naturally divide the work with no coordination: UPDATE TOP (50) ... SET ClaimedBy = @me WHERE ClaimedBy IS NULL. This is my default, because it needs no new infrastructure and scales.
  2. Make it idempotent with a unique key. "Daily summary for tenant X on date Y" with a unique constraint — the second and third instances fail the insert and stop. Much more robust than trying to prevent the double-run.
  3. Take a distributed lease. A database row or Redis key with a TTL, so one instance wins. Simple, but a lease can expire mid-job — so the work still needs to be safe if two instances briefly overlap.
  4. Move it out of the app. A Kubernetes CronJob, an Azure Function with a singleton trigger, or Hangfire/Quartz with a shared store. If the platform guarantees single execution, use that rather than building it.
Remember this

Prefer idempotent work over a perfect lock.

Locks fail — leases expire, networks partition, processes pause for GC. Work that's safe to run twice doesn't care.

The lock mechanics are covered in concurrency and Redis distributed primitives.

Background work triggered by a request 🟡 Intermediate

[HttpPost("/api/orders")]
public async Task<IActionResult> Create(CreateOrderRequest r, CancellationToken ct)
{
    var order = await _repo.CreateAsync(r, ct);

    _ = Task.Run(() => _email.SendConfirmationAsync(order));   // fire and forget
    return Ok();
}

Four things wrong with that:

  • Exceptions vanish. Nothing observes the task, so a failure is silent.
  • It uses request-scoped services after the request ends — the scope is disposed, so you get ObjectDisposedException.
  • Shutdown loses it. The host doesn't know about it and won't wait.
  • It's unbounded. A traffic spike starts thousands of concurrent tasks.
// 1. A bounded queue, registered as a singleton
public sealed class EmailQueue
{
    private readonly Channel<EmailJob> _channel =
        Channel.CreateBounded<EmailJob>(new BoundedChannelOptions(1000)
        {
            FullMode = BoundedChannelFullMode.Wait     // apply backpressure
        });

    public ValueTask EnqueueAsync(EmailJob job, CancellationToken ct) =>
        _channel.Writer.WriteAsync(job, ct);

    public IAsyncEnumerable<EmailJob> ReadAllAsync(CancellationToken ct) =>
        _channel.Reader.ReadAllAsync(ct);
}
var order = await _repo.CreateAsync(r, ct);
await _queue.EnqueueAsync(new EmailJob(order.Id, order.Email), ct);
return Ok();
public sealed class EmailWorker(
    EmailQueue queue, IServiceScopeFactory scopes, ILogger<EmailWorker> log)
    : BackgroundService
{
    protected override async Task ExecuteAsync(CancellationToken ct)
    {
        await foreach (var job in queue.ReadAllAsync(ct))
        {
            try
            {
                using var scope = scopes.CreateScope();
                var sender = scope.ServiceProvider.GetRequiredService<IEmailSender>();
                await sender.SendAsync(job, ct);
            }
            catch (Exception ex)
            {
                log.LogError(ex, "Failed to send email for order {OrderId}", job.OrderId);
            }
        }
    }
}

Now failures are logged, services come from a live scope, the host drains the queue on shutdown, and the bound means a spike causes backpressure rather than unbounded memory growth.

The honest limitation

An in-memory channel is still lost on restart. If losing a confirmation email is unacceptable, the queue has to be durable — Service Bus, or the outbox pattern so the job is committed in the same transaction as the order.

Say that in an interview. "A channel is right for work I can afford to lose; an outbox for work I can't" shows you know where the boundary is.

Don't block startup 🟡 Intermediate

MethodWhen it runsBlocks startup?
IHostedService.StartAsyncBefore the app accepts requestsYes — until it returns
BackgroundService.ExecuteAsyncCalled from StartAsyncOnly until the first await

So heavy work directly in StartAsync delays the app becoming ready — and if it exceeds the readiness probe's tolerance, the deployment fails.

Two exceptions worth making deliberately: applying database migrations and validating configuration. Those you often want to block on, because starting up with a bad schema or missing config is worse than failing the deployment. Everything else belongs after the first await.

Key takeaways
  • BackgroundService is a singleton — create a scope per unit of work.
  • Catch exceptions in the loop, or one failure stops the whole host.
  • Handle OperationCanceledException separately — shutdown isn't an error.
  • Keep the .NET shutdown timeout below the platform grace period, and check the token often.
  • Your job runs on every instance. Prefer claim-based or idempotent work over a lock.
  • Use a bounded channel for request-triggered work, never fire-and-forget Task.Run.
  • An in-memory channel loses work on restart — use an outbox if that matters.
  • Don't do heavy work in StartAsync; it delays readiness.

Common mistakes

  • Injecting DbContext instead of creating a scope.
  • No try/catch in the loop, so one failure takes the API down with it.
  • Logging OperationCanceledException as an error on every deployment.
  • while (true) and Task.Delay without the token.
  • Assuming the job runs once when there are three replicas.
  • Fire-and-forget Task.Run from a controller.
  • Unbounded channels, converting a slow consumer into an out-of-memory crash.
  • Unbounded batch size, so a backlog loads a million rows in one query.

Interview questions

You've written a BackgroundService that polls the database. What can go wrong? 🔥 Must know
How I'd answer

"Four things, and I've hit all of them."

"First, DI lifetime. A BackgroundService is a singleton, so injecting a DbContext means one context alive for the lifetime of the app. It accumulates every tracked entity, returns stale data because the change tracker caches, and isn't thread-safe. The fix is IServiceScopeFactory and a scope per unit of work."

"Second, exceptions. Since .NET 6, an unhandled exception in ExecuteAsync shuts down the host — so a transient database blip in a background job takes my API offline. The loop body needs its own try/catch that logs and continues, with an alert on the error rate so it doesn't fail silently forever."

"Third, shutdown. If I use while (true) and a bare Task.Delay, the service ignores cancellation and gets killed mid-work. I'd loop on the token, pass it to Delay, and check it between items so a long batch can actually stop. And I'd keep the .NET shutdown timeout below the platform's grace period, otherwise Kubernetes SIGKILLs me during the drain."

"Fourth, and the one people miss: it runs on every instance. Scale to three replicas and the job runs three times concurrently. For queue consumption that's a feature. For 'send the daily summary' it means three emails per customer."

"My preferred fix there is to make the work claim-based — a conditional UPDATE that claims a batch of rows — so instances divide the work naturally with no coordination. Or make it idempotent with a unique key, so a double run is harmless. I'd reach for a distributed lease only if neither works, because leases expire and you still need the work to be safe if two instances overlap."

"I'd also bound the batch size. A polling job that does ToListAsync() with no Take is fine until there's a backlog, and then it loads a million rows."

What they're really checking
  • Do you know it's a singleton and needs a scope?
  • Do you know an exception stops the host?
  • Do you think about multiple instances unprompted? That's the senior signal.
Weak answers
  • Red flag: only mentioning the DbContext issue.
  • Red flag: assuming the job runs once.
Likely follow-ups
  • Where exactly do you put the scope boundary?
  • How would you make the claim-based query safe under concurrency?
  • How do you monitor that the job is actually running?
A controller needs to send an email without making the caller wait. How?
How I'd answer

"The thing I'd avoid is fire-and-forget Task.Run, because it fails in four ways at once. Nothing observes the task so exceptions disappear silently. It typically uses request-scoped services after the request ended, giving ObjectDisposedException. The host doesn't know about it, so shutdown loses it. And it's unbounded — a traffic spike starts thousands of concurrent tasks."

"The in-process answer is a bounded channel plus a hosted service consumer. The controller writes a job to the channel and returns immediately. The consumer reads from it, creates its own DI scope per job, and handles failures. Bounded matters: if the consumer falls behind, writers wait rather than the queue growing until the process dies."

"That fixes all four problems — failures are logged, services come from a live scope, the host drains the channel on shutdown, and backpressure replaces unbounded growth."

"But I'd be honest about the limitation: an in-memory channel is lost on restart. For a confirmation email that might be acceptable. For something the business depends on, I'd use a durable queue — Service Bus — or better, the outbox pattern, where the job is written to a table in the same transaction as the order. Then it can't be lost, because either both committed or neither did."

"So the decision I'd actually make depends on the cost of losing it. Channel for nice-to-have work, outbox for anything where a silent loss is a real problem — and an email confirming a payment is probably in the second category."

What they're really checking
  • Do you know why fire-and-forget is wrong — specifically?
  • Do you know the channel + hosted service pattern?
  • Do you recognise the durability limit and name the outbox?
Weak answers
  • Red flag: "Task.Run and don't await it."
  • Red flag: an unbounded channel with no mention of the risk.
Likely follow-ups
  • What happens to queued items when the app restarts?
  • How would you retry a failed email?
  • How does this change with three instances?
