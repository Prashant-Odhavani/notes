Authentication & Authorization

Two words that get used interchangeably and mean completely different things — plus the authorization mistake that causes most real data leaks.

🟡 Intermediate 🔴 Advanced 🔥 Must know
Quick revision
  • Authentication = who are you? Authorization = are you allowed to do this?
  • 401 means "I don't know who you are". 403 means "I know, and you can't".
  • JWT for APIs (stateless, but you can't revoke it). Cookies for browser apps (revocable, but need CSRF protection).
  • Claims are facts about the user. Policies are rules over those claims. Prefer policies to hard-coded roles.
  • Endpoint-level authorization is not enough. "Can this user see this record?" needs a resource check.
  • The most common real breach is authorization filtered after retrieval, not enforced in the query.

Authentication vs authorization 🔥 Must know

In simple terms

Authentication establishes identity. It answers "who is this?"

Authorization establishes permission. It answers "may they do this?"

Think of it this way

Authentication is showing your passport at the airport — proving you are who you claim.

Authorization is your boarding pass — proving you may get on this particular flight, in this particular seat.

A valid passport doesn't get you on the plane. And that's exactly the mistake people make in code.

AuthenticationAuthorization
QuestionWho are you?May you do this?
RunsFirstAfter authentication
Failure status401 Unauthorized403 Forbidden
ProducesA ClaimsPrincipalA yes/no decision
MiddlewareUseAuthentication()UseAuthorization()
The status codes are misnamed

401 Unauthorized actually means unauthenticated — "I don't know who you are, try again with credentials".

403 Forbidden means authenticated but not permitted — "I know exactly who you are, and the answer is no".

Getting this right matters practically: a client seeing 401 should try refreshing its token; a client seeing 403 should not, because retrying won't help.

The trade-off in one line

JWTs buy you statelessness and pay for it with revocation.

You cannot un-issue a JWT. If a user is disabled, their token keeps working until it expires.

That's why access tokens should be short-lived — minutes, not days — paired with a longer-lived refresh token you can revoke because it's checked against a store.

builder.Services.AddAuthentication(JwtBearerDefaults.AuthenticationScheme)
    .AddJwtBearer(options =>
    {
        options.Authority = "https://login.example.com";   // fetches signing keys
        options.Audience  = "orders-api";

        options.TokenValidationParameters = new TokenValidationParameters
        {
            ValidateIssuer           = true,
            ValidateAudience         = true,
            ValidateLifetime         = true,
            ValidateIssuerSigningKey = true,           // never disable this
            ClockSkew                = TimeSpan.FromSeconds(30)   // default is 5 MINUTES
        };
    });
Production traps in JWT validation
  • Never disable signature validation. An unsigned or unverified token can be forged trivially — anyone can claim to be an admin.
  • Validate the audience. Without it, a token issued for a different service by the same identity provider is accepted by yours.
  • Default clock skew is 5 minutes. That means an expired token keeps working for up to five minutes. Usually fine, occasionally not — know it's there.
  • Don't put secrets in the payload. A JWT is signed, not encrypted — the payload is base64, readable by anyone holding the token.

Claims, roles and policies 🟡 Intermediate

In simple terms

A claim is a fact about the user: "email is x", "tenant is acme", "role is manager".

A policy is a named rule over those facts: "must be in the finance department and over 18".

[Authorize(Roles = "Admin,Manager,Supervisor,RegionalLead")]
public async Task<IActionResult> Approve(Guid id) { /* ... */ }

The problem: the rule ("who can approve") is now spelled out at every call site. Adding a role means finding and editing every attribute — and missing one is a security bug.

// Program.cs - the rule lives in one place
builder.Services.AddAuthorization(options =>
{
    options.AddPolicy("CanApproveOrders", policy =>
        policy.RequireAuthenticatedUser()
              .RequireClaim("permission", "orders:approve"));
});

// The endpoint states intent, not implementation
[Authorize(Policy = "CanApproveOrders")]
public async Task<IActionResult> Approve(Guid id) { /* ... */ }
Remember this

Authorize on what the user is doing, not on who they are.

"CanApproveOrders" survives a reorganisation. Roles = "Manager" doesn't.

The mistake that causes real breaches 🔥 Must know

In simple terms

[Authorize] answers "may this user call this endpoint?"

It does not answer "may this user see this specific record?"

[Authorize]
[HttpGet("/api/orders/{id:guid}")]
public async Task<IActionResult> Get(Guid id)
{
    var order = await _db.Orders.FindAsync(id);      // ANY order, from ANY tenant
    return order is null ? NotFound() : Ok(order);
}

Every check passed. The user is authenticated and allowed to call this endpoint. And they can read anyone's order by changing the ID in the URL.

This is IDOR — Insecure Direct Object Reference — and it's one of the most common real vulnerabilities in business applications.

[Authorize]
[HttpGet("/api/orders/{id:guid}")]
public async Task<IActionResult> Get(Guid id, CancellationToken ct)
{
    var tenantId = User.FindFirst("tenant_id")!.Value;

    var order = await _db.Orders
        .Where(o => o.Id == id && o.TenantId == tenantId)   // in the QUERY
        .FirstOrDefaultAsync(ct);

    return order is null ? NotFound() : Ok(order);
}
Why "in the query" matters, not just "check it"

This version is also wrong, even though it looks safe:

var order = await _db.Orders.FindAsync(id);
if (order.TenantId != tenantId) return Forbid();     // fetched it first

Three problems. You've already loaded another tenant's data into memory, where it can leak into logs or an exception dump. Returning 403 rather than 404 confirms the record exists, which is an information leak. And it relies on every developer remembering the check on every query — which is exactly the kind of thing that gets missed.

Putting the tenant filter in the query makes the safe path the default. Better still, enforce it centrally with a query filter — see tenant context.

Resource-based authorization

When the rule depends on the resource itself — "you can edit your own order, or any order if you're a manager" — use IAuthorizationService:

public sealed class OrderOwnerHandler : AuthorizationHandler<SameOwnerRequirement, Order>
{
    protected override Task HandleRequirementAsync(
        AuthorizationHandlerContext context, SameOwnerRequirement requirement, Order order)
    {
        var userId = context.User.FindFirst(ClaimTypes.NameIdentifier)?.Value;

        if (order.CreatedByUserId == userId || context.User.IsInRole("Manager"))
            context.Succeed(requirement);

        return Task.CompletedTask;
    }
}
var order = await _repo.GetForTenantAsync(id, tenantId, ct);
if (order is null) return NotFound();

var result = await _authorization.AuthorizeAsync(User, order, new SameOwnerRequirement());
return result.Succeeded ? Ok(order) : Forbid();

CORS 🟡 Intermediate

In simple terms

CORS is a browser mechanism. It lets your API say which other origins are allowed to read its responses from JavaScript.

It is not a security control for your API — anything that isn't a browser ignores it entirely.

builder.Services.AddCors(options =>
{
    options.AddPolicy("spa", policy =>
        policy.WithOrigins("https://app.example.com")   // explicit, not wildcard
              .AllowAnyHeader()
              .AllowAnyMethod()
              .AllowCredentials());
});

app.UseCors("spa");     // before UseAuthentication
Production trap

AllowAnyOrigin() combined with AllowCredentials() is rejected by the framework — deliberately, because it would let any site make authenticated requests on a user's behalf and read the response.

The wrong fix is to reflect the caller's Origin header back, which recreates exactly that hole. List your origins explicitly, from configuration.

And remember: a CORS error in the browser console usually means your API didn't allow it — it isn't a client bug. Also check ordering: CORS must run before authentication, or preflight OPTIONS requests get rejected.

CSRF 🟡 Intermediate

In simple terms

CSRF tricks a logged-in user's browser into making a request they didn't intend — because the browser attaches their cookie automatically.

Auth methodVulnerable to CSRF?Why
CookiesYesThe browser sends them on any request to your domain
Bearer token in a headerNoThe browser never adds it automatically — JS must

Defences, in order of importance:

  1. Antiforgery tokens. ASP.NET Core generates and validates them; MVC forms include them automatically, and [ValidateAntiForgeryToken] enforces it.
  2. SameSite=Lax or Strict cookies. The browser then won't send the cookie on cross-site requests. This is the default in modern browsers and blocks most CSRF on its own.
  3. Never use GET for state changes. A GET that deletes something can be triggered by an <img> tag.
The JWT-in-localStorage trade-off

Storing a token in localStorage removes CSRF risk — but adds XSS risk, because any injected script can read it.

An HttpOnly cookie can't be read by JavaScript, so XSS can't steal it — but it needs CSRF protection.

There's no free option. The usual recommendation for browser apps is an HttpOnly, Secure, SameSite cookie plus antiforgery tokens, because XSS is the more damaging of the two.

Key takeaways
  • Authentication = identity (401). Authorization = permission (403).
  • JWTs are stateless but effectively unrevocable — keep access tokens short-lived.
  • Always validate signature, issuer and audience. Know that default clock skew is 5 minutes.
  • A JWT payload is readable. Signed ≠ encrypted.
  • Use named policies over hard-coded roles — authorize on the action, not the job title.
  • [Authorize] protects endpoints, not rows. Scope the query.
  • Filtering after retrieval is still a leak, and 403-vs-404 confirms existence.
  • CORS is a browser feature, not API security. Never reflect the Origin header.
  • Cookies need CSRF protection; bearer tokens don't but are XSS-readable.

Common mistakes

  • No tenant or owner filter in the query — IDOR, the most common real breach.
  • Fetching then checking, so another tenant's data reaches memory and logs.
  • 403 where 404 is safer, confirming a record exists.
  • Long-lived access tokens with no refresh mechanism, so revocation is impossible.
  • Secrets in the JWT payload — it's readable by anyone with the token.
  • Disabling issuer or audience validation to "make it work".
  • Reflecting the Origin header to satisfy CORS.
  • Cookie auth with no antiforgery token.
  • Roles hard-coded in dozens of attributes, so changing the rule means editing them all.

Interview questions

Basic

What's the difference between authentication and authorization? 🔥 Must know
How I'd answer

"Authentication is identity — who are you. Authorization is permission — may you do this. Authentication has to happen first, because you can't evaluate permissions for someone you haven't identified."

"In ASP.NET Core they're separate middleware, and the order is load-bearing: UseAuthentication then UseAuthorization. Reverse them and every protected endpoint returns 401 even with a valid token, because authorization sees no identity."

"The status codes reflect the split, though they're badly named. 401 Unauthorized actually means unauthenticated — I don't know who you are. 403 Forbidden means authenticated but not permitted. That distinction matters to clients: a 401 should trigger a token refresh, a 403 shouldn't, because retrying won't help."

"The thing I'd add, because it's where real bugs come from, is that authorization has two levels. [Authorize] handles 'may this user call this endpoint'. It says nothing about 'may this user see this record'. That second question needs a filter in the query or a resource-based check, and forgetting it is how you get IDOR vulnerabilities."

What they're really checking
  • Do you have the definitions crisp?
  • Do you know the status code semantics?
  • Bonus: raising resource-level authorization unprompted.
Likely follow-ups
  • How would you stop a user reading another tenant's order?
  • Roles or policies — which and why?
  • Where does the identity actually come from?

Intermediate

JWT or cookie authentication for a new application?
How I'd answer

"It depends on the client. For a public API, a mobile app, or service-to-service calls, JWT — it's stateless, any service can validate it independently, and there's no shared session to worry about when you scale out."

"For a server-rendered browser app, cookies. The browser handles them, they can be HttpOnly so JavaScript can't read them, and crucially you can revoke a session immediately."

"The trade-off I'd name explicitly is revocation. A JWT is valid until it expires — you can't un-issue it. So if a user is disabled or a token is stolen, it keeps working. The mitigation is short-lived access tokens, minutes rather than days, plus a refresh token that is checked against a store and can be revoked. If someone tells me their JWTs last 24 hours, that's the thing I'd push on."

"There's also a security trade-off on the browser side that has no clean answer. A token in localStorage avoids CSRF but is readable by any XSS. An HttpOnly cookie is immune to XSS theft but needs CSRF protection. For a browser app I'd generally take the cookie plus antiforgery tokens and SameSite, because XSS is the more damaging of the two."

"For a SPA talking to an API, the modern pattern is often a backend-for-frontend holding the tokens server-side and using a cookie to the browser — you get cookie security without exposing tokens to JavaScript at all."

What they're really checking
  • Do you choose based on client type rather than fashion?
  • Do you raise revocation as the JWT weakness?
  • Bonus: the XSS/CSRF trade-off, and the BFF pattern.
Weak answers
  • Red flag: "JWT, it's more modern."
  • Red flag: not knowing JWTs can't be revoked.
Likely follow-ups
  • How do you handle logout with a JWT?
  • Where do you store a refresh token?
  • What validation would you configure on the bearer handler?

Advanced

A user changes the ID in a URL and sees another customer's data. How did that happen and how do you prevent it? ⭐ Senior-level
How I'd answer

"That's IDOR — insecure direct object reference. What happened is that the endpoint checked authentication and endpoint-level authorization, but never checked whether this user owns that particular record. So [Authorize] passed and the query fetched by ID with no ownership filter."

"The immediate fix is to put the ownership condition in the query — filter by tenant or owner as part of the WHERE, so a mismatched ID simply returns nothing and the endpoint returns 404."

"I'd be specific about why 'fetch then check' isn't good enough, because that's the version people write. If you load the record and then compare the tenant, you've already pulled another customer's data into memory, where it can end up in a log line or an exception dump. And returning 403 rather than 404 confirms the record exists, which is itself an information leak — an attacker can enumerate valid IDs."

"But the real fix is structural, because relying on every developer remembering the filter on every query will fail eventually. In EF Core I'd use a global query filter on tenant, wired to the current tenant from the request context. Then the filter is applied automatically and you have to explicitly opt out — the safe path becomes the default."

"I'd back that with tests: for each endpoint, a test that authenticates as tenant A and requests a tenant B resource, asserting 404. That's cheap and it catches regressions."

"For anything genuinely sensitive I'd also add resource-based authorization via IAuthorizationService, for rules that depend on the record — 'you can edit your own order, managers can edit any'. That can't live in an attribute, because it needs the loaded resource."

"And I'd audit for it rather than assume this was the only instance. If one endpoint was missing the filter, others probably are — I'd grep for direct FindAsync or Where(x => x.Id == id) without a tenant condition."

What they're really checking
  • Do you know the vulnerability class by name?
  • Do you know 403-vs-404 leaks information?
  • Do you go for a structural fix rather than patching one endpoint?
  • Do you think to audit for other instances?
Weak answers
  • Red flag: "add [Authorize]" — it was already there.
  • Red flag: using GUIDs instead of sequential IDs as the fix — that's obscurity, not authorization.
  • Red flag: fixing only the reported endpoint.
Likely follow-ups
  • How do global query filters work, and how do you handle admin queries that need to bypass them?
  • How would you test for this across every endpoint?
  • Where does the tenant ID come from, and can the client tamper with it?
