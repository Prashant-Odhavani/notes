HTTP & Web API Design

The previous section was how to build it in ASP.NET Core. This one is what to build — the protocol, the contract, and the standards.

🟡 Intermediate 🔥 Must know
Quick revision
  • HTTP methods have defined semantics — safe, idempotent, cacheable. Breaking them breaks proxies and clients.
  • Status codes are a contract. Clients branch on them, so changing one is a breaking change.
  • REST is a set of constraints, not "JSON over HTTP". Most APIs called REST aren't, and that's usually fine.
  • OAuth 2.0 is delegated authorization. OIDC adds identity on top. They're different jobs.
  • Idempotency keys are what make retries safe. Without them, a timeout is a coin flip.
  • Design for the client you have, not the purity of the model.

Why the protocol details matter 🟡 Intermediate

It's tempting to treat HTTP as a dumb pipe for JSON. The problem is that a lot of infrastructure relies on the semantics:

If you…Then…
Use GET to change stateA crawler, a browser prefetch, or a proxy can trigger it. And it may be cached
Use POST where PUT belongsClients can't safely retry, because POST isn't idempotent
Return 200 with an error in the bodyMonitoring shows a healthy API while every request fails
Return 500 for a validation errorClients retry it, and your alerts fire on user mistakes
Omit cache headersEvery client re-fetches unchanged data on every request
Remember this

HTTP semantics are a contract with infrastructure you don't control — browsers, proxies, CDNs, load balancers, client SDKs.

Break the contract and things go wrong in places you can't see or debug.

Senior signal

Being able to say why a rule exists rather than just following it.

"PUT must be idempotent so a client that times out can safely retry — and that's exactly the case where you don't know whether the first attempt succeeded" is a much stronger answer than "PUT is for updates".

Warm-up interview question

What makes a good API? ⭐ Senior-level
How I'd answer

"I'd start with predictability. If a client learns one endpoint, they should be able to guess the others — same naming, same pagination, same error shape, same auth. Consistency matters more than any individual design choice, because it's what lets someone use the API without reading all the docs."

"Then correct HTTP semantics, because infrastructure depends on them. GET doesn't change state so it's safe to cache and retry. PUT and DELETE are idempotent so clients can retry after a timeout. Status codes are accurate, so monitoring and client logic both work."

"Then useful errors. A stable machine-readable error type the client can branch on, a human-readable message, and a correlation ID they can quote in a support ticket. Not a 500 with a stack trace, and not a 200 with { "success": false }."

"And evolvability — designed so most changes are additive. Optional new fields, enums as strings, tolerant readers. Because the alternative is versioning, and every version is code you maintain forever."

"The thing I'd add that people miss: a good API is designed for the client you actually have. A chatty resource-per-entity design is elegant and terrible for a mobile app on a slow network. If the client needs one call to render a screen, give them an endpoint that does that — even if it's less 'pure'. Purity that costs the consumer twelve round trips isn't good design."

What they're really checking
  • Do you think about the consumer, or just the model?
  • Do you know why HTTP semantics matter?
  • Do you consider evolution, not just the first version?
Weak answers
  • Red flag: reciting REST constraints with no mention of the consumer.
  • Red flag: "it should be RESTful" as the whole answer.
Likely follow-ups
  • How do you handle a mobile client that needs fewer round trips?
  • What's the difference between 400 and 422?
  • How would you let clients retry safely?
