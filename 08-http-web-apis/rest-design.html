REST & API Design

What REST actually requires, why almost nothing is fully RESTful, and the design decisions that matter more than the label.

🟡 Intermediate 🔥 Must know
Quick revision
  • REST is a set of constraints, not "JSON over HTTP". Most APIs called REST are HTTP APIs, and that's usually fine.
  • Stateless is the constraint that actually buys you something: any server can handle any request, so you can scale horizontally.
  • HATEOAS is the constraint almost nobody implements — and be able to say why.
  • Model resources (nouns), not operations. Let the method be the verb.
  • Offset pagination breaks at scale. Use keyset/cursor pagination for large or live data.
  • Design for the client you have. A chatty design is elegant and awful on mobile.

What REST actually is 🟡 Intermediate

In simple terms

REST is an architectural style defined by six constraints. Follow them and you get specific properties — scalability, cacheability, independent evolution.

It is not a synonym for "an HTTP API that returns JSON".

ConstraintMeansDo real APIs follow it?
Client–serverSeparate concerns; they evolve independentlyYes, universally
StatelessEvery request carries everything needed; no server sessionMostly yes — and it's the valuable one
CacheableResponses say whether they can be cachedOften ignored
Uniform interfaceStandard methods, resource identification, self-describing messagesPartly
Layered systemProxies, gateways and caches can sit in betweenYes, by default
Code on demandServer can send executable code (optional constraint)Essentially never

Stateless — the one that pays for itself 🔥 Must know

Think of it this way

Stateful: a conversation with a receptionist who remembers you. Great — until they go to lunch and their replacement has no idea what you were discussing.

Stateless: every request is a complete written form. Any receptionist can process it, so you can add ten more and they all work.

That's the whole scaling argument. If the server holds session state, requests must go back to the same instance — sticky sessions — and losing that instance loses the session. Stateless means any instance handles any request, so you scale by adding instances.

It's also why JWTs are popular for APIs: the token carries the identity, so no server needs to look up a session.

Stateless doesn't mean no state anywhere

The database obviously holds state. What "stateless" rules out is per-client conversational state on the server — a shopping cart in an in-memory session, a multi-step wizard that only works if you hit the same instance.

Put that state in the database or in the client, and you've satisfied the constraint.

HATEOAS, and why nobody does it 💡 Good to know

{
  "id": "42",
  "status": "Paid",
  "total": 99.99,
  "_links": {
    "self":   { "href": "/api/orders/42" },
    "cancel": { "href": "/api/orders/42/cancel", "method": "POST" },
    "ship":   { "href": "/api/orders/42/ship",   "method": "POST" }
  }
}

The idea: the client discovers what it can do from the links, rather than hard-coding URLs. If an order can't be cancelled, the cancel link simply isn't there — so the client's UI is driven by the server's state machine.

Why it's rare in practice:

  • Clients hard-code URLs anyway, because it's simpler and they're written against a known version.
  • It roughly doubles payload size for a benefit most clients don't use.
  • Tooling is poor — code generators mostly ignore link relations.
  • A generated OpenAPI client already gives you discoverability at build time, which is what teams actually want.
Senior signal

The honest position is worth stating plainly: "Most APIs, including mine, sit at Richardson maturity level 2 — resources plus proper HTTP methods and status codes. Level 3, HATEOAS, is rarely worth it because clients don't consume the links and OpenAPI already gives us discoverability at build time."

That answer shows you know the model and have judgement about it. Claiming your API is fully RESTful invites a follow-up you probably can't defend.

Modelling resources 🔥 Must know

Remember this

URLs name things. HTTP methods supply the verbs.

If your URL contains a verb, you're probably doing RPC with extra steps.

Verbs in the URL

POST /api/getOrders
POST /api/createOrder
POST /api/deleteOrder?id=42
POST /api/updateOrderStatus

Resources plus methods

GET /api/orders
POST /api/orders
DELETE /api/orders/42
PATCH /api/orders/42

Conventions worth being consistent about:

RuleExample
Plural collection nouns/orders, not /order
Lowercase, hyphens not underscores/purchase-orders
Nest only to show ownership/orders/42/lines
Don't nest more than two levelsNot /customers/1/orders/42/lines/7/notes
Filters in the query string/orders?status=paid&from=2025-01-01

When an action doesn't fit a resource

Some operations genuinely aren't CRUD. "Cancel this order" isn't setting a field — it may refund a payment, release stock and send an email.

OptionLooks likeVerdict
Sub-resource actionPOST /orders/42/cancellationMost defensible — the cancellation is a thing
Verb endpointPOST /orders/42/cancelPragmatic, extremely common, perfectly readable
State field patchPATCH /orders/42 { "status": "Cancelled" }Hides the side effects; lets clients set states they shouldn't
Why the third option is the risky one

Exposing status as a writable field means the client is driving your state machine. There's nothing stopping them setting Shipped directly, skipping payment entirely — that's the over-posting problem again.

An explicit action endpoint makes the legal transitions the API surface. If there's no /ship endpoint for an unpaid order, it can't happen.

Pagination 🔥 Must know

Offset pagination — and why it breaks

GET /api/orders?page=3&pageSize=50
# → SELECT ... ORDER BY CreatedUtc OFFSET 100 ROWS FETCH NEXT 50 ROWS ONLY

Simple, and everyone understands it. Two problems appear at scale:

  1. It gets slower the deeper you go. OFFSET 100000 means the database reads and discards 100,000 rows before returning any. Page 1 is instant; page 2,000 times out.
  2. Items shift between pages. If a new order is inserted while the user is paging, everything moves down one — so they see a row twice, or miss one entirely. On a live dataset this is guaranteed, not theoretical.

Keyset (cursor) pagination — what to use instead

GET /api/orders?limit=50
→ { "items": [...], "nextCursor": "eyJjIjoiMjAyNS0wMS0xMCIsImkiOiI0MiJ9" }

GET /api/orders?limit=50&cursor=eyJjIjoiMjAyNS0wMS0xMCIsImkiOiI0MiJ9
-- No OFFSET. Uses the index to seek straight to the position.
SELECT TOP (50) *
FROM Orders
WHERE (CreatedUtc, Id) < (@lastCreatedUtc, @lastId)   -- composite tiebreak
ORDER BY CreatedUtc DESC, Id DESC;
OffsetKeyset / cursor
Performance at depthDegrades linearlyConstant
Stable with insertsNo — items shiftYes
Jump to page 50YesNo — only next/previous
Total count availableEasilyNeeds a separate query
Best forSmall, stable admin tablesLarge or live data, infinite scroll, APIs
How to choose

Does the user need to jump to an arbitrary page number? Then offset — and cap how deep they can go.

Otherwise use keyset. Infinite scroll, API consumers and event feeds never need page numbers.

The tiebreaker is not optional

Keyset pagination needs a unique sort key. If you order by CreatedUtc alone and two rows share a timestamp, the cursor is ambiguous — you'll skip or repeat rows.

Always append a unique column, usually the primary key: ORDER BY CreatedUtc DESC, Id DESC. And index that exact composite, or you've traded an offset scan for a sort.

Filtering, sorting and shaping 🟡 Intermediate

GET /api/orders
      ?status=paid,shipped          # multiple values
      &createdAfter=2025-01-01
      &minTotal=100
      &sort=-createdUtc,total       # '-' prefix = descending
      &fields=id,total,status       # sparse fieldset
      &limit=50
Production trap — unbounded query surfaces

Letting clients sort or filter on any field seems generous and is a denial-of-service vector. A sort on an unindexed column over ten million rows is a table scan and a sort — one request can saturate your database.

Three defences: allowlist the sortable and filterable fields, make sure each has a supporting index, and always enforce a maximum page size server-side. A client asking for limit=1000000 should get 100, not a timeout.

On exposing OData or raw query languages

It's tempting — one endpoint, infinite flexibility. But you've now published your schema as your API contract, you can't reason about which queries are possible, and you can't index for them. Renaming a column becomes a breaking change.

It works for genuinely analytical, internal, admin-facing endpoints. For a public API, an explicit allowlisted query surface is far easier to operate.

Design for the client you have ⭐ Senior-level

In simple terms

A perfectly normalised resource-per-entity API can require twelve round trips to render one screen.

On a mobile network, that's a slow app — and no amount of design purity fixes it.

Say a mobile order-detail screen needs the order, the customer, the lines, the product names and the shipment status. Strict resource design gives you:

GET /orders/42                    →  1 request
GET /customers/{customerId}       →  1
GET /orders/42/lines              →  1
GET /products/{id}  × 5           →  5
GET /shipments?orderId=42         →  1
                                    ───
                                     9 round trips

Three legitimate answers, and which to pick:

ApproachHowTrade-off
Expansion parameterGET /orders/42?expand=customer,lines.productStays one resource model; the expansion logic can get complex
Purpose-built endpointGET /orders/42/detail-viewOne fast call; couples the API to a UI screen
BFFA backend per client type that aggregatesCleanest separation; another service to own

For one or two clients, an expand parameter is usually enough. Once you have genuinely different clients — mobile, web, a partner API — with different needs and different teams, a BFF is the honest answer.

Senior signal

Naming the trade-off rather than picking a side. "A purpose-built endpoint couples my API to a UI screen, which I'd normally avoid — but nine round trips on a mobile connection is a worse problem than that coupling. I'd add the endpoint and be explicit that it exists for that screen."

That's an engineering decision. "It wouldn't be RESTful" is not.

Bulk operations 🟡 Intermediate

Sending 500 individual POSTs to import data is slow and hard to make transactional. But bulk endpoints raise a question people forget: what does partial failure return?

POST /api/orders/bulk
{ "items": [ {...}, {...}, {...} ] }

→ 207 Multi-Status
{
  "results": [
    { "index": 0, "status": 201, "id": "a1" },
    { "index": 1, "status": 400, "error": { "type": "validation", "detail": "..." } },
    { "index": 2, "status": 201, "id": "a3" }
  ]
}

The design decision to make explicitly: all-or-nothing, or best-effort? All-or-nothing is simpler to reason about but one bad row rejects 499 good ones. Best-effort needs per-item results and the client must handle them. Either is fine — silently doing one while documenting the other is not.

Key takeaways
  • REST is six constraints. Statelessness is the one that buys you horizontal scaling.
  • Most APIs are Richardson level 2. Saying so is more credible than claiming level 3.
  • URLs are nouns; methods are verbs. Verb endpoints for genuine actions are fine and common.
  • Don't expose status as a writable field — use explicit action endpoints.
  • Offset pagination degrades with depth and shifts with inserts. Keyset fixes both.
  • Keyset needs a unique tiebreaker column and a matching composite index.
  • Allowlist sortable and filterable fields, and cap page size server-side.
  • Design for the client. Nine round trips beats no coupling only in theory.

Common mistakes

  • Verbs in URLs for plain CRUD — POST /getOrders.
  • Deep nesting: /customers/1/orders/42/lines/7/notes/3.
  • Offset pagination on a large live table — slow and unstable.
  • No unique tiebreaker in a keyset cursor, so rows repeat or vanish.
  • No maximum page size, so a client can request a million rows.
  • Sorting on arbitrary unindexed columns.
  • Exposing status as writable, letting clients skip your state machine.
  • Bulk endpoints with undefined partial-failure behaviour.
  • Inconsistent conventions — snake_case here, camelCase there.

Interview questions

Is your API RESTful? What does that actually mean? ⭐ Senior-level
How I'd answer

"Honestly — mostly, not fully. REST is six constraints from Fielding's thesis, and the one almost nobody implements is HATEOAS, where the server sends links telling the client what it can do next. So I'd say my APIs sit at Richardson maturity level 2: resources, proper HTTP methods, meaningful status codes."

"The constraint I do care about is statelessness, because it's the one that buys something concrete. If no server holds per-client conversational state, any instance can handle any request — so I scale by adding instances rather than needing sticky sessions. That's also why JWTs are common for APIs: the token carries the identity so there's no session lookup."

"On HATEOAS I'd be direct about why I skip it. Clients hard-code URLs anyway because they're written against a known version. It roughly doubles payload size for a benefit most clients don't consume. And tooling largely ignores link relations — whereas a generated OpenAPI client already gives us discoverability at build time, which is what teams actually want."

"I'd also say that being 'RESTful' isn't the goal. What matters is consistency, correct HTTP semantics so infrastructure behaves, useful errors, and designing for the client you have. I'd happily add a purpose-built endpoint that collapses nine round trips into one for a mobile screen, even though it's less pure — nine round trips on a mobile connection is a worse problem than that coupling."

What they're really checking
  • Do you know REST is constraints, not a synonym for HTTP+JSON?
  • Are you honest about HATEOAS rather than overclaiming?
  • Do you know why statelessness matters?
  • Can you prioritise pragmatism over labels?
Weak answers
  • Red flag: "yes, fully RESTful" — the follow-up on HATEOAS will expose it.
  • Red flag: "REST means using JSON and HTTP verbs."
Likely follow-ups
  • What does stateless actually rule out?
  • How would you model "cancel an order"?
  • When would you choose gRPC or GraphQL instead?
How would you paginate an endpoint over 50 million rows? 🔥 Must know
How I'd answer

"Not with offset pagination — that's the key point. OFFSET makes the database read and discard every row before the offset, so page one is instant and page ten thousand times out. Performance degrades linearly with depth."

"There's a correctness problem too, which people notice less. If rows are being inserted while a user pages through, everything shifts — so they see the same row twice or skip one entirely. On a live table that's guaranteed, not a corner case."

"So I'd use keyset pagination. Instead of 'skip 100,000 rows', the cursor says 'give me rows after this one'. The query becomes a WHERE on the sort key, which uses the index to seek straight to position — constant time regardless of depth. And because it's anchored to a value rather than a count, inserts don't shift the window."

"Two implementation details that matter. The sort key must be unique, so I'd use a composite — ORDER BY CreatedUtc DESC, Id DESC — because two rows sharing a timestamp would make the cursor ambiguous. And I'd need an index on that exact composite, otherwise I've traded an offset scan for a sort."

"I'd encode the cursor as an opaque base64 token rather than exposing the raw values. That way it's clearly not something clients should construct, and I can change the internal representation later without breaking them."

"The trade-off I'd state: keyset gives up jumping to an arbitrary page number and cheap total counts. For an API, infinite scroll, or an event feed, nobody needs those. If a UI genuinely needs page numbers — an admin table someone navigates by page — I'd use offset but cap the depth and require a filter first, so nobody pages to row 500,000."

"And regardless of approach, a server-enforced maximum page size. A client asking for a million rows gets 100."

What they're really checking
  • Do you know why offset is slow — the read-and-discard mechanism?
  • Do you know about the shifting-rows correctness problem?
  • Do you mention the unique tiebreaker and the index?
  • Do you state what keyset gives up?
Weak answers
  • Red flag: offset pagination with no caveats.
  • Red flag: no mention of a maximum page size.
Likely follow-ups
  • How do you give the user a total count?
  • What if they want to sort by a different column?
  • What index would you create?
