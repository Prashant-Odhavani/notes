Reliability, Rate Limits & Webhooks

Designing an API that survives retries, protects itself from callers, and can call other people back without losing events.

🟡 Intermediate 🔴 Advanced ⭐ Senior-level
Quick revision
  • A timeout is the ambiguous case: you don't know whether the request succeeded. Everything here follows from that.
  • Idempotency keys make a POST safe to retry. Client supplies the key, server stores the result.
  • Retry only transient failures, with backoff and jitter, and a cap.
  • Timeout budgets: each hop's timeout must be shorter than its caller's, or you do work nobody is waiting for.
  • 429 needs Retry-After, and rate limit headers so clients can self-regulate.
  • Webhooks need signatures, timestamps and idempotency — you're asking someone to trust an unsolicited request.

Why a timeout is the hard case 🔥 Must know

In simple terms

If a request returns 500, you know it failed. If it returns 200, you know it worked.

If it times out, you know nothing. It may have completed and only the response was lost.

Think of it this way

You post a letter with a cheque and hear nothing back. Did it arrive and the reply got lost, or did the letter never arrive?

Send a second cheque and you might pay twice. Don't send it and the bill might go unpaid. You need a reference number on the cheque so the recipient can tell it's the same one.

That reference number is an idempotency key.

Idempotency keys 🔥 Must know

POST /api/payments
Idempotency-Key: 7f3a9c21-4e8b-11ee-be56-0242ac120002
Content-Type: application/json

{ "orderId": "42", "amount": 4999, "currency": "GBP" }

The server stores the key with the response. A repeat with the same key returns the stored response rather than charging again.

RequestServer behaviour
First time with key KProcess it, store the response against K, return it
Repeat with key K, same bodyReturn the stored response. Do not reprocess
Repeat with K while the first is still runningReturn 409 — "in progress, retry shortly"
Repeat with K but a different bodyReturn 422 — the key is being reused incorrectly
The two rows people forget

The in-progress case is the one that bites. A client times out after two seconds and retries, but the original request is still running. If you just check "have I seen this key?" and find nothing stored yet, you'll process it twice concurrently — which is exactly the scenario the key existed to prevent.

So the key needs to be claimed before processing, not recorded after. Insert the key with a status of in progress inside the same transaction, and let a unique constraint reject the duplicate.

The different body, same key case matters too — that's a client bug, and silently returning the old response hides it.

public async Task<Result<Payment>> ChargeAsync(
    string idempotencyKey, ChargeRequest request, CancellationToken ct)
{
    // 1. Already completed? Replay the stored response.
    var existing = await _db.IdempotencyRecords
        .FirstOrDefaultAsync(r => r.Key == idempotencyKey, ct);

    if (existing is { Status: RecordStatus.Completed })
        return Result.Success(existing.DeserializeResponse<Payment>());

    if (existing is { Status: RecordStatus.InProgress })
        return Result.Conflict("Request already in progress");

    // 2. CLAIM the key. The unique index is what actually makes this safe -
    //    two concurrent requests race here and exactly one wins.
    _db.IdempotencyRecords.Add(new IdempotencyRecord
    {
        Key = idempotencyKey,
        RequestHash = Hash(request),       // detect key reuse with a different body
        Status = RecordStatus.InProgress
    });

    try   { await _db.SaveChangesAsync(ct); }
    catch (DbUpdateException) when (IsUniqueViolation)
    {
        return Result.Conflict("Request already in progress");
    }

    // 3. Do the work, then record the outcome.
    var payment = await _gateway.ChargeAsync(request, ct);
    await MarkCompletedAsync(idempotencyKey, payment, ct);

    return Result.Success(payment);
}
Practical details
  • The client generates the key, not the server. It has to survive the client's own retry, so it's created before the first attempt.
  • Scope it per client. Two customers must be able to use the same key value without colliding — the uniqueness is on (client, key).
  • Set a retention period. Keys don't need to live forever; long enough to cover any plausible retry window — usually 24 hours to a few days — then purge.
  • Hash the request body. That's how you detect a client reusing a key for a different operation.

This is the HTTP-level expression of the same idea as the inbox pattern for message consumers — and both rely on a unique constraint rather than a check.

Retries that help rather than hurt 🔥 Must know

StatusRetry?Why
408, 429✅ Yes, after Retry-AfterExplicitly transient
500, 502, 503, 504✅ Yes, with backoffServer-side, likely transient
Timeout / connection reset⚠️ Only if idempotent or keyedOutcome unknown
400, 422❌ NoThe request is wrong. It'll be wrong next time
401, 403❌ No (401 → refresh token once, then stop)Retrying won't grant permission
404❌ NoWon't appear by retrying
409⚠️ DependsConcurrency conflict → re-read and retry. Duplicate → don't
Remember this

Retrying a 4xx is pure extra load for zero chance of success.

The rule: retry when the server or the network failed, never when the request was wrong.

Why jitter matters more than backoff

Fixed backoff, no jitter:
  t=0s     1000 requests fail
  t=1s     1000 retries arrive SIMULTANEOUSLY   ← recreates the spike
  t=3s     1000 retries arrive simultaneously
  t=7s     1000 retries arrive simultaneously

The dependency never gets a quiet moment to recover.
Exponential backoff + jitter:
  t=0s        1000 requests fail
  t=1.0-2.0s  retries spread across a window   ← recovery is possible
  t=2.1-4.3s  spread wider
  t=4.4-8.9s  spread wider still

Backoff alone reduces the rate. Jitter breaks the synchronisation — and synchronisation is what turns a blip into a sustained outage. It's the more important half.

Retry amplification across layers

If service A retries 3× into B, and B retries 3× into C, then C sees up to 16× the original load — at the exact moment it's struggling.

Two defences: only retry at one layer (usually the outermost, closest to the user), and pair retries with a circuit breaker so you stop entirely once a dependency is clearly down.

Timeout budgets 🔴 Advanced ⭐ Senior-level

In simple terms

Each service in a chain must give up before its caller does.

Otherwise you're doing work for a request nobody is waiting for any more.

Browser        30s   ── gives up here
  └─ Gateway   25s   ── must be under 30
      └─ API   20s   ── must be under 25
          ├─ DB          3s
          └─ Service B   8s  (incl. its own retries)
              └─ DB      2s

Each layer leaves headroom for its own error handling and response.
Production trap — the inverted budget

The common failure is the opposite shape: the browser gives up after 30 seconds while the API's HTTP client has the default 100-second timeout.

So the user sees an error at 30s, retries, and the API is now doing two pieces of abandoned work — for another 70 seconds each. Under load that's how you exhaust the thread pool with work whose results will be discarded.

Always set explicit timeouts, and check the arithmetic holds from the outside in.

Also: retries consume the budget. Three retries at 5 seconds each is 15 seconds plus backoff — so an inner timeout of 5s with 3 retries needs a total budget of at least 20s, not 5s. That's why resilience pipelines have both a per-attempt and a total timeout.

Rate limit responses 🟡 Intermediate

HTTP/1.1 429 Too Many Requests
Retry-After: 30
RateLimit-Limit: 100
RateLimit-Remaining: 0
RateLimit-Reset: 30
Content-Type: application/problem+json

{
  "type": "https://api.example.com/errors/rate-limit",
  "title": "Rate limit exceeded",
  "status": 429,
  "detail": "100 requests per minute allowed. Retry in 30 seconds."
}
HeaderPurpose
Retry-AfterThe important one. Seconds (or a date) until the client may retry
RateLimit-LimitThe quota for the window
RateLimit-RemainingHow much is left — lets clients self-throttle before hitting 429
RateLimit-ResetWhen the window resets
Why the headers matter

Without Retry-After, a well-behaved client has to guess — and it will usually guess too aggressively, keeping you overloaded.

The Remaining header is better still: it lets clients slow down before they get rejected, which is the outcome you actually want.

Configuring the limiter itself is covered in ASP.NET Core performance — including the important caveat that the built-in limiter is per-instance.

Webhooks 🔴 Advanced

In simple terms

A webhook is your API making an HTTP call to your customer when something happens — the inverse of them polling you.

Which means you're asking them to trust an unsolicited request from the internet. That drives every design decision below.

Signing — so the receiver can trust it

POST /customer-endpoint
X-Webhook-Id: evt_9f8e7d
X-Webhook-Timestamp: 1735689600
X-Webhook-Signature: v1=5257a869e7bcd...
Content-Type: application/json

{ "type": "order.shipped", "data": { "orderId": "42" } }

The signature is an HMAC of timestamp + "." + body, using a shared secret. The receiver recomputes it and compares.

ElementWhat it prevents
HMAC signatureForged deliveries — only someone with the secret can produce a valid one
Timestamp in the signed payloadReplay attacks — the receiver rejects anything older than a few minutes
Event IDDuplicate processing — the receiver dedupes on it
Constant-time comparisonTiming attacks on signature verification
Why the timestamp must be inside the signature

If you sign only the body, an attacker who captures one valid delivery can replay it forever — the signature stays valid because the body hasn't changed.

Signing timestamp.body means the receiver can reject old deliveries, and an attacker can't change the timestamp without invalidating the signature. That's the whole mechanism.

Delivery guarantees you should promise

PropertyWhat to promise
DeliveryAt least once. Never claim exactly-once — you can't
OrderingNot guaranteed. Include a sequence number or timestamp instead
RetriesExponential backoff over hours, then dead-letter
SuccessAny 2xx. Treat 4xx as permanent, 5xx and timeouts as retryable
TimeoutA few seconds — the receiver should acknowledge and process async
What to tell consumers to do

Good webhook documentation tells the receiver to:

  • Return 2xx immediately and process asynchronously. If they do work before responding and it takes longer than your timeout, you'll retry a delivery they actually handled.
  • Deduplicate on the event ID, because at-least-once means duplicates will happen.
  • Not rely on order — use the sequence number or event timestamp.
  • Verify the signature before doing anything with the payload.

Saying that unprompted shows you've operated a webhook system rather than just sent an HTTP POST.

Production trap — webhooks and SSRF

Letting customers register an arbitrary URL means your server makes requests to addresses they choose. That's a server-side request forgery vector: they can point it at http://169.254.169.254/ to hit a cloud metadata endpoint, or at internal addresses to probe your network.

Defences: require HTTPS, block private and link-local IP ranges after DNS resolution, don't follow redirects, and send webhooks from an egress-restricted network path — not from the same context that can reach your internal services.

Key takeaways
  • A timeout is ambiguous. Every reliability pattern here exists because of that.
  • Idempotency keys make POST retry-safe. Claim the key before processing, using a unique constraint.
  • Handle the in-progress case, or concurrent retries defeat the whole mechanism.
  • Retry 5xx and timeouts; never 4xx. Backoff reduces rate, jitter breaks synchronisation.
  • Retry at one layer only, or you amplify load 16× across three hops.
  • Each hop's timeout must be under its caller's — and retries consume that budget.
  • 429 without Retry-After makes clients guess badly.
  • Webhooks: sign with a timestamp inside the signature, promise at-least-once, no ordering.
  • Customer-supplied webhook URLs are an SSRF risk.

Common mistakes

  • Retrying a non-idempotent POST with no key — duplicate charges.
  • Checking the idempotency key instead of claiming it, so concurrent retries both process.
  • Retrying 400s and 404s — load with no possible benefit.
  • Fixed-delay retries, so all clients retry in lockstep.
  • Retrying at every layer, multiplying load on a struggling dependency.
  • Inner timeout longer than the caller's, doing abandoned work.
  • 429 with no Retry-After.
  • Webhooks signed without a timestamp — replayable forever.
  • Promising webhook ordering you can't actually guarantee.
  • No allowlist on webhook URLs — SSRF.

Interview questions

How do you make a POST endpoint safe to retry? 🔥 Must know
How I'd answer

"With an idempotency key. The client generates a unique key — usually a GUID — and sends it in a header on the first attempt and on every retry. The server stores the key with the outcome, so a repeat returns the stored response rather than doing the work again."

"The reason it's necessary is that a timeout is ambiguous. The client doesn't know whether the charge went through or the request never arrived. Without a key, retrying is a coin flip between 'failed request' and 'charged twice'."

"The implementation detail that actually matters — and the one people get wrong — is that you have to claim the key before processing, not record it after. If you just check 'have I seen this key?' and the original request is still in flight, you'll find nothing stored and process it a second time concurrently. Which is exactly the scenario the key was meant to prevent."

"So I'd insert the key with an in-progress status inside the transaction, and rely on a unique constraint to reject the duplicate. Two concurrent requests race on the insert and exactly one wins; the loser gets a 409 saying 'in progress, retry shortly'."

"A few other details. I'd scope the key per client, so two customers can't collide. I'd hash the request body and store it, so if a client reuses a key with a different payload I can return 422 rather than silently replaying the wrong response — that's a client bug worth surfacing. And I'd set a retention window, maybe 24 hours, rather than keeping keys forever."

"This is the same idea as the inbox pattern for message consumers — and in both cases the unique constraint is what provides the guarantee, not the check."

What they're really checking
  • Do you know the timeout is the ambiguous case?
  • Do you handle the in-progress race — the discriminating detail?
  • Do you know the unique constraint, not the check, is the guarantee?
Weak answers
  • Red flag: "make it a PUT" — doesn't work when the server assigns the ID.
  • Red flag: checking for existence without claiming.
Likely follow-ups
  • What if the same key arrives with a different body?
  • How long do you keep the keys?
  • Where do you store them, and what if that store fails?
Design a webhook system. What would you get right? ⭐ Senior-level
How I'd answer

"The framing I'd start from is that I'm asking a customer to trust an unsolicited HTTP request from the internet. Everything else follows from that."

"Signing. An HMAC over the payload using a per-customer secret, so they can verify it came from me. Critically, the signature covers a timestamp as well as the body — if I sign only the body, someone who captures one valid delivery can replay it forever, because the signature stays valid. With the timestamp inside, the receiver rejects anything older than a few minutes and an attacker can't alter it without breaking the signature."

"Delivery guarantees. I'd promise at-least-once and explicitly not promise ordering, because I can't. I'd include an event ID so receivers can deduplicate, and a sequence number or timestamp so they can detect out-of-order arrival. Claiming exactly-once would be a lie I'd have to defend later."

"Retries. Exponential backoff with jitter over several hours, treating 5xx and timeouts as retryable and 4xx as permanent. Then dead-letter it and notify the customer — ideally disabling the endpoint after sustained failure so I'm not retrying a dead URL forever."

"Reliability on my side. The event has to be written in the same transaction as the state change it describes, otherwise I'll either lose events or send ones for changes that rolled back. So an outbox, with a dispatcher reading from it."

"Documentation. I'd tell receivers to return 2xx immediately and process asynchronously — if they do the work before responding and exceed my timeout, I'll retry something they already handled. And to verify the signature before parsing the payload."

"The security thing I'd raise unprompted is SSRF. Letting customers register an arbitrary URL means my servers make requests to addresses they choose — including cloud metadata endpoints or internal IPs. So: require HTTPS, resolve the DNS and block private and link-local ranges, don't follow redirects, and send from an egress-restricted path rather than from a context that can reach internal services."

What they're really checking
  • Do you sign, and do you know the timestamp must be inside the signature?
  • Are you honest about at-least-once and no ordering?
  • Do you connect it to the outbox pattern?
  • Does SSRF occur to you? That's the senior signal.
Weak answers
  • Red flag: "POST the JSON to their URL" with no signing.
  • Red flag: promising ordering or exactly-once delivery.
  • Red flag: no retry or dead-letter strategy.
Likely follow-ups
  • How do you handle a customer whose endpoint is down for a day?
  • How would you let them replay missed events?
  • How do you rotate the signing secret without downtime?
