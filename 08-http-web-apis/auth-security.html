Auth & API Security

OAuth 2.0 and OIDC — what they're each for, which flow to use, and the API vulnerabilities that actually get exploited.

🟡 Intermediate 🔴 Advanced 🔥 Must know
Scope of this page

This is the standards side: OAuth flows, OIDC, JWT structure, token handling. The ASP.NET Core mechanics — configuring bearer auth, policies, resource-based authorization, CORS and antiforgery — are in section 07.

Quick revision
  • OAuth 2.0 is authorization, not authentication. It answers "may this app act on my behalf?"
  • OIDC sits on top of OAuth and adds authentication — the id_token tells you who the user is.
  • Authorization Code + PKCE for anything with a user. Client credentials for machine-to-machine.
  • Implicit and password flows are deprecated. Knowing that is a real signal.
  • A JWT is signed, not encrypted. Anyone holding it can read the payload.
  • Access token = short-lived, sent to APIs. Refresh token = long-lived, sent only to the auth server.

OAuth 2.0 vs OpenID Connect 🔥 Must know

In simple terms

OAuth 2.0 is about delegated access. "Let this app read my calendar" — it never tells the app who you are.

OIDC adds identity on top. "Here's who this user is, verifiably."

Think of it this way

OAuth is a hotel key card. It opens room 402 and the gym. It doesn't say your name, and the door doesn't care — it only checks whether the card grants access.

OIDC is the photo ID you showed at reception to get the card. That's what proves who you are.

The classic mistake — using an access token to identify the user

An access token is meant for the API, and its format isn't guaranteed. Some providers issue opaque strings; some rotate the format. It may not contain a user identifier at all.

An id_token is meant for the client, is always a JWT, and is where identity claims belong.

"We use OAuth for login" was a very common design and it's why OIDC was created — OAuth alone doesn't define how to prove identity, so everyone invented their own incompatible way.

The short version

User involved? Authorization Code with PKCE.

No user, just two services? Client Credentials.

That covers almost everything you'll build.

Authorization Code + PKCE, step by step

1. App generates a random 'code_verifier', hashes it -> 'code_challenge'

2. Browser -> auth server:
   /authorize?response_type=code
             &client_id=...&redirect_uri=...
             &code_challenge=XYZ&code_challenge_method=S256
             &scope=openid profile orders.read&state=abc123

3. User authenticates with the AUTH SERVER (your app never sees the password)

4. Auth server -> browser redirect:
   https://yourapp/callback?code=SHORT_LIVED_CODE&state=abc123
                                    ↑ useless on its own

5. App -> auth server (back channel, server to server):
   POST /token   grant_type=authorization_code
                 &code=SHORT_LIVED_CODE
                 &code_verifier=ORIGINAL_RANDOM   ← proves same requester

6. Auth server returns: access_token, id_token, refresh_token

Two protections in that flow are worth being able to explain, because they're what interviews probe:

MechanismProtects against
PKCE (code_verifier / code_challenge) Authorization code interception. The code travels through the browser, where a malicious app or a logged URL could capture it. Without PKCE, whoever holds the code can exchange it. With PKCE, they'd also need the original random verifier, which never left the legitimate app.
state parameter CSRF on the callback. The app checks the returned state matches what it sent, so an attacker can't trick a user's browser into completing their login and binding the attacker's account.
Why the code is exchanged server-side

Step 5 happens on the back channel — server to server, never through the browser. So the tokens themselves never appear in a URL, browser history, referrer header or proxy log.

That's exactly what the deprecated implicit flow got wrong: it returned the access token directly in the redirect fragment, so the token ended up in the browser's address bar. PKCE made authorization code viable for SPAs, which is why implicit was retired rather than fixed.

Why the two deprecated flows were deprecated

FlowProblem
Implicit Returned the access token in the URL fragment — so it landed in browser history, referrer headers and logs. No refresh tokens either, so it needed long-lived access tokens, making the exposure worse.
Resource Owner Password The application collects the user's password and sends it to the auth server. That defeats the whole point: the app now handles credentials, can't support MFA or federated login, and trains users to type their password into third-party UIs.
Senior signal

Knowing that implicit and password grants are deprecated — and why — is one of the cleanest ways to show your auth knowledge is current rather than from a 2016 tutorial.

If you see a codebase using the password grant, that's a finding worth raising: it usually means MFA can't be added without rework.

Remember this

Never send an ID token to an API, and never use an access token to identify a user.

They have different audiences. An API validating an id_token is accepting a token that wasn't issued for it.

The revocation problem

A JWT is validated by checking its signature. That means the API doesn't call the auth server — which is the whole performance benefit, and also the whole problem:

The consequence

You cannot revoke a JWT. If a user is disabled or a token is stolen, it keeps working until it expires.

The standard mitigation is short-lived access tokens plus a revocable refresh token:

  • Access token: 5–15 minutes. Worst case, a stolen token is useful for that long.
  • Refresh token: long-lived but stored server-side, so it can be revoked. The client exchanges it for a new access token when the old one expires.
  • Refresh token rotation: each refresh issues a new refresh token and invalidates the old one. If an old one is ever reused, that's evidence of theft — and the whole family gets revoked.
If you genuinely need instant revocation

Then stateless validation isn't enough and you have to reintroduce a check — a denylist of revoked token IDs (the jti claim) in a fast store like Redis, checked on each request.

That's a real trade-off: you've given up the statelessness you chose JWTs for. Worth doing for high-value operations, not for every request. Be able to say that rather than claiming JWTs are revocable.

Two things people get wrong about JWTs

1. Signed is not encrypted. The payload is base64, not encryption — anyone holding the token can read every claim. So no PII you wouldn't want exposed, and certainly no secrets. Signing guarantees integrity, not confidentiality.

2. Never trust the alg header. The historic attack is changing alg to none, or from RS256 to HS256 so the library verifies using the public key as an HMAC secret. Libraries pin the expected algorithm now, but only if you configure it — validate against your expected algorithm rather than accepting what the token claims.

Where a browser should store a token 🔴 Advanced

There is no free option

Both have a real attack. The question is which you'd rather defend against.

Most guidance prefers the cookie, because XSS token theft is silent and gives an attacker a reusable credential, whereas CSRF has a well-understood standard defence.

The pattern that avoids the choice is a backend-for-frontend: the BFF holds the tokens server-side and issues the browser a plain HttpOnly session cookie. The browser never holds a token at all, so XSS can't steal one — and the BFF handles refresh transparently.

The pattern behind most of them

Nearly every item on that list is trusting the client — trusting it to send only expected fields, to only request its own data, to only call the endpoints the UI shows.

The server has to assume the client is an attacker with your API documentation.

Production trap — "the UI doesn't show that button"

Hiding an action in the front end is not authorization. Anyone can read your JavaScript, watch the network tab, or just try the obvious URL.

Every endpoint needs a server-side check, and every query needs an ownership filter — regardless of what the UI offers. This is the single most common real-world API vulnerability, and it's always the same root cause.

Key takeaways
  • OAuth 2.0 = authorization. OIDC = authentication on top of it.
  • Access token for the API; ID token for the client. Don't mix them.
  • Authorization Code + PKCE for users; Client Credentials for services.
  • Implicit and password grants are deprecated — know why.
  • PKCE stops code interception; state stops callback CSRF.
  • JWTs are signed, not encrypted, and effectively unrevocable. Keep them short-lived.
  • Always validate issuer, audience, expiry and the expected algorithm.
  • Cookie vs localStorage is XSS vs CSRF. A BFF avoids the choice.
  • Most API breaches are the server trusting the client.

Common mistakes

  • Using an access token to identify the user instead of an ID token.
  • Long-lived access tokens with no refresh flow, making revocation impossible.
  • Not validating the audience, so a token for another service is accepted.
  • Putting PII or secrets in the JWT payload.
  • The password grant in new code, which blocks MFA.
  • Skipping PKCE for a SPA or mobile app.
  • Not checking state on the OAuth callback.
  • Relying on the UI to hide privileged actions.
  • Returning full entities and letting the client filter.

Interview questions

Intermediate

What's the difference between OAuth 2.0 and OpenID Connect? 🔥 Must know
How I'd answer

"OAuth 2.0 is an authorization framework. It's about delegated access — letting an application act on a user's behalf without the user handing over their password. The token it gives you says what the app may do, not who the user is."

"OpenID Connect is a thin layer on top of OAuth that adds authentication. It defines an id_token, always a JWT, containing verifiable identity claims — subject, email, name."

"The analogy I use is a hotel: the OAuth access token is the key card, which opens specific doors and says nothing about your name. OIDC is the photo ID you showed at reception."

"The reason this distinction matters practically is a very common mistake — using an OAuth access token to identify the user. Access tokens are meant for the API and their format isn't guaranteed; some providers issue opaque strings, and they may contain no user identifier at all. So code that parses an access token to find out who's logged in is relying on something the spec doesn't promise."

"That's actually why OIDC exists. Everyone was using OAuth for login and inventing their own incompatible way of getting identity out of it, so OIDC standardised it."

"So in practice: the ID token goes to my client and tells me who the user is. The access token goes to the API and proves permission. Different audiences, different jobs."

What they're really checking
  • Do you know OAuth alone isn't authentication?
  • Do you know the access/ID token split and their audiences?
  • Bonus: knowing why OIDC was created.
Weak answers
  • Red flag: "they're the same thing" or "OIDC is just OAuth for login".
  • Red flag: using an access token for identity with no caveat.
Likely follow-ups
  • Which flow would you use for a SPA?
  • What's in an ID token?
  • Can an API validate an ID token?
Which OAuth flow would you use for a single-page app, and why?
How I'd answer

"Authorization Code with PKCE. Not implicit — that used to be the recommendation for SPAs and it's been deprecated."

"Implicit returned the access token directly in the URL fragment of the redirect. So the token ended up in the browser address bar, in history, potentially in referrer headers and proxy logs. And because implicit didn't support refresh tokens, you needed long-lived access tokens, which made the exposure worse."

"Authorization Code avoids that by returning a short-lived code through the browser and exchanging it for tokens on a separate back-channel request. So the tokens never travel through the browser at all."

"The problem historically was that the exchange requires a client secret, and a SPA can't keep a secret — it's all downloadable. That's what PKCE solves. The app generates a random verifier, sends a hash of it with the authorize request, and sends the original when exchanging the code. Whoever intercepts the code can't use it without the verifier, which never left the app. So you get proof-of-possession without a stored secret."

"I'd also check the state parameter on the callback, which is a separate protection — it stops CSRF on the redirect, where an attacker tricks a user's browser into completing the attacker's login."

"And for token storage I'd think carefully. localStorage is readable by any XSS; an HttpOnly cookie isn't but needs CSRF protection. If the architecture allows it I'd prefer a backend-for-frontend that holds the tokens server-side and gives the browser a session cookie — then the browser never holds a token at all."

What they're really checking
  • Do you know implicit is deprecated, and why?
  • Can you explain what PKCE actually protects against?
  • Bonus: state, and the token storage trade-off.
Weak answers
  • Red flag: "implicit flow, because SPAs can't keep a secret" — the 2016 answer.
  • Red flag: naming PKCE without being able to say what it prevents.
Likely follow-ups
  • Where would you store the refresh token?
  • What does state protect against?
  • How do you handle silent token renewal?

Advanced

A user is disabled but their JWT still works. Is that a bug? ⭐ Senior-level
How I'd answer

"It's expected behaviour, not a bug — but it may well be an unacceptable design, and that distinction is the actual answer."

"A JWT is validated by checking its signature. The API doesn't call the auth server, which is exactly why it scales — but it also means the API has no idea the user was disabled. The token remains cryptographically valid until it expires."

"So the question becomes: how long is that window, and is it acceptable? If access tokens live 15 minutes, the worst case is 15 minutes of access after disabling. For most systems that's fine. If they live 24 hours, that's a genuine security problem and the fix is shortening the lifetime."

"The standard design is short access tokens plus a longer refresh token that is checked server-side. When the access token expires, the client refreshes — and at that point the auth server sees the account is disabled and refuses. So revocation takes effect within one access-token lifetime rather than immediately."

"I'd also mention refresh token rotation: each refresh issues a new refresh token and invalidates the old one. If an old one gets reused, that's evidence it was stolen, and you revoke the whole family."

"If the business genuinely needs instant revocation — say, a compromised account with access to payments — then stateless validation isn't sufficient and you have to reintroduce a check: a denylist of revoked token IDs, the jti claim, in Redis, checked per request."

"I'd be explicit that this gives up the statelessness you chose JWTs for. So I'd apply it selectively — on high-value operations rather than every request — or accept a short window everywhere else. That's the honest trade-off, and pretending JWTs are revocable is where people go wrong."

What they're really checking
  • Do you know this is inherent to stateless validation, not a defect?
  • Can you reason about the window rather than just naming it?
  • Do you know refresh rotation and the denylist option — and its cost?
Weak answers
  • Red flag: "just delete the token" — the client holds it, you can't.
  • Red flag: claiming JWTs can be revoked with no mechanism.
Likely follow-ups
  • How would you implement logout with JWTs?
  • What lifetime would you choose, and how would you decide?
  • What does a denylist cost you at scale?
