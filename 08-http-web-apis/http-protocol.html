HTTP Protocol

Methods, status codes and caching. Boring-sounding, and the source of a surprising number of production bugs.

🟢 Beginner 🟡 Intermediate 🔥 Must know
Quick revision
  • Safe = doesn't change state. Idempotent = doing it twice has the same effect as once.
  • GET is safe and idempotent. PUT/DELETE are idempotent but not safe. POST is neither.
  • PUT replaces the whole resource. PATCH applies a partial change — and is not idempotent in general.
  • 401 = I don't know who you are. 403 = I do, and no.
  • 409 = conflicts with current state. 422 = well-formed but semantically invalid.
  • ETags give you both cheap caching and optimistic concurrency, from one header.

Safe, idempotent, cacheable 🔥 Must know

In simple terms

Safe — the request doesn't change anything. You can send it freely.

Idempotent — sending it five times leaves the same result as sending it once.

These are different. A DELETE is idempotent but definitely not safe.

Think of it this way

Safe is reading a page in a book. Do it as often as you like; nothing changes.

Idempotent is a light switch set to "off". Flick it to off five times — still off. Something changed, but repeating it changes nothing further.

Neither is adding a line to a list. Do it five times and you have five lines.

Why idempotency is the important column

It determines whether a client can safely retry after a timeout.

A timeout means you don't know whether the request succeeded. If the method is idempotent, retrying is free. If it isn't, retrying might duplicate the effect.

Production trap — GET that changes state

An endpoint like GET /api/orders/123/cancel looks harmless and is a real hazard:

  • A browser prefetch or link preview can trigger it.
  • A crawler following links will fire every one it finds.
  • A proxy or CDN may cache the response, so the second call doesn't reach you.
  • An email client scanning links has been known to delete data this way.

State changes need POST, PUT, PATCH or DELETE. This is also the root of the CSRF-via-image-tag attack.

PUT vs PATCH 🔥 Must know

In simple terms

PUT says "make the resource look exactly like this" — it's a full replacement.

PATCH says "apply this change to it" — a partial modification.

PUT /api/customers/42
Content-Type: application/json

{ "name": "Ada Lovelace", "email": "ada@example.com", "tier": "Gold" }

# Omitting a field means "this field should be absent/default".
# Send only { "name": "Ada" } and email and tier may be wiped.
PATCH /api/customers/42
Content-Type: application/json

{ "email": "ada@newdomain.com" }

# Name and tier are untouched.
PUTPATCH
SemanticsFull replacementPartial update
Missing fields mean"remove / reset this""leave this alone"
Idempotent?YesNot necessarily
Can create the resource?Yes, if you allow it (client supplies the ID)No — the resource must exist
Why PATCH isn't automatically idempotent

It depends on the operation you express. A patch that says { "email": "x" } is idempotent — apply it twice, same result.

But JSON Patch allows relative operations: [{ "op": "add", "path": "/tags/-", "value": "vip" }] appends. Apply that twice and you have two vip tags.

So the spec can't promise idempotency for PATCH in general — even though most real-world patches happen to be idempotent.

Common mistake

Implementing PUT as a partial update — ignoring fields the client didn't send. It's convenient, and it breaks the contract: a client that legitimately wants to clear a field by omitting it can't, and a client that expects replacement semantics gets surprised.

If you want partial updates, use PATCH. If you implement PUT, honour replacement.

400 vs 422 vs 409 — the ones people argue about

A rule that resolves most of it

400 — I couldn't understand the request.

422 — I understood it, but it's not valid.

409 — I understood it and it's valid, but it clashes with the current state.

SituationCode
Malformed JSON400
"quantity": "abc" where a number was expected400
Required field missing400
"quantity": -5 — valid JSON, invalid value400 or 422 (both defensible)
Email already registered409
Cannot ship an unpaid order409
Insufficient stock409 (or 422)
Optimistic concurrency conflict409
The pragmatic answer

400 vs 422 is genuinely debated, and ASP.NET Core's built-in validation returns 400. Fighting that to return 422 is usually not worth it.

What matters far more is being consistent and giving a machine-readable error body. A client can handle "always 400 with a typed error" easily; it can't handle "sometimes 400, sometimes 422, sometimes 200 with an error object".

In an interview, say that. Knowing the distinction and knowing it's low-stakes is the mature answer.

Production trap — 200 with an error body

200 OK with { "success": false, "error": "..." } breaks everything that isn't your own client code:

  • Monitoring reports a 100% success rate while every request fails.
  • Load balancers and proxies treat it as healthy.
  • Retry policies won't retry it.
  • Generated clients throw away the error because the call "succeeded".

The status code is how you talk to infrastructure. The body is how you talk to the client. Use both.

Caching and conditional requests 🟡 Intermediate

In simple terms

An ETag is a version marker for a resource — usually a hash or a row version.

The client sends it back, and if nothing changed you reply 304 with no body.

GET /api/orders/42
→ 200 OK
  ETag: "a1b2c3"
  Cache-Control: private, max-age=60
  { ...order... }

# Later, the client asks again but includes what it has:
GET /api/orders/42
If-None-Match: "a1b2c3"
→ 304 Not Modified          # no body at all - just headers

The win is bandwidth and serialization cost. The server still checks, but it doesn't send or serialize the payload — which for a large response is most of the work.

The same header solves optimistic concurrency ⭐ Senior-level

PUT /api/orders/42
If-Match: "a1b2c3"
{ ...changes... }

→ 200 OK                    # still version a1b2c3, change applied
→ 412 Precondition Failed   # someone else changed it first
Remember this

If-None-Match on a GET = caching. "Only send it if it changed."

If-Match on a PUT = concurrency. "Only apply this if it hasn't changed."

That second form solves the lost update problem at the HTTP layer — the same problem EF Core solves with a RowVersion token, and the reason the two pair naturally: use the row version as the ETag. See EF Core concurrency.

Cache-Control, briefly

Production trap — public on authenticated responses

Marking a user-specific response public lets a shared cache — a CDN, a corporate proxy — store it and serve it to someone else.

That's a data leak caused by one header. Anything that varies by user is private at minimum, and no-store if it's sensitive. And use Vary on Authorization so caches key on the identity.

HTTP/1.1 vs 2 vs 3 🟡 Intermediate 💡 Good to know

HTTP/1.1HTTP/2HTTP/3
TransportTCPTCPQUIC (UDP)
Concurrent requestsOne per connection (so browsers open ~6)Multiplexed over one connectionMultiplexed over one connection
Head-of-line blockingAt the HTTP layerFixed at HTTP, remains at TCPFixed — independent streams

The one thing to remember about each

HTTP/2 fixed head-of-line blocking at the HTTP layer — but TCP still delivers in order, so one lost packet stalls every stream on that connection.

HTTP/3 moved to QUIC over UDP so streams are genuinely independent. A lost packet only stalls its own stream — which is why it helps most on mobile and lossy networks.

What it means practically: under HTTP/2 the old optimisations — domain sharding, concatenating files, image sprites — become counterproductive, because many small requests over one connection are now cheap. And gRPC requires HTTP/2, which is why it can't be called directly from a browser without a proxy.

Key takeaways
  • Safe ≠ idempotent. Idempotency is what makes retry-after-timeout safe.
  • Never change state with GET — prefetch, crawlers and caches will bite you.
  • PUT replaces, PATCH modifies. Don't implement PUT as partial.
  • 401 = unauthenticated, 403 = unauthorised. 409 = state conflict, 400/422 = invalid input.
  • Never return 200 with an error body — it lies to your monitoring and to proxies.
  • ETag + If-None-Match = caching. ETag + If-Match = optimistic concurrency.
  • Cache-Control: public on a user-specific response is a data leak.
  • HTTP/2 multiplexes but keeps TCP head-of-line blocking; HTTP/3 fixes it via QUIC.

Common mistakes

  • State-changing GET endpoints.
  • 200 with { success: false }, hiding failures from monitoring.
  • 500 for validation errors, causing pointless retries and false alerts.
  • PUT that ignores missing fields, so clients can't clear a value.
  • 403 for another tenant's record, confirming it exists.
  • 429 with no Retry-After, so clients guess and retry too fast.
  • Cache-Control: public on authenticated responses.
  • 201 with no Location header, so the client can't find what it created.

Interview questions

Basic

What's the difference between PUT and PATCH? 🔥 Must know
How I'd answer

"PUT is a full replacement — you're saying 'make the resource look exactly like this payload'. PATCH is a partial update — 'apply this change and leave the rest alone'."

"The practical consequence is what happens to fields you don't send. With PUT, omitting a field means it should be absent or reset. With PATCH, omitting it means leave it as it is. So sending { "name": "Ada" } as a PUT could legitimately wipe the email address."

"The other difference is idempotency. PUT is idempotent by definition — send it five times, same result. PATCH is not guaranteed to be, because the patch document can express relative operations. A JSON Patch that appends to an array applied twice gives you two entries."

"That matters for retries: a client that times out can safely retry a PUT, but can't assume the same for PATCH unless the API documents it as idempotent."

"The mistake I'd watch for in review is implementing PUT as a partial update because it's more convenient. It breaks the contract — a client can no longer clear a field by omitting it, and anyone relying on replacement semantics gets surprised. If you want partial updates, use PATCH and say so."

What they're really checking
  • Do you know it's about replacement vs modification, not just "update"?
  • Do you know PATCH isn't guaranteed idempotent, and why?
  • Do you connect it to retry safety?
Likely follow-ups
  • Can PUT create a resource?
  • What's JSON Patch vs JSON Merge Patch?
  • How would you make a POST safe to retry?

Intermediate

What status code would you return for each of these, and why?
How I'd answer

"I'd frame it with a rule first: 400 means I couldn't understand the request, 422 means I understood it but it isn't valid, and 409 means it's valid but it clashes with the current state."

"So — malformed JSON is 400. A missing required field is 400. A negative quantity is arguably either 400 or 422; ASP.NET Core's built-in validation gives 400 and I wouldn't fight that."

"Email already registered is 409 — the request is perfectly valid, it just conflicts with existing state. Same for trying to ship an unpaid order: that's an illegal state transition, so 409."

"An optimistic concurrency conflict is 409, or 412 specifically if the client sent an If-Match header — 412 Precondition Failed is more precise there."

"Not authenticated is 401, authenticated but not permitted is 403. And for a record belonging to another tenant I'd return 404, not 403 — because 403 confirms the record exists, which lets someone enumerate valid IDs."

"Rate limited is 429, and I'd always include Retry-After, otherwise well-behaved clients guess and usually guess too aggressively."

"The thing I'd emphasise is that consistency beats precision here. 400 vs 422 is genuinely debated and low-stakes. What actually breaks clients is inconsistency — sometimes 400, sometimes 200 with an error object. I'd pick a convention, document it, and apply it everywhere, with a machine-readable error type in the body so clients branch on that rather than on the message."

What they're really checking
  • Do you have a rule, or are you guessing per case?
  • Do you know 409 for state conflicts?
  • Do you volunteer 404-over-403 for cross-tenant access?
  • Do you value consistency over purity?
Weak answers
  • Red flag: 500 for anything caused by user input.
  • Red flag: 200 with an error flag in the body.
Likely follow-ups
  • What goes in the error response body?
  • What's the difference between 409 and 412?
  • Should a client retry a 409?
How would you use ETags? ⭐ Senior-level
How I'd answer

"An ETag is a version identifier for a resource — typically a hash of the content, or a row version from the database. It gives you two quite different things from one header, which is why it's worth knowing well."

"The first is caching. I return an ETag with the response. The client sends it back as If-None-Match on the next request, and if nothing changed I return 304 with no body. The server still does the lookup, but it skips serializing and sending the payload — which for a large response is most of the cost."

"The second is optimistic concurrency. The client sends the ETag as If-Match on a PUT. If the resource has changed since they read it, the tag won't match and I return 412 Precondition Failed. That solves the lost update problem — where two users load the same record, both edit, and the second save silently overwrites the first."

"So: If-None-Match on a read is caching, If-Match on a write is concurrency. Same header, opposite intent."

"For implementation, the neat part is that if you already use a RowVersion column for EF Core concurrency, that value is your ETag. You're exposing the concurrency token you already have rather than computing a hash."

"One detail worth knowing: strong versus weak ETags. A strong tag means byte-identical; a weak one (prefixed W/) means semantically equivalent. If your response includes a generated timestamp, byte-identical is impossible, so a weak tag is more honest."

What they're really checking
  • Do you know both uses, and that they're different headers?
  • Do you connect it to the lost-update problem?
  • Bonus: the RowVersion-as-ETag link, and strong vs weak.
Likely follow-ups
  • How does this compare with a Last-Modified header?
  • What do you do when the ETag doesn't match — 409 or 412?
  • How does this interact with a CDN?
