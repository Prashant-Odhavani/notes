The event loop 🔥 Must know

In simple terms

JavaScript has one call stack. When it's empty, the event loop takes the next queued piece of work and runs it to completion.

Nothing interrupts running code. There is no pre-emption, so there are no data races — and no parallelism either.

Think of it this way

A single chef in a kitchen. They work on one dish at a time, start to finish, and never abandon a dish halfway.

Orders queue up. Some orders are marked urgent (microtasks) and jump ahead of the normal queue (macrotasks) — but only between dishes, never during one.

So one dish that takes twenty minutes blocks every other order, urgent or not.

QueueContainsPriority
Call stack Currently executing code Runs to completion, uninterruptible
Microtask queue Promise.then, await continuations, queueMicrotask, MutationObserver Drained completely after each task
Macrotask queue setTimeout, setInterval, I/O, DOM events One per loop iteration
Render Style, layout, paint Between macrotasks, when the browser chooses
The rule that answers every ordering question

Run the current task to completion → drain all microtasks → maybe render → take one macrotask → repeat.

"Drain all microtasks" is the part people miss. If a microtask queues another microtask, that runs too, before any timer.

console.log('1 sync');

setTimeout(() => console.log('2 timeout'), 0);      // macrotask

Promise.resolve().then(() => console.log('3 promise'));   // microtask

queueMicrotask(() => console.log('4 microtask'));

console.log('5 sync');

// Output:
//   1 sync
//   5 sync        <- all synchronous code first
//   3 promise     <- microtasks, in queue order
//   4 microtask
//   2 timeout     <- macrotask last, despite the 0ms delay
setTimeout(fn, 0) does not mean "now"

It means "queue this as a macrotask". It runs after all synchronous code and after every pending microtask — and browsers clamp nested timeouts to a minimum of about 4ms anyway.

So setTimeout(fn, 0) is a way to yield to the event loop, letting rendering and input happen. It is not a way to run something soon.

If you want "after the current work but before anything else", that's queueMicrotask or Promise.resolve().then().

A microtask loop starves the page permanently
function spin() {
  Promise.resolve().then(spin);   // queues another microtask, forever
}
spin();
// The microtask queue never empties, so the browser NEVER renders again.
// The tab is frozen and must be killed.

Because microtasks are drained completely before anything else, a microtask that queues another microtask creates an infinite queue. No rendering, no input, no timers — ever.

An equivalent setInterval loop is harmless by comparison, because macrotasks yield between iterations.

This is a good thing to know because it's a real production hazard in recursive promise code, and it demonstrates you understand why the drain rule matters rather than just reciting it.

Where async/await fits

async function run() {
  console.log('A');            // synchronous - runs immediately
  await null;                  // yields; the rest becomes a microtask
  console.log('B');            // microtask
}

console.log('start');
run();
console.log('end');

// Output: start, A, end, B
//   Everything before the first await runs SYNCHRONOUSLY.
//   Everything after it is a microtask continuation.
The C# comparison worth holding onto

This is exactly like C#'s async state machine: code before the first await runs synchronously on the calling thread, and the continuation is scheduled.

The difference is where it resumes. In .NET the continuation may run on a different thread. In JavaScript it always resumes on the same and only thread, as a microtask.

Which means: no locks are ever needed, and no work is ever offloaded. You get thread safety for free and parallelism not at all.

Closures 🔥 Must know

In simple terms

A closure is a function that remembers the variables where it was defined, and keeps them alive after that scope has finished.

The critical detail: it captures the variable itself, not a snapshot of its value.

for (var i = 0; i < 3; i++) {
  setTimeout(() => console.log(i), 100);
}
// Prints: 3, 3, 3
//
// `var` is FUNCTION-scoped, so there is exactly ONE `i`.
// All three closures captured the same variable.
// By the time the timers fire, the loop has finished and i === 3.
for (let i = 0; i < 3; i++) {
  setTimeout(() => console.log(i), 100);
}
// Prints: 0, 1, 2
// `let` is BLOCK-scoped, so each iteration gets its own binding.
Remember this

A closure captures the variable, not the value.

That one sentence explains the loop puzzle, stale values in React effects, and why let replaced var.

C# has the identical issue with foreach captures in older versions — so the concept isn't foreign, just more visible here.

// Private state - the module pattern, before classes existed
function createCounter() {
  let count = 0;                              // not accessible from outside
  return {
    increment: () => ++count,
    get value() { return count; }
  };
}

// Debounce - the closure holds the pending timer between calls
function debounce(fn, ms) {
  let timer;                                  // survives across invocations
  return (...args) => {
    clearTimeout(timer);
    timer = setTimeout(() => fn(...args), ms);
  };
}
Closures are the main cause of front-end memory leaks

A closure keeps its captured scope alive for as long as the function is reachable. So an event listener that captures a large object keeps that object in memory until the listener is removed.

In a single-page application, components mount and unmount constantly. A listener added on mount and never removed leaks the entire captured scope every single time — including DOM nodes that are no longer in the document.

That's why every framework has a cleanup mechanism: React's effect return function, Angular's ngOnDestroy or takeUntilDestroyed. Every subscription and listener needs a matching teardown.

It's the browser equivalent of not disposing an IDisposable — same category of bug, and harder to spot because nothing errors.

The this keyword 🔥 Must know

The rule

In a normal function, this is determined by how the function is called, not where it was defined.

In an arrow function, this is captured from the enclosing scope and can't be changed.

class OrderService {
  constructor() { this.orders = []; }

  load() {
    fetch('/api/orders')
      .then(function (response) {
        this.orders = response;        // `this` is NOT the OrderService
      });                              // TypeError: cannot set property of undefined
  }
}
load() {
  fetch('/api/orders')
    .then(response => {
      this.orders = response;          // `this` is the OrderService
    });
}
Why this bites .NET developers specifically

In C#, this inside an instance method is always the instance. There is no way for it to be anything else, so there's no habit of thinking about it.

In JavaScript, extracting a method breaks it: const m = obj.method; m(); — this is now undefined, because the call site has no receiver. Passing obj.method as a callback does exactly that.

Practical rule: use arrow functions for callbacks. Then this is lexical, like every other variable, and behaves the way a C# developer expects.

The empty-array trap

[] is truthy, so if (items) is true even when the array is empty. To check for content you need items.length.

Related: 0 and "" are falsy, which breaks the common default-value idiom. count || 10 returns 10 when count is 0 — almost certainly a bug.

Use ?? instead: count ?? 10 only falls back on null or undefined. That's the same distinction as C#'s null-coalescing operator, and it's the correct default choice.

Prototypes 🔴 Advanced

In simple terms

Every object has a hidden link to another object, its prototype. Property lookups walk that chain until they find the property or reach null.

class is syntax over this. There's no separate class system underneath.

Why you rarely need this in practice

Use class syntax and it behaves close enough to C# that the prototype chain is invisible.

Where it surfaces: reading library source, understanding that methods live on the prototype and are shared between instances while fields are per-instance, and knowing that adding to a built-in prototype (Array.prototype.foo = ...) affects every array in the application — which is why "don't extend built-ins" is a firm rule.

For an interview, being able to say "class is sugar over prototypal inheritance, and method lookup walks the prototype chain" is sufficient depth unless the role is front-end specialist.

Promises 🔥 Must know

// All must succeed; rejects on the FIRST failure
const [user, orders] = await Promise.all([fetchUser(), fetchOrders()]);

// Never rejects - reports per-promise outcome
const results = await Promise.allSettled([a(), b(), c()]);
results.forEach(r => r.status === 'fulfilled' ? use(r.value) : log(r.reason));

// First to SETTLE wins, success or failure
const fastest = await Promise.race([fetchPrimary(), timeout(5000)]);

// First to SUCCEED; rejects only if all fail
const any = await Promise.any([mirrorA(), mirrorB()]);

Sequential awaits in a loop — the performance bug
const results = [];
for (const id of ids) {
  results.push(await fetchOne(id));      // 100 ids x 50ms = 5 seconds
}
const results = await Promise.all(ids.map(fetchOne));   // ~50ms total

Identical to the sequential-await mistake in C#, and just as common.

Two caveats. Promise.all issues all requests at once, so 10,000 ids means 10,000 simultaneous requests — you may need to batch. And it rejects on the first failure, losing the successful results; use allSettled when partial success matters.

Also worth knowing: array.forEach does not await. An async callback passed to forEach returns promises that nobody observes, so the loop completes immediately and errors are swallowed. Use for...of with await, or map plus Promise.all.

Key takeaways
  • One thread. Synchronous work blocks rendering and input entirely.
  • Run task → drain all microtasks → maybe render → one macrotask.
  • Promises are microtasks, timers are macrotasks — so a promise always resolves before a setTimeout(0).
  • A microtask that queues microtasks freezes the page permanently.
  • Code before the first await is synchronous; the rest is a microtask.
  • Closures capture variables, not values — hence the var loop puzzle.
  • Unremoved listeners and subscriptions leak the whole captured scope.
  • this comes from the call site; arrow functions capture it lexically.
  • === always, ?? rather than || for defaults.
  • [] and {} are truthy; 0 and "" are falsy.
  • Promise.all for parallel work; allSettled when partial success is fine.

Common mistakes

  • Expecting async to give parallelism. It only helps with waiting.
  • Sequential awaits in a loop.
  • async callback in forEach — nothing awaits it.
  • var in a loop with closures.
  • Not removing listeners or subscriptions, leaking scope.
  • A non-arrow callback losing this.
  • == and its coercion surprises.
  • value || default when 0 or "" is valid.
  • if (array) to test for content.
  • Promise.all over thousands of items with no batching.
  • Treating a TypeScript type as runtime validation.

Interview questions

Intermediate

Explain the event loop. What order does this code print? 🔥 Must know
How I'd answer

"JavaScript has a single call stack, so only one thing runs at a time and nothing interrupts running code. The event loop's job is to decide what runs next when the stack empties."

"The cycle is: run the current task to completion, then drain the entire microtask queue, then optionally render, then take exactly one macrotask — and repeat."

"Microtasks are promise callbacks, await continuations, queueMicrotask. Macrotasks are setTimeout, setInterval, DOM events, network callbacks."

"So for the classic example — a synchronous log, a setTimeout with zero delay, a resolved promise's .then, and another synchronous log — the order is: both synchronous logs first, then the promise callback, then the timeout. The promise beats the timer even though the timer says zero milliseconds, because microtasks are drained before any macrotask is taken."

"The part people miss is the word drain. It's not one microtask per iteration — it's all of them, including any queued by those microtasks. Which has a real consequence: a microtask that recursively queues another microtask means the queue never empties, so the browser never renders again and the tab is frozen permanently. An equivalent setInterval loop is harmless, because macrotasks yield between iterations."

"On async/await specifically: everything before the first await runs synchronously, and everything after it becomes a microtask continuation. That's structurally identical to C#'s async state machine — the difference being that in .NET the continuation might resume on a different thread, whereas here it's always the same thread. Which is why you never need a lock in JavaScript, and never get parallelism either."

"The practical implication I'd emphasise: setTimeout(fn, 0) doesn't mean 'now', it means 'yield to the event loop'. It's how you let rendering and input happen during a long operation. And a synchronous loop over a large array blocks everything — rendering, clicks, timers — because there's no other thread to pick up the slack."

What they're really checking
  • Do you know microtasks are drained fully, not one at a time?
  • Can you predict the ordering and explain why?
  • Do you know where the await boundary falls?
  • Do you connect it to UI responsiveness?
Weak answers
  • Red flag: "the callback queue" with no microtask/macrotask distinction.
  • Red flag: thinking setTimeout(fn, 0) runs immediately.
Likely follow-ups
  • Where does rendering fit in?
  • What's requestAnimationFrame?

What does this print, and why? for (var i = 0; i < 3; i++) setTimeout(() => console.log(i)) 🔥 Must know
How I'd answer

"It prints 3, 3, 3."

"Two things combine to cause it."

"First, var is function-scoped, not block-scoped. So there is exactly one i for the whole loop, not one per iteration. All three arrow functions close over the same variable."

"Second, closures capture the variable, not its value at capture time. So when the callbacks eventually run, they read whatever i currently holds."

"And because setTimeout queues a macrotask, none of the callbacks run until the synchronous loop has completely finished — at which point i is 3, the value that failed the loop condition. Hence three 3s."

"The fix is let, which is block-scoped — each iteration gets a fresh binding, so the closures capture three different variables and it prints 0, 1, 2. That's the main practical reason let replaced var."

"Before let existed you'd use an IIFE to create a scope per iteration, and you'll still see that in older code — an immediately-invoked function taking i as a parameter, so the parameter is a per-call copy."

"The reason this matters beyond the puzzle: it's the same mechanism behind stale values in React effects. If an effect closes over a state variable and the dependency array doesn't include it, the effect keeps reading the value from the render it was created in. Same closure semantics, much harder to spot. Recognising it as one concept rather than two separate gotchas is the useful part."

"C# has the identical issue with loop-variable capture — it was fixed for foreach in C# 5 but for loops still capture a single variable. So the concept isn't foreign, it's just more visible in JavaScript because callbacks are everywhere."

What they're really checking
  • Do you know the answer and the two reasons?
  • Do you know closures capture variables, not values?
  • Can you connect it to a real framework bug?
Likely follow-ups
  • Fix it without changing var.
  • What's the temporal dead zone?
  • How does this cause a memory leak?

Advanced

How do closures cause memory leaks in a single-page application? ⭐ Senior-level
How I'd answer

"A closure keeps its entire captured scope alive for as long as the function itself is reachable. So the leak happens when something holds a reference to a function longer than intended."

"The canonical case is an event listener that's never removed. If a component adds a window resize listener on mount, and the handler closes over the component's state or a DOM node, then window holds the handler, the handler holds the scope, and the scope holds the component. Unmounting the component doesn't help — window outlives it."

"In a single-page application that's severe, because components mount and unmount continuously. Every navigation leaks another copy. The page gets slower over an hour of use and nothing errors."

"Detached DOM nodes are the specific symptom to look for: nodes removed from the document but still referenced by a closure, so they can't be collected. DevTools' memory profiler reports them explicitly, which makes this diagnosable."

"Other common sources: uncleared intervals — setInterval holds its callback forever until clearInterval; unsubscribed observables in Angular, where the subject holds the subscriber; and caches or arrays that only grow, where each entry captures a scope."

"The fix is always symmetry: every subscription needs a matching teardown. React's effect cleanup function, Angular's ngOnDestroy or takeUntilDestroyed. Frameworks provide these precisely because this is the default failure mode."

"Coming from .NET, the mental model that helps is that this is the IDisposable problem — an unmanaged resource acquired without a matching release. The difference is that C# gives you using and analyser warnings, whereas here nothing warns you at all."

"For diagnosis I'd take heap snapshots in DevTools before and after repeating an action — navigate to a page and back ten times — and compare. If retained size grows monotonically and detached nodes accumulate, the retainer path in the snapshot shows exactly which closure is holding on. That's a reliable process rather than guesswork, which matters because these are invisible in normal testing."

What they're really checking
  • Do you understand the retention chain — listener → closure → scope?
  • Do you know detached DOM nodes as the symptom?
  • Do you know the framework cleanup hooks?
  • Do you have a diagnostic process?
Likely follow-ups
  • How does WeakMap help?
  • Show the cleanup in a React effect.
  • Why doesn't the GC collect it?
