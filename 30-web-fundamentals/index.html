The one that catches .NET developers hardest

There is no second thread to offload work to.

In .NET, a CPU-bound operation on a background thread leaves the UI responsive. In a browser, a synchronous loop over 100,000 items blocks everything — rendering, input, timers, network callbacks — until it finishes. The tab appears frozen.

Work either has to be broken into chunks that yield to the event loop, or moved to a Web Worker, which is a genuinely separate thread with no DOM access and message-passing only.

Reaching for async does not fix this. async only helps with waiting; it doesn't create parallelism. That distinction is the single most valuable thing on this page.

A note on TypeScript ⭐ Senior-level

Why it matters for you specifically

TypeScript is JavaScript with static types checked at build time. It compiles to JavaScript and disappears at runtime — there are no type checks in the shipped code.

For someone coming from C#, it's the difference between front-end work feeling foreign and feeling familiar. Both Angular and React are overwhelmingly written in it.

The distinction interviewers listen for

TypeScript types are erased at compile time. They are not runtime validation.

So declaring an API response as User does not guarantee the server sent a User. If the API returns something different, TypeScript is perfectly happy and your code fails at the point of use with a confusing error.

Anything crossing a trust boundary — an API response, form input, localStorage — needs runtime validation, with something like Zod. That's the same reasoning as validating incoming models server-side rather than trusting a declared type.

"Types are compile-time only, so I'd validate at the boundary" is a strong answer, because a lot of developers treat a TypeScript interface as a guarantee.

Being honest about your level ⭐ Senior-level

Senior signal — don't oversell front-end depth

If you're a backend-leaning developer, saying so plainly is better than bluffing. What interviewers want to know is whether you can work effectively across the stack, not whether you can recite CSS grid syntax.

A strong version: "I'm strongest on the .NET side. I'm comfortable building and maintaining Angular features, I understand the event loop and change detection well enough to debug performance problems, and I'd defer to a specialist on complex layout or design-system work."

That's credible and it tells them exactly where you fit. Claiming senior front-end skill and then failing a closure question is much worse than a calibrated answer — and the calibration itself reads as seniority.

You have a CPU-heavy calculation that freezes the page. How do you fix it? 🔥 Must know
How I'd answer

"First I'd be clear that async won't fix this, because that's the instinct coming from .NET and it's wrong here. JavaScript runs on one thread. async and await only help when you're waiting on something — a network call, a timer. They don't create parallelism, so wrapping a CPU-bound loop in an async function blocks the thread exactly as before."

"So there are two real options."

"A Web Worker, if the work is genuinely heavy. That's a separate OS thread with its own JavaScript context. You post the input to it, it computes, it posts the result back, and the main thread stays responsive throughout. The constraints are that it has no DOM access and communication is by message-passing with structured cloning — so you can't share objects, and transferring very large payloads has its own cost. For something like parsing a large file, image processing, or a heavy calculation, this is the correct answer."

"Chunking with yields, if the work is moderate or a worker is overkill. Process a few hundred items, then yield to the event loop so rendering and input can happen, then continue. setTimeout with zero delay works; requestIdleCallback is better because it runs only when the browser is idle; and scheduler.yield() is the modern purpose-built option where available."

"The trade-off: chunking keeps the page responsive but makes the total work slower, and the code more complex. A worker keeps full speed and adds the message-passing boundary."

"Before either, though, I'd ask whether this belongs in the browser at all. If it's a heavy computation over a large dataset, that's often work for the server — where I have real threads, more memory, and can cache the result. Moving it to an API endpoint can be simpler than either browser-side option, and it means every user isn't recomputing the same thing."

"And I'd check the obvious first: is it genuinely CPU-bound, or is it accidentally quadratic? A nested loop over an array where a Map lookup would do is a very common cause, and then the fix is algorithmic rather than architectural. I'd profile it in DevTools before deciding."

What they're really checking
  • Do you know async doesn't create parallelism?
  • Do you know Web Workers exist and their constraints?
  • Do you consider moving the work server-side?
  • Do you profile before optimising?
Weak answers
  • Red flag: "make it async" — the classic .NET transplant.
  • Red flag: no awareness that the UI thread is the only thread.
Likely follow-ups
  • How do you get data into and out of a Worker?
  • What's the difference between a microtask and a macrotask?
  • How would you measure the blocking time?
