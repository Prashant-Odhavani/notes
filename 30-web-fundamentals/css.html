CSS

Nobody expects you to recall every property. They expect you to know which layout system to reach for and why your z-index isn't working.

🟢 Beginner 🟡 Intermediate 💡 Good to know
Quick revision
  • box-sizing: border-box — set it globally and stop fighting the box model.
  • Flexbox for one dimension, Grid for two. That's the whole decision.
  • Specificity: inline > id > class > element. !important beats all of it and is a smell.
  • z-index only works on positioned elements, and only within its stacking context.
  • Mobile-first with min-width queries.
  • Animate transform and opacity — everything else costs layout or paint.
  • Custom properties are runtime values, unlike Sass variables.

The box model 🔥 Must know

Why this matters

With the default content-box, two elements at width: 50% with any padding no longer fit side by side — the padding pushes the total over 100%.

border-box makes width mean what you'd expect, so layouts compose predictably. It's the first thing in nearly every CSS reset for exactly this reason.

Margin collapse — the other box-model surprise

Adjacent vertical margins collapse to the larger of the two, not the sum. A 20px bottom margin next to a 30px top margin gives 30px of space, not 50px.

Worse, a parent with no padding or border collapses with its first and last child's margins, so a child's top margin can appear to push the parent down.

Horizontal margins never collapse. Flex and grid items don't collapse either — which is one reason gap in a flex or grid container is more predictable than margins for spacing.

Flexbox or Grid 🔥 Must know

The decision in one line

Flexbox lays out along one axis. Grid lays out along two.

A toolbar, a nav row, centring something, a stack of cards that wrap — flex.

A page layout with rows and columns that need to align both ways — grid.

.toolbar {
  display: flex;
  align-items: center;        /* cross axis  - vertical here */
  justify-content: space-between;  /* main axis - horizontal here */
  gap: 12px;                  /* replaces margin hacks entirely */
  flex-wrap: wrap;            /* allow wrapping on narrow screens */
}

.toolbar .spacer { flex: 1; }   /* grow to fill remaining space */
.page {
  display: grid;
  grid-template-columns: 240px 1fr;      /* sidebar + fluid content */
  grid-template-rows: auto 1fr auto;
  grid-template-areas:
    "header  header"
    "sidebar main"
    "footer  footer";
  min-height: 100vh;
  gap: 16px;
}
.page > header  { grid-area: header; }
.page > nav     { grid-area: sidebar; }
.page > main    { grid-area: main; }
.cards {
  display: grid;
  grid-template-columns: repeat(auto-fill, minmax(280px, 1fr));
  gap: 16px;
}
/* Fits as many 280px-minimum columns as will fit, then wraps.
   Adapts at every width without a single breakpoint. */
The auto-fill / minmax pattern is worth memorising

That single declaration replaces a stack of media queries for card grids, and it responds to the container rather than the viewport width when combined with container queries.

auto-fill keeps empty tracks; auto-fit collapses them, so a single card stretches to full width with auto-fit and stays 280px with auto-fill. That's the difference people trip over.

Mentioning this is a good practical signal, because it shows you write modern CSS rather than media-query-per-breakpoint CSS.

Centring, which used to be the joke
/* Both axes, two lines */
.parent { display: grid; place-items: center; }

/* Or with flex */
.parent { display: flex; align-items: center; justify-content: center; }

Worth knowing because interviewers occasionally ask it as a warm-up, and because the old answers — absolute positioning with negative margins, table-cell hacks — still appear in legacy stylesheets you'll have to maintain.

The resolution order
  1. !important wins over everything normal.
  2. Otherwise, higher specificity wins.
  3. On a tie, whichever comes later in the stylesheet wins.

Note that 0,1,0,0 beats 0,0,9,0 — one ID outranks any number of classes. Specificity doesn't carry.

Why !important is a genuine problem, not a style preference

It doesn't just win — it removes your ability to override later. The only way to beat an !important is another !important with higher specificity, so one use tends to breed more.

The typical trajectory: someone adds it to fix a specificity conflict, the next person can't override it so adds their own, and within a year the stylesheet has hundreds and normal cascade rules no longer predict anything.

The legitimate uses are narrow: overriding a third-party stylesheet you don't control, and utility classes that are meant to be unconditional. Everything else is a signal that selectors have grown too specific — and the fix is lowering specificity elsewhere, not raising it here.

Modern tools for managing specificity

:where() has zero specificity, so :where(.a, .b) p matches the same elements as .a p, .b p but is trivially overridable. Ideal for base and reset styles.

:is() matches the same way but takes the specificity of its most specific argument.

Cascade layers (@layer) let you declare precedence explicitly — reset, then base, then components, then utilities — so a low-specificity utility can still beat a high-specificity component selector. That's a much better tool than !important for the problem it usually solves.

Why z-index isn't working 🔥 Must know

The two reasons, and it's almost always one of them
  1. z-index only applies to positioned elements — anything except position: static, plus flex and grid items.
  2. It's only compared within the same stacking context. A child can never escape its parent's context, no matter how large its z-index.
.modal-overlay { position: fixed; z-index: 9999; }

.header {
  position: relative;
  z-index: 10;
  transform: translateZ(0);   /* creates a stacking context! */
}
.header .dropdown { position: absolute; z-index: 99999; }

/* The dropdown can NEVER appear above the modal.
   It's trapped inside .header's stacking context, which sits at z-index 10.
   99999 only competes with siblings INSIDE .header. */
These create a stacking context
position: relative/absolute with a z-index other than auto
position: fixed or sticky — always
transform, filter, perspective — any non-none value
opacity less than 1
will-change, contain: paint, isolation: isolate
Flex or grid items with a z-index
Senior signal — the transform/opacity surprise

The non-obvious entries are transform and opacity. Adding a hover animation or a fade to a container silently creates a stacking context, and suddenly a dropdown that worked stops escaping it.

That's a genuinely baffling bug — a change that looks purely visual breaks layering elsewhere — and knowing the cause immediately is a strong practical signal.

The structural fix for overlays is to not nest them: render modals, tooltips and dropdowns at the document root via a portal, which every framework provides. Then there's no ancestor context to escape. Trying to win with bigger numbers is the wrong approach — it can't work.

And keep z-index values to a small documented scale — 10, 20, 30 — rather than 9999. Escalating numbers is a symptom of not understanding contexts.

Responsive design 🟡 Intermediate

/* Base: the narrowest case, no media query */
.container { padding: 16px; }

/* Then progressively enhance upward */
@media (min-width: 768px)  { .container { padding: 24px; } }
@media (min-width: 1200px) { .container { padding: 32px; max-width: 1200px; } }
Why mobile-first rather than desktop-first

With min-width queries, the base styles are the simplest case and each breakpoint adds. With max-width you're overriding downward, which means more declarations and more specificity conflicts.

It also fails better: an unsupported or unmatched query leaves you with the mobile layout, which is usable on any screen. Desktop-first leaves a mobile user with a desktop layout, which isn't.

Practical point: choose breakpoints from where your content breaks, not from device names. Chasing specific phone widths is a losing game.

Modern responsive tools worth knowing

clamp() for fluid values without breakpoints: font-size: clamp(1rem, 2.5vw, 1.5rem) — a minimum, a preferred scaling value, and a maximum.

Container queries (@container) respond to the parent's width rather than the viewport's. That's the genuinely significant addition, because a card component can adapt based on the space it's actually given — so the same component works in a sidebar and in a full-width area without knowing where it is. Media queries never solved that.

dvh instead of vh on mobile, because 100vh includes the area behind the browser's collapsing address bar and causes the classic "content cut off at the bottom" bug on iOS.

Custom properties 🟡 Intermediate

:root {
  --color-primary: #2563eb;
  --spacing: 8px;
}

.card { padding: calc(var(--spacing) * 2); border-color: var(--color-primary); }

/* Overridable per scope - impossible with Sass variables */
.card--danger { --color-primary: #dc2626; }

/* And changeable at runtime */
@media (prefers-color-scheme: dark) {
  :root { --color-primary: #60a5fa; }
}

The practical consequence

Custom properties inherit and cascade, which makes theming genuinely easy — redefine a handful of variables on :root or on a container, and everything inside updates, including at runtime with no rebuild.

That's why dark mode is now a few variable overrides rather than a parallel stylesheet.

They're not a replacement for Sass variables in every case — you still can't use a custom property inside a media query condition — but for anything that might vary per component or per theme, they're the right tool.

Layout thrashing — the JavaScript side of this
// Forces a synchronous layout on EVERY iteration
items.forEach(el => {
  el.style.height = el.offsetHeight + 10 + 'px';   // read, then write, then read...
});
const heights = items.map(el => el.offsetHeight);        // all reads
items.forEach((el, i) => el.style.height = heights[i] + 10 + 'px');  // all writes

Reading a layout property such as offsetHeight, getBoundingClientRect or scrollTop forces the browser to flush pending style changes and recalculate layout synchronously.

Interleaving reads and writes means that happens on every iteration. Batching gives you one layout pass.

This is one of the most common causes of janky scroll and resize handlers, and it's invisible in the CSS — you have to look at the JavaScript.

will-change is not a general speed-up

It hints that a property will animate, so the browser can promote the element to its own layer in advance.

Applied broadly it hurts — each layer consumes memory, and too many layers slow compositing down. It also creates a stacking context, which can break z-index as above.

Use it on the specific element about to animate, ideally added just before and removed after. Adding will-change: transform to everything is a recognisable sign of cargo-culted optimisation.

Key takeaways
  • box-sizing: border-box globally, always.
  • Margins collapse vertically; gap in flex/grid is more predictable.
  • Flex for one axis, Grid for two. auto-fill/minmax replaces card breakpoints.
  • One ID beats any number of classes. !important removes your ability to override.
  • :where() and @layer are the modern answers to specificity wars.
  • z-index needs positioning and only competes within its stacking context.
  • transform and opacity create stacking contexts — the surprising cause of layering bugs.
  • Portal overlays to the root rather than fighting with numbers.
  • Mobile-first min-width; breakpoints from content, not devices.
  • Custom properties are runtime and inherit; Sass variables are compile-time.
  • Animate transform/opacity; batch DOM reads before writes.

Common mistakes

  • Not setting border-box, then fighting percentage widths.
  • !important to win a specificity fight.
  • Escalating z-index values instead of understanding stacking contexts.
  • Grid for a single-axis layout, or flex for a genuine two-axis one.
  • Desktop-first max-width queries.
  • Breakpoints named after devices.
  • Animating left, width or margin.
  • Interleaved DOM reads and writes.
  • will-change applied broadly.
  • 100vh on mobile, causing cut-off content.
  • Deeply nested selectors that are impossible to override.

Interview questions

Intermediate

My z-index: 9999 isn't working. Why? 🔥 Must know
How I'd answer

"Almost certainly one of two things, and the second is the interesting one."

"The element isn't positioned. z-index has no effect on position: static, which is the default. It needs relative, absolute, fixed or sticky — or to be a flex or grid item. So the property is simply being ignored."

"Or it's trapped in a stacking context. This is the usual cause when the value looks absurdly high. z-index is only compared against siblings within the same stacking context. If an ancestor creates a context, the child can never escape it — a child with z-index: 99999 inside a parent at z-index: 10 still sits at the parent's level relative to everything outside. The big number only competes inside that box."

"The part that catches people is what creates a stacking context. Obviously position: fixed and sticky do. But so do transform, filter, opacity below 1, will-change, and contain."

"That produces genuinely confusing bugs: someone adds a hover animation or a fade transition to a header — a purely visual change — and a dropdown inside it stops appearing above the page content. Nothing about the dropdown changed. The transform created a context around it."

"To diagnose, I'd walk up the DOM in DevTools looking at computed styles for any of those properties on ancestors. That finds it quickly once you know what you're looking for."

"The fix depends on which it is. If the element just isn't positioned, add position: relative. If it's a stacking context problem, then increasing the number cannot work — the structural answer is to render the overlay outside the offending ancestor. Every framework has a portal mechanism for exactly this: React's createPortal, Angular's CDK overlay. Render modals, tooltips and dropdowns at the document root and there's no ancestor context to escape."

"I'd also push back on 9999 generally. Escalating values are a symptom of not understanding contexts, and they make the layering unpredictable for the next person. I'd use a small documented scale — 10 for dropdowns, 20 for sticky headers, 30 for modals — defined as custom properties so it's visible in one place."

What they're really checking
  • Do you know z-index needs positioning?
  • Do you understand stacking contexts and containment?
  • Do you know transform and opacity create them?
  • Do you reach for portals rather than bigger numbers?
Weak answers
  • Red flag: "try a higher number."
  • Red flag: no mention of stacking contexts.

Flexbox or Grid — how do you choose? 🔥 Must know
How I'd answer

"The short version: Flexbox is one-dimensional, Grid is two-dimensional. Flex lays items out along a single axis and lets them wrap; Grid defines rows and columns that align in both directions."

"So a toolbar, a nav bar, a row of buttons, centring something, or a form row — Flexbox. It's also better when the item sizes should be driven by their content, because flex-grow and flex-basis distribute available space based on what's there."

"A page shell with a header, sidebar, main area and footer — Grid, because those need to align across both axes. grid-template-areas makes that layout readable in the CSS itself, which is a real maintainability benefit."

"The useful way I'd frame the distinction: Grid is layout-first, Flex is content-first. With Grid you define the structure and place items into it. With Flex the items' own sizes determine the outcome."

"And they compose — Grid for the page skeleton, Flex inside individual cells for the local arrangement. That's the normal shape of a real layout, not an either/or choice."

"One specific pattern I'd reach for: grid-template-columns: repeat(auto-fill, minmax(280px, 1fr)) for a card grid. That fits as many columns of at least 280px as will fit and wraps automatically — replacing three or four media queries with one line. auto-fit collapses empty tracks so a single card stretches full width; auto-fill keeps them so it stays 280px. That distinction catches people out."

"Practical note on spacing: gap works in both and is much better than margins, because you don't need :last-child exceptions and flex/grid items don't have margin collapse to reason about."

"On support — both are universally available now. Grid's subgrid is the only piece that's relatively recent, so if I needed nested alignment across a parent grid I'd check that specifically. Otherwise there's no compatibility reason to prefer one."

What they're really checking
  • Do you know the one-axis versus two-axis distinction?
  • Do you know they compose rather than compete?
  • Do you know a modern responsive pattern?
Likely follow-ups
  • What does flex: 1 expand to?
  • What's the difference between auto-fill and auto-fit?
