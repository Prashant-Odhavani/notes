jQuery & Legacy Front Ends

A large amount of working .NET software has a jQuery front end. Being able to work in it — and modernise it without a rewrite — is a genuinely useful skill.

🟡 Intermediate ⭐ Senior-level 💡 Good to know
Quick revision
  • jQuery solved problems that no longer exist — mainly browser inconsistency and a hostile DOM API.
  • Nearly every jQuery method now has a native equivalent, often with the same ergonomics.
  • It faded because the DOM API improved and because it doesn't scale to application state.
  • Don't rewrite a working jQuery app without a business reason.
  • Modernise incrementally — island by island, not big-bang.
  • ASP.NET MVC's unobtrusive validation depends on jQuery, which is why it lingers.
  • jQuery is still maintained. "Legacy" doesn't mean unsupported.

What jQuery solved 🟡 Intermediate

In simple terms

In 2006, the same JavaScript behaved differently in every browser, and the native DOM API was verbose and inconsistent.

jQuery gave you one API that worked everywhere, plus CSS selectors for finding elements — which the DOM didn't have.

Problem in 2006Status now
Every browser had different event handling and quirksSolved — standards convergence and evergreen browsers
No way to query by CSS selectorSolved — querySelectorAll
XMLHttpRequest was painful and inconsistentSolved — fetch
Class manipulation meant string surgery on classNameSolved — classList
Animation required manual timersSolved — CSS transitions and animations
No chaining or collection operationsPartly — the native API is still more verbose
jQuery didn't fail — it succeeded and was absorbed

Many of jQuery's ideas went into the platform. querySelectorAll exists because jQuery demonstrated that CSS selectors were the right query API.

So the honest framing is that jQuery won the argument and then became unnecessary. That's a better answer than "it's outdated", and it's a more accurate reading of the history.

It's also still actively maintained — version 4 is in development. "Legacy" here means "not what you'd choose for something new", not "abandoned".

// jQuery
$('#save').on('click', function () {
  $.ajax({ url: '/api/orders', method: 'POST', data: { id: 1 } })
    .done(function (res) { $('#status').text('Saved').addClass('ok'); })
    .fail(function ()    { $('#status').text('Failed').addClass('error'); });
});

// Native
document.querySelector('#save').addEventListener('click', async () => {
  const status = document.querySelector('#status');
  try {
    const res = await fetch('/api/orders', {
      method: 'POST',
      headers: { 'Content-Type': 'application/json' },
      body: JSON.stringify({ id: 1 })
    });
    if (!res.ok) throw new Error(res.statusText);   // fetch does NOT throw on 4xx/5xx
    status.textContent = 'Saved';
    status.classList.add('ok');
  } catch {
    status.textContent = 'Failed';
    status.classList.add('error');
  }
});
The fetch difference that causes real bugs

fetch does not reject on HTTP error statuses. A 404 or a 500 resolves successfully — the promise only rejects on a network failure.

$.ajax called .fail() for a 500. Code translated mechanically from jQuery therefore treats server errors as success, and you get "Saved" displayed after a failed request.

You must check response.ok explicitly. This is the most common mistake in jQuery-to-fetch migrations, and it fails silently in exactly the direction you don't want.

Also: fetch doesn't send cookies cross-origin unless you set credentials: 'include', where $.ajax had different defaults. That's the second migration surprise.

The two things native code is still more verbose about

Collection operations. $('.item').addClass('x') operates on every match. Natively you need document.querySelectorAll('.item').forEach(el => el.classList.add('x')). Note that querySelectorAll returns a NodeList, which has forEach but not map or filter — use Array.from() for those.

Event delegation. jQuery's $(parent).on('click', '.child', fn) handles dynamically-added children elegantly. Natively you attach to the parent and check event.target.closest('.child') yourself. Slightly more code, same behaviour.

A twelve-line helper covers both, which is why "we replaced jQuery with a small utility file" is a common and reasonable migration outcome.

Why it faded ⭐ Senior-level

The real reason — not bundle size

jQuery manipulates the DOM. Modern frameworks derive the DOM from state.

That's an architectural difference, not a syntax preference. In jQuery, the DOM is the state — to know whether a checkbox is ticked you inspect the checkbox.

Once an interface has enough interacting pieces, keeping the DOM consistent by hand becomes the dominant source of bugs. Frameworks make state the single source of truth and render from it.

// Every interaction must remember to update every dependent piece of UI
$('#qty').on('change', function () {
  const qty = +$(this).val();
  $('#lineTotal').text(qty * price);           // update the line
  $('#cartTotal').text(recalcCart());          // update the cart
  $('#checkout').prop('disabled', qty === 0);  // update the button
  $('#stockWarning').toggle(qty > stock);      // update the warning
  // Miss one of these and the UI is inconsistent, silently.
  // Now add a second place that can change quantity.
});
Why the framework version is different

In React or Angular you change quantity and every derived piece of UI updates because it was declared as a function of state.

There's no list of things to remember to update, so there's no possibility of forgetting one. The bug class disappears rather than being managed.

Contributing factorWeight
Imperative DOM updates don't scale to complex stateThe main one
Native APIs caught up, removing the compatibility needHigh
Component models enable reuse; jQuery plugins didn't composeHigh
Frameworks brought routing, forms, testing, toolingMedium
Bundle sizeLow — ~30KB gzipped is not the problem
Senior signal — bundle size is the weak argument

"jQuery is 30KB" is the reason people cite and the least important one. A React plus router plus state library bundle is considerably larger.

The real argument is architectural: imperative DOM manipulation means the number of update paths grows with the square of the number of interacting elements, and every one is a place to forget something.

Leading with bundle size in an interview suggests you've absorbed the conclusion without the reasoning. Leading with "the DOM as state doesn't scale" shows you understand why the industry moved.

"Rewrite it in React" is usually the wrong answer

A jQuery front end that works represents years of accumulated business rules, edge cases and bug fixes. A rewrite discards all of it and reintroduces the bugs — while delivering no new functionality for months.

This is the same reasoning as .NET Framework migration: the honest question is whether there's a business reason, not whether the technology is current.

Being willing to say "I wouldn't migrate this" is a strong signal, provided you can also describe how you would do it if the reason existed.

How to modernise incrementally

  1. Stop adding new jQuery. New features use the modern approach. The old code isn't the problem; growth of it is.
  2. Remove jQuery-dependent plugins where a native or small alternative exists — date pickers, modals, tooltips. Usually the largest chunk of the dependency.
  3. Replace jQuery calls with native equivalents in files you're touching anyway. Not as a dedicated project.
  4. Introduce components as islands. Mount a React or Angular component into one div on an existing page. The rest of the page stays as it is.
  5. Convert page by page, highest-value first.
  6. Drop jQuery when nothing references it.
// The existing page keeps working. One div becomes a modern component.
// _Layout.cshtml still loads jQuery for everything else.

import { createRoot } from 'react-dom/client';
import { OrderGrid } from './OrderGrid';

const host = document.getElementById('order-grid-root');
if (host) {
  createRoot(host).render(
    <OrderGrid customerId={host.dataset.customerId} />
  );
}
// Data passed in via data-* attributes rendered by Razor -
// so the server still owns auth and initial state.
The islands approach is the pragmatic answer

This is the strangler pattern applied to a front end. Each island is independently shippable, independently revertible, and the application keeps working throughout.

The one thing to plan deliberately: how the island gets its data and communicates back. Passing initial state via data- attributes rendered by Razor works well and keeps the server authoritative. Custom events, or a small shared store, handle communication out.

What to avoid is having jQuery and the framework both manipulating the same DOM subtree — they will fight, because the framework assumes it owns its tree and will overwrite external changes on the next render. Draw a clear boundary per element.

The .NET-specific legacy you'll meet 🟡 Intermediate

ThingWhat to know
Unobtrusive validation ASP.NET MVC emits data-val-* attributes read by jquery.validate.unobtrusive.js. Removing jQuery breaks client-side validation on every form — often the single reason it's still there
Razor partial + AJAX The classic pattern: fetch an HTML fragment and inject it. Works fine; note innerHTML is an XSS surface if any of it is user data
Bundling and minification System.Web.Optimization in older projects; a real bundler in modern ones
Web Forms UpdatePanel Partial postbacks with full ViewState. Very hard to modernise in place — usually a page-level rewrite
Bootstrap 3/4 Its JavaScript components depend on jQuery. Bootstrap 5 removed that dependency
The validation dependency is the practical blocker

If you remove jQuery from an MVC application, every [Required] and [EmailAddress] attribute stops producing client-side feedback. The server still validates — so it's not a security problem — but the user experience regresses badly, and it happens on every form at once.

Options: keep jQuery just for validation until forms are migrated; replace it with a native validation approach reading the same data-val-* attributes; or migrate forms to a framework with its own validation.

Knowing this specific coupling is a good practical signal for a .NET role, because it's the reason jQuery persists in so many otherwise-modern codebases.

Key takeaways
  • jQuery solved browser inconsistency and a poor DOM API — both largely gone.
  • Nearly every method has a native equivalent; collections and delegation are the verbose ones.
  • fetch doesn't reject on 4xx/5xx — check response.ok.
  • It faded because imperative DOM updates don't scale, not because of bundle size.
  • Don't rewrite a working jQuery app without a business reason.
  • Modernise as islands: stop adding, replace plugins, convert page by page.
  • Never let jQuery and a framework manage the same DOM subtree.
  • MVC unobtrusive validation depends on jQuery — plan for that specifically.
  • jQuery is still maintained; "legacy" means "not for new work".

Common mistakes

  • Translating $.ajax to fetch without checking response.ok.
  • Proposing a full rewrite with no business justification.
  • jQuery and a framework fighting over the same elements.
  • Removing jQuery and silently breaking MVC client validation.
  • innerHTML with user data — an XSS hole.
  • Citing bundle size as the main reason to move on.
  • A big-bang migration instead of islands.
  • Treating NodeList as an array — no map or filter.

Interview questions

Advanced / scenario

You inherit a large jQuery + ASP.NET MVC application. How would you modernise the front end? ⭐ Senior-level
How I'd answer

"My first question is whether we should, and I'd want a business reason rather than 'jQuery is old'. A working jQuery front end encodes years of business rules and edge-case fixes. A rewrite discards that, reintroduces the bugs, and delivers nothing new for months."

"Reasons I'd accept: the UI is genuinely complex and bugs cluster in DOM synchronisation; it's under active development and the team is slowed down; we need component reuse across many screens; or hiring is getting hard. Reasons I wouldn't: it's stable and rarely changed, or it's being retired within a year or two."

"Assuming there's a reason, I'd do it incrementally as islands — never big-bang."

"First, stop the bleeding. New features are built the modern way. The existing jQuery isn't the problem; more of it is."

"Then remove jQuery-dependent plugins — date pickers, modals, tooltips, carousels. These are usually the bulk of the coupling and often have native or small standalone replacements. Bootstrap 3 or 4 will be in here too, and its JavaScript needs jQuery; Bootstrap 5 dropped that."

"Then islands. Mount a component into a single div on an existing Razor page, passing initial state through data- attributes so the server still owns auth and initial data. The rest of the page carries on unchanged. Each island is independently shippable and revertible, so we're delivering value throughout rather than going dark."

"Then page by page, highest-value first, and drop jQuery when nothing references it."

"Three things I'd flag specifically for a .NET codebase."

"Unobtrusive validation is the real blocker. MVC emits data-val-* attributes consumed by jQuery Validate. Remove jQuery and client-side validation silently stops on every form at once. The server still validates so it isn't a security issue, but the UX regresses badly. So I'd plan for that explicitly — keep jQuery for validation until forms migrate, or replace it with something reading the same attributes."

"Never let jQuery and the framework manage the same DOM subtree. The framework assumes it owns its tree and will overwrite outside changes on the next render, producing bugs that look random. One clear owner per element."

"Check for Web Forms. If any of this is UpdatePanel with ViewState, that's a different and much harder problem — partial postbacks don't coexist with client-side components, so those pages need a genuine rewrite rather than incremental work."

"On framework choice, I'd weight team familiarity heavily. If the team knows Angular, Angular — the migration is hard enough without also learning a new framework. For islands specifically, React mounts into an existing page slightly more easily, and Angular Elements works too."

"And I'd ask about SEO and server rendering before committing. If these are public pages currently server-rendered by Razor, moving to client-rendered islands could hurt discoverability. Islands are actually good here — the page stays server-rendered and only the interactive parts are client-side — but that needs to be a deliberate choice rather than a side effect."

What they're really checking
  • Do you question whether migration is justified?
  • Do you propose incremental islands rather than a rewrite?
  • Do you know the unobtrusive-validation coupling?
  • Do you know jQuery and a framework can't share a subtree?
  • Do you weight team familiarity and SEO?
Weak answers
  • Red flag: "rewrite it in React" with no assessment.
  • Red flag: citing bundle size as the driver.
  • Red flag: no awareness of what breaks when jQuery is removed.
Likely follow-ups
  • How does an island get its data and report back?
  • How would you handle client validation during the transition?
  • How do you decide which page to convert first?
