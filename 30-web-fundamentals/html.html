HTML & Accessibility

Semantics aren't decoration — they're the API that assistive technology, search engines and browsers all read.

🟢 Beginner 🟡 Intermediate 🔥 Must know
Quick revision
  • Use the right element. A button gives you keyboard support, focus and semantics for free; a div gives you none of it.
  • Every input needs a label, properly associated.
  • The first rule of ARIA is not to use ARIA — native elements first.
  • Accessibility is largely keyboard operability. Tab through it.
  • CSS blocks rendering; scripts block parsing unless deferred.
  • Alt text describes purpose, and decorative images take alt="".
  • Client validation is UX, server validation is security.

Semantic elements 🔥 Must know

In simple terms

A <div> means nothing. A <button> tells the browser, the screen reader and the search engine what the thing is.

That meaning is what makes it keyboard-operable, announceable and navigable — without you writing any code.

<div class="btn" onclick="save()">Save</div>

<!-- Not focusable with Tab
     Doesn't respond to Enter or Space
     Announced as "Save" with no role - the user doesn't know it's actionable
     Not in the accessibility tree as a control
     No :focus-visible ring, no disabled state -->
<button type="button" onclick="save()">Save</button>

<!-- Focusable, keyboard-activated, announced as "Save, button",
     supports disabled, gets focus styling. All free. -->
Recreating a button correctly takes six attributes
<div role="button"
     tabindex="0"
     aria-pressed="false"
     aria-disabled="false"
     onclick="save()"
     onkeydown="if (event.key === 'Enter' || event.key === ' ') { event.preventDefault(); save(); }">
  Save
</div>

And that still doesn't fully match native behaviour — form submission, the disabled attribute genuinely blocking clicks, or Windows High Contrast Mode.

This is the concrete answer to "why does semantic HTML matter?": the native element is a large amount of behaviour you'd otherwise have to write and maintain. That's a much better argument than "it's good practice".

Button or link? The distinction interviewers check

<a href> navigates. <button> acts.

That's not cosmetic. A link can be opened in a new tab, copied, bookmarked, crawled and middle-clicked; a screen reader announces it as a link and lists it in the links index. A button does none of that and is announced as a control.

So "Delete" is a button. "View order" is a link — even in a single-page application, where it should still be an <a> with a real href that the router intercepts. A router link implemented as a div breaks open-in-new-tab, which users notice immediately.

Placeholder is not a label

A placeholder disappears the moment the user types, so they can't check what the field was for. It fails contrast requirements in most designs, isn't reliably announced, and vanishes entirely when the browser autofills.

It's the single most common accessibility failure in forms, and it's usually done for visual reasons that a floating label solves properly.

Placeholders are for examples — placeholder="e.g. 07700 900000" — not for naming the field.

Client validation is a convenience, never a control

required, type="email" and pattern give fast feedback and stop obvious mistakes. They are trivially bypassed — DevTools, a curl request, a disabled JavaScript engine.

Every rule must be enforced server-side. Client validation exists so the user doesn't wait for a round trip to learn their email is malformed; server validation is what actually protects the system.

Same reasoning as database constraints versus application validation — the outer layer is UX, the inner layer is correctness.

Accessibility 🔥 Must know

The 80% version
  1. Use native elements. Most accessibility comes free.
  2. Label every input.
  3. Tab through the page. Can you reach and operate everything, in a sensible order, and see where you are?
  4. Alt text on meaningful images, alt="" on decorative ones.
  5. Don't rely on colour alone to convey information.
  6. Check contrast — 4.5:1 for body text.

That covers the large majority of real failures. Everything below is refinement.

The first rule of ARIA is not to use ARIA

That's the actual wording in the specification, and it's the answer interviewers are listening for.

Incorrect ARIA is worse than none. role="button" on a div makes a screen reader announce "button" while the element still isn't keyboard-operable — so you've promised a control that doesn't work. No ARIA at all would at least have been announced as plain text.

ARIA doesn't add behaviour. It only changes what assistive technology reports. Every role you assert is a contract you have to implement yourself.

So: native element first, ARIA only to fill a genuine gap — a custom combobox, a live region, an icon-button name.

Focus management is the SPA-specific problem

In a traditional page load, the browser resets focus and screen readers announce the new page. In a single-page application nothing happens — the URL changes, content swaps, and focus stays wherever it was. A screen reader user gets no indication anything changed.

So route changes need explicit handling: move focus to the new content's heading, and announce the change via a live region.

Same for modals: focus must move into the dialog, be trapped while it's open, and return to the trigger element on close. The native <dialog> element does the trapping and restoration for you, which is why it's now the right default rather than a hand-rolled overlay.

The rendering path 🟡 Intermediate

  1. Parse HTML → DOM. Incremental, as bytes arrive.
  2. Parse CSS → CSSOM. Render-blocking — nothing paints until it's done.
  3. Combine into the render tree — DOM nodes plus computed styles.
  4. Layout (reflow) — compute geometry for every box.
  5. Paint — fill in pixels.
  6. Composite — assemble layers, potentially on the GPU.
Script tagBehaviour
<script>Blocks parsing — downloads and executes immediately
<script defer>Downloads in parallel, runs after parsing, in order
<script async>Downloads in parallel, runs as soon as ready, order not guaranteed
<script type="module">Deferred by default
The practical rules

CSS in the <head>, because it's render-blocking and you want it as early as possible. Loading it late causes a flash of unstyled content.

Scripts with defer, so parsing isn't blocked but execution order is preserved. async only for genuinely independent scripts like analytics — with async, script two can run before script one, which breaks anything with dependencies.

A blocking script in the <head> is the classic cause of a slow first paint: the browser stops parsing, fetches, executes, and only then continues building the DOM.

Reflow versus repaint, and why it matters

Reflow recalculates geometry — triggered by changing width, height, position, or adding elements. Expensive, because it can cascade to the whole subtree.

Repaint redraws pixels without changing geometry — colour, background, visibility. Cheaper.

Compositing only — transform and opacity — can run on the GPU without touching layout or paint at all. That's why animating transform: translateX() is smooth and animating left stutters: one is a composite, the other is a reflow on every frame.

Also worth knowing: reading a layout property forces a synchronous reflow. Reading offsetHeight inside a loop that also writes styles causes layout thrashing — the browser must recompute on every iteration. Batch reads, then writes.

Senior signal — the SPA/SEO trade-off

A client-rendered single-page application serves an almost-empty HTML document and builds the content in JavaScript. Google can execute JavaScript, but it's queued, budgeted and unreliable — and most other crawlers, plus link-preview generators for Slack, WhatsApp and social platforms, don't execute it at all.

So for anything discoverability-dependent — marketing pages, product listings, articles — you need server-side rendering or static generation. That's Angular Universal, Next.js, or pre-rendering at build time.

The calibrated position: a CRUD application behind a login has no SEO requirement and a SPA is entirely appropriate. A public catalogue does, and choosing pure client rendering there is a business problem wearing a technical costume. Being able to make that distinction is the point.

Key takeaways
  • Native elements carry behaviour — recreating a button properly takes six attributes and still falls short.
  • <a> navigates, <button> acts. Router links should still be anchors.
  • Every input needs an associated label. A placeholder is not a label.
  • Client validation is UX; the server enforces the rules.
  • Incorrect ARIA is worse than none — it asserts behaviour you must then implement.
  • Tab through the page; keyboard operability is most of accessibility.
  • SPAs must manage focus on route change and trap it in modals.
  • CSS blocks rendering; use defer for scripts.
  • Animate transform/opacity to stay on the compositor.
  • Client-only rendering hurts SEO and link previews — server-render public content.

Common mistakes

  • div with a click handler instead of a button.
  • Placeholder used as the label.
  • Missing autocomplete, breaking password managers.
  • ARIA roles without the matching keyboard behaviour.
  • No focus management on SPA route change.
  • Colour as the only indicator of state or error.
  • Blocking scripts in the <head>.
  • Animating left/top instead of transform.
  • Reading layout properties inside a write loop — layout thrashing.
  • Relying on client validation for correctness.
  • Client-only rendering for public content.

Interview questions

Intermediate

Why does semantic HTML matter? 🔥 Must know
How I'd answer

"Because the element you choose is behaviour, not just meaning — and that's a more concrete argument than 'good practice'."

"Take a <button> versus a <div> with a click handler. The button is focusable with Tab, activates on Enter and Space, is announced as 'Save, button' so the user knows it's actionable, supports the disabled attribute, appears in the accessibility tree as a control, and gets a focus ring."

"To match that with a div you need role="button", tabindex="0", a keydown handler for both Enter and Space with preventDefault, aria-disabled, and focus styling. Six additions — and it still won't submit a form or genuinely block clicks when disabled."

"So the honest framing is: the native element is a substantial amount of behaviour you'd otherwise write and maintain."

"Beyond that: assistive technology navigates by landmarks and headings, so nav, main and proper heading levels let a screen reader user jump straight to content instead of hearing everything. Search engines use structure to understand the page. And browser features depend on it — reader mode, autofill, translation all read semantics."

"One distinction I'd raise because it's frequently wrong: links navigate, buttons act. An <a href> can be opened in a new tab, copied, bookmarked and crawled, and is announced as a link. So even in a single-page application, a router link should be a real anchor with an href that the router intercepts — implementing it as a div breaks middle-click and open-in-new-tab, which users notice immediately."

"And it's increasingly a legal requirement — public sector and large commercial sites in the UK, EU and US face accessibility obligations. So this isn't only a craft argument; shipping an inaccessible interface is organisational risk."

What they're really checking
  • Do you know it's about behaviour, not just labels?
  • Can you enumerate what the native element gives you?
  • Do you know the link/button distinction?
Likely follow-ups
  • When would you use ARIA?
  • How do you make a custom dropdown accessible?
  • How would you test accessibility?

Advanced

How would you make a single-page application accessible? ⭐ Senior-level
How I'd answer

"SPAs break two things that traditional page loads handle automatically, and those are the SPA-specific problems worth focusing on rather than general accessibility advice."

"Route changes are silent. On a normal navigation the browser resets focus and the screen reader announces the new page. In a SPA the URL changes and content swaps, but focus stays exactly where it was — so a screen reader user gets no indication anything happened. They may not even realise they navigated."

"The fix is explicit: on route change, move focus to the new view's main heading — a container with tabindex="-1" that you call focus() on — and announce the change through a live region. Also update document.title, because some screen readers announce it and it matters for browser history regardless."

"Dynamic content updates are silent too. If a form submission shows an error, or a list filters, a sighted user sees it and a screen reader user doesn't. That needs a live region — aria-live="polite" for status messages, or role="alert" for errors, which announces without moving focus."

"The subtlety: the live region must exist in the DOM before the content changes. If you insert the element and its text together, many screen readers announce nothing — they're watching for changes within an existing region. That's a very common implementation mistake."

"Then focus management for modals. Focus must move into the dialog, be trapped while open, and return to the triggering element on close — otherwise a keyboard user closes the modal and finds themselves back at the top of the document. The native <dialog> element handles trapping and restoration, so I'd use that rather than hand-rolling it."

"Beyond the SPA-specific parts, the fundamentals still apply: native elements, labelled inputs, logical tab order, visible focus indicators, adequate contrast."

"On testing, because this is where teams go wrong: automated tools like axe catch maybe 30–40% of issues — missing labels, contrast failures, invalid ARIA. They cannot tell you whether the tab order is sensible, whether focus goes somewhere useful after an action, or whether the announcements make sense. So I'd run axe in CI as a floor, and do manual keyboard-only testing plus actual screen reader testing for the main flows."

"The single cheapest check: unplug the mouse and use the application. If you can't complete the primary journey with only a keyboard, neither can a substantial group of users. That finds more real problems in ten minutes than a scanner does."

What they're really checking
  • Do you know route changes need explicit focus and announcement?
  • Do you know the live-region-must-pre-exist detail?
  • Do you handle modal focus trapping and restoration?
  • Do you know automated tools only find a fraction?
Weak answers
  • Red flag: "run axe and fix what it reports."
  • Red flag: adding ARIA roles broadly to "improve accessibility".
  • Red flag: no awareness that SPAs differ from static pages here.
Likely follow-ups
  • How do you implement a focus trap?
  • aria-live="polite" vs assertive?
  • How would you add this to an existing large app?
