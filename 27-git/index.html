Git In Depth

Almost every confusing Git situation becomes obvious once you know that commits are immutable snapshots and branches are just labels pointing at one.

🟢 Beginner 🟡 Intermediate 🔴 Advanced 🔥 Must know
Quick revision
  • A commit is a full snapshot, not a diff. Diffs are computed on demand.
  • A branch is a movable pointer to one commit. That's the whole thing.
  • Commits are immutable. Rebase and amend create new ones.
  • Merge preserves history; rebase rewrites it.
  • Never rewrite shared history — unless everyone agrees.
  • revert for public branches, reset for local.
  • The reflog is your undo — nothing is really lost for about 90 days.
  • --force-with-lease, never plain --force.

The object model 🔥 Must know

Four object types, and that's all there is

Blob — the contents of a file. Tree — a directory listing, pointing at blobs and other trees. Commit — a pointer to one tree, plus parents, author and message. Tag — a named pointer, optionally annotated.

Every object is stored under the SHA-1 hash of its content. Identical content is stored once, however many commits or branches contain it.

  commit abc123
    tree      d4e5f6            <- the ENTIRE directory state at this point
    parent    789xyz            <- one parent; two if it is a merge commit
    author    ...
    message   "Add order validation"

  tree d4e5f6
    blob  aa11  Program.cs      <- unchanged files point at the SAME blob
    tree  bb22  Services/          as the previous commit. Nothing is copied.
    blob  cc33  README.md

  A branch is a FILE containing one hash:
    .git/refs/heads/main   ->  abc123

  HEAD is a file containing a ref:
    .git/HEAD              ->  ref: refs/heads/main
Senior signal — snapshots, not diffs, explains nearly everything

Most confusion about Git comes from imagining it stores changes. It doesn't — each commit records the complete state of the tree, and unchanged files simply point at the same blob as before. So there's no storage penalty.

Once you hold that, a lot of behaviour stops being mysterious:

Branching is instant because creating a branch writes a 41-byte file containing a hash. Nothing is copied.

A diff is computed, not stored — which is why Git can show you the difference between any two commits, however far apart, at the same cost.

Rebase can't move a commit, because a commit's hash is derived from its content including its parent. Change the parent and it's a different commit with a different hash. So rebase replays your changes as brand-new commits and abandons the originals — which is exactly why rewriting shared history is disruptive, and why the old commits are still recoverable from the reflog.

Nothing is deleted immediately. Unreferenced objects sit there until garbage collection, typically 90 days. That's the basis of every recovery below.

Being able to explain why rebase creates new commits — rather than just knowing it does — is the difference between having memorised commands and understanding the tool.

The index is a feature, not an obstacle

People treat staging as a formality — git add . and move on. It's actually the mechanism for making commits that are worth reading.

git add -p stages selected hunks within a file. So when you've fixed a bug and also renamed a variable and also added a log line, you can commit them separately — which makes each commit a single logical change that can be reviewed, reverted or cherry-picked on its own.

That matters later. A commit containing a bug fix mixed with unrelated refactoring can't be reverted cleanly, and git bisect pointing at it tells you almost nothing.

It's also a good final review: staging hunk by hunk is the last chance to notice the debug line or the commented-out block you left in.

Merge versus rebase 🔥 Must know

  Starting point:

             \
              D---E  feature

  MERGE (git checkout main; git merge feature)

             \     /
              D---E                D and E keep their original hashes

  REBASE (git checkout feature; git rebase main)

Senior signal — the rule is about where, not which is better

This gets asked as though one is correct. The useful answer distinguishes the two places they apply.

Rebase your own unpushed work, freely. Squash the "fix typo" and "actually fix it" commits, reorder, reword. Nobody else has those commits, so rewriting them costs nothing and the result is a branch that's pleasant to review.

Never rebase a branch other people have based work on. Their commits now reference parents that no longer exist on the remote, so their next pull produces duplicated commits and conflicts that make no sense. It's not that Git can't do it — it's that everyone else has to recover.

Rebase onto main rather than merging main into your feature branch, while the branch is yours. Repeatedly merging main in produces a feature branch littered with merge commits that make the diff hard to read, and it's the more common habit.

For integrating into main, the shape is a team decision, and all three are defensible: squash for a tidy one-commit-per-feature history, rebase-and-merge for linear history with individual commits preserved, merge commits for an exact record of what happened when.

What matters more than the choice is that it's consistent and enforced by the platform — set the allowed merge method in the repository settings rather than relying on each person picking the right button.

The squash trade-off nobody mentions until it bites

Squash merging gives a clean main branch, and it discards the individual commits. Which has two consequences worth knowing in advance.

git bisect gets coarser. When it identifies the bad commit, that commit is an entire feature — possibly hundreds of lines — rather than the specific change. You've traded review convenience for debugging precision.

Long-lived branches become painful. If a feature branch was squash-merged and someone continues working on the original branch, Git can't tell the squashed commit contains that work, so the next merge re-applies everything and conflicts heavily. The fix is to always branch fresh from main after a squash merge, never continue on a merged branch.

Squash suits short-lived branches with small, focused changes — which is what you want anyway. For long-running work with meaningful intermediate commits, rebase-and-merge preserves more useful information.

Senior signal — long-lived branches are the actual problem

The argument for trunk-based development isn't aesthetic. It's that merge difficulty grows with branch age and divergence, roughly non-linearly.

A two-week branch conflicts with everything that landed meanwhile. The person resolving those conflicts is making judgement calls about code they may not have written, under pressure to finish — which is exactly when logic gets silently broken. And a conflict resolved syntactically can still be semantically wrong, which no test necessarily catches.

There's a subtler cost: a long branch means integration problems are discovered late. Two people refactoring the same area in parallel find out at merge time rather than the same day.

So the goal is that branches live hours, not weeks, which requires two habits: breaking work into small independently-mergeable pieces, and using feature flags so incomplete work can merge safely while switched off.

That second point is what makes trunk-based work at all. Without flags, you either wait for the whole feature or ship something half-finished. With them, merging and releasing become separate decisions — which is the same decoupling that makes canary deployments possible.

GitFlow is not wrong, and it's a poor fit for a continuously-deployed service — all that release-branch machinery exists to manage versioned releases you support in parallel. If you deploy main several times a day, it's overhead. If you ship an on-premises product with three supported versions, it's the right shape.

Write the message for the person debugging this in a year

The diff already says what changed. The message's job is why — and why is the part that can't be reconstructed later.

So: a subject line in the imperative under about 72 characters, then a blank line, then the reasoning. What was wrong, why this approach, what was considered and rejected, anything surprising about the implementation.

That person in a year is usually you, looking at a line you don't understand and running git log -p on it. A message saying "fix bug" leaves you reverse-engineering the intent from the code.

Conventional Commits — the feat:, fix:, chore: prefixes — are worth adopting mainly because tooling can generate changelogs and derive semantic versions from them. The discipline of picking a type also nudges you toward one logical change per commit.

And reference the ticket, so the fuller discussion is one click away. Not instead of the explanation — issue trackers get migrated and links rot, so the commit should stand alone.

The size of a pull request determines whether it gets reviewed

This is the single most actionable thing about code review. A 50-line change gets read carefully. A 2,000-line change gets skimmed, and the reviewer comments on naming because that's all they can meaningfully assess.

So a large pull request often receives less scrutiny than a small one — the opposite of what its risk warrants.

Which makes "split this up" a legitimate and useful review comment, and one people are oddly reluctant to give. The techniques: separate refactoring from behaviour change into different pull requests; land the interface before the implementation; use feature flags so partial work can merge.

The related habit is mixing a rename or a reformat into a behavioural change. A 400-line diff where 380 lines are automated formatting means the 20 that matter are effectively unreviewed. Separate commits at minimum, separate pull requests ideally — and if your platform supports it, teach reviewers to hide whitespace-only changes.

Recovery 🔥 Must know

# THE UNDO BUTTON. Every position HEAD has held, for ~90 days.
git reflog
git reset --hard HEAD@{3}          # back to where you were three moves ago

# Committed to the wrong branch
git log --oneline -1               # note the hash
git reset --hard HEAD~1            # remove it from here
git checkout correct-branch
git cherry-pick              # apply it there

# Undo the last commit but KEEP the changes staged
git reset --soft HEAD~1

# Undo a commit that is already pushed - creates a NEW commit
git revert                   # safe on shared branches
git revert -m 1        # revert a merge: -m 1 keeps the main-line parent

# Recover a deleted branch
git reflog                         # find its tip
git branch recovered 

# Recover a commit lost by a bad rebase
git fsck --lost-found              # dangling commits, when reflog is not enough

# Find which commit introduced a bug
git bisect start
git bisect bad                     # current is broken
git bisect good v1.4.0             # this tag was fine
# test, then: git bisect good | git bisect bad ... until it names the commit
git bisect run dotnet test         # or let it drive itself

# Who changed this line, ignoring formatting-only commits
git blame -w -C --ignore-rev  path/to/File.cs

# Set aside work in progress
git stash push -m "half-done validation" --include-untracked
git stash list && git stash pop
Senior signal — the reflog means almost nothing is ever lost

The reflog records every position HEAD has held in this repository — every commit, checkout, reset, rebase and merge — for about 90 days by default.

So a "destroyed" branch, a bad reset --hard, or a rebase that mangled everything is recoverable: find the hash the reflog remembers and point a branch at it. The commits were never deleted, just unreferenced.

Knowing that changes how you work. It's what makes rebase and history editing reasonable rather than terrifying — the worst case is finding a hash in the reflog.

Two limits to state honestly. It's local, so it can't recover something that only ever existed on a machine you no longer have. And it only covers committed work — uncommitted changes destroyed by reset --hard or checkout -- are genuinely gone, which is the strongest argument for committing early and often, even messily. You can always tidy the history afterwards.

git fsck --lost-found is the deeper fallback, finding dangling objects the reflog doesn't reference.

reset versus revert, and why it matters on a shared branch

reset moves the branch pointer. History changes — commits disappear from the branch. Fine locally; on a shared branch it means the next push is a force push and everyone else's history diverges.

revert creates a new commit that undoes an earlier one. History grows rather than changing, so nobody else is disturbed.

Local mistake → reset. Public mistake → revert. That's the whole rule.

Reverting a merge commit needs -m 1, which tells Git which parent is the mainline. Without it, Git can't know which side you want to keep and refuses.

And when a force push is genuinely necessary — cleaning up your own feature branch — use --force-with-lease. It refuses if the remote has moved since you last fetched, so you can't silently destroy a colleague's push. Plain --force overwrites unconditionally, which is how someone's afternoon disappears.

Better still, protect main at the platform level: no force pushes, no deletion, required reviews and status checks. The reliable safeguards are the ones that don't depend on remembering anything.

bisect is the most underused command in Git

"It worked in the last release and it's broken now" over hundreds of commits is a binary search problem, and Git implements it for you. Twelve steps covers four thousand commits.

git bisect run makes it fully automatic: give it a command that exits non-zero on failure — a test, a script, a build — and it walks the history unattended and names the commit.

That turns an afternoon of guessing into a coffee break, and it's especially good for performance regressions and intermittent failures where reading diffs won't help.

The prerequisites are the argument for good commit hygiene: each commit needs to build and be testable, and small focused commits make the answer precise. A bisect that lands on a 3,000-line squashed merge tells you which feature, not which change — which is why the squash trade-off above is a real one.

Local hooks are a convenience, not a control

A pre-commit hook that formats code and scans for secrets is genuinely useful — it catches problems before they leave your machine.

It is not a guarantee. Hooks live in .git/hooks, which isn't version-controlled, so they're per-machine and per-developer. Anyone can skip one with --no-verify, and a new contributor simply won't have them.

So the same check must exist in CI, where it can't be bypassed. Hooks give fast feedback; CI provides the actual enforcement. Tools like Husky or a bootstrap script make hooks easier to distribute, and they don't change this.

Same principle as everywhere in this part of the handbook: a control that depends on every individual having configured something correctly isn't a control.

A secret in history is compromised — rotate it

Committing a connection string and then committing its deletion achieves nothing. It remains in every clone, every fork, every CI cache and every mirror.

So the response is always: rotate the credential immediately. History rewriting with git filter-repo or BFG is cosmetic and comes second — and it forces every collaborator to re-clone, so it isn't free.

Prevention is much cheaper: push protection and secret scanning in the platform, which blocks the push rather than reporting it afterwards, plus .gitignore covering appsettings.*.local.json and .env, and dotnet user-secrets for local development.

Same conclusion as managed identity: the strongest position is having no secret to commit in the first place.

Key takeaways
  • Commits are immutable content-addressed snapshots; branches are pointers.
  • Rebase can't move a commit — it replays it as a new one.
  • Unreferenced objects survive ~90 days, which is why recovery works.
  • Use git add -p so each commit is one logical change.
  • Rebase your own unpushed work; never rebase what others have based work on.
  • Squash suits short branches; it makes bisect coarser.
  • Never continue working on a squash-merged branch.
  • Trunk-based plus feature flags, because merge pain grows with branch age.
  • Commit messages explain why; the diff already shows what.
  • Pull request size determines whether it's genuinely reviewed.
  • Separate refactoring from behaviour change.
  • Reset for local mistakes, revert for public ones; -m 1 to revert a merge.
  • --force-with-lease, and protect main at the platform level.
  • bisect run automates regression hunting.
  • Local hooks aren't enforcement — CI is.
  • A committed secret must be rotated, not deleted.

Common mistakes

  • Rebasing a shared branch, forcing everyone else to recover.
  • Plain git push --force instead of --force-with-lease.
  • reset --hard on a pushed branch instead of revert.
  • Repeatedly merging main into a feature branch, cluttering its history.
  • Continuing to work on a squash-merged branch, then fighting the next merge.
  • Enormous pull requests that receive less review than small ones.
  • Refactoring mixed with behaviour change in one diff.
  • "fix", "wip", "updates" as commit messages.
  • Never using bisect, and reading diffs by hand instead.
  • Relying on local hooks with no CI equivalent.
  • Deleting a committed secret without rotating it.
  • main unprotected, so force pushes and deletions are possible.
  • Long-lived branches, discovering integration problems weeks late.

Interview questions

Intermediate

Merge or rebase? 🔥 Must know
How I'd answer

"They do different things, so I'd answer by where rather than picking a winner."

"Merge creates a commit with two parents, preserving both histories exactly. Rebase replays your commits on top of the target, producing linear history."

"The mechanical detail that matters: rebase doesn't move commits, it creates new ones. A commit's hash is derived from its content including its parent, so changing the parent necessarily produces a different commit. The originals still exist, unreferenced, until garbage collection — which is why the reflog can recover them."

"That's the whole reason rebasing shared history is disruptive. It isn't that Git refuses; it's that anyone who had the old commits now has history that diverges from the remote, and their next pull produces duplicates and nonsensical conflicts."

"So my rules:"

"Rebase my own unpushed work freely. Squash the 'fix typo' commits, reorder, reword. No one else has them, so it costs nothing and produces a branch that's pleasant to review."

"Rebase onto main rather than merging main into my branch, while the branch is mine. Repeatedly merging main in leaves the feature branch full of merge commits that make the diff harder to read — and that's the more common habit."

"Never rebase a branch someone else has based work on. If I absolutely must, it's a conversation first, not a force push."

"For integrating into main, all three options are defensible and it's a team decision. Squash gives one commit per feature and a very clean history. Rebase-and-merge keeps individual commits with linear history. Merge commits keep an exact record of what happened when."

"I'd lean toward squash for short-lived branches, which is what trunk-based development produces anyway. But I'd name the trade-off: squashing makes git bisect coarser. When bisect finds the bad commit, it's an entire feature rather than a specific change. You've traded debugging precision for a tidier log."

"And a practical gotcha with squash: never keep working on a squash-merged branch. Git can't tell the squashed commit contains that work, so the next merge re-applies everything and conflicts badly. Always branch fresh from main."

"One more thing on conflicts: rebase can make you resolve the same conflict repeatedly, once per replayed commit, whereas a merge resolves it once. git rerere helps a lot here — it remembers resolutions and reapplies them — and it's worth enabling if you rebase long branches."

"The part I'd emphasise: whatever the team picks, enforce it in the repository settings rather than relying on people choosing the right button. Consistency matters more than which one."

What they're really checking
  • Do you know rebase creates new commits, and why?
  • Do you have the shared-history rule?
  • Do you prefer rebasing onto main over merging main in?
  • Can you name the squash trade-off?
  • Do you treat the integration strategy as a team decision to enforce?
Weak answers
  • Red flag: "rebase is better, it's cleaner" with no caveats.
  • Red flag: not knowing why rebasing shared branches is a problem.
  • Red flag: thinking rebase modifies commits in place.
Likely follow-ups

  • How do you revert a squash-merged feature?

Advanced

A colleague force-pushed to main and work is missing. Recover it. ⭐ Senior-level
How I'd answer

"This is recoverable, and the first thing I'd do is stop anyone else from pushing or pulling — because the more people who fetch the rewritten main, the more local histories diverge and the messier the cleanup."

"Then I'd find the commits. The good news is nothing is actually deleted — a force push moves a pointer, and the old commits remain as unreferenced objects until garbage collection, roughly 90 days."

"The best source is someone's local clone. Anyone who had fetched main before the force push has the old commits, and their reflog records where their origin/main pointed. So git reflog show origin/main gives me the hash directly. Even simpler, someone who hasn't fetched since still has the correct history on disk."

"On the server side, GitHub and Azure DevOps both keep this: GitHub's Events API records the before-and-after SHAs of every push, and the Activity view shows force pushes with both hashes. So even with no usable local clone I can get the old tip."

"Once I have the hash, recovery is straightforward: create a branch at it, verify the history is what I expect, and restore main. I'd restore by merging the recovered commits rather than force pushing again, because another force push compounds the divergence for everyone who has already fetched."

"If the reflog isn't enough — say the rewrite happened locally and was garbage collected — git fsck --lost-found finds dangling commits directly in the object database."

"Then everyone else has to reconcile. Anyone who pulled the rewritten main has divergent history, and the clean fix is usually to reset their local main to the restored remote and rebase any local work on top. That's worth communicating explicitly, because the default reaction is to git pull, which creates a merge between the two histories and makes it worse."

"Then the more important part — why was this possible?"

"Branch protection on main should have prevented it outright: block force pushes, block deletion, require a pull request, require review and status checks. That's a repository setting, and it takes a minute."

"The reason I'd frame it that way is that this isn't a discipline problem to solve with a reminder. The command is one keystroke from a legitimate one, and people run it by accident — often trying to fix their own branch while on the wrong one. The fix is making it impossible, not asking people to be careful."

"I'd also establish --force-with-lease as the team default — it refuses if the remote has moved since your last fetch, so it can't silently overwrite someone else's push. It's strictly better than plain --force for every legitimate use, and setting push.useForceIfIncludes makes it the default behaviour."

"And I'd be careful about the tone of the follow-up. Someone force-pushing to main is usually a missing guardrail, not carelessness — the repository allowed a destructive operation with no confirmation. Treating it as a process failure rather than a personal one is both more accurate and more likely to get the protection turned on."

  • Do you know to look in reflogs and the platform's push history?
  • Do you restore by merging rather than another force push?
  • Do you address everyone else's divergent history?
  • Do you fix it with branch protection rather than a reminder?

A bug appeared somewhere in the last 300 commits. Find it. ⭐ Senior-level
How I'd answer

"git bisect, which turns this into a binary search — about eight or nine steps for 300 commits rather than reading 300 diffs."

"The prerequisite is a reliable way to tell good from bad, and I'd get that first. A failing test is ideal. A script that exits non-zero, or even manual steps I can perform consistently, works. Without a dependable check, bisect gives a confident wrong answer, because one mislabelled step sends it down the wrong half."

"So: git bisect start, mark the current commit bad, mark a known-good commit or tag good. Git checks out the midpoint, I test, mark it, and it converges."

"If I can automate the check, git bisect run dotnet test --filter FullyQualifiedName~TheTest does the whole thing unattended. That's the version worth remembering — it's the difference between an afternoon and a coffee break, and it's especially good for performance regressions where reading diffs wouldn't help at all."

"A few practical points."

"Commits that don't build. If the midpoint won't compile I can't test it, so git bisect skip excludes it and Git works around the gap. If many commits don't build, bisect gets unreliable — which is an argument for the discipline of every commit building."

"Intermittent bugs. Bisect assumes a deterministic answer. For a flaky failure I'd run the check enough times per step to be confident, or find a more deterministic reproduction first — otherwise a single false 'good' invalidates everything after it."

"Squashed history. If features were squash-merged, bisect lands on a whole feature rather than a specific change. Still a big narrowing, and then I can bisect within that feature's original branch if it still exists. This is the concrete cost of squash merging, and it's worth knowing before you need it."

"The bug might not be in our code. If bisect points at a commit that only bumps a package version, that's the answer — a dependency changed behaviour. Worth expecting, since it's easy to assume the culprit must be application logic."

"Once I have the commit, git show and I'm usually looking at a small diff with a message explaining the intent — which is where good commit hygiene pays off. A focused commit gives me the change and the reasoning together."

"Alternatives if bisect isn't practical: git log -S 'someString' finds commits that added or removed a specific string, and git log -L follows the history of a specific function or line range. Both are much faster when I already suspect a particular area."

"And git blame -w -C with --ignore-rev for formatting commits, so blame shows the last meaningful change rather than whoever reformatted the file."

"Afterwards I'd keep the reproduction as a regression test. That's the part that stops this recurring, and it's the actual deliverable — finding the commit is only half the job."

What they're really checking
  • Do you reach for bisect rather than reading diffs?
  • Do you establish a reliable good/bad test first?
  • Do you know bisect run?
  • Do you handle non-building commits and flaky tests?
  • Do you know log -S and log -L?
  • Do you add a regression test at the end?
Weak answers
  • Red flag: reading the log manually looking for suspicious commits.
  • Red flag: not knowing bisect exists.
  • Red flag: bisecting a flaky failure without addressing determinism.
Likely follow-ups
  • What if half the commits don't compile?
  • How would you bisect a performance regression?
  • What does git log -S do that grep doesn't?
