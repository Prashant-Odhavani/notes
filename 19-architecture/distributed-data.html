Distributed Data & Consistency

What replaces transactions once your data lives in more than one place. This is the highest-value page in the section for interviews.

🔴 Advanced 🔥 Must know ⭐ Senior-level
Quick revision
  • Dual write — writing to a database and a message broker in one method. Not atomic. This is the bug the outbox exists to fix.
  • Outbox — write the event to a table in the same transaction, dispatch it separately. Guarantees the event is never lost.
  • Inbox — record processed message IDs so a redelivery is skipped. That's idempotency for consumers.
  • Idempotency — doing it twice has the same effect as once. Mandatory with at-least-once delivery.
  • Saga — a multi-step process across services with compensating actions instead of rollback.
  • Exactly-once delivery doesn't exist. You get at-least-once delivery plus idempotent processing, which behaves like exactly-once.

Start with the bug: the dual write 🔥 Must know

Almost everything on this page exists because of this one problem.

public async Task CompleteOrderAsync(Guid orderId, CancellationToken ct)
{
    var order = await _db.Orders.SingleAsync(o => o.Id == orderId, ct);
    order.Complete();

    await _db.SaveChangesAsync(ct);                          // 1. database commits
    await _bus.PublishAsync(new OrderCompleted(orderId), ct); // 2. broker publish
}

Two separate systems, two separate commits, no transaction spanning them. So:

What failsResult
Publish fails after the DB commitOrder is complete, but fulfilment never hears. Silently lost work.
Process crashes between the two linesSame — order complete, no event
Swap the order (publish first)Event published, DB commit fails. Consumers react to something that never happened. Worse.
Remember this

You cannot make two independent systems commit atomically without a distributed transaction — and distributed transactions are avoided for good reasons (see below).

So instead you make one of them the source of truth, and derive the other from it. That's the outbox.

The outbox pattern 🔥 Must know

One line: write the message into your own database, in the same transaction as the data change, then publish it separately.
public async Task CompleteOrderAsync(Guid orderId, CancellationToken ct)
{
    var order = await _db.Orders.SingleAsync(o => o.Id == orderId, ct);
    order.Complete();

    // Same DbContext, same transaction as the order change.
    _db.OutboxMessages.Add(new OutboxMessage
    {
        Id          = Guid.NewGuid(),
        Type        = nameof(OrderCompleted),
        Payload     = JsonSerializer.Serialize(new OrderCompleted(orderId)),
        OccurredUtc = DateTime.UtcNow
    });

    await _db.SaveChangesAsync(ct);   // both commit, or neither does
}
public sealed class OutboxDispatcher(IServiceScopeFactory scopes, IMessageSender bus)
    : BackgroundService
{
    protected override async Task ExecuteAsync(CancellationToken ct)
    {
        while (!ct.IsCancellationRequested)
        {
            using var scope = scopes.CreateScope();          // scoped DbContext per batch
            var db = scope.ServiceProvider.GetRequiredService<AppDbContext>();

            var batch = await db.OutboxMessages
                .Where(m => m.ProcessedUtc == null)
                .OrderBy(m => m.OccurredUtc)                 // preserve ordering
                .Take(50)
                .ToListAsync(ct);

            foreach (var message in batch)
            {
                await bus.PublishAsync(message.Type, message.Payload, ct);
                message.ProcessedUtc = DateTime.UtcNow;
                await db.SaveChangesAsync(ct);   // mark after publish
            }

            if (batch.Count == 0) await Task.Delay(TimeSpan.FromSeconds(1), ct);
        }
    }
}

Why this is correct: the event and the state change commit together, so the event can never be lost. The dispatcher can crash, restart, or run twice — the message is safely in the table until it's marked sent.

What you've traded

The outbox gives you at-least-once delivery, not exactly-once. If the dispatcher publishes and then crashes before marking the row, the message is published again on restart.

That's fine — and it's the correct trade. Duplicate delivery is recoverable if consumers are idempotent. Lost messages are not recoverable at all.

Operating an outbox

  • Monitor the age of the oldest unsent row, not the count. If it's growing, the dispatcher is stuck or the broker is down.
  • Purge processed rows on a schedule, or the table grows forever and the polling query slows down.
  • Index on (ProcessedUtc, OccurredUtc) — the dispatcher query runs constantly.
  • Handle multiple dispatcher instances — use a lock, a lease column, or UPDLOCK/READPAST so two instances don't publish the same row.
  • Polling vs change feed: polling is simple and works everywhere. Some databases let you tail the log instead (SQL Server CDC, Postgres logical replication, Cosmos change feed), which lowers latency at the cost of more infrastructure.

Idempotency 🔥 Must know

Remember this

Idempotent means: doing it twice has the same effect as doing it once.

Once you accept at-least-once delivery, this stops being optional. It's what makes duplicates harmless.

Four ways to achieve it, roughly in order of preference:

TechniqueHowBest for
Naturally idempotent operationSET status = 'Shipped' rather than status = status + 1State assignment. The cheapest option — no extra machinery
Inbox / dedupe tableRecord processed message IDs; skip if seenMessage consumers
Idempotency keyCaller supplies a key; you store the result and replay itPublic APIs, payments
Conditional writeOptimistic concurrency / ETag / WHERE version = @expectedAnything with a version, and stale-update prevention

The inbox pattern

public async Task HandleAsync(OrderCompleted message, Guid messageId, CancellationToken ct)
{
    // Fast path: already handled.
    if (await _db.InboxMessages.AnyAsync(m => m.Id == messageId, ct))
        return;

    await using var tx = await _db.Database.BeginTransactionAsync(ct);

    // Record and process TOGETHER, so a crash can't record without processing.
    _db.InboxMessages.Add(new InboxMessage { Id = messageId, ProcessedUtc = DateTime.UtcNow });
    await DoTheWorkAsync(message, ct);

    await _db.SaveChangesAsync(ct);
    await tx.CommitAsync(ct);
}

Two details that matter:

  • The inbox row and the actual work must be in the same transaction. Recording first and processing after means a crash in between loses the work permanently.
  • The initial AnyAsync check is an optimisation, not the guarantee. Two concurrent deliveries can both pass it — so the primary key on InboxMessages.Id is what actually enforces uniqueness. One of them will fail on insert, which is correct.

Idempotency keys for APIs

POST /api/payments
Idempotency-Key: 7f3a9c21-4e8b-11ee-be56-0242ac120002
Content-Type: application/json

{ "orderId": "...", "amount": 4999, "currency": "GBP" }

The server stores the key with the response. A repeat with the same key returns the stored response rather than charging again. This is exactly how Stripe and most payment providers work, and it's why retrying a payment after a timeout is safe with them.

Production trap

The dangerous window is a timeout, because you genuinely don't know whether the operation succeeded. The request may have completed server-side and only the response was lost.

Without an idempotency key, retrying is a coin flip between "failed request" and "charged twice". With one, the retry is safe by construction — and this is the single most valuable thing to say in a payments interview question.

Sagas 🔥 Must know

One line: a business process across several services, where each step has a compensating action instead of a rollback.

You can't roll back a transaction another service already committed. So instead of undoing, you do something that counteracts it.

FORWARD PATH                          COMPENSATION (if a later step fails)
─────────────────────────────         ──────────────────────────────────────
1. Reserve stock             ────▶    Release stock
2. Authorize payment         ────▶    Void / refund the authorization
3. Create shipment           ────▶    Cancel the shipment
4. Send confirmation                  (nothing to undo - already sent)

Step 3 fails  →  run compensations for steps 2 and 1, in reverse order.
Compensation is not rollback

A rollback makes it as if nothing happened. A compensation is a new action that offsets the effect — and it's visible.

A refund isn't an un-charge: the customer saw the charge, their statement shows both lines, and their bank may have sent an alert. Sometimes there's no compensation — you can't un-send an email.

That's why saga step order matters: put the irreversible steps last.

Orchestrated vs choreographed sagas

OrchestratedChoreographed
Who drives itA coordinator serviceEach service reacts to the previous event
Process visibilityIn one place — readable and queryableEmergent; exists nowhere
"Where is order 123?"Query the orchestratorCheck six services' logs
Compensation logicCentralised, obvious homeScattered — and easily forgotten
CouplingOrchestrator knows everyoneServices only know events

For anything with compensation, orchestrate. The deciding factor is that someone will eventually ask what state a process is in, and choreography makes that expensive. More on both styles in event-driven architecture.

The parts people forget

  • The saga state must be persisted. If the orchestrator restarts mid-process, it has to resume — so "which step are we on" is a database row, not memory.
  • Compensations can fail too. They need retries, and eventually a human. A refund that fails silently is worse than the original problem.
  • Timeouts per step. A saga waiting forever for a reply is stuck invisibly. Every step needs a deadline and a decision about what happens when it passes.
  • Semantic locks. Between reserving stock and confirming, that stock is in an in-between state. Make it explicit — "reserved" rather than pretending it's still available.

Why not just use distributed transactions? 🔴 Advanced

Two-phase commit (2PC) does exist — a coordinator asks all participants to prepare, then tells them all to commit. It gives real atomicity. So why is it avoided?

ProblemWhy it matters
Locks held across the whole protocolEvery participant holds locks until everyone agrees. Throughput collapses under load
Coordinator is a single point of failureIf it dies after "prepare", participants are blocked holding locks, waiting for an answer that isn't coming
Availability is multiplicativeThe transaction needs every participant available. Five at 99.9% ≈ 99.5%
Poor supportMost modern datastores, message brokers and HTTP APIs don't participate in 2PC at all

The honest summary: 2PC trades availability for consistency, and does it in a way that scales badly. For most business processes, a saga with eventual consistency is the better trade — the business already tolerates it (an order being "processing" for thirty seconds is normal).

Eventual consistency, practically ⭐ Senior-level

One line: the system converges to a consistent state, but there's a window where different parts disagree.

The technical part is easy. The hard part is that users see the window — and that's a product decision, not just a technical one.

SituationHow to handle it
User saves, then immediately readsRead-your-own-writes: serve that user from the write store, or return the updated value in the write response
List still shows the old valueOptimistic UI — display the change locally while it propagates
Process takes secondsShow an explicit pending state. Honest, and it sets expectations
Two users edit the same thingOptimistic concurrency with a version — detect and tell them, don't silently overwrite
Senior signal

Asking "how stale is acceptable, and for whom?" before designing.

Most business data tolerates seconds of staleness. Some tolerates minutes. A few things — account balances at the point of withdrawal, seat allocation, inventory at checkout — tolerate none, and those need to stay in one transactional boundary.

Getting that classification right upfront is what makes the rest of the design possible.

Dead-letter queues 🟡 Intermediate

One line: where messages go when they can't be processed, so they don't block everything behind them.

A message can fail forever — malformed payload, a referenced entity that no longer exists, a bug. Without a DLQ it's retried indefinitely and blocks the queue. That's a poison message.

The standard flow:

  1. Delivery fails; the message returns to the queue.
  2. After N attempts (Service Bus defaults to 10 — verify current values), it moves to the DLQ.
  3. The main queue keeps flowing. Nothing is blocked.
  4. Someone gets alerted, investigates, fixes, and replays.
Production trap

Step 4 is the one teams skip. A DLQ nobody monitors is a silent data-loss bucket — messages accumulate for weeks and you find out when a customer asks why their order never shipped.

Alert on DLQ count > 0. Not a threshold — any message in the DLQ means something needs a human. And build the replay tooling before you need it, not during the incident.

Key takeaways
  • Dual writes silently lose data. The outbox is the fix, and it's not optional at scale.
  • Outbox gives at-least-once. That's the right trade — duplicates recover, losses don't.
  • Idempotency is mandatory once you have at-least-once. Inbox table, idempotency key, or a naturally idempotent operation.
  • Sagas compensate, they don't roll back. Put irreversible steps last.
  • Saga state must be persisted, and compensations need their own retries and alerting.
  • 2PC is avoided for availability and lock-duration reasons, not because it doesn't work.
  • Alert on any message reaching the DLQ, and build replay tooling in advance.

Common mistakes

  • Dual writes — the most common distributed data bug, and it's silent.
  • Publishing before the commit, so consumers react to changes that roll back.
  • No idempotency, so a redelivery double-charges or double-ships.
  • Inbox record committed separately from the work, so a crash between them loses the message permanently.
  • Saga state held in memory, so a restart loses in-flight processes.
  • Irreversible steps early in a saga — you can't compensate a sent email.
  • Unmonitored DLQ.
  • Eventual consistency introduced without telling product, so users get confusing UX nobody designed.

Interview questions

You save to the database and publish an event. How do you guarantee both happen? 🔥 Must know
How I'd answer

"You can't, if you do them as two separate operations — that's the dual-write problem. There's no transaction spanning your database and the broker, so if the publish fails after the commit, the state changed and nobody heard about it. And doing it the other way round is worse: consumers react to something that then rolled back."

"The fix is the outbox pattern. Instead of publishing directly, I insert the event into an Outbox table in my own database, in the same transaction as the state change. Now they're atomic — both commit or neither does."

"Then a separate background dispatcher polls that table, publishes the messages, and marks them sent. If it crashes, the messages are still in the table, so it just picks up where it left off."

"What that gives me is at-least-once delivery, not exactly-once. If the dispatcher publishes and dies before marking the row, it'll publish again on restart. That's the right trade — duplicates are recoverable if consumers are idempotent, but lost messages aren't recoverable at all."

"So the outbox always comes with idempotent consumers. On the consuming side I'd use an inbox table: record the message ID and do the work in one transaction, and skip if the ID is already there. The primary key on that table is what actually enforces it, not the existence check."

"Operationally, the things I'd watch are the age of the oldest unsent row — growing means the dispatcher is stuck — and purging processed rows so the table doesn't grow forever. And if there are multiple dispatcher instances, they need a lease or lock so they don't publish the same row twice."

What they're really checking
  • Do you recognise the dual-write problem by name?
  • Do you know the outbox gives at-least-once, and pair it with idempotency unprompted?
  • Have you actually operated one — the monitoring and purging details?
Weak answers
  • Red flag: "wrap both in a try/catch and retry the publish" — the process can die between them.
  • Red flag: "use a distributed transaction" without knowing why 2PC is avoided.
Likely follow-ups
  • How do you stop two dispatcher instances publishing the same message?
  • How do you preserve ordering with an outbox?
  • What's the latency cost, and how would you reduce it?
Two services need to stay consistent but can't share a transaction. What do you do? ⭐ Senior-level
How I'd answer

"First I'd challenge the split. If two things genuinely must be transactionally consistent at all times, that's strong evidence they belong in the same service and the same database. The service boundary is probably in the wrong place, and no pattern fully compensates for that."

"If the boundary is right — different teams, different scaling, a real ownership reason — then I'd use a saga and accept eventual consistency."

"Concretely: model the business process as a sequence of steps, each with a compensating action. Reserve stock, authorise payment, create shipment. If a later step fails, run the compensations in reverse — release the stock, void the authorisation."

"The important nuance is that compensation isn't rollback. A refund isn't an un-charge — the customer saw the charge and their bank may have alerted them. And some things have no compensation at all; you can't un-send an email. So I'd order the steps to put the irreversible ones last."

"I'd orchestrate rather than choreograph, because with compensation involved someone will absolutely ask 'where is order 123 and why is it stuck?' An orchestrator makes the process queryable and gives compensation an obvious home. The state has to be persisted so it survives a restart, and every step needs a timeout so a saga can't wait forever invisibly."

"And I'd get product involved, because eventual consistency is user-visible. 'Your order is being processed' as an explicit state is much better than pretending it's instant and having users refresh into confusing intermediate states."

"The thing I wouldn't do is reach for two-phase commit. It holds locks across all participants for the duration, the coordinator is a single point of failure that can leave participants blocked, and most modern datastores and brokers don't support it anyway."

What they're really checking
  • Do you question the boundary before accepting the constraint?
  • Do you know compensation ≠ rollback, with a concrete example?
  • Do you treat eventual consistency as a product decision?
Weak answers
  • Red flag: "use a distributed transaction" with no awareness of the cost.
  • Red flag: describing a saga with no mention of failure or compensation.
Likely follow-ups
  • What if a compensating action itself fails?
  • How do you detect a saga that's stuck?
  • How would you test a saga's failure paths?
How do you make a message consumer idempotent?
How I'd answer

"First I'd check whether the operation is already naturally idempotent, because that's the cheapest answer. Setting a status to 'Shipped' can run twice harmlessly. Incrementing a counter can't. If I can express the work as an assignment rather than a delta, I don't need any extra machinery."

"If it isn't naturally idempotent, the standard approach is an inbox table. Every message carries a unique ID, and I record processed IDs. On arrival, if the ID is already there, I skip."

"The critical detail is that the inbox record and the actual work must be in the same transaction. If I record first and process after, a crash in between means the message is marked done but the work never happened — and it'll never be retried, so it's lost silently. That's worse than the duplicate I was trying to prevent."

"The other detail: the existence check is an optimisation, not the guarantee. Two concurrent deliveries can both pass it. What actually enforces uniqueness is the primary key on the inbox table — one insert fails, which is exactly right. So I'd catch the unique-violation and treat it as 'already processed'."

"For public APIs I'd use the same idea with a client-supplied Idempotency-Key header, storing the response against the key and replaying it on a repeat. That's how payment providers work, and it's what makes retrying after a timeout safe — which is the case that really matters, because a timeout leaves you genuinely unsure whether the operation succeeded."

"Operationally, the inbox table needs a retention policy. Keeping IDs forever is unnecessary — the window only needs to be longer than the maximum possible redelivery delay, so something like a few days, with a cleanup job."

What they're really checking
  • Do you know natural idempotency is the cheapest option?
  • Do you get the same-transaction requirement and why?
  • Do you know the PK, not the check, is the real guarantee?
Likely follow-ups
  • What if the work involves calling another service that isn't idempotent?
  • How long do you keep processed message IDs?
  • How does this interact with ordering?
