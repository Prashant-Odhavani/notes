Application Architectures

Layered, Clean, Hexagonal, Onion, Vertical Slice and Modular Monolith — what each one actually changes, and when it's overkill.

🟡 Intermediate 🔥 Must know
Quick revision
  • Clean, Hexagonal and Onion are the same idea with different diagrams: business rules in the middle, dependencies pointing inward.
  • Classic layered architecture points the other way — the domain depends on data access, so it can't be tested or reused without the database.
  • The whole trick is the interface lives with the caller, and infrastructure implements it.
  • Vertical Slice organises by feature instead of by layer. Great for CRUD-heavy apps; less good when many features share complex rules.
  • Modular monolith = one deployable, hard internal boundaries. The right default for most systems.
  • All of these cost indirection. For a small CRUD service, two layers is honest and enough.

Classic layered (N-tier) 🟢 Beginner

One line: stack the code in layers — UI, business, data — with each layer calling the one below.
┌──────────────────┐
│   Presentation   │   Controllers, views
└────────┬─────────┘
         │ depends on
┌────────▼─────────┐
│  Business Logic  │   Services, rules
└────────┬─────────┘
         │ depends on          ← this arrow is the problem
┌────────▼─────────┐
│   Data Access    │   EF Core, SQL
└──────────────────┘

What goes wrong: your business logic depends on your data access layer. So:

  • You can't unit test business rules without a database.
  • EF entities leak upward and become your domain model, so persistence concerns shape your rules.
  • Changing storage means touching business code.
  • The "business layer" gradually becomes a thin pass-through, and the real logic ends up in controllers and stored procedures.

It's not useless — for a genuinely simple CRUD app it's honest and everyone understands it. But it doesn't survive complexity well.

Clean / Hexagonal / Onion — one idea 🔥 Must know

Remember this

Turn the dependency arrow around: infrastructure depends on the domain, never the reverse.

You do it by putting the interface in the inner layer and the implementation in the outer one.

        ┌──────────────────────────────────┐
        │  Infrastructure                  │  EF Core, HTTP clients, queues
        │   ┌──────────────────────────┐   │
        │   │  Application             │   │  Use cases, orchestration
        │   │    ┌────────────────┐    │   │
        │   │    │    Domain      │    │   │  Entities, rules, invariants
        │   │    │  (no deps)     │    │   │
        │   │    └────────────────┘    │   │
        │   └──────────────────────────┘   │
        └──────────────────────────────────┘
              all arrows point INWARD

  IOrderRepository       -> declared in Application
  SqlOrderRepository     -> implemented in Infrastructure

The three names differ mostly in vocabulary:

NameIts particular emphasisVocabulary
Hexagonal (Ports & Adapters)The app has "ports" (interfaces); adapters plug in — the UI is just another adapterPorts, adapters, driving/driven side
OnionConcentric layers, domain model at the centreDomain model, domain services, application services
CleanSame, with a stated "dependency rule" and use-case-centric application layerEntities, use cases, interface adapters, frameworks

If an interviewer asks the difference, the strong answer is: "They're the same idea. Hexagonal emphasises that every external thing is an adapter, Onion emphasises the layering, Clean adds the explicit dependency rule. In practice they produce the same project structure."

What it looks like in a .NET solution

Domain            (no project references at all)
   Order.cs, OrderLine.cs, Money.cs, OrderStatus.cs

Application       -> references Domain
   IOrderRepository.cs        <- interface lives HERE
   IUnitOfWork.cs
   PlaceOrderHandler.cs

Infrastructure    -> references Application, Domain
   SqlOrderRepository.cs      <- implementation lives HERE
   AppDbContext.cs
   StripePaymentGateway.cs

Api               -> references Application, Infrastructure (for DI wiring only)
   OrderController.cs
   Program.cs
The check that actually matters

Can the Domain project compile with zero package references — no EF Core, no ASP.NET, no JSON library? If yes, the dependency rule is real. If it references EF Core "just for the attributes", the rule is decorative.

What it costs

Trade-off

You get testable business rules, swappable infrastructure and clear boundaries.

You pay in indirection and mapping. A simple "get customer by ID" now passes through a controller, a handler, a repository interface, an implementation, and possibly two mapping steps. Newcomers navigate more files to follow one request.

For a service with real business rules, that's worth it. For CRUD over five tables, it's ceremony — and honest two-layer code would be better.

Vertical Slice architecture 🟡 Intermediate

One line: organise code by feature instead of by technical layer.
By layer — one feature is spread across four folders

Controllers/OrdersController.cs
Services/OrderService.cs
Repositories/OrderRepository.cs
DTOs/OrderDto.cs

By feature — everything for one use case together

Features/Orders/PlaceOrder/
  Command.cs, Handler.cs, Validator.cs, Endpoint.cs
Features/Orders/CancelOrder/
  Command.cs, Handler.cs, Endpoint.cs

Why it appeals: when you change a feature, everything you need is in one folder. You're not opening four projects to add a field. And each slice can be as simple or as complex as it needs to be — a trivial lookup doesn't need the full ceremony just because another feature does.

Where it struggles: when many slices share complex domain rules, you either duplicate them or extract a shared domain — at which point you're back to a layered core with vertical slices on top. That's a perfectly good outcome; it's just worth knowing it's where you'll land.

Modular monolith ⭐ Senior-level

One line: one deployable unit, but with internal boundaries as strict as if it were several services.

This is the most under-used architecture and, for most teams, the right default.

src/
  Modules/
    Orders/
      Orders.Domain/          internal
      Orders.Application/     internal
      Orders.Infrastructure/  internal   own DbContext, own tables/schema
      Orders.Contracts/       PUBLIC     the only thing other modules may reference
    Billing/
      ...same shape...
  Host/                       references every module, wires DI, one deployable

The rules that make it work — and they have to be enforced, not just intended:

  1. A module may only reference another module's Contracts project. Everything else is internal.
  2. Each module owns its own tables. No cross-module joins, and no foreign keys across module boundaries — otherwise you can't ever separate them.
  3. Cross-module communication is explicit — an in-process interface call or an in-process event. Never reaching into another module's repository.
  4. Enforce it mechanically. Project references plus an architecture test (NetArchTest or ArchUnitNET) that fails the build on a violation. Without that, the boundaries erode within months.
Why this is the right default

You get most of the design benefits of services — clear ownership, independent evolution, a real boundary — with none of the distributed cost.

One transaction. One deploy. One stack trace. And if a module later genuinely needs to be its own service, the seam already exists.

Choosing between them

StyleBest whenMain cost
Layered (N-tier)Simple CRUD; small team; short-lived appDomain coupled to data access; hard to test rules
Clean / Hexagonal / OnionReal business rules that must be testable and durableIndirection, mapping, more files per request
Vertical SliceMany independent use cases; CRUD-heavy with occasional complexityShared rules can get duplicated across slices
Modular monolithMost systems, most of the timeBoundaries erode unless mechanically enforced
MicroservicesSeveral teams needing independent deploy cadencesEverything in section 17

In plain terms: start with a modular monolith. Use Clean-style dependency inversion inside the modules that have real business rules, and let the simple CRUD modules be simple. Extract a service only when a specific module has a specific reason to deploy separately.

Key takeaways
  • Clean/Hexagonal/Onion are one idea: dependencies point inward, interfaces live with the caller.
  • The real test is whether your Domain project has zero infrastructure references.
  • Layered architecture's flaw is the direction of the arrow, not the layering itself.
  • Vertical slices optimise for changing one feature; layers optimise for changing one technical concern.
  • Modular monolith = service-style boundaries without distributed cost. Enforce it with architecture tests.
  • Match the ceremony to the complexity. Two layers is a legitimate answer for simple CRUD.

Common mistakes

  • Clean architecture with EF attributes on domain entities. The dependency rule is now decorative — you've paid the ceremony and kept the coupling.
  • Mapping between four near-identical models (entity → domain → DTO → view model) with no behavioural difference between them.
  • An "application service" that just forwards to a repository. If it adds nothing, it's a layer of indirection with no purpose.
  • Modules that share a DbContext "for convenience" — the boundary is now fictional.
  • Foreign keys across module boundaries, which permanently prevents separation.
  • Applying full Clean Architecture to a 5-table CRUD app, then wondering why simple changes take a day.

Interview questions

What's the difference between Clean, Hexagonal and Onion architecture?
How I'd answer

"Honestly — they're the same idea with different diagrams and vocabulary. All three say: put the business rules at the centre, and make every dependency point inward."

"Hexagonal calls the interfaces 'ports' and the implementations 'adapters', and its useful emphasis is that the UI is also just an adapter — not the top of a stack. Onion draws concentric circles with the domain model at the centre. Clean adds an explicit 'dependency rule' and organises the application layer around use cases."

"In a .NET solution all three produce roughly the same project structure: a Domain project with no references, an Application project that declares the interfaces, an Infrastructure project that implements them, and a host that wires it up."

"The mechanism that makes any of them work is the same one thing: the interface lives with the caller, not the implementer. IOrderRepository is defined in Application; SqlOrderRepository is in Infrastructure and depends on Application. That's what turns the arrow around."

"And the test I'd actually apply is whether the Domain project compiles with zero package references. If it has EF Core in it 'just for the attributes', the rule is decorative and you're paying the ceremony without getting the benefit."

What they're really checking
  • Do you understand the underlying principle, or just the diagrams?
  • Are you comfortable saying three named things are basically the same?
  • Do you know the concrete mechanism — interface ownership?
Weak answers
  • Red flag: inventing distinctions between them to sound thorough.
  • Red flag: describing layers without mentioning dependency direction.
Likely follow-ups
  • Where does validation live?
  • Do you map EF entities to separate domain entities, or use the same class? What's the trade-off?
  • Where does the DbContext go, and why?
What's a modular monolith, and why would you choose it over microservices? ⭐ Senior-level
How I'd answer

"A modular monolith is one deployable unit with internal boundaries as strict as if the modules were separate services. Each module owns its own data, exposes a narrow public contract, and everything else is internal."

"I'd choose it because it separates two things people usually conflate: modularity and distribution. Microservices give you both. But almost all the design benefits people want — clear ownership, independent evolution, a real boundary — come from modularity, and none of the costs do."

"With a monolith I still get one transaction across modules when I need it, one deploy, one stack trace, and no distributed tracing or saga infrastructure. Those aren't small savings — they're most of the operational burden of microservices."

"The thing that makes it work is enforcement. Boundaries that are only conventions erode within months, and then you have a big ball of mud with folders. So I'd enforce it mechanically: project references so a module physically cannot reference another module's internals, no foreign keys across module boundaries, separate schemas per module, and an architecture test that fails the build on a violation."

"And the payoff beyond simplicity is optionality. If one module later genuinely needs independent deployment — different scaling, a different team, a compliance boundary — the seam is already there. Extracting a well-isolated module is a real project but a tractable one. Extracting a module from a tangled monolith is not."

What they're really checking
  • Do you separate modularity from distribution?
  • Do you know boundaries need mechanical enforcement?
  • Can you argue against the fashionable option with reasons?
Likely follow-ups
  • How do two modules communicate without coupling?
  • Should modules share a database? What about a schema?
  • How do you decide when to extract one into a service?
Isn't Clean Architecture over-engineering for most projects?
How I'd answer

"Often, yes — and I'd rather say that than defend it reflexively."

"The cost is concrete. A simple 'get customer by ID' passes through a controller, a handler, a repository interface, an implementation, and maybe two mapping steps. Every one of those is a file a newcomer has to open to follow one request. If the business logic is 'validate three fields and save', that structure is pure overhead."

"So the question I ask is: are there business rules that must not be bypassed? If the domain has real invariants and state machines — pricing, entitlements, policy lifecycles — then isolating them so they can be tested without infrastructure genuinely pays. If it's CRUD, honest two-layer code is better, and I'd rather have that than ceremony."

"What I like doing in practice is applying it selectively. In a modular monolith, the two modules with real complexity get the full inward-dependency structure; the simple CRUD modules get a controller and a DbContext. Consistency across an entire codebase is less valuable than each part being appropriately simple."

"The one piece I'd keep almost everywhere is dependency inversion at I/O boundaries — time, HTTP calls, queues, external services. That's cheap and it's what makes tests fast and deterministic. It's the rest of the ceremony that's optional."

What they're really checking
  • Can you criticise a popular practice with specific costs?
  • Do you scale architecture to the actual complexity?
  • Do you know which single piece is worth keeping regardless?
Likely follow-ups
  • How do you avoid inconsistency when different modules use different structures?
  • At what point would you retrofit it into a CRUD app?
