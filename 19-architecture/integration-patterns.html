Integration & API Patterns

How components find each other and exchange work — the layer between "we have services" and "they actually cooperate".

🟡 Intermediate 🔥 Must know
Quick revision
  • Request/reply — caller waits for an answer. Simple, but the caller's availability is now tied to the callee's.
  • Fire-and-forget — caller doesn't wait. Decoupled, but you need a way to find out it failed.
  • API gateway — one entry point handling auth, routing, rate limiting, TLS.
  • BFF — a gateway per client type, so the mobile app isn't forced to use the web app's payload shapes.
  • Queue-based load levelling — put a queue in front of a component that can't absorb spikes. Converts a spike into a longer queue instead of an outage.
  • Claim check — don't put large payloads in messages. Store the blob, send the URL.

The four communication styles 🔥 Must know

Two independent choices: do I wait for a response? and do I know who I'm talking to?

StyleShapeGood forWatch out for
Request / reply Sync HTTP, gRPC You need the answer to continue — a price, a validation, a lookup Temporal coupling: if they're down, you're down. Latency adds up across hops
Fire and forget Send to a queue, don't wait Work that can happen later — emails, indexing, reports You won't know it failed unless you monitor for it
Publish / subscribe Publish to a topic, N subscribers Announcing facts; many independent reactions No idea who's listening; ordering and duplicates
Async request / reply Send, get a ticket, poll or get a callback Long operations — video encoding, report generation More moving parts: correlation, status storage, timeouts
Remember this

Synchronous calls create temporal coupling — both parties must be up at the same moment.

Chain four synchronous services at 99.9% each and your effective availability is about 99.6%. The maths gets worse fast.

Async request/reply, concretely

POST /api/reports
202 Accepted
Location: /api/reports/8f3c/status

GET /api/reports/8f3c/status
200 OK
{ "status": "Running", "startedAt": "2025-08-19T10:00:00Z" }

GET /api/reports/8f3c/status
200 OK
{ "status": "Completed", "resultUrl": "/api/reports/8f3c/download" }

The important details: return 202 Accepted, not 200 — the work isn't done. Give the caller a URL to check. And keep the status record around long enough that a client which crashed can come back and find out what happened.

API gateway 🔥 Must know

One line: a single front door that handles the concerns every service would otherwise implement itself.
           Internet
              │
        ┌─────▼──────────────────────────────┐
        │          API Gateway               │
        │  · TLS termination                 │
        │  · Authentication (validate JWT)   │
        │  · Rate limiting / quotas          │
        │  · Routing to the right service    │
        │  · Request/response logging        │
        │  · Response caching                │
        └───┬─────────────┬─────────────┬────┘
            ▼             ▼             ▼
       Orders svc    Catalog svc    Billing svc
       (no auth      (no TLS        (no rate
        code)         handling)      limiting)

What it genuinely buys you: those concerns get implemented once instead of per service, clients see one hostname, and internal topology can change without clients noticing.

Production trap — the gateway that ate the architecture

Gateways attract business logic. It starts reasonably — "just transform this response" — and ends with orchestration, validation and data mapping living in the gateway.

Now it's a single point of failure that every team has to change, deployments are coordinated, and you've rebuilt the ESB that microservices were supposed to escape.

Rule: the gateway does cross-cutting concerns. Never business rules.

Note also that authorization can't fully live at the gateway. It can check that the token is valid and the caller may reach the endpoint. It can't know that this user may see that specific order — that's a data-level decision, and it belongs in the service. Skipping it there is a common source of cross-tenant leaks; see tenant context.

Backend-for-Frontend 🟡 Intermediate

One line: one gateway per client type, shaped for that client's needs.

The problem it solves: a mobile app and a web app want very different things. Mobile wants fewer, smaller round trips because the network is slow. Web can afford several calls and wants richer payloads. One shared API ends up serving both badly — usually with a pile of ?include= and ?fields= parameters.

  Mobile app  ──▶  Mobile BFF   ──┐
                  (one call,       │
                   trimmed data)   │
                                   ├──▶  Orders / Catalog / Pricing services
  Web SPA     ──▶  Web BFF       ──┤
                  (richer, more    │
                   calls OK)       │
                                   │
  Partner API ──▶  Public API    ──┘
                  (stable contract,
                   versioned)

The trade-off: BFFs duplicate some logic across each one, and each needs owning and deploying. That's worth it when clients genuinely differ and are owned by different teams. It's not worth it for two clients that need almost the same thing.

Best practice

Have the client team own its BFF. That's the whole point — the mobile team can change their payload shape without negotiating with a platform team. If a central team owns all the BFFs, you've just built several gateways and kept the bottleneck.

Queue-based load levelling 🔥 Must know

Remember this

Put a queue in front of anything that can't absorb a spike.

The spike becomes a longer queue instead of an outage. Latency degrades gracefully instead of the system falling over.

// API: accept and enqueue. Returns in milliseconds regardless of load.
app.MapPost("/api/documents", async (UploadDocument cmd, IMessageSender sender, CancellationToken ct) =>
{
    var jobId = Guid.NewGuid();
    await sender.SendAsync(new ProcessDocument(jobId, cmd.BlobUrl), ct);
    return Results.Accepted($"/api/documents/{jobId}");
});

// Worker: processes at whatever rate the database and CPU can sustain.
// A traffic spike lengthens the queue - it does not overwhelm the database.

Where this is exactly right: a downstream system with a hard throughput limit — a legacy API, a third party with strict rate limits, a database that can only take so many writes per second.

What it doesn't fix

Levelling handles bursts, not a sustained overload. If arrival rate exceeds processing rate on average, the queue grows forever and latency goes to infinity.

So always monitor queue age — the time the oldest unprocessed message has been waiting. Queue length alone is meaningless without knowing throughput.

Competing consumers 🟡 Intermediate

One line: several instances read from the same queue; each message goes to exactly one of them.

This is how you scale queue processing — add instances, throughput rises. Two things to get right:

  • Message locking. While one consumer holds a message, others can't see it. If the consumer dies, the lock expires and the message reappears — which is exactly why you need idempotency.
  • Ordering is lost. Three consumers process three messages concurrently, so they can complete out of order. If you need ordering for related messages, you need sessions (Service Bus) or a partition key (Kafka, Event Hubs) so related messages go to the same consumer. See delivery and ordering.

Claim check 🟡 Intermediate 💡 Good to know

One line: put the big payload in storage and send a reference in the message.
// Bad: a 40 MB PDF in the message body. Most brokers reject it, and
// even if they don't, it destroys throughput for everyone else.

// Good: store it, send the pointer.
var blobUrl = await _blobs.UploadAsync(stream, ct);
await _sender.SendAsync(new DocumentUploaded(documentId, blobUrl, sizeBytes), ct);

Brokers have message size limits (Service Bus standard is 256 KB, premium 100 MB — verify current values before quoting). But even under the limit, large messages hurt: slower transfer, more memory per consumer, and one big message can delay everything behind it.

Two things to remember with claim check: the consumer needs permission to read the blob (use a short-lived SAS or managed identity), and you need a cleanup policy — otherwise orphaned blobs accumulate forever when messages fail permanently.

Strangler fig 🔴 Advanced

One line: replace a legacy system gradually by routing traffic away from it, piece by piece.
  1. Put a facade — usually a gateway or reverse proxy — in front of the legacy system. Everything still routes through to it. Nothing has changed functionally, and that's the point.
  2. Build one new capability behind the facade. Route just that path to the new implementation.
  3. Repeat, path by path, with each step independently shippable and revertible.
  4. When nothing routes to the legacy system, delete it.

Why this beats a rewrite: every step delivers value and can be reverted. A big-bang rewrite is a long period with no delivery, ending in one enormous risky cutover — and it has to catch up with two years of changes made to the legacy system meanwhile.

The hard part nobody mentions

Shared data. While both systems run, they usually need the same data — so you're either dual-writing, syncing, or letting the new system read the old database.

That's the part that determines whether the migration takes six months or three years, and it deserves more design attention than the routing.

Key takeaways
  • Sync calls chain availability multiplicatively. Four 99.9% services in series ≈ 99.6%.
  • Async request/reply returns 202 plus a status URL — don't fake it with a long-running request.
  • Gateways handle cross-cutting concerns. Business logic there rebuilds the ESB.
  • Data-level authorization can't live at the gateway.
  • Queue levelling absorbs bursts, not sustained overload. Monitor queue age.
  • Competing consumers scale throughput and destroy ordering. Use sessions or partition keys if order matters.
  • Claim check for anything large — and plan the cleanup.

Common mistakes

  • Business logic in the API gateway, turning it into a coupled single point of failure.
  • Relying on the gateway for data-level authorization, which it can't do — a common cross-tenant leak.
  • Long chains of synchronous calls, where latency and failure probability compound.
  • Fire-and-forget with no monitoring, so failures are invisible until a customer complains.
  • Large payloads in messages instead of claim check.
  • Alerting on queue length instead of queue age, which tells you nothing about impact.
  • Assuming ordering with competing consumers, which is exactly what they give up.

Interview questions

When would you use synchronous calls versus messaging between services?
How I'd answer

"The deciding question is whether the caller needs the answer to continue. If I'm checking a price or validating something before I can respond to the user, that's request/reply — faking it with messaging and a correlation timeout is more complex and no more reliable."

"If the work can happen afterwards — sending a confirmation email, updating a search index, generating a report — messaging is better, because the caller returns immediately and a slow or unavailable consumer doesn't affect the user."

"The thing I'd raise about synchronous chains is that they multiply availability. Four services at 99.9% in series gives you about 99.6%, and each hop adds latency. So a request path that touches five services synchronously is fragile by construction — and the fix is usually to move some of those calls off the request path entirely rather than to make each one faster."

"There's a middle option worth mentioning: async request/reply. Return 202 with a status URL and let the client poll or receive a callback. That's the right shape for anything genuinely long-running, like report generation or video processing, and it's much better than holding an HTTP request open for two minutes."

"One practical caution on messaging: it isn't free decoupling. You take on idempotency, ordering concerns, dead-letter monitoring and a harder debugging story. So I'd use it where it buys something real — absorbing spikes, decoupling availability, fanning out to several consumers — not just because it sounds more modern."

What they're really checking
  • Do you have a clear decision rule rather than a preference?
  • Do you know availability compounds across sync hops?
  • Do you know async request/reply as a third option?
Likely follow-ups
  • The user needs to see the result of a 30-second operation. How do you design it?
  • How do you stop a slow downstream service from exhausting your thread pool?
What's an API gateway, and what should it never do? ⭐ Senior-level
How I'd answer

"It's a single entry point in front of your services that handles the concerns every service would otherwise implement itself — TLS termination, authentication, rate limiting, routing, logging, sometimes response caching."

"The value is that those get done once, consistently, and clients see one hostname while the internal topology can change freely."

"What it should never do is business logic. That's the failure mode I've watched happen: it starts as 'just transform this response', then it's aggregating three services, then there's validation, then pricing rules. At that point the gateway is a single point of failure that every team must change, deployments need coordinating, and you've rebuilt the ESB that microservices were meant to avoid."

"The other thing it can't fully do is authorization. It can verify the token is valid and that the caller is allowed to hit the endpoint. It cannot know that this user may see that specific order — that's a data-level decision that needs the data. Teams that assume the gateway handles authorization end up with cross-tenant leaks, because a valid token for tenant A reaches an endpoint that returns tenant B's row."

"I'd also watch the deployment coupling. If every service change needs a gateway config change, the gateway has become a bottleneck. Routing should be generic enough that adding an endpoint doesn't require touching it."

What they're really checking
  • Do you know the boundary between cross-cutting and business concerns?
  • Do you know authorization can't be fully centralised?
  • Have you seen a gateway become a bottleneck?
Likely follow-ups
  • Where would you enforce tenant isolation, then?
  • What's the difference between a gateway and a BFF?
  • How do you stop the gateway being a single point of failure?
A downstream legacy API can only handle 50 requests/second, but you get bursts of 500. What do you do?
How I'd answer

"This is queue-based load levelling. I'd put a queue between us and the legacy API, accept requests fast, and have a worker consume at a rate the legacy system can sustain."

"So the API accepts the request, writes a message, and returns 202 with a status URL. The worker processes at a controlled rate — I'd cap concurrency explicitly rather than relying on it happening to be slow enough. A burst of 500 then becomes a longer queue and higher latency, not a downstream outage."

"I'd add a few things around that. Idempotency, because at-least-once delivery means retries will happen. A dead-letter queue with monitoring, so permanently failing messages surface instead of disappearing. And a circuit breaker, so if the legacy system starts failing we stop hammering it and give it room to recover."

"The important caveat is that levelling only fixes bursts. If sustained arrival rate exceeds 50/second on average, the queue grows without bound and latency goes to infinity — the queue just hides the problem for a while. So I'd monitor queue age, not queue length, because age directly reflects how stale the work is, and alert if the oldest message exceeds our acceptable latency."

"If the average genuinely exceeds capacity, then the answer is different: either the legacy system has to scale, or we shed load deliberately — reject with 429 and a Retry-After — which is much better than accepting work we can never complete."

What they're really checking
  • Do you know the pattern by name and mechanism?
  • Do you understand it only fixes bursts, not sustained overload?
  • Do you monitor the right metric?
Weak answers
  • Red flag: "add retries" — that increases load on an overloaded system.
  • Red flag: "add a queue" with no mention of the sustained-rate limit.
Likely follow-ups
  • How do you stop the queue growing unbounded?
  • The user needs to know when their request completed. How?
  • What if messages must be processed in order per customer?
