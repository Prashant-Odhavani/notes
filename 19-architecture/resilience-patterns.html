Resilience Patterns

How a system survives its dependencies failing — and how these same patterns cause outages when they're applied carelessly.

🟡 Intermediate 🔴 Advanced 🔥 Must know
Quick revision
  • Timeout — the most important one. Without it, a slow dependency exhausts your threads and takes you down too.
  • Retry — only for transient failures, only with backoff and jitter, only on idempotent operations.
  • Circuit breaker — stop calling something that's clearly broken. Fail fast, give it room to recover.
  • Bulkhead — isolate resources so one bad dependency can't consume everything.
  • Rate limiting — protect yourself from callers. Load shedding — reject work you can't complete.
  • Order matters: timeout → retry → circuit breaker → bulkhead, and the outer timeout must cover all retries.

The failure these prevent 🟢 Beginner

Remember this

The classic distributed outage isn't a service crashing. It's a service getting slow — and everything upstream piling up behind it until they all fall over.

Here's the mechanism, step by step, because interviewers ask you to trace it:

  1. A downstream dependency starts responding in 30 seconds instead of 50ms.
  2. Your requests to it don't fail — they wait. Each one holds a thread and a connection.
  3. New requests keep arriving. Threads accumulate in the waiting state.
  4. The thread pool or connection pool exhausts.
  5. Now every endpoint fails, including ones that never touch the slow dependency.
  6. Your callers start piling up behind you. The failure propagates upward.

Notice that the visible symptom — "the whole API is down" — is several steps away from the cause. That's why resilience patterns matter: they stop the propagation at step 2.

Timeout 🔥 Must know

One line: never wait indefinitely for anything that crosses a network.

This is the single highest-value resilience pattern, and the most commonly missing one.

var response = await _httpClient.GetAsync(url);   // default is 100 seconds!
// Client-level default
services.AddHttpClient<IPricingClient, PricingClient>(c =>
{
    c.BaseAddress = new Uri("https://pricing.internal/");
    c.Timeout = TimeSpan.FromSeconds(3);       // fail fast
});

// Per-call, combined with the caller's cancellation
using var cts = CancellationTokenSource.CreateLinkedTokenSource(ct);
cts.CancelAfter(TimeSpan.FromSeconds(2));
var response = await _httpClient.GetAsync(url, cts.Token);
Choosing the number

Set the timeout from the dependency's p99 latency, not from its average. If p99 is 200ms, a 2-second timeout is generous but still fails fast.

Common mistake: setting it to 30 seconds "to be safe". That's not safe — it means 30 seconds of holding a thread while the user has long since given up.

And your timeout must be shorter than your caller's, otherwise you're doing work for a request nobody is waiting for any more.

Timeouts apply to more than HTTP: database commands, message locks, distributed locks, and any await that could block indefinitely.

Retry 🔥 Must know

One line: try again, because some failures are temporary — but only under strict conditions.

Three conditions, all required:

  1. The failure must be transient. Timeouts, 503s, 429s, connection resets. Never retry a 400 or a validation failure — the answer won't change, and you're adding load for nothing.
  2. The operation must be idempotent, or protected by an idempotency key. Retrying a payment authorisation that actually succeeded charges the customer twice.
  3. Backoff with jitter. Without it, every client retries at the same instant and recreates the spike that caused the failure.
for (var i = 0; i < 5; i++)
{
    try { return await _client.PostAsync(url, content); }   // not idempotent!
    catch { await Task.Delay(100); }                        // fixed delay, no jitter
}                                                           // retries EVERYTHING, incl. 400s
var retry = new ResiliencePipelineBuilder<HttpResponseMessage>()
    .AddRetry(new RetryStrategyOptions<HttpResponseMessage>
    {
        MaxRetryAttempts = 3,
        BackoffType = DelayBackoffType.Exponential,
        UseJitter = true,                                  // spreads the retries out
        ShouldHandle = new PredicateBuilder<HttpResponseMessage>()
            .Handle<HttpRequestException>()
            .Handle<TimeoutRejectedException>()
            .HandleResult(r => r.StatusCode is HttpStatusCode.ServiceUnavailable
                                            or HttpStatusCode.TooManyRequests)
        // note: 400/401/404 are NOT retried
    })
    .Build();
Production trap — the retry storm

Retries multiply load on a system that is already struggling.

Three retries means 4× the traffic at exactly the worst moment. Add a second service that also retries and you have 16×. This is how a brief blip becomes a sustained outage — and it's entirely self-inflicted.

Always cap attempts, always use jitter, and always pair retries with a circuit breaker so you stop retrying when the dependency is properly down.

Circuit breaker 🔥 Must know

One line: after enough failures, stop calling — fail immediately instead of waiting, and try again later.
   ┌──────────┐   failures exceed threshold    ┌──────────┐
   │  CLOSED  │ ─────────────────────────────▶ │   OPEN   │
   │          │                                │          │
   │ calls go │                                │ calls    │
   │ through  │ ◀───────────────────────────── │ fail     │
   └──────────┘      trial call succeeded      │ instantly│
        ▲                                      └────┬─────┘
        │                                           │ after a break duration
        │            ┌───────────────┐              │
        └────────────│   HALF-OPEN   │◀─────────────┘
     trial succeeds  │ let ONE call  │
                     │ through to    │──── trial fails ──▶ back to OPEN
                     │ test recovery │
                     └───────────────┘

Why this helps both sides:

  • You stop waiting on something that's clearly broken — no threads held, fast failure, you can serve a fallback.
  • The dependency gets breathing room to recover instead of being hammered while it's trying to restart.

The half-open state is the clever part: after the break, one trial call is allowed through. If it succeeds the circuit closes; if it fails the circuit opens again. That's how it detects recovery without flooding the recovering service.

var pipeline = new ResiliencePipelineBuilder<HttpResponseMessage>()
    .AddTimeout(TimeSpan.FromSeconds(10))        // outermost: covers ALL retries
    .AddCircuitBreaker(new CircuitBreakerStrategyOptions<HttpResponseMessage>
    {
        FailureRatio = 0.5,                      // 50% of calls failing
        MinimumThroughput = 20,                  // ...over at least 20 calls
        SamplingDuration = TimeSpan.FromSeconds(30),
        BreakDuration = TimeSpan.FromSeconds(15)
    })
    .AddRetry(new RetryStrategyOptions<HttpResponseMessage> { MaxRetryAttempts = 3, UseJitter = true })
    .AddTimeout(TimeSpan.FromSeconds(2))         // innermost: per attempt
    .Build();
The ordering rule

Outer timeout → circuit breaker → retry → inner timeout.

The inner timeout bounds each attempt. The outer one bounds the whole operation including retries — otherwise 3 retries × 2s each can exceed what the caller will wait for.

Common mistake

MinimumThroughput exists for a reason. Without it, two failures during a quiet period (2 out of 2 calls = 100% failure) trip the breaker and take out a healthy dependency. Always require a meaningful sample before the breaker can open.

Bulkhead 🔴 Advanced

One line: partition your resources so one failure can't consume all of them.

Named after ship compartments — one flooded compartment doesn't sink the vessel.

WITHOUT bulkheads - one shared thread pool of 100:

  Slow recommendation service (nice-to-have)
        │
        ▼
  ┌─────────────────────────────────────┐
  │  100 threads, all waiting on it     │  ← checkout now fails too,
  └─────────────────────────────────────┘     even though it never calls
                                              the recommendation service
// Recommendations: nice to have. Cap it at 10 concurrent calls.
// Even if it hangs completely, only 10 threads are affected.
private readonly SemaphoreSlim _recommendationLimit = new(10);

public async Task<IReadOnlyList<Product>> GetRecommendationsAsync(CancellationToken ct)
{
    if (!await _recommendationLimit.WaitAsync(TimeSpan.FromMilliseconds(50), ct))
        return [];                    // shed rather than queue - it's optional data

    try { return await _recommendations.GetAsync(ct); }
    finally { _recommendationLimit.Release(); }
}

Bulkheads apply at several levels, and the higher levels matter more:

  • Thread/concurrency limits per dependency, as above.
  • Separate connection pools per database, so a slow reporting query can't exhaust the pool that checkout needs.
  • Separate instances — run critical and non-critical workloads on different compute, so a batch job can't starve the API.
  • Separate queues per priority or per tenant, so one noisy tenant can't monopolise processing. See noisy neighbours.

Four common algorithms, in increasing sophistication:

AlgorithmHow it worksNote
Fixed windowN requests per calendar minuteSimple, but allows a 2N burst across a window boundary
Sliding windowN requests in the trailing 60 secondsSmoother; more state to track

Best practice

Always return Retry-After with a 429. Without it, well-behaved clients guess — and usually retry too fast, which keeps you overloaded.

And rate limit per tenant or API key, not just globally. A global limit means one heavy user can consume everyone's quota, which is exactly the noisy-neighbour problem.

Fallback and graceful degradation 🟡 Intermediate

One line: when something fails, serve something useful instead of an error.
FallbackGood forDanger
Cached/stale dataProduct catalogue, config, reference dataUsers see outdated information — must be acceptable
Default valueRecommendations, personalisation, optional widgetsSilently degraded experience nobody notices is broken
Queue for laterAnything that doesn't need an immediate answerNeeds a way to report eventual failure
Reduced functionalityRead-only mode when writes failMust be explicitly communicated to the user
Production trap — the silent fallback

A fallback that hides a failure is a trap. If pricing falls back to a cached value and nobody is alerted, you can serve stale prices for days.

Every fallback must emit a metric and alert on sustained use. Falling back is fine; falling back unnoticed is not.

And never fall back to a default for something safety-critical. "Couldn't check permissions, so I'll allow it" is how breaches happen — fail closed for anything security-related.

Key takeaways
  • Timeouts first. They're the pattern that prevents the cascade, and the most often missing.
  • Retry only transient failures, only idempotent operations, always with jitter and a cap.
  • Retries multiply load — pair them with a circuit breaker or you amplify the outage.
  • Circuit breakers need a minimum throughput, or quiet periods trip them spuriously.
  • Bulkheads stop one bad dependency consuming everything. Separate pools, not just limits.
  • Every fallback needs a metric. Silent degradation is worse than failure.

Common mistakes

  • No timeout at all, or a default so long it's effectively none.
  • Retrying non-idempotent operations, causing duplicate charges or duplicate orders.
  • Retrying 4xx responses — the answer won't change, so it's pure extra load.
  • Fixed-delay retries with no jitter, so all clients hammer in lockstep.
  • A circuit breaker with no minimum throughput, tripping on two failures at 3am.
  • Total retry time exceeding the caller's timeout, so all the work is wasted.
  • Fallbacks with no alerting, so degraded mode becomes permanent and invisible.
  • Resilience only on HTTP calls, leaving database commands and message locks unbounded.

Interview questions

Explain the circuit breaker pattern. When would it hurt you? ⭐ Senior-level
How I'd answer

"It tracks failures to a dependency, and once they cross a threshold it stops making calls entirely — failing immediately instead of waiting. After a break period it lets one trial call through: succeed and it closes, fail and it opens again. That's the closed, open, half-open cycle."

"It helps both sides. I stop holding threads waiting on something that's clearly broken, so I can fail fast or serve a fallback. And the dependency gets room to recover instead of being hammered while it's restarting — which matters, because a service coming back up under full load often just falls over again."

"Where it hurts is misconfiguration, and I've seen both directions."

"Too sensitive: if there's no minimum throughput requirement, two failures during a quiet period is 100% failure rate, and you've taken out a perfectly healthy dependency. So the breaker needs a meaningful sample — something like 50% failures over at least 20 calls in 30 seconds."

"Wrong scope: a breaker on the whole client means one bad endpoint opens the circuit for all of them. If a service has one slow reporting endpoint and nine fast ones, breaking all ten is over-reacting."

"And the one people miss: a breaker without a fallback just converts a slow failure into a fast failure. That's still better — you're not exhausting threads — but the user still gets an error. The value really lands when you pair it with something useful: cached data, a default, or a degraded experience."

"I'd also make sure the breaker state is visible in telemetry. An open circuit is an incident signal, and if nobody can see it you'll be debugging 'the API is fast but returning errors' without the obvious clue."

What they're really checking
  • Do you know all three states and what half-open is for?
  • Can you name real misconfigurations?
  • Do you connect it to fallbacks and observability?
Weak answers
  • Red flag: describing only open and closed.
  • Red flag: no mention of thresholds or minimum throughput.
Likely follow-ups
  • How do retry and circuit breaker interact? Which wraps which?
  • What do you return while the circuit is open?
  • How would you test this?
Your service calls a payment API. It starts timing out. Walk me through what happens and how you'd protect against it.
How I'd answer

"Without protection, the failure mode is a cascade. Requests to the payment API stop returning but don't fail either — they wait. Each one holds a thread and a connection. New requests keep arriving, threads accumulate, and eventually the thread pool or connection pool is exhausted."

"At that point every endpoint starts failing, including ones that never touch payments. That's the part people miss — the visible symptom is 'the whole API is down', which is several steps away from the actual cause."

"To protect against it, in order of importance:"

"Timeout first, set from the payment API's p99 — maybe 3 seconds. That alone stops the cascade, because threads are released instead of accumulating. It's the highest-value thing and it's what's usually missing."

"Bulkhead second: cap concurrent calls to payments at some number well below my total capacity. Even if every one of those hangs for the full timeout, the rest of the service keeps serving."

"Circuit breaker third, so once it's clearly broken I stop trying and fail fast, and give it room to recover."

"Retry — but carefully, because payments are the case where retry is dangerous. A timeout means I don't know whether the charge went through. So retrying needs an idempotency key that the provider honours; otherwise I risk double-charging a customer, which is far worse than failing the request."

"For the user experience, I'd rather return a clear 'payment is being processed, we'll confirm shortly' than a 500 — which means the order goes into a pending state and reconciles against the provider later. That's more work, but for payments it's the honest design."

What they're really checking
  • Can you trace the cascade mechanism, not just name patterns?
  • Do you get that timeout is the critical one?
  • Do you recognise the "did it actually succeed?" ambiguity in payments?
Weak answers
  • Red flag: "add retries" as the first answer — that makes it worse.
  • Red flag: no mention of thread/connection pool exhaustion.
Likely follow-ups
  • How do you know whether the payment actually went through after a timeout?
  • What would you monitor to catch this earlier?
  • How do you test this behaviour before it happens in production?
How do retries make an outage worse?
How I'd answer

"They multiply load on a system that's already struggling — which is the exact opposite of what it needs."

"If every client retries three times, a service that's failing sees 4× its normal traffic. And because retries usually come with fixed delays, they arrive in synchronised waves — every client retrying at the same instant, recreating the spike."

"It compounds across layers too. If service A retries calls to B, and B retries calls to C, then C sees up to 16× the original load. A brief blip in C becomes a sustained outage, and it's entirely self-inflicted."

"There's also a subtle version: retry after a timeout. The original request may still be running server-side, so now the server is processing two copies of the same work while you wait on the second one. You've doubled the load per logical request without gaining anything."

"The mitigations are: jitter, so retries spread out instead of synchronising. A hard cap on attempts — three is usually plenty; if three didn't work, a fourth won't. A circuit breaker, so once the dependency is clearly down we stop retrying entirely. And only retrying genuinely transient failures — retrying a 400 is pure waste."

"The other side of it is that the receiving service should protect itself rather than trusting callers to behave. Rate limiting per client and load shedding when overloaded — returning 429 with Retry-After — is what actually stops a badly-behaved client from taking you down."

What they're really checking
  • Do you understand retry amplification and how it compounds across layers?
  • Do you know jitter's purpose specifically?
  • Do you think about defending from the receiving side too?
Likely follow-ups
  • What's a retry budget?
  • How do you retry safely when you can't tell whether the first attempt succeeded?
