Domain-Driven Design

A way of finding boundaries in complex business software — and the vocabulary interviewers expect you to use precisely.

🟡 Intermediate 🔴 Advanced ⭐ Senior-level
Quick revision
  • Bounded context — a boundary inside which a word means exactly one thing. This is the most valuable idea in DDD.
  • Aggregate — a cluster of objects treated as one unit for changes. Its root is the only way in.
  • An aggregate is a consistency boundary, not a "group of related things". That's the distinction most people get wrong.
  • Entity = has identity that persists through change. Value object = defined entirely by its values, immutable.
  • Domain event = something meaningful happened, stated in past tense.
  • DDD is for complex domains. On CRUD it's pure cost, and saying so is a senior signal.

What DDD is actually for 🟢 Beginner

Remember this

DDD's core claim: in complex business software, the hard part isn't the technology — it's understanding and modelling the business accurately.

So the code should be structured around the business, and use the business's own words.

It's usually split into two halves, and they have very different value:

What it coversHonest value
Strategic DDD Bounded contexts, context maps, ubiquitous language, anti-corruption layers High. Useful even on a monolith, even on a small team. This is where the real payoff is
Tactical DDD Aggregates, entities, value objects, repositories, domain services, domain events Depends. Excellent for complex invariants. Ceremony for CRUD

Most teams adopt the tactical patterns and skip the strategic thinking, which is backwards — the patterns are the cheap part.

Ubiquitous language 🔥 Must know

One line: developers and domain experts use the same words for the same things, and the code uses those words too.

This sounds soft. It isn't. Here's what it prevents:

Without it

Sales says "account" meaning the company.
Support says "account" meaning the login.
Finance says "account" meaning the billing record.

You build one Account table with 47 columns, and every query needs a comment explaining which kind of account it means.

With it

Organisation, UserAccount and BillingAccount — three concepts, three names, three tables.

Nobody has to ask which one a method means.

The practical version: write a glossary early, argue about the words, and then name your classes exactly that. If the business calls it a "policy renewal", don't name the class ContractUpdateProcessor.

Bounded context 🔥 Must know

Remember this

A bounded context is a boundary inside which each term has exactly one meaning.

The same real-world thing can appear in several contexts with different shapes — and that's correct, not duplication to eliminate.

Example. "Customer" in three contexts:

ContextWhat "Customer" means thereFields it cares about
SalesA prospect or account being sold toLead source, pipeline stage, assigned rep
BillingA party that owes moneyPayment method, tax ID, credit limit, invoices
SupportA person raising ticketsContact details, entitlement tier, ticket history

The instinct is to build one shared Customer class. That's the mistake. It produces a class that serves nobody well, changes for three different reasons, and forces three teams to coordinate on every change.

Three separate models, each small and fit for its purpose, linked by a shared customer ID, is the right answer.

Senior signal

Being comfortable with the same concept modelled differently in different places. Junior instinct is "don't repeat yourself — one Customer class". Senior instinct is that DRY applies to knowledge, not to shapes that merely look similar.

Bounded contexts are also the best available guide to service boundaries — a service per context is a far better starting point than a service per entity.

How contexts relate

RelationshipMeans
Shared kernelTwo contexts share a small common model. Powerful but couples them — change needs both teams
Customer/SupplierDownstream context's needs influence upstream's roadmap
ConformistDownstream just accepts upstream's model as-is (common with third parties)
Anti-corruption layerDownstream translates the upstream model into its own. The safest option
Published languageA shared, versioned contract both sides agree on — e.g. integration events

The anti-corruption layer is the one to remember. It's the strategic version of the Adapter pattern: when you integrate with a legacy system or a vendor, you translate their model into yours at the boundary, so their concepts don't spread through your codebase.

Entities vs value objects 🔥 Must know

EntityValue object
IdentityHas an ID that persists through changeNo ID — it is its values
EqualitySame ID = same thingSame values = same thing
MutabilityUsually mutable (through methods)Always immutable
ExampleOrder, Customer, InvoiceMoney, Address, DateRange, Email

The test: if two of these had identical values, would they be the same thing?

  • Two £10 notes with the same value — interchangeable. Value object.
  • Two customers named "John Smith" at the same address — still two different people. Entity.
public readonly record struct Email
{
    public string Value { get; }

    public Email(string value)
    {
        if (!value.Contains('@')) throw new ArgumentException("Invalid email", nameof(value));
        Value = value.ToLowerInvariant();     // normalised once, here
    }
}

// Now this is impossible to get wrong:
public void Register(Email email, CustomerId id) { ... }

// instead of this, where the arguments can be swapped silently:
public void Register(string email, string id) { ... }

Two things this buys you. Validation happens once, in the constructor — so an invalid Email can't exist anywhere in the program. And the compiler stops you passing arguments in the wrong order, which is a real bug class when everything is string.

Aggregates 🔴 Advanced ⭐ Senior-level

Remember this

An aggregate is a consistency boundary — the set of objects that must be updated together, in one transaction, to keep a rule true.

It is not "a group of related objects". That's the mistake that produces huge aggregates.

public sealed class Order          // aggregate root
{
    private readonly List<OrderLine> _lines = [];

    public OrderId Id { get; }
    public OrderStatus Status { get; private set; }
    public IReadOnlyList<OrderLine> Lines => _lines;   // read-only outside

    // The invariant lives here, where it cannot be bypassed:
    // "an order may never exceed 50 lines and must have at least one to be placed"
    public void AddLine(Sku sku, int quantity, Money unitPrice)
    {
        if (Status != OrderStatus.Draft)
            throw new InvalidOperationException("Cannot modify a placed order.");
        if (_lines.Count >= 50)
            throw new InvalidOperationException("An order may not exceed 50 lines.");

        _lines.Add(new OrderLine(sku, quantity, unitPrice));
    }
}

Nothing outside the aggregate may hold a reference to an OrderLine or modify it directly. If it could, the "max 50 lines" rule would be unenforceable.

The four rules that make aggregates work

  1. One transaction, one aggregate. If you're saving two aggregates in one transaction, your boundaries are probably wrong — or you actually need eventual consistency between them.
  2. Reference other aggregates by ID, not by object. Order holds a CustomerId, not a Customer. This keeps aggregates small and prevents accidental loading of half the database.
  3. Keep them small. A big aggregate means more contention (everyone locks it) and slower loads. If a rule doesn't need two things updated together, they're separate aggregates.
  4. The root enforces all invariants. That's the point of having a root.
Common mistake — the aggregate that ate the domain

Modelling Customer as an aggregate containing all their orders, which contain all their lines, which reference all their products.

Loading a customer now loads thousands of rows. Two users editing unrelated orders for the same customer collide on the same optimistic concurrency token. Nothing scales.

Ask: what rule requires these to change together? If there isn't one, they're separate aggregates linked by ID.

When a rule spans two aggregates

This comes up constantly, and it's a good interview follow-up. Say the rule is "a customer may not have more than 5 open orders".

Three honest options:

OptionHowCost
Merge the aggregatesCustomer owns OrdersUsually far too big. Rarely right
Check in the application serviceQuery the count before creating the orderA race window between check and write — needs a unique constraint or lock to be safe
Accept eventual consistencyCreate the order, then a handler detects the violation and compensatesThe rule can be briefly violated. Often fine for business rules that aren't safety-critical

The senior answer is to ask how strictly the rule must hold. Many "rules" turn out to tolerate a few seconds of violation, which makes the design far simpler. Ones that don't — financial limits, seat allocation — need a real lock or a database constraint.

Domain events 🟡 Intermediate

One line: a record that something meaningful happened, named in the past tense.
public sealed record OrderPlaced(OrderId OrderId, CustomerId CustomerId, Money Total)
    : IDomainEvent;

public sealed class Order
{
    public void Place()
    {
        if (_lines.Count == 0) throw new InvalidOperationException("Cannot place an empty order.");
        Status = OrderStatus.Placed;
        Raise(new OrderPlaced(Id, CustomerId, Total));   // Order doesn't know who cares
    }
}

Why this matters: without events, Order.Place() would have to call the email service, the inventory service and the analytics service — coupling the domain to all of them. With events, the order just states what happened.

Domain events vs integration events ⭐ Senior-level

A distinction interviewers like, and people confuse:

Domain eventIntegration event
ScopeInside one bounded contextCrosses contexts / services
TransportIn-process dispatchMessage broker
ContentsCan carry domain objectsPrimitives only — it's serialized and versioned
CouplingInternal; change it freelyA public contract; changing it breaks consumers
DeliverySame process, same transaction (or just after)At-least-once, via an outbox

The usual pattern: a domain event fires internally, a handler decides whether it's externally interesting, and if so publishes an integration event. That keeps your internal model free to change without breaking other services.

Production trap

Publishing an integration event before the transaction commits. If the commit then fails, other services have reacted to something that never happened — and you can't unsend a message.

Publish after commit, and use the outbox pattern so the event and the state change are committed atomically.

When not to use DDD ⭐ Senior-level

Being able to say this clearly is worth more in an interview than reciting the patterns.

  • The domain is genuinely simple. If the logic is "validate, save, return", a rich model adds files without adding safety.
  • It's a reporting or data pipeline. Those want a functional, data-oriented approach — not aggregates.
  • Nobody has access to a domain expert. DDD's engine is the conversation with people who know the business. Without that, you're inventing a model and dressing it up in DDD vocabulary.
  • The team doesn't know it. Half-applied DDD — anaemic entities in a folder called "Domain" — gets you the ceremony and none of the benefit.

Note the asymmetry, though: even when tactical DDD isn't worth it, bounded contexts and ubiquitous language usually still are. Those cost almost nothing.

Key takeaways
  • Strategic DDD (contexts, language) is high value and cheap. Tactical DDD (aggregates) depends on complexity.
  • A bounded context is where a word has one meaning. Different contexts modelling the same thing differently is correct.
  • An aggregate is a consistency boundary. Ask "what rule forces these to change together?"
  • One transaction per aggregate; reference other aggregates by ID.
  • Entity = identity survives change. Value object = it is its values, and it's immutable.
  • Domain events are internal; integration events are a public contract sent via an outbox.

Common mistakes

  • Huge aggregates containing everything related, causing contention and slow loads.
  • Aggregates referencing each other by object, so loading one loads half the database.
  • Anaemic "domain" entities — properties only, all rules in services. That's a folder name, not DDD.
  • One shared model across contexts, producing a class with 47 columns that serves nobody.
  • Value objects that are mutable, which reintroduces every aliasing bug they existed to prevent.
  • Domain events published before commit, so handlers react to rolled-back changes.
  • DDD vocabulary applied to CRUD — repositories, aggregates and domain services around a five-table app.

Interview questions

What is an aggregate, and how do you decide its boundaries? ⭐ Senior-level
How I'd answer

"An aggregate is a consistency boundary — the group of objects that has to be updated together, in one transaction, to keep some rule true. The root is the only entry point, so the rule can't be bypassed."

"The key thing is that it's not 'a group of related objects'. That's the mistake that produces enormous aggregates. The question I ask is: what invariant requires these to change together? If I can't name one, they're separate aggregates."

"So an Order and its Lines are one aggregate, because rules like 'total must equal the sum of the lines' and 'max 50 lines' need them consistent at every moment. But Order and Customer are separate, even though they're obviously related — there's no rule requiring them to change in the same transaction. Order holds a CustomerId, not a Customer."

"That ID-reference rule matters practically. If aggregates reference each other by object, loading one drags in a graph, and your ORM either lazy-loads unpredictably or you fetch far too much."

"Size matters too, for reasons that show up in production. A big aggregate is a contention point — everyone editing anything about a customer collides on the same concurrency token. Smaller aggregates mean less locking and faster loads."

"And when a rule genuinely spans two aggregates — 'a customer may not have more than 5 open orders' — I'd first ask how strictly it must hold. Many business rules tolerate a few seconds of violation, and then eventual consistency with a compensating action is much simpler. If it must be exact, I'd enforce it with a database constraint or an explicit lock rather than pretending the aggregate boundary handles it."

What they're really checking
  • Do you know it's a consistency boundary, not a containment hierarchy?
  • Do you know the ID-reference rule and why it exists?
  • Can you handle the cross-aggregate rule question without hand-waving?
Weak answers
  • Red flag: "an aggregate groups related entities" — true but misses the point.
  • Red flag: making Customer an aggregate containing all their orders.
Likely follow-ups
  • How do you enforce a rule that needs data from another aggregate?
  • How does aggregate design affect optimistic concurrency?
  • Where do repositories fit — one per aggregate, or per entity?
What's a bounded context, and how does it relate to microservices?
How I'd answer

"A bounded context is a boundary inside which every term has exactly one meaning. Outside it, the same word can mean something different — and that's fine."

"The example I'd give is 'customer'. In Sales it's a prospect with a pipeline stage and an assigned rep. In Billing it's a party that owes money, with a payment method and a credit limit. In Support it's a person raising tickets. Same real-world person, three genuinely different models."

"The instinct is to build one shared Customer class. That produces something with fifty columns that serves nobody well, changes for three different reasons, and forces three teams to coordinate on every change. Three small models linked by a customer ID is better — and that's not duplication, because they encode different knowledge."

"On microservices: bounded contexts are the best available guide to service boundaries. A service per context tends to work, because a context is already a place where the language and the rules are coherent — which usually means the data and the team are too."

"But I'd be careful about the reverse claim. Identifying a context doesn't mean you should deploy it separately. Contexts are a modelling boundary; services are a deployment boundary. You can have five bounded contexts in one modular monolith, which is often exactly the right answer — you get the modelling clarity without distributed cost."

What they're really checking
  • Do you understand contexts as a language boundary, not just a module?
  • Are you comfortable with the same concept modelled differently?
  • Do you separate modelling boundaries from deployment boundaries?
Likely follow-ups
  • How do two contexts share data without coupling?
  • What's an anti-corruption layer and when have you used one?
  • What if a single business process spans four contexts?
When would you NOT use DDD?
How I'd answer

"I'd split the answer, because the two halves of DDD have very different costs."

"The tactical patterns — aggregates, value objects, domain services, repositories — I'd skip when the domain is genuinely simple. If the logic is validate-save-return, a rich domain model adds files without adding safety. Same for reporting and data pipelines, which want a functional data-oriented approach, not aggregates."

"I'd also skip it if there's no access to a domain expert. The engine of DDD is the conversation with people who actually know the business. Without that you're inventing a model and dressing it in DDD vocabulary, which is the worst of both."

"And I'd be wary if the team doesn't know it. Half-applied DDD — anaemic entities in a folder called Domain, repositories that are just DbSet wrappers — gets you the ceremony and none of the benefit, and it's harder to unwind than plain code."

"But the strategic side is different. Bounded contexts and ubiquitous language cost almost nothing and pay off even on a small CRUD app. Agreeing that 'account' means three different things, and naming them accordingly, is just good engineering. So my honest position is: use the strategic thinking almost always, and use the tactical patterns where the invariants justify them."

What they're really checking
  • Can you criticise a methodology you also know well?
  • Do you distinguish the strategic and tactical halves?
  • Do you recognise half-applied DDD as a real failure mode?
Weak answers
  • Red flag: "DDD is always better" — dogma.
  • Red flag: equating DDD with "having a Domain folder".
Likely follow-ups
  • You join a team with a "Domain" project full of property bags. What do you do?
  • How do you introduce ubiquitous language without a big process change?
