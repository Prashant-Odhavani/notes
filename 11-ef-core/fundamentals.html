DbContext & Change Tracking

Understand the change tracker and most confusing EF behaviour stops being confusing.

🟢 Beginner 🟡 Intermediate 🔥 Must know
Quick revision
  • DbContext is scoped — one per request. Not thread-safe, and it accumulates state.
  • It's a unit of work. Nothing hits the database until SaveChanges.
  • Five entity states: Detached, Unchanged, Added, Modified, Deleted.
  • Tracked entities are compared against a snapshot — that's how EF knows what changed.
  • AsNoTracking for read-only queries. Less memory, less CPU, faster.
  • Identity resolution: a tracked context returns the same object instance for the same key — and ignores newer database values.
  • SaveChanges is a single transaction whether you asked for one or not.

DbContext is a unit of work 🔥 Must know

Think of it this way

A shopping basket. You add things, remove things, change quantities — and none of it reaches the shop's systems.

SaveChanges is the checkout: one atomic operation that either completes entirely or not at all.

var order = await db.Orders.FirstAsync(o => o.Id == id);  // 1 SELECT

order.Status = OrderStatus.Shipped;      // in memory only
order.ShippedUtc = DateTime.UtcNow;      // in memory only
db.OrderLines.Add(newLine);              // in memory only
db.Remove(oldLine);                      // in memory only

await db.SaveChangesAsync();             // ONE transaction: UPDATE, INSERT, DELETE
Remember this

SaveChanges always runs in a transaction, even if you never wrote BeginTransaction.

So one SaveChanges is atomic. Two SaveChanges calls are two transactions — and that's where people accidentally lose atomicity.

Why it's scoped 🔥 Must know

builder.Services.AddDbContext<AppDbContext>(options =>
    options.UseSqlServer(connectionString));
// Registers AppDbContext as SCOPED - one instance per HTTP request
LifetimeResult
Scoped ✅One per request. Changes within a request share a unit of work; disposed at the end
Singleton ❌Broken. Not thread-safe, and the tracker grows forever — a memory leak plus concurrency exceptions
Transient ⚠️Works, but two services in one request get different contexts, so they can't participate in the same SaveChanges
The two reasons a singleton DbContext fails

1. It isn't thread-safe. Two concurrent requests using the same context produce "A second operation was started on this context instance before a previous operation completed" — the most common EF exception there is, and almost always caused by either a singleton context or a missing await.

2. The change tracker never empties. Every entity ever loaded stays referenced, so memory grows without bound and SaveChanges gets slower over time because it re-scans everything. Eventually you also get key conflicts between unrelated requests.

When scoped doesn't fit

builder.Services.AddDbContextFactory<AppDbContext>(o => o.UseSqlServer(cs));

public class Worker(IDbContextFactory<AppDbContext> factory) : BackgroundService
{
    protected override async Task ExecuteAsync(CancellationToken ct)
    {
        while (!ct.IsCancellationRequested)
        {
            // A fresh context per iteration - fresh tracker, no accumulation
            await using var db = await factory.CreateDbContextAsync(ct);
            // ... work ...
            await Task.Delay(TimeSpan.FromMinutes(1), ct);
        }
    }
}
Why a factory rather than a scope

A background service is a singleton, so it can't inject a scoped DbContext — the container will refuse, and rightly so.

You can create a scope manually with IServiceScopeFactory, and that's fine. But IDbContextFactory is clearer when the context is all you need, and it's the only sane option for parallel work: each parallel branch needs its own context, because a single one can't be shared across concurrent operations.

How EF knows what changed

When a tracked entity is loaded, EF stores a snapshot of its original values.

At SaveChanges, it compares current values against that snapshot. Differences become the SET clause.

That's why you never call an "update" method — mutating a tracked object is enough.

var order = await db.Orders.FindAsync(id);   // tracked, snapshot stored
order.Status = OrderStatus.Shipped;          // now Modified
await db.SaveChangesAsync();                 // UPDATE [Order] SET Status=@p WHERE Id=@id

The Update() trap 🟡 Intermediate

var dto = await Request.ReadFromJsonAsync<OrderDto>();

var order = new Order { Id = dto.Id, Status = dto.Status };
db.Orders.Update(order);          // ALL columns marked Modified
await db.SaveChangesAsync();
// UPDATE sets every column - including ones the client never sent,
// overwriting them with default values.
var order = await db.Orders.FindAsync(dto.Id);
if (order is null) return NotFound();

order.Status = dto.Status;        // only this column ends up in the UPDATE
await db.SaveChangesAsync();
Why this causes real data loss

Update() on a detached entity marks every property as modified, because EF has no snapshot to compare against — it has to assume everything changed.

So a partial DTO wipes out every field it didn't include. Values become null or 0, and the operation looks entirely successful.

This is the most common serious EF Core bug in API code, and it maps exactly to the PUT vs PATCH distinction — a partial update needs partial semantics all the way down.

If you must update without loading, set individual properties as modified: db.Entry(order).Property(o => o.Status).IsModified = true;

Tracking vs no-tracking 🔥 Must know

// Tracked: snapshot per entity, entity kept in the tracker
var orders = await db.Orders.ToListAsync();

// Not tracked: no snapshot, no tracker entry
var report = await db.Orders.AsNoTracking().ToListAsync();

Remember this

If you're not going to change it, don't track it.

Typical gain is 10–30% on read-heavy queries — larger on big result sets, because you skip building a snapshot per row.

Even better: project into a DTO. A projection is automatically untracked, selects fewer columns, and can be served by a covering index. That's usually the bigger win.

// Selects 3 columns, no tracking, no entity materialisation
var summaries = await db.Orders
    .Where(o => o.CustomerId == customerId)
    .Select(o => new OrderSummary(o.Id, o.CreatedUtc, o.Total))
    .ToListAsync();
Making no-tracking the default
options.UseQueryTrackingBehavior(QueryTrackingBehavior.NoTracking);

Defensible for a read-heavy API, and you then opt in with .AsTracking() where you intend to modify.

The risk is that someone loads an entity, changes it, calls SaveChanges, and nothing happens — silently. No exception, no update. That's a nasty bug class, so it's a decision to make deliberately and document, not a default to flip casually.

Identity resolution 🔴 Advanced

In simple terms

A tracking context keeps one object instance per primary key.

Query for the same row twice and you get the same object back — not two copies.

var a = await db.Orders.FirstAsync(o => o.Id == 1);
a.Status = OrderStatus.Cancelled;             // local change, not saved

var b = await db.Orders.FirstAsync(o => o.Id == 1);   // hits the database again

Console.WriteLine(ReferenceEquals(a, b));     // True  - same instance
Console.WriteLine(b.Status);                  // Cancelled - the LOCAL value
The rule that catches people

EF does execute the second query. But when materialising the result it finds the key is already tracked, so it keeps your in-memory values and discards the database ones.

That's correct — losing your unsaved changes would be worse — but it means a long-lived context can serve stale data indefinitely.

To force a refresh: await db.Entry(a).ReloadAsync(), or use AsNoTracking(), or use a new context. And this is another argument for scoped lifetime: a short-lived context can't go stale.

The flip side: AsNoTracking duplicates objects

Without tracking there's no identity map, so loading 100 orders that all belong to one customer with Include(o => o.Customer) materialises 100 separate Customer objects.

Usually harmless. It matters if you're comparing references, mutating them, or the object is large enough that 100 copies is real memory. AsNoTrackingWithIdentityResolution() gives you an identity map without full change tracking — the middle option most people don't know exists.

What SaveChanges does 🟡 Intermediate

  1. Detect changes — compare every tracked entity against its snapshot.
  2. Order the operations by foreign-key dependencies, so parents insert before children.
  3. Open a transaction (unless one is already open).
  4. Execute the statements, batched where the provider supports it.
  5. Read back generated values — identity keys, computed columns, rowversion.
  6. Commit, then mark everything Unchanged and refresh snapshots.
Two consequences worth knowing

Batching is real. EF Core batches multiple statements into one round trip — up to a provider limit. Adding 50 entities is a handful of round trips, not 50. That's why AddRange then one SaveChanges beats a loop with SaveChanges inside.

Dependency ordering is free. Add a parent and child in one go and EF works out that the parent must be inserted first, then uses the generated key for the child. Doing that by hand is real work, and it's one of the strongest arguments for an ORM on the write path.

foreach (var item in items)          // 1000 items
{
    db.Orders.Add(item);
    await db.SaveChangesAsync();     // 1000 round trips, 1000 transactions
}
db.Orders.AddRange(items);
await db.SaveChangesAsync();
But don't take it too far

One SaveChanges with 500,000 entities is also wrong — the change tracker holds all of them, change detection becomes O(n) over a huge set, and the transaction and log grow enormous.

For genuinely large volumes, batch in chunks of a few thousand with a fresh context per chunk, or use bulk operations. The sweet spot is "batched, but bounded".

Hooking into SaveChanges 🔴 Advanced

public class AuditInterceptor(IUserContext user) : SaveChangesInterceptor
{
    public override ValueTask<InterceptionResult<int>> SavingChangesAsync(
        DbContextEventData e, InterceptionResult<int> result, CancellationToken ct = default)
    {
        var ctx = e.Context;
        if (ctx is null) return base.SavingChangesAsync(e, result, ct);

        foreach (var entry in ctx.ChangeTracker.Entries<IAuditable>())
        {
            if (entry.State == EntityState.Added)
            {
                entry.Entity.CreatedUtc = DateTime.UtcNow;
                entry.Entity.CreatedBy  = user.UserId;
            }
            else if (entry.State == EntityState.Modified)
            {
                entry.Entity.ModifiedUtc = DateTime.UtcNow;
                entry.Entity.ModifiedBy  = user.UserId;
            }
        }
        return base.SavingChangesAsync(e, result, ct);
    }
}

Register with options.AddInterceptors(...). This is the right home for audit stamps, soft deletes and outbox writes — anything that must happen on every save and would otherwise be duplicated in every handler.

Key takeaways
  • DbContext is a unit of work — a notepad, not a live connection.
  • Scoped lifetime. Singleton breaks on thread safety and unbounded tracker growth.
  • IDbContextFactory for background services and parallel work.
  • Five states; EF derives them by comparing against a snapshot.
  • Mutating a tracked entity is enough — no Update() call.
  • Update() on a detached entity marks every column modified and silently wipes fields.
  • AsNoTracking for reads; projection into a DTO is usually better still.
  • Identity resolution keeps your local values and discards fresher database ones.
  • One SaveChanges = one transaction, with batching and FK ordering handled.
  • Interceptors are the place for cross-cutting save behaviour.

Common mistakes

  • Singleton DbContext, causing concurrency exceptions and memory growth.
  • Injecting a scoped context into a singleton such as a background service.
  • Update() with a partial DTO, overwriting unsent fields.
  • SaveChanges inside a loop.
  • Tracking read-only queries that feed an API response.
  • Two SaveChanges calls where atomicity was required.
  • Expecting a re-query to return fresh data for an already-tracked entity.
  • Missing await — producing the "second operation started" error on a correctly-scoped context.
  • Loading tens of thousands of entities into one context.
  • EnableSensitiveDataLogging in production.

Interview questions

Basic

Why is DbContext registered as scoped? 🔥 Must know
How I'd answer

"Two hard reasons and one design reason."

"It isn't thread-safe. One DbContext can't handle concurrent operations. As a singleton, two simultaneous requests produce 'a second operation was started on this context instance before a previous operation completed' — which is probably the most commonly seen EF exception."

"The change tracker accumulates. Every entity loaded stays referenced for the life of the context. A singleton therefore leaks memory indefinitely, and SaveChanges gets progressively slower because change detection has to scan everything it's ever seen."

"And scoped matches the unit-of-work model. A web request is naturally one unit of work — several services can share the same context, make their changes, and one SaveChanges commits them atomically. Transient would give each service its own context, so they couldn't participate in the same transaction."

"Where scoped doesn't fit is background services, because those are singletons and the container correctly refuses to inject a scoped dependency into one. There I'd use IDbContextFactory and create a context per unit of work — which also means a fresh tracker each iteration rather than one growing forever."

"Same applies to parallel work: if I'm processing items concurrently, each branch needs its own context, because one can't be shared across concurrent operations."

"One thing worth adding: the 'second operation' error also happens on a correctly-scoped context if someone forgets an await, so two operations overlap within the same request. Same symptom, different cause — worth checking both."

What they're really checking
  • Do you know both reasons — thread safety and tracker growth?
  • Do you know what to do in a background service?
  • Do you connect it to the unit-of-work idea?
Likely follow-ups
  • How do you use EF in a background service?
  • What if two services in one request both need to save?
  • What's context pooling?

Intermediate

What does AsNoTracking do, and when would you use it? 🔥 Must know
How I'd answer

"By default EF tracks every entity a query returns — it stores a snapshot of the original values and keeps the entity in the change tracker, so that when I mutate a property it can work out what changed at SaveChanges."

"That's essential if I'm going to modify the entity, and pure overhead if I'm not. AsNoTracking skips the snapshot and the tracker entry."

"So I'd use it for anything read-only: API responses, reports, dropdown lists, exports. Typically 10–30% faster, and more on large result sets because you're not building a snapshot per row."

"But the better answer for most read paths is projection — Select into a DTO. That's automatically untracked, and it also selects fewer columns, which means less network traffic and the possibility of the query being served entirely by a covering index. So projection usually beats AsNoTracking on a full entity, and I'd reach for it first."

"There's a behavioural difference worth knowing, not just a performance one. Tracking gives you identity resolution — one object instance per primary key. Without tracking there's no identity map, so if I load 100 orders that all belong to the same customer with Include, I get 100 separate Customer objects rather than 100 references to one. Usually harmless, but it matters if I'm comparing references or the object is large. AsNoTrackingWithIdentityResolution gives you the identity map without full change tracking, which is the middle option people tend not to know about."

"You can make no-tracking the default with UseQueryTrackingBehavior, and for a read-heavy API that's defensible. The risk is that someone loads an entity, modifies it, calls SaveChanges, and nothing happens — silently, no exception. That's a nasty bug class, so I'd only do it as a deliberate, documented decision."

What they're really checking
  • Do you know it's the snapshot that's being skipped?
  • Do you know projection is usually better?
  • Do you know about identity resolution as a behavioural difference?
Likely follow-ups
  • Does AsNoTracking change the SQL?
  • What breaks if you make it the global default?
  • How would you measure the difference?
A PUT endpoint uses db.Update(entity) and fields are being wiped. Why? ⭐ Senior-level
How I'd answer

"Because Update() on a detached entity marks every property as modified."

"EF has no snapshot for a detached entity — it never loaded it, so it has nothing to compare against. It has to assume everything changed, so the generated UPDATE sets every column."

"So if the client sent a partial payload and the code constructed a new entity from it, every field the client didn't send is at its CLR default — null, 0, DateTime.MinValue — and those defaults get written over the real data. And it looks entirely successful: no exception, no warning."

"The fix I'd default to is load, then assign. Fetch the tracked entity, set only the properties the request actually changes, and call SaveChanges. EF compares against the snapshot and generates an UPDATE containing only the changed columns. Costs one extra SELECT, and that's almost always worth it — it also gives you a natural not-found check and a place to enforce authorisation on the existing row."

"If I genuinely need to avoid the read — a hot path, or a high-volume update — I'd attach and mark specific properties: db.Attach(e); db.Entry(e).Property(x => x.Status).IsModified = true;. Explicit about what's changing, single round trip."

"There's a broader point here: this is the PUT versus PATCH distinction showing up in the data layer. Update() has PUT semantics — full replacement. If the API is really doing a partial update, then the whole stack needs partial semantics, and using Update() is a mismatch between what the endpoint promises and what the persistence layer does."

"I'd also add optimistic concurrency here while I'm at it — a rowversion column — so two concurrent edits don't silently overwrite each other. That's the same class of bug: a lost update that nothing reports."

What they're really checking
  • Do you know why — no snapshot, so everything is assumed modified?
  • Do you know the load-then-assign fix and its cost?
  • Do you know the explicit IsModified alternative?
  • Bonus: do you connect it to PUT vs PATCH and to lost updates?
Weak answers
  • Red flag: "always use Update" with no awareness.
  • Red flag: not knowing what a snapshot is.
Likely follow-ups
  • How would you implement PATCH properly?
  • What SQL does each version generate?
  • How does rowversion fit in?
