Entity Framework Core

The default data-access layer in .NET, and the most common source of production performance problems. Both facts are worth understanding.

🟡 Intermediate 🔥 Must know

The mental model that prevents most EF bugs 🔥 Must know

In simple terms

EF Core does two distinct jobs, and almost every confusing behaviour comes from mixing them up:

  1. It translates LINQ into SQL. Your C# query becomes a database query.
  2. It tracks objects in memory and works out the INSERT, UPDATE and DELETE statements needed to make the database match.
Think of it this way

The DbContext is a notepad, not a live connection to the database.

You load some rows onto the notepad. You scribble changes. Nothing happens in the database.

Then you call SaveChanges, and EF reads the notepad, works out what changed, and sends the minimum set of statements to make it so.

Remember this

Three questions answer most EF Core problems:

  1. Is this running in the database or in memory? — explains performance surprises.
  2. Is this entity tracked? — explains why SaveChanges did nothing, or did too much.
  3. How many queries did that just make? — explains almost everything else.

Version context

Content targets EF Core 8/9. Where a feature arrived in a specific version it's named — ExecuteUpdate/ExecuteDelete in EF Core 7, complex types and primitive collections in 8, LeftJoin/RightJoin operators in 10.

Two behaviours that changed and still cause confusion: client-side evaluation of WHERE clauses was removed in EF Core 3.0 — it now throws instead of silently loading the table — and EF Core 3.0 stopped generating implicit ToList() boundaries. If someone describes EF behaviour that doesn't match what you see, they may be remembering EF6 or EF Core 2.

The position worth holding

These aren't competitors. Use EF Core for the write side and Dapper for awkward reads.

Change tracking is genuinely valuable when you're mutating an object graph. It's pure overhead when you're producing a read-only report — and that's exactly where hand-written SQL wins.

They can share the same connection and transaction, so mixing them costs nothing architecturally.

EF Core is a leaky abstraction, and that's fine ⭐ Senior-level

The honest framing

EF Core hides SQL, but it cannot hide the database. Indexes, execution plans, transactions and locking all still apply.

So you can't use EF Core well without understanding the database underneath. Every serious EF problem is really a database problem wearing a C# costume.

Looks like an EF problemIs actually
"EF is slow"An N+1 pattern, or a missing index
"Include returns way too much data"A cartesian explosion from multiple collection includes
"Saving takes forever"Thousands of round trips instead of a set-based statement
"Random timeouts under load"Lock contention, or a long-running transaction
"It worked in dev"Dev has 200 rows; production has 8 million
The habit that makes you good at EF Core

Log the SQL in development and read it.

options.UseSqlServer(cs)
       .LogTo(Console.WriteLine, LogLevel.Information)
       .EnableSensitiveDataLogging();     // DEV ONLY - logs parameter values

Most EF performance problems are obvious within seconds of seeing the generated SQL, and invisible otherwise. Developers who look at the SQL write dramatically better EF code than those who don't — it's the single highest-leverage habit in this section.

EnableSensitiveDataLogging must never be on in production: it writes parameter values, which means personal data and secrets in your logs.

Would you use an ORM at all? ⭐ Senior-level
How I'd answer

"Yes, for most of an application — and I'd expect to drop out of it in specific places rather than treat that as a failure."

"What EF Core is genuinely good at is the write side. Loading an object graph, mutating it, and having the right INSERTs and UPDATEs worked out in dependency order is real work that I don't want to hand-write. Migrations are the other big one — having schema changes versioned alongside the code that needs them is worth a lot."

"Where it's weaker is complex reads. A reporting query with several aggregates and window functions is easier to write, read and tune as SQL. And EF can generate awkward SQL for it — not wrong, but not what I'd have written."

"So my default shape is EF Core for the domain and CRUD, and Dapper or raw SQL for reporting and the few hot read paths. They can share a connection and transaction, so there's no architectural cost to mixing them."

"The thing I'd be clear about is that EF Core doesn't remove the need to understand the database. It hides SQL; it doesn't hide indexes, execution plans, transactions or locking. Nearly every 'EF is slow' problem I've dealt with was an N+1 pattern, a missing index, or a cartesian explosion from multiple collection includes — database problems in C# clothing."

"The failure mode I'd watch for is treating it as a black box. Teams that never look at the generated SQL ship queries that load whole tables to filter three rows. Turning on SQL logging in development is a cheap habit that prevents most of it."

What they're really checking
  • Do you have a reasoned position rather than a preference?
  • Do you know where an ORM is weak?
  • Do you know EF doesn't excuse you from knowing SQL?
Likely follow-ups
  • Give an example of SQL you'd rather write by hand.
  • How do you share a transaction between EF and Dapper?
  • What's the cost of change tracking?
