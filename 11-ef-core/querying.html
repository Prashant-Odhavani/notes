Querying & Loading Strategies

How you load related data determines whether a page takes 50ms or 8 seconds. This is the highest-value EF Core page.

🟡 Intermediate 🔴 Advanced 🔥 Must know
Quick revision
  • Three loading strategies: eager (Include), lazy (on property access), explicit (Load).
  • Lazy loading causes N+1 — the single biggest EF performance problem.
  • Two or more collection Includes cause a cartesian explosion. Fix with AsSplitQuery.
  • IQueryable is deferred. Nothing executes until you enumerate it.
  • Project into a DTO instead of Include-ing whole entities where you can.
  • EF Core 3.0+ throws rather than silently evaluating a WHERE clause in memory.
  • Global query filters handle soft delete and multi-tenancy in one place.

Deferred execution 🔥 Must know

In simple terms

An IQueryable is a description of a query, not a result.

Nothing runs until you enumerate it — ToList, First, Count, Any, or a foreach.

var query = db.Orders.Where(o => o.Status == OrderStatus.Open);   // no SQL yet

if (customerId.HasValue)
    query = query.Where(o => o.CustomerId == customerId);          // still no SQL

if (from.HasValue)
    query = query.Where(o => o.CreatedUtc >= from);                // still no SQL

var results = await query
    .OrderByDescending(o => o.CreatedUtc)
    .Take(50)
    .ToListAsync();          // NOW one SQL statement with all of it
The trap: enumerating too early
var orders = db.Orders.ToList()                    // loads the WHOLE table
                     .Where(o => o.Total > 1000)   // filters in memory
                     .ToList();
var orders = await db.Orders
    .Where(o => o.Total > 1000)      // filters in SQL
    .ToListAsync();

Once you call ToList, you're holding List<T> — everything after that is LINQ to Objects running in your process.

Same trap with AsEnumerable(), and with returning IEnumerable<T> from a repository method: the caller adding .Where(...) is now filtering in memory, and there is no warning at all. Return IQueryable<T> or a finished result — not IEnumerable<T>.

Remember this

The question to ask about every LINQ line: is this running in SQL Server or in my process?

IQueryable → database. IEnumerable → memory. That's the whole distinction, and it explains most EF performance surprises.

Eager loading

var order = await db.Orders
    .Include(o => o.Customer)                 // reference
    .Include(o => o.Lines)                    // collection
        .ThenInclude(l => l.Product)          // nested
    .FirstOrDefaultAsync(o => o.Id == id);
var customer = await db.Customers
    .Include(c => c.Orders.Where(o => o.CreatedUtc >= cutoff)
                          .OrderByDescending(o => o.CreatedUtc)
                          .Take(10))
    .FirstAsync(c => c.Id == id);
Filtered include gotcha

The collection on the returned entity contains only the filtered subset, but it's marked as loaded. So any code that later treats customer.Orders as "all this customer's orders" is now silently wrong.

Fine when the entity is going straight into a response. Risky if it flows into domain logic that calculates a total. In that situation, project instead.

Lazy loading, and why to avoid it

// requires Microsoft.EntityFrameworkCore.Proxies
options.UseLazyLoadingProxies();

// and every navigation must be virtual
public virtual Customer Customer { get; set; } = null!;
var orders = await db.Orders.Take(1000).ToListAsync();   // 1 query

foreach (var o in orders)
    Console.WriteLine(o.Customer.Name);                  // 1000 more queries
Why lazy loading is genuinely dangerous

The database access is invisible. o.Customer.Name is a property read. Nothing in the code suggests a network round trip, so it survives every code review.

It's fine in development. 20 test rows means 20 fast queries. Production has 10,000 rows and the endpoint times out.

It breaks after disposal. Access a navigation after the DbContext is disposed — very easy if entities are returned from a service — and you get ObjectDisposedException.

It serialises unpredictably. A JSON serializer walking navigations triggers loads for everything it touches, so one response can fire hundreds of queries.

My position: leave it off. An explicit Include that's slightly verbose beats an invisible query. If a navigation is null when you needed it, you get a clear NullReferenceException at development time rather than a silent performance cliff in production.

Explicit loading

var order = await db.Orders.FindAsync(id);

if (includeLines)
    await db.Entry(order).Collection(o => o.Lines).LoadAsync();

if (includeCustomer)
    await db.Entry(order).Reference(o => o.Customer).LoadAsync();

// Or query the navigation without materialising it
var lineCount = await db.Entry(order).Collection(o => o.Lines).Query().CountAsync();

Useful for conditional loading driven by a request parameter, and the .Query() form lets you count or filter a navigation without loading it into memory at all.

Cartesian explosion 🔥 Must know

The problem in one sentence

Two collection Includes in one query produce rows × rows, because SQL has no way to return two independent lists in one result set.

var order = await db.Orders
    .Include(o => o.Lines)        // 50 lines
    .Include(o => o.Payments)     // 10 payments
    .Include(o => o.Shipments)    // 5 shipments
    .FirstAsync(o => o.Id == id);

// The JOIN returns 50 x 10 x 5 = 2,500 rows.
// Every Order column is repeated 2,500 times.
// EF de-duplicates them back to 65 objects - after transferring all of it.
Why SQL does this

You ask for one customer's phone numbers and their email addresses in a single table.

The only way to fit both lists into one flat grid is to pair every phone number with every email address. Three phones and four emails become twelve rows.

The data is all there — but you've transferred twelve rows to convey seven facts.

var order = await db.Orders
    .Include(o => o.Lines)
    .Include(o => o.Payments)
    .Include(o => o.Shipments)
    .AsSplitQuery()               // 4 queries, 66 rows total
    .FirstAsync(o => o.Id == id);
Single querySplit query
Round tripsOneOne per collection
Rows transferredMultipliedSum, not product
ConsistencyAtomic snapshotSeparate queries — data can change between them
Best forOne collection, or small onesMultiple or large collections
Senior signal — the consistency trade-off

Split queries aren't strictly better. They run as separate statements, so unless you're inside an explicit transaction with a suitable isolation level, another transaction can modify the data between them — giving you an order whose lines and payments come from different moments.

In practice that's rarely material for display data, and I'd default to split for multiple collections because the row multiplication is a much bigger practical risk. But knowing the trade exists, and that it's fixable with a transaction where it matters, is the discriminating answer.

You can set it globally with o.UseQuerySplittingBehavior(QuerySplittingBehavior.SplitQuery) and opt out per query with AsSingleQuery().

Often the better answer: don't include at all
var vm = await db.Orders
    .Where(o => o.Id == id)
    .Select(o => new OrderViewModel
    {
        Id           = o.Id,
        CustomerName = o.Customer.Name,            // JOIN, one column
        LineCount    = o.Lines.Count(),            // aggregate in SQL
        Total        = o.Lines.Sum(l => l.Total),  // aggregate in SQL
        Lines        = o.Lines.Select(l => new LineDto(l.Sku, l.Quantity)).ToList()
    })
    .FirstOrDefaultAsync();

This selects exactly the columns needed, computes the aggregates in the database instead of loading rows to count them, and returns nothing tracked.

Most cartesian-explosion problems are really "we loaded entities when we needed a view model". Projection is the fix that also solves three other problems at once.

What EF can and can't translate 🟡 Intermediate

// A custom C# method - EF has no idea what it does
var results = await db.Orders
    .Where(o => IsHighValue(o))          // InvalidOperationException
    .ToListAsync();

// Some framework methods have no SQL equivalent
.Where(o => o.Sku.Equals(sku, StringComparison.OrdinalIgnoreCase))   // throws
// Inline the predicate
.Where(o => o.Total > 1000 && o.Status == OrderStatus.Open)

// Or a reusable expression
private static readonly Expression<Func<Order, bool>> HighValue =
    o => o.Total > 1000 && o.Status == OrderStatus.Open;

var results = await db.Orders.Where(HighValue).ToListAsync();
EF Core 3.0 changed this deliberately

EF Core 2.x would silently give up, load the whole table, and evaluate your WHERE clause in memory. Correct results, catastrophic performance, no warning at all.

EF Core 3.0 throws instead. That felt like a regression to some teams and was absolutely the right call — a loud failure at development time beats a silent table scan in production.

Client evaluation is still allowed in the final Select projection, where it's harmless because the data has already been reduced. So .Select(o => new { Label = FormatLabel(o.Total) }) works fine.

Dropping to SQL 🟡 Intermediate

// Returns mapped entities; composable with LINQ
var orders = await db.Orders
    .FromSql($"SELECT * FROM [Order] WHERE Total > {threshold}")
    .Where(o => o.Status == OrderStatus.Open)      // added as an outer query
    .ToListAsync();

// Non-entity result type (EF Core 8+)
var report = await db.Database
    .SqlQuery<RevenueRow>($"EXEC dbo.usp_Revenue @from = {from}, @to = {to}")
    .ToListAsync();

// Set-based command, no entities involved
var affected = await db.Database.ExecuteSqlAsync(
    $"UPDATE [Order] SET Status = 'Archived' WHERE CreatedUtc < {cutoff}");
FromSql vs FromSqlRaw — this matters

FromSql takes a FormattableString. The interpolated values become SQL parameters automatically, so it's injection-safe by construction — the interpolation syntax is a little misleading here, but the values never become part of the SQL text.

FromSqlRaw takes a plain string. Interpolating user input into it is a SQL injection vulnerability, exactly as in ADO.NET.

Use FromSql unless you genuinely need dynamic SQL, and if you do, pass values as explicit SqlParameters and whitelist any identifiers.

ExecuteSql bypasses the change tracker

A raw UPDATE or DELETE doesn't go through EF's tracking, so entities already loaded in the context still hold the old values — and a subsequent SaveChanges can write them back over your change.

Same applies to ExecuteUpdate and ExecuteDelete. Use them on a context that hasn't loaded the affected entities, or reload afterwards. This is a genuinely confusing bug when you hit it.

Global query filters 🔴 Advanced

protected override void OnModelCreating(ModelBuilder b)
{
    b.Entity<Order>().HasQueryFilter(o => !o.IsDeleted && o.TenantId == _tenantId);
}

// Every query on Order now includes those predicates automatically.
// To bypass for an admin or repair tool:
var all = await db.Orders.IgnoreQueryFilters().ToListAsync();
Good forWatch out for
Soft delete — no more forgotten !IsDeletedThe filter is invisible, so "the row exists but the query returns nothing" is confusing until you know
Multi-tenancy — a missed filter is a data leak, so centralising it is a security winFilters don't apply to Find by key, or to raw SQL
Consistency across every queryA required navigation to a filtered-out row can throw
Senior signal — the tenant-id capture bug

The filter expression is compiled into the model, and the model is cached per context type — not per instance.

So capturing _tenantId in the filter only works if the field is read at query time rather than baked in at model build. Get this wrong and one tenant's filter gets applied to another tenant's requests — a cross-tenant data leak that appears only under concurrency.

The safe pattern is to reference a field on the context instance (EF re-reads it per query), and to configure the model cache key with IModelCacheKeyFactory if the filter shape itself varies. Being aware that model caching interacts with this is exactly the kind of detail that separates people who've shipped multi-tenant EF from people who've read about it.

And I'd still enforce tenancy at the database level too — Row-Level Security — because a filter you can call IgnoreQueryFilters() on isn't a security boundary.

Pagination 🟡 Intermediate

var page = await db.Orders
    .Where(o => o.CustomerId == id)
    .OrderByDescending(o => o.CreatedUtc)
    .ThenByDescending(o => o.Id)               // tiebreaker - mandatory
    .Skip((pageNumber - 1) * pageSize)
    .Take(pageSize)
    .Select(o => new OrderListItem(o.Id, o.CreatedUtc, o.Total))
    .ToListAsync();
var page = await db.Orders
    .Where(o => o.CustomerId == id)
    .Where(o => o.CreatedUtc < lastCreated
             || (o.CreatedUtc == lastCreated && o.Id < lastId))
    .OrderByDescending(o => o.CreatedUtc).ThenByDescending(o => o.Id)
    .Take(pageSize)
    .ToListAsync();
Two pagination requirements people forget

A tiebreaker in OrderBy is mandatory. Without it, rows with equal sort values can appear on two pages or on none — and it's intermittent, so it passes testing.

Skip gets slower as the offset grows, because the database reads and discards every skipped row. Page 5,000 reads 100,000 rows to return 20. For feeds and infinite scroll, use keyset. See the SQL page for the mechanics.

Key takeaways
  • IQueryable is deferred and runs in SQL; IEnumerable runs in memory.
  • Never return IEnumerable<T> from a data-access method.
  • Eager loading by default. Lazy loading hides queries and causes N+1.
  • Multiple collection includes multiply rows. AsSplitQuery, or better, project.
  • Split queries lose the atomic snapshot — usually acceptable, worth knowing.
  • Projection solves row bloat, tracking cost and over-fetching at once.
  • EF Core 3.0+ throws on untranslatable WHERE clauses rather than silently scanning.
  • FromSql parameterises; FromSqlRaw does not.
  • ExecuteUpdate/ExecuteDelete bypass the change tracker.
  • Global query filters centralise soft delete and tenancy, but aren't a security boundary.

Common mistakes

  • Lazy loading enabled, producing N+1 that nothing in the code reveals.
  • ToList() then Where() — filtering in memory.
  • Returning IEnumerable<T> from a repository.
  • Several collection Includes with no AsSplitQuery.
  • Include-ing whole entities to render three fields.
  • Loading a collection to .Count it instead of counting in SQL.
  • FromSqlRaw with interpolated user input — SQL injection.
  • ExecuteUpdate on entities the context has already loaded.
  • No tiebreaker in paged OrderBy.
  • Deep Skip on large tables.
  • Returning entities from a controller, letting the serializer walk navigations.

Interview questions

Intermediate

Explain the N+1 problem and how you'd fix it. 🔥 Must know
How I'd answer

"N+1 is one query to fetch a list, then one more query per item in that list to fetch related data. So 1,000 orders plus their customers is 1,001 queries."

"The reason it's dangerous is that each individual query is fast. Nothing shows up in a slow-query log; they're all 2ms. But 1,001 round trips at a millisecond of network latency each is a full second of pure waiting before the database has done any real work. And the plan cache looks perfectly healthy."

"The classic cause is lazy loading. order.Customer.Name is a property read — nothing in that line suggests a database round trip, so it survives code review, and it works fine in development with 20 test rows. Then production has 10,000 and the endpoint times out."

"The fix depends on what I actually need."

"If I need the entities, eager loading: .Include(o => o.Customer). One query with a join."

"If I only need a few fields — which is usually the case — projection: .Select(o => new { o.Id, CustomerName = o.Customer.Name }). That's better than Include because it selects only the columns needed, doesn't materialise or track entities, and can potentially be served entirely from a covering index."

"The mistake to avoid when fixing it is swapping N+1 for a cartesian explosion. If I add several collection Includes to one query — lines, payments, shipments — SQL has no way to return three independent lists in one flat result, so it pairs every combination. 50 × 10 × 5 is 2,500 rows to convey 65 objects, with every parent column repeated. Fix that with AsSplitQuery(), which issues one query per collection so rows add rather than multiply."

"How I'd catch it: log the SQL in development and count queries per request. Most N+1 is obvious the moment you see the same statement repeated with different parameters, and completely invisible otherwise. I'd also consider an assertion in integration tests that a given endpoint issues no more than N queries — that stops it regressing."

"And the structural prevention: leave lazy loading off. Then a navigation you forgot to include is null and fails loudly in development, rather than quietly costing a round trip in production."

What they're really checking
  • Do you know why it's invisible — each query is fast?
  • Do you know projection is usually better than Include?
  • Do you know the cartesian explosion you can create while fixing it?
  • Do you know how to detect it?
Weak answers
  • Red flag: "add Include" with no mention of split queries or projection.
  • Red flag: no idea how you'd detect it.
Likely follow-ups
  • What SQL does AsSplitQuery generate?
  • When is a single query still better?
  • How do you enforce this in CI?
Eager vs lazy vs explicit loading — which do you use? 🔥 Must know
How I'd answer

"Eager is Include — related data comes back with the main query. My default, because it's explicit: reading the code tells you exactly what's loaded and roughly what SQL runs."

"Lazy loads on property access via proxies. I'd leave it disabled."

"Explicit is db.Entry(x).Collection(...).LoadAsync() — you load when you decide to. Useful when loading is genuinely conditional, like an ?include=lines query parameter, or when you want to query a navigation without materialising it: .Collection(o => o.Lines).Query().CountAsync() gets a count without pulling the rows."

"On lazy loading specifically, my objection isn't that it's slow in principle — it's that the cost is invisible. A property read triggering a network round trip isn't visible at the call site, so it passes review, and it's fine in dev with small data. That combination is what makes it a production problem rather than a design preference."

"Two other concrete failure modes. It throws ObjectDisposedException if a navigation is touched after the context is disposed, which happens easily when entities are returned from a service layer. And a JSON serializer walking navigations will trigger loads for everything it touches, so a single response can fire hundreds of queries — which is also a good argument for never returning entities directly from a controller."

"In practice though, my most common answer is none of the three — project. If I need an order number, customer name and line count, I don't want entities at all. A Select into a DTO gets exactly those columns, computes the count in SQL rather than loading rows to count them, returns nothing tracked, and sidesteps the whole loading-strategy question."

"So: project for reads, Include when I need real entities to modify, explicit when loading is conditional, lazy never."

What they're really checking
  • Can you state all three accurately?
  • Is your objection to lazy loading about visibility, not just speed?
  • Do you reach for projection first?
Likely follow-ups
  • How does lazy loading work — what are proxies doing?
  • When would you accept lazy loading?
  • What's a filtered include, and what's the risk?

Advanced / scenario

An endpoint returns 200 orders with lines and payments. It's taking 12 seconds. What do you do? ⭐ Senior-level
How I'd answer

"First I'd look at the generated SQL and count the queries. That immediately tells me which of three very different problems this is, and they have different fixes."

"If it's hundreds of queries — N+1, almost certainly lazy loading or a foreach touching navigations. Fix with Include or, better, projection."

"If it's one enormous query — cartesian explosion. Two collection includes on 200 orders with, say, 20 lines and 5 payments each is 200 × 20 × 5 = 20,000 rows, with every order column repeated 100 times. EF de-duplicates back to the right objects, but only after transferring all of it. Fix with AsSplitQuery()."

"If it's one reasonable query that's just slow — that's a database problem, so I'd get the execution plan and look for a missing index or a non-SARGable predicate."

"But before optimising, I'd ask the more useful question: does the client actually need 200 fully-hydrated orders with all their lines and payments? Usually not. A list view needs an order number, date, customer name, total and status. That's a projection returning 200 small rows instead of an object graph."

"So my likely fix is a projection with the aggregates computed in SQL — Total = o.Lines.Sum(l => l.Total), LineCount = o.Lines.Count() — plus AsNoTracking, which the projection gives me for free. That typically turns 12 seconds into tens of milliseconds, because it's a fundamentally smaller amount of work rather than the same work done faster."

"Then the API design question: is 200 even bounded? If that number can grow, this endpoint has an unbounded query surface and will break again at 2,000. I'd add pagination with a maximum page size, and keyset paging if it's a feed rather than numbered pages."

"Then I'd verify: SQL logging to confirm the query count dropped, and I'd add an integration test asserting the endpoint issues no more than a handful of queries — because this is exactly the kind of fix that regresses the next time someone adds a field to the response."

"One thing I'd flag if the numbers stay large: at some point the right answer isn't a better EF query, it's a read model — a denormalized table or view built for this screen. But I'd only go there after projection and pagination, because those are hours of work and a read model is weeks plus ongoing consistency concerns."

What they're really checking
  • Do you diagnose by looking at the SQL first?
  • Can you distinguish N+1 from cartesian explosion from a slow query?
  • Do you question whether the payload should be that large at all?
  • Do you address the unbounded query surface?
  • Do you verify and guard against regression?
Weak answers
  • Red flag: guessing without looking at the SQL.
  • Red flag: "add caching" as the first move.
  • Red flag: no mention of pagination.
Likely follow-ups
  • How would you write the projection?
  • What's the consistency risk with split queries?
  • When would you build a read model instead?
