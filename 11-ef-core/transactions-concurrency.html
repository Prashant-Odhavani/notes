Transactions & Concurrency

Getting atomicity right, and stopping two users from silently overwriting each other.

🟡 Intermediate 🔴 Advanced 🔥 Must know
Quick revision
  • One SaveChanges = one transaction, automatically. Two calls = two transactions.
  • Explicit transactions only when you need several SaveChanges calls, or raw SQL, to be atomic together.
  • Optimistic concurrency needs a token — a rowversion column is the standard answer.
  • DbUpdateConcurrencyException means somebody else got there first. You must decide what to do.
  • Retry plus an explicit transaction requires an execution strategy, or EF throws.
  • Never do side effects inside a transaction — use the outbox pattern.
  • Prefer an atomic ExecuteUpdate over read-modify-write where you can.

The implicit transaction 🔥 Must know

In simple terms

SaveChanges wraps everything it does in a transaction, whether you asked or not.

So one call is atomic across every insert, update and delete it produces — even across multiple tables.

db.Orders.Add(order);              // INSERT Order
db.OrderLines.AddRange(lines);     // INSERT OrderLine x N
inventory.Stock -= qty;            // UPDATE Inventory

await db.SaveChangesAsync();       // ONE transaction. All or nothing.
db.Orders.Add(order);
await db.SaveChangesAsync();       // transaction 1 - COMMITTED

inventory.Stock -= qty;
await db.SaveChangesAsync();       // transaction 2 - if this throws,
                                   // the order exists with no stock deducted
Remember this

The number of SaveChanges calls is the number of transactions.

If two changes must succeed or fail together, they belong in one SaveChanges — or inside an explicit transaction.

Most "we ended up with an orphaned record" bugs are a second SaveChanges that someone added later without noticing what it did to atomicity.

Explicit transactions 🟡 Intermediate

await using var tx = await db.Database.BeginTransactionAsync();
try
{
    db.Orders.Add(order);
    await db.SaveChangesAsync();          // need the generated Id below

    await db.Database.ExecuteSqlAsync(
        $"UPDATE Inventory SET Stock = Stock - {qty} WHERE Sku = {sku} AND Stock >= {qty}");

    audit.OrderId = order.Id;
    db.AuditEntries.Add(audit);
    await db.SaveChangesAsync();

    await tx.CommitAsync();
}
catch
{
    await tx.RollbackAsync();             // dispose would roll back anyway
    throw;
}
You need an explicit transaction when
Several SaveChanges calls must be atomic — usually because a later step needs a generated key
You mix EF and raw SQL, or EF and Dapper
You need a specific isolation level
You need to read your own uncommitted writes before deciding whether to commit
Sharing a transaction with Dapper
await using var tx = await db.Database.BeginTransactionAsync();

var conn = db.Database.GetDbConnection();
var raw  = tx.GetDbTransaction();          // the underlying DbTransaction

var rows = await conn.QueryAsync<Row>(sql, param, transaction: raw);

db.Orders.Add(order);
await db.SaveChangesAsync();
await tx.CommitAsync();                    // both participate

This is why "EF for writes, Dapper for awkward reads" costs nothing architecturally — they share the connection and the transaction. Worth knowing, because interviewers often expect the two to be mutually exclusive.

Lost updates 🔥 Must know

The bug in plain terms

Two people open the same product edit form. Both see the price as £100.

One changes it to £120 and saves. The other changes the description and saves.

The price is back to £100. Nobody was told anything went wrong.

Why EF doesn't prevent this by default

EF only updates the columns that changed on its snapshot. So it isn't a whole-row overwrite — which helps.

But if both users changed the same column, the second write wins with no detection at all. And if the code uses Update() on a detached entity, every column is overwritten.

Optimistic concurrency 🔥 Must know

public class Product
{
    public int Id { get; set; }
    public decimal Price { get; set; }
    public string Description { get; set; } = null!;

    [Timestamp]                                  // SQL Server rowversion
    public byte[] Version { get; set; } = null!;
}

// Fluent equivalent:
b.Property(p => p.Version).IsRowVersion();
What EF then does

The generated UPDATE gains AND Version = @originalVersion.

If somebody else changed the row, the database bumped Version, so zero rows are affected — and EF turns that into DbUpdateConcurrencyException.

UPDATE Product
SET    Price = @p0
WHERE  Id = @p1 AND Version = @p2;      -- the guard
-- 0 rows affected -> someone else won

Handling the exception

try
{
    await db.SaveChangesAsync();
}
catch (DbUpdateConcurrencyException ex)
{
    var entry    = ex.Entries.Single();
    var current  = entry.CurrentValues;                       // what we tried to save
    var database = await entry.GetDatabaseValuesAsync();      // what's actually there

    if (database is null)
        return Conflict("This record was deleted by another user.");

    // 1. LAST WRITER WINS - reload the token and retry
    entry.OriginalValues.SetValues(database);
    await db.SaveChangesAsync();

    // 2. FIRST WRITER WINS - abandon our change
    // return Conflict("Someone else updated this. Please reload.");

    // 3. MERGE - keep theirs except for the fields we own
    // foreach (var p in entry.Metadata.GetProperties()) { ... }
}
StrategyUse when
Last writer winsLow-stakes fields, or a background process where the newest value is correct
First writer wins — tell the userUsually right for user-facing edits. Honest, and they can decide
MergeDifferent users edit disjoint fields, and you can prove which is which
Senior signal — this is a UX decision, not a technical one

EF can detect the conflict. It cannot know what should happen — that depends on what the data means.

A stock count: last writer wins is probably wrong; you want an atomic decrement instead. A support ticket's status: telling the user "someone else changed this, here's what they set" is right. A background enrichment job: overwriting is fine.

The weak answer is "catch it and retry" for everything. The strong answer names the choice and ties it to the domain — and says explicitly that a silent retry on a user-facing edit just reintroduces the lost update you were preventing.

rowversion vs a concurrency token on a column

rowversion is a database-maintained 8-byte value that changes on any update to the row. Nothing to remember, works for every column.

Alternatively mark a specific property with IsConcurrencyToken() — often a LastModified timestamp. Narrower: two users editing genuinely different columns won't conflict, which can be what you want.

For PostgreSQL the equivalent is the system xmin column (b.UseXminAsConcurrencyToken()). Worth knowing, since rowversion is SQL Server-specific.

Better than detection: don't read first ⭐ Senior-level

var inv = await db.Inventory.FirstAsync(i => i.Sku == sku);
if (inv.Stock >= qty)              // ← another request can pass this too
{
    inv.Stock -= qty;
    await db.SaveChangesAsync();
}
var affected = await db.Inventory
    .Where(i => i.Sku == sku && i.Stock >= qty)
    .ExecuteUpdateAsync(s => s.SetProperty(i => i.Stock, i => i.Stock - qty));

if (affected == 0)
    throw new InsufficientStockException(sku);
Remember this

The best fix for a concurrency problem is often to remove the read.

No read-modify-write means no window, no version token, no retry, and no exception handling. One statement, one round trip.

ExecuteUpdate arrived in EF Core 7. Before that this needed raw SQL — which is why a lot of older code uses the pessimistic or optimistic patterns where this would now be simpler.

ExecuteUpdate bypasses the change tracker

It generates SQL directly, so entities already loaded in the context keep their old values — and a later SaveChanges can write them back over your update.

It also doesn't fire interceptors, so audit stamps and soft-delete logic don't apply. And it isn't included in SaveChanges' transaction — if you need both atomic, wrap them in an explicit transaction.

So it's excellent for set-based work and wrong for anything relying on tracking behaviour.

Retry and transactions 🔥 Must know

options.UseSqlServer(cs, sql => sql.EnableRetryOnFailure(
    maxRetryCount: 5,
    maxRetryDelay: TimeSpan.FromSeconds(30),
    errorNumbersToAdd: null));
This combination throws, and the message is confusing

With retry enabled, calling BeginTransaction gives you:

"The configured execution strategy 'SqlServerRetryingExecutionStrategy' does not support user-initiated transactions."

That's deliberate. Retry works per operation — but retrying one SaveChanges inside a transaction that already failed is meaningless, because the transaction is gone. EF refuses rather than doing something incorrect.

var strategy = db.Database.CreateExecutionStrategy();

await strategy.ExecuteAsync(async () =>
{
    await using var tx = await db.Database.BeginTransactionAsync();

    db.Orders.Add(order);
    await db.SaveChangesAsync();

    audit.OrderId = order.Id;
    db.AuditEntries.Add(audit);
    await db.SaveChangesAsync();

    await tx.CommitAsync();
});
The requirement people miss

The block passed to ExecuteAsync can run more than once. So it must be idempotent — and it must not depend on state mutated by a previous attempt.

Two concrete hazards. Entities added in a failed attempt are still tracked, so a naive retry can insert duplicates; build the entity graph inside the block, not outside it. And anything non-database in there — an email, an HTTP call, a message published — happens once per attempt.

Same requirement as HTTP retry-safety. It's the same problem in a different layer.

Side effects and the outbox ⭐ Senior-level

db.Orders.Add(order);
await db.SaveChangesAsync();               // committed

await _bus.PublishAsync(new OrderPlaced(order.Id));   // ← what if this fails?
// Order exists. Nobody downstream knows. Silent inconsistency.
await using var tx = await db.Database.BeginTransactionAsync();
db.Orders.Add(order);
await db.SaveChangesAsync();

await _bus.PublishAsync(new OrderPlaced(order.Id));   // published

await tx.CommitAsync();                    // if THIS fails, the message is already out
// Downstream reacts to an order that doesn't exist.
db.Orders.Add(order);

db.OutboxMessages.Add(new OutboxMessage
{
    Id       = Guid.CreateVersion7(),
    Type     = nameof(OrderPlaced),
    Payload  = JsonSerializer.Serialize(new OrderPlaced(order.Id)),
    OccurredUtc = DateTime.UtcNow
});

await db.SaveChangesAsync();     // order AND message committed atomically

// A background worker reads unsent rows, publishes, marks them sent.
Remember this

You cannot atomically write to a database and a message broker. There's no shared transaction.

So write the intent to the same database, in the same transaction, and publish afterwards from a separate process.

You get at-least-once delivery, which means consumers must be idempotent. That's a real cost, and it's much smaller than silent inconsistency.

Wiring it into an interceptor

Putting the outbox write in a SaveChanges interceptor means domain code raises events on the entity and the infrastructure turns them into outbox rows automatically — so no handler can forget.

That's the difference between the outbox being a pattern the team must remember, and a guarantee the system provides.

Isolation levels in EF 🔴 Advanced

await using var tx = await db.Database
    .BeginTransactionAsync(System.Data.IsolationLevel.Serializable);
You rarely need to change it

EF uses the database's default, which for SQL Server is READ COMMITTED.

Raising isolation to solve a concurrency bug is almost always the wrong instrument — it costs concurrency across the whole application and often doesn't fix the actual problem.

Prefer, in order: an atomic ExecuteUpdate, then a rowversion token, then a targeted lock. And if reads are blocking writes, the answer is RCSI at the database level — which needs no application change at all.

Key takeaways
  • One SaveChanges is one transaction. Two calls are two transactions.
  • Explicit transactions for multi-save units, mixed SQL, or a specific isolation level.
  • EF and Dapper can share a connection and transaction.
  • Lost updates aren't detected without a concurrency token.
  • rowversion adds a guard to the WHERE clause; zero rows means conflict.
  • What to do on conflict is a domain decision, not a technical default.
  • Removing the read — ExecuteUpdate with the condition inline — beats detecting the conflict.
  • ExecuteUpdate bypasses tracking, interceptors and the SaveChanges transaction.
  • Retry plus explicit transaction needs an execution strategy, and the block must be idempotent.
  • Never publish messages or send email inside a transaction. Use the outbox.

Common mistakes

  • Two SaveChanges calls where atomicity was required.
  • No concurrency token, so lost updates go undetected.
  • Catching DbUpdateConcurrencyException and blindly retrying — reintroducing the lost update.
  • Read-modify-write where an atomic update would work.
  • BeginTransaction with retry enabled and no execution strategy.
  • Building entities outside a retried block, causing duplicate inserts.
  • Publishing messages inside a transaction.
  • ExecuteUpdate on entities the context already tracks.
  • Raising the isolation level instead of fixing the operation.
  • A transaction spanning user think-time.

Interview questions

Intermediate

Two users edit the same record. How do you handle it in EF Core? 🔥 Must know
How I'd answer

"Without anything in place, it's a lost update — the second save silently overwrites the first, and nobody is told."

"EF helps a little by default: it only updates the columns that changed on its snapshot, so two users editing genuinely different fields don't clobber each other. But if they touched the same column, the second write wins with no detection. And if the code uses Update() on a detached entity, every column gets overwritten regardless."

"The standard fix is optimistic concurrency with a rowversion column — [Timestamp], or IsRowVersion() in fluent config. SQL Server maintains it automatically, changing it on any update to the row."

"EF then adds AND Version = @original to the UPDATE. If someone else has saved since we loaded, the version differs, zero rows are affected, and EF raises DbUpdateConcurrencyException."

"The important part is what you do with that exception, because that's a product decision, not a technical one. EF can detect the conflict; it can't know what should happen."

"For a user-facing edit form I'd almost always go first writer wins: return a 409, tell the user someone else changed it, and show them what changed so they can decide. That's honest. Silently retrying with the new version is the one option I'd avoid, because it reintroduces exactly the lost update I was trying to prevent."

"Last writer wins is reasonable for a background enrichment job where the newest value is by definition correct. Merge works if users edit provably disjoint fields, but it's more code and I'd want a real reason."

"For getting at the details: ex.Entries gives the failing entity, and GetDatabaseValuesAsync() gives the current database state, so you can show a proper diff. It returning null means the row was deleted, which needs a different message."

"And I'd ask whether this needs conflict detection at all. If it's really 'decrement stock', the better answer is to remove the read: ExecuteUpdate with the condition in the WHERE clause. No read-modify-write means no window, no token, no exception handling — one statement. Detection is for cases where a human is editing something and there's genuinely a decision to make."

"One portability note: rowversion is SQL Server-specific. On PostgreSQL the equivalent is the system xmin column via UseXminAsConcurrencyToken()."

What they're really checking
  • Do you name it as a lost update?
  • Do you know the mechanism — the guard in the WHERE clause?
  • Do you treat the resolution as a domain decision?
  • Do you know a blind retry defeats the purpose?
  • Bonus: do you suggest avoiding the read entirely?
Weak answers
  • Red flag: "catch it and retry" with no discussion.
  • Red flag: reaching for SERIALIZABLE or a lock first.
Likely follow-ups
  • What SQL does EF generate with a rowversion?
  • How would you show the user what changed?
  • What if the row was deleted rather than updated?

Advanced / scenario

Placing an order must save to the database and publish an event. How do you make that reliable? ⭐ Senior-level
How I'd answer

"The core issue is that you cannot atomically write to a database and a message broker — there's no shared transaction, so any ordering you pick has a failure mode."

"Save then publish: if the publish fails, the order exists and nothing downstream knows. Silent inconsistency — no email, no fulfilment, and no error anywhere."

"Publish then save: if the save fails, downstream services react to an order that doesn't exist. Worse, because now other systems have acted on fiction."

"Publish inside the transaction: looks tidier and is the same problem — the message is already out when the commit fails. And it holds database locks for the duration of a network call to the broker, which is its own problem."

"So I'd use the outbox pattern. In the same SaveChanges — therefore the same transaction — I write the order and a row to an OutboxMessages table containing the serialised event. Both commit atomically or neither does. There's no dual write at all, because the message is just more rows in the same database."

"Then a background worker polls for unsent rows, publishes them to the broker, and marks them sent. If publishing fails it retries; if the process dies the row is still there."

"The cost is that this gives at-least-once delivery, not exactly-once. The worker can publish and then crash before marking the row sent, so the message goes out twice. That means consumers must be idempotent — typically dedupe on a message ID they've recorded, an inbox table. That's a real requirement and I'd state it explicitly rather than pretend the outbox solves delivery semantics."

"Implementation details I'd get right. I'd put the outbox write in a SaveChanges interceptor, so domain code raises events on the entity and the infrastructure turns them into outbox rows automatically — otherwise it's a pattern someone will forget in one handler and you're back to a dual write."

"The worker needs a claim step so multiple instances don't publish the same row — an atomic update marking rows as being processed, or an UPDLOCK, READPAST read. And it needs ordering if the events are causally related, which usually means partitioning by aggregate."

"I'd also add a filtered index on unsent rows so the poll is cheap on a big table, and a cleanup job to archive sent messages — an outbox table nobody prunes becomes a problem in itself."

"One alternative worth naming: if the database supports change data capture, you can tail the log instead of polling — that's the transactional-outbox-via-CDC variant, lower latency and no polling overhead, at the cost of more infrastructure. And if this is all within one service and the consumer could just read the database, I'd question whether an event is needed at all."

What they're really checking
  • Do you recognise the dual-write problem?
  • Can you explain why all three naive orderings fail?
  • Do you know the outbox pattern and its at-least-once consequence?
  • Do you handle multiple workers claiming rows?
  • Do you make it structural rather than a convention?
Weak answers
  • Red flag: "publish inside the transaction."
  • Red flag: claiming the outbox gives exactly-once delivery.
  • Red flag: reaching for a distributed transaction / MSDTC.
Likely follow-ups
  • How do consumers deduplicate?
  • How do you guarantee ordering?
  • What if the outbox table grows to 200 million rows?
You enabled EnableRetryOnFailure and now BeginTransaction throws. Why? ⭐ Senior-level
How I'd answer

"EF refuses the combination on purpose. The message is that the retrying execution strategy 'does not support user-initiated transactions'."

"The reasoning: retry operates per operation. If I have a transaction spanning three SaveChanges calls and the second one fails transiently, retrying just that call is meaningless — the transaction has already been aborted. EF would be retrying into a dead transaction and producing something incoherent, so it throws instead of guessing."

"The fix is to make the whole transaction the retryable unit, using an execution strategy: db.Database.CreateExecutionStrategy(), then put the BeginTransaction, all the saves and the commit inside strategy.ExecuteAsync(...). Now if anything inside fails transiently, the entire block re-runs from the beginning — which is the only correct granularity."

"The requirement that comes with that, and it's the part people miss: the block can run more than once, so it has to be idempotent."

"Two concrete hazards there. First, entities added to the context in a failed attempt are still tracked — so if I build the entity graph outside the block and only add it inside, a retry can insert duplicates. The graph should be constructed inside the block. Second, anything non-database in there — publishing a message, sending an email, calling an API — happens once per attempt. Those belong outside, or behind an outbox."

"I'd also sanity-check whether the explicit transaction is needed at all. Often it's there because someone added a second SaveChanges, and the two saves could be merged into one — which is atomic automatically and sidesteps the whole issue. The usual legitimate reason is needing a generated key from the first save, and for that the execution strategy is the right answer."

"Worth noting this is the same idempotency requirement as retry-safety in HTTP APIs. Any time something can be retried, the work has to tolerate being done twice — the layer changes, the constraint doesn't."

What they're really checking
  • Do you understand why EF refuses rather than treating it as a bug?
  • Do you know the execution-strategy fix?
  • Do you know the block must be idempotent, and why tracked entities are a hazard?
  • Do you question whether the transaction is needed?
Likely follow-ups
  • Which errors does EF consider transient?
  • What happens if all retries are exhausted?
  • How does this interact with the outbox?
