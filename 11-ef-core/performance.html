EF Core Performance

EF Core is fast. Most "EF is slow" problems are three or four specific mistakes, and they're all measurable.

🟡 Intermediate 🔴 Advanced 🔥 Must know
Quick revision
  • Count the queries first. That single number identifies most problems.
  • Project into DTOs. Fewer columns, no tracking, covering-index eligible.
  • Round trips dominate — 1,000 fast queries beat one slow query for total time.
  • ExecuteUpdate/ExecuteDelete for set-based work. No loading, no tracking.
  • SqlBulkCopy for genuinely large inserts — orders of magnitude faster.
  • Compiled queries save query-plan compilation, not database time. Small, real win on hot paths.
  • Context pooling helps high-throughput APIs with simple contexts.
  • Measure before and after. Most EF "optimisations" applied blind do nothing.

The counter worth adding permanently
public class QueryCountInterceptor : DbCommandInterceptor
{
    public static readonly AsyncLocal<int> Count = new();

    public override InterceptionResult<DbDataReader> ReaderExecuting(
        DbCommand command, CommandEventData e, InterceptionResult<DbDataReader> result)
    {
        Count.Value++;
        return result;
    }
}
// Log it per request in dev; assert on it in integration tests.

An integration test asserting "this endpoint issues at most 4 queries" catches N+1 regressions permanently. Without it, someone adds a field to a response model in six months and the endpoint quietly goes back to 400 queries.

This is the single most effective EF performance practice I know, because it turns a recurring problem into a build failure.

Round trips are the dominant cost 🔥 Must know

Think of it this way

Fetching 100 items from a warehouse.

One trip with a trolley: a few minutes. A hundred separate trips, each one fast: an afternoon.

The walking is the cost, not the lifting.

PatternRound tripsTypical cost
1,000 lazy-loaded navigations1,001~1 second of pure latency
Include1~10ms
Projection1, fewer columns~5ms
SaveChanges in a loop, 1,000 items1,000 transactions~10 seconds
AddRange then one SaveChanges~25 batches~300ms
SqlBulkCopy1 stream~50ms
Remember this

Latency multiplies; work adds.

A cloud database at 1–2ms per round trip means 1,000 round trips is a second or two of doing nothing. That's why query count matters more than query speed, and why it's the first thing to look at.

Projection is the biggest single win 🔥 Must know

var orders = await db.Orders
    .Include(o => o.Customer)
    .Include(o => o.Lines)
    .Where(o => o.CustomerId == id)
    .ToListAsync();

// 40 Order columns + 25 Customer columns + every line, all tracked,
// to render Id, date, customer name and a total.
var orders = await db.Orders
    .Where(o => o.CustomerId == id)
    .Select(o => new OrderListItem
    {
        Id           = o.Id,
        CreatedUtc   = o.CreatedUtc,
        CustomerName = o.Customer.Name,            // JOIN, one column
        LineCount    = o.Lines.Count(),            // COUNT in SQL
        Total        = o.Lines.Sum(l => l.Total)   // SUM in SQL
    })
    .ToListAsync();
Projection gives youMechanism
Fewer columns transferredOnly what's in the Select
No change trackingNon-entity results aren't tracked
No cartesian explosionCollections become correlated subqueries
Aggregates computed in the databaseCOUNT/SUM instead of loading rows to count
Covering index eligibilityNarrow column set can be served entirely from an index
No over-posting riskYou can't accidentally serialise a field you didn't intend to
Senior signal — projection is a design decision, not a tweak

Loading entities to build a response is a category error: an entity models the write side — invariants, behaviour, identity. A response models what a screen needs.

Once you separate them, the performance benefits follow automatically, and you stop leaking domain structure into your API contract. That's the read-model idea from CQRS applied at the smallest useful scale — no separate database, no eventual consistency, just a different query.

Framing it that way is much stronger than "projection is faster", because it explains why it keeps being the answer.

Bulk operations 🔥 Must know

Set-based update and delete

var stale = await db.Orders
    .Where(o => o.CreatedUtc < cutoff && o.Status == OrderStatus.Pending)
    .ToListAsync();                       // 50,000 entities materialised and tracked

foreach (var o in stale) o.Status = OrderStatus.Expired;
await db.SaveChangesAsync();              // 50,000 UPDATE statements, batched
var affected = await db.Orders
    .Where(o => o.CreatedUtc < cutoff && o.Status == OrderStatus.Pending)
    .ExecuteUpdateAsync(s => s.SetProperty(o => o.Status, OrderStatus.Expired));

// UPDATE [Order] SET Status = @p WHERE CreatedUtc < @c AND Status = @s
// Nothing loaded. Nothing tracked. One round trip.
What ExecuteUpdate and ExecuteDelete skip

They generate SQL directly, which means they bypass:

  • Change tracking — already-loaded entities keep stale values, and a later SaveChanges can overwrite your update.
  • Interceptors — audit stamps and soft-delete conversion don't run.
  • The SaveChanges transaction — wrap both in an explicit transaction if they must be atomic together.
  • Cascade behaviour configured in EF — the database's FK actions still apply, but EF's in-memory cascade doesn't.

Also worth knowing: a large ExecuteDelete is still one big transaction, so it can escalate to a table lock. Batch it with .OrderBy(...).Take(5000) in a loop for very large deletes.

const int ChunkSize = 2_000;

foreach (var chunk in items.Chunk(ChunkSize))
{
    await using var db = await factory.CreateDbContextAsync();
    db.ChangeTracker.AutoDetectChangesEnabled = false;   // O(n^2) otherwise
    db.Orders.AddRange(chunk);
    await db.SaveChangesAsync();
}
Why one context for 500,000 entities collapses

Change detection is O(n) per call and it runs on every Add, so adding n entities to one context is roughly O(n²).

At 500,000 entities that isn't "slow" — it effectively stops. Memory also holds every entity plus its snapshot.

Two fixes: AutoDetectChangesEnabled = false while bulk-adding (call ChangeTracker.DetectChanges() once before saving if needed), and a fresh context per chunk so the tracker starts empty. Both matter; the fresh context matters more.

using var bulk = new SqlBulkCopy(connection)
{
    DestinationTableName = "dbo.[Order]",
    BatchSize            = 10_000,
    BulkCopyTimeout      = 0
};
bulk.ColumnMappings.Add(nameof(Order.CustomerId), "CustomerId");
bulk.ColumnMappings.Add(nameof(Order.Total),      "Total");

await bulk.WriteToServerAsync(dataReader);
Knowing when to stop using the ORM is a senior signal

"I'd use SqlBulkCopy for a 2-million-row import" is a stronger answer than any EF tuning, because it recognises that change tracking has no value when there's nothing to track.

The same reasoning applies to reporting queries: if there's no object graph to mutate, an ORM is doing work you're paying for and not using.

Compiled queries 🔴 Advanced

private static readonly Func<AppDbContext, int, Task<Order?>> GetOrderById =
    EF.CompileAsyncQuery((AppDbContext db, int id) =>
        db.Orders.FirstOrDefault(o => o.Id == id));

// Usage
var order = await GetOrderById(db, id);
What they actually save

EF caches query plans automatically, keyed on the expression-tree shape. But it still has to walk and hash the expression tree on every call to find the cache entry.

A compiled query skips that. It saves CPU in your process, not database time.

Realistic expectations

Typically 10–30% off the EF overhead — which on a query where the database takes 20ms and EF takes 0.3ms is noise.

Worth it for a genuinely hot, simple, unchanging query executed thousands of times a second. Not worth the loss of readability anywhere else, and it can't be built dynamically, so it doesn't work for queries with optional filters.

If someone reaches for compiled queries before fixing an N+1, they're optimising the wrong order of magnitude — and saying so is the better interview answer.

Context pooling 🔴 Advanced

builder.Services.AddDbContextPool<AppDbContext>(
    o => o.UseSqlServer(cs), poolSize: 128);
In simple terms

Instead of constructing a DbContext per request, instances are reused — reset and returned to a pool at the end of the request.

It avoids the cost of building the internal service provider and model reference each time.

Works whenBreaks when
The context has a parameterless-ish constructor taking only optionsThe context injects scoped services — a tenant provider, a user context
No per-request state on the contextYou store _tenantId or similar as a field
Very high request throughputModerate traffic — the gain is unmeasurable
The pooling bug that leaks data across tenants

If your context holds a _tenantId field — commonly used with a global query filter — pooling reuses the instance with the previous request's value unless you explicitly reset it.

That's a cross-tenant data leak that appears only under concurrency, in production, intermittently.

Pooling is safe for a stateless context and dangerous for a stateful one. Given the gain is only meaningful at very high throughput, I wouldn't enable it without a measured reason — the risk/reward is poor otherwise.

When a DBA shows you a slow query from Query Store, that comment tells you exactly which C# produced it. Without it, mapping generated SQL back to source is genuinely painful on a large codebase.

Fix things in this order ⭐ Senior-level

  1. Query count — eliminate N+1. Usually 10–100× wins.
  2. Row count — fix cartesian explosion and unbounded result sets. Often 10×.
  3. Column count — project instead of loading entities. Often 2–5×.
  4. Database indexes — the query is now sensible; make it fast. Sometimes 100×.
  5. Set-based operations — ExecuteUpdate, bulk copy. 10–100× on writes.
  6. Tracking — AsNoTracking. 10–30%.
  7. Micro-optimisation — compiled queries, pooling. Single-digit percentages.
Remember this

Steps 1 to 4 are almost always where the time is. Steps 6 and 7 are where people start, because they're the ones with names.

If someone proposes context pooling before checking the query count, they're chasing 3% while ignoring a 50× problem.

Key takeaways
  • Log the SQL and count queries. Assert on the count in integration tests.
  • Round trips dominate — latency multiplies while work adds.
  • Projection fixes columns, tracking, row bloat and aggregates in one change.
  • ExecuteUpdate/ExecuteDelete for set-based writes — but they bypass tracking, interceptors and the save transaction.
  • Chunk large inserts with a fresh context; disable auto-detect-changes.
  • SqlBulkCopy past roughly 50,000 rows.
  • Compiled queries save EF overhead, not database time.
  • Context pooling is dangerous with a stateful context — cross-tenant leaks.
  • TagWith to trace generated SQL back to source.
  • Fix query count, then rows, then columns, then indexes. Micro-optimise last.

Common mistakes

  • Optimising without measuring, then not knowing what helped.
  • Loading entities to build a response.
  • Loading a collection to .Count() it.
  • SaveChanges inside a loop.
  • 500,000 entities in one context — O(n²) change detection.
  • ExecuteUpdate on already-tracked entities, then saving stale values back.
  • Compiled queries before fixing N+1.
  • Context pooling with a tenant field on the context.
  • Blaming EF for a missing database index.
  • Testing on 200 rows when production has 8 million.
  • EnableSensitiveDataLogging left on in production.

Interview questions

Intermediate

How would you update the status of 100,000 rows? 🔥 Must know
How I'd answer

"Not by loading them. The naive version — query them into a list, loop setting the property, call SaveChanges — materialises 100,000 entities with snapshots, then issues 100,000 UPDATE statements. Batched, so it's not 100,000 round trips, but it's still a huge amount of pointless work."

"Since EF Core 7 the right answer is ExecuteUpdateAsync: db.Orders.Where(...).ExecuteUpdateAsync(s => s.SetProperty(o => o.Status, OrderStatus.Expired)). That translates to a single UPDATE ... WHERE .... Nothing loaded, nothing tracked, one round trip. Before EF Core 7 this needed ExecuteSqlRaw, which is why a lot of older code does it the slow way."

"Three things I'd be careful about."

"It bypasses the change tracker, so any of those entities already loaded in the context keep their old values — and a subsequent SaveChanges could write them back over my update. It also skips interceptors, so audit stamps and soft-delete conversion don't run. If audit fields matter here I'd set them in the SetProperty calls explicitly."

"It's one transaction, so 100,000 rows can cross the lock escalation threshold and take a table lock, blocking the application for the duration. At this size I'd batch it — .OrderBy(o => o.Id).Take(5000) in a loop until zero rows are affected, with a short delay between batches. Slower in wall clock, invisible to users, and resumable if it's interrupted."

"It isn't in the SaveChanges transaction, so if it needs to be atomic with other changes I'd wrap both in an explicit transaction."

"For the analogous insert case — 100,000 new rows — I'd use SqlBulkCopy rather than EF at all. Change tracking has no value when there's nothing to track, and bulk copy streams the rows with minimal logging, typically 10 to 100 times faster. Recognising when to stop using the ORM is part of using it well."

"And I'd ask whether this should be an online operation at all. A 100,000-row status change is often a maintenance job, in which case batching plus off-peak scheduling matters more than raw speed."

What they're really checking
  • Do you know ExecuteUpdate exists?
  • Do you know what it bypasses?
  • Do you think about lock escalation and batching?
  • Do you know when to leave the ORM entirely?
Weak answers
  • Red flag: load-loop-save with no concern.
  • Red flag: ExecuteUpdate with no awareness of tracking or locking implications.
Likely follow-ups
  • How do you set audit fields with ExecuteUpdate?
  • Why does batching avoid the table lock?
  • How would you make the job resumable?

Advanced / scenario

The team says "EF Core is too slow, we should replace it with Dapper." How do you respond? ⭐ Senior-level
How I'd answer

"I'd want to see the measurements before agreeing to a rewrite, because in my experience 'EF is slow' almost always turns out to be three or four specific mistakes rather than the framework — and those mistakes are usually cheaper to fix than to migrate away from."

"The first thing I'd do is turn on SQL logging and count queries per request. That one number usually identifies the problem in minutes."

"Hundreds of queries means N+1 — lazy loading, or a loop touching navigations. That's not an EF speed problem, it's a usage problem, and Dapper wouldn't fix it either. Written badly, Dapper produces exactly the same N+1 — you'd just be writing the SQL for it by hand."

"One enormous query means cartesian explosion from multiple collection includes. Fixed with AsSplitQuery or a projection."

"A reasonable query that's slow means it's a database problem — missing index, non-SARGable predicate, bad statistics. Rewriting the data layer changes nothing; the same SQL would be equally slow from Dapper."

"The other thing I'd check is whether we're loading entities to build API responses. That's extremely common and it's the biggest easy win — projecting into DTOs cuts columns, removes tracking, avoids row multiplication and computes aggregates in SQL, all in one change."

"Now, EF does have real overhead: change tracking, expression-tree translation, entity materialisation. Dapper is genuinely faster per query. But that overhead is typically a fraction of a millisecond against a database call of 5 to 50 milliseconds. If we're 12 seconds slow, EF's overhead is not where those 12 seconds are."

"So my counter-proposal wouldn't be 'keep EF, it's fine' — it'd be fix the actual problems, then use both deliberately. EF Core for the write side and CRUD, where change tracking, dependency-ordered inserts and migrations do real work I don't want to hand-write. Dapper for complex reporting queries and any genuinely hot read path, where I want to control the SQL exactly. They share a connection and transaction, so mixing them costs nothing architecturally."

"On the cost side: a full migration to Dapper means rewriting every query, losing migrations — so schema management needs replacing too — losing dependency-ordered saves, and hand-writing all the concurrency handling. That's months of work with a real regression risk, and afterwards the N+1 is still there unless someone fixes it. Whereas the projection and AsSplitQuery changes are days."

"I'd also want to know what's driving this. Sometimes 'EF is slow' really means 'we don't understand what SQL it's generating', and the fix is turning on logging plus a query-count assertion in integration tests. That gives the team visibility and stops the problem recurring — which a rewrite wouldn't."

What they're really checking
  • Do you ask for evidence before agreeing to a rewrite?
  • Do you know the real causes and that Dapper wouldn't fix them?
  • Are you honest that EF has genuine overhead, and about its scale?
  • Can you cost the alternative?
  • Do you propose using both rather than picking a side?
Weak answers
  • Red flag: agreeing immediately.
  • Red flag: defending EF with no acknowledgement of its overhead.
  • Red flag: no diagnostic plan.
Likely follow-ups
  • Show me how you'd share a transaction between them.
  • What would you replace migrations with?
  • How do you stop N+1 coming back?
