Modelling & Migrations

Mapping your classes to tables, and changing the schema on a running system without taking it down.

🟡 Intermediate 🔴 Advanced ⭐ Senior-level
Quick revision
  • Fluent API for anything non-trivial. Attributes put persistence concerns in your domain classes.
  • Owned types map a value object into the parent's table. Complex types (EF Core 8+) do it properly — no identity, no tracking.
  • Value converters map a domain type to a column — strongly-typed IDs, enums as strings.
  • Never edit an applied migration. Add a new one.
  • Don't run Update-Database in production. Generate an idempotent script and review it.
  • Expand/contract is the pattern for zero-downtime schema change: add, backfill, switch, remove — across separate deployments.
  • Every migration must work with both the old and new application version, because both run at once during a rolling deploy.

Fluent API vs attributes 🟡 Intermediate

public class Order
{
    public int Id { get; set; }

    [Required, MaxLength(50)]
    [Column("order_number", TypeName = "varchar(50)")]
    public string OrderNumber { get; set; } = null!;

    [Precision(19, 4)]
    public decimal Total { get; set; }
}
// Domain: no persistence knowledge at all
public class Order
{
    public int Id { get; set; }
    public string OrderNumber { get; set; } = null!;
    public decimal Total { get; set; }
}

// Configuration: one file per entity
public class OrderConfiguration : IEntityTypeConfiguration<Order>
{
    public void Configure(EntityTypeBuilder<Order> b)
    {
        b.ToTable("Order");
        b.HasKey(o => o.Id);

        b.Property(o => o.OrderNumber)
            .HasColumnName("order_number")
            .HasColumnType("varchar(50)")
            .IsRequired();

        b.Property(o => o.Total).HasPrecision(19, 4);

        b.HasIndex(o => o.OrderNumber).IsUnique();
    }
}

// Registered once
protected override void OnModelCreating(ModelBuilder b)
    => b.ApplyConfigurationsFromAssembly(typeof(AppDbContext).Assembly);

The practical position

Fluent API, in one IEntityTypeConfiguration per entity.

Attributes are fine for genuinely universal things like [Key] on a conventionally-named property. But mixing both means two places to look, and fluent silently overrides attributes — so the attribute you're reading may not be in effect.

The separate-file approach also keeps OnModelCreating from becoming a 900-line method, which is where this ends up otherwise.

Relationships 🔥 Must know

b.HasMany(o => o.Lines)
 .WithOne(l => l.Order)
 .HasForeignKey(l => l.OrderId)
 .OnDelete(DeleteBehavior.Cascade);      // true ownership: lines die with the order

b.HasOne(o => o.Customer)
 .WithMany(c => c.Orders)
 .HasForeignKey(o => o.CustomerId)
 .OnDelete(DeleteBehavior.Restrict);     // don't let a customer delete take orders with it
DeleteBehaviorEffectUse for
CascadeDeletes dependentsGenuine composition — order lines
RestrictThrows if dependents existDefault choice for associations
SetNullNulls the FKOptional relationships
ClientCascadeEF cascades in memory; no database cascadeSQL Server multiple-cascade-path errors
NoActionNo FK enforcement of deletesRarely what you want
Cascade defaults bite twice

EF Core defaults to cascade delete for required relationships. So deleting a customer can silently take every order with it — see cascade chains for why that's worse than it sounds.

Separately, EF cascades tracked entities in memory even when the database wouldn't. So loading a parent with its children and then removing the parent can delete children the database FK would have protected. Configure delete behaviour explicitly rather than relying on the convention.

Many-to-many

public class Product { public List<Category> Categories { get; set; } = []; }
public class Category { public List<Product> Products { get; set; } = []; }

b.Entity<Product>()
 .HasMany(p => p.Categories)
 .WithMany(c => c.Products)
 .UsingEntity("ProductCategory");         // EF creates and manages the join table
When you still need an explicit join entity

The moment the relationship itself has data — when it was added, by whom, a sort order, a soft-delete flag.

That's a signal the join isn't really a join: it's an entity in its own right. Model it explicitly with two one-to-many relationships, and name it something meaningful (ProductCategoryAssignment) rather than a concatenation.

Owned and complex types 🔴 Advanced

In simple terms

A value object — Money, Address, DateRange — has no identity of its own. It's just a bundle of values that belongs to something else.

You want it as a class in your domain, and as columns in the owner's table.

public record Address(string Line1, string City, string PostCode, string Country);

public class Customer
{
    public int Id { get; set; }
    public Address Billing  { get; set; } = null!;
    public Address Shipping { get; set; } = null!;
}

b.ComplexProperty(c => c.Billing,  a => a.IsRequired());
b.ComplexProperty(c => c.Shipping, a => a.IsRequired());

// Columns: Billing_Line1, Billing_City, ... Shipping_Line1, ...

Senior signal — why complex types were added

Owned types were EF's stand-in for value objects, and they leaked: an owned instance has a hidden identity, so assigning the same Address object to both Billing and Shipping throws — "the instance of entity type cannot be tracked because another instance with the same key is already being tracked".

That's nonsense for a value object. The whole point of one is that two equal values are interchangeable.

Complex types fixed it by having genuinely no identity. Knowing why they exist is a much better answer than knowing they exist — it shows you've hit the owned-type limitation in real code.

Value converters 🔴 Advanced

public readonly record struct OrderId(int Value);

b.Property(o => o.Id)
 .HasConversion(id => id.Value, value => new OrderId(value));
b.Property(o => o.Status).HasConversion<string>().HasMaxLength(30);
Store enums as strings, or pin the ordinals

By default EF stores an enum as its integer ordinal. Reorder the enum members — or insert one in the middle — and every existing row now means something different. Nothing errors. Cancelled becomes Shipped.

Two safe options: HasConversion<string>(), which is self-describing in the database and survives reordering; or explicit values (Open = 1, Paid = 2) that you never change.

Strings cost a little space and are slightly slower to index. Worth it — this is the same trap covered in the enum section, and it causes silent data corruption rather than a visible failure.

Converters break translation

EF can't translate operations it can't express on the converted column. An enum-as-string converter means Where(o => o.Status > OrderStatus.Open) becomes a string comparison — alphabetical, not ordinal — which is silently wrong rather than an error.

Comparisons and range queries on converted properties need thinking about. Equality is always fine.

Migrations 🔥 Must know

dotnet ef migrations add AddOrderStatus
dotnet ef migrations remove              # only if NOT applied anywhere
dotnet ef database update                # dev only
dotnet ef migrations script --idempotent --output migrate.sql
dotnet ef migrations bundle               # self-contained executable for CI/CD
RuleWhy
Never edit an applied migration Environments that already ran it won't re-run it. They'd silently diverge
Always read the generated migration EF sometimes generates a destructive operation — a drop-and-recreate where you expected a rename
Never Update-Database in production No review step, no rollback plan, and it needs schema-modify rights from the app
One logical change per migration Reviewable, and you can deploy them independently
Commit the snapshot file The model snapshot is how EF diffs. Merge conflicts there are real and must be resolved properly
The rename that deletes your data

Rename a property and EF often generates DropColumn followed by AddColumn — because it diffs the model, and it can't tell a rename from "one column gone, another arrived".

That compiles, runs, reports success, and silently discards every value in that column.

Fix it by editing the migration to use migrationBuilder.RenameColumn(...) before applying it anywhere. This is the single strongest argument for reading every generated migration — the destructive version looks exactly as normal as the safe one.

Applying migrations in production

ApproachAssessment
Idempotent SQL script, reviewed and applied by the pipeline Best default. Reviewable, auditable, works with existing DBA processes
Migration bundle — a self-contained executable Good for containerised pipelines. No SDK needed on the runner
Migrate() at startup Fine for a single-instance internal app. Dangerous when scaled out — several instances race, and the app needs DDL permissions permanently
Why startup migration breaks at scale

Three replicas starting simultaneously all call Migrate(). EF takes a lock on the history table, so they mostly serialise — but on a slow migration the others hit their startup timeout and the orchestrator restarts them mid-migration.

It also means the application's connection needs permission to alter the schema forever, which is a standing privilege you don't want. And there's no review gate: a migration that drops a column ships the moment the pod starts.

Run migrations as a separate, ordered pipeline step. In Kubernetes that's an init container or a Job that must complete before the rollout.

Zero-downtime schema change ⭐ Senior-level

The constraint that drives everything

During a rolling deploy, the old and new application versions run at the same time, against the same database.

So every migration must be compatible with both. That single requirement is what makes schema change hard, and it's what most people miss.

OperationSafe?Why
Add a nullable column✅Old code ignores it
Add a column with a default✅Old inserts get the default
Add a table or index✅Use ONLINE = ON for large tables
Add a NOT NULL column, no default❌Old code's inserts fail immediately
Drop or rename a column❌Old code still selects it
Narrow a type or tighten a constraint❌Old code can write values that now violate it

Expand / contract

  1. Expand. Add the new nullable column. Deploy. Nothing reads it yet.
  2. Dual write. Deploy code writing both old and new, still reading old.
  3. Backfill. Populate the new column in batches for existing rows.
  4. Switch reads. Deploy code reading the new column. Verify.
  5. Stop writing the old. Deploy.
  6. Contract. Drop the old column — in a later release, once you're confident.
Remember this

A rename becomes six deployments. That's not over-engineering — it's what "no downtime" costs.

Each step is independently safe and independently revertible. At no point are the two application versions incompatible with the schema.

The trap is compressing steps to save time. Doing 1 and 2 together is usually fine; doing 5 and 6 together means you can't roll back the previous release.

The backfill detail people get wrong

A single UPDATE over 50 million rows takes a table lock via lock escalation and blocks the application for the duration.

Backfill in batches of a few thousand, each its own transaction, with a small delay between them. Slower in wall-clock time, invisible to users — and resumable if it's interrupted, which a single giant statement is not.

Key takeaways
  • Fluent API in per-entity configuration files. Don't mix with attributes.
  • Configure delete behaviour explicitly — EF defaults to cascade on required relationships.
  • Skip navigations for plain many-to-many; an explicit entity once the join carries data.
  • Complex types over owned types for value objects — owned types have a hidden identity.
  • Store enums as strings, or pin explicit ordinal values forever.
  • Value converters break comparisons and range translation.
  • Read every generated migration — renames become drop-and-add and lose data.
  • Never edit an applied migration; add a new one.
  • Idempotent scripts or bundles in the pipeline, not Migrate() at startup.
  • Expand/contract, because old and new code run simultaneously during a rolling deploy.
  • Backfill in batches.

Common mistakes

  • Mixing attributes and fluent config, so the effective setting isn't where you're looking.
  • Relying on default cascade behaviour.
  • Enums as ordinals, then reordering the enum.
  • Editing an applied migration and diverging environments.
  • Not reading generated migrations, shipping a data-destroying rename.
  • Migrate() at startup on a scaled-out app.
  • Adding a NOT NULL column with no default during a rolling deploy.
  • Dropping a column in the same release that stops using it.
  • Backfilling with one huge UPDATE.
  • Not committing the model snapshot, or resolving its merge conflicts by picking one side.

Interview questions

Intermediate

How do you manage EF Core migrations across environments? 🔥 Must know
How I'd answer

"Migrations live in source control alongside the code that needs them, and I'd apply them through the pipeline rather than from a developer machine or at application startup."

"In development, dotnet ef database update is fine. I'd always read the generated migration before committing it, though — EF diffs the model, so it can't tell a rename from 'one column disappeared and another appeared'. It generates DropColumn then AddColumn, which runs successfully and silently discards every value in that column. That one has bitten enough people that reading the migration is non-negotiable for me."

"For production, I'd generate an idempotent SQL script — dotnet ef migrations script --idempotent. It has guards so it only applies what's missing, it can be reviewed like any other change, it fits whatever DBA process already exists, and it's auditable afterwards. Migration bundles are a good alternative in containerised pipelines since the runner doesn't need the SDK."

"I'd specifically avoid Migrate() at startup for anything scaled out. Three replicas starting together all try to migrate; EF locks the history table so they mostly serialise, but on a slow migration the others hit their startup probe timeout and get restarted mid-migration. It also means the app's own credentials need DDL permissions permanently, and there's no review gate — a migration that drops a column ships the instant a pod starts."

"So it becomes a separate ordered pipeline step: in Kubernetes, a Job or init container that must complete before the rollout proceeds."

"Two team practices that matter as much as the mechanics. Never edit an applied migration — environments that already ran it won't re-run it, so they diverge silently; add a new migration instead. And the model snapshot file is part of the migration, so merge conflicts in it have to be resolved properly rather than by picking a side, or the next generated diff will be wrong."

"I'd also keep migrations small — one logical change each. Easier to review, and they can be deployed independently, which matters a lot for the expand/contract sequence."

What they're really checking
  • Do you know why startup migration is a problem at scale?
  • Do you know about the rename data-loss trap?
  • Do you treat migrations as reviewable artefacts?
  • Do you know about the snapshot file?
Likely follow-ups
  • How do you roll back a migration?
  • What does --idempotent actually generate?
  • Two developers add migrations on separate branches. What happens?

Advanced / scenario

You need to rename a column on a table with 50 million rows, with no downtime. How? ⭐ Senior-level
How I'd answer

"The constraint that drives the whole answer is that during a rolling deploy the old and new application versions are both running against the same database. So every intermediate state has to work for both. That's what makes this six deployments rather than one."

"I'd use expand/contract:"

"1. Expand. Add the new column as nullable. Deploy. Old code ignores it, new code doesn't use it yet — completely safe, and revertible for free."

"2. Dual write. Deploy code that writes both columns and still reads the old one. Now every new or updated row has both values."

"3. Backfill. Populate the new column for existing rows. Critically, in batches — a few thousand rows per transaction with a short delay between. A single UPDATE over 50 million rows crosses the lock escalation threshold, takes a table lock, and blocks the application for however long it runs. Batching also makes it resumable, which a single statement isn't. I'd track progress so I can restart where it stopped."

"4. Verify, then switch reads. Confirm no rows are left unpopulated, then deploy code that reads the new column. This is the deployment I'd watch most closely, and it's still revertible because the old column is intact and being maintained."

"5. Stop writing the old column. Deploy."

"6. Contract. Drop the old column — in a later release, once we're confident and past the point of wanting to roll back."

"On the EF side specifically: I'd hand-write the migration for step 1 rather than let EF diff a renamed property, because that produces DropColumn plus AddColumn and destroys the data. And for a genuine in-place rename where downtime is acceptable, EF has RenameColumn, which is a metadata operation — worth knowing so you don't over-engineer when a maintenance window exists."

"The thing I'd push back on is compressing the steps. Combining 1 and 2 is usually fine. Combining 5 and 6 means you cannot roll back the previous release, because the old code would reference a column that no longer exists — you've traded a deployment for losing your escape route."

"And I'd ask the framing question first: is the rename worth six deployments? Sometimes it is — a genuinely misleading column name causes bugs. Sometimes the honest answer is to leave the column named as it is and map it in the fluent configuration with HasColumnName, so the domain model reads correctly and the database keeps its history. That's one line instead of a multi-week sequence, and proposing it is often the more senior answer."

What they're really checking
  • Do you know old and new code run simultaneously?
  • Do you know the expand/contract sequence?
  • Do you batch the backfill, and know why?
  • Do you keep rollback available at each step?
  • Do you consider whether it's worth doing at all?
Weak answers
  • Red flag: a single RenameColumn migration with no consideration of running instances.
  • Red flag: one big UPDATE to backfill.
  • Red flag: dropping the old column in the same release.
Likely follow-ups
  • How would you verify the backfill completed correctly?
  • What if the column is in a unique index?
  • How does this change if you also need to change the type?
