Development & Code Review

The daily loop — and why code review is the highest-leverage and most consistently misused practice in it.

🟡 Intermediate 🔥 Must know
Quick revision
  • PR size is the strongest predictor of review quality. Past ~400 lines, defect detection collapses and people approve on vibes.
  • Review is for what tests can't check: failure behaviour, backwards compatibility, concurrency, security, migration safety.
  • Anything a machine can check should be checked by a machine. Style debates in review are wasted attention.
  • Label comments blocking / suggestion / nit. Ambiguity about which is which is the main source of review friction.
  • "Done" means deployed, observable and revertible — not "code complete".
  • Never mix a refactor and a behaviour change in one PR.

Pull request size 🔥 Must know

Remember this

Small PRs aren't a discipline problem. They're a design skill.

PR sizeWhat actually happens
< 100 linesReviewed properly, usually within hours. Comments are substantive.
100–400 linesStill reviewable in one sitting. Practical upper bound for real scrutiny.
400–1000 linesReviewed in skimming mode. Comments cluster on the first files and on style.
> 1000 linesEffectively unreviewed. "LGTM" and defects pass through.

It's also a self-reinforcing loop: big PRs get reviewed slowly, slow review encourages batching, batching makes PRs bigger. Worth breaking deliberately.

How to actually get them small:

  • Separate refactor from behaviour. Two PRs: one that provably changes nothing, one that changes one thing.
  • Merge behind a feature flag. Incomplete work can land safely if it's unreachable, which removes the incentive to batch.
  • Expand and contract for schemas. Add the column, backfill, switch reads, remove the old one — four small safe changes instead of one dangerous one.
  • Land the interface and tests first, then the implementation.
Best practice

Write a short PR description covering: what changed, why, how you verified it, and what the reviewer should look hardest at. Two minutes of writing saves twenty minutes of reviewer archaeology — the cheapest thing you can do to get better reviews.

What to actually look for ⭐ Senior-level

Junior reviewers find naming and formatting. Senior reviewers find what will page someone at 3am.

CategoryQuestions to ask of the diff
Failure behaviourWhat happens on timeout, partial write, duplicate delivery, or a null from that call? Is the failure logged with enough context to diagnose?
ConcurrencyCan two requests hit this at once? Is there a read-modify-write with no guard? Any async void, or blocking on async code?
Data safetyIs the migration reversible? Does it lock a large table? Can old and new code run against this schema simultaneously?
Backwards compatibilityDoes this break an API consumer, a stored message shape, or a payload already sitting in a queue?
SecurityInput validated server-side? Authorization enforced in the query, not after retrieval? Concatenated SQL, secrets in config, PII in logs?
ResourcesDisposal, connection lifetime, unbounded collections, unbounded retries, missing cancellation or timeouts.
Performance shapeN+1 query. Work in a loop that should be a set operation. Sequential awaits that could run concurrently. Loading a whole table to count it.
ObservabilityIf this misbehaves in production, can you tell from telemetry?
TestsDo they test behaviour or implementation? Would they fail if the logic were wrong? Is the error path covered?

A diff worth blocking on

// PR: "Add loyalty points on order completion"
public async Task CompleteOrderAsync(Guid orderId)
{
    var order = await _db.Orders.FirstAsync(o => o.Id == orderId);
    order.Status = OrderStatus.Completed;

    var customer = await _db.Customers.FirstAsync(c => c.Id == order.CustomerId);
    customer.LoyaltyPoints += (int)(order.Total / 10);   // read-modify-write

    await _db.SaveChangesAsync();
    await _bus.PublishAsync(new OrderCompleted(orderId)); // dual write
}

None of these would be caught by a unit test with a mocked context:

  1. Lost update. The loyalty increment is a read-modify-write with no concurrency token. Two concurrent completions silently lose points.
  2. Wrong failure behaviour. FirstAsync throws on a missing order — a 500 instead of a 404. Worse, it throws on an already-completed order instead of being idempotent.
  3. Dual write. If the process dies between SaveChangesAsync and PublishAsync, the order is complete and no consumer ever hears about it.
public async Task<Result> CompleteOrderAsync(Guid orderId, CancellationToken ct)
{
    var order = await _db.Orders.SingleOrDefaultAsync(o => o.Id == orderId, ct);

    if (order is null) return Result.NotFound();
    if (order.Status == OrderStatus.Completed) return Result.Ok();   // idempotent

    order.Complete();                       // domain method enforces legal transition

    var customer = await _db.Customers.SingleAsync(c => c.Id == order.CustomerId, ct);
    customer.AddLoyaltyPoints(order.Total); // RowVersion causes a retry on conflict

    // event committed in the SAME transaction as the state change
    _db.OutboxMessages.Add(OutboxMessage.For(new OrderCompleted(order.Id)));

    await _db.SaveChangesAsync(ct);
    return Result.Ok();
}

The fix isn't "more code" — it's moving three decisions somewhere they can't be forgotten: the legal transition into the domain object, delivery atomicity into the outbox, and lost-update protection into an optimistic concurrency token.

Note the added CancellationToken too — a request the client abandoned shouldn't keep holding a connection.

Three habits do most of the work:

  1. Label severity — blocking, suggestion, nit — so the author knows what gates the merge.
  2. Explain the failure, not just the rule, so the author learns the reasoning rather than the ritual.
  3. Switch to a call after three round trips. Async text is a terrible medium for disagreement and an excellent medium for escalating it.
Common mistake

The reviewer who rewrites the author's approach in comments. It's slow, demoralising, and usually produces a worse result than a five-minute conversation. If a design is genuinely wrong, the problem happened before the PR — the fix is earlier involvement, not a longer comment thread.

Definition of Done 🟡 Intermediate

A shared DoD stops "done" meaning six different things. A realistic one:

  • Acceptance criteria met, including the error paths.
  • Automated tests at the right level, passing in CI, and they'd fail if the logic were wrong.
  • Reviewed and approved; blocking comments resolved.
  • Telemetry added — the feature can be seen working or failing in production.
  • Backwards compatible, or a documented migration and rollback path exists.
  • Deployed to production (possibly flag-off) — not sitting in a branch.
  • Docs updated where behaviour changed: API docs, runbook, ADR.
  • No known defects deferred without a tracked ticket.
Senior signal

"Done" including deployed and observable is a real dividing line. Teams where done means "merged" accumulate a queue of unreleased changes, which makes every release bigger, riskier and harder to diagnose — the opposite of what they intended.

The principle: every rule a human enforces in review gets enforced inconsistently and resentfully. Encode it or drop it.

Key takeaways
  • Keep PRs under ~400 lines. It's a design skill, not willpower.
  • Review for failure behaviour, concurrency, data safety and rollout — not naming.
  • Label comments by severity, and explain the failure not the rule.
  • Never mix refactoring with behaviour change — it breaks review and git bisect.
  • Automate everything a linter can check.
  • "Done" includes deployed, observable and revertible.

Common mistakes

  • Enormous PRs, then complaining reviews are slow. The causation runs the other way.
  • Review as style enforcement while concurrency and failure handling go unexamined.
  • Approving without understanding, because the author is senior or the queue is long.
  • Mixing refactoring with behaviour change, making both unreviewable and unbisectable.
  • Requiring two approvals on everything, converting review into a queueing problem.
  • No follow-through on non-blocking comments — they're either worth a ticket or worth deleting.

Interview questions

What do you look for in a code review?
How I'd answer

"I read for the things automation and tests can't see. Formatting, naming conventions and obvious null handling should be caught by analysers before the PR exists — if I'm spending review attention there, the pipeline is under-configured."

"In priority order: failure behaviour — what this does on timeout, duplicate delivery or partial failure. Concurrency — whether two requests can interleave and corrupt state. Data safety — whether a migration is reversible and whether old and new code can coexist during a rolling deploy. Authorization — whether it's enforced in the query rather than filtered afterwards. And resource handling: disposal, timeouts, cancellation."

"Then design fit: does this belong in this layer, and will the next similar requirement fit or force a copy-paste?"

"I read the tests as carefully as the code. Tests that assert on implementation details are a liability — they break on every refactor and teach the team that tests are noise."

"And I'm explicit about severity. I label comments blocking, suggestion or nit, because the most common review friction I've seen is an author not knowing whether a comment is a gate or an opinion."

What they're really checking
  • Does your review add value beyond a linter?
  • Do you think about production behaviour and rollout?
  • Do you communicate in a way that keeps a team functional?
Weak answers
  • Red flag: naming, formatting and "does it follow SOLID" as the whole answer.
  • Red flag: no mention of tests, failure paths or rollout safety.
Likely follow-ups
  • You're reviewing a 2,000-line PR. What do you do?
  • How do you review code in an area you don't know well?
  • Show me a bug you caught in review that tests wouldn't have.
How do you handle a reviewer blocking your PR over something you disagree with?
How I'd answer

"First I work out whether we're disagreeing about facts or preference, because they need different handling."

"If it's factual — 'this will deadlock', 'this breaks the mobile client' — the fastest resolution is evidence. Write the test, run it, share the result. That ends most factual disputes in minutes and leaves no residue."

"If it's preference — a different but equally valid structure — I weigh it against the cost of the argument. If their approach isn't worse, I take it. Consistency has real value, and the PR shipping today has more value than my structural preference."

"If I think it's genuinely worse, I say why once, concretely, and ask what would change their mind. If we're still stuck after one round trip, I switch medium — a ten-minute call resolves what twenty comments won't."

"And if we still disagree, I'd rather escalate to a team decision than to authority: 'we disagree on this pattern, let's decide it as a convention and write it down.' That turns a recurring argument into a settled rule. What I avoid is either quietly resenting it or going around the reviewer — both cost far more than the code."

What they're really checking
  • Emotional maturity under disagreement — a strong predictor of seniority.
  • Can you separate substantive from stylistic disagreement?
Likely follow-ups
  • What if the blocker is a principal engineer and you're new?
  • How do you stop the same argument recurring every sprint?
You need to refactor a large legacy class and deliver a feature in it. How do you sequence it?
How I'd answer

"I'd never do both in one change. The reviewer can't distinguish the behaviour change from the movement, and if something breaks in production, bisecting a combined commit tells you very little."

"So: characterisation tests first, then refactor with no behaviour change, then the feature."

"Characterisation tests are the step people skip. Legacy code often has no tests and no spec, so before touching it I write tests that assert what it currently does — including behaviour that looks wrong. That gives me a net proving the refactor changed nothing, and it frequently surfaces surprising existing behaviour that turns out to be depended on somewhere."

"Then I refactor in the smallest steps that keep the build green — extract a method, introduce a seam, move a dependency to a constructor parameter — merging frequently rather than accumulating a giant branch."

"If the class is genuinely hostile, I wouldn't attempt a full rewrite. I'd carve out just the part the feature needs — a strangler approach at class scale — and leave the rest. Refactoring the whole thing is rarely justified by the feature, and an unfinished large refactor is worse than none, because it leaves two patterns in place."

What they're really checking
  • Discipline about separating mechanical from semantic change.
  • Do you know how to work safely without a test suite?
  • Do you scope refactoring to the value it delivers?
Weak answers
  • Red flag: "I'd rewrite it properly."
  • Red flag: refactoring with no tests, relying on careful reading.
Likely follow-ups
  • The class has a static dependency you can't inject. What now?
  • How do you write a characterisation test for something that hits the database and sends email?
