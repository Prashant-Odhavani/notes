Operations & Incident Management

Knowing your system is healthy, finding out fast when it isn't, and handling the hour when it isn't.

🟡 Intermediate 🔴 Advanced ⭐ Senior-level
Quick revision
  • Monitoring answers questions you knew to ask. Observability lets you answer questions you didn't anticipate, from data already being emitted.
  • Metrics = cheap, aggregate, alertable. Logs = detailed, expensive. Traces = causality across services. You need all three, for different jobs.
  • SLI = the measurement. SLO = your target. SLA = the contract. Error budget = 1 − SLO.
  • Alert on symptoms users feel, not causes. High CPU isn't an incident. Failing checkouts are.
  • Every page must be actionable, urgent, and have a runbook. Otherwise it's a dashboard item.
  • Postmortems are blameless because good people make errors in badly-designed systems. Output: two or three tracked actions.

Monitoring vs observability 🔥 Must know

Remember this

Monitoring: "is the thing I predicted would break, broken?"

Observability: "why is p99 latency doubled for one tenant, only on uploads over 10MB, only since Tuesday?" — answerable without shipping new code.

The practical difference is usually dimensionality and correlation.

  • Record request duration → you can alert on it, but you can't decompose it.
  • Record duration with tenant, endpoint, version and outcome as dimensions, sharing a correlation ID with logs and traces → you can slice your way to the cause.

What to instrument

Two standard frameworks, both worth naming in an interview:

  • RED (request-driven services): Rate, Errors, Duration — per endpoint and per dependency call.
  • USE (resources): Utilisation, Saturation, Errors — CPU, memory, connection pools, thread pools, queues.

Saturation is the one people miss. It tells you a system is about to fail rather than that it already has: connection pool at 95%, thread pool queue growing, message lag increasing. Those are the metrics worth paging on early.

// Histogram, not a gauge: percentiles matter, averages hide the tail.
private static readonly Histogram<double> Duration =
    Telemetry.Meter.CreateHistogram<double>("orders.submit.duration", "ms");

public async Task<IResult> SubmitAsync(SubmitOrder cmd, CancellationToken ct)
{
    using var activity = Telemetry.Source.StartActivity("SubmitOrder");
    activity?.SetTag("tenant.id", cmd.TenantId);

    var sw = Stopwatch.GetTimestamp();
    var outcome = "ok";
    try
    {
        return Results.Ok(await orders.SubmitAsync(cmd, ct));
    }
    catch (InsufficientStockException ex)
    {
        outcome = "insufficient_stock";      // EXPECTED - not an error rate
        log.LogInformation(ex, "Rejected order for {Tenant}", cmd.TenantId);
        return Results.Conflict(ex.Message);
    }
    catch (Exception ex)
    {
        outcome = "error";
        activity?.SetStatus(ActivityStatusCode.Error, ex.Message);
        log.LogError(ex, "Order submit failed for {Tenant}", cmd.TenantId);
        throw;
    }
    finally
    {
        Duration.Record(Stopwatch.GetElapsedTime(sw).TotalMilliseconds,
            new KeyValuePair<string, object?>("outcome", outcome),
            new KeyValuePair<string, object?>("tenant", cmd.TenantId));
    }
}

Three decisions doing real work here:

  1. A histogram, so you can compute p95/p99 rather than a mean that hides the tail.
  2. An outcome dimension separating expected business rejections from unexpected failures — so a spike in out-of-stock doesn't look like an outage.
  3. Tenant as a dimension, which in a multi-tenant system is what lets you tell "everything is broken" from "one tenant is broken".
Common mistake — cardinality explosion

Putting unbounded values into metric dimensions: user IDs, order IDs, raw URLs with parameters. Every distinct combination creates a new time series. This will either bankrupt your telemetry bill or get your metrics dropped.

High-cardinality identifiers belong in logs and traces. Tenant is usually acceptable (hundreds). User usually isn't (millions).

SLIs, SLOs, SLAs and error budgets 🔥 Must know

TermWhat it isExample
SLIThe measurement — a user-visible property% of checkout requests returning 2xx within 800ms
SLOYour internal target over a window99.5% over 30 rolling days
SLAThe contractual promise, with consequences99.0% monthly, or service credits apply
Error budget1 − SLO: the failure you're allowed to spend0.5% of 30 days ≈ 3.6 hours

The SLA is always looser than the SLO — you want internal alarms firing well before contractual breach.

Why the error budget is the useful idea

It turns "should we ship this risky change?" from an opinion into arithmetic.

Budget remaining → take risks: ship the migration, deploy on Thursday. Budget exhausted → reliability work takes priority over features until it recovers.

Senior signal

Choosing the right SLI matters more than choosing the right number. "Availability of the API" measured by a health endpoint can read 100% while every real request fails.

A good SLI is measured as close to the user as possible and reflects something they care about: successful checkouts, documents processed within the promised window, search results returned. If you only say one thing about SLOs in an interview, say that.

Alerting people don't learn to ignore 🔴 Advanced

Alert fatigue is the dominant operational failure mode. A team paged six times a night for things that resolve themselves will eventually miss the one that matters — not through negligence, but through entirely rational adaptation.

Alert onNot onWhy

Certificate expiring in 14 daysCertificate expiredPredictable failures should be prevented, not alerted on

Rules that survive a real on-call rotation:

  • Every page must be actionable. If the only possible action is "watch it", it shouldn't have woken anyone.
  • Every page needs a runbook link in the alert: what it means, how to confirm, what to try first, how to escalate.
  • Two tiers. Page for user-impacting and urgent. Ticket for everything else. Most alerts belong in tier two.
  • Review alerts monthly. Delete any that fired and required no action. This one habit does more for on-call health than any tooling.
  • Alert on absence too. A nightly job that stops running produces no errors at all. Only a "didn't complete by 03:00" alert catches it.

Incident management 🟡 Intermediate

The point of incident process is to stop smart people doing uncoordinated things under stress.

Four roles, even if one person holds several on a small team:

  • Incident commander — owns the response, makes decisions, does not debug. The common failure in small teams is that the best debugger becomes commander and then stops commanding because they're deep in a stack trace.
  • Investigators — the people changing things, one at a time, announcing each change.
  • Communications — updates stakeholders on a fixed cadence so nobody has to interrupt the responders.
  • Scribe — timestamps what was observed and done. Invaluable for the postmortem; nobody remembers accurately afterwards.

The response order

  1. Stabilise before diagnosing. If a rollback or flag flip restores service, do it and investigate afterwards. Understanding isn't required for recovery.
  2. Establish blast radius. Who's affected, which regions, which tenants, which operations. This drives severity and communication.
  3. Look at what changed. The overwhelming majority of incidents follow a change — a deploy, a config edit, a flag, a certificate, a threshold crossed by organic growth. Check the deployment timeline before theorising.
  4. One change at a time. Parallel fixes make it impossible to know what worked, and can compound the failure.
  5. Communicate on a timer, even with nothing new. "Still investigating, next update in 30 minutes" prevents the flood of individual questions.
Production trap

Restarting the service because "it fixes it" — without capturing diagnostics first. You've destroyed the evidence (memory dump, thread state, current connections) and guaranteed the incident recurs with no more information than last time.

Capture first when it costs seconds: memory dump, metrics snapshot, thread dump. Then restart.

Severity levels

SevMeaningResponse
1Complete outage or data loss; core business stoppedPage immediately, all hands, exec comms, status page

Agreeing these in advance is what stops the argument about whether something is "really" a Sev 1 while it's on fire. Err upward — downgrading an over-declared incident is cheap.

Postmortems ⭐ Senior-level

What blameless actually means

Not "nobody made a mistake". It means the analysis targets the conditions that let a normal human error become an outage — because those are what you can change.

Not actionable

"Priya ran the wrong script."

Four actionable findings

"A destructive script could be run against production from a laptop, with no confirmation, no dry-run, and nothing detected it for 40 minutes."

A postmortem worth writing contains:

  • Impact in user terms: how many users, which operations, how long, what data.
  • Timeline with timestamps: started, detected, mitigated, resolved. Detection lag is often the most damning number and the most fixable.
  • Contributing factors, plural. Real incidents have several — a latent bug, a missing alert, a misleading dashboard, a rushed change. A single "root cause" usually means the analysis stopped early.
  • What went well. Tells you which investments paid off.
  • Actions — two or three, each with an owner and a date. Twenty actions means zero actions.

The metric to watch across postmortems isn't how many you write — it's whether time-to-detect is falling. Prevention has diminishing returns. Detection and recovery speed don't.

On-call that's sustainable

  • The team that writes the code carries the pager. Nothing improves reliability faster than the author being woken by their own alert.
  • Rotation large enough that on-call recurs no more than every 4–6 weeks.
  • Compensate it, and give time back after a bad night.
  • Track pages per shift with an explicit budget. More than one or two a night means fixing alerting or reliability takes priority over features.
  • Handover at the end of each shift: what fired, what's still degraded, what to watch.
Key takeaways
  • Metrics to alert, traces and logs to diagnose. Correlation ID ties them together.
  • Keep unbounded IDs out of metric dimensions.
  • Pick SLIs close to the user. A health endpoint is not availability.
  • Alert on symptoms and saturation, never on CPU alone.
  • Stabilise, then diagnose. Capture evidence before restarting.
  • Postmortems should produce 2–3 owned actions and drive down time-to-detect.

Common mistakes

  • Dashboards nobody looks at, alerts everyone silences.
  • Logging everything at Information level, so the signal is unfindable and the bill is enormous.
  • No correlation ID, so a request can't be followed across services. Cheap to add, transformative during an incident.
  • Alerting on causes (CPU, memory) rather than symptoms (errors, latency).
  • Postmortems ending in "be more careful" or a new mandatory review step.
  • Secrets or PII in logs — a security incident created by the observability system.
  • Measuring MTTR without time-to-detect, which is usually the larger half.

Interview questions

What's the difference between monitoring and observability?
How I'd answer

"Monitoring is checking known conditions. You decide in advance what to measure and what value is bad, and you get alerted when it crosses. It handles the failure modes you anticipated."

"Observability is a property of the system: whether the telemetry it already emits is rich enough to answer questions you didn't anticipate, without shipping new code."

"The practical test is a novel question — 'why is p99 latency doubled for one tenant, only on uploads over 10MB, only since Tuesday?' With monitoring alone you can't answer that; you'd add logging and wait for it to happen again. With good observability you slice existing telemetry by tenant, size bucket and version and find it in minutes."

"Concretely the difference is dimensionality and correlation. Recording request duration gives you an alert. Recording it with tenant, endpoint, outcome and version as dimensions, plus a correlation ID shared with logs and traces, gives you the ability to decompose."

"I wouldn't present observability as replacing monitoring though. Metrics are what you alert on because they're cheap and aggregate well. Traces and structured logs are what you use after the alert fires, to find out why."

What they're really checking
  • Can you distinguish them without reciting "three pillars" as a slogan?
  • Have you actually debugged something using telemetry?
Weak answers
  • Red flag: "observability is metrics, logs and traces" — that lists the inputs, not the property.
  • Red flag: naming vendors instead of explaining the concept.
Likely follow-ups
  • What would you add to a service that currently has only logs?
  • How do you control telemetry cost at high volume?
  • What is cardinality and why does it matter?
You're paged: the API is returning 500s for about 20% of requests. Walk me through it. ⭐ Senior-level
How I'd answer

"First I establish scope and impact, because that drives everything. Which endpoints, which regions, which tenants — and is it 20% of all traffic, or 100% of one slice?"

"That distinction eliminates most of the hypothesis space in about a minute. A uniform 20% usually means one unhealthy instance out of five, or a dependency failing intermittently. A concentrated 20% — one tenant, one endpoint — points at data or a specific code path."

"In parallel I check what changed. Most incidents follow a change, so: deployment timeline, feature flags, config edits, infrastructure events. If a deploy went out in the window, that's my working hypothesis and I'd seriously consider rolling back or flipping the flag before diagnosing further. Restoring service is the priority; understanding can happen afterwards with the evidence I capture on the way."

"If nothing changed on our side, I look at saturation and dependencies — connection pool utilisation, thread pool queue length, database CPU, downstream error rates and latency."

"There's a common shape worth calling out: a slow dependency causes requests to pile up until the thread or connection pool exhausts, and then the symptom is 500s on endpoints that have nothing to do with the slow dependency. So I'd explicitly check whether the failing endpoints share a resource with a slow one, rather than assuming they share a bug."

"Throughout: a running note with timestamps, communication on a fixed cadence, one change at a time. Once service is restored, capture anything perishable — a dump if a process is misbehaving — before recycling. Then the postmortem, where the question I most want answered is why we found out from an alert about 500s rather than something that would have caught it earlier."

What they're really checking
  • Do you stabilise first, or debug while customers are down?
  • Do you narrow systematically rather than guessing?
  • Do you know resource exhaustion produces symptoms far from its cause?
Weak answers
  • Red flag: "check the logs" as the entire method.
  • Red flag: restarting everything immediately, destroying the evidence.
  • Red flag: no mention of communication or of what changed recently.
Likely follow-ups
  • The 500s are only from one tenant. Does that change your approach?
  • Logs show TaskCanceledException from an HTTP client. What now?
  • Rollback didn't fix it. What does that tell you?
How do you set an SLO for a service that's never had one?
How I'd answer

"I start from the user journey, not the infrastructure. Pick the two or three operations that matter most — for a commerce API probably search, add-to-cart and checkout — and define an SLI for each that reflects what the user experiences: proportion of requests succeeding within a latency threshold, measured as close to the user as possible."

"Then I look at current performance before choosing a target. An SLO the service has never met isn't a target, it's a permanent alarm the team learns to ignore. If we're at 99.3%, setting 99.9% means the error budget is exhausted forever and every rule attached to it becomes meaningless."

"So I'd set the initial target slightly above recent actual performance, make it visible, and tighten it deliberately as reliability work lands."

"I'd also want the target justified by what the business needs rather than by how many nines sound impressive. Each extra nine costs disproportionately more — multi-region, redundancy, more sophisticated failover — and for many internal or B2B systems 99.9% is genuinely enough. Asking 'what does an hour of downtime cost us, and when?' produces a more honest answer than asking what target we want."

"Finally, an SLO only matters if something follows from breaching it. So I'd agree the consequence up front: when the error budget is exhausted, reliability work takes priority over features until it recovers. Without that, it's just a number on a dashboard."

What they're really checking
  • Do you pick user-centric indicators over infrastructure metrics?
  • Do you understand the cost curve of additional nines?
  • Do you connect the SLO to a decision rule?
Likely follow-ups
  • Your dependency offers 99.9%. What can you promise on top of it?
  • How do you set an SLO for an async pipeline where there's no request?
