Agile, Scrum, Kanban & DevOps

The process layer — plus technical debt, refactoring and documentation, which is where process meets code.

🟢 Beginner 🟡 Intermediate
Quick revision
  • Agile is a set of values about responding to change. Scrum and Kanban are two mechanisms for creating short feedback loops. Confusing the values with the ceremonies is the standard mistake.
  • Scrum = fixed iterations, scope frozen inside them. Kanban = continuous flow with WIP limits. Choose by the shape of the work.
  • DevOps = removing the handoff between building and running. "You build it, you run it."
  • Technical debt is only a useful word if you talk about the interest — what it costs per sprint.
  • Deliberate debt taken for a deadline is a legitimate decision. Accidental debt from ignorance isn't the same thing.
  • Documentation that survives lives next to the code and answers why, not what.

Agile, minus the industry 🟢 Beginner

The underlying claim is narrow and defensible:

For most software, requirements can't be fully known up front. So a process that produces working software frequently and adapts will beat one that plans exhaustively and executes.

Everything else — ceremonies, certifications, tooling — is implementation detail. Most of the industry's dysfunction comes from adopting the detail and discarding the claim.

The diagnostic that actually works

How quickly can feedback change what we build next?

A team running every ceremony perfectly but shipping twice a year has the form without the substance. A team with no ceremonies that releases daily and adjusts is doing the thing that matters.

Scrum vs Kanban 🔥 Must know

ScrumKanban
CadenceFixed sprints (1–4 weeks), scope frozen insideContinuous flow; work pulled as capacity frees
Core constraintThe sprint commitmentWIP limits per column
PlanningUp front per sprintJust in time per item
Key metricsVelocity, sprint burndownCycle time, throughput, WIP, flow efficiency
RolesPO, Scrum Master, DevelopersNone prescribed
Good fitFeature work with plannable scope; teams needing rhythmSupport, ops, incident-heavy, unpredictable arrivals
Fails whenPriorities change mid-sprint constantly; interrupts dominateNo WIP discipline — becomes an infinite to-do list with a board

The honest recommendation for most product teams: Scrum's rhythm plus Kanban's WIP discipline — which is roughly what "Scrumban" means in practice.

Sprint boundaries give useful checkpoints for planning and reflection. WIP limits are what actually reduce cycle time, via Little's Law.

And if a team is drowning in unplanned work, Kanban is the honest choice. Pretending you can commit to a sprint while 40% of capacity is interrupts just produces failed sprints and demoralisation.

Common mistake

Retros that generate ten actions and complete none.

The pattern that works: start each retro by reviewing the previous actions. If they weren't done, that's the first topic — usually they were too vague or had no owner. One completed improvement per fortnight compounds. Ten uncompleted ones teach the team that retros are theatre.

DevOps 🟡 Intermediate

One line: the people who build the software also run it, so the incentives stop being opposed.

DevOps started as a response to a specific dysfunction: developers rewarded for shipping change, operators rewarded for stability, throwing work over a wall at each other.

What actually changes when a team owns operations:

  • Observability stops being an afterthought — the person who'll debug it at 2am is writing it now.
  • Deployment gets automated quickly, because the team doing it manually is the team suffering it.
  • Reliability work gets prioritised honestly, because the cost is felt rather than exported.
The caveat worth stating in an interview

"You build it, you run it" is only sustainable with a real rotation, compensation and enough people. Imposed on a team of four with no alerting hygiene, it's just unpaid overtime with a modern name.

Platform teams exist to make it viable — paved paths, shared pipelines, observability infrastructure — so product teams can own their services without each reinventing the operational layer.

Technical debt ⭐ Senior-level

Remember this

The metaphor only works if you talk about the interest — what it costs you every sprint.

Without that, "technical debt" just means "code I don't like".

TypeOriginHow to treat it
Deliberate + prudent"We ship the simple version for the deadline and fix it in March"Legitimate. Record it with the reason and a date — it's a decision, not a failure
Deliberate + reckless"No time for tests"Usually a false economy — the rework arrives in the same release
Accidental + prudent"Now it's built, we see the better design"Normal and healthy. Refactor next time you touch it
Accidental + recklessNobody knew betterA skills and review problem, not a scheduling one
Bit rotFramework EOL, deprecated APIsNon-negotiable scheduled maintenance — the deadline is set by someone else

Getting debt work funded

Arguments that fail

"The code is messy."
"It's not clean architecture."
"We need a rewrite quarter."

Arguments that work

"Changes in billing take 3× longer than elsewhere, and 60% of last quarter's incidents came from there."

"This framework stops getting security updates in November."

The delivery mechanism matters as much as the argument. Large refactoring projects are hard to fund and frequently abandoned halfway, leaving two patterns in the codebase — worse than either.

Continuous small repayment attached to feature work is more effective and rarely needs permission: when you touch an area, leave it better, bounded to the change you're making. Reserving a fixed slice of capacity (commonly 10–20%) formalises it without a business case each time.

Senior signal — knowing what NOT to fix

Code that's ugly but stable, rarely touched and well covered costs almost nothing to leave alone. Debt only has interest if you keep visiting it.

So prioritise by change frequency, not by how uncomfortable the code makes you. "I'd leave that alone, we haven't touched it in two years" is judgement, not laziness.

Refactoring as a habit

Refactoring means changing structure without changing behaviour. That constraint is what makes it safe — abandoning it is what makes "refactors" break production.

  • Tests first. Without them you're not refactoring, you're rewriting and hoping. If tests don't exist, write characterisation tests that pin current behaviour — including behaviour that looks wrong.
  • Small steps, build green, commit often. A refactor branch open for two weeks will conflict with everything.
  • Never in the same commit as behaviour change — see development.
  • Prefer the boy-scout rule (leave the area slightly better) over scheduled refactoring projects.
  • Know when to stop. Refactoring toward an abstraction that isn't needed yet is over-engineering with better branding.

Documentation that survives 🟡 Intermediate

Most documentation dies because it duplicates what the code already says — so it drifts, and then it actively misleads.

The documentation worth writing captures what code can't:

ArtifactAnswersWhere it lives
READMEHow do I run, test and debug this locally?Repo root; verified by a new joiner following it
ADRWhy is it built this way, and what did we reject?/docs/adr, immutable — see ADRs
RunbookThis alert fired — what do I do?Linked directly from the alert
API referenceWhat's the contract?Generated from code (OpenAPI), never hand-maintained
Architecture overviewWhat are the components and how do they talk?One diagram, in the repo, dated
Onboarding guideWhat context does a new engineer need?Updated by each new joiner as they hit gaps

Two rules keep it honest: put it in the repository so it's versioned and reviewed with the code, and prefer why over what — the code already documents what it does, and does it accurately.

Key takeaways
  • Pick Scrum or Kanban by how work arrives, not by preference.
  • WIP limits reduce cycle time. Ceremonies alone don't.
  • Retros: review last time's actions first, and finish one or two.
  • DevOps is an ownership model. The tooling follows from it.
  • Fund debt with change-time and incident data, and repay it incrementally.
  • Don't repay debt in code you never touch.
  • Documentation lives in the repo and explains why.

Common mistakes

  • Adopting ceremonies without shortening the feedback loop — form without function.
  • Velocity used as a performance metric, which guarantees estimate inflation.
  • Sprint commitments treated as promises to external stakeholders, converting a planning tool into a liability.
  • "Definition of done" stopping at merged, so unreleased work piles up.
  • Debt discussed as an aesthetic complaint rather than a measurable cost.
  • Documentation written once at project start — worse than none, because people trust it.
  • Retro actions with no owner.

Interview questions

Scrum or Kanban — which do you prefer?
How I'd answer

"I don't have a fixed preference — I'd pick based on how the work arrives."

"Scrum assumes you can meaningfully commit to a scope for a fixed period, which works for feature development where priorities are stable for a couple of weeks. Kanban assumes work arrives unpredictably and optimises flow instead, which is right for support-heavy or platform teams."

"The failure I've seen most is running Scrum in an environment that's really Kanban. The team commits, 40% of capacity goes to production issues, the sprint fails, and everyone concludes the team is underperforming — when the process was simply mismatched. There I'd either move to Kanban, or explicitly reserve capacity for unplanned work and commit to less. The honest fix is to stop pretending the work is plannable."

"The elements I actually care about aren't framework-specific: small batches, WIP limits, a real demo to someone who'll use the software, and a retro that produces one action that gets done. I'd take a team with those and no framework over a certified Scrum team without them."

"If pushed for a default: sprint cadence for rhythm and planning, with Kanban's WIP limits inside it — because WIP limits are what actually reduce cycle time."

What they're really checking
  • Can you reason about process fit instead of advocating a brand?
  • Have you seen process fail, and do you know why?
Weak answers
  • Red flag: reciting the Scrum guide's roles and events.
  • Red flag: "process is overhead, we just ship" — real teams need coordination mechanisms.
Likely follow-ups
  • How would you handle a team where half the capacity is unplanned support?
  • What if the PO changes priorities mid-sprint every sprint?
How do you convince management to invest in reducing technical debt? ⭐ Senior-level
How I'd answer

"I'd stop using the phrase 'technical debt'. To a non-engineer it sounds like engineers wanting time to make the code nicer. I'd translate it into what the business already tracks: delivery speed, incident frequency, and risk."

"That means gathering evidence first. Which modules take disproportionately long to change — measurable from PR cycle time by area. Where do incidents originate — measurable from postmortems. What manual work recurs every sprint."

"Then the pitch is concrete: 'changes to billing take about three times longer than equivalent work elsewhere, and it was implicated in six of our nine incidents last quarter. Two sprints on it should bring change time down to normal, which pays back within a quarter.' That's an investment case — it can be argued with or accepted on its merits."

"I'd also propose the smallest credible slice rather than a rewrite. A large remediation project is a big bet that's easy to refuse and easy to abandon halfway. Fixing the single worst area, showing a measurable improvement, then asking for the next one is what builds the credibility that funds the rest."

"And for the ongoing baseline I'd prefer a standing allocation — maybe 15% of capacity — so routine repayment doesn't need a business case every time."

"The other half is prioritisation. Not all debt is worth repaying. Code that's ugly but stable and rarely touched has almost no interest. Targeting by change frequency and incident correlation is also what makes the argument credible — it shows I'm proposing to fix the expensive parts, not everything that offends me."

What they're really checking
  • Can you communicate engineering concerns in business terms?
  • Do you prioritise debt by cost rather than taste?
  • Do you propose incremental, verifiable work?
Weak answers
  • Red flag: "management should just trust engineers".
  • Red flag: asking for a rewrite or a dedicated "tech debt quarter".
Likely follow-ups
  • What if you get the two sprints and it takes four?
  • How do you stop the debt reaccumulating?
What does DevOps mean to you, beyond tooling?
How I'd answer

"It's about removing the handoff between the people who build software and the people who run it — because that handoff creates opposed incentives, and every dysfunction follows from that. The tooling is a consequence, not the substance."

"Concretely, on a team that has it, the same people write the code, own the pipeline, carry the pager and write the postmortem."

"That changes behaviour in ways process mandates can't. People add useful telemetry because they'll be the ones searching for it at 2am. Deployment becomes boring quickly because nobody wants a stressful manual procedure they personally have to run. Reliability work gets prioritised because the cost is felt by the team rather than exported."

"I'd add one caveat, because it's where the idea gets abused: 'you build it, you run it' without a real rotation, compensation and enough headcount is just unpaid on-call. Making it sustainable usually needs a platform capability — shared pipelines, paved-path deployment, observability infrastructure — so each product team isn't rebuilding the operational fundamentals."

"And the metric I'd watch to know it's working is the DORA set, particularly time to restore — shared ownership shows up there first."

What they're really checking
  • Do you understand it as an ownership model rather than a job title or toolchain?
  • Do you recognise the sustainability caveat?
Weak answers
  • Red flag: listing tools — Docker, Kubernetes, Jenkins — as the definition.
  • Red flag: "DevOps is a role we hire for" with no acknowledgement of the tension.
Likely follow-ups
  • How do you introduce this in an organisation with a separate ops department?
  • What should a platform team own, and what shouldn't it?
