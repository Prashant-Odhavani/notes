Testing & Quality

Testing as part of delivery rather than a phase — what runs where, who owns it, and how quality gates stop being theatre.

🟡 Intermediate 🔥 Must know
Scope of this page

This is testing as a lifecycle concern. The mechanics — test doubles, xUnit, mocking, integration setup, coverage, flaky tests — are in section 31.

Quick revision
  • Shift-left = move each check as early as it can meaningfully run. That includes types, analysers and contract tests — not just "write more unit tests".
  • A quality gate only counts if failing it actually blocks and someone acts. Gates people override train the team to ignore signals.
  • Test strategy is the senior artefact: what's verified where, what's deliberately not tested, and how fast the suite must stay.
  • Environment fidelity beats environment count.
  • Flaky tests are the most corrosive quality problem there is. Quarantine them the same day.
  • The team owns quality. QA owns testing expertise.

Shift-left, properly understood 🟡 Intermediate

The mental model worth carrying is a ladder from cheapest feedback to most expensive:

Senior signal — the row candidates forget

Some defects cannot be found before production at any reasonable cost: real traffic shapes, real data skew, real third-party behaviour, real cache hit ratios.

Mature teams accept that and invest in making production failures small, detectable and reversible — rather than pretending a staging environment eliminates them. Saying that reads as experience, as long as you pair it with the controls that make it responsible: flags, canaries, and a rollback trigger defined in advance.

Owning a test strategy ⭐ Senior-level

It's usually half a page, and its main value is the explicit decisions about what not to test. Four questions:

  1. What must never break? Rank flows by cost of failure — money movement, data loss, auth. Those get redundant coverage: unit + integration + a production synthetic check.
  2. Where is each behaviour verified? Domain rules at unit level. Persistence, transactions and query correctness at integration level against a real database engine. A small number of end-to-end journeys. Verifying the same rule at three levels is waste that also slows everyone down.
  3. What are we deliberately not testing? Third-party library internals, framework behaviour, trivial getters, generated code, UI layout that changes weekly. Writing this down prevents coverage-driven busywork.
  4. What's the time budget? PR feedback under about 10 minutes. Past that, people batch changes and review less carefully.

Production trap — flaky tests

This is the most corrosive quality problem a team can have, because it turns a red build from information into noise. Once "just re-run it" is normal, genuine failures get re-run too.

The only strategy that works: quarantine the flaky test out of the blocking suite immediately, raise a ticket with an owner, fix or delete it within a fixed window. A deleted flaky test is strictly better than a tolerated one.

Environments and test data 🔴 Advanced

The typical dysfunction: four environments, none matching production, all shared, all with stale data, and a queue to use them.

  • Prefer ephemeral to shared. A database container per test run (Testcontainers) removes the whole class of "someone else's test data broke mine" failures and lets tests run in parallel.
  • Fidelity where it matters. Run integration tests against the same database engine and version as production. An in-memory provider will accept queries the real engine rejects, and won't reproduce transaction, collation or index behaviour — so it gives false confidence exactly where you needed real confidence.
  • Never copy production data unmasked. It's a data-protection incident waiting to happen. Use generated data plus a small, masked, curated set of real edge cases.
  • Make setup explicit and local to the test. Shared fixtures produce tests that pass or fail depending on execution order, and nobody can read a test to learn what it needs.

Common mistake

Load testing a scaled-down environment and extrapolating linearly. Systems don't degrade linearly — thread pools, connection pools, lock contention and cache hit ratios all have knees in the curve. A test at 20% of production capacity mostly proves the code compiles.

If you can't test at scale, at least identify which resource saturates first and reason about it explicitly.

Who owns quality

Remember this

The team owns quality. QA specialists own testing expertise.

A dedicated QA function is valuable for exploratory testing, designing test strategy, adversarial thinking developers are bad at on their own code, and representing the user's real workflow.

It's not valuable as a downstream gate that receives "finished" work and finds bugs a week later. That guarantees long feedback loops and diffuses responsibility.

The practical test: when a defect reaches production, is the reaction "QA missed it" or "our process let it through — where would we have caught it earliest?" The first answer indicates the broken model.

Key takeaways
  • Move each check as early as it can meaningfully run — and accept that some can only run in production.
  • Write down what you deliberately don't test.
  • Keep PR feedback under ten minutes or the whole strategy degrades.
  • Integration tests need the real database engine, not an in-memory substitute.
  • Quarantine flaky tests the same day. They destroy trust in every other test.
  • Load-test with realistic data volume, or don't bother.

Common mistakes

  • Coverage as a goal, producing tests with no assertions and false confidence.
  • An E2E-heavy suite: slow, flaky, and it fails without telling you where the defect is.
  • Mocking everything, so tests verify the mock configuration rather than the system.
  • Testing implementation details, so every refactor breaks tests and the team learns to distrust them.
  • No test for the failure path — which is where the actual production defects live.
  • Treating a passing pipeline as proof of correctness rather than absence of known regressions.

Interview questions

What's your testing strategy for a new service?
How I'd answer

"I start from risk, not from the pyramid diagram. Which flows would be most expensive if they broke — usually anything touching money, permissions or data integrity? Those get redundant verification: unit tests for the rules, integration tests against a real database for persistence and transactions, and a synthetic check running against production so we hear about a failure before customers do."

"For the bulk of the code I want fast unit tests around domain logic with no infrastructure, and integration tests for anything crossing a boundary — repositories, message handlers, HTTP endpoints — using a real database in a container."

"I'd specifically avoid the in-memory provider. It doesn't enforce constraints or reproduce transaction behaviour, so it passes tests that production would fail. That's worse than no test, because it's confidence you haven't earned."

"Then a deliberately small number of end-to-end journeys — maybe five, critical paths only. They're the slowest and flakiest thing in the suite and their cost grows faster than their value."

"I'd also write down what we're not testing: framework behaviour, third-party libraries, trivial mapping. And I'd set a time budget — PR feedback under ten minutes — because once the suite is slow, people batch changes and stop running it locally, and the whole strategy degrades regardless of how good the tests are."

What they're really checking
  • Do you reason from risk, or recite the pyramid?
  • Do you know the real trade-offs of E2E tests and in-memory providers?
  • Do you treat suite speed as a design constraint?
Weak answers
  • Red flag: "80% coverage" as the strategy.
  • Red flag: "unit test everything and mock all dependencies" — produces tests that pass while the system is broken.
Likely follow-ups
  • How do you test a message consumer end to end?
  • What's your view on the in-memory EF Core provider?
  • How do you keep integration tests isolated when they share a database?
CI takes 45 minutes and people have started merging without waiting. What do you do?
How I'd answer

"The behaviour is the real problem. A gate people route around is worse than no gate, because it creates the illusion of verification. So I'd treat suite duration as an incident for the delivery process, not a nice-to-have."

"First, measure. Test suites are almost always dominated by a small number of tests — usually E2E tests, tests with real sleeps, and integration tests that rebuild a database per test. Profiling usually finds 10% of tests consuming 80% of the time."

"Then concrete moves. Parallelise across agents — the easiest win, often 4–5×. Replace Thread.Sleep with proper waiting or deterministic time control. Share expensive setup safely: one database container per test collection with per-test transaction rollback or unique tenant IDs, rather than recreating it per test."

"Then split the pipeline by risk. Fast unit and integration tests block the PR; slow E2E and performance tests run post-merge on main with alerting — so failures still surface but don't gate every change."

"And I'd delete or quarantine tests that have never caught a regression but fail intermittently. They're pure cost."

"Longer term, if E2E is where the time goes, that usually means coverage is at the wrong level. Moving those assertions down to integration tests is both faster and gives better failure localisation. I'd set an explicit ten-minute budget for the PR gate and treat exceeding it as a build failure, so it doesn't creep back."

What they're really checking
  • Do you treat developer feedback latency as a real engineering problem?
  • Do you know concrete techniques, or just "optimise the tests"?
  • Are you willing to delete tests?
Likely follow-ups
  • How do you decide which tests are safe to move out of the blocking gate?
  • What if the slowness is one integration suite nobody understands?
A critical bug reached production despite passing tests and QA. How do you respond? ⭐ Senior-level
How I'd answer

"Fix and stabilise first — rollback or flag off, verify recovery, communicate. The analysis comes after the bleeding stops."

"Then it should be blameless in a specific sense: look for the conditions that made the mistake possible, not the person who made it."

"The question I want answered isn't 'who missed it' but 'at which point could this have been caught most cheaply, and why wasn't it?' That usually lands in one of three places. The scenario was never a requirement — so the gap is upstream, and the fix is a checklist question about that class of failure. Or it wasn't testable at any level we run — it only shows up with production data skew or concurrent traffic — and then the honest answer is that the fix is detection and rollback speed, not more tests. Or the test existed but asserted the wrong thing."

"Then I'd write one or two specific actions with owners and dates: a regression test at the level that would have caught it, and usually an alert that would have detected it in minutes instead of hours."

"I'd resist adding a broad new process step like another manual sign-off. That slows every future change to address one past failure and rarely catches the next one. Honestly, the most valuable outcome is usually improved detection, not prevention — over a long enough period something always gets through, and what distinguishes a good team is how fast they notice and how small the blast radius was."

What they're really checking
  • Blameless analysis instinct.
  • Do you accept that some defects can't be prevented economically?
  • Are your corrective actions proportionate and specific?
Weak answers
  • Red flag: "QA should have caught it."
  • Red flag: "add more manual testing before release."
Likely follow-ups
  • What if the same class of bug recurs three months later?
  • How would you have detected this in production within five minutes?
