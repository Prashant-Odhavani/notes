CI/CD, Release & Deployment

How a merged commit becomes production safely — and why "deploy" and "release" being the same event causes most risky releases.

🟡 Intermediate 🔴 Advanced 🔥 Must know
Quick revision
  • Deploy ≠ release. Deploy = the code is running. Release = users can see it. Feature flags separate them, and that's what makes frequent deployment safe.
  • CI means everyone integrates into mainline daily and every integration is verified — not "we have a build server".
  • Build the artifact once, promote the same artifact. Rebuilding per environment means you never tested what you shipped.
  • Define the rollback trigger before you ship — a metric and a threshold, decided in advance.
  • Every schema change must work with the currently deployed code. Expand → migrate → contract.
  • DORA four keys. Speed and stability move together — the trade-off people assume doesn't exist.

Continuous integration 🟢 Beginner

One line: everyone merges into the mainline at least daily, and every merge is automatically verified.

CI is a practice, not a tool. A team with an elaborate Jenkins setup and three-week feature branches is not doing CI.

Why it matters: divergence between a branch and mainline grows with time, and the difficulty of reconciling it grows faster than linearly. Two branches that each refactor the same area produce a conflict no tool can resolve safely. Daily integration keeps every merge small and boring.

A pipeline earning the name does at minimum: build with warnings as errors, run unit and integration tests, run analysers and format checks, scan dependencies for vulnerabilities, and produce a single versioned artifact. And it must be fast enough that people wait for it — see the ten-minute budget.

Senior signal

Most organisations should aim for continuous delivery with low-friction promotion, and treat continuous deployment as an outcome of maturity rather than a goal.

The value is being able to deploy at any moment. Whether you press the button automatically matters far less than whether a hotfix can reach production in twenty minutes.

Pipeline design 🟡 Intermediate

Remember this

Build once, promote the same artifact.

Environment differences belong in configuration supplied at runtime, never in the build. Rebuilding per environment means the thing you tested isn't the thing you shipped.

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-dotnet@v4
        with: { dotnet-version: '9.0.x' }
      - run: dotnet publish src/Api -c Release -o out /p:Version=1.0.${{ github.run_number }}
      - run: dotnet test --no-build -c Release
      - uses: actions/upload-artifact@v4
        with: { name: api, path: out }

  deploy-prod:
    needs: build
    environment: production        # protection rule: requires approval
    runs-on: ubuntu-latest
    steps:
      - uses: actions/download-artifact@v4
        with: { name: api }        # THE SAME bits that were tested
      - run: ./deploy.sh production

The important detail is that deploy-prod downloads the artifact — it doesn't rebuild. Rebuilding introduces the possibility of different dependency resolution, a different compiler patch version, or different source state. Pipeline mechanics in depth: GitHub Actions.

Deployment strategies 🔥 Must know

RecreateStop old, start newDowntimeRedeploy old — also downtimeInternal tools; maintenance windows are acceptable

How to choose: rolling for infrastructure change, flags for behaviour change.

Rolling deployments handle "new binary, same behaviour" well. When the risk is that the logic is wrong, a flag is far better — reversible in seconds, no deployment, no schema to unwind.

Common mistake

Describing blue/green as "zero risk" in an interview. It removes deployment downtime, but it doesn't solve the hard part: shared state. Both environments usually talk to the same database, so an incompatible schema change breaks green just as badly — and switching back doesn't undo data the new version wrote.

Blue/green solves cutover, not compatibility.

Feature flags in practice 🔴 Advanced

public async Task<Money> QuoteAsync(Order order, CancellationToken ct)
{
    // Default is the OLD path: a flag service outage degrades to "as before".
    if (!await features.IsEnabledAsync("NewPricingEngine", order.TenantId))
        return await legacy.QuoteAsync(order, ct);

    try
    {
        var quote = await rules.QuoteAsync(order, ct);

        // Shadow comparison during rollout: log divergence, trust the old path.
        var control = await legacy.QuoteAsync(order, ct);
        if (control != quote)
            log.LogWarning("Pricing divergence {Order}: legacy {A} vs new {B}",
                order.Id, control, quote);

        return quote;
    }
    catch (Exception ex)
    {
        // A flagged path must never take down the unflagged one.
        log.LogError(ex, "New pricing failed for {Order}; falling back", order.Id);
        return await legacy.QuoteAsync(order, ct);
    }
}

Three things make this a safe rollout rather than a risky one:

  1. The default is the old behaviour, so a flag service outage degrades gracefully.
  2. The new path can't fail the request.
  3. Shadow comparison produces evidence. After a week of zero divergence warnings you have a real argument for switching — instead of a hope.
Production trap — flags are debt with a fuse

Every flag doubles the number of code paths, and combinations multiply. Set an expiry when you create one, remove it as a tracked task once the rollout is done, and never let a flag become permanent configuration by accident. If it's permanent, it's a setting — and it needs tests covering both values.

Database changes and rolling deploys ⭐ Senior-level

Remember this

During any rolling deployment, old and new code run at the same time against the same schema.

So every schema change must be compatible with the currently deployed code.

The pattern is expand and contract, across several separate releases:

StepChangeSafe because
1. ExpandAdd the new nullable column. Don't touch the old one.Old code ignores a column it doesn't know about
2. Dual writeDeploy code that writes both, reads old.Old code still writing only the old column
3. BackfillBatch-migrate historical rows, off-peak.It's data only
4. Switch readsRead new, still write both.Rollback is safe — old data is still current
5. ContractStop writing old; later release drops the column.Only after every instance runs the new code
 
-- Deployed alongside the app release that uses the new name.
EXEC sp_rename 'dbo.Customer.Email', 'EmailAddress', 'COLUMN';

During the rollout, half the instances still run old code and query Email. Every one of those requests fails.

And rolling back the app doesn't help — the column is already renamed, so old code fails just as hard. You've turned a routine deploy into an outage with no fast exit.

-- Release 1: expand (safe with old code running)
ALTER TABLE dbo.Customer ADD EmailAddress nvarchar(256) NULL;
-- Release 1 app code: write both, read Email.

-- Backfill in batches so the table is never locked for long.
WHILE 1 = 1
BEGIN
    UPDATE TOP (5000) dbo.Customer
       SET EmailAddress = Email
     WHERE EmailAddress IS NULL AND Email IS NOT NULL;
    IF @@ROWCOUNT = 0 BREAK;
    WAITFOR DELAY '00:00:01';   -- let other work through
END

-- Release 2 app code: read EmailAddress, still write both.
-- Release 3 app code: stop writing Email.
-- Release 4 (days later): ALTER TABLE dbo.Customer DROP COLUMN Email;

Four releases instead of one. Feels like overhead until the first time it saves you.

The batched backfill matters independently: a single UPDATE over millions of rows holds locks, blows up the transaction log, and can block the application for minutes. See locking and blocking.

Rollback strategy

"We can roll back" is only true if someone verified it recently. Things that quietly make rollback impossible:

  • Schema changes already applied.
  • Messages published in a new format old consumers can't parse.
  • Cache entries written in a new shape.
  • Data the new version wrote that the old version misinterprets rather than rejecting.

What to actually do:

  • Define the trigger before shipping. "If 5xx rate on this endpoint exceeds 1% over five minutes, or p95 latency doubles, we roll back." Decided in advance it's mechanical; decided during an incident it's an argument.
  • Prefer flag-off to redeploy. Seconds versus minutes.
  • Know your forward-only cases. Once you've destroyed data or published events, you can only fix forward. Identify those in design — "roll back" isn't available.
  • Practise it. A rollback path exercised for the first time during an incident is a hypothesis, not a plan.

DORA metrics 🔥 Must know

MetricMeasuresImproved by
Deployment frequencyHow often you shipSmaller batches, automation, flags

Change failure rate% of deployments causing degradationBetter pre-merge verification, smaller changes, canaries
Time to restoreHow long a failure lastsFast rollback, good alerting, practised runbooks
The counter-intuitive part

Speed and stability move together. Teams that deploy more often also have lower change failure rates.

The mechanism is batch size: frequent deployment forces small changes, and small changes are easier to review, diagnose and reverse.

Key takeaways
  • Separate deploy from release with flags. That single change makes frequent deployment safe.
  • Build once, promote the artifact. Never rebuild per environment.
  • Rolling for infrastructure change, flags for behaviour change, canary when only real traffic tells you the truth.
  • Blue/green doesn't solve schema compatibility. Nothing does except expand/contract.
  • Backfill in batches, always.
  • Decide the rollback trigger before you ship.

Common mistakes

  • Rebuilding per environment, so what's tested is never what's shipped.
  • Environment-specific code paths (if (env == "prod")) instead of configuration.
  • Schema migration coupled to the app release with no compatibility window.
  • Secrets in pipeline variables instead of a secret store with managed identity — see App Configuration & Key Vault.
  • Manual steps only one person knows. That's the true single point of failure.
  • Deploying Friday afternoon without rollback. The problem is never the day — it's the absent rollback path.
  • No smoke test after deployment, so the first person to notice is a customer.

Interview questions

Explain blue/green versus canary, and when you'd choose each.
How I'd answer

"Blue/green runs two complete environments. All traffic is on blue, you deploy to green, verify it, then switch everything at once — usually a load balancer or DNS change. Rollback is switching back, which is nearly instant."

"The costs are double infrastructure during the switch, and that verification happens with synthetic traffic — so you learn nothing about real user behaviour until you've already committed everyone."

"Canary sends a small fraction of real traffic to the new version — 1%, then 5%, then 25% — while watching error rates and latency. You find problems with real traffic patterns, real data and real cache behaviour while only a small fraction of users is exposed."

"Canary's costs: you need traffic splitting, telemetry good enough to compare cohorts, and both versions run concurrently for longer — which makes schema and message compatibility mandatory rather than optional."

"I'd choose canary for a high-traffic service where the risk is that logic behaves differently under real load. That's exactly what blue/green can't detect before full cutover. I'd choose blue/green for lower-traffic services where 1% is too small a sample to tell you anything, or where the change is infrastructural and I want a clean reversible cutover."

"In practice I'd combine either with feature flags, because the flag gives second-level reversibility for the behaviour itself. And I'd say explicitly that neither addresses the database — a breaking schema change is equally fatal in both, which is why expand-and-contract is the real prerequisite."

What they're really checking
  • Do you know the mechanics — and more importantly the limits of each?
  • Do you recognise shared state as the thing neither solves?
Weak answers
  • Red flag: definitions only, no selection criteria.
  • Red flag: claiming blue/green gives zero-risk deployment.
Likely follow-ups
  • How do you canary a background message consumer, where there's no HTTP traffic to split?
  • What metrics decide whether the canary is promoted?
  • How does this work when the change includes a schema migration?
Rename a heavily-used column on a 200-million-row table with zero downtime. ⭐ Senior-level
How I'd answer

"I wouldn't rename it. A rename is a single atomic change that breaks every deployed instance still using the old name — and it makes rollback impossible, because reverting the application doesn't revert the schema."

"Instead, a parallel change across several releases."

"Release one adds the new nullable column and deploys code that writes both but keeps reading the old one. That's safe against instances running the previous build, because they just ignore a column they don't know about."

"Then I backfill in batches — a few thousand rows at a time with a short pause, off-peak, monitoring log growth and blocking. A single UPDATE across 200 million rows would hold locks, bloat the transaction log, and potentially escalate to a table lock. That's an outage in itself."

"Release two switches reads to the new column while still writing both, so rollback to release one stays completely safe — both columns are current. I'd let that soak for a few days and run a reconciliation query to verify they agree for recently written rows."

"Release three stops writing the old column. Only after that's been stable long enough that rolling back past it is implausible does a final release drop it."

"If the column is indexed I'd also create the new index online where the edition supports it — a non-online build on a table that size blocks writes for a long time."

"The property I'm protecting throughout is that at every instant, both the currently deployed code and the immediately previous version work against the current schema. That's what zero downtime actually requires, and it's why the answer is four releases rather than one clever statement."

What they're really checking
  • Do you understand that rolling deploys mean two code versions coexist?
  • Do you know batched backfill and why a single large UPDATE is dangerous?
  • Do you preserve rollback safety at each step?
Weak answers
  • Red flag: "put the app in maintenance mode" when asked for zero downtime.
  • Red flag: one migration with a rename, "deployed together with the app".
  • Red flag: no mention of batching the backfill.
Likely follow-ups
  • How do you keep the two columns consistent if writes also happen through stored procedures?
  • What if you find a divergence after switching reads?
  • How would you do the equivalent in Cosmos DB, where there's no schema?
Your team deploys once a month and every release is stressful. How would you change that?
How I'd answer

"The stress is a symptom of batch size. A monthly release contains a month of changes, so if anything breaks the suspect list is enormous, diagnosis is slow, and rollback discards a month of work — which means nobody wants to roll back, which makes incidents longer."

"Every problem in that sentence gets better as the batch gets smaller. So the goal is more frequent deployment, and the work is removing whatever currently makes frequency impossible."

"I'd start by mapping what actually happens between merge and production and timing each step. Usually you find a small number of blockers: a manual regression cycle that takes days, a change-approval board that meets weekly, an environment that must be booked, or a deployment procedure only one person can perform. Each has a different fix."

"Then I'd sequence it to build confidence rather than demand trust. First make deployment itself boring and automated, including a smoke test and a scripted rollback — a deployment nobody fears is a prerequisite for everything else. Second, introduce feature flags so merging stops being the same event as releasing; that removes most of the argument against deploying frequently, because deploying dark code is genuinely low risk. Third, replace the manual regression cycle incrementally with automated coverage of the critical paths, so the gate becomes fast rather than removed."

"And I'd measure change failure rate before and after, because the objection will be 'moving faster will break things' — and the data reliably shows the opposite once batch size falls. Framing it as risk reduction rather than speed is usually what gets it accepted."

What they're really checking
  • Do you understand batch size as the underlying variable?
  • Can you sequence an organisational change so it earns trust incrementally?
  • Do you measure the outcome rather than assert the benefit?
Likely follow-ups
  • What if the monthly cadence is imposed by a customer contract?
  • How do you handle a change advisory board that won't move?
