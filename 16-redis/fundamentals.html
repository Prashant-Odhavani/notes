Architecture & Data Types

One design decision — single-threaded execution — explains most of Redis's behaviour, including its worst failure mode.

🟢 Beginner 🟡 Intermediate 🔥 Must know
Quick revision
  • Command execution is single-threaded. Every command is atomic, and one slow command blocks everything.
  • Never run KEYS in production. It's O(N) and blocks the server. Use SCAN.
  • Hashes for objects with independently-updated fields — not a serialized JSON blob.
  • Sorted sets are the differentiating structure: ranked queries in O(log n).
  • INCR is atomic, which makes counters and rate limits trivial.
  • Lua scripts run atomically — that's how you get multi-step atomicity.
  • Pipelining removes round trips; it isn't a transaction.

The single-threaded model 🔥 Must know

In simple terms

Redis executes commands on one thread, one at a time, from a queue. There is no concurrency between commands.

It's still extremely fast because everything is in memory and there's no lock contention, no context switching, and no coordination overhead.

ConsequenceWhat it means for you
Every command is atomic No command can interleave with another. INCR can't lose an increment
No locks needed Which is why it's fast despite being single-threaded
One slow command blocks everything The critical failure mode. An O(N) command on a large key stalls every other client
More cores don't help throughput Scale with more instances or cluster mode, not a bigger box
Remember this

Atomicity and the blocking failure mode are the same property.

You get free atomicity because nothing runs concurrently. You get catastrophic latency spikes from one expensive command for exactly the same reason.

That trade is the single most useful thing to understand about Redis, and it's the answer to a lot of "why did Redis get slow?" questions.

KEYS is the classic. A developer runs KEYS user:* to check something, the instance has ten million keys, and every client times out for several seconds. It's not a slow query — it's an outage.

UNLINK instead of DEL is the less-known one and worth remembering: deleting a large collection blocks the event loop while memory is freed, and UNLINK hands that to a background thread.

"Single-threaded" is now partly historical

Redis 6+ uses threaded I/O — reading from and writing to sockets happens on multiple threads. Redis 7 added more background work, and lazy freeing moves deallocation off the main thread.

But command execution is still a single thread, which is what preserves atomicity and the blocking behaviour. So the mental model holds; the nuance is that network handling scales with cores while command processing doesn't.

Worth saying precisely, because "Redis is single-threaded" gets challenged and the accurate version is "command execution is single-threaded".

Strings and atomic counters

var db = multiplexer.GetDatabase();

// Atomic increment - no read-modify-write, no race
long views = await db.StringIncrementAsync("post:1041:views");

// Set with expiry, only if absent - the lock and idempotency primitive
bool acquired = await db.StringSetAsync(
    "lock:order:1041", token, TimeSpan.FromSeconds(30), When.NotExists);
Why INCR matters more than it looks

In a relational database, incrementing a counter safely means either an atomic UPDATE ... SET x = x + 1 or optimistic concurrency. Two application instances doing read-modify-write would lose an increment.

In Redis it's one command, atomic by construction, because commands don't interleave. That's why counters, rate limits and sequence numbers are trivial here and fiddly elsewhere.

SET key value NX EX 30 is the same idea for locks — set-if-absent with expiry in one atomic operation. Doing those as two commands is the classic broken lock.

Hashes vs serialized blobs 🟡 Intermediate

await db.StringSetAsync($"user:{id}", JsonSerializer.Serialize(user));

// Updating one field: read all, deserialize, change, serialize, write all.
// Two round trips, full payload twice, and a lost-update race between them.
await db.HashSetAsync($"user:{id}", new[]
{
    new HashEntry("name",  user.Name),
    new HashEntry("email", user.Email),
    new HashEntry("visits", user.Visits)
});

// One field, one round trip, no read, no race
await db.HashSetAsync($"user:{id}", "email", newEmail);
await db.HashIncrementAsync($"user:{id}", "visits");     // atomic
var email = await db.HashGetAsync($"user:{id}", "email"); // partial read

Update one fieldRead + write, with a race windowOne atomic HSET

How to choose

Hash when fields are read or written independently, or you need atomic field updates.

JSON string when the object is always read and written whole — which is the common case for a cached read model, and there's nothing wrong with it.

The mistake is using a JSON blob and then doing read-modify-write on one field, which is both slow and a lost-update bug.

Sorted sets — the one to know ⭐ Senior-level

// Add or update a score - O(log n)
await db.SortedSetAddAsync("leaderboard", playerId, score);

// Top 10, highest first - O(log n + 10)
var top = await db.SortedSetRangeByRankWithScoresAsync(
    "leaderboard", 0, 9, Order.Descending);

// THIS is the hard part elsewhere: one player's rank, in O(log n)
long? rank = await db.SortedSetRankAsync("leaderboard", playerId, Order.Descending);

// Players scoring between 1000 and 2000
var band = await db.SortedSetRangeByScoreAsync("leaderboard", 1000, 2000);
Senior signal — why sorted sets are genuinely differentiating

"What is this user's rank?" is the query that's hard everywhere else. In SQL you need a window function computed over the whole table on every call — so it gets slower as the table grows, and you can't index your way out of it.

Redis maintains the ordering as a skip list, so rank lookup and range queries are both logarithmic. That's a genuine algorithmic advantage, not just an in-memory speed advantage.

The same structure covers more than leaderboards, and recognising that is the useful part:

  • Sliding-window rate limiting — score = timestamp, remove old entries, count what remains.
  • Time-series with range queries — score = epoch, then query a time window.
  • Priority queues — score = priority, pop the lowest.
  • Delayed jobs — score = "run at" time, poll for scores below now.

Using a sorted set with a timestamp score is one of the most reusable techniques in Redis.

Sorted sets grow forever unless you trim them

A leaderboard or a rate-limit window accumulates members indefinitely. There's no per-member TTL — expiry applies to the whole key.

So you must trim explicitly: ZREMRANGEBYRANK to cap the size, or ZREMRANGEBYSCORE to drop entries older than a cutoff. For a rate-limit window that removal is part of the algorithm; for a leaderboard it's a maintenance job someone has to remember.

An untrimmed sorted set that reaches millions of members also makes any O(N) command on it a blocking event — so this is a correctness and availability concern.

Bitmaps, HyperLogLog and Streams 🔴 Advanced

// One bit per user id
await db.StringSetBitAsync($"active:{date:yyyyMMdd}", userId, true);

long activeToday = await db.StringBitCountAsync($"active:{date:yyyyMMdd}");

// Users active on BOTH days - a bitwise AND, server-side
await db.StringBitOperationAsync(Bitwise.And, "active:both",
    new RedisKey[] { "active:20240601", "active:20240602" });
StructureTrade-off
Bitmap Exact and tiny — but needs dense integer ids. Sparse ids waste space
HyperLogLog Approximate (~0.81% error) in a fixed ~12 KB, for any cardinality. Counts unique items without storing them
Stream Persistent log with consumer groups and acknowledgement — unlike pub/sub, which drops messages with no subscriber
HyperLogLog is the right answer surprisingly often

"How many unique visitors today?" with a set means storing every visitor id — potentially gigabytes.

HyperLogLog answers it in 12 KB regardless of volume, with about 0.8% error. For an analytics figure nobody acts on individually, that error is irrelevant and the memory saving is enormous.

The constraint: you cannot ask whether a specific item is in it, and you can't remove items. It counts, and that's all. So it's right for metrics and wrong for membership — which is exactly the distinction to draw if it comes up.

Senior signal — versioned keys solve the deployment problem

You change a cached DTO's shape and deploy. The cache holds entries in the old format, and the new code deserializes them — either throwing, or worse, silently producing objects with default values.

Options are flushing the cache on deploy (a stampede against a cold cache, at the worst moment) or handling both formats (permanent complexity).

A version prefix in the key sidesteps it entirely. New code writes and reads v2:, old entries under v1: are simply never read again and expire on their own TTL. No flush, no dual-format code, and a rollback works because the old version still finds its own keys.

That last property is what makes it a strong answer: it makes cache format changes safely reversible, which flushing does not.

A missing TTL is a slow memory leak

Keys written without an expiry stay until explicitly deleted or evicted. So a cache that's mostly TTL'd but has one code path that forgets grows steadily for months, then hits maxmemory — at which point the eviction policy starts discarding keys, possibly including ones you assumed were persistent.

The failure is delayed and unrelated to the code that caused it, which makes it hard to trace.

Set the TTL in the same call as the value — SET key value EX 300, not SET then EXPIRE. A crash between two commands leaves an immortal key, and wrapping every write in a helper that requires a TTL argument is a cheap structural fix.

Multi-step atomicity 🔥 Must know

MechanismGives youDoesn't
Pipelining Many commands in one round trip Not atomic — other clients' commands can interleave
MULTI/EXEC Commands execute consecutively with nothing between No rollback, and you can't read a value mid-transaction to branch on it
WATCH Optimistic concurrency — aborts if a watched key changed Needs retry logic
Lua script Atomic, with logic and branching Blocks the server while it runs — keep it short 
const string script = @"
    local current = tonumber(redis.call('GET', KEYS[1]) or '0')
    local limit   = tonumber(ARGV[1])
    if current < limit then
        redis.call('INCR', KEYS[1])
        if current == 0 then
            redis.call('EXPIRE', KEYS[1], ARGV[2])
        end
        return 1
    end
    return 0";

var allowed = (int)await db.ScriptEvaluateAsync(script,
    new RedisKey[] { $"rate:{userId}" },
    new RedisValue[] { 100, 60 }) == 1;
Remember this

MULTI/EXEC is not a database transaction.

Commands are queued and run consecutively, but there's no rollback — if one fails, the others still applied. And you can't read a value inside the transaction and branch on it, because nothing executes until EXEC.

So for anything conditional — "increment only if under the limit" — you need Lua, which runs as a single atomic unit and can contain real logic.

Lua blocks the server, so keep scripts tiny

A script runs to completion on the single command thread. Nothing else executes meanwhile.

So a script that loops over a large collection is exactly the blocking failure mode from the top of this page — with the added problem that it can't be interrupted cleanly.

Rule of thumb: a handful of commands with simple branching, no unbounded loops, no KEYS. Use EVALSHA with a cached script hash rather than sending the source every time — StackExchange.Redis handles that automatically.

Pipelining is the easy performance win

100 sequential GETs at 1ms round-trip each is 100ms of pure waiting. Pipelined, it's one round trip.

In StackExchange.Redis you get this by not awaiting immediately — collect the Tasks, then await them all. The multiplexer batches them automatically.

Or use MGET/HMGET for a genuine multi-key read. Either way, the fix for "Redis is slow" is very often round trips rather than Redis.

Key takeaways
  • Command execution is single-threaded: that's both the free atomicity and the blocking risk.
  • Never KEYS in production — SCAN. And UNLINK over DEL for large keys.
  • Hashes for independently-updated fields; a JSON string when the object is read and written whole.
  • Sorted sets give O(log n) rank and range — the genuinely differentiating structure.
  • A timestamp-scored sorted set covers rate limiting, time series, delayed jobs and priority queues.
  • Sorted sets need explicit trimming; there's no per-member TTL.
  • HyperLogLog counts uniques in 12 KB but can't test membership.
  • Version your key prefixes so cache format changes are reversible.
  • Set the TTL in the same command as the value.
  • MULTI/EXEC has no rollback and can't branch — use Lua for conditional logic.
  • Pipeline to remove round trips; it isn't atomicity.

Common mistakes

  • KEYS in production, blocking every client.
  • DEL on a huge collection instead of UNLINK.
  • Read-modify-write on a JSON blob — slow and a lost-update race.
  • Writing keys with no TTL, leaking memory until eviction starts.
  • SET then EXPIRE as two commands.
  • Expecting MULTI/EXEC to roll back.
  • Long-running Lua scripts blocking the event loop.
  • Sequential awaits where pipelining would collapse the round trips.
  • Unbounded sorted sets and lists.
  • No version prefix, so a DTO change breaks on deployment.
  • Scaling up the instance to get more command throughput.

Interview questions

Intermediate

Redis is single-threaded. Why is it fast, and what's the risk? 🔥 Must know
How I'd answer

"It's fast because everything is in memory and, being single-threaded for command execution, there's no lock contention, no context switching and no coordination overhead. A lot of a multi-threaded database's work is synchronisation, and Redis simply doesn't do any."

"The important consequence is that every command is atomic for free. Commands can't interleave, so INCR can't lose an increment and SET NX can't race. That's why counters, rate limits and locks are trivial in Redis and fiddly in a relational database."

"And the risk is the same property: one slow command blocks everything. There's one queue, so an O(N) command on a large key stalls every other client for its entire duration."

"The classic example is KEYS. Someone runs KEYS user:* to check something, the instance has ten million keys, and every client times out for several seconds. That's not a slow query, it's an outage — and it's usually caused by a person at a console rather than by application code. SCAN is the cursor-based alternative that returns incrementally."

"Others in the same family: HGETALL or SMEMBERS on a huge collection, LRANGE 0 -1, and a long-running Lua script — which is worse because it can't be interrupted cleanly."

"One that's less well known and worth mentioning: DEL on a key with millions of elements blocks while the memory is freed. UNLINK does the same delete but hands the deallocation to a background thread. So for large collections, UNLINK always."

"The other operational implication: more CPU cores don't increase command throughput. So you scale with more instances or cluster mode, not a bigger machine — which catches people who try to fix a throughput problem by resizing."

"I'd also be precise about the terminology, because it gets challenged: Redis 6 added threaded I/O, so socket reads and writes use multiple threads, and Redis 7 moved more background work off the main thread. But command execution is still single-threaded, which is what preserves both the atomicity guarantee and the blocking behaviour. So the accurate statement is 'command execution is single-threaded', not 'Redis is single-threaded'."

What they're really checking
  • Do you connect atomicity and the blocking risk as the same property?
  • Do you know the specific dangerous commands?
  • Do you know UNLINK?
  • Do you know the accurate version of "single-threaded"?
Likely follow-ups
  • How does SCAN work, and what are its guarantees?
  • How would you find a slow command in production?
  • How do you scale Redis throughput?

Advanced / scenario

Design a leaderboard for 10 million players with live ranks. ⭐ Senior-level
How I'd answer

"A sorted set, and I'd explain why this is the case where Redis is genuinely the right tool rather than just a fast one."

"ZADD leaderboard score playerId to write, which is O(log n). Then ZREVRANGE 0 9 for the top ten, and ZREVRANK for an individual player's rank — also O(log n)."

"That rank query is the hard part. In SQL, 'what rank is this player?' needs a window function computed across the whole table on every call. With 10 million rows that's expensive, it gets worse as you grow, and you can't index your way out of it because the answer depends on every other row. Redis maintains the ordering as a skip list, so it's logarithmic. That's an algorithmic advantage, not just an in-memory speed advantage."

"On memory: roughly 10 million members at something like 60–90 bytes each is on the order of a gigabyte. Worth calculating rather than assuming, and it's a reason to keep player ids short — the member string is stored per entry."

"Ties are the detail people miss. Equal scores are ordered lexicographically by member, so two players with the same score get arbitrary but stable relative ranks. If the product wants 'earliest to reach the score ranks higher', I'd encode that into the score itself — a composite like score * 10^10 + (maxTimestamp - achievedAt) — so the ordering is correct without a second lookup. That's the standard trick and it needs care with float precision, since Redis scores are doubles with 53 bits of integer precision."

"Trimming. A sorted set has no per-member TTL, so it grows forever. If only the top N matter I'd ZREMRANGEBYRANK periodically. If it's seasonal, I'd use a separate key per season — leaderboard:2024-06 — with a TTL on the whole key, which is cleaner than trimming and gives historical leaderboards for free."

"Scale and hot keys. One sorted set is one key, so it lives on one shard in cluster mode. All leaderboard traffic hits that node, and no amount of sharding helps because you can't split a single key. For 10 million players with heavy read traffic I'd expect that to be the bottleneck."

"Two mitigations. Read replicas for the rank and range queries, accepting slight staleness — which is fine for a leaderboard. And caching the top N separately, since 'top 100' is requested constantly and changes less often than individual ranks; that's a small string key with a one-second TTL, which removes most of the read load."

"Durability. I'd treat Redis as the serving layer, not the source of truth. Scores get written to a durable store as well, so the sorted set can be rebuilt — because with only RDB snapshots you lose recent writes on failover, and a leaderboard that resets is a visible product failure. Rebuilding 10 million members takes a while, so I'd want that path tested rather than theoretical."

"One thing I'd push back on: live ranks for all 10 million players is rarely the real requirement. Usually it's 'top 100' plus 'my rank and the few players around me' — ZREVRANGE rank-2 rank+2. That's a much smaller problem, and worth confirming before designing for the general case."

What they're really checking
  • Do you reach for a sorted set and know why rank is the hard query?
  • Do you handle ties deliberately?
  • Do you know a single key can't be sharded?
  • Do you consider memory, trimming and durability?
  • Do you question the requirement?
Weak answers
  • Red flag: a SQL table with ORDER BY score and no awareness of the rank cost.
  • Red flag: no mention of the hot-key problem.
  • Red flag: treating Redis as the source of truth with no rebuild path.
Likely follow-ups
  • How do you encode the tiebreaker without losing precision?
  • How would you rebuild after a total loss?
  • What if scores updated thousands of times per second?
