Locks, Rate Limiting & Pub/Sub

Redis as coordination infrastructure. The lock section is where interviewers find out whether you understand distributed systems or just the API.

🔴 Advanced ⭐ Senior-level 🔥 Must know
Quick revision
  • A lock is SET key token NX EX ttl — atomic, with expiry, in one command.
  • Release with Lua, checking the token, or you'll release someone else's lock.
  • A Redis lock is not a correctness guarantee. It reduces duplicate work; it doesn't prevent it.
  • Fencing tokens are the only way to make lock-protected work genuinely safe.
  • Redlock is contested. Know both sides of the argument.
  • Rate limiting: fixed window is simple and lets double bursts through; sliding window is accurate; token bucket allows controlled bursts.
  • Pub/sub is fire-and-forget. Use Streams when delivery matters.

Distributed locks 🔥 Must know

var token = Guid.NewGuid().ToString();   // identifies THIS holder

// Atomic: set only if absent, with expiry, in one command
bool acquired = await db.StringSetAsync(
    key:    $"lock:{resource}",
    value:  token,
    expiry: TimeSpan.FromSeconds(30),
    when:   When.NotExists);
const string releaseScript = @"
    if redis.call('GET', KEYS[1]) == ARGV[1] then
        return redis.call('DEL', KEYS[1])
    else
        return 0
    end";

await db.ScriptEvaluateAsync(releaseScript,
    new RedisKey[]   { $"lock:{resource}" },
    new RedisValue[] { token });
Three ways to write this wrong

1. SETNX then EXPIRE as two commands. If the process dies between them, the lock has no expiry and is held forever. Nothing can ever acquire it again. Use the single SET ... NX EX form.

2. Releasing with a plain DEL. If your lock expired and someone else acquired it, your DEL releases their lock — so now two holders think they have it. The token check is what prevents this, and it must be atomic, hence Lua.

3. No expiry at all. The holder crashes and the lock is permanent. Always set a TTL, and make it longer than the worst-case work duration.

The honest limits ⭐ Senior-level

The uncomfortable truth

A Redis lock cannot guarantee mutual exclusion. Not because of an implementation flaw — because of what a timeout means in a distributed system.

  Client A: acquires the lock, TTL 30s
  Client A: begins work
  Client A: stops for 35 seconds  (GC pause, VM migration, network partition)
  Redis:    lock expires
  Client B: acquires the lock  -- legitimately, from Redis's point of view
  Client B: begins the same work
  Client A: resumes, believing it still holds the lock

  Both A and B are now doing the work. No bug in Redis. No bug in the lock code.
Remember this

A distributed lock with a timeout is an optimisation, not a guarantee.

It reliably reduces duplicate work. It cannot prevent it, because a process can be paused for longer than any TTL you choose and has no way to detect that it was.

Which means: the work protected by the lock must be safe to run twice. If it isn't, the lock is not enough and you need something else.

If the work isThen
Idempotent — an upsert, a recomputation A Redis lock is fine. Running twice is harmless, you're just avoiding waste
Not idempotent — charging a card, sending an email The lock is insufficient. You need a fencing token, or a database-level guarantee

Fencing tokens — the actual solution

// Redis INCR is atomic, so this is a strictly increasing sequence
long fence = await db.StringIncrementAsync("fence:orders");

// Pass the token to whatever performs the protected work.
// The RESOURCE rejects anything with a stale token.
await _writer.WriteAsync(data, fence);

// In the resource (e.g. a SQL UPDATE):
//   UPDATE resource SET data = @data, fence = @fence
//   WHERE id = @id AND fence < @fence
// Client A's stale token is now smaller than B's, so A's write is rejected.
Senior signal — why fencing is the real answer

The fencing token moves the safety check from the lock to the resource being protected.

In the pause scenario: A holds fence 41, B acquires and holds fence 42. B writes with 42. A wakes up and writes with 41 — and the resource rejects it, because 41 is not greater than 42. A's stale write cannot land, regardless of how long A was paused.

That's a genuine guarantee rather than a probabilistic one, and it doesn't depend on any timing assumption.

The catch, and it's a significant one: the resource has to support it. A SQL table can (a fence column and a conditional update). S3 or a third-party payment API generally cannot. So fencing is available when you control the write target, and when you don't, you need idempotency at that boundary instead — which is why idempotency keys exist.

Mentioning fencing tokens unprompted is one of the clearest signals that you've thought about distributed locking properly rather than copied a code sample.

The Redlock debate 🔴 Advanced

PositionArgument
Redlock (Redis author) Acquire the lock on a majority of N independent Redis nodes. Survives individual node failure without replication lag losing the lock
The critique (Kleppmann) It depends on bounded clock drift and bounded process pauses. Neither is guaranteed, so it's not safe for correctness. If you need correctness, use fencing tokens
The response Redlock is for efficiency, not correctness, and that's an acceptable trade for the vast majority of use cases
What to actually say about this

Both sides are right about different questions, and the useful position is:

For efficiency — avoiding duplicate work, ensuring one instance runs a scheduled job — a single-instance Redis lock is fine and Redlock is unnecessary complexity.

For correctness — where running twice causes real damage — no timeout-based lock is sufficient. Use fencing tokens, or move the guarantee into the database with a unique constraint or a conditional update.

So the practical conclusion is that Redlock occupies a narrow middle ground: more complex than needed for efficiency, and still not sufficient for correctness. That's why most teams use a simple single-instance lock and make the protected work idempotent.

In .NET, RedLock.net implements it if you want it, and StackExchange.Redis plus the pattern above is enough for most cases.

Practical lock details that matter
  • TTL longer than the worst case, not the average. A TTL shorter than the work means the lock expires mid-operation, which is the failure above happening by design.
  • Extend long-running locks with a watchdog that renews while work continues — but only if the token still matches.
  • Always release in a finally, so an exception doesn't hold the lock for the full TTL.
  • Don't wait forever. Fail fast or time out, otherwise contention becomes a thread-pool exhaustion problem.
  • Consider whether you need a lock at all. An atomic conditional update in the database is often simpler and genuinely safe.

Rate limiting 🔥 Must know

AlgorithmBehaviourCost
Fixed window N per calendar minute. Allows 2N across a boundary One counter. Cheapest
Sliding window log Exactly N in any rolling window A sorted set per client — more memory
Sliding window counter Approximates the above by weighting the previous window Two counters. Good compromise
Token bucket Steady refill, allows a burst up to capacity Two values. Usually the best UX 
const string script = @"
    local current = redis.call('INCR', KEYS[1])
    if current == 1 then
        redis.call('EXPIRE', KEYS[1], ARGV[2])
    end
    return current <= tonumber(ARGV[1]) and 1 or 0";

var key = $"rate:{userId}:{DateTime.UtcNow:yyyyMMddHHmm}";   // per-minute bucket
var allowed = (int)await db.ScriptEvaluateAsync(script,
    new RedisKey[] { key }, new RedisValue[] { 100, 60 }) == 1;
The fixed-window boundary problem

With a limit of 100 per minute, a client can send 100 requests at 10:00:59 and another 100 at 10:01:00 — 200 requests in two seconds, both within the stated limit.

For protecting a downstream service from overload, that burst is exactly what you were trying to prevent.

Fixed window is still a reasonable default for coarse API quotas where the limit is about fairness rather than protection. When the limit exists to protect capacity, use sliding window or token bucket.

const string script = @"
    local now    = tonumber(ARGV[1])
    local window = tonumber(ARGV[2])
    local limit  = tonumber(ARGV[3])

    -- Drop entries outside the window
    redis.call('ZREMRANGEBYSCORE', KEYS[1], 0, now - window)

    local count = redis.call('ZCARD', KEYS[1])
    if count < limit then
        redis.call('ZADD', KEYS[1], now, ARGV[4])   -- unique member per request
        redis.call('EXPIRE', KEYS[1], window)
        return 1
    end
    return 0";
Senior signal — the sorted-set sliding window

This is the canonical use of a timestamp-scored sorted set: score is the timestamp, members are individual requests. Removing entries older than the window and counting what remains gives an exact rolling count.

It's accurate, and it costs memory proportional to the request count — one member per request within the window. For 100 requests per minute per user across a million users, that's real memory, so the EXPIRE on the key matters.

The middle ground worth knowing is the sliding window counter: keep the current and previous fixed-window counts, and weight the previous one by how far into the current window you are. Two integers instead of N members, and it approximates a sliding window closely enough for most purposes.

Being able to name that trade — exact and memory-hungry versus approximate and cheap — is the senior answer rather than just implementing one.

Token bucket is usually the best user experience

Tokens refill at a steady rate up to a capacity. A client that's been idle has a full bucket and can burst; a sustained heavy client is limited to the refill rate.

That matches how people actually use APIs — occasional bursts of legitimate activity, not a perfectly even request rate. A strict sliding window rejects a legitimate burst that a token bucket happily absorbs.

It's also what most public APIs use, and it pairs naturally with the RateLimit-* response headers — remaining tokens and refill time map directly onto them.

ASP.NET Core has built-in rate limiting

Since .NET 7, AddRateLimiter provides fixed window, sliding window, token bucket and concurrency limiters as middleware.

The important limitation: it's per-instance, in-memory. With three replicas behind a load balancer, a 100-per-minute limit becomes effectively 300.

So the built-in limiter is right for protecting a single instance's resources, and you need Redis when the limit must be enforced globally across instances. That distinction is exactly what an interviewer is checking when they ask you to implement rate limiting rather than configure it.

Pub/sub vs Streams 🔥 Must know

Pub/SubStreams
PersistenceNone — messages vanishPersistent log
No subscriber onlineMessage is lostRetained until read
DeliveryAt-most-onceAt-least-once, with acknowledgement
Consumer groupsNo — every subscriber gets everythingYes — work is distributed
ReplayNoYes
Use forCache invalidation broadcast, live notificationsWork queues, event processing
Remember this

Pub/sub is fire-and-forget. If nobody is listening, the message is simply gone.

So it's right for broadcasts where a miss is tolerable — "invalidate this cache key on every instance", "push this notification to connected clients".

It is wrong for anything that must be processed. A subscriber restarting during a deploy misses every message sent in that window, silently.

// Publisher: after invalidating in Redis, tell every instance to drop its L1
var sub = multiplexer.GetSubscriber();
await sub.PublishAsync(RedisChannel.Literal("cache:invalidate"), key);

// Subscriber, on every instance
await sub.SubscribeAsync(RedisChannel.Literal("cache:invalidate"), (_, message) =>
{
    _localCache.Remove(message.ToString());   // clear the in-process copy
});
This is what makes hybrid caching work

The hard problem with an in-process L1 cache is that each instance holds its own copy, so invalidating Redis doesn't clear them.

Pub/sub broadcasts the invalidation to every instance, which drops its local entry. And pub/sub's unreliability is acceptable here precisely because the L1 TTL is short — a missed message means one instance is stale for a few more seconds, not indefinitely.

HybridCache and the Redis backplane in SignalR both work this way. It's a good example of choosing a deliberately unreliable mechanism because the failure mode is bounded.

// Produce
await db.StreamAddAsync("orders", new NameValueEntry[]
{
    new("orderId", orderId), new("total", total)
});

// Consume as part of a group - each message goes to ONE consumer in the group
var entries = await db.StreamReadGroupAsync(
    "orders", "processors", consumerName: Environment.MachineName,
    position: ">", count: 10);

foreach (var entry in entries)
{
    await ProcessAsync(entry);
    await db.StreamAcknowledgeAsync("orders", "processors", entry.Id);  // ACK
}
Streams are not a replacement for a real broker

Streams give you persistence, consumer groups, acknowledgement and a pending-entries list for unacknowledged messages — genuinely useful, and a big step up from pub/sub.

What they don't give you: the routing, dead-letter handling, delivery retry policies, management tooling and durability guarantees of Service Bus, RabbitMQ or Kafka. And because Redis is memory-first, a stream that grows large is a memory problem — you must trim it with XTRIM or MAXLEN.

So Streams are a good fit when you already run Redis and need a lightweight work queue. If messaging is central to the architecture, use a broker built for it. Saying that is better than defending Streams as a general messaging solution.

Key takeaways
  • SET key token NX EX ttl to acquire; Lua with a token check to release.
  • A timeout-based lock cannot guarantee exclusion — a process can pause longer than any TTL.
  • So the protected work must be idempotent, or you need fencing tokens.
  • Fencing moves the check to the resource, which is a real guarantee — if the resource supports it.
  • Redlock is complex for efficiency and insufficient for correctness; the middle ground is narrow.
  • Fixed window allows 2N across a boundary; sliding window is exact but memory-hungry; token bucket gives the best UX.
  • ASP.NET Core's built-in limiter is per-instance — Redis is needed for a global limit.
  • Pub/sub is at-most-once with no persistence. Fine for cache invalidation, wrong for work.
  • Streams add persistence, groups and acknowledgement, and still aren't a full broker.

Common mistakes

  • SETNX then EXPIRE — a crash between them means a permanent lock.
  • Releasing with DEL instead of a token-checked Lua script.
  • Treating a Redis lock as a correctness guarantee.
  • A lock TTL shorter than the work.
  • Not releasing in a finally.
  • Reaching for Redlock when a single-instance lock plus idempotency would do.
  • Fixed-window rate limiting where burst protection was the point.
  • Assuming ASP.NET Core's rate limiter is global across instances.
  • Pub/sub for work that must be processed.
  • Untrimmed streams consuming memory indefinitely.

Interview questions

Advanced / scenario

Implement a distributed lock so only one instance runs a scheduled job. 🔥 Must know
How I'd answer

"The mechanism is a single atomic command: SET lock:job token NX EX 30. Set only if absent, with an expiry, in one operation. If it returns success, this instance runs the job."

"Three details that make it correct."

"The NX and EX must be in the same command. Doing SETNX and then EXPIRE means that if the process dies between them, the lock has no expiry and is held forever — nothing can ever acquire it again. That's the classic broken implementation."

"The value must be a unique token, and release must check it. If I release with a plain DEL, and my lock had already expired and been acquired by another instance, I'd be deleting their lock — so two instances end up running. The check-and-delete has to be atomic too, which means a small Lua script, because a GET followed by a DEL has a race in the gap."

"Release in a finally, so an exception doesn't hold the lock for the full TTL."

"Now the important part, which is what I'd want to say even though the question didn't ask: this does not guarantee that only one instance runs the job."

"The failure sequence: instance A acquires with a 30-second TTL, starts work, then stops for 35 seconds — a long GC pause, a VM migration, a network partition. Redis expires the lock. Instance B acquires it legitimately and starts the same job. A resumes, still believing it holds the lock. Both are now running, and there's no bug anywhere — that's just what a timeout means in a distributed system."

"So the practical conclusion is that the job must be safe to run twice. For most scheduled jobs it is — a recomputation, an upsert, a cleanup sweep — and then the lock is doing exactly what you want: reducing duplicate work as an efficiency measure."

"If running twice would cause real damage — sending customer emails, charging cards, posting ledger entries — a lock is the wrong tool on its own. Two options there. Fencing tokens: an atomic INCR gives a monotonically increasing number, passed to whatever performs the write, and the resource rejects anything with a lower token than it's already seen. A's stale write can't land after B's, regardless of how long A was paused. That's a genuine guarantee, but the resource has to support it — a SQL table can with a fence column and a conditional update; a third-party API generally can't."

"Or put the guarantee in the database: a unique constraint on a job-run row for that period, so the second instance's insert simply fails. That's often simpler and it's genuinely safe, because it doesn't depend on any timing assumption."

"On Redlock — acquiring across a majority of independent Redis nodes — I'd say the debate is worth knowing but the conclusion is that it occupies a narrow middle ground: more complex than necessary for efficiency, and still not sufficient for correctness, because it relies on bounded clock drift and bounded pauses. So I'd use a simple single-instance lock and make the work idempotent, which is what most teams settle on."

"Two practical notes: the TTL should exceed the worst-case job duration, not the average, otherwise the lock expiring mid-job is a designed-in failure. And for long jobs I'd add a watchdog that renews the lock while work continues, renewing only if the token still matches."

"Finally — if this is running on a platform that already offers singleton scheduling, like a Kubernetes CronJob or Azure Functions with a singleton attribute, I'd use that instead of building it. Same guarantees, no code."

What they're really checking
  • Do you know NX and EX must be atomic?
  • Do you use a token and release with Lua?
  • Do you know a lock isn't a correctness guarantee? This is the discriminator.
  • Do you know fencing tokens?
  • Do you consider the platform already solving it?
Weak answers

  • Red flag: releasing with DEL.
  • Red flag: presenting it as guaranteed mutual exclusion.

Implement rate limiting: 100 requests per minute per user, across 5 instances. ⭐ Senior-level
How I'd answer

"The 'across five instances' part is the whole question, because it rules out the easy answer. ASP.NET Core's built-in rate limiter is per-instance and in-memory, so a 100-per-minute limit across five replicas becomes effectively 500. I need shared state, which means Redis."

"The simplest correct implementation is a fixed window: a key like rate:{userId}:{yyyyMMddHHmm}, INCR it, set the expiry on first increment, and allow if the result is under 100. One Lua script so the increment and the expiry are atomic — otherwise a crash between them leaves a key with no TTL that blocks the user permanently."

"That's cheap and it has a flaw I'd name upfront: the boundary problem. A client can send 100 requests at 10:00:59 and another 100 at 10:01:00 — 200 in two seconds, both technically within the limit. If the limit exists for fairness or billing, that's acceptable. If it exists to protect a downstream service from overload, that burst is exactly what I was trying to prevent."

"So the question I'd ask is what the limit is for, because it determines the algorithm."

"For accuracy, a sliding window log with a sorted set: score is the request timestamp, one member per request. Remove entries older than the window with ZREMRANGEBYSCORE, count with ZCARD, add if under the limit — all in one Lua script. That's exact for any rolling 60 seconds. The cost is memory proportional to request volume — one member per request per user — so with a million users that's real, and the key needs an EXPIRE so idle users don't accumulate."

"The middle ground is a sliding window counter: keep the current and previous minute's counts and weight the previous one by how far into the current minute you are. Two integers instead of N members, and it approximates a rolling window closely enough for most purposes. That's what I'd probably choose for a high-volume API."

"For the best user experience I'd use a token bucket — tokens refill steadily up to a capacity, so an idle client can burst and a sustained heavy client is held to the refill rate. That matches real usage better than a strict window, which rejects legitimate bursts. It's also what most public APIs use, and it maps directly onto the RateLimit-* response headers."

"Regardless of algorithm, the response matters: 429 with a Retry-After header, plus RateLimit-Limit, RateLimit-Remaining and RateLimit-Reset so well-behaved clients can self-regulate rather than retrying blindly."

"Two operational points. What happens if Redis is down? Failing every request because the rate limiter is unavailable is worse than not rate limiting — so I'd fail open, log it, and possibly fall back to a per-instance limiter as a rough backstop. That's a deliberate decision to make, not something to discover during an incident."

"And the limiter itself must be cheap, because it runs on every request. A Lua script is one round trip; anything involving multiple sequential calls per request adds latency to the entire API and makes the limiter a bottleneck in front of everything."

What they're really checking
  • Do you spot that per-instance limiting doesn't work here?
  • Do you know the fixed-window boundary flaw?
  • Can you compare algorithms by what the limit is for?
  • Do you use Lua for atomicity?
  • Do you decide the Redis-down behaviour?
  • Do you return proper 429 headers?
Weak answers
  • Red flag: in-memory counters with multiple instances.
  • Red flag: INCR and EXPIRE as separate non-atomic calls.
  • Red flag: no thought about a Redis outage.
Likely follow-ups
  • Write the token bucket in Lua.
  • How would you rate limit by IP and by user together?
  • How do you handle a client that ignores Retry-After?
