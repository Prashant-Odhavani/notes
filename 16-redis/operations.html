Persistence, Clustering & Failure

What happens when memory fills, when a node dies, and when Redis is simply gone. The last one is the question most teams haven't answered.

🟡 Intermediate 🔴 Advanced ⭐ Senior-level
Quick revision
  • RDB = periodic snapshot, compact, loses recent writes. AOF = command log, more durable, larger.
  • Redis replication is asynchronous — a failover can lose acknowledged writes.
  • Set maxmemory and an eviction policy. The default may reject writes rather than evict.
  • allkeys-lru for a cache, volatile-lru when some keys must persist.
  • Cluster mode shards by key hash, and multi-key commands need the same slot.
  • Hash tags — {user:1}:profile — force keys onto the same slot.
  • A single hot key can't be sharded. Cluster mode doesn't help it.

Senior signal — decide whether Redis is a cache or a database

This is the question persistence configuration actually answers, and it's worth stating before discussing settings.

If Redis is a cache, persistence barely matters. Losing everything means a cold cache and a temporary latency increase, and you can rebuild from the source of truth. RDB snapshots for convenience are enough, and some teams disable persistence entirely to avoid the fork cost.

If Redis holds data you can't rebuild — sessions, a leaderboard, a rate-limit state you care about — then you need AOF with everysec, and you should be honest that you've made Redis a database with weaker durability than a real one.

Most production setups use both: AOF for recovery granularity, RDB for fast restarts and backups. Azure Cache for Redis offers RDB or AOF on Premium tiers and no persistence on lower ones — which is a detail worth knowing, because "we're on Standard" means you have no persistence at all.

The fork memory spike

An RDB snapshot forks the process. Copy-on-write means the child shares memory initially, but pages modified during the snapshot get copied — so a write-heavy instance can approach double its memory usage while snapshotting.

If maxmemory is set close to the machine's physical memory, that spike can trigger swapping or an out-of-memory kill. It's a genuine cause of Redis instances dying mysteriously during backups.

Rule of thumb: don't let Redis use more than about half the available memory if you're taking RDB snapshots on a write-heavy instance.

Eviction 🔥 Must know

What happens when memory fills

When Redis reaches maxmemory, the eviction policy decides what to do. One of the options is to stop accepting writes.

PolicyEvictsUse when
noevictionNothing — writes fail with an errorRedis holds data you can't lose
allkeys-lruLeast recently used, any keyPure cache. The usual choice
allkeys-lfuLeast frequently usedCache with a stable hot set
volatile-lruLRU, only keys with a TTLMixed use — some keys must survive
volatile-ttlWhichever expires soonestRarely the best choice
allkeys-randomAny key at randomWhen access is genuinely uniform
The volatile-lru trap

volatile-lru only evicts keys that have a TTL. That sounds like a safe choice — it protects your persistent keys.

But if memory fills and there aren't enough TTL'd keys to evict, Redis starts rejecting writes exactly as if it were noeviction. You get write errors on a cache, which is surprising and hard to diagnose.

So volatile-lru is only safe if you're confident TTL'd keys always dominate memory usage. If Redis is purely a cache, allkeys-lru is more robust — it will always find something to evict.

And a separate point: mixing cache and non-cache data in one Redis instance is the real problem. Two instances, or two databases with different policies, avoids the whole dilemma.

LRU here is approximate

Redis doesn't maintain a true LRU list — that would cost memory and time on every access. It samples a few random keys and evicts the least recently used of those.

maxmemory-samples controls the sample size (default 5). Higher is more accurate and slightly more CPU.

In practice the approximation is close enough that it doesn't matter, but it's worth knowing if someone asks why an obviously-cold key survived while a warmer one was evicted.

Replication and failover 🟡 Intermediate

TopologyGives you
Single instanceNothing on failure. Fine for a pure cache in dev

SentinelAutomatic failover and client discovery
ClusterSharding plus automatic failover
Managed (Azure Cache, ElastiCache)All of the above, configured for you
Replication is asynchronous — a failover can lose writes

The primary acknowledges a write before replicating it. So if the primary fails after acknowledging and before replicating, the promoted replica has never seen that write.

WAIT can block until N replicas acknowledge, which narrows the window and doesn't close it — and it costs latency on every write.

The practical consequence: don't rely on Redis for data whose loss you can't tolerate. A lost cache entry is a cache miss. A lost session logs someone out. A lost ledger entry is a serious problem — and that's not what Redis is for.

This is worth stating plainly in an interview, because "we use Redis for X and it's replicated so it's safe" is a common and incorrect assumption.

Cluster mode 🔴 Advanced

How sharding works

Cluster mode divides the keyspace into 16,384 hash slots. Each key hashes to a slot, and each node owns a range of slots.

The client library learns the slot map and routes each command to the right node directly.

Multi-key commands need the same slot
MGET user:1:profile user:2:profile
  -> CROSSSLOT error: keys must hash to the same slot
Only the part inside {braces} is hashed:

  {user:1}:profile
  {user:1}:settings
  {user:1}:orders
  -> all hash to the same slot, so MGET and Lua work across them

Any command touching several keys — MGET, SUNION, a transaction, a Lua script with multiple KEYS — requires them all in one slot.

Hash tags are the mechanism, and they're a design decision made at key-naming time. Retrofitting them means changing every key, which invalidates the whole cache. So if there's any chance of cluster mode later, adopt hash tags for related keys from the start — the cost is nil and the retrofit is painful.

Senior signal — hash tags trade the CROSSSLOT problem for a hot-slot problem

Over-using hash tags defeats the point of sharding. If every key is tagged {tenant:acme}, all of that tenant's data lands on one node — so a large tenant creates a hot node, and cluster mode gives you nothing.

The balance: tag only the keys you genuinely need to access together atomically or in one command. Everything else should distribute freely.

That's the same tension as choosing a partition key — co-location buys atomicity and multi-key operations, and costs distribution. Recognising it as the same trade-off across three different databases is the useful insight.

Hot keys ⭐ Senior-level

The limit sharding can't fix

A single key lives on a single node. If one key receives enormous traffic — a global config document, a leaderboard, a popular product — that node is the bottleneck.

Adding nodes doesn't help. You cannot split one key.

MitigationHow
Local L1 cacheCache it in-process with a short TTL. Most reads never reach Redis. Usually the best answer
Read replicasSpread reads across replicas, accepting slight staleness
Key replicationWrite to config:0–config:9, read a random one
Split the valueIf it's a large hash, split into several keys that shard separately
A local cache is the right answer more often than people expect

If a config document is read on every request and changes twice a day, caching it in-process for 30 seconds removes essentially all Redis traffic for it — and the staleness is irrelevant.

People reach for Redis scaling because the problem appears to be a Redis problem. It's usually a round trip problem, and the fix is not making the round trip.

Combine with pub/sub invalidation if you need the local copies dropped promptly on change.

Finding a hot key

redis-cli --hotkeys samples key access (needs an LFU policy). MONITOR shows every command in real time — useful for a few seconds of diagnosis and never to leave running, since it has real overhead.

redis-cli --bigkeys finds the large keys, which are a related problem: a large key makes any O(N) command on it a blocking event. Hot and big are different problems with different fixes, and worth distinguishing.

When Redis is down 🔥 Must know

The question to have answered in advance

Is Redis optional or load-bearing?

If it's a cache, a Redis outage should mean slower responses. If your application returns errors when Redis is unavailable, you've converted a performance optimisation into a reduction in availability.

ConcernWhat to do
Cache readsCatch, log, fall through to the database
Cache writesCatch and ignore — a failed populate is harmless
Rate limitingDecide deliberately: fail open (allow) or closed (reject)
Distributed locksCan't acquire — usually means skip the work rather than proceed unlocked
SessionsUsers are logged out. This is why session state in Redis needs persistence
Repeated failuresA circuit breaker, so you stop paying the timeout on every request
The cascade: falling through can take out the database

Falling through to the database is correct — and if the database can't serve 100% of traffic uncached, a Redis outage becomes a database outage. Which is worse.

So "degrade gracefully" needs a second question: can the source of truth handle full load? If not, you need load shedding — serve stale data if you have any, reject a proportion of requests, or queue them — rather than letting every request pile onto the database.

A circuit breaker matters here too. Without one, every request waits for the Redis timeout before falling through, so response times increase by that timeout across the board and thread-pool exhaustion follows. The breaker makes failures fast rather than slow, which is what keeps the application responsive.

Naming this cascade is a strong senior signal, because "fall back to the database" is the standard answer and it's incomplete.

Evictions and the slowlog are the two that matter most

A non-zero eviction rate means Redis is discarding keys because it's out of memory, not because they expired. So your carefully-chosen TTLs aren't being honoured, hit rate drops, and the database takes more load — with no error anywhere. It's the most commonly missed Redis metric.

The slowlog records commands exceeding a threshold, which is exactly how you catch the KEYS or HGETALL that blocked the server. Since one slow command stalls everything, a single slowlog entry can explain a fleet-wide latency spike.

Managed Redis: know what your tier gives you

On Azure Cache for Redis: Basic is a single node with no SLA and no failover — dev only. Standard is a replicated pair with automatic failover. Premium adds persistence, clustering, zone redundancy and VNet injection. Enterprise adds active geo-replication and Redis modules.

The one people get caught by: persistence and clustering require Premium. A team on Standard that assumes their Redis data survives a restart is mistaken, and that's a bad thing to discover during an incident.

Also worth knowing that scaling tiers involves a failover, so it isn't a zero-impact operation.

Key takeaways
  • Decide whether Redis is a cache or a database — that answers the persistence question.
  • RDB for backups and fast restarts, AOF everysec to bound data loss. Often both.
  • RDB forks, which can nearly double memory on a write-heavy instance.
  • Always set maxmemory and a policy. allkeys-lru for a pure cache.
  • volatile-lru can start rejecting writes if TTL'd keys run out.
  • Replication is asynchronous, so failover can lose acknowledged writes.
  • Cluster shards into 16,384 slots; multi-key commands need one slot, so hash tags are a key-naming decision.
  • Over-tagging recreates a hot node and defeats sharding.
  • A single hot key can't be sharded — use a local L1 cache.
  • A cache failure must degrade, not fail — and check the database can take full load.
  • Monitor evictions and the slowlog above everything else.

Common mistakes

  • No maxmemory set, so Redis grows until the OS kills it.
  • noeviction on a cache, so writes fail when it fills.
  • volatile-lru with too few TTL'd keys, producing write errors.
  • Assuming replication prevents data loss.
  • Assuming a managed tier has persistence when it doesn't.
  • No hash tags, then discovering CROSSSLOT errors when enabling cluster mode.
  • Tagging everything with the tenant, so one node holds it all.
  • Scaling the cluster to fix a hot key.
  • Redis failures failing requests.
  • No circuit breaker, so every request pays the timeout during an outage.
  • Not monitoring evictions.
  • Leaving MONITOR running.

Interview questions

Intermediate

What happens when Redis runs out of memory? 🔥 Must know
How I'd answer

"It depends entirely on the eviction policy, and the important point is that one of the options is to stop accepting writes."

"With noeviction, Redis rejects writes with an error once maxmemory is reached. Reads keep working. That's correct if Redis holds data you can't lose, and it's a poor choice for a cache — you'd rather lose a cold entry than fail a write."

"With allkeys-lru it evicts the least recently used key regardless of TTL. That's the usual choice for a pure cache, because it will always find something to evict, so writes never fail."

"allkeys-lfu evicts least frequently used, which is better when there's a stable hot set — LRU can evict a frequently-used key that just happens not to have been touched recently."

"The one I'd flag as a trap is volatile-lru. It only evicts keys that have a TTL, which sounds safe because it protects your persistent keys. But if memory fills and there aren't enough TTL'd keys to reclaim, it behaves exactly like noeviction and starts rejecting writes. Getting write errors on something you configured as a cache is surprising and hard to diagnose."

"And the underlying issue there is mixing cache and non-cache data in one instance. If some keys must survive and others are disposable, separate instances — or at least separate databases with different policies — avoids the dilemma entirely."

"Two things I'd add."

"LRU is approximate. Redis samples a handful of random keys and evicts the least recently used of those, rather than maintaining a true LRU list — which would cost memory and time on every access. maxmemory-samples tunes it. It's close enough in practice, and it explains why an obviously-cold key sometimes survives."

"Monitor the eviction rate. A non-zero eviction count means keys are dying before their TTL because you're out of memory — so your TTL strategy isn't being honoured, the hit rate drops, and the database silently takes more load. There's no error anywhere. It's the most commonly missed Redis metric and it's the one that tells you the cache is undersized."

"I'd also make sure maxmemory is actually set. If it isn't, Redis grows until the OS kills the process — which is a much worse failure than eviction."

What they're really checking
  • Do you know writes can fail rather than data being evicted?
  • Do you know the volatile-lru trap?
  • Do you monitor evictions?
  • Do you know LRU is sampled?
Likely follow-ups
  • LRU or LFU for your workload?
  • How do you size a Redis instance?
  • What if some keys must never be evicted?

Advanced / scenario

Redis goes down in production. What happens to your application? ⭐ Senior-level
How I'd answer

"The honest answer is that it depends on decisions made long before the outage, and the question I'd want answered in design is: is Redis optional or load-bearing?"

"If it's a cache, the application should keep working, more slowly. Every cache read needs to catch the exception, log it, and fall through to the database. Cache writes can be caught and ignored — a failed populate is harmless. If instead a Redis exception propagates and fails the request, then a performance optimisation has become a reduction in availability, which is the opposite of the intent."

"But 'fall through to the database' is the incomplete answer, and this is the part I'd emphasise: can the database handle 100% of traffic uncached? If the cache was absorbing 95% of reads, falling through means twenty times the database load arriving instantly. So a Redis outage becomes a database outage, which is worse — you've turned a degradation into a full failure."

"So for a load-bearing cache I'd want load shedding: serve stale data if any is available, reject a proportion of requests with a 503 and Retry-After, or queue them. Deliberately serving some users a degraded experience beats everyone getting nothing."

"A circuit breaker is essential regardless. Without one, every request waits for the Redis connection timeout before falling through — so if that's two seconds, every response is two seconds slower and you exhaust the thread pool under load. The breaker makes the failure fast instead of slow, which is what keeps the application responsive. It also stops hammering a recovering Redis instance."

"Then the non-cache uses, each of which needs its own decision:"

"Rate limiting — fail open or closed? Failing closed rejects all traffic because the limiter is unavailable, which is usually worse than not limiting. I'd fail open, log loudly, and possibly fall back to a per-instance in-memory limiter as a rough backstop."

"Distributed locks — can't acquire, so the protected work shouldn't run. Skipping a scheduled job is normally better than running it unlocked on every instance."

"Sessions — everyone is logged out, which is a visible incident. If sessions are in Redis, that's an argument for persistence and replication, and for asking whether they belong there at all."

"On the client side, the StackExchange.Redis setting that matters is AbortOnConnectFail = false. With the historical default of true, if Redis is briefly unavailable the multiplexer throws and never reconnects — so a transient blip during a deployment permanently breaks caching until the application is restarted."

"And after an outage there's a cold cache problem: Redis comes back empty, so every request misses and the database gets the full uncached load again — plus a stampede on the hot keys. Stampede protection and possibly a warm-up matter here, because recovery can be as damaging as the outage."

"The thing I'd want to have done in advance is test this — block Redis in a staging environment and watch what actually happens. Nobody's assumptions about degradation survive first contact, and it's much better to find out deliberately."

What they're really checking
  • Do you distinguish optional from load-bearing?
  • Do you catch the cascade to the database?
  • Do you know a circuit breaker is needed, and why?
  • Do you decide per-use-case rather than globally?
  • Do you consider the cold-cache recovery?
  • Do you test it?
Weak answers
  • Red flag: "fall back to the database" with no capacity consideration.
  • Red flag: letting Redis exceptions fail requests.
  • Red flag: no mention of the recovery being a second spike.
Likely follow-ups
  • How would you warm the cache after recovery?
  • Fail open or closed for rate limiting, and why?
  • How do you test a Redis outage safely?
