Redis & Caching

Redis is the default answer to "make it faster", and adding a cache is one of the easiest ways to introduce a correctness bug. Both halves matter.

🟡 Intermediate 🔥 Must know

More than a cache 🔥 Must know

In simple terms

Redis is an in-memory data structure server. Not a key-value store that happens to be fast — a server that exposes hashes, sorted sets, lists and streams as network-accessible primitives.

Caching is its most common use, and it's the least interesting thing it does.

UseWhy Redis rather than something else
CacheSub-millisecond reads, shared across all instances
Distributed lockAtomic set-if-not-exists with expiry, in one operation
Rate limiterAtomic counters with TTL; sorted sets for sliding windows
LeaderboardSorted sets give ranked queries in log time — genuinely hard elsewhere
Session storeFast, shared, and expiry is built in
Queue / streamLists for simple queues, Streams for consumer groups
Pub/subFan-out to subscribers — fire-and-forget, no persistence
DeduplicationSET NX as an idempotency key store
Senior signal — the sorted set is the differentiator

Most of what Redis does you could approximate elsewhere. The sorted set is the one that's genuinely difficult to replicate.

"Give me ranks 50–100 by score, and tell me this user's rank" is O(log n) in Redis and awkward in every relational database — you'd need a window function over the whole table on each query.

Sorted sets are also the right answer for sliding-window rate limiting, time-series with range queries, priority queues, and "top N by score" of any kind.

Knowing Redis for its data structures rather than as a key-value cache is what separates using it from using it well.

Before you add a cache ⭐ Senior-level

The questions to ask first
  1. Is the slow thing actually slow, or just called too often? An N+1 pattern isn't fixed by caching — it's fixed by not doing it.
  2. Would an index fix it? Far cheaper, and it doesn't add a consistency problem.
  3. How stale can this be? If the answer is "not at all", caching is the wrong tool.
  4. What happens when the cache is empty or down? If the answer is "the site falls over", you've added a dependency, not a cache.
A cache is a second source of truth

That's the framing that matters. Every cache entry is a copy of data that can now disagree with the database.

So you've traded a performance problem for a correctness problem — usually a good trade, and it is a trade. The bugs that follow are the worst kind: intermittent, environment-dependent, and impossible to reproduce locally because your local cache is empty.

"Add caching" is the most common answer to a performance question in interviews, and the strongest version of that answer names the invalidation strategy in the same breath. Without one, you've described half a solution.

The answer is often both

Hybrid caching: a short-lived in-process cache in front of Redis. The L1 absorbs repeated reads with no network hop; the L2 keeps instances roughly consistent and survives restarts.

.NET 9 ships HybridCache which does exactly this, and also solves stampede — which is the harder problem and the reason to use it rather than hand-rolling the two layers.

The trade-off to state: the L1 makes staleness worse, because now each instance can hold a different version for the duration of its local TTL. Keep local TTLs short — seconds — and treat them as a throughput optimisation rather than the primary cache.

builder.Services.AddSingleton<IConnectionMultiplexer>(_ =>

        Password = password,

        ConnectRetry = 3,
        ConnectTimeout = 5000
    }));
Two registration mistakes that cause production incidents

1. Creating a multiplexer per request. It's a heavyweight object that multiplexes all commands over a small number of connections. Creating one per request exhausts sockets and produces timeouts under load — and it looks fine in development. Singleton, always.

2. AbortOnConnectFail = true (the historical default). If Redis is briefly unavailable at startup, the multiplexer throws and never reconnects. A transient blip during a deployment permanently breaks caching until the app is restarted. Setting it to false means it keeps retrying in the background, which is what you want in every managed-Redis environment.

IDistributedCache is a lowest-common-denominator API

It gives you byte arrays keyed by string — get, set, refresh, remove. That's it.

No hashes, no sorted sets, no atomic increments, no Lua, no pub/sub. So it can't do locks, rate limiting, leaderboards or anything else in the table at the top of this page.

It's fine for straightforward caching where provider-independence matters. For anything else you need IConnectionMultiplexer directly — and that's not a failure of abstraction, it's the point where you've stopped using Redis as a cache and started using it as a data structure server.

How I'd answer

"Probably eventually, but not first — because caching hides a performance problem rather than fixing it, and it introduces a second source of truth."

"I'd want to know why it's slow before deciding. Three possibilities, with very different answers."

"Too many queries rather than slow ones. If it's an N+1 pattern — 400 queries at 2ms each — caching would mask it, but the fix is to not issue 400 queries. That's a data-access change and it's strictly better than caching, because there's no staleness."

"One genuinely slow query. Then I'd look at the execution plan first. If a missing index is the cause, an index is far cheaper than a cache — no extra infrastructure, no invalidation logic, no new failure mode. Caching a query that should take 5ms is solving the wrong problem."

"Genuinely expensive work that's inherently repeated. An aggregate over millions of rows, an external API call, a computed report. That's where caching is the right answer, because the work is unavoidable and the result is reusable."

"If I do add a cache, I'd decide four things upfront rather than discovering them later."

"How stale can this be? That's a product question, not a technical one, and it sets the TTL. If the answer is 'not at all', caching is the wrong tool."

"How does it get invalidated? This is the hard part and the part people skip. TTL alone, explicit invalidation on write, or both. Without an answer here I've described half a solution."

"What happens on a cache miss storm? If a popular key expires and a thousand requests all miss simultaneously, they all hit the database at once — the stampede problem. That needs handling deliberately, and it's the failure mode that turns a cache into an outage."

"What happens when Redis is down? If the answer is 'the site falls over', I've added a dependency rather than a cache. It should degrade to hitting the database, slower but working."

"On the technology: for a single instance IMemoryCache is nanoseconds and needs no infrastructure. The moment there are multiple instances, in-process caching means each one holds a different version and invalidation becomes very hard — that's when Redis earns its place. In .NET 9 I'd reach for HybridCache, because it gives both layers plus stampede protection, which is the piece that's genuinely awkward to write correctly by hand."

"The framing I'd land on: a cache is a second source of truth. Usually a good trade, always a trade, and the bugs it produces are intermittent and environment-dependent — which is exactly the kind you can't reproduce locally because your local cache is empty."

What they're really checking
  • Do you diagnose before caching?
  • Do you know an index or fixing N+1 is usually better?
  • Do you name invalidation and staleness tolerance unprompted?
  • Do you consider stampede and cache-down behaviour?
Weak answers
  • Red flag: "add Redis" as the immediate answer.
  • Red flag: no invalidation strategy.
  • Red flag: no thought about what happens when the cache is unavailable.
Likely follow-ups
  • How would you handle a cache stampede?
  • Delete or update the cache on a write?
  • How do you pick a TTL?
