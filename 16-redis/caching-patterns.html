Caching Patterns & Invalidation

Reading from a cache is easy. Knowing when the cached value became wrong is the whole problem.

🟡 Intermediate 🔴 Advanced 🔥 Must know
Quick revision
  • Cache-aside is the default: check cache, miss → load → populate.
  • Delete on write, don't update. Updating races; deleting doesn't.
  • Add jitter to TTLs or everything written together expires together.
  • Stampede: a hot key expires and every request hits the database at once.
  • Penetration: requests for keys that don't exist bypass the cache entirely.
  • Cache the absence too — a short-TTL null marker.
  • Never let a cache failure fail the request. Degrade to the database.

The four patterns 🔥 Must know

PatternHow it worksTrade-off
Cache-aside (lazy loading) App checks cache; on miss, loads from the database and populates The default. Only caches what's asked for; first request is always slow
Read-through The cache layer loads on miss, transparently to the app Cleaner call sites; needs a library that supports it
Write-through Writes go to cache and database together, synchronously Cache is always warm and correct; every write is slower
Write-behind Write to cache, flush to the database asynchronously Fastest writes, and you can lose data. Rarely worth it 
public async Task<Product?> GetAsync(int id, CancellationToken ct)
{
    var key = $"v1:product:{id}";

    // 1. Try the cache - and never let a cache failure fail the request
    try
    {
        var cached = await _cache.StringGetAsync(key);
        if (cached.HasValue)
            return JsonSerializer.Deserialize<Product>(cached!);
    }
    catch (RedisException ex)
    {
        _logger.LogWarning(ex, "Cache read failed for {Key}, falling through", key);
    }

    // 2. Load from the source of truth
    var product = await _repository.GetAsync(id, ct);
    if (product is null) return null;

    // 3. Populate, fire-and-forget so a slow cache doesn't slow the response
    try
    {
        await _cache.StringSetAsync(key,
            JsonSerializer.Serialize(product),
            TtlWithJitter(TimeSpan.FromMinutes(10)));
    }
    catch (RedisException ex)
    {
        _logger.LogWarning(ex, "Cache write failed for {Key}", key);
    }

    return product;
}
A cache failure must never fail the request

Without the try/catch, a Redis outage takes down every endpoint that reads from the cache — so you've turned a performance optimisation into a hard dependency and reduced availability.

The correct behaviour is to log and fall through to the database. Slower, still working.

One caveat worth stating: if the database can't handle 100% of traffic uncached, falling through turns a cache outage into a database outage. So this needs a circuit breaker and a load-shedding plan for caches that are load-bearing rather than merely helpful. Knowing which of the two you have is the real question.

Where write-behind is genuinely right

Write-behind looks reckless — you acknowledge a write that isn't durable yet. And for high-volume, low-value, aggregate-shaped data it's exactly right.

View counts, "last seen" timestamps, analytics events. Incrementing Redis on every page view and flushing to the database every 30 seconds turns a million writes into a few thousand. Losing 30 seconds of view counts on a crash costs nothing.

The rule: write-behind is acceptable when the data is statistical rather than transactional. Never for anything a user or an auditor would notice missing.

Delete or update on write 🔥 Must know

The question

When data changes, do you update the cache with the new value, or delete the entry and let the next read repopulate it?

The answer is almost always delete, and the reason is a race condition.

Two concurrent writers, A setting price=10 and B setting price=20:

  A: writes price=10 to the database
  B: writes price=20 to the database        <-- database now says 20
  B: writes price=20 to the cache
  A: writes price=10 to the cache           <-- cache now says 10

Database: 20. Cache: 10. Permanently inconsistent until the TTL expires.
Remember this

Write to the database, then delete the cache key.

Deleting is idempotent and order-independent — two concurrent deletes leave the same state. Two concurrent updates can leave the cache holding the older value indefinitely.

Order matters too: database first, then cache. Delete-then-write leaves a window where a reader repopulates the cache with the old value just before the database changes.

Even delete-after-write has a small window
  Reader:  cache miss, reads price=10 from the database
  Writer:  writes price=20 to the database
  Writer:  deletes the cache key
  Reader:  writes price=10 into the cache      <-- stale value, no TTL pressure

Rare — it needs the reader's database read to land before the write and its cache write to land after the delete — but on a hot key it happens.

Mitigations, in increasing order of effort: a short TTL so the window is bounded (usually enough); delayed double-delete, deleting again after a second; or invalidating from the database change log — the outbox or CDC approach — which removes the race entirely because invalidation is driven by committed changes.

Being able to say "a short TTL bounds this and I'd only build more if the data genuinely can't be stale" is the calibrated answer. Reaching straight for CDC is over-engineering for most systems.

private static TimeSpan TtlWithJitter(TimeSpan baseTtl)
{
    // +/- 10%, so keys written together don't expire together
    var jitterMs = Random.Shared.Next(
        (int)(-baseTtl.TotalMilliseconds * 0.1),
        (int)( baseTtl.TotalMilliseconds * 0.1));
    return baseTtl + TimeSpan.FromMilliseconds(jitterMs);
}
Senior signal — why jitter is not optional

Without jitter, everything cached in the same burst expires in the same instant.

The scenario: you deploy, the cache is cold, the first minute of traffic populates ten thousand keys all with a 10-minute TTL. Exactly ten minutes later, all ten thousand expire simultaneously and every subsequent request is a miss. The database gets the full uncached load in one spike.

Worse, it's self-perpetuating: the repopulation happens in another tight burst, so it recurs every ten minutes. A periodic latency spike with no obvious cause, and the interval is a clue nobody thinks to look for.

Ten percent of random jitter spreads it out completely. It's three lines of code and it's the same reasoning as jitter in retry backoff — synchronised clients are the problem in both cases.

Cache stampede 🔥 Must know

Think of it this way

A shop with one item everyone wants. It's in stock, so nobody queues.

The moment it sells out, every customer simultaneously asks the stockroom for another. The stockroom, which was handling one request a minute, gets a thousand at once.

In simple terms

A popular key expires. Between expiry and repopulation, every concurrent request misses and they all query the database for the same thing.

Also called thundering herd or dogpile. It's most dangerous on exactly the keys the cache was protecting — the hottest ones.

MitigationHowCost
Per-key locking First miss acquires a lock and loads; others wait for it Waiting requests are held. Usually the right answer
Stale-while-revalidate Serve the expired value while one request refreshes it Briefly stale, no latency spike. Best UX
Probabilistic early refresh Refresh at random before expiry, more likely as expiry approaches Elegant; the value never actually expires under load
Background refresh A job repopulates hot keys before they expire Needs to know which keys are hot 
builder.Services.AddHybridCache(options =>
{
    options.DefaultEntryOptions = new HybridCacheEntryOptions
    {
        Expiration      = TimeSpan.FromMinutes(10),   // L2 (Redis)
        LocalCacheExpiration = TimeSpan.FromMinutes(1) // L1 (in-process)
    };
});

// Concurrent calls for the same key run the factory ONCE.
// The rest await that result - stampede protection is built in.
var product = await _hybridCache.GetOrCreateAsync(
    $"product:{id}",
    async token => await _repository.GetAsync(id, token),
    cancellationToken: ct);
This is the main reason to use HybridCache

Hand-rolling stampede protection correctly is fiddly — you need per-key coordination that works across instances, doesn't deadlock, and releases properly when the loader throws.

HybridCache gives you that plus the L1/L2 layering and tag-based invalidation. For new caching code in .NET 9 it's the default choice, and "I'd use HybridCache because it solves stampede" is a better answer than describing a lock you'd write yourself.

Note it dedupes within an instance by default. Across many instances you can still get one loader per instance — far better than one per request, and worth knowing the limit.

Cache penetration 🔴 Advanced

In simple terms

Requests for keys that don't exist. Cache miss, database miss, nothing cached — so every single request reaches the database.

The cache provides no protection at all, because there's nothing to cache.

const string NullMarker = "\0null";

var cached = await _cache.StringGetAsync(key);
if (cached.HasValue)
    return cached == NullMarker ? null : Deserialize(cached!);

var product = await _repository.GetAsync(id, ct);

if (product is null)
{
    // Short TTL - it may be created shortly
    await _cache.StringSetAsync(key, NullMarker, TimeSpan.FromSeconds(30));
    return null;
}

await _cache.StringSetAsync(key, Serialize(product), TtlWithJitter(TenMinutes));
return product;
Why this matters beyond performance

Penetration is an attack vector. Someone requesting /api/products/999999999 in a loop with random ids bypasses your cache entirely and sends every request to the database. A cache that protects you at 10,000 requests per second provides zero protection against this.

Negative caching with a short TTL fixes it — the second request for a non-existent id is a cache hit.

The TTL should be short, because the entity might be created moments later and a long negative TTL means new records appear to 404 for minutes. Thirty seconds is a reasonable default.

For very large key spaces a Bloom filter is the heavier answer — it can say "definitely not present" without a lookup. Worth knowing as an option, rarely necessary.

What to cache, and what not to ⭐ Senior-level

Good candidateBad candidate
Expensive to compute, cheap to storeCheap queries — an indexed primary-key lookup is already fast
Read far more than writtenWrite-heavy data — you'd invalidate constantly
Tolerates being seconds staleAnything you act on irreversibly — balances, stock at checkout
Shared across usersHighly personalised data with a low hit rate
External API responsesData subject to per-user authorisation, unless the key includes the user
The security trap: caching authorised data under an unauthorised key

Cache a response under document:1041 without the requesting user in the key, and the first authorised user's copy is served to everyone who asks — including people who shouldn't see it.

That's a data breach caused by a caching decision, and it's easy to introduce when adding caching to an existing endpoint that already does its own authorisation.

Two correct approaches: include the identity in the key when the response varies by permission, or cache the raw entity and authorise after reading — so the cache holds data and the authorisation check still runs per request. The second is usually better because it keeps the hit rate high.

Same class of bug as a Cache-Control: public header on a personalised response.

Measuring it 🟡 Intermediate

MetricTells you
Hit rateWhether the cache is earning its place. Below ~80% is worth investigating
Latency, cached vs uncachedWhether it's actually helping
Eviction rateNon-zero means memory pressure — keys are dying before their TTL
Memory used vs maxmemoryHow close you are to eviction
Key count and memory per key typeWhich prefix is consuming the space
Senior signal — a low hit rate means the cache is pure cost

A 20% hit rate means 80% of requests pay the cache lookup and the database query, plus the serialization cost of populating. That's slower than no cache at all.

Common causes worth naming: TTL too short relative to access frequency; keys too specific, so nothing is ever requested twice; eviction pressure killing entries early; or the data is simply not reused, which means caching was the wrong answer.

"I'd measure the hit rate and remove the cache if it's low" is a good answer, because removing a cache is a move most people never consider.

Key takeaways
  • Cache-aside by default; write-behind only for statistical data you can afford to lose.
  • Delete the key on write, don't update it — deletes are idempotent and order-independent.
  • Database first, then invalidate.
  • A short TTL bounds the remaining race; CDC-driven invalidation removes it if you really need that.
  • Jitter every TTL, or keys written together expire together and the spike recurs.
  • Stampede hits your hottest keys. HybridCache solves it; stale-while-revalidate is the best UX.
  • Cache negative results with a short TTL — penetration is also an attack vector.
  • Never cache authorised responses under a key that omits the identity.
  • A cache failure must degrade to the database, not fail the request.
  • Measure hit rate; a low one means the cache is costing you.

Common mistakes

  • Updating the cache on write instead of deleting, creating a permanent-until-TTL inconsistency.
  • Invalidating before the database write.
  • No jitter, producing synchronised expiry spikes.
  • No stampede protection on hot keys.
  • Not caching nulls, leaving penetration open.
  • Caching per-user data under a shared key — a data leak.
  • A cache exception failing the request.
  • Caching data that must be current, like stock at checkout.
  • No TTL at all, relying on invalidation being perfect.
  • Never measuring the hit rate.
  • Caching a cheap indexed lookup, adding complexity for no gain.

Interview questions

Intermediate

How do you keep a cache consistent with the database? 🔥 Must know
How I'd answer

"I'd start by being honest that you don't get perfect consistency — a cache is a second copy of the data, so there's always a window. The goal is to make the window small and bounded, and to decide how much staleness the data can tolerate."

"My default is write to the database, then delete the cache key. Two specifics there, and both matter."

"Delete rather than update. If two writers both update the cache, they can land in the opposite order to their database writes — writer A commits price 10, writer B commits price 20, then B updates the cache to 20 and A updates it to 10. The database says 20, the cache says 10, and it stays wrong until the TTL expires. Deleting is idempotent and order-independent, so concurrent deletes converge on the same state."

"Database first, then invalidate. If you delete first, a reader can repopulate the cache from the old database value in the gap before the write commits — and now you've cached stale data with a full TTL ahead of it."

"There's still a smaller race even doing it in that order: a reader that reads the database just before the write, and writes to the cache just after the delete. Rare, but real on a hot key."

"For that I'd rely on a short TTL as the backstop, because it bounds how long any inconsistency can survive. That's usually enough. If the data genuinely can't be stale, the heavier options are a delayed double-delete — deleting again a second later — or driving invalidation from the database change log via CDC or an outbox, which removes the race because invalidation follows committed changes rather than racing them."

"I'd frame that as a ladder and stop at the cheapest rung that meets the requirement. Reaching straight for CDC is over-engineering for most systems."

"Always set a TTL, even with explicit invalidation. Invalidation code has bugs, gets missed on new code paths, and doesn't know about writes from other services or manual data fixes. The TTL is what stops one missed invalidation being permanent."

"And the product question that determines all of this: how stale can this be? Reference data can be hours old. A user's own profile needs invalidating on write because they notice their own edits immediately. Stock levels at checkout shouldn't be cached at all — I'd rather read the database than oversell."

What they're really checking
  • Do you know why delete beats update — the specific race?
  • Do you get the ordering right?
  • Do you keep a TTL as a backstop, and say why?
  • Do you treat staleness tolerance as a product question?
Weak answers
  • Red flag: "update the cache when the data changes" with no race analysis.
  • Red flag: claiming perfect consistency is achievable.
  • Red flag: no TTL because "we invalidate properly".
Likely follow-ups
  • What if two services write to the same table?
  • How would CDC-based invalidation work?
  • How do you invalidate a list that contains the changed item?

Advanced / scenario

Your database gets a huge traffic spike every 10 minutes. Why? ⭐ Senior-level
How I'd answer

"A regular ten-minute interval is a strong clue — that's almost certainly a cache TTL, and I'd expect to find a 10-minute expiry somewhere in the caching code."

"The mechanism is synchronised expiry. If a batch of keys was written at roughly the same time — after a deployment, a cache flush, or a restart — and they all got the same fixed 10-minute TTL, they all expire in the same instant. Every request in that moment is a miss, so the database receives the full uncached load at once."

"And it's self-perpetuating: the repopulation happens in another tight burst, all with the same TTL, so it recurs every ten minutes indefinitely. That's why it looks like a scheduled job when there isn't one."

"There may be a stampede layered on top. If one very hot key expires, every concurrent request for it misses simultaneously and they all issue the same database query — so instead of one refresh you get hundreds of identical queries."

"The fixes, and I'd do the first two immediately."

"Jitter the TTLs. Plus or minus ten percent random, so keys written together don't expire together. Three lines of code, and it breaks the synchronisation permanently. Same principle as jitter in retry backoff — synchronised clients are the problem in both cases."

"Add stampede protection. In .NET 9 that's HybridCache, where concurrent GetOrCreateAsync calls for the same key run the factory once and the rest await the result. Hand-rolling per-key coordination that works across instances and releases correctly when the loader throws is genuinely fiddly, so I'd use the built-in one."

"Consider stale-while-revalidate for the hottest keys — serve the expired value while one request refreshes in the background. Nobody waits, and the database sees one query instead of a spike. Best user experience of the options, at the cost of briefly serving stale data."

"To confirm the diagnosis rather than assume it, I'd correlate the database spike timestamps against cache miss rate and eviction metrics. If misses spike at the same instant, it's expiry. If the spike correlates with evictions instead, that's a different problem — memory pressure killing keys early — and the fix is more memory or a better eviction policy, not jitter."

"One more possibility worth ruling out: if there genuinely is a scheduled job on a ten-minute cron — a cache warmer, a sync, a report — that would look identical from the database side. So I'd check for that before rewriting caching code."

What they're really checking
  • Do you recognise a regular interval as a TTL signature?
  • Can you explain why it's self-perpetuating?
  • Do you know jitter is the fix?
  • Do you distinguish expiry from eviction?
  • Do you confirm before fixing?
Weak answers
  • Red flag: "increase the database size."
  • Red flag: "increase the TTL" — that changes the interval, not the spike.
  • Red flag: no mention of jitter.
Likely follow-ups
  • How does stale-while-revalidate work in practice?
  • How would you warm the cache after a deployment?
  • What if the spike were on eviction rather than expiry?
