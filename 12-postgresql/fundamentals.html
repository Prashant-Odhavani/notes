Fundamentals & Data Types

The type system is richer than SQL Server's, and two defaults will catch you out on day one.

🟢 Beginner 🟡 Intermediate 🔥 Must know
Quick revision
  • Unquoted identifiers fold to lowercase. Order becomes order; "Order" stays capitalised and must always be quoted.
  • String comparison is case-sensitive by default. Unlike SQL Server.
  • Use text — there's no performance benefit to varchar(n) here.
  • timestamptz, always. timestamp without a zone is a trap.
  • numeric for money, never float. There's also a money type — don't use it.
  • jsonb, not json — binary, indexable, deduplicated keys.
  • ON CONFLICT is the upsert, and it's better than MERGE.

Identifier folding 🔥 Must know

In simple terms

PostgreSQL lowercases every unquoted identifier. Double-quoting makes it exact and case-sensitive forever.

CREATE TABLE Orders (Id int);        -- actually creates "orders" with column "id"
SELECT Id FROM Orders;               -- works: both folded to lowercase
SELECT "Id" FROM "Orders";           -- ERROR: relation "Orders" does not exist

CREATE TABLE "Orders" ("Id" int);    -- creates it capitalised
SELECT Id FROM Orders;               -- ERROR: relation "orders" does not exist
SELECT "Id" FROM "Orders";           -- works, and now quoting is mandatory forever
Why this hits .NET developers specifically

EF Core names tables and columns after your C# classes and properties — so PascalCase. The Npgsql provider therefore quotes everything, giving you a database where every identifier requires quotes in hand-written SQL.

That works, and it's miserable for anyone writing queries in psql or a BI tool. Every statement needs SELECT "OrderNumber" FROM "Order".

The fix is UseSnakeCaseNamingConvention() from the EFCore.NamingConventions package. OrderNumber becomes order_number — idiomatic Postgres, no quoting needed anywhere, and EF handles the mapping.

Decide this before the first migration. Changing it later renames every table and column in the database.

Case-sensitive comparison 🔥 Must know

-- Stored: 'bob@example.com'
SELECT * FROM users WHERE email = 'Bob@Example.com';   -- 0 rows

-- SQL Server's default collation WOULD have matched this.
OptionHowAssessment
Normalise on write Lowercase before inserting Simplest and fastest. Indexes work normally. My default for emails and usernames
citext type CREATE EXTENSION citext; Transparent — comparisons and unique constraints are case-insensitive
Expression index CREATE INDEX ON users (lower(email)); Query must use lower(email) = lower($1) to match the index
Non-deterministic collation CREATE COLLATION ... deterministic = false Most correct for Unicode, but blocks some index optimisations and pattern matching
Case-insensitive uniqueness is the real requirement

Matching on read is only half the problem. Without case-insensitive uniqueness, bob@x.com and Bob@x.com are two accounts — which is an account-takeover vector, not just untidy data.

Either citext with a normal unique constraint, or a unique index on lower(email). Normalising on write plus a plain unique constraint also works, provided every write path normalises — which is why enforcing it in the database is safer.

timestamp vs timestamptz — get this right

timestamptz stores an absolute point in time (as UTC) and converts to the session time zone on read. That's almost always what you want.

timestamp stores a wall-clock reading with no zone at all. Two rows can both say 01:30 and refer to different instants — and during a daylight-saving fallback, that hour occurs twice with no way to distinguish them. It's unfixable retroactively.

Npgsql 6+ enforces the distinction: timestamptz requires DateTimeKind.Utc, and passing a Local or Unspecified DateTime throws. That change annoyed people and it's correct — it stops you storing ambiguous data. Use DateTime.UtcNow, or DateTimeOffset.

Remember this

Use jsonb. The only reason to choose json is if you must reproduce the original document byte-for-byte, including key order — which is rare and usually a sign the document should be stored as text instead.

CREATE TABLE event (
    id      bigserial PRIMARY KEY,
    payload jsonb NOT NULL
);

-- Extract: ->  returns jsonb,  ->> returns text
SELECT payload ->> 'orderId'                    AS order_id,
       payload -> 'customer' ->> 'country'      AS country
FROM   event;

-- Containment: does the document contain this shape?
SELECT * FROM event WHERE payload @> '{"status": "shipped"}';

-- GIN index supporting containment and key-exists
CREATE INDEX ix_event_payload ON event USING gin (payload);

-- B-tree on one extracted field - cheaper if you only query that field
CREATE INDEX ix_event_order ON event ((payload ->> 'orderId'));
Senior signal — when jsonb is right, and when it's an escape hatch

Good uses: genuinely schemaless data — webhook payloads you must retain verbatim, per-tenant custom fields, feature flags, audit snapshots of a row as it was, sparse attributes where 200 columns would be mostly null.

Bad use: avoiding schema design. If you're querying and filtering on the same five keys in every request, those are columns. You've given up constraints, foreign keys, type checking and good cardinality estimates in exchange for not writing a migration.

The test I'd apply: does anything enforce what's in there? If the answer is "the application, we hope", and the data is business-critical, it should be columns.

Being able to argue both sides is the senior answer — a lot of Postgres codebases have a data jsonb column that quietly became the actual schema, with no constraints on any of it.

Two jsonb costs to know

Updates rewrite the whole document. Changing one key in a 200 KB jsonb value writes a new 200 KB row version — MVCC has no partial update. A hot document updated frequently causes serious bloat.

Large values go to TOAST. Anything over roughly 2 KB is compressed and moved to a side table, so reading it is an extra fetch. That's fine for occasional reads and expensive if it's on your hot path.

Arrays 🟡 Intermediate

CREATE TABLE article (
    id   bigserial PRIMARY KEY,
    tags text[] NOT NULL DEFAULT '{}'
);

SELECT * FROM article WHERE 'postgres' = ANY(tags);   -- contains
SELECT * FROM article WHERE tags @> ARRAY['sql'];      -- contains all
SELECT * FROM article WHERE tags && ARRAY['sql','ef']; -- overlaps

CREATE INDEX ix_article_tags ON article USING gin (tags);
When an array beats a junction table

Use an array for a small, unordered set of scalars with no attributes of their own and no referential integrity requirement — tags, permission strings, ISO country codes.

Use a junction table the moment you need a foreign key, per-relationship data (who added it, when), or you want to query "which articles have this tag" efficiently across a large table without relying on a GIN index.

The array is genuinely simpler when it fits. The mistake is using one for something that turns out to be an entity — you can't constrain it, and refactoring later means a data migration. Note EF Core maps string[] to text[] natively with Npgsql, so this is ergonomic from .NET.

Sequences aren't transactional

A rolled-back transaction does not return its sequence value. That's deliberate — otherwise the sequence would be a contention point serialising all inserts.

So identity columns have gaps. That's normal and not a bug. It does mean an ID is not a count, and never use "max ID" as a row count or an invoice number.

Also: after a bulk data load with explicit IDs, the sequence is left behind and the next insert collides. Reset it with setval — a classic post-migration failure.

Upsert with ON CONFLICT 🔥 Must know

INSERT INTO inventory (sku, stock, updated_at)
VALUES ($1, $2, now())
ON CONFLICT (sku) DO UPDATE
    SET stock      = inventory.stock + EXCLUDED.stock,
        updated_at = now();
INSERT INTO processed_message (message_id, processed_at)
VALUES ($1, now())
ON CONFLICT (message_id) DO NOTHING;
-- 0 rows affected = already processed. The inbox pattern in one statement.
Why this beats MERGE

ON CONFLICT is atomic and concurrency-safe by design — it relies on a unique constraint, so two concurrent inserts can't both succeed.

SQL Server's MERGE needs HOLDLOCK to be safe and has a history of correctness bugs. This is one place Postgres is simply better, and it's worth saying so.

EXCLUDED is the row you tried to insert — that's the keyword people forget.

This is the idempotency primitive

ON CONFLICT DO NOTHING plus checking the affected-row count is the whole implementation of an inbox, or an idempotency key.

Insert wins → do the work. Zero rows → already handled, return the previous outcome. One statement, no race window, no read-then-insert gap.

Schemas and search_path 🟡 Intermediate

In simple terms

A Postgres schema is a namespace inside a database — closest to a SQL Server schema, not a SQL Server database.

search_path decides which schemas unqualified names resolve against. Default: "$user", public.

The search_path security issue

If a user can create objects in a schema that appears earlier in search_path, they can shadow a legitimate function or table — and code calling it unqualified silently gets theirs.

That's a real privilege-escalation path, especially inside SECURITY DEFINER functions.

Mitigations: REVOKE CREATE ON SCHEMA public FROM PUBLIC (the default since Postgres 15), and set an explicit search_path on any SECURITY DEFINER function. Worth knowing because it's a genuine Postgres-specific security question.

Schema-per-tenant

A common multi-tenant pattern: one schema per tenant, switching search_path per connection. Good isolation and per-tenant backup within one database.

It scales to hundreds of tenants, not thousands — every schema multiplies the system catalogue, and migrations must run N times. It also interacts badly with connection pooling, since search_path is connection state that a pooled connection carries into the next request.

See multi-tenant SaaS for the trade-offs.

Generated columns and domains 💡 Good to know

CREATE TABLE order_line (
    quantity   int NOT NULL,
    unit_price numeric(19,4) NOT NULL,
    total      numeric(19,4) GENERATED ALWAYS AS (quantity * unit_price) STORED
);

-- A reusable constrained type
CREATE DOMAIN email AS citext
    CHECK (VALUE ~ '^[^@\s]+@[^@\s]+\.[^@\s]+$');

Generated columns are always STORED in PostgreSQL — there's no virtual/computed-on-read variant as in SQL Server. So they cost storage and are indexable, which is usually the trade you want.

Key takeaways
  • Unquoted identifiers fold to lowercase. Use snake_case naming with EF Core, decided before the first migration.
  • String comparison is case-sensitive. Fix uniqueness, not just matching.
  • text over varchar(n) — no performance difference.
  • timestamptz always; Npgsql enforces UTC for it.
  • numeric for money; avoid the money type.
  • jsonb over json. Great for genuinely schemaless data, bad as a substitute for schema design.
  • jsonb updates rewrite the whole document; large values go to TOAST.
  • Arrays suit attribute-free scalar sets; junction tables once you need integrity.
  • Sequences aren't transactional — gaps are normal, and reset them after a bulk load.
  • ON CONFLICT is a safe, atomic upsert and the natural idempotency primitive.

Common mistakes

  • PascalCase identifiers, so every hand-written query needs quotes.
  • Assuming case-insensitive comparison, breaking login and creating duplicate accounts.
  • timestamp instead of timestamptz.
  • varchar(50) everywhere out of SQL Server habit.
  • The money type — locale-dependent and fixed-scale.
  • json instead of jsonb, so nothing is indexable.
  • jsonb as the whole schema, losing every constraint.
  • Frequent small updates to large jsonb documents — bloat.
  • Not resetting sequences after importing rows with explicit IDs.
  • Read-then-insert where ON CONFLICT would be atomic.
  • Leaving CREATE on public granted to everyone.

Interview questions

Intermediate

You're moving a .NET app from SQL Server to PostgreSQL. What breaks? 🔥 Must know
How I'd answer

"I'd split it into things that break loudly and things that break silently. The silent ones are the dangerous list."

"Silent, and the first thing I'd check: case-sensitive string comparison. SQL Server's default collation is case-insensitive; Postgres is case-sensitive. So WHERE email = 'Bob@x.com' stops matching bob@x.com — logins fail, lookups return nothing, and no error is raised anywhere."

"Worse than the matching problem is uniqueness. Without case-insensitive uniqueness, bob@x.com and Bob@x.com become two accounts, which is an account-takeover vector rather than untidy data. I'd fix that with citext or a unique index on lower(email) — enforced in the database, not by hoping every write path normalises."

"Silent: timestamp vs timestamptz. If the migration maps to plain timestamp, you've stored wall-clock readings with no zone. Ambiguous across daylight-saving transitions and unfixable retroactively. timestamptz throughout, and Npgsql 6+ actually enforces this by rejecting non-UTC DateTime values for it — irritating at first, and it's protecting you."

"Loud: identifier folding. Postgres lowercases unquoted identifiers, so EF Core's PascalCase names all get quoted. It works, but you end up with a database where every hand-written query needs SELECT "OrderNumber" FROM "Order", which anyone using psql or a BI tool will hate. I'd use UseSnakeCaseNamingConvention() — and decide that before the first migration, because changing it later renames everything."

"Loud: T-SQL doesn't port. Stored procedures, functions and triggers need rewriting in PL/pgSQL. Different syntax, different error handling, no @@IDENTITY, TOP becomes LIMIT, no NOLOCK — and that last one isn't a loss, since Postgres readers never block writers anyway."

"Feature mapping. rowversion for optimistic concurrency becomes UseXminAsConcurrencyToken(). MERGE becomes ON CONFLICT, which is genuinely better — atomic by design rather than needing HOLDLOCK. Full-text moves from catalogues to tsvector plus a GIN index."

"Operational, and easy to overlook: connection pooling. Postgres uses a process per connection, not a thread, so connections are much more expensive. A .NET service that scaled out happily against SQL Server can exhaust max_connections. If there are several services or it's serverless, PgBouncer goes in front."

"And VACUUM. Postgres keeps dead row versions in the table, so a write-heavy workload needs autovacuum tuned or you get bloat and eventually a wraparound emergency. That's a new operational responsibility that has no SQL Server equivalent."

"How I'd de-risk it: run both in parallel and diff results on a real dataset, because the case-sensitivity and null-ordering differences won't show up in unit tests. Postgres also sorts NULLs last by default rather than first, which quietly changes paginated results."

What they're really checking
  • Do you lead with the silent failures?
  • Do you catch the uniqueness problem, not just matching?
  • Do you know the timestamptz and Npgsql behaviour?
  • Do you raise connection pooling and vacuum as new responsibilities?
Weak answers
  • Red flag: "EF Core abstracts it, just change the provider."
  • Red flag: only listing syntax differences.
Likely follow-ups
  • How would you make email lookups case-insensitive and fast?
  • What's xmin?
  • Why is a process-per-connection model a problem?

Advanced / scenario

A developer wants to store all tenant custom fields in a jsonb column. Do you agree? ⭐ Senior-level
How I'd answer

"For genuinely tenant-defined custom fields, yes — that's one of the best uses of jsonb. The alternative is either 200 mostly-null columns, or an entity-attribute-value table, and EAV is worse: every query becomes a pile of self-joins and you still have no type safety."

"So if tenants really do define their own fields at runtime, jsonb is the right tool. It's indexable with GIN, queryable with containment operators, and Npgsql maps it to a POCO or JsonDocument cleanly."

"What I'd want to establish first is whether they're actually tenant-defined. The question I'd ask is: is the application code reading specific keys by name? If there's code doing payload->>'priority' and filtering on it, that's not a custom field — that's a column someone didn't want to write a migration for. Those should be columns, because as jsonb you've given up not-null constraints, foreign keys, type checking and good cardinality estimates."

"The planner point is worth being concrete about: Postgres has poor statistics on jsonb key extraction, so a filter on an extracted key often estimates badly and you get the wrong join strategy. That's a real performance consequence, not a purity argument."

"So my answer would be: both. Fields the product defines are columns. Genuinely tenant-defined ones go in jsonb. That's a very common and defensible shape."

"Then I'd want three things in place."

"Some validation. Unconstrained jsonb becomes a landfill. Either a CHECK constraint on structure, or a tenant-level field-definition table the application validates against, so we know what should be in there. Without that, in two years nobody can tell you what keys exist or what types they hold."

"The right index for the actual queries. A GIN index on the whole column supports containment and key-exists. If they only ever filter on two specific keys, a B-tree expression index on those extractions is much smaller and faster. Indexing the whole document by default is a common waste."

"Awareness of the update cost. MVCC has no partial update, so changing one key rewrites the entire document as a new row version. On a large document updated frequently, that's significant bloat and vacuum pressure. And anything over about 2 KB goes to TOAST, so it's an extra fetch on read. If the custom fields are hot and the document is large, I'd want to know that before committing."

"The failure mode I'd name explicitly: I've seen a data jsonb column start as 'just a few custom fields' and quietly become the real schema, with the whole domain inside it and no constraints on any of it. That's the outcome to design against, and the way to prevent it is being strict now about which fields are product-defined."

What they're really checking
  • Do you accept jsonb where it's appropriate rather than reflexively preferring columns?
  • Do you have a test for which is which?
  • Do you know the planner and statistics implication?
  • Do you know the update-rewrite and TOAST costs?
  • Do you insist on some validation?
Weak answers
  • Red flag: "never use jsonb, normalise everything."
  • Red flag: "jsonb for everything, it's flexible."
  • Red flag: no mention of indexing or validation.
Likely follow-ups
  • GIN vs a B-tree expression index here?
  • How would you validate the structure?
  • How do you migrate a jsonb key into a real column later?
