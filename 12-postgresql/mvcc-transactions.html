MVCC, Transactions & Locking

The one genuinely different thing about PostgreSQL. Understand MVCC and half the operational behaviour follows from it.

🟡 Intermediate 🔴 Advanced 🔥 Must know
Quick revision
  • Every row version carries xmin and xmax — the transactions that created and deleted it.
  • Readers never block writers, writers never block readers. No exceptions, no setting.
  • An UPDATE is delete-plus-insert. Old versions stay in the table until vacuumed.
  • Three isolation levels: Read Committed (default), Repeatable Read, Serializable. There's no Read Uncommitted.
  • PostgreSQL's SERIALIZABLE is real — SSI, not locking. It can raise serialization failures you must retry.
  • SELECT ... FOR UPDATE SKIP LOCKED is the queue primitive.
  • Long-running transactions are the enemy — they block vacuum and cause bloat.

How MVCC works 🔥 Must know

In simple terms

PostgreSQL never overwrites a row in place. An UPDATE writes a new version and marks the old one as expired.

Each version records which transaction created it (xmin) and which deleted it (xmax). Your transaction has a snapshot — a set of transaction IDs it considers visible — and reads whichever version that snapshot says it should see.

SELECT xmin, xmax, ctid, * FROM "order" WHERE id = 42;
-- xmin: transaction that created this version
-- xmax: transaction that expired it (0 if still current)
-- ctid: physical location (page, offset)
Think of it this way

A document with tracked changes that are never accepted or rejected — just accumulated.

Everyone reading gets a view filtered to "the state as of when I started reading". Nobody waits for anyone else, because nobody is editing the copy you're looking at.

Eventually someone has to go through and delete the superseded revisions. That's VACUUM.

Everything follows from this one design
  • Readers never block writers — a reader looks at an older version, so a writer creating a new one doesn't interfere.
  • VACUUM exists because dead versions are in the table, not a separate version store.
  • Tables bloat if vacuum can't keep up.
  • COUNT(*) is a scan — visibility must be checked per row.
  • Updates are expensive — a new row version usually means updating every index.
  • Long transactions are harmful — they hold a snapshot, so nothing newer than it can be cleaned up.
Senior signal — the comparison to SQL Server

SQL Server's default is locking Read Committed: readers take shared locks, so readers block writers. Row versioning is optional, and when enabled with RCSI the versions go to tempdb.

PostgreSQL has no locking-reads mode at all. Versions live in the table.

So the trade is visible: Postgres gets non-blocking reads for free and pays with vacuum and bloat. SQL Server gets no vacuum but blocks readers unless you opt into versioning, and then pays in tempdb.

Framing it as a trade rather than "Postgres is better" is the answer that lands.

Two differences from the SQL Server table

Dirty reads cannot happen. MVCC means you always read a committed version — there's no mechanism to see uncommitted data. READ UNCOMMITTED is accepted for compatibility and does nothing.

PostgreSQL's REPEATABLE READ prevents phantom reads. The ANSI standard allows them at that level, and SQL Server does allow them — but Postgres implements it as a full snapshot taken at the start of the transaction, so no new rows can appear. It's closer to SQL Server's SNAPSHOT than to its REPEATABLE READ.

Read Committed — the per-statement subtlety

What it actually guarantees

Each statement gets a fresh snapshot. So two identical queries in one transaction can return different results.

Fine for most work. Wrong when you need several statements to agree on one consistent view — a report with subtotals, or a balance check followed by a transfer.

The Read Committed behaviour that surprises everyone

If an UPDATE is blocked waiting for another transaction's row lock, and that transaction commits a change to the row, PostgreSQL re-evaluates the WHERE clause against the new version and proceeds if it still matches.

So UPDATE accounts SET balance = balance - 100 WHERE id = 1 AND balance >= 100 is safe — it re-checks against the committed value.

But a SELECT earlier in the transaction saw the old value. So read-then-update logic can act on a value that's already stale, even though the UPDATE itself is atomic. That's why putting the condition in the UPDATE matters here too.

Serializable — genuinely different ⭐ Senior-level

In simple terms

SQL Server implements SERIALIZABLE with range locks — it physically prevents conflicting access, which blocks a lot.

PostgreSQL uses Serializable Snapshot Isolation (SSI): transactions run optimistically with no extra locking, and Postgres detects whether the outcome could differ from some serial order. If so, it aborts one with a serialization failure.

Write skew — the anomaly only Serializable catches

-- Rule: at least one doctor must always be on call.
-- Currently two are: Alice and Bob.

-- Transaction A (Alice)              -- Transaction B (Bob)
BEGIN;                                BEGIN;
SELECT count(*) FROM shift            SELECT count(*) FROM shift
 WHERE on_call = true;   -- 2          WHERE on_call = true;   -- 2
-- "2 > 1, safe to go off call"       -- "2 > 1, safe to go off call"
UPDATE shift SET on_call = false      UPDATE shift SET on_call = false
 WHERE doctor = 'Alice';               WHERE doctor = 'Bob';
COMMIT;                               COMMIT;
-- Nobody is on call. Neither transaction did anything wrong.
Why lower levels can't catch this

They wrote different rows. There's no update conflict, no lost update, no phantom in either transaction's own reads.

The problem is that each decision was based on data the other invalidated. Under SERIALIZABLE, Postgres tracks the read/write dependencies, spots the cycle, and aborts one with error 40001.

// 40001 = serialization_failure, 40P01 = deadlock_detected. Both retryable.
var policy = Policy
    .Handle<PostgresException>(e => e.SqlState is "40001" or "40P01")
    .WaitAndRetryAsync(3, attempt =>
        TimeSpan.FromMilliseconds(Random.Shared.Next(20, 60) * attempt));   // jitter

await policy.ExecuteAsync(async () =>
{
    await using var tx = await db.Database
        .BeginTransactionAsync(IsolationLevel.Serializable);
    // ... work ...
    await tx.CommitAsync();
});
Serializable without retry logic is broken

Serialization failures aren't errors in the usual sense — they're the mechanism working as designed. The transaction was rolled back cleanly and re-running it will normally succeed.

So if you enable SERIALIZABLE and don't retry, you've converted a correctness guarantee into intermittent user-facing 500s under load.

Two requirements: the retried block must be idempotent (no emails sent, no messages published inside it), and retries need jitter so two conflicting transactions don't collide again immediately.

Senior signal — when Serializable is the right call

The strongest case is a multi-row invariant you can't express as a constraint — "at least one doctor on call", "total allocations must not exceed budget", "no overlapping bookings across these rules". Those are write-skew problems, and Serializable solves them correctly with far less code than hand-rolled locking.

Where I wouldn't use it: as a general default. It costs retries, and the predicate-tracking structures have a memory limit — exceed it and Postgres escalates to coarser tracking, producing false serialization failures on transactions that weren't really conflicting.

So: Serializable for the specific operations with a genuine multi-row invariant, Read Committed everywhere else. Saying "I'd apply it per transaction, not globally" is the discriminating answer.

SKIP LOCKED — a proper work queue

WITH claimed AS (
    SELECT id
    FROM   job
    WHERE  status = 'pending'
    ORDER BY created_at
    LIMIT  10
    FOR UPDATE SKIP LOCKED          -- each worker gets a different 10
)
UPDATE job j
SET    status = 'processing', started_at = now(), worker_id = $1
FROM   claimed c
WHERE  j.id = c.id
RETURNING j.*;
Why this matters

Without SKIP LOCKED, workers queue behind each other on the same rows — ten workers effectively process one at a time.

With it, each worker takes rows nobody else has locked. Linear scaling, no duplicate processing, and it's all one atomic statement.

This is a legitimately good answer to "how would you build a job queue without a message broker?" — combined with RETURNING, the claim and the fetch are a single round trip.

When a database queue is the right choice

Good: moderate throughput, you already have Postgres, and you want the job enqueue to be transactional with your business data — which is exactly the outbox requirement. No dual write, no extra infrastructure.

Reaches its limit at: very high throughput, fan-out to many independent consumers, or needing replay and long retention. Then a real broker earns its keep.

Two operational notes: index the queue as a partial index on pending rows only, and vacuum that table aggressively — a queue table is the classic high-churn bloat case, because every claim is an update.

Advisory locks 🔴 Advanced

-- Session-scoped: held until released or the connection ends
SELECT pg_try_advisory_lock(hashtext('nightly-reconciliation'));
-- returns true if acquired, false if someone else holds it
SELECT pg_advisory_unlock(hashtext('nightly-reconciliation'));

-- Transaction-scoped: released automatically at commit or rollback
SELECT pg_advisory_xact_lock(hashtext('tenant-42-import'));
Use forNote
Only one instance runs a scheduled jobSimpler than a distributed lock if you already have Postgres

Two advisory-lock traps

Prefer pg_advisory_xact_lock — it's released automatically. A session-scoped lock leaked by code that forgot to unlock stays held until the connection closes, and with connection pooling that connection is reused, so the next request inherits the lock.

They don't survive failover. An advisory lock is in-memory on one instance. After a failover it's gone, so two workers can run simultaneously. Fine for "avoid duplicate work"; not a correctness guarantee — for that you need a database row with a unique constraint.

Long transactions are the real hazard 🔥 Must know

Why they're worse here than on SQL Server

A transaction holds a snapshot. Vacuum cannot remove any row version that snapshot might still need — even in completely unrelated tables.

So one forgotten open transaction stops cleanup database-wide. Dead rows accumulate, tables and indexes bloat, and queries slow down as they scan through the debris.

SELECT pid, state, now() - xact_start AS duration,
       now() - state_change AS idle_for,
       left(query, 80) AS query
FROM   pg_stat_activity
WHERE  state IN ('idle in transaction', 'active')
  AND  xact_start < now() - interval '5 minutes'
ORDER BY xact_start;
idle in transaction is the state to alert on

That means an application opened a transaction and then did something else — waited on an HTTP call, waited for user input, or hit an exception path that never committed or rolled back.

It holds locks and blocks vacuum while doing no work at all. It's the single most damaging thing an application can do to a Postgres database.

Defences: set idle_in_transaction_session_timeout so the server kills them, and statement_timeout to bound individual queries. In .NET, make sure every transaction is in a using block so an exception disposes and rolls it back — and never put a network call inside one.

Prevention is the same as anywhere: consistent access order, short transactions, and the right indexes so statements lock fewer rows. Postgres has no lock escalation, so a large DELETE won't suddenly take a table lock — but it will create a huge number of dead rows for vacuum to deal with.

Key takeaways
  • MVCC keeps old row versions in the table, tagged with xmin/xmax.
  • Readers never block writers — that's architectural, not configurable.
  • No dirty reads possible; READ UNCOMMITTED behaves as Read Committed.
  • REPEATABLE READ here also prevents phantoms — closer to SQL Server's SNAPSHOT.
  • Read Committed takes a fresh snapshot per statement, and re-evaluates a blocked UPDATE's WHERE.
  • SERIALIZABLE uses SSI — optimistic, no extra locking, raises 40001.
  • Serializable without retry logic converts correctness into intermittent 500s.
  • Write skew is the anomaly only Serializable catches.
  • FOR UPDATE SKIP LOCKED plus RETURNING is a solid job queue.
  • Prefer transaction-scoped advisory locks; they don't survive failover.
  • idle in transaction blocks vacuum database-wide. Set the timeouts.

Common mistakes

  • SERIALIZABLE with no retry on 40001.
  • Assuming SERIALIZABLE blocks like SQL Server's does.
  • Looking for NOLOCK — it doesn't exist and isn't needed.
  • Read-then-update instead of putting the condition in the UPDATE.
  • Transactions held open across HTTP calls or user think-time.
  • No idle_in_transaction_session_timeout.
  • A worker queue without SKIP LOCKED, so workers serialise.
  • Session-scoped advisory locks with connection pooling.
  • Treating advisory locks as a correctness guarantee across failover.
  • Retrying without jitter, so conflicting transactions collide repeatedly.

Intermediate

How does PostgreSQL's MVCC differ from SQL Server's concurrency model? 🔥 Must know
How I'd answer

"The one-sentence version: PostgreSQL keeps old row versions in the table itself; SQL Server keeps them in tempdb, and only if you opt in."

"In Postgres, an UPDATE never overwrites in place — it writes a new row version and marks the old one expired. Each version carries xmin and xmax, the transactions that created and deleted it, and your transaction has a snapshot that decides which version it sees."

"SQL Server's default is locking Read Committed: readers take shared locks, so readers block writers. You can enable row versioning with RCSI, and then versions go to tempdb."

"A surprising amount follows from that one difference, which is why I'd lead with it."

"Readers never block writers in Postgres — not as a setting, as architecture. There's no NOLOCK because there's nothing to avoid."

"VACUUM exists because dead versions are in the table. That's a real operational responsibility with no SQL Server equivalent — tables bloat if autovacuum can't keep up."

"COUNT(*) is a full scan, because visibility has to be checked per row and lives in the heap."

"Long transactions are much more damaging. A transaction holds a snapshot, and vacuum can't remove any version that snapshot might need — including in unrelated tables. So one session sitting idle in transaction blocks cleanup database-wide. On SQL Server a long transaction holds locks and grows tempdb; on Postgres it degrades the whole database."

"Updates are relatively expensive, because a new row version usually means adding an entry to every index. Postgres mitigates this with HOT updates — if no indexed column changed and there's space on the page, no index is touched at all. Which is a good argument for not indexing volatile columns unnecessarily."

"I'd frame it as a genuine trade rather than one being better. Postgres gets non-blocking reads for free and pays with vacuum and bloat. SQL Server has no vacuum but blocks readers by default, and pays in tempdb once you enable versioning."

What they're really checking
  • Can you name where versions are stored — the key difference?
  • Do you derive consequences rather than list features?
  • Do you know why long transactions matter more here?
  • Do you present it as a trade-off?
Likely follow-ups
  • What exactly does vacuum do?
  • Why is COUNT(*) slow?

Advanced / scenario

You need to enforce "at most one active subscription per customer" but the rule spans several rows. How? ⭐ Senior-level
How I'd answer

"I'd try to make it a constraint first, because a constraint is enforced regardless of which code path writes, and only reach for isolation levels if the rule genuinely can't be expressed that way."

"For this specific rule, a partial unique index does it exactly: CREATE UNIQUE INDEX ux_one_active ON subscription (customer_id) WHERE status = 'active'."

"That's ideal. It's a real constraint, so two concurrent inserts can't both win — one gets a unique violation I catch and handle. No isolation level needed, no retry loop, and nobody can bypass it with a script. This is also a case where Postgres is nicer than SQL Server, because partial indexes here work with parameterised queries."

"If the rule were about overlapping date ranges — no two active periods may overlap for a customer — I'd use an exclusion constraint with GiST: EXCLUDE USING gist (customer_id WITH =, active_period WITH &&). Same benefit: the database enforces it."

"Where neither works is a rule involving an aggregate across rows — 'total allocated must not exceed the budget', or the classic 'at least one doctor must remain on call'. You can't express those as a unique or exclusion constraint, and they're vulnerable to write skew: two transactions each read the aggregate, each independently conclude their change is safe, and both commit. They touched different rows, so there's no update conflict — no lower isolation level catches it."

"For that, SERIALIZABLE is the correct tool. Postgres implements it as SSI, which is genuinely different from SQL Server's range-locking version — it adds no locks, runs optimistically, and detects whether the outcome could differ from a serial order. If it could, one transaction is aborted with error 40001."

"Which means retry logic is mandatory, not optional. A serialization failure isn't an error, it's the mechanism working — the transaction rolled back cleanly and re-running it will usually succeed. I'd wrap it in a retry policy handling 40001 and 40P01, with jitter so two conflicting transactions don't collide again immediately. And the retried block has to be idempotent, so no emails or published messages inside it."

"I'd apply Serializable per transaction, not globally. It costs retries, and the predicate-tracking structures have a memory limit — exceed it and Postgres falls back to coarser tracking, which produces false serialization failures on transactions that weren't actually conflicting."

"The alternative to Serializable, if I wanted to avoid retries, is to serialise on a single row — SELECT ... FOR UPDATE on the customer row before checking the aggregate. That gives a clear lock ordering and no retries, at the cost of throughput per customer. For a per-customer rule that's often perfectly acceptable, since contention is naturally partitioned."

"So the order I'd work through: unique or exclusion constraint if the rule fits, then a row lock on the natural parent, then Serializable with retries. Constraint first, because it's the only option nothing can bypass."

What they're really checking
  • Do you reach for a constraint before an isolation level?
  • Do you know partial unique and exclusion constraints?
  • Can you identify write skew and why lower levels miss it?
  • Do you know Postgres Serializable is SSI and needs retries?
  • Do you offer the row-lock alternative?
Weak answers
  • Red flag: checking in application code with no database enforcement.
  • Red flag: SERIALIZABLE with no retry handling.
  • Red flag: assuming it blocks like SQL Server's Serializable.
Likely follow-ups
  • Write the exclusion constraint.
  • How do you surface a unique violation as a friendly error?
  • What causes false serialization failures?
Build a job queue in PostgreSQL for ten worker instances. ⭐ Senior-level
How I'd answer

"The core of it is SELECT ... FOR UPDATE SKIP LOCKED, which is what makes this viable rather than a bad idea."

"Each worker runs a single statement: a CTE that selects the next N pending jobs ordered by creation time with FOR UPDATE SKIP LOCKED, then updates those rows to 'processing' with RETURNING to get them back. One round trip, atomic claim and fetch."

"SKIP LOCKED is the essential part. Without it, all ten workers queue behind each other on the same top rows, so you effectively get one worker. With it, each takes rows nobody else has locked — linear scaling and no duplicate processing."

"The reason I'd consider a database queue at all rather than a broker: the enqueue can be transactional with the business data. Creating an order and queueing its confirmation email happen in one transaction, so there's no dual-write problem. That's the outbox pattern, and getting it for free is a genuine advantage over a separate broker."

"Details I'd get right:"

"A partial index on pending jobs — ON job (created_at) WHERE status = 'pending'. The queue table may hold millions of completed rows; the index should only cover the few thousand that are claimable. Rows leave the index as they're processed, so it stays tiny."

"Aggressive autovacuum on that table. Every claim is an update, so a queue table is the classic high-churn bloat case — I'd set per-table autovacuum thresholds much lower than the default rather than relying on the global settings."

"Stuck-job recovery. If a worker dies mid-job the row stays 'processing' forever. So I'd record started_at and worker_id, and have a sweeper reset rows in processing beyond a timeout back to pending. Plus an attempt counter and a dead-letter status, so a job that fails repeatedly stops being retried and gets surfaced rather than looping."

"Archiving. Completed jobs need moving out or the table grows unbounded. Either a delete-after-retention job, or partition by month and drop old partitions — which is far cheaper than deleting rows."

"Avoid polling every 100ms from ten workers. That's a constant load for nothing. I'd use LISTEN/NOTIFY to wake workers when a job is enqueued, with a slow poll as a fallback — because NOTIFY isn't durable, so a missed notification needs the poll to catch it."

"Where I'd say this stops being the right choice: very high throughput, fan-out to many independent consumers, or needing replay and long retention. Then a real broker earns its complexity. But for moderate volumes in a system already on Postgres, this is less infrastructure, transactionally correct, and easier to inspect — you can just query the queue."

What they're really checking
  • Do you know SKIP LOCKED and why it's essential?
  • Do you raise the transactional-enqueue advantage?
  • Do you handle stuck jobs and dead-lettering?
  • Do you think about bloat and archiving?
  • Do you know when a broker is the better answer?
Weak answers
  • Red flag: SELECT then UPDATE in separate statements, allowing duplicate claims.
  • Red flag: no recovery for crashed workers.
  • Red flag: no awareness of bloat on a high-churn table.
Likely follow-ups
  • How do you guarantee ordering per customer?
  • What are the limits of LISTEN/NOTIFY?
  • How would you add scheduled/delayed jobs?
