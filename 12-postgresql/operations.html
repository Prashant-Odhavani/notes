Vacuum, Partitioning, Replication & HA

The operational side. Vacuum and connection pooling are the two things that catch teams moving from SQL Server.

🔴 Advanced ⭐ Senior-level 💡 Good to know
Quick revision
  • Vacuum reclaims dead row versions and updates the visibility map. It's not optional maintenance — it's part of how the engine works.
  • Bloat is space held by dead rows. Autovacuum prevents it; it doesn't shrink an already-bloated table.
  • Transaction-ID wraparound is the emergency case. Postgres will refuse writes to protect itself.
  • Never VACUUM FULL in production — it takes an exclusive lock. Use pg_repack.
  • Declarative partitioning — and DETACH is the near-instant archive.
  • One process per connection, so you need PgBouncer beyond a few hundred.
  • Replication is physical (streaming) or logical. Different tools for different jobs.

Vacuum 🔥 Must know

In simple terms

MVCC leaves dead row versions in the table. Vacuum does three things:

  1. Marks dead row space reusable for future inserts in that table.
  2. Updates the visibility map, which is what enables index-only scans.
  3. Freezes old transaction IDs to prevent wraparound.

All three matter. People know about the first and are surprised by the other two.

VACUUMVACUUM FULL
Lock takenLight — reads and writes continueACCESS EXCLUSIVE — blocks everything
Returns space to the OSNo — reuses it internallyYes — rewrites the table
Disk neededNone extraA second full copy
Rebuilds indexesNoYes
Production-safeYesNo
VACUUM FULL is an outage

It takes an ACCESS EXCLUSIVE lock — no reads, no writes, for as long as it takes to rewrite the table. On a 200 GB table that's hours, and it needs 200 GB of free disk.

Use pg_repack instead. It achieves the same compaction by building a copy and swapping it in, taking only a brief exclusive lock at the very end. It needs the same extra disk, and it doesn't take your application down.

Knowing pg_repack exists is a good operational signal, because the obvious answer to bloat is the dangerous one.

Autovacuum tuning

-- Default: vacuum when dead rows > 50 + 20% of the table.
-- On a 100-million-row table that's 20 MILLION dead rows first.
SHOW autovacuum_vacuum_scale_factor;   -- 0.2

-- Per-table override for a high-churn table
ALTER TABLE job SET (
    autovacuum_vacuum_scale_factor  = 0.01,   -- 1% instead of 20%
    autovacuum_vacuum_cost_delay    = 0,      -- don't throttle
    autovacuum_analyze_scale_factor = 0.02
);
Remember this

The autovacuum defaults are tuned for small tables.

The 20% scale factor means a large table accumulates a huge amount of bloat before vacuum even starts — and then the vacuum is enormous and slow.

For big or high-churn tables, set per-table thresholds. Small and frequent beats large and rare.

SELECT relname,
       n_live_tup, n_dead_tup,
       round(100.0 * n_dead_tup / nullif(n_live_tup + n_dead_tup, 0), 1) AS dead_pct,
       last_autovacuum, last_autoanalyze
FROM   pg_stat_user_tables
WHERE  n_dead_tup > 10000
ORDER BY n_dead_tup DESC;
Three things that stop vacuum working

1. Long-running transactions. Vacuum can't remove any version a live snapshot might need — anywhere in the database. One session idle in transaction stalls cleanup globally. This is the most common cause by far.

2. Abandoned replication slots. A slot holds WAL and an xmin horizon for a replica that may no longer exist. Bloat grows and the WAL directory fills the disk. Check pg_replication_slots for inactive slots — this one has taken down real systems.

3. Cost-based throttling. Autovacuum deliberately pauses to limit I/O impact. On a busy table it can fall permanently behind. autovacuum_vacuum_cost_delay defaults to 2ms — setting it to 0 for specific tables lets vacuum keep up.

Transaction-ID wraparound ⭐ Senior-level

In simple terms

Transaction IDs are 32-bit — about 4 billion. Visibility is decided by comparing them, so they can't simply wrap around; old rows would appear to be from the future and become invisible.

Vacuum prevents this by freezing old rows — marking them as visible to everyone, so their original transaction ID no longer matters.

What happens if freezing falls behind

Postgres escalates: warnings in the log, then more aggressive autovacuum that cannot be cancelled, and finally at around 3 million remaining IDs it refuses all writes and requires a single-user-mode vacuum to recover.

That's a full outage with a recovery measured in hours, and it's the classic Postgres horror story.

The causes are always the same three: a very long-lived transaction, an abandoned replication slot, or autovacuum throttled so hard it can't keep up on a high-write table. Monitor age(datfrozenxid) and alert well before it matters.

SELECT datname, age(datfrozenxid) AS xid_age
FROM   pg_database
ORDER BY xid_age DESC;
-- autovacuum_freeze_max_age default 200,000,000. Limit ~2,000,000,000.
-- Alert well before 500 million.
Worth mentioning: 64-bit transaction IDs

This whole class of problem is being addressed by moving to 64-bit transaction IDs, work that's been in progress across recent versions. On any version you'll meet in production today, it's still a 32-bit counter you need to monitor.

Declarative partitioning 🔴 Advanced

CREATE TABLE metric (
    id          bigserial,
    recorded_at timestamptz NOT NULL,
    value       numeric NOT NULL,
    PRIMARY KEY (recorded_at, id)          -- partition key must be in the PK
) PARTITION BY RANGE (recorded_at);

CREATE TABLE metric_2024_06 PARTITION OF metric
    FOR VALUES FROM ('2024-06-01') TO ('2024-07-01');

CREATE TABLE metric_2024_07 PARTITION OF metric
    FOR VALUES FROM ('2024-07-01') TO ('2024-08-01');

-- Catch-all so an out-of-range insert doesn't fail
CREATE TABLE metric_default PARTITION OF metric DEFAULT;
-- Detach: instant, the partition becomes a standalone table
ALTER TABLE metric DETACH PARTITION metric_2023_01 CONCURRENTLY;

-- Then archive, compress or drop it
DROP TABLE metric_2023_01;
GainsCosts
Instant archive via DETACH / DROPThe partition key must be in every unique constraint, including the PK
Partition pruning skips irrelevant partitionsQueries not filtering on the key touch every partition
Vacuum and index builds per partitionToo many partitions slows planning noticeably
Cheaper, smaller indexes per partitionNeeds a job to create future partitions
Senior signal — partitioning is a vacuum strategy here

On SQL Server, partitioning is about manageability — mainly switching.

On PostgreSQL it's also a vacuum strategy, and that's the extra reason. Vacuum operates per table, so a single 2 TB table means one enormous vacuum that may never finish inside its window. Partitioned into monthly chunks, only the current partition is churning; older ones get frozen once and then need almost nothing.

And dropping old data becomes DROP TABLE on a partition rather than a DELETE that creates a billion dead rows for vacuum to chase. That's the argument that makes partitioning compelling on Postgres specifically.

The counterweight: don't over-partition. Query planning time grows with partition count, so hundreds of partitions can measurably slow simple queries.

Two practical details

DETACH CONCURRENTLY (PostgreSQL 14+) avoids the brief exclusive lock that plain DETACH takes on the parent — worth using on a busy table.

Create partitions ahead of time. A scheduled job that maintains the next few months, or an extension like pg_partman. Without it, inserts land in the DEFAULT partition (or fail if there isn't one) — and attaching a new partition afterwards requires scanning the default partition to check for rows that belong elsewhere, which is slow and takes locks.

Replication 🟡 Intermediate

Streaming (physical)Logical
ReplicatesWAL — byte-level block changesRow changes, decoded
GranularityWhole clusterPer table / per publication
Replica isRead-only, identicalWritable; can have extra tables and indexes

How to choose

Streaming for high availability. One command to set up, minimal lag, an exact copy.

Logical for moving data between systems — a major-version upgrade with no downtime, or feeding a data warehouse or search index.

Logical replication is also how CDC tools work — Debezium reads the logical decoding stream, which is how you get an event feed out of Postgres without triggers.

Synchronous vs asynchronous

synchronous_commitCommit waits untilOn failover
offNothing — not even local diskCan lose recent local commits
localLocal WAL flushedCan lose whatever hadn't replicated
on (default)Local flush, and standby flush if configuredDepends on synchronous_standby_names

Synchronous replication with one standby is a liability

If you require synchronous commit and the only synchronous standby becomes unavailable, the primary stops accepting writes — it's waiting for an acknowledgement that will never arrive.

You've made a durability improvement into an availability risk. So synchronous replication needs at least two candidate standbys (ANY 1 (s1, s2)), or a monitoring system that demotes to asynchronous automatically.

This is a good thing to raise unprompted, because "use synchronous replication for zero data loss" sounds unambiguously correct until you think about the failure mode.

Replica lag and read-your-own-writes

Asynchronous replicas lag. A user creates a record, gets redirected, and the replica hasn't received it — a 404 on something they just made.

Same problem and same fixes as SQL Server read replicas: route per query rather than globally, or return the entity you already have instead of re-reading.

Postgres-specific detail: a long query on a hot standby can conflict with WAL replay. Either replay pauses (increasing lag) or the query is cancelled, depending on hot_standby_feedback and max_standby_streaming_delay. Enabling hot_standby_feedback avoids the cancellations but lets replica queries hold back vacuum on the primary — another route to bloat.

Connection pooling 🔥 Must know

Why this matters more than on SQL Server

PostgreSQL forks one OS process per connection. Each has its own memory, and the scheduler has to manage all of them.

So a few hundred connections is genuinely a lot. Thousands will degrade the instance badly even if most are idle.

LayerRole
Npgsql pool (in-process)Reuses connections within one application instance. On by default
PgBouncer (external)Multiplexes many clients onto few server connections
Where a .NET service breaks

Npgsql's pool is per process. So 20 container replicas with Maximum Pool Size=100 can demand 2,000 connections — and max_connections is probably 100 or 200.

You get "remaining connection slots are reserved" errors under load, and it looks like a database problem when it's an arithmetic one.

Two fixes, and you usually want both: size the per-instance pool for the replica count (max_connections ÷ replicas, with headroom), and put PgBouncer in front so many client connections share few server ones. Serverless platforms that scale to many instances essentially require a pooler.

PgBouncer modeServer connection held forNotes
sessionThe client's whole sessionSafest, least benefit
transactionOne transactionThe usual choice — big gain, some restrictions
statementOne statementBreaks multi-statement transactions
What transaction-mode pooling breaks

Because a different server connection may serve your next transaction, anything that relies on session state stops working: SET outside a transaction, session advisory locks, LISTEN/NOTIFY, temporary tables, and WITH HOLD cursors.

Two .NET-specific ones. Server-side prepared statements are tied to a connection — Npgsql handles this if you disable them or use a compatible setup, but a naive configuration produces "prepared statement already exists" errors that are confusing to diagnose.

And a schema-per-tenant design switching search_path per request is unsafe in transaction mode, because the next request inherits it. Set it inside the transaction, or use SET LOCAL.

High availability 🔴 Advanced

Postgres has no built-in automatic failover

Unlike SQL Server Always On, core PostgreSQL provides replication but not automatic promotion. You need an external orchestrator:

  • Patroni — the de facto standard. Uses etcd or Consul for leader election.
  • repmgr, pg_auto_failover — lighter alternatives.
  • Managed services — Azure Flexible Server, RDS, Aurora do it for you. Which is a strong reason to use one.

Saying "I'd use a managed service, or Patroni if self-hosting" is the right answer. Hand-rolling failover with scripts is how you get split-brain, because correct leader election needs a consensus store — not a health check and a promotion script.

Backup and PITR

MethodGives you
pg_dump / pg_dumpallLogical dump. Portable across versions; slow to restore at scale; no PITR
pg_basebackup + WAL archivePoint-in-time recovery. The real answer
pgBackRest / barmanProduction tooling — parallel, incremental, compressed, verified
SnapshotsFast, but must be crash-consistent across all volumes
Remember this

pg_dump is not a backup strategy for a production database.

It gives no point-in-time recovery, so your RPO is "since the last dump". Restoring a large dump is also very slow because it replays every insert and rebuilds every index.

For real RPO you need a base backup plus continuous WAL archiving — pgBackRest or the managed service's equivalent. pg_dump is for moving a database, not for protecting one.

And the same rule as everywhere

A backup that has never been restored is not a backup. Automate a restore into a separate environment, measure how long it takes so you know your real RTO, and keep offsite immutable copies — replication does not protect you from DELETE without a WHERE clause, or from ransomware.

Key takeaways
  • Vacuum reclaims dead rows, maintains the visibility map, and freezes transaction IDs.
  • Autovacuum defaults suit small tables — set per-table thresholds for big or high-churn ones.
  • Long transactions and abandoned replication slots are what stop vacuum working.
  • Wraparound eventually blocks all writes. Monitor age(datfrozenxid).
  • Never VACUUM FULL in production — use pg_repack.
  • Partitioning is also a vacuum strategy here; DETACH replaces mass deletes.
  • Streaming replication for HA, logical for upgrades and CDC.
  • Synchronous replication with a single standby can halt writes.
  • One process per connection — size pools for replica count and use PgBouncer.
  • Transaction-mode pooling breaks session state, including search_path tricks.
  • No built-in failover — managed service or Patroni.
  • pg_dump is not a backup strategy; you need WAL archiving for PITR.

Common mistakes

  • Ignoring vacuum until a table is 5× its necessary size.
  • VACUUM FULL on production, causing an unplanned outage.
  • Leaving default autovacuum settings on a 200-million-row table.
  • Abandoned replication slots filling the disk and blocking cleanup.
  • Not monitoring transaction-ID age.
  • Deleting old rows in bulk instead of dropping a partition.
  • Hundreds of partitions, slowing query planning.
  • Sizing Npgsql pools per instance without multiplying by replica count.
  • Transaction-mode PgBouncer with session-scoped SET or advisory locks.
  • Synchronous replication with one standby.
  • pg_dump as the only backup.
  • Hand-rolled failover scripts with no consensus store.

Interview questions

Intermediate

What is vacuum, and what happens if it doesn't run? 🔥 Must know
How I'd answer

"Vacuum exists because of MVCC. An UPDATE in PostgreSQL doesn't overwrite a row — it writes a new version and marks the old one dead. Those dead versions stay in the table, so something has to clean them up."

"It actually does three jobs, and people usually only know the first."

"One, it marks dead row space reusable for future inserts into that table. Note it doesn't normally return space to the operating system — it recycles it internally."

"Two, it updates the visibility map, which is what makes index-only scans possible. That means vacuum is a read-performance feature, not just cleanup. A table that hasn't been vacuumed recently loses index-only scans and queries get slower with no plan change that looks meaningful."

"Three, it freezes old transaction IDs to prevent wraparound. That's the one with catastrophic consequences."

"If it falls behind, three things happen in order of severity."

"Bloat. The table and its indexes grow far beyond the live data. Every scan reads more pages, so everything slows down — and importantly, you can't fix that with query tuning."

"Lost index-only scans, from the visibility map going stale."

"Transaction-ID wraparound. IDs are 32-bit, and visibility is decided by comparing them, so they can't just wrap. If freezing falls far enough behind, Postgres escalates: warnings, then an aggressive autovacuum that can't be cancelled, and finally it refuses all writes and needs single-user-mode recovery. That's a multi-hour outage and it's the classic Postgres horror story."

"The causes are consistently the same three. Long-running transactions — vacuum can't remove any version a live snapshot might need, so one session sitting idle in transaction blocks cleanup across the whole database. Abandoned replication slots, which hold an xmin horizon for a replica that may not exist any more, and also fill the disk with retained WAL. And cost-based throttling, where autovacuum's deliberate pauses mean it can never catch up on a high-churn table."

"What I'd actually do: monitor n_dead_tup and last_autovacuum in pg_stat_user_tables, alert on age(datfrozenxid), alert on inactive replication slots, and set idle_in_transaction_session_timeout so the server kills abandoned transactions."

"And I'd tune per table. The default scale factor is 20%, which on a 100-million-row table means waiting for 20 million dead rows — then the vacuum is enormous. For high-churn tables I'd set it to 1% and remove the cost delay. Small and frequent beats large and rare."

"One thing I'd avoid: VACUUM FULL to fix existing bloat. It takes an ACCESS EXCLUSIVE lock, so nothing can read or write for however long it takes to rewrite the table. pg_repack does the same compaction with only a brief lock at the end."

What they're really checking
  • Do you connect vacuum to MVCC rather than treating it as generic maintenance?
  • Do you know the visibility map / read-performance angle?
  • Do you know about wraparound and what it does?
  • Do you name the three blockers?
  • Do you know VACUUM FULL is unsafe and what to use instead?
Weak answers
  • Red flag: "it's like a defrag, autovacuum handles it."
  • Red flag: recommending VACUUM FULL.
Likely follow-ups
  • How would you find out if a table is bloated?
  • Why does a long transaction block vacuum in an unrelated table?
  • What does freezing actually change on the row?

Advanced / scenario

Your .NET API scaled from 3 to 20 replicas and Postgres is refusing connections. What's happening? ⭐ Senior-level
How I'd answer

"Almost certainly connection exhaustion, and it's arithmetic rather than a database fault."

"Npgsql pools connections per process. So if the connection string has Maximum Pool Size=100 — and 100 is a common default people set without thinking — then 20 replicas can demand 2,000 connections. max_connections is probably 100 or 200. At 3 replicas it fit; at 20 it doesn't."

"The error is 'remaining connection slots are reserved for superusers', or Npgsql timing out waiting for a pooled connection."

"Why Postgres can't just be told to allow more: it uses one OS process per connection, not a thread. Each has its own memory and the scheduler has to manage all of them. So raising max_connections to 2,000 doesn't fix it — it converts a clear error into severe performance degradation, plus a real out-of-memory risk because work_mem is allocated per operation per connection."

"Immediate mitigation: reduce the per-instance pool size. Twenty replicas against max_connections = 200 means something like 8 per instance with headroom for migrations and admin sessions. That's a config change and a restart. Worth noting most services need far fewer connections than people assume — if requests are mostly async and queries are fast, a small pool handles high throughput."

"The proper fix: PgBouncer in transaction mode. Clients connect to PgBouncer, which multiplexes many client connections onto a small number of server connections. A server connection is only held for the duration of a transaction, so a few dozen server connections can serve thousands of clients. That's the standard answer, and it's essentially mandatory on a platform that scales to many instances."

"But I'd check what transaction-mode pooling breaks before switching, because it's not transparent. Anything relying on session state stops working: SET outside a transaction, session-scoped advisory locks, LISTEN/NOTIFY, temporary tables."

"Two that specifically bite .NET. Server-side prepared statements are tied to a connection, so a naive setup produces 'prepared statement already exists' errors — Npgsql needs configuring for this. And if there's a schema-per-tenant design switching search_path, that's now unsafe, because the next request can inherit the previous tenant's setting. It has to move inside the transaction as SET LOCAL — and that's a cross-tenant data leak if missed, so I'd check for it specifically."

"Then I'd look at whether the connections are being used or just held. Long-running or idle in transaction sessions hold a connection while doing nothing — and on Postgres those also block vacuum, so it's two problems. I'd set idle_in_transaction_session_timeout and statement_timeout regardless of how this resolves."

"And I'd double-check the total: background workers, scheduled jobs, migrations, monitoring agents and any BI tool all consume from the same budget, and they're the ones people forget when doing the arithmetic."

What they're really checking
  • Do you know Npgsql pools per process?
  • Do you know why raising max_connections isn't the fix?
  • Do you know PgBouncer and what transaction mode breaks?
  • Do you catch the search_path tenancy hazard?
  • Do you account for non-API consumers?
Weak answers
  • Red flag: "increase max_connections" as the whole answer.
  • Red flag: not knowing the pool is per process.
  • Red flag: recommending PgBouncer with no awareness of its restrictions.
Likely follow-ups
  • How would you size the pool properly?
  • How do prepared statements work with PgBouncer?
  • What monitoring would tell you this was coming?
