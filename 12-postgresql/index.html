Why a .NET developer meets PostgreSQL 🟢 Beginner

In simple terms

Since .NET became cross-platform, the reasons to pair it with SQL Server became weaker.

PostgreSQL has no licence cost, runs everywhere, is the default in most cloud marketplaces, and has a genuinely excellent EF Core provider (Npgsql). So a lot of greenfield .NET now ships on Postgres.

Which means two interview scenarios are common: "we use Postgres, are you comfortable with it?" and "we're moving off SQL Server — what would you watch out for?" This section is written for both.

The three that cause real bugs
  1. Case sensitivity. WHERE Email = 'Bob@x.com' won't match bob@x.com. This breaks logins on day one of a migration.
  2. Identifier folding. A table created as "Order" must always be quoted; created as Order it becomes order. Mixing the two produces "relation does not exist" on a table you can see.
  3. VACUUM. Dead row versions accumulate in the table. Postgres cleans up automatically, but a workload that outruns autovacuum causes bloat, and eventually a transaction-ID wraparound emergency.
Senior signal — the one-sentence summary

"PostgreSQL keeps old row versions in the table; SQL Server keeps them in tempdb, and only if you ask."

That single design difference explains why Postgres readers never block writers, why VACUUM exists, why COUNT(*) can't use an index-only scan the way it does elsewhere, why updates are effectively delete-plus-insert, and why bloat is a thing you monitor.

Being able to derive all of that from one fact is a much better answer than listing features.

The GUID point is worth internalising

On SQL Server, a random GUID as the clustered key causes constant page splits, because the clustered index is the table and rows must be stored in key order.

PostgreSQL tables are heaps — rows go wherever there's room. So a random UUID primary key has no equivalent insert penalty. Index pages still split, but that's far less costly than reorganising the table.

That's a genuinely useful thing to know if you're carrying SQL Server habits across, and a good concrete answer to "what would you do differently on Postgres?"

Connection pooling needs more thought here

PostgreSQL uses one OS process per connection, not a thread. So connections are considerably more expensive than on SQL Server, and a few hundred is a lot.

Npgsql pools client-side, which handles a single application. But several services, or a serverless platform that scales to many instances, will exhaust max_connections — at which point you need PgBouncer or the cloud provider's equivalent in front.

Covered on the operations page. It comes up often because it's the first thing that breaks when a .NET service scales out.

Version context

Content targets PostgreSQL 15–17. Where a feature is version-specific it's named — MERGE in 15, parallel VACUUM improvements, and the incremental backup added in 17.

Managed variants (Azure Database for PostgreSQL Flexible Server, AWS RDS/Aurora) differ mainly in what they let you configure and in how HA is provided; the engine behaviour described here is the same.
