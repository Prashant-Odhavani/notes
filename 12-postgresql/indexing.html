Indexing

Everything from the SQL indexing page still applies. What's new is that PostgreSQL has several index types, and heap storage changes the mechanics.

🟡 Intermediate 🔴 Advanced 🔥 Must know
Quick revision
  • Tables are heaps. There's no clustered index — every index is secondary and points at a physical row location.
  • B-tree for equality, ranges and sorting. The default and 90% of what you need.
  • GIN for "contains" — arrays, jsonb, full-text, trigram search.
  • BRIN for huge naturally-ordered tables. Tiny index, big win on time-series.
  • Partial indexes (WHERE) are excellent and underused.
  • Expression indexes make lower(email) and jsonb extraction fast.
  • Index-only scans need the visibility map — so vacuum affects read performance.
  • Always CREATE INDEX CONCURRENTLY in production.

No clustered index 🔥 Must know

In simple terms

A SQL Server table is its clustered index — rows are physically stored in key order.

A PostgreSQL table is a heap: rows go wherever there's free space. Every index is secondary, storing the key plus a ctid (physical page and offset).

ConsequenceEffect
No insert-position penaltyRandom UUID primary keys are fine — no page splits from out-of-order inserts
Every index lookup may need a heap fetchUnless the index can answer alone — see index-only scans
No "clustering key in every index"Indexes are narrower than the SQL Server equivalent
Physical order driftsCLUSTER reorders once, but doesn't maintain it
An UPDATE writes a new row versionWhich usually means updating every index on the table
Senior signal — HOT updates

Because an update creates a new row version, it normally has to add a new entry to every index — which is why tables with ten indexes have expensive updates.

PostgreSQL optimises this with HOT (Heap-Only Tuple) updates: if no indexed column changed and there's room on the same page, the new version is chained on that page and no index is touched at all.

Two practical consequences. Don't index columns you update frequently unless you need to — each one disqualifies HOT. And leave some free space with a lower fillfactor on update-heavy tables, because HOT needs room on the page.

This is a genuinely Postgres-specific answer and a strong signal in an interview.

B-tree 🔥 Must know

-- Equality columns first, then range, then sort
CREATE INDEX ix_order_customer_status_created
    ON "order" (customer_id, status, created_at DESC);

-- Covering: include non-key columns at the leaf level (PG 11+)
CREATE INDEX ix_order_lookup
    ON "order" (customer_id, created_at DESC)
    INCLUDE (total, status);

Everything on the SQL indexing page about composite column order, prefixes, selectivity and SARGability applies unchanged. B-tree supports =, <, >, BETWEEN, IN, IS NULL, LIKE 'prefix%', and ordering.

The LIKE 'prefix%' collation catch

A standard B-tree index cannot support LIKE 'abc%' unless the database uses the C locale — because in other collations, sort order doesn't match byte-prefix order.

The fix is a text_pattern_ops index:
CREATE INDEX ix_sku_prefix ON product (sku text_pattern_ops);

That index serves LIKE and ~ prefix matching but not ordinary </> comparisons — so you may want both. This catches people who add an index for a prefix search and see no improvement.

The other index types ⭐ Senior-level

TypeAnswersUse for
B-tree Equality, ranges, sorting The default. Almost everything
GIN "Contains one of / all of" jsonb, arrays, full-text (tsvector), trigram search
GiST Overlap, proximity, containment Ranges, geometry/PostGIS, nearest-neighbour, exclusion constraints
BRIN Very coarse range filtering Huge append-only tables ordered by the indexed column
Hash Equality only Rarely — B-tree does equality nearly as well and much more
How to remember which
  • Is it one scalar value per row? → B-tree.
  • Does one row contain many values you search within? → GIN. (Array of tags, jsonb keys, words in a document.)
  • Is it about overlap or distance? → GiST.
  • Is the table enormous and physically ordered by this column? → BRIN.

GIN

-- jsonb containment
CREATE INDEX ix_event_payload ON event USING gin (payload);
SELECT * FROM event WHERE payload @> '{"status":"shipped"}';

-- Array overlap
CREATE INDEX ix_article_tags ON article USING gin (tags);
SELECT * FROM article WHERE tags && ARRAY['sql','postgres'];

-- Full-text search
ALTER TABLE article ADD COLUMN search tsvector
    GENERATED ALWAYS AS (to_tsvector('english', title || ' ' || body)) STORED;
CREATE INDEX ix_article_search ON article USING gin (search);
SELECT * FROM article WHERE search @@ websearch_to_tsquery('english', 'postgres index');
CREATE EXTENSION pg_trgm;
CREATE INDEX ix_product_name_trgm ON product USING gin (name gin_trgm_ops);

-- Now a LEADING wildcard can use an index
SELECT * FROM product WHERE name ILIKE '%widget%';
Trigram indexes are a genuinely useful trick

LIKE '%text%' is the classic unindexable predicate — on SQL Server your options are full-text search or a scan.

A pg_trgm GIN index makes it indexable, because it indexes overlapping three-character sequences rather than the whole string. It also powers fuzzy matching with similarity() and the % operator, which is how you build a decent typo-tolerant search without a separate search engine.

Being able to answer "how would you make a substring search fast?" with something other than "you can't" is a strong Postgres-specific signal.

GIN write cost, and fastupdate

GIN indexes are expensive to update — one row can produce many index entries. Postgres mitigates this with a pending list (fastupdate, on by default): new entries are appended cheaply and merged later.

The side effect is that a query may have to scan that unmerged pending list, so latency is inconsistent until autovacuum merges it. On a write-heavy table with a large GIN index that's a real cause of intermittent slow queries — and the answer is usually more aggressive vacuuming of that table rather than dropping the index.

BRIN

CREATE INDEX ix_metric_time ON metric USING brin (recorded_at)
    WITH (pages_per_range = 32);
How BRIN works, and why it's so small

It stores only the min and max value per block range — not per row.

A query filtering on a date range skips every block range whose min/max can't contain it. So a BRIN index on a billion-row table might be a few megabytes, versus tens of gigabytes for a B-tree.

The catch: it only works if the data is physically ordered by that column. On append-only, time-ordered inserts it is naturally. On randomly-updated data it's useless — every block range spans the whole value range.

The BRIN answer interviewers like

"For a large append-only time-series table I'd consider BRIN on the timestamp instead of a B-tree — it's orders of magnitude smaller, cheap to maintain, and for range scans over a naturally time-ordered table it's usually enough."

Then the honest caveat: "it's much less precise, so it's wrong for point lookups, and it only works while physical order tracks the column."

Partial indexes 🔥 Must know

-- 500 million orders; 40,000 are pending
CREATE INDEX ix_order_pending ON "order" (created_at)
    WHERE status = 'pending';

-- Only index active users
CREATE UNIQUE INDEX ux_user_email_active ON users (lower(email))
    WHERE deleted_at IS NULL;
BenefitDetail
TinyFits in memory; far fewer pages to read
Cheap to maintainRows leave the index when they stop matching the predicate
Conditional uniquenessEnforce "one active row per email" while allowing soft-deleted duplicates
Senior signal — this is better than SQL Server's filtered index

SQL Server's filtered indexes have a significant limitation: a query using a parameter generally can't use them, because the value isn't known at compile time.

PostgreSQL plans at execution with the actual parameter values available, so WHERE status = $1 can use a partial index when the planner can prove the predicate holds. That makes partial indexes far more broadly useful here.

The conditional-unique pattern is also the standard Postgres answer to soft delete — and knowing that SQL Server needs a computed column or a filtered unique index with different caveats shows you've used both.

Expression indexes 🔥 Must know

-- Case-insensitive lookup
CREATE INDEX ix_users_email_lower ON users (lower(email));
SELECT * FROM users WHERE lower(email) = lower($1);   -- must match the expression

-- Index one jsonb key
CREATE INDEX ix_event_order ON event ((payload ->> 'orderId'));

-- Index a computed value
CREATE INDEX ix_order_month ON "order" (date_trunc('month', created_at));
Remember this

On SQL Server, wrapping a column in a function kills the seek and your only option is to rewrite the query.

PostgreSQL lets you index the expression itself. So the function-on-column pattern becomes viable — provided the query uses the identical expression.

That's a real capability difference, and a good thing to raise when asked about SARGability across both databases.

Index-only scans and the visibility map 🔴 Advanced

In simple terms

An index entry doesn't record whether its row version is visible to your transaction — that's in the heap.

So normally, even a covering index still needs a heap fetch to check visibility. Which would defeat the point.

PostgreSQL avoids that with the visibility map: a bitmap marking pages where every row is visible to all transactions. If the index entry points at such a page, no heap fetch is needed — an index-only scan.

Which means vacuum affects read performance

Only VACUUM sets visibility-map bits. So a table that hasn't been vacuumed recently has few all-visible pages, and index-only scans silently degrade into index scans with heap fetches.

Symptom: a query that was fast gets slower after a bulk load or a burst of writes, with no plan change that looks meaningful — but EXPLAIN ANALYZE shows a large Heap Fetches count on an Index Only Scan node.

"Vacuum is a read-performance feature, not just cleanup" is a genuinely senior thing to know, because everyone treats vacuum as garbage collection only.

Why COUNT(*) is slower than you expect

The reason

Same root cause. COUNT(*) must confirm each row is visible to your snapshot, and visibility lives in the heap.

So an exact count is a full scan — index-only if the visibility map is well maintained, still a scan either way. There's no stored row count to read.

-- Good-enough estimate, instant, from the planner statistics
SELECT reltuples::bigint FROM pg_class WHERE relname = 'order';

-- "Are there more than 1000?" without counting them all
SELECT count(*) FROM (SELECT 1 FROM "order" WHERE ... LIMIT 1001) t;
The UI consequence

Showing "1,234,567 results" on a paginated screen over a big table means a full count on every page load.

Options: an estimate from reltuples, a capped count ("1000+ results"), a maintained counter table, or keyset pagination with no total at all — which is what most large sites actually do, and for good reason.

Creating indexes safely 🔥 Must know

CREATE INDEX CONCURRENTLY ix_order_customer ON "order" (customer_id);
DROP INDEX CONCURRENTLY ix_order_old;
A plain CREATE INDEX locks out writes

It takes a SHARE lock, which blocks every INSERT, UPDATE and DELETE on the table until it finishes. On a large table that's an outage.

CONCURRENTLY takes two passes and allows writes throughout. The costs:

  • Roughly twice as slow.
  • Cannot run inside a transaction block — which matters for EF Core migrations, since Postgres runs migrations transactionally by default. You need migrationBuilder.Sql("CREATE INDEX CONCURRENTLY ...", suppressTransaction: true).
  • On failure it leaves an invalid index that still costs writes but serves no reads. Check pg_index.indisvalid, drop it, and retry — this is the part people don't know, and an invisible invalid index can sit there for months.

Finding unused and duplicate indexes ⭐ Senior-level

SELECT s.relname AS table_name,
       s.indexrelname AS index_name,
       s.idx_scan,                                    -- times used
       pg_size_pretty(pg_relation_size(s.indexrelid)) AS size
FROM   pg_stat_user_indexes s
JOIN   pg_index i ON i.indexrelid = s.indexrelid
WHERE  s.idx_scan = 0
  AND  NOT i.indisunique                              -- keep constraint indexes
ORDER BY pg_relation_size(s.indexrelid) DESC;
Two caveats before dropping anything

idx_scan is cumulative since the last statistics reset, so check pg_stat_get_db_stat_reset_time() before concluding an index is unused — a recent reset makes everything look unused.

And it's per-node: an index used only by a read replica shows zero scans on the primary. Check every instance, and sample long enough to cover monthly reporting.

Also check index bloat. A B-tree that's been heavily updated accumulates dead entries; REINDEX CONCURRENTLY (Postgres 12+) rebuilds it without blocking writes. That's often a bigger win than adding anything.

Key takeaways
  • Heap storage means no clustered index, so random UUID keys are fine.
  • HOT updates skip index maintenance when no indexed column changed — don't index volatile columns needlessly.
  • B-tree for scalars; GIN for many-values-per-row; GiST for overlap; BRIN for huge ordered tables.
  • pg_trgm GIN makes LIKE '%x%' indexable.
  • text_pattern_ops is needed for prefix LIKE outside the C locale.
  • Partial indexes work with parameters here, unlike SQL Server filtered indexes.
  • Expression indexes make function-wrapped predicates viable.
  • Index-only scans depend on the visibility map, so vacuum affects read speed.
  • COUNT(*) is a scan — visibility lives in the heap.
  • CREATE INDEX CONCURRENTLY always in production; check for invalid indexes after a failure.

Common mistakes

  • Plain CREATE INDEX on a large production table, blocking all writes.
  • Not noticing a failed CONCURRENTLY left an invalid index.
  • GIN on everything, paying heavy write costs for queries that need B-tree.
  • BRIN on randomly-ordered data, where it does nothing.
  • Expression index that doesn't match the query's expression exactly.
  • Expecting a plain B-tree to serve LIKE 'abc%' outside the C locale.
  • Assuming COUNT(*) is cheap.
  • Ignoring Heap Fetches on an index-only scan.
  • Indexing frequently-updated columns and disabling HOT updates.
  • Dropping "unused" indexes based on stats since a recent reset.

Interview questions

Intermediate

When would you use a GIN index instead of a B-tree? 🔥 Must know
How I'd answer

"The distinction I use: B-tree indexes one value per row; GIN indexes many values per row."

"So if a column holds a single scalar — a customer ID, a date, a status — that's B-tree, and it handles equality, ranges and sorting."

"GIN is for when one row contains a collection you want to search inside. An array of tags, the keys and values in a jsonb document, the words in a tsvector. GIN builds a reverse map from each individual element back to the rows containing it — essentially an inverted index."

"Concretely I'd reach for GIN for: jsonb containment queries with @>, array overlap with &&, full-text search with @@, and trigram search."

"That last one is worth highlighting because it solves a problem that has no good answer on SQL Server. LIKE '%widget%' with a leading wildcard can't use a B-tree anywhere — but a pg_trgm GIN index makes it indexable, because it indexes overlapping three-character sequences rather than whole strings. That's also how you get fuzzy, typo-tolerant matching with similarity() without adding a separate search engine."

"The cost is writes. One row can produce many index entries, so GIN is significantly more expensive to maintain than B-tree. Postgres softens that with a pending list — fastupdate — where new entries are appended cheaply and merged later. The side effect is that queries may have to scan that unmerged list, so on a write-heavy table with a big GIN index you get intermittently slower queries until autovacuum merges it. The fix there is usually more aggressive vacuuming on that table rather than removing the index."

"I'd also mention GiST briefly, since it's the one people forget: it's for overlap and proximity rather than containment — range types, geometry, nearest-neighbour searches, and it's what backs exclusion constraints. So 'no two bookings for this room can overlap' is a GiST exclusion constraint, which is a genuinely nice capability."

What they're really checking
  • Do you have a clear rule, or just a list of use cases?
  • Do you know about trigram indexes?
  • Do you know GIN's write cost and the pending list?
  • Bonus: do you know GiST and exclusion constraints?
Likely follow-ups
  • How would you index a specific jsonb key rather than the whole document?
  • Write an exclusion constraint for overlapping bookings.
  • What's the trade-off with fastupdate?

Advanced / scenario

You need to add an index to a 400-million-row table in production. How? ⭐ Senior-level
How I'd answer

"CREATE INDEX CONCURRENTLY, and I'd plan around its specific failure modes rather than just running it."

"The reason it's not optional: a plain CREATE INDEX takes a SHARE lock on the table, which blocks every insert, update and delete until it completes. On 400 million rows that's tens of minutes to hours — an outage, not a maintenance blip."

"CONCURRENTLY does two passes and lets writes continue throughout. It's roughly twice as slow, which is entirely worth it."

"Four things I'd account for."

"It can't run inside a transaction block. That matters directly for EF Core, because Npgsql runs migrations in a transaction by default. So it needs migrationBuilder.Sql("CREATE INDEX CONCURRENTLY ...", suppressTransaction: true). Get that wrong and the migration fails with a confusing error."

"On failure it leaves an invalid index. This is the part people don't know. If it's interrupted — a timeout, a deadlock, someone cancelling it — you're left with an index that still costs write overhead but is never used for reads. I'd check pg_index.indisvalid afterwards, drop any invalid index, and retry. An invisible invalid index taxing every write can sit there for months."

"It needs a long-lived snapshot, so it can be blocked by, and will hold up, other things. It waits for existing transactions to finish before starting, so a long-running transaction or an idle-in-transaction session will stall it indefinitely. I'd check pg_stat_activity first and kill idle transactions. It also means autovacuum can't clean dead rows on that table while it runs, so a long build on a hot table causes bloat."

"It's I/O heavy. I'd run it off-peak, and I'd consider raising maintenance_work_mem for the session — that has a large effect on build speed."

"Before running it at all, I'd ask whether a smaller index would do. On 400 million rows a partial index is often dramatically better: if the query only ever looks at status = 'pending' and that's 40,000 rows, indexing just those gives a tiny index that fits in memory and is cheap to maintain. Unlike SQL Server's filtered indexes, Postgres can use a partial index with parameterised queries, so this is broadly applicable."

"And if it's a time-series table queried by date range, BRIN might be the answer instead — orders of magnitude smaller and far quicker to build, as long as the physical order tracks the timestamp."

"Then I'd verify: confirm the index is valid, check with EXPLAIN ANALYZE that the query actually uses it, and watch pg_stat_user_indexes.idx_scan to confirm it's being used in production rather than just existing."

What they're really checking
  • Do you know a plain CREATE INDEX blocks writes?
  • Do you know about invalid indexes after a failed concurrent build?
  • Do you know the transaction-block restriction, and how that hits EF migrations?
  • Do you consider a smaller index instead?
  • Do you verify it's actually used?
Weak answers
  • Red flag: plain CREATE INDEX with no concern.
  • Red flag: knowing CONCURRENTLY but none of its caveats.
  • Red flag: no consideration of whether the index is the right shape.
Likely follow-ups
  • How do you find an invalid index?
  • Why does a long transaction block the build?
  • How would you do this on a table with a replica?
