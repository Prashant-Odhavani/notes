Planner, EXPLAIN & Tuning

Reading EXPLAIN ANALYZE properly is the whole skill. The tuning knobs matter far less than people think — with three exceptions.

🟡 Intermediate 🔴 Advanced 🔥 Must know
Quick revision
  • EXPLAIN (ANALYZE, BUFFERS) — always both. Buffers tells you cache vs disk.
  • Compare rows= estimated against actual rows. A big gap explains almost every bad plan.
  • Multiply by loops — actual rows is per loop. This trips everyone up once.
  • No NOLOCK equivalent needed; EXPLAIN ANALYZE actually runs the query, so wrap writes in a rolled-back transaction.
  • pg_stat_statements is the equivalent of Query Store. Enable it.
  • Three settings that matter most: work_mem, random_page_cost, effective_cache_size.
  • A sequential scan isn't a bug — for large result sets it's correct.

Reading EXPLAIN 🔥 Must know

EXPLAIN (ANALYZE, BUFFERS, VERBOSE, SETTINGS)
SELECT o.id, o.total, c.name
FROM   "order" o
JOIN   customer c ON c.id = o.customer_id
WHERE  o.created_at >= now() - interval '7 days'
ORDER BY o.created_at DESC
LIMIT  50;
OptionGives you
ANALYZEActually runs it — real row counts and timings
BUFFERSShared hits vs reads — cache or disk
VERBOSEOutput columns per node
SETTINGSAny non-default planner settings in effect
WALWAL volume generated — useful for write tuning
ANALYZE executes the statement

Unlike SQL Server's estimated plan, EXPLAIN ANALYZE genuinely runs the query — including UPDATE and DELETE.

To analyse a write safely:

BEGIN; EXPLAIN (ANALYZE, BUFFERS) UPDATE ...; ROLLBACK;

Easy to forget, and expensive to forget on production.

The loops mistake everyone makes once

actual rows=1 loops=50000 is 50,000 rows, not one. Same for time: actual time=0.002 with 50,000 loops is 100ms total, not 0.002ms.

This is the reason people misread Postgres plans. An inner node that looks trivially cheap can be the entire runtime once you multiply.

Rule: always read loops before concluding a node is cheap. A nested loop with a huge outer input is exactly what a bad estimate produces.

Use a plan visualiser

Paste the output into explain.dalibo.com or explain.depesz.com. They do the loop multiplication for you, highlight where estimates diverged badly, and show which node actually consumed the time.

Mentioning that you use one is a small practical signal — nobody reads large plans by eye.

Scan and join nodes 🟡 Intermediate

Seq ScanReads the whole tableYou expected few rows. Fine when returning most of the table

Index Only ScanAnswered from the index aloneGood — but check Heap Fetches isn't high
Bitmap Heap ScanCollect row locations, sort them, read the heap in physical orderNormal for mid-range selectivity. Watch for lossy
Nested LoopFor each outer row, probe the innerLarge outer input — the classic bad-estimate symptom
Hash JoinBuild a hash table, probe itBatches > 1 means it spilled to disk
Merge JoinBoth inputs sorted, mergedUsually cheapest when inputs are already ordered
SortOrdering rowsSort Method: external merge Disk — spilled
Bitmap scans — the one with no SQL Server equivalent

Between "few rows" (index scan) and "most rows" (seq scan) there's a middle ground.

A bitmap scan reads the index to build a bitmap of which pages contain matches, then reads those pages in physical order — turning scattered random I/O into sequential I/O.

It's usually a sign the planner made a sensible choice. If you see lossy, the bitmap exceeded work_mem and degraded to page granularity, so it re-checks each row — more work_mem helps.

Spills are the biggest single cost to look for

Sort Method: external merge Disk: 84320kB means the sort didn't fit in work_mem and went to disk. Same for Buckets: ... Batches: 8 on a hash join.

That's frequently a 10–100× difference on that node, and it's the most actionable thing in a plan.

Two fixes, and the order matters: fix the estimate (statistics, rewrite the predicate) so it plans for the real row count, or raise work_mem for that session or query. Raising it globally is risky — see below.

-- The planner thinks these are independent, so it multiplies selectivities
-- and badly underestimates. City and postcode are obviously correlated.
CREATE STATISTICS stx_address_city_post (dependencies, ndistinct)
    ON city, postcode FROM address;

ANALYZE address;
Senior signal — the independence assumption

By default the planner assumes columns are statistically independent, so it estimates WHERE city = 'Ahmedabad' AND state = 'Gujarat' as selectivity(city) × selectivity(state).

But every Ahmedabad row is already Gujarat. So the real selectivity is just the city's — and the estimate can be out by a factor of thirty.

That underestimate then produces a nested loop and a tiny work_mem grant, and the query falls off a cliff.

CREATE STATISTICS (PostgreSQL 10+) teaches the planner about the dependency. Knowing this exists is a strong signal, because it's the fix for a whole class of "the plan is inexplicably terrible" problems — and SQL Server's equivalent (multi-column statistics) works differently enough to be worth mentioning.

Finding the expensive queries 🔥 Must know

CREATE EXTENSION IF NOT EXISTS pg_stat_statements;
-- requires shared_preload_libraries = 'pg_stat_statements' and a restart

SELECT calls,
       round(total_exec_time::numeric, 1)          AS total_ms,
       round(mean_exec_time::numeric, 2)           AS mean_ms,
       rows,
       round(100.0 * shared_blks_hit
             / nullif(shared_blks_hit + shared_blks_read, 0), 1) AS cache_hit_pct,
       left(query, 90) AS query
FROM   pg_stat_statements
ORDER BY total_exec_time DESC        -- TOTAL, not mean
LIMIT  20;
Remember this

Order by total time, not mean.

A 5-second query run twice a day costs 10 seconds. An 80ms query run 40,000 times an hour costs nearly an hour of CPU.

The second is the real problem, and nobody has complained about it.

-- postgresql.conf
-- shared_preload_libraries = 'pg_stat_statements,auto_explain'
-- auto_explain.log_min_duration = '500ms'
-- auto_explain.log_analyze = on
-- auto_explain.log_buffers = on
-- auto_explain.log_nested_statements = on
Why auto_explain is worth the overhead

The hardest performance problems are intermittent — a query that's fast when you test it and slow at 3am under a different data distribution or a different plan.

auto_explain logs the actual plan for anything over a threshold, so you get the bad plan rather than trying to reproduce it. That's often the difference between solving it and guessing.

log_analyze does add per-query overhead, so use a sensible threshold rather than logging everything.

The settings that actually matter ⭐ Senior-level

SettingDefaultTypicalWhat it does
shared_buffers128 MB25% of RAM Postgres' own page cache
effective_cache_size4 GB50–75% of RAM A hint — how much the OS is likely caching. Costs nothing, changes plans
work_mem4 MB16–64 MB Per operation memory for sorts and hashes
maintenance_work_mem64 MB512 MB–2 GB Vacuum and index builds
random_page_cost4.01.1 on SSD Random vs sequential I/O cost ratio
max_connections100100–200 + PgBouncer Each connection is a process
work_mem is per operation, not per query

A single query with three sorts and two hash joins can use five times work_mem. With parallel workers, multiply again.

So work_mem = 256MB with 100 connections is not a 25 GB worst case — it's much higher, and that's how you get an out-of-memory kill on the database.

The right approach: a modest global value, then raise it for the specific queries that need it — SET LOCAL work_mem = '256MB' inside a transaction, or per-role for a reporting user. Tuning it globally to fix one report is the classic mistake.

Senior signal — random_page_cost on SSDs

The default of 4.0 encodes the assumption that a random read costs four times a sequential one — true for spinning disks, wrong for SSDs and cloud block storage, where the ratio is closer to 1.1.

Leaving it at 4.0 makes the planner systematically overvalue sequential scans and undervalue index scans. So you get seq scans on queries that should be using an index, and adding indexes doesn't help because the planner won't choose them.

Lowering it to 1.1 on SSD-backed storage is one of the highest-value single changes on a badly-tuned instance, and it's free. effective_cache_size is the other one — it allocates nothing, it just tells the planner how much caching to assume, and leaving it at 4 GB on a 64 GB machine makes index scans look far more expensive than they are.

What disables parallelism

Parallel plans are silently ruled out by: a VOLATILE function in the query, writes (INSERT/UPDATE/DELETE can't be parallelised in the same way), cursors, and FOR UPDATE.

The one that catches people: a user-defined function must be marked PARALLEL SAFE, and the default is PARALLEL UNSAFE. So adding an innocuous helper function to a SELECT can turn an 8-worker plan into a serial one, with no indication why.

That's the Postgres analogue of scalar UDFs forcing a serial plan on SQL Server — same failure, different mechanism.

A tuning workflow 🔥 Must know

  1. pg_stat_statements, ordered by total time. Find what actually costs.
  2. EXPLAIN (ANALYZE, BUFFERS) on the worst one.
  3. Compare estimated vs actual rows at each node, remembering loops.
  4. Look for spills — external merge sorts, hash batches > 1.
  5. Check shared read vs hit — is this an I/O or a CPU problem?
  6. Fix the cause: statistics, an index, a rewrite, or extended statistics.
  7. Re-measure. One change at a time.
Before tuning a query, check the boring things

Is the table bloated? A table 4× its necessary size means every scan reads 4× the pages. That's a vacuum problem, not a query problem, and no amount of query tuning fixes it.

Are statistics current? pg_stat_user_tables.last_analyze.

Is random_page_cost still 4.0 on SSD storage? If so, fix that before concluding the planner is making bad choices — it's making rational choices from wrong inputs.

Key takeaways
  • EXPLAIN (ANALYZE, BUFFERS) — and remember ANALYZE executes the statement.
  • actual rows is per loop. Multiply by loops.
  • Cost units are only meaningful for comparing plans.
  • Bitmap heap scans are a healthy middle ground, not a problem.
  • Spills to disk are the most actionable finding — fix the estimate first, then work_mem.
  • The planner assumes column independence; CREATE STATISTICS fixes correlated columns.
  • pg_stat_statements ordered by total time; auto_explain for intermittent problems.
  • work_mem is per operation — set it modestly and raise it per query.
  • random_page_cost = 1.1 on SSD, and set effective_cache_size properly. Both free.
  • A PARALLEL UNSAFE function silently disables parallel plans.
  • Check bloat and statistics before blaming the query.

Common mistakes

  • Reading actual rows without loops and misjudging which node is expensive.
  • Running EXPLAIN ANALYZE on an UPDATE outside a transaction.
  • Treating cost units as milliseconds.
  • Assuming a Seq Scan is always wrong.
  • Raising work_mem globally to fix one report, then running out of memory.
  • Leaving random_page_cost at 4.0 on SSDs and wondering why indexes are ignored.
  • Leaving effective_cache_size at the default on a large machine.
  • Not enabling pg_stat_statements, so there's no baseline.
  • Ordering by mean time and missing the frequent cheap query.
  • Tuning a query on a bloated table.
  • Adding an unsafe function and losing parallelism silently.

Interview questions

Intermediate

Walk me through reading an EXPLAIN ANALYZE output. 🔥 Must know
How I'd answer

"I'd run it as EXPLAIN (ANALYZE, BUFFERS) — buffers matters because it tells me whether the pages came from cache or disk, which decides whether this is an I/O problem or a CPU one."

"First thing to be careful about: ANALYZE actually executes the statement. Unlike SQL Server's estimated plan, this runs it — including writes. So for an UPDATE I'd wrap it in BEGIN ... ROLLBACK."

"Then I read it inside out — the most indented nodes execute first, and results flow upward."

"The number I look at first is estimated rows= versus actual rows at each node. That single comparison explains most bad plans, because the planner chose the join strategy and the memory allocation from those estimates. If it expected 100 rows and got 2 million, it picked a nested loop where it needed a hash join, and sized the sort memory for 100 rows."

"The trap I'd flag explicitly: actual rows is per loop, not the total. So actual rows=1 loops=50000 is 50,000 rows, and actual time=0.002 with 50,000 loops is 100ms, not 0.002ms. That's the single most common way people misread a Postgres plan — an inner node looks free until you multiply."

"Next I look for spills. Sort Method: external merge Disk: 84MB means the sort exceeded work_mem and went to disk; Batches: 8 on a hash join means the same. That's often a 10 to 100 times difference on that node, and it's the most actionable thing in the output."

"Then buffers: shared hit is cache, shared read is disk. A node with heavy reads points at either a missing index, insufficient memory, or a bloated table making every scan read more pages than it should."

"One thing I don't do is treat the cost= numbers as time. They're arbitrary units, only meaningful for comparing candidate plans — and they're derived from the same estimates that may be wrong."

"For anything non-trivial I'd paste it into a visualiser like explain.dalibo.com. It does the loop multiplication, highlights where estimates diverged, and shows which node actually consumed the time. Nobody reads a large plan by eye reliably."

What they're really checking
  • Do you know ANALYZE executes the query?
  • Do you look at estimated vs actual rows first?
  • Do you know about loops? This is the discriminating detail.
  • Do you look for spills and buffer reads?
Likely follow-ups
  • What's a bitmap heap scan and when is it chosen?
  • What would you do about a spilling sort?
  • Why might estimates be wrong?

Advanced / scenario

The planner keeps choosing a sequential scan even though a suitable index exists. Why? ⭐ Senior-level
How I'd answer

"I'd work through this roughly in order of how often it's the answer, and the first one is a Postgres-specific configuration issue people miss."

"One — random_page_cost is still at its default of 4.0. That encodes the assumption that a random read costs four times a sequential one, which was true for spinning disks and is wrong for SSDs and cloud storage, where it's closer to 1.1. Leaving it at 4.0 makes the planner systematically overvalue sequential scans and undervalue index scans. So it's not making a bad decision — it's making a rational decision from wrong inputs, and adding more indexes won't help. Same for effective_cache_size: left at the 4 GB default on a 64 GB machine, index scans look far more expensive than they are. Both are free to fix."

"Two — the planner is right. If the query returns a large fraction of the table, a sequential scan genuinely is cheaper than an index scan plus a heap fetch per row. That's not a bug. I'd check the actual row count before assuming otherwise — this is also why a bitmap heap scan often appears in the middle ground, and that's a healthy choice rather than a problem."

"Three — bad row estimates. If it thinks the predicate matches most of the table it picks a scan. I'd compare estimated with actual rows. Common causes: stale statistics after a bulk load, or correlated columns — the planner assumes independence, so city = 'Ahmedabad' AND state = 'Gujarat' gets estimated as the product of two selectivities when every Ahmedabad row is already Gujarat. That can be out by thirty times. CREATE STATISTICS ... (dependencies, ndistinct) fixes it."

"Four — the index can't serve this predicate. A plain B-tree can't support LIKE 'abc%' unless the database is in the C locale, because sort order doesn't match byte-prefix order in other collations. You need a text_pattern_ops index. That one catches people who add an index for a prefix search and see no change at all."

"Five — a type mismatch. Comparing a bigint column to a numeric parameter, or a text column to a differently-collated value, can prevent index use. Same family of problem as implicit conversion on SQL Server."

"Six — the expression doesn't match. If the index is on lower(email) the query must use lower(email) = ..., exactly. And a function wrapping a column with no matching expression index means no index scan at all."

"Seven — table bloat. If the table is four times larger than it needs to be, the planner's cost model reflects that size and a scan looks even worse than it should. But the real fix there is vacuum, not the query."

"How I'd actually test it: SET enable_seqscan = off for the session and re-run EXPLAIN ANALYZE. If the index plan is genuinely faster, the cost model is mis-calibrated — which points at settings or statistics. If it's slower, the planner was right all along. That's a diagnostic switch, not a fix; I'd never leave it set."

What they're really checking
  • Do you know about random_page_cost and SSDs? That's the Postgres-specific answer.
  • Do you accept the planner is sometimes right?
  • Do you know the collation issue with prefix LIKE?
  • Do you know the enable_seqscan diagnostic trick, and that it's not a fix?
Weak answers
  • Red flag: "add a hint" — Postgres deliberately has no query hints.
  • Red flag: leaving enable_seqscan = off in production.
  • Red flag: no mention of checking estimates.
Likely follow-ups
  • Why does PostgreSQL not have query hints?
  • What does CREATE STATISTICS actually store?
  • How would you find out if a table is bloated?
