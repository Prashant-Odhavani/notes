Onboarding, Billing & Migration

The tenant lifecycle. Provisioning gets built early and badly; offboarding gets built when a lawyer asks.

🟡 Intermediate 🔴 Advanced ⭐ Senior-level
Quick revision
  • Provisioning must be automated and idempotent — it's a distributed workflow that partially fails.
  • Meter usage from day one, even before you bill for it.
  • Never compute a bill from application state — bill from an immutable usage ledger.
  • Entitlements are per tenant; feature flags are per rollout. Different mechanisms.
  • Tenant migration needs dual-write or a read-only window.
  • GDPR erasure includes backups, which is the hard part.
  • Export before delete — offboarding customers are entitled to their data.

Provisioning a tenant 🔥 Must know

Why this is harder than it looks

Creating a tenant isn't one insert. It's a multi-step workflow across several systems — catalogue, database, identity provider, billing, storage — any of which can fail partway.

Which makes it a saga, and it needs to be treated as one rather than as a controller action.

  1. Reserve the tenant slug            <- unique constraint; must not race
  2. Create the catalogue record        <- status: Provisioning
  3. Provision the data store           <- new DB, or a row in the shared one
  4. Run schema migrations             <- can fail, must be resumable
  5. Seed reference and default data
  6. Create the identity tenant / app registration
  7. Create the billing customer        <- external system, may already exist
  8. Provision blob container / storage
  9. Send the invitation to the admin user
 10. Mark the catalogue record Active   <- the ONLY step that makes it usable

  Fail at step 7 and you have a database, an identity tenant and no billing.
  Retrying naively creates a second database.
Provisioning must be idempotent, and the state must be explicit

This is the failure people hit in the first month of real onboarding: a step fails, someone retries, and now there are two databases, two billing customers, or an identity tenant nobody records.

Two requirements. Each step must be safe to re-run — check whether the resource already exists before creating it, and use deterministic names derived from the tenant id rather than random ones, so a retry finds the previous attempt instead of making another.

And the tenant's status must be explicit and persisted — Provisioning, Active, Suspended, Deleting — with the last completed step recorded, so a resumed run continues rather than restarting.

Critically, the tenant must not be usable until the final step. A half-provisioned tenant that can log in but has no billing record or no seeded data produces confusing support tickets and, worse, real usage you can't invoice.

And there needs to be a cleanup path for provisioning that fails permanently, or you accumulate orphaned databases and identity registrations that nobody can attribute.

public async Task<Result> ProvisionAsync(ProvisionRequest req, CancellationToken ct)
{
    // Deterministic id, so a retry addresses the same tenant
    var tenantId = DeterministicGuid.From(req.Slug);

    var tenant = await _catalogue.FindAsync(tenantId, ct)
                 ?? await _catalogue.CreateAsync(tenantId, req, ct);

    if (tenant.Status == TenantStatus.Active) return Result.Ok();   // already done

    // Each step checks-then-creates and records progress, so this resumes
    await RunStepAsync(tenant, ProvisionStep.DataStore,
        () => _stores.EnsureCreatedAsync(tenant, ct), ct);

    await RunStepAsync(tenant, ProvisionStep.Migrations,
        () => _migrator.MigrateAsync(tenant, ct), ct);

    await RunStepAsync(tenant, ProvisionStep.Identity,
        () => _identity.EnsureTenantAsync(tenant, ct), ct);

    await RunStepAsync(tenant, ProvisionStep.Billing,
        () => _billing.EnsureCustomerAsync(tenant, ct), ct);

    // Only now is it usable
    await _catalogue.SetStatusAsync(tenant.Id, TenantStatus.Active, ct);
    return Result.Ok();
}
Deterministic ids make retries safe

Generating the tenant id from a hash of the slug — rather than Guid.NewGuid() — means a retried provisioning request addresses the same tenant. So the catalogue lookup finds the previous attempt and resumes.

Same technique for downstream resource names: a database called t_{tenantId} and a billing customer with the tenant id as its idempotency key. Then "create if not exists" is genuinely achievable across all of them.

With random ids, a retry has no way to discover what the previous attempt created — so you either leak resources or build a reconciliation process to find them. Determinism is much cheaper.

Senior signal — bill from an immutable ledger, never from application state

The tempting implementation is to count from live data: SELECT COUNT(*) FROM Documents WHERE TenantId = @t at month end.

That breaks in ways that matter commercially. Deletions change history — a tenant who created 10,000 documents and deleted 9,000 gets billed for 1,000, which is wrong under a consumption model. You cannot reproduce a past invoice, so a billing dispute is unanswerable. Retroactive changes silently alter old bills. And a schema change can break historical billing.

The correct shape is an append-only usage ledger: a row per billable event with the tenant, the meter, the quantity and the timestamp. Never updated, never deleted. Invoices are computed by summing a period, and the computed invoice is itself stored — so it's reproducible even if the ledger is later reinterpreted.

That also makes the whole thing auditable, which matters the first time a customer disputes a charge — you can show them exactly what was counted and when.

"Meter into an immutable ledger and store the computed invoice" is the answer that shows you've dealt with billing rather than reasoned about it.

public sealed record UsageRecord(
    Guid TenantId,
    string Meter,              // "api.requests", "storage.gb", "documents.created"
    decimal Quantity,
    DateTime OccurredUtc,
    string IdempotencyKey);    // so a retry doesn't double-count

// Written asynchronously - metering must never fail the user's request
await _usage.RecordAsync(new UsageRecord(
    tenant.TenantId, "documents.created", 1, DateTime.UtcNow,
    IdempotencyKey: $"doc:{document.Id}"), ct);
Three metering details that cause real problems

Metering must not fail the operation. If writing the usage record throws, the user's document creation should still succeed. So it goes through a queue or an outbox — but then it's at-least-once, which is why the idempotency key matters: without it a retry double-counts and you overbill.

Define "active user" precisely and in writing. Logged in this month? Performed any action? Merely provisioned? Each gives a different invoice, and the ambiguity surfaces as a dispute. Seat-based billing looks simple and this is where it isn't.

Meter before you bill. Instrument usage from launch even on a flat-fee plan. When you later introduce consumption pricing you'll have historical data to set the tiers sensibly — otherwise you're guessing, and you'll discover your limits are wrong after announcing them.

Entitlements and feature flags 🔥 Must know

EntitlementFeature flag
Answers"Has this tenant paid for it?""Is this code enabled yet?"

LifetimePermanentTemporary — removed after rollout

Changing itAn upgrade or a contract changeA config toggle
Senior signal — conflating these is a mess that's hard to unwind

Using one flag system for both means you can never delete a flag, because some flags are permanent entitlements and some are temporary rollout switches, and after a year nobody knows which is which.

So the codebase accumulates hundreds of flags, each doubling the paths through the code, and removing any of them risks disabling something a customer pays for.

Keep them separate. Entitlements live on the tenant record, derived from the plan, and are checked as tenant.Plan.Includes(Feature.AdvancedReporting) — permanent, commercially owned, and auditable. Feature flags live in a flag system with an owner and a removal date, and are deleted once the rollout completes.

They compose legitimately: a new feature ships behind a flag for rollout, and once fully rolled out the flag is removed and the entitlement check remains. Being explicit about that distinction is a good architectural signal, because most teams discover it too late.

// Permanent, commercial
if (!_tenant.Plan.Includes(Feature.ApiAccess))
    return Results.Forbid();   // or 402 Payment Required, with an upgrade link

// Quantitative entitlements need enforcing at the write, atomically
var used = await _seats.CountActiveAsync(_tenant.TenantId, ct);
if (used >= _tenant.Plan.SeatLimit)
    return Results.Problem("Seat limit reached for your plan.", statusCode: 402);

// Temporary, engineering - removed after rollout
if (await _flags.IsEnabledAsync("new-pricing-engine", _tenant.TenantId))
    return await _newEngine.PriceAsync(order, ct);
Enforce quantitative limits atomically

A check-then-insert on a seat limit has a race: two concurrent invitations both read 9 of 10 seats used, both proceed, and the tenant now has 11 seats on a 10-seat plan.

That's the lost update problem, and the fix is the same: an atomic conditional insert, or a unique constraint on a seat-slot table, rather than reading a count and then acting on it.

It matters commercially, not just technically — a tenant discovering they can exceed their limit will keep doing it, and reclaiming those seats later is an awkward customer conversation.

Migrating a tenant ⭐ Senior-level

When you need this

Moving a tenant from the pooled shared schema to their own database — because they've grown, signed an enterprise contract, or become a noisy neighbour.

Also moving between regions for data residency, or between pods for capacity.

ApproachDowntimeComplexity
Read-only window Minutes of read-only Low. Usually the right answer
Full maintenance window Minutes to hours offline Lowest, and least acceptable
Dual-write None High — two stores, reconciliation, cutover logic
Change-feed replication Seconds Moderate — if you already have CDC or an outbox
  1. Provision the target and migrate its schema to the same version.
  2. Copy the bulk of the data while the tenant continues working normally.
  3. Put the tenant into read-only mode — a status on the catalogue record that the application enforces.
  4. Copy the delta since the bulk copy.
  5. Verify — row counts per table, checksums on key tables, a few spot-checked records.
  6. Update the catalogue to point at the new store and clear read-only.
  7. Keep the old data for a defined period before deleting it.
Senior signal — a read-only window is usually the right trade

Dual-write gives zero downtime and costs a great deal: writing to two stores, handling partial failures between them, reconciling divergence, and a cutover that has to be atomic. It's a genuinely difficult distributed-systems problem for a one-off operation.

A read-only window of a few minutes is usually acceptable to a B2B customer if it's scheduled and communicated — and it removes the entire class of consistency problems, because nothing changes while you copy the delta.

"Your account will be read-only for ten minutes at 2am on Sunday" is an easy conversation. Rebuilding a tenant's data after a botched dual-write is not.

The details that make it work: read-only must be enforced by the application from the catalogue status, not by hoping nobody writes. Verify before cutover, with row counts and checksums rather than a visual check. And keep the old data for a week or two — because the rollback path is repointing the catalogue back, and that only works if the source still exists.

GDPR erasure and backups — the genuinely hard part

A right-to-erasure request means removing personal data from everywhere, including backups. And you cannot selectively delete one tenant's rows from a backup of a shared database without restoring, modifying and re-taking it — which is impractical and would break every other tenant's restore point.

The accepted position is to document it honestly: personal data is deleted from live systems immediately, and expires from backups within the stated retention period, which is defined and short — typically 30 or 35 days. Regulators have generally accepted that where the retention period is documented, bounded, and backups are not used for anything except recovery.

What you must be able to state: where the data lives (every table, blob container, search index, log store, analytics warehouse and third-party system), how long backups retain it, and that backups are not queried operationally.

The parts most often missed are logs, the analytics warehouse and third-party processors — the customer support tool, the email provider, the error tracker. A GDPR request covers those too, and "we deleted it from the database" is an incomplete answer.

Database-per-tenant makes this dramatically easier: drop the database, and their backups are their own and expire independently. That's a real argument for the model that rarely appears in the cost comparison.

Export before delete, and make it self-service

A departing customer is usually contractually entitled to their data, and GDPR gives a right to portability regardless. So export is a feature, not a favour.

Build it self-service — a request that produces a downloadable archive of their data in a documented format (JSON or CSV plus any files). Doing it manually per customer is expensive, error-prone, and slow at exactly the moment goodwill matters.

It also has value beyond offboarding: enterprise procurement asks about data portability, and being able to demonstrate it removes an objection during the sale.

Sequence it correctly: export, confirm they have it, then delete. Deleting first and then receiving an export request is not recoverable.

Key takeaways
  • Provisioning is a saga across several systems — make it idempotent and resumable.
  • Deterministic ids and resource names make retries safe.
  • A tenant must not be usable until the final provisioning step completes.
  • Have a cleanup path for permanently failed provisioning.
  • Bill from an append-only usage ledger, and store the computed invoice.
  • Metering must not fail the user's operation, so it needs an idempotency key.
  • Define "active user" precisely; meter from launch even on flat pricing.
  • Entitlements are permanent and commercial; feature flags are temporary and engineering-owned.
  • Enforce quantitative limits atomically, not check-then-insert.
  • A short read-only window beats dual-write for tenant migration.
  • Verify with row counts and checksums, and keep the source data for rollback.
  • GDPR erasure covers logs, analytics and third parties — and backups need a documented policy.
  • Export before delete, self-service.

Common mistakes

  • Manual provisioning, so onboarding doesn't scale and is inconsistent.
  • Non-idempotent provisioning, so a retry creates duplicate resources.
  • A tenant usable mid-provisioning, generating unbillable usage.
  • Orphaned resources from failed provisioning with no cleanup.
  • Computing bills from live application state.
  • No idempotency key on usage records, so retries overbill.
  • Metering that can fail the user's request.
  • No agreed definition of "active user", producing billing disputes.
  • Entitlements and feature flags in one system, so flags can never be removed.
  • Check-then-insert on seat limits.
  • Dual-write for a one-off tenant migration.
  • No verification before cutover, or source data deleted immediately.
  • No answer for backups in a GDPR erasure request.
  • Forgetting logs, analytics and third parties when deleting tenant data.
  • No export capability until a customer leaves.

Interview questions

Advanced / scenario

A customer invokes their right to erasure. Walk me through what happens. 🔥 Must know
How I'd answer

"The first thing I'd need is a documented inventory of everywhere their data lives, because 'delete it from the database' is an incomplete answer and the gaps are where the compliance failure is."

"That inventory covers: every table in the operational database, blob or file storage, the search index, the cache, logs, the analytics warehouse, and third-party processors — the support tool, the email provider, the error tracker, the payment provider. Those last three categories are the ones teams miss, and a GDPR request covers them all."

"The sequence I'd follow: export first, because they're usually contractually entitled to their data and GDPR gives a portability right regardless — and deleting before exporting isn't recoverable. Then confirm they have it. Then delete."

"Then soft delete with a grace period, because erasure requests are occasionally mistaken or disputed, and a reversible window of a defined length is prudent. Then hard delete from all live systems."

"The hard part is backups, and I'd be honest about it rather than claim it's solved. You cannot selectively remove one tenant's rows from a backup of a shared database — that would require restoring it, modifying it and re-taking it, which is impractical and would invalidate every other tenant's restore point."

"So the accepted position is to document it: personal data is deleted from live systems immediately and expires from backups within a stated retention period — typically 30 or 35 days. Regulators have generally accepted that where the period is defined, bounded, and backups aren't used for anything except recovery. What you cannot do is have indefinite backup retention and claim compliance."

"There's a related exception worth mentioning: some data you're legally required to retain — invoices and transaction records for tax purposes, typically six or seven years. Erasure doesn't override that. So the honest answer is that personal data is deleted while legally-mandated financial records are retained in a minimised form, and that distinction needs to be in the privacy policy rather than improvised when asked."

"The architectural observation I'd make: database-per-tenant makes this dramatically easier. You drop the database, and their backups are their own and expire independently — so there's no shared-backup problem at all. That's a genuine argument for the model that rarely appears in the cost comparison, and it's one enterprise procurement teams specifically ask about."

"Practically, I'd want this automated and tested rather than a runbook someone follows under pressure. A deletion workflow that enumerates every store, with a verification step confirming the data is gone, and an audit record of what was deleted and when — because you may need to demonstrate compliance later, and 'we're fairly sure we deleted it' isn't evidence."

"And I'd flag the immutable usage ledger as something to think about, since I'd have argued for billing from an append-only ledger. Those records need either anonymising — replacing the tenant identifier while keeping the aggregate for financial reporting — or falling under the legal-retention exception. Append-only and right-to-erasure are in genuine tension, and it's better to have decided that in advance."

What they're really checking
  • Do you know the data inventory extends beyond the database?
  • Do you export before deleting?
  • Are you honest about the backup problem, with a documented policy?
  • Do you know legal retention can override erasure?
  • Do you connect it to the isolation model?
  • Do you spot the tension with an immutable ledger?
Weak answers
  • Red flag: "delete their rows" with no mention of backups, logs or third parties.
  • Red flag: claiming backups can be selectively edited.
  • Red flag: no export step.
Likely follow-ups
  • How do you handle the usage ledger?
  • How would you prove deletion happened?
  • What if a third-party processor can't delete on request?
How would you move a large tenant from the shared database to its own, with minimal disruption? ⭐ Senior-level
How I'd answer

"I'd use a short read-only window rather than dual-write, and I'd justify that choice explicitly because zero-downtime sounds better and usually isn't worth it here."

"Dual-write means writing to both stores during the transition, handling the case where one write succeeds and the other fails, reconciling divergence, and making the cutover atomic. That's a genuinely hard distributed-systems problem to build and test — for a one-off operation."

"A read-only window of a few minutes, scheduled and communicated, removes that entire class of problem because nothing changes while I copy the delta. 'Your account will be read-only for ten minutes at 2am Sunday' is an easy conversation with a B2B customer. Recovering a tenant's data after a botched dual-write is not."

"The sequence:"

"Provision the target and migrate its schema to exactly the same version as the source — a version mismatch here is a subtle way to corrupt the copy."

"Bulk copy while they work normally. This is the bit that takes time, and it happens with no impact. I'd copy in foreign-key order so referential integrity holds at every point."

"Enter read-only mode, enforced by the application from a status on the catalogue record — not by hoping nobody writes. That flag needs to be checked in one place that all writes pass through, which is another argument for having a tenant context service rather than ambient state."

"Copy the delta since the bulk copy. Small, so this is quick."

"Verify — row counts per table, checksums on the important ones, and spot-check a few records including recently-modified ones. Not a visual check; an automated comparison that fails loudly."

"Flip the catalogue to point at the new store and clear read-only. Because connection resolution is at runtime from the catalogue, that's a config change rather than a deployment — which is exactly why runtime resolution matters architecturally."

"Keep the source data for a week or two. The rollback path is repointing the catalogue back, and that only works while the source still exists. Deleting immediately removes your escape route."

"Things I'd get right that are easy to miss. Background jobs and queued messages for that tenant — in-flight work will target the old store, so I'd drain the queue before the window or ensure consumers resolve the connection per message rather than caching it. Caches need invalidating for that tenant, or you'll serve stale data from the old store's cached results. Their blob storage may need moving too, and that's often larger than the database. And a rehearsal against a copy first, because the first attempt reveals the ordering problems."

"If a read-only window genuinely isn't acceptable — a global tenant with no quiet period — change-feed replication is the middle option: replicate continuously from the source using CDC or an outbox until the target is caught up, then a seconds-long cutover. That's much less work than dual-write if the change-capture mechanism already exists, and considerably more if it doesn't."

What they're really checking
  • Do you choose read-only over dual-write, with reasoning?
  • Do you verify with counts and checksums before cutover?
  • Do you keep the source for rollback?
  • Do you consider background jobs, caches and blob storage?
  • Do you rehearse it?
Weak answers
  • Red flag: dual-write chosen reflexively for zero downtime.
  • Red flag: no verification step.
  • Red flag: deleting the source immediately.
Likely follow-ups
  • How do you enforce read-only reliably?
  • What if the copy takes longer than the window?
  • How would you handle in-flight background jobs?
