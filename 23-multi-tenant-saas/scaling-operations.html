Scaling & Noisy Neighbours

In a shared system, one tenant's behaviour is everyone else's performance problem. The defences are mostly about limits and visibility.

🔴 Advanced ⭐ Senior-level 🔥 Must know

The noisy neighbour problem 🔥 Must know

In simple terms

One tenant does something heavy — a bulk import, an unbounded report, a runaway integration — and every other tenant's response times degrade.

They did nothing wrong and they're the ones complaining. That asymmetry is what makes this the defining operational problem of shared multi-tenancy.

Shared resourceHow one tenant monopolises it
Database CPU and I/OAn expensive query, or a missing index on their data volume
Connection poolLong-running transactions holding connections
Application threadsSlow synchronous work occupying request threads
Background job queueA bulk import enqueuing 100,000 jobs
Cache memoryLarge working set evicting everyone else's entries
Rate-limited third partiesConsuming a shared external API quota
LocksContention on shared tables or sequences
The queue is the one people forget

API rate limiting gets attention. Background job queues rarely do, and they're where fairness breaks worst.

One tenant starts a bulk import that enqueues 100,000 jobs. A shared FIFO queue processes them in order — so every other tenant's job sits behind that backlog. A different tenant's password-reset email is now hours late, and nothing is technically broken.

A single rate limit doesn't help, because the work was legitimately submitted and legitimately queued.

The fixes are structural: a queue per tenant with round-robin consumption, or priority queues separating interactive work from bulk, or concurrency limits per tenant so one tenant can only ever occupy N workers.

Separating interactive from bulk is usually the cheapest effective step — a password reset and a 100,000-row import should never share a queue, regardless of tenancy.

// ASP.NET Core's built-in limiter is PER INSTANCE, so with 5 replicas a
// 100/min limit becomes 500/min. For a genuine global limit, back it with Redis.
builder.Services.AddRateLimiter(options =>
{
    options.AddPolicy("per-tenant", httpContext =>
    {
        var tenant = httpContext.RequestServices
            .GetRequiredService<ITenantContext>();

        // Partition by tenant, and read the limit from their plan
        return RateLimitPartition.GetTokenBucketLimiter(
            partitionKey: tenant.TenantId,
            factory: _ => new TokenBucketRateLimiterOptions
            {
                TokenLimit = tenant.Plan.BurstLimit,
                TokensPerPeriod = tenant.Plan.RequestsPerMinute,
                ReplenishmentPeriod = TimeSpan.FromMinutes(1),
                QueueLimit = 0                       // reject rather than queue
            });
    });

    options.OnRejected = async (ctx, ct) =>
    {
        ctx.HttpContext.Response.StatusCode = StatusCodes.Status429TooManyRequests;
        ctx.HttpContext.Response.Headers.RetryAfter = "60";
        await ctx.HttpContext.Response.WriteAsJsonAsync(new
        {
            error = "Rate limit exceeded for your plan.",
            limit = ctx.HttpContext.RequestServices
                .GetRequiredService<ITenantContext>().Plan.RequestsPerMinute
        }, ct);
    };
});
Senior signal — token bucket, and limits tied to the plan

Two choices in that code worth defending.

A token bucket rather than a fixed window. A fixed window allows 2N requests across a boundary — 100 at 10:00:59 and 100 at 10:01:00 — which is exactly the burst you were protecting against. A token bucket refills steadily and permits a bounded burst, which matches how integrations actually behave: idle for a while, then a batch.

Limits read from the tenant's plan, not hardcoded. That makes the limit a product feature — enterprise plans get higher limits, and support can raise one temporarily without a deploy. If limits are constants, every exception becomes a code change.

And the .NET-specific point: ASP.NET Core's built-in limiter is per-instance and in-memory. With five replicas a 100/minute limit is effectively 500/minute. For a genuine global limit you need shared state — a Redis-backed limiter, as on the Redis page. That's the distinction interviewers are checking when they ask you to implement rate limiting rather than configure it.

Decide what happens when the limiter is unavailable

If the limit is enforced through Redis and Redis is down, do you fail open (allow everything) or fail closed (reject everything)?

Failing closed means a cache outage becomes a total outage — almost always worse than being briefly un-throttled. So fail open, log loudly, and optionally fall back to the per-instance limiter as a rough backstop.

That's a decision to make deliberately in design, not to discover during an incident when every tenant is getting 429s because the rate limiter can't reach its store.

Database-level isolation 🔴 Advanced

ModelMechanism available
Database per tenant, elastic poolPer-database min and max — the strongest and simplest control
Shared schema, Azure SQLQuery Store to identify the offender; Resource Governor only on-premises
Shared schema, application-enforcedCommand timeouts, mandatory paging, result caps
Cosmos DBThroughput per container, or hierarchical partition keys with per-tenant monitoring
Read replicasRoute heavy tenant reporting to a replica
In a shared schema, the application is your only governor

Azure SQL has no per-tenant resource governance within one database — Resource Governor is an on-premises feature. So in a shared schema, all enforcement has to happen in the application.

Which means: command timeouts so no single query can run for minutes; mandatory paging with a maximum page size, so no endpoint can return an unbounded result set; result-count caps that fail loudly rather than silently truncating; and rejecting queries with no tenant-selective filter, since those are both a leak risk and a full-table scan.

That last one connects to the unbounded query surface problem: an endpoint accepting arbitrary filters and date ranges is a denial-of-service vector against your own shared database, and in a multi-tenant system the victim is other customers.

If per-tenant resource limits are genuinely required, that's an argument for moving that tenant to its own database in an elastic pool — where the platform enforces it.

Per-tenant observability 🔥 Must know

The rule

Every metric, log line and trace needs a tenant dimension.

Without it you cannot answer the first question of any incident — is this one tenant or everyone? — and you cannot identify which tenant is causing a load problem.

Aggregate p99 latency across all tenants hides the case where one tenant is experiencing 10 seconds and everyone else is fine.

SignalWhy per-tenant
Request rate and latencyIdentify the noisy tenant and the affected ones
Error rateAn error spike for one tenant is usually their data or config
Database time consumedThe strongest signal of a noisy neighbour
Throttled requestsA tenant hitting limits is a support conversation, or an upsell
Storage and row countsGrowth planning and plan enforcement
Background job queue depthFairness, and a stuck tenant
Feature usageProduct decisions, and billing
Cardinality — the practical constraint

Adding a tenant dimension to every metric multiplies your time series by the tenant count. With ten thousand tenants and fifty metrics that's five hundred thousand series, which is expensive in most metrics backends and can be slow to query.

The pragmatic shape: tenant id on logs and traces always, since those are queried selectively rather than aggregated. For metrics, either restrict the tenant dimension to a small set of important counters, or emit per-tenant detail only for the top N tenants by volume and bucket the rest.

Trace baggage is the efficient mechanism for the tenant id, because it propagates across services and through message headers automatically — so a downstream service and an async consumer both have it without you passing it explicitly.

Cost per tenant ⭐ Senior-level

Why it matters commercially

Without per-tenant cost you cannot tell whether a customer is profitable, price a plan sensibly, or justify moving a tenant to dedicated infrastructure.

And in a shared model it's genuinely hard, because the bill arrives as one number for the whole platform.

CostAttribution approach
Dedicated resourcesDirect — tag the resource with the tenant
Shared computeApportion by request count or measured request duration
Shared databaseApportion by query time consumed, or by row and storage share
StorageMeasure per tenant directly — usually straightforward
EgressSum response bytes per tenant
Third-party APIsCount calls per tenant at the point of use
Senior signal — measure request duration, not request count

Apportioning shared compute by request count is easy and misleading. A tenant making 100,000 trivial requests and one making 1,000 heavy reports may cost the same, or the reverse.

Request duration, or better, database time consumed, tracks actual resource use. The practical version is to record elapsed time and the database time per request tagged by tenant, then apportion the shared bill by each tenant's share of the total.

That's approximate and it's defensible — good enough to identify the tenant consuming 40% of your database while paying 2% of your revenue, which is the finding that actually changes decisions.

The commercial consequence worth naming: this is how you discover that your cheapest plan is loss-making, and it's the data that justifies either a price change, a usage limit, or moving that customer to dedicated infrastructure where their cost is visible.

Teams that never measure this find out when the cloud bill outgrows revenue growth and nobody can explain why.

"Restore just our data" is the request that exposes the model

A customer runs a bad import and asks you to roll back to yesterday. In a shared schema you cannot restore the database — that would revert every other tenant.

So the procedure is: restore a copy of the database to the point in time, then selectively copy that tenant's rows back across every affected table, in foreign-key order, while the live system continues taking writes for them.

That's bespoke, error-prone work under time pressure, and it's slow. Write and test the runbook before you need it — including which tables are tenant-owned and what order they must be restored in.

The alternative that avoids most of this is soft deletes plus an audit trail for destructive operations, so "undo this import" becomes a supported feature rather than a database recovery exercise. That's worth building deliberately in a shared model, because it converts a recovery problem into a product one.

Tiered SLAs need mechanisms, not just contract wording

Selling an enterprise tier with a stronger uptime or RPO commitment means you must actually be able to deliver it differently.

In a fully shared model you can't: everyone shares the same database, the same backup schedule and the same failure domain. So a 99.9% tier and a 99.99% tier are the same system with different paperwork — and when an outage happens, both are breached identically.

Delivering genuinely tiered availability requires different infrastructure — a dedicated database with zone redundancy, geo-replication, or a separate pod for premium tenants.

So a tiered SLA is an architecture commitment, not a sales decision. Being the person who points that out before the contract is signed is valuable.

Key takeaways
  • Noisy neighbours are the defining operational problem of shared multi-tenancy.
  • Background job queues are where fairness breaks worst — separate interactive from bulk.
  • Limit at several layers: requests, concurrency, query cost, storage, payload size.
  • Token bucket over fixed window; read limits from the tenant's plan.
  • ASP.NET Core's rate limiter is per-instance — Redis-back it for a global limit.
  • Decide the fail-open behaviour when the limiter's store is unavailable.
  • In a shared schema the application is your only resource governor.
  • Every log and trace needs a tenant dimension; be careful with metric cardinality.
  • Attribute cost by request duration or database time, not request count.
  • Per-tenant restore is very hard in a shared schema — write the runbook in advance.
  • Soft deletes convert a recovery problem into a product feature.
  • Tiered SLAs require tiered infrastructure, not just tiered contracts.

Common mistakes

  • No per-tenant limits, so one tenant can degrade everyone.
  • A shared FIFO job queue, letting one bulk import starve everyone.
  • Rate limiting per instance and assuming it's global.
  • Fixed-window limits where burst protection was the point.
  • Hardcoded limits, so every exception needs a deploy.
  • Failing closed when the rate-limit store is down.
  • Unbounded endpoints with no maximum page size.
  • No tenant dimension on logs, traces or metrics.
  • Per-tenant metrics for every metric, causing a cardinality explosion.
  • Cost attributed by request count.
  • Discovering per-tenant restore is impossible during an incident.
  • Selling a tiered SLA the architecture can't deliver.

Advanced / scenario

One tenant's activity is slowing the system for everyone. What do you do? 🔥 Must know
How I'd answer

"I'd separate the immediate mitigation from the structural fix, because the first thing needed is to stop the harm to other tenants."

"First, identify it — which requires per-tenant telemetry. If every metric, log line and trace carries a tenant dimension, this is a query. If it doesn't, I'm correlating timestamps against customer complaints, which is slow and this is exactly the incident where you find out you needed it."

"The strongest signal is database time consumed per tenant, not request count — a tenant making 100,000 trivial requests may cost far less than one running 1,000 heavy reports. In Azure SQL, Query Store plus the tenant id in the query context, or an application-level measure of elapsed database time tagged by tenant."

"Immediate mitigation, in order of how quickly I can apply it: throttle that tenant specifically, if limits are configurable per tenant rather than hardcoded — which is a good argument for reading limits from their plan record. If it's one runaway query or job, kill it. If it's a bulk operation, move it to a lower-priority queue so it stops competing with interactive work."

"Then I'd want to know what they're actually doing, because it changes the response. Legitimate heavy use means a capacity or plan conversation. A missing index on their data volume means it's my bug, not their behaviour — and a tenant with ten times more data than anyone else frequently exposes a query that was fine for everyone else. A runaway integration in a retry loop means it's probably their bug, and I should be rejecting it with 429s."

"Structurally, the fixes depend on the shared resource."

"Per-tenant rate limits at the API — token bucket rather than fixed window, because a fixed window allows a double burst across the boundary. And Redis-backed, because ASP.NET Core's built-in limiter is per-instance, so with five replicas a 100/minute limit is really 500/minute."

"Concurrency limits as well as rate limits, since a tenant making few but very slow requests can occupy all your threads without exceeding a request-rate limit."

"Queue fairness, which is the one people miss. A shared FIFO queue means one tenant's 100,000-job import puts every other tenant's work behind it — so a password reset is hours late and nothing is technically broken. That needs a per-tenant concurrency allowance, or separate queues for interactive versus bulk work. Separating interactive from bulk is usually the cheapest effective step."

"Bounded endpoints — mandatory paging with a maximum page size, command timeouts, and result caps. In a shared schema the application is the only resource governor available, because Azure SQL has no per-tenant governance within one database."

"And the option I'd raise if this tenant is persistently the problem: move them to their own database in an elastic pool. Then the platform enforces the isolation, their cost becomes visible and attributable, and other tenants are structurally protected rather than protected by limits I have to tune. That's also the commercial conversation — if they're consuming 40% of capacity, that should be reflected in what they pay."

"Which is why runtime connection resolution from a tenant catalogue matters: it makes that move a migration plus a config row rather than a code change."
