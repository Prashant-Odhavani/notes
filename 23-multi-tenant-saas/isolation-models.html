Tenant Isolation Models

The decision that shapes everything else — and the one you should design to be able to change per tenant rather than globally.

🔴 Advanced ⭐ Senior-level 🔥 Must know
Quick revision
  • Shared schema — cheapest, highest leak risk, hardest per-tenant operations.
  • Database per tenant — strongest isolation, trivial per-tenant restore, most expensive.
  • Schema per tenant — a middle ground that inherits problems from both.
  • The hybrid is what mature products run — pooled by default, dedicated on demand.
  • Resolve the connection at runtime from a catalogue, never from configuration.
  • Migrating N databases is the real operational cost of the dedicated models.
  • Every migration must work with both old and new application code.

Shared schema 🔥 Must know

In simple terms

One database, one set of tables, and a TenantId column on every tenant-owned table. Every query filters by it.

StrengthsWeaknesses
Lowest cost per tenant — one database, shared capacityHighest leak risk — one missing predicate
One schema migration for everyonePer-tenant restore is very hard
Scales to very many tenantsNoisy neighbours share indexes, buffer pool and locks
Simple deployment and monitoringPer-tenant deletion is genuinely difficult
Cross-tenant analytics are trivialNo per-tenant data residency or encryption keys
The two problems that bite later, not at launch

Restoring one tenant. A customer asks you to roll back a bad bulk import from Tuesday. With a shared schema you cannot restore the database — that would revert every other tenant too. So you restore a copy to a point in time, then selectively copy that tenant's rows back across every affected table, respecting foreign keys. That's bespoke work under time pressure, and it's the request that most often exposes the model's limits.

Deleting one tenant completely. GDPR erasure means removing their data from every table and from backups. In a shared schema, the backups contain other tenants too, so you cannot simply delete them — you're relying on retention expiry, and you need a documented answer for the gap.

Neither is a reason to avoid a shared schema. Both are reasons to know the answer before a customer asks, because inventing it during an incident is considerably worse.

Database per tenant 🔥 Must know

StrengthsWeaknesses
Isolation is structural — a leak requires connecting to the wrong databaseHighest cost, especially with idle tenants
Per-tenant restore is trivialN schema migrations per release
Per-tenant deletion is a dropN databases to monitor, back up and connect to
Noisy neighbours are containedCross-tenant reporting needs a separate store
Data residency and per-tenant keys are possibleConnection pool fragmentation across many databases
Per-tenant performance tuningProvisioning is now a workflow, not an insert
Elastic pools make the cost argument much weaker

The usual objection is cost: 500 databases sized for their peaks is expensive.

Elastic pools change that — many databases share a pool of capacity, so you pay for aggregate usage rather than per-database peaks. You keep database-per-tenant isolation with pooled economics.

It works because tenant peaks are usually uncorrelated — different time zones and working patterns. If all tenants were busy simultaneously a pool wouldn't help, and that's the thing to verify against metrics rather than assume.

Two details to configure: a per-database maximum so one tenant can't consume the whole pool (the noisy-neighbour control), and a minimum for tenants with contractual performance commitments.

So "database per tenant is too expensive" is a weaker argument than it used to be, and mentioning pools is a good practical signal.

Schema per tenant 🟡 Intermediate

The middle option

One database, one schema per tenant — acme.Orders, globex.Orders. Isolation by schema rather than by column or by database.

It inherits problems from both sides

Better isolation than a shared schema, and it still shares a database — so noisy neighbours remain, since tenants compete for the same buffer pool, CPU and log.

And you get the N-migrations problem of database-per-tenant without the benefits: you still can't restore one tenant independently, because point-in-time restore operates on the whole database.

It also scales worse than people expect. Hundreds of schemas each with dozens of tables produces tens of thousands of objects, which slows metadata operations and makes tooling unhappy.

So it's a legitimate choice in a narrow band — you want stronger-than-column isolation, have a moderate tenant count, and can't justify separate databases. But if you're taking on N migrations anyway, database-per-tenant usually gives more for the same operational cost. That's the argument worth making.

The hybrid model 🔥 Must know

What mature products actually run

Pooled shared schema for the many small tenants. A dedicated database for large, regulated or noisy ones.

The three models are usually presented as a choice. In practice you want both, because the requirements genuinely differ per customer — and forcing one trade-off on everyone means either overpaying for small tenants or under-serving large ones.

  Tenant catalogue (the routing table):

  tenant     model        connection
  ---------- ------------ --------------------------------
  acme       dedicated    Server=eu-1;Database=t_acme       <- enterprise, EU residency
  globex     dedicated    Server=us-1;Database=t_globex     <- high volume, noisy
  small-co   pooled       Server=pool-1;Database=shared_a   <- one of 400
  tiny-ltd   pooled       Server=pool-1;Database=shared_a
  ...

  The application resolves the connection per request from this table.
  Moving a tenant between models is a data migration plus a row update.
public sealed class TenantDbContextFactory(
    ITenantContext tenant,
    ITenantCatalogue catalogue,
    IOptions<DbOptions> options)
{
    public async Task<AppDbContext> CreateAsync(CancellationToken ct)
    {
        // Cached in memory; the catalogue changes rarely
        var placement = await catalogue.GetPlacementAsync(tenant.TenantId, ct);

        var builder = new DbContextOptionsBuilder<AppDbContext>()
            .UseSqlServer(placement.ConnectionString);

        return new AppDbContext(builder.Options, tenant);
    }
}
Senior signal — runtime resolution is the architectural requirement

The hybrid model only works if the application resolves the connection at runtime from a catalogue rather than reading one connection string from configuration.

Once it does, moving a tenant from pooled to dedicated is a data migration plus a catalogue update — no code change, no redeploy. Without it, that move is a code change and a special case, so in practice it never happens and large tenants stay in the pool causing problems.

So this is the decision that determines whether the model is changeable per tenant. It costs little to build up front and is expensive to retrofit, because every data-access path assumes a single configured connection.

Two practical points: cache the catalogue, since it changes rarely and you don't want a lookup per request; and be aware that many distinct connection strings mean fragmented connection pools — each string gets its own pool, so with hundreds of dedicated tenants you can exhaust connections in a way a single pool wouldn't.

Promote a tenant to dedicated when
They contractually require data isolation, residency, or their own encryption keys
Their load measurably degrades pooled neighbours
They need per-tenant restore or retention guarantees
They're large enough that per-tenant cost attribution matters commercially
Compliance requires demonstrable physical separation

The pod model 🔴 Advanced

Scaling beyond one deployment

A pod (or cell, or shard) is a complete, independent copy of the whole stack — app instances, database, cache — serving a subset of tenants.

You scale by adding pods rather than by growing one deployment.

GainsCosts
Blast radius is one pod, not everyoneSignificant operational complexity
Deploy to one pod first — a natural canaryN of everything to monitor and patch
Per-region pods give data residencyTenant-to-pod routing must be reliable
Known capacity per pod, so growth is predictableMoving a tenant between pods is real work
A noisy tenant affects only its podCross-pod reporting needs aggregation
The underrated benefit is deployment safety

Pods give you a genuine canary at the infrastructure level: deploy to one pod holding 5% of tenants, watch it, then roll forward. A bad release affects a known, bounded set of customers rather than everyone.

That's more valuable than the scaling argument for most products, because the scaling ceiling is rarely the real constraint — deployment risk is.

It also caps the blast radius of an outage: a pod failure is a visible incident for those tenants and invisible to the rest, which changes the shape of your SLA conversations.

The honest caveat: this is a lot of machinery. It suits products with many tenants and a platform team. Reaching for it early is over-engineering, and it's the kind that's hard to unwind.

Migrating schemas across many databases ⭐ Senior-level

This is the real operational cost of the dedicated models

One schema change becomes N migrations, each of which can fail independently — so at any moment some tenants are on the new schema and some aren't.

Which means every migration must work with both the old and the new application code. Not as a nice-to-have — as a structural requirement, because you cannot migrate 500 databases atomically.

  1. Make every migration backward compatible. Add nullable columns, add tables, never rename or drop in the same release as the code that stops using them.
  2. Version each database and record it in the catalogue, so you always know the true state.
  3. Migrate a canary set first — internal tenants, then a handful of small ones.
  4. Roll forward in batches, with a bounded concurrency so you don't saturate the server.
  5. Make migrations idempotent and resumable, because some will fail and be retried.
  6. Report progress and failures per tenant — a dashboard, not a log file.
  7. Contract in a later release, once every database is migrated and no code reads the old shape.
Expand and contract, over separate releases

Renaming a column looks like one change and cannot be done in one release when the migration isn't atomic across tenants.

Release 1 (expand): add the new column, write to both, read from the old. Works with old and new code.

Release 2: read from the new column. Both columns still exist.

Release 3 (contract): stop writing the old column, then drop it — only once every database has been migrated and telemetry confirms nothing reads it.

Three releases for a rename feels excessive and is the only safe sequence. Attempting it in one means that during the rollout, new code hits un-migrated databases and old code hits migrated ones — and both break.

Same discipline as API contract versioning, applied to schemas: you cannot change both sides simultaneously.

Failure is normal at scale, so plan for partial state

With 500 databases, a migration run will have failures — a database mid-restore, a lock timeout, one tenant with unexpected data that violates a new constraint.

So the design requirements are: idempotent migrations that can be re-run safely, resumable batches that don't restart from the beginning, per-tenant version tracking so you know exactly who's where, and the application tolerating both schemas for the duration.

The failure mode to avoid is a migration that half-succeeds with no record of which tenants completed — then you're inspecting 500 databases by hand to find out.

EF Core migrations work per-context, so the usual shape is a small orchestrator that enumerates the catalogue and applies migrations tenant by tenant with retry, rather than a single dotnet ef database update.

Choosing 🔥 Must know

If…Then
Thousands of small self-serve tenantsShared schema, pooled
Tens of enterprise tenants with contractsDatabase per tenant
A mix — and most products areHybrid, with runtime resolution
Regulated data, or residency requirementsDatabase per tenant, possibly per region
Per-tenant restore is a stated requirementDatabase per tenant
Very many tenants and a platform teamPods, each internally pooled
You genuinely don't know yetShared schema with tenant id everywhere, designed to allow extraction
Senior signal — start pooled, but design for extraction

If the customer profile is uncertain, a shared schema is the right start: cheapest, one migration, fastest to build.

The critical caveat is to design so a tenant can be extracted later. That means: the tenant id on every tenant-owned table from day one, no cross-tenant foreign keys, connection resolution through a catalogue even while every tenant resolves to the same connection, and no query that assumes all tenants live together.

Those cost almost nothing up front. Without them, extracting your first enterprise customer means a schema change, a data-access rewrite, and a migration — at exactly the moment a large deal depends on it.

"Start pooled, keep extraction cheap" is the answer that shows you've thought about the second year, not just the launch.

Key takeaways
  • Shared schema is cheapest and has the highest leak risk plus the hardest per-tenant operations.
  • Know your answer for per-tenant restore and GDPR deletion before a customer asks.
  • Database per tenant makes isolation structural and restore trivial, at N migrations.
  • Elastic pools substantially weaken the cost objection to dedicated databases.
  • Schema per tenant inherits noisy neighbours and N migrations without per-tenant restore.
  • The hybrid is what mature products run — pooled by default, dedicated on demand.
  • Runtime connection resolution from a catalogue is what makes the hybrid possible.
  • Many connection strings fragment connection pools.
  • Pods bound the blast radius and give a genuine deployment canary.
  • Every migration must work with both old and new code — expand/contract over three releases.
  • Migrations must be idempotent, resumable, and version-tracked per tenant.
  • Start pooled if unsure, but keep extraction cheap.

Common mistakes

  • No tenant id on some tables, blocking extraction later.
  • Cross-tenant foreign keys, making a tenant impossible to separate.
  • One connection string in configuration, so the model can't vary per tenant.
  • Discovering per-tenant restore is impossible when a customer asks.
  • No answer for GDPR deletion in a shared schema.
  • Schema per tenant chosen without realising it keeps noisy neighbours.
  • Renaming a column in one release across many databases.
  • Non-idempotent migrations that can't be retried.
  • No per-tenant schema version tracking.
  • Elastic pools with no per-database cap.
  • Reaching for pods before the tenant count justifies it.
