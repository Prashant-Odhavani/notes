Tenant Context & Security

The most important page in this section. A cross-tenant leak is a breach, and it's always caused by something small.

🔴 Advanced ⭐ Senior-level 🔥 Must know
Quick revision
  • Never trust a client-supplied tenant id. Derive it from a signed token, or validate entitlement.
  • Tenant context is a scoped service — not a static, not a manually-set AsyncLocal.
  • Enforce isolation structurally: query filters, then row-level security underneath.
  • The tenant id must be in every cache key.
  • Background jobs have no request — the tenant must travel in the message.
  • EF Core caches the model per context type, which is a real leak vector.
  • Tenant id in logs and trace baggage, or incidents are unanswerable.

[HttpGet("orders")]
public async Task<IActionResult> Get([FromQuery] Guid tenantId)
{
    // The caller chooses the tenant. Change the parameter, read someone else's data.
    var orders = await _db.Orders.Where(o => o.TenantId == tenantId).ToListAsync();

[HttpGet("orders")]
public async Task<IActionResult> Get()
{
    // Tenant comes from the validated token, not from the request.
    // The query filter applies it automatically - see below.
    var orders = await _db.Orders.ToListAsync();
    return Ok(orders);
}

This looks obviously wrong written out, and it appears in real systems constantly — usually because an internal endpoint took a tenant id for legitimate reasons and later became reachable externally.

The rule: the tenant is an attribute of the authenticated identity, never a request parameter. If an endpoint genuinely needs to act on another tenant — a support tool — that's a separate, explicitly authorised code path with its own audit trail, not the same handler with a parameter.

This is IDOR at the tenant level, and the blast radius is an entire customer's data rather than one record.

public sealed class TenantResolutionMiddleware(RequestDelegate next)
{
    public async Task InvokeAsync(HttpContext ctx, ITenantContextSetter setter,
                                  ITenantStore store)
    {
        // 1. From the validated token - authentication has already run
        var claim = ctx.User.FindFirst("tenant_id")?.Value;
        if (!Guid.TryParse(claim, out var tenantId))
        {
            ctx.Response.StatusCode = StatusCodes.Status401Unauthorized;
            return;
        }

        // 2. Look it up - so a deactivated tenant is rejected here, once
        var tenant = await store.FindAsync(tenantId, ctx.RequestAborted);
        if (tenant is null || !tenant.IsActive)
        {
            ctx.Response.StatusCode = StatusCodes.Status403Forbidden;
            return;
        }

        // 3. If the URL also names a tenant, it MUST match the token
        if (ctx.Request.RouteValues.TryGetValue("tenantSlug", out var slug) &&
            !string.Equals(slug?.ToString(), tenant.Slug, StringComparison.OrdinalIgnoreCase))
        {
            ctx.Response.StatusCode = StatusCodes.Status403Forbidden;
            return;
        }

        setter.Set(tenant);
        ctx.Items["TenantId"] = tenant.Id;              // for logging enrichment
        await next(ctx);
    }
}
Middleware order matters, and getting it wrong fails open

Tenant resolution must run after UseAuthentication() — otherwise ctx.User is unauthenticated and there's no claim to read.

And it must run before anything that touches tenant data, including UseAuthorization() if your policies are tenant-aware.

The dangerous ordering mistake is placing it after the endpoint's own logic or in a filter that some routes skip — because then the tenant context is unset rather than wrong, and depending on how the query filter handles a null tenant, you may get every tenant's data instead of none.

Design the null-tenant case to return nothing, never everything. Failing closed is the whole point.

Holding the context 🔥 Must know

public interface ITenantContext
{
    Guid TenantId { get; }
    string Slug { get; }
    bool IsResolved { get; }
}

// Only the middleware can set it - the rest of the app only reads
public interface ITenantContextSetter { void Set(Tenant tenant); }

internal sealed class TenantContext : ITenantContext, ITenantContextSetter
{
    private Tenant? _tenant;

    public bool IsResolved => _tenant is not null;

    public Guid TenantId => _tenant?.Id
        ?? throw new InvalidOperationException("Tenant not resolved.");   // fail loudly

    public string Slug => _tenant?.Slug
        ?? throw new InvalidOperationException("Tenant not resolved.");

    public void Set(Tenant tenant) =>
        _tenant = _tenant is null
            ? tenant
            : throw new InvalidOperationException("Tenant already set.");  // set once
}

// Registered scoped - one per request
services.AddScoped<TenantContext>();
services.AddScoped<ITenantContext>(sp => sp.GetRequiredService<TenantContext>());
services.AddScoped<ITenantContextSetter>(sp => sp.GetRequiredService<TenantContext>());
Senior signal — three design choices in that code

Throwing when unresolved, rather than returning Guid.Empty. An empty tenant id flowing into a query silently matches nothing — or worse, matches rows where the column is empty. Throwing makes a missing tenant an immediate, obvious failure rather than a quiet data-correctness problem.

Separating the setter interface. Application code can inject ITenantContext and read; only the middleware gets ITenantContextSetter. So no handler can change the tenant mid-request, accidentally or otherwise.

Set-once semantics. A second Set throws, which catches a bug where two middlewares or a filter both try to resolve.

And it must be scoped, never static or singleton. A static field holding the tenant is a cross-request leak under concurrency, and it's the kind that works perfectly under manual testing and fails under load.

Enforcing isolation structurally 🔥 Must know

The principle

If isolation depends on developers remembering to filter, you will have a leak.

Not because developers are careless — because there are thousands of queries, new people join, and one missed predicate is enough.

So isolation must be enforced by a mechanism that applies by default, with a second layer underneath for when the first is bypassed.

Layer 1 — EF Core global query filters

public class AppDbContext(DbContextOptions options, ITenantContext tenant) : DbContext(options)
{
    // A FIELD read per query, not a captured constant - see the trap below
    private Guid TenantId => tenant.TenantId;

    protected override void OnModelCreating(ModelBuilder builder)
    {
        // Apply to every entity implementing ITenantOwned - no per-entity opt-in
        foreach (var entity in builder.Model.GetEntityTypes()
                     .Where(e => typeof(ITenantOwned).IsAssignableFrom(e.ClrType)))
        {
            var param = Expression.Parameter(entity.ClrType, "e");
            var body = Expression.Equal(
                Expression.Property(param, nameof(ITenantOwned.TenantId)),
                Expression.Property(Expression.Constant(this), nameof(TenantId)));

            builder.Entity(entity.ClrType)
                   .HasQueryFilter(Expression.Lambda(body, param));
        }
    }

    // Also stamp the tenant on insert, so it can't be forgotten
    public override Task<int> SaveChangesAsync(CancellationToken ct = default)
    {
        foreach (var e in ChangeTracker.Entries<ITenantOwned>()
                     .Where(e => e.State == EntityState.Added))
        {
            e.Entity.TenantId = TenantId;
        }
        return base.SaveChangesAsync(ct);
    }
}
The EF Core model cache trap — the leak that only appears under load

EF Core caches the compiled model per DbContext type, not per instance. So the query filter expression is compiled once and reused for every context instance.

If the filter captures the tenant id by value at model-build time — for example HasQueryFilter(e => e.TenantId == _tenantId) where _tenantId was read in the constructor — then the first request's tenant id is baked into the cached model and applied to every subsequent request, for every tenant.

That's a cross-tenant leak of the worst kind: it works perfectly in single-tenant testing, appears only under concurrent multi-tenant traffic, and reads other tenants' data silently.

The fix is to reference a property on the context instance, as in the code above — Expression.Property(Expression.Constant(this), nameof(TenantId)) — so EF evaluates it per query rather than capturing a value. If the filter's shape varies per tenant, you also need a custom IModelCacheKeyFactory so each variant gets its own cached model.

This is the highest-value .NET-specific detail in this section, and it's a genuinely subtle bug.

Where query filters don't apply

Global query filters are excellent and not complete. They don't apply to:

  • FindAsync by primary key — it can return another tenant's row if you know the id.
  • Raw SQL — FromSql, ExecuteSql, Dapper.
  • Explicit IgnoreQueryFilters(), which any developer can add.
  • Direct database access — a script, an admin tool, a reporting connection.

FindAsync is the one that surprises people. It checks the change tracker then queries by key, bypassing the filter — so FindAsync(someOtherTenantsOrderId) returns the row. Use a filtered FirstOrDefaultAsync instead, or accept that you need layer 2.

Layer 2 — row-level security in the database

-- The predicate function
CREATE FUNCTION dbo.fn_TenantAccessPredicate(@TenantId uniqueidentifier)
RETURNS TABLE WITH SCHEMABINDING
AS
RETURN SELECT 1 AS ok
WHERE @TenantId = CAST(SESSION_CONTEXT(N'TenantId') AS uniqueidentifier);
GO

-- FILTER blocks reads; BLOCK stops writing rows for another tenant
CREATE SECURITY POLICY dbo.TenantIsolationPolicy
    ADD FILTER PREDICATE dbo.fn_TenantAccessPredicate(TenantId) ON dbo.[Order],
    ADD BLOCK PREDICATE dbo.fn_TenantAccessPredicate(TenantId) ON dbo.[Order] AFTER INSERT
WITH (STATE = ON);
// An EF Core interceptor, so it can't be forgotten per-query
public sealed class TenantSessionInterceptor(ITenantContext tenant) : DbConnectionInterceptor
{
    public override async Task ConnectionOpenedAsync(
        DbConnection connection, ConnectionEndEventData eventData, CancellationToken ct = default)
    {
        if (!tenant.IsResolved) return;

        await using var cmd = connection.CreateCommand();
        cmd.CommandText = "EXEC sp_set_session_context @key=N'TenantId', @value=@tenantId";
        var p = cmd.CreateParameter();
        p.ParameterName = "@tenantId";
        p.Value = tenant.TenantId;
        cmd.Parameters.Add(p);
        await cmd.ExecuteNonQueryAsync(ct);
    }
}
Senior signal — why the second layer is what makes this defensible

Query filters protect the application's own EF queries. Row-level security protects everything — raw SQL, Dapper, a stored procedure, a reporting tool, a developer connected with SSMS, and code that called IgnoreQueryFilters().

So the two layers cover genuinely different failure modes, and that's the definition of defence in depth rather than redundancy.

Two operational requirements. The application's login must not be db_owner or have ALTER ANY SECURITY POLICY, because RLS doesn't apply to those — so an over-privileged connection string silently disables the protection you think you have. And the session context must be set on every connection, which with connection pooling means using an interceptor rather than doing it once at startup, since a pooled connection is reused across requests and tenants.

That pooling detail is the one that catches people: set it once and a recycled connection carries the previous tenant's context.

Being able to explain that layer 2 exists specifically because layer 1 can be bypassed — and naming the privilege and pooling caveats — is the answer that demonstrates you've deployed this rather than read about it.

var key = $"product:{productId}";                    // NO TENANT
var cached = await _cache.GetStringAsync(key);
// Tenant A's product is served to Tenant B. Silent, and cached for the TTL.
public sealed class TenantCache(IDistributedCache cache, ITenantContext tenant)
{
    // The tenant is prepended here; callers cannot omit it
    private string Key(string suffix) => $"t:{tenant.TenantId}:{suffix}";

    public Task<string?> GetAsync(string suffix) => cache.GetStringAsync(Key(suffix));
    public Task SetAsync(string suffix, string value, DistributedCacheEntryOptions o) =>
        cache.SetStringAsync(Key(suffix), value, o);
}
Make the safe path the only path

The pattern in that helper generalises: rather than documenting "remember to include the tenant", remove the ability to omit it.

A TenantCache that no caller can bypass. A repository base class that applies the filter. A blob helper that builds the path. If the unsafe call isn't expressible, it can't be written by a new developer on their second day.

Then add an architecture test that fails the build if anything injects IDistributedCache directly — the same mechanical enforcement as module boundaries. Conventions erode; a failing build doesn't.

Background jobs and messages 🔥 Must know

// Publishing: capture the current tenant into the message
await _bus.Publish(new RecalculatePricing(
    TenantId: _tenant.TenantId,          // explicit, not ambient
    ProductIds: ids), ct);

// Consuming: create a scope and set the tenant BEFORE any data access
public async Task Consume(ConsumeContext<RecalculatePricing> ctx)
{
    await using var scope = _scopeFactory.CreateAsyncScope();

    scope.ServiceProvider.GetRequiredService<ITenantContextSetter>()
         .Set(await _store.GetAsync(ctx.Message.TenantId));

    var handler = scope.ServiceProvider.GetRequiredService<PricingRecalculator>();
    await handler.RunAsync(ctx.Message.ProductIds, ctx.CancellationToken);
}
Background work is where isolation quietly stops applying

All the protection described above hangs off a request. Middleware resolves the tenant, a scoped service holds it, and the query filter reads it.

A background service has none of that. It's a singleton, there's no request, no middleware ran, and the tenant context is unresolved.

So a nightly job that iterates records is operating with no tenant filter at all — and depending on how the unresolved case is handled, it either throws (good) or processes every tenant's data (bad, and it may well write results to the wrong tenant).

Two rules. The tenant id must be an explicit field in every message and job parameter — never inferred, never ambient. And the job must create a scope per tenant and set the context before touching data, so all the normal protections apply inside it.

For a job that genuinely spans tenants — a nightly billing run — the correct shape is to enumerate tenants and process each in its own scope, not to run one unscoped query across all of them.

Tenant in logs and traces 🟡 Intermediate

// Logging: a scope so every log line in the request carries it
using (_logger.BeginScope(new Dictionary<string, object>
{
    ["TenantId"] = tenant.TenantId,
    ["TenantSlug"] = tenant.Slug
}))
{
    await next(ctx);
}

// Tracing: baggage travels across service and message boundaries
Activity.Current?.SetBaggage("tenant.id", tenant.TenantId.ToString());
The first question in every incident is "one tenant or all of them?"

Without the tenant on log lines and traces, that question takes an hour of correlation. With it, it's a filter.

It also lets you answer things you'll be asked routinely: which tenant is generating this load, which tenants were affected by the outage window, is this error specific to one customer's data.

Use baggage rather than a span attribute for the tenant, because baggage propagates across service boundaries and through message headers — so a downstream service and an async consumer both have it without passing it explicitly.

One caution: the tenant identifier is fine to log; tenant data is not. A log line containing another customer's record is itself a leak, and logs are frequently more widely readable than the database.

Key takeaways
  • The tenant is an attribute of the authenticated identity — never a request parameter.
  • Resolve from a signed claim; if the URL also names a tenant, it must match.
  • Tenant context is scoped, set once, read-only, and throws when unresolved.
  • Design the unresolved case to return nothing, never everything.
  • Layer 1: EF Core global query filters applied to every tenant-owned entity.
  • Reference a context property in the filter — a captured value gets baked into the cached model and leaks.
  • Query filters don't cover FindAsync, raw SQL, or IgnoreQueryFilters.
  • Layer 2: row-level security, with a non-db_owner login and session context set per connection.
  • Every cache key needs the tenant. Make the safe path the only path.
  • Background jobs have no request — carry the tenant in the message, scope per tenant.
  • Tenant id in logs and as trace baggage; tenant data in neither.

Common mistakes

  • Tenant id from a query string or body, trusted.
  • Tenant context in a static or singleton, leaking across requests.
  • Returning Guid.Empty when unresolved instead of throwing.
  • A query filter capturing the tenant id by value, baked into the cached model.
  • Relying on query filters alone, with no RLS underneath.
  • An application login with db_owner, silently bypassing RLS.
  • Session context set once rather than per pooled connection.
  • FindAsync for tenant-owned entities.
  • Cache keys without the tenant.
  • Background jobs with no tenant scope.
  • Admin endpoints sharing the normal authorisation policy.
  • Blob paths and search indexes without tenant scoping.
