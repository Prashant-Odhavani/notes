Multi-Tenant SaaS

One system serving many customers who must never see each other's data. The isolation decision shapes everything else, and it's expensive to change.

🔴 Advanced ⭐ Senior-level 🔥 Must know

What multi-tenancy actually requires 🔥 Must know

In simple terms

One deployment serves many organisations. Each tenant experiences it as their system, and must never be able to reach another tenant's data — by any route, including bugs.

The engineering problem isn't the feature work. It's that every single query, every cache key, every log line and every background job has to be tenant-aware, and one that isn't is a breach.

ConcernWhat it means in practice
Data isolation No query can return another tenant's rows. Enforced structurally, not by discipline
Performance isolation One tenant's heavy usage must not degrade others — the noisy-neighbour problem
Tenant context Every request, job and message must know which tenant it's acting for
Per-tenant configuration Features, limits, branding, and sometimes region
Operational granularity Restore one tenant, migrate one tenant, delete one tenant's data on request
Cost attribution Knowing what each tenant costs you, which is harder than it sounds
The failure that matters more than all the others

A cross-tenant data leak is not an ordinary bug. It's a breach — reportable under GDPR, potentially contract-terminating, and the kind of incident that ends a B2B SaaS product's reputation.

And it's usually caused by something small: one query missing its WHERE TenantId = @tenantId, a cache key without the tenant in it, a background job iterating all records, or an admin endpoint that forgot to scope.

Which is why the answer is never "be careful in code review". It has to be structural — a mechanism that makes the unscoped query impossible or harmless: global query filters, row-level security, or separate databases.

If your protection is "developers remember", you will have a leak eventually. That framing — defence in depth, structural not procedural — is the single most important thing to convey on this topic.

The decisions, and how reversible they are ⭐ Senior-level

Tenant identifier — where it lives, how it's resolved Hard. It's in every table and every request path

Remember this

Put the tenant id on every tenant-owned table from day one, even if you start with a shared schema.

It costs a column. It buys you the ability to enforce isolation structurally, to migrate a single tenant later, and to move to a different isolation model without a full redesign.

Retrofitting it into a live system with hundreds of tables is one of the least pleasant projects available.

Senior signal — the hybrid model is what mature products actually run

The three models are usually presented as a choice. In practice successful products run more than one at once.

The common shape: most tenants share a schema in a pooled database, because they're small and numerous and cost matters. Large or regulated tenants get their own database, because they demand isolation, have data-residency requirements, or generate enough load to be a noisy neighbour.

The key architectural requirement is that a tenant can be moved between models without a rewrite — which means the application resolves the tenant's connection at runtime from a catalogue, rather than having one connection string in configuration.

"I'd design so a tenant can graduate to its own database when it needs to" is a strong answer, because it accepts that the requirements differ per customer instead of forcing one trade-off on everyone. Same reasoning as graduating a tenant out of an elastic pool.

The mistake that's specific to .NET

EF Core caches the model per DbContext type, not per instance. So a global query filter that captures a tenant id incorrectly can be baked into the cached model — and then one tenant's filter is applied to another tenant's requests.

That's a cross-tenant leak that appears only under concurrency, in production, and passes every test that runs one tenant at a time.

The safe pattern is to reference a field on the context instance that EF re-reads per query, and to configure IModelCacheKeyFactory if the filter's shape varies per tenant. Covered on the tenant context page, and it's the single highest-value .NET-specific detail in this section.

How would you design a multi-tenant SaaS application? 🔥 Must know
How I'd answer

"I'd start with questions, because the isolation decision is the one that's hardest to reverse and it depends entirely on the customer profile."

"How many tenants, and how large? Ten thousand small tenants and fifty enterprise customers are completely different problems. What do they demand? Enterprise B2B contracts frequently require data isolation, data residency, or their own encryption keys. What's the compliance position — GDPR, HIPAA, SOC 2? And can one tenant generate enough load to affect others?"

"For most products my answer is a hybrid: shared schema in a pooled database for the many small tenants, with the ability for a large or regulated tenant to graduate to its own database. The key architectural requirement is that the connection is resolved at runtime from a tenant catalogue rather than sitting in configuration, so moving a tenant between models doesn't require a rewrite."

"But whichever model, the thing I'd be most careful about is data isolation, enforced structurally rather than by discipline."

"A cross-tenant leak isn't an ordinary bug — it's a reportable breach and potentially contract-terminating. And it's caused by something small: one query missing its tenant predicate, a cache key without the tenant in it, a background job iterating all records, or an admin endpoint that forgot to scope."

"So I'd want defence in depth. EF Core global query filters so the predicate is applied automatically and a developer can't forget it. SQL row-level security underneath, so even a hand-written query or a direct database connection is filtered — that's the layer that protects you when the application layer is bypassed. And the tenant id on every tenant-owned table from day one, even in a shared schema, because it's what makes both of those possible and retrofitting it later is horrible."

"For tenant context, middleware resolves the tenant — from a subdomain, a header, or preferably a JWT claim since that's signed and can't be spoofed — and puts it in a scoped service. Crucially, the tenant must never be taken from user-supplied input without validating that the authenticated principal is entitled to it. A tenant id in a request body or query string that's trusted is the most direct possible leak."

"Then the parts people forget: the tenant id must be in every cache key, or one tenant's cached response is served to another. Background jobs and message consumers need the tenant carried in the message and a scope created per tenant, because there's no HTTP request to resolve from. And the tenant id belongs in logs and traces — as trace baggage — so the first question in any incident, 'is this one tenant or everyone?', is answerable."

"On noisy neighbours, per-tenant rate limiting backed by Redis so the limit is global across instances, plus per-tenant query monitoring so I can see which tenant is generating load. In a pooled database, per-database caps if I'm using elastic pools."

"And I'd plan the operational granularity up front, because it's usually retrofitted badly: restoring one tenant's data, migrating one tenant to a different database, and deleting a tenant's data completely on request. That last one is a GDPR requirement and it's genuinely hard in a shared schema — you need to know every table and every backup that contains their data."

"One .NET-specific trap I'd flag: EF Core caches the model per context type, not per instance. A global query filter that captures the tenant id wrongly can bake one tenant's filter into the cached model and apply it to another tenant's requests. That's a leak that only appears under concurrency and passes every single-tenant test."

What they're really checking
  • Do you ask about tenant profile before choosing a model?
  • Do you propose a hybrid with runtime connection resolution?
  • Do you insist on structural isolation with defence in depth?
  • Do you cover caches, background jobs and logs — not just queries?
  • Do you refuse to trust a client-supplied tenant id?
  • Do you plan per-tenant restore and deletion?
Weak answers
  • Red flag: "add a TenantId column and filter in queries" with no enforcement mechanism.
  • Red flag: picking an isolation model with no questions.
  • Red flag: no mention of caches or background jobs.
Likely follow-ups
  • How do you migrate 500 databases' schemas safely?
  • How do you delete one tenant's data from backups?
  • How would you detect a leak before a customer does?
