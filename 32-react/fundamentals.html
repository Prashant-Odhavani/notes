Components, JSX & Hooks

Hooks are simple rules with subtle consequences. The dependency array and stale closures account for most React bugs.

🟡 Intermediate 🔴 Advanced 🔥 Must know
Quick revision
  • The component function re-runs entirely on every render.
  • Never mutate state. Replace it.
  • Hooks must be called unconditionally, in the same order every render.
  • useEffect synchronises with things outside React — not a lifecycle hook.
  • Every value used inside an effect belongs in the dependency array.
  • Return a cleanup function from any effect that subscribes.
  • Use the updater form — setCount(c => c + 1) — when the new value depends on the old.

State 🔥 Must know

const [items, setItems] = useState([]);

// WRONG - React compares by reference, so it sees no change and won't re-render
items.push(newItem);
setItems(items);

// WRONG for the same reason
user.name = 'Ravi';
setUser(user);
setItems([...items, newItem]);                     // new array
setItems(items.filter(i => i.id !== id));          // new array
setItems(items.map(i => i.id === id ? { ...i, done: true } : i));

setUser({ ...user, name: 'Ravi' });                // new object
Remember this

React decides whether to re-render by comparing the new state to the old with Object.is.

Mutating and passing the same reference means they're identical, so React concludes nothing changed. The data is correct and the screen is stale — with no error.

Exactly the same reference-comparison rule as Angular's OnPush. Two frameworks, one constraint.

The updater form

// Both read the SAME `count` from this render's closure.
// Result: count + 1, not count + 2.
function handleClick() {
  setCount(count + 1);
  setCount(count + 1);
}
function handleClick() {
  setCount(c => c + 1);
  setCount(c => c + 1);    // receives the result of the previous updater
}                          // Result: count + 2
Why: state is a snapshot, not a live value

count is a const captured in this render's closure. It does not change during the render, and it does not change inside an event handler either.

So setCount(count + 1) twice computes the same result twice. The updater form setCount(c => c + 1) asks React for the current value at the point it's applied, which chains correctly.

Rule: if the new value depends on the old, use the updater form. It's also what makes an effect or a callback safe to omit the state from its dependency array — which removes a common cause of re-running effects.

Batching

React batches multiple setState calls within the same event into a single re-render — so three updates in one handler cause one render, not three.

Since React 18 this applies to all contexts including promises, timeouts and native event handlers (automatic batching). Before 18 it only applied inside React event handlers, so setTimeout callbacks rendered per update.

Practical consequence: you cannot read updated state immediately after setting it. The value in scope is still this render's snapshot.

The rules of hooks 🔥 Must know

RuleWhy
Only at the top level — not in conditions, loops or nested functions React identifies hooks by call order, not by name. A conditional call shifts every subsequent hook's identity
Only in components or custom hooks They need the render context to attach state to 
function Profile({ userId }) {
  if (!userId) return null;              // early return BEFORE hooks

  const [user, setUser] = useState(null);   // sometimes call 1, sometimes never
  const [posts, setPosts] = useState([]);   // identity shifts between renders
}
function Profile({ userId }) {
  const [user, setUser] = useState(null);
  const [posts, setPosts] = useState([]);

  if (!userId) return null;              // conditional return AFTER hooks
  return <div>{user?.name}</div>;
}
Why order matters — the mechanism

React stores hook state in an array per component, indexed by call order. The first useState is slot 0, the second slot 1, and so on. There are no names involved.

So if a conditional skips a hook on one render, every subsequent hook reads the wrong slot — your posts state now returns what user held.

That's why the rule is absolute rather than stylistic, and why the ESLint plugin react-hooks/rules-of-hooks should be an error rather than a warning. It's one of the few lint rules that catches genuine correctness bugs.

useEffect 🔥 Must know

What it's actually for

useEffect exists to synchronise your component with something outside React — a subscription, a timer, a browser API, an imperative library.

It is not a lifecycle hook, and thinking of it as componentDidMount leads to most of the misuse.

// Runs after EVERY render - rarely what you want
useEffect(() => { /* ... */ });

// Runs once, after the first render
useEffect(() => { /* ... */ }, []);

// Runs when userId changes
useEffect(() => { /* ... */ }, [userId]);
useEffect(() => {
  const handler = () => setWidth(window.innerWidth);
  window.addEventListener('resize', handler);

  // Runs before the next effect and on unmount
  return () => window.removeEventListener('resize', handler);
}, []);
Missing cleanup is the standard React memory leak

Without the return function, every mount adds another listener and none are ever removed. In an app where components mount and unmount on navigation, that accumulates — and because the handler closes over component state, the whole scope leaks with it.

Same mechanism as closure-based leaks generally, and the same as Angular's unsubscribed observables.

Anything that starts something needs cleanup: event listeners, intervals, timeouts, subscriptions, AbortController for in-flight requests, WebSocket connections.

The dependency array 🔴 Advanced

function Search({ query, onResults }) {
  useEffect(() => {
    fetch(`/api/search?q=${query}`)
      .then(r => r.json())
      .then(onResults);          // `onResults` used but not declared
  }, [query]);                   // lying - it also depends on onResults
}
The rule, and why it's absolute

Every reactive value used inside the effect must be in the dependency array.

Omitting one doesn't stop it being used — it means the effect keeps using the value from the render when it last ran. That's a stale closure, and it produces bugs that look like race conditions.

The fix is never to remove the dependency. It's to make the value stable — useCallback for functions, the updater form for state, or a ref for something that genuinely shouldn't retrigger.

Stale closures

function Timer() {
  const [count, setCount] = useState(0);

  useEffect(() => {
    const id = setInterval(() => {
      setCount(count + 1);        // `count` is captured as 0, forever
    }, 1000);
    return () => clearInterval(id);
  }, []);                         // effect never re-runs, so never sees a new count

  return <p>{count}</p>;          // stays at 1
}
useEffect(() => {
  const id = setInterval(() => {
    setCount(c => c + 1);        // asks React for the current value
  }, 1000);
  return () => clearInterval(id);
}, []);                          // legitimately empty now
Senior signal — this is the same closure bug as the var loop

The effect ran once with count equal to 0. The interval callback closed over that value. Since the effect never re-runs, the callback holds 0 permanently, so every tick sets state to 1.

That's identical to the var in a loop with setTimeout puzzle — a closure captured a value from a scope that has since moved on. Same mechanism, harder to spot because there's no obvious loop.

Recognising it as one concept rather than two separate React gotchas is what makes it debuggable. When something inside an effect or callback has an unexpectedly old value, the question is always "which render's closure is this code from?"

Race conditions in data-fetching effects
useEffect(() => {
  fetch(`/api/orders/${id}`).then(r => r.json()).then(setOrder);
}, [id]);
// Change id fast: request for id=1 can resolve AFTER id=2,
// so you display order 1 while the URL says 2.
useEffect(() => {
  const controller = new AbortController();

  fetch(`/api/orders/${id}`, { signal: controller.signal })
    .then(r => r.json())
    .then(setOrder)
    .catch(e => { if (e.name !== 'AbortError') setError(e); });

  return () => controller.abort();   // cancel on id change or unmount
}, [id]);

This is the same problem Angular solves with switchMap — cancel the previous request so a stale response can't overwrite a newer one.

Which is a strong argument for React Query: it handles cancellation, deduplication, caching and loading states, so hand-written fetching effects mostly shouldn't exist.

When not to use an effect ⭐ Senior-level

Deriving state from propsCalculate it during render. No state needed
Resetting state when a prop changesA key on the component
Responding to a user eventDo it in the event handler
Fetching dataReact Query, or a framework loader
Transforming data for displayCompute in render, memoise if genuinely expensive
 
const [fullName, setFullName] = useState('');
useEffect(() => {
  setFullName(`${first} ${last}`);   // extra render, extra state, can drift
}, [first, last]);
const fullName = `${first} ${last}`;   // no state, no effect, always correct
The key trick for resetting state
// Instead of an effect that clears form state when the user changes:
<EditProfileForm key={userId} user={user} />

// A different key means React unmounts the old component and mounts a
// fresh one - so all its state resets automatically.

This is the idiomatic answer to "reset state when a prop changes", and it's much more reliable than an effect that has to remember every piece of state to clear.

It works because key is how React establishes component identity. A new key is a new component as far as reconciliation is concerned.

Knowing this is a good signal — it shows familiarity with the official guidance rather than just the API surface.

useRef 🟡 Intermediate

useStateuseRef
Triggers a re-renderYesNo
Survives rendersYesYes
MutableNo — replace itYes, via .current
Use forAnything the UI displaysDOM nodes, timer ids, values the UI doesn't show
 
// 1. A DOM reference
const inputRef = useRef<HTMLInputElement>(null);
useEffect(() => { inputRef.current?.focus(); }, []);

// 2. A mutable value that shouldn't cause renders
const timerRef = useRef<number>();
const start = () => { timerRef.current = window.setInterval(tick, 1000); };
const stop  = () => { clearInterval(timerRef.current); };
A ref is not a way to avoid re-rendering

If a value appears in the UI, it belongs in state. Putting it in a ref means the screen won't update when it changes — which looks like a performance win and is actually a bug.

The distinction: state is what the UI is derived from; a ref is a box you keep something in.

Timer ids, previous values for comparison, whether something has already run, a scroll position you only read imperatively — refs. Anything rendered — state.

Context 🟡 Intermediate

const ThemeContext = createContext<Theme>('light');

function App() {
  const [theme, setTheme] = useState<Theme>('light');

  // Memoise, or every App render gives consumers a new object
  const value = useMemo(() => ({ theme, setTheme }), [theme]);

  return (
    <ThemeContext.Provider value={value}>
      <Layout />
    </ThemeContext.Provider>
  );
}

function DeepChild() {
  const { theme } = useContext(ThemeContext);   // no prop drilling
}
Context re-renders every consumer

When a context value changes, every component consuming it re-renders — regardless of whether it uses the part that changed.

So a single context holding user, theme, cart and notifications means a cart update re-renders every component reading any of it.

Two fixes. Split contexts by change frequency — a rarely-changing theme context separate from a frequently-changing cart context. And memoise the value object, because value={{ theme, setTheme }} creates a new object on every provider render, so consumers re-render even when nothing meaningful changed.

Context is designed for low-frequency, widely-read values — theme, locale, current user. For frequently-changing shared state, a store library with selector-based subscriptions is the better tool.

Custom hooks 🟡 Intermediate

function useDebounced<T>(value: T, delay = 300): T {
  const [debounced, setDebounced] = useState(value);

  useEffect(() => {
    const id = setTimeout(() => setDebounced(value), delay);
    return () => clearTimeout(id);     // cancel if value changes again
  }, [value, delay]);

  return debounced;
}

// Usage
const query = useSearchInput();
const debouncedQuery = useDebounced(query, 400);
Custom hooks share logic, not state

Each call to a custom hook gets its own independent state. Two components using useDebounced don't share anything.

That's the common misunderstanding — people expect a custom hook to behave like a singleton service. It's closer to a function that happens to be able to use hooks.

To share state you need context, a store, or lifting the state to a common parent. Custom hooks are for reusing behaviour: debouncing, media queries, local storage sync, form handling.

Naming must start with use — that's how the linter knows to apply the hook rules to it.

StrictMode double-invokes effects in development

In development, React 18+ intentionally mounts, unmounts and remounts each component — so effects run twice.

That's not a bug, it's a detector: an effect that isn't correctly cleaned up behaves differently on the second run, so problems surface immediately rather than in production. An effect that logs twice or fetches twice in development is telling you its cleanup is incomplete.

It doesn't happen in production builds. Suppressing it with a ref flag defeats the purpose — the right response is to make the effect idempotent and properly cleaned up.

Key takeaways
  • The component function re-runs entirely; hooks are how values survive between renders.
  • Replace state, never mutate — React compares by reference.
  • Use the updater form when the new value depends on the old.
  • Hooks are identified by call order, so they must be unconditional.
  • useEffect synchronises with the outside world; it's not a lifecycle hook.
  • Every reactive value used in an effect goes in the dependency array — omitting one causes a stale closure.
  • Always return cleanup from an effect that starts something.
  • Cancel in-flight requests, or a stale response can overwrite a newer one.
  • Derive during render rather than in an effect; use key to reset state.
  • Refs for things the UI doesn't display; state for anything rendered.
  • Context re-renders all consumers — split by change frequency and memoise the value.
  • Custom hooks share behaviour, not state.

Common mistakes

  • Mutating state and expecting a re-render.
  • setX(x + 1) twice in one handler.
  • Hooks after an early return or inside a condition.
  • Omitting dependencies to stop an effect re-running.
  • No cleanup function on subscriptions, timers or listeners.
  • No request cancellation, allowing stale responses to win.
  • An effect to derive state from props.
  • A ref for displayed values.
  • One large context for everything.
  • Unmemoised context value objects.
  • Suppressing StrictMode double-invocation instead of fixing cleanup.

Interview questions

Intermediate

Explain useEffect and its dependency array. 🔥 Must know
How I'd answer

"useEffect runs code after render, and its purpose is synchronising your component with something outside React — a subscription, a timer, a browser API, an imperative library."

"I'd stress that framing, because thinking of it as componentDidMount causes most of the misuse. It's not a lifecycle hook; it's a synchronisation mechanism."

"The dependency array controls when it re-runs. No array means after every render. An empty array means once after the first render. Listed values mean it re-runs when any of them changes."

"The rule is that every reactive value used inside the effect must be in the array. And the reason omitting one is dangerous is subtle: it doesn't stop the value being used, it means the effect keeps using the value from the render when it last ran. That's a stale closure, and it produces bugs that look like race conditions."

"The classic example is an interval that calls setCount(count + 1) with an empty dependency array. The effect ran once when count was 0, the callback closed over that zero, and since the effect never re-runs it holds zero forever — so the counter sticks at 1."

"And the important insight is that this is the same closure behaviour as the classic var-in-a-loop puzzle. A callback captured a value from a scope that has since moved on. Same mechanism, just harder to spot because there's no visible loop. Once you see it that way, the debugging question becomes 'which render's closure is this code from?'"

"The fix is never to remove the dependency to silence the linter. It's to make the value stable — the updater form setCount(c => c + 1) asks React for the current value so the effect genuinely doesn't depend on count, or useCallback for a function, or a ref for something that shouldn't retrigger."

"Cleanup is the other half. The returned function runs before the next effect and on unmount. Anything that starts something needs it — listeners, intervals, subscriptions, an AbortController for in-flight requests. Without it you leak on every mount, and because the handler closes over component state, the whole scope leaks with it."

"The thing I'd add unprompted: a lot of effects shouldn't exist. Deriving state from props should be a calculation during render. Resetting state when a prop changes is better done with a key on the component. Responding to a user action belongs in the event handler. And data fetching is better handled by React Query, which solves cancellation, caching and loading states that a hand-written effect has to reimplement badly."

What they're really checking
  • Do you frame it as synchronisation, not a lifecycle hook?
  • Do you understand stale closures mechanically?
  • Do you fix them by stabilising rather than removing deps?
  • Do you know cleanup is mandatory?
  • Do you know when not to use an effect?
Weak answers
  • Red flag: "it's componentDidMount for functions".
  • Red flag: removing dependencies to stop re-runs.
  • Red flag: no mention of cleanup.

Why can't you call hooks conditionally? 🔥 Must know
How I'd answer

"Because React identifies hooks by call order, not by name."

"Internally, each component has an array of hook state, and React walks it positionally as your function runs. The first useState gets slot 0, the second slot 1, the useEffect after them slot 2. There are no identifiers involved — React has no idea what you called the variables."

"So if a condition skips a hook on some render, every hook after it shifts by one slot. Your posts state starts reading whatever user held. It's not a warning-level problem — the state genuinely becomes wrong, and it depends on the condition, so it's intermittent."

"The most common way this happens isn't an explicit if around a hook — it's an early return. if (!userId) return null; placed above the hooks means on some renders none of them are called at all."

"So the pattern is: all hooks first, unconditionally, then branch. The conditional return goes after them. That sometimes means calling a hook whose result you won't use on this render, which feels wasteful and is correct — the cost is negligible and the alternative is broken."

"For conditional behaviour the condition goes inside the hook rather than around it. An effect that should only fetch when there's an id: call useEffect unconditionally and put the guard in the body. Same for a query hook — most data-fetching libraries have an enabled option for exactly this."

"Practically, I'd have react-hooks/rules-of-hooks configured as an error, not a warning. It's one of the few lint rules that catches genuine correctness bugs rather than style, and it's reliable — it won't let this through."

"If a component has genuinely different hook requirements depending on a condition, that's usually a sign it should be two components with a conditional render choosing between them. Each gets its own consistent hook order, and the code is clearer about the fact there are two cases."

What they're really checking
  • Do you know the mechanism — positional slots?
  • Do you know early returns are the common cause?
  • Do you know to put conditions inside hooks?
  • Do you suggest splitting the component when appropriate?
Likely follow-ups
  • How does React store hook state?
  • How would you conditionally fetch data?
  • Why must custom hooks start with "use"?
