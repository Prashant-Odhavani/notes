React

One idea, applied consistently: the UI is a function of state. Almost everything else follows from that.

🟡 Intermediate 🔥 Must know

The one idea 🔥 Must know

In simple terms

You don't tell React what to change. You describe what the UI should look like for the current state, and React works out the DOM operations.

When state changes, your component function runs again, producing a new description. React compares it to the previous one and applies the difference.

Think of it this way

jQuery is giving someone step-by-step directions: turn left, then right, then stop.

React is giving them the destination address. How they get there is not your concern — and if the destination changes, you just give the new address.

function OrderStatus({ order }) {
  const [expanded, setExpanded] = useState(false);

  // This is a DESCRIPTION, not a set of instructions.
  // It re-runs whenever `order` or `expanded` changes.
  return (
    <div>
      <button onClick={() => setExpanded(!expanded)}>
        {order.reference} — {order.status}
      </button>
      {expanded && <OrderLines lines={order.lines} />}
    </div>
  );
}
Remember this

UI = f(state).

There is no list of DOM updates to remember. You can't forget to update the button when the status changes, because the button's text is declared as a function of the status.

That's the bug class imperative DOM manipulation creates, and it disappears rather than being managed.

DI container resolves dependencies No DI container. Props, context, or module imports
Framework provides routing, HTTP, forms You choose libraries. React renders; that's all
Two-way binding One-way. Data down via props, changes up via callbacks
Lifecycle hooks for each phase useEffect for synchronising with things outside React
The shift that causes the most confusion

A component function runs from top to bottom on every single render.

So a local variable is recreated each time. A function defined in the body is a new function object on every render. An object literal is a new object.

That's why hooks exist: useState is how a value survives between renders, useRef is how a mutable box survives, useMemo and useCallback are how you keep the same object identity when something downstream compares by reference.

Coming from a class-based framework, the instinct is that the component is an instance with persistent fields. It isn't. Internalising "the function re-runs entirely" explains most of React's apparent strangeness — including stale closures, which are the same capture-the-variable behaviour from plain JavaScript.

Senior signal — the state-management shift matters more than the API changes

The biggest practical change in React over the last five years isn't a new hook. It's the realisation that most "global state" was actually cached server data.

Teams used to put fetched API data in Redux, then hand-write loading flags, error states, cache invalidation and refetch logic — hundreds of lines of boilerplate per feature.

React Query and similar libraries own that entirely. Once server data lives there, most applications need very little genuine global client state — a theme, the current user, maybe a sidebar toggle. Which is why "do we need Redux?" is now usually answered "probably not".

Saying that distinguishes someone who's worked through the shift from someone who learned React from older material. Covered on the state page.

This list is the actual trade-off with Angular

Angular ships routing, HTTP, forms, DI and testing. React ships a renderer, and you assemble the rest.

The upside is picking best-in-class tools and not carrying what you don't use — React Query genuinely has no Angular equivalent of similar maturity.

The downside is decision cost and divergence. Two React codebases at the same company can look completely different, so moving between them means relearning the architecture. Angular's opinionation is what prevents that.

Neither is wrong. But "React is more flexible" and "Angular is more consistent" are the same fact viewed from either side, and being able to say that is a better answer than advocating for one.

Angular or React for a new project? ⭐ Senior-level
How I'd answer

"My first answer is whichever the team already knows — and I'd mean that seriously rather than as a way of avoiding the question. Both are mature and capable. Framework familiarity outweighs the technical differences for almost every real project, and choosing the one the team doesn't know costs months of reduced velocity plus the mistakes people make while learning."

"If the team has no strong preference, the differences that actually matter:"

"Angular is a framework; React is a library. Angular ships routing, HTTP, forms, DI and testing, and there's one obvious way to do each. React ships a renderer and you choose the rest — React Router, React Query, React Hook Form, a state library."

"That's the real trade. Angular's opinionation means ten developers write similar code and a new starter recognises the structure. React's flexibility means better tool choices and more divergence — two React codebases at the same company can look nothing alike, so moving between teams means relearning the architecture."

"So I'd lean Angular for a large or rotating team, particularly in an enterprise where consistency and onboarding matter more than picking the optimal library. And React for a small aligned team, or where the ecosystem has something specific you want."

"For a .NET team specifically, Angular tends to feel natural — constructor injection, decorators, TypeScript throughout, an injector hierarchy that behaves like ASP.NET Core's service lifetimes. The concepts transfer rather than needing to be learned fresh. React's model — a function that re-runs entirely, immutable state, no DI container — takes more adjustment for someone used to class instances with mutable fields."

"Where React has a genuine edge: server-side rendering and the data layer. Next.js is more mature than Angular Universal, and React Query has no Angular equivalent of comparable maturity for server-state caching. If the application is content-heavy and SEO matters, or the data layer is complex, that's a real consideration."

"What I'd push back on is choosing based on benchmarks or popularity. Performance differences between them are dominated by how you write the code — a badly-written React app with unnecessary re-renders is slower than a well-written Angular app with OnPush, and vice versa. And hiring-pool arguments cut both ways depending on the market."

What they're really checking
  • Do you lead with team familiarity rather than technical advocacy?
  • Can you state the framework-versus-library trade honestly?
  • Do you know where each genuinely has an edge?
  • Do you resist benchmark-driven reasoning?
Weak answers
  • Red flag: "React, it's faster" or "Angular, it's more enterprise".
  • Red flag: no acknowledgement of team context.
Likely follow-ups
  • What would make you migrate an existing app?
  • How do you handle state in React without Redux?
  • What's the SSR story in each?
