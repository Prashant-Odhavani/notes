Server state vs client state 🔥 Must know

The distinction that solves most of this

Server state is data you don't own. It lives in a database, other people change it, and your copy is a cache that can go stale.

Client state is data you do own. A modal being open, a form's current values, which tab is selected. Nobody else can change it and it doesn't exist anywhere else.

Why putting server data in Redux was a mistake

A generic store has no concept of staleness. So every feature had to hand-write: a loading flag, an error field, a "have we fetched this yet?" check, cache invalidation on mutation, refetch on window focus, request deduplication, and retry logic.

That's hundreds of lines of near-identical boilerplate per feature — actions, reducers, thunks, selectors — reimplementing a cache badly.

React Query does all of it as a library concern. Once server data moves there, what's left as genuine global client state is usually tiny: the current user, a theme, maybe a sidebar toggle. Which is why "do we need Redux?" is now usually answered "probably not".

This shift is the single most useful thing to understand about modern React state management, and it's why older tutorials feel so much heavier than current practice.

React Query 🔥 Must know

function OrderList({ customerId }: { customerId: string }) {
  const { data, isPending, isError, error, refetch } = useQuery({
    queryKey: ['orders', customerId],          // identity of this cached data
    queryFn: ({ signal }) => fetchOrders(customerId, signal),
    staleTime: 30_000                          // fresh for 30s; no refetch
  });

  if (isPending) return <Skeleton />;
  if (isError)   return <Error message={error.message} onRetry={refetch} />;

  return <ul>{data.map(o => <li key={o.id}>{o.reference}</li>)}</ul>;
}

Caching keyed by queryKey — two components asking for the same data share one request
Deduplication — simultaneous identical requests become one
Stale-while-revalidate — show cached data instantly, refresh in the background
Refetch on window focus and reconnect
Retry with backoff on failure
Request cancellation via the signal
Loading, error and pending states
Garbage collection of unused cache entries
The queryKey is the whole design

The key is the cache identity. ['orders', customerId] means each customer's orders are cached separately, and changing customerId automatically fetches the new set — no effect, no manual refetch.

It's also how invalidation works: after a mutation, invalidateQueries({ queryKey: ['orders'] }) marks every orders query stale, so any mounted component refetches. Hierarchical keys make that precise — invalidate all orders, or just one customer's.

Getting keys right is most of using React Query well. Include every value the query depends on, in a consistent order.

const queryClient = useQueryClient();

const { mutate, isPending } = useMutation({
  mutationFn: (order: NewOrder) => createOrder(order),
  onSuccess: () => {
    // Anything cached under ['orders'] is now stale - refetch it
    queryClient.invalidateQueries({ queryKey: ['orders'] });
  }
});
const { mutate } = useMutation({
  mutationFn: toggleDone,

  onMutate: async (id) => {
    await queryClient.cancelQueries({ queryKey: ['todos'] });
    const previous = queryClient.getQueryData<Todo[]>(['todos']);

    // Update the UI immediately, before the server responds
    queryClient.setQueryData<Todo[]>(['todos'], old =>
      old?.map(t => t.id === id ? { ...t, done: !t.done } : t));

    return { previous };                    // context for rollback
  },

  onError: (_err, _id, context) => {
    queryClient.setQueryData(['todos'], context?.previous);   // roll back
  },

  onSettled: () => {
    queryClient.invalidateQueries({ queryKey: ['todos'] });   // reconcile
  }
});
Senior signal — optimistic updates need all three handlers

The pattern is only correct with the full set: onMutate applies the change and captures the previous state, onError restores it, and onSettled invalidates so the cache reconciles with whatever the server actually did.

Skipping the rollback means a failed mutation leaves the UI showing a change that didn't happen — worse than no optimism, because the user believes it succeeded.

Skipping cancelQueries means an in-flight refetch can land after your optimistic write and overwrite it, so the change appears to revert briefly.

Worth being calibrated about when to use it: optimistic updates suit high-confidence, low-stakes, easily-reversible actions — toggling a checkbox, liking something. Not for a payment, where showing success before confirmation is actively dangerous.

Choosing a client state approach 🔥 Must know

Escalate only when you have to
  1. useState in the component — the default. Most state is local.
  2. Lift to the nearest common parent when siblings need it.
  3. useReducer when several fields change together with real transitions.
  4. Context for genuinely global, low-frequency values.
  5. A store (Zustand) when context re-renders become a problem or the state is complex.
  6. Redux Toolkit for large applications needing strict conventions and time-travel debugging.

Most applications should stop at step 4.

const useCartStore = create<CartState>((set) => ({
  items: [],
  add: (item) => set(s => ({ items: [...s.items, item] })),
  clear: () => set({ items: [] })
}));

// This component re-renders ONLY when the count changes,
// not when any other part of the store does.
function CartBadge() {
  const count = useCartStore(s => s.items.length);
  return <span>{count}</span>;
}
Senior signal — why a store beats context for frequently-changing state

Context has no selector mechanism. Any change to the context value re-renders every consumer, whether or not it uses the field that changed. So a cart context also holding the user means a cart update re-renders everything reading the user.

A store like Zustand subscribes per-selector. useCartStore(s => s.items.length) only re-renders when that derived value changes, so adding an item doesn't disturb unrelated components.

That's the concrete technical reason to reach for a store, and it's a better answer than "context doesn't scale". Context is excellent for what it's designed for — low-frequency, widely-read values like theme, locale and current user, where the re-render cost is irrelevant because it happens rarely.

Forms 🟡 Intermediate

const schema = z.object({
  reference: z.string().min(1, 'Required').max(20),
  email:     z.string().email('Invalid email'),
  quantity:  z.coerce.number().int().min(1)
});

type FormValues = z.infer<typeof schema>;    // types derived from the schema

function OrderForm() {
  const { register, handleSubmit, formState: { errors, isSubmitting } } =
    useForm<FormValues>({ resolver: zodResolver(schema) });

  return (
    <form onSubmit={handleSubmit(save)}>
      <label htmlFor="reference">Reference</label>

             aria-invalid={!!errors.reference}
             aria-describedby="reference-error" />
      {errors.reference &&
        <p id="reference-error" role="alert">{errors.reference.message}</p>}

      <button disabled={isSubmitting}>Save</button>
    </form>
  );
}

Zod earns its place because TypeScript doesn't exist at runtime

A TypeScript type is erased at compile time. Declaring an API response as Order guarantees nothing about what the server sent — if it sends something different, TypeScript is content and your code fails later with a confusing error.

Zod validates at runtime and derives the TypeScript type from the same schema via z.infer. So there's one definition, and the type is guaranteed to match what was actually validated.

That makes it valuable at every trust boundary — form input, API responses, localStorage, URL parameters. Same principle as validating incoming models server-side: never trust a declared type across a boundary.

Client validation is still not security

A Zod schema in the browser is trivially bypassed — DevTools, a direct API call, a modified bundle.

So the same schema logic must run server-side. Sharing the schema between client and server is genuinely valuable when both are TypeScript; with a .NET backend you're maintaining the rules twice, which is a real cost worth acknowledging.

Client validation exists so the user gets immediate feedback. Server validation is what protects the system.

Senior signal — put filter state in the URL

A filtered, sorted, paginated list stored in useState means the user can't bookmark it, can't share it, loses it on refresh, and the back button doesn't work as they expect.

Putting it in search parameters — ?status=open&page=2&sort=date — makes the URL the source of truth. It's shareable, refresh-safe, back-button-correct, and it pairs naturally with React Query because the params become part of the queryKey.

It also removes a piece of state you'd otherwise have to manage and synchronise.

That's a design instinct interviewers notice, because it shows you think about the user's actual behaviour rather than just component structure.

Key takeaways
  • Server state is a cache; client state is owned. Separating them removes most complexity.
  • React Query gives caching, deduplication, revalidation, retries and cancellation for free.
  • The queryKey is the cache identity and the invalidation handle.
  • Optimistic updates need onMutate, onError rollback and onSettled.
  • Escalate state: useState → lift → useReducer → context → store. Most stop at context.
  • Context re-renders every consumer; a store subscribes per selector.
  • React Hook Form is uncontrolled, so typing doesn't re-render the form.
  • Zod validates at runtime and derives the type — TypeScript types are erased.
  • Client validation is UX; the server enforces.
  • Filter and pagination state belongs in the URL.

Common mistakes

  • Server data in Redux, hand-writing cache logic.
  • Reaching for Redux by default before trying local state.
  • One large context for unrelated concerns.
  • Unmemoised context values.
  • Controlled inputs with a useState per field on a large form.
  • Trusting TypeScript types for API responses.
  • Optimistic updates without rollback.
  • Optimistic updates on payments or other irreversible actions.
  • Filter state in component state rather than the URL.
  • Duplicating server state into local state, so the two drift.
  • Route guards treated as authorisation.

Intermediate

How do you manage state in a React application? 🔥 Must know
How I'd answer

"The first thing I'd do is separate server state from client state, because conflating them is what makes state management feel hard."

"Server state is data I don't own — it lives in a database, other people change it, and my copy is a cache that can go stale. It needs loading and error states, caching, refetching and invalidation."

"Client state is data I own — is this modal open, which tab is selected, what's in this form. Nobody else can change it and it doesn't exist anywhere else."

"Server state goes in React Query. That's the single highest-value decision, because a generic store has no concept of staleness — so putting fetched data in Redux means hand-writing a loading flag, an error field, cache invalidation, refetch-on-focus, deduplication and retry logic for every feature. That's hundreds of lines of near-identical boilerplate reimplementing a cache badly. React Query does all of it as a library concern."

"Once server data moves there, what's left as global client state is usually tiny — the current user, a theme, maybe a sidebar toggle. Which is why 'do we need Redux?' is now normally answered 'probably not'."

"For the client state that remains, I'd escalate only as needed. useState in the component by default, since most state is genuinely local. Lift it to the nearest common parent when siblings need it. useReducer when several fields change together with real state transitions — that's more testable and makes invalid combinations harder. Context for genuinely global low-frequency values."

"I'd reach for a store when context becomes a performance problem, and I'd be specific about why: context has no selector mechanism, so any change to the value re-renders every consumer regardless of which field they read. A store like Zustand subscribes per selector, so useCartStore(s => s.items.length) only re-renders when that derived value changes."

"Redux Toolkit I'd justify by team and scale rather than technology — a large codebase with many contributors benefits from enforced conventions and the devtools time-travel debugging. It's not wrong, it's just more machinery than most applications need now that server state is handled elsewhere."

"Two other things I'd mention. URL as state for filters, sorting and pagination — it makes links shareable, survives refresh, makes the back button behave, and the params become part of the React Query key naturally. And don't copy server state into local state, because then you have two sources of truth that drift; derive from the query result instead."

What they're really checking
  • Do you lead with the server/client distinction?
  • Do you know what React Query replaces and why?
  • Do you escalate rather than defaulting to Redux?
  • Do you know the technical reason context struggles?

  • Red flag: no distinction between cached server data and owned state.
  • Red flag: "context doesn't scale" with no mechanism.

Advanced

Implement an optimistic update. What can go wrong? ⭐ Senior-level
How I'd answer

"An optimistic update applies the change to the UI before the server confirms it, so the interaction feels instant. With React Query that's three handlers on the mutation, and all three are necessary."

"onMutate runs before the request. It cancels any in-flight refetch for that key, captures the current cached value, then writes the optimistic change into the cache and returns the previous value as context."

"onError restores that captured value — the rollback."

"onSettled invalidates the query so the cache reconciles with whatever the server actually did, on both success and failure."

"Now what goes wrong."

"No rollback. The most common omission. A failed mutation leaves the UI showing a change that never happened — which is worse than no optimism, because the user believes it succeeded and moves on."

"Not cancelling in-flight queries. If a refetch is already running, it can land after your optimistic write and overwrite it with server data that doesn't include the change. The user sees their change appear and then revert, which looks like a random glitch. That's what cancelQueries prevents."

"Assuming the server produces the same result. If the server assigns an id, a timestamp, or applies business rules — a discount, a status transition — the optimistic value won't match. So the onSettled invalidation isn't optional; it's what reconciles the guess with reality. For a created item that means a temporary id in the cache that gets replaced, and any code keyed on that id has to tolerate it changing."

"Concurrent mutations. Two rapid toggles both capture 'previous' state, and if one fails the rollback can restore a value that's already stale, undoing the other change. React Query's cancelQueries plus invalidation handles most of this, but for genuinely high-frequency mutations I'd consider serialising them or debouncing."

"Then the judgement call, which is the more important part: optimism is only appropriate for high-confidence, low-stakes, easily-reversible actions. Toggling a checkbox, liking a post, reordering a list — where failure is rare and the correction is unremarkable."

"Never for a payment, an order submission, or anything irreversible. Showing 'payment successful' before the server confirms is actively harmful — the user leaves believing they've paid. There, a pending state is correct even though it feels slower."

"And it interacts with the idempotency question: if the mutation is retried after an ambiguous timeout, the server needs an idempotency key so the retry doesn't create a duplicate. Optimistic UI plus automatic retry without idempotency is how you get two orders from one click."

What they're really checking
  • Do you know all three handlers and why each is needed?
  • Do you know about cancelling in-flight refetches?
  • Do you know the server may produce a different result?
  • Do you know when optimism is inappropriate?
  • Do you connect retries to idempotency?
Weak answers
  • Red flag: no rollback.
  • Red flag: applying it to payments.
  • Red flag: no reconciliation with the server result.
Likely follow-ups
  • How do you handle the temporary id for a created item?
  • What if two mutations race?
  • How would you show a failure to the user gracefully?
