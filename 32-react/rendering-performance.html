Rendering & Performance

Re-rendering is not the problem people think it is. Knowing what's actually expensive is the skill.

🟡 Intermediate 🔴 Advanced 🔥 Must know
Quick revision
  • A re-render is running your function and diffing — not touching the DOM.
  • State change re-renders that component and all its children, by default.
  • Keys give elements identity. Index keys break on reorder or insert.
  • memo compares props by reference, so inline objects and functions defeat it.
  • Don't memoise pre-emptively. Measure first — memoisation has a cost.
  • The real fix is usually fewer DOM nodes or less work per render.
  • The React Compiler automates memoisation, which makes most manual tuning obsolete.

What a re-render actually costs 🔥 Must know

In simple terms

A re-render means React calls your component function again and compares the returned description to the previous one.

It does not mean the DOM is updated. React only touches the DOM where the descriptions differ.

PhaseWorkCost
RenderCall the function, build the element treeUsually cheap — it's just JavaScript
ReconcileDiff against the previous treeCheap, and proportional to tree size
CommitApply DOM changesThe expensive part
Remember this

A re-render that produces identical output costs almost nothing. React diffs, finds no change, and touches no DOM.

So "this component re-renders too often" is frequently not a problem worth solving. What's expensive is:

  • Expensive work inside the render — sorting, filtering, formatting thousands of items.
  • Very large trees — thousands of components, where even cheap work multiplies.
  • Actual DOM changes — layout and paint.

Chasing re-render counts without measuring is the most common wasted effort in React performance work.

What triggers a re-render 🔥 Must know

CauseScope
State change in the componentThat component and all descendants
Parent re-rendersAll children, unless wrapped in memo
Context value changesEvery consumer, regardless of which field changed
A hook the component uses updatesThat component
Props changing is not a trigger

This surprises people. A child re-renders because its parent re-rendered, not because its props changed. React doesn't check whether props differ before re-rendering a child — it just renders the whole subtree.

memo is what adds that check: it compares props by reference and skips the render if they're all equal.

Which is why passing an inline object or arrow function defeats memo entirely — those are new references every render, so the comparison always fails.

Reconciliation and keys 🔥 Must know

Why keys exist

When React diffs a list, it needs to know which new element corresponds to which old one. Position isn't enough — inserting at the front shifts everything.

A key is the element's identity. Same key means "this is the same item, update it". Different key means "this is a different item, unmount the old and mount the new".

{items.map((item, i) => <TodoRow key={i} todo={item} />)}

// Insert a new item at the front:
//   Before: key 0 = "Buy milk",  key 1 = "Walk dog"
//   After:  key 0 = "NEW ITEM",  key 1 = "Buy milk",  key 2 = "Walk dog"
//
// React thinks item 0 CHANGED from "Buy milk" to "NEW ITEM" rather than
// a new item being inserted. So it reuses the wrong component instances -
// and any internal state (a checkbox, an open editor, focus) stays with
// the wrong row.
{items.map(item => <TodoRow key={item.id} todo={item} />)}
Why index keys are a correctness bug, not a performance one

The usual explanation is that index keys are "slower". The real problem is wrong state.

If each row has internal state — a checkbox, an inline edit field, focus — that state belongs to the component instance. Reuse the instance for a different item and the state follows the position, not the data. So you tick row 2, insert an item at the top, and the tick is now on the wrong row.

That's a data-integrity bug the user can see, and it's silent in testing because it needs a specific sequence.

Index keys are acceptable only when the list is static — never reordered, filtered, or added to — and the items have no internal state. Otherwise use a stable id from the data.

And never use Math.random() as a key: a new key every render means React unmounts and remounts every item, every time. That's genuinely catastrophic for both performance and state.

memo, useMemo, useCallback 🔥 Must know

ToolMemoisesUse when
memo(Component)The component's render outputAn expensive component whose props rarely change
useMemo(fn, deps)A computed valueExpensive calculation, or a stable object reference
useCallback(fn, deps)A function referencePassing a callback to a memoised child or an effect dependency
 
const Row = memo(function Row({ item, onSelect }) { /* ... */ });

function List({ items }) {
  return items.map(item => (
    <Row
      key={item.id}
      item={item}
      onSelect={() => select(item.id)}    // NEW function every render
      style={{ padding: 8 }}              // NEW object every render
    />
  ));
  // memo compares by reference, so both always differ.
  // Every Row re-renders. The memo does nothing except add a comparison cost.
}
const ROW_STYLE = { padding: 8 };        // module scope - one object, forever

function List({ items }) {
  // Stable across renders; the child gets the id from its own props
  const handleSelect = useCallback((id) => select(id), []);

  return items.map(item => (
    <Row key={item.id} item={item} onSelect={handleSelect} style={ROW_STYLE} />
  ));
}
Senior signal — memoisation is not free, and partial application is worse than none

Every useMemo and useCallback has a cost: storing the previous value, comparing dependencies on every render, and the memory it holds. For a cheap calculation the bookkeeping can exceed the work saved.

More importantly, memoisation is all-or-nothing along a path. Wrapping a child in memo while passing it an inline arrow function achieves precisely nothing — you've added the comparison cost and kept the re-render. That's a very common pattern in code that looks optimised.

So the honest position: measure first, memoise the specific thing that's slow. Blanket memoisation makes code harder to read, adds bugs when dependency arrays are wrong, and frequently makes things marginally slower.

The exception where useMemo is right without measuring: keeping a reference stable because something downstream depends on identity — a context value, an effect dependency, a prop to a memoised child. That's correctness, not optimisation.

The React Compiler changes this calculus

React 19's compiler analyses your components at build time and inserts memoisation automatically — so it can determine which values are stable and skip re-renders without memo, useMemo or useCallback in your source.

Where it applies, most manual memoisation becomes unnecessary, and the "should I memoise this?" question largely disappears.

It requires code that follows the rules — no mutation during render, no side effects in the render body. Which is another reason the rules matter: they're what makes automated optimisation possible.

For an interview: know it exists, know it doesn't remove the need to understand why re-renders happen, and be aware most production codebases aren't using it yet.

Profiling 🔥 Must know

ToolShows
React DevTools ProfilerWhich components rendered, how long each took, and why it rendered
"Highlight updates" settingVisual flash on re-render — quick way to spot excess
Chrome Performance panelLong tasks, layout, paint — for non-React costs
LighthouseCore Web Vitals, initial load
"Why did this render?" is the feature to use

In the DevTools Profiler settings, enabling "Record why each component rendered" attributes each render to a cause — a state change, a props change and which prop, a context update, or a parent re-render.

That turns guesswork into diagnosis. "This list re-renders because the context value changed" is actionable; "this seems to render a lot" isn't.

And it frequently reveals that the component you suspected is cheap, while something unexpected — a context provider high in the tree — is causing wide re-renders.

Long lists ⭐ Senior-level

import { useVirtualizer } from '@tanstack/react-virtual';

function OrderList({ orders }) {
  const parentRef = useRef<HTMLDivElement>(null);

  const virtualizer = useVirtualizer({
    count: orders.length,            // 10,000
    getScrollElement: () => parentRef.current,
    estimateSize: () => 48
  });

  return (
    <div ref={parentRef} style={{ height: 600, overflow: 'auto' }}>
      <div style={{ height: virtualizer.getTotalSize(), position: 'relative' }}>
        {virtualizer.getVirtualItems().map(v => (
          <div key={orders[v.index].id}
               style={{ position: 'absolute', top: v.start, height: v.size }}>
            {orders[v.index].reference}
          </div>
        ))}
      </div>
    </div>
  );
  // ~15 DOM nodes regardless of list length.
}
The insight that matters

Memoisation cannot fix a 10,000-node DOM.

Browser layout, paint and memory costs scale with node count, independently of React. Even a perfectly memoised list of 10,000 rows is slow to scroll because the browser has 10,000 elements to manage.

So the fix is rendering fewer nodes — virtualisation, or server-side paging. Same conclusion as Angular's virtual scrolling, for the same non-framework reason.

Ask whether the data should be there at all

Before virtualising, the better question is often whether the client needs 10,000 rows. Server-side paging reduces the payload, the query cost and the DOM — three problems with one change.

Virtualisation is right when the user genuinely needs to scroll a long list continuously — a log viewer, a large table with sorting. Paging is right when they're looking for something specific, because search and filters serve them better than scrolling.

That's a product question as much as a technical one, and raising it is usually the more senior response.

function SearchPage() {
  const [query, setQuery] = useState('');
  const [isPending, startTransition] = useTransition();
  const [results, setResults] = useState<Item[]>([]);

  function onChange(e: ChangeEvent<HTMLInputElement>) {
    setQuery(e.target.value);            // urgent - the input must stay responsive

    startTransition(() => {              // non-urgent - can be interrupted
      setResults(expensiveFilter(e.target.value));
    });
  }

  return (
    <>
      <input value={query} onChange={onChange} />
      <div style={{ opacity: isPending ? 0.6 : 1 }}>
        <ResultList items={results} />
      </div>
    </>
  );
}
What useTransition actually does

It marks an update as interruptible. If a more urgent update arrives — another keystroke — React abandons the in-progress render and starts again with the newer value.

Without it, a slow render blocks the main thread and the input visibly lags behind typing, because the keystroke can't be processed until the render finishes.

This is the closest React gets to the yielding described on the web fundamentals page — it doesn't add a thread, it makes rendering abandonable so the single thread can service urgent work first.

Note it helps with rendering cost, not with a genuinely slow computation. If expensiveFilter takes 400ms of pure JavaScript, that still blocks — that needs a Web Worker or a better algorithm.

Key takeaways
  • A re-render is a function call plus a diff — the DOM commit is the expensive part.
  • A re-render producing identical output costs almost nothing; don't chase render counts.
  • Children re-render because the parent did, not because props changed.
  • Context re-renders every consumer.
  • Index keys cause wrong state, not just slowness — use stable ids.
  • memo compares by reference, so inline objects and arrows defeat it entirely.
  • Memoisation costs something; measure before applying it.
  • useMemo for reference stability is correctness, not optimisation.
  • The React Compiler automates most of this, given rule-following code.
  • Use the profiler's "why did this render?" rather than guessing.
  • Memoisation can't fix a huge DOM — virtualise or page.
  • useTransition makes renders interruptible; it doesn't speed up computation.

Common mistakes

  • Index keys on lists that reorder, filter or have row state.
  • Math.random() or a new object as a key.
  • memo with inline function or object props — no effect.
  • Blanket memoisation without measuring.
  • Wrong dependency arrays in useMemo/useCallback, causing stale values.
  • One large context, re-rendering everything on any change.
  • Unmemoised context values.
  • Rendering thousands of rows instead of virtualising or paging.
  • Expensive work in the render body rather than memoised or moved out.
  • Optimising without the profiler.

Interview questions

Intermediate

Why shouldn't you use array index as a key? 🔥 Must know
How I'd answer

"The usual explanation is that it's slower, and that undersells it — the real problem is incorrect state."

"Keys are how React establishes element identity during reconciliation. Same key means 'this is the same item, update it in place'. Different key means 'different item, unmount the old one and mount a new one'."

"With index keys, identity is tied to position. So if you insert an item at the front, the item that was at index 0 is now at index 1 — but React sees key 0 still exists and concludes the item at position 0 simply changed. It reuses that component instance for a completely different piece of data."

"That matters because a component instance owns its internal state. If each row has a checkbox, an inline edit field, or focus, that state stays with the position rather than following the data. So you tick row two, insert something at the top, and the tick is now against the wrong record."

"That's a data-integrity bug the user can see, and it's silent in testing because it needs a specific sequence of interactions. Uncontrolled inputs are the worst case — the DOM value stays put while the props change around it."

"The fix is a stable identity from the data — item.id. If the data has no id, generating one when the item is created and keeping it is better than falling back to the index."

"Index keys are acceptable in one narrow case: the list is genuinely static — never reordered, filtered, sorted or added to — and the items have no internal state. A fixed set of labels, for instance. But it's a small saving for a real risk, so I'd default to a real key."

"And the one that's actively harmful: key={Math.random()}. A new key every render means React unmounts and remounts every item on every render — destroying all state, losing focus, and doing maximum possible DOM work. I've seen that added deliberately to 'force a refresh', which is solving a state problem with the most expensive tool available."

What they're really checking
  • Do you know it's a correctness issue, not just performance?
  • Can you explain the state-follows-position mechanism?
  • Do you know the narrow case where it's fine?
Likely follow-ups
  • How does React use keys during reconciliation?
  • How can a key be used deliberately to reset state?
  • What if the data genuinely has no unique id?

Advanced

A React page feels sluggish. Walk me through diagnosing it. ⭐ Senior-level
How I'd answer

"I'd resist the instinct to start adding memo, because that's usually wasted work. First I'd establish what kind of slow — slow to load, or slow to interact — since they have unrelated causes."

"For slow to interact, I'd open the React DevTools Profiler, record the interaction, and turn on 'record why each component rendered'. That attributes every render to a cause — state change, specific prop change, context update, or parent render. That turns guesswork into diagnosis."

"Then I'd look for which of four things it is."

"Expensive work in a render body. Sorting or filtering thousands of items on every render. That's a real cost and useMemo is the right answer — this is the case where memoisation genuinely helps."

"Too many DOM nodes. If it's a large table or list, no amount of memoisation helps — browser layout and paint scale with node count independently of React. The fix is virtualisation or server paging. I'd check the Elements panel for the node count, because this is easy to confirm."

"Wide re-renders from context. A context value changing re-renders every consumer regardless of which field they use. A single context holding user, theme and cart means a cart update re-renders everything. Fix by splitting contexts by change frequency and memoising the value object — an unmemoised value={{ a, b }} is a new object every provider render."

"Actual DOM thrash. If the commit phase dominates the profile rather than render, that's real DOM work — which might be a missing key causing unmount/remount of a whole list."

"For slow to load, that's a bundle and network problem: check the bundle with an analyser, verify routes are code-split, look for the usual heavy libraries, and check the network panel for N+1 API calls or oversized payloads."

"Two things I'd be careful about."

"Don't chase re-render counts. A re-render producing identical output costs almost nothing — React diffs, finds no change, touches no DOM. 'This renders 40 times' is only a problem if those renders are doing expensive work. Optimising cheap re-renders adds complexity for no measurable gain."

"Verify the fix. Re-profile after each change. I've seen people add memoisation everywhere, ship it, and never confirm anything improved — and partial memoisation frequently achieves nothing, because a memo with an inline arrow prop just adds a comparison cost while still re-rendering."

"Worth noting the React Compiler in React 19 automates most of this — it inserts memoisation at build time, so manual tuning becomes largely unnecessary. It still requires understanding why renders happen, and most production codebases aren't on it yet."

What they're really checking
  • Do you profile before optimising?
  • Do you know "why did this render?" exists?
  • Do you know memoisation can't fix DOM size?
  • Do you know cheap re-renders aren't worth chasing?
  • Do you verify the fix?
Weak answers
  • Red flag: "wrap everything in memo".
  • Red flag: treating any re-render as a problem.
  • Red flag: no measurement at any point.
Likely follow-ups
  • When is useMemo definitely worth it?
  • How would you split a context?
  • What does useTransition help with, and what doesn't it?
