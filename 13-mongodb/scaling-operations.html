Sharding, Change Streams & Atlas

Sharding is the decision you can't easily take back. Change streams are the feature most people don't know they have.

🔴 Advanced ⭐ Senior-level 💡 Good to know
Quick revision
  • The shard key is the whole decision. Get it wrong and every query hits every shard.
  • A query without the shard key is scatter-gather — broadcast to all shards, results merged.
  • Monotonically increasing keys create a hot shard. All writes land on one.
  • Hashed keys distribute writes but kill range queries. That's the trade.
  • Resharding exists since 5.0 — but it's expensive, not a reason to be casual.
  • Change streams read the oplog and give you a reliable, resumable event feed.
  • skip pagination degrades — and on a sharded cluster it's much worse.

Sharded cluster architecture 🟡 Intermediate

The key consequence of this design

mongos routes a query to specific shards only if it can work out where the data is — which requires the shard key to be in the query.

Without it, the query is broadcast to every shard and the results merged. That's called scatter-gather, and it means adding shards makes things worse, not better.

Choosing the shard key 🔥 Must know

Three properties, all required
  1. High cardinality — enough distinct values to split into many chunks. A shard key with 3 values caps you at 3 chunks.
  2. Even distribution — no single value holding a disproportionate share of the data or the writes.
  3. Present in your queries — otherwise every read is scatter-gather.

The third is the one people forget, and it's the one that determines whether sharding helps at all.

CandidateVerdict
{ _id: 1 } with ObjectId Bad. ObjectIds increase monotonically, so every insert goes to the same chunk — one hot shard
{ createdAt: 1 } Bad for the same reason. All new writes on one shard
{ _id: "hashed" } Perfect write distribution. But every range query and most reads become scatter-gather
{ country: 1 } Bad — low cardinality, and hugely uneven
{ tenantId: 1, createdAt: 1 } Usually good in multi-tenant systems — queries are already tenant-scoped
{ userId: 1, timestamp: 1 } Good for per-user time-series — distributes by user, ranges within one
Senior signal — the compound key resolves the dilemma

The apparent choice is between hashed (writes distribute, reads scatter) and ranged (reads target, writes concentrate on one shard).

A compound key with a high-cardinality prefix gets both. { userId: 1, timestamp: 1 } spreads writes across shards because users hash out evenly, while still allowing a targeted range query for one user's history — because userId identifies the shard and timestamp orders within it.

That's the answer to "how do you shard time-series data without a hot shard?", and it's much stronger than picking one of the two extremes.

The constraint: the prefix must be in your queries. If most reads are cross-user, no shard key saves you — and that's a signal sharding is the wrong tool for that workload.

The monotonic-key hot shard

This is the most common sharding mistake. With { createdAt: 1 } or a default ObjectId _id, every new document has a higher key than the last, so every insert lands in the highest chunk — which lives on one shard.

Result: one shard takes 100% of the write load while the others idle. You've paid for a sharded cluster and got a single-node write path plus network hops.

The balancer then continuously splits and migrates that chunk, so you also get constant migration overhead on the busiest shard. It's actively worse than not sharding.

Targeted vs scatter-gather 🔥 Must know

// TARGETED - mongos routes to one shard
db.order.find({ tenantId: "acme", createdAt: { $gte: from } });

// TARGETED - shard key prefix present
db.order.find({ tenantId: "acme" });

// SCATTER-GATHER - no shard key, broadcast to every shard
db.order.find({ status: "pending" });

// SCATTER-GATHER, and worse - every shard must sort, then mongos merges
db.order.find({ status: "pending" }).sort({ createdAt: -1 }).limit(20);
TargetedScatter-gather
Shards contactedOne (or few)All
LatencySingle-shard latencyThe slowest shard's
Scales with shard countYes — more shards, more throughputNo — more shards is worse
SortingDone on the shardEach shard sorts, then mongos merges
Remember this

Scatter-gather latency is the slowest shard's latency, every time.

With 10 shards, every query waits for whichever one is currently slowest — so you've made your tail latency the maximum of 10 samples instead of one.

That's why "the shard key must be in your queries" isn't a nicety. A cluster where most queries are scatter-gather performs worse than the single replica set it replaced.

Chunks and the balancer 🔴 Advanced

ConceptDetail
Chunk size128 MB default. The balancer splits chunks that exceed it
MigrationMoves a chunk between shards. Uses I/O and network; can be windowed
Jumbo chunkA chunk that cannot be split because all its documents share one shard-key value
Balancing windowRestrict migrations to off-peak hours
Jumbo chunks — the unfixable case

A chunk is split by shard-key value. If a single value has more data than the chunk size — say tenantId: "biggest-customer" holding 400 GB — that chunk cannot be split. There's no boundary to split on.

It's marked jumbo, the balancer stops trying to move it, and that shard is permanently oversized. You can't fix it by adding shards.

This is why cardinality within a shard-key value matters, not just cardinality across values. A compound key gives you finer boundaries: { tenantId: 1, createdAt: 1 } can split within a large tenant, where { tenantId: 1 } alone cannot.

Being able to explain jumbo chunks is a strong signal, because it's the failure that reveals whether someone has actually operated a sharded cluster.

Resharding

Possible since 5.0, still not cheap

reshardCollection rewrites the entire collection with a new shard key. That was previously impossible — the only route was a full manual migration to a new collection.

But it duplicates the collection during the operation, so it needs the disk space and I/O headroom, and it takes as long as it takes on a large dataset. There's also a brief write-blocking period at the end for the cutover.

So it's an escape hatch, not permission to be casual. Choose the shard key as though you can't change it, and treat resharding as the recovery plan rather than the plan.

Change streams ⭐ Senior-level

In simple terms

A change stream is a subscribable feed of changes to a collection, database or the whole cluster. It reads the oplog, so it sees every change regardless of which application made it.

Crucially, it's resumable: each event carries a resume token you can store and restart from.

var options = new ChangeStreamOptions
{
    FullDocument = ChangeStreamFullDocumentOption.UpdateLookup,   // whole doc, not just the delta
    StartAfter   = savedResumeToken                              // pick up where we left off
};

// Filter server-side so we only receive what we care about
var pipeline = new EmptyPipelineDefinition<ChangeStreamDocument<Order>>()
    .Match(c => c.OperationType == ChangeStreamOperationType.Update
             || c.OperationType == ChangeStreamOperationType.Insert);

using var cursor = await orders.WatchAsync(pipeline, options, ct);

await cursor.ForEachAsync(async change =>
{
    await Handle(change.FullDocument);
    await SaveResumeToken(change.ResumeToken);   // AFTER handling, for at-least-once
}, ct);
Use forInstead of
Publishing domain eventsDual-writing to a message broker
Keeping a search index or cache in syncPolling for changed documents
Maintaining a denormalized copyApplication code remembering to update both
Audit trailsManual logging on every write path
Real-time UI updatesClient polling
Senior signal — change streams solve the dual-write problem

The classic dual-write problem: save to the database, then publish an event. If the publish fails, the data changed and nothing downstream knows.

A change stream inverts it. You only write to the database, and the event feed is derived from the oplog — the same durable record the database already committed. There's nothing to keep in sync, because there's only one write.

That's effectively a built-in outbox, and it's genuinely one of MongoDB's better features. It's also how CDC tools integrate with Mongo.

Two things to get right: store the resume token after handling, not before, so a crash replays rather than skips — which makes it at-least-once, so handlers must be idempotent. And filter server-side with a pipeline, or you're streaming every change in the collection to your process and discarding most of it.

Change stream limits

Requires a replica set — they read the oplog, so a standalone node can't serve them. That catches people whose dev environment is standalone.

The resume token expires with the oplog. If a consumer is down longer than the oplog window, its token is gone and it cannot resume — you're into a full resync. So oplog size is effectively your maximum consumer downtime, and it's worth sizing deliberately.

UpdateLookup is a second read. It fetches the current document, so you get the latest version rather than the state at the time of the change — and if the document changed again since, you'll see the newer value. For ordering-sensitive logic, use the change description rather than the looked-up document.

Pagination at scale 🔥 Must know

db.order.find({ tenantId: "acme" })
        .sort({ createdAt: -1 })
        .skip(100000)          // reads and discards 100,000 documents
        .limit(20);
db.order.find({
    tenantId:  "acme",
    $or: [
      { createdAt: { $lt: lastCreatedAt } },
      { createdAt: lastCreatedAt, _id: { $lt: lastId } }   // tiebreaker
    ]
})
.sort({ createdAt: -1, _id: -1 })
.limit(20);
Why skip is worse on a sharded cluster

On a single replica set, skip(100000) reads and discards 100,000 documents — bad but linear.

On a sharded cluster it's worse: mongos cannot know how the skipped documents are distributed, so each shard must return its first 100,020 documents for merging. Ten shards means a million documents transferred to return twenty.

Keyset pagination avoids this entirely, and the tiebreaker on _id is mandatory — without it, documents sharing a timestamp get skipped or duplicated across page boundaries. Same mechanics as SQL keyset pagination.

If you need a total count as well
db.order.aggregate([
  { $match: { tenantId: "acme" } },
  { $facet: {
      page:  [ { $sort: { createdAt: -1 } }, { $limit: 20 } ],
      total: [ { $count: "count" } ]
  }}
]);

$facet gets both in one round trip. But an exact count over a large collection is still a full scan — so for big datasets, prefer an approximate count (estimatedDocumentCount), a capped count ("1000+"), or no total at all.

Two operational settings worth checking

IP access list. An Atlas cluster open to 0.0.0.0/0 — which people set during development and forget — is reachable from anywhere with only the password protecting it. Use a private endpoint or VPC peering for anything real.

Oplog size. It bounds both how far a secondary can lag and still catch up, and how long a change stream consumer can be down and still resume. The default is often too small for a write-heavy workload, and the consequence only appears during an incident.

Monitoring that actually tells you something

Replication lag — rising lag means secondaries can't keep up, which breaks secondary reads and threatens the oplog window.

Cache hit ratio / page faults — the working set no longer fits in memory, which is the most common cause of a cluster suddenly getting slow.

Scanned-to-returned ratio — the equivalent of totalDocsExamined/nReturned across the workload. A rising number means queries are losing index support.

Connection count — a leaked MongoClient per request shows up here first.

Key takeaways
  • The shard key needs high cardinality, even distribution, and presence in your queries.
  • Monotonic keys (ObjectId, createdAt) create a single hot shard.
  • Hashed distributes writes but makes reads scatter-gather.
  • A compound key with a high-cardinality prefix gets both.
  • Scatter-gather latency equals the slowest shard's, so it doesn't scale with shard count.
  • Jumbo chunks can't be split — cardinality within a key value matters too.
  • Resharding exists since 5.0 but is expensive; choose as if it's permanent.
  • Change streams give a resumable event feed and remove the dual-write problem.
  • Save the resume token after handling; handlers must be idempotent.
  • Oplog size bounds both secondary lag tolerance and consumer downtime.
  • skip is much worse when sharded — use keyset with a tiebreaker.

Common mistakes

  • Sharding on ObjectId or a timestamp, creating a hot shard.
  • A shard key absent from most queries, so everything is scatter-gather.
  • Low-cardinality shard keys such as country or status.
  • Not anticipating jumbo chunks from a dominant key value.
  • Sharding before exhausting vertical scale and indexing.
  • Storing the change stream resume token before handling, so a crash skips events.
  • No server-side filter on a change stream.
  • Change streams against a standalone node — they simply don't work.
  • An undersized oplog, so consumers can't resume after downtime.
  • skip-based deep pagination, especially when sharded.
  • Exact counts on large collections for every page load.
  • 0.0.0.0/0 left in the Atlas access list.

Interview questions

Advanced / scenario

Choose a shard key for an events collection: 50 million events/day, queried by user and by time range. ⭐ Senior-level
How I'd answer

"I'd go with { userId: 1, timestamp: 1 }, and I'd explain it by ruling out the obvious alternatives, because each fails in an instructive way."

"{ timestamp: 1 } is the trap. It matches the query pattern, and it's monotonically increasing — so every new event has a higher key than the last and lands in the highest chunk, which lives on one shard. That shard takes 100% of the write load while the others idle, and the balancer continuously splits and migrates that chunk on top of it. At 50 million events a day that's actively worse than not sharding. Same problem with { _id: 1 }, since ObjectId also increases over time."

"{ _id: "hashed" } is the over-correction. Writes distribute perfectly, and now every query is scatter-gather — including 'this user's events last week'. That means every read waits for the slowest of N shards, so tail latency becomes the maximum of N samples and adding shards makes reads worse. You've solved writes by breaking reads."

"The compound key gets both. userId as the prefix has high cardinality and spreads writes across all shards, because concurrent users hash out evenly. And because userId is in the query, mongos can route 'this user's events in this range' to a single shard, where timestamp orders them within the chunk. Targeted read, distributed write."

"The condition for that working is that userId is genuinely in most queries. Given the stated pattern — queried by user and by time — it is. If a lot of queries were cross-user, like 'all events in the last hour', those would still be scatter-gather and I'd want to know how frequent they are before committing."

"Two further things I'd raise."

"Jumbo chunks. If one user is enormously more active than the rest — a system account, or a bot — their events could exceed the chunk size for a single userId value. With a compound key that's survivable, because the chunk can be split on timestamp within that user. With { userId: 1 } alone it couldn't be split at all, would be marked jumbo, and that shard would be permanently oversized. That's a direct argument for the compound key beyond query routing."

"Retention. 50 million a day is 18 billion a year, and event data usually has a finite useful life. I'd want a TTL index for automatic expiry, or better, time-based collections or partitions so old data is dropped rather than deleted — dropping is near-instant, deleting 50 million documents is expensive and churns the cache."

"And I'd question the premise slightly: for pure append-heavy telemetry, a time-series collection (5.0+) is purpose-built for this and handles the bucketing internally. If the events are genuinely metrics rather than domain events, that's likely a better fit than a general-purpose sharded collection. I'd want to know which they are before finalising."

What they're really checking
  • Do you spot the monotonic hot-shard trap?
  • Do you know hashed keys break range queries?
  • Do you reach the compound key and explain why it gets both?
  • Do you consider jumbo chunks?
  • Do you raise retention at that volume?
Weak answers
  • Red flag: { timestamp: 1 } because it matches the queries.
  • Red flag: hashed with no mention of the read cost.
  • Red flag: no retention plan for 18 billion documents a year.
Likely follow-ups
  • What if you also need "all events in the last hour" frequently?
  • How would you reshard if you got it wrong?
  • How does a time-series collection differ internally?
You need to keep a search index in sync with a MongoDB collection. How? ⭐ Senior-level
How I'd answer

"I'd use a change stream, and I'd contrast it with the two approaches people reach for first, because it's clearly better than both."

"Dual write — the application writes to Mongo and then to the search index — has the classic dual-write problem. If the second write fails, the two diverge silently and there's no mechanism to notice or recover. And it puts the responsibility on every code path that writes, so one forgotten path is a permanent inconsistency."

"Polling for changed documents works, but it needs a reliable updatedAt on every write, it misses deletes entirely, and there's a tradeoff between polling frequency and load where neither end is good."

"A change stream avoids both. It reads the oplog — the durable record Mongo already committed — so the event feed is derived from the write rather than being a second write. There's nothing to keep in sync because there's only one write. It sees every change regardless of which application or script made it, and it includes deletes."

"Implementation details that matter:"

"Store the resume token after handling, not before. Each event carries a token; if the consumer crashes, it restarts from the last stored one. Storing it before handling means a crash skips the event permanently. Storing it after means the event may be replayed — so it's at-least-once, and the handler must be idempotent. For a search index that's easy, since indexing the same document twice is naturally idempotent."

"Filter server-side with a $match in the watch pipeline, so I only receive the operation types and fields I care about rather than streaming every change to my process and discarding most of it."

"FullDocument = UpdateLookup so I get the whole document rather than just the delta — a search index needs the full record. Worth knowing that's a second read and returns the current version, so if the document changed again I'll see the newer state. For a search index that's fine, arguably preferable. For ordering-sensitive logic it wouldn't be."

"Batch the writes to the search index rather than one call per event — at any real volume, per-event indexing is the bottleneck, not the change stream."

"The risk I'd plan for explicitly: the resume token expires with the oplog. If the consumer is down longer than the oplog window, the token is unusable and there's no way to resume — I'd need a full rebuild. So I'd size the oplog for the longest realistic outage, alert on consumer lag so I know before it's too late, and have a documented full-reindex procedure. That reindex path is needed anyway for schema changes to the index."

"One alternative worth mentioning: if this is on Atlas, Atlas Search maintains a Lucene index on the collection natively, with no consumer to run. That's less infrastructure and less to go wrong, so I'd check whether it meets the search requirements before building a pipeline to Elasticsearch."

What they're really checking
  • Do you know change streams exist and why they beat dual writes?
  • Do you get the resume-token ordering right?
  • Do you know it's at-least-once and require idempotency?
  • Do you plan for the token expiring?
  • Do you consider the managed option?
Weak answers
  • Red flag: dual write with no consistency mechanism.
  • Red flag: saving the resume token before processing.
  • Red flag: no plan for when the consumer falls behind.
Likely follow-ups
  • How do you handle a full reindex without downtime?
  • What happens if the consumer processes events out of order?
  • How would you run multiple consumer instances?
