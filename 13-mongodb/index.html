MongoDB

The document database you're most likely to meet. The hard part isn't the API — it's unlearning relational modelling habits at the right moments.

🟡 Intermediate ⭐ Senior-level

The mental shift 🔥 Must know

In simple terms

In a relational database you model the data, normalise it, and let the query planner work out how to answer questions.

In MongoDB you model the access pattern. You shape documents so that the queries your application actually makes are single, cheap reads.

The question that drives every schema decision

"What does the application read together?"

Data read together should usually be stored together. That's the whole design philosophy, and it's the opposite instinct to normalisation.

The corollary: you must know your queries before you design the schema. In a relational database you can normalise first and figure out queries later. Here that gets you a document store pretending to be a slow relational database.

Think of it this way

A relational database is a filing system: every fact in exactly one drawer, and you walk between drawers to assemble an answer.

A document database is a set of prepared folders — each one already contains everything needed for a particular job. Faster to use, and if a shared fact changes you have to update several folders.

Senior signal — the honest position

"Schema-less" is the most misleading selling point in this space. There is always a schema — the difference is whether it's declared in the database or implied by your application code.

With MongoDB it's implied, which means the database won't stop a bad write, and after two years of changing requirements a collection can contain four different document shapes. Every read path then needs defensive code.

That flexibility is genuinely valuable during rapid iteration and genuinely expensive in a mature system — which is why schema validation exists and should usually be on.

Being able to say that is worth more than either enthusiasm or dismissal. "It's flexible" and "it's not a real database" are both weak answers.

What changed, and why old objections are outdated

Several common criticisms are years out of date, and knowing that matters:

  • Multi-document ACID transactions exist — replica sets since 4.0, sharded clusters since 4.2.
  • The default write concern is majority since 5.0. The old "it acknowledges writes it hasn't stored" criticism referred to defaults that changed.
  • Schema validation with JSON Schema since 3.6.
  • Joins via $lookup in the aggregation pipeline.

So the real trade-offs today are about modelling and operations, not durability. Content here targets MongoDB 7/8 and the MongoDB.Driver 3.x C# driver.

The .NET side 🟡 Intermediate

// One MongoClient per application. It owns the connection pool.
builder.Services.AddSingleton<IMongoClient>(_ =>
    new MongoClient(builder.Configuration.GetConnectionString("Mongo")));

builder.Services.AddScoped(sp =>
    sp.GetRequiredService<IMongoClient>().GetDatabase("shop"));

// Conventions: register once, at startup, before any mapping happens
var pack = new ConventionPack
{
    new CamelCaseElementNameConvention(),          // C# PascalCase -> JSON camelCase
    new IgnoreExtraElementsConvention(true),       // tolerate unknown fields on read
    new EnumRepresentationConvention(BsonType.String)   // enums as strings, not ints
};
ConventionRegistry.Register("app", pack, _ => true);
DetailWhy it matters
MongoClient as a singletonIt holds the connection pool. Creating one per request exhausts connections — the equivalent of the HttpClient mistake
IgnoreExtraElementsWithout it, a document containing a field your class doesn't have throws on deserialisation. Essential during schema evolution
Enums as stringsSame ordinal trap as EF Core — reorder the enum and existing documents change meaning
Conventions registered at startupClass maps are built once and cached. Registering later has no effect on already-mapped types

The LINQ boundary is the same trap as EF Core

The C# driver translates LINQ to the aggregation pipeline — but only what it can translate. Anything else either throws or, depending on the API surface used, silently pulls documents into memory.

Same discipline as EF Core: know where the boundary is, and log the generated command in development so you can see what's actually being sent.

In the driver that's ClusterConfigurator with a command-started event, or .ToString() on a queryable to see the pipeline.

When would you choose MongoDB over a relational database? 🔥 Must know
How I'd answer

"My default for a business application is still relational, and I'd want a specific reason to move away from it. So I'd frame this as what makes MongoDB the better fit rather than as a general preference."

"The strongest case is data with a natural document shape that's read as a unit. A product with variants, options and category-specific attributes; a CMS page; an order with its lines. In a relational schema that's five tables and a join every time you display it. As a document it's one read, and the shape matches how the application thinks about it."

"The second case is genuinely varying structure. A catalogue where laptops have screen size and RAM while shoes have size and colour. In SQL that's either sparse columns, an EAV table, or a JSON column — and if you're reaching for a JSON column for most of the record, a document database is the honest version of that."

"Third, scale-out as a starting assumption. Sharding is built in rather than something you bolt on."

"Where I'd stay relational: anything with multi-entity invariants — 'total allocations must not exceed the budget' is a constraint the relational engine can enforce and Mongo can't. Anything needing ad-hoc reporting across many entities, because SQL is genuinely better at queries nobody anticipated. And anything where the queries aren't known yet, because normalisation is the more flexible starting point — document modelling requires knowing the access patterns up front."

"I'd also correct a couple of outdated objections, because they come up. MongoDB has had multi-document ACID transactions since 4.0, and 4.2 for sharded clusters. And the default write concern has been majority since 5.0, so the old 'it acknowledges writes it hasn't durably stored' criticism was about defaults that changed. The real trade-offs now are about modelling and operations, not durability."

"The thing I'd be honest about is that 'schema-less' is misleading. There's always a schema — the question is whether the database enforces it or your application implies it. With Mongo it's implied, so nothing stops a bad write, and after two years of changes a collection can hold four document shapes and every read path needs defensive code. That flexibility is valuable while iterating and costly in a mature system, which is why I'd turn on schema validation once the shape settles."

"And practically: polyglot persistence is usually the right answer. Relational for transactional core data, Mongo for the catalogue or the event log. The failure mode is picking one for everything on principle."

What they're really checking
  • Do you have criteria, or a preference?
  • Do you know where document modelling is weak?
  • Are you current on transactions and write concerns?
  • Are you honest about "schema-less"?
Weak answers
  • Red flag: "it's faster" or "it scales better" with no mechanism.
  • Red flag: "it doesn't support transactions" — outdated by years.
  • Red flag: "schema-less means we can move faster" with no acknowledgement of the cost.
Likely follow-ups
  • How would you model an order and its lines?
  • What happens when a document needs to exceed 16 MB?
  • How do you handle schema changes across millions of documents?
