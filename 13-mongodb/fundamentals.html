Documents & Schema Design

This is the page that matters. Almost every MongoDB production problem traces back to a modelling decision.

🟡 Intermediate 🔴 Advanced 🔥 Must know
Quick revision
  • Data read together should be stored together. The one rule everything follows from.
  • Embed for one-to-few, owned, read-as-a-unit data. Reference for one-to-many, shared, or independently-queried data.
  • Unbounded arrays are the number one anti-pattern. Any array that grows without limit is a future outage.
  • 16 MB document limit — a hard ceiling, and if you're near it the model is wrong.
  • Duplication is expected, but you must decide how it stays consistent.
  • Turn on schema validation once the shape settles.
  • Documents growing in place cause moves — size them realistically up front.

Two type traps that cause real bugs

1. decimal silently becomes a string or double. The C# driver does not map decimal to Decimal128 by default. Without [BsonRepresentation(BsonType.Decimal128)] you get a string (unsortable, uncomparable in queries) or a double (imprecise). For money that's a genuine correctness problem, and it's silent.

2. Missing is not null. { } and { status: null } are different documents. A query for status: null matches both, which surprises people; to distinguish, use $exists. It also means an index on a sparse field behaves differently from what you'd expect — worth checking with $exists: true explicitly when it matters.

Embedding vs referencing 🔥 Must know

{
  "_id": ObjectId("..."),
  "orderNumber": "ORD-1041",
  "createdAt": ISODate("2024-06-01T10:22:00Z"),
  "customer": {                      // extended reference: id + the fields we display
    "customerId": ObjectId("..."),
    "name": "A. Patel",
    "email": "a.patel@example.com"
  },
  "lines": [                          // bounded: an order has a few dozen lines at most
    { "sku": "KB-01", "name": "Keyboard", "qty": 1, "unitPrice": NumberDecimal("49.99") },
    { "sku": "MS-02", "name": "Mouse",    "qty": 2, "unitPrice": NumberDecimal("19.50") }
  ],
  "total": NumberDecimal("88.99")     // computed, stored
}
Embed whenReference when
Read together — you almost always want bothRead independently — you often want one without the other
One-to-few, with a known boundOne-to-many or many-to-many, unbounded
The child is owned — meaningless aloneThe child is shared between parents
Updated together, atomicallyUpdated on very different schedules
The child doesn't need its own queriesYou need to query or aggregate children directly
The three-question test
  1. Is it bounded? If the array can grow without limit — embed nothing, reference.
  2. Is it read together? If yes, embed. If you usually want one without the other, reference.
  3. Is it shared? If several parents reference the same child and it changes, reference — or embed only the fields that don't change.

Boundedness comes first, because an unbounded array is the failure that can't be tuned away.

The unbounded array anti-pattern 🔥 Must know

{
  "_id": ObjectId("..."),
  "name": "A. Patel",
  "orders": [ /* every order this customer has ever placed */ ],
  "loginEvents": [ /* every login, forever */ ]
}
What goes wrongWhy
Hits the 16 MB limitThen writes simply fail. Nothing you can tune
Every read loads everythingFetching a customer's name transfers megabytes
Every write rewrites the documentAppending one login rewrites the whole thing — no partial update at storage level
Document movesGrowing past its allocated space means relocating it, and updating every index entry
Index bloatA multikey index has one entry per array element per document
Working set blows upHuge documents evict everything else from cache
Why this is the most damaging mistake

It's invisible in development and testing. Ten test customers with three orders each works perfectly. The problem arrives eighteen months later with your most valuable customer — the one with 40,000 orders — and by then fixing it means migrating live data and rewriting every code path that touches the document.

The rule: if you cannot state an upper bound, don't embed it. Not "it's probably fine", an actual number. "An order has at most a few hundred lines" is a bound. "Customers place a lot of orders" is not.

Design patterns ⭐ Senior-level

Extended reference

// In the order document
"customer": {
  "customerId": ObjectId("..."),      // for fetching the full record
  "name":       "A. Patel",           // duplicated: what we show on the order list
  "email":      "a.patel@example.com"
}
Why it's the most useful pattern

Rendering an order list needs the customer's name. A pure reference means a $lookup or a second query per order — the N+1 problem in a different database.

Copying the two or three fields you actually display makes the list a single read. Keep the ID so you can fetch the authoritative record when you need everything.

Only duplicate fields that rarely change. Name and email, yes. Loyalty tier that updates nightly, no.

You must decide how the copy stays current

A customer changes their name. Every order carrying the old copy is now stale.

Options, and you have to pick one deliberately: accept it (an order arguably should show the name at time of purchase — that's a historical snapshot, not stale data); update on change with a bulk update or a change-stream handler; or refresh on read for the current record only.

The failure is not deciding. That's how you get a system where nobody knows whether a displayed name is current or historical.

The bucket pattern

{
  "_id":      ObjectId("..."),
  "deviceId": "sensor-42",
  "hour":     ISODate("2024-06-01T10:00:00Z"),
  "count":    60,
  "sumValue": NumberDecimal("1284.5"),      // pre-computed
  "minValue": NumberDecimal("18.2"),
  "maxValue": NumberDecimal("24.9"),
  "readings": [
    { "t": ISODate("2024-06-01T10:00:00Z"), "v": 21.4 },
    { "t": ISODate("2024-06-01T10:01:00Z"), "v": 21.6 }
    /* ... up to 60 - BOUNDED by the hour */
  ]
}
Compared to one document per readingBenefit
60× fewer documentsFar less per-document overhead
60× fewer index entriesIndex fits in memory
Pre-computed aggregatesHourly stats need no aggregation at all
Bounded arrayThe time window is the bound — this is the key property

This is how you do time-series data without unbounded arrays. MongoDB 5.0+ also has native time-series collections, which apply the same idea internally — prefer those for new work, and understand bucketing because it's the same reasoning and still needed for non-metric data.

The rest, briefly

PatternProblem it solves
Computed Store the total, average or count rather than recomputing per read. Trades write work for read speed
Subset Embed the most recent 10 comments; keep the rest in another collection. Bounds the array and covers the common read
Outlier Most documents fit the normal shape; a rare few don't. Flag them and handle separately rather than designing for the outlier
Schema versioning A schemaVersion field so code can handle multiple shapes during migration — and you can find un-migrated documents
Polymorphic Different document shapes in one collection with a type discriminator. Fine when they're read together
Approximation Increment a view counter every 10th time by 10. Cuts write load where exactness doesn't matter
Senior signal — subset plus extended reference together

The two patterns compose into the answer for most "one-to-many but I need some of it inline" problems.

A blog post embeds its latest 10 comments (subset — bounded, covers the page view) with each comment carrying the author's name and avatar URL (extended reference — no lookup needed). Full comment history lives in a separate collection, queried only when someone clicks "show all".

One read renders the page. Being able to combine patterns rather than reciting them individually is what distinguishes someone who has designed a real schema.

The 16 MB limit 🟡 Intermediate

Remember this

16 MB is a hard limit, and it's not really the constraint.

Long before you reach it, a large document is already causing problems: every read transfers it all, every write rewrites it all, and it evicts other data from cache.

If a document is approaching even 1 MB, the model is probably wrong. The limit exists to stop you doing something you shouldn't be doing.

If you're near the limitDo this
An unbounded arrayMove it to its own collection with a reference
Time-series growthBucket by time window, or use a time-series collection
Large binary contentObject storage (S3, Blob Storage) and store the URL. Not GridFS unless you need file-like streaming
Genuinely huge single recordsSplit by access pattern — hot fields in one document, cold detail in another

Schema validation ⭐ Senior-level

db.createCollection("order", {
  validator: {
    $jsonSchema: {
      bsonType: "object",
      required: ["orderNumber", "customer", "lines", "total", "createdAt"],
      properties: {
        orderNumber: { bsonType: "string", pattern: "^ORD-[0-9]+$" },
        total:       { bsonType: "decimal", minimum: 0 },
        createdAt:   { bsonType: "date" },
        customer: {
          bsonType: "object",
          required: ["customerId", "name"],
          properties: { customerId: { bsonType: "objectId" } }
        },
        lines: {
          bsonType: "array",
          minItems: 1,
          maxItems: 500,                       // enforce the bound explicitly
          items: {
            bsonType: "object",
            required: ["sku", "qty", "unitPrice"],
            properties: { qty: { bsonType: "int", minimum: 1 } }
          }
        }
      }
    }
  },
  validationLevel: "moderate",     // only validate inserts and valid existing docs
  validationAction: "error"        // "warn" logs instead of rejecting
});
SettingEffect
validationLevel: "strict"All inserts and updates validated
validationLevel: "moderate"Inserts, plus updates to documents that already conform. The migration-friendly option
validationAction: "error"Reject the write
validationAction: "warn"Log it and allow. How you roll this out safely
The rollout sequence

Add the validator with validationAction: "warn" first. Watch the logs for a full business cycle. Fix whatever writes are violating it. Then switch to "error".

Going straight to error on an existing collection breaks whichever code path nobody remembered — a nightly job, an admin tool, a partner integration.

And use moderate rather than strict, so updates to legacy documents that don't conform aren't blocked before you've migrated them.

Senior signal — the timing argument

"Schema flexibility is valuable while you're still discovering the shape, and a liability once you've found it."

So the recommendation is: no validation while prototyping, then add it as the model stabilises. That captures the actual benefit of a document database without accepting the long-term cost of a collection containing four different shapes.

That framing beats both "always validate" and "flexibility is the point", because it puts the decision on a timeline.

Mapping in .NET 🟡 Intermediate

public class Order
{
    [BsonId]
    public ObjectId Id { get; set; }

    [BsonElement("orderNumber")]
    public string OrderNumber { get; set; } = null!;

    [BsonRepresentation(BsonType.Decimal128)]      // REQUIRED for money
    public decimal Total { get; set; }

    [BsonRepresentation(BsonType.String)]          // not the ordinal
    public OrderStatus Status { get; set; }

    [BsonIgnoreIfNull]                              // omit rather than store null
    public string? Notes { get; set; }

    public List<OrderLine> Lines { get; set; } = [];
}
Three mapping decisions with consequences

Decimal128 for money. Without the attribute you get a string or a double. A string can't be compared or summed in a query; a double is imprecise. Both are silent.

Enums as strings. Otherwise the stored value is an ordinal, and reordering the enum changes what existing documents mean — the same trap as EF Core, with no migration to catch it.

IgnoreExtraElements. Set it globally via a convention. Without it, reading a document that has a field your class doesn't throws — which happens constantly during schema evolution and during a rolling deploy, where old code reads documents written by new code.

Key takeaways
  • Model the access pattern, not the data. Store together what's read together.
  • Embed for bounded, owned, read-together data; reference otherwise.
  • Boundedness is the first test — unbounded arrays are the failure you can't tune away.
  • Extended reference avoids lookups; decide how the copies stay current.
  • Bucket time-series data so arrays are bounded by the window.
  • Subset plus extended reference solves most "some of it inline" problems.
  • 16 MB is a hard limit, but 1 MB already means the model is suspect.
  • Add schema validation as the model stabilises; roll out with warn then error.
  • Decimal128 for money, enums as strings, IgnoreExtraElements globally.
  • Missing and null are different; a null query matches both.

Common mistakes

  • Unbounded embedded arrays — the single most damaging modelling error.
  • Normalising as you would in SQL, then needing a $lookup for every read.
  • Designing the schema before knowing the queries.
  • Duplicating volatile fields in an extended reference.
  • Duplicating without deciding how consistency is maintained.
  • One document per sensor reading instead of bucketing.
  • Binary blobs in documents instead of object storage.
  • decimal with no Decimal128 representation.
  • Enums stored as ordinals.
  • No IgnoreExtraElements, so deserialisation throws mid-deploy.
  • No schema validation years after the model settled.
  • Treating missing and null as the same thing.

Interview questions

Intermediate

How would you model a blog with posts, comments and authors? 🔥 Must know
How I'd answer

"I'd start by asking what the read patterns are, because in MongoDB the schema follows from that rather than from the entities. I'd assume: a post page showing the post plus its comments, a homepage listing recent posts, and an author page listing their posts."

"Given that, three collections: post, comment and author."

"Author is referenced, not embedded — an author has many posts, so embedding would duplicate their whole profile everywhere. But I'd use an extended reference: the post stores authorId plus the author's name and avatarUrl. Those are the only author fields the post page displays, and they change rarely. That makes rendering a post or a post list a single read with no lookup — which is the N+1 problem in a different database if you get it wrong."

"Comments are the interesting decision. Fully embedding them is the obvious move and it's the classic mistake, because comments are unbounded. One popular post gets 50,000 comments, and then every read of that post transfers all of them, every new comment rewrites the whole document, and eventually you hit the 16 MB limit and writes just fail. That failure is invisible in testing — ten test posts with three comments each works perfectly."

"So I'd use the subset pattern: embed the most recent 10 or 20 comments in the post for the initial page render, and keep the full set in a comment collection keyed by postId. 'Show all comments' queries that collection with pagination. Each embedded comment carries the commenter's name and avatar — extended reference again — so no lookup is needed."

"That gives one read for the common case, a bounded array, and no ceiling on comment count."

"Computed fields on the post: commentCount, and if there's voting, a score. Counting from another collection on every page view is wasteful when the number is displayed every time."

"Consistency: when a comment is added I update both the subset array and the comment collection, and increment the count. Ideally in a transaction; realistically the count can be eventually consistent with a reconciliation job, because a slightly stale comment count is not a business problem. I'd make that call explicitly rather than by accident."

"Indexes: comment on { postId: 1, createdAt: -1 } for paging, post on { authorId: 1, publishedAt: -1 } for the author page and { publishedAt: -1 } for the homepage."

"The thing I'd flag: if the author's display name changes, every post carrying the copy is stale. For a blog I'd probably just accept that and refresh it with a bulk update when a profile changes — it's infrequent. But it's a decision to make, not something to leave undefined."

What they're really checking
  • Do you ask about read patterns first?
  • Do you catch that comments are unbounded?
  • Do you know the subset and extended-reference patterns?
  • Do you address how duplicated data stays current?
  • Do you mention indexes?
Weak answers
  • Red flag: embedding all comments with no bound.
  • Red flag: three fully-normalised collections needing $lookup on every page.
  • Red flag: not asking what the queries are.
Likely follow-ups
  • How do you keep the embedded subset in sync?
  • How do you paginate 50,000 comments?
  • What if comments need threading?

Advanced / scenario

A collection has documents approaching 16 MB and writes are failing. What do you do? ⭐ Senior-level
How I'd answer

"This is almost always an unbounded array, so first I'd confirm that — find the largest documents with $bsonSize in an aggregation, and see which field accounts for the size."

"Then I'd separate stopping the bleeding from fixing the model, because writes failing is an active incident."

"Immediate: stop appending to the array. Depending on what it is, that might mean writing new entries to a separate collection right away, even before the full migration, so the affected documents stop growing. If the array is something like an event log where old entries aren't needed, trimming with $slice buys time — though I'd only do that if I'm certain the data being dropped isn't needed, and I'd copy it out first."

"The real fix depends on what the array is."

"If it's an unbounded child collection — orders on a customer, comments on a post — it moves to its own collection with a reference back, and I'd apply the subset pattern: keep the most recent N embedded for the common read, full history separate. That preserves the single-read benefit for the normal case without the ceiling."

"If it's time-series data — readings, metrics, events — I'd use the bucket pattern: one document per entity per hour or day, with the array bounded by the time window, plus pre-computed count, sum, min and max on the bucket so range queries don't need to aggregate the raw points. Or a native time-series collection on 5.0+, which does the same thing internally."

"If it's binary content — images, attachments — that shouldn't be in the document at all. Object storage with a URL in the document. GridFS only if I genuinely need file-like chunked streaming."

"The migration itself is the part that needs care, because this is live data."

"I'd add a schemaVersion field, write the application to read both shapes, deploy that first, then migrate documents in batches in the background, then remove the old read path once nothing is left at the old version. That's expand/contract — same reasoning as a zero-downtime schema change, because old and new code run simultaneously during a rolling deploy."

"I'd batch the migration, not run one enormous update — it's resumable that way, and it doesn't saturate the cluster. And the schemaVersion field is what lets me find the un-migrated documents and confirm completion."

"Then prevention, because this recurs otherwise: schema validation with a maxItems on the array, so the database refuses to let it grow unbounded again. Rolled out as warn first to find violating code paths, then error."

"The lesson I'd articulate is that 16 MB wasn't the real problem — long before that, every read was transferring megabytes and every append was rewriting the whole document. A document over about 1 MB already indicates the model is wrong. The limit just makes it visible eventually, which is arguably a feature."

What they're really checking
  • Do you diagnose before acting?
  • Do you separate immediate mitigation from the real fix?
  • Do you know the subset and bucket patterns?
  • Do you plan a live migration that tolerates both shapes?
  • Do you prevent recurrence with validation?
Weak answers
  • Red flag: "split the document" with no migration plan.
  • Red flag: a single bulk migration script on live data.
  • Red flag: no prevention, so it happens again.
Likely follow-ups
  • How do you find the biggest documents?
  • How do you make the migration resumable?
  • What bucket size would you choose, and why?
