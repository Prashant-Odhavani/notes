Transactions, Write & Read Concerns

Where MongoDB asks you to make durability and consistency decisions that a relational database makes for you.

🟡 Intermediate 🔴 Advanced ⭐ Senior-level
Quick revision
  • A replica set is one primary and several secondaries. All writes go to the primary.
  • Single-document operations are always atomic — including updates to nested fields and arrays.
  • Write concern = how many nodes must acknowledge. majority is the default since 5.0.
  • Read concern = how up-to-date and how durable the data you read is.
  • Read preference = which node you read from. Secondaries lag.
  • Transactions exist (4.0 replica sets, 4.2 sharded) but are a design smell if you need them often.
  • Causal consistency via sessions is usually the right fix for read-your-own-writes.

Replica sets 🔥 Must know

In simple terms

A replica set is a group of nodes holding the same data. One primary accepts all writes; secondaries replicate from it by replaying its oplog — a capped collection of every change.

If the primary becomes unreachable, the remaining nodes hold an election and one secondary is promoted.

ConceptDetail
PrimaryThe only node accepting writes. Reads go here by default
SecondaryReplays the oplog. Readable if you ask, and lags behind
OplogCapped collection of idempotent change records. Its size bounds how far behind a secondary can fall and still catch up
ElectionNeeds a majority of voting members. Typically completes in ~10–12 seconds
ArbiterVotes but holds no data. Generally avoid — see below
Odd numbers, and why arbiters are a trap

An election needs a strict majority of voting members, so a 3-node set tolerates one failure and a 4-node set still only tolerates one — the fourth vote adds nothing and adds cost. Always odd.

Arbiters look like a cheap way to make the count odd, and they undermine durability. With Primary–Secondary–Arbiter, a majority write needs 2 of 3 acknowledgements — but the arbiter holds no data, so it can never acknowledge. That means every majority write requires the single secondary. Lose it and writes stall entirely.

Use three data-bearing nodes. That's the answer whenever an interviewer offers you an arbiter.

During an election, writes fail

There is no primary for roughly 10–12 seconds, so writes are rejected and the driver surfaces errors.

Which is why retryable writes exist and are on by default in modern drivers: the driver retries a failed write once after a new primary is elected, using a transaction ID so a duplicate isn't applied. That turns a failover from a burst of user-visible errors into a brief latency spike.

It only covers single-document writes, and it requires the operation to be retryable in the first place — which is why unacknowledged writes can't use it.

Single-document atomicity 🔥 Must know

db.order.updateOne(
  { _id: orderId, status: "pending" },      // condition and update in one operation
  {
    $set:  { status: "paid", paidAt: new Date() },
    $inc:  { version: 1 },
    $push: { events: { type: "payment", at: new Date() } }
  }
);
// Every field change here either all happens or none of it does.
Remember this

A single document is the atomicity boundary.

Everything inside one document — nested objects, arrays, counters — updates atomically. No transaction required.

This is the strongest argument for embedding: if related data lives in one document, you get transactional consistency for free. Which means a good schema removes most of the need for transactions in the first place.

const result = db.inventory.updateOne(
  { sku: sku, stock: { $gte: qty } },        // the check is part of the update
  { $inc: { stock: -qty } }
);

if (result.modifiedCount === 0) throw new Error("Insufficient stock");

Same pattern as the atomic SQL update — putting the condition in the operation removes the window a read-modify-write would leave open. It's the first thing to reach for, before transactions.

Write concern 🔥 Must know

0Nothing — fire and forgetYou don't know if it worked. Can't be retried

// Money: durability over latency
var payments = db.GetCollection<Payment>("payment")
    .WithWriteConcern(WriteConcern.WMajority.With(journal: true));

// Analytics events: throughput over durability
var events = db.GetCollection<Event>("event")
    .WithWriteConcern(new WriteConcern(1));
Senior signal — why majority is what makes a write durable

With w: 1 the primary acknowledges as soon as it has the write. If that primary then fails before replicating, the new primary never saw it — and when the old node rejoins, that write is rolled back. It was acknowledged to your application and then silently disappeared.

w: "majority" means a majority of nodes have it, so any newly-elected primary must already contain it — elections require a majority, and those nodes have the write.

That's the mechanism, and it's why the default changed in 5.0. The old "MongoDB loses writes" criticism was about w: 1 defaults, and it was fair at the time.

journal: true is a separate axis: it waits for the write-ahead log to be flushed to disk, so it survives a process crash rather than just a failover.

The distinction that matters

local can show you a write that later gets rolled back — because it was on the primary but not replicated when that primary failed.

So if you read a value and then do something irreversible based on it — dispatch goods, charge a card, call an external API — readConcern: "majority" is the right choice. Otherwise you can act on data that ends up never having existed.

Reading from secondaries is a correctness decision

Secondaries replay the oplog asynchronously, so they lag — usually milliseconds, sometimes much more under write load or during index builds.

So the classic bug: user creates a document, gets redirected, the read hits a secondary that hasn't replayed it yet, and they get a 404 on the thing they just made. Intermittent, environment-dependent, and miserable to reproduce.

Never set secondaryPreferred globally. Set it per operation, on reads that genuinely tolerate staleness: reports, exports, dashboards, search.

Same problem and same discipline as SQL read replicas — route per query, never per application.

Causal consistency — the better fix

using var session = await client.StartSessionAsync(new ClientSessionOptions
{
    CausalConsistency = true
});

await orders.InsertOneAsync(session, order);

// Even reading from a secondary, this is guaranteed to reflect the insert above.
// The driver passes the operation time; the secondary waits until it has caught up.
var found = await orders.Find(session, o => o.Id == order.Id).FirstOrDefaultAsync();
Senior signal — this is the answer to read-your-own-writes

A causally consistent session tracks the cluster time of your last operation and sends it with subsequent reads. A secondary that hasn't reached that point waits rather than returning stale data.

So you get read-your-own-writes and secondary reads, which the naive "just read from the primary" answer gives up on.

The cost is latency when the secondary is behind — you wait instead of getting wrong data, which is usually the right trade. Knowing this exists is a strong signal, because most people answer the read-your-own-writes question with "read from the primary" and stop there.

Multi-document transactions ⭐ Senior-level

using var session = await client.StartSessionAsync();

await session.WithTransactionAsync(async (s, ct) =>
{
    await accounts.UpdateOneAsync(s,
        a => a.Id == fromId && a.Balance >= amount,
        Builders<Account>.Update.Inc(a => a.Balance, -amount), cancellationToken: ct);

    await accounts.UpdateOneAsync(s,
        a => a.Id == toId,
        Builders<Account>.Update.Inc(a => a.Balance, amount), cancellationToken: ct);

    return true;
}, cancellationToken: ct);
// WithTransactionAsync retries on TransientTransactionError automatically.

Needing transactions often means the schema is wrong

This is the answer interviewers are listening for, and it's genuinely the right framing.

MongoDB gives you atomicity within a document for free. If you frequently need to change two documents atomically, ask whether they should be one document. An order and its lines almost certainly should be — then "add a line and update the total" is one atomic updateOne, not a transaction.

Transactions are a genuine escape hatch for cases where the data legitimately can't be co-located — an account-to-account transfer between two independently-queried accounts is the textbook example, and it's textbook precisely because it's one of the few that doesn't reduce to embedding.

So: use them, don't design around them. A codebase where most writes are transactional is using MongoDB as a slow relational database.

The alternative for cross-document work

Where a transaction doesn't fit — spanning services, or exceeding 60 seconds — the answer is the same as anywhere distributed: a saga with compensating actions, and idempotent operations so retries are safe.

Change streams are how you trigger the next step reliably, since they read the oplog rather than depending on the writer to publish anything.

Optimistic concurrency 🟡 Intermediate

var result = await orders.UpdateOneAsync(
    o => o.Id == id && o.Version == expectedVersion,     // the guard
    Builders<Order>.Update
        .Set(o => o.Status, newStatus)
        .Inc(o => o.Version, 1));

if (result.MatchedCount == 0)
    throw new ConcurrencyException("Modified by another user; reload and retry.");

There's no built-in rowversion equivalent, so you maintain the version field yourself. The pattern is otherwise identical to EF Core's optimistic concurrency, and the same rule applies: what to do on conflict is a domain decision, and a silent retry reintroduces the lost update.

Key takeaways
  • One primary takes all writes; secondaries replay the oplog and lag.
  • Odd number of data-bearing nodes. Avoid arbiters — they can't acknowledge majority writes.
  • Single-document operations are fully atomic, including arrays and nested fields.
  • A good schema removes most of the need for transactions.
  • w: "majority" is what makes a write survive failover; w: 1 can be rolled back.
  • journal: true is a separate axis — surviving a crash, not a failover.
  • readConcern: "majority" before acting irreversibly on a value.
  • Never set secondaryPreferred globally — route per operation.
  • Causally consistent sessions give read-your-own-writes from secondaries.
  • Transactions exist but are slow, time-limited, and usually a schema signal.
  • Optimistic concurrency is a manual version field.

Common mistakes

  • w: 1 for data that matters, losing writes on failover.
  • An arbiter in a three-node set, so majority writes depend on one secondary.
  • Even numbers of voting members.
  • secondaryPreferred set globally, causing read-your-own-writes bugs.
  • Transactions for work that should be one document.
  • Long-running transactions hitting the 60-second limit.
  • No retry on TransientTransactionError — use WithTransaction.
  • Read-modify-write where an atomic conditional update would work.
  • No version field, so concurrent edits silently overwrite.
  • Assuming reads reflect writes without a causal session.
  • Developing against a standalone node, so transactions fail only in production.

Interview questions

Intermediate

What does write concern majority actually guarantee? 🔥 Must know
How I'd answer

"It guarantees the write has been acknowledged by a majority of data-bearing nodes, which means it will survive a failover."

"The mechanism is what makes it interesting. With w: 1, the primary acknowledges as soon as it has the write itself. If that primary then fails before replicating, the surviving nodes hold an election — and the new primary never saw that write. When the old primary rejoins, the write is rolled back. So your application was told the write succeeded, and it silently ceased to exist."

"With majority, a majority of nodes have the write before it's acknowledged. Since an election also requires a majority, any node that can become primary must already contain it. That's why it's durable — the two majorities have to overlap."

"Worth noting this became the default in MongoDB 5.0. The old criticism that 'MongoDB loses writes' was about the w: 1 default, and it was a fair criticism at the time."

"journal: true is a separate and independent axis. That waits for the write-ahead log to be flushed to disk, so the write survives a process crash rather than a failover. Majority plus journal is the belt-and-braces setting for something like a payment."

"There's a trap worth mentioning: arbiters break this. In a Primary–Secondary–Arbiter set, a majority is 2 of 3 — but the arbiter holds no data and can never acknowledge a write. So every majority write depends on the single secondary, and if it goes down, writes stall completely. The answer is three data-bearing nodes."

"On the trade-off: majority costs latency, because you're waiting for a network round trip to another node. So I'd set it per collection rather than globally — majority plus journal for payments and orders, w: 1 for analytics events where throughput matters and losing a few on failover is acceptable. Making that an explicit per-collection decision is the point."

"And there's a read-side counterpart people forget: readConcern: "majority". The default read concern is local, which can return a write that later gets rolled back. So if I'm going to act irreversibly on a value I've read — dispatch goods, charge a card — I want majority on the read too, not just the write."

What they're really checking
  • Do you know the rollback mechanism, not just the definition?
  • Do you know majority and journal are different axes?
  • Do you know the arbiter trap?
  • Do you mention the read-concern counterpart?
Likely follow-ups
  • What happens to the rolled-back write?
  • How long does an election take?
  • What are retryable writes?

Advanced / scenario

You need to transfer money between two accounts. Walk me through it. ⭐ Senior-level
How I'd answer

"This is the case where a MongoDB transaction is genuinely the right answer — and I'd say why, because for most things it isn't."

"MongoDB gives atomicity within a single document for free. So my first question on any 'update two things atomically' problem is whether they should be one document. Here they legitimately shouldn't: two accounts are independent entities, queried and updated separately, and embedding one in the other makes no sense. So this is one of the few textbook cases that doesn't reduce to better modelling."

"So: a multi-document transaction, using session.WithTransactionAsync — which matters because it retries TransientTransactionError automatically, and those will happen under contention. Hand-rolling startTransaction/commitTransaction without retry logic is a common mistake."

"Inside it, the debit must be a conditional update: { _id: from, balance: { $gte: amount } } with $inc: { balance: -amount }, then check modifiedCount. If it's zero, there weren't sufficient funds and I abort. That way the balance check and the decrement are one atomic operation rather than a read followed by a write — no window for a concurrent transfer to slip through."

"Write concern majority with journal: true. This is money: I don't want a transfer acknowledged and then rolled back by a failover, or lost to a process crash."

"Read concern snapshot inside the transaction, so both reads see a consistent point in time."

"Then the parts that matter more than the transaction itself."

"Idempotency. The client may retry after a timeout without knowing whether the first attempt succeeded — the ambiguous-timeout problem. So the transfer needs a client-supplied idempotency key, recorded in a transfer collection with a unique index, inserted inside the same transaction. A duplicate key means this transfer already happened and I return the original result. Without that, a retry moves the money twice, and no amount of transactional correctness prevents it."

"A ledger, not just balances. I'd write an immutable double-entry record of the transfer in the same transaction rather than only mutating two balance fields. That gives auditability, it's how you reconcile when something goes wrong, and it means the balance can be derived and checked rather than trusted. For money that's not optional — and if the balance field is a computed convenience over the ledger, a corrupted balance is recoverable."

"Keep it short. There's a 60-second transaction limit and the whole thing holds locks, so no external calls, no notification sending inside it. Publishing 'transfer completed' goes through a change stream or an outbox after commit."

"One thing I'd raise: if this is the core of the product, I'd question MongoDB for it. A financial ledger with multi-entity invariants — balances must never go negative, debits must equal credits — is what relational databases with constraints are genuinely better at. Mongo transactions work, they're slower than single-document operations, and I'd lose the ability to enforce a cross-document invariant declaratively. If money movement is one feature in a document-shaped system, this design is fine. If it's the whole system, I'd want that conversation."

What they're really checking
  • Do you use a conditional update rather than read-then-write?
  • Do you know WithTransaction handles retries?
  • Do you set write and read concern appropriately for money?
  • Do you raise idempotency — the thing transactions don't solve?
  • Do you suggest a ledger?
  • Are you willing to question the database choice?
Weak answers
  • Red flag: read balance, check in code, then write.
  • Red flag: no retry handling on transient errors.
  • Red flag: default write concern for a financial operation.
  • Red flag: no idempotency, so a client retry double-spends.
Likely follow-ups
  • What if the two accounts are on different shards?
  • How do you reconcile if a balance drifts from the ledger?
  • What happens if the transaction exceeds 60 seconds?
