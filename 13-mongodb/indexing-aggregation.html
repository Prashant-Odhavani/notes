Indexing & Aggregation

Compound index order follows one rule — ESR. Aggregation follows one rule — filter early.

🟡 Intermediate 🔴 Advanced 🔥 Must know
Quick revision
  • ESR: Equality, then Sort, then Range. The compound index rule.
  • Prefix rule applies — an index on {a, b, c} serves queries on a, {a,b}, {a,b,c}.
  • An unindexed sort is a hard failure past 100 MB, not just slow.
  • Multikey for arrays — one index entry per element. Only one array field per index.
  • TTL index deletes expired documents automatically. Genuinely useful.
  • $match and $project first in a pipeline, always.
  • explain("executionStats") — compare nReturned against totalDocsExamined.

The ESR rule 🔥 Must know

In simple terms

Order compound index fields as: Equality first, then Sort, then Range.

It's the same reasoning as SQL composite indexes, with one important difference — sort comes before range, not after.

db.order.find({
    customerId: ObjectId("..."),          // Equality
    status:     "shipped",                // Equality
    total:      { $gte: 100 }             // Range
}).sort({ createdAt: -1 })                // Sort
db.order.createIndex({
    customerId: 1,      // E
    status:     1,      // E
    createdAt: -1,      // S
    total:      1       // R
});
Why sort before range — and why this differs from SQL

A range predicate makes everything after it in the index unordered with respect to the query. So if total came before createdAt, the results within the range wouldn't be in createdAt order and MongoDB would need an in-memory sort.

An in-memory sort isn't just slower here — it has a 100 MB hard limit. Exceed it and the query fails with an error unless allowDiskUse is set.

SQL Server would spill to disk and be slow. MongoDB stops. That's why ESR puts sort before range: avoiding the blocking sort matters more than narrowing the range scan.

Remember this

An unindexed sort is a correctness risk, not just a performance one.

It works in development with 500 documents and fails in production at scale — with an error, not a slowdown. That makes sort support the first thing to check when designing an index.

Multikey — the array index

// Document: { tags: ["postgres", "sql", "indexing"] }
db.article.createIndex({ tags: 1 });      // becomes multikey automatically

db.article.find({ tags: "sql" });         // uses the index
Two multikey limits that surprise people

1. Only one array field per compound index. createIndex({ tags: 1, categories: 1 }) fails if both are arrays — the number of index entries would be the product of both array lengths, which explodes.

2. Multikey indexes can't support a covered query. MongoDB can't reconstruct the original array from index entries, so it always fetches the document. So the "index-only" optimisation is off the table for any query touching an array field.

Also worth knowing: one index entry per array element per document. A document with 1,000 tags contributes 1,000 index entries — which is another reason unbounded arrays are expensive.

TTL indexes

// Delete sessions 24 hours after createdAt
db.session.createIndex({ createdAt: 1 }, { expireAfterSeconds: 86400 });

// Per-document expiry: set expireAfterSeconds: 0 and store the exact expiry time
db.token.createIndex({ expiresAt: 1 }, { expireAfterSeconds: 0 });
// { expiresAt: ISODate("2024-06-01T12:00:00Z") } is deleted at that moment
Why the second form is the useful one

expireAfterSeconds: 0 with an explicit expiresAt field lets each document have its own lifetime. That's how you do sessions with variable duration, idempotency keys with a per-operation TTL, or a cache with different expiry per entry.

The caveat: the background remover runs roughly every 60 seconds, so deletion is approximate. Don't rely on TTL for anything security-sensitive — a token must be validated as expired in code, not merely assumed gone. And on a replica set, deletion happens on the primary and replicates, so secondaries may briefly still return the document.

Partial and conditional-unique indexes

// Index only pending orders - tiny index on a huge collection
db.order.createIndex(
    { createdAt: 1 },
    { partialFilterExpression: { status: "pending" } }
);

// Unique email, but only among non-deleted users
db.user.createIndex(
    { email: 1 },
    { unique: true, partialFilterExpression: { deletedAt: { $exists: false } } }
);
The query must match the filter

MongoDB only uses a partial index when it can prove the query is a subset of the filter expression. So a query with no status predicate won't use the index above, even if every matching document happens to be pending.

Also: unique with a partial filter behaves differently from sparse — prefer partial, it's clearer and more capable. sparse exists mostly for historical reasons.

Reading explain 🔥 Must know

db.order.find({ customerId: ObjectId("..."), status: "shipped" })
        .sort({ createdAt: -1 })
        .explain("executionStats");
FieldWhat to look for
stage: "COLLSCAN"Full collection scan — no usable index
stage: "IXSCAN"Index scan. Good

stage: "SORT"In-memory sort — the index didn't support the sort
nReturnedDocuments returned

totalDocsExaminedDocuments read
executionTimeMillisWall clock
The one number that matters

The ratio of totalDocsExamined to nReturned.

1:1 — ideal. The index found exactly the right documents.

0 docs examined — even better: a covered query, answered from the index alone.

100,000:10 — you're scanning to find ten documents. The index is wrong or missing.

And a SORT stage anywhere means the index doesn't support the sort — fix the index order.

db.order.createIndex({ customerId: 1, status: 1, total: 1 });

db.order.find(
    { customerId: ObjectId("..."), status: "shipped" },
    { _id: 0, total: 1 }              // MUST exclude _id unless it's in the index
);
// totalDocsExamined: 0 - answered entirely from the index
Covered queries need three things

Every field in the query, every field in the projection, and _id explicitly excluded — because _id is returned by default and isn't in your index.

Forgetting _id: 0 is the usual reason a query that should be covered isn't. And as noted above, a multikey index can never produce a covered query.

The aggregation pipeline 🔥 Must know

db.order.aggregate([
  // 1. FILTER FIRST - can use an index, cuts everything downstream
  { $match: { status: "completed",
              createdAt: { $gte: ISODate("2024-01-01") } } },

  // 2. Reduce the document shape early - less to carry through
  { $project: { customerId: 1, total: 1, createdAt: 1 } },

  // 3. Aggregate
  { $group: {
      _id: { customer: "$customerId",
             month: { $dateTrunc: { date: "$createdAt", unit: "month" } } },
      revenue: { $sum: "$total" },
      orders:  { $sum: 1 }
  }},

  // 4. Sort and limit together - MongoDB optimises this into a top-K sort
  { $sort:  { revenue: -1 } },
  { $limit: 10 },

  // 5. Join LAST, on 10 documents rather than a million
  { $lookup: {
      from: "customer", localField: "_id.customer",
      foreignField: "_id", as: "customer"
  }},
  { $unwind: "$customer" },
  { $project: { _id: 0, name: "$customer.name", revenue: 1, orders: 1 } }
]);
StageDoesNote
$matchFilterUse an index — put it first
$project / $setReshape, compute fieldsReduce size early
$groupAggregateBlocking — consumes the whole input
$sortOrderBlocking unless served by an index
$lookupLeft outer joinExpensive — do it late, on few documents
$unwindOne document per array elementMultiplies document count
$facetSeveral pipelines on one inputCount plus page in one round trip
$merge / $outWrite results to a collectionOn-demand materialised views
The rule for pipeline order

Reduce the data as early as possible.

$match first — it's the only stage that can use an index to avoid reading documents at all. Then $project to shrink each document. Aggregate. Sort and limit. Join last, when there are few documents left to join.

A $lookup before $match joins a million documents and then throws away 999,990 of them.

Senior signal — know what the optimiser does for you

MongoDB reorders some stages automatically: it moves $match earlier past $project where it safely can, and it merges $sort followed by $limit into a top-K sort — which only keeps K documents in memory instead of sorting everything.

That last one matters: $sort alone on a large set can hit the 100 MB memory limit, whereas $sort + $limit together often won't.

But it cannot move $match past $group or $unwind, because that would change the result. So a filter that logically applies to the input but is written after a $group stays where you put it. Verify with explain rather than trusting the optimiser to fix your ordering.

Memory limits

LimitDetail
100 MB per blocking stage$sort, $group. Exceeding it errors unless allowDiskUse

allowDiskUse: trueSpills to disk. Default since 6.0 for most stages
The $push trap

$group with $push accumulating all matching documents into an array can exceed the 16 MB output document limit — and allowDiskUse does not help, because that's a document size limit, not a memory limit.

If you need all the documents in a group, either $limit what you push, or restructure so the grouping produces summary values rather than collections.

$lookup — and when not to use it ⭐ Senior-level

The honest position

$lookup is a left outer join, and it works. It is also much less efficient than a relational join — it executes as a per-document lookup against the foreign collection.

So it's fine on a small result set and a bad idea across millions of documents.

ReasonableReconsider the model
After $match/$limit, joining tens of documentsJoining before filtering
Occasional reporting or admin queries$lookup on a hot read path
Ad-hoc analysisTwo or three $lookup stages chained
The design answer

If a $lookup is on a frequently-used read path, that's usually a signal the extended reference pattern should have been applied — copy the two or three fields you need into the document and skip the join entirely.

Always index the foreignField. Without an index it's a collection scan per input document, which is catastrophic and easy to miss because it still returns correct results.

"Frequent $lookup means the schema needs revisiting" is a much better answer than optimising the lookup, because it addresses why it's there.

Key takeaways
  • ESR: Equality, Sort, Range. Sort before range, unlike SQL.
  • An unindexed sort fails at 100 MB rather than merely being slow.
  • Prefix rule applies — one compound index serves several query shapes.
  • One array field per index; multikey can't produce a covered query.
  • TTL with expireAfterSeconds: 0 gives per-document expiry, ±60 seconds.
  • Partial indexes over sparse; combine with unique for conditional uniqueness.
  • In explain, compare totalDocsExamined to nReturned; watch for SORT and COLLSCAN.
  • Covered queries need _id: 0 and every field in the index.
  • $match first, $lookup last.
  • $sort + $limit becomes a top-K sort; $group with $push can blow the 16 MB output limit.
  • Frequent $lookup on a hot path means the schema should change.

Common mistakes

  • Range before sort in a compound index, forcing an in-memory sort.
  • One index per field instead of compound indexes matching real queries.
  • Ignoring a SORT stage in explain until it fails in production.
  • Forgetting _id: 0 and losing a covered query.
  • Two array fields in one index — it just errors.
  • $lookup before $match, joining everything then discarding it.
  • No index on the foreignField of a $lookup.
  • $group with $push exceeding 16 MB.
  • Relying on the optimiser to move $match past $group — it can't.
  • Trusting TTL for security-sensitive expiry instead of validating in code.
  • Never looking at the generated pipeline.

Interview questions

Intermediate

How do you decide the field order in a compound index? 🔥 Must know
How I'd answer

"I use the ESR rule — Equality, Sort, Range."

"So equality predicates first, then whatever the query sorts by, then range predicates. For a query filtering on customerId and status with equality, filtering total by range, and sorting by createdAt, the index would be { customerId: 1, status: 1, createdAt: -1, total: 1 }."

"The reasoning for equality first is the same as in SQL — those fields narrow the scan to a small contiguous region of the index."

"But the interesting part is why sort comes before range here, which is the opposite of the SQL rule. A range predicate makes everything after it in the index unordered relative to the query, so if the range field came first, results wouldn't emerge in sort order and MongoDB would need an in-memory sort."

"And an in-memory sort in MongoDB isn't just slower — it has a 100 MB hard limit, and exceeding it makes the query fail rather than spill to disk. So it's a correctness risk: it works in development with a few hundred documents and errors in production. Avoiding the blocking sort is worth more than narrowing the range scan, which is why ESR orders it that way."

"How I'd verify: explain("executionStats"), and check two things. Is there a SORT stage? If so the index isn't supporting the sort. And what's the ratio of totalDocsExamined to nReturned? Ideally 1:1 — if it's examining 100,000 documents to return 10, the index is wrong."

"Two other things I'd factor in. The prefix rule applies, so {a, b, c} also serves queries on just a or {a, b} — which means one well-designed compound index often replaces three single-field ones, and that's less write overhead. And if a query only needs a couple of fields, extending the index to cover them gives a covered query that examines zero documents — though I'd need to remember _id: 0 in the projection, since _id is returned by default and won't be in the index."

What they're really checking
  • Do you know ESR by name?
  • Do you know why sort precedes range — the 100 MB failure?
  • Do you verify with explain, and know which numbers matter?
  • Bonus: prefix rule and covered queries.
Likely follow-ups
  • What if there are two sort fields?
  • Why can't a multikey index cover a query?
  • How many indexes is too many?

Advanced / scenario

An aggregation over 20 million orders takes 90 seconds. How would you improve it? ⭐ Senior-level
How I'd answer

"I'd start with explain on the pipeline and check whether the first stage is using an index at all, because that decides everything downstream."

"Stage order first. The most common problem is a pipeline that doesn't reduce data early. $match must be first — it's the only stage that can use an index to avoid reading documents. Then $project to shrink each document before carrying it through. And $lookup must be last: a lookup before the match joins 20 million documents and then throws nearly all of them away. Moving a $lookup to after $match and $limit can be the entire fix."

"I'd be careful not to assume the optimiser fixes this. It does move $match earlier past $project where it safely can, and it merges $sort plus $limit into a top-K sort — but it cannot move a $match past $group or $unwind, because that would change the result. So a filter written after a group stays there."

"Then indexes. The $match needs one, following ESR. And if there's a $lookup, the foreignField must be indexed — without it that's a collection scan per input document, which is catastrophic and easy to miss because the results are still correct."

"Then check for blocking stages hitting limits. $sort and $group have a 100 MB working limit; a $group using $push can also exceed the 16 MB output document limit, and allowDiskUse doesn't help there because it's a document size limit, not memory."

"But the bigger question I'd raise is whether this should be computed on demand at all."

"If it's a dashboard that runs on every page load over 20 million documents, no amount of pipeline tuning makes that a good idea — it's re-deriving the same answer repeatedly. Options, roughly in order of how much I'd like them:"

"Pre-aggregate on write. Maintain a rollup collection — daily revenue per customer — updated as orders are created, or by a scheduled job. Then the dashboard reads a few hundred documents instead of scanning 20 million. That's the computed pattern, and it's usually the right answer for a dashboard."

"$merge into a materialised view, refreshed on a schedule. Same idea with less bespoke code — and $merge can update incrementally rather than rebuilding, so it can run frequently."

"Run it on a secondary with an analytics read preference — or an Atlas analytics node — so a heavy report doesn't compete with production traffic. That doesn't make it faster, but it stops it hurting everything else, which is often the actual complaint."

"Bucket the source data, if it's time-series in nature. If orders were bucketed daily with pre-computed sums, the aggregation reads far fewer documents by construction."

"So my likely recommendation would be: fix the obvious pipeline ordering and indexing first because that's cheap and might be enough, then move to a pre-aggregated rollup if it's a repeated dashboard query. And if it's a genuinely ad-hoc analytical workload rather than an application feature, I'd question whether it belongs in the operational database at all — that's what an analytics store is for."

What they're really checking
  • Do you check pipeline ordering before anything else?
  • Do you know what the optimiser can and can't reorder?
  • Do you know $lookup's foreign index requirement?
  • Do you question whether it should be computed on demand?
  • Do you separate "make it faster" from "stop it hurting production"?
Weak answers
  • Red flag: "add allowDiskUse" as the fix.
  • Red flag: only tuning the pipeline, never questioning the requirement.
  • Red flag: assuming the optimiser reorders everything.
Likely follow-ups
  • How would you keep a rollup collection accurate?
  • How does $merge differ from $out?
  • What are the risks of reading from a secondary?
