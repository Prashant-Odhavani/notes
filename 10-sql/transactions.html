Transactions & Concurrency

Where correctness bugs hide. These problems appear only under load, which is exactly why interviewers ask about them.

🟡 Intermediate 🔴 Advanced 🔥 Must know
Quick revision
  • ACID: Atomicity, Consistency, Isolation, Durability. Isolation is the one with dials.
  • Higher isolation = more correctness, less concurrency. That's the whole trade-off.
  • SQL Server defaults to READ COMMITTED using locks — so readers block writers.
  • READ_COMMITTED_SNAPSHOT (RCSI) gives the same isolation without readers blocking. Usually the right setting.
  • NOLOCK is not "no locking, same data". It can return rows twice, miss rows, and read uncommitted data.
  • Deadlock ≠ blocking. Blocking resolves itself; a deadlock is a cycle the server has to kill.
  • Consistent access order prevents most deadlocks.
  • Lost update is the bug read-modify-write causes, and no isolation level below REPEATABLE READ prevents it.

ACID 🔥 Must know

PropertyMeansIn practice
Atomicity All or nothing A crash mid-transaction rolls back on recovery. You never see half a transfer
Consistency Constraints hold at commit Foreign keys, checks and triggers are all satisfied — or the commit fails
Isolation Concurrent transactions don't corrupt each other The configurable one. Everything below is about this
Durability Committed means survives a crash Write-ahead log flushed before commit acknowledges
The one that's often misunderstood

ACID's C is not "the data makes business sense". It means declared database constraints hold.

If your business rule isn't expressed as a constraint, ACID doesn't protect it. That's a good reason to express invariants as constraints rather than only in code.

Durability has a dial too

SQL Server offers delayed durability — commit returns before the log is flushed, batching writes.

Faster, and you can lose the last few committed transactions on a crash. Acceptable for high-volume telemetry; not for payments. Worth knowing that "durable" is a choice, because it shows you understand what the log flush costs.

The four concurrency problems 🔥 Must know

Learn the problems first

Isolation levels are only meaningful as answers to these. If you know the problems, you can derive the levels instead of memorising a grid.

ProblemWhat happensConcrete example
Dirty read You read data another transaction hasn't committed You read a £1000 balance mid-transfer; that transfer rolls back. The value never existed
Non-repeatable read You read the same row twice and get different values A report reads a total, then re-reads it for a subtotal — they disagree, so the report doesn't add up
Phantom read You re-run the same query and new rows appear COUNT(*) returns 10, then 11, inside one transaction
Lost update Two read-modify-writes; one silently overwrites the other Two users each read stock 10, each decrement, each write 9. Two sold, one deducted
Lost update is the one that matters most in application code

It's not in the classic ANSI list, and it's by far the most common real bug — because read-modify-write is what ORMs do. Load an entity, change a property, save.

No isolation level below REPEATABLE READ prevents it, and raising isolation to fix it destroys concurrency. The real fixes are:

  • Optimistic concurrency — a rowversion column, checked on update.
  • Atomic update — SET Stock = Stock - 1 WHERE Stock >= 1, no read at all.
  • Pessimistic lock — UPDLOCK on the read.

Isolation levels 🔥 Must know

LevelDirty readNon-repeatablePhantomMechanism
READ UNCOMMITTED ❌ allowed❌ allowed❌ allowed Takes no shared locks
READ COMMITTED (default) ✅ prevented❌ allowed❌ allowed Shared locks released immediately after reading
REPEATABLE READ ✅✅❌ allowed Shared locks held until commit
SERIALIZABLE ✅✅✅ Range locks — locks rows that don't exist yet
SNAPSHOT ✅✅✅ Row versions in tempdb — no read locks at all
How to remember the ladder

Each level up holds locks longer or over more:

  • READ UNCOMMITTED — no read locks.
  • READ COMMITTED — locks during the read.
  • REPEATABLE READ — locks until commit.
  • SERIALIZABLE — locks the range, so no one can insert into it.

SNAPSHOT sits outside the ladder: it uses versioning instead of locking, which is why it prevents everything without blocking.

Why REPEATABLE READ still allows phantoms

It locks the rows it read. It can't lock rows that don't exist yet.

So another transaction can still INSERT a matching row, and re-running the query returns it. SERIALIZABLE fixes this with range locks — locking the key range itself, blocking inserts into it.

That mechanism explains why SERIALIZABLE is so expensive: it blocks writes to rows that don't exist.

Snapshot isolation and RCSI ⭐ Senior-level

In simple terms

Instead of locking, SQL Server keeps old versions of rows in tempdb. A reader sees the version that was committed when it started, and never waits for a writer.

Readers don't block writers, writers don't block readers. That's the headline.

-- RCSI: makes the DEFAULT level non-blocking. Statement-level consistency.
ALTER DATABASE MyDb SET READ_COMMITTED_SNAPSHOT ON;

-- Enables the explicit SNAPSHOT level. Transaction-level consistency.
ALTER DATABASE MyDb SET ALLOW_SNAPSHOT_ISOLATION ON;
RCSISNAPSHOT
Snapshot takenAt each statementAt transaction start
Code changes neededNone — replaces the default behaviourMust request the level explicitly
Repeatable reads?No — a later statement sees newer dataYes, for the whole transaction
Update conflict errorsNoYes — error 3960, must be handled
Senior signal — recommend RCSI, and name the cost

For most OLTP applications RCSI is a large, cheap win: reporting reads stop blocking writes, and it needs no application changes at all.

But name the costs, because that's what separates a recommendation from a slogan:

  • tempdb load. The version store lives there. Size and monitor it.
  • 14 bytes per row added for versioning, which causes page splits on existing tables the first time rows are updated.
  • A long-running transaction pins versions, so the store grows until it commits. One forgotten open transaction can fill tempdb.
  • Enabling it needs exclusive database access, so it's a maintenance-window change.

This is also, notably, the model PostgreSQL uses by default — its MVCC keeps versions in the table itself, which is why VACUUM exists there.

Snapshot update conflicts

-- Under SNAPSHOT isolation:
-- If another transaction modified a row you're updating after your
-- snapshot was taken, you get:
--   Msg 3960: Snapshot isolation transaction aborted due to update conflict.
-- The transaction is terminated. The application must retry.

This is optimistic concurrency enforced by the engine. It's a feature — but it means SNAPSHOT requires retry logic, whereas RCSI doesn't. That difference is usually why RCSI is the pragmatic choice.

Why NOLOCK is worse than people think 🔥 Must know

The misconception

Most developers believe NOLOCK means "I might read slightly stale data, but it's fast".

That's wrong. NOLOCK (= READ UNCOMMITTED) can return results that were never true at any point in time.

What can happenWhy
Dirty readsYou see uncommitted data that then rolls back
The same row twiceA page split during your scan moves a row ahead of your position, so you read it again
Missing rows entirelyA row moves behind your scan position and is skipped — even though it was committed the whole time
Corrupt valuesReading a wide column mid-update can return a torn value
Query failureError 601: "could not continue scan with NOLOCK due to data movement"
The one that ends the argument

SELECT COUNT(*) FROM Orders WITH (NOLOCK) can return a count that is wrong in either direction — not stale, wrong — because rows can be double-counted or skipped due to page movement during the scan.

For a financial total, that's not "slightly out of date". It's a number that never existed.

If the goal is non-blocking reads, the correct answer is RCSI — same non-blocking behaviour, actual consistency, and no code changes.

Locking basics 🟡 Intermediate

LockTaken byCompatible with
Shared (S)ReadsOther shared locks
Exclusive (X)WritesNothing
Update (U)The read phase of an updateShared only — prevents conversion deadlocks
Intent (IS/IX)Higher levels, signalling intent belowLets the engine check conflicts without scanning every row
Why the Update lock exists

An UPDATE reads first, then writes. If it took a shared lock to read and then upgraded to exclusive, two concurrent updates would both hold shared locks and both wait to upgrade — a guaranteed deadlock.

The U lock is asymmetric: only one transaction can hold it, so the second waits instead of deadlocking.

Lock escalation 🔴 Advanced

Why a big DELETE blocks everything

Around 5,000 locks on one object, SQL Server escalates row locks to a single table lock — because tracking millions of row locks costs more memory than it's worth.

Consequence: DELETE FROM Orders WHERE CreatedUtc < '2020-01-01' removing 2 million rows takes a table lock and blocks the entire table for the duration.

Fix: batch it. Delete 2,000–5,000 rows at a time in a loop, each in its own transaction. Stays below the escalation threshold, keeps the log small, and each batch releases locks quickly.

WHILE 1 = 1
BEGIN
    DELETE TOP (5000) FROM dbo.[Order]
    WHERE CreatedUtc < '2020-01-01';

    IF @@ROWCOUNT < 5000 BREAK;

    WAITFOR DELAY '00:00:00.100';   -- let other work through
END

Deadlocks 🔥 Must know

Blocking vs deadlock

Blocking is a queue at a door. Annoying, but it clears — the person ahead will finish.

Deadlock is two people in a doorway, each refusing to move until the other does. Nobody finishes. Something external has to intervene.

In simple terms

A deadlock is a cycle: A holds a lock B wants, B holds a lock A wants.

SQL Server detects it (roughly every 5 seconds), picks a victim — usually the one with less log work to undo — kills it with error 1205, and rolls it back.

-- Transaction A                    -- Transaction B
BEGIN TRAN                          BEGIN TRAN
UPDATE Account SET .. WHERE Id=1    UPDATE Account SET .. WHERE Id=2
-- holds X on row 1                 -- holds X on row 2
UPDATE Account SET .. WHERE Id=2    UPDATE Account SET .. WHERE Id=1
-- waits for B                      -- waits for A     ← deadlock

Preventing them

TechniqueWhy it works
Consistent access order If everything touches accounts in ascending Id order, a cycle is impossible. The most effective fix
Shorter transactions Less time holding locks = smaller collision window
Right indexes A scan locks far more rows than a seek. Many deadlocks are really missing-index problems
RCSI Eliminates the entire read-versus-write deadlock category
Lower isolation where safe SERIALIZABLE range locks are a major source
UPDLOCK on the initial read Takes the update lock upfront rather than upgrading later
Never-mentioned but important: deadlocks are normal

A busy system will have some. You cannot design them all away.

So retry logic isn't optional — error 1205 is explicitly retryable, because the victim was rolled back cleanly and the conflicting transaction has now finished. Retry with a short random delay (jitter) so both victims don't collide again immediately.

Retrying is only safe if the transaction is retry-safe — one atomic unit with no side effects outside the database. Sending an email inside the transaction breaks that.

Practical concurrency patterns ⭐ Senior-level

1. Atomic update — no read at all

UPDATE Inventory
SET    Stock = Stock - @qty
WHERE  Sku = @sku
  AND  Stock >= @qty;              -- the check is IN the update

IF @@ROWCOUNT = 0
    THROW 50001, 'Insufficient stock', 1;

There's no read-modify-write, so there's no window for a lost update. The condition and the change are one statement. If it applies to your problem, this is the simplest and fastest answer.

2. Optimistic concurrency with rowversion

public class Product
{
    public int Id { get; set; }
    public decimal Price { get; set; }

    [Timestamp]                       // maps to SQL rowversion
    public byte[] RowVersion { get; set; } = default!;
}

// EF adds "AND RowVersion = @original" to the UPDATE.
// Zero rows affected -> someone else changed it first.
try
{
    await db.SaveChangesAsync();
}
catch (DbUpdateConcurrencyException)
{
    // Reload, re-apply, or tell the user their view was stale
}
Remember this

Optimistic = assume no conflict, detect it at write time, handle the failure.

Pessimistic = lock upfront so a conflict can't happen.

Optimistic scales better and is the right default for web applications, because you can't hold a lock across a user thinking about a form for two minutes.

3. Pessimistic locking, when you must

BEGIN TRAN;

SELECT Stock
FROM   Inventory WITH (UPDLOCK, ROWLOCK)   -- lock now, not later
WHERE  Sku = @sku;

-- ... application logic ...

UPDATE Inventory SET Stock = @newStock WHERE Sku = @sku;

COMMIT;
Keep it inside one round trip

A pessimistic lock held across application logic is holding a database lock while your app does work — and if that work includes an HTTP call, you're holding a row lock for the duration of someone else's network latency.

If you need UPDLOCK, do the whole thing in a stored procedure or a single short batch. Never hold a lock across a user interaction.

4. Application locks for singleton work

EXEC sp_getapplock @Resource = 'NightlyReconciliation',
                   @LockMode = 'Exclusive',
                   @LockOwner = 'Session',
                   @LockTimeout = 0;          -- fail fast if held
-- returns 0 acquired, -1 timeout
-- ... work ...
EXEC sp_releaseapplock @Resource = 'NightlyReconciliation', @LockOwner = 'Session';

Useful when several instances of a background service must not run the same job simultaneously. Simpler than a distributed lock if you already have SQL Server — though it's tied to a session, so a connection drop releases it.

Transactions in .NET 🟡 Intermediate

await using var tx = await db.Database.BeginTransactionAsync();
try
{
    db.Orders.Add(order);
    await db.SaveChangesAsync();

    inventory.Stock -= order.Quantity;
    await db.SaveChangesAsync();

    await tx.CommitAsync();
}
catch
{
    await tx.RollbackAsync();      // also happens on dispose
    throw;
}
Three .NET transaction traps

1. Side effects inside the transaction. Sending an email or calling an API inside a transaction means a rollback can't undo it — and a retry does it twice. Use the outbox pattern: write the intent to a table in the same transaction, publish afterwards.

2. Long transactions. SaveChanges inside a loop over 10,000 items, all in one transaction, holds locks for minutes and bloats the log. Batch it.

3. TransactionScope escalating to MSDTC. Touch two different connections inside one scope and it promotes to a distributed transaction. That's slow, needs MSDTC configured, and isn't supported at all on Linux — a nasty surprise during a migration.

Key takeaways
  • Isolation is the configurable part of ACID; the rest you get for free.
  • Learn the four anomalies — the levels then make sense as answers to them.
  • Higher isolation holds locks longer or over more. SERIALIZABLE locks rows that don't exist.
  • SNAPSHOT uses versions, not locks — that's why it doesn't block.
  • RCSI is usually the best default: non-blocking reads, no code changes, tempdb cost.
  • NOLOCK can return rows twice or skip them. Use RCSI instead.
  • Lock escalation at ~5,000 locks turns a big delete into a table lock. Batch it.
  • Deadlocks need consistent access order and retry logic. They're normal.
  • Lost update is the common real bug: prefer atomic updates, then rowversion.
  • Never put side effects or user think-time inside a transaction.

Common mistakes

  • NOLOCK everywhere as a performance fix.
  • Read-modify-write with no version check — silent lost updates.
  • Large DELETE/UPDATE in one transaction, escalating to a table lock.
  • No retry on error 1205. Deadlocks are inevitable, not exceptional.
  • Inconsistent access order across procedures, creating deadlock cycles.
  • Emails or API calls inside a transaction.
  • Transactions spanning user interaction.
  • Enabling SNAPSHOT without handling error 3960.
  • Assuming SERIALIZABLE is just "safer", then wondering about the blocking.
  • Not monitoring tempdb after enabling RCSI.

Interview questions

Basic

Explain ACID. 🔥 Must know
How I'd answer

"Atomicity — all or nothing. A transfer either debits and credits, or does neither. If the server crashes halfway, recovery rolls it back from the log."

"Consistency — declared constraints hold at commit. Worth being precise here: this doesn't mean the data makes business sense, it means foreign keys, checks and unique constraints are satisfied. If a business rule isn't expressed as a constraint, ACID doesn't protect it — which is a good argument for putting invariants in the schema rather than only in code."

"Isolation — concurrent transactions don't corrupt each other. This is the one that's configurable, and it's where all the interesting trade-offs live."

"Durability — once committed, it survives a crash. Implemented with a write-ahead log: the log is flushed to disk before the commit is acknowledged."

"Two things I'd add. First, isolation is the only one with dials, so in practice 'ACID' usually means 'A, C and D are guaranteed, and I is whatever you configured'. Second, even durability has a dial — SQL Server has delayed durability, where commit returns before the log flush. Faster, and you can lose the last few committed transactions on a crash. Fine for telemetry, not for payments."

What they're really checking
  • Can you go beyond the acronym?
  • Do you know Consistency means constraints, not business correctness?
  • Do you know isolation is the configurable one?
Likely follow-ups
  • What's the default isolation level?
  • How does the write-ahead log give you both A and D?

Intermediate

Someone adds NOLOCK to every query to fix blocking. What do you say? 🔥 Must know
How I'd answer

"I'd push back, and I'd be specific about why — because the usual mental model of NOLOCK is wrong."

"Most people think it means 'slightly stale data, but fast'. It doesn't. NOLOCK is READ UNCOMMITTED, and it can return results that were never true at any point in time."

"Concretely: it reads uncommitted data that may roll back, so you can report a value that never existed. It can return the same row twice, and it can skip committed rows entirely — because if a page split moves a row during your scan, the row can end up ahead of or behind your scan position. It can return torn values on wide columns being updated. And it can fail outright with error 601, 'could not continue scan due to data movement'."

"The example that usually ends the discussion: SELECT COUNT(*) WITH (NOLOCK) can be wrong in either direction. Not stale — wrong. For a financial figure that's not a performance optimisation, it's a correctness bug that only shows up under load."

"Then I'd give them what they actually want, because the underlying goal is reasonable — reads shouldn't block writes. The answer is RCSI: ALTER DATABASE ... SET READ_COMMITTED_SNAPSHOT ON. Readers get a consistent point-in-time view from the version store instead of taking shared locks. Non-blocking reads, real consistency, and no application changes at all."

"I'd name the costs so it's an honest recommendation: the version store lives in tempdb so that needs sizing and monitoring, rows gain 14 bytes for versioning which causes some page splits the first time they're updated, a long-running transaction pins versions and grows the store, and enabling it needs exclusive database access so it's a maintenance-window change."

"And I'd look at why there's blocking in the first place. Usually it's missing indexes causing scans that lock far more rows than necessary, or transactions held open too long. Fixing that helps everything; NOLOCK just hides it."

"The one place I'd accept NOLOCK: an ad-hoc diagnostic query on a live system where I need a rough number and must not add blocking. Never in application code."

What they're really checking
  • Do you know NOLOCK does more than dirty reads?
  • Do you know RCSI, and that it needs no code changes?
  • Do you state the costs, and look for the root cause?
Weak answers
  • Red flag: "it's fine for reporting" with no caveat.
  • Red flag: "never use it" with no explanation and no alternative.
Likely follow-ups
  • Difference between RCSI and SNAPSHOT?
  • What's the tempdb impact?
  • How would you find the real cause of the blocking?

Advanced / scenario

Two users buy the last item at the same time and you oversell. How do you fix it? ⭐ Senior-level
How I'd answer

"That's a lost update. Both requests read stock as 1, both decided it was available, both wrote 0. The read and the write weren't atomic, so there was a window between them."

"Worth being clear that no isolation level below REPEATABLE READ prevents this, and raising isolation to fix it would hurt concurrency across the whole application. So the fix belongs in how the operation is written."

"My first choice is an atomic conditional update: UPDATE Inventory SET Stock = Stock - @qty WHERE Sku = @sku AND Stock >= @qty, then check @@ROWCOUNT. If it's zero, there wasn't enough stock and I fail the request."

"This works because there's no read-modify-write at all — the check and the decrement are one statement, and the engine takes an exclusive lock on that row for the duration. There's no window. It's also the fastest option, since there's no extra round trip and no retry."

"Second option: optimistic concurrency with a rowversion column. EF Core adds AND RowVersion = @original to the update, so zero rows affected means someone else got there first and I get a DbUpdateConcurrencyException to handle. I'd use this when the update is more complex than one arithmetic change — when there's real domain logic between the read and the write that I can't express in a single statement."

"Third: pessimistic — SELECT ... WITH (UPDLOCK) then update, in one transaction. This serialises access to that row, so it costs throughput on hot items. I'd only reach for it if the logic genuinely can't be expressed either of the other two ways, and I'd keep the whole thing in one short batch or a stored procedure — never holding that lock across application logic or an HTTP call."

"Two things I'd raise beyond the immediate fix."

"What the business actually wants. For a high-value or high-contention item, serialising on one row is a throughput ceiling. An alternative is reservations: insert a reservation row with a unique constraint and a TTL, so contention moves from an update on one hot row to inserts, and expiry handles abandoned carts. That's also how you support a 'held for 10 minutes' checkout, which the atomic decrement can't."

"Whether preventing it is even the right goal. Airlines deliberately oversell. The question is whether the cost of a rare oversell is lower than the cost of the contention — and whether there's a compensating process. Asking that is often more valuable than the locking discussion, because it changes which solution is correct."

What they're really checking
  • Do you name it as a lost update and explain the window?
  • Do you reach for the atomic update first, rather than locking?
  • Do you know optimistic vs pessimistic and when each fits?
  • Do you consider throughput and the business rule, not just correctness?
Weak answers
  • Red flag: "use SERIALIZABLE" as the whole answer.
  • Red flag: a lock held across application logic or a user session.
  • Red flag: solving it only in application code, so a second writer reintroduces the bug.
Likely follow-ups
  • Now make it work across two services with separate databases.
  • How do you handle expiring reservations?
  • What if stock is cached in Redis?
You're seeing frequent deadlocks in production. Walk me through it. ⭐ Senior-level
How I'd answer

"First I'd separate deadlocks from blocking, because they're often confused and the fixes differ. Blocking is a queue — slow, but it resolves. A deadlock is a cycle that can't resolve, so SQL Server kills one side with error 1205."

"Then I'd get the actual deadlock graphs. They're in the system_health extended events session by default, so the data is already there without turning anything on. The graph tells me the two statements, the resources, and the lock modes — which is nearly always enough to identify the pattern."

"Most deadlocks I've seen fall into three shapes."

"Inconsistent access order. One procedure updates Account then Audit; another updates Audit then Account. Fix: agree an order and apply it everywhere. This is the single most effective change, and it's usually a small one."

"Missing index. This one surprises people. If a query scans instead of seeking, it takes locks on far more rows than it needs — so the collision surface is much larger. Adding the right index converts a scan to a seek and the deadlocks often disappear entirely, without touching transaction logic. Always worth checking, because it's the cheapest fix."

"Lock escalation. A bulk operation crossing the ~5,000-lock threshold escalates to a table lock and collides with everything. Fix: batch it — a few thousand rows per transaction in a loop."

"Alongside that: are transactions longer than they need to be? Anything not part of the atomic unit — reads that could happen before, API calls, logging — should be outside it."

"And I'd check whether RCSI is on. It eliminates the whole read-versus-write deadlock category, since readers use the version store instead of taking shared locks. If those are the deadlocks we're seeing, that's a one-setting fix."

"Then the part people leave out: retry logic is mandatory regardless. A busy system will always have some deadlocks and you can't design them all away. Error 1205 is explicitly retryable — the victim was rolled back cleanly and the other transaction has now completed. I'd retry with a short randomised delay so the two victims don't collide again immediately."

"The caveat on retry: it's only safe if the transaction is genuinely retry-safe — one atomic unit with no side effects outside the database. If it sends an email or calls an API, retrying does that twice. So if I find non-retryable transactions, that's the first thing to fix, before adding retries."

"Finally I'd add monitoring on the deadlock count so we know whether the fixes worked, rather than waiting for the next complaint."

What they're really checking
  • Do you distinguish deadlock from blocking?
  • Do you know deadlock graphs are already being captured?
  • Do you know missing indexes cause deadlocks?
  • Do you treat retry as mandatory, and know when it isn't safe?
Weak answers
  • Red flag: "add NOLOCK".
  • Red flag: trying to eliminate deadlocks entirely with no retry logic.
  • Red flag: guessing without reading a deadlock graph.
Likely follow-ups
  • How does SQL Server choose the victim?
  • Why does an index change fix a deadlock?
  • How do you make a transaction retry-safe?
