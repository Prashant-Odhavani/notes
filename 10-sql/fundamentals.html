Relational Fundamentals

Keys, constraints and normalization. The decisions here are the hardest to change later, because data accumulates under them.

🟢 Beginner 🟡 Intermediate 🔥 Must know
Quick revision
  • Constraints are the cheapest correctness you can buy. The database enforces them regardless of which application, script or admin tool writes.
  • Normalize to 3NF by default, then denormalize deliberately with a measured reason.
  • Surrogate keys (an ID column) for stability; natural keys as a unique constraint alongside.
  • A random GUID as a clustered primary key causes page splits and fragmentation. Use sequential IDs or a sequential GUID.
  • NULL means "unknown", not "empty". It breaks equality comparisons and skews aggregates.
  • The many-to-many junction table is where people forget the composite unique constraint.

Constraints: correctness the app can't bypass 🔥 Must know

In simple terms

A constraint is a rule the database enforces — not your application.

That matters because your application is not the only thing that writes to the database.

Think of it this way

Validating in the application is a bouncer on the front door. Effective — until someone comes in through the fire exit.

A constraint is a lock on the thing itself. The migration script, the admin tool, the support engineer running an UPDATE, and the second application nobody told you about all hit the same lock.

ConstraintGuaranteesAlso gives you
PRIMARY KEYUnique and not nullAn index (clustered by default in SQL Server)
FOREIGN KEYThe referenced row existsPrevents orphans; drives cascade behaviour
UNIQUENo duplicatesAn index — and it's how you make idempotency work
CHECKA value satisfies a predicateThe optimiser can sometimes use it
NOT NULLA value is presentSimpler queries; better plans
DEFAULTA value when none is suppliedLets you add a column without touching every writer
 
CREATE TABLE dbo.OrderLine
(
    Id          int IDENTITY(1,1) NOT NULL,
    OrderId     int               NOT NULL,
    Sku         varchar(50)       NOT NULL,
    Quantity    int               NOT NULL,
    UnitPrice   decimal(19,4)     NOT NULL,

    CONSTRAINT PK_OrderLine PRIMARY KEY (Id),

    -- No orphan lines, ever
    CONSTRAINT FK_OrderLine_Order FOREIGN KEY (OrderId)
        REFERENCES dbo.[Order](Id) ON DELETE CASCADE,

    -- The same SKU can't appear twice on one order
    CONSTRAINT UQ_OrderLine_Order_Sku UNIQUE (OrderId, Sku),

    -- Rules that hold no matter who writes
    CONSTRAINT CK_OrderLine_Quantity  CHECK (Quantity > 0),
    CONSTRAINT CK_OrderLine_UnitPrice CHECK (UnitPrice >= 0)
);

Every one of those has caught a real bug somewhere. The UNIQUE (OrderId, Sku) in particular is how you stop a double-click adding two identical lines — and it works even when the application's check-then-insert has a race window.

Senior signal — constraints as concurrency control

A unique constraint isn't just data hygiene, it's a concurrency primitive.

Application-level "check if it exists, then insert" always has a gap where another request can insert between the two. A unique constraint closes it — one insert wins, the other gets a violation you catch and handle.

That's exactly the mechanism behind idempotency keys and the inbox pattern. Same idea, three contexts.

Cascade behaviour — choose it deliberately

ON DELETEEffectUse when
NO ACTION / RESTRICTBlocks the deleteDefault choice. Forces the caller to be explicit
CASCADEDeletes the children tooTrue ownership — order lines with an order
SET NULLNulls the referenceOptional relationships
Production trap — cascade chains

CASCADE is transitive. Deleting one customer can cascade to orders, then order lines, then shipments — and you've deleted 50,000 rows from a one-row DELETE, inside one transaction, holding locks the whole time.

Worse, it's silent: nothing warns you how much you just removed.

My default is NO ACTION and an explicit delete in the right order, or a soft delete. Use CASCADE only for genuine composition — where the child is meaningless without the parent — and never across more than one level.

Choosing a primary key 🔥 Must know

Surrogate key (int/bigint identity)Natural key (email, ISBN, code)
StabilityNever changesCan change — people change email addresses
Size4–8 bytesOften much larger
MeaningNone — that's the pointMeaningful, so it leaks business rules into keys
JoinsFast and narrowWider; slower to index
Remember this

Use a surrogate primary key and add the natural key as a unique constraint.

You get stable joins and the business rule enforced. Choosing one or the other is a false dilemma.

The GUID problem 🔴 Advanced

Why random GUIDs hurt as clustered keys

In SQL Server, the clustered index is the table — rows are stored in key order.

A random GUID inserts into the middle of that order. When the target page is full, SQL Server splits it: allocates a new page and moves half the rows. Do that constantly and you get fragmentation, wasted space, and far more I/O.

Key choiceInsert patternConsequence
int IDENTITYAlways at the endNo splits. Compact. Fastest
NEWID() (random GUID)Random positionConstant page splits, heavy fragmentation
NEWSEQUENTIALID()Mostly at the endGood — but restarts on reboot, so not globally monotonic
Sequential GUID (e.g. GUID v7)Mostly at the endGood, and client-generatable

GUIDs have real advantages: the client can generate the ID before a round trip, they don't leak row counts, and they're safe to merge across databases. So the answer isn't "never use GUIDs".

CREATE TABLE dbo.[Order]
(
    Id          uniqueidentifier NOT NULL,   -- the public, client-generatable key
    OrderNumber bigint IDENTITY  NOT NULL,   -- sequential, for physical ordering
    CreatedUtc  datetime2(3)     NOT NULL,

    -- Unique but NON-clustered: no page splits from random inserts
    CONSTRAINT PK_Order PRIMARY KEY NONCLUSTERED (Id)
);

-- Cluster on something that increases monotonically
CREATE CLUSTERED INDEX IX_Order_OrderNumber ON dbo.[Order](OrderNumber);
The key insight

Primary key and clustered index are separate decisions. SQL Server makes the PK clustered by default, but you can override it.

So you can keep a GUID as the logical identity while clustering on something sequential. That's how you get GUID benefits without the fragmentation — and knowing they're separable is the senior-level part of this answer.

Normalization 🔥 Must know

In simple terms

Normalization means storing each fact in exactly one place.

If a value appears twice, the two copies can disagree — and eventually they will.

The three that matter

CREATE TABLE Orders
(
    OrderId       int,
    CustomerName  varchar(100),      -- repeated on every order
    CustomerEmail varchar(200),      -- repeated, and can disagree
    ProductSkus   varchar(500),      -- 'SKU-1,SKU-2,SKU-3'  ← not atomic
    Total         decimal(19,4)
);
FormRuleWhat it prevents
1NF Every column holds a single atomic value; no repeating groups The comma-separated SKU list. You can't index, join or constrain it
2NF 1NF, plus every non-key column depends on the whole key Partial dependencies in composite-key tables
3NF 2NF, plus no non-key column depends on another non-key column CustomerName depending on customer, not on order

The concrete problems with that table:

  • Update anomaly. A customer changes email — you must update every order they ever placed, and if one UPDATE misses a row, the data now disagrees with itself.
  • Insert anomaly. You can't record a customer who hasn't ordered yet.
  • Delete anomaly. Delete their last order and you lose the customer entirely.
  • Unqueryable. "Which orders contain SKU-2?" needs a string search that can't use an index — and matches SKU-20 too.
CREATE TABLE dbo.Customer
(
    Id    int IDENTITY PRIMARY KEY,
    Name  varchar(100) NOT NULL,
    Email varchar(200) NOT NULL,
    CONSTRAINT UQ_Customer_Email UNIQUE (Email)
);

CREATE TABLE dbo.[Order]
(
    Id         int IDENTITY PRIMARY KEY,
    CustomerId int NOT NULL REFERENCES dbo.Customer(Id),
    CreatedUtc datetime2(3) NOT NULL
);

CREATE TABLE dbo.OrderLine
(
    Id        int IDENTITY PRIMARY KEY,
    OrderId   int NOT NULL REFERENCES dbo.[Order](Id) ON DELETE CASCADE,
    Sku       varchar(50) NOT NULL,
    Quantity  int NOT NULL CHECK (Quantity > 0),
    UnitPrice decimal(19,4) NOT NULL,
    CONSTRAINT UQ_OrderLine_Order_Sku UNIQUE (OrderId, Sku)
);
How to remember 3NF

Every non-key column must depend on the key, the whole key, and nothing but the key.

When to denormalize ⭐ Senior-level

In simple terms

Denormalization means deliberately duplicating data to make reads faster.

You're trading write complexity and a risk of inconsistency for read speed. That trade needs a reason.

CaseWhy it's legitimate
Historical snapshot Copying the price and address onto an order isn't duplication — an invoice must show what was charged then, not today's price. This is the most defensible case
Expensive aggregate A cached OrderCount on a customer, when counting live is measurably too slow
Reporting / read model A flattened table optimised for queries, kept separate from the write model — the CQRS approach
Avoiding a cross-service join In a distributed system you may have to copy data because you can't join across services
Senior signal — the snapshot distinction

Storing the unit price on an order line looks like denormalization and isn't. The product's current price and the price this customer paid are two different facts.

Joining to Product.Price to display an old invoice is a genuine bug — the invoice total would change when someone edits the product. I've seen that ship.

Being able to make that distinction is worth more than reciting the normal forms.

If you denormalize, decide how it stays consistent

A cached count or total will drift. Pick a mechanism and write it down:

  • Same transaction — always correct, adds write contention on the parent row.
  • Trigger — automatic, but invisible to developers reading the app code.
  • Async update — cheap writes, briefly stale.
  • Periodic reconciliation — necessary regardless, because the others will drift.

The mistake is denormalizing and never deciding — then discovering the count has been wrong for eight months.

NULL 🟡 Intermediate

In simple terms

NULL means unknown, not zero and not empty string.

Which is why comparing to it doesn't work the way you'd expect.

SELECT * FROM Customer WHERE MiddleName = NULL;      -- returns NOTHING, ever
SELECT * FROM Customer WHERE MiddleName IS NULL;     -- correct

-- NULL propagates through arithmetic and concatenation
SELECT 100 + NULL;                                   -- NULL
SELECT 'Hello ' + NULL;                              -- NULL

-- Aggregates SKIP nulls - which changes the answer
SELECT COUNT(*)        FROM Customer;                -- 1000 (all rows)
SELECT COUNT(Phone)    FROM Customer;                -- 640  (non-null only)
SELECT AVG(Discount)   FROM [Order];                 -- average of non-nulls,
                                                     -- NOT (sum / row count)
Production trap — NOT IN with nulls

If the subquery returns even one NULL, NOT IN returns no rows at all:

-- Returns nothing if ANY CustomerId in Order is NULL
SELECT * FROM Customer
WHERE Id NOT IN (SELECT CustomerId FROM [Order]);
SELECT * FROM Customer c
WHERE NOT EXISTS (SELECT 1 FROM [Order] o WHERE o.CustomerId = c.Id);

The logic is that x NOT IN (1, NULL) means x <> 1 AND x <> NULL, and the second comparison is unknown — so the whole predicate can never be true. It returns an empty result with no error, which is why it survives testing on data that happens to have no nulls.

Prefer NOT EXISTS as a habit.

Modelling relationships 🟢 Beginner

RelationshipImplementation
One-to-manyForeign key on the "many" side. The common case
Many-to-manyA junction table with a foreign key to each side
One-to-oneShared primary key, or a unique foreign key
Self-referencingA nullable foreign key to the same table (manager, parent category)
 
CREATE TABLE dbo.ProductCategory
(
    ProductId  int NOT NULL REFERENCES dbo.Product(Id)  ON DELETE CASCADE,
    CategoryId int NOT NULL REFERENCES dbo.Category(Id) ON DELETE CASCADE,

    -- The composite PK is what prevents duplicate pairs.
    -- Without it, the same product can be added to a category twice.
    CONSTRAINT PK_ProductCategory PRIMARY KEY (ProductId, CategoryId)
);

-- The PK indexes (ProductId, CategoryId). Queries filtering by CategoryId
-- alone can't use it efficiently, so add the reverse index.
CREATE INDEX IX_ProductCategory_Category ON dbo.ProductCategory(CategoryId, ProductId);

Both details matter. The composite primary key enforces uniqueness; the reverse index makes "which products are in this category?" fast. Column order in a composite index is covered on the indexing page.

Choosing types 🟡 Intermediate

ForUseNot
Moneydecimal(19,4)float/real — can't represent 0.1 exactly
Timestampsdatetime2, stored UTCdatetime (less precise), local time
Dates onlydateA datetime with a zero time you must remember to strip

Flagsbitvarchar(1) holding 'Y'/'N'
Enumstinyint with explicit values, or varcharAn implicit ordinal you later reorder
Two type mistakes with real consequences

Oversized strings. nvarchar(4000) for a country code isn't just wasteful. SQL Server estimates memory grants from declared size, so oversized columns cause excessive memory reservations — and a query that spills to disk because of a bad grant is dramatically slower.

Storing local time. Store UTC and convert at the edges. Local time breaks across daylight-saving transitions — an hour that occurs twice, and an hour that doesn't exist — and it's almost impossible to fix retroactively because you can't tell which offset each row used.

Key takeaways
  • Constraints are enforced regardless of who writes. They're the cheapest correctness available.
  • A unique constraint is also a concurrency primitive — it closes check-then-insert races.
  • Default to NO ACTION; CASCADE chains delete more than you expect.
  • Surrogate PK plus a unique constraint on the natural key. Not either/or.
  • PK and clustered index are separate decisions — that's how you use GUIDs safely.
  • Normalize to 3NF; denormalize with a measured reason and a stated consistency mechanism.
  • Historical snapshots aren't denormalization — they're a different fact.
  • NULL is unknown. Use IS NULL, and prefer NOT EXISTS over NOT IN.
  • decimal for money, datetime2 in UTC, realistic string lengths.

Common mistakes

  • No foreign keys "for performance" — you get orphans and the optimiser loses information it could have used.
  • Random GUID as a clustered PK, causing constant page splits.
  • Comma-separated values in a column — unindexable, unjoinable, unconstrained.
  • Joining to current product price to display a historical invoice.
  • = NULL instead of IS NULL.
  • NOT IN with a nullable subquery, silently returning nothing.
  • float for money.
  • Local time in the database.
  • Junction table with no composite key, allowing duplicate pairs.
  • Denormalized counts with no reconciliation, drifting silently.

Interview questions

Basic

What is normalization, and would you always normalize? 🔥 Must know
How I'd answer

"Normalization is organising data so each fact lives in exactly one place. The practical formulation I use is that every non-key column must depend on the key, the whole key, and nothing but the key — that gets you to third normal form, which is where I'd default."

"The reason isn't tidiness, it's the anomalies. If a customer's email is copied onto every order, then changing it means updating every one of those rows — and if one UPDATE misses a row, your data now contradicts itself. Same with inserts: you can't record a customer who hasn't ordered yet. And deletes: removing their last order loses the customer."

"So I'd normalize to 3NF by default and denormalize deliberately, with a measured reason."

"Legitimate reasons: an expensive aggregate where counting live is genuinely too slow, a separate read model for reporting, or in a distributed system where you can't join across services so you have to copy data."

"The distinction I'd make though — and people get this wrong — is that historical snapshots aren't denormalization. Storing the unit price on an order line looks like duplication, but the product's current price and the price this customer paid are two different facts. Joining to the product table to display an old invoice is a genuine bug: the total would change when someone edits the product."

"And if I do denormalize, I'd decide upfront how it stays consistent — same transaction, trigger, async update — plus a reconciliation job, because it will drift. The failure I've seen is denormalizing and never deciding, then finding the cached count has been wrong for months."

What they're really checking
  • Can you state the rule usefully rather than reciting 1NF/2NF/3NF definitions?
  • Do you know the anomalies it prevents?
  • Do you know the snapshot distinction? That's the senior part.
Likely follow-ups
  • Give me an example where you'd denormalize.
  • How do you keep a denormalized count accurate?
  • What's the downside of too many joins?

Intermediate

Would you use a GUID or an int for a primary key? ⭐ Senior-level
How I'd answer

"It depends on whether I need client-side generation and distributed uniqueness, and my answer is usually that the trade-off is avoidable — because the primary key and the clustered index are separate decisions."

"The problem with GUIDs isn't the type, it's random insert position when the GUID is the clustered key. In SQL Server the clustered index is the table, so rows are stored in key order. A random GUID inserts into the middle. When that page is full, SQL Server splits it — allocates a new page and moves half the rows. Constant inserts means constant splits, so you get heavy fragmentation, wasted space and much more I/O."

"An int IDENTITY always appends, so there are no splits, and it's 4 bytes instead of 16 — which matters because every non-clustered index carries the clustering key."

"But GUIDs have real advantages. The client can generate the ID before a round trip, which is useful for offline-capable apps and for building an object graph before saving. They don't leak row counts. And they merge safely across databases."

"So the answer I'd usually give is: keep the GUID as the primary key but make it non-clustered, and cluster on something monotonic — an identity column or a creation timestamp. You get the logical benefits without the fragmentation."

"If I do need a GUID as the clustered key, I'd use a sequential one — NEWSEQUENTIALID() server-side, or a GUID v7 style value client-side. Worth knowing that NEWSEQUENTIALID restarts after a reboot, so it's mostly-sequential rather than globally monotonic."

What they're really checking
  • Do you know why random GUIDs are a problem — page splits, specifically?
  • Do you know PK and clustered index are separable? That's the discriminating answer.
  • Do you know non-clustered indexes carry the clustering key?
Weak answers
  • Red flag: "GUIDs are slower" with no mechanism.
  • Red flag: "always use int" with no acknowledgement of distributed cases.
Likely follow-ups
  • What's a page split, exactly?
  • Why does clustering key width affect every other index?
  • How does this differ in PostgreSQL?
Why not just enforce all your rules in application code?
How I'd answer

"Because the application isn't the only thing that writes to the database. There's the migration script, the admin tool, the support engineer running an UPDATE at 2am, the reporting job, and eventually a second application nobody told you about."

"Application validation is a bouncer on the front door. A constraint is a lock on the thing itself — it holds regardless of the route in."

"There's a second reason that's less obvious: constraints give the query optimiser information. A NOT NULL column, a foreign key, a unique constraint — these let it eliminate joins, choose better plans and make better cardinality estimates. Dropping foreign keys 'for performance' often makes queries slower, not faster."

"And a unique constraint is genuinely a concurrency primitive, not just data hygiene. Application-level check-then-insert always has a race window where two requests both find nothing and both insert. A unique constraint closes it — one wins, the other gets a violation you catch. That's the mechanism behind idempotency keys and the inbox pattern."

"I'd still validate in the application, for a good user experience — you want a clear field-level error, not a constraint violation surfaced as a 500. But that's for UX. The constraint is for correctness, and you want both."

"The one place I'd push back on myself: very complex cross-row business rules usually don't belong in CHECK constraints or triggers, because they become invisible logic that's hard to test and debug. Those belong in the domain model. Constraints are for invariants that are simple and absolute."

What they're really checking
  • Do you know the app isn't the only writer?
  • Do you know constraints help the optimiser?
  • Do you know where the boundary is — what shouldn't be a constraint?
Likely follow-ups
  • How do you surface a constraint violation as a friendly error?
  • When would you use a trigger?
  • How do you add a NOT NULL column to a table with existing rows?
