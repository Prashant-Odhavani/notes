Query Performance & Execution Plans

A repeatable workflow beats knowing tricks. Interviewers ask this to find out whether you diagnose or guess.

🟡 Intermediate 🔴 Advanced 🔥 Must know
Quick revision
  • Measure, don't guess. Query Store or the DMVs tell you which query is actually the problem.
  • Estimated vs actual rows is the single most useful number in a plan. A big gap explains almost every bad plan choice.
  • Bad estimate → wrong join type and wrong memory grant → spills to disk. That's the chain.
  • Parameter sniffing: same query, wildly different performance depending on the parameter value.
  • Get the actual plan, not the estimated one. Only the actual plan has real row counts.
  • Wait types tell you what the server is waiting on — CPU, I/O, locks, memory.
  • Fix the cause, not the symptom. A hint that papers over a bad estimate breaks later.

The tuning workflow 🔥 Must know

In simple terms

Almost every real tuning task follows the same five steps. Having them in order is worth more than knowing a dozen individual fixes.

  1. Find the actual problem query. Not the one someone complained about — the one consuming the resources. Query Store or DMVs.
  2. Get the actual execution plan with real row counts.
  3. Compare estimated vs actual rows at each operator. Find where they diverge.
  4. Identify the cause — statistics, SARGability, missing index, fan-out, parameter sniffing.
  5. Fix and re-measure. One change at a time, so you know what worked.
Step 1 is the one people skip

Developers tune the query they were told about. That's often not the expensive one.

A query taking 5 seconds and running twice a day costs 10 seconds. A query taking 80ms and running 40,000 times an hour costs nearly an hour of CPU. The second one is the problem, and nobody is complaining about it.

Sort by total resource consumption, not duration. That reframing alone is a good senior signal.

Finding the expensive queries 🟡 Intermediate

SELECT TOP 20
    qs.execution_count,
    qs.total_worker_time / 1000    AS total_cpu_ms,
    qs.total_worker_time / qs.execution_count / 1000 AS avg_cpu_ms,
    qs.total_logical_reads / qs.execution_count      AS avg_reads,
    SUBSTRING(st.text, (qs.statement_start_offset/2) + 1,
        ((CASE qs.statement_end_offset WHEN -1 THEN DATALENGTH(st.text)
          ELSE qs.statement_end_offset END - qs.statement_start_offset)/2) + 1) AS stmt
FROM sys.dm_exec_query_stats qs
CROSS APPLY sys.dm_exec_sql_text(qs.sql_handle) st
ORDER BY qs.total_worker_time DESC;      -- TOTAL, not average
Query Store is better — turn it on

The DMVs above only show what's currently cached, and the cache clears on restart, on memory pressure, and when statistics change.

Query Store persists query performance history in the database itself, with plan changes over time. That's what lets you answer "this got slow last Tuesday — what changed?", which the plan cache can't.

It's on by default in Azure SQL and from SQL Server 2022. On older versions, enabling it is one of the highest-value things you can do to a production database.

Reading an execution plan 🔥 Must know

Plan typeContainsUse for
Estimated (Ctrl+L)Only the optimiser's guessesQuick check without running an expensive query
Actual (Ctrl+M)Estimated and real row counts, spill warnings, actual time per operatorReal diagnosis. Always prefer this
The three things to look at, in order
  1. Estimated vs actual rows. A gap over ~10× is your prime suspect.
  2. Warnings on operators — implicit conversion, spills, missing index, no join predicate. Yellow triangles are free diagnosis.
  3. The fattest arrow. Arrow thickness is row count. A thick arrow early means you're moving far more data than the result needs.
Ignore the operator cost percentages

The percentages in a plan are derived from the estimates. If the estimate is wrong, the percentages are wrong too — and the operator showing "2%" can be the one taking all the time.

In an actual plan, use actual elapsed time and actual rows per operator instead. This trips up a lot of people who learned to "look for the high-percentage operator".

Join operators, in one line each
  • Nested Loops — good when the outer input is small and the inner side has an index. Terrible when the outer input turns out to be large.
  • Hash Match — good for large unsorted inputs. Needs memory.
  • Merge Join — cheapest, but requires both inputs already sorted on the join key.

The optimiser picks based on estimated row counts. So a bad estimate means the wrong join — which is why estimates matter more than any individual operator.

Bad estimates: the root of most bad plans ⭐ Senior-level

Think of it this way

You tell a caterer to expect 20 guests. They set 20 places and cook 20 meals.

2,000 people arrive.

Nothing about the plan was unreasonable — it was built for the wrong number. That's what a bad cardinality estimate does, and why the failure is so disproportionate.

Consequence of a low estimateEffect
Nested loops chosenMillions of iterations instead of one hash build
Memory grant sized too smallSort or hash spills to tempdb — often the biggest single factor
Serial plan chosenOne core doing work that could be parallelised
Wrong index chosenSeek plus a million key lookups instead of a scan

The local-variable trap

A parameter gets its actual value sniffed at compile time, so the optimiser can use the histogram.

A local variable has no value at compile time, so SQL Server falls back to a fixed guess — 30% of the table for an inequality, or the density for equality.

That means moving a parameter into a local variable "for clarity" can change the plan dramatically. It's also occasionally used deliberately as a poor man's OPTIMIZE FOR UNKNOWN — which is worth knowing, because you'll see it in old code and wonder why.

Parameter sniffing 🔥 Must know

In simple terms

SQL Server compiles a plan using the first parameter value it sees, then reuses that plan for every later call.

If parameter values imply very different amounts of data, one plan can't be good for all of them.

Think of it this way

You plan a route for a bicycle. It's a great route — narrow lanes, short cuts.

Then you reuse that same route for a lorry.

Nothing was wrong with the plan. It was made for a different shape of problem.

CREATE PROCEDURE dbo.usp_OrdersByCountry @country char(2)
AS
SELECT * FROM [Order] WHERE Country = @country;

EXEC dbo.usp_OrdersByCountry 'LU';   -- 200 rows      -> nested loops + seeks. Good.
EXEC dbo.usp_OrdersByCountry 'US';   -- 8 million rows -> SAME plan. 8M seeks + lookups.
The symptom that identifies it

The same query is sometimes fast and sometimes slow, with no code change.

Often it goes bad after a restart, a failover, or a statistics update — because that's when the plan is recompiled, possibly with an unrepresentative first parameter.

And the classic tell: it's fast when I run the same SQL in SSMS but slow from the app — because SSMS compiled a fresh plan with your parameter, while the app is reusing the cached one.

FixCostUse when
OPTION (RECOMPILE)Compiles every execution — CPU per call, and no plan reuseInfrequent queries with very skewed parameters. Usually the simplest correct answer
OPTIMIZE FOR (@p = 'US')Always plans for that valueYou know the dominant case
OPTIMIZE FOR UNKNOWNUses average density, ignores the actual valueYou want consistent mediocre rather than sometimes-terrible

Senior signal — the honest ranking

Consistent-mediocre beats occasionally-catastrophic. An 800ms query every time is usually better for a system than 50ms most of the time and 90 seconds sometimes, because the 90-second case is what exhausts the thread pool and takes the site down.

But I'd check the boring causes first. Sometimes the "parameter sniffing problem" is a missing index — with the right index both plans are fast and the sniffing stops mattering. Reaching for hints before checking indexes fixes the symptom and leaves the cause.

Query Store plan forcing is also worth naming: if you can see the good plan in history, you can force it without changing any code — very useful as an immediate mitigation while you fix the real problem.

Spills and memory grants 🔴 Advanced

In simple terms

Sorts and hash joins need memory, granted before the query runs, based on the estimate.

The grant is fixed. If the estimate was too low, the operator runs out of memory mid-flight and spills to tempdb — disk instead of RAM.

Why a spill is so expensive

It's not a gentle degradation. Sorting 2 million rows in memory versus writing them to tempdb, reading them back in sorted runs, and merging is frequently a 10–100× difference.

In an actual plan a spill shows as a warning on the Sort or Hash Match operator. It's one of the most actionable things you can find — and the fix is usually to fix the estimate, not to ask for more memory.

The opposite problem exists too: an over-estimate grants far too much memory, which other queries then have to wait for. That shows as RESOURCE_SEMAPHORE waits — queries waiting for a memory grant while the server has plenty of free memory.

Statistics 🟡 Intermediate

In simple terms

Statistics are a histogram of a column's data distribution. They're how the optimiser guesses row counts.

Auto-update happens after roughly 20% of rows change (or SQRT(1000 × rows) on newer versions with the better threshold). On a big table, 20% is a lot of drift.

SELECT
    OBJECT_NAME(s.object_id) AS table_name,
    s.name                   AS stat_name,
    sp.last_updated,
    sp.rows,
    sp.modification_counter          -- rows changed since last update
FROM sys.stats s
CROSS APPLY sys.dm_db_stats_properties(s.object_id, s.stats_id) sp
WHERE sp.modification_counter > 1000
ORDER BY sp.modification_counter DESC;
The ascending-key problem

Statistics on an ever-increasing column — a creation date or identity — are always out of date at the top end. The newest rows are beyond the last histogram step, so the optimiser estimates very few rows for "created today".

Which is exactly the query dashboards run constantly. Classic symptom: today's report is slow, last month's is fine.

Mitigations: update statistics on that table more often than the automatic threshold, and enable TF 2371 on older versions for the lower auto-update threshold. This is a good specific thing to mention — it shows real operational experience.

Wait statistics 🔴 Advanced

In simple terms

Plans tell you what a query does. Wait stats tell you what the server is waiting for — which is where to look when the whole instance is slow rather than one query.

Wait typeMeansLook at
PAGEIOLATCH_*Waiting to read data from diskMissing indexes, insufficient memory, slow storage
LCK_M_*Blocked by another transaction's lockLong transactions, missing indexes, isolation level
CXPACKET / CXCONSUMERParallelism coordinationOften benign; check MAXDOP and cost threshold
RESOURCE_SEMAPHOREWaiting for a memory grantOver-estimated grants from bad statistics
WRITELOGWaiting for the transaction logLog file storage speed; too many small transactions
SOS_SCHEDULER_YIELDCPU pressureGenuinely CPU-bound queries; scalar UDFs
PAGELATCH_* on tempdbtempdb allocation contentionAdd tempdb data files (one per core up to 8)
Remember this

Wait stats for "the server is slow". Execution plans for "this query is slow".

Using the wrong tool for the question is why people spend a day tuning a query when the real problem was tempdb contention or a full log drive.

The N+1 problem is usually the biggest single win

Each query is fast, so nothing looks wrong in the plan cache — they're all 2ms. But 1 + 1,000 round trips at 1ms of network latency each is a full second of pure waiting, before the database has done anything.

It's invisible in a plan, invisible in a slow-query log, and obvious the moment you count queries per request. Which is why request-level query counting in development is worth setting up.

Key takeaways
  • Find the query consuming the most total resource, not the one someone noticed.
  • Always get the actual plan. The estimated plan can't show you what went wrong.
  • Estimated vs actual rows is the highest-value number in a plan.
  • Ignore cost percentages — they're derived from the same estimates that may be wrong.
  • Bad estimate → wrong join and undersized memory grant → spill to tempdb.
  • Parameter sniffing: same query, inconsistent speed. Check indexes before adding hints.
  • Consistent-mediocre beats occasionally-catastrophic.
  • Ascending keys mean statistics are always stale at the top — today's data estimates badly.
  • Wait stats for server-wide problems; plans for single queries.
  • In .NET, N+1 and missing projection usually cost more than any single query's plan.

Common mistakes

  • Tuning the query someone complained about rather than the expensive one.
  • Reading the estimated plan and drawing conclusions about actual behaviour.
  • Chasing the highest cost percentage instead of actual time and rows.
  • Adding hints before checking indexes and statistics.
  • OPTION (RECOMPILE) on a query running thousands of times a minute — trading a plan problem for a CPU problem.
  • Ignoring spill warnings.
  • Never enabling Query Store, so "it got slow last week" is unanswerable.
  • Tuning queries when wait stats point at storage, tempdb or the log.
  • Changing several things at once, so you don't know what helped.
  • Testing on a dataset that isn't production-shaped.

Interview questions

Intermediate

A page that used to load in 200ms now takes 30 seconds. Walk me through your diagnosis. 🔥 Must know
How I'd answer

"First I'd establish what changed and when, because 'used to be fast' is the most useful clue I have. A deployment? A data volume threshold? A failover or restart? Did it degrade gradually or overnight?"

"Then I'd confirm it's actually the database. A slow page might be N+1 queries, a slow external call, or something on the application side entirely. I'd look at APM traces or just log the query count and total database time for that request. If it's 400 queries at 2ms each, the plan is irrelevant and the fix is in the data access code."

"Assuming it is one query: I'd get the actual execution plan, and compare estimated versus actual rows at each operator. That single comparison explains most bad plans, because the optimiser chose join types and memory grants from those estimates. If it expected 100 rows and got 2 million, it picked nested loops where it needed a hash join, and the memory grant was sized for 100 rows so any sort spilled to tempdb."

"Given it was fast before and is slow now with no code change, my leading hypotheses are:"

"Parameter sniffing. The plan was recompiled — after a restart, a failover, or a statistics update — with an unrepresentative parameter, and now every call reuses that bad plan. Quick test: run the same SQL in SSMS with the same parameters. If it's fast there and slow from the app, that's almost certainly it, because SSMS compiled a fresh plan."

"Stale statistics. The table grew and the histogram no longer reflects it. Auto update needs ~20% of rows changed, which on a large table is a lot of drift. And if the query filters on a date or identity column there's the ascending-key problem — the newest rows are beyond the last histogram step, so 'today' always estimates low. Classic version of this: today's dashboard is slow, last month's is fine."

"A data volume threshold crossed. A plan that was fine at 100,000 rows becomes untenable at 5 million. Nothing changed except size."

"An index was dropped or disabled — worth checking, it happens during maintenance."

"For an immediate mitigation I'd look at Query Store, which keeps plan history. If I can see the previous good plan I can force it — that buys the site back in minutes with no deployment, while I fix the actual cause."

"Then I'd change one thing at a time and re-measure, so I know what worked rather than shipping four changes and guessing."

What they're really checking
  • Do you ask what changed before diving in?
  • Do you check it's even the database?
  • Do you know the estimated-vs-actual comparison?
  • Do you separate immediate mitigation from root cause?
Weak answers
  • Red flag: "add an index" immediately.
  • Red flag: restarting SQL Server — it clears the cache, appears to fix it, and teaches you nothing.
  • Red flag: no mention of reading a plan.
Likely follow-ups
  • How do you confirm parameter sniffing?
  • What's the downside of forcing a plan?
  • How would you detect N+1 in development?

Advanced / scenario

Explain parameter sniffing and how you'd fix it. ⭐ Senior-level
How I'd answer

"SQL Server compiles a plan the first time a query runs, using the actual parameter values it sees — that's the sniffing, and normally it's helpful, because using real values gives better estimates than guessing. The plan is then cached and reused."

"The problem is data skew. If I have a procedure filtering orders by country, and the first call is for Luxembourg with 200 rows, the optimiser builds a perfectly sensible plan — nested loops, index seek, key lookups. Then someone calls it for the US with 8 million rows and gets that same plan: 8 million seeks and 8 million key lookups instead of one scan and a hash join. It might take minutes."

"The symptom is the same query being inconsistently slow with no code change, and it often starts after a restart, failover, or statistics update — because that's when the plan gets recompiled with whatever parameter happens to arrive first. The classic tell is 'it's fast in SSMS but slow from the app', because SSMS compiled a fresh plan for your parameter."

"Fixes, and I'd order them deliberately."

"First, check whether it's really a sniffing problem. Quite often the right index is missing, and with it both plans are fast — so the skew stops mattering. Reaching for hints before checking indexes fixes the symptom and leaves the cause in place."

"OPTION (RECOMPILE) — compiles every execution with the actual parameter, so every call gets an appropriate plan. Simple and usually correct. The cost is CPU per execution and no plan reuse, so I wouldn't put it on something running thousands of times a minute — that trades a plan problem for a CPU problem."

"OPTIMIZE FOR UNKNOWN — ignores the actual value and uses average density. You get a consistently average plan. That's often the right trade, because consistent-mediocre beats occasionally-catastrophic: an 800ms query every time is better for the system than 50ms usually and 90 seconds sometimes, since the 90-second case is what exhausts the thread pool and takes the site down."

"OPTIMIZE FOR (@p = 'US') when I genuinely know the dominant case and want to guarantee the big one is fast."

"Splitting the procedure when there are two genuinely different access patterns — a branch on row count that calls one of two procedures, each getting its own plan. More code, but both cases are optimal and it's explicit rather than relying on a hint's side effects."

"And as an immediate mitigation, Query Store plan forcing: if the good plan is in history I can force it without touching code or deploying. That's the fastest way to stop the bleeding while I decide on the real fix."

"One thing I'd flag: WITH RECOMPILE on the whole procedure is a blunter instrument than OPTION (RECOMPILE) on the statement — it recompiles everything, so I'd use the statement hint where I can."

What they're really checking
  • Do you know sniffing is normally beneficial, and skew is the actual problem?
  • Can you name the symptom and the SSMS-vs-app tell?
  • Do you check indexes before hinting?
  • Do you articulate the consistency-vs-peak trade-off?
  • Do you know about plan forcing?
Weak answers
  • Red flag: "OPTION (RECOMPILE)" with no mention of cost.
  • Red flag: describing sniffing as a bug in SQL Server.
  • Red flag: clearing the plan cache as a fix.
Likely follow-ups
  • Why does a local variable behave differently from a parameter?
  • What are the risks of forcing a plan long-term?
  • How does this interact with statistics updates?
The whole database server is slow, not one query. Where do you start? ⭐ Senior-level
How I'd answer

"Different question from a slow query, and I'd use a different tool: wait statistics. They tell me what the server is waiting on, which points at the bottleneck instead of making me guess."

"I'd look at sys.dm_os_wait_stats — or better, sys.dm_exec_session_wait_stats and what's actually happening right now, since cumulative stats since startup can be dominated by history that's no longer relevant."

"Then I'd interpret the top waits:"

"PAGEIOLATCH means reading from disk — so either not enough memory to hold the working set, missing indexes causing scans that read far more than needed, or genuinely slow storage. LCK_M_* means blocking, so I'd look at long transactions and isolation level, and consider RCSI. WRITELOG points at log storage or too many small transactions. RESOURCE_SEMAPHORE means queries queuing for memory grants, usually because bad estimates are causing over-sized grants. PAGELATCH on tempdb is allocation contention, fixed by adding tempdb data files. SOS_SCHEDULER_YIELD is CPU pressure."

"Alongside that I'd check the boring operational things, because they're common and quick to rule out: is a disk full, is the log growing because a backup hasn't run, is there a maintenance job or index rebuild running right now, has someone started a large reporting query, did the VM get resized, is another workload sharing the storage."

"Then I'd check whether it's actually one query causing it all. A single bad plan running thousands of times can saturate CPU or flood I/O and make everything look slow. So high total-resource consumers from Query Store, not just averages."

"The important thing is the order: waits tell me which direction to look, then I drill into specific queries. Going straight to query tuning when the answer is a full log drive or tempdb contention wastes a day and fixes nothing."

"And I'd separate mitigation from diagnosis. If the system is down, killing a runaway query or failing over buys time. But I'd capture the wait stats and plans first, because a restart clears exactly the evidence I need."

What they're really checking
  • Do you know wait stats are the tool for server-wide problems?
  • Can you interpret the common wait types?
  • Do you check operational basics — disks, backups, maintenance?
  • Do you capture evidence before mitigating?
Weak answers
  • Red flag: going straight to individual query tuning.
  • Red flag: "restart it" as step one.
  • Red flag: "add more memory" with no diagnosis.
Likely follow-ups
  • How many tempdb files, and why?
  • What does a high CXPACKET actually tell you?
  • How would you find the query saturating CPU?
