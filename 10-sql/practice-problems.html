SQL Interview Problems

Ten problems that come up repeatedly. The query matters less than the reasoning — so each one includes what to say while you write it.

🟡 Intermediate 🔴 Advanced 🔥 Must know
How to handle a SQL problem in an interview
  • Ask about ties and nulls first. "Second highest — if two people share the top salary, is the second highest the same value or the next distinct one?" That question alone earns credit.
  • Say what you're reaching for and why before writing. "This is top-N-per-group, so a window function."
  • Mention the index you'd want. Almost nobody does, and it's the difference between a correct answer and a good one.
  • State your assumptions out loud rather than silently picking one.

1. Second highest salary 🔥 Must know

Ask this before writing anything

"If two employees both earn the highest salary, is the second highest that same value, or the next distinct one?"

Almost always they mean the next distinct value — and asking shows you've noticed the ambiguity that makes this a real question rather than a lookup.

WITH Ranked AS (
    SELECT Name, Salary,
           DENSE_RANK() OVER (ORDER BY Salary DESC) AS rnk
    FROM   Employee
)
SELECT Name, Salary FROM Ranked WHERE rnk = 2;
SELECT Name, Salary
FROM   Employee
ORDER BY Salary DESC
OFFSET 1 ROWS FETCH NEXT 1 ROW ONLY;
ApproachSemantics
DENSE_RANK() = 2Second distinct salary. Returns everyone earning it. Usually correct
ROW_NUMBER() = 2Second row. With tied top salaries, returns another person on the top salary
OFFSET 1 FETCH 1Same as ROW_NUMBER, and non-deterministic on ties
MAX(...) WHERE < MAX(...)Works, doesn't generalise to Nth, harder to read
What to say out loud

"I'll use DENSE_RANK because it treats tied salaries as one level, so rank 2 is genuinely the second-highest salary rather than the second row. If you wanted exactly one person I'd use ROW_NUMBER with a tiebreaker so it's deterministic. And rnk = 2 generalises straight to Nth, which the MAX-based version doesn't."

Follow-up they'll ask: what if there is no second salary? This returns an empty set. If they need a NULL row instead, that's a LEFT JOIN from a single-row derived table.

2. Nth highest per group 🔥 Must know

WITH Ranked AS (
    SELECT e.Name, d.Name AS Department, e.Salary,
           DENSE_RANK() OVER (PARTITION BY e.DepartmentId
                              ORDER BY e.Salary DESC) AS rnk
    FROM Employee e
    JOIN Department d ON d.Id = e.DepartmentId
)
SELECT Department, Name, Salary
FROM   Ranked
WHERE  rnk <= 3
ORDER BY Department, Salary DESC;
SELECT d.Name AS Department, e.Name, e.Salary
FROM Department d
CROSS APPLY (
    SELECT TOP (3) Name, Salary
    FROM   Employee
    WHERE  DepartmentId = d.Id
    ORDER BY Salary DESC
) e;
The performance point that impresses

PARTITION BY numbers every employee, then discards all but the top three. CROSS APPLY does one small seek per department and stops at three.

With an index on (DepartmentId, Salary DESC), APPLY is usually much faster — especially with many departments and many employees each.

Say it as: "Both are correct. I'd start with the window function for readability, and switch to CROSS APPLY if this were hot, because it can stop after three rows per department instead of ranking everyone."

Note CROSS APPLY with TOP returns exactly 3 rows even when there's a tie at third — a semantic difference, not just a performance one, and worth stating.

3. Remove duplicates, keep the newest 🔥 Must know

WITH Dupes AS (
    SELECT Id,
           ROW_NUMBER() OVER (PARTITION BY Email
                              ORDER BY CreatedUtc DESC, Id DESC) AS rn
    FROM   Customer
)
DELETE FROM Dupes WHERE rn > 1;
DetailWhy
ROW_NUMBER, not RANKRANK would give tied rows the same rank 1 and delete neither
, Id DESC tiebreakerWithout it, rows sharing a timestamp make the survivor non-deterministic — the same query can keep a different row on each run
DELETE FROM DupesYou can delete through a CTE. Surprises people, and it's the cleanest form
What a good candidate adds unprompted

"On a big table I'd batch this" — DELETE TOP (5000) FROM Dupes WHERE rn > 1 in a loop, to stay under lock escalation and keep the log manageable.

"And then I'd add a unique constraint on Email", so the duplicates can't come back. That second point is the one that separates fixing the data from fixing the problem — and interviewers notice it.

4. Consecutive days — gaps and islands 🔴 Advanced

The problem

Find users who logged in on 3 or more consecutive days.

This is the classic "gaps and islands" pattern, and it has a trick worth memorising because it looks like magic otherwise.

WITH Numbered AS (
    SELECT UserId, LoginDate,
           ROW_NUMBER() OVER (PARTITION BY UserId ORDER BY LoginDate) AS rn
    FROM (SELECT DISTINCT UserId, LoginDate FROM Login) d
),
Grouped AS (
    -- Consecutive dates minus consecutive row numbers = a CONSTANT per run
    SELECT UserId, LoginDate,
           DATEADD(day, -rn, LoginDate) AS grp
    FROM   Numbered
)
SELECT UserId,
       MIN(LoginDate) AS StreakStart,
       MAX(LoginDate) AS StreakEnd,
       COUNT(*)       AS Days
FROM   Grouped
GROUP BY UserId, grp
HAVING COUNT(*) >= 3;
Why the trick works

Take dates 1, 2, 3 then 7, 8. Row numbers are 1, 2, 3, 4, 5.

Subtract: 1-1, 2-2, 3-3 → all give 0. Then 7-4, 8-5 → both give 3.

Consecutive dates increment at the same rate as row numbers, so the difference is constant within a run and jumps at every gap. That constant becomes your grouping key.

Two details that show experience

SELECT DISTINCT first. If a user logs in twice on one day, the row numbers advance twice and the difference breaks. Almost everyone misses this, and it's a correctness bug not a style point.

Name the pattern. Saying "this is gaps and islands" tells the interviewer you've seen the class of problem, not just solved this instance. The same technique handles consecutive order numbers, contiguous date ranges, and session-grouping by inactivity.

5. Running total and month-over-month change 🟡 Intermediate

WITH Monthly AS (
    SELECT DATEFROMPARTS(YEAR(CreatedUtc), MONTH(CreatedUtc), 1) AS Month,
           SUM(Total) AS Revenue
    FROM   [Order]
    GROUP BY DATEFROMPARTS(YEAR(CreatedUtc), MONTH(CreatedUtc), 1)
)
SELECT
    Month,
    Revenue,
    SUM(Revenue) OVER (ORDER BY Month
                       ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW) AS RunningTotal,
    LAG(Revenue) OVER (ORDER BY Month) AS PrevMonth,
    Revenue - LAG(Revenue) OVER (ORDER BY Month) AS Change,
    CAST(100.0 * (Revenue - LAG(Revenue) OVER (ORDER BY Month))
         / NULLIF(LAG(Revenue) OVER (ORDER BY Month), 0) AS decimal(10,2)) AS PctChange
FROM Monthly
ORDER BY Month;
DetailWhy it matters
ROWS BETWEEN explicitlyThe default frame is RANGE, which includes all rows with the same ORDER BY value. Explicit ROWS is correct and faster
NULLIF(..., 0)Prevents divide-by-zero. Returns NULL instead of erroring
CAST(100.0 * ...)100.0 not 100 — integer division would truncate to 0
Aggregate first, window secondWindow functions can't nest inside aggregates, so the monthly rollup has to be its own step
The gap that catches people

If a month has no orders it's absent from Monthly entirely — so LAG returns the previous month that had data, not the previous calendar month.

Silently wrong for a report. The fix is a calendar table (or a recursive CTE generating months) LEFT JOINed to the data.

Raising this unprompted is a strong signal — it's the kind of bug that ships and then produces numbers nobody can reconcile.

6. Customers with no orders 🟢 Beginner

SELECT c.Id, c.Name
FROM   Customer c
WHERE  NOT EXISTS (SELECT 1 FROM [Order] o WHERE o.CustomerId = c.Id);
SELECT c.Id, c.Name
FROM      Customer c
LEFT JOIN [Order] o ON o.CustomerId = c.Id
WHERE     o.Id IS NULL;
SELECT Id, Name FROM Customer
WHERE Id NOT IN (SELECT CustomerId FROM [Order]);
-- Returns ZERO ROWS if any CustomerId is NULL
Say the null point — it's the whole reason this gets asked

"I'd use NOT EXISTS rather than NOT IN, because if the subquery returns even one NULL, NOT IN returns no rows at all. The logic is that x NOT IN (1, NULL) means x <> 1 AND x <> NULL, and comparing to NULL is unknown — so the predicate can never be true."

"It fails silently with no error, which is why it survives testing on data that happens to have no nulls."

7. Median 🔴 Advanced

SELECT DISTINCT
    DepartmentId,
    PERCENTILE_CONT(0.5) WITHIN GROUP (ORDER BY Salary)
        OVER (PARTITION BY DepartmentId) AS MedianSalary
FROM Employee;
WITH Ranked AS (
    SELECT Salary,
           ROW_NUMBER() OVER (ORDER BY Salary) AS rn,
           COUNT(*)    OVER ()                 AS total
    FROM   Employee
)
SELECT AVG(CAST(Salary AS decimal(19,4))) AS Median
FROM   Ranked
WHERE  rn IN ((total + 1) / 2, (total + 2) / 2);   -- handles odd and even
Why the second version's WHERE works

With 7 rows: (7+1)/2 = 4 and (7+2)/2 = 4 — the same row, so AVG of one value.

With 8 rows: (8+1)/2 = 4 and (8+2)/2 = 5 — two rows, averaged.

Integer division handles both cases with no CASE statement. Worth explaining rather than just writing.

PERCENTILE_CONT vs PERCENTILE_DISC

PERCENTILE_CONT interpolates between the two middle values — a true median, and it can return a value not present in the data.

PERCENTILE_DISC returns an actual value from the dataset.

For salary, CONT is usually what's wanted. Also note PERCENTILE_CONT is a window function, not an aggregate — hence the DISTINCT and OVER, which surprises people expecting to use it with GROUP BY.

8. Pivot: months as columns 🟡 Intermediate

SELECT
    CustomerId,
    SUM(CASE WHEN MONTH(CreatedUtc) = 1 THEN Total ELSE 0 END) AS Jan,
    SUM(CASE WHEN MONTH(CreatedUtc) = 2 THEN Total ELSE 0 END) AS Feb,
    SUM(CASE WHEN MONTH(CreatedUtc) = 3 THEN Total ELSE 0 END) AS Mar
FROM   [Order]
WHERE  YEAR(CreatedUtc) = 2024
GROUP BY CustomerId;
The answer that ends the question well

"I'd write this with conditional aggregation because it's portable and readable. But the more useful point is that pivoting in SQL requires knowing the columns at query time. If the set of columns is dynamic, you need dynamic SQL, and that gets unpleasant to maintain and secure.

I'd usually return the data in its long form and pivot in the presentation layer — Excel, the reporting tool, or the UI. Those are designed for it and it keeps the SQL simple."

Also worth noting: WHERE YEAR(CreatedUtc) = 2024 is not SARGable. I'd write it as a date range — >= '2024-01-01' AND < '2025-01-01' — so an index seek is possible. Catching that in your own answer is a good signal.

9. Employees earning more than their manager 🟢 Beginner

SELECT e.Name AS Employee, e.Salary,
       m.Name AS Manager,  m.Salary AS ManagerSalary
FROM      Employee e
JOIN      Employee m ON m.Id = e.ManagerId      -- INNER: excludes the CEO
WHERE     e.Salary > m.Salary;
The clarification to raise

"An INNER JOIN here excludes anyone with no manager — the CEO. That's probably right, since 'earns more than their manager' is undefined for them. But if you wanted them included I'd use a LEFT JOIN and treat a null manager salary explicitly."

Stating the boundary case rather than silently choosing is what they're listening for. Self-join questions are usually testing whether you think about the root of the hierarchy.

10. Latest row per key 🔥 Must know

Why this one matters

This is the most common shape in real work — latest status per order, current price per product, newest login per user.

The naive version is subtly wrong, so it's a good test.

SELECT CustomerId, MAX(CreatedUtc) AS Latest, Total   -- which Total?
FROM   [Order]
GROUP BY CustomerId, Total;                            -- wrong grouping to compensate
WITH Latest AS (
    SELECT *,
           ROW_NUMBER() OVER (PARTITION BY CustomerId
                              ORDER BY CreatedUtc DESC, Id DESC) AS rn
    FROM   [Order]
)
SELECT CustomerId, Id, CreatedUtc, Total, Status
FROM   Latest
WHERE  rn = 1;
SELECT c.Id, c.Name, o.Id AS LatestOrderId, o.Total
FROM Customer c
OUTER APPLY (                              -- OUTER keeps customers with no orders
    SELECT TOP (1) Id, Total, CreatedUtc
    FROM   [Order]
    WHERE  CustomerId = c.Id
    ORDER BY CreatedUtc DESC, Id DESC
) o;
The two things to say

Why the naive version fails: MAX(CreatedUtc) gives you the latest date, but the other columns in the row aren't tied to it — so you either get a grouping error or you add columns to GROUP BY and change the meaning entirely. You need the whole row, not the max of one column.

The index: "I'd want (CustomerId, CreatedUtc DESC). With that, OUTER APPLY does a single-row seek per customer, which beats numbering every order and discarding all but one."

And OUTER rather than CROSS — that's the detail that distinguishes "customers and their latest order" from "customers who have ordered".

Patterns worth memorising
  • Nth highest / top N per group → DENSE_RANK or ROW_NUMBER in a CTE, filter outside. CROSS APPLY when it's hot.
  • Deduplication → ROW_NUMBER partitioned by the duplicate key, delete rn > 1. Then add the unique constraint.
  • Consecutive runs → date minus row number is constant within a run. Distinct first.
  • Running totals / period comparison → window functions with an explicit ROWS frame, and LAG.
  • "Has no related rows" → NOT EXISTS, never NOT IN.
  • Latest row per key → ROW_NUMBER = 1, or OUTER APPLY TOP 1 with the right index.
  • Ties are always the hidden question. Ask before you write.
  • Mention the index. It's the cheapest way to stand out.

Mistakes candidates make

  • Writing immediately without clarifying ties, nulls or expected output shape.
  • Silence. The interviewer is assessing reasoning, and can't hear any.
  • RANK where ROW_NUMBER is needed, so deduplication deletes nothing.
  • No tiebreaker in ORDER BY, making the result non-deterministic.
  • Integer division — 100 * a / b truncating to zero.
  • Forgetting DISTINCT in gaps-and-islands.
  • Missing calendar gaps in period-over-period comparisons.
  • Never mentioning indexes.
  • Non-SARGable predicates like YEAR(col) = 2024 in your own answer.
  • Not saying "on a large table I'd batch this" for a bulk delete.
