SQL & Azure SQL

The database is where most production performance problems actually live. This is the section that pays off most in interviews and in the job.

🟡 Intermediate 🔴 Advanced 🔥 Must know
Quick revision
  • Most "slow API" problems are slow queries, missing indexes, or blocking — not application code.
  • Indexing is the highest-value SQL topic. If you know one thing deeply, make it this.
  • Know how to read an execution plan well enough to spot a scan, a lookup and a bad estimate.
  • Isolation levels and locking explain almost every "it works alone but breaks under load" bug.
  • Interviewers care far more about why a query is slow than about exotic syntax.
  • Azure SQL questions are mostly about tiers, scaling and HA — the SQL itself is the same.

Remember this

The question behind almost every senior SQL question is: do you understand what the database is actually doing?

Someone who can read a plan, explain why an index wasn't used, and reason about locking will out-perform someone who knows more syntax.

What to prioritise

If you're short on preparation time, in this order:

  1. Indexing — clustered vs non-clustered, column order, covering indexes, and why an index sometimes isn't used.
  2. Execution plans and tuning — reading a plan, SARGability, parameter sniffing.
  3. Transactions and concurrency — isolation levels, blocking, deadlocks.
  4. Querying — joins, CTEs, window functions, pagination that scales.
  5. Fundamentals — normalization and when to break it.
  6. Azure SQL — if the role is Azure-based.

One mental model to carry ⭐ Senior-level

Nearly every SQL performance answer comes back to the same idea:

How many pages does the database have to read to answer this question?

Everything follows from that:

  • An index exists so the engine reads a few pages instead of all of them.
  • A covering index means it doesn't have to go back to the table for extra columns.
  • A wrong column order in a composite index means the engine can't seek, so it scans.
  • A non-SARGable predicate (a function on the column) means the index can't be used at all.
  • Bad statistics mean the optimiser guesses the wrong row count and picks the wrong plan.

If you can trace a slow query back to "it's reading too many pages, and here's why", you can answer most tuning questions without memorising anything.
