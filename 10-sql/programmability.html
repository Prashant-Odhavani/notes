Procedures, Views, Functions & Triggers

Server-side logic. Some of it is genuinely valuable; some of it is the reason a query is 100× slower than it should be.

🟡 Intermediate 🔴 Advanced ⭐ Senior-level
Quick revision
  • Scalar UDFs are the biggest hidden performance killer in SQL Server. One in a WHERE clause runs per row and blocks parallelism.
  • Inline table-valued functions are fine. Multi-statement TVFs are not — they're a black box to the optimiser.
  • Views don't store data or improve performance. They're names for queries. Only indexed views materialise.
  • Triggers run inside your transaction, invisibly, on every write. Treat them as a last resort.
  • Always SET NOCOUNT ON in procedures — it removes a network round trip per statement.
  • Dynamic SQL: sp_executesql with parameters, never string concatenation.
  • The stored-proc-vs-ORM debate is mostly settled — use both, for what each is good at.

Scalar functions — the performance trap 🔥 Must know

In simple terms

A scalar UDF looks like a normal function call. But before SQL Server 2019 it was interpreted, row by row — like calling a method inside a loop over a million rows, with no ability to see inside it.

CREATE FUNCTION dbo.GetCustomerTier(@customerId int)
RETURNS varchar(20)
AS
BEGIN
    DECLARE @total decimal(19,4);
    SELECT @total = SUM(Total) FROM [Order] WHERE CustomerId = @customerId;
    RETURN CASE WHEN @total > 10000 THEN 'Gold'
                WHEN @total > 1000  THEN 'Silver'
                ELSE 'Bronze' END;
END;
GO

-- Runs the function - and its aggregate query - ONCE PER CUSTOMER ROW
SELECT Id, Name, dbo.GetCustomerTier(Id) AS Tier
FROM   Customer;
Why it's slowDetail
Per-row execution100,000 customers = 100,000 executions of that inner query
No parallelismA scalar UDF makes the whole query plan serial, even the parts that don't use it
Invisible costPre-2019 the plan shows the UDF as almost free. The real cost doesn't appear anywhere
Kills SARGabilityA UDF in WHERE means no index seek
 
SELECT c.Id, c.Name,
       CASE WHEN t.Total > 10000 THEN 'Gold'
            WHEN t.Total > 1000  THEN 'Silver'
            ELSE 'Bronze' END AS Tier
FROM Customer c
LEFT JOIN (
    SELECT CustomerId, SUM(Total) AS Total
    FROM   [Order]
    GROUP BY CustomerId
) t ON t.CustomerId = c.Id;
SQL Server 2019+ improved this — with conditions

Scalar UDF inlining (compatibility level 150+) rewrites simple scalar UDFs into the calling query, so they can be optimised and parallelised properly.

But it only applies to inlineable functions — no loops, no cursors, no EXEC, no time-dependent functions, no aggregates in some cases. A complex UDF still runs per row.

So the honest answer in an interview is: "much better on 2019+ at compatibility level 150, but I'd still check sys.sql_modules.is_inlineable rather than assume, and I'd prefer set-based logic anyway."

Inline vs multi-statement table-valued functions 🔴 Advanced

CREATE FUNCTION dbo.OrdersForCustomer(@customerId int)
RETURNS TABLE
AS
RETURN                                    -- single statement, no BEGIN/END
(
    SELECT Id, CreatedUtc, Total
    FROM   [Order]
    WHERE  CustomerId = @customerId
);
CREATE FUNCTION dbo.OrdersForCustomerMS(@customerId int)
RETURNS @r TABLE (Id int, CreatedUtc datetime2, Total decimal(19,4))
AS
BEGIN                                     -- BEGIN/END = multi-statement
    INSERT @r SELECT Id, CreatedUtc, Total FROM [Order] WHERE CustomerId = @customerId;
    RETURN;
END;
Inline TVFMulti-statement TVF
Optimiser treatmentExpanded into the outer query, like a viewA black box — executed separately
Row estimateAccurate, from the underlying tablesFixed guess — 1 row pre-2014, 100 after
Predicate pushdownYesNo
VerdictUse freelyAvoid unless there's no alternative
How to tell them apart instantly

BEGIN means trouble.

An inline TVF is RETURNS TABLE AS RETURN (SELECT ...) — no BEGIN. Anything with BEGIN...END is multi-statement and opaque to the optimiser.

Senior signal — why the fixed estimate is so damaging

A multi-statement TVF that actually returns 500,000 rows is estimated at 100.

So the optimiser picks a nested-loop join and a tiny memory grant. Then reality arrives: 500,000 iterations of the loop, and a sort that spills to disk because the grant was sized for 100 rows.

That's not "a bit slower" — it's frequently a 100× difference, and it looks inexplicable until you know the estimate is hardcoded.

Views 🟢 Beginner

In simple terms

A view is a saved query with a name. It stores no data and does nothing for performance — the query still runs when you select from it.

Its value is abstraction and security, not speed.

Good useWhy
Security boundaryGrant access to a view exposing only some columns or rows, not the base table
Hiding join complexityOne name instead of a five-table join repeated everywhere
Compatibility shimRename or restructure a table and keep a view with the old shape
Row-level filteringA tenant-scoped view, though a query filter is usually better
The nested-view problem

Views built on views built on views. Each level looks reasonable; the flattened query is a 20-table join.

Two consequences. The optimiser has a compile-time budget, and past a certain complexity it stops searching and returns whatever it has — so you get a mediocre plan for a query nobody wrote. And you often join to tables you don't need any columns from, because a lower-level view included them.

My rule: one level of nesting. If you need more, the logic probably belongs in a procedure or a materialised table.

Indexed views — actual materialisation

CREATE VIEW dbo.vw_CustomerRevenue
WITH SCHEMABINDING                          -- required
AS
SELECT CustomerId,
       SUM(Total)   AS Revenue,
       COUNT_BIG(*) AS Orders               -- COUNT_BIG, not COUNT
FROM   dbo.[Order]
GROUP BY CustomerId;
GO

CREATE UNIQUE CLUSTERED INDEX IX_vw_CustomerRevenue
    ON dbo.vw_CustomerRevenue(CustomerId);  -- this materialises it
Indexed views: real cost, real restrictions

The results are physically stored and maintained synchronously — every write to [Order] now also updates the indexed view, inside the same transaction. Reads get much faster; writes get slower and contend more.

Restrictions are significant: SCHEMABINDING, deterministic expressions only, COUNT_BIG not COUNT, no outer joins, no subqueries, no DISTINCT, no HAVING, and specific SET options required on every connection that writes to the base tables.

Good for a stable, heavily-read aggregate on a table with modest write volume. Bad on a hot write path — there, an async read model is the better trade.

Stored procedures 🟡 Intermediate

CREATE OR ALTER PROCEDURE dbo.usp_CreateOrder
    @CustomerId int,
    @Total      decimal(19,4),
    @OrderId    int OUTPUT
AS
BEGIN
    SET NOCOUNT ON;                 -- no per-statement row-count messages
    SET XACT_ABORT ON;              -- any error aborts the whole transaction

    BEGIN TRY
        BEGIN TRANSACTION;

        INSERT dbo.[Order] (CustomerId, Total, CreatedUtc)
        VALUES (@CustomerId, @Total, SYSUTCDATETIME());

        SET @OrderId = SCOPE_IDENTITY();   -- SCOPE_IDENTITY, not @@IDENTITY

        COMMIT TRANSACTION;
    END TRY
    BEGIN CATCH
        IF XACT_STATE() <> 0 ROLLBACK TRANSACTION;
        THROW;                      -- preserves the original error
    END CATCH
END;
LineWhy it matters
SET NOCOUNT ONSuppresses "n rows affected" messages. Each one is a network packet — in a loop that's a measurable cost
SET XACT_ABORT ONWithout it, some errors leave the transaction open and the procedure continues. This is the single most common source of orphaned transactions
SCOPE_IDENTITY()@@IDENTITY returns the last identity in the session — including one inserted by a trigger. That's a real bug, not a style point
XACT_STATE()Checks whether a transaction is still rollback-able before trying
THROWRe-raises with the original error number and message. RAISERROR loses that

Procedures vs an ORM ⭐ Senior-level

The pragmatic position

ORM for CRUD and domain logic. SQL — procedure or raw query — for set-based and performance-critical work.

"All logic in stored procedures" and "never write SQL" are both positions that cost teams real money.

The "procedures are faster because plans are cached" claim

This was true long ago and isn't a meaningful advantage now. SQL Server caches plans for parameterised ad-hoc queries too, and EF Core parameterises everything it generates.

The genuine advantages of procedures are control over the exact SQL, the ability to fix a query in production without a deployment, and a smaller permissions surface — you can grant EXECUTE on a procedure without granting table access at all.

Correcting the plan-cache myth is a good signal, because it's repeated constantly.

Dynamic SQL 🔥 Must know

CREATE PROCEDURE dbo.usp_SearchBad @name nvarchar(100)
AS
BEGIN
    DECLARE @sql nvarchar(max) =
        N'SELECT * FROM Customer WHERE Name LIKE ''%' + @name + '%''';
    EXEC(@sql);                     -- @name = "'; DROP TABLE Customer --"
END;
CREATE PROCEDURE dbo.usp_Search @name nvarchar(100)
AS
BEGIN
    SET NOCOUNT ON;

    DECLARE @sql nvarchar(max) =
        N'SELECT Id, Name FROM dbo.Customer WHERE Name LIKE @p';

    EXEC sp_executesql @sql,
         N'@p nvarchar(102)',
         @p = '%' + @name + '%';
END;
A stored procedure is not automatically injection-safe

This is a persistent myth. Procedures are safe when they use parameters. A procedure that concatenates strings is exactly as vulnerable as concatenating in C# — arguably worse, because it usually runs with higher privileges.

sp_executesql takes parameters; EXEC(@sql) does not. That's the distinction.

For identifiers that genuinely can't be parameterised — a dynamic table or column name — validate against a whitelist and wrap with QUOTENAME(). Never interpolate raw input into an identifier position.

Triggers 🔴 Advanced

In simple terms

A trigger is code that runs automatically on INSERT, UPDATE or DELETE — inside the same transaction as the statement that fired it.

So it's invisible logic on your write path, and its failures are your failures.

Why triggers cause outages
  • Invisible. A developer reading the C# and the procedure has no reason to suspect additional work is happening.
  • Inside your transaction. A slow trigger makes every write slow and extends lock duration.
  • Fail together. A trigger error rolls back the original statement, so a bug in auditing stops orders being placed.
  • Cascade. Triggers fire triggers, up to 32 levels. Debugging that is genuinely difficult.
  • Set-based, not row-based. inserted and deleted hold all affected rows — a trigger written for one row silently corrupts data on a 1,000-row update.
CREATE TRIGGER trg_Order_Audit ON dbo.[Order] AFTER UPDATE
AS
BEGIN
    DECLARE @id int;
    SELECT @id = Id FROM inserted;      -- 1000 rows updated -> ONE arbitrary id
    INSERT Audit (OrderId, ChangedUtc) VALUES (@id, SYSUTCDATETIME());
    -- 999 changes never audited, and which one you got is undefined
END;
CREATE TRIGGER trg_Order_Audit ON dbo.[Order] AFTER UPDATE
AS
BEGIN
    SET NOCOUNT ON;
    IF @@ROWCOUNT = 0 RETURN;           -- cheap exit on no-op updates

    INSERT dbo.Audit (OrderId, OldTotal, NewTotal, ChangedUtc)
    SELECT i.Id, d.Total, i.Total, SYSUTCDATETIME()
    FROM   inserted i
    JOIN   deleted  d ON d.Id = i.Id
    WHERE  i.Total <> d.Total;          -- only log actual changes
END;
Defensible trigger usesBetter handled elsewhere
Auditing you must guarantee even for direct SQL writesBusiness logic — put it in the domain model
Enforcing an invariant a constraint can't expressSending notifications — use the outbox pattern
Making a legacy schema work without touching old callersMaintaining denormalized aggregates on hot tables
Modern alternatives worth naming

Temporal tables (SYSTEM_VERSIONING = ON) give you full row history maintained by the engine — no trigger to write or maintain, and it handles set-based updates correctly by construction. If the requirement is "keep history of this table", that's the answer now.

Change Data Capture or change tracking for feeding downstream systems, instead of a trigger that writes to a queue table.

Temp tables vs table variables 🟡 Intermediate

#temp@table
StatisticsYesNo — estimates 1 row
IndexesAnyPK/unique only
TransactionsParticipates and rolls backSurvives rollback
ParallelismAllowedForces serial in many cases
Best forAnything over a few hundred rowsSmall sets; table-valued parameters
Remember this

Table variables estimate one row no matter what they contain.

Put 200,000 rows in one and the optimiser still plans for one — nested loops, tiny memory grant, spills. Default to #temp unless you specifically need a table-valued parameter.

The rollback difference is occasionally useful: a table variable keeps its contents after a rollback, so you can record what went wrong.

Error handling 🟡 Intermediate

BEGIN TRY
    -- work
END TRY
BEGIN CATCH
    IF XACT_STATE() <> 0 ROLLBACK TRANSACTION;

    INSERT dbo.ErrorLog (Number, Severity, Procedure_, Line, Message, OccurredUtc)
    VALUES (ERROR_NUMBER(), ERROR_SEVERITY(), ERROR_PROCEDURE(),
            ERROR_LINE(), ERROR_MESSAGE(), SYSUTCDATETIME());

    THROW;                          -- rethrow unchanged for the caller
END CATCH
What TRY...CATCH does not catch

Compile errors, most severity-20+ errors, and connection-level failures such as a timeout or a killed session.

That last one matters: a command timeout in .NET doesn't run your CATCH block, so the transaction can be left open until the connection is reset. SET XACT_ABORT ON is the mitigation, and it's why it belongs in every procedure that opens a transaction.

Key takeaways
  • Scalar UDFs run per row and force a serial plan. Inlining in 2019+ helps only if the function qualifies.
  • Inline TVFs are expanded like views. Multi-statement TVFs are black boxes with a hardcoded row estimate.
  • BEGIN in a function body means multi-statement — that's the tell.
  • Views store nothing. Only indexed views materialise, synchronously, at write cost.
  • Limit view nesting to one level.
  • SET NOCOUNT ON and SET XACT_ABORT ON in every procedure.
  • SCOPE_IDENTITY(), never @@IDENTITY.
  • Procedures are only injection-safe if they use parameters. sp_executesql, not EXEC.
  • Triggers are set-based and run in your transaction. Prefer temporal tables for history.
  • #temp for anything sizeable; table variables estimate one row.

Common mistakes

  • Scalar UDF in a SELECT or WHERE over a large table.
  • Multi-statement TVF where an inline one would work.
  • Views on views on views.
  • Missing SET NOCOUNT ON, adding a round trip per statement.
  • Missing SET XACT_ABORT ON, leaving transactions open after errors.
  • @@IDENTITY returning a trigger's identity value.
  • String concatenation in dynamic SQL inside a procedure.
  • Triggers assuming a single row.
  • Business logic in triggers, invisible to everyone reading the application.
  • Table variables holding large result sets.
  • RAISERROR instead of THROW, losing the original error.

Interview questions

Intermediate

Why are scalar functions a performance problem? 🔥 Must know
How I'd answer

"Three reasons, and the third is the one that catches people."

"Per-row execution. A scalar UDF in a SELECT list or WHERE clause is invoked once per row. If it contains a query — say an aggregate over another table — you've turned one query into a million."

"It forces a serial plan. This is the big one. A scalar UDF anywhere in the query makes the entire plan serial, including the parts that have nothing to do with the function. So a query that would have used eight cores now uses one."

"The cost is invisible. Pre-2019, execution plans attribute almost no cost to the UDF. So you look at the plan, see nothing obviously wrong, and the query is still slow. You have to know to look for it — that's why it's such a common hidden problem."

"There's also a SARGability angle: a UDF wrapped around an indexed column in WHERE means no index seek, because the index is sorted by the raw value, not the function's output."

"The fix is to make it set-based — usually rewriting the function's logic as a join to a derived table or a CASE expression in the outer query. Or convert it to an inline table-valued function and CROSS APPLY it, because inline TVFs are expanded into the calling query and optimised as one unit."

"On SQL Server 2019 and later there's scalar UDF inlining at compatibility level 150, which rewrites simple scalar UDFs into the query and largely fixes this. But it only applies to inlineable functions — no loops, no cursors, no EXEC, various other restrictions. So I'd check sys.sql_modules.is_inlineable rather than assume it's handled, and I'd still write it set-based if I had the choice."

What they're really checking
  • Do you know about the serial plan, not just per-row execution?
  • Do you know the cost is hidden in the plan?
  • Are you aware of 2019 inlining and its limits?
Likely follow-ups
  • Inline vs multi-statement TVF?
  • How would you find scalar UDFs hurting a workload?
  • Rewrite this UDF set-based.
When would you use a trigger? ⭐ Senior-level
How I'd answer

"Rarely, and I'd want a specific reason — because triggers are invisible logic on the write path."

"The problems: a trigger runs inside the transaction of the statement that fired it, so it makes every write slower and holds locks longer. If it errors, the original statement rolls back — meaning a bug in your audit logic stops orders being placed. They cascade up to 32 levels deep, which is miserable to debug. And nobody reading the application code has any reason to know they exist."

"The bug I'd specifically call out: triggers are set-based, not row-based. inserted and deleted contain all affected rows. So SELECT @id = Id FROM inserted works perfectly in testing with single-row updates, and then a 1,000-row batch update silently audits one arbitrary row and loses 999. That's a data-loss bug that passes every test."

"Where I'd still use one: auditing that must hold even for writes that bypass the application — a support engineer running an UPDATE, a migration script, a second application. That's the same argument as constraints over application validation, and it's genuinely valid."

"Also enforcing an invariant a constraint can't express, or making a legacy schema change work without touching old callers."

"Where I wouldn't: business logic, notifications, or maintaining denormalized aggregates on a hot table. Notifications should use the outbox pattern — write the intent in the same transaction, publish after commit — so a failing email doesn't roll back an order."

"And for the most common case, auditing, I'd reach for temporal tables now instead. The engine maintains full row history, it handles set-based updates correctly by construction, and there's no trigger code to get wrong. If the requirement is 'keep history of this table', writing a trigger for it in 2024 is doing work the engine already does."

What they're really checking
  • Do you know triggers are set-based? That's the bug that matters.
  • Do you know they run in the caller's transaction?
  • Do you know temporal tables exist?
  • Can you name a legitimate use rather than just dismissing them?
Likely follow-ups
  • Write a correct set-based audit trigger.
  • How do temporal tables work?
  • INSTEAD OF vs AFTER triggers?

Advanced / scenario

Should business logic live in stored procedures or application code? ⭐ Senior-level
How I'd answer

"My default is domain logic in the application, set-based data work in SQL — and I'd treat 'everything in procedures' and 'never write SQL' as two failure modes rather than two camps."

"The case for application code: it's version-controlled with the feature that needs it, the compiler helps when you refactor, it's testable without a database, and it's where the domain model lives so the logic sits next to the concepts it operates on. For most business rules that's decisive."

"The case for SQL is narrower but real. Set-based work — a bulk update over a million rows, a complex aggregation, a data migration. An ORM does that row by row and it's orders of magnitude slower. Total control over the query when you need a specific plan, a hint, or an indexed-view match. Fixing production without a deployment, which occasionally matters a great deal. And a smaller permissions surface — you can grant EXECUTE on a procedure without granting any table access, which is genuinely useful in regulated environments."

"One myth I'd correct: 'procedures are faster because plans are cached'. That was true long ago. SQL Server caches plans for parameterised ad-hoc queries too, and EF Core parameterises everything. It's not a reason to choose procedures today."

"The concrete failure mode of all-in-procedures: logic scattered across 400 procedures with no compiler checking, no unit tests, and no way to know what calls what. Renaming a column becomes a text search. I've worked in that and it's very slow to change safely."

"The concrete failure mode of never-write-SQL: someone loads 50,000 entities into memory to compute a sum, or a nightly job takes six hours because it does row-by-row updates through the ORM."

"So in practice: EF Core for CRUD and the domain model, raw SQL or a procedure for the handful of places where set-based or plan control matters — and those live in version control as migration scripts, not as objects someone edited in Management Studio, because that's the part that actually causes pain."

What they're really checking
  • Do you have a defensible position, or a dogmatic one?
  • Can you name the failure modes of both extremes?
  • Do you know the plan-cache argument is outdated?
  • Do you raise version control for procedures?
Weak answers
  • Red flag: "procedures are faster" as the main argument.
  • Red flag: "never use stored procedures" with no acknowledgement of bulk operations.
Likely follow-ups
  • How do you version-control procedures?
  • How do you do a bulk update efficiently from .NET?
  • How do you test a procedure?
