Partitioning, Replication & Recovery

Scaling the database, and being able to get it back. The second half is what actually ends careers.

🔴 Advanced ⭐ Senior-level 💡 Good to know
Quick revision
  • Partitioning is not a performance feature. Its real value is manageability — near-instant archiving via partition switching.
  • Scale reads with replicas; scale writes by sharding. Only one of those is easy.
  • RPO = how much data you can lose. RTO = how long you can be down. Everything else follows from those two numbers.
  • Full + differential + log backups give point-in-time recovery. Log backups are what make the RPO small.
  • An untested backup is not a backup. Restore is the only real test.
  • Simple recovery model = no log backups = you lose everything since the last full backup.
  • Replicas are asynchronous by default — reading from one means reading slightly stale data.

Table partitioning 🔴 Advanced

In simple terms

Partitioning splits one logical table into several physical pieces, usually by date range.

Queries and application code don't change at all — it's still one table name.

The misconception worth correcting in an interview

Partitioning is primarily a manageability feature, not a performance feature.

Partition elimination does help — a query filtered on the partition key skips irrelevant partitions. But a good index gives you most of the same benefit with far less complexity.

Where partitioning is genuinely transformative is partition switching: moving an entire partition in or out of a table is a metadata operation. Archiving a month of data goes from a multi-hour, log-flooding DELETE to something that completes in under a second.

Saying "I'd partition this to make queries faster" is the answer they're listening for as a mistake.

-- 1. Function: where the boundaries are
CREATE PARTITION FUNCTION pf_Monthly (datetime2(3))
AS RANGE RIGHT FOR VALUES
   ('2024-01-01', '2024-02-01', '2024-03-01', '2024-04-01');

-- 2. Scheme: which filegroup each partition lives on
CREATE PARTITION SCHEME ps_Monthly
AS PARTITION pf_Monthly ALL TO ([PRIMARY]);

-- 3. Table on the scheme. The partition column MUST be in every unique index.
CREATE TABLE dbo.OrderHistory
(
    Id         bigint       NOT NULL,
    CreatedUtc datetime2(3) NOT NULL,
    Total      decimal(19,4) NOT NULL,
    CONSTRAINT PK_OrderHistory PRIMARY KEY CLUSTERED (CreatedUtc, Id)
) ON ps_Monthly(CreatedUtc);
-- Staging table: identical structure, same filegroup, same indexes
CREATE TABLE dbo.OrderHistory_Archive_202401 (...);

-- Metadata-only. No data is copied, no rows are logged.
ALTER TABLE dbo.OrderHistory
    SWITCH PARTITION 2 TO dbo.OrderHistory_Archive_202401;

-- Now drop, compress, or move that table wherever you like.
Partitioning gives youPartitioning costs you
Near-instant archive and purge via switchingThe partition column must be in every unique index — including the PK
Partition-level index rebuildsReal complexity: functions, schemes, filegroups, a sliding-window job
Partition-level compression (cold data compressed, hot not)Queries not filtering on the partition key can get slower
Piecemeal restore of just the hot partitionsStatistics are per-table by default, so estimates on huge tables can suffer
RANGE RIGHT vs RANGE LEFT, and the empty-partition rule

RANGE RIGHT puts the boundary value in the right (later) partition. With date boundaries that's what you want — '2024-02-01' belongs to February, not January. RANGE LEFT with dates leads to off-by-one bugs that are hard to spot.

And always split an empty partition. Splitting a partition containing data moves every row and is fully logged — the exact expensive operation you adopted partitioning to avoid. A sliding-window job should add the next empty partition ahead of time, not when data arrives.

Senior signal — "scale up first" is often correct

Doubling the size of a managed database instance takes minutes and needs no architectural change. Sharding takes months and permanently increases the complexity of everything.

A modern single instance handles a genuinely large workload. Most applications that "need sharding" actually need three indexes and to stop running reports against the primary.

Reaching for distributed architecture before exhausting the cheap options is a common over-engineering signal — and saying so is a strong senior answer, provided you also know where the ceiling is and what you'd do when you hit it.

Replication lag is a correctness problem, not just latency

// Write goes to the primary
await _writeDb.Orders.AddAsync(order);
await _writeDb.SaveChangesAsync();

// Redirect to the order page - which reads from a replica
return RedirectToAction("Details", new { id = order.Id });

// The replica hasn't received it yet -> 404 on the order the user just created
MitigationHow it works
Read from primary after a writeSticky-to-primary for that user for a few seconds. Simple and effective
Return the written entityDon't re-read at all — you already have it
Route by intentReporting and search → replica; anything in a write flow → primary
Synchronous commitNo lag, but write latency now includes the replica round trip
Remember this

Replicas are for workloads that tolerate stale data.

Dashboards, reports, search, exports, analytics — yes. Anything the user is about to read back after writing — no.

Deciding this per query, deliberately, is the whole skill. A global "reads go to the replica" switch is how you ship intermittent 404s.

Synchronous vs asynchronous commit — the actual trade

Synchronous: the primary waits for the secondary to harden the log before acknowledging the commit. Zero data loss on failover, and every write pays the network round trip. Practical only within a datacentre or availability zone.

Asynchronous: the primary commits immediately. Writes are fast and you can replicate across regions, but a failover loses whatever hadn't shipped.

So the common production shape is synchronous within the region for HA and asynchronous to another region for disaster recovery. That's a good concrete answer, because it shows the two requirements are different.

HA is not backup

A replica faithfully replicates DELETE FROM Orders with no WHERE clause. Within seconds every copy is equally wrong.

HA protects against infrastructure failure. Backups protect against mistakes, corruption and ransomware. You need both, and confusing them is a genuinely dangerous mistake.

Backup and recovery 🔥 Must know

Start with the two numbers

RPO — Recovery Point Objective: how much data can we afford to lose? Determines backup frequency.

RTO — Recovery Time Objective: how long can we be down? Determines backup strategy and where the copies live.

Both come from the business, not from you. Everything technical follows from them.

Backup typeContainsRestore role
FullThe entire databaseThe baseline. Everything builds on it
DifferentialAll changes since the last fullReduces how many log backups you must apply
Transaction logAll log records since the last log backupPoint-in-time recovery. This is what makes RPO small
The standard strategy

Weekly full → daily differential → log backups every 5–15 minutes.

Restore order: full, then the latest differential, then every log backup after it, in order, to the moment you want.

The log interval is your RPO. Want to lose at most 5 minutes? Back up the log every 5 minutes.

Recovery models

ModelLog backupsPoint-in-time restoreUse for
FullRequiredYesAny production database
SimpleNot possibleNoDev, test, rebuildable data warehouses
Bulk-loggedYesLimited during bulk operationsTemporarily, during a large load
Two failure modes that recur constantly

1. Simple recovery in production. Someone switched it to "stop the log growing". The log stops growing because it's truncated at each checkpoint — and now log backups are impossible, so the RPO is silently "since the last full backup". Often discovered during an incident.

2. Full recovery with no log backups. The mirror image: the model is correct but nobody configured log backups, so the log grows forever until the disk fills and the database stops accepting writes. Then someone shrinks the log, which fixes nothing and fragments everything.

Both are really the same mistake — treating the log as a nuisance rather than as the mechanism that makes point-in-time recovery possible.

Test the restore, not the backup

Senior signal

A backup job reporting success proves a file was written. It does not prove the file is restorable, that you have the right encryption key, that anyone knows the procedure, or that the restore fits inside the RTO.

Things I'd want in place:

  • Automated restore to a separate environment, regularly. This is the only real test, and it also gives you a realistic dataset for testing.
  • RESTORE VERIFYONLY plus CHECKSUM as a cheap continuous check.
  • A measured RTO. "We can restore" means nothing without "in 40 minutes" — and a 2 TB restore over a network is not fast.
  • Offsite and immutable copies. Ransomware encrypts network-reachable backups too. Immutability is what makes a backup ransomware-proof.
  • A written, tested runbook. During an incident nobody invents a restore procedure correctly.
RESTORE DATABASE MyDb FROM DISK = 'full.bak'
    WITH NORECOVERY, REPLACE;                  -- stay in restoring state

RESTORE DATABASE MyDb FROM DISK = 'diff.bak'
    WITH NORECOVERY;

RESTORE LOG MyDb FROM DISK = 'log1.trn' WITH NORECOVERY;
RESTORE LOG MyDb FROM DISK = 'log2.trn'
    WITH STOPAT = '2024-06-01T14:32:00', RECOVERY;   -- stop just before the mistake
Recovering from a bad DELETE without downtime

Don't restore over the live database. Restore a copy to the moment before the mistake, then copy the affected rows back.

Far less disruptive, and it doesn't discard the legitimate work that happened after the mistake — which a straight point-in-time restore of the production database would throw away.

Sharding — the last resort 🔴 Advanced

In simple terms

Sharding splits data across multiple databases by some key — tenant, customer, region. It's the only way to scale writes beyond one machine.

It also removes cross-shard joins, cross-shard transactions and cross-shard uniqueness. Permanently.

You loseConsequence
Cross-shard joinsAggregate in the application, or maintain a separate reporting store
Cross-shard transactionsNeed sagas
Global uniquenessNeed a distributed ID scheme
Simple schema changesNow a rolling operation across N databases
Even loadHot shards — one large tenant can outgrow its shard
Choosing the shard key is the decision you can't take back

Resharding a live system is one of the hardest operations in this business. So the key has to be right the first time.

You want a key that appears in nearly every query, distributes evenly, and matches your natural consistency boundary. Tenant ID in a B2B SaaS is the classic good example — most queries are already scoped to a tenant, so almost nothing needs to cross shards.

A bad key means every query fans out to every shard, which is slower than the single database you started with. See multi-tenant SaaS for the tenancy angle.

Key takeaways
  • Partitioning is for manageability — switching makes archiving instant. It's not primarily a performance feature.
  • Always split empty partitions, and use RANGE RIGHT for dates.
  • Scale up and add indexes before considering distribution.
  • Replicas serve stale-tolerant reads. Route per query, never globally.
  • Sync commit within a region for HA, async across regions for DR.
  • HA is not backup — a replica replicates your mistakes perfectly.
  • RPO and RTO are business decisions; the backup strategy follows from them.
  • Log backup interval = your RPO.
  • Simple recovery model means no point-in-time restore. Check this on every production database.
  • Only a tested restore counts, and immutable offsite copies are what survive ransomware.

Common mistakes

  • Partitioning for performance when an index would do.
  • Splitting a partition that contains data, causing a fully-logged data movement.
  • Routing all reads to a replica, producing intermittent read-your-own-writes bugs.
  • Treating HA as backup.
  • Production databases in simple recovery.
  • Full recovery model with no log backups, filling the disk.
  • Shrinking the log routinely instead of backing it up.
  • Never testing a restore.
  • Backups only on network shares reachable from the compromised server.
  • Sharding before scaling up or fixing indexes.

Interview questions

Intermediate

Design a backup strategy for a system that can lose at most 5 minutes of data. 🔥 Must know
How I'd answer

"Five minutes is the RPO, so that directly sets the log backup interval: transaction log backups every 5 minutes. That's the only mechanism that gives point-in-time recovery, so it has to be in place."

"The prerequisite is that the database is in the full recovery model. In simple recovery, log backups aren't possible at all, so the RPO would silently be 'since the last full backup' — worth verifying explicitly, because I've seen production databases in simple recovery that nobody knew about until an incident."

"Then a weekly full backup and daily differentials. The differentials aren't about RPO, they're about RTO — without them a restore has to replay a week of log backups, which could be 2,000 files. With daily diffs it's the full, one diff, and at most a day of logs."

"Then I'd ask about RTO, because it's the number people forget. If the requirement is 15 minutes and the database is 2 TB, log shipping to a warm standby or an availability group isn't optional — a restore from files won't finish in time no matter how the backups are arranged. If RTO is 4 hours, restoring from backup is fine."

"Beyond the schedule, the parts that actually determine whether this works:"

"Automated restore testing. A successful backup job proves a file was written. It doesn't prove the file is restorable, that we have the encryption key, or that the restore fits in the RTO. I'd restore to a separate environment on a schedule and verify — which conveniently also gives us a realistic dataset for testing."

"Offsite and immutable copies. Ransomware encrypts backups on reachable network shares. Immutability — write-once storage with a retention lock — is what makes a backup actually survive that."

"Backup CHECKSUM and RESTORE VERIFYONLY as a cheap continuous validity check, plus regular DBCC CHECKDB, because backing up an already-corrupt database just gives you corrupt backups."

"A written runbook, and monitoring that alerts on a missed backup — not just a failed one. A job that silently stopped running is the common case."

"And I'd separate HA from backup explicitly. An availability group gives fast failover for infrastructure failure, but a replica faithfully replicates a bad DELETE within seconds. Backups are what protect against mistakes, corruption and ransomware. We need both, for different reasons."

What they're really checking
  • Do you connect RPO to log backup frequency?
  • Do you ask about RTO, not just RPO?
  • Do you know differentials are an RTO optimisation?
  • Do you talk about testing restores and immutability?
  • Do you distinguish HA from backup?
Weak answers
  • Red flag: "nightly full backups" for a 5-minute RPO.
  • Red flag: no mention of testing the restore.
  • Red flag: "we have a replica, so we're covered."
Likely follow-ups
  • Someone deleted a table 20 minutes ago. Walk me through recovery.
  • What's the restore order and why?
  • How do you handle a 5 TB database within a 30-minute RTO?

Advanced / scenario

A 900-million-row table is causing problems. Would you partition it? ⭐ Senior-level
How I'd answer

"My first question is what problem specifically, because partitioning solves a narrow set of problems and people usually reach for it expecting a general speed-up."

"If the problem is slow queries, partitioning is probably the wrong tool. I'd look at indexes first. Partition elimination helps only when the query filters on the partition key, and a good index on that same column gives most of the same benefit with none of the complexity. I'd want to see the plans before agreeing to partition anything."

"If the problem is archiving or purging — that's where partitioning is genuinely transformative. Deleting 30 million old rows normally means a long-running, fully-logged operation that escalates to a table lock and blocks the application. With partitioning, SWITCH PARTITION moves the whole partition out as a metadata operation — under a second, barely any log. That alone can justify the complexity."

"If the problem is maintenance windows — index rebuilds or statistics updates taking too long — partitioning lets you rebuild one partition at a time, which fits in a window."

"If the problem is storage cost, partitioning lets you compress cold partitions heavily and leave the hot one uncompressed. That's a real win on a table where 95% of the data is never read."

"So my answer depends on the answer to that first question. Assuming it's archiving, I'd partition by month on the date column, and be clear about the costs upfront:"

"The partition column must be in every unique index including the primary key, which often means changing the PK — a real migration on a 900-million-row table, not a quick change. Queries that don't filter on the partition key can get slower, because they now touch every partition. And it needs a sliding-window job to add future partitions and switch out old ones, which is operational code somebody has to own."

"Two implementation details I'd get right because they're easy to get wrong: use RANGE RIGHT so a boundary date falls in the later partition — RANGE LEFT with dates causes off-by-one bugs — and always split empty partitions. Splitting one that contains data moves every row and is fully logged, which is exactly the operation we adopted partitioning to avoid."

"Before any of that though, I'd ask the cheaper questions: does all 900 million rows need to be in the live table at all? If 95% is historical and rarely queried, moving it to a separate archive table or a cheaper store may solve the problem outright, with far less complexity than partitioning. And batched deletes in a loop handle purging adequately for many workloads — a few thousand rows per transaction, staying under the lock escalation threshold."

What they're really checking
  • Do you ask what problem you're solving?
  • Do you know partitioning is manageability-first, not performance-first?
  • Do you know switching is the real win?
  • Do you name the PK constraint and the sliding-window job?
  • Do you consider simpler options first?
Weak answers
  • Red flag: "yes, partitioning makes queries faster."
  • Red flag: no mention of the unique-index requirement.
  • Red flag: jumping to partitioning without looking at indexes.
Likely follow-ups
  • How does partition switching actually work?
  • What breaks if the PK doesn't include the partition column?
  • How would you do the migration with minimal downtime?
Reads are overloading the primary. How do you scale? ⭐ Senior-level
How I'd answer

"I'd go cheapest-first, because the expensive options are also the irreversible ones."

"First, find out what the reads actually are. Very often a small number of queries account for most of the load — a missing index causing scans, or an N+1 pattern generating thousands of tiny queries per request. Fixing those can remove the problem entirely, and it's hours of work rather than weeks."

"Second, is reporting running against the primary? That's an extremely common cause, and it's a routing decision rather than an architectural one. Analytical queries scanning large tables alongside OLTP traffic is the classic pattern here."

"Third, caching. A read that never reaches the database is the cheapest possible read. Reference data, lookup tables, expensive aggregates — all good candidates. The hard part is invalidation, so I'd start with things where a short TTL is acceptable rather than trying to build precise invalidation everywhere."

"Fourth, scale up. Unglamorous and frequently correct. Doubling instance size takes minutes, needs no code change, and is trivially reversible. Compared to any distributed option it's almost free — I'd want a clear reason not to do this before moving on."

"Fifth, read replicas. Now we're changing the application's consistency model, so this needs care. The critical rule is route per query, not globally. Replicas are asynchronous, so a global 'reads go to the replica' switch produces read-your-own-writes bugs — the user creates an order, gets redirected to it, and sees a 404 because the replica hasn't caught up. Intermittent, environment-dependent, and miserable to debug."

"So I'd route deliberately: reporting, search, exports and dashboards to the replica; anything in a write flow to the primary. And where a user has just written something, either return the entity I already have rather than re-reading, or pin that user to the primary for a few seconds."

"Sixth, a dedicated read model — a denormalized shape built for the queries, updated asynchronously. More moving parts, but it's the right answer when the read pattern is genuinely different from the write pattern, like a search or analytics surface."

"Sharding I'd treat as a separate conversation, because it's for write scaling, not read scaling. If reads are the problem, sharding is a lot of permanent complexity aimed at the wrong bottleneck."

"The thing I'd emphasise is that steps one to four are reversible and cheap, and step five changes the consistency guarantees the whole application relies on. So I'd want to have genuinely exhausted the cheap options before making that trade — not because replicas are bad, but because 'we added replicas' is a much harder thing to undo than 'we added an index'."

What they're really checking
  • Do you diagnose before scaling?
  • Do you consider scale-up rather than jumping to distribution?
  • Do you know replication lag is a correctness issue?
  • Do you route per query rather than globally?
  • Do you separate read scaling from write scaling?
Weak answers
  • Red flag: "shard it" for a read problem.
  • Red flag: replicas with no mention of lag.
  • Red flag: skipping straight past indexing and caching.
Likely follow-ups
  • How do you implement read-your-own-writes with a replica?
  • How do you decide cache TTLs?
  • When does scale-up stop being an option?
