Querying

Joins, CTEs and window functions. Most SQL interview questions are really testing whether you understand logical processing order.

🟢 Beginner 🟡 Intermediate 🔥 Must know
Quick revision
  • Logical order: FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY. This explains almost every "why can't I…" question.
  • WHERE filters rows; HAVING filters groups.
  • A filter on the right table in a WHERE clause turns a LEFT JOIN into an INNER JOIN. Put it in the ON instead.
  • Window functions don't collapse rows. That's the whole point of them versus GROUP BY.
  • ROW_NUMBER vs RANK vs DENSE_RANK differ only in how they handle ties.
  • A CTE is not a temp table. It's usually inlined, and it can be evaluated more than once.
  • OFFSET pagination degrades as the offset grows. Keyset doesn't.

Logical processing order 🔥 Must know

In simple terms

SQL isn't executed in the order you write it. It's evaluated in this order:

#ClauseWhat exists at this point
1FROM / JOINRows are combined
2WHEREIndividual rows filtered. No groups yet, no aliases from SELECT
3GROUP BYRows collapse into groups
4HAVINGGroups filtered. Aggregates now available
5SELECTOutput columns and aliases created here
6ORDER BYAliases available, because SELECT already ran
7OFFSET / FETCHThe window of rows is taken
Remember this — it answers three separate interview questions
  • Why can't I use a SELECT alias in WHERE? — the alias doesn't exist yet (step 5 vs step 2).
  • But it works in ORDER BY? — yes, that's step 6, after SELECT.
  • Why can't I use COUNT(*) in WHERE? — grouping hasn't happened. Use HAVING.

Joins 🔥 Must know

JoinReturns
INNER JOINOnly rows matching on both sides
LEFT JOINAll left rows; NULLs where no match
RIGHT JOINSame, mirrored. Rare — people rewrite as LEFT for readability
FULL OUTER JOINEverything from both sides
CROSS JOINCartesian product — every combination
CROSS APPLYLike INNER JOIN, but the right side can reference the left row
OUTER APPLYLike LEFT JOIN with that same capability
The classic trap — the LEFT JOIN that isn't
SELECT c.Name, o.Total
FROM      Customer c
LEFT JOIN [Order]  o ON o.CustomerId = c.Id
WHERE o.Status = 'Shipped';           -- ← destroys the LEFT JOIN

Customers with no orders get NULL for o.Status, and NULL = 'Shipped' is unknown — so those rows are filtered out. You've written a LEFT JOIN and got an INNER JOIN.

SELECT c.Name, o.Total
FROM      Customer c
LEFT JOIN [Order]  o ON o.CustomerId = c.Id
                    AND o.Status     = 'Shipped';

The rule: conditions on the outer (right) table belong in ON. Conditions on the preserved (left) table belong in WHERE.

This is asked constantly, because it separates people who've memorised join diagrams from people who understand what the filter is doing.

APPLY — the underused one 🔴 Advanced

In simple terms

APPLY runs the right-hand expression once per left row, and the expression can reference that row's columns.

A normal JOIN can't do that. This is how you do "top N per group" cleanly.

SELECT c.Name, o.OrderId, o.CreatedUtc, o.Total
FROM Customer c
CROSS APPLY (
    SELECT TOP (3) OrderId, CreatedUtc, Total
    FROM   [Order]
    WHERE  CustomerId = c.Id          -- references the outer row
    ORDER BY CreatedUtc DESC
) o;
APPLY vs ROW_NUMBER for top-N-per-group

Both work. The difference is where the work happens.

ROW_NUMBER numbers every row, then discards all but the top few. CROSS APPLY does a small seek per customer and stops at 3.

With a supporting index on (CustomerId, CreatedUtc DESC), APPLY is usually much faster on large tables. With few groups and many rows each, or no useful index, ROW_NUMBER can win. Knowing there's a choice — and why — is the senior answer.

Fan-out: the duplicate-rows surprise

SELECT c.Name, SUM(o.Total) AS Revenue
FROM Customer c
JOIN [Order]     o ON o.CustomerId = c.Id
JOIN OrderLine   l ON l.OrderId    = o.Id      -- one row per LINE
GROUP BY c.Name;                                -- Total counted once per line
What happened

Joining to OrderLine multiplied each order row by its number of lines. An order with 4 lines now contributes its Total four times.

Any time you join to a "many" table and then aggregate, check for fan-out. Aggregate in a subquery or APPLY before joining.

Subqueries: EXISTS, IN, JOIN 🟡 Intermediate

FormSemanticsUse when
EXISTSTrue on the first match; handles nulls correctlyDefault choice for "does a related row exist?"
INValue in a set. Breaks with nulls when negatedSmall literal lists
JOINCombines rows — can duplicate the left sideYou need columns from the other table
Remember this

Need columns from the other table? JOIN. Just checking existence? EXISTS.

Using a JOIN for existence checks is how you get accidental duplicates and reach for DISTINCT to hide them.

SELECT DISTINCT c.Id, c.Name          -- DISTINCT is hiding a bug
FROM Customer c
JOIN [Order] o ON o.CustomerId = c.Id;
SELECT c.Id, c.Name
FROM Customer c
WHERE EXISTS (SELECT 1 FROM [Order] o WHERE o.CustomerId = c.Id);
NOT IN with nullable columns

If the subquery returns even one NULL, NOT IN returns zero rows — no error, no warning. Covered in detail on the fundamentals page.

Habit: use NOT EXISTS.

CTEs 🟡 Intermediate

In simple terms

A CTE (WITH ... AS) is a named subquery that makes a query readable by naming its steps.

It is not a temp table. In SQL Server the definition is usually inlined into the outer query.

WITH MonthlyRevenue AS (
    SELECT CustomerId,
           DATEFROMPARTS(YEAR(CreatedUtc), MONTH(CreatedUtc), 1) AS Month,
           SUM(Total) AS Revenue
    FROM   [Order]
    WHERE  CreatedUtc >= '2024-01-01'
    GROUP BY CustomerId, DATEFROMPARTS(YEAR(CreatedUtc), MONTH(CreatedUtc), 1)
),
Ranked AS (
    SELECT *, ROW_NUMBER() OVER (PARTITION BY Month ORDER BY Revenue DESC) AS rn
    FROM   MonthlyRevenue
)
SELECT Month, CustomerId, Revenue
FROM   Ranked
WHERE  rn <= 5
ORDER BY Month, Revenue DESC;
The CTE misconception that causes real bugs

Referencing a CTE twice can execute it twice.

WITH Expensive AS (SELECT ... /* heavy aggregation */ ...)
SELECT * FROM Expensive a JOIN Expensive b ON b.Month = a.Month;
-- The heavy work may run twice, not once

Worse, if the CTE contains a non-deterministic expression such as NEWID() or GETDATE(), the two evaluations can return different values — which produces genuinely baffling bugs.

If you need it materialised once, use a #temp table.

CTE#temp tableTable variable
MaterialisedNo — usually inlinedYesYes (in tempdb)
StatisticsFrom the base tablesYes — real statisticsNone (estimates 1 row)
IndexableNoYesPK/unique only
Best forReadability, recursionLarge intermediate sets, reuseSmall sets, table-valued params
Senior signal

"I'd switch that CTE to a #temp table" is a strong, specific tuning move — because a temp table gets real statistics, so the optimiser knows how many rows it actually holds.

A chain of five CTEs over millions of rows often produces a terrible plan for exactly this reason: the estimates compound and drift further from reality at every level. Breaking the chain with one temp table gives the optimiser a fresh, accurate starting point.

Table variables are the opposite trap — they estimate one row regardless of content, which is fine for 10 rows and catastrophic for 100,000.

Recursive CTEs

WITH OrgChart AS (
    -- Anchor: the starting point
    SELECT Id, Name, ManagerId, 0 AS Depth
    FROM   Employee
    WHERE  ManagerId IS NULL

    UNION ALL

    -- Recursive part: references the CTE itself
    SELECT e.Id, e.Name, e.ManagerId, o.Depth + 1
    FROM   Employee e
    JOIN   OrgChart o ON e.ManagerId = o.Id
)
SELECT * FROM OrgChart
ORDER BY Depth, Name
OPTION (MAXRECURSION 100);          -- guard against cycles
Always set MAXRECURSION

The default is 100, and hitting it raises an error mid-result. But the important case is cyclic data — employee A manages B who manages A. Without a bound that recurses forever, and MAXRECURSION 0 means unlimited, which is how you hang a production server.

Set an explicit sensible bound, and if hierarchies get deep or hot, consider storing a materialised path instead of recursing on every read.

Window functions 🔥 Must know

In simple terms

A window function computes a value across a set of related rows without collapsing them.

GROUP BY gives you one row per group. A window function keeps every row and adds the group's answer alongside.

Think of it this way

GROUP BY is a summary report: one line per department.

A window function is the full staff list with an extra column showing each person's department average next to their own salary — so you can compare.

-- GROUP BY: 5 departments -> 5 rows
SELECT Department, AVG(Salary) AS DeptAvg
FROM   Employee
GROUP BY Department;

-- Window: 500 employees -> 500 rows, each with its department average
SELECT Name, Department, Salary,
       AVG(Salary) OVER (PARTITION BY Department)            AS DeptAvg,
       Salary - AVG(Salary) OVER (PARTITION BY Department)   AS VsAvg
FROM   Employee;

Ranking functions — the tie question

FunctionTiesSequence with a tie at 2nd
ROW_NUMBER()Broken arbitrarily — always unique1, 2, 3, 4
RANK()Same rank, then skips1, 2, 2, 4
DENSE_RANK()Same rank, no gap1, 2, 2, 3
NTILE(4)Splits into bucketsQuartiles
Remember this

RANK skips, DENSE_RANK doesn't, ROW_NUMBER never ties.

Olympic medals are RANK — two silvers means no bronze. "Distinct salary levels" is DENSE_RANK. "Pick exactly one row per group" is ROW_NUMBER.

WITH Dupes AS (
    SELECT Id,
           ROW_NUMBER() OVER (PARTITION BY Email ORDER BY CreatedUtc DESC) AS rn
    FROM   Customer
)
DELETE FROM Dupes WHERE rn > 1;      -- deletes through the CTE

This is the canonical deduplication query, and a common interview task. ROW_NUMBER is essential here — RANK would tie both duplicates at 1 and delete neither.

LAG and LEAD

SELECT
    CreatedUtc,
    Total,
    LAG(Total)  OVER (ORDER BY CreatedUtc) AS PrevTotal,
    Total - LAG(Total) OVER (ORDER BY CreatedUtc) AS Change,
    LEAD(CreatedUtc) OVER (ORDER BY CreatedUtc) AS NextOrderDate
FROM [Order]
WHERE CustomerId = @customerId;

Month-over-month change, gap detection, time between events, state transitions — all of these are LAG/LEAD. Before window functions this required a self-join on a computed row number, which was slow and unreadable.

Running totals and frames 🔴 Advanced

SELECT
    CreatedUtc, Total,

    -- Running total: start of partition to current row
    SUM(Total) OVER (ORDER BY CreatedUtc
                     ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW) AS RunningTotal,

    -- 7-row moving average
    AVG(Total) OVER (ORDER BY CreatedUtc
                     ROWS BETWEEN 6 PRECEDING AND CURRENT ROW) AS MovingAvg7
FROM [Order];
ROWS vs RANGE — a real correctness difference

With an ORDER BY and no explicit frame, the default is RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW.

RANGE includes all peer rows with the same ordering value. So if three orders share a timestamp, a "running total" using the default jumps by all three at once and shows the same value on all three rows — not what a running total should look like.

ROWS counts physical rows and behaves as expected. Be explicit and prefer ROWS unless you specifically want peer-inclusive behaviour.

RANGE is also generally slower.

Where window functions can and can't go

They're evaluated at SELECT time, so you cannot reference one in WHERE, GROUP BY or HAVING of the same query level.

Wrap it in a CTE or subquery and filter outside — which is exactly why the top-N-per-group pattern always has two levels.

Grouping 🟡 Intermediate

SELECT   CustomerId, COUNT(*) AS Orders, SUM(Total) AS Revenue
FROM     [Order]
WHERE    CreatedUtc >= '2024-01-01'   -- filters ROWS, before grouping
GROUP BY CustomerId
HAVING   COUNT(*) > 5                  -- filters GROUPS, after
ORDER BY Revenue DESC;
Performance note that's easy to state and easy to forget

Filter in WHERE whenever you can. It removes rows before grouping, so there's less to group.

A condition in HAVING that doesn't involve an aggregate is a mistake — it groups everything and then throws groups away.

SELECT   Region, Product, SUM(Total) AS Revenue
FROM     Sales
GROUP BY GROUPING SETS (
    (Region, Product),   -- detail
    (Region),            -- per-region subtotal
    ()                   -- grand total
);

One pass instead of three queries and a UNION. ROLLUP is the shorthand for a hierarchy; CUBE gives every combination. GROUPING() tells you whether a NULL is a subtotal marker or real data.

Aggregating strings

SELECT o.Id,
       STRING_AGG(l.Sku, ', ') WITHIN GROUP (ORDER BY l.Sku) AS Skus
FROM   [Order] o
JOIN   OrderLine l ON l.OrderId = o.Id
GROUP BY o.Id;

Before 2017 this needed the FOR XML PATH trick, which you'll still see in older codebases — and which breaks on data containing & or <.

Pagination ⭐ Senior-level

SELECT Id, CreatedUtc, Total
FROM   [Order]
ORDER BY CreatedUtc DESC
OFFSET 100000 ROWS FETCH NEXT 20 ROWS ONLY;
-- Reads and discards 100,000 rows to return 20
SELECT TOP (20) Id, CreatedUtc, Total
FROM   [Order]
WHERE  (CreatedUtc < @lastCreatedUtc)
   OR  (CreatedUtc = @lastCreatedUtc AND Id < @lastId)   -- tiebreak
ORDER BY CreatedUtc DESC, Id DESC;
OFFSETKeyset
Cost at page 5000Grows linearly — reads everything skippedConstant
Jump to page NYesNo — next/previous only
Total page countYesNot without a separate count
Stable under insertsNo — rows shift, items are skipped or repeatedYes
Remember this

Numbered page links → OFFSET. Infinite scroll or an API feed → keyset.

The tiebreaker column is mandatory. Without it, rows sharing a timestamp get skipped or duplicated at page boundaries.

Set operations 🟢 Beginner

Reconciliation trick worth remembering

To check two tables hold the same data:

(SELECT * FROM A EXCEPT SELECT * FROM B) UNION ALL (SELECT * FROM B EXCEPT SELECT * FROM A)

Empty result means identical. Very useful when validating a migration or a denormalized copy — and EXCEPT compares NULLs as equal, which is exactly what you want here and what a join comparison gets wrong.

MERGE — use with caution 🔴 Advanced

MERGE does insert/update/delete in one statement. It reads well, and it has a long history of bugs and concurrency problems.

Why many teams avoid it

MERGE is not atomic against concurrent writers by default — two concurrent merges on the same key can deadlock or both attempt an insert, giving a primary-key violation. You need HOLDLOCK/SERIALIZABLE on the target to make it safe.

It also has a documented history of incorrect-results bugs with filtered indexes and partitioned tables.

For a single-row upsert, an explicit UPDATE then INSERT IF NOT EXISTS inside a transaction — or an insert that catches the unique violation — is easier to reason about. Being aware of this is a good senior signal, because MERGE looks like the obvious right answer.

Key takeaways
  • Logical order explains alias scope, WHERE vs HAVING, and where window functions can go.
  • Filtering the outer table in WHERE silently converts LEFT JOIN to INNER. Filter in ON.
  • CROSS APPLY can reference the outer row — the clean top-N-per-group tool.
  • Joining to a "many" table then aggregating causes fan-out and wrong totals.
  • EXISTS for existence, JOIN for columns. DISTINCT is often hiding a fan-out.
  • A CTE isn't materialised and may run twice. #temp gives real statistics.
  • Window functions keep rows; GROUP BY collapses them.
  • RANK skips, DENSE_RANK doesn't, ROW_NUMBER is always unique.
  • Be explicit with frames — ROWS, not the RANGE default.
  • Keyset pagination for feeds; OFFSET only for numbered pages.

Common mistakes

  • Filtering the right table of a LEFT JOIN in WHERE.
  • DISTINCT to hide join duplicates instead of fixing the join.
  • Aggregating after joining to a child table, so sums are multiplied.
  • NOT IN with a nullable subquery.
  • Assuming a CTE is materialised, or that it runs once.
  • Table variables for large sets — the optimiser estimates one row.
  • Non-aggregate conditions in HAVING that belong in WHERE.
  • Relying on the default RANGE frame for running totals.
  • OFFSET pagination on deep pages, and with no tiebreaker column.
  • UNION where UNION ALL would do, paying for a needless sort.
  • ORDER BY in a view or subquery — it isn't guaranteed to be preserved.

Interview questions

Basic

Difference between WHERE and HAVING? 🔥 Must know
How I'd answer

"WHERE filters individual rows before grouping. HAVING filters groups after grouping."

"The reason comes from the logical processing order — FROM, WHERE, GROUP BY, HAVING, SELECT, ORDER BY. At WHERE time there are no groups yet, so you can't reference an aggregate. By HAVING time the groups exist, so you can."

"So 'orders since January' goes in WHERE, and 'customers with more than five orders' goes in HAVING."

"There's a performance point too: put anything you can in WHERE, because it removes rows before the grouping work happens. A non-aggregate condition sitting in HAVING is a mistake — you group everything and then throw groups away."

"That same processing order answers two related questions, incidentally. You can't use a SELECT alias in WHERE because SELECT runs later — but you can in ORDER BY, because that's after SELECT. And you can't reference a window function in WHERE either, for the same reason, which is why top-N-per-group always needs a CTE or subquery wrapper."

What they're really checking
  • Do you know the logical order, or just memorise the rule?
  • Do you mention the performance implication?
Likely follow-ups
  • Why can't you use an alias in WHERE?
  • Can HAVING work without GROUP BY?

Intermediate

You wrote a LEFT JOIN but customers with no orders are missing. Why? 🔥 Must know
How I'd answer

"Almost certainly there's a filter on the right-hand table in the WHERE clause, which converts the LEFT JOIN into an INNER JOIN."

"The mechanism: the join does produce a row for the customer with no orders — with NULL in every order column. Then WHERE o.Status = 'Shipped' evaluates NULL = 'Shipped', which is unknown, not true. So the row is filtered out. The join worked; the WHERE undid it."

"The fix is to move the condition into the ON clause. There it's part of deciding what counts as a match, so unmatched customers are still preserved with nulls."

"The rule I keep in mind: conditions on the outer table go in ON; conditions on the preserved table go in WHERE."

"There's a legitimate use of the same mechanism, worth mentioning: LEFT JOIN ... WHERE o.Id IS NULL is the standard 'anti-join' — find customers with no orders. That's deliberately exploiting the null rows. Though these days I'd write it as NOT EXISTS, which says what it means and usually gets the same or a better plan."

What they're really checking
  • Do you understand why, in terms of nulls and three-valued logic?
  • Do you know the ON vs WHERE rule?
  • Bonus: do you know the anti-join pattern?
Likely follow-ups
  • Write me an anti-join.
  • What if the filter is on the left table instead?
  • Does this apply to FULL OUTER JOIN?
ROW_NUMBER vs RANK vs DENSE_RANK? 🔥 Must know
How I'd answer

"They differ only in how they treat ties."

"ROW_NUMBER always gives distinct sequential numbers — ties are broken arbitrarily, so you get 1, 2, 3, 4."

"RANK gives tied rows the same rank and then skips: 1, 2, 2, 4. That's Olympic medals — two silvers means no bronze."

"DENSE_RANK gives tied rows the same rank with no gap: 1, 2, 2, 3. That's what you want for 'how many distinct salary levels are above this person'."

"Which to use depends on what you're doing. For picking exactly one row per group — deduplication, latest-record-per-key, top-N-per-group — it has to be ROW_NUMBER, because it's the only one guaranteed to produce a single row with the value 1. If you used RANK for deduplication and two rows tied, both would get rank 1 and you'd delete neither."

"One practical note: because ROW_NUMBER breaks ties arbitrarily, the result isn't deterministic unless the ORDER BY inside the OVER clause is unique. So for deduplication I always add a tiebreaker like the primary key — otherwise re-running the same query can pick a different survivor, which makes it non-reproducible and awkward to test."

"And all three are evaluated at SELECT time, so you can't filter on them in the same query level — the rn <= 5 filter always needs a CTE or subquery around it."

What they're really checking
  • Can you state the tie behaviour precisely?
  • Do you know which one deduplication requires, and why?
  • Do you mention determinism and the tiebreaker?
Likely follow-ups
  • Write a query deleting duplicate emails, keeping the newest.
  • How would you get the 2nd highest salary per department?
  • How does CROSS APPLY compare for top-N-per-group?

Advanced / scenario

A report query with five chained CTEs takes 4 minutes. How do you approach it? ⭐ Senior-level
How I'd answer

"I'd get the actual execution plan first and compare estimated versus actual rows at each operator. With chained CTEs that's usually where the answer is."

"The reason is that a CTE isn't materialised — it's inlined into the outer query, so the optimiser produces one plan for the whole thing and has to estimate cardinality through five levels of transformation. Estimation error compounds. By level five it might think 100 rows and actually be handling 2 million, so it picks nested loops where it needed a hash join."

"So my first move is usually to break the chain with a #temp table at the point where the estimate first diverges badly. A temp table has real statistics, so everything downstream starts from an accurate row count. I've seen that alone take a query from minutes to seconds, without changing any logic."

"I'd also check whether any CTE is referenced more than once. If it is, the work may be executing twice — that's invisible in the SQL and obvious in the plan. Materialising it fixes that too."

"Then the usual suspects: is anything non-SARGable — a function wrapped around an indexed column? Any implicit conversions? Any spilling sorts or hash joins, which mean the memory grant was too small because of those bad estimates? And is there fan-out — a join to a child table before an aggregate, which both inflates the row count and can make the numbers wrong as well as slow."

"Something I'd raise beyond the query itself: if this is a report over transactional tables, the real answer might not be query tuning. It may be that reporting shouldn't run against the OLTP database at all — a read replica, a nightly denormalized table, or a proper read model. A 4-minute report also holding locks on live tables is a bigger problem than its runtime."

"And I'd want to know whether it's always slow or only sometimes. Intermittent points at parameter sniffing — a cached plan compiled for an unrepresentative parameter value — which is a completely different fix from a structural one."

What they're really checking
  • Do you start from evidence — the actual plan — rather than guessing?
  • Do you know why chained CTEs specifically cause estimation problems?
  • Do you know the temp-table-for-statistics move?
  • Do you consider whether the workload belongs there at all?
Weak answers
  • Red flag: "add indexes" with no diagnosis.
  • Red flag: thinking CTEs are temp tables.
  • Red flag: no mention of reading the plan.
Likely follow-ups
  • Why does a temp table have better statistics than a CTE?
  • When would a table variable be the wrong choice?
  • How do you stop the report blocking live writes?
