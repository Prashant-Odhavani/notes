Indexing

The single highest-leverage database skill. Most "the database is slow" problems are an index problem, and most index problems are a column-order problem.

🟡 Intermediate 🔴 Advanced 🔥 Must know
Quick revision
  • An index is a sorted copy of some columns plus a pointer back to the row. That one sentence explains almost everything else.
  • The clustered index is the table — one per table. Non-clustered indexes are separate structures that point back to it.
  • Column order in a composite index is everything. Equality columns first, then the range column, then sorting.
  • A covering index answers the query entirely from the index — no lookup back to the table.
  • Wrapping a column in a function kills the seek. That's the SARGability rule.
  • Every index slows writes and takes space. They're not free.
  • SELECT * defeats covering indexes — that's the real cost of it.

What an index actually is 🔥 Must know

Think of it this way

A phone book sorted by surname. Finding "Patel" takes seconds — you jump to P, then narrow down.

Now find everyone with the phone number 555-0142. You read the entire book, because it isn't sorted that way.

That's a seek versus a scan. Both search the same data; one uses the ordering and one can't.

In simple terms

An index is a separate, sorted structure containing the indexed columns plus a pointer back to the full row.

It's a B-tree, so lookups are logarithmic — a few page reads instead of millions. On a table with 10 million rows, that's roughly 3–4 reads instead of ~40,000.

OperationWhat it meansCost
Index seekNavigate the B-tree to the exact rowsLogarithmic. What you want
Index scanRead the whole indexLinear, but narrower than the table
Table / clustered index scanRead every rowLinear over the full table. Usually the problem
Key lookupFound it in a non-clustered index, now fetch remaining columnsPer row. Cheap once, expensive 100,000 times
A scan isn't always bad

If a query returns most of the table, scanning is cheaper than seeking — seeking 800,000 times plus 800,000 lookups is worse than reading the table once.

That's why the optimiser sometimes ignores your index, and it's a legitimate decision. A scan is only a problem when you expected a small result set and got a full read.

Clustered vs non-clustered 🔥 Must know

ClusteredNon-clustered
What it isThe table itself, stored in key orderA separate sorted copy of chosen columns
How manyOne per tableMany (SQL Server allows 999)
Leaf level holdsThe full rowIndex key + the clustering key as the pointer
Extra lookup?No — the data is thereYes, unless the index covers the query
Remember this

The clustered index is not a pointer to the data. It IS the data.

Which is why there's only one — a table can only be physically sorted one way.

Every non-clustered index stores the clustering key as its pointer. So a wide clustered key makes every other index on that table bigger.

Senior signal — why clustering key width matters

Cluster on a uniqueidentifier (16 bytes) instead of an int (4 bytes) and every non-clustered index row carries 12 extra bytes.

Ten indexes on a 50-million-row table: that's roughly 6 GB of pure overhead, which means more pages, more I/O, and less of the useful data fitting in memory.

"The clustering key is in every index" is the fact that makes this a senior-level answer rather than a definition.

What to cluster on

  • Narrow — it's duplicated into every other index.
  • Increasing — appends avoid page splits.
  • Unique — otherwise SQL Server silently adds a 4-byte uniquifier.
  • Static — updating a clustering key physically moves the row and updates every non-clustered index.

An int IDENTITY satisfies all four, which is why it's the default answer. See the GUID discussion for when the identity column and the primary key should be different columns.

Composite index column order 🔥 Must know

Think of it this way

A phone book sorted by (LastName, FirstName).

"Find Patel, Anita" — instant. "Find all the Patels" — instant, they're together.

"Find everyone called Anita" — useless. You read the whole book, because Anitas are scattered across every surname.

Remember this

A composite index can only be seeked on a left-to-right prefix of its columns.

(A, B, C) supports queries on A, (A,B), (A,B,C).

It does not support a seek on B alone, or C alone.

The ordering rule

  1. Equality columns first — anything compared with =.
  2. Then the range column — >, <, BETWEEN, LIKE 'x%'. Only one range column can be used efficiently.
  3. Then ORDER BY columns, so sorting is free.
  4. Then everything else as INCLUDE — not key columns.
SELECT OrderId, Total, CreatedUtc
FROM   dbo.[Order]
WHERE  CustomerId = @customerId          -- equality
  AND  Status     = 'Shipped'            -- equality
  AND  CreatedUtc >= @from               -- range
ORDER BY CreatedUtc DESC;
CREATE INDEX IX_Order_Bad
    ON dbo.[Order](CreatedUtc, CustomerId, Status);

Once the seek hits the range on CreatedUtc, the rows are ordered by date — so CustomerId and Status are scattered inside that date range. SQL Server seeks to the date range, then scans and filters. On a wide date range, that's most of the index.

CREATE INDEX IX_Order_Customer_Status_Created
    ON dbo.[Order](CustomerId, Status, CreatedUtc DESC)
    INCLUDE (Total);
PartWhy
CustomerId, StatusBoth equality — they narrow to a small contiguous block
CreatedUtc DESCRange and the sort. Inside the block, rows are already in the requested order — no sort operator at all
INCLUDE (Total)Needed in the output, never filtered on. Included = no key-lookup, without widening the tree
The trick with ORDER BY

Matching the index order to the ORDER BY removes the sort operator entirely. That's not a small win: sorts need a memory grant, and if the estimate is too low the sort spills to disk — often the difference between 50ms and 5 seconds.

In an execution plan, a Sort with a spill warning is one of the most reliable signals that an index is missing.

Selectivity, and where it doesn't apply

In simple terms

Selectivity is how much a column narrows the result. CustomerId is highly selective; IsActive with two values is not.

Among equality columns, put the most selective first — it narrows fastest.

But this rule never overrides the equality-before-range rule. Query shape beats selectivity every time.

Two composite-index traps

1. A skipped column breaks the seek. With (A, B, C), a query filtering on A and C can seek on A only, then filter C by scanning. Usable, but far from a full seek.

2. IN is a set of equalities, not a range. Status IN ('New','Paid') still seeks — SQL Server does one seek per value. So IN doesn't force the column later in the key, which surprises people.

Covering indexes and INCLUDE 🟡 Intermediate

In simple terms

A covering index contains every column the query needs — filters, joins, ORDER BY and output.

SQL Server answers the query from the index alone and never touches the table. In the plan you'll see no Key Lookup.

Key columnsINCLUDE columns
Stored inEvery level of the B-treeLeaf level only
Can seek/filter onYesNo
Can sort byYesNo
Size impactWidens the whole treeOnly the leaves
Use forWHERE, JOIN, ORDER BYSELECT output columns
Remember this

Key columns are for finding. INCLUDE columns are for returning.

If you filter or sort by it, it's a key. If you only display it, include it.

This is the real cost of SELECT *

A carefully covering index stops covering the moment someone adds a column to the SELECT list — and SELECT * guarantees it never covers anything.

So the plan silently changes from a clean seek to a seek plus a key lookup per row. Nothing errors. Nothing warns you. The query is just 50× slower under load.

That's a much better answer to "why avoid SELECT *?" than "it returns extra data".

SARGability — why your index isn't used 🔥 Must know

In simple terms

SARGable means "Search ARGument able" — the predicate can use an index seek.

The rule is one sentence: if the indexed column is wrapped in anything, the seek is gone.

Why, intuitively

The index is sorted by the column's actual value. Ask for YEAR(CreatedUtc) = 2024 and the database can't jump anywhere — it has to compute YEAR() for every row to find out which qualify.

The phone book is sorted by surname. "Everyone whose surname has 6 letters" means reading all of it.

Not SARGable ❌SARGable ✅
WHERE YEAR(CreatedUtc) = 2024WHERE CreatedUtc >= '2024-01-01' AND CreatedUtc < '2025-01-01'
WHERE UPPER(Email) = @eWHERE Email = @e — collation already handles case
WHERE Name LIKE '%smith%'WHERE Name LIKE 'smith%' — leading wildcard can't seek
WHERE Total * 1.2 > 100WHERE Total > 100 / 1.2
WHERE ISNULL(Status,'New') = 'New'WHERE Status = 'New' OR Status IS NULL
WHERE CAST(Id AS varchar) = @idWHERE Id = @id with a typed parameter
WHERE DATEDIFF(day, CreatedUtc, GETDATE()) <= 7WHERE CreatedUtc >= DATEADD(day, -7, GETDATE())
The pattern

Transform the parameter, never the column.

Every fix in that table is the same move: get the function off the left-hand side.

Implicit conversion — the invisible one 🔴 Advanced

// Column is varchar(50). The parameter defaults to nvarchar.
cmd.Parameters.AddWithValue("@sku", sku);
What happens

nvarchar has higher datatype precedence than varchar, so SQL Server converts the column, not the parameter — CONVERT(nvarchar, Sku) = @sku.

Which is a function on the column. The index seek is gone, on every row.

cmd.Parameters.Add("@sku", SqlDbType.VarChar, 50).Value = sku;
Why this one is so common

AddWithValue infers the type from the .NET value, and a .NET string becomes nvarchar. So every varchar column queried through AddWithValue loses its index seek.

It's invisible in the SQL and invisible in the C#. The only visible sign is a CONVERT_IMPLICIT in the execution plan, plus a warning on the SELECT operator.

This is a genuinely good answer to "tell me about a performance problem you found", because it's real, widespread, and the fix is one line.

The OR problem

SELECT * FROM Customer WHERE Email = @e OR Phone = @p;

No single index covers both sides, so SQL Server often scans. Two indexes plus a UNION usually beats it, because each half can seek:

SELECT * FROM Customer WHERE Email = @e
UNION
SELECT * FROM Customer WHERE Phone = @p;

Filtered and other specialised indexes 🔴 Advanced

-- 50 million orders; 40,000 are pending. Index only those.
CREATE INDEX IX_Order_Pending
    ON dbo.[Order](CreatedUtc)
    INCLUDE (CustomerId, Total)
    WHERE Status = 'Pending';

Tiny index, fits in memory, cheap to maintain — because rows leave the index when their status changes. Ideal for queue-like tables where you only ever query the active subset.

Filtered index gotcha

The query's predicate must provably imply the filter. A literal WHERE Status = 'Pending' works. A parameter WHERE Status = @status generally will not use it, because the value isn't known at compile time.

That surprises people who add a filtered index and see no improvement. Options are OPTION (RECOMPILE), or a dedicated query with the literal.

TypeUse for
FilteredQueries always touching a small subset
ColumnstoreAnalytical aggregation over millions of rows. Huge compression; poor for single-row lookups
Full-textWord search in large text — what LIKE '%x%' can't do
UniqueEnforcing a rule and giving the optimiser a guarantee it can use

Indexes are not free ⭐ Senior-level

CostDetail
Write amplificationEvery INSERT writes to the table and every index. 10 indexes = 11 writes
Update costAn UPDATE only touches indexes containing that column — so narrow indexes are cheaper
StorageIndexes routinely exceed the size of the table
MemoryIndex pages compete with data pages for buffer pool. Bloat pushes useful data out
LockingMore structures to lock during writes; more deadlock surface
MaintenanceRebuilds, statistics updates, longer backups
Senior signal — duplicate and unused indexes

The most common real-world index problem isn't a missing index. It's fifteen overlapping indexes added over five years by different people, several of which are prefixes of each other and some of which no query has used since 2021.

(CustomerId) is entirely redundant if (CustomerId, Status) exists — the second serves every query the first would. Drop it.

sys.dm_db_index_usage_stats shows reads vs writes per index. An index with 0 seeks and 2 million updates is pure cost. Removing indexes is often a bigger win than adding them, and proposing that is a strong senior signal.

Missing-index suggestions — use with care

SELECT
    d.statement,
    d.equality_columns,
    d.inequality_columns,
    d.included_columns,
    s.user_seeks,
    s.avg_user_impact
FROM sys.dm_db_missing_index_details d
JOIN sys.dm_db_missing_index_groups  g ON g.index_handle = d.index_handle
JOIN sys.dm_db_missing_index_group_stats s ON s.group_handle = g.index_group_handle
ORDER BY s.avg_user_impact * s.user_seeks DESC;
Don't apply these blindly

The DMV suggests an index per query in isolation. It doesn't know about your other indexes, doesn't consider write cost, doesn't consolidate, and often over-includes columns.

Apply 12 suggestions verbatim and you'll get 12 overlapping indexes and slower writes. Treat them as evidence about which queries are struggling, then design a smaller consolidated set yourself.

Also: the counters reset on restart, so a low count may just mean a recent failover.

Fragmentation and fill factor 🔴 Advanced

In simple terms

Fragmentation is when the logical order of index pages no longer matches their physical order, usually caused by page splits.

Fill factor leaves free space on each page so inserts have room, reducing splits — at the cost of a larger index.

FragmentationAction
< 10%Nothing
10–30%REORGANIZE — online, resumable, no big log growth
> 30%REBUILD — faster result, also refreshes statistics
Modern nuance worth mentioning

Fragmentation matters much less on SSDs and cloud storage than it did on spinning disks — random reads are no longer catastrophically slower than sequential.

Out-of-date statistics are usually the bigger problem. A nightly rebuild of every index is often wasted I/O and log volume; updating statistics is cheaper and fixes more.

Saying that shows you've operated a database rather than just read the maintenance checklist.

Key takeaways
  • An index is a sorted copy plus a pointer. Everything follows from that.
  • The clustered index is the table. Its key is duplicated into every non-clustered index — keep it narrow.
  • Composite indexes seek on a left-to-right prefix only.
  • Order: equality, then range, then ORDER BY, then INCLUDE.
  • Matching the index to ORDER BY removes the sort — and sorts spill to disk.
  • Covering = no key lookup. SELECT * is what destroys it.
  • Function on the column = no seek. Transform the parameter instead.
  • AddWithValue on a varchar column causes implicit conversion and kills the seek.
  • Every index taxes writes. Duplicate and unused indexes are usually the bigger problem.
  • Statistics matter more than fragmentation on modern storage.

Common mistakes

  • Indexing every column separately instead of designing composite indexes for real queries.
  • Range column first in a composite index.
  • Putting output columns in the key instead of INCLUDE, widening the whole tree.
  • SELECT *, silently breaking covering indexes.
  • YEAR(col) = and friends, then wondering why the index is unused.
  • AddWithValue against varchar columns.
  • Applying every missing-index suggestion verbatim.
  • Never dropping anything — accumulating overlapping indexes for years.
  • Nightly full rebuilds when a statistics update would do.
  • Assuming a scan is always wrong — for large result sets it's correct.

Interview questions

Basic

Clustered vs non-clustered index? 🔥 Must know
How I'd answer

"The clustered index is the table — the rows are physically stored in that key order. So you get exactly one per table, because data can only be sorted one way."

"A non-clustered index is a separate structure holding the indexed columns in sorted order, plus a pointer back to the row. In SQL Server that pointer is the clustering key."

"That last detail has a consequence people miss: the clustering key is stored in every non-clustered index. So if you cluster on a 16-byte GUID rather than a 4-byte int, every other index on the table carries 12 extra bytes per row. On a 50-million-row table with ten indexes that's several gigabytes of pure overhead — more pages, more I/O, and less useful data fitting in memory."

"The practical implication when reading a plan: if a non-clustered index doesn't contain every column the query needs, you get a key lookup back to the clustered index — per row. Cheap for ten rows, catastrophic for a hundred thousand. Fixing that is what covering indexes are for."

"So when choosing a clustering key I want narrow, increasing, unique and static. An int IDENTITY hits all four — narrow so indexes stay small, increasing so inserts append instead of splitting pages, unique so SQL Server doesn't add a hidden uniquifier, and static because changing a clustering key physically moves the row and updates every index pointing at it."

What they're really checking
  • Do you know the clustered index is the data?
  • Do you know the clustering key lives in every other index?
  • Can you connect it to key lookups in a plan?
Likely follow-ups
  • What's a key lookup and how do you eliminate it?
  • What happens if the clustering key isn't unique?
  • Can a primary key be non-clustered?

Intermediate

Given a query with two equality filters, a date range and an ORDER BY, what index would you create? 🔥 Must know
How I'd answer

"I'd order the columns: equality first, then the range, then the sort, then include the output columns."

"So for WHERE CustomerId = @c AND Status = @s AND CreatedUtc >= @from ORDER BY CreatedUtc DESC, returning Total, I'd create (CustomerId, Status, CreatedUtc DESC) INCLUDE (Total)."

"The reasoning: the two equality columns narrow to a small contiguous block of the index. Inside that block, rows are ordered by CreatedUtc, so the range is a contiguous slice — and it's already in the order the query wants, so there's no sort operator at all."

"That sort matters more than it sounds. Sorts need a memory grant, and if the estimate is too low the sort spills to disk — that's frequently the difference between 50 milliseconds and five seconds."

"Total goes in INCLUDE rather than the key because I never filter or sort by it, I just return it. INCLUDE columns live only at the leaf level, so I get a covering index — no key lookups — without widening the whole B-tree."

"The mistake I'd specifically avoid is putting CreatedUtc first. Once you seek on a range, everything after it in the key is scattered within that range — so SQL Server would seek the date range and then scan and filter for customer and status. On a wide date range that's most of the index."

"Two caveats. Only one range column can be used efficiently, so if there were a second range predicate I'd have to pick which one the index serves. And I'd check whether an existing index already covers this — if (CustomerId, Status) exists, I'd extend it rather than add a fourth overlapping index, because every index taxes writes."

What they're really checking
  • Do you know the equality-then-range-then-sort ordering, and why?
  • Do you know why range-first is worse — mechanically?
  • Do you distinguish key from INCLUDE?
  • Do you consider extending an existing index instead of adding one?
Weak answers
  • Red flag: one index per column.
  • Red flag: "put the most selective column first" applied mechanically, ignoring query shape.
Likely follow-ups
  • What if there were two range predicates?
  • How would you verify the sort disappeared?
  • What if the ORDER BY were ascending?

Advanced / scenario

A query has the right index but the plan shows a scan. Why? ⭐ Senior-level
How I'd answer

"I'd work through a short list, roughly in order of how often it's the answer."

"One — the predicate isn't SARGable. If the column is wrapped in a function, the seek is impossible. YEAR(CreatedUtc) = 2024, UPPER(Email) = @e, LIKE '%text%', DATEDIFF(day, CreatedUtc, GETDATE()) <= 7. The index is sorted by the actual value, so the database has to compute the function for every row to find out which qualify. The fix is always the same move — transform the parameter, not the column."

"Two — implicit conversion, and this is the one that's invisible. If the column is varchar and the parameter arrives as nvarchar, then because nvarchar has higher datatype precedence SQL Server converts the column, not the parameter. That's a function on the column, so the seek is gone. In .NET this happens automatically with AddWithValue, because a .NET string becomes nvarchar. You spot it as CONVERT_IMPLICIT in the plan and a warning on the SELECT operator."

"Three — the optimiser is right. If the query returns a large fraction of the table, a scan genuinely is cheaper than millions of seeks plus lookups. That's not a bug."

"Four — stale statistics. If it thinks 10 rows match and actually 2 million do, it picks a plan for the wrong shape. I'd compare estimated versus actual row counts in the plan; a large gap points straight at statistics. UPDATE STATISTICS and retry."

"Five — column order. The index might exist but be unusable for this query. If it's (A, B, C) and I'm filtering on B alone, there's no seekable prefix."

"Six — parameter sniffing. The cached plan was compiled for a very different parameter value. Same SQL, wildly different performance depending on input. That's where OPTION (RECOMPILE) or OPTIMIZE FOR UNKNOWN come in."

"Practically I'd get the actual execution plan first, not the estimated one, and look at three things: estimated vs actual rows, any CONVERT_IMPLICIT, and warnings on the SELECT operator. That usually identifies it within a minute."

What they're really checking
  • Do you have a systematic list, or do you guess?
  • Do you know about implicit conversion? That's the discriminating one.
  • Do you accept that a scan is sometimes correct?
  • Do you read actual vs estimated rows?
Likely follow-ups
  • How would you fix the implicit conversion in EF Core?
  • What exactly is parameter sniffing?
  • How do you make LIKE '%text%' fast?
A table has 15 indexes and writes are slow. What do you do? ⭐ Senior-level
How I'd answer

"This is common, and the answer is usually to remove indexes rather than tune anything."

"First I'd get the evidence: sys.dm_db_index_usage_stats gives seeks, scans and lookups against updates for each index. An index with zero seeks and two million updates is pure cost — it's slowing every write and helping nothing. One caveat: those counters reset when the instance restarts, so I'd check uptime before concluding an index is unused, and ideally sample over a period long enough to include monthly reporting jobs."

"Then I'd look for redundancy. If (CustomerId, Status) exists, then a separate (CustomerId) index is entirely redundant — the composite serves every query the single-column one would, because a composite index seeks on any left-to-right prefix. That pattern is everywhere in codebases that have had missing-index suggestions applied over the years."

"Then consolidation. (A, B) and (A, B, C) — keep the wider one. (A, B) INCLUDE (X) and (A, B) INCLUDE (Y) — merge into one with both includes."

"On the write cost itself, worth being precise: an INSERT touches the table plus every index, so 15 indexes means 16 writes. But an UPDATE only touches indexes that contain the updated column — which is another argument for narrow keys and against putting volatile columns in lots of indexes."

"How I'd actually ship it: I wouldn't drop nine indexes on a Friday. I'd disable rather than drop first, so re-enabling is quick if something regresses; verify over a full business cycle including month-end reporting; then drop. And I'd script the definitions before touching anything so recreating is trivial."

"The root cause is usually worth naming too — 15 indexes generally means someone applied every missing-index DMV suggestion verbatim. Those suggestions look at one query in isolation and ignore write cost and existing indexes entirely, so I'd treat them as evidence about which queries are struggling, not as a list to execute."

What they're really checking
  • Do you think of removing indexes as a valid fix?
  • Do you know the prefix rule well enough to spot redundancy?
  • Do you use evidence rather than opinion?
  • Do you have a safe rollout — disable before drop?
Weak answers
  • Red flag: only talking about adding indexes.
  • Red flag: dropping based on one day's DMV data.
Likely follow-ups
  • How do you know an index isn't needed for a quarterly report?
  • Difference between disabling and dropping an index?
  • Would you ever have 15 legitimate indexes?
