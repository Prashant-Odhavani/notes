Azure SQL

The managed options, what they cost you in control, and the application changes that actually matter when you move.

🟡 Intermediate ⭐ Senior-level 💡 Good to know
Quick revision
  • Three options: SQL Database (PaaS, single database), Managed Instance (near-full SQL Server), SQL Server on a VM (you manage everything).
  • vCore is the default purchasing model now. DTU is a legacy blended metric that makes capacity planning guesswork.
  • HA is built in and free — you don't configure availability groups.
  • Backups are automatic with point-in-time restore for 7–35 days.
  • Transient faults are normal. Retry logic isn't optional — this is the single biggest application change.
  • Elastic pools share capacity across many databases with uneven load — the multi-tenant workhorse.
  • Use Managed Identity, not connection-string passwords.

How to choose, in one line each
  • New application? SQL Database.
  • Migrating an existing app that uses SQL Agent, cross-database queries or Service Broker? Managed Instance — it exists precisely so you don't have to rewrite those.
  • Need a specific SQL Server version, an unusual extension, or full OS control? VM, and accept that patching and backups are now your job.

DTU vs vCore 🟡 Intermediate

In simple terms

DTU is a single blended number covering CPU, memory and I/O. You buy "100 DTUs" without knowing how much of each you get.

vCore separates them — you choose cores and storage explicitly, so you can size for what you actually need.

DTUvCore
TransparencyOpaque blend — hard to reason aboutExplicit cores, memory, storage
Scale independentlyNo — one dialYes
Hybrid Benefit (reuse licences)NoYes — often a large saving
Serverless / HyperscaleNoYes
VerdictLegacy. Small, predictable databases onlyThe default choice
Why DTU causes real problems

You can be at 100% DTU without knowing whether you're CPU-bound, memory-bound or I/O-bound. So the only remedy is to buy a bigger DTU tier — you can't fix the actual constraint because you can't see it.

Under vCore, the same investigation tells you "we're I/O bound", and you address that specifically.

"I'd move off DTU so I can see which resource is the constraint" is a good, concrete senior answer.

Senior signal — two non-obvious tier facts

Business Critical includes a readable secondary at no extra cost. Set ApplicationIntent=ReadOnly in the connection string and reporting traffic goes to a different replica. That's often the cheapest way to stop reports affecting live traffic, and people routinely pay for a separate geo-replica without realising they already have one.

Hyperscale backups are snapshot-based, so backup and restore time is largely independent of database size. A 50 TB restore is minutes, not days. That changes the RTO conversation completely for large databases — and it's the reason to choose Hyperscale even when you don't need 100 TB.

Serverless: know the cold start

Auto-pause is genuinely useful for dev and test — you stop paying for compute entirely. But resuming takes roughly a minute, and the first connection fails rather than waiting.

So serverless needs retry logic even more than usual, and it's a poor fit for anything user-facing with sporadic traffic — the user who arrives after an idle period gets an error.

Elastic pools ⭐ Senior-level

Think of it this way

200 tenants each need occasional bursts of capacity but sit idle most of the time.

Provisioning each one for its peak is like giving every office worker their own printer sized for the busiest day of the year.

An elastic pool is the shared printer room: one pool of capacity, drawn on by whoever needs it.

Good fitPoor fit
Many databases with uncorrelated peaksAll databases busy at the same time — no headroom to share
Low average utilisation per databaseConsistently high utilisation
Database-per-tenant SaaSA single dominant database that starves the rest
The mechanism that makes them work — and the trap

Pools let you set per-database min and max vCores. The max stops one tenant consuming the whole pool; the min guarantees a floor for important tenants.

Without a per-database cap, one tenant running a bad report degrades every other tenant in the pool — the classic noisy-neighbour problem, and the thing people forget to configure.

Pools also share the storage limit, so one large tenant can exhaust it for everyone. Both are why uncorrelated peaks matter: if everyone is busy simultaneously, a pool is just a smaller total allocation.

Geo-replication vs failover group

Use failover groups.

Geo-replication alone gives you a secondary — but failing over means changing the connection string everywhere, which is a deployment during an incident.

A failover group provides a listener endpoint that follows the primary. Failover needs no application change at all. Same replication underneath, dramatically better operationally.

Two DR facts worth stating

Geo-replication is asynchronous, so a regional failover can lose the last few seconds of committed transactions — typically an RPO around 5 seconds. If that's unacceptable you need a different design, not a different setting.

Automated backups are region-local by default. Configure geo-redundant backup storage, or a regional outage takes your restore points with it. That's a setting, not a given, and it's an easy thing to miss.

Transient faults — the change your code actually needs 🔥 Must know

Why this is different from on-prem

Azure SQL performs maintenance, patching and reconfiguration continuously, and can move your database between nodes.

So brief connection failures are expected behaviour, not incidents. Code that assumed a stable connection breaks.

builder.Services.AddDbContext<AppDbContext>(options =>
    options.UseSqlServer(connectionString, sql =>
    {
        sql.EnableRetryOnFailure(
            maxRetryCount: 5,
            maxRetryDelay: TimeSpan.FromSeconds(30),
            errorNumbersToAdd: null);       // known transient codes by default

        sql.CommandTimeout(30);
    }));
ErrorMeaningRetry?

40501Service busy — throttledYes, longer backoff
49918/49919/49920Not enough resources to process the requestYes
10928/10929Resource limit reachedYes

18456Login failedNo
The trap: retry plus explicit transactions

EnableRetryOnFailure retries individual operations. If you have an explicit transaction spanning several SaveChanges calls, a retry of one call inside it makes no sense — the transaction is already dead. EF Core throws rather than doing something incorrect.

The fix is to wrap the whole unit in an execution strategy so the entire transaction is retried as one atomic block:

var strategy = db.Database.CreateExecutionStrategy();

await strategy.ExecuteAsync(async () =>
{
    await using var tx = await db.Database.BeginTransactionAsync();
    // ... multiple SaveChangesAsync calls ...
    await tx.CommitAsync();
});

The retried block must be idempotent, because it may run more than once. That's the part people miss — and it's exactly the same requirement as retry-safety in HTTP APIs.

Senior signal — Managed Identity is the answer to secret rotation

Key Vault is a real improvement over a password in appsettings.json, but you're still managing a secret — storing it, rotating it, auditing who read it.

Managed Identity removes the secret entirely. There's nothing to leak in a config file, a log, a screenshot or a repository.

"I'd use Managed Identity so there's no credential to rotate" is a much stronger answer than "I'd put the password in Key Vault", and it's the same reasoning as avoiding long-lived secrets generally.

Two Azure SQL security defaults to check

"Allow Azure services to access this server" sounds harmless. It permits connections from any Azure subscription, including other tenants'. Turn it off and use a private endpoint or specific firewall rules.

Row-Level Security is enforced by the database, which makes it genuinely valuable for multi-tenancy — a forgotten WHERE TenantId = ... in one query can't leak data. But note it does not apply to members of db_owner unless you explicitly enable that, so the account your application connects with must not be over-privileged.

The cost argument for tuning

On-prem, a wasteful query costs nothing extra — the hardware is already paid for. In the cloud it shows up on the invoice every month.

So "we added an index and dropped two service tiers" is a real, recurring saving, and framing tuning as cost reduction rather than a technical nicety is often how you get time allocated for it.

Key takeaways
  • SQL Database for new apps, Managed Instance for lift-and-shift, VM only when you need OS control.
  • vCore over DTU — you can see which resource is the constraint.
  • Business Critical includes a free readable secondary via ApplicationIntent=ReadOnly.
  • Hyperscale's snapshot backups make restore time largely size-independent.
  • Elastic pools need uncorrelated peaks and per-database caps.
  • HA and backups are built in; geo-redundant backup storage is a setting to check.
  • Failover groups, not bare geo-replication — the listener endpoint is the point.
  • Transient-fault retry is mandatory, and explicit transactions need an execution strategy.
  • Managed Identity removes the secret rather than protecting it.
  • Query tuning is now a recurring cost saving.

Common mistakes

  • No retry logic, treating normal transient faults as outages.
  • Explicit transactions with retry enabled and no execution strategy.
  • Geo-replication without a failover group, so failover needs a deployment.
  • Assuming backups are geo-redundant when they're region-local by default.
  • Paying for a read replica when Business Critical already includes one.
  • Elastic pools with no per-database max, so one tenant starves the rest.
  • Serverless for user-facing traffic, exposing cold starts to users.
  • "Allow Azure services" left enabled.
  • Passwords in connection strings instead of Managed Identity.
  • Scaling up to fix a query problem — now you pay for it monthly.
  • Expecting SQL Agent in SQL Database.

Interview questions

Intermediate

What changes in your application when you move from SQL Server to Azure SQL? 🔥 Must know
How I'd answer

"The biggest one, and the one that catches teams out, is transient faults. Azure SQL patches and reconfigures continuously and can move your database between nodes, so brief connection failures are normal operation rather than incidents. Code written against a stable on-prem instance assumes the connection just works."

"So retry logic isn't optional. With EF Core that's EnableRetryOnFailure, which knows the transient error numbers — 40613 when the database is moving, 40501 when it's throttled, the resource-limit ones. And importantly it does not retry things like login failures, which would just mask a configuration problem."

"The subtlety there: retry works per operation, so if I have an explicit transaction spanning several SaveChanges calls, EF Core throws rather than retrying — because retrying one call inside a dead transaction would be wrong. I have to wrap the whole unit in an execution strategy so the entire transaction retries as one block. And that block must be idempotent, because it can run more than once."

"Second: feature gaps if it's SQL Database rather than Managed Instance. No SQL Agent, so scheduled jobs move to Elastic Jobs, a Function or a background service. No cross-database queries. No CLR, Service Broker or linked servers. If the existing app relies on those, Managed Instance is the migration target — that's what it exists for."

"Third: connection handling matters more. Connections are more expensive and there are hard limits per tier, so pooling has to be right, and connections shouldn't be held open across long operations. Latency is also higher than a database on the same LAN, which makes chatty access patterns and N+1 queries hurt considerably more."

"Fourth: things you no longer do. Backups, patching and HA are managed. That's genuinely less work, but it also means you can't tune what you can't see — no filegroup layout, no instance-level trace flags."

"And I'd change two things deliberately as part of the move: Managed Identity instead of a password in the connection string, since it removes the secret entirely rather than protecting it, and enabling Query Store if it isn't already, because performance troubleshooting without server access is much harder and Query Store is most of what you get."

What they're really checking
  • Do you know transient faults are the headline change?
  • Do you know the transaction + retry interaction?
  • Do you know the SQL Database feature gaps?
  • Do you mention Managed Identity?
Likely follow-ups
  • Which errors are transient and which aren't?
  • How would you replace SQL Agent jobs?
  • How do you troubleshoot performance without server access?

Advanced / scenario

Design the Azure SQL setup for a SaaS product with 500 tenants. ⭐ Senior-level
How I'd answer

"The first decision is the tenancy model, because everything else follows from it, and I'd want to know the customer profile before choosing — are these 500 similar small tenants, or 20 large enterprises and 480 small ones?"

"Database per tenant gives the strongest isolation, per-tenant restore, per-tenant scaling, and it makes data residency and 'delete all our data' requests trivial. The cost is 500 schemas to keep in sync and 500 databases to provision and monitor."

"Shared database with a tenant column is the cheapest and simplest to deploy, but a single missing WHERE TenantId is a cross-tenant data leak, and you can't restore one tenant without affecting everyone."

"For 500 tenants my default would be database-per-tenant inside elastic pools, which is close to what elastic pools were built for. Each tenant gets isolation; the pool means I'm not paying for 500 idle databases sized for their individual peaks."

"That works because tenant peaks are usually uncorrelated — different time zones, different working patterns. If they were all busy simultaneously, a pool wouldn't help and I'd need provisioned capacity instead. That's the question I'd check the metrics for rather than assume."

"Two pool details I'd get right: set a per-database max so one tenant running a bad report can't consume the whole pool — that's the noisy-neighbour problem and it's a configuration you have to remember. And set a min for tenants with contractual performance commitments. I'd also plan for large tenants to graduate out of the pool onto their own database, so growth doesn't require re-architecting."

"On tier: General Purpose for the pool by default. I'd consider Business Critical if latency matters, partly because it includes a free readable secondary — so per-tenant reporting can go to ApplicationIntent=ReadOnly and stop competing with live traffic."

"Schema management is the real operational cost of this model and I'd design for it from the start: idempotent migrations applied by an automated rolling job, version tracking per database, canary tenants first, and — critically — every migration must work with both the old and new application code, because 500 databases don't upgrade instantly. Backward-compatible migrations aren't a nice-to-have here, they're structural."

"Routing: a catalog database mapping tenant to connection string, cached in the application. That's also what lets me move a tenant to a different pool or region without a code change."

"HA and DR: built-in HA with zone redundancy, geo-redundant backup storage — which I'd verify rather than assume, since backups are region-local by default. Auto-failover groups for the pool if the RTO justifies the cost. Point-in-time restore per database is a genuine advantage here: I can restore one tenant to 3pm yesterday without touching the other 499, which is impossible in the shared-database model and is exactly the kind of request that actually arrives."

"Security: Managed Identity so there's no credential to rotate, private endpoints, and I'd still add Row-Level Security as defence in depth even with separate databases — belt and braces on the thing that would be a breach."

"The thing I'd flag as the main risk: operational tooling has to be built up front. With 500 databases, anything manual becomes impossible. Provisioning, migration, monitoring, per-tenant cost attribution and de-provisioning all need automating early, and teams routinely underestimate that because it works fine at 10 tenants."

What they're really checking
  • Do you start from the tenancy model?
  • Do you know elastic pools need uncorrelated peaks?
  • Do you set per-database caps for noisy neighbours?
  • Do you plan for schema rollout across many databases?
  • Do you raise per-tenant restore as an advantage?
  • Do you recognise operational tooling as the real cost?
Weak answers
  • Red flag: picking a tenancy model with no reasoning.
  • Red flag: no mention of how 500 schemas stay in sync.
  • Red flag: elastic pools with no per-database limits.
Likely follow-ups
  • How do you migrate a schema across 500 databases safely?
  • What happens when one tenant becomes 40% of your load?
  • How do you attribute cost per tenant?
