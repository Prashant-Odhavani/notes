High-Scale Booking System

One invariant matters absolutely: never sell the same thing twice. Everything else in the design can be eventually consistent.

🔴 Advanced ⭐ Senior-level

Senior signal — split the system by consistency requirement immediately

The most useful early observation is that this system has two halves with completely different needs.

Browsing and search — "what's available for these dates?" — is read-heavy, high volume, and tolerates staleness. If the page says twelve seats left and there are actually eleven, nothing bad happens; the booking attempt will simply be re-validated.

Allocation — "this specific seat is now mine" — is low volume, extremely contended, and requires absolute consistency. Selling one seat twice is unacceptable in a way that being slightly wrong about availability isn't.

Recognising that lets you use the right tool for each: a denormalised, cached, replicated read model for search, and a small strongly-consistent transactional core for allocation.

Which also fixes the scale problem. The high-volume traffic goes to the part that can be replicated and cached arbitrarily; only the genuinely contended operation touches the strongly-consistent store — and there are far fewer of those.

The mistake is treating the whole system as needing one guarantee. Making search strongly consistent is expensive and pointless; making allocation eventually consistent sells the same seat twice.

Relational is the right choice here, and that's worth saying confidently

The instinct in a design interview is to reach for something distributed. For allocation, a single-primary relational database is the correct answer, and being able to justify that is a stronger signal than proposing something more elaborate.

The reason: the invariant you must enforce is uniqueness of an allocation, and a relational database enforces that natively with a unique constraint or a conditional update — atomically, correctly, with no coordination logic to write and get wrong.

The volumes support it too. Even a very popular event releasing 50,000 seats over a few minutes is a few hundred allocations a second — well within a single well-indexed database's capability. The browse traffic is the large number, and that's handled by caching and replicas which scale independently.

Where you'd reconsider: allocation genuinely exceeding a single primary's write throughput, or a hard multi-region write requirement. Then you partition by event or venue — which works because allocations never span events, so each partition is independently consistent. That's a natural shard key, and worth mentioning as the path if the numbers demanded it.

Preventing double-booking 🔥 Must know

-- WRONG: check-then-act. Two requests both see Available and both proceed.
-- SELECT Status FROM Seats WHERE SeatId = @seatId;   -- 'Available'
-- IF available: UPDATE Seats SET Status = 'Held' WHERE SeatId = @seatId;

-- RIGHT: one atomic statement. The database decides the winner.
UPDATE Seats
SET    Status    = 'Held',
       HeldBy    = @userId,
       HoldToken = @holdToken,
       ExpiresAt = DATEADD(minute, 10, SYSUTCDATETIME())
WHERE  SeatId    = @seatId
  AND (Status    = 'Available'
       OR (Status = 'Held' AND ExpiresAt < SYSUTCDATETIME()));   -- reclaim an expired hold

-- @@ROWCOUNT = 1 -> this caller won the seat
-- @@ROWCOUNT = 0 -> someone else holds it. Return 409, suggest alternatives.
Check-then-act is the bug, and the atomic conditional write is the answer

The naive implementation reads the status, decides, then writes. Under contention two requests both read Available, both decide to proceed, and both write — so the seat is sold twice.

The window is milliseconds, which is why it survives testing and fails on the day tickets go on sale. It looks impossible until thousands of people click at once.

The fix is a single conditional statement where the condition and the write are one atomic operation. Exactly one caller gets @@ROWCOUNT = 1; everyone else gets zero and is told the seat is gone.

That's the same primitive as DynamoDB condition expressions, a Cosmos _etag check, Redis SET NX, and EF Core's rowversion. Every store gives you one atomic conditional write, and every correct allocation scheme is built on it. Recognising it as one idea rather than five APIs is what the question is testing.

Note the OR (Status = 'Held' AND ExpiresAt < now) clause: it reclaims an expired hold in the same atomic operation, so a stale hold never blocks a sale and there's no dependency on a cleanup job having run. That detail is what makes the design robust rather than merely correct in theory.

Don't add a distributed lock to something the database already guarantees

Reaching for a Redis distributed lock here is a common instinct and it's a downgrade. It adds a dependency, introduces lock-expiry edge cases, and — critically — a lock in Redis cannot guarantee anything about a write to SQL. If the lock expires mid-operation, two callers proceed and the invariant is broken with no error.

The database's own conditional write is stronger, because the condition and the effect are the same operation. There's no window.

The principle worth stating: enforce an invariant in the store that owns the data. A lock elsewhere is advisory; a constraint in the database is absolute.

Pessimistic locking with UPDLOCK is correct but behaves worse: under contention callers queue, so latency climbs and connections are held. The conditional update lets losers fail immediately, which is the better user experience — "that seat just went, here are three others" beats a five-second wait followed by the same news.

Senior signal — expiry must be enforced on read, not by a job

The obvious implementation is a background job that clears expired holds every minute. That's useful and it must not be the only mechanism, because if the job stops — a deployment, a crash, a misconfigured schedule — inventory is silently stranded and seats that should be on sale aren't.

Which is a bad failure: nothing errors, revenue is quietly lost, and the symptom is "customers say it's sold out but we have seats."

So the allocation statement itself treats an expired hold as available — the OR (Status = 'Held' AND ExpiresAt < now) clause. Then correctness never depends on the job having run; the job becomes an optimisation that keeps counts tidy rather than a correctness requirement.

That's a generally useful pattern: make the read path self-correcting so background cleanup is optional. The same reasoning applies to TTL-based caches, soft-deleted rows, and anything with an expiry — if a stopped job can cause incorrect behaviour, the design has a hidden dependency.

On storing holds in Redis: tempting, because a TTL handles expiry for free. But a hold is real inventory state, and Redis is not as durable as your database — losing it means holds vanish and seats are double-sold. Redis is fine as a cache of availability; the truth belongs with the bookings.

Search and availability 🟡 Intermediate

Availability shown to users is a hint, not a promise

The read model is seconds behind, so a user may see a seat that's just been taken. That's acceptable — as long as the design makes it explicit that the only authoritative check is the allocation attempt itself.

So the flow is: browse against the cached read model, then attempt to allocate, and handle failure gracefully. A 409 on the allocation isn't an error condition to avoid; it's the normal outcome under contention and the UI should present it as such — "that seat just went, here are alternatives" — rather than as a system failure.

Two consequences worth naming. Don't try to make the read model strongly consistent; you'd serialise all reads through the primary and lose the ability to cache, for a guarantee that's still stale by the time the user clicks.

And project the read model from the write side — via change feed, or an outbox — rather than dual-writing. Dual-writing means the two can diverge permanently with nothing to reconcile them.

For a high-demand release, add a queue or waiting room in front: admit users at a controlled rate rather than letting 100,000 people hit allocation simultaneously. That converts a thundering herd into an orderly queue, and it's how ticketing platforms handle onsales.

Payment and the confirm step 🔥 Must know

1  POST /holds        atomic claim -> hold token, expires in 10 min
2  POST /payments     idempotency key = hold token. Provider charges.
3  POST /bookings     confirm: hold token + payment reference
                        conditional update Held -> Booked, only if token matches
                        AND not expired
4  publish BookingConfirmed (via outbox) -> email, read model update

FAILURE CASES THAT MATTER:
  paid, then confirm fails      -> retry confirm; hold may have expired
                                   -> compensate: refund, or honour and reconcile
  hold expired during payment   -> extend on payment start, cap the extension
  duplicate confirm             -> idempotent: second attempt returns the same booking
  duplicate payment attempt     -> idempotency key means the provider charges once
"Paid but not confirmed" is the case that decides whether this design is sound

The dangerous window is between a successful charge and a successful booking record. The customer has been debited and holds nothing.

Every mitigation matters here:

Use the hold token as the payment idempotency key. Then a retried payment cannot double-charge, because the provider recognises the key and returns the original result.

Extend the hold when payment starts, with a cap. Otherwise a slow payment page means the hold expires, the seat is resold, and the charge succeeds against nothing — the worst possible ordering.

Make confirmation idempotent. A retry with the same hold token and payment reference returns the existing booking rather than creating a second one or failing.

Record payment intent before charging, so a charge that succeeds while your process dies is recoverable — you have a record saying "we were about to charge for this hold" and can reconcile against the provider.

Have a reconciliation job comparing provider transactions against bookings, and a documented decision for mismatches: refund, or honour the booking and fix it manually. Which one depends on the business, and having decided in advance is the point — because at 2am someone will otherwise guess.

The honest framing: you cannot make a charge and a database write atomic across two systems. What you can do is make every step idempotent, record intent before acting, and reconcile — so the window is detectable and recoverable rather than silent.

Overbooking, if the business wants it 🔴 Advanced

Overbooking is a business policy, and it changes the invariant

Airlines and hotels deliberately sell more than they have, because a predictable percentage of customers don't turn up. If that's a requirement, the invariant changes from "never sell the same unit twice" to "never exceed capacity × an overbooking factor".

That's a different design: allocation becomes a counter with a limit rather than allocation of specific units — UPDATE Inventory SET Sold = Sold + 1 WHERE Sold < Capacity * @factor, which is still one atomic conditional write.

And it needs the business process around it: a waitlist, a documented compensation policy, and a way to prioritise who gets bumped.

Worth raising because it demonstrates that you understand which requirements are technical and which are commercial. "Never double-book" sounds absolute and is actually a business decision — and asking whether it's genuinely absolute is a good question. For a cinema seat, yes. For a hotel room, often not.

Key takeaways
  • Split by consistency requirement: search can be stale, allocation cannot.
  • A single-primary relational database is the right choice for allocation.
  • Partition by event or venue if writes ever exceed one primary — allocations never span events.
  • Check-then-act is the bug; one atomic conditional write is the fix.
  • Reclaim expired holds in the same statement, so correctness doesn't need a job.
  • Don't add a distributed lock to something the database already guarantees.
  • Losers should fail fast with alternatives, not queue behind a lock.
  • Holds are inventory state — durable, not Redis-only.
  • Availability shown to users is a hint; the allocation attempt is the truth.
  • Project the read model from the write side; never dual-write.
  • A waiting room converts a thundering herd into an orderly queue.
  • Hold token as the payment idempotency key; extend the hold when payment starts.
  • Record intent before charging, make confirm idempotent, and reconcile.
  • Ask whether "never double-book" is absolute — overbooking may be policy.
