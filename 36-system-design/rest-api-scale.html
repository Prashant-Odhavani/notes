Large-Scale REST API

A public API is a contract you cannot take back. Most of the design is about being able to change it later without breaking anyone.

Senior signal — a public contract is the constraint that shapes everything

The read/write ratio tells you to cache. The collection size tells you how to paginate. But the answer that shapes the most decisions is "we cannot ask consumers to change quickly."

That single constraint means: every response shape must be extensible, every field you add is permanent, every field you remove is a breaking change requiring a version, and every default you choose is one you'll live with for years.

Which reframes the design work. It isn't "what's the cleanest API for today's requirements" — it's "what can I change later without a coordinated release across partners I don't control?"

The practical consequences run through every section below: return objects rather than arrays at the top level so you can add metadata; make pagination opaque so you can change its implementation; put the version in a predictable place; and know which consumers use which version, because you can never deprecate anything otherwise.

An internal API consumed only by your own SPA is a completely different problem — you can change both sides together, so most of this is unnecessary ceremony. Being able to say which situation you're in, and design accordingly, is the signal.

Version rarely, and additively by default

A new version is expensive: two code paths, two sets of tests, two documentation sets, and a migration conversation with every consumer. So the goal is to need one as rarely as possible.

Most changes can be additive and therefore need no version at all. Adding a field is safe if consumers ignore unknown properties. Adding an optional parameter is safe. Adding an endpoint is safe. Adding an enum value is a grey area — safe if consumers handle unknown values, breaking if they switch exhaustively, so it's worth documenting the expectation explicitly.

What genuinely breaks: removing or renaming a field, changing a type, making an optional parameter required, changing a default, changing an error code's meaning, or tightening validation. Those need a version.

Two structural choices that reduce version pressure. Return an object at the top level, never a bare array — { "data": [...], "pagination": {...} } — because you can add sibling properties later, and you cannot add anything to an array. And keep enums and status values extensible, documenting that consumers must tolerate new values.

When you do version, version the whole API rather than individual endpoints. Per-endpoint versions produce a matrix nobody can reason about — a consumer on v2 of orders and v1 of customers, with undefined interactions.

Deprecation only works if you know who uses what

Publishing a v2 is the easy half. Retiring v1 is where APIs accumulate permanent maintenance burden — and the blocker is almost always that nobody knows who's still calling it.

So instrument version usage per consumer from the start. Then "we'd like to retire v1" becomes a specific list of partners to contact rather than an open-ended risk, and the conversation is possible at all.

The process that works: announce with a date, emit the Deprecation and Sunset headers so automated clients and tooling can see it, contact the identified consumers directly, then — usefully — run brownouts: short deliberate outages of the old version. That converts "we didn't realise it affected us" into a discovery during a scheduled window rather than at final shutdown.

And be realistic: some consumers never migrate. At some point the decision is commercial — cut them off, or keep v1 alive for one partner. Having usage data makes that a decision rather than a guess.

Pagination 🔥 Must know

  OFFSET / PAGE NUMBER
    GET /v1/orders?page=5000&pageSize=50
    -> SELECT ... ORDER BY CreatedAt OFFSET 250000 ROWS FETCH NEXT 50

    The database walks 250,000 rows to discard them. Cost grows with depth.
    AND: a row inserted between requests SHIFTS everything, so page 2
         can repeat or skip items. Silent data loss in an export.

  KEYSET / CURSOR
    GET /v1/orders?limit=50&cursor=eyJjIjoiMjAyNS0wOC0yMSIsImkiOjQ0fQ
    -> SELECT ... WHERE (CreatedAt, Id) < (@lastCreatedAt, @lastId)
       ORDER BY CreatedAt DESC, Id DESC FETCH NEXT 50

    Constant cost at any depth. Stable under concurrent inserts.
    Cost: no random access to "page 500", no total count.

The performance argument is well known. The correctness one is more serious and less discussed.

A consumer exporting a collection page by page while rows are being inserted will skip items: a new row at the top shifts everything down, so the item that was last on page 1 is now first on page 2 and is never returned. Delete a row and items shift the other way, producing duplicates.

Nothing errors. The export completes and is quietly incomplete — which for a partner reconciling data is a genuine problem, and one they'll blame on you and be right to.

Keyset pagination is stable because the cursor identifies a position in a sort order rather than a count of rows. Inserts before or after don't move it.

Two implementation details. The sort must be on a unique, stable tuple — usually a timestamp plus id as a tiebreaker — because a non-unique sort key means rows can be skipped at page boundaries.

And make the cursor opaque — base64 the internal state. Consumers must treat it as a token rather than parsing it, which lets you change the implementation later. Expose ?after=2025-08-21 and you've published your sort strategy as part of the contract.

On totals: an exact count is expensive on a large table, and consumers rarely need it. Offer hasMore, and an approximate count only if genuinely required.

Senior signal — ETags give you concurrency control, not just caching

Most people know ETag as a caching mechanism. The more valuable use in a write-capable API is If-Match for optimistic concurrency.

Without it, two clients reading an order and both updating it means the second silently overwrites the first — the classic lost update, and the client has no way to detect it happened.

With If-Match, the second update returns 412 Precondition Failed, and the client can re-read, re-apply and retry. That's a correctness feature delivered by the same header, and it costs almost nothing to add if the entity already has a version or rowversion column.

Two related points worth making. Requiring If-Match on updates is a defensible design choice for a public API — it forces consumers to handle concurrency rather than silently losing data, and you can return 428 Precondition Required if they omit it.

And the caching hazard: Cache-Control: public on an authenticated response is a data leak. A shared cache or CDN may serve one user's data to another, and it's not your cache to purge. Authenticated responses are private at minimum, and the safest default is a middleware that sets that automatically for any authenticated request, so it can't be forgotten per endpoint.

Three ways rate limiting is commonly wrong

A global limit rather than per-consumer. If the cap is 10,000 a minute and one partner uses 9,500, everyone else shares 500 — so they're throttled because of someone else's behaviour. The limit must be per consumer.

Per-instance counting. ASP.NET Core's built-in rate limiter is per-process, so a 1,000-per-minute limit becomes 5,000 across five instances. It has to be a distributed counter, or enforced at the gateway.

Keying on something forgeable. Keying on a client-supplied header means the caller changes the value and resets their limit, so the limit does nothing. Key on the subscription or a claim from a token you validated — and validate the token before rate limiting on anything from it, or you're trusting an unverified value.

Beyond correctness, the thing that makes limits usable is telling consumers where they stand. Retry-After and the RateLimit-* headers let a well-behaved client back off smoothly. Without them, a client that hits a limit retries immediately and makes it worse — so the headers protect you as much as them.

One honesty point: distributed rate limits are approximate at scale, since counters aren't perfectly synchronised. Fine for protection, not for billing.

Bulk endpoints need per-item results, not all-or-nothing

Partners will otherwise make 10,000 individual calls, which is slow for them and expensive for you. So a batch endpoint is worth providing — and the design question is what happens when item 47 of 100 is invalid.

All-or-nothing means one bad item rejects the whole batch. For a partner submitting a day's data that's frustrating and encourages them to submit one at a time — defeating the purpose.

Per-item results — a 207 Multi-Status style response with a result per item — is usually right: the 99 valid items are processed, and the response says exactly which one failed and why.

Two things that must come with it. A maximum batch size, enforced, or someone submits 500,000 items in one request. And idempotency, because a batch that times out will be retried and must not double-process the items that succeeded — which means per-item keys, not one key for the whole batch.

On filtering: an allow-list of filterable and sortable fields, never arbitrary expressions. Exposing something OData-like or accepting raw predicates means consumers can construct queries that scan your largest table, and you've made your database a public interface with no ability to add an index for every combination.

Senior signal — at 20:1 reads to writes, caching is the design, not an optimisation

10,000 reads a second against 500 writes is a 20:1 ratio. That number decides the architecture: if 80% of reads can be served from cache, the database sees 2,000 reads a second instead of 10,000 — which is the difference between comfortable and needing to shard.

So caching isn't a later optimisation here; it's load-bearing, and the design has to say what is cached, for how long, and how it's invalidated.

Which means being specific per data type rather than uniform. Reference data — currencies, categories, product types — can cache for hours. An order can cache for a minute and be invalidated on write. A permission check should barely cache at all, because stale authorisation is a security issue rather than a stale display.

The invalidation rule worth stating: delete on write, don't update. Two concurrent writers updating a cache can interleave and leave it permanently wrong, whereas a delete's worst case is a redundant database read.

And the counterintuitive scaling point: scaling out the API tier increases pressure on the database, because each instance has its own connection pool. If the database is the constraint, more API instances make it worse — so find what saturated first rather than adding instances by default.

Key takeaways
  • "Consumers can't change quickly" is the constraint that shapes everything.
  • Return an object at the top level, never a bare array.
  • Additive changes need no version; removals and type changes do.
  • Version the whole API, not individual endpoints.
  • Track version usage per consumer, or you can never deprecate.
  • Emit Deprecation and Sunset headers; consider brownouts.
  • Keyset pagination — offset is slow at depth and silently loses data during exports.
  • Sort on a unique tuple; make the cursor opaque.
  • ETags give conditional GETs and If-Match optimistic concurrency.
  • Never Cache-Control: public on authenticated responses.
  • Rate limit per consumer, distributed, keyed on a validated claim.
  • Return Retry-After and RateLimit-* headers.
  • Bulk endpoints with per-item results, a size cap and per-item idempotency.
  • Allow-list filters — never arbitrary query expressions.
  • At 20:1 reads, caching is the architecture; delete on write.
  • Scaling out the API tier adds database connections.
