Multi-Tenant SaaS Platform

The isolation model is the decision everything else follows from — and it's the one you can't cheaply change later.

The two answers that shape everything

250× size skew means any design tuned for the median tenant will break for the largest. Every query, every pagination decision, every export has to work at both ends — and the largest tenant may need different infrastructure entirely.

Data residency means a tenant's data must be placed in a specific region. That single requirement makes routing indirection non-negotiable: the application must resolve where a tenant's data lives at runtime rather than reading one connection string from configuration.

Which is convenient, because that same indirection is what later lets you move a tenant to dedicated infrastructure. One requirement forces the mechanism that solves three problems.

And note what the scale figure does: 500 requests a second is not a scale problem. A single well-indexed database handles it. So this design is about isolation, fairness and operations — not throughput — and saying that early stops you designing the wrong thing.

The decision: shared schema by default, with an escape hatch

Shared database with a TenantId column for the 490-odd standard tenants, and a dedicated database for anyone who needs it — enterprises demanding isolation, tenants with residency requirements, and the outlier that's 250× the median.

The reasoning: at 5,000 tenants, database-per-tenant means 5,000 migrations per release, 5,000 backup configurations and 5,000 sets of monitoring. That's not a cost problem so much as an operational one — a failed migration on tenant 3,847 is a support ticket nobody notices for a week, and the fleet becomes impossible to keep uniform.

The honest cost of shared schema is that isolation depends on your code being correct rather than on infrastructure. One missing WHERE TenantId is a data breach. That's a real risk and the whole reason the enforcement below has to be structural.

What makes this a strong answer rather than a compromise is supporting both models from day one. If the code can already route a tenant to a different database, then "this enterprise customer needs dedicated infrastructure" is a data migration rather than a re-architecture — and you can quote a price for it instead of saying no.

Retrofitting that later is genuinely expensive, which is why it belongs in the initial design even though most tenants will never use it.

Senior signal — the catalogue is the piece that makes everything else possible

A tenant catalogue is a small lookup — tenant id to connection string, storage account, region, tier and configuration — resolved per request and heavily cached.

It looks like plumbing. It's what enables four separate capabilities that are otherwise impossible:

Data residency, by placing a tenant's row in a different region's database. Moving a tenant to dedicated infrastructure, which becomes a row update plus a data copy. Per-tenant configuration and staged rollouts, enabling a feature for ten tenants before all of them. And mixed isolation models in one codebase.

Without it, the connection string is one configuration value and none of those are available at any price.

Two implementation notes worth stating. It must be cached aggressively — it's read on every request and changes rarely — with invalidation on tenant update, because a catalogue lookup per request is a hot key on your most critical path.

And it's a single point of failure: if the catalogue is unavailable, no request can be served at all. So it needs the highest availability configuration in the system, and the in-process cache is what keeps you serving through a brief outage.

Tenant identity comes from the token, and nowhere else

The tenant id must be a claim in the validated JWT. Never a header, never a query parameter, never a field in the request body.

If a client can supply its own tenant id, then changing one value reads another customer's data. That's not a bug, it's an authorisation bypass with a trivial exploit — and it has happened to real products.

Two related rules that follow:

Tenant context must be scoped, resolved once per request into a scoped service. A static, a singleton, or an AsyncLocal that leaks across an async boundary means one request can observe another's tenant — which is intermittent, load-dependent, and the hardest version of this bug to find because it presents identically to a caching problem.

Background work must carry the tenant explicitly in the message. A queue consumer has no ambient HTTP context, so if tenant resolution depends on one, background jobs either fail or — much worse — inherit whatever was last set.

Enforcing isolation structurally 🔥 Must know

public sealed class AppDbContext(DbContextOptions o, ITenantContext tenant) : DbContext(o)
{
    protected override void OnModelCreating(ModelBuilder b)
    {
        foreach (var entity in b.Model.GetEntityTypes()
                                .Where(e => typeof(ITenantOwned).IsAssignableFrom(e.ClrType)))
        {
            // CRITICAL: the filter reads tenant.TenantId at QUERY time.
            // Capturing the value here instead would bake ONE tenant's id into
            // the cached model and apply it to every tenant - a silent breach
            // that passes every single-tenant test.
            b.Entity(entity.ClrType).AddQueryFilter<ITenantOwned>(
                e => e.TenantId == tenant.TenantId);
        }
    }

    public override int SaveChanges()
    {
        // Stamp TenantId on insert so it can never be forgotten or forged
        foreach (var e in ChangeTracker.Entries<ITenantOwned>()
                                       .Where(e => e.State == EntityState.Added))
        {
            e.Entity.TenantId = tenant.TenantId;
        }
        return base.SaveChanges();
    }
}

The model-cache trap is the one that catches experienced teams

EF Core caches the compiled model. If a global query filter captures the tenant id by value when the model is built, that one tenant's id is compiled into the filter and applied to every subsequent request, for every tenant.

The consequence is severe and completely silent: either tenants see one specific tenant's data, or they see nothing at all, depending on whose request happened to build the model first. It varies between deployments, which makes it look like an infrastructure problem.

And it passes every single-tenant test, which is why it reaches production.

The fix is that the filter expression must reference a scoped service so the value is read at query time — as in the code above. Worth also being aware that this makes the model cache key tenant-dependent in some configurations, so it's worth measuring the model-building cost with many tenants.

The general lesson: anything cached at application level must not capture request-scoped state. Same class of bug as a scoped service captured by a singleton, and it applies to compiled queries and cached expressions too.

Per tenant, never global — and shared queues are the one people miss

A global rate limit makes noisy neighbours worse: if one tenant consumes 95% of the allowance, everyone else is throttled because of someone else's behaviour. The limit has to be per tenant, and distributed rather than per-instance — otherwise it multiplies as you scale out.

The control that's most often forgotten is the shared queue. If all tenants' background work goes into one queue and a tenant submits 100,000 items, everyone else's work sits behind it. Their exports and notifications are delayed by hours through no fault of their own, and nothing in the system reports an error.

The fix is either a queue per tenant — practical up to a few hundred — or a scheduler that round-robins across tenants rather than processing strictly in arrival order. That's fair scheduling, and it's the difference between a platform and a shared queue.

The framing worth stating: shared infrastructure defaults to first-come-first-served, which under load means whoever generates the most load wins. Fairness has to be built deliberately; it is never the default.

Provisioning is a multi-step distributed operation, so treat it as one

Tenant creation touches several systems — your database, the catalogue, storage, the identity provider, possibly the billing system. Any of them can fail, and the operation takes longer than a request should.

So doing it inline in an HTTP request is wrong twice over: it times out, and a failure halfway leaves a half-created tenant with no record of what succeeded. Then a retry either fails on the parts that already exist or duplicates them.

Durable Functions or a saga gives you idempotent, resumable steps with the progress persisted — so a retry resumes rather than restarts, and a permanent failure leaves an inspectable record rather than orphaned resources.

An explicit status field matters too: a tenant in Provisioning must not be usable, because a partially-created tenant that accepts logins produces very confusing failures.

And design deprovisioning at the same time, with a soft-delete window. Suspension should be reversible; deletion should be delayed and then genuinely complete. Which raises the requirement most designs forget: GDPR erasure means you must be able to prove a tenant's data is gone — including from backups, logs, telemetry and any analytics store. That's much easier to answer with a dedicated database than with rows scattered through a shared one, and it's a legitimate argument for offering dedicated infrastructure to customers who ask about it.

Senior signal — tenant enrichment is the single highest-value operational decision

The first question in every multi-tenant incident is "is this one customer or everyone?", and the answer changes everything you do next.

Without a tenant dimension on telemetry, it's unanswerable — you end up correlating support tickets against timestamps. With it, it's a query.

It must be added before you need it, because you cannot retrospectively split by a dimension you never recorded, and the first serious incident is exactly when you'll want six months of history by tenant.

One important constraint: enrich with identifiers, never with data. A telemetry item containing a customer's record is itself a leak, and telemetry is typically readable by more people than the database is.

The same dimension then gives you cost attribution — which turns "is this customer profitable?" from a guess into a number, and is how you discover that a tenant paying £200 a month costs £2,000 in RUs and egress.

Key takeaways
  • Shared schema by default; dedicated database as a supported option from day one.
  • Database-per-tenant at scale is an operational problem, not just a cost one.
  • A tenant catalogue enables residency, migration, per-tenant config and mixed models.
  • The catalogue is a single point of failure — cache it hard.
  • Tenant id from the validated token only, in a scoped service.
  • Background jobs must carry tenant explicitly.
  • Global query filters must read tenant at query time, not capture it.
  • Enforce isolation structurally, and test cross-tenant reads.
  • Per-tenant rate limits and concurrency, distributed not per-instance.
  • Shared queues are the forgotten noisy-neighbour path — schedule fairly.
  • Provisioning is a durable workflow with an explicit status.
  • Design deprovisioning and GDPR erasure up front.
  • Tenant id on all telemetry — identifiers only, never data.
  • Attribute cost per tenant, including egress.
