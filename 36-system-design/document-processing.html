File / Document Processing

Long-running work triggered by an upload. The design questions are all about durability, progress and what happens to the file that breaks stage three.

🔴 Advanced ⭐ Senior-level

Two numbers eliminate the obvious designs

2 GB files mean the upload cannot go through your API. A single 2 GB upload occupies a web instance for its whole duration — bandwidth, memory, request timeout, a thread — and a handful of concurrent ones exhausts the app while storage sits idle.

20-minute processing means it cannot happen in a request, and it also rules out several serverless defaults: the Consumption plan for Functions has an execution limit well below that.

So both the ingress and the processing have to be restructured, and saying so early frames the whole design: direct-to-storage upload, event-driven trigger, durable orchestration. Everything else follows.

The third answer that matters is untrusted input. Customer-supplied files are an attack surface in a way that internal data isn't — malformed PDFs that crash parsers, zip bombs, macro-laden documents, files that claim one type and are another. That makes quarantine and scanning structural requirements rather than nice-to-haves.

Senior signal — three specific choices, each with a reason

Direct upload via a user delegation SAS. The API issues a short-lived, write-only URL and the client uploads straight to storage, which is built for it and scales independently. I'd use a user delegation SAS rather than one signed with the account key, because an account-key SAS cannot be revoked without rotating the key and breaking everything else using it. And the API chooses the blob name, never the client, so a client can't overwrite someone else's file or escape the container with a path.

Event Grid rather than the classic blob trigger. The polling blob trigger scans logs, so it can be minutes late on a busy container and is unreliable at volume. Event Grid is push-based and arrives in seconds. Microsoft's own guidance is to prefer it, and knowing that specific limitation is a good signal.

Durable orchestration rather than a chain of queues. Chained queues work and you end up hand-building the state machine: which stage are we on, what were the intermediate results, how do we resume after a crash, how do we report progress. Durable Functions gives you that — state persisted between activities, per-activity retry policies, and a queryable status endpoint for free.

The one thing to be careful of: orchestrator code must be deterministic, because it replays from history to rebuild state. No DateTime.Now, no random values, no direct I/O in the orchestrator — all of that belongs in activities. That constraint surprises people and it's the source of most Durable Functions bugs.

Never trust the client to report completion

The tempting design is: client uploads, then calls POST /documents/{id}/complete. It fails in two directions.

The client may not call it — the browser closed, the connection dropped, the mobile app was backgrounded. Now a file sits in storage that will never be processed, and nothing knows.

The client may call it dishonestly, claiming completion for a file it never uploaded, or for someone else's blob name.

Storage is the authority. The BlobCreated event fires when the blob actually exists, with its real size and path. That's the only trustworthy completion signal, and it works whatever the client does afterwards.

The related detail: sniff the content type rather than trusting the extension or the declared MIME type. A file named invoice.pdf can be anything, and handing an executable to a PDF parser is how parser exploits get delivered. Read the magic bytes and verify they match what the pipeline expects.

And add a lifecycle rule on the quarantine container, because clients request upload URLs and never use them. Those blobs accumulate and cost money indefinitely if nothing removes them.

One bad file must not stop the pipeline

The failure mode that takes down document pipelines: a file that crashes the extraction stage, retried indefinitely, occupying a worker forever. Then a second arrives. Eventually every worker is looping on poison input and nothing else is processed — while the queue looks healthy and no error rate spikes.

Three defences, and all three are needed:

A bounded retry count, after which the document moves to a Failed state with the reason recorded. The customer is told their file couldn't be processed, which is a much better outcome than silence.

Hard resource limits per activity — a timeout and a memory cap. A parser that hangs must be killed, not waited on. In a container that means a memory limit; in a Function, an explicit timeout on the activity rather than relying on the orchestration's overall limit.

Isolation for the risky stage. Parsing untrusted documents is the highest-risk operation here, so it should run somewhere a crash or a compromise is contained — its own container, its own identity with minimal permissions, no network egress if the parser doesn't need it. Then a parser exploit gets an attacker into a sandbox rather than into your application's identity.

And the operational necessity: alert on the failed count. A steady trickle of failures is a bug; a sudden spike is either an attack or a regression in a parser library. Neither is visible if failures just accumulate in a table nobody queries.

Idempotent stages 🔥 Must know

[Function(nameof(ExtractText))]
public async Task<ExtractResult> ExtractText([ActivityTrigger] DocumentRef doc,
                                              CancellationToken ct)
{
    // Deterministic output location, derived from the input.
    // A retry overwrites the same blob rather than creating a second one.
    var outputPath = $"extracted/{doc.TenantId}/{doc.DocumentId}/text.json";
    var output = _processed.GetBlobClient(outputPath);

    // Already done by a previous attempt? Return, don't redo 15 minutes of OCR.
    if (await output.ExistsAsync(ct))
    {
        _log.StageAlreadyComplete(doc.DocumentId, nameof(ExtractText));
        return await ReadResultAsync(output, ct);
    }

    using var cts = CancellationTokenSource.CreateLinkedTokenSource(ct);
    cts.CancelAfter(TimeSpan.FromMinutes(15));       // hard cap on a hostile input

    var text = await _ocr.ExtractAsync(doc.BlobUri, cts.Token);

    // Overwrite is safe BECAUSE the path is deterministic
    await output.UploadAsync(Serialize(text), overwrite: true, ct);
    return new ExtractResult(outputPath, text.PageCount);
}
Deterministic output paths make retries free

Durable Functions retries activities, and a crashed orchestration replays. So every activity will run more than once at some point, and the design has to make that harmless.

The technique is a deterministic output location derived from the input — tenant, document id, stage. Then a retry overwrites the same blob instead of creating text-1.json, text-2.json, and there's no accumulation to clean up.

The existence check on top is what makes it efficient as well as correct: if a 15-minute OCR already completed and the orchestration crashed afterwards, the retry returns immediately rather than redoing the work. On a slow expensive stage that's the difference between a minor blip and a serious delay.

The general pattern, which applies well beyond this design: make each stage's effect content-addressed so repeating it converges rather than accumulating. That's the same instinct as "prefer absolute over relative operations" in idempotent message handling — set the value rather than append a value.

The status people forget is "stuck"

Designs usually cover Pending, Processing, Complete and Failed. The state that actually generates support tickets is documents that are still Processing and never will be — because the orchestration died in a way that produced no failure, or a worker was killed mid-activity and nothing resumed it.

Nothing errors. The document sits in Processing forever, the customer waits, and you find out when they complain.

So: store a last-updated timestamp per stage and alert on anything exceeding an expected duration. That converts a silent stall into a detected problem — and it's the kind of alert that catches failures you didn't anticipate, which is where its value is.

Store the orchestration instance id on the document row too. Then support can query the orchestration's history directly and see which activity it stopped at, rather than reasoning from logs.

And distinguish user-safe failure reasons from technical ones. "This PDF is password-protected" is helpful and actionable. A stack trace is neither, and exposing it leaks internal detail — so store both, surface the first.

Senior signal — keep the originals, and delete the intermediates

Two storage decisions that pull in opposite directions, and both are right.

Keep the original uploads. When the extraction model improves, or a bug is found in classification, you need to reprocess — and you can only do that if the source still exists. A pipeline that discards inputs after processing can never be improved retrospectively, which is a decision you make once and regret for years.

Delete the intermediates. Extracted text, page images, thumbnails at three sizes — these are derived, regenerable, and they accumulate faster than the originals. A lifecycle rule removing intermediates after a retention window is straightforward cost control.

The framing: keep what you cannot recreate; delete what you can.

On archival tiering, one caution worth stating: Archive is not readable. Rehydration takes hours, so archiving originals means reprocessing becomes an overnight operation rather than an afternoon one. Cool or Cold is usually the better tier for anything you might genuinely reprocess — and the minimum-retention charges mean a colder tier can cost more if you move data too early.

And the scaling constraint worth raising: cap the concurrency of the expensive stage. If OCR calls an ML endpoint with a rate limit, unbounded scale-out means every call is throttled — elastic compute in front of a fixed-capacity dependency moves the failure rather than removing it.

Key takeaways
  • Large files and long processing rule out synchronous handling in both directions.
  • Direct upload via a short-lived, write-only user delegation SAS; the API picks the blob name.
  • Event Grid, not the polling blob trigger.
  • Storage reports completion — never trust the client.
  • Sniff content types; never trust the extension.
  • Lifecycle rule for abandoned uploads.
  • Durable orchestration gives resumable state, per-stage retries and status for free.
  • Orchestrator code must be deterministic — no time, randomness or I/O.
  • Quarantine first, scan, then move to processed.
  • Bounded retries, hard timeouts, and isolate the parsing stage.
  • Alert on failure count — a spike is an attack or a library regression.
  • Deterministic output paths make retries converge rather than accumulate.
  • Alert on documents stuck in a stage; store the orchestration instance id.
  • Keep originals so you can reprocess; delete intermediates.
  • Cap concurrency on the expensive stage.

What they're really checking
  • Do you keep large files out of the app tier?
  • Do you know the polling blob trigger's limitation?
  • Do you make storage the completion authority?
  • Do you use durable orchestration and know the determinism rule?
  • Do you make stages idempotent with deterministic outputs?
  • Do you volunteer poison-input handling and isolation?
  • Do you cover the stuck state and retention policy?
Weak answers
  • Red flag: uploading through the API.
  • Red flag: trusting a client completion callback.
  • Red flag: unlimited retries on a failing document.
