Notification & Real-Time Platform

The hard parts are not delivery. They are fan-out amplification, preference evaluation, and not sending the same thing four times.

🔴 Advanced ⭐ Senior-level

Two answers that simplify the design substantially

Ordering isn't required. That removes partitioned consumers, sessions, sequence tracking and head-of-line blocking management. Worth confirming explicitly, because if ordering were required — "the cancellation must not arrive before the confirmation" — the design changes significantly.

Duplicates are survivable but should be prevented. So the transport can be plain at-least-once and deduplication happens in the pipeline, rather than needing exotic delivery guarantees. Much cheaper than trying to build exactly-once, which isn't achievable anyway.

The answer that complicates things is the fan-out shape. One event producing 10,000 notifications across four channels is 40,000 sends, and that amplification is the real scaling characteristic of this system — not request volume. A platform handling 100 events a second is comfortable until one of those events is a broadcast.

Senior signal — separate the fan-out stage from the send stage

The decision that matters most is publishing one message per event, not one per recipient, and expanding it in a dedicated stage.

If the producer publishes 10,000 messages, several things go wrong. The publishing service blocks while doing it. A failure halfway leaves an unknown subset published with no record of progress. Retrying republishes everything. And the producer now needs to know about recipients and preferences, which isn't its job.

With a fan-out stage: one durable message in, expansion happens once, per-delivery rows are written in batches, and each delivery is independently retryable. If the worker crashes halfway, the persisted rows record exactly what already exists — so a retry resumes rather than duplicating.

It also means fan-out and sending scale independently. Expanding 10,000 recipients is a database operation; sending 10,000 emails is rate-limited by a provider. Those want completely different concurrency, and coupling them means one constrains the other.

Per-channel queues matter for the same reason. If SMS shares a queue with email and Twilio is down, retrying SMS delays every email. Separate queues contain a provider outage to its own channel — the bulkhead pattern applied to messaging.

Preferences and suppression 🔥 Must know

1  GLOBAL UNSUBSCRIBE / legal suppression   -> never send. No exceptions.
2  Hard bounce or spam complaint             -> suppress that address
3  Channel disabled by the user              -> skip that channel
4  This notification type opted out          -> skip
5  QUIET HOURS in the user's time zone       -> defer, or drop if time-sensitive
6  DIGEST preference                         -> accumulate, do not send now
7  Rate cap ("max 5 emails per day")         -> defer or drop
8  DEDUPLICATION key already sent recently   -> skip
                                             -> otherwise SEND

TRANSACTIONAL notifications - password reset, security alert, receipt - bypass
steps 2-7 but NEVER step 1. That distinction is legal, not a preference.
The transactional versus marketing distinction is a legal boundary

A password reset must arrive even if the user has turned off email notifications and it's 3am — otherwise they're locked out of their account. So transactional messages bypass preferences.

They must not bypass a global unsubscribe or a legal suppression. Under GDPR, PECR and CAN-SPAM the consequences of sending to someone who has withdrawn consent are regulatory, not a customer-satisfaction issue.

So every notification type needs an explicit classification — transactional or marketing — and that classification decides which rules apply. Getting it wrong in either direction is bad: a marketing message classified as transactional is a compliance breach, and a password reset classified as marketing means users can't recover their accounts.

Two structural points. The classification belongs on the notification type definition, not decided per send, so it's reviewable and consistent. And hard bounces must feed back into suppression automatically — continuing to send to an address that permanently rejected mail damages your sender reputation, which degrades deliverability for every other customer. That's a shared resource being spent by a bug.

Quiet hours need the user's time zone, stored explicitly

"Don't send between 10pm and 8am" is meaningless without knowing whose 10pm. So the user's time zone has to be stored — as an IANA identifier like Europe/London, not as a UTC offset, because offsets change with daylight saving and a stored offset is wrong for half the year.

Then a deferred notification needs a scheduled delivery mechanism. Service Bus scheduled messages handle this directly: set ScheduledEnqueueTime to the end of quiet hours and the broker holds it. No polling table, no timer job.

The design question worth raising: what happens to a deferred notification that's no longer relevant? An "invoice overdue" deferred to 8am may have been paid at 11pm. So the send step should re-check relevance rather than trusting the queued message — which is the same read-current-state-rather-than-trust-the-payload principle from event handling.

And a cap on deferral: if quiet hours would delay something by more than a few hours, it may be better to drop it than to send stale information the next morning.

Deduplication 🔥 Must know

// The key describes WHAT is being said to WHOM, on which channel.
// Deterministic, so a retry produces the same key.
var dedupKey = $"{notificationType}:{recipientId}:{channel}:{entityId}:{bucket:yyyyMMddHH}";

var delivery = new Delivery
{
    DedupKey  = dedupKey,          // UNIQUE INDEX on this column
    Recipient = recipientId,
    Channel   = channel,
    Status    = DeliveryStatus.Pending
};

try
{
    _db.Deliveries.Add(delivery);
    await _db.SaveChangesAsync(ct);      // insert FIRST - the DB is the arbiter
}
catch (DbUpdateException e) when (e.IsUniqueViolation())
{
    // Already created by a duplicate message or a retry. Not an error.
    _log.DuplicateSuppressed(dedupKey);
    return;
}

// Only now enqueue the send. If this fails, a sweeper picks up
// Pending rows older than a threshold and re-enqueues them.
await _queue.SendAsync(new SendDelivery(delivery.Id), ct);
Insert first, let the unique index decide — never check-then-insert

The tempting implementation is "have we sent this? no? then send it." Under any concurrency — a duplicate message, two instances processing the same event, a retry — both checks pass and both send.

So the deduplication key gets a unique index, and the code inserts first. The second attempt fails on the constraint, which is caught and treated as success. The database arbitrates atomically and no amount of concurrency defeats it.

That's the same primitive as the booking system's conditional update and an HTTP idempotency key: make the database the arbiter, not your code.

Two details that matter for it to work. The key must be deterministic — derived from the event and recipient, not generated fresh on receipt, or every retry produces a new key and dedupes nothing. And it usually needs a time bucket, because "you have a new message" should be sendable again tomorrow; a permanently unique key would suppress it forever.

Note also the ordering in the code: the row is committed before the send is enqueued. The reverse order means a send can happen with no record of it — so a retry duplicates. This way the failure mode is a row with no send, which a sweeper can detect and re-enqueue. Prefer a recoverable gap over an unrecoverable duplicate.

Senior signal — persist first, push second

The mistake is treating the real-time push as the delivery mechanism. It isn't: a WebSocket push to a user who isn't connected simply vanishes, with no error and no record.

So the notification is written to a store first, and the push is a hint that something new exists. A connected user sees it instantly; a disconnected user sees it when they next load the page and fetch unread items. Same data, two delivery paths, one source of truth.

That also makes reconnection straightforward: the client remembers the last notification id it saw and requests anything newer. No replay buffer on the server, no delivery tracking per connection — which matters because a user can have several connections open across devices and tabs.

On scale-out, the detail worth knowing: WebSocket connections are stateful and pinned to one instance. So instance A cannot push to a user connected to instance B without a backplane — Redis, or Azure SignalR Service which handles it as a managed concern. Without one, scaling out means notifications only reach the subset of users who happen to be connected to the instance that handled the event.

And each connection consumes memory and a socket for its whole lifetime, so concurrent connections, not requests per second, is the capacity metric — which is why the Azure service exists: it moves that capacity concern off your app plan entirely.

Provider failure and retries 🔥 Must know

FailureResponse
Transient provider error (5xx, timeout)Retry with backoff and jitter
Rate limited (429)Respect Retry-After; throttle the consumer
Invalid recipient (4xx)Do not retry. Mark failed, suppress the address
Provider fully downCircuit breaker; queue depth grows rather than burning retries
Hard bounce (async callback)Add to the suppression list permanently
Soft bounceRetry later, with a limit
Retries exhaustedDead-letter, and alert on DLQ depth
A provider outage should grow a queue, not burn through retries

When a provider is completely down, retrying each message three times with backoff means every message exhausts its retries and dead-letters. Then recovery involves replaying a dead-letter queue full of messages that were never actually undeliverable.

A circuit breaker changes that: once the failure rate crosses a threshold, stop calling the provider and stop consuming the queue. Messages accumulate — which is exactly what a queue is for — and processing resumes when the breaker closes. Nothing is lost and nothing needs replaying.

The distinction that makes retries useful at all: retry 5xx and timeouts, never 4xx. An invalid email address will be invalid on the fourth attempt too, so retrying wastes quota and delays real work. Worse, repeatedly sending to a known-bad address damages sender reputation.

Two things worth having. A secondary provider for critical channels, with the breaker failing over to it — genuinely valuable for SMS and password-reset email, where an hour of downtime is a serious incident. And alerting on dead-letter depth, because a DLQ nobody watches is the same as discarding the messages.

Senior signal — a per-type kill switch is the control you'll be grateful for

A notification platform can do damage very quickly. A bug in recipient resolution, a mis-scheduled job, or a reprocessed backlog can send tens of thousands of wrong messages in minutes — and you cannot un-send an email.

So a feature flag per notification type, and a global pause, are worth having from day one. When something goes wrong the response is "turn it off now, investigate after", and needing a deployment to do that costs you thousands of messages.

The related protections: a rate cap per recipient, so a bug can't send one person 500 emails, and a total volume alert — "we've sent 10× the normal hourly volume" catches a runaway before a customer complains.

This is the operational lesson specific to systems with irreversible external side effects. In most systems a bug means bad data you can correct. Here it means messages in customers' inboxes, and the only available control is how fast you can stop it.

Which is also the argument for rendering templates at send time rather than at fan-out: a broken template can be fixed while messages are still queued, instead of having baked wrong content into 40,000 pending rows.

Key takeaways
  • Fan-out amplification, not request volume, is the scaling characteristic.
  • Publish one message per event; expand in a dedicated fan-out stage.
  • Fan-out and sending scale independently, so don't couple them.
  • Per-channel queues, so a provider outage is contained.
  • Confirm ordering isn't required — it removes a lot of complexity.
  • Evaluate preferences in a fixed order, stopping at the first block.
  • Transactional bypasses preferences but never a legal suppression.
  • Hard bounces must feed suppression automatically — reputation is shared.
  • Store IANA time zones, not offsets, for quiet hours.
  • Re-check relevance before sending a deferred notification.
  • Deduplicate with a deterministic key and a unique index; insert first.
  • Commit the row before enqueuing the send — prefer a recoverable gap to a duplicate.
  • Persist first, push second; a WebSocket push to a disconnected user vanishes.
  • SignalR needs a backplane once you scale out; connections are the capacity metric.
  • A provider outage should grow a queue, not exhaust retries — use a breaker.
  • Retry 5xx, never 4xx.
  • A per-type kill switch and a volume alert, because you can't un-send.
