Distributed Background Jobs

Two hard problems: making a scheduled job run exactly once across many instances, and knowing what happened when it didn't.

🔴 Advanced ⭐ Senior-level

Three kinds of work, three mechanisms — don't build one thing

The first useful observation is that "background jobs" covers three quite different problems, and a single mechanism serves none of them well.

Scheduled work — "run at 2am" — needs a trigger and a singleton guarantee. The hard part is making it run once when several instances exist.

Queued work — "process this item" — needs throughput, retries and dead-lettering. The hard part is fairness and poison messages.

Long-running work — "the monthly billing run" — needs progress, checkpointing and resumability. The hard part is that it will be interrupted, so it must resume rather than restart.

Saying that up front frames the design and prevents the common answer of "a table of jobs and a polling worker", which handles the easy case and fails at all three hard parts.

The pattern that ties them together: a schedule should enqueue work, not do it. The 2am trigger fires once and publishes messages; the queue consumers do the work with all the retry and scaling behaviour that brings.

A timer in the web app is the single most common background-job bug

A BackgroundService or hosted timer inside the web application runs on every instance. It works perfectly in development and on one instance, then silently multiplies the moment you scale out.

The damage is that nothing errors. A nightly invoicing job on three instances sends every invoice three times. Customers notice before your monitoring does, because there's no failure to alert on — the job succeeded, repeatedly.

There's a second failure in the same place: on App Service without Always On, the app unloads when idle, so on a low-traffic site the timer silently stops running altogether. Same code, opposite failure, equally invisible.

So scheduled work belongs outside the web app — a Function with a timer trigger, or a dedicated worker. And the reason isn't only correctness: a web app's instance count is scaled for request handling, which is the wrong control for background work.

If it must stay in-process, it needs a distributed lock or an atomic claim — and note that "let instance 0 do it" doesn't work, because instance identity isn't stable across restarts and scaling events.

Senior signal — exactly-once triggering still isn't exactly-once effect

Even with a perfect singleton trigger, the job can start, do half its work, and crash. When it next runs — or when another instance reclaims a stale lease — it starts again.

So a singleton guarantee gets you "one instance starts the run". It does not get you "the work happens once". The job body itself must be idempotent, and that's the part people skip.

Concretely, for an invoicing run: rather than "generate invoices for all accounts", the job should iterate accounts and claim each one atomically — UPDATE Accounts SET InvoicedFor = @period WHERE Id = @id AND InvoicedFor <> @period. Then a crash halfway means the restart skips what's already done, and a duplicate trigger is harmless.

That also gives you resumability for free, which is what the long-running case needs anyway.

The framing worth stating: a distributed lock reduces the probability of concurrent execution; idempotency makes concurrent execution harmless. The second is strictly more valuable, because any lock has an expiry and therefore a window. If you can only have one, have idempotency.

Long-running work 🔥 Must know

  BAD: one long transaction over 200,000 accounts
    holds locks for hours, blocks everything, and a failure at 90%
    rolls back all of it. Nothing is recoverable and nothing is visible.

  GOOD: a driver that enqueues, and workers that claim
    1  trigger (singleton)  ->  create a RunId, enumerate the work
    2  enqueue one message per unit of work (per account, per batch)
    3  workers consume, each unit:
         - claimed atomically, so a duplicate is a no-op
         - committed in its own transaction
         - progress recorded against the RunId
    4  completion detected when outstanding units reach zero
    5  failures recorded per unit -> retried -> parked, run marked partial

  Properties: resumable, parallelisable, observable, and one bad account
  cannot stop the other 199,999.
Senior signal — convert a long job into many short ones

The instinct for "process 200,000 accounts" is a loop in one long-running process. That fails in four ways, and it's worth naming all of them because each is a different objection.

It isn't resumable. A crash at 90% means starting over, and on a job that takes four hours that's most of a day lost.

It isn't parallelisable. One process means one thread of progress, however much capacity you have available.

It's opaque. "Is it working or hung?" has no answer without progress records.

One bad record stops everything. Account 47,000 has malformed data, the job throws, and the remaining 153,000 are never processed.

Splitting into one queued unit of work per account or batch fixes all four at once. Each unit commits independently, retries independently, and a poison record dead-letters without affecting the rest. Progress is just a count of completed units. And scaling is adding consumers.

The trade-off to state: you lose the ability to treat the whole run as one transaction. If the business genuinely needs "all invoices or none", that's a different design — usually a two-phase approach where units are prepared and then committed together. Worth asking, because it's rarely a real requirement and assuming it costs you all four benefits above.

Very large tenantIts own worker pool, so it can't starve the shared one
A single FIFO queue is unfair by construction

This is the failure people don't anticipate because nothing breaks. A tenant triggers a bulk operation producing 100,000 work items. They all go into the queue. Every other tenant's export, notification and report now sits behind them — delayed by hours, with no error anywhere.

Queue depth looks high but healthy. Consumers are working. The job platform is functioning exactly as designed, and 200 customers are having a bad day.

So fairness has to be designed. The two workable shapes:

A queue per tenant with consumers round-robining across them. Simple and fair; practical up to a few hundred queues, beyond which the management overhead grows.

A work table with per-tenant claiming — one store, and the scheduler takes the next item for each tenant in rotation rather than the globally oldest item. Scales to any number of tenants and needs a slightly cleverer query.

Either way, add a per-tenant concurrency cap, so even in rotation one tenant can't occupy every worker. And for a genuinely enormous tenant, a dedicated pool is often simpler than making the shared scheduler handle a 250× outlier.

The principle, which recurs throughout this handbook: shared infrastructure defaults to first-come-first-served, which under load means whoever submits the most wins.

The alert that matters is the job that didn't run

Every other failure mode announces itself. An exception is logged, a message dead-letters, a duration spikes. A job that stops being triggered produces nothing at all — no error, no log line, no metric change. Just silence.

And the causes are mundane: the timer was disabled during an incident and never re-enabled, a deployment removed the function, the app idled out because Always On was off, a schedule expression was edited wrongly, the subscription hit a quota.

In every case the first indication is a business consequence, usually weeks later. Invoices weren't sent. Statements weren't generated. Data wasn't archived and now the table is enormous.

So the necessary alert is "expected run has not happened" — a watchdog comparing each schedule's last successful run against its expected frequency, alerting when the gap is too large. That's a dead-man's switch, and it's the only monitoring that detects absence.

It's the same principle as the business-metric alert: monitoring for things that happened cannot detect things that stopped happening. Every scheduled job needs one, and it's the check most platforms are missing.

Run history is cheap and repeatedly valuable

A row per execution — job name, run id, started, finished, outcome, units processed, units failed — answers most operational questions immediately and costs almost nothing.

It gives you: whether it ran, how long it took compared to usual, whether failures are trending, and which specific units failed so they can be replayed. Without it, every one of those requires trawling logs, and log retention is usually shorter than the questions you'll be asked.

Two additions worth having. A heartbeat — a last-progress timestamp updated during a long run — so "stuck" is distinguishable from "still working", which is otherwise impossible to tell from outside.

And a manual trigger with parameters, audited: re-run last night's job for one tenant, or for a specific date range. That request will come, and without it the answer is a deployment or a hand-written script — both of which are worse than a button with an audit trail.

Functions scaling out is what breaks the database

Queue-triggered Functions scale on backlog, which is the feature — and the platform will happily add dozens or hundreds of instances. Each has its own connection pool.

So a backlog of 100,000 items can produce two hundred instances and thousands of connections against a database with a hard limit. It then rejects connections for everyone, including the web application that was perfectly healthy — a batch workload has taken down the interactive one.

Fixes: cap the scale-out with functionAppScaleLimit or a maximum instance count, increase batch size rather than instance count so the same throughput uses fewer connections, and lower the per-instance pool size since an instance handling a few messages doesn't need 100.

The general principle: elastic compute in front of a fixed-capacity dependency moves the failure rather than removing it. Autoscaling is only safe when everything downstream can absorb the concurrency it produces.

Worth also knowing that for Event Hubs and Cosmos change-feed triggers the opposite applies — scaling is capped at the partition count, so lag can grow while the function refuses to scale, which looks like a platform fault and is a design constraint.

Key takeaways
  • Three kinds of work — scheduled, queued, long-running — need three mechanisms.
  • A schedule should enqueue work, not do it.
  • A timer in the web app runs on every instance and silently multiplies.
  • Without Always On, an in-app timer silently stops instead.
  • "Instance 0 does it" doesn't work — instance identity isn't stable.
  • Singleton triggering is not exactly-once effect; the job body must be idempotent.
  • A lock reduces the probability of concurrency; idempotency makes it harmless.
  • Convert a long job into many claimed units — resumable, parallel, observable, poison-tolerant.
  • Ask whether "all or nothing" is a real requirement before giving that up.
  • A single FIFO queue is unfair by construction — round-robin per tenant.
  • Per-tenant concurrency caps, and a dedicated pool for an outlier.
  • Run history per execution answers most operational questions cheaply.
  • A heartbeat distinguishes stuck from still-working.
  • Alert on the run that didn't happen — a dead-man's switch.
  • Cap Function scale-out, or the backlog takes down the database.
