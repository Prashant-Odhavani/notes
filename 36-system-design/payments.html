Payment Processing System

Money makes every distributed-systems problem consequential. The design is mostly about making failure detectable and recoverable rather than preventing it.

🔴 Advanced ⭐ Senior-level

Senior signal — say clearly that this is not a scale problem

Tens of transactions a second is trivially within a single relational database. So a candidate who starts sharding, or reaches for an eventually-consistent store, has misread the question.

The difficulty here is correctness under partial failure, not throughput. Specifically: what happens when you call the provider and don't get a response? What happens when the charge succeeds and your database write fails? How do you know, hours later, whether the money moved?

Which means the design choices are the opposite of a high-scale system: a single relational database with real transactions, strong consistency everywhere, and an append-only audit trail. Boring, and correct.

Saying that explicitly — "I'd use SQL with transactions because the volumes don't justify anything else and I want the strongest consistency I can get" — is a stronger answer than proposing something distributed, because it shows you're matching the design to the actual risk.

The single most valuable architectural decision is never seeing the card number

Using the provider's hosted fields — an iframe, or a redirect — means the card details go from the customer's browser directly to the provider and never through your infrastructure. You receive a token.

That drops your PCI DSS obligation to SAQ A, the simplest self-assessment questionnaire. If card data touches your servers, you're at SAQ D: penetration testing, network segmentation, formal key management, quarterly scans, and an annual audit. That's a substantial and permanent cost, in engineering time as much as money.

So the decision isn't primarily about security posture — it's about compliance scope, and it's one of the clearest cost-reduction decisions available in a payment design. Worth stating in those terms.

The related discipline: never log request bodies on payment endpoints. A well-meaning debug log that captures the full request can put card data in your log store, which puts your log store in PCI scope, and it will be a compliance finding even though nothing was breached. This is one of the few places where a logging decision has regulatory consequences.

And verify webhook signatures. An unverified webhook endpoint means anyone who knows the URL can POST "payment succeeded" and receive goods for free.

Idempotency 🔥 Must know

  Client            Your API                Provider
    |                  |                       |
    |--- POST pay ---->|                       |
    |                  |---- charge ---------->|
    |                  |                       |  charge SUCCEEDS
    |                  |<--- x  timeout  --x---|  response LOST
    |                  |                       |
    |   no response    |  you do not know if the money moved
    |   client retries |
    |--- POST pay ---->|---- charge ---------->|  WITHOUT an idempotency key,
    |                  |                       |  this charges AGAIN

public async Task<PaymentResult> PayAsync(PayRequest req, CancellationToken ct)
{
    // 1. The key comes from the CLIENT, per logical payment attempt.
    //    Generated server-side would give a retry a new key and defeat the point.
    var attempt = new PaymentAttempt
    {
        IdempotencyKey = req.IdempotencyKey,     // UNIQUE INDEX on (TenantId, Key)
        OrderId        = req.OrderId,
        AmountMinor    = req.AmountMinor,
        Currency       = req.Currency,
        Status         = PaymentStatus.Pending
    };

    try
    {
        // 2. Insert FIRST. The database arbitrates, not an application check.
        _db.PaymentAttempts.Add(attempt);
        await _db.SaveChangesAsync(ct);
    }
    catch (DbUpdateException e) when (e.IsUniqueViolation())
    {
        // A retry, or a concurrent duplicate. Return the ORIGINAL outcome.
        var existing = await _db.PaymentAttempts
            .SingleAsync(a => a.IdempotencyKey == req.IdempotencyKey, ct);

        return existing.Status switch
        {
            PaymentStatus.Succeeded => PaymentResult.From(existing),
            PaymentStatus.Failed    => PaymentResult.From(existing),
            // Still in flight - do NOT charge again. Tell the client to poll.
            _                       => PaymentResult.InProgress(existing.Id)
        };
    }

    // 3. Pass the same key to the provider, so even if OUR logic fails,
    //    THEY deduplicate. Defence in depth, and free.
    var result = await _provider.ChargeAsync(new ChargeRequest
    {
        Token          = req.PaymentToken,
        AmountMinor    = req.AmountMinor,
        Currency       = req.Currency,
        IdempotencyKey = req.IdempotencyKey
    }, ct);

    attempt.Apply(result);                       // Succeeded / Failed / RequiresAction
    await _db.SaveChangesAsync(ct);
    return PaymentResult.From(attempt);
}
Three layers, and each covers a different failure

The client-generated key is what makes a retry recognisable as the same logical attempt. Generated server-side, every retry gets a new key and deduplicates nothing — which is the most common way this is implemented wrongly.

The unique index is what makes it correct under concurrency. An application-level "have we already processed this key?" check is a check-then-act race that both callers pass. Insert first and let the constraint decide.

Passing the key to the provider covers the case where your own logic is wrong or your process dies between the insert and the charge. The provider then returns the original charge rather than creating a second one. It costs nothing and it's the layer that saves you when the other two have a gap.

The subtle case worth calling out is the Pending branch. If a duplicate arrives while the first attempt is still in flight, you must not charge — but you also can't return a result you don't have. Returning "in progress, poll this id" is correct. Returning an error invites another retry, and charging is a double charge.

And record intent before acting: the row exists before the charge is attempted. So a process that dies mid-charge leaves evidence that a charge may have happened, which reconciliation can resolve. The reverse order leaves money moved with no record at all — which is the one genuinely unrecoverable state.

RULES:
  - transitions are append-only events; the row's status is a projection
  - a terminal state is never left except by an explicit new event
  - unknown provider status  ->  stay Pending, let reconciliation resolve it
  - NEVER delete or overwrite history. Money needs an audit trail.
Senior signal — model it as events, and never guess a state

Two design choices carry most of the weight here.

Append-only transitions. Every state change is a recorded event with a timestamp, a source (API, webhook, reconciliation, manual) and the provider's reference. The current status is a projection of those. That gives you an audit trail that's a regulatory requirement, and it makes "why is this payment in this state?" answerable months later. Overwriting a status column loses exactly the information you need during a dispute.

Never infer a state you don't have. If a provider call times out, the correct status is Pending — not Failed. Marking it failed is the dangerous move: the customer may have been charged, and now your records say otherwise, so nothing will ever reconcile it and the customer has to notice.

Pending is uncomfortable and it's honest: we don't know. Reconciliation resolves it against the provider, which is exactly what reconciliation is for.

That principle generalises: an unknown outcome is a distinct state, not a failure. Collapsing "we don't know" into "it failed" is how money goes missing in ledgers — and it's the single most common modelling error in payment systems.

Webhooks 🔥 Must know

RequirementWhy
Verify the signatureOtherwise anyone can claim a payment succeeded
Return 200 fast; process asynchronouslySlow handlers get retried, then disabled
Idempotent by event idWebhooks are delivered more than once

Don't trust amounts blindlyVerify against your own record

Webhooks are notifications, not a source of truth

Treating a webhook as authoritative is the mistake. They arrive twice, out of order, late, or — if your endpoint was down long enough for the provider to give up — not at all.

So the handler's job is narrow: verify the signature, record the event by its id (unique index, so redelivery is a no-op), return 200 immediately, and process from a queue. A handler that does real work inline gets retried because it was slow, and providers eventually disable an endpoint that keeps failing.

Out-of-order handling matters concretely: a refund.succeeded arriving before payment.succeeded must not crash and must not leave the payment marked as merely refunded with no record of the charge. Use the provider's event timestamp or sequence to reject anything older than what you've already applied — version-based rejection rather than enforcing order.

And the crucial point: the webhook is a fast path, not the guarantee. The guarantee is reconciliation. If you rely on webhooks alone, a few hours of endpoint downtime means permanently missing payments in your records — and you'd never know which ones.

Reconciliation 🔥 Must know

MismatchMeaningAction
Provider has a charge, we don't Charged and unrecorded — the worst case Investigate; fulfil or refund. Always alert
We have Pending, provider has succeeded A lost response or a missed webhook Mark succeeded, complete fulfilment
We have Pending, provider has nothing The charge never happened Mark failed after a grace period
Amounts differ A partial capture, currency conversion, or a bug Investigate individually
We have succeeded, provider has refunded A missed refund webhook Apply the refund; check fulfilment
Senior signal — reconciliation is the design, not an afterthought

Most candidates describe the happy path and idempotency. Reconciliation is what separates a design that mostly works from one you'd trust with money.

The reasoning is unavoidable: you cannot make a charge at a provider and a write to your database atomic. There is no transaction spanning both. So a window exists where they disagree, and no amount of care in the code closes it — you can only make the disagreement detectable.

Which means a scheduled job — daily at minimum, hourly for higher volumes — that fetches provider transactions for a period and compares them against your records. Every mismatch is either resolved automatically or raised for a human.

Two things that make it genuinely useful rather than theatre. Alert on mismatch count, because a job that logs discrepancies nobody reads is worse than none — it creates the impression of coverage. And decide the policy in advance for the hard case: a charge the provider has and you don't. Refund it, or honour it and fix records? That's a business decision, and having made it beforehand means nobody guesses at 2am.

The same reasoning applies to Pending attempts that never resolved: a sweeper queries the provider after a grace period and settles them, rather than leaving rows in limbo forever.

Refunds, disputes and the ledger 🔴 Advanced

A refund is a new transaction, not an undo

This is the same distinction as compensation versus rollback, and here it's literal: the original charge still happened. The customer sees a charge and a credit on their statement, the card fees on the original may not be returned, and both appear in your accounting.

So refunds are modelled as their own records linked to the payment, with their own idempotency keys, their own states, and support for partial and multiple refunds — the sum of which must never exceed the original amount. That last constraint belongs in the database, enforced by a check on insert, not in application logic.

Disputes and chargebacks are worse, because they're initiated externally and arrive as webhooks. You have a fixed window to submit evidence, so the system needs to notify someone and record what was submitted — a chargeback lost by default because nobody saw the notification is a pure and avoidable loss.

On the ledger: for anything beyond simple payments, a double-entry ledger — every movement as balanced entries, append-only — is worth the effort. It makes the books provably balanced and it's what finance teams and auditors expect. A single Balance column that gets updated is very hard to audit and impossible to explain once it's wrong.

And always store money as minor units in an integer with an explicit currency. decimal is acceptable; double is a genuine defect, because binary floating point cannot represent 0.10 exactly and the errors accumulate silently across sums.

Key takeaways
  • This is a correctness problem, not a scale problem — a single SQL database with transactions.
  • Never let card data touch your servers; that's the difference between SAQ A and SAQ D.
  • Never log request bodies on payment paths.
  • Idempotency in three layers: client key, unique index, provider key.
  • Insert first — an application-level duplicate check is a race.
  • A duplicate arriving mid-flight gets "in progress", not an error and not a charge.
  • Record intent before charging; the reverse leaves money moved with no record.
  • Append-only state transitions — the status is a projection.
  • An unknown outcome is Pending, never Failed.
  • Webhooks are a fast path: verify signature, dedupe by event id, return 200, process async.
  • Handle out-of-order webhooks by timestamp rejection.
  • Reconciliation is the guarantee, because charge and write can't be atomic.
  • Alert on mismatches, and pre-decide the policy for a charge you have no record of.
  • A refund is a new transaction; enforce the total in the database.
  • Money as integer minor units with a currency — never double.
