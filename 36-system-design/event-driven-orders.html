Event-Driven Order System

The interesting question is not how to publish events. It is where to draw the service boundaries so you need as few sagas as possible.

The trap in this question is that "event-driven order system" sounds like an invitation to draw five microservices. The stronger answer starts by asking what must be transactional together, and letting that define the boundaries.

Stock reservation and order creation must be atomic. If they're in separate services, you need a saga for the core flow — the most common operation in the system — with compensation logic, eventual consistency and partial-failure states. If they're in one service, it's a single database transaction: correct, simple, and impossible to get wrong.

So my boundary would be an Orders service owning orders and stock reservations, with payment, shipping and notifications as separate concerns reached asynchronously.

And with one team of eight, I'd start as a modular monolith — enforced module boundaries in one deployable — because the single real benefit of separate services is independent deployability, and one team deploying together doesn't need it. The costs are immediate: network calls, distributed tracing, versioned contracts, and no transactions across boundaries.

Saying that is a strong signal precisely because the question seems to invite the opposite. The number of sagas in a design is a good proxy for whether the boundaries are right.

The dual-write problem 🔥 Must know

  Outcomes:

  You cannot make a database write and a broker publish atomic.
  There is no transaction spanning both.
public async Task<Order> PlaceOrderAsync(PlaceOrder cmd, CancellationToken ct)
{
    await using var tx = await _db.Database.BeginTransactionAsync(ct);

    // 1. Reserve stock - atomic conditional write, same database
    var reserved = await _db.Database.ExecuteSqlAsync($"""
        UPDATE Stock SET Reserved = Reserved + {cmd.Quantity}
        WHERE  Sku = {cmd.Sku}
          AND  OnHand - Reserved >= {cmd.Quantity}
        """, ct);

    if (reserved == 0) throw new InsufficientStockException(cmd.Sku);

    // 2. Create the order
    var order = Order.Create(cmd);
    _db.Orders.Add(order);

    // 3. Write the EVENT INTO THE SAME DATABASE, same transaction
    _db.OutboxMessages.Add(new OutboxMessage
    {
        Id        = Guid.CreateVersion7(),          // also the dedup key downstream
        Type      = nameof(OrderPlaced),
        Payload   = Serialize(new OrderPlaced(order.Id, order.Total, cmd.Sku)),
        OccurredAt = _clock.UtcNow
    });

    await _db.SaveChangesAsync(ct);
    await tx.CommitAsync(ct);      // stock, order and event commit TOGETHER

    return order;
}

// A separate publisher reads unpublished outbox rows and sends them.
// At-least-once: it may publish twice if it crashes after send, before marking
// sent. Consumers must be idempotent - which they must be anyway.
The outbox is the answer, and its guarantee is precise

The event is written to the same database, in the same transaction as the business change. So either both happen or neither does — there's no window.

A separate publisher then reads unpublished rows and sends them to the broker, marking them sent. If it crashes after sending but before marking, it sends again — so the outbox gives you at-least-once publication, not exactly-once.

That's the right trade. Duplicates are handled by idempotent consumers, which you need anyway because the broker itself is at-least-once. Losing an event is not recoverable; receiving one twice is.

Two things worth knowing. On Azure SQL you'd typically poll the outbox table with a short interval and a READPAST hint so multiple publishers don't contend. On Cosmos DB and DynamoDB the change feed is a built-in outbox — you don't need the table at all, because the store already gives you an ordered log of committed changes. Knowing that is a good detail.

And the alternative worth naming: if the consumer is in the same database, you may not need events at all. The outbox exists because the broker is a separate system. Reaching for events between two modules in one database is adding a distributed-systems problem you didn't have.

This is usually posed as a choice and it's better treated as two different jobs.

Orchestration for the order process itself, because it has compensation. When payment fails you must release the reservation — that requires something knowing what has already happened and what to undo. In choreography that knowledge is scattered across services, and answering "why is this order stuck?" means correlating logs from four systems.

Choreography for reactions that don't affect the outcome. Analytics, the recommendation engine, the customer's activity feed — these subscribe to OrderConfirmed and the orchestrator neither knows nor cares. Adding one changes nothing.

The distinguishing question: does the outcome depend on this step succeeding? If yes, the coordinator must know about it. If no, it's a subscriber.

Two saga details worth stating. Irreversible steps go last — you cannot un-send an email, so it happens once everything reversible has succeeded. And compensations must be idempotent and can themselves fail, so they need retries and eventually a human, because an order stuck half-compensated is worse than either end state.

And an explicit status throughout. A Pending order is visible but not treated as real — which is the semantic equivalent of a lock, and what makes eventual consistency tolerable to everything else reading the data.

There is no isolation, and that has design consequences

A database transaction is invisible until it commits. A saga is visible at every intermediate step — another process can read the half-completed state, and often does.

So the design has to make partial states safe to observe. The mechanism is an explicit status: a Pending order appears in the customer's order list marked as processing, isn't counted in revenue, isn't sent to the warehouse, and can't be modified. That's a semantic lock — the row exists but is not yet real.

Without it, everything reading orders has to know which combinations of fields mean "not finished yet", which is exactly the kind of implicit knowledge that produces bugs in every consumer.

The other consequence: ordering compensation matters. Release the reservation before refunding, or after? If the customer sees a refund and the item still unavailable, they'll re-order and fail. Small details, and they're what distinguishes a saga that works from one that produces support tickets.

Which is why the honest advice bears repeating: if the steps can live in one transaction, put them in one transaction. A saga is what you use when they genuinely cannot — and the goal of good boundary design is to need fewer of them.

Event schema evolution is the part that bites eighteen months in

An event is a published contract with consumers you may not control, and it lives in message queues and possibly in an event store — so old versions exist in flight while new code is deployed.

The rules that keep it workable:

Only add optional fields. Removing or renaming a field breaks consumers reading it. Changing a type is worse, because it deserialises to something wrong rather than failing.

Consumers must ignore unknown fields, so a producer can add one without a coordinated release. That has to be verified — some serialiser configurations throw on unknown properties, which turns an additive change into an outage.

Version the event type when a breaking change is genuinely needed — OrderPlacedV2 published alongside V1 until consumers migrate. Which means you need to know who consumes what, and that's an argument for keeping a record rather than discovering it by breaking someone.

And the design choice that reduces all of this: keep events small — identifiers and the fact, not full state. "Order 123 was placed" changes far less often than a payload containing every order field, and it doesn't couple the producer to what each consumer needs. The cost is a callback to fetch detail, which is usually worth it — and it makes consumers naturally tolerant of duplicates and reordering, because they read current state rather than trusting a snapshot.

Living with eventual consistency ⭐ Senior-level

SymptomHandling
User places an order and doesn't see itReturn the created order directly; don't read from a projection
Order shows as Pending for a few secondsShow it honestly — "processing" is fine
Report totals differ from the transactional viewTimestamp the projection: "as at 14:32"
A projection falls behindAlert on consumer lag, not just errors

Senior signal — read-after-write is the eventual-consistency problem users notice

Most staleness is invisible. A report a few seconds behind is fine; a projection catching up is fine. The one users always notice is doing something and not seeing it.

Place an order, get redirected to the order list, and it isn't there — because the list reads a projection that hasn't caught up. That reads as a lost order, and it generates a duplicate attempt.

Three fixes, in order of preference. Return the created resource in the response so the client already has it and doesn't need to re-read. Read the user's own recent writes from the authoritative store rather than the projection. Or show the pending state explicitly — "your order is being processed" is honest and reassuring, where an empty list is neither.

What not to do is make the projection strongly consistent. That serialises reads through the write side and removes the reason the projection exists.

And the property that makes projections safe to have at all: they can be rebuilt. If a projection is wrong — a bug, a missed event, a schema change — you replay from the events rather than trying to repair in place. Which requires that events are retained long enough, and that rebuilding is a tested procedure rather than a theory. Building it before you need it matters, because the day you need it is a bad day to write new code.

Key takeaways
  • Draw boundaries from what must be transactional — stock and orders belong together.
  • The number of sagas is a proxy for whether the boundaries are right.
  • One team of eight doesn't need independent deployability; start modular.
  • Save-then-publish is broken — no transaction spans a database and a broker.
  • The outbox writes the event in the same transaction; publication is at-least-once.
  • Change feed is a built-in outbox in Cosmos and DynamoDB.
  • Orchestrate the process, choreograph the independent reactions.
  • Irreversible steps last; compensations are idempotent and can fail.
  • Compensation is a new business action, not a rollback.
  • A saga has no isolation — an explicit Pending status is the semantic lock.
  • Consumers: idempotent, order-tolerant, poison-safe, ignore unknown fields.
  • Keep events small — identifiers and the fact, not full state.
  • Version the event type for breaking changes, and know who consumes what.
  • Read-after-write is the staleness users notice — return the created resource.
  • Projections must be rebuildable, and rebuilding must be tested.
