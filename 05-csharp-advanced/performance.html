Performance, Reflection & Internals

How to know something is faster rather than believe it — plus the metaprogramming features that power DI containers, ORMs and serializers.

🔴 Advanced ⭐ Senior-level 💡 Good to know
Quick revision
  • Measure, don't guess. Use BenchmarkDotNet, not a Stopwatch in a loop.
  • Optimise what a profiler points at. Intuition about hot paths is usually wrong.
  • Reflection is slow because it resolves at runtime and skips inlining. Cache the lookup, or compile a delegate once.
  • Expression trees are code as data. They power EF Core's SQL translation and fast object mapping.
  • Source generators do the same work at compile time — the modern alternative to runtime reflection.
  • The biggest wins are almost never micro-optimisations. They're algorithmic, or a removed database round trip.

Measuring properly 🔥 Must know

In simple terms

You cannot reason about .NET performance from reading code. The JIT, the GC and the CPU all interfere.

The only reliable answer comes from measuring — and measuring correctly is harder than it looks.

var sw = Stopwatch.StartNew();
for (var i = 0; i < 1_000_000; i++) DoWork();
Console.WriteLine(sw.ElapsedMilliseconds);

Four things make this untrustworthy:

  1. JIT warm-up. The first calls are interpreted or unoptimised. You're measuring compilation, not execution.
  2. No GC isolation. A collection triggered by unrelated code lands in your timing.
  3. Dead code elimination. If the result is unused, the JIT may remove the call entirely — and you'll measure an empty loop.
  4. One sample. No variance, no confidence interval. You can't tell a real 5% improvement from noise.
[MemoryDiagnoser]                        // also reports allocations
public class StringBenchmarks
{
    private readonly string[] _lines = Enumerable.Range(0, 1000)
                                                 .Select(i => $"line {i}")
                                                 .ToArray();

    [Benchmark(Baseline = true)]
    public string Concatenation()
    {
        var result = "";
        foreach (var l in _lines) result += l;
        return result;
    }

    [Benchmark]
    public string Builder()
    {
        var sb = new StringBuilder();
        foreach (var l in _lines) sb.Append(l);
        return sb.ToString();
    }
}

It warms up, runs many iterations, discards outliers, reports mean and standard deviation, and with [MemoryDiagnoser] tells you allocations and GC counts per operation. Returning the value also prevents dead-code elimination.

Best practice

Always report allocations alongside time. Two implementations can have identical throughput in a benchmark while one allocates 10× more — and under real load that extra GC pressure is what hurts.

Also: benchmark in Release configuration. Debug builds disable optimisations, so Debug numbers are meaningless.

Benchmarking vs profiling

BenchmarkingProfiling
Answers"Is A faster than B?""Where is the time actually going?"

The right order

Profile first, then benchmark.

Profiling tells you which 3% of the code matters. Benchmarking then proves your change to that 3% actually helped. Doing it the other way round means optimising code nobody executes.

Reflection 🟡 Intermediate

In simple terms

Reflection lets code inspect and use types it wasn't compiled against — read properties by name, call methods by name, create instances of types discovered at runtime.

It's how a lot of the framework works: DI containers finding constructors, serializers reading properties, test runners discovering [Fact] methods, ORMs mapping columns.

var type = typeof(Order);

foreach (var prop in type.GetProperties())
    Console.WriteLine($"{prop.Name}: {prop.PropertyType.Name}");

// Create and populate without compile-time knowledge
var instance = Activator.CreateInstance(type)!;
type.GetProperty("Total")!.SetValue(instance, 99.99m);

Why it's slow, and what to do

Reflection is roughly one to two orders of magnitude slower than direct access. The reasons:

  • Member lookup is a string-based search through metadata.
  • Calls go through an indirection layer that can't be inlined.
  • Arguments get boxed into object[].
  • Security and type checks happen on every call.
foreach (var order in orders)                     // 100,000 iterations
{
    var prop = typeof(Order).GetProperty("Total"); // string lookup, every time
    var total = (decimal)prop!.GetValue(order)!;   // boxed
}
var prop = typeof(Order).GetProperty("Total")!;   // once
foreach (var order in orders)
{
    var total = (decimal)prop.GetValue(order)!;    // still boxes, but no lookup
}
// Build a strongly-typed getter from an expression tree, then reuse it.
// After this, calls are close to direct property access speed.
private static readonly Func<Order, decimal> GetTotal = BuildGetter();

static Func<Order, decimal> BuildGetter()
{
    var param = Expression.Parameter(typeof(Order), "o");
    var body  = Expression.Property(param, nameof(Order.Total));
    return Expression.Lambda<Func<Order, decimal>>(body, param).Compile();
}

That's the technique real libraries use. AutoMapper, Dapper and the DI container all build and cache compiled delegates rather than reflecting on every call — which is why they're fast despite being reflection-based at startup.

Reflection and trimming / AOT

If you publish with trimming or Native AOT, reflection becomes a real problem: the trimmer can't see that a type is used only via reflection, so it removes it — and you get a runtime failure that didn't happen in a normal build.

That's a large part of why source generators exist, and why System.Text.Json gained a source-generated mode.

Expression trees 🔴 Advanced

In simple terms

An expression tree is your code represented as data — a tree of objects describing what the code means, rather than compiled instructions.

Because it's data, you can read it. And because you can read it, you can translate it into something else.

Think of it this way

A Func is a sealed machine. You can press the button and get a result, but you can't see inside.

An Expression is the blueprint for that machine. You can read it, analyse it, and build a different machine from it — say, one made of SQL.

Func<Order, bool>             compiled = o => o.Total > 100;   // executable
Expression<Func<Order, bool>> tree     = o => o.Total > 100;   // inspectable

var binary = (BinaryExpression)tree.Body;
Console.WriteLine(binary.NodeType);   // GreaterThan
Console.WriteLine(binary.Left);       // o.Total
Console.WriteLine(binary.Right);      // 100

This is exactly how EF Core turns LINQ into SQL — it walks the tree and emits WHERE [Total] > @p0. Covered from the LINQ side in LINQ in depth.

The two things you'd actually use them for:

  1. Composable, translatable filters. An Expression<Func<T, bool>> can be combined and passed to EF; a Func cannot. That's the basis of the Specification pattern.
  2. Fast dynamic access. Compile a delegate once instead of reflecting repeatedly, as shown above.
Also: strongly-typed member names

Expression trees are how APIs get compile-time-safe property references: builder.Property(o => o.Total) in EF's fluent API, or Include(o => o.Customer). The library reads the tree to find the member name, so a rename is caught by the compiler rather than failing at runtime like a magic string would.

Attributes 🟢 Beginner

In simple terms

An attribute is metadata attached to code. It does nothing by itself — something else has to read it and act on it.

[AttributeUsage(AttributeTargets.Class)]
public sealed class AuditedAttribute(string category) : Attribute
{
    public string Category { get; } = category;
}

[Audited("Financial")]
public class Invoice { }

// Something has to look for it - usually at startup, then cache the result
var attr = typeof(Invoice).GetCustomAttribute<AuditedAttribute>();
Console.WriteLine(attr?.Category);      // "Financial"

This is the model behind [HttpGet], [Required], [Fact], [Authorize] — declarative markers that a framework discovers by reflection.

Common mistake

Reading attributes on a hot path. GetCustomAttribute is reflection, so it's slow. Scan once at startup and cache into a dictionary — which is exactly what ASP.NET Core does when it builds the endpoint table, rather than reflecting per request.

Source generators 🔴 Advanced 💡 Good to know

In simple terms

A source generator inspects your code at compile time and writes additional C# that gets compiled alongside it.

It's reflection's job, done before the program runs.

Runtime reflectionSource generator
When it runsEvery call, or once at startupAt build time
Runtime costRealZero — it's just normal compiled code
Startup costCan be significantNone
Trimming / AOTOften breaksWorks — the code is visible to the compiler
DebuggableHardYes — you can inspect the generated source

Where you'll already be using them, whether you know it or not:

  • System.Text.Json source-generated serialization — no reflection, works under AOT.
  • [LoggerMessage] — generates high-performance logging methods with no boxing and no string allocation when the level is disabled.
  • [GeneratedRegex] — compiles the regex at build time instead of startup.
  • Records — arguably the original: the compiler generates Equals, GetHashCode, ToString and Deconstruct for you.
public static partial class Log
{
    [LoggerMessage(Level = LogLevel.Warning,
                   Message = "Order {OrderId} failed validation: {Reason}")]
    public static partial void OrderInvalid(ILogger logger, Guid orderId, string reason);
}

// Call site: no boxing of orderId, and if Warning is disabled nothing is formatted.
Log.OrderInvalid(_logger, order.Id, "missing address");

Compared with _logger.LogWarning("Order {OrderId} ...", order.Id, reason), this avoids boxing the Guid into object[] and skips formatting entirely when the level is off. On a high-volume path that's a measurable win for a one-line change.

What actually moves the needle ⭐ Senior-level

This is the most useful part of the page for interviews. Optimisations, roughly in order of impact:

ImpactChangeTypical gain
HugeRemove an N+1 query100 round trips → 1
HugeAdd a missing database indexSeconds → milliseconds
HugeFix an O(n²) algorithm (e.g. Contains on a list in a loop)Minutes → milliseconds
LargeCache an expensive repeated computation or callDepends on hit rate
LargeParallelise independent I/O with WhenAllSum of latencies → max
LargeProject only the columns neededLess I/O, less allocation
MediumRemove blocking calls causing thread pool starvationFixes a latency cliff
SmallPool large buffers, avoid LOH churnLower GC pressure
TinyReplace LINQ with a for loopNanoseconds per item
TinyStringBuilder for four concatenationsNothing measurable
Remember this

The top of that table is I/O and algorithms. The bottom is allocation micro-optimisation.

Engineers reach for the bottom because it's visible in the code they're reading. The wins are at the top.

How to say this in an interview

"My first question is always where is the time going — and in a typical .NET web app the answer is almost never CPU in my C#. It's a database round trip, a missing index, or an HTTP call I'm waiting on. So I'd profile, find the dominant cost, and fix that. I'd only look at allocations and LINQ overhead once a profiler shows CPU or GC is genuinely the bottleneck."

That answer demonstrates judgement, which is what the question is testing.

Key takeaways
  • Profile to find what to optimise; benchmark to prove the fix. In that order.
  • BenchmarkDotNet in Release, with [MemoryDiagnoser]. Never a raw Stopwatch.
  • Reflection is 10–100× slower. Cache the lookup, or compile a delegate once.
  • Expression trees are code as data — the basis of SQL translation and fast dynamic access.
  • Source generators do reflection's work at compile time, and survive trimming/AOT.
  • The big wins are I/O and algorithms, not allocations.

Common mistakes

  • Optimising without measuring, then being unable to say whether it helped.
  • Benchmarking in Debug, or with a Stopwatch and one iteration.
  • Reflecting inside a loop instead of hoisting or compiling a delegate.
  • Reading attributes per request rather than caching at startup.
  • Micro-optimising LINQ while an N+1 query dominates the request.
  • Reporting time without allocations — GC pressure only shows up under real load.
  • Using reflection-based serialization under AOT and hitting runtime failures.

Interview questions

How do you approach a performance problem? 🔥 Must know
How I'd answer

"I start by defining what 'slow' means and for whom — is it p95 latency on one endpoint, is it throughput under load, is it memory growth? Optimising without a target means you can't tell when you're done."

"Then I measure before changing anything. In a .NET web app the time is almost never CPU in my own code — it's a database round trip, a missing index, or an external HTTP call. So I'd look at distributed tracing or Application Insights first, to see the breakdown between my code and its dependencies."

"Once I know the dominant cost, I fix that. The order of impact is fairly consistent: remove an N+1 query, add a missing index, fix an accidental O(n²), then caching and parallelising independent I/O. Those are order-of-magnitude changes. Allocation tuning and LINQ-versus-loop are percentage changes, so I only go there once a profiler says CPU or GC is the bottleneck."

"When I do make a micro-optimisation, I prove it with BenchmarkDotNet in Release with [MemoryDiagnoser], so I get allocations as well as time. A Stopwatch in a loop measures JIT warm-up and random GC pauses more than it measures my code."

"And I'd verify in production, not just in the benchmark. I've seen changes that were clearly faster in isolation and made no difference at all to the user, because the real bottleneck was somewhere else entirely."

What they're really checking
  • Do you measure first, or optimise on instinct?
  • Do you know I/O usually dominates in a web app?
  • Do you know how to benchmark correctly?
Weak answers
  • Red flag: jumping straight to "avoid LINQ, use StringBuilder".
  • Red flag: "add more servers" before diagnosing.
Likely follow-ups
  • What's the difference between profiling and benchmarking?
  • Where would you look first if CPU is at 90%?
  • How do you profile a container you can't attach a debugger to?
Why is reflection slow, and how would you make a reflection-heavy path fast?
How I'd answer

"It's slow for a few compounding reasons. Member lookup is a string-based search through type metadata. The invocation goes through an indirection layer the JIT can't inline. Arguments get boxed into an object[]. And there are access and type checks on every call. Together that's typically one to two orders of magnitude slower than direct access."

"The first fix is just to stop doing the lookup repeatedly. If GetProperty("Total") is inside a loop, hoist it out — the PropertyInfo is reusable. That alone removes most of the cost in a lot of real code."

"The proper fix is to compile a delegate once. Build an expression tree representing the property access and call .Compile(), cache the resulting Func<Order, decimal> in a static field, and after that you're at close to direct property access speed. That's the technique Dapper and AutoMapper use — reflect once at startup, then execute compiled delegates."

"The modern answer, though, is often to avoid runtime reflection entirely and use a source generator. It does the same inspection at compile time and emits ordinary C#, so there's zero runtime cost, no startup penalty, and — importantly — it survives trimming and Native AOT. Reflection tends to break under trimming, because the trimmer can't see that a type is only used reflectively and removes it."

"That's exactly why System.Text.Json gained a source-generated mode, and why [LoggerMessage] and [GeneratedRegex] exist."

What they're really checking
  • Do you know the specific reasons, not just "reflection is slow"?
  • Do you know the compiled-delegate technique?
  • Bonus: source generators, and the trimming/AOT angle.
Likely follow-ups
  • How does Dapper map columns to properties so quickly?
  • What breaks under Native AOT, and why?
  • When would you write your own source generator?
