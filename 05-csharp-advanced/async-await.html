async / await

The most misunderstood feature in C#, and one of the most commonly asked. Start by unlearning "async makes it run on another thread".

🟡 Intermediate 🔴 Advanced 🔥 Must know
Quick revision
  • async is about not holding a thread while waiting. It creates no threads.
  • It makes your app handle more concurrent requests. It does not make any single request faster.
  • The compiler rewrites an async method into a state machine — the same mechanism as yield return.
  • Never use .Result or .Wait() on an async call. That's the classic deadlock.
  • async void is only ever correct for event handlers. Exceptions in it crash the process.
  • Pass a CancellationToken everywhere. An abandoned request should stop doing work.

What async actually does 🔥 Must know

In simple terms

When your code waits for something external — a database, an HTTP call, a file — the thread would normally sit there doing nothing.

async/await lets the thread go and do something else, and come back when the result arrives.

Think of it this way

Synchronous: a waiter takes your order, walks to the kitchen, and stands there watching the chef until the food is ready. One waiter, one table at a time.

Async: the waiter takes your order, hands it to the kitchen, and serves other tables. When the food is ready, they bring it. Same waiter, twenty tables.

Notice: the food doesn't cook any faster. You just need far fewer waiters.

Remember this

async improves scalability, not speed.

A single request takes exactly as long. But the server can handle far more of them at once, because threads aren't parked waiting on I/O.

Why this matters concretely

A web server has a limited thread pool. If every request blocks a thread for 200ms waiting on the database:

SynchronousAsync
Thread held during the DB callYes — the whole 200msNo — released back to the pool
Concurrent requests with 100 threads~100Thousands
Behaviour under load spikeThread pool exhausts, requests queue, latency explodesDegrades gracefully
Latency of one request200ms200ms — identical

That last row is the one people miss. Async is not a performance optimisation for the individual user. It's a capacity optimisation for the server.

How the compiler makes it work 🔴 Advanced

An async method isn't executed the way you wrote it. The compiler rewrites it into a state machine — a class that remembers where it paused.

public async Task<int> GetTotalAsync(int orderId)
{
    var order = await _db.FindAsync(orderId);      // pause point 1
    var tax   = await _tax.CalculateAsync(order);  // pause point 2
    return order.Subtotal + tax;
}

Conceptually, the compiler turns that into something like:

class GetTotalAsyncStateMachine
{
    int    _state;          // where did we pause? -1 = not started
    Order  _order;          // locals become FIELDS, so they survive the pause
    int    _tax;
    TaskAwaiter<Order> _awaiter;

    void MoveNext()
    {
        switch (_state)
        {
            case -1:  start the DB call; if not finished, save state and RETURN
            case 0:   _order = result of DB call; start the tax call; RETURN
            case 1:   _tax = result; set the Task's result; done
        }
    }
}

Three consequences worth knowing:

  1. Locals become fields. They have to survive across the pause, so they move onto the state machine object — which means they're on the heap, not the stack.
  2. The method returns early. At the first incomplete await, control returns to the caller. The rest runs later, when the awaited thing completes.
  3. It's the same machinery as yield return. If iterators made sense to you, async is the same idea with a callback instead of a caller pulling.
Why async methods allocate

That state machine is an object. So is the Task. In a hot path called millions of times, that adds up — which is exactly what ValueTask exists to address.

Note the optimisation though: if an async method completes synchronously (everything it awaits was already finished), the state machine can stay on the stack and no heap allocation happens. That's why ValueTask helps most on cache-hit style methods.

Why .Result deadlocks 🔥 Must know

This is the single most asked async question, because it caused real outages in a whole generation of ASP.NET applications.

// A synchronous method calling async code
public string GetName(int id)
{
    return GetNameAsync(id).Result;      // DEADLOCK
}

private async Task<string> GetNameAsync(int id)
{
    var customer = await _db.FindAsync(id);
    return customer.Name;                 // needs the original context to resume
}

The mechanism, step by step

  1. GetName calls GetNameAsync, then .Result blocks the current thread waiting for the task.
  2. Inside, await _db.FindAsync(id) captures the synchronisation context — a promise to resume on that same original thread.
  3. The database call completes. The continuation needs the original thread to run on.
  4. But that thread is blocked at step 1, waiting for the task to finish.
  5. The task can't finish until the continuation runs. The continuation can't run until the thread is free. Deadlock.
Think of it this way

You're holding the only door key, standing in the doorway waiting for a delivery. The courier needs to get through the door to hand it to you.

Neither of you can move. Nothing errors — you just both wait forever.

public async Task<string> GetNameAsync(int id)
{
    var customer = await _db.FindAsync(id);
    return customer.Name;
}
// The caller awaits too, and so on up to the framework entry point.
Important nuance for modern .NET

ASP.NET Core has no synchronisation context. So this specific deadlock does not happen there.

But .Result is still wrong in ASP.NET Core, for a different reason: it blocks a thread pool thread. Do it under load and you get thread pool starvation — the pool injects new threads slowly (roughly one or two per second), so requests queue and latency climbs sharply.

So the rule is the same, the failure mode differs: classic ASP.NET/WPF → deadlock. ASP.NET Core → starvation. Knowing that distinction is a strong senior answer.

ConfigureAwait(false)

In simple terms

ConfigureAwait(false) says: "I don't need to resume on the original context — any thread pool thread will do."

That avoids the deadlock and skips the cost of marshalling back to a specific thread.

WhereUse it?Why
Library codeYes, alwaysYou don't know your caller's context; don't take a dependency on it
ASP.NET Core app codeNot neededThere's no synchronisation context to capture
WPF / WinForms UI codeNo — after the await you need the UI threadTouching a control from a pool thread throws

The mistakes that cause incidents 🔥 Must know

async void

public async void ProcessOrder(Order order)     // async VOID
{
    await _service.SubmitAsync(order);          // if this throws...
}

Three problems, all serious:

  • You can't await it. The caller has no way to know when it finished.
  • You can't catch its exceptions. There's no Task to carry them, so the exception is raised on the synchronisation context — which usually means it crashes the process.
  • Fire and forget by accident. Callers assume it completed when it hasn't.

The only legitimate use is an event handler, because the delegate signature returns void. Even then, wrap the whole body in a try/catch.

Awaiting sequentially when you could parallelise

var customer = await _customers.GetAsync(id);      // 100ms
var orders   = await _orders.GetAsync(id);         // 100ms
var invoices = await _invoices.GetAsync(id);       // 100ms
var customerTask = _customers.GetAsync(id);        // started, not awaited
var ordersTask   = _orders.GetAsync(id);
var invoicesTask = _invoices.GetAsync(id);

await Task.WhenAll(customerTask, ordersTask, invoicesTask);

var customer = await customerTask;                 // already complete
Two caveats on WhenAll
  • Only do this when the calls are genuinely independent. If the second needs the first's result, sequential is correct.
  • Never share a DbContext across concurrent tasks. It isn't thread-safe, and you'll get a "second operation started on this context" exception. Each concurrent operation needs its own scope.
  • If several tasks throw, await Task.WhenAll(...) rethrows only the first exception. Inspect task.Exception if you need all of them.

Fake async

public Task<int> ComputeAsync(int[] data) =>
    Task.Run(() => Compute(data));     // CPU work pushed to a pool thread

In a web app this is counterproductive. You haven't freed a thread — you've moved the work to a different pool thread and added scheduling overhead. The request thread is still waiting.

Remember this

async is for I/O-bound work — waiting on something external.

Task.Run is for CPU-bound work, and in a web app it usually doesn't help at all. It's for keeping a desktop UI responsive.

Task vs ValueTask 🔴 Advanced 💡 Good to know

In simple terms

Task is a class — every one is a heap allocation.

ValueTask is a struct — if the result is already available, there's no allocation at all.

// Usually a cache hit -> returns synchronously -> no Task allocated
public ValueTask<Customer> GetAsync(int id)
{
    if (_cache.TryGetValue(id, out var cached))
        return new ValueTask<Customer>(cached);      // zero allocation

    return new ValueTask<Customer>(LoadFromDbAsync(id));
}
Production trap — ValueTask has rules

A ValueTask may only be consumed once. You must not:

  • await it twice
  • call .Result before it completes
  • store it and await it later
  • pass it to Task.WhenAll

Break those and you get undefined behaviour, not a clean exception. If you need any of that, call .AsTask() once and use the Task.

So: use Task by default. Reach for ValueTask only in a hot path that usually completes synchronously — and only with a benchmark showing it helps.

Cancellation 🔥 Must know

In simple terms

A CancellationToken is a way of saying "stop, nobody needs this any more".

If the user closed the browser, continuing to query the database is pure waste.

[HttpGet]
public async Task<IActionResult> Search(string term, CancellationToken ct)
{
    // ASP.NET Core supplies ct and cancels it when the client disconnects
    var results = await _repo.SearchAsync(term, ct);
    return Ok(results);
}

public async Task<List<Order>> SearchAsync(string term, CancellationToken ct) =>
    await _db.Orders
        .Where(o => o.Reference.Contains(term))
        .ToListAsync(ct);                        // the DB command is cancelled too

For long CPU loops, check it yourself:

foreach (var row in millionRows)
{
    ct.ThrowIfCancellationRequested();     // throws OperationCanceledException
    Process(row);
}
Best practice

Accept a CancellationToken in every async method you write, and pass it down. Defaulting it (CancellationToken ct = default) keeps callers happy.

And don't catch OperationCanceledException and log it as an error — cancellation is normal. Logging it as an error means every user who navigates away generates a false alarm.

Key takeaways
  • async releases threads while waiting. It creates no threads and makes nothing faster.
  • It buys scalability: more concurrent requests on the same thread pool.
  • The compiler builds a state machine; locals become heap fields.
  • .Result/.Wait() → deadlock in classic ASP.NET, thread pool starvation in ASP.NET Core. Wrong either way.
  • ConfigureAwait(false) in libraries; unnecessary in ASP.NET Core; harmful in UI code.
  • async void only for event handlers — exceptions crash the process.
  • Task.WhenAll for independent calls, but never share a DbContext.
  • ValueTask only for hot paths that usually complete synchronously, and it's single-consume.
  • Thread a CancellationToken through everything.

Common mistakes

  • .Result or .Wait() to bridge sync and async code.
  • async void anywhere except an event handler.
  • Sequential awaits on independent calls, tripling latency for no reason.
  • Sharing a DbContext across Task.WhenAll — it isn't thread-safe.
  • Task.Run around synchronous code in a web app, calling it "async".
  • Not passing CancellationToken, so abandoned work keeps running.
  • Logging OperationCanceledException as an error — creates alert noise.
  • async with no await inside — generates a warning and a pointless state machine.

Interview questions

Basic

What does async/await actually do? Does it create a thread? 🔥 Must know
How I'd answer

"No, it doesn't create a thread — that's the most common misconception. What it does is let the current thread be released while you're waiting for something external."

"Concretely: when I await a database call, the thread doesn't sit there. It goes back to the thread pool and serves other requests. When the database responds, a continuation is scheduled and the rest of my method runs — possibly on a different thread."

"The important framing is that this is about scalability, not speed. A single request takes exactly as long either way. But if each request spends 200ms waiting on I/O, a synchronous app with 100 threads handles about 100 concurrent requests, while an async one handles thousands with the same pool."

"Mechanically, the compiler rewrites the method into a state machine — the same machinery as yield return. Locals become fields on that state machine so they survive across the pause point, which is also why async methods allocate."

"And the corollary: if the work is CPU-bound rather than I/O-bound, async doesn't help at all. There's nothing to wait for. Task.Run moves it to another pool thread, which is useful for keeping a desktop UI responsive but pointless in a web app — you've just moved the work sideways."

What they're really checking
  • Do you know it isn't about threads? This is the discriminating question.
  • Do you say scalability rather than speed?
  • Bonus: the state machine, and the I/O vs CPU distinction.
Weak answers
  • Red flag: "it runs the code on a background thread."
  • Red flag: "it makes the code faster."
Likely follow-ups
  • What's the difference between async and multithreading?
  • When would Task.Run be the right call?
  • What does the compiler generate?

Intermediate

Why does .Result deadlock, and is that still true in ASP.NET Core? ⭐ Senior-level
How I'd answer

"In classic ASP.NET or a WPF app, it deadlocks because of the synchronisation context."

"The sequence is: I call .Result, which blocks the current thread waiting for the task. Inside the async method, the await captured the synchronisation context — a promise to resume on that same thread. When the I/O completes, the continuation needs that thread. But the thread is blocked waiting for the task, and the task can't complete until the continuation runs. Both sides wait forever."

"In ASP.NET Core there is no synchronisation context, so that specific deadlock doesn't happen. Continuations just run on any thread pool thread."

"But .Result is still wrong there, for a different reason: thread pool starvation. Every blocked call ties up a pool thread doing nothing. The pool only injects new threads slowly — roughly one or two a second — so under load you get a queue of requests waiting for threads, and latency climbs badly. It looks like the app has suddenly become slow with no obvious cause, which makes it nasty to diagnose."

"So the failure mode differs by platform but the rule is the same: async all the way up. If I'm genuinely stuck at a boundary I can't make async — a legacy interface, a constructor — I'd rather restructure than block. If I truly can't, GetAwaiter().GetResult() at least preserves the original exception instead of wrapping it in AggregateException, but it's still a smell I'd want to remove."

What they're really checking
  • Can you explain the deadlock mechanism, not just recite the rule?
  • Do you know ASP.NET Core changed this — and that it's still wrong?
  • Do you know thread pool starvation as a named failure mode?
Weak answers
  • Red flag: "never use .Result" with no reason.
  • Red flag: claiming it still deadlocks in ASP.NET Core.
Likely follow-ups
  • What does ConfigureAwait(false) do, and where should you use it?
  • How would you detect thread pool starvation in production?
  • How do you call async code from a constructor?
What's wrong with async void?
How I'd answer

"Three things, and the exception one is the serious one."

"First, you can't await it. The caller has no handle on it, so it has no way of knowing when the work finished — or whether it finished at all. That turns into fire-and-forget by accident."

"Second, and worst: exceptions can't be caught. With async Task, an exception is captured on the returned task and rethrown when you await it. With async void there's no task to put it on, so it gets raised on the synchronisation context — which typically means it takes the process down. A try/catch around the call site does nothing, because the method returned at the first await."

"Third, you can't compose it — no WhenAll, no timeout, no cancellation coordination."

"The one legitimate use is an event handler, because the delegate signature requires void. Even then I'd wrap the entire body in a try/catch so nothing escapes."

"If I genuinely want fire-and-forget — say, logging telemetry where I don't care about the result — I'd still return Task and handle it deliberately: either await it, or attach a continuation that logs failures. Silent failure is the thing to avoid."

What they're really checking
  • Do you know the exception behaviour specifically?
  • Do you know the event-handler exception to the rule?
  • Do you have a safe fire-and-forget pattern?
Likely follow-ups
  • How do you do fire-and-forget safely in ASP.NET Core?
  • What happens to an exception in a Task nobody ever awaits?

Advanced

Your API's latency jumps from 50ms to 8 seconds under load, with low CPU. What's happening? ⭐ Senior-level
How I'd answer

"Low CPU with high latency points strongly at thread pool starvation — requests are queuing for threads rather than doing work. If it were a genuine CPU bottleneck, CPU would be pinned."

"The classic cause is blocking calls on async code somewhere in the request path — .Result, .Wait(), or a synchronous I/O call. Each one parks a pool thread doing nothing. The pool grows, but only by about one or two threads per second, so a traffic spike outruns it and requests sit in the queue."

"To confirm it, I'd look at the ThreadPool metrics — queue length and thread count. A climbing queue length with flat CPU is the signature. In .NET the ThreadPool.ThreadCount and ThreadPool.QueueLength counters show this directly, and a dump would show most threads sitting in a wait."

"The immediate mitigation, if I need the site up now, is to raise the minimum thread count so the pool doesn't have to grow gradually. That's a sticking plaster — it hides the problem rather than fixing it, and I'd say so."

"The real fix is to find and remove the blocking calls. I'd grep for .Result, .Wait() and GetAwaiter().GetResult(), and look for synchronous I/O — File.ReadAllText, a sync HTTP client, sync EF methods. Then make that path async all the way up. I'd also add an analyser to fail the build on new blocking calls, so it doesn't come back."

"Two other things I'd rule out, because they look similar: a slow downstream dependency causing requests to pile up — where the fix is timeouts and a circuit breaker rather than async — and connection pool exhaustion on the database, which also shows as waiting with low CPU. All three are 'waiting on a limited resource', so I'd check which resource before acting."

What they're really checking
  • Can you read "high latency + low CPU" as a waiting problem?
  • Do you know thread pool growth is slow, and why that matters?
  • Do you separate mitigation from fix, and consider alternative causes?
Weak answers
  • Red flag: "add more servers" without diagnosing.
  • Red flag: raising the thread pool minimum and calling it fixed.
Likely follow-ups
  • How would you find the blocking call in a large codebase?
  • How is this different from connection pool exhaustion?
  • What would you monitor to catch it before customers do?
