Concurrency & Parallelism

Shared mutable state is where correctness goes to die. This page is about spotting that in code review and choosing the cheapest tool that fixes it.

🟡 Intermediate 🔴 Advanced 🔥 Must know
Quick revision
  • Concurrency = several things in progress. Parallelism = several things executing at the same instant. Different problems.
  • The bug is almost always a read-modify-write: read a value, change it, write it back — with a gap another thread can use.
  • lock is the default tool. It's cheap when uncontended and only works in-process.
  • Interlocked for simple atomic counters — much cheaper than a lock.
  • SemaphoreSlim when you need to limit concurrency, or need an async-friendly lock. You cannot await inside lock.
  • Concurrent collections make individual operations safe, not your multi-step logic.

Concurrency vs parallelism 🔥 Must know

In simple terms

Concurrency is about dealing with many things at once — managing multiple tasks that are all in flight.

Parallelism is about doing many things at once — actually executing simultaneously on multiple cores.

Think of it this way

Concurrency: one chef with four pans on the hob. They're all cooking, and the chef moves between them. One person, four things in progress.

Parallelism: four chefs, four pans. Genuinely simultaneous.

A single-core machine can be concurrent. It cannot be parallel.

Remember this

In a web API, you almost always want concurrency (async I/O), not parallelism.

The server is already running many requests in parallel. Adding Parallel.ForEach inside a request usually just steals threads from other requests.

The core problem: read-modify-write 🔥 Must know

Almost every thread-safety bug you will ever see has this shape.

private int _count;

public void Increment()
{
    _count++;        // THREE operations, not one
}

_count++ compiles to: read the value, add one, write it back. Two threads can interleave:

TimeThread AThread B_count
1reads 55
2reads 55
3computes 65
4computes 65
5writes 66
6writes 66 — should be 7

Two increments, one counted. This is a lost update, and it's the same bug you get in a database without a concurrency token — see transactions & concurrency.

Senior signal — spotting this in review

Look for any sequence that reads shared state, then acts on it:

if (!dict.ContainsKey(k)) dict.Add(k, v); — another thread can add between the check and the add.
if (_instance == null) _instance = new(); — two instances.
balance = balance - amount; — lost update.

The pattern to train yourself on is: "is there a gap between the decision and the action?"

lock — the default tool 🔥 Must know

private readonly object _gate = new();
private int _count;

public void Increment()
{
    lock (_gate)          // only one thread inside at a time
    {
        _count++;
    }
}

lock is syntax sugar over Monitor.Enter/Exit in a try/finally, so the lock is always released even if the body throws.

The rules that matter

RuleWhy
Lock on a private readonly objectNobody outside can lock on it, so nobody can deadlock you accidentally
Never lock on thisExternal code can also lock on your instance
Never lock on a string or typeof(X)Interned strings and Type objects are shared process-wide
Keep the body tinyEverything inside is serialised — it's your bottleneck
Never call out to unknown code inside a lockIt might take another lock, and you get a deadlock
You cannot await inside lockCompile error. A monitor is thread-affine and the continuation may run on another thread
Modern detail 💡 Good to know

.NET 9 / C# 13 added a dedicated System.Threading.Lock type that lock recognises and which is faster than locking on a plain object. If you're on .NET 9+, prefer private readonly Lock _gate = new();.

Cheaper and better options 🟡 Intermediate

Before reaching for a lock, check whether one of these fits — they're usually simpler and faster.

Interlocked — atomic operations without a lock

private int _count;

public void Increment() => Interlocked.Increment(ref _count);

// Also: Add, Exchange, CompareExchange, Read (for 64-bit on 32-bit platforms)

Far cheaper than a lock for simple counters. CompareExchange also lets you build lock-free update loops, though that gets subtle fast.

Immutability — the option that needs no synchronisation at all

In simple terms

If nothing can change, there's nothing to race on.

The cheapest concurrency fix is usually to remove the shared mutable state.

// An immutable record shared across threads is inherently safe to read.
public sealed record PricingRules(decimal VatRate, decimal Discount);

// Swap the whole thing atomically instead of mutating fields.
private PricingRules _rules = new(0.20m, 0m);

public void Update(PricingRules next) => Volatile.Write(ref _rules, next);
public PricingRules Current => Volatile.Read(ref _rules);

Reference assignment is atomic in .NET, so readers always see either the old object or the new one — never a half-updated one. That's a genuinely useful pattern for configuration and rule sets.

Just don't share it

In ASP.NET Core, the simplest fix for most thread-safety questions is scoped lifetime — each request gets its own instance, so there's no sharing to protect. Reach for locking only when state genuinely must be shared, which is rarer than people assume.

SemaphoreSlim — the async-friendly lock 🟡 Intermediate

You can't await inside a lock. SemaphoreSlim is the answer.

private readonly SemaphoreSlim _gate = new(1, 1);   // initial 1, max 1 = a mutex

public async Task<Config> GetConfigAsync(CancellationToken ct)
{
    await _gate.WaitAsync(ct);
    try
    {
        if (_cached is not null) return _cached;
        _cached = await LoadFromDiskAsync(ct);    // await INSIDE the critical section
        return _cached;
    }
    finally
    {
        _gate.Release();      // MUST be in finally, or one exception locks it forever
    }
}

It also does the other job — limiting concurrency:

private readonly SemaphoreSlim _limit = new(5, 5);

public async Task<Result> CallAsync(Request r, CancellationToken ct)
{
    await _limit.WaitAsync(ct);
    try   { return await _api.SendAsync(r, ct); }
    finally { _limit.Release(); }
}

That's the bulkhead pattern in a few lines — one slow dependency can't consume all your threads.

Production trap

Release() must be in a finally. If an exception escapes between WaitAsync and Release, that permit is gone permanently. Do it once with a semaphore of 1 and every subsequent caller hangs forever — and it looks like a deadlock with no obvious cause.

Concurrent collections 🟡 Intermediate

TypeUse for
ConcurrentDictionary<K,V>Shared lookup/cache. The workhorse
ConcurrentQueue<T>FIFO producer/consumer
ConcurrentBag<T>Unordered collection, optimised for same-thread add/take
BlockingCollection<T>Producer/consumer with a bounded capacity
Channel<T>Preferred for async producer/consumer
Production trap — thread-safe operations, unsafe logic

This is the single most important thing to understand about concurrent collections:

if (!dict.ContainsKey(key))          // thread-safe call
    dict.TryAdd(key, Expensive());   // thread-safe call
// ...but another thread can add between the two. And Expensive() may run twice.
var value = dict.GetOrAdd(key, k => Expensive());

Concurrent collections make individual operations atomic, not your multi-step logic. Use the combined methods — GetOrAdd, AddOrUpdate, TryUpdate — which exist precisely for this.

Even GetOrAdd has a caveat: the factory delegate can run more than once under contention, though only one result is stored. If the factory is expensive or has side effects, wrap the value in Lazy<T>.

Channels — the modern producer/consumer 🔴 Advanced

In simple terms

A Channel<T> is a thread-safe queue designed for async — producers write, consumers await items, and it handles backpressure.

// Bounded: if the consumer falls behind, writers WAIT rather than
// letting the queue grow until you run out of memory.
var channel = Channel.CreateBounded<Order>(new BoundedChannelOptions(1000)
{
    FullMode = BoundedChannelFullMode.Wait
});

// Producer
await channel.Writer.WriteAsync(order, ct);

// Consumer - typically in a BackgroundService
await foreach (var order in channel.Reader.ReadAllAsync(ct))
    await ProcessAsync(order, ct);
Why bounded matters

An unbounded queue turns a slow consumer into an out-of-memory crash. The queue grows until the process dies.

A bounded queue turns it into visible slowness instead — producers block, and you find out early. Always prefer bounded, and monitor the depth.

Parallel.ForEach and PLINQ 🟡 Intermediate

Parallel.ForEach(images, img => Resize(img));      // CPU-bound: good fit

// Cap it so you don't monopolise the machine
Parallel.ForEach(images,
    new ParallelOptions { MaxDegreeOfParallelism = Environment.ProcessorCount / 2 },
    img => Resize(img));
Two things people get wrong
  • Don't use Parallel.ForEach for I/O. It blocks a thread per item. For async I/O use Task.WhenAll, or Parallel.ForEachAsync (.NET 6+) which is the async-aware version.
  • Don't use it inside a web request. The server is already handling requests in parallel; grabbing all the cores for one request starves the others and makes overall throughput worse.

The body must also be thread-safe. Writing to a shared List<T> from inside Parallel.ForEach will corrupt it — use a concurrent collection or aggregate per-thread and combine at the end.

Key takeaways
  • Concurrency (I/O, async) is what web apps need. Parallelism (CPU, cores) is rarer.
  • Nearly every bug is a read-modify-write with a gap. Train yourself to spot the gap.
  • Try immutability or scoped lifetime before locking — remove the sharing, remove the problem.
  • lock on a private readonly object, tiny body, no calls out, no await.
  • Interlocked for counters; SemaphoreSlim for async or for limiting.
  • Release() in a finally, always.
  • Concurrent collections protect single operations, not your multi-step logic. Use GetOrAdd.
  • Bounded channels turn a slow consumer into slowness, not an OOM crash.
  • Locks are in-process only. Multiple instances need a distributed lock.

Common mistakes

  • _count++ on a shared field and assuming it's atomic.
  • ContainsKey then Add on a concurrent dictionary.
  • Locking on this, a string, or a Type.
  • Calling out to unknown code inside a lock — a classic deadlock route.
  • SemaphoreSlim.Release() not in a finally.
  • Unbounded channels or queues, which convert slowness into an OOM crash.
  • Parallel.ForEach for I/O, or inside a web request.
  • Sharing a DbContext across concurrent tasks — it isn't thread-safe.
  • Assuming an in-process lock protects anything when the app runs on three instances.

Interview questions

Basic

What's the difference between concurrency and parallelism?
How I'd answer

"Concurrency is dealing with many things at once — several tasks in flight, and you manage the switching between them. Parallelism is doing many things at the same instant, which needs multiple cores."

"The analogy I use is a chef: one chef with four pans on the hob is concurrent — everything's in progress and they move between them. Four chefs with four pans is parallel. A single-core machine can be concurrent but never parallel."

"In C# they map to different tools. Concurrency is async/await and Task.WhenAll, and it's for I/O — you're not using CPU, you're waiting. Parallelism is Parallel.For or PLINQ, and it's for CPU-bound work you want to finish faster."

"For a typical web API, the answer is almost always concurrency. The requests are I/O-bound — database, HTTP calls — so async lets one thread serve many requests. And the server is already running requests in parallel, so using Parallel.ForEach inside a single request usually just steals cores from other requests and makes overall throughput worse."

What they're really checking
  • Do you have a clear distinction, or use the words interchangeably?
  • Do you map them to the right C# tools and the right workload types?
Likely follow-ups
  • When would Parallel.ForEach be right?
  • Does async use extra threads?

Intermediate

Is this code thread-safe? 🔥 Must know 
private readonly Dictionary<string, Customer> _cache = new();

public Customer Get(string id)
{
    if (!_cache.ContainsKey(id))
        _cache[id] = LoadFromDb(id);
    return _cache[id];
}
How I'd answer

"No, and it's unsafe in two separate ways."

"First, the logic is a read-modify-write. Two threads can both find the key missing, both call LoadFromDb, and both write. So you do the expensive load twice. That's wasteful but not corrupting."

"Second, and much worse: Dictionary<K,V> is not thread-safe for writes at all. Concurrent writes can corrupt its internal buckets. The symptom isn't a clean exception — you can get an infinite loop inside the dictionary, or a NullReferenceException from inside framework code, and it's very hard to trace back."

"The fix depends on what I need. If it's genuinely a cache, I'd use ConcurrentDictionary with GetOrAdd, which makes the whole check-and-add one atomic operation."

"There's a subtlety worth mentioning though: GetOrAdd's factory can still run more than once under contention — only one result gets stored. If LoadFromDb is expensive or has side effects, I'd store Lazy<Customer> as the value so only one thread actually executes the load."

"And honestly, in an ASP.NET Core app I'd first ask whether this needs to be shared at all. If scoped-per-request works, there's no concurrency problem to solve. If it does need to be a real cache, I'd use IMemoryCache — because a hand-rolled dictionary cache has no size limit and no expiry, which is a memory leak waiting to happen."

What they're really checking
  • Do you spot both problems — the logic race and the collection corruption?
  • Do you know Dictionary corrupts rather than throwing cleanly?
  • Bonus: the GetOrAdd factory caveat, and the unbounded-cache concern.
Weak answers
  • Red flag: "wrap it in a lock" only — works, but misses that there's a purpose-built type, and serialises every read.
  • Red flag: not knowing Dictionary can corrupt.
Likely follow-ups
  • What if you're running three instances of the app?
  • How would you add expiry?
  • Why is Lazy<T> the fix for the double-load?
Why can't you await inside a lock, and what do you use instead?
How I'd answer

"It's a compile error, and the reason is that a monitor is thread-affine — the thread that acquired it must be the thread that releases it."

"With await, the continuation after the await may run on a completely different thread. So you'd have thread A holding the lock and thread B trying to release it, which the monitor doesn't allow. Worse, thread A could return to the pool and pick up other work while still nominally holding the lock — which is a recipe for deadlock."

"The replacement is SemaphoreSlim with a count of one. It isn't thread-affine, so it works across an await, and it has WaitAsync so you're not blocking a thread while waiting for the lock either."

"The critical detail is that Release() has to be in a finally. If an exception escapes between the wait and the release, that permit is gone permanently — and with a semaphore of one, every subsequent caller hangs forever. It presents as a deadlock with no obvious cause, which is nasty to debug."

"I'd also step back and ask whether I need mutual exclusion at all. Often the async critical section is guarding a lazy initialisation, and Lazy<Task<T>> or AsyncLazy expresses that more clearly. And if it's cache population, IMemoryCache.GetOrCreateAsync already handles it."

What they're really checking
  • Do you know why, not just that it's disallowed?
  • Do you know SemaphoreSlim and the finally requirement?
Likely follow-ups
  • What happens if Release is called more times than Wait?
  • How would you implement an async-safe lazy initialiser?

Advanced

You need to ensure a job runs only once, but the app runs on three instances. How? ⭐ Senior-level
How I'd answer

"The first thing to say is that lock and SemaphoreSlim are in-process only. They coordinate threads within one process, so with three instances you get three independent locks and the job runs three times. That's the trap in this question."

"So I need coordination through something all three instances can see. A few options, and I'd pick based on how bad a double-run is."

"If a double-run is merely wasteful — say, regenerating a cache — the simplest answer is a database row as a lease. Each instance tries a conditional update: UPDATE Jobs SET OwnerId = @me, ExpiresAt = @exp WHERE Name = @n AND (OwnerId IS NULL OR ExpiresAt < GETUTCDATE()). Exactly one row gets updated; that instance wins. It's transactional, needs no new infrastructure, and the expiry means a crashed instance doesn't block forever."

"If I already have Redis, SET key value NX PX 30000 is a one-liner lock with a TTL. Fast, but I'd be honest that it's not a perfect lock — under network partitions or GC pauses you can get two holders, which is the whole Redlock debate. Fine for 'avoid duplicate work', not fine for 'must never happen twice'."

"If correctness genuinely matters, I'd stop relying on the lock and make the work idempotent instead. Give the job a unique key for the run — a date, a sequence — and enforce it with a unique constraint. Then a double-run is harmless: the second one fails the insert and stops. That's much more robust than trying to build a perfect distributed lock, and it's the answer I'd lead with for anything that moves money or sends messages."

"There's also the option of not solving it myself: a scheduler that guarantees single execution — a Kubernetes CronJob, Azure Functions with a singleton trigger, or Hangfire/Quartz with a shared store. If the platform already offers it, using it beats hand-rolling."

What they're really checking
  • Do you know in-process locks don't work across instances? That's the whole question.
  • Do you scale the solution to how bad a double-run actually is?
  • Do you reach for idempotency rather than a perfect lock?
Weak answers
  • Red flag: "use a lock" — doesn't work across processes.
  • Red flag: "use a static flag" — same problem.
  • Red flag: claiming a Redis lock gives a hard guarantee.
Likely follow-ups
  • What happens if the instance holding the lease crashes?
  • How do you handle the lease expiring mid-job?
  • What's the Redlock controversy about?
