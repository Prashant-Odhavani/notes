Memory Management & GC

Why "managed memory" doesn't mean "can't leak", how the collector actually decides what to free, and how to diagnose growth in production.

🟡 Intermediate 🔴 Advanced 🔥 Must know
Quick revision
  • The GC frees anything not reachable from a root. Reachability, not scope, is what matters.
  • Three generations. Gen 0 collection is very cheap; Gen 2 is expensive and collects everything.
  • Short-lived garbage is nearly free. The cost comes from objects surviving and being promoted.
  • Objects over ~85 KB go on the Large Object Heap, which isn't compacted by default — so it fragments.
  • IDisposable is for unmanaged resources — handles, sockets, connections. The GC doesn't know about those.
  • A .NET "leak" is almost always something long-lived holding something short-lived: a static collection, an event handler, or a captured closure.

How the collector decides 🔥 Must know

In simple terms

The GC starts from a set of roots — static fields, local variables on active call stacks, CPU registers — and follows every reference it can reach.

Anything it reaches is kept. Everything else is garbage, and its memory is reclaimed.

Think of it this way

Imagine a warehouse where every box is either tied by string to the front door, or tied to a box that is.

The collector walks in, follows all the string, and marks what it reaches. Anything with no path back to the door gets thrown out — even if the box is full and looks important.

Remember this

It's about reachability, not scope.

Setting a variable to null rarely helps — the variable was going out of scope anyway. What keeps objects alive is a long-lived thing still pointing at them.

Generations — why this is fast 🟡 Intermediate

Scanning the whole heap on every collection would be far too slow. So the GC exploits an empirical observation: most objects die very young.

GenerationWhat's in itCollection costFrequency
Gen 0Brand new objectsVery cheap — small region, most of it is garbageOften
Gen 1Survived one collectionCheap. Acts as a bufferLess often
Gen 2Survived twice+. Long-lived objectsExpensive — scans everythingRarely
LOHObjects ≥ ~85 KBCollected with Gen 2; not compacted by defaultRarely

A Gen 0 collection typically only has to look at a small nursery region, and since most of it is dead, it reclaims a lot for very little work.

The counter-intuitive consequence

Allocating lots of short-lived objects is cheap. Gen 0 handles them efficiently.

What's expensive is objects that survive — they get promoted to Gen 1, then Gen 2, and Gen 2 collections are the ones that hurt.

Common mistake

"Avoid all allocation" is the wrong lesson. A million short-lived objects in a request are handled fine by Gen 0.

The thing to actually avoid is mid-life crisis: objects that live just long enough to get promoted to Gen 2 but then die — a cache with a short TTL, a buffer held across an await. Those make Gen 2 grow and force expensive collections.

The Large Object Heap 🔴 Advanced

Objects of roughly 85 KB or more go straight to the LOH. Two consequences:

  • They're effectively born in Gen 2. So they're only reclaimed by expensive collections.
  • The LOH isn't compacted by default. Freeing a 200 KB block leaves a 200 KB hole. If the next request needs 300 KB it can't use that hole, so the heap grows even though there's free space — fragmentation.

The usual culprit is large arrays: a byte[] for a file upload, a List<T> that grows past the threshold, or a large string.

// Bad in a hot path: a new 100 KB array per call, straight to the LOH
var buffer = new byte[100_000];

// Better: reuse pooled buffers
var pool = ArrayPool<byte>.Shared;
var buffer = pool.Rent(100_000);
try
{
    // ...use buffer. Note: it may be LARGER than requested.
}
finally
{
    pool.Return(buffer);        // must return it, or the pool starves
}
Two ArrayPool gotchas
  • Rent can return a bigger array than you asked for. Always track your own length — don't use buffer.Length.
  • The buffer may contain data from a previous use. Pass clearArray: true to Return if it held anything sensitive.

IDisposable — what the GC can't do 🔥 Must know

In simple terms

The GC manages memory. It knows nothing about file handles, sockets, database connections or OS locks.

IDisposable is how you release those deterministically, at a moment you choose.

Think of it this way

The GC is a cleaner who tidies up rubbish. It's very good at that.

But it has no idea you left the tap running or borrowed a library book. Those need you to deliberately turn it off and hand it back — that's Dispose.

// C# 8+ using declaration - disposed at the end of the enclosing scope
using var conn = new SqlConnection(connectionString);
await conn.OpenAsync(ct);
// conn.Dispose() runs here, even if something throws
Production trap — the connection leak

Forgetting using on a database connection doesn't leak memory — the GC collects the object eventually. It leaks the connection back to the pool late, or not at all.

The symptom is "Timeout expired. The timeout period elapsed prior to obtaining a connection from the pool" under load. It looks like a database problem and it's actually a missing using.

Finalizers — and why you almost never write one 🔴 Advanced

A finalizer (~MyClass()) is a last-resort safety net that the GC calls before reclaiming an object. It exists in case someone forgot to call Dispose.

Why you should avoid them:

  • An object with a finalizer survives an extra collection. It gets put on a queue, the finalizer thread runs it, and only then can the memory be freed — so it's automatically promoted.
  • You can't control when it runs. It could be seconds later, or at process exit.
  • If the finalizer throws or blocks, it stalls the finalizer queue for every other object.
The rule

Only write a finalizer if you hold a raw unmanaged handle directly — a IntPtr from a native API.

If you only hold other IDisposable objects, implement IDisposable and no finalizer. That's the overwhelmingly common case.

public sealed class OrderRepository : IDisposable
{
    private readonly SqlConnection _conn;

    public OrderRepository(string cs) => _conn = new SqlConnection(cs);

    // We only hold a managed IDisposable, so this is all we need.
    public void Dispose() => _conn.Dispose();
}

Finding a real memory leak ⭐ Senior-level

In simple terms

In .NET a "leak" means: something the GC can still reach is keeping objects alive that you thought were finished with.

So the question is always: what is still pointing at this?

The four causes, in order of how often they occur

CauseWhat it looks like
1. Event handlers A long-lived publisher holds a strong reference to every subscriber. Short-lived subscribers that never unsubscribe can never be collected.
2. Static collections A static Dictionary used as a cache with no eviction. It only ever grows.
3. Captured closures A lambda stored somewhere long-lived captures this implicitly, pinning the whole object.
4. Captive dependencies A scoped service (like a DbContext) injected into a singleton. It now lives for the process lifetime. 
public class OrderView            // created per request / per window
{
    public OrderView(IOrderNotifier notifier)   // notifier is a SINGLETON
    {
        notifier.OrderChanged += OnOrderChanged;   // subscribes...
    }

    private void OnOrderChanged(object? s, EventArgs e) { }
    // ...and never unsubscribes. The singleton now holds this OrderView forever.
}
public sealed class OrderView : IDisposable
{
    private readonly IOrderNotifier _notifier;

    public OrderView(IOrderNotifier notifier)
    {
        _notifier = notifier;
        _notifier.OrderChanged += OnOrderChanged;
    }

    public void Dispose() => _notifier.OrderChanged -= OnOrderChanged;
}

How to actually diagnose it

  1. Confirm it's real. Memory rising isn't a leak — the GC is lazy and won't collect until it needs to. A leak is memory that rises and never comes back down after a Gen 2 collection. Watch the trend over hours, not minutes.
  2. Take two dumps. One early, one after growth. On Linux/containers: dotnet-dump collect -p <pid>.
  3. Compare object counts. In dotnet-dump analyze, use dumpheap -stat on both and look for the type whose count grew. That type is usually the symptom, not the cause.
  4. Find what's rooting it. gcroot <address> shows the chain of references keeping it alive. This is the step that gives you the answer — it names the static, the event, or the singleton.
  5. Fix the root, not the symptom. Unsubscribe, add eviction, or fix the lifetime.
Best practice

Track Gen 2 heap size and time in GC as metrics, not just total process memory. Total memory is noisy — the GC deliberately holds onto memory it might reuse. A steadily climbing Gen 2 with no plateau is the real signal.

Span<T> and avoiding allocation 🔴 Advanced 💡 Good to know

In simple terms

Span<T> is a window onto memory you already have — an array, a string, a stack buffer — without copying it.

var csv = "1234,5678,9012";

// Allocates three new strings
var partsAlloc = csv.Split(',');

// Zero allocation: each slice is a view over the original string's memory
ReadOnlySpan<char> span = csv;
var first = span[..4];              // no new string
var value = int.Parse(first);       // parses directly from the span

Where it earns its place: parsers, serializers, and hot paths processing lots of text or binary data. It's the reason modern .NET JSON and HTTP handling got dramatically faster.

The constraint that catches people out

Span<T> is a ref struct — it can only live on the stack. So you cannot:

  • store it in a field of a class
  • use it in an async method across an await
  • capture it in a lambda
  • put it in a collection

If you need any of those, use Memory<T>, which is heap-friendly and can be converted to a span when you need one.

Workstation vs Server GC 🔴 Advanced 💡 Good to know

Workstation GCServer GC
HeapsOneOne per logical core
Optimised forLow latency, low memoryThroughput
Default forDesktop appsASP.NET Core apps
Memory useLowerHigher — multiple heaps
The container gotcha

Server GC allocates a heap per core, so in a container with a low memory limit but many visible cores, it can reserve far more memory than the limit allows — and get OOM-killed.

Modern .NET is container-aware and reads cgroup limits, but if you're seeing unexplained OOM kills in Kubernetes, checking whether Server GC suits your CPU/memory ratio is a reasonable step. Setting ServerGarbageCollection=false for small containers is a known tuning move — measure it, don't assume.

Key takeaways
  • The GC collects what's unreachable. Scope is irrelevant; roots are everything.
  • Gen 0 is cheap. Short-lived garbage is nearly free; surviving objects are what cost you.
  • Objects ≥ ~85 KB go to the LOH, are born effectively in Gen 2, and fragment.
  • IDisposable is for unmanaged resources. Missing using leaks connections, not memory.
  • Don't write finalizers unless you hold a raw handle. They delay collection.
  • Leaks are event handlers, static caches, closures capturing this, and captive dependencies.
  • Diagnose with two dumps, dumpheap -stat, then gcroot.
  • Span<T> avoids copies but can't cross an await or live in a field.

Common mistakes

  • Subscribing to an event and never unsubscribing — the number one .NET leak.
  • A static dictionary as a cache with no size limit or eviction.
  • Injecting a DbContext into a singleton — captive dependency.
  • Missing using on connections, streams and HttpResponseMessage.
  • Writing a finalizer when the class only holds managed disposables.
  • Calling GC.Collect() to "fix" memory. It forces an expensive full collection and almost always makes things worse.
  • Treating rising memory as a leak without checking whether it recovers after Gen 2.
  • Large byte[] per request instead of pooling — LOH fragmentation.

Interview questions

Basic

How does garbage collection work in .NET?
How I'd answer

"The GC works on reachability. It starts from a set of roots — statics, locals on active stacks, registers — follows every reference it can reach, marks those objects as live, and reclaims everything else."

"The key optimisation is generations. Scanning the whole heap every time would be too slow, so it exploits the fact that most objects die young. New objects go in Gen 0, which is small and mostly garbage — so collecting it is quick and reclaims a lot. Survivors get promoted to Gen 1, then Gen 2. Gen 2 collections scan everything and are expensive, but they're rare."

"The practical consequence people get backwards: allocating lots of short-lived objects is cheap. What's expensive is objects surviving and being promoted. So the thing to avoid isn't allocation generally — it's objects that live just long enough to reach Gen 2 and then die."

"There's also the Large Object Heap for anything around 85 KB or more. Those effectively start in Gen 2, and the LOH isn't compacted by default, so it fragments — free space exists but in the wrong size holes. That's why large buffers are usually pooled rather than allocated per use."

"And the thing the GC explicitly doesn't do is unmanaged resources. It has no idea about file handles or database connections, which is what IDisposable is for."

What they're really checking
  • Do you know it's reachability, not reference counting?
  • Do you know generations and why they exist?
  • Bonus: the "short-lived garbage is cheap" insight, and the LOH.
Weak answers
  • Red flag: describing reference counting — that's COM/Python, not .NET.
  • Red flag: "it frees objects when they go out of scope."
Likely follow-ups
  • What's the difference between Workstation and Server GC?
  • Should you ever call GC.Collect()?
  • What's the LOH threshold and why does it matter?

Intermediate

Can you have a memory leak in C#? Give an example. 🔥 Must know
How I'd answer

"Absolutely — managed memory doesn't prevent leaks, it just changes what a leak is. In .NET a leak means something reachable from a root is keeping objects alive that you thought were done with."

"The most common cause I've hit is event handlers. A publisher holds a strong reference to every subscriber. If the publisher is a singleton and subscribers are created per request, and nobody unsubscribes, then every subscriber ever created stays alive for the process lifetime. Memory grows steadily and never recovers."

"Second most common is a static collection used as a cache with no eviction. It only ever grows. That one's obvious in hindsight and very easy to write."

"Third is closures capturing this. If a lambda touches any instance field, it captures the whole object implicitly — and if that lambda is stored in a timer, a static registry or an event, the object can't be collected."

"And the ASP.NET Core–specific one: a captive dependency — injecting a scoped DbContext into a singleton. Now that context lives forever, which leaks memory and also gives you stale data and eventually a disposed-object exception."

"For diagnosis I'd take two dumps separated by the growth period, run dumpheap -stat on both to see which type's count grew, then gcroot on an instance to see the reference chain keeping it alive. That last step is what actually names the culprit — the growing type is usually just the symptom."

What they're really checking
  • Do you know managed ≠ leak-proof?
  • Can you name specific, realistic causes?
  • Have you actually diagnosed one — do you know gcroot?
Weak answers
  • Red flag: "no, the GC handles it."
  • Red flag: "you forget to call Dispose" — that leaks resources, not usually memory.
Likely follow-ups
  • How would you confirm it's a leak rather than the GC just being lazy?
  • What's a weak reference and when would you use one?
  • How do you prevent the event handler leak by design?
What's the difference between Dispose and a finalizer? ⭐ Senior-level
How I'd answer

"Dispose is deterministic — I call it, or using calls it, at a moment I control. A finalizer is non-deterministic: the GC calls it at some unspecified point before reclaiming the object, and possibly not until process exit."

"They exist for different jobs. Dispose is how you release unmanaged resources promptly — connections, file handles, sockets. A finalizer is a safety net for when someone forgot to call Dispose, so a native handle doesn't leak forever."

"The cost of a finalizer is the part people miss. An object with one survives an extra collection: the GC can't free it immediately, it goes on the finalization queue, a dedicated thread runs the finalizer, and only then is the memory reclaimable. So finalizable objects are automatically promoted, which is exactly what you don't want. And if a finalizer blocks or throws, it stalls the queue for everything else."

"So my rule is: only write a finalizer if the class holds a raw unmanaged handle directly. If it only holds other IDisposable objects — which is the normal case — implement IDisposable and no finalizer at all."

"If I do need both, that's the full dispose pattern: Dispose() does the cleanup and calls GC.SuppressFinalize(this) so the finalizer is skipped when disposal happened properly. And a protected virtual Dispose(bool disposing) distinguishes the two paths — from the finalizer you must not touch other managed objects, because they may already be collected."

What they're really checking
  • Do you know finalizers delay collection?
  • Do you know when a finalizer is actually needed (rarely)?
  • Bonus: SuppressFinalize and why the finalizer path can't touch managed objects.
Likely follow-ups
  • Why can't a finalizer safely use other managed objects?
  • What is SafeHandle and why is it preferred?
  • What does IAsyncDisposable add?

Advanced

A service's memory grows 200 MB a day and never recovers. Walk me through diagnosing it. ⭐ Senior-level
How I'd answer

"First I'd confirm it's genuinely a leak rather than the GC being lazy. Rising memory on its own proves nothing — the runtime holds onto memory it might reuse. What I want to see is whether it comes back down after a Gen 2 collection. So I'd look at Gen 2 heap size as a metric rather than total process memory, over hours. A steady climb with no plateau is a real leak."

"Then two dumps: one early, one after a day of growth. dotnet-dump collect works in containers, which matters because that's usually where this is happening."

"I'd run dumpheap -stat on both and diff them. That gives me the type whose instance count grew — but I'd treat that as the symptom. If a million OrderView objects are alive, the question is what's holding them."

"So the important step is gcroot on one of those instances. That prints the reference chain from a root down to the object, and it names the actual culprit — a static field, an event's invocation list, a singleton's field."

"In my experience the answer is one of four things. An event handler that was never unsubscribed, where the publisher is long-lived. A static collection used as a cache with no eviction. A closure capturing this and being stored somewhere long-lived, like a timer callback. Or a captive dependency — a scoped service injected into a singleton."

"Once I know the root, the fix is usually small: unsubscribe in Dispose, swap the static dictionary for MemoryCache with a size limit and expiry, or fix the DI lifetime."

"For prevention I'd add Gen 2 heap size and time-in-GC to the dashboard with an alert on a sustained upward trend, so the next one gets caught in days rather than when the container starts getting OOM-killed."

What they're really checking
  • Do you validate the premise before investigating?
  • Do you know the actual tooling, or just talk about "profiling"?
  • Do you distinguish the growing type from the root cause?
Weak answers
  • Red flag: "restart the service nightly."
  • Red flag: "call GC.Collect()."
  • Red flag: "use a profiler" with no idea what you'd look at.
Likely follow-ups
  • What if the growing type is byte[] or string?
  • How would you do this in a container you can't attach a debugger to?
  • What's the difference between a leak and LOH fragmentation?
