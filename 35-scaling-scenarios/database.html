Database Scaling

The database is the usual real ceiling. Most of these problems are about a query plan, a key choice, or work that shouldn't be running there at all.

🔴 Advanced ⭐ Senior-level
Quick revision
  • "It was fast last week" → data growth crossed a threshold, or the plan changed.
  • Scans are fine until they aren't. Cost grows with rows; the query didn't change.
  • Hot partition: adding capacity never helps. Increase key cardinality.
  • Every index makes writes slower. Read wins are paid for on write.
  • Reporting on the transactional database is the most common self-inflicted wound.
  • Read replicas are eventually consistent — read-after-write will surprise you.
  • Batch jobs need batching, not one big transaction.
  • Unbounded tables have a cliff, not a slope.

Scenario: a query that was fast is now slow 🔥 Must know

A new N+1 Started at a deployment; hundreds of fast calls Include or a projection
Index fragmentation or a dropped index After maintenance or a schema change Rebuild, or restore the index
Senior signal — gradual versus sudden splits the causes in half

Before looking at any plan, establish the shape of the degradation, because it eliminates half the possibilities immediately.

Gradual — slower each month — is almost always a scan whose cost grows with the table. The query didn't change; the data did. A missing index that costs 20ms on 50,000 rows costs two seconds on five million, and nothing in the code looks different. This is the single most common "it used to be fast".

Sudden, with no deployment, points at a plan change. The optimiser chose differently — new statistics, a recompile, or parameter sniffing where the plan was compiled for an atypical parameter and cached.

Parameter sniffing is worth being able to describe, because it produces a genuinely confusing symptom: the same query is fast for some inputs and slow for others, and which is which can flip after a restart or a statistics update. That's because the cached plan suits the parameter it was compiled for, and a plan good for one customer with ten orders is terrible for one with a million.

Sudden, at a deployment is a code change — a new N+1, a changed query, a lost AsNoTracking, an Include that now pulls far more data.

So "when did it change, and was it gradual or sudden?" is the first question, and it's worth asking out loud in an interview.

Read the plan, and know what you're looking for

The plan answers most of this, and there are four things worth checking specifically.

Scans where a seek was expected. A clustered index scan on a large table with a selective predicate means no usable index.

Estimated versus actual rows. A large discrepancy means the optimiser was working from bad information — stale statistics, or a parameter it couldn't sniff usefully — and every downstream choice follows from that estimate. This is usually the most informative single number in a plan.

Key lookups. The index was used to find rows, then the engine went back to the table for columns the index didn't cover. Adding those as INCLUDE columns often removes most of the cost.

Spills to disk. A sort or hash that exceeded its memory grant, which is slow and usually follows from the bad estimate above.

For Azure SQL, Query Store is the tool that answers "what changed": it keeps plan history per query, so you can see the exact point a plan regressed and force the previous one as an immediate mitigation. That's a much stronger answer than "I'd look at the plan".

Scenario: one partition is saturated 🔥 Must know

  Provisioned: 10,000 RU/s across 10 physical partitions = 1,000 RU/s each

  partition 0   [##########]  1000 RU/s   THROTTLED - 429s
  partition 1   [#         ]   100 RU/s
  partition 2   [          ]     0 RU/s
  ...

  Total consumption: 1,100 of 10,000 RU/s.
  The metric says 11% utilised. Users are getting errors.

  Doubling to 20,000 RU/s -> 20 partitions -> 1,000 RU/s each.
  The hot key STILL hashes to one partition. Nothing improves.
This is the same problem in every store, and capacity never fixes it

Cosmos DB partition keys, DynamoDB partition keys, Kafka and Event Hubs partition keys, Redis hot keys, sequential blob name prefixes, and a SQL table partitioned on a skewed column. One problem, six APIs.

The reason capacity doesn't help is worth stating precisely: throughput is divided across partitions, and a single key always maps to exactly one partition. Adding partitions gives each one a smaller share — so in some configurations, scaling up makes the hot partition worse.

And the aggregate metric is actively misleading. Total consumption at 11% while users see 429s is exactly what this looks like, which is why you must split the metric by partition to see it at all.

What actually works:

  • Increase key cardinality. A synthetic key — tenantId_bucket where bucket is a hash suffix — spreads one logical key across N partitions. Cost: reads for that key must fan out across the buckets.
  • Choose a different key. The real fix and usually a migration, because the key is immutable in Cosmos and DynamoDB.
  • Hierarchical partition keys in Cosmos, which subdivide within a tenant so a large tenant isn't confined to one physical partition.
  • Cache the hot key, which removes read pressure without changing the model — the pragmatic immediate mitigation.
  • Separate the outlier. One enormous tenant in its own container or database, which is often simpler than making the shared model handle both.

The mitigation-versus-fix framing matters here: caching or throttling the hot caller restores service today; the key change is a migration you plan properly.

Scenario: writes can't keep up 🔴 Advanced

CauseFixCost
Too many indexesDrop unused ones — every index is written on every insertSome reads get slower
One row per eventBatch inserts, or SqlBulkCopyLatency before durability
Log write throughputHigher tier, or fewer/larger transactionsCost, or larger blast radius
Page latch contention on a sequential keyA different key, or table partitioningLoses index locality
Triggers or computed indexesMove the work out of the write pathConsistency becomes eventual
Synchronous writes in the request pathQueue and write asynchronouslyThe client no longer knows it persisted
The two highest-value checks on a write-heavy table

Count the indexes. Every non-clustered index must be maintained on every insert, update and delete that touches its columns. A table with twelve indexes does thirteen writes per insert. Teams add indexes to fix read performance and rarely remove any, so this accumulates invisibly — and the DMVs will tell you which indexes have never been used since the last restart.

That's the clearest example of the general rule: a read optimisation is paid for on write, and on a write-heavy table the bill can exceed the benefit.

Check the write pattern. One row per statement is enormously more expensive than batching — each is a round trip, a transaction and a log flush. Batching a thousand inserts into one operation is routinely an order of magnitude faster, and SqlBulkCopy more again for bulk loads.

Beyond that, the structural change is queue-based writes: accept the request, publish to a queue, write in batches from a consumer. That converts a throughput ceiling into a latency trade-off, which is usually the better problem to have. The honest cost is that the caller gets a 202 rather than a confirmation, so the API contract changes and the client needs a way to check status.

Scenario: intermittent timeouts and blocking 🔥 Must know

CauseSignature
Long transactionsLocks held far longer than the work requires
An HTTP call inside a transactionLock duration depends on a third party
Lock escalationBulk update takes a table lock at ~5,000 row locks
Serializable isolationRange locks blocking more than expected
DeadlocksError 1205; two paths taking locks in different orders
A report against live tablesLong shared locks blocking writers
A transaction's cost is its duration, not its size

The mental model that fixes most blocking: a transaction holds locks until it commits, so what matters is how long it's open — not how much data it touches.

Which makes the worst pattern clear: an external call inside a transaction. Begin, update a row, call a payment provider, commit. Now the lock is held for however long that provider takes — normally 200ms, occasionally 30 seconds — and every writer touching that row waits behind a third party you don't control. Under load that cascades into timeouts that look like a database problem.

Same for a transaction spanning user interaction, or one that starts before some expensive computation.

The fix is to do the slow work outside the transaction, and if the external call must be atomic with the write, that's what the outbox pattern is for: write the intent locally in the transaction, commit, then perform the call from a separate process with retries.

Two more that come up: lock escalation, where a bulk update crossing about 5,000 row locks takes a table lock instead and blocks everything — batch the update to stay below it. And deadlocks, which are usually two code paths taking the same locks in different orders; the fix is consistent ordering, plus a retry, since a deadlock victim is a transient failure by design.

Scenario: reporting is killing the database 🔥 Must know

Materialised summariesFast, cheap queriesStaleness; maintenance on write

READ UNCOMMITTED / snapshotStops report locks blocking writersDirty reads, or version-store pressure
Senior signal — these are different workloads sharing one machine

The framing that makes this decision easy: transactional and analytical workloads want opposite things.

OLTP wants many small, selective, indexed operations with low latency and short locks. Analytics wants to scan millions of rows and aggregate. Running both on one server means the report's scans evict the working set from the buffer pool, its shared locks block writers, and its memory grants starve everything else.

So the first question isn't "how do I make this report faster?" — it's "why is this running here at all?"

A read replica is the cheapest real separation: on Azure SQL it's a connection-string change (ApplicationIntent=ReadOnly) with a Business Critical or Hyperscale tier. Almost no work, and it removes the interference completely.

The trade to state honestly: replicas are asynchronous, so a report may not see the last few seconds of writes — fine for reporting, and it breaks read-after-write. Routing ordinary application reads to a replica means a user can save a record and not see it, which is a much more visible problem than a slightly stale report.

So: reports and exports to the replica, user-facing reads that follow a write to the primary. That distinction is what separates a considered answer from "use a read replica".

Scenario: a table that grew without bound 🟡 Intermediate

Unbounded growth is a cliff, not a slope

An events, audit or notifications table with no retention policy behaves fine for a long time and then degrades quickly — because performance holds while the working set fits in memory and falls off when it doesn't.

So the symptom is "it was fine last month", and the cause is months old.

The options, and they compose:

  • Archive and delete on a retention policy. The real fix, and the deletion itself must be batched — a single DELETE of ten million rows takes a table lock, fills the log and blocks everything.
  • Table partitioning by date, so old data can be switched out almost instantly rather than deleted row by row.
  • Move cold data to cheaper storage — blob, or an analytical store — if it must be retained.
  • Cosmos DB or DynamoDB TTL, where the platform expires rows for you. Much better than a cleanup job, because there's nothing to schedule or monitor.

The prevention is the point though: every table that grows per-event needs a retention decision when it's created. That's a five-minute conversation at design time and a migration afterwards — and "how big will this be in three years?" is a genuinely useful review question.

Key takeaways
  • Gradual degradation is a scan meeting more rows; sudden is a plan change.
  • Parameter sniffing makes the same query fast for some inputs and slow for others.
  • Query Store shows when a plan regressed and can force the old one.
  • Estimated versus actual rows is the most informative number in a plan.
  • A hot partition can't be fixed with capacity — increase key cardinality.
  • Aggregate utilisation hides a hot partition entirely; split by partition.
  • Every index is a write cost; check for unused ones on write-heavy tables.
  • Batch writes; queue-based writes trade a throughput ceiling for a latency one.
  • A transaction's cost is its duration — never an HTTP call inside one.
  • Batch bulk updates to stay under lock escalation.
  • OLTP and analytics want opposite things — separate them.
  • Read replicas are asynchronous, so they break read-after-write.
  • Unbounded tables degrade suddenly; decide retention at design time.
  • Batch large deletes, or partition and switch out.

Common mistakes

  • Scaling the tier for what is a missing index.
  • Adding capacity for a hot partition.
  • Reading aggregate RU or DTU and concluding there's headroom.
  • Adding indexes without removing any, on a write-heavy table.
  • One insert per row in a bulk load.
  • An HTTP call inside a transaction.
  • A single DELETE for millions of rows.
  • Reporting queries against live transactional tables.
  • Routing user reads to a replica, breaking read-after-write.
  • READ UNCOMMITTED everywhere to avoid blocking.
  • No retention policy on an events or audit table.
  • Retrying a deadlock victim's whole request without idempotency.

Interview questions

Advanced

A query that took 50ms now takes 8 seconds. Nothing was deployed. 🔥 Must know
How I'd answer

"'Nothing was deployed' is the useful constraint — it rules out a code change, so either the data changed or the plan changed. The first thing I'd establish is whether this was gradual or sudden, because that separates those two cleanly."

"If gradual — slower over weeks — it's almost certainly a scan meeting more rows. The query was always doing a scan; it just didn't matter at 50,000 rows and does at five million. Nothing changed except the data, which is why it feels mysterious. The fix is an index, and I'd confirm from the plan that there's a scan where a seek should be."

"If sudden, with no deployment, it's a plan change. And the specific one I'd suspect is parameter sniffing."

"The mechanism: SQL Server compiles a plan for the first parameter values it sees and caches it. If that first execution was for a customer with ten orders, the plan uses a nested loop with index seeks — perfect for ten rows, catastrophic for a customer with a million. So the same query text is fast for some parameters and slow for others."

"And it flips without warning: a restart, a failover, a statistics update or a memory-pressure eviction causes a recompile, and whichever parameter arrives first sets the plan for everyone. That's exactly 'it was fine yesterday'."

"Query Store is how I'd confirm it, and this is the concrete answer I'd give. It keeps plan history per query, so I can see the point the plan changed, compare the two plans, and see the duration distribution. On Azure SQL it's on by default."

"It also gives me the fastest mitigation: force the previous plan. That's a minutes-not-hours fix, and I'd label it as a mitigation — it's a hint pinned to a query, and it can become wrong as the data changes, so it needs revisiting rather than leaving forever."

"Other candidates I'd check. Stale statistics — if a large data load happened, the optimiser may be working from bad row estimates, and a large gap between estimated and actual rows in the plan is the tell. That's usually the most informative single number in a plan, because every downstream choice follows from the estimate."

"Blocking, if it's intermittent rather than consistent — the query itself may be fine and waiting behind something else. Wait statistics distinguish that immediately: LCK_ waits mean blocking, not a slow plan."

"A dropped or disabled index, if there was any maintenance. Worth a quick check because it's cheap to rule out and embarrassing to miss."

"Longer-term fixes, depending on the cause. For parameter sniffing: OPTIMIZE FOR UNKNOWN to get an average-case plan, or RECOMPILE if the compile cost is acceptable relative to the work, or splitting the query so the skewed and typical cases get different plans. Each has a real cost, and I'd choose based on how skewed the data actually is."

"And on prevention: an alert on p95 duration per query from Query Store, so a regression is caught in hours rather than when someone complains. Automatic plan correction is worth considering too — Azure SQL can detect a regression and revert the plan itself, which handles the common case without anyone being paged."

What they're really checking
  • Do you separate gradual from sudden first?
  • Can you explain parameter sniffing mechanically?
  • Do you know Query Store and forcing a plan?
  • Do you check estimated versus actual rows?
  • Do you rule out blocking with wait statistics?
  • Do you treat forcing a plan as a mitigation?
Weak answers
  • Red flag: "add an index" with no diagnosis.
  • Red flag: scaling the database tier.
  • Red flag: no awareness that plans change on their own.
Likely follow-ups
  • Why would forcing a plan be a bad long-term fix?
  • How would you handle genuinely skewed data?
  • What would you alert on?
Cosmos DB is returning 429s but you're using 15% of provisioned RUs. ⭐ Senior-level
How I'd answer

"That combination is diagnostic on its own: throughput is provisioned per container and divided across physical partitions, so 15% aggregate with throttling means one partition is at its share while the others are idle. A hot partition."

"The arithmetic makes it concrete. 10,000 RU/s across ten physical partitions is 1,000 RU/s each. If one partition is taking 1,000 and the rest take almost nothing, total consumption is around 11% and that one partition is throttling every request."

"I'd confirm it by looking at normalised RU consumption per partition key range, which Azure Monitor exposes. The aggregate metric is the thing that misled us; the per-partition view shows it immediately. Same principle as never trusting an average across instances."

"Then find which key. Usually one of three things: a tenant far larger than the others, a poorly-chosen key with low cardinality — status, country, type — or a synthetic hotspot like using today's date so all of today's writes land in one place."

"The critical point is that adding RUs does not fix this. Doubling to 20,000 gives twenty partitions at 1,000 each — the hot key still hashes to exactly one. In some cases scaling up makes it worse, because each partition's share shrinks. So the instinctive fix is not only ineffective, it's expensive."

"That's worth saying explicitly, because it's the same physics as a hot key in Redis, a skewed Kafka partition key, and a sequential blob name prefix. One problem, different APIs — and in all of them capacity is not the lever."

"Immediate mitigation, since the real fix is a migration: cache the hot key if reads dominate — that removes pressure without touching the data model. Throttle or queue the hot writer if it's writes. And make sure the SDK's retry-on-429 with backoff is configured, so throttling degrades latency rather than surfacing as errors."

"The real fixes, and the choice depends on the cause."

"A synthetic key — tenantId_bucket where bucket is a hash of the item id modulo N. That spreads one logical key across N partitions. The cost is real: reads for that tenant must now fan out across all N buckets, so a point read becomes a cross-partition query. Worth it for a write hotspot, often not worth it for reads."

"Hierarchical partition keys, which is usually the better answer for the large-tenant case: partition on tenant and then a subkey, so Cosmos can split a single tenant across physical partitions while keeping queries for that tenant efficient. That's specifically designed for this problem."

"Separate the outlier. If one tenant is a hundred times the others, putting them in their own container or account is often simpler than making a shared model serve both extremes — and it gives them isolated throughput, which is a benefit rather than a workaround."

"A different partition key entirely, if it was just wrong. That's the honest answer and it's a migration: the key is immutable, so it means a new container and a copy, usually via change feed with dual-write during the transition."

"On prevention, two things. Per-partition monitoring and alerting, because the aggregate will never show this. And treating partition key choice as an architectural decision reviewed up front — it's irreversible, and the cardinality question 'how many distinct values, and how evenly distributed?' takes two minutes to ask at design time versus a migration later."

What they're really checking
  • Do you recognise a hot partition from the aggregate/throttle mismatch?
  • Do you know throughput is divided per partition?
  • Do you know adding RUs doesn't help, and can explain why?
  • Do you know synthetic and hierarchical keys, with their costs?
  • Do you separate mitigation from the migration?
  • Do you connect it to hot keys elsewhere?
Weak answers
  • Red flag: "increase the RUs."
  • Red flag: unaware throughput is divided across partitions.
  • Red flag: proposing a key change with no mention of migration.
Likely follow-ups
  • How would you migrate to a new partition key with no downtime?
  • What does a synthetic key cost you on reads?
  • What would you have asked at design time?
