SNAT port exhaustion — the outbound limit that surprises everyone

Instances share a limited pool of SNAT ports for outbound connections to public endpoints. Each distinct destination connection consumes one, and a closed connection holds its port in TIME_WAIT for a period afterwards.

So an app making many outbound HTTP calls exhausts the pool and new outbound connections fail or hang — while CPU, memory and request counts all look completely normal. It presents as "the third-party API is down", and it isn't.

The leading cause is new HttpClient() per request. Each instance opens fresh connections rather than reusing a pool, so port consumption scales with request volume instead of with the number of destinations.

Fixes, in order:

  • IHttpClientFactory, or a properly reused client, so connections are pooled and ports are reused. This alone resolves most cases.
  • Private endpoints or service endpoints for Azure services, so that traffic doesn't consume SNAT ports at all.
  • A NAT Gateway, which provides a much larger port pool and a stable outbound IP as a bonus.
  • Connection lifetime limits so pooled connections are recycled rather than accumulating.

Worth knowing because the App Service metrics don't show it clearly — it's in the Diagnose and Solve blade under SNAT, and if you don't know the concept exists you won't find it.

ARR affinity is the reason scale-out sometimes does nothing

App Service enables session affinity by default, pinning each client to one instance with a cookie. It exists so legacy stateful apps survive scale-out.

For a stateless app it's actively harmful. Adding instances doesn't relieve existing clients, because they stay pinned to the instance they started on — so you scale from two to six and the load distribution barely changes.

It also prevents graceful instance replacement, and losing an instance drops those users' state rather than failing over.

Turn it off for anything stateless. It's one setting, and if the app genuinely needs it, that's a signal to move session state to Redis rather than to keep the pinning.

Pending pods: check requests before capacity

kubectl describe pod names the reason in Events, and the most common one isn't a genuine capacity shortage — it's requests that don't fit any node. A pod requesting 8 CPU on a cluster of 4-core nodes will never schedule, however many nodes you add.

The next most common is over-requesting across the board. Because the scheduler allocates on requests rather than usage, a cluster where every pod requests four times what it uses looks full at 25% real utilisation — and the autoscaler dutifully adds nodes nobody needs. Right-sizing requests from observed p95 usage commonly reclaims 2–4×.

Then the AKS-specific one: IP exhaustion. With traditional Azure CNI, every pod consumes a VNet IP and addresses are pre-allocated per node based on maximum pods — so a node configured for 110 pods reserves 110 addresses on joining. Thirty nodes is 3,300 addresses against a /24 holding 251. The autoscaler adds a node, there are no IPs, and it never becomes ready.

That one can't be fixed in place, because a subnet in use can't be resized — hence Azure CNI Overlay as the correct default, where only nodes consume VNet addresses.

Functions scaling out is what breaks the database

This is the most common Functions scaling incident, and it's counterintuitive because the platform is doing exactly what you asked.

A queue backlog causes the platform to add instances — dozens, or hundreds. Each instance has its own connection pool. So two hundred instances with a modest pool each is thousands of connections against a database with a hard limit.

The result is connection timeouts across the whole system, including from your web app, which was healthy — because it's now competing with two hundred function instances for the same finite server.

Fixes:

  • Cap the scale-out — functionAppScaleLimit, or maximum instance count on Flex Consumption. The most direct control, and the one people don't know exists.
  • Reduce batch concurrency so each instance does more per invocation rather than each invocation opening its own resources.
  • Lower the per-instance pool size, since a function instance handling a few messages doesn't need a pool of 100.
  • Reserve database headroom for the interactive workload, so batch processing can't starve user-facing requests.

The general lesson: elastic compute in front of a fixed-capacity dependency moves the failure, it doesn't remove it. Automatic scaling is only safe if everything downstream can absorb the resulting concurrency — which is the same reasoning as scaling out a web app onto a shared database.

Partition count is a hard scaling ceiling

For Event Hubs and Cosmos change feed triggers, the platform will not create more instances than there are partitions or leases, because there's nothing for the extra instances to read.

So a hub with four partitions gives at most four concurrent function instances, however large the backlog. Scaling settings, plan tier and instance limits make no difference — and the metric shows the function not scaling while lag grows, which looks like a platform fault.

Which makes the partition count a capacity decision taken at creation, and one you can't easily reverse: increasing it later remaps keys and breaks ordering. This is the concrete reason to provision partitions generously up front.

If you're already at the ceiling and can't add partitions, the remaining levers are processing faster per event — larger batches, less per-event work — or fanning out: the triggered function does minimal work and posts to a queue, where a queue-triggered function scales without the partition constraint.

Senior signal — lock duration and prefetch explain most Service Bus oddities

Two settings cause most of the confusing behaviour, and they interact.

Lock duration is how long a received message is invisible to other consumers. If processing takes longer, the lock expires, the message is redelivered, and you now have two consumers doing the same work — while the first one's eventual Complete fails with a lock-lost exception.

The fix is either to renew the lock while working — the SDK can do this automatically — or to make the work shorter than the lock. Raising the lock duration is the blunt option and it delays recovery when a consumer genuinely dies.

Prefetch pulls messages to the client ahead of processing, which improves throughput and has a catch: prefetched messages have their locks running. So a consumer that prefetches 100 messages and processes them slowly will see later ones expire while still in its local buffer — and meanwhile those messages are invisible to the idle consumer next door.

That's the "messages are delayed but consumers are idle" symptom, and it's why prefetch should be modest — a few times the concurrent processing count, not hundreds — unless processing is genuinely fast.

Both come back to the same principle: a message held is a message nobody else can process, so hold time is the thing to minimise.

Log write rate is the limit nobody plans for

Every Azure SQL tier caps transaction log write throughput in MB/s, and it's a hard limit reached long before CPU on write-heavy workloads.

The symptom is distinctive: writes are slow or throttled while CPU sits low. Which looks like a mystery if you're only watching DTU as a single number, because DTU blends CPU, data IO and log IO — so 100% DTU tells you nothing about which resource is the constraint.

So the diagnostic is to check the individual metrics rather than the composite: sys.dm_db_resource_stats reports CPU, data IO and log IO separately, and LOG_RATE_GOVERNOR appearing in wait statistics is conclusive.

Fixes are about generating less log: batch writes rather than one row per statement, drop unused indexes since every index is logged on every write, avoid updating columns that didn't change, and use minimal logging for bulk loads where the recovery model allows. Scaling the tier raises the limit and is the expensive answer.

Worth knowing simply because "DTU is at 100%" is not a diagnosis — it's the start of one.

Aggregate RU utilisation is the most misleading metric in Azure

Throughput is provisioned per container and divided evenly across physical partitions. So 10,000 RU/s across ten partitions is 1,000 RU/s each, and a single hot key can throttle while total consumption reads 11%.

Which produces the exact contradiction people report: "we're getting 429s and the portal says we're using 15% of our RUs." Both are true.

And the instinctive fix is worse than useless — doubling to 20,000 RU/s gives twenty partitions at 1,000 each, so the hot key's share is unchanged while the bill doubles. In some cases the per-partition share shrinks.

So the metric to use is normalised RU consumption per partition key range, which Azure Monitor exposes and which shows this immediately. Then the real options are increasing key cardinality — a synthetic suffix, or hierarchical partition keys — caching the hot key as an immediate mitigation, or separating an outlier tenant.

The transferable lesson, and it appears throughout this section: an aggregate metric across partitions, instances or tenants will reassure you while a single unit is failing. Split by dimension before believing any headline number.

Key takeaways
  • App Service: turn off ARR affinity for stateless apps.
  • SNAT port exhaustion presents as a third-party outage — use IHttpClientFactory.
  • AKS pending pods: check requests and IP exhaustion before capacity.
  • Over-requesting makes a cluster look full at 25% utilisation.
  • Azure CNI Overlay avoids IP exhaustion, which can't be fixed in place.
  • Functions scaling out overwhelms fixed-capacity dependencies — cap the scale-out.
  • Event Hubs and Cosmos triggers cap instances at the partition count.
  • Service Bus: lock duration and prefetch cause most redelivery and delay problems.
  • A prefetched message has a running lock and is invisible to idle consumers.
  • Azure SQL: DTU is a composite — check CPU, data IO and log IO separately.
  • Log write rate throttles writes while CPU looks low.
  • Cosmos: aggregate RU utilisation hides a hot partition completely.
  • Adding RUs cannot fix a hot key and may reduce its share.
  • Split every metric by dimension before trusting the headline.

Common mistakes

  • Scaling out App Service with ARR affinity on.
  • new HttpClient() per request, exhausting SNAT ports.
  • Adding AKS nodes when requests don't fit any node size.
  • Traditional Azure CNI on a small subnet.
  • HPA on CPU for a queue consumer.
  • Uncapped Function scale-out against a fixed-capacity database.
  • Expecting Functions to scale past the partition count.
  • A large prefetch with slow processing.
  • Processing longer than the lock duration without renewal.
  • Reading DTU as one number instead of its components.
  • Scaling the SQL tier for a log-rate limit caused by unbatched writes.
  • Adding RUs for a hot partition.
  • Auto-inflate with no alert, leaving throughput units high permanently.
  • Assuming classic App Service or APIM can be scaled reactively.

How I'd answer

"On App Service or a VM-based service, my first thought is SNAT port exhaustion — because that's the failure mode that specifically affects outbound connections while every normal metric looks healthy."

"The mechanism: instances share a limited pool of SNAT ports for outbound connections to public endpoints. Each connection to a distinct destination consumes one, and a closed connection holds its port in TIME_WAIT for a while afterwards. Once the pool is exhausted, new outbound connections fail or hang."

"It's deceptive because nothing in the usual metrics moves. CPU, memory, request count and response time on inbound requests all look fine. The symptom looks like the third-party API being down — and the third party is fine."

"The most common cause is new HttpClient() per request. Each one opens fresh connections rather than reusing a pool, so port consumption scales with request volume rather than with the number of destinations. Which is why it only appears under load — at low traffic the ports recycle fast enough."

"That's slightly counterintuitive because HttpClient implements IDisposable, so disposing it looks correct. Disposing it is exactly what causes the problem, because the underlying connection goes to TIME_WAIT."

"I'd confirm it in the Diagnose and Solve Problems blade, which has a SNAT-specific detector showing port allocation and failures. That's worth knowing because it's not in the default metrics view — if you don't know the concept exists you won't find it."

"Fixes, in order. IHttpClientFactory so connections are pooled and reused — that alone resolves most cases, and it also fixes the opposite problem of a singleton client caching DNS forever, which matters when a dependency fails over."

"Private endpoints or service endpoints for Azure services, so that traffic doesn't traverse the public path and doesn't consume SNAT ports at all. Often the biggest single reduction, since a lot of outbound traffic is to Azure services."

"A NAT Gateway, which gives a much larger port pool — and a stable outbound IP as a bonus, which solves the separate problem of third parties allow-listing your IP and it changing when you scale."

"Bounded connection lifetime so pooled connections are recycled rather than accumulating, which IHttpClientFactory handles via PooledConnectionLifetime."

"Other candidates with the same shape I'd rule out. Thread pool starvation, if there's sync-over-async — but that would slow inbound requests too, so outbound-only failures point away from it. The dependency actually being slow, which dependency telemetry would show as duration rather than connection failures. DNS — either a singleton client with a stale cached address, or resolution failures."

"In AKS the equivalent problem exists at the load balancer or NAT Gateway level, with ports shared across the whole node pool — so one chatty pod can exhaust ports for everything on that node. Same diagnosis, different place to look."

"The general lesson I'd draw: the limits that catch you are the ones the default dashboard doesn't show. Inbound metrics look healthy because the problem is entirely on the outbound side — which is why knowing the platform's specific limits matters as much as general debugging skill."

Your Function scales to 200 instances and the whole platform breaks. Explain. ⭐ Senior-level
How I'd answer

"The platform did exactly what it was configured to do, and that's the problem: elastic compute in front of a fixed-capacity dependency moves the failure rather than removing it."

"The mechanism: a queue backlog causes the scale controller to add instances. Each instance has its own connection pool. Two hundred instances with even a modest pool each is thousands of connections against a database with a hard connection limit."

"So the database starts rejecting connections — and it rejects them for everyone, including the web application that was perfectly healthy and is now competing with two hundred function instances for the same finite server. A batch workload has taken down the interactive one."

"The same applies to any downstream with a fixed ceiling: a third-party API with a rate limit, Redis, or a Cosmos container with provisioned RUs. Two hundred instances hitting a rate-limited API means almost every call is throttled, and if there are retries it's much worse."

"Fixes, and the first one is the direct control."

"Cap the scale-out — functionAppScaleLimit, or maximum instance count on Flex Consumption. That's the setting people don't know exists, and it's the difference between elastic and unbounded. I'd size it from what the database can actually support."

"Reduce per-instance resource use. A function instance handling a handful of messages doesn't need a connection pool of 100 — lowering Max Pool Size means more instances fit within the same database budget."

"Increase batch size instead of instance count. Processing 32 messages per invocation rather than 1 gets the same throughput with far fewer instances and far fewer connections. Usually the best trade, because the per-invocation overhead was the inefficiency."

"Reserve headroom for the interactive workload. Either separate databases, or explicit limits so batch work can't consume everything the user-facing path needs. That's the same 'per tenant, not global' fairness reasoning applied to workload classes."

"The partition-count case is worth mentioning because it's the mirror image. For Event Hubs and Cosmos change feed triggers, the platform won't scale past the partition count — so you can also have the opposite problem: lag growing while the function refuses to scale, which looks like a platform fault and is a design constraint. That count is fixed at creation and increasing it later remaps keys."

"How I'd have caught it earlier: load test with a realistic backlog, not a trickle. This failure only appears when the scale controller actually scales, so a test that never triggers scaling proves nothing. And alert on database connection counts and rejections, not just on the function's own metrics — because the function looks healthy throughout; it's everything else that's failing."

"The principle I'd state: autoscaling is only safe if every downstream dependency can absorb the concurrency it produces. Otherwise you've built a very efficient way to overwhelm your own database — and it's the same reasoning as scaling out a web app onto a shared database, just with a much higher ceiling."

  • Do you note the function's own metrics look healthy?
