Multi-Tenant Scaling

Shared infrastructure means one customer's behaviour is everyone's problem. Most of these scenarios are about containing that.

🔴 Advanced ⭐ Senior-level
Quick revision
  • Noisy neighbour is the defining problem of shared infrastructure.
  • Per-tenant quotas, not a global limit. A global limit lets one tenant consume it all.
  • Tenant dimension on every metric, or you cannot diagnose anything.
  • Tenant size distribution is always skewed. Design for the largest, not the median.
  • A very large tenant is a hot partition. Same physics, same non-fix.
  • Isolation must be structural — enforced by the framework, not by remembering.
  • Know your cost per tenant, or a customer can be unprofitable invisibly.
  • Plan the escape hatch: moving one tenant to dedicated infrastructure.

Scenario: one tenant is degrading everyone 🔥 Must know

Where it bitesMechanism
DatabaseTheir queries consume DTUs/RUs, evict the buffer pool, hold locks
Connection poolTheir concurrency exhausts connections everyone shares
Thread poolTheir long requests occupy threads
QueueTheir 100,000 messages sit ahead of everyone else's
CacheTheir working set evicts everyone else's entries
Rate limitA global limit means they consume the whole allowance
A global rate limit doesn't protect anyone from a noisy neighbour

The instinct is to add a rate limit. A global one makes it worse: if the limit is 10,000 requests a minute and one tenant sends 9,500, everyone else shares the remaining 500 — and now they're being throttled because of someone else's behaviour.

So the limit has to be per tenant, keyed on the tenant id from the validated token, not from a header the caller controls. Then a tenant hitting their ceiling gets 429s and nobody else is affected. That turns a shared-fate problem into a contained one.

Two implementation details that matter. It must be distributed — Redis-backed — because a per-instance limiter multiplies as you scale out, so a 1,000-per-minute limit becomes 5,000 across five instances. And return Retry-After, so a well-behaved client backs off rather than retrying immediately and making it worse.

Beyond rate limiting, the same "per tenant, not global" logic applies to every shared resource: concurrency limits per tenant (a bulkhead), queue partitioning or separate queues so one tenant's backlog doesn't delay others, and cache quotas so one working set can't evict everyone.

The framing worth stating: fairness has to be designed in. Shared infrastructure defaults to first-come-first-served, which under load means whoever generates the most load wins.

You cannot diagnose this without a tenant dimension

The first question in any multi-tenant incident is "is this one customer or everyone?" — and the answer determines everything that follows.

If telemetry isn't enriched with tenant id, that question is unanswerable. You end up correlating support tickets against timestamps, which is slow and unreliable.

So: tenant id on every request, dependency, exception and log entry, added once by a telemetry initialiser rather than per log statement. Then requests by tenant, p95 by tenant and errors by tenant are queries rather than investigations.

For the database specifically, you want to attribute consumption too. Cosmos DB reports RU charge per request, so aggregating by tenant is straightforward. For SQL, Query Store plus a tenant identifier in the query context or application name gets you most of the way.

Do this before you need it. You cannot retrospectively split by a dimension you never recorded — which is precisely what you'll want during the first serious incident.

Senior signal — a very large tenant is a hot partition

If the partition key is tenant id, then all of that tenant's data and traffic is on one physical partition, bounded by that partition's throughput and storage limits. In Cosmos DB that's a hard ceiling, and in DynamoDB the same.

Which means it's the hot partition problem again — and so is the non-fix: adding throughput doesn't help, because their key still maps to one partition, which now gets a smaller share of a larger total.

The options, and they're the same shape as always:

Hierarchical partition keys in Cosmos — tenant, then a subkey — so a single tenant can span physical partitions while queries scoped to that tenant remain efficient. This is exactly what the feature is for.

A synthetic subkey for the same effect where hierarchical keys aren't available, at the cost of fanning reads across buckets.

Move them to dedicated infrastructure. Often the right answer, and worth stating without embarrassment: a customer a hundred times larger than the median has genuinely different requirements, and forcing the shared model to serve both extremes usually degrades it for everyone. They can also typically pay for it.

What matters most is knowing this before onboarding. "How much data will they have, and what's our current largest?" is a question the sales conversation should trigger, because the answer may be a quarter of engineering work rather than a configuration change.

Assumptions that only hold for small tenants

The pattern to watch for is code that works because the data is small, with nothing marking it as an assumption.

Loading a full collection into memory — "get all users for the tenant" — is fine at 50 and fatal at 500,000. Especially in a foreach that then queries per item.

OFFSET-based pagination degrades linearly with depth: page 10,000 means the database counts through everything before it. Keyset pagination is constant-cost and the fix is straightforward, but it changes the API contract, so it's better done early.

Synchronous export. A CSV generated in-request works until it takes longer than the request timeout — then it fails for exactly the customers who most want it. Large exports belong in a background job with a download link.

Unbounded queries with no maximum page size, which is fine until someone requests pageSize=100000.

The useful review question: "what happens if this tenant has a million rows?" Asking it routinely is cheaper than discovering the answer during onboarding — and a load test with a deliberately oversized synthetic tenant catches most of it mechanically.

Scenario: an isolation failure 🔥 Must know

CauseStructural defence
A query missing the tenant filterGlobal query filters + an architecture test
IgnoreQueryFilters() used somewhereAllow-list it; fail the build elsewhere
Raw SQL bypassing filtersReview, and keep raw SQL rare and reviewed
A cache key without the tenantA key-builder that always includes it
Tenant context with the wrong lifetimeScoped, never static or singleton-captured
An id from the request body, not the tokenResolve tenant from the validated token only
A background job with no tenant contextCarry tenant explicitly in the message
Isolation must be enforced by construction, not by discipline

Every place a developer could forget the tenant filter is a latent data breach. So the design goal is to reduce the number of places where forgetting is possible to as near zero as the framework allows.

EF Core global query filters are the main tool: applied at the model level, so every query for that entity carries the filter automatically. Correct by default, and forgetting requires actively calling IgnoreQueryFilters().

Two traps specific to that mechanism, both worth knowing:

The model is cached. If a filter captures the tenant id by value when the model is built, one tenant's id is baked into the cached model and used for everyone. The filter must read from a scoped service at query time — and this bug is severe, silent, and passes every single-tenant test.

Filters don't apply to raw SQL or to ExecuteUpdate/ExecuteDelete, so those need the filter written explicitly and deserve heightened review.

Beyond the ORM: resolve tenant only from the validated token, never from a header or body — a client-supplied tenant id is an authorisation bypass waiting to happen. Keep tenant context scoped, because a static or singleton-captured value leaks across requests intermittently and under load, which is the hardest version of this bug to find.

And test it: write as tenant A, read as tenant B, assert nothing comes back. Plus an architecture test asserting IgnoreQueryFilters appears nowhere outside an allow-list. Those two cover most of the realistic failures mechanically, which is the only enforcement that scales.

Scenario: a tenant is unprofitable ⭐ Senior-level

AttributeHow
Requests and computeRequest count and duration by tenant dimension
DatabaseRU charge per request (Cosmos); Query Store attribution (SQL)
StorageRow or document counts and blob usage per tenant
MessagingMessages published and consumed per tenant
EgressResponse bytes per tenant — often the surprise
SupportNot infrastructure, and frequently the largest cost
Cost per tenant is a product decision that needs engineering data

In a shared system, cost is a single bill and it hides everything. So a customer paying £200 a month can be costing £2,000 in RUs and egress, and nobody knows — because the bill only shows a total.

Attribution changes what the business can do: price by usage, introduce fair-use limits, decide whether an expensive customer is strategic or should be repriced. All of which need per-tenant numbers, and none of which engineering can decide alone.

The pragmatic approach is proportional attribution rather than exact accounting: allocate shared cost by each tenant's share of requests, RUs and storage. That's approximate and entirely adequate for spotting the outliers, which is what you actually want. Exact per-tenant cost accounting is a large project with diminishing returns.

Two things worth flagging as commonly missed: egress, which is easy to overlook and can dominate for a tenant downloading large exports, and the cost of a heavy tenant on everyone else's experience — which doesn't show up as cost at all, but as p95 latency for other customers. That's a real cost paid in churn rather than in cloud spend.

And the same data supports capacity planning: knowing cost per tenant means you can forecast what the next hundred customers will cost, rather than discovering it.

Scenario: moving one tenant to dedicated infrastructure 🔴 Advanced

1  PROVISION       new database/container, same schema, same code version

2  BACKFILL        copy their data. Read-only source ideally, or accept a
                   catch-up phase. Verify counts and checksums.

3  DUAL-WRITE      writes go to both. Reads still from the old.
     or CDC/change feed replicating old -> new continuously

4  VERIFY          compare. Not just counts - sample records field by field.
                   Let it run long enough to catch drift.

5  CUT OVER        brief write pause for that tenant only, final catch-up,
                   flip their routing. Other tenants unaffected throughout.

6  SOAK            keep the old data read-only for days. Rollback = flip back.

7  DECOMMISSION    only after the soak. Deleting early removes your rollback.
Senior signal — routing indirection is what makes this possible at all

The migration above only works if the application can already route a tenant to different infrastructure. If the connection string is a single configuration value, there is no migration path — you'd be changing everyone's.

So the enabling design is a tenant catalogue: a lookup from tenant id to its connection string, storage account and configuration, resolved per request. Once that exists, moving a tenant is a row change plus a data copy. Without it, it's a re-architecture.

That's worth building before you need it, and it's cheap to add early. It also gives you per-tenant configuration, staged rollouts by tenant, and the ability to place tenants in different regions for data residency — all valuable independently.

Two specifics on the migration itself. A brief write pause for one tenant is usually acceptable — a maintenance window for one customer is a very different conversation from downtime for everyone, which is the main advantage of per-tenant migration over a big-bang move.

And verify by sampling records, not just counting them. Matching row counts with mismatched field values is the failure that gets discovered weeks later, and by then the old data is gone. Keep the source read-only through a soak period so rollback stays available — the same overlap-don't-cut-over principle as credential rotation and schema change.

Key takeaways
  • Noisy neighbour is the defining problem; fairness must be designed in.
  • A global rate limit lets one tenant consume everyone's allowance.
  • Per-tenant limits, distributed, keyed on the token's tenant id, with Retry-After.
  • Apply "per tenant, not global" to concurrency, queues and cache too.
  • Tenant dimension on all telemetry, added before you need it.
  • Tenant size is always skewed — design for the largest, not the median.
  • A very large tenant is a hot partition; capacity doesn't fix it.
  • Hierarchical partition keys, a synthetic subkey, or dedicated infrastructure.
  • Watch for assumptions that only hold at small scale: in-memory loads, OFFSET, sync export.
  • Isolation enforced by construction — global filters, plus tests for bypasses.
  • The EF Core model cache will bake one tenant's id into the filter if captured by value.
  • Resolve tenant from the validated token only.
  • Attribute cost per tenant proportionally; don't forget egress.
  • A tenant catalogue is what makes per-tenant migration possible.
  • Verify by sampling fields, and soak before decommissioning.

Common mistakes

  • A global rate limit instead of per-tenant.
  • Per-instance rate limiting, so limits multiply on scale-out.
  • No tenant dimension in telemetry, making diagnosis impossible.
  • Designing for the median tenant and being surprised by the largest.
  • Adding throughput for a large tenant on a tenant-keyed partition.
  • Loading a tenant's full collection into memory.
  • OFFSET pagination that degrades for large tenants.
  • Synchronous exports that time out for the biggest customers.
  • Tenant id from a header or request body rather than the token.
  • Tenant context in a static or singleton, leaking across requests.
  • A query filter capturing tenant id by value, baked into the cached model.
  • A shared queue, so one tenant's backlog delays everyone.
  • No cost visibility per tenant.
  • No routing indirection, so no tenant can ever be moved.
  • Deleting source data immediately after a migration.

One tenant's usage is making the platform slow for everyone. What do you do? 🔥 Must know
How I'd answer

"I'd work in three phases: confirm it's actually one tenant, contain it, then fix the fairness problem structurally."

"First, confirm and quantify. I'd look at requests, p95 latency and RU or DTU consumption grouped by tenant. That immediately tells me whether it's one tenant, and which resource they're consuming — because the fix differs completely depending on whether it's database throughput, connections, queue depth or cache."

"That query is only possible if telemetry carries a tenant dimension. If it doesn't, that's my first finding, because otherwise I'm correlating support tickets against timestamps — and I'd want the enrichment added regardless of how this incident resolves."

"Then work out what they're doing, because the response depends on it. Legitimate growth is a capacity and pricing conversation. A misconfigured integration polling every second is a conversation with them. An expensive query pattern — an unbounded report, a missing filter — might be something we can optimise on their behalf."

"Containment, and this is where the important design point sits. Per-tenant rate limiting — not a global limit, because a global limit makes it worse: if the cap is 10,000 a minute and they use 9,500, everyone else shares 500 and is being throttled for someone else's behaviour."

"So limits keyed on the tenant id from the validated token, enforced in a distributed store rather than per instance — because a per-instance limiter multiplies as you scale out, so a 1,000-per-minute limit becomes 5,000 across five instances. And returning Retry-After, so a well-behaved client backs off instead of retrying immediately."

"Alongside that, a concurrency limit per tenant — a bulkhead — so they can only ever occupy a slice of the thread and connection pools rather than all of it. That contains the blast radius structurally rather than depending on a threshold being tuned correctly."

"If it's queue-based work, a shared queue means their 100,000 messages sit ahead of everyone else's, so other tenants wait behind them. The fix is per-tenant queues, or a scheduler that round-robins across tenants rather than processing strictly in order — fair scheduling rather than first-come-first-served."

"If it's the database, and they're genuinely large, the deeper problem may be that the partition key is tenant id — in which case all their traffic is on one physical partition and adding throughput doesn't help, because their key still maps to one place. That's the hot partition problem, and the answers are hierarchical partition keys, a synthetic subkey, or moving them out."

"Which brings up the escape hatch. If one tenant is a hundred times the median, forcing the shared model to serve both extremes usually degrades it for everyone. Moving them to dedicated infrastructure is often the right engineering answer, and they can typically pay for it — so it's a commercial option as well as a technical one."

"That's only possible if the application can route a tenant to different infrastructure — a tenant catalogue mapping tenant to connection string and configuration. If the connection string is a single config value, there's no migration path at all. Worth building early, and it's cheap then."

"On prevention, the framing I'd offer: shared infrastructure defaults to first-come-first-served, which under load means whoever generates the most load wins. Fairness has to be designed in — per-tenant quotas, per-tenant concurrency, fair queue scheduling — and alerting per tenant so a change in one customer's behaviour is visible before it's everyone's problem."

What they're really checking
  • Do you confirm with per-tenant data before acting?
  • Do you know a global rate limit makes it worse?
  • Do you know per-instance limits multiply?
  • Do you apply fairness to queues and concurrency, not just requests?
  • Do you recognise a large tenant as a hot partition?
  • Do you raise dedicated infrastructure and the routing prerequisite?
Weak answers
  • Red flag: "add a rate limit" with no per-tenant keying.
  • Red flag: scaling up as the whole answer.
  • Red flag: no way to identify which tenant.
Likely follow-ups
  • How would you implement a distributed per-tenant limit?
  • How do you schedule a queue fairly across tenants?
  • How would you move that tenant out with no downtime for others?
Sales has signed a customer with 200× your largest tenant's data. What do you check? ⭐ Senior-level
How I'd answer

"I'd treat this as a project rather than an onboarding, and the first thing I'd do is build a synthetic tenant at that scale in a test environment and run the real workload against it. Reasoning about which things break is much less reliable than measuring."

"The hard limits first, because those aren't optimisations — they're blockers."

"If the partition key is tenant id, they may exceed a single physical partition. In Cosmos DB that's a hard storage and throughput ceiling per partition, and adding RUs doesn't help because their key still maps to one partition. That's the first thing I'd check, because if it's a problem the answer is either hierarchical partition keys or dedicated infrastructure, and both are significant work."

"Then the assumptions that only hold at small scale. These are the ones that pass every test and fail on the day."

"Anything loading a full collection into memory. 'Get all users for the tenant' is fine at 50 and fatal at 500,000 — especially inside a loop that then queries per item."

"OFFSET-based pagination, which degrades linearly with depth: page 10,000 means counting through everything before it. Keyset pagination is constant-cost, and it changes the API contract, so it's better done before onboarding than after."

"Synchronous exports and reports. A CSV generated in-request works until it exceeds the request timeout — and then it fails for exactly the customer who most wants it. Those need to become background jobs with a download link."

"Queries that scan. A missing index that costs 20ms on 50,000 rows costs seconds on ten million. The query didn't change; the data did. So I'd review the plans for their access patterns specifically, at their volume."

"Batch jobs and their windows. A nightly job that takes twenty minutes today may not fit in the window with 200× the data, and it may hold locks long enough to affect other tenants."

"Cache behaviour. Their working set may evict every other tenant's entries, so everyone else's hit rate collapses. That's a noisy-neighbour effect that shows up as other customers getting slower, which is easy to misattribute."

"The onboarding itself is its own risk. Importing their initial data is a bulk load that can saturate the database and degrade everyone — so it needs to be throttled, batched, run off-peak, and ideally against a replica or a staged path rather than the live transactional load."

"Then the honest conversation. My recommendation might well be dedicated infrastructure for them — their own database, possibly their own deployment. Not as a failure of the shared design, but because a customer 200× the median has genuinely different requirements, and forcing one model to serve both extremes usually degrades it for the other 500 customers."

"That needs a tenant catalogue — routing tenant to connection string and configuration per request. If we don't have that, adding it is a prerequisite and I'd say so, because without it there's no way to place a tenant anywhere different."

"And I'd give the business real numbers rather than a yes or no: what it costs to serve them on shared infrastructure, what it costs dedicated, what engineering work each path needs and how long. Then the commercial decision is informed — including the option of pricing it appropriately, which is often the answer for a customer of that size."

"The thing I'd want to avoid is the failure mode where nobody asks until go-live. 'How much data will they have, and what's our current largest?' should be a standard question during the sales process, because the answer is sometimes a quarter of engineering work rather than a configuration change."
