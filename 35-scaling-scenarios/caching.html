Caching Failures

A cache turns a load problem into a correctness problem and an availability problem. Worth it, and only if you know which failures you've bought.

🔴 Advanced ⭐ Senior-level
Quick revision
  • Stampede: everything expires at once and the database gets every miss.
  • Jitter every TTL. Identical TTLs synchronise expiry.
  • A cache must be optional. If Redis down means app down, it's a dependency.
  • Hot key: one key saturates one shard. Adding nodes doesn't help.
  • Cache the absence too, or missing keys hit the database every time.
  • Invalidate on write, don't just wait for the TTL.
  • Tenant id in every key, or you'll serve one customer another's data.
  • Delete rather than update — two writers updating a cache can leave it wrong forever.

Senior signal — jitter is free and it prevents the common case

Everything else on that list involves real complexity. Jitter is one line and it removes the synchronisation that makes a stampede possible in the first place.

The reason it works: a stampede isn't really about cache misses, it's about simultaneous cache misses. Spread the same number of misses over sixty seconds instead of one, and the database handles them comfortably.

Where jitter isn't enough is a single very hot key — a homepage, a configuration blob, a pricing table. There, one expiry means a thousand simultaneous misses regardless of jitter, because it's one key. That's the case for single-flight: the first caller acquires a short lock and repopulates, the others either wait briefly or serve the stale value.

Serving stale while refreshing in the background is usually the best user-facing behaviour, and it's worth naming as a deliberate choice: you're trading a few seconds of staleness for never having a user-visible miss. For most cached data that's obviously the right trade, and stating it that way shows you know it's a trade.

The deployment case is worth calling out separately, because it's the most common trigger: every instance starts cold at the same moment. A rolling deployment helps by spreading it; cache warming plus a readiness gate helps more, because the instance doesn't take traffic until it's useful.

Scenario: Redis goes down and so does the app 🔥 Must know

public async Task<Product?> GetAsync(int id, CancellationToken ct)
{
    var key = $"product:{_tenant.Id}:{id}";      // tenant in the key - always

    // A cache failure must NEVER fail the request.
    try
    {
        var cached = await _cache.GetStringAsync(key, ct);
        if (cached is not null)
            return cached == NullMarker ? null : Deserialize(cached);
    }
    catch (RedisException ex)
    {
        _log.CacheReadFailed(key, ex);           // log it, then carry on
    }

    var product = await _repository.GetAsync(id, ct);

    try
    {
        // Cache the ABSENCE too, briefly - see cache penetration below
        var value = product is null ? NullMarker : Serialize(product);
        var ttl = product is null
            ? TimeSpan.FromSeconds(30)
            : Jitter(TimeSpan.FromMinutes(10));  // +/- 15%, so expiry spreads

        await _cache.SetStringAsync(key, value,
            new DistributedCacheEntryOptions { AbsoluteExpirationRelativeToNow = ttl }, ct);
    }
    catch (RedisException ex)
    {
        _log.CacheWriteFailed(key, ex);          // still not fatal
    }

    return product;
}

private static TimeSpan Jitter(TimeSpan baseTtl) =>
    baseTtl * (0.85 + Random.Shared.NextDouble() * 0.30);
If a cache outage is an app outage, it isn't a cache

A cache is an optimisation. Losing it should make the system slower, not broken. If an unhandled RedisException propagates into a 500, you've added a hard dependency and reduced your availability — the composite is now less reliable than the database alone.

So every cache access is wrapped, failures are logged and swallowed, and the request falls through to the source. That's the baseline.

But there's a second-order problem that catches people, and it's the more interesting half: can the source survive 100% of the traffic?

If the cache was absorbing 90% of reads, losing it means the database suddenly takes ten times its normal load — and falls over. So the app degrades gracefully into a database outage, which is a total outage anyway.

Which means graceful degradation needs more than a try/catch:

  • A short in-process fallback cache — IMemoryCache with a 30-second TTL. Not shared, and it absorbs the repeated reads that would otherwise all reach the database.
  • Load shedding when the cache is unavailable: serve fewer requests properly rather than all of them badly.
  • Circuit-break the cache itself, so you stop paying a connection timeout on every request once it's clearly down.
  • Know the numbers. If you can't say what the database does at 10× read load, you don't know whether your degradation works — and a game day is how you find out.

That last point is what separates the textbook answer from the operational one: "the cache is optional" is only true if the source can take the load.

Scenario: one Redis node is saturated 🔴 Advanced

Two Redis facts that explain most of its incidents

Command execution is single-threaded per node. So one expensive command blocks every other client on that node for its duration. A KEYS * on a large keyspace, a SMEMBERS on a million-member set, or fetching a 50 MB value stops everything.

That's why "Redis got slow and we don't know why" is usually one bad command rather than capacity, and why SLOWLOG is the first thing to look at. Use SCAN rather than KEYS, always, and keep values small.

A hot key lives on exactly one shard. So adding nodes to a cluster doesn't help — the key still hashes to one place. Same physics as every other hot-partition problem in this handbook.

The fixes are specific to caching though, and rather nice: put a short-lived in-process cache in front of the hot key, so most reads never reach Redis at all. A two-second IMemoryCache entry on a key read a thousand times a second removes 99.8% of the traffic, and two seconds of staleness is almost always acceptable for something that hot.

Or replicate the key under several suffixes and have clients pick one at random, which spreads it across shards at the cost of N writes on invalidation.

The in-process option is usually the right answer, and it's a good illustration of a general principle: a two-tier cache handles hot keys that a single tier can't.

Scenario: users see stale data 🔥 Must know

StrategyStalenessRisk
TTL onlyUp to the TTLSimple and predictable. Often enough
Delete on writeNear zeroThe recommended active approach

Write-throughZeroCache is on the write path, so its failures matter
Event-driven invalidationNear zero, across servicesNeeds reliable eventing
Senior signal — delete, don't update

This looks like a minor preference and it's a correctness argument.

Updating the cache after a write has an interleaving that leaves it wrong forever. Two writers: A writes value 1 to the database, B writes value 2 to the database, B updates the cache to 2, A updates the cache to 1. The database says 2; the cache says 1, and nothing will ever correct it until the TTL expires. If the TTL is long or absent, that's a permanent inconsistency.

Deleting has no such interleaving. The worst outcome is a redundant delete, and the next read repopulates from the source — which is authoritative. So the failure mode is a wasted database read rather than wrong data.

The general rule: invalidate rather than synchronise. Keeping two copies in agreement is genuinely hard; throwing one away is trivial. Same reasoning as preferring a rebuild over a patch.

Two related details worth having. Delete after the database commit, not before, or a concurrent read can repopulate the cache with the old value in the window between. And a short TTL as a backstop regardless of active invalidation, because an invalidation will be missed eventually — a code path someone forgot, a failed event — and a TTL bounds how long that costs you.

Also: decide what staleness is acceptable per data type. A product description tolerating five minutes is a completely different problem from a stock level or a permission check, and treating them the same is how you end up either over-engineering or overselling inventory.

Cache penetration is also an attack

If a key that doesn't exist isn't cached, then every request for a missing id reaches the database. Normal traffic makes this a minor inefficiency.

Deliberate traffic makes it a denial of service: requesting /api/products/999999991, ...992, ...993 generates a database query per request with no cache protection at all. The cache is completely bypassed by construction.

The fix is to cache the absence — a null marker with a short TTL, thirty seconds or so. Short, because the entity may be created shortly and you don't want to serve "not found" for ten minutes after it exists.

For very large keyspaces a Bloom filter is the scalable version: it answers "definitely not present" cheaply without storing an entry per missing key, at the cost of occasional false positives that fall through to the database.

And the diagnostic habit worth having: measure the hit rate. A cache with a 20% hit rate is adding latency, memory cost and a failure mode for very little benefit — and nobody notices, because it's "working". Hit rate per key prefix tells you which caches are earning their place.

A cache key must include everything the value depends on

That's the whole rule, and it's the one that causes security incidents rather than performance problems.

If the value differs by tenant, user, role, locale or API version, every one of those must be in the key. Omit the tenant and you will eventually serve one customer another customer's data — which is a reportable breach, not a bug.

It's an easy mistake because it works perfectly in development, where there's one tenant. And it's easy to introduce later: a method gains a filter that varies by role, and the cache key isn't updated to match.

Structural defences, since review won't catch this reliably:

  • A key-building helper that always includes tenant and user from the ambient context, so constructing a key without them requires deliberately bypassing it.
  • Separate Redis databases or key prefixes per environment, so a misconfiguration can't cross environments.
  • A test that populates the cache as tenant A and reads as tenant B, asserting isolation. That's a five-line test for a whole class of breach.
  • Never cache authorisation decisions for long, and prefer caching the inputs — roles, permissions — over the decision, so revocation takes effect on the next evaluation.

And be very careful with CDN or response caching of anything authenticated. A Cache-Control: public on a personalised response means a shared cache may serve one user's data to another — the same bug, at a layer where the blast radius is much larger and the cache isn't yours to purge.

Key takeaways
  • A stampede is about simultaneous misses — jitter every TTL, always.
  • Single-flight or serve-stale for a single very hot key.
  • Deployments create stampedes because every instance starts cold.
  • A cache failure must never fail the request.
  • "The cache is optional" is only true if the source survives 100% of the load.
  • An in-process fallback cache absorbs a Redis outage.
  • Redis is single-threaded per node — one slow command blocks everyone.
  • Never KEYS; check SLOWLOG first.
  • A hot key lives on one shard; put a local cache in front of it.
  • Delete on write, don't update — concurrent updates can leave it permanently wrong.
  • Delete after the commit, and keep a short TTL as a backstop.
  • Cache the absence, briefly, or missing keys bypass the cache entirely.
  • Measure hit rate — a 20% hit rate is cost without benefit.
  • The key must contain everything the value depends on, especially tenant.
  • Test cross-tenant isolation; never Cache-Control: public on personalised responses.

Common mistakes

  • Identical TTLs, so everything expires together.
  • An unhandled cache exception failing the request.
  • Assuming the database can absorb a cache outage without checking.
  • Updating the cache on write rather than deleting.
  • Invalidating before the commit, so a read repopulates stale data.
  • No TTL at all when relying on active invalidation.
  • Not caching misses, leaving the database exposed to unknown ids.
  • Never measuring hit rate.
  • KEYS in production.
  • Adding Redis nodes for a hot key.
  • Tenant id missing from the cache key.
  • Caching authorisation decisions so revocation doesn't take effect.
  • A shared cache across environments.

Every ten minutes the database spikes and requests time out. Diagnose it. 🔥 Must know
How I'd answer

"A regular ten-minute period is a very strong signal — that's almost certainly a cache TTL, and I'd expect to find a ten-minute expiry in the code. It's a cache stampede."

"The mechanism: all the entries were populated at roughly the same moment — usually at a deployment, when every instance starts cold — and they were given identical TTLs. So they all expire in the same second. Every concurrent request misses simultaneously, and a thousand identical queries hit the database at once."

"Then it becomes self-sustaining: the database saturates, queries slow, requests time out before they can repopulate the cache, so the next wave misses too. And the ten-minute rhythm persists because each repopulation resets the clock in unison."

"The point I'd make is that the cache made this worse than having no cache. Without it the database would see steady load; with it, the load arrives as synchronised walls."

"I'd confirm by correlating database load with cache miss rate — misses spiking at the same instant as the database spike is conclusive. Redis INFO gives hits and misses, and any reasonable cache wrapper should be emitting a hit-rate metric."

"Fixes, and the first one is nearly free."

"TTL jitter — randomise each entry's TTL by ±15%. That's one line, and it's the whole fix for the common case, because a stampede isn't about misses, it's about simultaneous misses. Spread the same number of misses across ninety seconds and the database won't notice."

"If it's a single very hot key — a pricing table, a configuration blob — jitter doesn't help, because it's one key expiring once. There I'd use single-flight: the first caller takes a short distributed lock and repopulates while the others wait briefly or serve the stale value."

"Serve stale while refreshing is usually the best user-facing behaviour: return the expired value immediately and refresh in the background, so no user ever waits for a miss. I'd state that as a deliberate trade — a few seconds of staleness for eliminating user-visible misses — which for most cached data is obviously worth it."

"Cache warming on startup for the deployment case, gated behind the readiness probe so an instance doesn't take traffic until it's useful. Combined with a rolling deployment, that stops all instances going cold in the same second."

"Two things I'd check while I'm there, because they're adjacent and commonly wrong."

"Is a cache failure fatal? If an unhandled RedisException becomes a 500, we've made the cache a hard dependency and reduced availability below the database alone. Every access should be wrapped and fall through to the source."

"Can the database survive losing the cache entirely? If the cache absorbs 90% of reads, then losing it means 10× database load — so 'the cache is optional' is only true if the source can take the traffic. That's worth knowing before it happens, and a short in-process fallback cache plus load shedding is what makes the degradation real rather than theoretical."

"On prevention: alert on cache miss rate, not just database load, because the miss spike precedes the symptom. And I'd treat 'identical TTL' as something to catch in review, since jitter costs nothing and the failure mode is severe."

What they're really checking
  • Do you recognise a periodic spike as a TTL?
  • Can you explain why it's self-sustaining?
  • Do you reach for jitter first?
  • Do you know jitter doesn't help a single hot key?
  • Do you check whether a cache failure is fatal?
  • Do you ask whether the database survives a cache outage?
Weak answers
  • Red flag: scaling the database.
  • Red flag: increasing the TTL as the only fix.
  • Red flag: not connecting the period to a cache expiry.
Likely follow-ups
  • How would you implement single-flight across instances?
  • What happens when Redis fails entirely?
  • How do you warm the cache safely on startup?
A customer reports seeing another customer's data. Where do you look? ⭐ Senior-level
How I'd answer

"I'd treat this as a potential data breach from the first minute, not a bug — because that changes what I do first and there may be notification obligations with a clock on them."

"Immediate actions. Preserve evidence: the exact request, timestamp, user, and the response they saw. Then assess blast radius — is it one customer, or systemic? And notify whoever owns incident response, because the disclosure decision is not mine to make alone and it has legal deadlines."

"If I can identify the affected path and it's a shared cache, flushing the relevant cache keys is a fast containment step — it stops further wrong responses while I investigate."

"Then the candidates, and I'd start with caching because it's the most common cause of exactly this symptom."

"A cache key missing the tenant id. The classic. product:42 instead of product:tenant7:42 — so whichever tenant populates it first serves everyone. It passes every test in development because there's one tenant, and it's easy to introduce later when a method gains a filter and the key isn't updated."

"A key missing user or role, where the response varies by permission — so a cached admin view is served to a standard user. Same bug, and it's an authorisation bypass rather than just a leak."

"Response or CDN caching of an authenticated response. If Cache-Control: public is set on a personalised response, a shared cache serves one user's page to another. Worse than the Redis case, because the cache isn't ours to purge and the blast radius is much larger."

"Then the non-cache causes."

"A missing tenant filter in a query. If EF Core global query filters are in use, someone may have called IgnoreQueryFilters(), or written raw SQL that bypasses them, or added a repository method that doesn't apply the filter. This is the one that global filters exist to prevent, which is exactly why bypassing them needs to be hard."

"Tenant context resolved incorrectly. If tenant id is held in something with the wrong lifetime — a static, a singleton, or an AsyncLocal that leaks across an async boundary — then one request can see another's context. That's a genuinely nasty one because it's intermittent and load-dependent, and it presents exactly like a caching bug."

"A scoped service captured by a singleton, which is the DI version of the same problem."

"How I'd narrow it. Is it reproducible or intermittent? Reproducible points at a key or a query; intermittent and load-dependent points at context or lifetime. Does it affect one endpoint or several? One endpoint suggests a specific cache key or repository method; several suggests tenant resolution, which is much more serious."

"And I'd check the telemetry for whether the tenant dimension on the request matches the data returned — which is only possible if telemetry was enriched with tenant id, and is the strongest argument for having done that."

"The fix has to be structural, because this class of bug is invisible in review and catastrophic in production:"

"A key-building helper that always takes tenant and user from the ambient context, so producing a key without them requires deliberately going around it. Then correctness is the default rather than something each developer remembers."

"A test that writes as tenant A and reads as tenant B, asserting isolation. Five lines, and it covers a whole class of breach. I'd want one per cached read path."

"An architecture test asserting no repository method returns an entity type without the tenant filter, and that IgnoreQueryFilters appears nowhere outside a small allow-list."

"Never Cache-Control: public on an authenticated response, enforced by a middleware that sets private-no-store by default for authenticated requests."

"The framing I'd land on: tenant isolation must be enforced by construction, not by discipline. Every mechanism where a developer can forget the tenant is a latent breach, and the number of places you have to remember should be as close to zero as the design allows."

What they're really checking
  • Do you treat it as a breach with notification implications?
  • Do you preserve evidence and contain before diagnosing?
  • Do you check cache keys first, including CDN caching?
  • Do you know tenant-context lifetime bugs present identically?
  • Do you use reproducible-versus-intermittent to narrow it?
  • Is your fix structural rather than a code correction?
Weak answers
  • Red flag: fixing the one key and closing the ticket.
  • Red flag: no consideration of disclosure.
  • Red flag: only looking at the query, not the cache.
Likely follow-ups
  • How would you prove no other tenant was affected?
  • How does an AsyncLocal leak across requests?
  • What would you enforce in CI?
