API & Service Scaling

Five scenarios. In four of them the instinctive fix is wrong, and the reason is always that something finite is being contended.

Scaling out is where most people start, and it often makes it worse

If the constraint is the database — and it usually is — then more application instances means more connections competing for the same finite server capacity.

Concretely: each instance has its own connection pool, default 100 for SQL Server. Three instances is up to 300 connections; ten instances is 1,000 — against a database that has a hard limit and will start rejecting or queueing. So you've converted "the app is slow" into "the app can't connect", which is worse and looks unrelated.

The same applies to any shared downstream: a third-party API with a rate limit, a Redis instance, a Service Bus namespace. Scaling the tier that isn't the bottleneck just applies more pressure to the one that is.

And scaling out only works at all if the app is stateless. In-memory session, an in-memory cache, a rate limiter counting locally, and — the damaging one — a background timer that now runs on every instance, so a nightly job fires ten times.

So the honest sequence is: find what saturated first, and scale that. Which is often the database, and the fix there is usually queries and indexes rather than a bigger tier.

The controls that actually hold under 10×

Beyond capacity, four things change the shape of the problem rather than the size of the machine.

Caching. If 80% of requests read the same data, caching removes 80% of the database load — which is a far bigger lever than any tier increase. Check the read/write ratio first, because that's what decides whether it's worth it.

Rate limiting per caller. Distributed, not per-instance, or it multiplies as you scale. This also protects you from the case where the 10× is one bad client.

Queue-based load levelling. If the work doesn't need a synchronous answer, accept the request, return 202 with a status URL, and process from a queue. Then a traffic spike grows a queue rather than timing out — the system degrades in latency instead of failing. That's the single most effective structural change for spiky load.

Load shedding. Above a threshold, reject fast with 429 and Retry-After. Sounds worse than queueing and isn't: a request that times out after 30 seconds consumed resources and helped nobody. Fast rejection keeps the system alive for the requests it can serve, and tells the client something useful.

Senior signal — thread pool starvation is the .NET scaling bug

It's the most common cause of "the app is slow under load but CPU is low" in .NET, and the mechanism is worth being able to explain rather than just recognising the fix.

A blocking call on a thread pool thread holds that thread for the whole duration of the I/O. The pool starts with roughly one thread per core and injects additional threads slowly — around one or two per second — because the heuristic assumes threads are busy computing, not blocked.

So under a burst, requests arrive faster than threads become available. They queue. Latency climbs steeply with concurrency, and CPU stays low because nothing is computing — everything is waiting.

It typically presents as a database problem, because the visible symptom is slow queries. The queries are fine; the requests are queueing before they reach the database.

Two things make it worse. It's self-reinforcing: slower responses mean more concurrent in-flight requests, which means more blocked threads. And one .Result deep in a call chain is enough — a fully async controller calling a synchronous helper still blocks.

Immediate mitigation is ThreadPool.SetMinThreads to raise the floor, which buys time and does not fix it. The fix is async all the way down. Finding the offenders: analyzer rules for sync-over-async, or dotnet-stack in production showing dozens of threads parked on the same .GetAwaiter().GetResult() frame.

Connection pool exhaustion looks identical and isn't

Also latency-with-low-CPU, and the distinguishing detail is where the wait happens: requests wait before any query executes, and the error mentions the pool — "Timeout expired. The timeout period elapsed prior to obtaining a connection from the pool."

Common causes, in order:

Connections not disposed. A missing using, or a DbContext resolved as a singleton so it never releases. The pool drains and never recovers.

Connections held too long. A long transaction, or a connection opened before an HTTP call and still held during it. The pool size is adequate; the holding time isn't.

Genuinely too small for the concurrency. The legitimate case, and the one people assume first.

The trap: raising the pool size scales the problem rather than fixing it. The database has its own connection limit, and pools are per-instance — so three instances at 200 each is 600 connections against a server that may cap lower. You move the failure from the app to the database, where it's harder to diagnose.

So diagnose holding time before increasing size. The right pool size is a function of concurrency and how long each connection is held; halving the holding time is equivalent to doubling the pool, and it doesn't cost the database anything.

The .NET leak suspects, in order

An unbounded cache or a static dictionary that only ever grows. The most common by a distance, and often intentional code that nobody bounded — IMemoryCache with no SizeLimit, or a ConcurrentDictionary used as a cache with no eviction.

Event handlers never unsubscribed. A subscription roots the subscriber, so a long-lived publisher keeps every short-lived subscriber alive.

Captured context in a long-lived delegate. A lambda registered once capturing a scoped service keeps that whole object graph — including a DbContext and its change tracker — alive forever.

HttpClient created per request, which leaks sockets in TIME_WAIT rather than managed memory — so it presents as connection failures rather than memory growth. IHttpClientFactory fixes both that and the opposite problem, a singleton client caching DNS forever.

A DI lifetime mistake: a scoped service captured by a singleton, so one request's object graph never releases.

To find it: dotnet-gcdump twice, several minutes apart, and compare. What grew between the snapshots is the answer, and the retention path shows what's rooting it. Much faster than reasoning about the code.

And remember the container interaction: .NET sizes the GC heap from the memory limit, so a tight limit makes the GC work harder — high CPU and pause time — and may still get OOM-killed. Raising the limit can reduce CPU, which is genuinely counterintuitive.

Two CPU causes worth knowing specifically

GC pressure. High CPU with high allocation rate usually means excessive allocation, not expensive computation. Typical sources: string concatenation in a loop, LINQ over large collections creating intermediate arrays, boxing, and materialising an entire query result to filter it in memory. The fix is to allocate less — Span<T>, pooling, and pushing filtering into the database — rather than tuning the GC.

Regex backtracking. A catastrophically backtracking pattern can take exponential time on a crafted input, so one request saturates a core indefinitely. If the pattern is applied to user input, that's a denial-of-service vector, not just a performance issue.

The mitigations: always set a matchTimeout, use RegexOptions.NonBacktracking where the pattern allows it, and prefer the source-generated [GeneratedRegex] attribute. If a single endpoint pins one core while others are fine, this is high on the list — and it's easy to confirm from a stack sample.

Key takeaways
  • Find what saturated first, and scale that — usually not the app tier.
  • Scaling out multiplies connection demand on a shared database.
  • Scaling out requires a stateless app, or timers and caches break.
  • Caching, per-caller rate limits, queue-based levelling and load shedding change the shape.
  • Fast rejection beats a request that times out after consuming resources.
  • Latency with low CPU: thread pool, connection pool, CPU throttling, or a slow dependency.
  • Sync-over-async holds a pool thread and the pool grows slowly — hence queueing.
  • One .Result deep in the chain is enough to cause it.
  • Connection pool waits happen before any query runs; fix holding time before pool size.
  • Memory rising and never recovering after GC is a leak; compare two gcdumps.
  • Unbounded caches are the leading .NET leak.
  • IHttpClientFactory for both socket exhaustion and DNS caching.
  • High CPU is often allocation, not computation.
  • Regex backtracking on user input is a DoS vector — always set a timeout.

Common mistakes

  • Scaling out when the database is the bottleneck.
  • Raising the connection pool size without checking holding time.
  • Scaling out a stateful app, multiplying timers and breaking sessions.
  • Blocking on async anywhere in the request path.
  • Reading CPU percent instead of throttled seconds in a container.
  • Raising the memory limit for what is actually a leak.
  • An unbounded IMemoryCache with no size limit or expiry.
  • new HttpClient() per request, exhausting sockets.
  • Regex on user input with no timeout.
  • Filtering in memory after fetching everything.
  • Queueing indefinitely under overload rather than shedding load.
  • Per-instance rate limiting, so the limit multiplies with scale.

"If I have warning, the first thing I'd do is find the actual bottleneck rather than guess it — because 'add more instances' is the instinctive answer and it's frequently wrong."

"Load test to find what breaks first. That's the whole exercise: push until something saturates, and the thing that saturates first is what you scale. Everything else is speculation."

"Then the structural changes, which help more than capacity."

Latency is 5 seconds, CPU is 20%, the database says queries take 10ms. Explain it. ⭐ Senior-level
How I'd answer

"Those three facts together are very informative. The database is fast and the CPU is idle, so the time is being spent waiting, and it isn't waiting on the database doing work. Almost certainly requests are queueing before they reach it."

"My first hypothesis is thread pool starvation from sync-over-async, because it produces exactly this signature."

"The mechanism: a blocking call — .Result, .Wait(), .GetAwaiter().GetResult() — holds a thread pool thread for the entire duration of the I/O. The pool starts around one thread per core and injects more at roughly one or two per second, because the heuristic assumes threads are computing rather than blocked."

"So under load, requests arrive faster than threads free up and they queue. The 10ms query is genuinely 10ms; the request spent 4.99 seconds waiting for a thread to run it on. And CPU is low because nothing is computing — everything is waiting."

"I'd confirm with dotnet-counters: thread pool queue length rising and thread count climbing slowly. And dotnet-stack to see the stacks — if dozens of threads are parked on the same .GetAwaiter().GetResult() frame, that's conclusive. Both work in a container via kubectl debug."

"The second candidate with the same signature is connection pool exhaustion, and the distinguishing detail is where the wait happens: requests wait before any query executes, and the error mentions the pool — 'timeout period elapsed prior to obtaining a connection'. That fits 'the database says queries are 10ms' too, because the database only sees the queries that got a connection."

"Causes there: connections not disposed, a DbContext registered as a singleton, connections held across an HTTP call, or a pool genuinely too small. I'd check pool wait time to distinguish."

"Third, if this is in a container, CPU throttling. A CPU limit is enforced per 100ms period, so a container that consumes its quota is paused for the remainder. Average CPU looks low precisely because it's paused rather than idle — which is why 20% is not the reassurance it appears to be. I'd check container_cpu_cfs_throttled_seconds_total, not CPU percent."

"Fourth, lock contention — a lock or semaphore serialising requests through a critical section. Also low CPU, also scales with concurrency, and dotnet-stack distinguishes it because the blocked threads share a different frame."

"The question that separates these fastest: does latency scale with concurrency? If yes, it's queueing — one of the four above. If a single request in isolation is also slow, then it's a genuinely slow path and I'd be looking at something else entirely, like a dependency the telemetry isn't capturing."

"On mitigation: ThreadPool.SetMinThreads raises the floor and buys time, and I'd be explicit that it's a workaround — it hides the problem at moderate load and the same wall reappears higher up. The fix is async all the way down, and I'd note that one .Result deep in the call chain is enough, so a fully async controller can still starve. Analyzer rules catch these at build time, which is the structural version of the fix."

What they're really checking
  • Do you conclude the time is spent queueing, not working?
  • Can you explain the thread pool injection mechanism?
  • Do you distinguish pool exhaustion from thread starvation?
  • Do you know CPU percent hides throttling?
  • Do you name the tools that confirm it?
  • Do you treat SetMinThreads as a workaround?
Weak answers
  • Red flag: "add more instances."
  • Red flag: concluding it's fine because CPU is low.
  • Red flag: SetMinThreads presented as the fix.
Likely follow-ups
  • How do you prove it's thread starvation and not the pool?
  • What if it's a third-party library blocking internally?
  • How would you prevent this reaching production again?
