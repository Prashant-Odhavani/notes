Docker & Kubernetes

A container is a process with a restricted view of the machine. Everything else follows from that, including why orchestration exists.

🟢 Beginner 🟡 Intermediate 🔥 Must know

What a container actually is 🔥 Must know

In one sentence

A container is an ordinary process on the host, started with a restricted view of the filesystem, network and process list, and a cap on how much CPU and memory it can use.

There is no guest operating system. ps on the host shows your container's process directly.

Think of it this way

A virtual machine is a separate flat in a building — its own walls, plumbing and heating. It boots an entire operating system.

A container is a room in a shared flat with a lock on the door. It has its own space and can't see what's in the other rooms, but the plumbing and heating are shared.

That's why a container starts in milliseconds and a VM takes a minute: there's nothing to boot. And it's why containers on one host must share the same kernel.

The mechanisms, in case you're asked

Containers are built from ordinary Linux kernel features rather than anything exotic.

Namespaces restrict what a process can see — its own process list, network interfaces, mount points, hostname and users. That's the isolation.

cgroups restrict what it can use — CPU shares, memory limit, I/O bandwidth. That's the resource control, and it's the mechanism behind Kubernetes requests and limits.

A union filesystem stacks read-only image layers with one writable layer on top. That's why ten containers from one image cost roughly one image's worth of disk.

Being able to name those three is usually enough. The reason it's worth knowing rather than memorising is that it explains the consequences: shared kernel means weaker isolation than a VM, which is why you don't rely on container boundaries alone for hostile multi-tenancy, and why a kernel vulnerability affects every container on the host.

Senior signal — the real win is the immutable artefact

"Consistent environments" is the usual answer and it undersells it. .NET already had reasonable environment consistency compared with, say, Python.

The more valuable property is that the image is a single immutable, content-addressed artefact. The bytes tested in staging are the exact bytes running in production — not a rebuild from the same commit, the identical image.

That collapses a whole class of question. "Was this built with the right configuration?" "Did the deploy pick up the new dependency?" "Is production running what we tested?" All answerable by digest.

It's also what makes rollback trivial and reliable: deploy the previous tag. No rebuild, no restore, no pipeline run — and no risk that rebuilding produces something subtly different because a transitive dependency moved.

Two things it does not solve, worth saying so you don't oversell it: configuration and data still live outside the image — that's the point — and containers do nothing about a bad architecture. A monolith in a container is a containerised monolith.

Why orchestration exists 🟡 Intermediate

The gap Docker leaves

Docker runs a container on one machine. That's the whole scope.

Production needs more: many machines, restart on crash, replace a failed host, roll out a new version without downtime, route traffic to healthy instances, scale on load, and give services a stable way to find each other.

That list is what Kubernetes is. It's a control loop that continuously moves actual state toward declared state.

Declarative, and why that's the whole idea

You don't tell Kubernetes to start three pods. You declare that three should exist, and a controller works continuously to make that true.

Kill a pod and another appears. Lose a node and its pods are rescheduled elsewhere. Change the image tag and the deployment rolls pods over gradually, checking readiness as it goes.

That reconciliation loop is the mental model to carry. It explains behaviour that otherwise looks strange — like a pod you deleted coming straight back, or a rollout stalling because a new pod never became ready and the controller correctly refuses to continue.

It also means debugging is usually about the gap between declared and actual: kubectl describe tells you what the controller is trying to do and why it can't.

Worth separating these, because they're often bundled and they don't carry equal weight for a .NET developer.

Docker is table stakes. Writing a sensible multi-stage Dockerfile, understanding layer caching, and running dependencies locally with Compose are ordinary day-to-day skills. Not knowing them is a real gap.

Kubernetes is a platform commitment, and plenty of well-run .NET systems never touch it — because App Service or Container Apps covers the requirement with a fraction of the operational surface.

So in an interview, the answer that lands is knowing the concepts well enough to reason about them, plus being able to say when Kubernetes is not the right choice. Reaching for a cluster for three services is a judgement error, and recognising that reads as more senior than reciting primitives.

What you should be solid on regardless: images and layers, requests and limits, readiness versus liveness, and graceful shutdown. Those four come up constantly and the mistakes are expensive — see probes done wrong causing outages.

Interview questions

Basic

What's the difference between a container and a virtual machine? 🔥 Must know
How I'd answer

"The core difference is that a VM virtualises hardware and a container virtualises the operating system."

"A VM runs a complete guest OS with its own kernel on top of a hypervisor. A container is just a process on the host, started with a restricted view of the filesystem, network and process list, and a cap on CPU and memory. If I run ps on the host I can see the container's process directly — there's no boundary in the way you might expect."

"Everything practical follows from that. There's no OS to boot, so a container starts in milliseconds rather than tens of seconds. It's tens of megabytes rather than gigabytes, because it holds the app and its dependencies rather than a whole OS. And you can run hundreds on a host instead of tens."

"The mechanisms, if it's useful: namespaces restrict what the process can see, cgroups restrict what it can use, and a union filesystem stacks read-only image layers with one writable layer. That last one is why ten containers from the same image cost roughly one image's worth of disk."

"The trade-off worth being honest about: isolation is weaker. A VM boundary is enforced by hardware; a container boundary is enforced by kernel features, and the kernel is shared. So a kernel vulnerability potentially affects every container on the host, and a privileged container can often escape entirely."

"Which is why containers alone aren't a security boundary for hostile workloads. If I were running untrusted code — a customer's build script, say — I'd want VM-level isolation, or something like gVisor. For my own services in a trusted estate, containers are fine."

"One more practical consequence: the kernel must match. Windows containers need a Windows host and Linux containers need a Linux kernel. Docker Desktop makes this invisible on Windows by running a Linux VM underneath, which is worth knowing because it explains why 'it works on my Windows machine' can mean 'it works in a Linux VM on my Windows machine'."

"And they're not exclusive — in practice containers usually run on VMs. AKS nodes are VMs. So it's layered rather than a choice, with the VM providing the hard boundary between tenants and containers providing density and packaging within it."

What they're really checking
  • Do you know a container is a host process, not a small VM?
  • Can you connect that to start time, size and density?
  • Are you honest about weaker isolation?
  • Do you know the kernel must match?
Weak answers
  • Red flag: "a container is a lightweight VM."
  • Red flag: claiming equal isolation to a VM.
  • Red flag: thinking a Linux container runs on a Windows kernel.
Likely follow-ups
  • Would you run untrusted code in a container?
  • How does Docker Desktop run Linux containers on Windows?
  • Why is an image with ten layers not ten times the size?
