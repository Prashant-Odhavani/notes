Containers in Production

Where the interesting failures live. Most of them come from four numbers and two probes being wrong.

Memory and CPU need opposite treatment

They behave differently under pressure, and configuring them the same way is the underlying mistake.

Memory is incompressible. A process either has the memory it needs or it dies — there's no degraded mode. So overcommitting memory means an OOM kill rather than a slowdown. Set request equal to limit: the scheduler reserves what the container can actually use, and the pod gets a better QoS class so it isn't the first thing evicted when the node runs short.

CPU is compressible. A process short of CPU runs slower, which is a perfectly acceptable degraded mode. So set a request and consider omitting the limit — then a burst uses spare node capacity instead of being throttled while the node sits idle.

CPU throttling is worth understanding because it's counterintuitive: the limit is enforced per 100ms period, so a container at its limit is paused for the rest of each period. For a request that needs a short burst of work, that turns a 20ms operation into 100ms+ of wall-clock latency — while kubectl top reports modest average CPU. Latency that doesn't correlate with visible CPU usage is the signature, and container_cpu_cfs_throttled_seconds_total is the metric that confirms it.

The counterargument for setting CPU limits is predictability and preventing one noisy pod monopolising a node. That's legitimate on shared clusters — but then the limit needs to be generous, not equal to the request.

Nothing set is the worst option

A pod with no requests is BestEffort: the scheduler assumes it needs nothing, so it packs it onto any node, and it's the first thing evicted when that node comes under memory pressure.

Worse, it distorts the whole cluster. The scheduler's view of node capacity is built from requests, so unrequested pods make nodes look free when they're not. The result is nodes that appear to have headroom and are actually overloaded — and the cluster autoscaler won't add capacity, because by its accounting there's plenty.

Then everything on that node degrades together, and the pod that gets killed is often not the one causing the problem.

A LimitRange per namespace applies defaults so an unspecified pod still gets sensible numbers, and a ResourceQuota caps the namespace total. Both are worth having — they make the good configuration the default rather than something every team must remember.

builder.Services.AddHealthChecks()
    // Liveness: is THIS PROCESS functioning? No dependencies.
    .AddCheck("self", () => HealthCheckResult.Healthy(), tags: ["live"])

    // Readiness: can this instance serve requests? Dependencies allowed.
    .AddNpgSql(connectionString, name: "db",    tags: ["ready"])
    .AddRedis(redisConnection,   name: "cache", tags: ["ready"],
              failureStatus: HealthStatus.Degraded);   // cache down != cannot serve

var app = builder.Build();

// Liveness - never touches the database
app.MapHealthChecks("/health/live", new HealthCheckOptions
{
    Predicate = r => r.Tags.Contains("live")
});

// Readiness - Degraded still returns 200, so a soft dependency
// does not remove the pod from load balancing
app.MapHealthChecks("/health/ready", new HealthCheckOptions
{
    Predicate = r => r.Tags.Contains("ready"),
    ResultStatusCodes =
    {
        [HealthStatus.Healthy]   = StatusCodes.Status200OK,
        [HealthStatus.Degraded]  = StatusCodes.Status200OK,
        [HealthStatus.Unhealthy] = StatusCodes.Status503ServiceUnavailable
    }
});
A liveness probe that checks the database causes the outage it was meant to prevent

This is the most damaging probe mistake, and it's common because it looks thorough.

If liveness checks the database, then a 30-second database blip fails liveness on every pod simultaneously. Kubernetes restarts them all. Now you have a full outage, a thundering herd of reconnections when the database recovers, and a cold cache — from a transient issue that would have resolved itself.

Liveness must only check what a restart could fix. A restart doesn't fix the database. So the liveness endpoint should confirm the process is responsive and nothing more.

Readiness may check dependencies, because removing a pod from load balancing is reversible and harmless. But even there, be careful: if every pod's readiness fails at once, the Service has no endpoints and you're returning errors anyway — you've just chosen a different failure mode.

Which is why the Degraded status above matters. Redis being unavailable usually means slower responses, not an inability to serve — so it maps to 200 and the pod stays in rotation. Distinguishing hard from soft dependencies in the health check is a genuinely senior detail.

Startup probes exist because slow boots get killed

A .NET app doing JIT warm-up, migrations, or loading a large cache can take 30+ seconds to be useful. If the liveness probe starts checking immediately with a 3-failure threshold, it kills the container during startup — every time, forever.

The result is a permanent CrashLoopBackOff that looks like a broken application and is a broken probe.

Tuning initialDelaySeconds is the old workaround and it's a bad trade: set it long enough for the worst-case boot and you've also delayed detection of a genuine hang by that long.

startupProbe solves it properly. It gets a generous window — failureThreshold × periodSeconds — and liveness doesn't run at all until it passes. So slow starts are tolerated and, once running, liveness reacts quickly. Long window for boot, short window for hangs, no compromise.

Graceful shutdown 🔥 Must know

  t=0    Pod marked Terminating
         TWO THINGS START IN PARALLEL:
           (a) removal from Service endpoints  -- takes time to propagate
           (b) preStop hook, then SIGTERM to the container

  t=0..n  Endpoint removal propagates to every kube-proxy / ingress.
          UNTIL IT DOES, NEW REQUESTS STILL ARRIVE.

  SIGTERM  app should: stop accepting new work, finish in-flight, close cleanly

  t=30s   terminationGracePeriodSeconds elapsed -> SIGKILL. No cleanup.
Senior signal — the race is why you need a preStop sleep

Endpoint removal and SIGTERM happen concurrently, not in sequence. So there's a window where the pod has been told to shut down but the load balancer is still sending it traffic.

That window is small — usually a second or two — and it produces exactly the symptom teams report: a handful of 502s on every deployment, too few to be obviously broken and consistent enough to be annoying.

A preStop hook that simply sleeps for a few seconds fixes it. The pod keeps serving normally during the sleep while endpoint removal propagates, and only then does the application receive SIGTERM.

Sleeping is the correct implementation, which feels wrong and isn't. There's no signal that says "endpoint removal is complete", so waiting a fixed short period is the mechanism Kubernetes gives you.

On the application side, .NET handles SIGTERM through IHostApplicationLifetime automatically: Kestrel stops accepting connections and waits for in-flight requests up to the shutdown timeout. The default timeout is 30 seconds and worth setting explicitly — it must be shorter than terminationGracePeriodSeconds, or the kernel kills the process mid-request while it's still politely draining.

spec:
  terminationGracePeriodSeconds: 45      # must exceed app shutdown timeout + preStop
  containers:
    - name: api
      lifecycle:
        preStop:
          exec:
            command: ["/bin/sleep", "5"]  # let endpoint removal propagate
      env:
        # Kestrel drains for up to 30s; 30 + 5 preStop < 45 grace period
        - name: HOSTOPTIONS__SHUTDOWNTIMEOUT
          value: "00:00:30"
---
# Stop a node drain taking every replica at once
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata: { name: orders-api }
spec:
  minAvailable: 2                        # NOT equal to replicas - see the note
  selector:
    matchLabels: { app: orders-api }
A PodDisruptionBudget that's too strict blocks drains forever

A PDB tells Kubernetes the minimum that must stay available during voluntary disruption — a node drain, a cluster upgrade, the autoscaler removing a node.

Without one, a drain can evict every replica of a service simultaneously and you get an outage during a routine upgrade.

With minAvailable set equal to replicas, nothing can ever be evicted. The drain hangs indefinitely, the cluster upgrade stalls, and the autoscaler can't remove empty nodes so you keep paying for them. That's its own incident, and a confusing one because everything looks healthy.

So minAvailable must leave slack — 2 of 3, or a percentage. And note a PDB protects against voluntary disruption only: a node failing hard takes its pods regardless, which is what topology spread constraints across zones are for.

Senior signal — the memory limit changes runtime behaviour, not just the kill threshold

.NET reads the container's memory limit and sizes its GC heap from it. So the limit is an input to the runtime, not merely a boundary the kernel enforces.

Set it too tight and the GC runs far more aggressively to stay inside — burning CPU, adding pause time, and possibly still being killed. Which produces a genuinely confusing profile: high CPU, poor latency, and memory that looks fine because the GC is working hard to keep it that way.

Raising the memory limit can therefore reduce CPU usage. That's the counterintuitive result worth knowing.

Server GC is another consideration. It's the ASP.NET Core default and tuned for throughput: one heap per core, and it holds memory rather than returning it. In a container with a 256Mi limit and 16 visible cores that's a poor fit. Either switch to Workstation GC, or keep Server GC with DOTNET_GCConserveMemory / GCHeapCount tuned. It's a real trade — Workstation is more memory-efficient and somewhat lower throughput — so measure rather than assume.

Also leave headroom below the limit: the GC heap isn't the only memory the process uses. Native allocations, thread stacks and the runtime itself all count against the cgroup limit, so a heap limit at 100% of the container limit will still get OOM-killed.

Being able to explain that .NET is container-aware — and how — is a strong signal, because most candidates treat the limit as purely a ceiling.

Debugging in production 🔥 Must know

# Ephemeral debug container sharing the target's namespaces.
# Gives you a shell and tooling next to a chiseled/distroless image.
kubectl debug -it orders-api-7d4f-x2n \
  --image=mcr.microsoft.com/dotnet/sdk:9.0 \
  --target=api

# Inside it, the .NET diagnostic tools work against the target process:
dotnet-counters monitor -p 1                  # GC, thread pool, request rate, live
dotnet-stack report   -p 1                    # all thread stacks - finds deadlocks
dotnet-gcdump collect -p 1                    # heap contents for leak hunting
dotnet-trace collect  -p 1 --profile cpu-sampling

# Copy a pod with a debug-friendly command, leaving the original running
kubectl debug orders-api-7d4f-x2n --copy-to=debug-pod --container=api -- sleep infinity

# Pull an artefact out
kubectl cp orders-api-7d4f-x2n:/tmp/dump.gcdump ./dump.gcdump
This is what makes minimal images practical

The usual objection to chiseled or distroless images is "how do I debug it with no shell?" The answer is that you bring the tooling when you need it rather than shipping it permanently.

kubectl debug attaches an ephemeral container in the pod's namespaces, so it sees the same network, the same process tree, and (with --target) can attach diagnostics to the running process. The debug container disappears afterwards; the image stays minimal.

For .NET the payoff is real: dotnet-counters for live GC and thread-pool statistics, dotnet-stack for a full thread dump — which is how you identify a deadlock or thread-pool starvation — and dotnet-gcdump for what's actually on the heap.

Thread pool starvation is worth knowing by its signature: rising queue length with low CPU, requests queuing behind blocked threads. Almost always sync-over-async — a .Result or .Wait() on a hot path. dotnet-counters shows it directly, and it's very hard to diagnose from logs alone.

The prerequisite: set this up before you need it. RBAC must permit pods/ephemeralcontainers, and the first time you use it shouldn't be during an incident.

Cost 🟡 Intermediate

LeverEffect
Right-size requests from observed usageUsually the largest single saving
Cluster autoscaler with a sensible minimumRemoves idle nodes

KEDA scale-to-zeroIdle consumers cost nothing
Fewer, larger nodesLess per-node system overhead — with a bigger blast radius
Over-requesting is the usual cost problem

Because the scheduler allocates on requests, a cluster where every pod requests four times what it uses looks full at 25% real utilisation. The autoscaler dutifully adds nodes nobody needs.

So the highest-value cost exercise is comparing kubectl top — or better, p95 usage over a couple of weeks — against the declared requests, and closing the gap. It's common to find a 2–4× over-allocation and reclaim it with no code change and no risk to capacity.

The Vertical Pod Autoscaler can recommend values based on observed usage, which is a good input even if you don't let it apply them automatically.

Two cautions. Don't right-size down to average usage — requests need to cover normal peaks, or you're trading cost for latency. And on spot nodes, the discount is real but eviction is arbitrary and can take a whole node pool at once, so they suit batch, CI and stateless workloads with plenty of replicas — not your only API pool.

Key takeaways
  • Requests drive scheduling; limits drive runtime behaviour under pressure.
  • Memory: request = limit, because memory is incompressible.
  • CPU: set a request, consider omitting the limit; throttling is per-100ms.
  • Nothing set is worst — BestEffort, evicted first, and it distorts scheduling.
  • LimitRange and ResourceQuota make good defaults structural.
  • Startup protects slow boots; readiness removes traffic; liveness restarts.
  • Never check a shared dependency in liveness.
  • Map Degraded to 200 so soft dependencies don't drop the pod.
  • Endpoint removal races SIGTERM — a preStop sleep is the fix.
  • App shutdown timeout must be shorter than the grace period.
  • PDB with slack; minAvailable = replicas blocks drains forever.
  • .NET sizes the GC heap from the container limit — leave headroom.
  • kubectl debug plus dotnet-counters/-stack/-gcdump.
  • Right-sizing requests is usually the biggest cost win.

Common mistakes

  • No requests or limits at all, giving BestEffort QoS.
  • Memory request below the limit, so nodes are overcommitted.
  • A tight CPU limit, causing throttling that looks like slow code.
  • Liveness checking the database, restarting every pod during a blip.
  • No startup probe on a slow-starting app, so liveness kills it forever.
  • No readiness probe, so rollouts replace healthy pods with broken ones.
  • No preStop hook, producing 502s on every deployment.
  • Shutdown timeout longer than the grace period, so SIGKILL interrupts draining.
  • minAvailable equal to replicas, blocking drains and upgrades.
  • Ignoring Server GC in a small-memory container.
  • A GC heap limit at 100% of the container limit.
  • Requests set from guesswork, over-allocating the cluster several times over.
  • Spot nodes for the primary API pool.

Interview questions

Advanced

Every deployment produces a handful of 502s. Why, and how do you fix it? ⭐ Senior-level
How I'd answer

"That's the classic shutdown race, and it happens because endpoint removal and SIGTERM are concurrent, not sequential."

"When a pod is deleted, Kubernetes does two things in parallel: it removes the pod from the Service endpoints, and it sends SIGTERM to the container. But endpoint removal has to propagate — to every kube-proxy on every node, and to the ingress controller. That takes a second or two."

"So there's a window where the application has been told to shut down while the load balancer is still sending it requests. Those requests hit a closing listener and become 502s. Small enough not to look broken, consistent enough to be irritating — which is exactly the symptom described."

"The fix has three parts."

"A preStop hook that sleeps for about five seconds. The pod keeps serving normally during the sleep while endpoint removal propagates, and only then does the app receive SIGTERM. Sleeping feels like a hack and it's the correct implementation — there's no signal that says 'endpoint removal is complete', so a fixed short wait is the mechanism Kubernetes provides."

"Handle SIGTERM properly. .NET does most of this: Kestrel stops accepting new connections and waits for in-flight requests up to the host shutdown timeout. What I'd check is that nothing else exits early — background services should observe the cancellation token and drain rather than abandoning work, and a message consumer should stop pulling new messages while finishing the current one."

"Get the timeouts in the right order. The application shutdown timeout must be shorter than terminationGracePeriodSeconds, with the preStop sleep accounted for. If the grace period expires first, SIGKILL lands mid-request and you've reintroduced the problem you were fixing. So something like 5 seconds preStop plus a 30-second drain inside a 45-second grace period."

"There's a second cause worth checking, because it produces the same symptom from the other direction: pods being added before they're ready. If there's no readiness probe, Kubernetes considers a started container ready and routes traffic to it immediately — before the app has finished booting. So you get errors from the new pods as well as the old ones."

"And on the caller side, in Kubernetes specifically: connection reuse. A long-lived HttpClient holding a pooled connection to a pod that's now gone will fail on that connection. IHttpClientFactory with a bounded PooledConnectionLifetime handles it, and a retry policy on idempotent requests covers the remaining race — because with a rolling deployment there's always some window."

"To verify the fix I'd run a load test through a deployment and watch for non-200s. That's the only real confirmation, and it's worth having as a test rather than an assumption, because every one of these settings can silently regress."

"The general principle: graceful shutdown is a distributed-systems problem, not a process one. The application exiting cleanly isn't sufficient — the rest of the system has to stop pointing at it first, and nothing tells you when that's happened."

What they're really checking
  • Do you know endpoint removal and SIGTERM are concurrent?
  • Do you know preStop sleep is the correct fix?
  • Do you get the timeout ordering right?
  • Do you also consider readiness on the way in?
  • Do you handle client-side connection reuse?
Weak answers
  • Red flag: "add retries" as the only fix.
  • Red flag: assuming endpoint removal completes before SIGTERM.
  • Red flag: a longer grace period with no shutdown handling.
Likely follow-ups
  • What if a request legitimately takes two minutes?
  • How do you drain a message consumer?
  • How would you prove the fix works?
A service is slow but CPU looks low. Where do you look? ⭐ Senior-level
How I'd answer

"Low CPU with high latency is a distinctive combination — it means the work isn't CPU-bound, so something is waiting or being prevented from running. I'd check four things, in rough order of how often they're the cause in containers."

"CPU throttling. The container-specific one, and the most commonly missed. A CPU limit is enforced per 100ms period, so a container that consumes its quota is paused for the rest of that period. A request needing a short burst of work gets suspended repeatedly — turning 20ms of work into 100ms+ of wall-clock time."

"And crucially, average CPU looks low, because the container spends most of each period idle-because-throttled. So kubectl top is reassuring and wrong. The metric that confirms it is container_cpu_cfs_throttled_seconds_total. The fix is a more generous CPU limit, or removing it and relying on the request — CPU is compressible, so absorbing a burst is better than throttling."

"Thread pool starvation. The .NET-specific one. Sync-over-async — a .Result or .Wait() on a hot path — blocks pool threads. The pool injects new threads slowly, so requests queue behind blocked threads while CPU sits idle. Latency climbs with concurrency and CPU doesn't."

"dotnet-counters shows it directly: queue length rising, thread count climbing. dotnet-stack gives every thread's stack, and if dozens are parked on the same .Result, that's the answer. Both are runnable in production via kubectl debug without shipping a shell in the image."

"Waiting on a dependency. A slow SQL query, a slow HTTP call, lock contention, or connection-pool exhaustion. Application Insights' dependency telemetry answers this quickly — either one dependency is slow, or there are hundreds of fast ones, which is an N+1 and invisible in any latency percentile because nothing is individually slow."

"Connection-pool exhaustion is worth calling out because it mimics everything else: requests wait for a free connection, so latency is high and nothing is busy. Usually caused by connections not being disposed, or a pool size that's fine on one instance and inadequate once you've scaled out — the database has a finite total."

"GC pressure. If the memory limit is tight, .NET's GC — which sizes its heap from the container limit — runs aggressively to stay inside it. That produces pause time and, oddly, higher CPU rather than lower, so it wouldn't fit this symptom perfectly. But high allocation rates with frequent Gen2 collections can add latency that looks like waiting, and dotnet-counters shows GC counts and pause time per generation."

"Server GC is a factor here too: it's the ASP.NET Core default, allocates per-core heaps and holds memory. In a small container with many visible cores that's a poor fit, and Workstation GC can be measurably better."

"How I'd narrow it: does latency scale with concurrency? If yes, it's queueing — throttling, thread pool, or connection pool. If latency is constant regardless of load, it's a slow dependency or a slow code path. That one question splits the four causes into two pairs and saves a lot of time."

"The general point: in containers, low CPU with high latency should make you suspect throttling before anything else, because the metric everyone looks at actively hides it."

What they're really checking
  • Do you suspect CPU throttling, and know average CPU hides it?
  • Do you know the thread-pool starvation signature?
  • Do you use dotnet-counters/dotnet-stack in a container?
  • Do you consider connection-pool exhaustion?
  • Do you have a way to narrow it — latency versus concurrency?
Weak answers
  • Red flag: "scale out" without a diagnosis.
  • Red flag: concluding it's fine because CPU is low.
  • Red flag: no awareness of CPU throttling in containers.
Likely follow-ups
  • How would you prove throttling is happening?
  • How do you find sync-over-async in a large codebase?
  • Server GC or Workstation GC here?
