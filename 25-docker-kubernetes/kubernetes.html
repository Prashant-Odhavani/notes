Kubernetes

A control loop that moves actual state toward declared state. Every primitive below is a different kind of declaration.

🟡 Intermediate 🔴 Advanced 🔥 Must know
Quick revision
  • Pod — one or more containers sharing a network and lifecycle. Disposable.
  • Deployment — "keep N pods of this spec running", plus rolling updates.
  • Service — a stable name and IP in front of a changing set of pods.
  • Ingress — HTTP routing from outside into Services.
  • Labels and selectors are the glue. Nothing references pods by name.
  • Secrets are base64, not encrypted.
  • StatefulSet for stable identity and per-pod storage.
  • Namespaces scope names and quota, and don't isolate the network by default.

The reconciliation model 🔥 Must know

The one idea

You submit a declaration of what should exist. A controller watches, compares it to reality, and acts to close the gap — continuously, forever.

You never tell Kubernetes to do something. You tell it what should be true.

Think of it this way

A thermostat isn't given the instruction "turn on the heating." It's given a target temperature, and it keeps acting until the room matches.

So a deleted pod comes back, a lost node's pods reappear elsewhere, and a changed image tag rolls out gradually — not because anyone issued those commands, but because the declaration still says three healthy pods of version 1.4 should exist.

This is also how you debug

Because every problem is a gap between declared and actual, the diagnostic question is always "what is the controller trying to do, and what's stopping it?"

kubectl describe answers that. The Events section at the bottom is where the answer usually is: FailedScheduling because no node has enough CPU, ImagePullBackOff because the registry credential is wrong, CrashLoopBackOff because the container exits on startup.

That's the habit worth having: describe before logs. Logs tell you what the application said; describe tells you whether the platform even got as far as running it.

And a rollout that appears "stuck" is usually the controller behaving correctly — refusing to continue because a new pod never became ready. That's the system protecting you, not failing.

Pods, ReplicaSets and Deployments 🔥 Must know

ObjectResponsibility
PodThe unit of scheduling. Containers inside share an IP, localhost and volumes
ReplicaSetKeeps N identical pods running. You don't create these directly
DeploymentManages ReplicaSets to give you rolling updates and rollback
Senior signal — a Deployment is a ReplicaSet manager, and that's how rollback works

Changing a Deployment's pod template doesn't modify the existing ReplicaSet. It creates a new one and shifts replicas from old to new gradually, respecting maxUnavailable and maxSurge.

The old ReplicaSet stays, scaled to zero. Which is exactly why kubectl rollout undo is fast: it scales the old ReplicaSet back up. No rebuild, no re-pull if the image is still cached — same property as an App Service slot swap.

It also explains the rollout pausing behaviour. New pods must pass readiness before the old ones are removed, so a broken image doesn't take the service down — the rollout stalls with the old pods still serving. That's the safety property, and it only works if you have a readiness probe. Without one, Kubernetes considers a started container ready and will happily replace every working pod with broken ones.

Which is the practical point: no readiness probe means no safe rollout.

apiVersion: apps/v1
kind: Deployment
metadata:
  name: orders-api
  labels: { app: orders-api }
spec:
  replicas: 3
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxUnavailable: 0        # never go below 3 healthy during a rollout
      maxSurge: 1              # add one at a time
  selector:
    matchLabels: { app: orders-api }    # MUST match the template labels
  template:
    metadata:
      labels: { app: orders-api }
    spec:
      containers:
        - name: api
          image: myacr.azurecr.io/orders-api:1.4.2
          ports: [{ containerPort: 8080 }]
          resources:
            requests: { cpu: "200m", memory: "256Mi" }
            limits:   { memory: "256Mi" }
          readinessProbe:
            httpGet: { path: /health/ready, port: 8080 }
            periodSeconds: 5
          livenessProbe:
            httpGet: { path: /health/live, port: 8080 }
            periodSeconds: 15
            failureThreshold: 3
          envFrom:
            - configMapRef: { name: orders-config }
          env:
            - name: POD_NAME
              valueFrom: { fieldRef: { fieldPath: metadata.name } }
Labels and selectors are the entire wiring mechanism

Nothing in Kubernetes references a pod by name. A Deployment finds its pods by label selector. A Service finds its endpoints the same way. So do NetworkPolicies and PodDisruptionBudgets.

That's why spec.selector.matchLabels must match spec.template.metadata.labels. Get it wrong and the Deployment creates pods it doesn't consider its own — so it creates more, endlessly, and nothing obviously errors.

The subtler bug is a Service selector that's too broad. If it selects app: orders-api and you deploy a second Deployment sharing that label — a canary, say — the Service silently sends traffic to both. Which is sometimes what you want and frequently a surprise.

A Deployment's selector is also immutable after creation, so getting labels right early matters. Convention helps: app, version and component, with the Service selecting on app only when you genuinely want every version behind it.

Why Ingress rather than a LoadBalancer per service

Each LoadBalancer Service provisions a real cloud load balancer with its own public IP. Ten services means ten load balancers, ten IPs, ten sets of TLS certificates and ten line items on the bill.

An Ingress gives you one entry point that routes by host and path to many Services — centralising TLS termination, certificate management via cert-manager, and any rewriting or auth at the edge.

Mechanically: the Ingress resource is just a declaration, and an ingress controller (NGINX, Application Gateway Ingress Controller, Traefik) is what implements it. No controller means the resource does nothing at all, silently — which is a common first-time confusion.

Worth knowing that Gateway API is the successor: better multi-team support, proper separation between infrastructure and route ownership, and richer traffic rules. Ingress is what you'll meet in existing clusters; Gateway API is where it's going.

Service DNS, and the detail that catches people

A Service gets a DNS name: orders-api within the same namespace, orders-api.production.svc.cluster.local fully qualified. That name is stable while the pods behind it come and go — which is the whole point.

The gotcha: this is DNS, and .NET's HttpClient caches connections. A long-lived HttpClient with a pooled connection to a pod that has since been deleted keeps trying to use it — because the DNS lookup already happened.

That's why IHttpClientFactory with a bounded PooledConnectionLifetime matters in Kubernetes specifically: pods are replaced constantly, so connection reuse has to be time-bounded or you'll see intermittent failures after every deployment.

Also: Service load balancing is L4, not L7. It distributes connections, not requests. So with HTTP/2 or gRPC, which multiplex many requests over one connection, a client can pin all its traffic to a single pod. That's the standard gRPC-in-Kubernetes surprise, and it needs either client-side load balancing via a headless Service or a proxy that understands L7.

Secrets are base64-encoded, and that's the whole protection

A Kubernetes Secret is not encrypted by default. It's base64, which is encoding — trivially reversible and not a security measure at all.

What that means practically: anyone with get secrets in the namespace can read every value, they appear in etcd backups in recoverable form, and they're visible to anyone who can describe the pod's environment.

So the sensible position is to avoid Secrets holding real secrets. Use workload identity so the pod gets an Entra token and no credential exists, and for things that genuinely must be a secret — a third-party API key — mount it from Key Vault with the Secrets Store CSI driver, so it's never a Kubernetes object.

If you must use Secrets, enable encryption at rest for etcd and restrict RBAC on the secrets resource specifically. But the better answer is not to need them.

And never commit a Secret manifest to Git. If GitOps requires it, that's what SealedSecrets or SOPS exist for — the committed form is encrypted and only the cluster can decrypt it.

Environment variables don't reload; mounted files do

A ConfigMap consumed as environment variables is read once at container start. Updating the ConfigMap changes nothing until the pod restarts — and nothing tells you that, so the config looks applied and isn't.

Consumed as a mounted volume, the file is updated by the kubelet within a minute or two. So an application using .NET's file-based configuration with reloadOnChange picks it up without a restart.

Which is the better pattern when you want dynamic configuration — mount a JSON file and let IConfiguration reload it. Read it through IOptionsMonitor, though, not IOptions, or the change is loaded and never observed.

The common workaround for the env-var case is to annotate the pod template with a hash of the ConfigMap, so changing the config changes the template and triggers a rolling update. That's deliberate and visible, which is often preferable to configuration silently changing under a running app.

The other workload types 🟡 Intermediate

KindGives youUse for
StatefulSet Stable names (db-0, db-1), ordered start-up, per-pod persistent volume Databases, brokers, anything with per-replica identity
DaemonSet One pod per node, automatically on new nodes Log collectors, node agents, CNI components
Job Runs to completion, with retries Database migrations, one-off tasks
CronJob Jobs on a schedule Nightly batch, cleanup
A StatefulSet doesn't make software distributed

StatefulSets provide the primitives stateful software needs: a stable hostname, a volume that follows the pod, and ordered rollout. They provide nothing about replication, failover, leader election or backup.

So running PostgreSQL as a StatefulSet gives you PostgreSQL with stable storage. It does not give you a highly-available PostgreSQL — that requires an operator that understands replication and promotion, or a managed service.

Which is why the usual advice holds: run stateless workloads on Kubernetes and use managed services for data, unless there's a specific reason not to. Azure SQL, Cosmos DB and Azure Cache for Redis handle backup, patching, failover and point-in-time restore — all of which you would otherwise be building and testing yourself, in the part of the system where mistakes are least recoverable.

Being able to say that is a stronger signal than knowing StatefulSet mechanics.

Jobs are how migrations should run

Running Database.Migrate() at application startup is convenient and it goes wrong at scale: with three replicas, three pods try to migrate simultaneously. EF Core takes a lock so it usually survives, but the pods that lose it are blocked, may fail their readiness probe, and can restart-loop while waiting.

A Job — or a Helm pre-upgrade hook — runs the migration exactly once, to completion, before the new pods roll out. If it fails, the deployment stops, which is what you want.

That also forces the discipline that matters more: the migration must be backward compatible, because old pods are still serving while it runs. Expand-and-contract across separate releases — add the column, deploy code that writes both, migrate data, then remove — same as any rolling deployment.

Kubernetes doesn't create that requirement; it just makes ignoring it break in production rather than in staging.

Namespaces and scoping 🟡 Intermediate

A namespace gives youIt does not give you
A scope for object namesNetwork isolation — pods can reach any namespace by default
An RBAC boundaryNode isolation — workloads still share nodes
ResourceQuota and LimitRangeA security boundary against hostile tenants
A logical grouping for teams or environmentsSeparate control planes
Flat network by default — namespaces don't stop traffic

The default Kubernetes network model is every pod can reach every other pod, in any namespace. Namespaces scope names, not traffic.

So a compromised pod in a low-value namespace can talk directly to your payments service, and nothing is blocking it.

NetworkPolicies are how you restrict that, and the strong pattern is default-deny per namespace, then allow what's needed — an allow-list, since a deny-list will always be incomplete. On AKS this needs a network policy engine (Azure Network Policy or Cilium) to be enabled, or the policies are accepted and silently do nothing, which is worse than not having them.

And for genuinely hostile multi-tenancy — running other people's code — namespaces are not the answer at all. That needs separate clusters, or VM-level isolation, because the container boundary is a shared kernel.

The kubectl you actually use 🟢 Beginner

kubectl get pods -o wide                    # what exists, on which node, restart counts
kubectl describe pod orders-api-7d4f-x2n    # EVENTS at the bottom - start here
kubectl logs orders-api-7d4f-x2n            # current container
kubectl logs orders-api-7d4f-x2n --previous # the one that just crashed
kubectl logs -l app=orders-api --tail=100   # across all pods by label

kubectl get events --sort-by=.lastTimestamp # cluster-wide, chronological
kubectl top pods                            # actual CPU/memory vs requests

kubectl rollout status deploy/orders-api    # is the rollout progressing?
kubectl rollout undo   deploy/orders-api    # scale the previous ReplicaSet back up

kubectl port-forward svc/orders-api 8080:80 # reach a ClusterIP service locally
kubectl debug -it orders-api-7d4f-x2n \
  --image=mcr.microsoft.com/dotnet/sdk:9.0 --target=api   # shell alongside a shell-less image
--previous and debug are the two worth memorising

logs --previous is what you need for a CrashLoopBackOff, because the current container has only just started and hasn't produced the error yet. The reason it crashed is in the previous container's logs, and without this flag you'll watch an empty log and conclude there's nothing there.

kubectl debug attaches an ephemeral container sharing the target's namespaces — so you get a shell and tooling alongside a chiseled or distroless image that has neither. That's what makes minimal images practical to run: you don't need a shell in the image, you bring one when you need it.

And the ordering habit: describe before logs. If the container never started — bad image reference, missing ConfigMap, unschedulable — there are no logs to read, and describe tells you that in one line.

Key takeaways
  • Declarative reconciliation: you declare state, controllers close the gap continuously.
  • describe before logs; the Events section holds most answers.
  • A Deployment manages ReplicaSets — that's why rollback is instant.
  • No readiness probe means no safe rollout.
  • Labels and selectors are the only wiring; a Deployment's selector is immutable.
  • ClusterIP by default; Ingress instead of a load balancer per service.
  • Service load balancing is L4, so gRPC and HTTP/2 can pin to one pod.
  • Bound PooledConnectionLifetime — pods are replaced constantly.
  • Secrets are base64, not encrypted; prefer workload identity or the CSI driver.
  • Env vars need a restart; mounted files reload.
  • StatefulSet gives identity and storage, not high availability.
  • Run migrations as a Job, and make them backward compatible.
  • Namespaces don't isolate the network — that's NetworkPolicies, default-deny.
  • logs --previous for crash loops; kubectl debug for shell-less images.

Common mistakes

  • No readiness probe, so a broken image replaces every healthy pod.
  • Selector and template labels mismatched, so pods multiply.
  • A Service selector too broad, sending traffic to a canary unintentionally.
  • A LoadBalancer per service instead of one Ingress.
  • An Ingress resource with no controller installed, silently doing nothing.
  • Real secrets in Kubernetes Secrets, readable and in etcd backups.
  • Committing Secret manifests to Git.
  • Expecting env-var ConfigMap changes to apply without a restart.
  • Running a production database as a StatefulSet with no operator.
  • Migrating at application startup with multiple replicas.
  • Assuming namespaces block traffic.
  • NetworkPolicies with no policy engine enabled on AKS.
  • Reading logs without --previous on a crash loop.

Interview questions

Intermediate

Explain Pod, Deployment and Service, and how they relate. 🔥 Must know
How I'd answer

"They're three layers, each solving a problem the one below leaves open."

"A Pod is the unit of scheduling — one or more containers that share a network namespace, so they see each other on localhost, and share volumes. The key property is that pods are disposable. They get a new IP each time, they're evicted, rescheduled and replaced. You never manage them directly."

"A Deployment declares 'three pods matching this spec should exist'. A controller makes that true — replacing crashed pods, rescheduling when a node dies. It also handles rolling updates."

"The mechanism there is worth knowing: a Deployment doesn't manage pods directly, it manages ReplicaSets. Changing the pod template creates a new ReplicaSet and shifts replicas across gradually. The old one stays at zero replicas — which is why rollout undo is nearly instant: it just scales the old ReplicaSet back up."

"And the safety property: new pods must pass their readiness probe before old ones are removed. So a broken image stalls the rollout with the old pods still serving. That only works if you have a readiness probe — without one, Kubernetes treats a started container as ready and will cheerfully replace every working pod with broken ones. No readiness probe means no safe rollout."

"A Service solves the addressing problem the first two create. Pods come and go with different IPs, so nothing can depend on a pod address. A Service is a stable name and virtual IP in front of whichever pods currently match its selector, with DNS so another service connects to orders-api and doesn't care what's behind it."

"Which brings up the thing that actually ties all three together: labels and selectors. Nothing references anything by name. The Deployment finds its pods by label, the Service finds its endpoints by label. That's the whole wiring model, and it's why a mismatch between spec.selector and the template labels causes strange behaviour — the Deployment creates pods it doesn't recognise as its own, so it creates more."

"Two things I'd add that matter in practice."

"Service load balancing is L4 — it distributes connections, not requests. With HTTP/2 or gRPC multiplexing many requests over one connection, a client can end up pinned to a single pod. That's the standard gRPC surprise and it needs client-side load balancing or an L7 proxy."

"And connection lifetime. Because pods are replaced constantly, a long-lived HttpClient holding a pooled connection to a deleted pod fails intermittently after every deployment. IHttpClientFactory with a bounded PooledConnectionLifetime handles it — that's a .NET-specific detail that matters much more in Kubernetes than elsewhere."

What they're really checking
  • Do you know pods are disposable and not managed directly?
  • Do you know a Deployment manages ReplicaSets, enabling rollback?
  • Do you connect readiness probes to safe rollouts?
  • Do you identify labels and selectors as the wiring?
  • Do you know Services are L4?
Weak answers
  • Red flag: managing pods directly.
  • Red flag: no mention of readiness in the rollout.
  • Red flag: thinking a Service is an L7 load balancer.
Likely follow-ups
  • What happens if a new pod never becomes ready?
  • How does traffic get in from outside?
  • Why would gRPC calls all hit one pod?

Advanced

A pod is in CrashLoopBackOff. How do you diagnose it? ⭐ Senior-level
How I'd answer

"CrashLoopBackOff means the container starts, exits, and Kubernetes restarts it with increasing backoff. So the container is being created — that already rules out scheduling and image-pull problems, which show up as different statuses."

"I'd go in a specific order, because the fast checks eliminate whole categories."

"kubectl describe pod first, and the Events section at the bottom. That tells me the last exit code and reason, which immediately narrows it: OOMKilled with exit 137 is a memory limit; a non-zero application exit code means the process itself failed; and a failing liveness probe is a different problem entirely — the app may be fine and the probe is killing it."

"That last case is worth calling out because the fix is the opposite of what it looks like. If the liveness probe has no initialDelaySeconds and the app takes 20 seconds to start, the probe fails during startup and kills the container before it's ready — forever. It looks like a broken application and it's a broken probe. startupProbe is the correct fix, since it suspends liveness until the app is up."

"kubectl logs --previous next. This is essential and easily missed: the current container has only just started, so its logs are empty or partial. The actual exception is in the previous container's output. Without the flag you look at an empty log and conclude there's nothing to see."

"From the logs, the usual .NET causes are recognisable. Configuration missing — an unbound required option, or a null connection string, which is why ValidateOnStart() is worth having so the message is explicit rather than a NullReferenceException. A dependency unreachable at startup — the database isn't accepting connections yet, or a NetworkPolicy is blocking it. A DI resolution failure, which throws at build time and is usually obvious. Or a migration failing if migrations run at startup."

"If the logs show nothing at all, that points elsewhere: the entrypoint is wrong — a mismatched DLL name, or a command that isn't in the image — or the container can't start because a mounted ConfigMap or Secret doesn't exist, which describe would have shown. Or it exits 0 immediately, which for a worker usually means the host isn't being awaited."

"If it's OOMKilled, that's a distinct path. I'd check whether the limit is simply too low, and note the .NET-specific detail that the GC sizes its heap from the container limit — so a tight limit makes the GC far more aggressive, burning CPU, and can push the process over anyway. Raising the limit sometimes improves CPU as well as stopping the kills."

"For anything I can't reproduce from logs, I'd get inside it. kubectl debug attaches an ephemeral container sharing the pod's namespaces, so I can check DNS resolution, reach the database, and inspect mounted files — even with a chiseled image that has no shell of its own. If the image does have a shell, overriding the command to sleep infinity in a copy of the pod lets me poke at it without the crash loop fighting me."

"On the environment-difference angle: if it runs locally and crash-loops in the cluster, the differences are almost always configuration, identity, or network. Different config source, a workload identity not federated to the right service account — the missing azure.workload.identity/use label is a classic — or a NetworkPolicy blocking egress. I'd check those three before suspecting the application."

"And to stop it recurring: a startup probe with a generous window, a liveness probe that checks only what a restart could fix, never a dependency — otherwise a 30-second database blip restarts every pod at once and you've caused a full outage — and configuration validation at startup so the failure message names the problem."

What they're really checking
  • Do you know describe comes first and gives the exit reason?
  • Do you know logs --previous?
  • Do you recognise a liveness probe killing a slow-starting app?
  • Do you know startupProbe is the fix?
  • Do you know the .NET GC/limit interaction for OOM?
  • Do you check config, identity and network for environment differences?
Weak answers
  • Red flag: "check the logs" and stopping there.
  • Red flag: not knowing --previous.
  • Red flag: raising the memory limit without diagnosing.
Likely follow-ups
  • Difference between startup, readiness and liveness probes?
  • How do you get a shell into an image that has none?
  • How would you confirm a NetworkPolicy is blocking you?
