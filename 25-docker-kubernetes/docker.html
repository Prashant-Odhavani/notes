Docker & Containerization

The Dockerfile is where most of the mistakes live. Layer caching and base image choice are the two things worth understanding properly.

Images and layers 🔥 Must know

The model

An image is a stack of read-only layers. Each Dockerfile instruction that changes the filesystem adds one.

A running container adds one writable layer on top. When it's removed, that layer goes with it — which is why containers are ephemeral and anything you need to keep goes in a volume or an external store.

PropertyConsequence
Layers are cached by contentAn unchanged instruction is reused, not re-run
Changing a layer invalidates every layer after itOrder your Dockerfile from least to most volatile
Layers are shared between imagesTen images on one base cost one base
Layers are additiveDeleting a file later doesn't shrink the image
Layers are pulled in parallelSmaller layers can mean faster startup on a cold node
A secret added in one layer and deleted in another is still in the image

This is the consequence of layers being additive, and it's the one that actually causes incidents.

If a Dockerfile copies a credentials file, uses it, then runs rm in a later instruction, the file is still present in the earlier layer. Anyone who can pull the image can extract it — docker save and unpack, no special tooling.

The same applies to a nuget.config containing a private feed PAT, an SSH key used to clone a dependency, or an appsettings.Production.json copied by an over-broad COPY . ..

The fixes: BuildKit secret mounts (--mount=type=secret), which make a secret available during one instruction without persisting it; multi-stage builds, where the secret stays in a stage you don't copy from; and a .dockerignore so sensitive files never enter the build context at all.

And the rule underneath: configuration is injected at runtime, never baked in. An image should be identical across environments — that's what makes it the artefact you tested.

A .NET Dockerfile worth copying 🔥 Must know

# ---------- build ----------
FROM mcr.microsoft.com/dotnet/sdk:9.0 AS build
ARG BUILD_CONFIGURATION=Release
WORKDIR /src

# 1. Copy ONLY the project files first.
#    These change rarely, so the restore layer below stays cached
#    across every source-code-only change.
COPY Directory.Packages.props Directory.Build.props nuget.config ./
COPY src/Orders.Api/Orders.Api.csproj              src/Orders.Api/
COPY src/Orders.Application/Orders.Application.csproj src/Orders.Application/
COPY src/Orders.Domain/Orders.Domain.csproj        src/Orders.Domain/

# 2. Restore. Cached unless a .csproj or lock file changed.
RUN --mount=type=cache,target=/root/.nuget/packages \
    dotnet restore src/Orders.Api/Orders.Api.csproj

# 3. NOW copy the source. This layer changes on every commit,
#    and everything above it is still cached.
COPY src/ src/

RUN --mount=type=cache,target=/root/.nuget/packages \
    dotnet publish src/Orders.Api/Orders.Api.csproj \
      -c $BUILD_CONFIGURATION -o /app/publish \
      --no-restore /p:UseAppHost=false

# ---------- runtime ----------
FROM mcr.microsoft.com/dotnet/aspnet:9.0 AS final
WORKDIR /app

# The Microsoft images ship a non-root user (uid 64198). Use it.
USER $APP_UID

# Kestrel binds 8080 by default in .NET 8+ images - no root needed for that
EXPOSE 8080
ENV ASPNETCORE_HTTP_PORTS=8080

COPY --from=build /app/publish .
ENTRYPOINT ["dotnet", "Orders.Api.dll"]
Senior signal — the restore-before-source split is the point of the whole file

The two-step copy looks like fussiness. It's the difference between a 20-second build and a three-minute one, on every single commit.

Because layers invalidate downward: if you COPY . . and then restore, any source change invalidates the copy layer, so the restore re-runs and every package is fetched again.

Copying only the .csproj files first means the restore layer is keyed on project dependencies, which change rarely. Source changes invalidate only the layers below it.

That's the same reasoning that puts apt-get install before COPY in any Dockerfile: least volatile first. The general principle is worth stating rather than just the .NET recipe.

The BuildKit --mount=type=cache on the NuGet folder is the modern addition — it persists the package cache across builds even when the layer is invalidated, which helps CI where the layer cache is often cold.

Worth mentioning as an alternative: dotnet publish /t:PublishContainer builds an image with no Dockerfile at all, handling layering, non-root and base image selection for you. For a straightforward service it's genuinely simpler, and it doesn't need a Docker daemon in CI.

Multi-stage isn't only about size — it's about what ships

A single-stage build on the SDK image gives you a ~800 MB image containing the compiler, the SDK, NuGet caches and your source code. The runtime image is well under half that.

Size matters for pull time and registry cost, but the security argument is stronger: the production container has no compiler and no source. Anyone who gets a shell in it can't build or inspect anything, and the attack surface is only what the app needs to run.

It also gives you a clean place to run tests — a stage between build and final that executes dotnet test, so a failing test fails the image build and a broken image can't be produced at all.

That's structural rather than procedural: it isn't a pipeline step someone can skip.

Chiseled images are the modern answer

Microsoft's chiseled images are Ubuntu-based and stripped to what .NET actually needs: no shell, no package manager, no root user.

Two benefits. The vulnerability surface collapses — most CVEs reported against a container image are in OS packages the app never uses, and removing them removes the findings, which is a real saving in remediation effort. And no shell means no shell to exploit; a great deal of post-compromise tooling assumes one exists.

The cost is that you can't docker exec into it to poke around, which changes how you debug. Diagnostics must come from telemetry, or from ephemeral debug containers that attach a shell alongside the pod — which is where Kubernetes' kubectl debug earns its place.

On Alpine: it's smaller, and it uses musl rather than glibc. That's mostly fine for .NET now, but native dependencies compiled against glibc can fail in ways that are unpleasant to diagnose. Chiseled gives you comparable size on a familiar libc, so it's usually the better trade.

Trimming and AOT: real gains, real constraints

ReadyToRun pre-compiles IL to native code, improving startup at the cost of a larger image. Low risk, and a sensible default for anything where cold start matters.

Trimming removes unused IL. It can break reflection-based code — some serialisers, DI conventions, EF Core patterns — and the failure appears at runtime, not build time. So it needs real testing of the trimmed artefact, not just a successful build.

Native AOT gives dramatic startup and memory improvements and the tightest constraints: no runtime code generation, no unbounded reflection, and several frameworks don't support it. It works well for minimal APIs and console tools; it's often impractical for a large MVC app with EF Core.

The honest position: ReadyToRun by default, AOT where startup genuinely dominates — a Function or a scale-to-zero service — and treat trimming as something to verify rather than enable and hope. For a long-running web service, startup time is amortised and the constraints usually aren't worth it.

.dockerignore 🟢 Beginner

**/bin/
**/obj/
**/.vs/
**/node_modules/
**/.git/
**/.env
**/appsettings.*.json      # keep environment config out of the image
**/*.user
**/TestResults/
Dockerfile*
docker-compose*
README.md
It affects correctness, not just speed

The build context is everything sent to the daemon. Without a .dockerignore that includes bin and obj, you ship local build output into the image — which can be a different configuration or target framework than the one you just built, producing genuinely confusing behaviour.

It's also a security control. Excluding .git keeps your full history out of the image. Excluding .env and appsettings.*.json keeps local secrets and connection strings out.

And it's a speed control: sending a node_modules folder or a large .git directory to the daemon on every build is wasted time before anything starts.

Worth pairing with a narrow COPY — copying specific paths rather than COPY . . — so the image contains what you intended even if the ignore file is incomplete. Belt and braces, and cheap.

Service discovery inside a Compose network

Containers on a user-defined network reach each other by service name, with Docker's embedded DNS resolving it. So the API connects to Server=sqlserver, not to an IP.

That's the same idea as a Kubernetes Service, and it's why moving from Compose to Kubernetes is less of a jump than it looks — both give a stable name in front of a moving target.

Two things to know. Port mapping is only for host access: within the network, containers use the container port regardless of what's published. Publishing 8080:8080 is for your browser, not for the other containers.

And localhost inside a container is that container. Trying to reach the host database on localhost from inside a container is the classic first-day mistake — the host is host.docker.internal on Docker Desktop.

services:
  api:
    build:
      context: .
      dockerfile: src/Orders.Api/Dockerfile
    ports: ["8080:8080"]
    environment:
      ASPNETCORE_ENVIRONMENT: Development
      ConnectionStrings__Default: "Server=sqlserver;Database=orders;User Id=sa;Password=${SA_PASSWORD};TrustServerCertificate=True"
      ConnectionStrings__Redis: "redis:6379"
    depends_on:
      sqlserver: { condition: service_healthy }   # WAIT for healthy, not just started
      redis:     { condition: service_started }

  sqlserver:
    image: mcr.microsoft.com/mssql/server:2022-latest
    environment:
      ACCEPT_EULA: "Y"
      MSSQL_SA_PASSWORD: ${SA_PASSWORD}
    ports: ["1433:1433"]
    volumes: ["sqldata:/var/opt/mssql"]
    healthcheck:
      test: ["CMD-SHELL", "/opt/mssql-tools18/bin/sqlcmd -S localhost -U sa -P \"$$MSSQL_SA_PASSWORD\" -C -Q 'SELECT 1'"]
      interval: 10s
      retries: 10
      start_period: 30s

  redis:
    image: redis:7-alpine
    ports: ["6379:6379"]

volumes:
  sqldata:
depends_on alone doesn't mean "ready"

Plain depends_on waits for the container to start, not for the service inside it to be usable. SQL Server takes 20–30 seconds to accept connections after the container is running.

So the API starts, tries to connect, fails, and — depending on your startup code — either crashes or logs a confusing error. It's the standard "works the second time you run it" symptom.

condition: service_healthy with a real health check fixes it properly, which is why the check above runs an actual query rather than checking a port.

Worth also making the application resilient to it, with connection retry on startup, since the same race exists in production during a rolling deployment or a database failover. The Compose fix makes development pleasant; retry logic makes production correct — and you want both.

Senior signal — patching containers means rebuilding, not updating

There's no apt upgrade in a running container's lifecycle. A CVE in a base image layer is fixed by rebuilding on the patched base and redeploying.

Which has a real organisational consequence: your patching cadence is your deployment cadence. A service last deployed eight months ago is running eight-month-old OS packages, whatever your vulnerability policy says.

So container security depends on being able to rebuild and redeploy routinely — meaning a reliable pipeline and a test suite you trust. Teams that deploy rarely accumulate vulnerabilities they can't practically fix, because the redeploy itself is risky.

That's why "we scan images" is only half an answer. The scan produces findings; the ability to ship resolves them. A useful framing: a scheduled rebuild of unchanged services, so patches land even when the code doesn't change.

The other half is tagging discipline. Immutable version tags — or digests — so you know exactly what's running and can roll back precisely. :latest defeats both: you can't tell what's deployed, and you can't reliably go back.

Key takeaways
  • Each instruction is a cached layer; changing one invalidates everything below.
  • Order least-volatile to most-volatile — project files and restore before source.
  • Layers are additive: a deleted secret is still in the image.
  • Use BuildKit secret mounts and a real .dockerignore.
  • Multi-stage so no compiler or source ships to production.
  • A test stage makes a broken image impossible to build.
  • Chiseled images are the best production default — no shell, no root.
  • ReadyToRun by default; AOT where startup dominates; verify trimming.
  • depends_on needs service_healthy, and the app still needs retry.
  • localhost in a container is that container.
  • Non-root, read-only root filesystem, dropped capabilities, no Docker socket.
  • Patching means rebuilding — your patch cadence is your deploy cadence.
  • Immutable tags or digests, never :latest.

Common mistakes

  • COPY . . before dotnet restore, destroying the cache on every commit.
  • Shipping the SDK image to production.
  • Secrets copied then deleted, still extractable from the layer.
  • No .dockerignore, so bin, obj, .git and local config go in.
  • Running as root when the image ships a non-root user.
  • :latest tags, so you can't tell what's deployed or roll back.
  • Connection strings baked into the image instead of injected.
  • Writing application data to the container filesystem with no volume.
  • Using localhost to reach another container.
  • Relying on depends_on without a health condition.
  • Enabling trimming without testing the trimmed output.
  • Mounting the Docker socket into a container.

Advanced

Your image is 1.2 GB and builds take six minutes. Fix both. ⭐ Senior-level
How I'd answer

"Two different problems with overlapping fixes. I'd measure first — docker history shows which layers are large, and BuildKit output shows which steps are slow and which were cached — because guessing here wastes time."

"On size, the usual causes in order."

"Shipping the SDK image. If the final stage is dotnet/sdk, that alone is most of the 1.2 GB — compiler, SDK, NuGet caches. Moving to a multi-stage build with dotnet/aspnet as the final stage typically takes it to around 220 MB. Chiseled takes it lower again, and removes the shell and package manager while it's at it."

"The build context being copied in. Without a .dockerignore, bin, obj, node_modules and .git all go into the image. A large .git directory alone can be hundreds of megabytes — and it's a security issue too, since it contains your full history."

"Files deleted in a later layer. Layers are additive, so rm in a later instruction doesn't reclaim anything — it just adds a deletion marker. Anything downloaded and cleaned up must be in the same RUN, or better, in a stage you don't copy from."

"Frontend build artefacts. If there's a Node build, the whole node_modules tree often ends up in the image when only the compiled output is needed. That's a separate build stage copying just dist."

"On build time, this is almost always cache invalidation rather than slow compilation."

"The dominant cause is COPY . . before dotnet restore. Every source change invalidates the copy layer, so restore re-runs and every package is fetched again. Splitting it — copy the .csproj files, restore, then copy source — means a typical code-only change skips restore entirely. That's usually minutes down to tens of seconds."

"Then a BuildKit cache mount on the NuGet packages folder, which persists across builds even when the layer is invalidated. That's specifically valuable in CI, where the layer cache is frequently cold and the fix above doesn't help."

"In CI I'd also check whether the layer cache exists at all. A fresh runner has none, so --cache-from pointing at the registry, or a registry-backed BuildKit cache, is what makes previous layers reusable. Optimising Dockerfile order and then throwing the cache away every build is a common wasted effort."

"Other build-time items: parallel stages, since BuildKit runs independent stages concurrently — a Node build and a .NET build don't need to be sequential. And --no-restore on publish so it doesn't restore a second time."

"On whether to reach for trimming or AOT for size — I'd be cautious. Trimming can break reflection-based code at runtime, not build time, so it needs the trimmed artefact properly tested. AOT is more constrained again. For a long-running web service the startup benefit is amortised and the image savings are usually not worth the risk. I'd take the easy 80% from multi-stage and chiseled first."

"The order I'd actually do it: multi-stage and a .dockerignore — biggest size win, near-zero risk. Reorder for caching — biggest time win, no risk. Then chiseled, then CI cache configuration. Measure after each, because the first two usually resolve most of it and the rest can be judged against effort."
