LINQ Performance & Providers

Where LINQ costs you real money: N+1 queries, work moving to the wrong machine, and allocations in hot loops.

🟡 Intermediate 🔴 Advanced 🔥 Must know
Quick revision
  • N+1 — one query for the list, then one more per item. The single most common LINQ-related performance bug.
  • Client evaluation — the provider can't translate part of your query, so it fetches everything and filters in memory.
  • Project to only the columns you need. Select into a DTO beats fetching whole entities.
  • Use AsNoTracking for read-only queries — EF stops building change-tracking state.
  • In hot loops, each LINQ operator allocates an enumerator and each lambda may allocate a closure. A for loop can be genuinely faster.
  • Order matters: filter (Where) before you sort or project, so less data moves through the pipeline.

The N+1 problem 🔥 Must know

In simple terms

You run one query to get a list, then accidentally run another query for every item in that list.

100 orders becomes 101 database round trips.

Think of it this way

You've got a shopping list with 50 items, and you drive to the shop and back once per item.

Each trip is fast. Fifty trips is your afternoon gone. The fix isn't a faster car — it's one trip.

var orders = await db.Orders.Take(100).ToListAsync();      // 1 query

foreach (var order in orders)
{
    // Lazy loading: each access hits the database again
    Console.WriteLine(order.Customer.Name);                 // 100 more queries
}
var orders = await db.Orders
    .Include(o => o.Customer)          // JOIN - fetched together
    .Take(100)
    .ToListAsync();
var summaries = await db.Orders
    .Take(100)
    .Select(o => new OrderSummary(o.Id, o.Customer.Name, o.Total))
    .ToListAsync();

The third version generates a single query selecting three columns. No entity materialisation, no change tracking, no over-fetching.

The N+1 that hides in a projection

This is the version people miss. It looks like a projection, but the inner ToList() forces a separate query per order:

var result = orders.Select(o => new
{
    o.Id,
    Lines = db.OrderLines.Where(l => l.OrderId == o.Id).ToList()   // N queries
});

If orders is already a materialised list, EF has no way to combine these. Use Include on the original query, or a single grouped query, or EF Core's AsSplitQuery() which does two queries deliberately rather than N.

How to detect it

  1. Log the SQL. In EF Core, LogTo(Console.WriteLine) in development. If you see the same query shape repeating, that's N+1.
  2. Count queries per request in telemetry. Application Insights shows dependency counts — a request making 200 SQL calls is obvious once you look.
  3. Watch for it in review. Any navigation-property access inside a loop over materialised entities is suspect.

Client evaluation and translation failures 🔴 Advanced

In simple terms

EF can only translate the C# it understands. If your Where calls something it can't turn into SQL, it can't push the filter to the database.

// IsEligible() is your own C# method. There is no SQL equivalent.
var eligible = await db.Customers
    .Where(c => IsEligible(c))       // EF Core 3.0+: throws InvalidOperationException
    .ToListAsync();
This behaviour changed — and the change was good

Before EF Core 3.0, EF would silently give up, fetch the entire table, and run your method in memory. Queries worked in development with 50 rows and collapsed in production with 5 million.

From EF Core 3.0, it throws instead. That's a much better default: a loud failure at development time beats a silent one at 3am. If you genuinely want client evaluation, you now have to ask for it with AsEnumerable(), which makes the intent visible in code review.

Three ways to fix it:

var eligible = await db.Customers
    .Where(c => c.IsActive && c.CreditScore > 600)     // becomes a WHERE clause
    .ToListAsync();
// An Expression can be translated; a Func cannot.
public static Expression<Func<Customer, bool>> IsEligible() =>
    c => c.IsActive && c.CreditScore > 600;

var eligible = await db.Customers.Where(IsEligible()).ToListAsync();
var eligible = (await db.Customers
        .Where(c => c.IsActive)        // cheap filter in SQL - cuts it to a small set
        .ToListAsync())
    .Where(c => ComplexRule(c))        // expensive C# rule on the small set
    .ToList();

Option 2 is the interesting one for interviews: it's the difference between Func<T, bool> and Expression<Func<T, bool>>, and it's the basis of the Specification pattern.

Over-fetching 🔥 Must know

The most common EF performance problem after N+1, and the easiest to fix.

// Order has 30 columns including a large Notes field.
// You need two of them.
var list = await db.Orders.ToListAsync();
var names = list.Select(o => new { o.Id, o.Total });
var names = await db.Orders
    .Select(o => new { o.Id, o.Total })      // projection happens in SQL
    .ToListAsync();

Projecting early does three things at once: less data over the wire, no entity objects allocated, and EF skips change tracking because there's no entity to track.

AsNoTracking

var orders = await db.Orders
    .AsNoTracking()                 // don't build change-tracking snapshots
    .Where(o => o.Total > 1000)
    .ToListAsync();
In simple terms

By default EF keeps a snapshot of every entity it loads, so it can work out what changed when you call SaveChanges.

If you're only reading, that snapshot is wasted work and wasted memory. AsNoTracking skips it.

It matters most on large result sets — the tracking cost scales with the number of entities. For a single-entity lookup you'll never notice.

Don't use it if you intend to update

An untracked entity isn't known to the context, so modifying it and calling SaveChanges does nothing. You'd have to attach it explicitly — at which point you may as well have tracked it.

Note that projections are untracked automatically. If you Select into a DTO, there's nothing to track, so AsNoTracking is redundant.

Operator order matters 🟡 Intermediate

var top = orders
    .OrderByDescending(o => o.Total)      // sorts all 1,000,000
    .Where(o => o.Status == Status.Paid)  // then filters
    .Take(10);
var top = orders
    .Where(o => o.Status == Status.Paid)  // cut it down first
    .OrderByDescending(o => o.Total)
    .Take(10);
Remember this

Filter, then sort, then project, then page.

Every operator processes whatever the previous one gave it — so shrink the data as early as possible.

The exception: IQueryable

Against a database, order matters much less, because EF builds one SQL statement and the query optimiser decides the actual execution order. Filtering before sorting is still good practice for readability and portability, but it isn't the performance cliff it is in memory.

In-memory LINQ has no optimiser. Every operator runs exactly as written.

Allocation costs in hot paths 🔴 Advanced 💡 Good to know

LINQ is not free. Each operator in a chain allocates an enumerator object, and each lambda that captures a variable allocates a closure.

// Called millions of times in a tight loop
public int SumMatching(int[] values, int threshold) =>
    values.Where(v => v > threshold).Sum();     // 'threshold' is captured -> closure
public int SumMatching(int[] values, int threshold)
{
    var sum = 0;
    for (var i = 0; i < values.Length; i++)
        if (values[i] > threshold) sum += values[i];
    return sum;
}
Keep this in proportion

This matters in a hot loop — millions of iterations, or a per-request path in a high-throughput service. It does not matter in a controller action that runs 100 times a second.

LINQ's readability is worth real allocations almost everywhere. Rewrite as a loop when a profiler tells you to, not on suspicion. Saying that in an interview is a better answer than "LINQ is slow, avoid it".

Key takeaways
  • N+1 is the big one. Look for navigation access inside a loop, and log your SQL in development.
  • Include fixes N+1; a projection is usually better still.
  • EF Core 3.0+ throws on untranslatable queries instead of silently fetching everything. That's a feature.
  • Expression<Func<>> can be translated; Func<> cannot.
  • Project to the columns you need. AsNoTracking for read-only entity queries.
  • Filter before sorting in memory. Against SQL, the optimiser handles it.
  • LINQ allocates. Rewrite as a loop only when a profiler says so.

Common mistakes

  • Navigation property access inside a loop — the textbook N+1.
  • .ToList() before filtering, moving the whole table into memory.
  • Fetching whole entities for a read-only list view instead of projecting.
  • AsNoTracking then trying to save — the update silently does nothing.
  • Sorting before filtering on a large in-memory collection.
  • Contains on a large list inside a loop — O(n²). Use a HashSet.
  • Assuming LINQ is always fine in a hot path — and equally, avoiding it everywhere "for performance" without measuring.

Interview questions

What is the N+1 problem, and how do you find and fix it? 🔥 Must know
How I'd answer

"It's when you run one query to fetch a list and then, without meaning to, one more query for each item in that list. Fetch 100 orders and touch order.Customer.Name in a loop and you've made 101 round trips."

"Each individual query is fast, which is why it hides in development with 20 rows and then falls over in production. The cost is dominated by round-trip latency, not by the queries themselves."

"To find it, I'd log the generated SQL — in EF Core that's LogTo in development. The signature is obvious once you look: the same query shape repeating with a different parameter. In production I'd look at dependency counts per request in Application Insights; a request making 200 SQL calls stands out immediately."

"To fix it, Include is the direct answer — it turns the related data into a join so it comes back with the original query. But usually I'd prefer a projection: Select into a DTO with just the fields I need. That's one query, only the columns I use, no entity materialisation, and no change tracking."

"One caveat with Include: if you include several collections, you get a cartesian product — the row count multiplies and you transfer far more data than you need. EF Core's AsSplitQuery() handles that by issuing one query per collection instead. So it's two or three queries by design rather than N by accident."

"Prevention-wise, I'd disable lazy loading. Lazy loading is what makes N+1 invisible — the code looks like a property access. With it off, you have to be explicit about what you're loading, and the problem stops happening silently."

What they're really checking
  • Do you know the mechanism, not just the name?
  • Can you say how you'd detect it, not just fix it?
  • Bonus: cartesian explosion and lazy loading as the root cause.
Weak answers
  • Red flag: "use Include" with no mention of detection or projections.
  • Red flag: not knowing it's about round trips rather than query cost.
Likely follow-ups
  • What's the downside of Include on two collections?
  • Should lazy loading ever be enabled?
  • How would you catch this in CI rather than in production?
Is LINQ slower than a for loop? Does it matter?
How I'd answer

"For in-memory collections, yes — measurably. Each operator in a chain allocates an enumerator, each element goes through at least one delegate call, and a lambda that captures a local allocates a closure object. A hand-written loop does none of that."

"Whether it matters depends entirely on where the code sits. In a request handler that runs a few hundred times a second over a list of twenty items, the difference is unmeasurable and I'd take the readability every time. In a loop running millions of iterations, or a per-element path in a high-throughput pipeline, it shows up clearly in a profiler and I'd rewrite it."

"So my position is: write LINQ by default, and optimise where a profiler points. I wouldn't pre-emptively write loops everywhere — that's trading a large readability cost across the whole codebase for a saving in the 1% of it that's hot."

"There are also cheap wins that cost no readability. Using .Count the property rather than .Count() the method on a list. First(predicate) rather than Where(...).First(). MinBy rather than sorting to take one item. Building a HashSet once instead of calling Contains on a list inside a loop — that last one turns an O(n²) into O(n), which is an algorithmic fix, not a micro-optimisation."

"And I'd separate this from IQueryable entirely. There, the performance question isn't allocation — it's whether the work happens in the database or in my process, and that's orders of magnitude more important than enumerator overhead."

What they're really checking
  • Do you know the actual mechanism of the overhead?
  • Do you keep it proportionate rather than cargo-culting?
  • Do you distinguish micro-optimisation from algorithmic improvement?
Weak answers
  • Red flag: "LINQ is slow, avoid it" — dogma.
  • Red flag: "it makes no difference" — it does; you just usually don't care.
Likely follow-ups
  • Where does the closure allocation come from exactly?
  • How would you benchmark this properly?
Your EF query throws "could not be translated". What's happening and what do you do? ⭐ Senior-level
How I'd answer

"It means EF walked my expression tree and hit something it can't turn into SQL — usually a call to one of my own methods, or a .NET API with no SQL equivalent."

"The important context is that this used to not throw. Before EF Core 3.0, EF would silently fetch the whole table and evaluate that part in memory. So the query worked fine in development against a small dataset and then became a full table scan in production. Throwing instead was a deliberate breaking change, and a good one — I'd much rather find out at development time."

"To fix it I'd look at what can't be translated. Usually the rule can be expressed directly in LINQ that EF understands — comparisons, string methods it maps, arithmetic. That's the best outcome because the filter stays in the database."

"If I want the rule reusable, I'd write it as an Expression<Func<T, bool>> rather than a method returning bool. An expression can be composed into the query tree and translated; a compiled delegate can't. That distinction is exactly the basis of the Specification pattern."

"If the logic genuinely can't be translated — something involving an external service, or complex C# — then I'd do it in two stages: push whatever cheap filters I can into SQL to reduce the set, materialise that, then apply the expensive rule in memory. The key is that the SQL filter has to cut the data down enough that the in-memory step is on a small set."

"What I'd avoid is reaching for AsEnumerable() as a reflex to make the error go away. That silences the compiler and reintroduces the exact full-table-scan behaviour EF Core 3 was trying to prevent."

What they're really checking
  • Do you know the EF Core 3.0 behaviour change and why it happened?
  • Do you know Expression vs Func is the lever?
  • Do you recognise AsEnumerable() as papering over it?
Likely follow-ups
  • How would you write a reusable, composable filter that EF can translate?
  • What can you do if you need a SQL function EF doesn't know about?
