LINQ In Depth

One query syntax over collections, databases and XML. The two things interviewers actually probe are when it runs and where it runs.

🟢 Beginner 🟡 Intermediate 🔥 Must know
Quick revision
  • LINQ is just extension methods that take delegates. No magic.
  • Deferred execution — building a query does nothing. It runs when you enumerate it.
  • IEnumerable runs in memory. IQueryable is translated to SQL. That one line is the most important thing on this page.
  • IQueryable works by building an expression tree — data describing your code — which a provider converts to SQL.
  • First vs Single vs FirstOrDefault: know which throws and when.
  • Casting IQueryable to IEnumerable too early is how you accidentally load an entire table into memory.

What LINQ actually is 🟢 Beginner

In simple terms

LINQ gives you one way to write "filter, transform, group, sort" that works over any source — a list, a database table, a JSON document.

It isn't a language feature. It's a set of extension methods plus some compiler sugar.

// Query syntax - looks like SQL
var q1 = from o in orders
         where o.Total > 100
         orderby o.CreatedUtc descending
         select o.Id;

// Method syntax - what the compiler turns the above into
var q2 = orders.Where(o => o.Total > 100)
               .OrderByDescending(o => o.CreatedUtc)
               .Select(o => o.Id);

Query syntax is only sugar. It's occasionally clearer for joins and let clauses; method syntax is more common and composes better. Use whichever reads better — they compile to the same thing.

Deferred execution 🔥 Must know

In simple terms

Writing a LINQ query doesn't run it. You've built a description of work to do.

It runs when something asks for the results.

Think of it this way

A LINQ query is a recipe, not a meal. Writing down "chop onions, then fry" doesn't cook anything.

The cooking starts when someone sits down to eat — and if you hand the same recipe to two people, it gets cooked twice.

var numbers = new List<int> { 1, 2, 3 };

var query = numbers.Where(n => n > 1);    // nothing has run yet

numbers.Add(4);                            // change the source AFTER building the query

Console.WriteLine(string.Join(",", query)); // 2,3,4  <- includes the new item!

The query ran at the string.Join, by which time the list had four items. This catches people out constantly.

How to remember which is which

If the method returns another IEnumerable, it's deferred — there's still more query to build.

If it returns a concrete value or collection (a number, an object, a List), it had to run to produce it.

Production trap — enumerating twice

Because the query is a recipe, enumerating it twice executes it twice:

var expensive = db.Orders.Where(o => o.Total > 1000);   // no query yet

if (expensive.Any())                       // QUERY 1
    foreach (var o in expensive) { }       // QUERY 2 - same data, fetched again
var expensive = await db.Orders.Where(o => o.Total > 1000).ToListAsync();

if (expensive.Count > 0)                   // in-memory now
    foreach (var o in expensive) { }       // no second query

Note the second version also uses .Count rather than .Any() — on a materialised list that's just reading a field.

IEnumerable vs IQueryable 🔥 Must know

In simple terms

IEnumerable<T> — the filtering happens in your process, in C#.

IQueryable<T> — the filtering is translated into SQL and happens in the database.

Think of it this way

IEnumerable is ordering everything on the menu and then picking what you want at the table. The kitchen did all the work; most of it goes in the bin.

IQueryable is telling the kitchen what you want. Only that gets cooked and carried out.

IEnumerable<T>IQueryable<T>
Where the work happensIn your process, in memoryAt the data source (usually the database)
What the lambda becomesA compiled delegate (Func<T, bool>)An expression tree (Expression<Func<T, bool>>)
Typical useLINQ to Objects — lists, arraysEF Core, any remote provider
What you pay for a mistakeCPU and memory in your appNothing — or a runtime translation error
NamespaceSystem.Linq.EnumerableSystem.Linq.Queryable

The mistake that costs the most

// AsEnumerable() switches from IQueryable to IEnumerable.
// Everything after it happens in YOUR process.
var recent = db.Orders
    .AsEnumerable()                               // SELECT * FROM Orders  (all 10 million)
    .Where(o => o.CreatedUtc > cutoff)            // filtered in C#
    .ToList();
var recent = await db.Orders
    .Where(o => o.CreatedUtc > cutoff)            // SELECT ... WHERE CreatedUtc > @cutoff
    .ToListAsync();

Same result, wildly different cost. The first version transfers every row over the network and allocates an object for each one.

Where this sneaks in

You rarely write AsEnumerable() by accident. The realistic causes are:

  • A repository method returning IEnumerable<T> instead of IQueryable<T>, so every caller's filtering happens in memory.
  • Calling .ToList() early "to make it concrete", then filtering the list.
  • A Where containing something EF can't translate — some providers then silently evaluate it client-side (EF Core 3.0+ throws instead, which is much better).

Expression trees — why IQueryable can do this 🔴 Advanced

In simple terms

A delegate is compiled code — you can run it, but you can't look inside it.

An expression tree is data describing that code — you can inspect it, which means you can translate it into something else, like SQL.

// Compiled to machine code. Runnable, opaque.
Func<Order, bool> asDelegate = o => o.Total > 100;

// Compiled to an object graph. Inspectable.
Expression<Func<Order, bool>> asExpression = o => o.Total > 100;

// You can walk the tree:
var body = (BinaryExpression)asExpression.Body;
Console.WriteLine(body.NodeType);    // GreaterThan
Console.WriteLine(body.Left);        // o.Total
Console.WriteLine(body.Right);       // 100

That inspectability is the whole trick. EF Core walks the tree, sees "greater than", "member access on Total", "constant 100", and emits WHERE [Total] > @p0.

It's also why some C# doesn't work in an EF query: if EF can't map a construct to SQL, it can't translate it. That's covered on the LINQ performance page.

The operators worth knowing well 🟡 Intermediate

Select vs SelectMany

var orders = new[]
{
    new Order { Lines = [ "a", "b" ] },
    new Order { Lines = [ "c" ] }
};

// Select: one result per order -> a sequence OF SEQUENCES
IEnumerable<string[]> nested = orders.Select(o => o.Lines);   // [["a","b"], ["c"]]

// SelectMany: flattens them into one sequence
IEnumerable<string> flat = orders.SelectMany(o => o.Lines);   // ["a","b","c"]
Remember this

Select = map. SelectMany = map and flatten.

If you find yourself writing .Select(...).SelectMany(x => x), you wanted SelectMany from the start.

First, Single, and the OrDefault variants 🔥 Must know

A frequent interview question because the difference is about intent, not just behaviour.

MethodNo matchOne matchMany matches
First()ThrowsReturns itReturns the first
FirstOrDefault()Returns null/defaultReturns itReturns the first
Single()ThrowsReturns itThrows
SingleOrDefault()Returns null/defaultReturns itThrows
In simple terms — how to choose

Use Single when more than one match would mean your data is corrupt — looking up by primary key, for example. You want it to throw.

Use First when several matches are legitimate and you just want one — the newest order, the highest bidder.

Add OrDefault when "not found" is a normal outcome you'll handle.

The performance difference ⭐ Senior-level

First can stop as soon as it finds a match. Single must keep looking to prove there isn't a second one.

Against a database, EF translates Single to TOP 2 so it can detect a duplicate — while First becomes TOP 1. A small difference, but it's a good detail to know.

GroupBy, and where it differs from SQL

var byCustomer = orders
    .GroupBy(o => o.CustomerId)
    .Select(g => new
    {
        CustomerId = g.Key,       // the grouping value
        Count      = g.Count(),   // g itself is IEnumerable<Order>
        Total      = g.Sum(o => o.Total)
    });

The key difference from SQL: LINQ's GroupBy gives you the actual grouped items, not just aggregates. In SQL you can only select the key and aggregate functions.

Common mistake with EF Core

Because LINQ GroupBy can return whole objects and SQL can't, EF has to either translate it to a GROUP BY (only if you just use the key and aggregates) or give up and do the grouping in memory.

Older EF Core versions silently fetched everything and grouped client-side. Modern versions throw a translation error instead. Either way: if you group in EF, only use the key and aggregates in the projection.

Any() vs Count() > 0

if (db.Orders.Count(o => o.CustomerId == id) > 0)   // SELECT COUNT(*) - counts every row

if (await db.Orders.AnyAsync(o => o.CustomerId == id))   // SELECT EXISTS / TOP 1

Count has to examine every matching row. Any stops at the first one. For a customer with 50,000 orders that's a real difference.

But — on an already-materialised List<T>, use .Count (the property). It's O(1); Any() sets up an enumerator.

Key takeaways
  • LINQ is extension methods taking delegates. Query syntax is sugar over method syntax.
  • Queries are recipes. They run when enumerated — and enumerating twice runs them twice.
  • Methods returning IEnumerable are deferred; methods returning a value are immediate.
  • IEnumerable = in your process. IQueryable = translated to SQL.
  • Expression trees are what make translation possible — code as inspectable data.
  • Single means "more than one is a bug". First means "give me one".
  • Any() beats Count() > 0 against a database; .Count wins on a list.

Common mistakes

  • Enumerating the same query twice and doing two database round trips.
  • .ToList() too early, so filtering happens in memory instead of SQL.
  • Returning IEnumerable<T> from a repository — callers lose the ability to compose a translated query, and may enumerate after the connection closes.
  • Count() > 0 against a database instead of Any().
  • Using Single where duplicates are legitimate — it throws in production on data that was always going to happen.
  • Modifying a collection while enumerating it — throws InvalidOperationException.
  • Assuming OrderBy is stable across providers. In memory it is; in SQL, row order without ORDER BY is undefined.

Interview questions

Basic

What's the difference between IEnumerable and IQueryable? 🔥 Must know
How I'd answer

"The short version: IEnumerable filtering happens in your process, IQueryable filtering gets translated and happens at the data source."

"The mechanism is the difference between a delegate and an expression tree. IEnumerable.Where takes a Func<T, bool> — compiled code that can only be executed. IQueryable.Where takes an Expression<Func<T, bool>> — an object graph describing the code, which a provider like EF Core can walk and turn into a SQL WHERE clause."

"Why it matters in practice: if I have ten million orders and I call AsEnumerable() before Where, I've just told the database to send me every row so I can filter them in C#. Keep it as IQueryable and it becomes a WHERE clause and I get back the handful I asked for."

"The way this actually bites in real code is a repository returning IEnumerable<T>. It looks harmless, but it means every caller's filtering runs in memory. There's a genuine trade-off there though — returning IQueryable leaks the query capability out of the data layer, so the caller can write something that doesn't translate or that keeps the connection open. I'd usually rather return a materialised result from a purpose-built method than expose IQueryable broadly."

What they're really checking
  • Do you know it's delegates vs expression trees?
  • Can you name the concrete cost?
  • Bonus: do you see the repository design tension?
Weak answers
  • Red flag: "IQueryable is for databases" with no mechanism.
  • Red flag: "IQueryable is faster" — it isn't inherently; it just moves the work.
Likely follow-ups
  • What is an expression tree?
  • What happens if EF can't translate your Where?
  • Should a repository return IQueryable?

Intermediate

What is deferred execution, and when has it caused you a problem?
How I'd answer

"Deferred execution means building a LINQ query doesn't run it. You've created a description of the work; it executes when something enumerates it — a foreach, ToList, Count, First."

"The benefit is composition and efficiency. I can build a query in several steps, add a filter conditionally, and nothing runs until the end — so only one query goes to the database, with all the filters combined. And Take(10) genuinely stops early rather than materialising everything first."

"Where it's bitten me is double enumeration. Code like if (query.Any()) foreach (var x in query) looks completely reasonable and executes the query twice. Against a database that's two round trips for the same data. The fix is to materialise once with ToList and then work with the list."

"The subtler one is capturing a variable that changes. If I build a query that closes over a loop variable and enumerate it later, I get the variable's final value, not the value when I built the query — which is really the closure-capture issue showing up through LINQ."

"And there's a lifetime version of it: returning IEnumerable from a method that opened a database connection in a using. By the time the caller enumerates, the connection is disposed. That one produces a confusing exception a long way from the cause."

What they're really checking
  • Do you know the benefit as well as the trap?
  • Have you actually hit double enumeration?
  • Bonus: the disposed-connection failure.
Likely follow-ups
  • Which LINQ methods force execution?
  • How would you build a query with optional filters?
  • What does AsNoTracking change?
First, FirstOrDefault, Single, SingleOrDefault — when do you use each?
How I'd answer

"They differ on what happens with zero matches and with many matches, and I choose based on what would mean a bug."

"Single throws if there isn't exactly one. I use it when more than one match would mean the data is corrupt — a lookup by primary key or a unique constraint. I want the exception, because silently taking the first one would hide a real problem."

"First throws only if there are none. I use it when several matches are legitimate and I genuinely want one of them — the most recent order, the highest bid — usually with an OrderBy so 'first' is deterministic."

"The OrDefault variants return null instead of throwing when there's nothing. I use those when 'not found' is a normal outcome I'm going to handle — a lookup that might legitimately miss."

"The performance nuance is that First can stop at the first match, whereas Single has to keep going to prove there isn't a second. Against a database EF translates Single to TOP 2 and First to TOP 1."

"One thing I'd flag: FirstOrDefault on a value-type sequence returns 0, not null — so you can't distinguish 'not found' from 'found a zero'. There's an overload that takes an explicit default, or use a nullable type."

What they're really checking
  • Do you choose based on intent rather than habit?
  • Do you know Single throwing is often the desired behaviour?
  • Bonus: the value-type default trap.
Weak answers
  • Red flag: "I always use FirstOrDefault because it doesn't throw."
Likely follow-ups
  • Which SQL does EF generate for each?
  • What does First without OrderBy return from a database?
