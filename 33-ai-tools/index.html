AI Tools for Engineers

Interviewers now ask about this. The answer that lands is specific about where it helps, honest about where it doesn't, and clear that you own the output.

🟡 Intermediate ⭐ Senior-level
Quick revision
  • You own the code you commit, regardless of what produced it.
  • Strongest at well-specified, verifiable work — tests, migrations, boilerplate.
  • Weakest where correctness depends on context it can't see — your domain, your constraints.
  • Confident and wrong is the failure mode, not confused and wrong.
  • Context is the main lever. Vague prompt, generic answer.
  • Review generated code harder, not less — you didn't build a mental model writing it.
  • Never paste secrets or customer data into a tool.
  • Verification has to be independent of the thing that generated the code.

The useful predictor isn't difficulty. It's whether you can cheaply tell if the output is right.

A complex EF Core query is a good candidate despite being hard, because you can read the generated SQL and check the execution plan. A three-line business rule is a poor candidate despite being trivial, because whether it's correct depends on domain knowledge the tool doesn't have — and it will produce something plausible either way.

That reframes the question. Not "is this too hard for AI?" but "if this is subtly wrong, will I find out?" If the answer is a compiler error, a failing test or a readable diff, generation is low-risk. If the answer is "a customer notices in three weeks", it isn't.

Which is also why test generation is the highest-value use and needs a caveat: tests generated from the implementation encode what the code does, including its bugs. They're excellent for covering edge cases you hadn't considered, and they don't verify intent. So generate tests from the requirement where you can, and always read what the test actually asserts.

Confident wrongness is the real risk, not obvious errors

Obviously broken output is harmless — it doesn't compile, or it's clearly nonsense, and you discard it. The dangerous output is code that looks exactly like what a competent developer would write and is subtly wrong.

Concurrency is the canonical example. A cache-aside implementation with a check-then-act race, a Lazy<T> without the right thread-safety mode, an async void in a hot path. All look idiomatic. All fail under load rather than in review.

Multi-tenancy is another. A repository method missing the tenant filter reads perfectly and returns another customer's data. Nothing about the code signals a problem.

What makes this worse than a human writing the same bug is the absence of a confidence signal. A colleague uncertain about a concurrency detail says so, or leaves a comment, or asks. Generated code arrives uniformly assured whether it's correct or invented.

So the mitigation isn't "trust it less" in general — it's knowing which categories to distrust specifically: concurrency, security boundaries, anything involving your domain invariants, and anything where a recent API changed. Those get read line by line regardless of how good they look.

Project-level instructions are worth more than better prompts

Most tools support a persistent instructions file — CLAUDE.md, Cursor rules, Copilot instructions. That's where the durable leverage is, because it applies to every request without restating it.

Worth putting in it: the target framework and language version (so you stop getting .NET Framework patterns), your architectural conventions (where handlers live, how errors are returned, which result type you use), hard constraints (every query filters by tenant; no raw SQL; async all the way), and the commands to build and test so a tool can verify its own work.

That last one is the highest-value line in the file. A tool that can run your tests can catch its own mistakes before you see them, which changes the review burden materially.

Keep it short and factual. A long document of aspirations is less useful than ten specific rules — and if a rule is important enough to state, it's usually worth enforcing with an analyzer or a test as well, so it holds regardless.

Senior signal — generated code needs more review, and here's the mechanism

The instinct is that reviewing generated code is the same as reviewing a colleague's. It's harder, for a specific reason.

When you write code yourself, you build a mental model as you go — you considered the null case, you thought about what happens on retry, you know why the lock is where it is. Reviewing your own work, you're checking against a model you already hold.

With generated code you have no such model. You're reading plausible code without the reasoning that produced it, so it's easy to accept structure you'd have questioned had you been building it.

There's a second effect worth naming: accepted code is harder to question than proposed code. Once it's in the file and compiling, the bar to rewrite it feels higher than the bar to write it differently in the first place. That's an anchoring effect and it's why "it works, ship it" is a stronger pull with generated code.

The practical response is to verify independently of the generator. Read the generated SQL rather than trusting the LINQ. Run the test and check it fails when you break the implementation — a test that passes both ways asserts nothing. Check the API against real documentation, not against a confident description of it.

And the honest test: could you explain every line to a colleague, and would you defend it in review? If not, you don't understand it well enough to be accountable for it — and you will be.

What not to paste 🔥 Must know

Know your organisation's policy, and treat generated code as code

Organisations vary enormously — some run approved enterprise tooling with contractual guarantees about training and retention; others prohibit external tools for proprietary code entirely. In an interview, saying you'd check the policy before using a tool on their codebase is a better answer than either enthusiasm or blanket refusal.

Two other things worth having a position on.

Licensing. Generated code can resemble training data. For most everyday code that's not a practical concern, and it's worth knowing the tools have filters for verbatim matches, and that your organisation may have a view on it. Don't overstate the risk; don't pretend it's zero.

Generated code is still code. It goes through the same review, the same analyzers, the same dependency scanning, the same tests. Which means the safeguards that matter are the ones you already have — and it's an argument for having them be structural: an analyzer that rejects string-concatenated SQL catches it whoever wrote it. That's more reliable than a reviewer noticing.

Senior signal — the honest position on productivity

The claims range from "no real effect" to "ten times faster". Both are unhelpful, and the calibrated view is more specific.

It's genuinely large on well-specified mechanical work: a set of DTOs and mappers, tests for existing code, a repetitive refactor across thirty files, a Bicep template you'd otherwise write from documentation.

It's modest or negative on work where the difficulty is understanding — a subtle bug in unfamiliar code, a design decision with real trade-offs, anything depending on constraints not written down anywhere. There, the time goes into comprehension, and generated code can actively cost you by producing a plausible answer that sends you down the wrong path.

There's also a cost that doesn't show up in a velocity metric: reviewing code you didn't write is slower than reviewing code you did, and if the review is skipped the cost simply moves to production.

Which is why lines of code is the wrong measure — it rewards generating more, and more code is a liability. The measures that matter are unchanged: does it work, is it maintainable, did it reach production without incident.

Saying that plainly reads as more credible than either enthusiasm or dismissal, because it shows you've actually used the tools on real work rather than formed a position about them.

Key takeaways
  • You own what you commit — the tool is not accountable.
  • The predictor is verifiability, not difficulty: "if this is wrong, will I find out?"
  • Strongest on tests, boilerplate, mechanical refactors, syntax, explanation.
  • Weakest on domain rules, concurrency, and anything version-sensitive.
  • Confident wrongness with no uncertainty signal is the real risk.
  • Tests generated from the implementation encode its bugs.
  • Context is the lever; project instruction files beat better prompts.
  • Include the build and test commands so the tool can check itself.
  • Generated code needs more review — you have no mental model of it.
  • Verify independently: read the SQL, break the implementation and confirm the test fails.
  • Never paste secrets or customer data; know the organisation's policy.
  • Analyzers and tests are the guardrail that doesn't depend on attention.
  • Don't measure lines of code — more code is a liability.

Common mistakes

  • Committing code you couldn't explain in review.
  • Accepting a large diff without checking what else changed.
  • Trusting generated tests without confirming they fail when the code breaks.
  • Not stating the framework version, then getting outdated patterns.
  • Assuming an API exists because it was named confidently.
  • Skipping concurrency review because the code looks idiomatic.
  • Losing a domain invariant — the tenant filter, the audit write.
  • Pasting a connection string or customer record into a tool.
  • Using it to avoid understanding rather than to go faster.
  • Relying on prompts instead of a project instructions file.
  • Blaming the tool for a defect you shipped.

Intermediate

How do you use AI tools in your work? 🔥 Must know
How I'd answer

"I use them daily, and I'd describe it as a fast draft plus my judgement rather than delegation. The line I hold is that I own what I commit — if it's wrong in production that's on me, not the tool."

"The way I decide what to use it for isn't difficulty, it's verifiability: if this comes back subtly wrong, will I find out cheaply?"

"Where the answer is yes, I use it heavily. Tests for existing code — including edge cases I hadn't considered. Boilerplate: DTOs, mappers, validators, Bicep templates. Mechanical refactors across many files, where the compiler verifies most of it. Fiddly syntax — regex, a KQL query, a Dockerfile. And explaining unfamiliar code, which I then check against the source."

"A complex EF Core query is a good example of hard-but-verifiable: I can read the generated SQL and look at the execution plan, so a wrong answer surfaces immediately."

"Where the answer is no, I'm much more careful. Business rules, where correctness depends on domain knowledge the tool doesn't have. Concurrency, where wrong code looks idiomatic and fails under load. Anything touching a security boundary or a multi-tenant filter — a repository method missing the tenant filter reads perfectly and returns another customer's data."

"The specific thing I watch for is confident wrongness. A colleague unsure about a concurrency detail tells you, or leaves a comment. Generated code arrives uniformly assured whether it's right or invented. So there's no signal to calibrate against, and I have to supply the scepticism myself."

"On making it useful: context matters more than prompt wording. I give it the actual code, the real error and stack trace, the framework version, and an example of the pattern we use. And I keep a project instructions file in the repository — target framework, our conventions, hard rules like 'every query filters by tenant', and the commands to build and test."

"That last part is the highest-value line, because a tool that can run the tests catches its own mistakes before I see them."

"On review, I'd say something slightly counterintuitive: I review generated code harder than my own. When I write something I build a mental model as I go — I considered the null case, I know why the lock is there. With generated code I have none of that, so I'm reading plausible code without the reasoning behind it, and it's easy to accept structure I'd have questioned while building it."

"So I verify independently of the generator: read the SQL rather than trusting the LINQ, and check a generated test actually fails when I break the implementation — because a test that passes either way asserts nothing."

"My honest position on productivity: large on well-specified mechanical work, modest or negative where the difficulty is understanding. On a subtle bug in unfamiliar code it can cost me time by producing a plausible answer that sends me down the wrong path. That's worth being clear about rather than claiming a uniform multiplier."

"And I'd check the organisation's policy before pointing any tool at their codebase — I'd never paste credentials or customer data, and I know positions differ on proprietary code."

What they're really checking
  • Do you take ownership rather than deferring to the tool?
  • Can you distinguish where it helps from where it doesn't, with reasons?
  • Do you know confident wrongness is the failure mode?
  • Do you review generated code more carefully, and can you say why?
  • Are you calibrated about productivity rather than evangelical?
  • Do you raise data handling and policy?
Weak answers
  • Red flag: "it writes most of my code" with no review process.
  • Red flag: refusing to use them, with no reasoning.
  • Red flag: claiming a large uniform productivity gain.
Likely follow-ups
  • Tell me about a time it gave you something wrong.
  • How do you stop juniors using it instead of learning?
  • What's in your project instructions file?

Advanced

A junior's pull request is mostly generated and they can't explain it. What do you do? ⭐ Senior-level
How I'd answer

"I'd separate the code from the capability, because they need different responses and conflating them is how this goes badly."

"On the pull request, my position is simple and it isn't about AI: if you can't explain it, it isn't ready. That's true of code copied from Stack Overflow, or from another part of the codebase, or generated. The standard is that the author understands what they're asking me to be responsible for maintaining."

"So I wouldn't reject it — I'd go through it with them. Pick the parts that matter and ask what they do: 'what happens if two requests hit this at once?', 'why is the lock here?', 'what does this return when the list is empty?'. That's a normal review conversation, and it usually surfaces the real problems quickly — because the questions you'd naturally ask are exactly the ones generated code tends to get wrong."

"I'd be careful about tone. The tool isn't the problem — plenty of good engineers use it heavily, including me. The problem is shipping something you can't stand behind, and framing it as 'you used AI' rather than 'you can't explain this' teaches the wrong lesson and makes them hide it next time."

"On the capability, this is the part I'd actually worry about. There's a real risk that fluent output substitutes for the struggle that builds understanding. Debugging something hard, being stuck, reading the framework source — that's how you develop the judgement to know when generated code is wrong. Skip it and you're permanently dependent on something that's confidently wrong part of the time."

"So I'd talk about how to use it rather than whether. Something like: use it to explain things and to check your work freely — that accelerates learning. Be more cautious about using it to produce code in areas you're still learning, because you can't yet evaluate the output. And always read what it gives you well enough to modify it, not just well enough to run it."

"I'd also make it concrete with an example. Show them a case where it produces something plausible and wrong — a cache-aside implementation with a check-then-act race is ideal, because it looks completely idiomatic and fails under load. That lands better than a general warning, because it demonstrates that 'looks right' and 'is right' are genuinely different."

"Then the systemic part, which is where I'd put most of the effort: if a reviewer's attention is the only thing catching this, we'll miss it. So I'd want the guardrails to be structural."

"Analyzers that reject string-concatenated SQL. An architecture test that fails if a repository method doesn't apply the tenant filter. Mutation testing, so a test suite that asserts nothing shows up as a number rather than as a reviewer's hunch. Those catch the problem regardless of who or what wrote the code — which is the same principle as branch protection over asking people not to force-push."

"And a project instructions file in the repository encoding our conventions and constraints, so the tool's default output is closer to correct for everyone. That's a cheap fix that improves the baseline rather than relying on each person prompting well."

"The framing I'd land on: the review standard hasn't changed, and the way it gets violated has. It used to be someone not thinking carefully. Now it can be someone accepting something that reads better than their own work would. Same bar, different failure mode — and the response is better automated enforcement plus honest conversations, not a policy about tools."

What they're really checking
  • Do you hold the same standard without making it about the tool?
  • Do you coach rather than reject?
  • Do you distinguish learning uses from producing uses?
  • Do you make it concrete with a real failure mode?
  • Do you push toward structural enforcement over reviewer attention?
Weak answers
  • Red flag: banning AI tools.
  • Red flag: approving it because it works.
  • Red flag: making it about the tool rather than accountability.
Likely follow-ups
  • Which guardrails would you add first?
  • How do you tell a good use from a bad one in review?
  • Would your answer differ for a senior engineer?
