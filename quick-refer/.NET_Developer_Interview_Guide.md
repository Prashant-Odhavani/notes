# .NET Developer (5–6 Years) — Structured Interview Guide

## How to Use This Guide
- Ask questions roughly in order: Basic → Intermediate → Advanced, per topic.
- Compare the candidate's answer to "Expected Answer." You don't need a word-for-word match — look for the *reasoning*.
- Use "What to Look For" and "Red Flags" to judge depth, not just correctness.
- If the candidate answers well, ask one of the follow-ups to probe deeper.
- Score each topic using the 1–5 scale at the end of that section.
- A candidate with genuine 5–6 years of experience should comfortably clear Basic, mostly clear Intermediate, and get *some* Advanced questions right with reasonable reasoning — even if not perfect. Struggling badly at Basic/Intermediate level is the real warning sign, not missing one Advanced question.

## Topic 1: Unit Testing (xUnit / NUnit / MSTest)

### Basic

**Q1. What is the purpose of a unit test, and what does "Arrange, Act, Assert" mean?**
- *Expected Answer:* A unit test verifies that a small, isolated piece of code (usually a method) behaves as expected. Arrange = set up inputs/dependencies/mocks; Act = call the method under test; Assert = verify the result matches expectations.
- *Example:*
```csharp
[Fact]
public void Add_TwoNumbers_ReturnsSum()
{
    // Arrange
    var calculator = new Calculator();
    // Act
    var result = calculator.Add(2, 3);
    // Assert
    Assert.Equal(5, result);
}
```
- *What to Look For:* Clear separation of the three steps, understanding that tests should be independent and repeatable.
- *Red Flags:* Doesn't know AAA at all; thinks unit tests test the whole application end-to-end.
- *Follow-up:* "Why is it a problem if Arrange, Act, and Assert are all mixed together in one test?"
- *Difficulty:* Basic

**Q2. What's the difference between `[Fact]` and `[Theory]` in xUnit (or the NUnit/MSTest equivalents)?**
- *Expected Answer:* `[Fact]` is a test with no parameters — runs once. `[Theory]` with `[InlineData]` (or NUnit's `[TestCase]`, MSTest's `[DataRow]`) runs the same test logic multiple times with different input data — used for parameterized tests.
- *Example:*
```csharp
[Theory]
[InlineData(2, 3, 5)]
[InlineData(-1, 1, 0)]
public void Add_ReturnsExpectedSum(int a, int b, int expected)
{
    Assert.Equal(expected, new Calculator().Add(a, b));
}
```
- *What to Look For:* Recognizes parameterized testing reduces duplication.
- *Red Flags:* Has never used parameterized tests despite years of experience.
- *Follow-up:* "When would you prefer `[MemberData]` over `[InlineData]`?"
- *Difficulty:* Basic

**Q3. What is a mock, and why do we use mocking libraries like Moq?**
- *Expected Answer:* A mock is a fake implementation of a dependency (e.g., a repository or external service) used to isolate the unit under test, control its behavior, and verify interactions without hitting real databases/APIs.
- *Example:*
```csharp
var mockRepo = new Mock<IUserRepository>();
mockRepo.Setup(r => r.GetById(1)).Returns(new User { Id = 1, Name = "Test" });
```
- *What to Look For:* Understands mocking is about isolation, not just "faking data."
- *Red Flags:* Confuses mocking with using a real test database.
- *Follow-up:* "How would you verify that a method was called exactly once on a mock?"
- *Difficulty:* Basic

### Intermediate

**Q4. What's the difference between a Mock, a Stub, and a Fake?**
- *Expected Answer:* A **Stub** returns canned/predefined data with no behavior verification. A **Mock** is used to verify interactions (e.g., "was this method called with these arguments"). A **Fake** is a working, simplified implementation (e.g., an in-memory database) that behaves like the real thing but isn't production-ready.
- *What to Look For:* Can articulate the distinction with examples, not just definitions.
- *Red Flags:* Uses the three terms interchangeably with no distinction, or has never heard of "Fake."
- *Follow-up:* "Can you give an example of when you'd choose a Fake over a Mock?"
- *Difficulty:* Intermediate

**Q5. How do you test a method that depends on `DateTime.Now` or other non-deterministic values?**
- *Expected Answer:* Abstract the dependency behind an interface (e.g., `IDateTimeProvider` or `IClock`) and inject it, so tests can control the returned value. Avoid calling `DateTime.Now` directly inside business logic.
- *Example:*
```csharp
public interface IClock { DateTime Now { get; } }
```
- *What to Look For:* Recognizes the general principle: anything non-deterministic (time, random, GUIDs, external calls) should be abstracted for testability.
- *Red Flags:* Says "you just can't test that" or suggests `Thread.Sleep` hacks.
- *Follow-up:* "What other non-deterministic things commonly cause testing problems?"
- *Difficulty:* Intermediate

**Q6. How do you test an async method, and what mistakes have you seen developers make when unit testing async code?**
- *Expected Answer:* Test methods should be `async Task` (not `async void`), and `await` the method under test. Common mistakes: using `.Result` or `.Wait()` (can deadlock), forgetting to await inside the test (causing false positives), not testing cancellation or exception paths.
- *Example:*
```csharp
[Fact]
public async Task GetUserAsync_ReturnsUser()
{
    var result = await _service.GetUserAsync(1);
    Assert.NotNull(result);
}
```
- *What to Look For:* Awareness of deadlock risks and false-positive tests.
- *Red Flags:* Doesn't know async tests need to be awaited properly.
- *Follow-up:* "What happens if you use `.Result` in a unit test — could it hang?"
- *Difficulty:* Intermediate

**Q7. How do you test that a service correctly throws an exception under certain conditions?**
- *Expected Answer:* Use `Assert.Throws<T>()` (or `Assert.ThrowsAsync<T>()` for async) and assert on the exception type and optionally the message.
- *Example:*
```csharp
var ex = await Assert.ThrowsAsync<ArgumentException>(() => service.Process(null));
Assert.Equal("Input cannot be null", ex.Message);
```
- *What to Look For:* Knows the correct assertion pattern, and that testing exception *type* alone is often not enough for meaningful coverage.
- *Red Flags:* Wraps code in try/catch and manually fails the test — a sign of unfamiliarity with the framework.
- *Follow-up:* "Would you assert on the exact message text? Why or why not?"
- *Difficulty:* Intermediate

### Advanced

**Q8. How would you structure unit tests for a Controller/Service/Repository layered application? What do you actually mock at each layer?**
- *Expected Answer:* For Controllers — mock the service layer, test HTTP-related concerns (status codes, model validation, routing). For Services — mock repositories/external dependencies, test business logic. For Repositories — typically use integration tests against an in-memory or test database rather than unit tests, since their job is to talk to real infrastructure.
- *What to Look For:* Understands *what* belongs in a unit test vs. integration test, not just "mock everything."
- *Red Flags:* Tries to unit test repositories by mocking the DbContext extensively, or mocks nothing and hits a real database in "unit" tests.
- *Follow-up:* "Where's the line between a unit test and an integration test for you?"
- *Difficulty:* Advanced

**Q9. What makes a test suite "brittle," and how do you avoid writing brittle tests?**
- *Expected Answer:* Brittle tests break when implementation details change even though behavior is correct — often caused by over-specifying mock interactions, testing private methods indirectly, or asserting on exact internal structure. Fix: test behavior/outcomes, not implementation; avoid over-mocking; keep tests focused on one concern.
- *What to Look For:* Real experience maintaining test suites over time, not just theory.
- *Red Flags:* Has never experienced test suites becoming a maintenance burden.
- *Follow-up:* "Tell me about a time a refactor broke a lot of tests even though behavior didn't change — what did you learn?"
- *Difficulty:* Advanced

**Q10. Scenario: Your CI pipeline shows 95% code coverage, but bugs keep reaching production. What could be going wrong?**
- *Expected Answer:* High coverage doesn't mean good tests — tests may not assert meaningful outcomes (e.g., just calling a method without checking results), edge cases/error paths might be untested, or tests may be tightly coupled to implementation and give false confidence. Coverage is a proxy metric, not a quality metric.
- *What to Look For:* Critical thinking about metrics vs. real quality.
- *Red Flags:* Believes high coverage automatically equals good quality.
- *Follow-up:* "How would you assess whether a test suite is actually good, beyond coverage %?"
- *Difficulty:* Advanced

**Q11. What's the difference between xUnit, NUnit, and MSTest in practice, and does it matter which one a team uses?**
- *Expected Answer:* Functionally similar; differences are mostly syntax/attributes (`[Fact]`/`[Theory]` vs `[Test]`/`[TestCase]` vs `[TestMethod]`/`[DataRow]`), test lifecycle management (xUnit creates a new class instance per test by default; NUnit/MSTest share instance with setup/teardown attributes), and ecosystem/tooling support. It matters less which one you pick and more that the team is consistent and understands the chosen framework's lifecycle behavior.
- *What to Look For:* Awareness that xUnit's "new instance per test" model avoids shared-state bugs common in other frameworks.
- *Red Flags:* Claims one framework is "clearly better" with no substantive reasoning, or has only ever used one and doesn't know any differences exist.
- *Follow-up:* "How does xUnit handle test setup/teardown differently from NUnit?"
- *Difficulty:* Advanced

### Topic 1 Scoring Guide
- **1/5:** Doesn't know AAA pattern or what mocking is for.
- **2/5:** Can write a basic test but has never mocked dependencies or tested async/exceptions.
- **3/5:** Comfortable with mocking, parameterized tests, async testing — solid day-to-day tester.
- **4/5:** Understands test isolation trade-offs, layered testing strategy, brittle test causes.
- **5/5:** Can critique test suite quality, discuss coverage pitfalls, and reason about test architecture across a large codebase.
- **Expected for 5–6 yrs:** Should reliably hit 3/5, often 4/5.

## Topic 2: HTML & CSS

### Basic

**Q1. What's the difference between a `<div>` and a semantic element like `<section>` or `<article>`? Why does semantic HTML matter?**
- *Expected Answer:* `<div>` has no semantic meaning — it's a generic container. Semantic elements (`<header>`, `<nav>`, `<main>`, `<article>`, `<footer>`) convey meaning about content structure, improving accessibility (screen readers), SEO, and code readability.
- *What to Look For:* Mentions accessibility/SEO, not just "it looks the same."
- *Red Flags:* Thinks semantic HTML is purely cosmetic or unnecessary.
- *Follow-up:* "How does a screen reader benefit from semantic tags specifically?"
- *Difficulty:* Basic

**Q2. Explain the CSS box model.**
- *Expected Answer:* Every element is a box made of content, padding, border, and margin (from inside out). `box-sizing: border-box` makes width/height include padding and border; default `content-box` doesn't.
- *What to Look For:* Mentions `box-sizing` and why it matters practically (avoiding layout surprises).
- *Red Flags:* Doesn't know what `box-sizing` does.
- *Follow-up:* "Why do many CSS resets set `box-sizing: border-box` globally?"
- *Difficulty:* Basic

**Q3. What is CSS specificity, and how is it calculated?**
- *Expected Answer:* Determines which rule wins when multiple rules target the same element. Roughly: inline styles > IDs > classes/attributes/pseudo-classes > element selectors. `!important` overrides normal specificity.
- *What to Look For:* Can roughly explain the hierarchy without needing exact point values memorized.
- *Red Flags:* Has no concept of why some CSS rules "don't apply" despite being written.
- *Follow-up:* "Why is overusing `!important` considered bad practice?"
- *Difficulty:* Basic

### Intermediate

**Q4. What's the difference between Flexbox and Grid, and when would you choose one over the other?**
- *Expected Answer:* Flexbox is one-dimensional (row OR column) — great for aligning items in a line (navbars, toolbars). Grid is two-dimensional (rows AND columns) — better for overall page/component layout.
- *Example:*
```css
.container { display: flex; justify-content: space-between; align-items: center; }
```
- *What to Look For:* Practical reasoning about when to pick each, not just definitions.
- *Red Flags:* Has never used Grid, or thinks they're fully interchangeable.
- *Follow-up:* "How would you center a div both vertically and horizontally using Flexbox?"
- *Difficulty:* Intermediate

**Q5. How does responsive design work with media queries? Walk me through a mobile-first approach.**
- *Expected Answer:* Mobile-first means writing base styles for small screens, then using `min-width` media queries to add complexity for larger screens. Reduces overrides compared to desktop-first (`max-width`) approaches.
- *Example:*
```css
.card { width: 100%; }
@media (min-width: 768px) { .card { width: 50%; } }
```
- *What to Look For:* Understands the rationale for mobile-first, not just syntax.
- *Red Flags:* Doesn't know the difference between `min-width` and `max-width` queries.
- *Follow-up:* "What breakpoints do you typically use, and why?"
- *Difficulty:* Intermediate

**Q6. What's a common layout problem you've run into (e.g., collapsing margins, overflow issues, z-index stacking) and how did you solve it?**
- *Expected Answer:* Open-ended — looking for a real story. E.g., collapsing margins between adjacent block elements solved with padding or a BFC (`overflow: hidden` / flex container); z-index issues from unexpected stacking contexts solved by understanding `position` + `z-index` combos.
- *What to Look For:* A genuine, specific past experience, not generic textbook description.
- *Red Flags:* Can't recall any real layout bug they've debugged.
- *Follow-up:* "What creates a new stacking context in CSS?"
- *Difficulty:* Intermediate

### Advanced

**Q7. Scenario: A page looks correct on desktop but breaks completely on mobile Safari — text overflows and buttons are unclickable. How would you debug it?**
- *Expected Answer:* Check viewport meta tag, inspect via remote debugging (Safari Web Inspector or Chrome device emulation), look for fixed-width elements not using responsive units, check `overflow`/`flex-wrap`, look for `100vh` issues on iOS Safari (address bar affecting viewport height), test touch target sizes and z-index for clickability.
- *What to Look For:* Systematic debugging approach, awareness of Safari-specific quirks.
- *Red Flags:* Only suggests "add more CSS" without a diagnostic process.
- *Follow-up:* "Why does `100vh` behave oddly on mobile Safari specifically?"
- *Difficulty:* Advanced

**Q8. How would you approach making a complex data table accessible (keyboard navigable, screen-reader friendly)?**
- *Expected Answer:* Use proper `<table>`, `<thead>`, `<th scope="col/row">` semantics, ARIA roles only when native HTML isn't sufficient, ensure keyboard focus order is logical, provide captions/labels, test with a screen reader.
- *What to Look For:* Knows native semantics come before ARIA ("no ARIA is better than bad ARIA").
- *Red Flags:* Suggests wrapping everything in `<div>`s with ARIA roles instead of using native elements.
- *Follow-up:* "When would you actually need ARIA roles vs. relying on native HTML?"
- *Difficulty:* Advanced

### Topic 2 Scoring Guide
- **1/5:** No grasp of box model or specificity.
- **2/5:** Can write basic layouts but struggles with Flexbox/Grid or responsive design.
- **3/5:** Comfortable building responsive layouts with Flexbox/Grid, understands specificity.
- **4/5:** Debugs real cross-browser/responsive issues, understands accessibility basics.
- **5/5:** Deep accessibility knowledge, cross-browser quirks, performance-aware CSS.
- **Expected for 5–6 yrs (if front-end adjacent):** 3/5–4/5. Note: for a primarily back-end .NET dev, 2/5–3/5 is acceptable — judge in context of their role.

## Topic 3: JavaScript & jQuery

### Basic

**Q1. What's the difference between `var`, `let`, and `const`?**
- *Expected Answer:* `var` is function-scoped and hoisted (initialized as `undefined`); `let`/`const` are block-scoped and live in a "temporal dead zone" until declared. `const` cannot be reassigned (but object/array contents can still be mutated).
- *What to Look For:* Mentions scoping differences and the temporal dead zone, not just "const can't change."
- *Red Flags:* Thinks `const` makes objects immutable.
- *Follow-up:* "Can you mutate a `const` array? Why or why not?"
- *Difficulty:* Basic

**Q2. What is a closure? Give an example.**
- *Expected Answer:* A function that "remembers" variables from its enclosing scope even after that scope has finished executing.
- *Example:*
```javascript
function counter() {
  let count = 0;
  return () => ++count;
}
const increment = counter();
increment(); // 1
increment(); // 2
```
- *What to Look For:* Can explain *why* it works (lexical scoping), and give a practical use case (e.g., private state, event handlers).
- *Red Flags:* Can't produce any working example.
- *Follow-up:* "Where have you used closures in real code — maybe in event handlers or React hooks?"
- *Difficulty:* Basic

**Q3. What's the difference between `==` and `===`?**
- *Expected Answer:* `==` performs type coercion before comparing; `===` compares value and type without coercion. `===` is generally preferred to avoid unexpected bugs.
- *What to Look For:* Can give an example of coercion surprises (e.g., `'' == 0` is `true`).
- *Red Flags:* Doesn't know coercion exists.
- *Follow-up:* "Give me an example where `==` produces a surprising result."
- *Difficulty:* Basic

### Intermediate

**Q4. Explain the difference between Promises and async/await. Are they different things?**
- *Expected Answer:* async/await is syntactic sugar over Promises — it makes asynchronous code read like synchronous code. Under the hood, an `async` function always returns a Promise, and `await` pauses execution until the Promise resolves/rejects.
- *Example:*
```javascript
async function getUser(id) {
  try {
    const res = await fetch(`/api/users/${id}`);
    return await res.json();
  } catch (err) {
    console.error(err);
  }
}
```
- *What to Look For:* Understands they're not fundamentally different, just different syntax; knows error handling differs (`.catch()` vs `try/catch`).
- *Red Flags:* Thinks async/await is a completely separate concurrency model from Promises.
- *Follow-up:* "How would you run multiple async operations in parallel instead of sequentially?"
- *Difficulty:* Intermediate

**Q5. What is event bubbling and event delegation? Why is delegation useful?**
- *Expected Answer:* Bubbling: an event fires on the target element and then "bubbles up" through its ancestors. Delegation: attaching a single event listener to a parent element to handle events from its children (using `event.target`), useful for dynamically added elements and performance (fewer listeners).
- *Example:*
```javascript
document.getElementById('list').addEventListener('click', (e) => {
  if (e.target.matches('li')) console.log(e.target.textContent);
});
```
- *What to Look For:* Practical understanding of why delegation matters for dynamic content.
- *Red Flags:* Doesn't know what bubbling is.
- *Follow-up:* "How would you stop an event from bubbling further?"
- *Difficulty:* Intermediate

**Q6. What is hoisting, and how does it affect `var` vs `let`/`const` vs function declarations?**
- *Expected Answer:* Declarations are moved to the top of their scope during compilation. `var` is hoisted and initialized as `undefined`; `let`/`const` are hoisted but not initialized (temporal dead zone — accessing before declaration throws); function declarations are fully hoisted (usable before their definition in code); function expressions are not.
- *What to Look For:* Distinguishes behavior across all these cases.
- *Red Flags:* Thinks nothing is hoisted, or that everything behaves the same way.
- *Follow-up:* "Why does accessing a `let` variable before its declaration throw an error instead of returning `undefined`?"
- *Difficulty:* Intermediate

### Advanced

**Q7. Scenario: A page has a memory leak — after navigating between views many times, the browser tab's memory keeps growing. What JavaScript patterns commonly cause this, and how would you investigate?**
- *Expected Answer:* Common causes: event listeners not removed on cleanup, timers (`setInterval`) not cleared, closures holding references to large objects/DOM nodes, detached DOM nodes still referenced in JS. Investigate using Chrome DevTools Memory tab — take heap snapshots before/after navigation and compare retained objects.
- *What to Look For:* Concrete debugging methodology (heap snapshots, detached nodes), not just "check for leaks."
- *Red Flags:* No idea how to use browser dev tools for memory profiling.
- *Follow-up:* "What's a 'detached DOM node' and why does it leak memory?"
- *Difficulty:* Advanced

**Q8. How does the JavaScript event loop work — what's the difference between the microtask queue and the macrotask (callback) queue?**
- *Expected Answer:* JS is single-threaded; the event loop processes the call stack, then microtasks (Promise callbacks, `queueMicrotask`) fully drain before moving to the next macrotask (setTimeout, I/O, UI rendering). This explains why `Promise.resolve().then()` runs before a `setTimeout(fn, 0)`.
- *What to Look For:* Can explain ordering with an example, understands why this matters for perceived performance/bugs.
- *Red Flags:* Confuses "asynchronous" with "multi-threaded."
- *Follow-up:* "What would print first: a `setTimeout(fn, 0)` or a `Promise.resolve().then(fn)`? Why?"
- *Difficulty:* Advanced

**Q9. (jQuery-specific) In a codebase mixing jQuery and modern JS/frameworks, what problems have you seen, and how do you avoid direct DOM manipulation conflicts?**
- *Expected Answer:* jQuery directly manipulating the DOM can conflict with framework-managed DOM (e.g., React/Angular re-rendering and overwriting jQuery's changes, or vice versa causing "detached" elements or duplicate event handlers). Solution: avoid mixing where possible, isolate jQuery to legacy sections, or wrap third-party jQuery plugins carefully within framework lifecycle hooks.
- *What to Look For:* Real experience with legacy/hybrid codebases.
- *Red Flags:* Has never encountered or considered this problem despite claiming jQuery experience.
- *Follow-up:* "How would you migrate a page gradually from jQuery to a modern framework?"
- *Difficulty:* Advanced

### Topic 3 Scoring Guide
- **1/5:** No understanding of closures, scope, or async basics.
- **2/5:** Knows syntax but can't explain hoisting, closures, or event loop reasoning.
- **3/5:** Solid with Promises/async-await, closures, event delegation.
- **4/5:** Can debug memory leaks, reason about event loop ordering.
- **5/5:** Deep JS internals knowledge, performance-aware, comfortable in legacy/hybrid codebases.
- **Expected for 5–6 yrs:** 3/5–4/5.

## Topic 4: Angular

### Basic

**Q1. What's the difference between a Component and a Module in Angular?**
- *Expected Answer:* A Component controls a piece of the UI (template + logic + styles). A Module (`NgModule`, or standalone components in newer Angular) groups related components/services/directives together and manages dependency injection scope and what's available to the app.
- *What to Look For:* Understands modules as organizational/DI boundaries, not just "another file."
- *Red Flags:* Doesn't know what a module is for at all.
- *Follow-up:* "Have you worked with standalone components (no NgModule)? How does that change things?"
- *Difficulty:* Basic

**Q2. Explain the difference between `@Input()` and `@Output()`.**
- *Expected Answer:* `@Input()` passes data from a parent component into a child component. `@Output()` (paired with `EventEmitter`) lets a child component emit events/data up to the parent.
- *Example:*
```typescript
@Input() userName: string;
@Output() userSelected = new EventEmitter<User>();
```
- *What to Look For:* Clear grasp of unidirectional data flow (parent-to-child props, child-to-parent events).
- *Red Flags:* Confuses direction of data flow.
- *Follow-up:* "How would a component communicate with a sibling component that isn't a direct parent/child?"
- *Difficulty:* Basic

**Q3. What is Dependency Injection in Angular, and why use it?**
- *Expected Answer:* Angular's DI system provides services/dependencies to components/other services automatically via constructor injection, rather than components creating their own dependencies. Improves testability, reusability, and separation of concerns.
- *Example:*
```typescript
constructor(private userService: UserService) {}
```
- *What to Look For:* Connects DI to testability (can inject mocks in tests).
- *Red Flags:* Manually instantiates services with `new` inside components.
- *Follow-up:* "What's the difference between providing a service at the root level vs. a component level?"
- *Difficulty:* Basic

### Intermediate

**Q4. What are Angular lifecycle hooks? Name a few and explain when you'd use `ngOnInit` vs the constructor.**
- *Expected Answer:* Hooks: `ngOnChanges`, `ngOnInit`, `ngDoCheck`, `ngAfterViewInit`, `ngOnDestroy`, etc. Constructor is for basic class setup/DI only; `ngOnInit` runs after Angular has set up input bindings — the right place for initialization logic that depends on `@Input()` values or triggering API calls.
- *What to Look For:* Knows *why* to separate constructor logic from `ngOnInit`.
- *Red Flags:* Puts all initialization logic in the constructor.
- *Follow-up:* "Why is `ngOnDestroy` important, and what do you typically clean up there?"
- *Difficulty:* Intermediate

**Q5. What's the difference between Template-driven forms and Reactive forms? When would you choose one over the other?**
- *Expected Answer:* Template-driven forms use directives in the HTML template (`ngModel`) with logic mostly declared in markup — simpler for basic forms. Reactive forms are defined programmatically in the component class (`FormGroup`, `FormControl`) — better for complex validation, dynamic forms, and easier unit testing.
- *What to Look For:* Practical reasoning, not just definitions.
- *Red Flags:* Has only used one and can't articulate any trade-off.
- *Follow-up:* "How would you add a custom validator to a Reactive form?"
- *Difficulty:* Intermediate

**Q6. Explain Observables and how RxJS operators like `map`, `switchMap`, and `mergeMap` differ.**
- *Expected Answer:* Observables represent streams of async data over time (vs. Promises which resolve once). `map` transforms emitted values. `switchMap` cancels the previous inner observable when a new value arrives (good for search-as-you-type/cancel stale HTTP requests). `mergeMap` runs all inner observables concurrently without cancelling.
- *Example:*
```typescript
this.searchTerm$.pipe(
  debounceTime(300),
  switchMap(term => this.api.search(term))
).subscribe(results => this.results = results);
```
- *What to Look For:* Correctly distinguishes `switchMap` from `mergeMap`/`concatMap` with a real use case.
- *Red Flags:* Uses `subscribe()` everywhere instead of operators, or can't explain the difference between any of the "MapOperators."
- *Follow-up:* "What's a common bug caused by not unsubscribing from an Observable?"
- *Difficulty:* Intermediate

**Q7. What are Angular route guards, and what are the different types?**
- *Expected Answer:* Guards control navigation: `CanActivate` (can user access this route), `CanDeactivate` (confirm leaving a route, e.g., unsaved changes), `Resolve` (pre-fetch data before activating a route), `CanLoad`/`CanMatch` (control lazy-loaded module loading).
- *What to Look For:* Knows practical use cases (auth guards, unsaved-changes prompts).
- *Red Flags:* Has never implemented any route guard despite Angular experience.
- *Follow-up:* "How would you implement an authentication guard that redirects unauthenticated users to a login page?"
- *Difficulty:* Intermediate

### Advanced

**Q8. Explain Angular's change detection mechanism. What's the difference between default and `OnPush` change detection strategy?**
- *Expected Answer:* Default: Angular checks the entire component tree on any async event (checking for changes via Zone.js patches). `OnPush`: component only re-checks when its `@Input()` references change (by reference, not deep equality), an event originates from within it, or it's manually marked dirty — significantly improves performance in large apps.
- *What to Look For:* Understands reference equality is key to `OnPush` working correctly (immutable data patterns).
- *Red Flags:* Has never used `OnPush` or doesn't understand why mutating an object in place wouldn't trigger it.
- *Follow-up:* "If you're using OnPush and update an array item in place with `.push()`, why might the UI not update?"
- *Difficulty:* Advanced

**Q9. Scenario: Your Angular app has grown to 50+ modules and initial load time has become slow. How would you improve it?**
- *Expected Answer:* Lazy load feature modules/routes, use `OnPush` change detection broadly, apply preloading strategies for likely-next routes, use standalone components with fine-grained imports, analyze bundle size with `source-map-explorer`/Angular's build stats, tree-shake unused code, defer non-critical third-party libraries.
- *What to Look For:* Multiple concrete strategies, not just "lazy load everything."
- *Red Flags:* Only one shallow answer, no mention of measuring/profiling before optimizing.
- *Follow-up:* "How would you measure where the time is actually going before optimizing?"
- *Difficulty:* Advanced

**Q10. How would you implement authentication/authorization in an Angular app talking to a .NET API — covering token storage, refresh, and route protection?**

## Topic 6: SOLID Principles

For each principle: simple explanation, bad example, improved example, interview question, real-world scenario.

### S — Single Responsibility Principle
- *Explanation:* A class should have only one reason to change — one job/responsibility.
- *Bad Example:*
```csharp
class Invoice {
    public void CalculateTotal() { /* ... */ }
    public void SaveToDatabase() { /* ... */ }
    public void SendEmailReceipt() { /* ... */ }
}
```
- *Improved Example:* Split into `Invoice` (calculation), `InvoiceRepository` (persistence), `InvoiceNotifier` (email).
- *Interview Question:* "What's wrong with a class that both calculates business logic and sends emails? How would you fix it?"
- *Real-World Scenario:* "You have an `OrderService` class that validates orders, saves to the DB, calls a payment gateway, and logs everything. How would you refactor it, and why?"

### O — Open/Closed Principle
- *Explanation:* Classes should be open for extension but closed for modification — add new behavior without changing existing, tested code.
- *Bad Example:*
```csharp
public decimal CalculateDiscount(string customerType) {
    if (customerType == "Regular") return 0;
    if (customerType == "Premium") return 0.1m;
    // adding a new type means modifying this method again
}
```
- *Improved Example:* Use polymorphism/strategy pattern — an `IDiscountStrategy` interface with implementations per customer type, injected or resolved via a factory.
- *Interview Question:* "Every time we add a new customer type, we have to modify this if/else chain and re-test the whole method. How would you redesign it?"
- *Real-World Scenario:* "Your payment system needs to support a new payment provider every few months. How would you design it so adding a provider doesn't touch existing code?"

### L — Liskov Substitution Principle
- *Explanation:* Subtypes must be substitutable for their base types without breaking correctness — a derived class shouldn't change expected behavior in surprising ways.
- *Bad Example:*
```csharp
class Rectangle { public virtual int Width { get; set; } public virtual int Height { get; set; } }
class Square : Rectangle {
    public override int Width { set { base.Width = base.Height = value; } }
}
// Code expecting Rectangle behavior breaks when given a Square
```
- *Improved Example:* Don't force `Square` to inherit `Rectangle` if their invariants differ — use a common `IShape` interface with independent implementations instead.
- *Interview Question:* "Why is the classic 'Square inherits Rectangle' example considered a violation of LSP?"
- *Real-World Scenario:* "A derived class throws `NotImplementedException` for a method the base class defines. Is this a problem? Why?"

### I — Interface Segregation Principle
- *Explanation:* Clients shouldn't be forced to depend on methods they don't use — prefer several small, specific interfaces over one large, general one.
- *Bad Example:*
```csharp
interface IWorker {
    void Work();
    void Eat();
}
class RobotWorker : IWorker {
    public void Work() { }
    public void Eat() { throw new NotImplementedException(); } // robots don't eat
}
```
- *Improved Example:* Split into `IWorkable` and `IFeedable`; `RobotWorker` only implements `IWorkable`.
- *Interview Question:* "You've implemented an interface method just by throwing `NotImplementedException`. What does that usually indicate?"
- *Real-World Scenario:* "A `IRepository` interface has 15 methods but most implementations only need 3–4 of them. How would you redesign it?"

### D — Dependency Inversion Principle
- *Explanation:* High-level modules shouldn't depend on low-level modules directly — both should depend on abstractions (interfaces). This enables loose coupling and testability.
- *Bad Example:*
```csharp
class OrderService {
    private SqlOrderRepository _repo = new SqlOrderRepository(); // tightly coupled
}
```
- *Improved Example:*
```csharp
class OrderService {
    private readonly IOrderRepository _repo;
    public OrderService(IOrderRepository repo) { _repo = repo; }
}
```
- *Interview Question:* "Why is directly `new`-ing up a concrete repository inside a service considered bad practice?"
- *Real-World Scenario:* "How does .NET's built-in dependency injection container relate to the Dependency Inversion Principle?"

### Topic 6 Scoring Guide
- **1/5:** Cannot name or explain any SOLID principle correctly.
- **2/5:** Can define principles but can't identify violations in code.
- **3/5:** Recognizes violations and can suggest reasonable fixes.
- **4/5:** Applies SOLID naturally in system design discussions with real trade-offs.
- **5/5:** Discusses when *not* to over-apply SOLID (over-engineering risk) with nuance.
- **Expected for 5–6 yrs:** 3/5–4/5 — should be able to spot violations in real code, not just recite definitions.

**Q3. What is the difference between method overloading and method overriding?**

**Q4. What's the difference between an interface and an abstract class in C#? When would you choose one over the other?**

- *Example:*

class Car {

- *What to Look For:* Real reasoning about flexibility/coupling, ideally a real example of inheritance causing problems.

- *What to Look For:* Practical, incremental refactoring approach with risk awareness.

**Q7. What are `sealed` classes/methods in C#, and why would you use them?**
- *Expected Answer:* `sealed` prevents further inheritance (on a class) or further overriding (on a method). Used to protect invariants, prevent misuse in class hierarchies not designed for extension, and can provide minor performance benefits (JIT can sometimes optimize non-virtual calls better).
- *What to Look For:* Knows it's a deliberate design choice, not just a rarely-used keyword.
- *Red Flags:* Has never encountered or considered using `sealed`.
- *Follow-up:* "Can a sealed class still implement interfaces?"
- *Difficulty:* Advanced

## Topic 8: C#

### Basic

**Q1. What's the difference between value types and reference types in C#?**
- *Expected Answer:* Value types (structs, primitives like `int`, `bool`, `enum`) hold their data directly and are typically stored on the stack (or inline); copying them copies the data. Reference types (classes, arrays, strings — though strings are immutable) store a reference to the data on the heap; copying copies the reference, not the underlying object.
- *Example:*
```csharp
struct Point { public int X, Y; }
var p1 = new Point { X = 1 };
var p2 = p1; // copy
p2.X = 99; // p1.X is still 1
```
- *What to Look For:* Understands copy-by-value vs copy-by-reference implications.
- *Red Flags:* Thinks structs are always on the stack in every scenario (boxed structs, fields in classes complicate this) or can't explain the copy behavior at all.
- *Follow-up:* "What happens when a struct is boxed — what does that mean?"
- *Difficulty:* Basic

**Q2. What is the difference between `IEnumerable<T>` and `List<T>`?**
- *Expected Answer:* `IEnumerable<T>` is an interface representing a sequence that can be iterated (potentially lazily/deferred), doesn't guarantee count or indexing. `List<T>` is a concrete, in-memory collection supporting indexing, `Count`, adding/removing items.
- *What to Look For:* Mentions deferred execution possibility with `IEnumerable`.
- *Red Flags:* Thinks they're interchangeable with no performance/behavior differences.
- *Follow-up:* "Why might iterating an `IEnumerable<T>` twice execute the underlying query twice?"
- *Difficulty:* Basic

**Q3. What is exception handling in C#, and what's the difference between `finally` and `catch`?**
- *Expected Answer:* `catch` handles specific exception types when thrown. `finally` runs regardless of whether an exception occurred — used for cleanup (closing connections, releasing resources).
- *Example:*
```csharp
try { /* risky code */ }
catch (SqlException ex) { /* handle */ }
finally { connection.Close(); }
```
- *What to Look For:* Knows `finally` always executes (except in extreme cases like process termination).
- *Red Flags:* Uses empty catch blocks to "swallow" all exceptions.
- *Follow-up:* "Why is catching the base `Exception` type everywhere considered bad practice?"
- *Difficulty:* Basic

### Intermediate

**Q4. Explain `async`/`await` in C#. What does `await` actually do?**
- *Expected Answer:* `async` marks a method as asynchronous, allowing use of `await`. `await` suspends execution of the method (without blocking the calling thread) until the awaited Task completes, then resumes — the compiler generates a state machine behind the scenes.
- *Example:*
```csharp
public async Task<User> GetUserAsync(int id) {
    var response = await _httpClient.GetAsync($"/users/{id}");
    return await response.Content.ReadFromJsonAsync<User>();
}
```
- *What to Look For:* Understands it's non-blocking, and can explain the state machine concept at a high level.
- *Red Flags:* Thinks `async`/`await` creates new threads (it doesn't inherently — it's about freeing up threads for I/O-bound work).
- *Follow-up:* "Does `async`/`await` create a new thread? Why or why not?"
- *Difficulty:* Intermediate

**Q5. What is `IDisposable` and the `using` statement for? Why do they matter?**
- *Expected Answer:* `IDisposable` defines a `Dispose()` method for releasing unmanaged resources (file handles, DB connections, network sockets) deterministically. `using` ensures `Dispose()` is called automatically even if an exception occurs, avoiding resource leaks.
- *Example:*
```csharp
using var connection = new SqlConnection(connString);
connection.Open();
```
- *What to Look For:* Connects this to resource leaks / real production issues (e.g., connection pool exhaustion).
- *Red Flags:* Doesn't know when to implement `IDisposable` on their own classes.
- *Follow-up:* "When would you need to implement `IDisposable` yourself, versus relying on the garbage collector?"
- *Difficulty:* Intermediate

**Q6. Explain generics in C# and why they're useful.**
- *Expected Answer:* Generics allow writing type-safe, reusable code that works with any type, determined at compile time, avoiding boxing/unboxing overhead and casting errors that come with non-generic collections (like old `ArrayList`).
- *Example:*
```csharp
public class Repository<T> where T : class {
    public T GetById(int id) { /* ... */ }
}
```
- *What to Look For:* Mentions type safety and performance (avoiding boxing).
- *Red Flags:* Can't explain why generics are preferred over `object`-based code.
- *Follow-up:* "What does the `where T : class` constraint do?"
- *Difficulty:* Intermediate

**Q7. What's the difference between `Task` and `Task<T>`, and what does `Task.WhenAll` do?**
- *Expected Answer:* `Task` represents an asynchronous operation with no return value; `Task<T>` returns a value of type `T` on completion. `Task.WhenAll` runs multiple tasks concurrently and completes when all of them finish, useful for parallelizing independent async operations.
- *Example:*
```csharp
var task1 = GetUserAsync(1);
var task2 = GetOrdersAsync(1);
await Task.WhenAll(task1, task2);
```
- *What to Look For:* Knows `WhenAll` improves performance over sequential awaits when operations are independent.

### Advanced

**Q8. Explain garbage collection in .NET at a high level. What are generations, and why do they exist?**
- *Expected Answer:* .NET GC is generational: Gen 0 (short-lived objects, collected frequently/cheaply), Gen 1 (buffer between short and long-lived), Gen 2 (long-lived objects, collected less often but more expensively). Objects surviving a collection get promoted to the next generation. This design is based on the observation that most objects die young, so frequent cheap collections of Gen 0 handle most garbage efficiently.
- *What to Look For:* Understands the generational hypothesis and why it matters for performance.
- *Red Flags:* Thinks GC runs on a fixed schedule unrelated to memory pressure, or has zero awareness of generations.
- *Follow-up:* "What's a Large Object Heap (LOH), and why can it cause performance problems?"
- *Difficulty:* Advanced

**Q9. What are nullable reference types in modern C#, and how do they help prevent bugs?**
- *Expected Answer:* Enabled via `<Nullable>enable</Nullable>`, the compiler tracks reference type nullability at compile time (`string?` vs `string`) and warns when a possibly-null reference is dereferenced without a check — catching potential `NullReferenceException`s at compile time rather than runtime. Doesn't change runtime behavior — it's a static analysis feature.
- *What to Look For:* Knows it's compile-time warnings, not a runtime guarantee.
- *Red Flags:* Thinks enabling nullable reference types makes `NullReferenceException` impossible at runtime.
- *Follow-up:* "If nullable reference types are just warnings, can you still get a NullReferenceException at runtime with them enabled?"
- *Difficulty:* Advanced

**Q10. Scenario: A .NET API's memory usage keeps climbing under load and never comes back down, even after traffic drops. How would you investigate this?**
- *Expected Answer:* Check for classic leak patterns: static collections growing indefinitely, event handlers not unsubscribed, `IDisposable` objects not disposed (e.g., `HttpClient` misuse, DB connections), large object heap fragmentation. Use tools like `dotnet-counters`, `dotnet-trace`, or a memory profiler (dotMemory, PerfView) to take memory dumps and analyze retained object graphs.
- *What to Look For:* Names concrete diagnostic tools, not just "add more RAM" or vague guesses.
- *Red Flags:* Only suggests restarting the app or scaling out without investigating the root cause.
- *Follow-up:* "What's a common mistake developers make with `HttpClient` that causes socket exhaustion or memory issues?"
- *Difficulty:* Advanced

**Q11. What is pattern matching in modern C#, and can you show an example using `switch` expressions or records?**
- *Expected Answer:* Pattern matching lets you test and destructure values based on shape/type concisely, replacing verbose if/else chains. Records provide concise immutable data types with built-in value equality.
- *Example:*
```csharp
string Describe(object obj) => obj switch {
    int n when n < 0 => "negative number",
    int => "number",
    string s when string.IsNullOrEmpty(s) => "empty string",
    null => "null",
    _ => "unknown"

```
- *What to Look For:* Familiarity with modern C# syntax (relevant to how current their day-to-day experience is).
- *Red Flags:* Has never used records or switch expressions despite claiming recent .NET experience.
- *Follow-up:* "How is value equality on a `record` different from equality on a regular `class`?"
- *Difficulty:* Advanced

### Intermediate

**Q4. What is deferred execution in LINQ, and why does it matter?**
- *Expected Answer:* Most LINQ query operators (like `Where`, `Select`) don't execute immediately — they build up an expression/iterator that only runs when enumerated (e.g., via `foreach`, `.ToList()`, `.Count()`). This means the underlying data source is queried at enumeration time, which can cause surprises if the data changes between query definition and execution, or cause a query to run multiple times if enumerated repeatedly.
- *Example:*
```csharp
var query = dbContext.Users.Where(u => u.IsActive); // not executed yet
var count = query.Count(); // executes now
```
- *What to Look For:* Real understanding of when queries actually hit the database/execute.
- *Red Flags:* Thinks all LINQ methods execute immediately.
- *Follow-up:* "What LINQ methods force immediate execution?"
- *Difficulty:* Intermediate

**Q5. What's the difference between `IEnumerable<T>` and `IQueryable<T>` in the context of Entity Framework?**
- *Expected Answer:* `IQueryable<T>` builds an expression tree that gets translated into SQL and executed on the database server (efficient filtering/sorting happens in the DB). `IEnumerable<T>` operates in-memory — if you call `.AsEnumerable()` too early, subsequent LINQ operations run in application memory instead of the database, which can be a serious performance problem with large datasets.
- *Example:*
```csharp
// BAD: pulls ALL rows into memory before filtering
var users = dbContext.Users.AsEnumerable().Where(u => u.IsActive);
// GOOD: filter executes in SQL
var users = dbContext.Users.Where(u => u.IsActive);
```
- *What to Look For:* Recognizes this as a common real-world EF performance bug.
- *Red Flags:* Doesn't know the difference or has caused this exact bug without realizing it.
- *Follow-up:* "Have you seen a query pull way more data than needed because of this? What happened?"
- *Difficulty:* Intermediate

**Q6. What does `GroupBy` do, and how would you get a count per group?**
- *Expected Answer:* Groups elements sharing a common key into a sequence of `IGrouping<TKey, TElement>`, each acting like a mini-collection for that group.
- *Example:*
```csharp
var countByDept = employees
    .GroupBy(e => e.Department)
    .Select(g => new { Department = g.Key, Count = g.Count() });
```
- *What to Look For:* Correct syntax and understanding that grouping in EF often translates to SQL `GROUP BY`.
- *Red Flags:* Can't produce working `GroupBy` syntax at all.
- *Follow-up:* "How does `GroupBy` behave differently when used against an in-memory list vs. an `IQueryable` from EF Core?"
- *Difficulty:* Intermediate

### Advanced

**Q7. Scenario: A LINQ query using multiple nested `Where`/`Select` clauses against EF Core is generating a huge, slow SQL query with unnecessary joins. How would you investigate and fix it?**
- *Expected Answer:* Use EF Core logging (`ILogger`) or tools like `dotnet-trace`/SQL Profiler to see the generated SQL. Look for unintentional eager loading (`Include` chains), N+1 query patterns, or projections causing unnecessary joins. Fix by projecting only needed columns early with `Select`, using `AsNoTracking()` for read-only queries, splitting queries (`AsSplitQuery()`) where appropriate, and avoiding client-side evaluation.
- *What to Look For:* Concrete diagnostic steps and multiple real fixes.
- *Red Flags:* Has never looked at generated SQL from EF Core.
- *Follow-up:* "What is the N+1 query problem, and how do you detect and fix it in EF Core?"
- *Difficulty:* Advanced

**Q8. What does `Aggregate` do, and can you give an example where it's useful beyond what `Sum`/`Count` can do?**
- *Expected Answer:* `Aggregate` applies an accumulator function over a sequence to reduce it to a single value — useful for custom reduction logic that built-in methods (`Sum`, `Count`, `Max`) don't directly support.
- *Example:*
```csharp
var longestWord = words.Aggregate((longest, next) => next.Length > longest.Length ? next : longest);
```
- *What to Look For:* Can produce a working, non-trivial example.
- *Red Flags:* Has never used `Aggregate` and can't reason through what it does even when told the signature.
- *Follow-up:* "What's a performance risk of using `Aggregate` (or LINQ in general) on a very large in-memory collection?"
- *Difficulty:* Advanced

**Q9. What's a common LINQ mistake that causes multiple database round-trips instead of one, and how would you fix it?**
- *Expected Answer:* The N+1 problem — e.g., looping over a list of entities and lazily accessing a navigation property inside the loop, causing one query per iteration. Fix: eager load with `.Include()`, or restructure the query to fetch everything needed in a single query/projection upfront.
- *Example:*
```csharp
// BAD - N+1
foreach (var order in dbContext.Orders) {
    Console.WriteLine(order.Customer.Name); // triggers a query per order if lazy loading
}
// GOOD
var orders = dbContext.Orders.Include(o => o.Customer).ToList();
```
- *What to Look For:* Can name the N+1 problem explicitly and describe the fix.
- *Red Flags:* Has never heard of N+1 despite years of EF experience.
- *Follow-up:* "How would you detect an N+1 problem in production without manually reading every query?"
- *Difficulty:* Advanced

**Q7. What's the difference between `Tracking` and `NoTracking` queries in EF Core? When should you use each?**

**Q8. Scenario: Your ASP.NET Core API is suddenly taking 5 seconds instead of 500ms to respond. Walk me through how you'd investigate.**

## Topic 11: SQL

### Basic

**Q1. What's the difference between `INNER JOIN`, `LEFT JOIN`, and `RIGHT JOIN`?**
- *Expected Answer:* `INNER JOIN` returns only matching rows from both tables. `LEFT JOIN` returns all rows from the left table plus matches from the right (NULLs where no match). `RIGHT JOIN` is the mirror of `LEFT JOIN`.
- *Example:*
```sql
SELECT c.Name, o.OrderId
FROM Customers c
LEFT JOIN Orders o ON o.CustomerId = c.Id;
```
- *What to Look For:* Can explain with a practical example (e.g., "customers with no orders still appear").
- *Red Flags:* Confuses LEFT and RIGHT or doesn't know NULLs appear in unmatched rows.
- *Follow-up:* "How would you find customers who have never placed an order using a JOIN?"
- *Difficulty:* Basic

**Q2. What's the difference between `WHERE` and `HAVING`?**
- *Expected Answer:* `WHERE` filters rows before grouping/aggregation. `HAVING` filters groups after `GROUP BY` aggregation (e.g., filtering on an aggregate like `COUNT(*)`).
- *Example:*
```sql
SELECT Department, COUNT(*) as EmployeeCount
FROM Employees
GROUP BY Department
HAVING COUNT(*) > 10;
```
- *What to Look For:* Knows `WHERE` can't reference aggregate functions.
- *Red Flags:* Tries to use `WHERE COUNT(*) > 10`.
- *Follow-up:* "Why can't you use an aggregate function like `COUNT(*)` in a `WHERE` clause?"
- *Difficulty:* Basic

**Q3. What are primary keys and foreign keys, and why do we use constraints?**
- *Expected Answer:* Primary key uniquely identifies each row in a table (no duplicates, no NULLs). Foreign key enforces a relationship/reference to another table's primary key, maintaining referential integrity (preventing orphaned records).
- *What to Look For:* Mentions referential integrity as the "why," not just definitions.
- *Red Flags:* Doesn't know why foreign keys matter for data integrity.
- *Follow-up:* "What happens if you try to delete a parent row that has child rows referencing it via a foreign key?"
- *Difficulty:* Basic

### Intermediate

**Q4. What is a CTE (Common Table Expression), and why would you use one over a subquery?**
- *Expected Answer:* A CTE (`WITH ... AS (...)`) is a named, temporary result set defined for use within a single query — improves readability, allows recursive queries, and can be referenced multiple times without repeating the subquery.
- *Example:*
```sql
WITH ActiveCustomers AS (
    SELECT * FROM Customers WHERE IsActive = 1
)
SELECT * FROM ActiveCustomers WHERE Country = 'USA';
```
- *What to Look For:* Mentions readability/recursion as motivations.
- *Red Flags:* Doesn't know what a CTE is despite years of SQL experience.
- *Follow-up:* "How would you write a recursive CTE — e.g., to get an employee's full management chain?"
- *Difficulty:* Intermediate

**Q5. What's the difference between a clustered and a non-clustered index?**
- *Expected Answer:* A clustered index determines the physical storage order of the table's data (only one per table). A non-clustered index is a separate structure with pointers back to the actual data rows (a table can have many). Clustered indexes are typically on the primary key by default (in many RDBMSs).
- *What to Look For:* Understands the physical vs. logical distinction.
- *Red Flags:* Thinks a table can have multiple clustered indexes.
- *Follow-up:* "Why might adding too many non-clustered indexes hurt write performance?"
- *Difficulty:* Intermediate

**Q6. What's the difference between transaction isolation levels, and can you explain what a "dirty read" is?**
- *Expected Answer:* Isolation levels (Read Uncommitted, Read Committed, Repeatable Read, Serializable) control how much transactions can see of each other's uncommitted changes and trade off consistency vs. concurrency. A dirty read happens when a transaction reads data written by another transaction that hasn't yet committed (and might roll back) — possible under Read Uncommitted.
- *What to Look For:* Can explain at least dirty reads and the general trade-off between isolation and concurrency/performance.
- *Red Flags:* Has never heard of isolation levels.
- *Follow-up:* "What's the default isolation level in SQL Server, and what problem does it still allow?"
- *Difficulty:* Intermediate

**Q7. How would you paginate query results efficiently for a large table?**
- *Expected Answer:* Use `OFFSET`/`FETCH` (or `LIMIT`/`OFFSET` depending on DB) but be aware `OFFSET` gets slower on large offsets since the DB still scans skipped rows; for very large datasets, "keyset pagination" (filtering by the last seen ID/sort key, e.g., `WHERE Id > @lastId ORDER BY Id`) is more efficient.
- *Example:*
```sql
SELECT * FROM Orders ORDER BY Id OFFSET 1000000 ROWS FETCH NEXT 20 ROWS ONLY;
-- vs keyset:
SELECT TOP 20 * FROM Orders WHERE Id > @lastId ORDER BY Id;
```
- *What to Look For:* Awareness of `OFFSET` performance degradation at scale.
- *Red Flags:* Only knows `OFFSET`/`FETCH` and has no idea it can be slow for deep pages.
- *Follow-up:* "Why does keyset pagination scale better than offset-based pagination?"
- *Difficulty:* Intermediate

### Advanced

**Q8. Scenario: A query runs fine with 1,000 rows but takes minutes with 10 million rows. How would you investigate and fix it?**
- *Expected Answer:* Look at the query execution plan (look for table scans instead of index seeks, missing indexes, poor join order, implicit conversions preventing index usage). Check if appropriate indexes exist on filter/join columns, whether statistics are up to date, whether the query does unnecessary work (SELECT * instead of needed columns), and consider query rewriting or adding covering indexes.
- *What to Look For:* Mentions execution plans explicitly as the primary diagnostic tool.
- *Red Flags:* Only suggests "add an index" with no process for identifying *which* index or verifying the plan improved.
- *Follow-up:* "What's an example of something that could prevent SQL Server from using an existing index even if one exists on the filtered column?"
- *Difficulty:* Advanced

**Q9. What is a deadlock, and how would you diagnose and prevent one?**
- *Expected Answer:* A deadlock occurs when two or more transactions hold locks the others need, forming a cycle with no way to proceed — the DB engine detects this and kills one transaction (the "victim"). Diagnose via deadlock graphs/trace flags/extended events. Prevent by accessing tables/rows in a consistent order across transactions, keeping transactions short, using appropriate isolation levels, and adding proper indexing to reduce lock scope.
- *What to Look For:* Understands the cyclic wait concept and at least one prevention strategy.
- *Red Flags:* Has never dealt with a deadlock in production or doesn't know how the DB resolves them.
- *Follow-up:* "Tell me about a real deadlock you've debugged — what caused it?"
- *Difficulty:* Advanced

**Q10. What is normalization, and can over-normalizing a database cause problems? Give an example.**
- *Expected Answer:* Normalization reduces data redundancy by organizing data into related tables (1NF, 2NF, 3NF, etc.). Over-normalizing can hurt read performance (excessive joins for common queries) — sometimes deliberate denormalization (or materialized/indexed views) is used for reporting/read-heavy workloads.
- *What to Look For:* Balanced view — knows normalization isn't an absolute good, understands the read/write trade-off.
- *Red Flags:* Treats normalization as always correct with no situational trade-offs.
- *Follow-up:* "When would you deliberately denormalize a schema?"
- *Difficulty:* Advanced

## Topic 12: Microservices

### Basic

**Q1. What's the difference between a monolith and a microservices architecture?**
- *Expected Answer:* A monolith is a single deployable application containing all functionality. Microservices split functionality into independently deployable services, each owning its own data and communicating over the network. Trade-offs: microservices offer independent scaling/deployment but add operational complexity (network calls, distributed data, monitoring).
- *What to Look For:* Balanced view — mentions trade-offs, not "microservices are always better."
- *Red Flags:* Believes microservices are a silver bullet with no downsides.
- *Follow-up:* "When would you actually recommend staying with a monolith?"
- *Difficulty:* Basic

**Q2. What's the difference between synchronous and asynchronous communication between services?**
- *Expected Answer:* Synchronous (e.g., REST/gRPC calls) — caller waits for a response; simpler but creates tighter coupling and cascading failure risk. Asynchronous (message queues, events) — caller doesn't wait; more resilient and decoupled but adds complexity around eventual consistency and debugging.
- *What to Look For:* Mentions cascading failure risk with sync calls.
- *Red Flags:* Doesn't know async messaging options exist (queues/event buses).
- *Follow-up:* "Give an example of when you'd choose async messaging over a direct REST call between two services."
- *Difficulty:* Basic

**Q3. What is an API Gateway, and why use one in a microservices architecture?**
- *Expected Answer:* A single entry point that routes client requests to the appropriate backend service, and can handle cross-cutting concerns like authentication, rate limiting, request aggregation, and logging — so clients don't need to know about internal service topology.
- *What to Look For:* Understands it centralizes cross-cutting concerns.
- *Red Flags:* Thinks it's just a load balancer with no additional responsibilities.
- *Follow-up:* "What's a downside of putting too much logic into the API Gateway?"
- *Difficulty:* Basic

### Intermediate

**Q4. What is the "database per service" pattern, and what problem does it solve? What new problem does it create?**
- *Expected Answer:* Each microservice owns its own database, preventing tight coupling through a shared schema and allowing independent evolution/scaling. New problem: querying across services becomes harder (no simple cross-service JOINs), and maintaining consistency across services requires new patterns (Sagas, eventual consistency).
- *What to Look For:* Understands both the benefit and the new complexity it introduces.
- *Red Flags:* Thinks each service can just query another service's database directly "when convenient."
- *Follow-up:* "How would you generate a report that needs data from three different services' databases?"
- *Difficulty:* Intermediate

**Q5. What is the Saga pattern, and why is it needed in microservices?**
- *Expected Answer:* Since distributed transactions (2-phase commit) across services are impractical at scale, Sagas coordinate a sequence of local transactions across services, with compensating actions to undo prior steps if a later step fails — either via **choreography** (services react to each other's events) or **orchestration** (a central coordinator directs the sequence).
- *Example:* Order → Payment → Inventory reservation. If inventory fails, a compensating transaction refunds the payment.
- *What to Look For:* Can explain choreography vs. orchestration and compensating transactions.
- *Red Flags:* Has never heard of Sagas or thinks distributed 2PC transactions are the standard solution at scale.
- *Follow-up:* "Would you choose choreography or orchestration for a 5-step order process? Why?"
- *Difficulty:* Intermediate

**Q6. What is idempotency, and why does it matter in distributed systems with retries?**
- *Expected Answer:* An idempotent operation produces the same result no matter how many times it's executed. Matters because network failures cause retries — without idempotency, a retried "charge customer" or "create order" call could duplicate the action (double charge, duplicate order).
- *Example:* Using a client-generated idempotency key on a payment request so the server can recognize and ignore duplicate submissions.
- *What to Look For:* Concrete example connecting idempotency to retry safety.
- *Red Flags:* Doesn't understand why retries without idempotency are dangerous.
- *Follow-up:* "How would you implement an idempotency key for a 'create order' API endpoint?"
- *Difficulty:* Intermediate

**Q7. What is the Circuit Breaker pattern, and when does it activate?**
- *Expected Answer:* A resilience pattern that "trips" (stops making calls) to a failing downstream service after a threshold of failures, failing fast instead of piling up timeouts, and periodically allows a test request through to check recovery (half-open state) before fully closing again.
- *What to Look For:* Knows the three states: closed, open, half-open.
- *Red Flags:* Confuses circuit breakers with simple retry logic.
- *Follow-up:* "What's the difference between a retry policy and a circuit breaker, and how do they work together (e.g., in Polly)?"
- *Difficulty:* Intermediate

### Advanced

**Q8. Scenario: Two microservices need to update related data (e.g., an Order service and an Inventory service) — how would you handle consistency without a distributed transaction?**
- *Expected Answer:* Use the Saga pattern with compensating transactions, or an outbox pattern combined with event-driven messaging to reliably publish events after a local transaction commits (avoiding the "dual write" problem of writing to a DB and a message queue non-atomically). Emphasize eventual consistency as an accepted trade-off, with idempotent consumers handling retries/duplicates.
- *What to Look For:* Mentions the outbox pattern and/or Saga, and understands eventual consistency isn't a bug — it's a deliberate trade-off.
- *Red Flags:* Suggests a distributed 2-phase-commit transaction as the primary solution, unaware of its practical issues at scale.
- *Follow-up:* "What is the 'dual write problem,' and how does the Outbox pattern solve it?"
- *Difficulty:* Advanced

**Q9. How would you design authentication and authorization across multiple microservices?**
- *Expected Answer:* Use a centralized identity provider (OAuth2/OpenID Connect — e.g., IdentityServer, Azure AD, Auth0) issuing JWTs. Services validate the token independently (no shared session state), with claims embedded for authorization. For service-to-service calls, use client credentials flow or mutual TLS; consider a service mesh (e.g., Istio) for automatic mTLS between services.
- *What to Look For:* Mentions token validation being stateless/local to each service (no central "ask the auth service every time" bottleneck), and service-to-service auth specifically.
- *Red Flags:* Has each service call a central auth service synchronously on every request to validate tokens (creates a bottleneck/single point of failure), or has no plan for service-to-service auth at all.
- *Follow-up:* "How do you handle token revocation in a stateless JWT-based system?"
- *Difficulty:* Advanced

**Q10. What observability practices (logging, monitoring, tracing) are essential in a microservices architecture, and why?**
- *Expected Answer:* Centralized structured logging (e.g., ELK/Seq) since logs are spread across many services; distributed tracing (correlation/trace IDs propagated across service calls, using tools like OpenTelemetry/Jaeger/Zipkin) to follow a single request across service boundaries; metrics/dashboards (Prometheus/Grafana, Application Insights) for health and performance; centralized alerting.
- *What to Look For:* Specifically mentions correlation/trace IDs — this is the key differentiator vs. monolith logging.
- *Red Flags:* Plans to debug issues by SSH-ing into individual servers and grepping local logs.
- *Follow-up:* "How would you trace a single user request as it flows through five different services?"
- *Difficulty:* Advanced

**Q11. What are common real-world problems teams run into when adopting microservices, and how do you mitigate them?**
- *Expected Answer:* Examples: distributed monolith (services too tightly coupled, must deploy together anyway), chatty inter-service communication causing latency, difficulty debugging across service boundaries, data consistency challenges, and increased operational/infrastructure overhead. Mitigate with clear service boundaries (domain-driven design), proper observability, async communication where appropriate, and starting with a monolith until boundaries are well understood ("monolith first").
- *What to Look For:* Real, specific experience-based examples rather than textbook listing.
- *Red Flags:* Only positive things to say about microservices with no acknowledgment of real challenges.
- *Follow-up:* "Have you ever seen a 'distributed monolith' in practice? What made it one?"
- *Difficulty:* Advanced

### Topic 12 Scoring Guide
- **1/5:** Can't explain the difference between monolith and microservices.
- **2/5:** Knows basic concepts but not Sagas, idempotency, or circuit breakers.
- **3/5:** Understands resilience patterns and database-per-service trade-offs.
- **4/5:** Can design cross-service consistency and auth strategies with reasoning.
- **5/5:** Deep, battle-tested experience with distributed systems trade-offs and failure modes.
- **Expected for 5–6 yrs:** 2/5–4/5 depending heavily on whether their past roles actually used microservices — probe honestly rather than penalizing lack of exposure if their background is monolith-heavy.

## Topic 13: Azure Cloud

### Basic

**Q1. What's the difference between Azure App Service and Azure Functions?**
- *Expected Answer:* App Service hosts full web apps/APIs continuously running with more control over runtime/scaling. Azure Functions is serverless — event-triggered, scales automatically (including to zero), billed per execution — best for short-lived, event-driven tasks.
- *What to Look For:* Knows when to pick one over the other, not just definitions.
- *Red Flags:* Thinks they're interchangeable with no trade-offs.
- *Follow-up:* "When would you choose Azure Functions instead of an App Service?"
- *Difficulty:* Basic

**Q2. What is Azure Key Vault used for?**
- *Expected Answer:* Securely stores secrets, connection strings, certificates, and encryption keys, avoiding hardcoding sensitive values in config files or source control; integrates with Managed Identity so apps can retrieve secrets without storing credentials themselves.
- *What to Look For:* Connects it to real security practice (no secrets in appsettings.json/source control).
- *Red Flags:* Stores connection strings/passwords directly in config files checked into source control.
- *Follow-up:* "How would an App Service authenticate to Key Vault without storing a secret to access it?"
- *Difficulty:* Basic

**Q3. What's the difference between Blob Storage and Azure SQL?**
- *Expected Answer:* Blob Storage is for unstructured data (files, images, backups, logs) — object storage. Azure SQL is a managed relational database for structured, transactional data with querying/joins/ACID guarantees.
- *What to Look For:* Correctly categorizes use cases.
- *Red Flags:* Would try to store large binary files directly in a SQL database column without considering Blob Storage.
- *Follow-up:* "How would you store and serve user-uploaded profile pictures for a web app?"
- *Difficulty:* Basic

### Intermediate

**Q4. What is Managed Identity in Azure, and why is it preferred over storing credentials?**
- *Expected Answer:* Managed Identity gives an Azure resource (App Service, Function, VM) an automatically-managed identity in Azure AD, allowing it to authenticate to other Azure services (Key Vault, SQL, Storage) without any stored credentials/connection secrets — eliminating secret rotation/leak risk.
- *What to Look For:* Understands the security benefit (no secret to leak/rotate).
- *Red Flags:* Doesn't know Managed Identity exists, defaults to connection strings with embedded credentials everywhere.
- *Follow-up:* "What's the difference between a system-assigned and user-assigned managed identity?"
- *Difficulty:* Intermediate

**Q5. How does Azure Service Bus differ from Azure Storage Queues, and when would you use each?**
- *Expected Answer:* Storage Queues are simpler, cheaper, good for basic decoupling with large capacity but limited features. Service Bus supports advanced messaging features: topics/subscriptions (pub/sub), sessions, dead-lettering, FIFO ordering, transactions — better for complex enterprise messaging scenarios.
- *What to Look For:* Practical distinction, real usage experience.
- *Red Flags:* Has never used either or can't articulate any difference.
- *Follow-up:* "What is dead-lettering, and why is it useful?"
- *Difficulty:* Intermediate

**Q6. How would you set up CI/CD for a .NET application deploying to Azure?**
- *Expected Answer:* Typically Azure DevOps Pipelines or GitHub Actions: build/test on push/PR, then deploy to App Service/AKS/Functions using deployment slots for zero-downtime swaps, with separate stages for dev/staging/production and approval gates for production.
- *What to Look For:* Mentions deployment slots or blue-green-style deployment for zero downtime.
- *Red Flags:* Deploys directly to production with no staging environment or rollback plan.
- *Follow-up:* "How do deployment slots help you achieve zero-downtime deployments?"
- *Difficulty:* Intermediate

### Advanced

**Q7. Scenario: Your Azure App Service is unexpectedly costing much more than budgeted. How would you investigate and reduce costs without hurting performance?**
- *Expected Answer:* Review Azure Cost Management/Advisor recommendations, check App Service Plan tier/scale-out settings (over-provisioned instances), look at underutilized resources (idle dev/test environments left running), consider consumption-based options (Functions) for spiky workloads, review data egress and storage tier costs, right-size SQL DTU/vCore tiers based on actual usage.
- *What to Look For:* Concrete cost-analysis approach, mentions specific Azure cost tools.
- *Red Flags:* Only suggests "scale down" blindly without analyzing usage patterns first.
- *Follow-up:* "How would you decide whether to scale up (bigger instance) vs. scale out (more instances)?"
- *Difficulty:* Advanced

**Q8. How would you design a scalable, resilient architecture on Azure for a .NET API expecting unpredictable traffic spikes?**
- *Expected Answer:* Use auto-scaling App Service plans or Azure Container Apps/AKS with horizontal pod autoscaling, put a caching layer (Azure Cache for Redis) in front of expensive DB calls, use Azure Front Door/Application Gateway for load balancing and global distribution, decouple spiky workloads via Service Bus/Queue + Functions, and use Application Insights for real-time monitoring/alerting.
- *What to Look For:* Multi-layered architectural thinking (compute + caching + queuing + monitoring), not a single-service answer.
- *Red Flags:* Suggests "just use a bigger VM" as the entire strategy.
- *Follow-up:* "How would Azure Front Door or Application Gateway help here specifically?"
- *Difficulty:* Advanced

**Q9. What security practices would you apply to a production Azure-hosted .NET application?**
- *Expected Answer:* Managed Identity instead of stored credentials, Key Vault for secrets, network isolation (VNet integration, Private Endpoints), enforce HTTPS/TLS, Web Application Firewall (WAF) on Front Door/App Gateway, least-privilege RBAC roles, regular dependency/vulnerability scanning, enable diagnostic logging/Azure Monitor alerts for suspicious activity.
- *What to Look For:* Layered security thinking (identity, network, secrets, monitoring), not just "we use HTTPS."
- *Red Flags:* Only mentions HTTPS as their entire security answer.
- *Follow-up:* "What's a Private Endpoint, and why would you use one instead of exposing a service over the public internet?"
- *Difficulty:* Advanced

### Topic 13 Scoring Guide
- **1/5:** No familiarity with basic Azure services relevant to .NET.
- **2/5:** Has deployed a basic app to App Service but no deeper knowledge.
- **3/5:** Comfortable with Key Vault, Managed Identity, Service Bus, CI/CD basics.
- **4/5:** Can design for cost, scale, and security thoughtfully.
- **5/5:** Deep, hands-on architecture experience across multiple Azure services in production.
- **Expected for 5–6 yrs (if Azure is part of their stack):** 2/5–4/5 — heavily dependent on actual project exposure; probe specifically rather than assuming.

## Topic 14: AWS Cloud

### Basic

**Q1. What's the AWS equivalent of Azure App Service / how would you host a .NET API on AWS?**
- *Expected Answer:* Options include Elastic Beanstalk (PaaS-like, similar to App Service), ECS/EKS (containers), or EC2 (full VM control) for hosting the API; Lambda for serverless functions (via .NET Lambda runtime).
- *What to Look For:* Knows multiple valid options and roughly when to use each.
- *Red Flags:* Only knows EC2 and has never heard of Elastic Beanstalk, ECS, or Lambda.
- *Follow-up:* "When would you choose ECS over plain EC2 for a .NET API?"
- *Difficulty:* Basic

**Q2. What is AWS Lambda, and when would you use it over a traditional server?**
- *Expected Answer:* Serverless compute that runs code in response to events without managing servers, scales automatically, billed per invocation/duration. Good for event-driven, short-lived, spiky workloads; less ideal for long-running or very latency-sensitive workloads with cold-start concerns.
- *What to Look For:* Mentions cold starts as a trade-off.
- *Red Flags:* Thinks Lambda is a drop-in replacement for all compute needs with no trade-offs.
- *Follow-up:* "What is a 'cold start,' and how would you mitigate it for a .NET Lambda function?"
- *Difficulty:* Basic

**Q3. What's the difference between S3, RDS, and DynamoDB?**
- *Expected Answer:* S3 is object storage for files/unstructured data. RDS is managed relational database (SQL Server, PostgreSQL, MySQL, etc.) for structured/transactional data. DynamoDB is a managed NoSQL key-value/document database for high-scale, low-latency access patterns with flexible schema.
- *What to Look For:* Correctly categorizes each service's use case.
- *Red Flags:* Confuses DynamoDB with a relational database (e.g., expects JOINs).
- *Follow-up:* "When would you choose DynamoDB over RDS for a new feature?"
- *Difficulty:* Basic

### Intermediate

**Q4. What is IAM, and what does "least privilege" mean in that context?**
- *Expected Answer:* IAM (Identity and Access Management) controls who/what can access AWS resources and what actions they can perform, via users, roles, and policies. Least privilege means granting only the minimum permissions necessary for a task — reducing blast radius if credentials are compromised.
- *What to Look For:* Mentions least privilege as a security principle, not just a definition of IAM.
- *Red Flags:* Defaults to attaching `AdministratorAccess` to everything "to avoid permission errors."
- *Follow-up:* "How would you grant a Lambda function access to only one specific S3 bucket?"
- *Difficulty:* Intermediate

**Q5. What's the difference between SQS and SNS, and when would you use each?**
- *Expected Answer:* SQS is a point-to-point message queue (one consumer processes each message) — good for decoupling and buffering work. SNS is pub/sub — a message published to a topic can fan out to multiple subscribers (which can include SQS queues, Lambda, email, etc.).
- *What to Look For:* Correctly distinguishes queue (1:1 processing) vs. topic (1:many fan-out).
- *Red Flags:* Thinks they're interchangeable.
- *Follow-up:* "How would you fan out a single event to multiple independent services for processing?"
- *Difficulty:* Intermediate

**Q6. How would you use Secrets Manager (or Parameter Store) in a .NET app deployed on AWS?**
- *Expected Answer:* Store connection strings/API keys/secrets in Secrets Manager (or SSM Parameter Store for lower-cost, less-rotation-heavy needs) and retrieve them at startup/runtime via the AWS SDK, using an IAM role attached to the compute resource (EC2 instance profile, ECS task role, Lambda execution role) rather than embedding credentials.
- *What to Look For:* Mentions IAM roles for secretless access (parallel to Azure's Managed Identity).
- *Red Flags:* Hardcodes secrets in `appsettings.json` or environment variables checked into source control.
- *Follow-up:* "What's the difference between Secrets Manager and Parameter Store, and when would you pick one over the other?"
- *Difficulty:* Intermediate

### Advanced

**Q7. What AWS services would you choose to build a scalable, resilient .NET API, and why?**
- *Expected Answer:* Example architecture: ECS Fargate (or EKS) behind an Application Load Balancer for the API, RDS (Multi-AZ) or Aurora for the database, ElastiCache (Redis) for caching, SQS for decoupling async work, CloudWatch for monitoring/alarms, Auto Scaling based on CPU/request metrics, Secrets Manager for credentials, and CloudFront for static asset delivery/CDN.
- *What to Look For:* Multi-layered architecture reasoning (compute, data, caching, async, monitoring), tailored justification for each choice.
- *Red Flags:* Names services with no reasoning for why each fits the scenario.
- *Follow-up:* "Why choose Fargate over managing your own EC2 instances for ECS?"
- *Difficulty:* Advanced

**Q8. How would you design for high availability and disaster recovery on AWS for a critical .NET application?**
- *Expected Answer:* Deploy across multiple Availability Zones (and potentially multiple regions for DR), use Multi-AZ RDS for automatic failover, Auto Scaling Groups spanning AZs, Route 53 health checks and failover routing, regular automated backups/snapshots, and a documented RTO/RPO-driven DR plan (e.g., pilot light, warm standby, or multi-region active-active depending on requirements).
- *What to Look For:* Mentions RTO/RPO concepts and multi-AZ as the baseline, multi-region as an escalation depending on requirements.
- *Red Flags:* Thinks a single EC2 instance with periodic manual backups constitutes "high availability."
- *Follow-up:* "What's the difference between RTO and RPO, and how do they influence your DR strategy?"
- *Difficulty:* Advanced

**Q9. What cost-optimization strategies have you applied (or would apply) on AWS for a .NET workload?**
- *Expected Answer:* Right-sizing EC2/RDS instances based on actual utilization (CloudWatch metrics), using Reserved Instances/Savings Plans for predictable workloads, Spot Instances for fault-tolerant/batch workloads, S3 lifecycle policies to move infrequently accessed data to cheaper tiers, and serverless (Lambda/Fargate) for spiky/low-traffic workloads to avoid paying for idle capacity.
- *What to Look For:* Multiple concrete levers, ideally from real experience.
- *Red Flags:* No familiarity with any cost-optimization mechanism beyond "use a smaller instance."
- *Follow-up:* "When would Spot Instances be risky to use, and how would you mitigate that risk?"
- *Difficulty:* Advanced

### Topic 14 Scoring Guide
- **1/5:** No familiarity with core AWS services relevant to .NET hosting.
- **2/5:** Has deployed something basic to EC2/Elastic Beanstalk but nothing deeper.
- **3/5:** Comfortable with IAM, SQS/SNS, Secrets Manager basics.
- **4/5:** Can design multi-service architectures with cost/HA reasoning.
- **5/5:** Deep, hands-on production experience across compute, data, networking, and cost optimization.
- **Expected for 5–6 yrs (if AWS is part of their stack):** 2/5–4/5 — many .NET shops use Azure more than AWS; judge in context of their actual project history rather than penalizing pure lack of exposure.

### 4. Distinguishing Experience Levels

**Junior-level knowledge (0–2 years):**
- Knows syntax but struggles to explain *why* something works.
- Can write code that works for the happy path but misses edge cases, error handling, or performance implications.
- Rarely has real production debugging stories — answers are textbook-recited.

**Mid-level knowledge (2–4 years):**
- Solid on Basic and most Intermediate questions across topics.
- Can implement features independently but may need guidance on architecture-level decisions.
- Has some real debugging stories, though may lack systematic diagnostic process.

**Strong 5–6 year developer (target for this role):**
- Comfortably clears Basic, handles most Intermediate questions fluently, and gets a meaningful portion of Advanced questions right — even if imperfectly reasoned.
- Explains trade-offs (not just "correct" answers) — e.g., why one approach over another given constraints.
- Has specific, detailed real-world stories for scenario questions (slow queries, memory leaks, production incidents) with a systematic diagnostic approach.
- Understands the "why" behind patterns (SOLID, DI, caching, resilience) rather than just applying them by rote.

**Senior/Architect-level knowledge (7+ years, often beyond this role's target):**
- Handles nearly all Advanced questions with nuance, including discussing when a "best practice" is actually the *wrong* choice for a given context.
- Thinks in terms of system-wide trade-offs (cost, team velocity, operational burden) — not just technical correctness.
- Can mentor through a problem, asking clarifying questions back, considering multiple valid solutions and weighing them.

**Practical tip:** The clearest signal isn't whether they get an Advanced question "right" — it's *how* they reason through it when they're unsure. A 5–6 year developer who says "I haven't hit that exact scenario, but here's how I'd approach investigating it" is a strong candidate. One who guesses confidently and incorrectly, or gives a purely textbook non-answer, is a weaker signal.

### 5. Practical Coding / Problem-Solving Questions (10–15)

These are meant to be worked through together (whiteboard, shared editor, or verbally) — not take-home assignments.

1. **FizzBuzz variant:** Write a function that returns "Fizz" for multiples of 3, "Buzz" for multiples of 5, "FizzBuzz" for both — then extend it to accept a configurable rule set (e.g., a dictionary of divisor → word). *(Tests: basic coding + ability to generalize a solution.)*
2. **Reverse a string without using built-in reverse methods.** Then ask: "What's the time/space complexity of your solution?"
3. **Given a list of orders, use LINQ to find the top 3 customers by total spend.** *(Tests: LINQ fluency — GroupBy, OrderByDescending, Take.)*
4. **Write a method to check if a string is a palindrome, ignoring case and non-alphanumeric characters.**
5. **Given an `IEnumerable<int>`, find duplicate values efficiently.** Then ask about time complexity of their approach vs. a nested-loop approach.
6. **Design a simple `IRepository<T>` interface and a basic in-memory implementation** — tests understanding of generics + interfaces.
7. **Write a SQL query to find the second-highest salary in an Employees table** (without using `LIMIT`/`TOP` naively) — tests window functions or subquery thinking.
8. **Given a deadlock scenario description (two stored procedures updating tables in opposite order), explain how you'd fix it.**
9. **Implement a basic retry mechanism with exponential backoff for an HTTP call** — tests resilience pattern understanding.
10. **Design a class hierarchy (or composition-based design) for a simple `Shape` area calculator (Circle, Rectangle, Triangle)** — tests OOP/SOLID application, watch for whether they default to inheritance or composition appropriately.
11. **Given a snippet with a `NullReferenceException`, find and fix the bug** — tests debugging under pressure.
12. **Write a LINQ query to detect the N+1 problem in a given EF Core code sample and fix it.**
13. **Design a basic rate limiter for an API endpoint** (conceptually or in code) — tests architecture + practical coding blend.
14. **Given a race condition scenario (two threads incrementing a shared counter), explain the bug and fix it** (e.g., using `lock` or `Interlocked`).
15. **Write a method to flatten a nested list/tree structure using recursion** — tests recursion comfort, a common gap even among experienced devs.

### 6. Red Flags: Signs of Exaggerated Experience

Watch for these patterns — any single one isn't disqualifying, but multiple together are a strong signal the candidate's resume overstates their hands-on depth:

1. **Can recite definitions fluently but can't apply them to a scenario.** E.g., defines SOLID perfectly but can't spot a violation in a code sample.
2. **No real production incident stories.** Someone with 5–6 years should have at least one memorable "things broke and I had to fix it" story for at least a couple of topics.
3. **Claims deep expertise in an unusually large number of unrelated technologies** (e.g., "expert" in Angular, React, AWS, Azure, microservices, and mobile) with no depth in any single one.
4. **Cannot explain *why* they made a technical choice** — only describes *what* they did, not trade-offs considered.
5. **Gets basic questions wrong but attempts to answer advanced ones with confident, generic buzzwords.** Genuine depth usually shows a consistent gradient — struggling on advanced but solid on basic/intermediate is normal; the reverse pattern is a red flag.
6. **Cannot walk through their own resume project in technical detail** — vague when asked "what was your specific contribution to this system?"
7. **Blames every past project's problems entirely on "bad management" or "legacy code" with no reflection on their own role or learning.**
8. **Uses correct terminology but the underlying explanation reveals a misunderstanding** — e.g., says "we used microservices" but describes a single deployable monolith with multiple internal classes.
9. **Cannot reason through a novel problem out loud** — freezes or goes silent rather than thinking through it verbally, even for simpler coding questions appropriate to their level.
10. **Inconsistent depth across claimed skills on the resume** — e.g., extremely detailed and fluent about one framework, but shallow/generic about another skill listed with equal prominence, suggesting the second was only lightly used or padded.
