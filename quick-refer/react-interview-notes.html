1. React Fundamentals

Concept

React is a JavaScript library (not a full framework) for building user interfaces using a component-based, declarative approach. Instead of manually manipulating the DOM (imperative), you describe what the UI should look like for a given state, and React figures out how to update the DOM efficiently.

Core ideas: - Declarative UI — describe the end state, not the steps to get there. - Component-based — UI split into independent, reusable pieces. - Virtual DOM — an in-memory representation of the UI used to compute minimal real-DOM updates. - Unidirectional data flow — data flows parent → child via props; child communicates back via callbacks.

Practical Example

// Imperative (vanilla JS) — you tell the browser HOW
const btn = document.createElement('button');
btn.textContent = 'Clicked 0 times';
let count = 0;
btn.addEventListener('click', () => {
  count++;
  btn.textContent = `Clicked ${count} times`;
});
document.body.appendChild(btn);

// Declarative (React) — you describe WHAT the UI looks like for a given state
function Counter() {
  const [count, setCount] = React.useState(0);
  return (
    <button onClick={() => setCount(count + 1)}>
      Clicked {count} times
    </button>
  );
}

Explanation

  • In vanilla JS, you manually track count and manually update textContent.
  • In React, count is state. When setCount is called, React re-renders the component function, computes the new Virtual DOM, diffs it against the previous one, and patches only the changed DOM node (the text inside the button).
  • Expected behavior: clicking the button always shows the correct, up-to-date count — React guarantees the UI is a pure function of state.

Interview Q&A

Q: Is React a framework or a library? A: A library. It only handles the view layer. Routing, state management, and HTTP are handled by additional libraries (React Router, Redux/Zustand, Axios), unlike frameworks like Angular which are batteries-included.

Q: What problem does React solve? A: Efficient, predictable UI updates for complex, frequently-changing interfaces, by replacing manual DOM manipulation with a declarative, component-based model backed by a diffing algorithm.

Q: What is the Virtual DOM and why is it faster? A: A lightweight JS object tree mirroring the real DOM. React diffs the new virtual tree against the previous one ("reconciliation") and applies only the minimal set of real DOM mutations, since direct DOM manipulation is expensive (layout/reflow/repaint).

Quick Revision

  • React = library, view layer only.
  • Declarative + component-based + Virtual DOM + unidirectional data flow.
  • State change → re-render → diff → minimal DOM patch.

Real-World Use Case

Any interactive UI: dashboards, SPAs, e-commerce product listings that filter/sort without full page reloads.

2. JSX

Concept

JSX (JavaScript XML) is syntactic sugar that lets you write HTML-like syntax inside JavaScript. It is not required to use React (you can use React.createElement directly) but makes component trees far more readable. JSX is compiled (by Babel) into React.createElement calls.

Practical Example

const element = <h1 className="title">Hello, {user.name}!</h1>;

// Babel compiles the above to:
const element = React.createElement(
  'h1',
  { className: 'title' },
  'Hello, ',
  user.name,
  '!'
);

function Greeting({ user }) {
  return (
    <div>
      {user ? <h1>Welcome back, {user.name}</h1> : <h1>Please log in</h1>}
    </div>
  );
}

Explanation

  • { } embeds any JavaScript expression (not statements) inside JSX.
  • JSX must return a single root element (or a Fragment <>...</>).
  • className instead of class, htmlFor instead of for — because JSX attributes map to DOM properties in camelCase, and class/for are reserved words in JS.
  • Every element in JSX ultimately becomes a React.createElement(type, props, ...children) call, which returns a plain JS object describing the element (this object IS the "virtual DOM node").

Interview Q&A

Q: Can you use if statements directly inside JSX? A: No — JSX only accepts expressions inside {}. Use ternaries, &&, or move logic above the return statement.

Q: Why do we need key prop when rendering lists in JSX? A: Covered in detail in Section 10, but briefly: it gives React a stable identity for each item across renders, so it can correctly match, reorder, add, or remove items during reconciliation instead of re-rendering everything.

Q: What does React.createElement return? A: A plain JavaScript object ({ type, props, key, ref, ... }) — a lightweight description of a DOM node or component instance, not an actual DOM node.

Quick Revision

  • JSX → React.createElement() calls (compiled by Babel).
  • Must return one root node (or <>fragment</>).
  • {} = JS expressions only, not statements.
  • camelCase attributes (onClick, className, tabIndex).

3. Components: Functional vs Class

Concept

A component is a reusable, isolated piece of UI. React historically supported class components (ES6 classes extending React.Component, with lifecycle methods) and now favors functional components (plain functions + Hooks, since React 16.8).

Practical Example

// Class Component (legacy but still asked in interviews)
class Welcome extends React.Component {
  constructor(props) {
    super(props);
    this.state = { visits: 0 };
  }
  componentDidMount() {
    this.setState({ visits: this.state.visits + 1 });
  }
  render() {
    return <h1>Hello, {this.props.name} (visit #{this.state.visits})</h1>;
  }
}

// Functional Component with Hooks (modern standard)
function Welcome({ name }) {
  const [visits, setVisits] = React.useState(0);
  React.useEffect(() => {
    setVisits(v => v + 1);
  }, []);
  return <h1>Hello, {name} (visit #{visits})</h1>;
}

Explanation

  • Class components need this binding, a constructor for state initialization, and separate lifecycle methods (componentDidMount, componentDidUpdate, etc.).
  • Functional components use Hooks (useState, useEffect) to achieve the same thing with less boilerplate, no this, and better logic reuse (custom hooks vs HOC/render-props gymnastics).
  • Both examples render an <h1> and increment a visit counter once on mount — expected output is identical.

Interview Q&A

Q: Why did React introduce Hooks? A: To solve: (1) reusing stateful logic without HOC/render-prop wrapper hell, (2) huge components split by lifecycle method rather than by concern, (3) confusing this binding in classes.

Q: Are class components deprecated? A: No, they're still fully supported, but Hooks are the recommended approach for new code, and most modern libraries/docs assume functional components.

Q: Can Hooks be used inside class components? A: No. Hooks only work inside functional components or other custom Hooks.

Q: What are the Rules of Hooks? A: (1) Only call Hooks at the top level — never inside loops, conditions, or nested functions. (2) Only call Hooks from React function components or custom Hooks. This is because React tracks Hooks by call order, not by name.

Quick Revision

  • Functional + Hooks = modern standard.
  • Rules of Hooks: top-level only, React functions only.
  • Class components: still valid, lifecycle methods, this binding needed.

Real-World Use Case

Legacy codebases (pre-2019) often have class components; new codebases and interviews for modern roles expect functional + Hooks fluency, but you should still be able to read/refactor class components.

4. Props vs State

Concept

  • Props ("properties"): data passed from parent to child. Read-only from the child's perspective (immutable within that component).
  • State: data owned and managed within a component, that can change over time and triggers a re-render when updated.

Practical Example

function App() {
  const [cartCount, setCartCount] = React.useState(0);
  return <Cart itemCount={cartCount} onAdd={() => setCartCount(c => c + 1)} />;
}

function Cart({ itemCount, onAdd }) {
  // itemCount is a PROP — Cart cannot modify it directly
  return (
    <div>
      <p>Items in cart: {itemCount}</p>
      <button onClick={onAdd}>Add Item</button>
    </div>
  );
}

Explanation

  • cartCount is state owned by App.
  • itemCount is a prop received by Cart — Cart cannot do itemCount = 5; it can only ask the parent to change it (via the onAdd callback), which is the essence of unidirectional data flow.
  • Clicking the button calls onAdd, which calls setCartCount in App, which re-renders App and passes the new itemCount down to Cart.

Interview Q&A

Q: Can a child component modify its own props? A: No — mutating props directly is an anti-pattern and React will not reflect the change; the source of truth remains the parent's state. The child should call a callback prop instead.

Q: What happens when state updates — does the whole app re-render? A: No. Only the component that owns the state and its descendants re-render (unless optimized with memo). Siblings and ancestors above the state owner do not re-render because of that state change.

Q: Is setState/the state setter synchronous? A: No, in React 18+ state updates are batched (even outside event handlers, due to automatic batching) — multiple setState calls in the same tick are merged into a single re-render for performance.

Quick Revision

Props State
Owned by Parent (passed to child) The component itself
Mutable? No (read-only in child) Yes (via setter)
Triggers re-render? Yes, when parent passes new prop values Yes, when updated
Analogy Function arguments Local variable with setState

Real-World Use Case

A <ProductCard price={product.price} onAddToCart={...} /> — price is a prop from a product list; whether the "Added ✓" checkmark shows is local state inside ProductCard.

5. Hooks — Core

5.1 useState

Concept: Adds local state to a functional component. Returns [value, setter].

function Counter() {
  const [count, setCount] = React.useState(0);

  // Functional update form — SAFE for updates based on previous state
  const increment = () => setCount(prev => prev + 1);

  return (
    <div>
      <p>{count}</p>
      <button onClick={increment}>+1</button>
      <button onClick={() => { increment(); increment(); }}>+2 (correct)</button>
      <button onClick={() => { setCount(count + 1); setCount(count + 1); }}>
        +2 (BUGGY — only adds 1)
      </button>
    </div>
  );
}

Explanation: Calling setCount(count + 1) twice in the same handler uses the same stale count from that render's closure both times, so it only increments by 1 net. Using the functional updater form setCount(prev => prev + 1) always operates on the latest pending value, so calling it twice correctly adds 2. This is one of the most common React interview gotchas.

Interview Q&A - Q: Why is my state not updating immediately after calling the setter? A: State updates are asynchronous/batched; the new value is available on the next render, not immediately after the call in the same function. - Q: When should you use the functional updater setState(prev => ...) vs setState(newValue)? A: Use the functional form whenever the new state depends on the previous state, especially inside loops, timeouts, or multiple updates in one handler, to avoid stale closures. - Q: Can you call useState conditionally? A: No — violates Rules of Hooks; must be called unconditionally at the top level.

Quick Revision - useState is async & batched. - Use functional updates for state-based-on-previous-state. - Initial value is only used on the first render (lazy initializer function form: useState(() => expensiveInit()) avoids recomputing it every render).

5.2 useEffect

Concept: Runs side effects (data fetching, subscriptions, manual DOM manipulation, timers) after render. Replaces componentDidMount, componentDidUpdate, and componentWillUnmount combined.

function UserProfile({ userId }) {
  const [user, setUser] = React.useState(null);

  React.useEffect(() => {
    let cancelled = false;
    setUser(null); // reset while loading new user
    fetchUser(userId).then(data => {
      if (!cancelled) setUser(data);
    });
    return () => { cancelled = true; }; // cleanup: avoid setting state on unmounted/stale request
  }, [userId]); // re-run whenever userId changes

  if (!user) return <p>Loading...</p>;
  return <h2>{user.name}</h2>;
}

Explanation: - The dependency array [userId] tells React to re-run the effect only when userId changes. - [] (empty array) → runs once after initial mount only (like componentDidMount). - No array at all → runs after every render (rarely what you want). - The returned function is the cleanup function, run before the effect re-runs and on unmount — critical for cancelling subscriptions/requests to avoid memory leaks or race conditions ("setting state on an unmounted component").

Interview Q&A - Q: Difference between useEffect and useLayoutEffect? A: useEffect runs asynchronously after the browser has painted; useLayoutEffect runs synchronously before paint, blocking visual updates — use it only when you must measure/mutate the DOM before the user sees a flicker (e.g., measuring an element's size to reposition a tooltip). - Q: What is a stale closure in useEffect? A: When the effect's callback captures an old value of state/props from the render it was created in because a variable was omitted from the dependency array, causing it to act on outdated data. - Q: Why does an empty dependency array [] sometimes cause bugs? A: If the effect uses props/state that can change, but [] says "never re-run," the effect keeps using the original values (stale closure) forever. - Q: How do you fetch data on mount and handle cleanup properly? A: Use useEffect(() => {...}, []) with an AbortController or a cancelled flag as shown above.

Quick Revision - Dependency array controls when effect re-runs: [] = once, [a,b] = on change of a/b, omitted = every render. - Always clean up subscriptions/timers/requests in the returned cleanup function. - useLayoutEffect = sync, before paint (rare, for DOM measurement). useEffect = async, after paint (common case).

Real-World Use Case: Fetching data when a route param changes, subscribing to WebSocket events, setting up setInterval timers, syncing with document.title.

5.3 useRef

Concept: Returns a mutable object { current: value } that persists across renders without causing a re-render when changed. Two main uses: (1) accessing DOM nodes directly, (2) storing any mutable value that shouldn't trigger re-renders (like a timer ID or previous value).

function TextInputWithFocusButton() {
  const inputRef = React.useRef(null);
  const renderCount = React.useRef(0);
  renderCount.current++; // mutating this does NOT cause a re-render

  return (
    <>
      <input ref={inputRef} type="text" />
      <button onClick={() => inputRef.current.focus()}>Focus the input</button>
      <p>This component rendered {renderCount.current} times</p>
    </>
  );
}

Explanation: inputRef.current gives direct access to the actual DOM <input> node after mount, letting you call imperative APIs like .focus() that have no declarative React equivalent. renderCount demonstrates a ref used as an instance variable — it survives re-renders but changing it never schedules a new render (unlike state).

Interview Q&A - Q: useRef vs useState — when to use which? A: Use useState when the value's change should be reflected in the UI (needs a re-render). Use useRef when you need to persist a value across renders but changing it should NOT trigger a re-render (DOM node reference, timer ID, previous prop value, mutable flags). - Q: Does updating ref.current cause a re-render? A: No, never — this is the key distinguishing feature from state. - Q: How would you access a child DOM node from a parent? A: Pass a ref down; for custom components you additionally need forwardRef (see Section 18) since refs aren't accepted as regular props by default.

Quick Revision - ref.current mutation ⇒ no re-render. - Use for: DOM access, storing timers/intervals, tracking previous values, avoiding stale closures in some patterns.

5.4 useContext

Concept: Lets a component read a value from the nearest matching Context.Provider above it in the tree, without prop drilling (passing props through many intermediate layers that don't need them).

const ThemeContext = React.createContext('light');

function App() {
  const [theme, setTheme] = React.useState('light');
  return (
    <ThemeContext.Provider value={theme}>
      <Toolbar />
      <button onClick={() => setTheme(t => (t === 'light' ? 'dark' : 'light'))}>
        Toggle Theme
      </button>
    </ThemeContext.Provider>
  );
}

function Toolbar() {
  return <ThemedButton />; // Toolbar doesn't need theme, just passes tree down
}

function ThemedButton() {
  const theme = React.useContext(ThemeContext); // read directly, no prop drilling
  return <button className={theme}>I am styled by theme context</button>;
}

Explanation: Without Context, theme would need to be passed as a prop through Toolbar even though Toolbar itself never uses it ("prop drilling"). useContext(ThemeContext) lets ThemedButton grab the value directly from the nearest <ThemeContext.Provider> ancestor. When theme state changes, every component consuming that context re-renders, regardless of how deep it is.

Interview Q&A - Q: What problem does Context solve? A: Prop drilling — passing data through many layers of components that don't themselves need it. - Q: Downside of Context? A: Every consumer re-renders whenever the Provider's value changes, even if the consumer only cares about part of the value — this can cause unnecessary re-renders in large trees; mitigated by splitting contexts or memoizing the provider value. - Q: Context vs Redux — when to choose which? A: Context is built-in and fine for low-frequency, simple global data (theme, auth user, locale). Redux/Zustand are better for complex, frequently-updated state with time-travel debugging, middleware, or where render-optimization matters, because they use selector-based subscriptions instead of re-rendering all consumers.

Quick Revision - Solves prop drilling. - All consumers re-render on Provider value change — memoize value with useMemo to avoid needless re-renders from new object references each render. - Best for: theme, auth/user, locale, low-frequency global settings.

6. Hooks — Performance

6.1 useMemo

Concept: Memoizes the result of an expensive calculation, recomputing it only when a dependency changes — avoiding recalculation on every render.

function ProductList({ products, searchTerm }) {
  const filteredProducts = React.useMemo(() => {
    console.log('Filtering...'); // only logs when products or searchTerm change
    return products.filter(p => p.name.toLowerCase().includes(searchTerm.toLowerCase()));
  }, [products, searchTerm]);

  return (
    <ul>
      {filteredProducts.map(p => <li key={p.id}>{p.name}</li>)}
    </ul>
  );
}

Explanation: Without useMemo, products.filter(...) would re-run on every render of ProductList, even ones caused by unrelated state changes (e.g., a parent re-rendering for a different reason). useMemo caches the array and only recomputes it when products or searchTerm actually change (reference or value differs from last render).

6.2 useCallback

Concept: Memoizes a function reference itself (not its result), so the same function identity is preserved across renders unless dependencies change. Important because in JS, () => {} creates a new function on every render by default.

function Parent() {
  const [count, setCount] = React.useState(0);
  const [text, setText] = React.useState('');

  // Without useCallback, handleClick is a NEW function every render,
  // causing Child (wrapped in React.memo) to re-render even when unrelated `text` changes.
  const handleClick = React.useCallback(() => {
    setCount(c => c + 1);
  }, []); // no dependencies — function never needs to change

  return (
    <>
      <input value={text} onChange={e => setText(e.target.value)} />
      <Child onClick={handleClick} count={count} />
    </>
  );
}

const Child = React.memo(function Child({ onClick, count }) {
  console.log('Child rendered');
  return <button onClick={onClick}>Count: {count}</button>;
});

Explanation: Typing in the <input> updates text state and re-renders Parent. Without useCallback, handleClick would be a brand-new function reference each time, and since Child is wrapped in React.memo (which does a shallow prop comparison), the new function reference would make Child think its props changed, causing an unnecessary re-render. With useCallback([]), handleClick keeps the same reference, so React.memo correctly skips re-rendering Child when only text changes.

6.3 React.memo

Concept: A higher-order component that skips re-rendering a component if its props haven't shallowly changed — the component-level equivalent of useMemo/useCallback.

const ExpensiveRow = React.memo(function ExpensiveRow({ item }) {
  console.log('Rendering row', item.id);
  return <li>{item.name}</li>;
});

Interview Q&A

Q: useMemo vs useCallback — what's the actual difference? A: useCallback(fn, deps) is literally useMemo(() => fn, deps) — it's useMemo specialized for caching functions. useMemo caches a computed value; useCallback caches a function reference.

Q: Does useMemo/useCallback guarantee the value is never recomputed? A: No — React may still discard the memoized cache in rare situations (e.g., under memory pressure in future React versions with features like the offscreen/memory-recycling capabilities). Treat them as a performance hint, not a semantic guarantee.

Q: Is useMemo always a good idea? A: No. Memoization itself has a cost (storing the value, comparing dependencies). For cheap calculations, useMemo can be slower than just recalculating. Use it only for genuinely expensive computations or to preserve reference equality for React.memo/dependency arrays.

Q: What does React.memo compare — deep or shallow? A: Shallow comparison by default (Object.is per prop). You can pass a custom comparison function as the second argument for deep/custom equality.

Q: Common mistake with React.memo + object/array props? A: Passing a new object/array/function literal as a prop (<Child style={{color:'red'}} />) creates a new reference every render, defeating memo's shallow comparison — must memoize the object with useMemo/useCallback or hoist it outside the component.

Quick Revision

Hook/API Memoizes Use when
useMemo A computed value Expensive calculations (filtering/sorting large lists, derived data)
useCallback A function reference Passing callbacks to memoized children, or as effect dependencies
React.memo Whole component render output Component re-renders often with same props (list items, pure display components)

Real-World Use Case

A data table with 10,000 rows: wrap each Row in React.memo, memoize the sort/filter logic with useMemo, and memoize event handlers with useCallback so scrolling/filtering doesn't re-render every row.

7. useReducer & Custom Hooks

7.1 useReducer

Concept: An alternative to useState for managing complex state logic involving multiple sub-values or where the next state depends on the previous one in structured ways — similar to Redux's reducer pattern, but local to a component.

const initialState = { count: 0, step: 1 };

function reducer(state, action) {
  switch (action.type) {
    case 'increment': return { ...state, count: state.count + state.step };
    case 'decrement': return { ...state, count: state.count - state.step };
    case 'setStep': return { ...state, step: action.payload };
    default: throw new Error(`Unknown action: ${action.type}`);
  }
}

function Counter() {
  const [state, dispatch] = React.useReducer(reducer, initialState);
  return (
    <div>
      <p>Count: {state.count} (step: {state.step})</p>
      <button onClick={() => dispatch({ type: 'increment' })}>+</button>
      <button onClick={() => dispatch({ type: 'decrement' })}>−</button>
      <input
        type="number"
        value={state.step}
        onChange={e => dispatch({ type: 'setStep', payload: Number(e.target.value) })}
      />
    </div>
  );
}

Explanation: dispatch sends an "action" object to the reducer function, which is a pure function (state, action) => newState. This centralizes all state transition logic in one place instead of scattering multiple setState calls, making complex updates easier to test and reason about.

Interview Q&A - Q: useState vs useReducer — when to pick which? A: useState for simple, independent values. useReducer when: state is a complex object/multiple sub-values that update together, the next state depends heavily on the previous state, or you want to centralize/test transition logic (similar shape to Redux). - Q: Is useReducer a replacement for Redux? A: Not exactly — useReducer manages local component state. Redux/Zustand manage global app state shared across the tree with additional tooling (devtools, middleware, persistence).

7.2 Custom Hooks

Concept: A custom Hook is a JavaScript function whose name starts with use and that calls other Hooks internally — a mechanism to extract and reuse stateful logic across components.

// Custom Hook: reusable logic for tracking window width
function useWindowWidth() {
  const [width, setWidth] = React.useState(window.innerWidth);
  React.useEffect(() => {
    const handleResize = () => setWidth(window.innerWidth);
    window.addEventListener('resize', handleResize);
    return () => window.removeEventListener('resize', handleResize);
  }, []);
  return width;
}

function ResponsiveComponent() {
  const width = useWindowWidth();
  return <p>{width < 768 ? 'Mobile view' : 'Desktop view'}</p>;
}

Explanation: useWindowWidth encapsulates the useState + useEffect + event-listener logic. Any component can call useWindowWidth() to get reactive access to window width — logic is reused without HOC/render-prop wrapping, and each component gets its own independent state (custom Hooks don't share state between callers, only the logic).

Interview Q&A - Q: Do two components using the same custom Hook share state? A: No — each call to the custom Hook creates completely independent state instances; only the logic is shared, not the data. - Q: What's the naming convention and why does it matter? A: Must start with use (e.g., useFetch) — this is a convention enforced by ESLint's react-hooks plugin so it knows to apply Rules of Hooks checks to your function. - Q: Give an example of a common custom hook you'd write. A: useFetch(url) (data fetching with loading/error state), useLocalStorage(key, initialValue), useDebounce(value, delay), usePrevious(value).

Quick Revision

  • Custom Hooks = reusable logic, not shared state.
  • Must start with use; can call other Hooks inside.
  • useReducer: complex/related state transitions, action-based, pure reducer function.

8. Component Lifecycle

Concept

Class components expose explicit lifecycle methods across three phases: Mounting, Updating, Unmounting. Functional components achieve the same via useEffect with different dependency arrays.

Mapping Table (frequently asked)

Class Lifecycle Method Hook Equivalent When it runs
constructor useState(initialValue) Before first render — init state
componentDidMount useEffect(() => {...}, []) Once, after first render
componentDidUpdate useEffect(() => {...}, [dep1, dep2]) After updates, when deps change
componentWillUnmount useEffect(() => { return () => {...} }, []) (the cleanup fn) Before unmount
shouldComponentUpdate React.memo(Component) Controls re-render decision
getDerivedStateFromProps Compute directly during render, or useEffect Sync state from props
componentDidCatch / getDerivedStateFromError No Hook equivalent — must use a class-based Error Boundary Catch render errors

Practical Example

class Timer extends React.Component {
  state = { seconds: 0 };

  componentDidMount() {
    this.interval = setInterval(() => {
      this.setState(prev => ({ seconds: prev.seconds + 1 }));
    }, 1000);
  }

  componentWillUnmount() {
    clearInterval(this.interval); // cleanup — prevents memory leak
  }

  render() {
    return <p>Seconds: {this.state.seconds}</p>;
  }
}

// Equivalent with Hooks
function Timer() {
  const [seconds, setSeconds] = React.useState(0);

  React.useEffect(() => {
    const interval = setInterval(() => setSeconds(s => s + 1), 1000);
    return () => clearInterval(interval); // cleanup, same purpose as componentWillUnmount
  }, []);

  return <p>Seconds: {seconds}</p>;
}

Explanation

Both versions start a setInterval once when the component mounts, and clean it up when it unmounts, preventing the classic memory leak of an interval that keeps running (and trying to call setState) after the component is gone.

Interview Q&A

Q: Why is there no Hook equivalent to componentDidCatch? A: Error Boundaries rely on lifecycle methods (static getDerivedStateFromError, componentDidCatch) that don't have Hook equivalents yet — you must still use a class component to build an Error Boundary (see Section 15).

Q: What order do lifecycle methods run in during mount? A: constructor → getDerivedStateFromProps → render → componentDidMount.

**Q: How do you replicate componentDidUpdate-only-for-a-specific-propbehavior with hooks?** A:useEffect(() => {...}, [specificProp])— but note this *also* runs on mount, unlikecomponentDidUpdatewhich only fires on updates; if you truly need "update only," track a ref flag (e.g.,isFirstRender`) to skip the first invocation.

Quick Revision

  • Mount → Update → Unmount = three phases.
  • useEffect([]) ≈ mount+unmount only; useEffect([deps]) ≈ mount+update on dep change.
  • Error boundaries still require class components.

9. Event Handling in React

Concept

React wraps native DOM events in a cross-browser wrapper called SyntheticEvent (in React 17+ this is attached at the root container, not document, improving multi-React-version compatibility). Handlers are passed as camelCase props (onClick, onChange) receiving a function reference, not a string.

Practical Example

function SearchBox() {
  const [query, setQuery] = React.useState('');

  function handleChange(e) {
    setQuery(e.target.value); // e is a SyntheticEvent
  }

  function handleSubmit(e) {
    e.preventDefault(); // prevent full page reload on form submit
    console.log('Searching for:', query);
  }

  return (
    <form onSubmit={handleSubmit}>
      <input value={query} onChange={handleChange} />
      <button type="submit">Search</button>
    </form>
  );
}

Explanation

  • onChange fires on every keystroke (unlike native onchange, which only fires on blur) because React normalizes it to behave like an input event.
  • e.preventDefault() stops the browser's default full-page form submission (which would reload the page and discard React state).
  • Passing onClick={handleClick} (reference) vs onClick={handleClick()} (invocation, wrong — calls immediately during render) is a very common beginner mistake.

Interview Q&A

Q: What is a SyntheticEvent? A: React's cross-browser wrapper around the native event object, normalizing properties/behavior across browsers, pooled for performance in older React versions (pooling was removed in React 17+).

Q: onClick={handleClick} vs onClick={() => handleClick(id)} — difference? A: The first passes the function reference directly (called by React on click). The second wraps it in an inline arrow function so you can pass arguments — but creates a new function every render (relevant for React.memo optimization discussions).

Q: How do you stop event bubbling in React? A: e.stopPropagation() inside the handler, same conceptual API as native DOM, works because SyntheticEvents implement the same interface.

Quick Revision

  • Always pass a function reference, not a call (onClick={fn} not onClick={fn()}).
  • e.preventDefault() / e.stopPropagation() work as expected on SyntheticEvent.
  • React 17+ attaches listeners to the root DOM container, not document.

10. Conditional Rendering, Lists & Keys

Concept

  • Conditional rendering: showing different JSX based on state/props, via ternaries, &&, if above return, or a lookup object.
  • Lists: rendering arrays of data with .map().
  • Keys: a special string prop React uses to identify which array items changed/added/removed, critical for correct and efficient reconciliation.

Practical Example

function TodoList({ todos, isLoading }) {
  if (isLoading) return <Spinner />; // early return pattern

  if (todos.length === 0) {
    return <p>No todos yet!</p>;
  }

  return (
    <ul>
      {todos.map(todo => (
        <li key={todo.id}>
          {todo.completed ? <s>{todo.text}</s> : todo.text}
        </li>
      ))}
    </ul>
  );
}

Explanation

key={todo.id} (a stable, unique ID from data) lets React match each <li> across renders correctly even if the array is reordered, filtered, or items are added/removed in the middle. Without a stable key, React falls back to matching by index, which can cause wrong DOM reuse — e.g., input values or component state "sticking" to the wrong row after a reorder/delete.

Interview Q&A

Q: Why shouldn't you use array index as key? A: If the list can be reordered, filtered, or have items inserted/removed anywhere but the end, using the index as key causes React to misattribute state/DOM (e.g., a text input's typed value appears on the wrong row after deleting an earlier row), because the "identity" of index 2 silently refers to a different data item after the array shifts.

Q: When IS index-as-key acceptable? A: Only when the list is static, never reordered, never filtered, and has no items inserted/removed in the middle — e.g., a fixed, unchanging list of labels.

Q: What happens if you don't provide a key at all? A: React will use the array index by default and log a console warning ("Each child in a list should have a unique key prop"), with the same risks as explicitly using index.

Q: {condition && <Component />} — gotcha to know? A: If condition is 0 (a falsy number, not boolean), React renders the literal 0 on the screen because 0 && <X/> evaluates to 0, not false. Fix: use condition > 0 && <X/> or Boolean(condition) && <X/>.

Quick Revision

  • Keys must be stable, unique, and derived from data (not Math.random(), not array index for dynamic lists).
  • && short-circuit gotcha with falsy numbers (0, NaN) rendering literally.
  • Keys are used only by React internally — not accessible via props.key inside the component.

Comparison: Ways to Conditionally Render

Technique Best for
condition ? <A/> : <B/> Two mutually exclusive branches
condition && <A/> Show or show-nothing
Early return null / return <X/> Guard clauses at top of component
Lookup object {status: {loading: <Spinner/>, error: <Err/>}}[state] 3+ branches, avoids long if/else chains

11. Forms — Controlled vs Uncontrolled

Concept

  • Controlled component: form input's value is driven by React state (value={state} + onChange) — React is the "single source of truth."
  • Uncontrolled component: form input manages its own state internally in the DOM; React reads the value only when needed, via a ref.

Practical Example

// Controlled
function ControlledForm() {
  const [name, setName] = React.useState('');
  return (
    <input value={name} onChange={e => setName(e.target.value)} />
  );
}

// Uncontrolled
function UncontrolledForm() {
  const nameRef = React.useRef();

  function handleSubmit(e) {
    e.preventDefault();
    console.log('Submitted:', nameRef.current.value); // read DOM value only on submit
  }

  return (
    <form onSubmit={handleSubmit}>
      <input ref={nameRef} defaultValue="" />
      <button type="submit">Submit</button>
    </form>
  );
}

Explanation

  • In the controlled version, every keystroke goes through React state, so name always reflects the exact input value, and you can validate/transform/disable the submit button in real time.
  • In the uncontrolled version, the DOM <input> manages its own value; React only reads it via nameRef.current.value when the form is submitted, similar to plain HTML forms with less re-render overhead per keystroke.

Interview Q&A

Q: Controlled vs uncontrolled — when to choose which? A: Controlled for: instant validation, conditional disabling, formatting-as-you-type, or syncing input with other UI. Uncontrolled for: simple forms, file inputs (<input type="file"> must be uncontrolled — its value can't be set programmatically for security reasons), or integrating with non-React code/performance-sensitive large forms.

Q: Why must <input type="file"> always be uncontrolled? A: For security reasons the browser doesn't allow JS to set a file input's value; you can only read it via ref or the onChange event's e.target.files.

Q: How do you reset an uncontrolled form? A: Call formRef.current.reset() (native DOM form reset) or remount the component by changing its key.

Q: Common performance issue with controlled forms with many fields? A: Every keystroke re-renders the whole form component; for very large forms, this can be mitigated by splitting fields into separate components, using useReducer, or using an uncontrolled approach with libraries like React Hook Form (which minimizes re-renders via refs + subscription).

Quick Revision

Controlled Uncontrolled
Source of truth React state The DOM
Access value state variable ref.current.value
Real-time validation Easy Harder (must read via ref on each event)
Re-renders per keystroke Yes No
File inputs N/A — cannot be controlled Required

Real-World Use Case

Login/signup forms with real-time validation → controlled. A simple one-off "upload a file" widget or performance-critical form with hundreds of fields → uncontrolled or a library like React Hook Form.

12. Context API & State Management

Concept

As apps grow, "where should this state live?" becomes a key architectural question. Options, roughly in order of scope: 1. Local state (useState/useReducer) — data used by one component/its direct children. 2. Lifted state — moved up to the nearest common ancestor when siblings need to share it. 3. Context API — global-ish data needed by many components at different depths, low update frequency. 4. External state library (Redux, Zustand, Jotai, Recoil) — complex, frequently-updated, cross-cutting global state with devtools/middleware needs.

Practical Example — Combining useReducer + Context (a common interview pattern: "build a mini Redux")

const CartContext = React.createContext();

function cartReducer(state, action) {
  switch (action.type) {
    case 'add': return [...state, action.item];
    case 'remove': return state.filter(item => item.id !== action.id);
    default: return state;
  }
}

function CartProvider({ children }) {
  const [cart, dispatch] = React.useReducer(cartReducer, []);
  const value = React.useMemo(() => ({ cart, dispatch }), [cart]); // memoize to avoid re-renders
  return <CartContext.Provider value={value}>{children}</CartContext.Provider>;
}

function useCart() {
  const context = React.useContext(CartContext);
  if (!context) throw new Error('useCart must be used within a CartProvider');
  return context;
}

// Usage anywhere in the tree:
function AddToCartButton({ product }) {
  const { dispatch } = useCart();
  return <button onClick={() => dispatch({ type: 'add', item: product })}>Add to Cart</button>;
}

Explanation

This pattern (useReducer + Context + a custom useX hook) gives you Redux-like global state management using only built-in React APIs — a very common thing to be asked to implement live in interviews. React.useMemo around the context value prevents creating a new object on every CartProvider render, which would otherwise cause every consumer to re-render even if cart itself hasn't changed.

Interview Q&A

Q: "Build me a simple global state solution without Redux" — what do you reach for? A: useReducer + Context + a custom hook wrapping useContext with an error check for "used outside provider," exactly as above.

Q: Why wrap the custom hook (useCart) with an error check? A: Fails fast with a clear error message if a developer forgets to wrap their component tree in <CartProvider>, instead of a confusing undefined.dispatch is not a function error later.

Q: What's the main scaling limitation of Context for state management? A: All consumers re-render on any value change (no fine-grained/selector-based subscriptions like Redux+useSelector or Zustand), and there's no built-in devtools/time-travel debugging/middleware.

Quick Revision

  • Escalation path: local state → lifted state → Context → external library.
  • Always memoize Context Provider value if it's an object/array.
  • useReducer + Context = "poor man's Redux," commonly asked to implement live.

13. Redux / Redux Toolkit / Zustand

Concept

Redux is a predictable state container based on three principles: (1) single source of truth (one store), (2) state is read-only (changed only via dispatched actions), (3) changes are made with pure reducer functions. Redux Toolkit (RTK) is the modern, official, opinionated way to write Redux with far less boilerplate. Zustand is a minimal, hook-based alternative state library, popular for its simplicity.

Practical Example — Redux Toolkit

// counterSlice.js
import { createSlice } from '@reduxjs/toolkit';

const counterSlice = createSlice({
  name: 'counter',
  initialState: { value: 0 },
  reducers: {
    incremented: state => { state.value += 1; }, // "mutating" syntax — safe due to Immer under the hood
    decremented: state => { state.value -= 1; },
  },
});

export const { incremented, decremented } = counterSlice.actions;
export default counterSlice.reducer;

// store.js
import { configureStore } from '@reduxjs/toolkit';
import counterReducer from './counterSlice';
export const store = configureStore({ reducer: { counter: counterReducer } });

// Component
import { useSelector, useDispatch } from 'react-redux';
import { incremented } from './counterSlice';

function Counter() {
  const count = useSelector(state => state.counter.value); // selector — only re-renders if this slice changes
  const dispatch = useDispatch();
  return <button onClick={() => dispatch(incremented())}>{count}</button>;
}

Practical Example — Zustand (much less boilerplate)

import { create } from 'zustand';

const useCounterStore = create(set => ({
  count: 0,
  increment: () => set(state => ({ count: state.count + 1 })),
}));

function Counter() {
  const count = useCounterStore(state => state.count); // selector — component only re-renders on `count` changes
  const increment = useCounterStore(state => state.increment);
  return <button onClick={increment}>{count}</button>;
}

Explanation

  • In RTK, state.value += 1 looks like mutation but Redux Toolkit uses Immer internally, which turns this into a safe, immutable update behind the scenes — this addresses the classic "Redux is too much boilerplate/never mutate state directly" pain point.
  • useSelector/Zustand's selector function subscribes the component only to the specific slice of state it needs — the component re-renders only when that slice changes, not on every store update (this is the key advantage over plain Context, which re-renders all consumers on any value change).

Interview Q&A

Q: Why use Redux/Zustand over Context for state management? A: Selector-based subscriptions (re-render only what changed), devtools with time-travel debugging, middleware (logging, async thunks/sagas), and better performance at scale for frequently-updated state.

Q: What are the three principles of Redux? A: Single source of truth (one store), state is read-only (only changed via actions), changes made with pure reducer functions.

Q: How does Redux Toolkit reduce boilerplate compared to "classic" Redux? A: createSlice auto-generates action creators and action types from reducer names; Immer allows writing "mutating" logic safely; configureStore sets up devtools and common middleware (like redux-thunk) by default.

Q: Redux vs Zustand — key differences? A: Redux: more structure/ceremony, mature ecosystem, middleware (sagas/thunks), strong devtools, good for large teams needing conventions. Zustand: minimal API, no boilerplate/providers required, hook-based, faster to set up for small-to-medium apps, less opinionated structure.

Q: What is a "thunk" in Redux? A: A function (instead of a plain action object) dispatched to handle async logic (e.g., API calls) before dispatching the actual action — enabled via redux-thunk middleware, included by default in RTK's configureStore.

Quick Revision

  • Redux: single store, read-only state, pure reducers.
  • RTK: createSlice, Immer-powered "mutation" syntax, less boilerplate, default middleware.
  • useSelector/Zustand selectors: fine-grained re-render control, unlike Context.
  • Zustand: no <Provider> needed, minimal API, great for small/medium apps.

Real-World Use Case

Large e-commerce app: cart, auth, wishlist, filters all in Redux/RTK with devtools for debugging complex state transitions across many features and teams. Small dashboard app: Zustand for simplicity without ceremony.

14. React Router

Concept

React Router is the standard library for client-side routing in React SPAs — mapping URL paths to components without full page reloads.

Practical Example (React Router v6+)

import { BrowserRouter, Routes, Route, Link, useParams, useNavigate } from 'react-router-dom';

function App() {
  return (
    <BrowserRouter>
      <nav>
        <Link to="/">Home</Link>
        <Link to="/products/42">Product 42</Link>
      </nav>
      <Routes>
        <Route path="/" element={<Home />} />
        <Route path="/products/:id" element={<ProductDetail />} />
        <Route path="*" element={<NotFound />} /> {/* catch-all 404 */}
      </Routes>
    </BrowserRouter>
  );
}

function ProductDetail() {
  const { id } = useParams(); // read the :id URL segment
  const navigate = useNavigate();
  return (
    <div>
      <p>Viewing product {id}</p>
      <button onClick={() => navigate(-1)}>Go Back</button>
    </div>
  );
}

Explanation

  • <Link to="..."> renders an <a> tag but intercepts the click to update the URL via the History API without a full page reload, preserving app state (unlike a plain <a href>).
  • useParams() extracts dynamic segments (:id) from the matched route.
  • useNavigate() gives programmatic navigation (e.g., after form submit, redirect on auth failure).
  • The path="*" catch-all route matches anything not matched above it — must be listed last.

Interview Q&A

Q: <Link> vs <a href> — why does it matter? A: <a href> triggers a full browser page reload (losing all React state, re-downloading JS bundles). <Link> updates the URL via the History API and lets React Router swap components client-side, keeping the SPA experience intact.

Q: How do you protect a route (require authentication)? A: Wrap the route element in a component that checks auth state and either renders the children or a <Navigate to="/login" /> redirect — a common pattern is a <ProtectedRoute> wrapper component.

Q: How does nested routing work in v6? A: Using <Outlet /> inside a parent route's element as a placeholder for matched child routes, combined with nested <Route> definitions — enables shared layouts (e.g., a sidebar that persists across child pages).

Q: What's the difference between BrowserRouter and HashRouter? A: BrowserRouter uses the HTML5 History API for clean URLs (/products/42) but requires server configuration to handle deep links (serve index.html for all routes). HashRouter uses a URL hash (/#/products/42) which works without server config since the hash never gets sent to the server, but is considered less clean/SEO-friendly.

Quick Revision

  • <Link>/<NavLink> = client-side nav, no reload.
  • useParams, useNavigate, useLocation, useSearchParams = key hooks.
  • <Outlet/> for nested layouts.
  • BrowserRouter needs server rewrite rules for deep links; HashRouter doesn't but is less clean.

15. Error Boundaries

Concept

A component that catches JavaScript errors thrown during rendering in its child tree, logs them, and displays a fallback UI instead of crashing the whole app. Must be a class component (no Hook equivalent exists yet). Does NOT catch errors in event handlers, async code, SSR, or errors thrown in the boundary itself.

Practical Example

class ErrorBoundary extends React.Component {
  state = { hasError: false };

  static getDerivedStateFromError(error) {
    return { hasError: true }; // update state so next render shows fallback UI
  }

  componentDidCatch(error, info) {
    console.error('Logged to error service:', error, info.componentStack);
  }

  render() {
    if (this.state.hasError) {
      return <h2>Something went wrong. Please refresh.</h2>;
    }
    return this.props.children;
  }
}

// Usage
function App() {
  return (
    <ErrorBoundary>
      <BuggyComponent />
    </ErrorBoundary>
  );
}

Explanation

If BuggyComponent throws during rendering (e.g., accessing a property of undefined), React unmounts the tree below the nearest Error Boundary and calls getDerivedStateFromError (to compute fallback state) and componentDidCatch (for logging side effects), so the fallback UI (<h2>Something went wrong...</h2>) renders instead of a blank white screen / full app crash.

Interview Q&A

Q: What errors does an Error Boundary NOT catch? A: Errors in event handlers (use plain try/catch there), errors in asynchronous code (setTimeout, promises — unless the resulting setState throws during render), server-side rendering errors, and errors thrown inside the Error Boundary itself.

Q: Why is there no useErrorBoundary hook? A: Catching render errors requires intercepting React's render/commit lifecycle in a way current Hooks don't expose; you must use the class lifecycle methods getDerivedStateFromError/componentDidCatch. (Third-party libraries like react-error-boundary wrap this class internally and expose a hook-friendly API.)

Q: How granular should Error Boundaries be? A: Wrap logical sections (e.g., each widget/route) rather than one boundary for the whole app, so one broken widget doesn't take down the entire page — a common best practice.

Quick Revision

  • Class component only; getDerivedStateFromError (render fallback) + componentDidCatch (side-effect logging).
  • Does NOT catch: event handler errors, async errors, SSR errors.
  • Best practice: multiple granular boundaries around independent sections, not just one global boundary.

16. Higher-Order Components (HOC) & Render Props

Concept

Both are pre-Hooks patterns for reusing component logic. - HOC: a function that takes a component and returns a new, enhanced component: withX(Component) => EnhancedComponent. - Render Props: a component that takes a function as a prop (often called children or render) and calls it with data, letting the consumer decide what to render.

Practical Example — HOC

function withLoading(WrappedComponent) {
  return function WithLoadingComponent({ isLoading, ...props }) {
    if (isLoading) return <p>Loading...</p>;
    return <WrappedComponent {...props} />;
  };
}

const UserListWithLoading = withLoading(UserList);
// Usage: <UserListWithLoading isLoading={true} users={[]} />

Practical Example — Render Props

function MouseTracker({ render }) {
  const [position, setPosition] = React.useState({ x: 0, y: 0 });
  function handleMouseMove(e) {
    setPosition({ x: e.clientX, y: e.clientY });
  }
  return <div onMouseMove={handleMouseMove}>{render(position)}</div>;
}

// Usage
<MouseTracker render={({ x, y }) => <p>Mouse at ({x}, {y})</p>} />

Explanation

Both patterns solve "share this logic across multiple components" without duplicating code. withLoading wraps any component to inject loading behavior. MouseTracker tracks mouse position internally but delegates the actual rendering to whatever function is passed in, so different consumers can display the position however they like.

Interview Q&A

Q: Why have custom Hooks mostly replaced HOCs and render props? A: Both patterns cause "wrapper hell" — deeply nested component trees in devtools, prop name collisions between multiple HOCs, and harder-to-trace data flow. Custom Hooks achieve the same logic reuse with flat function composition and no extra component nesting/wrapper components in the tree.

Q: What's a common gotcha with HOCs? A: Forgetting to forward refs (solved with React.forwardRef inside the HOC) and forgetting to copy over static methods from the wrapped component (libraries like hoist-non-react-statics handle this).

Q: Are HOCs/render props deprecated? A: No, still valid and occasionally the right tool (e.g., some library APIs, or class-component codebases where Hooks aren't available), but for new code, custom Hooks are almost always preferred.

Quick Revision

  • HOC: Component => EnhancedComponent. Watch for naming collisions & ref forwarding.
  • Render props: pass a function as a prop to control rendering.
  • Both largely superseded by custom Hooks, but still appear in older codebases/some libraries (e.g., React Router v5's <Route render={...}>, Formik).

17. Portals

Concept

ReactDOM.createPortal(child, domNode) renders a child into a different part of the actual DOM tree than its parent component, while still behaving like a normal React child for context, event bubbling, and lifecycle purposes.

Practical Example

function Modal({ children, onClose }) {
  return ReactDOM.createPortal(
    <div className="modal-overlay" onClick={onClose}>
      <div className="modal-content" onClick={e => e.stopPropagation()}>
        {children}
      </div>
    </div>,
    document.getElementById('modal-root') // a sibling <div> outside the main #root, defined in index.html
  );
}

Explanation

Even though the modal's DOM nodes live under #modal-root (outside the app's #root div — necessary to escape overflow:hidden/z-index stacking issues from parent containers), it still participates in the same React tree: events fired inside it bubble up to React parent handlers as if it were rendered inline, and it can still consume Context from ancestors.

Interview Q&A

Q: Why use a Portal instead of just rendering normally? A: To escape CSS constraints of a parent container (e.g., overflow: hidden, z-index stacking contexts) for modals, tooltips, dropdowns, and toast notifications that need to visually "float" above everything regardless of DOM nesting.

Q: Does event bubbling still work "normally" through a portal? A: Yes — React bubbles events through the React component tree, not the DOM tree, so a click inside a portaled modal still bubbles to React event handlers on its logical parent, even though it's a DOM sibling, not a DOM descendant.

Q: Does a Portal break Context? A: No — Context works based on the component tree, unaffected by where the DOM node physically lives.

Quick Revision

  • Use case: modals, tooltips, dropdowns, toasts — anything needing to break out of parent CSS stacking/overflow.
  • DOM location differs from React tree location; events & context still follow the React tree.

18. Refs, forwardRef & useImperativeHandle

Concept

  • By default, refs cannot be passed to custom components as a regular prop (ref is special and intercepted by React).
  • React.forwardRef lets a custom component accept a ref and forward it to an inner DOM node.
  • useImperativeHandle customizes what the parent's ref actually exposes, instead of the raw DOM node.

Practical Example

const FancyInput = React.forwardRef(function FancyInput(props, ref) {
  const inputRef = React.useRef();

  React.useImperativeHandle(ref, () => ({
    focus: () => inputRef.current.focus(),
    clear: () => { inputRef.current.value = ''; },
    // Note: does NOT expose the full DOM node — only this controlled API
  }));

  return <input ref={inputRef} {...props} />;
});

function Parent() {
  const fancyRef = React.useRef();
  return (
    <>
      <FancyInput ref={fancyRef} />
      <button onClick={() => fancyRef.current.focus()}>Focus</button>
      <button onClick={() => fancyRef.current.clear()}>Clear</button>
    </>
  );
}

Explanation

Without forwardRef, <FancyInput ref={fancyRef}/> would fail silently (ref would be null inside FancyInput, since ref isn't passed through props like other attributes). useImperativeHandle restricts what the parent can do via the ref to exactly .focus() and .clear(), rather than exposing the entire raw DOM node — an encapsulation best practice for reusable component libraries.

Interview Q&A

Q: Why can't you just pass ref as a normal prop? A: React treats ref (and key) as special reserved props consumed by React itself for its own bookkeeping — they are never forwarded through props.ref to the component function, so you must explicitly opt in with forwardRef.

Q: When would you use useImperativeHandle instead of just forwarding the raw DOM ref? A: When you want to expose a controlled, minimal API to parents (e.g., only .focus()/.reset()) rather than the entire DOM node, protecting encapsulation in a reusable component library.

Q: In React 19, is forwardRef still necessary? A: React 19 allows ref to be passed as a regular prop directly to function components without forwardRef — but forwardRef is still supported for backward compatibility and is important to know for interviews covering React 16–18 codebases (the vast majority in production today).

Quick Revision

  • ref and key are NOT regular props — never passed through props.
  • forwardRef(Component) — required to accept refs on custom (non-DOM) components (pre React 19).
  • useImperativeHandle — expose a curated API via ref instead of the raw node.

19. Reconciliation, Virtual DOM & Fiber

Concept

  • Reconciliation: the algorithm React uses to diff the new Virtual DOM tree against the previous one and determine the minimal set of real DOM mutations needed.
  • Fiber: React's internal reconciliation engine (since React 16), which reworked the old synchronous, recursive "stack" algorithm into an incremental, interruptible one, enabling features like time-slicing, Concurrent Mode/Concurrent Rendering, and prioritized updates.

Explanation (conceptual — mostly discussion-based, less code)

React's diffing makes two key simplifying assumptions (heuristics) instead of a full generic tree-diff (which would be O(n³) and too slow): 1. Different element types produce different trees — if a <div> becomes a <span> at the same position, React tears down the old subtree entirely and builds a new one, rather than trying to patch it. 2. Keys hint at stable identity across renders for list children — enabling matching by key instead of by position (this is why keys matter, tying back to Section 10).

Fiber breaks rendering work into units ("fibers," one per component) that can be paused, resumed, aborted, or reprioritized — e.g., React can pause rendering a big update to handle a more urgent one (like text input), then resume, instead of blocking the main thread for the whole update in one synchronous pass (which was the pre-Fiber "stack reconciler" behavior).

Interview Q&A

Q: What are the two phases of Fiber's rendering process? A: Render/Reconciliation phase (can be paused/aborted, computes what changed — no DOM mutations yet, "pure" and interruptible) and Commit phase (applies the DOM mutations — synchronous, cannot be interrupted, so the user never sees a half-updated UI).

Q: Why did React move from the old "stack" reconciler to Fiber? A: The old recursive stack-based algorithm was synchronous and couldn't be paused once started, causing dropped frames/jank on large updates since it blocked the main thread until the entire tree was processed. Fiber allows incremental, interruptible rendering with prioritization (urgent updates like typing can interrupt less urgent ones like a big list re-render).

Q: Does changing an element's type at the same position preserve component state? A: No — React unmounts and destroys state for the entire old subtree if the element type differs (e.g., <Comp1/> swapped for <Comp2/> at the same JSX position resets all descendant state), even if they render visually similar output.

Q: What's the significance of "keys" in reconciliation, technically? A: They override React's default positional matching heuristic for list children, letting React match by identity (key) even when order/position changes, correctly preserving or discarding component state and DOM nodes.

Quick Revision

  • Reconciliation = diffing algorithm; Fiber = the engine that makes it incremental/interruptible/prioritized.
  • Two Fiber phases: Render (interruptible) → Commit (synchronous, atomic).
  • Different element type at same position ⇒ full unmount/remount, state lost.
  • Keys enable identity-based matching instead of position-based matching.

20. Performance Optimization Techniques

Concept

A checklist of techniques to reduce unnecessary re-renders and work, roughly in order of typical impact:

  1. React.memo — skip re-render if props are shallow-equal (Section 6).
  2. useMemo/useCallback — stabilize references/expensive computations (Section 6).
  3. Code-splitting/lazy loading — reduce initial bundle size (Section 21).
  4. Virtualization (e.g., react-window/react-virtualized) — render only visible rows of huge lists.
  5. Avoid inline object/array/function literals passed as props to memoized children (creates new references every render).
  6. Move state down ("state colocation") — keep state as close as possible to where it's used, so unrelated siblings don't re-render.
  7. Composition over memo gymnastics — pass children as props instead of rendering them inside the parent, so the parent's re-render doesn't force the child to re-render.

Practical Example — "Move state down" / composition to avoid unnecessary re-renders

// BEFORE: typing in the input re-renders the entire ExpensiveChart, even though it doesn't depend on text
function Bad() {
  const [text, setText] = React.useState('');
  return (
    <div>
      <input value={text} onChange={e => setText(e.target.value)} />
      <ExpensiveChart /> {/* re-renders on every keystroke, unnecessarily */}
    </div>
  );
}

// AFTER: colocate the input's state inside its own component
function SearchInput() {
  const [text, setText] = React.useState('');
  return <input value={text} onChange={e => setText(e.target.value)} />;
}

function Good() {
  return (
    <div>
      <SearchInput />
      <ExpensiveChart /> {/* no longer re-renders when typing, since it's a sibling, unaffected by SearchInput's state */}
    </div>
  );
}

// ALTERNATIVE: composition — pass ExpensiveChart as `children`
function GoodWithComposition({ children }) {
  const [text, setText] = React.useState('');
  return (
    <div>
      <input value={text} onChange={e => setText(e.target.value)} />
      {children} {/* children reference doesn't change, so React skips re-rendering it even though parent re-renders */}
    </div>
  );
}
// Usage: <GoodWithComposition><ExpensiveChart /></GoodWithComposition>

Explanation

In Bad, ExpensiveChart is a direct child rendered from within the same component that owns text state, so every re-render of the parent (on every keystroke) re-renders ExpensiveChart too (unless it's wrapped in memo). Moving the input's state into its own leaf component (Good), or passing ExpensiveChart in via children/props (GoodWithComposition), avoids the unnecessary re-render without needing React.memo at all — because in the composition version, the children prop reference doesn't change between GoodWithComposition's own re-renders (React doesn't recreate the JSX passed to it from further up the tree).

Interview Q&A

Q: How do you profile which components are re-rendering unnecessarily? A: React DevTools Profiler tab — record an interaction, inspect the flame graph, look for components that rendered without their props/state changing (can be highlighted via the "Highlight updates when components render" setting).

Q: React.memo didn't prevent a re-render — why? A: Almost always because a prop is a new object/array/function reference every render (inline arrow functions, object literals, or unmemoized useCallback/useMemo dependencies), which fails memo's shallow equality check even though the "meaningful" data hasn't changed.

Q: What is virtualization / windowing, and why does it matter? A: Rendering only the DOM nodes currently visible in the viewport (plus a small buffer) for very long lists, instead of all 10,000 rows at once — massively reduces DOM node count, memory, and initial render time. Libraries: react-window, react-virtualized, @tanstack/react-virtual.

Q: Is premature optimization (wrapping everything in memo/useMemo) a good idea? A: No — it adds code complexity and its own overhead (comparison costs) with sometimes negligible benefit; a common React best practice is to profile first, then optimize the specific component/computation shown to be a bottleneck.

Quick Revision

  • Optimize in this order of effort/impact: profile → memoize the actual bottleneck → virtualize huge lists → code-split.
  • Composition (children prop) can avoid re-renders even without memo.
  • Inline literals ({}, [], () => {}) as props defeat memo's shallow comparison.

21. Code Splitting, Lazy Loading & Suspense

Concept

Code splitting breaks a large JS bundle into smaller chunks loaded on demand, reducing initial load time. React.lazy() + dynamic import() lazily loads a component's code only when it's actually rendered; <Suspense> shows a fallback UI while the lazy chunk is being fetched.

Practical Example

const Dashboard = React.lazy(() => import('./Dashboard')); // separate JS chunk, fetched on demand

function App() {
  const [showDashboard, setShowDashboard] = React.useState(false);
  return (
    <div>
      <button onClick={() => setShowDashboard(true)}>Load Dashboard</button>
      {showDashboard && (
        <React.Suspense fallback={<p>Loading dashboard...</p>}>
          <Dashboard />
        </React.Suspense>
      )}
    </div>
  );
}

Explanation

Dashboard's code is not included in the main bundle at all — it's fetched as a separate .js chunk only when showDashboard becomes true and <Dashboard/> is actually rendered for the first time. While that chunk downloads, <Suspense>'s fallback ("Loading dashboard...") is shown; once loaded, React swaps in the real component.

Interview Q&A

Q: Why is code splitting important for performance? A: Smaller initial bundle ⇒ faster Time-to-Interactive, especially for large apps where most users only visit a few routes/features — no need to download code for the admin panel if the user never opens it.

Q: What does <Suspense> do, conceptually? A: Lets a component "suspend" rendering (signal it's not ready yet — waiting on a lazy import or, in newer React with data-fetching integrations, an async data source) and declaratively show a fallback UI until it's ready, without manual isLoading state plumbing for this specific case.

Q: Can Suspense catch errors from a failed lazy import? A: No — Suspense only handles the loading state; a failed dynamic import() (e.g., network failure) throws an error that must be caught by an Error Boundary wrapped around it.

Q: Route-based vs component-based code splitting — which is more common? A: Route-based (lazy-loading each page/route) is the most common and highest-impact starting point, since users typically only need the code for the route they're currently on.

Quick Revision

  • React.lazy(() => import('./X')) + <Suspense fallback={...}> = standard lazy-loading pattern.
  • Combine with an Error Boundary to handle chunk load failures.
  • Route-based code splitting = biggest, easiest performance win for most apps.

22. Server-Side Rendering, Next.js & Hydration

Concept

  • CSR (Client-Side Rendering): browser downloads a near-empty HTML shell + JS bundle, then React renders everything client-side. Slower first paint, but rich interactivity once loaded.
  • SSR (Server-Side Rendering): the server renders the initial HTML (with real content) and sends it to the browser, which shows content immediately, then React "hydrates" it (attaches event listeners/makes it interactive) on the client.
  • Hydration: the process of React attaching to server-rendered HTML on the client, reusing the existing DOM nodes rather than recreating them, and wiring up event handlers/state.
  • Next.js: the most popular React framework providing built-in SSR, Static Site Generation (SSG), file-based routing, API routes, and (in the App Router) React Server Components.

Practical Example (conceptual Next.js structure)

// app/products/[id]/page.js  (Next.js App Router — Server Component by default)
async function ProductPage({ params }) {
  const product = await fetch(`https://api.example.com/products/${params.id}`).then(r => r.json());
  // This runs on the SERVER — no client-side loading spinner needed, no client JS shipped for this fetch
  return <h1>{product.name}</h1>;
}
export default ProductPage;

Explanation

This component runs entirely on the server: the fetch call executes server-side, and the fully-rendered HTML (with the product name already in it) is sent to the browser — no client-side loading state, no extra client JS bundle for this data-fetching logic (React Server Components ship zero JS to the client unless explicitly marked "use client").

Interview Q&A

Q: Why use SSR over pure CSR? A: Faster perceived load (content visible before JS finishes downloading/parsing), better SEO (crawlers see real content immediately instead of an empty <div id="root">), and better performance on low-end devices/slow networks.

Q: What is "hydration mismatch" and what causes it? A: An error/warning when the server-rendered HTML doesn't match what the client would render on first render — common causes: using Date.now()/Math.random()/window-dependent logic during render, or conditionally rendering based on something only available client-side (like localStorage), producing different markup server vs client.

Q: React Server Components (RSC) vs SSR — are they the same thing? A: No. SSR renders the initial HTML for a normal client component tree (all components still ship their JS and re-hydrate). RSC is a newer model where certain components run only on the server and never ship their JS to the client at all (no hydration needed for them) — you explicitly opt individual components into client-side interactivity with a "use client" directive.

Q: Downsides of SSR? A: Increased server load/complexity (needs a Node.js server or serverless functions, not just static file hosting), and Time-to-Interactive can still lag behind Time-to-First-Paint if hydration is slow on a large page ("uncanny valley" of visible-but-not-yet-interactive UI).

Quick Revision

CSR SSR SSG
HTML generated In browser On server, per request At build time
First paint speed Slower Fast Fastest
SEO Poor (without extra work) Good Good
Data freshness Always current Always current Only as fresh as last build
Server cost Low (static hosting) Higher (needs server) Low (static hosting)

Real-World Use Case

Marketing/blog pages → SSG (build once, serve as static files, best performance). Personalized dashboards with per-user data → SSR or CSR. E-commerce product pages needing SEO + fresh stock/price data → SSR.

23. Testing React Apps

Concept

React Testing Library (RTL) is the standard testing approach, philosophically focused on testing components the way a user would interact with them (querying by visible text/role/label, not implementation details like internal state or CSS classes), typically run with Jest or Vitest as the test runner.

Practical Example

// Counter.jsx
function Counter() {
  const [count, setCount] = React.useState(0);
  return (
    <div>
      <p>Count: {count}</p>
      <button onClick={() => setCount(c => c + 1)}>Increment</button>
    </div>
  );
}

// Counter.test.jsx
import { render, screen, fireEvent } from '@testing-library/react';
import Counter from './Counter';

test('increments count when button is clicked', () => {
  render(<Counter />);

  expect(screen.getByText('Count: 0')).toBeInTheDocument();

  fireEvent.click(screen.getByRole('button', { name: /increment/i }));

  expect(screen.getByText('Count: 1')).toBeInTheDocument();
});

Explanation

render(<Counter/>) mounts the component into a virtual DOM (jsdom). screen.getByText/getByRole query the rendered output the way a real user would find elements (by visible text or accessible role), rather than reaching into component internals (e.g., wrapper.state('count'), which is an implementation-detail-coupled anti-pattern from older tools like Enzyme). fireEvent.click simulates a real user click, and the assertion checks the resulting DOM output, not internal state directly.

Interview Q&A

Q: Why does RTL discourage testing implementation details (like internal state)? A: Tests coupled to internals break during refactors that don't change user-visible behavior (e.g., renaming a state variable or switching from useState to useReducer), creating brittle tests that don't actually verify what matters — what the user sees/can do.

Q: getByText vs findByText vs queryByText — differences? A: getBy* throws immediately if not found (synchronous, use for elements expected to already be present). findBy* returns a Promise and retries until found or timeout (use for elements that appear after async operations, like after a fetch resolves). queryBy* returns null instead of throwing if not found (use when asserting something is absent).

Q: How do you test a component with an async data fetch? A: Mock the fetch/API call (e.g., with jest.mock or msw — Mock Service Worker), render the component, then use await screen.findByText(...) to wait for the resolved UI state instead of a synchronous getBy*.

Q: What's the difference between unit tests, integration tests, and E2E tests for React apps? A: Unit: a single component/function in isolation (RTL + Jest). Integration: multiple components working together (also RTL, but rendering a bigger tree, sometimes with a mocked Context/Router). E2E: full app in a real browser against a real (or realistic) backend (Cypress, Playwright) — simulates real user journeys end-to-end.

Quick Revision

  • RTL philosophy: query and interact like a user, not implementation details.
  • getBy (sync, throws) vs findBy (async, waits) vs queryBy (sync, returns null) — pick based on sync/async/absence-check.
  • Mock network calls; use findBy* for anything appearing after an async resolution.

24. Advanced Patterns

24.1 Compound Components

Concept: A set of components that work together to form a cohesive UI, sharing implicit state via Context, giving the consumer flexible control over structure/order (like native <select>/<option>).

const TabsContext = React.createContext();

function Tabs({ children, defaultIndex = 0 }) {
  const [activeIndex, setActiveIndex] = React.useState(defaultIndex);
  return (
    <TabsContext.Provider value={{ activeIndex, setActiveIndex }}>
      {children}
    </TabsContext.Provider>
  );
}

Tabs.List = function TabList({ children }) {
  return <div className="tab-list">{children}</div>;
};

Tabs.Tab = function Tab({ index, children }) {
  const { activeIndex, setActiveIndex } = React.useContext(TabsContext);
  return (
    <button
      className={activeIndex === index ? 'active' : ''}
      onClick={() => setActiveIndex(index)}
    >
      {children}
    </button>
  );
};

Tabs.Panel = function TabPanel({ index, children }) {
  const { activeIndex } = React.useContext(TabsContext);
  return activeIndex === index ? <div>{children}</div> : null;
};

// Usage — consumer controls structure/order/spacing freely
<Tabs defaultIndex={0}>
  <Tabs.List>
    <Tabs.Tab index={0}>Profile</Tabs.Tab>
    <Tabs.Tab index={1}>Settings</Tabs.Tab>
  </Tabs.List>
  <Tabs.Panel index={0}>Profile content</Tabs.Panel>
  <Tabs.Panel index={1}>Settings content</Tabs.Panel>
</Tabs>

Explanation: Tabs, Tabs.List, Tabs.Tab, and Tabs.Panel implicitly share state through TabsContext without the consumer having to manually wire up activeIndex/onChange props on every sub-component — similar to how <select> and <option> work together natively in HTML. This gives maximum layout flexibility (consumer can add wrapper divs, reorder, style each independently) while keeping shared logic centralized.

Interview Q&A - Q: What problem do compound components solve vs a single monolithic component with many props? A: Avoids a huge prop-explosion API (<Tabs tabLabels={[...]} tabContent={[...]} activeStyle={...} ...>) by letting consumers compose sub-components directly with JSX, giving far more layout/styling flexibility. - Q: Real-world examples in popular libraries? A: Radix UI, Headless UI, React Bootstrap's <Nav>/<Nav.Item>, native <select>/<option>.

24.2 Controlled vs Uncontrolled Components (Design Pattern, beyond forms)

This same "who owns the state" question (Section 11) generalizes to any component API design — e.g., an <Accordion isOpen={...} onToggle={...}> (controlled by parent) vs <Accordion defaultOpen={true}> (manages its own state internally). Many production component libraries support both via patterns like the "state reducer pattern" or accepting an optional controlled value + falling back to internal state if omitted.

24.3 The "State Reducer" Pattern

Concept: An advanced pattern (popularized by Kent C. Dodds) where a component exposes its internal reducer logic to the consumer, letting them intercept and override specific state transitions without losing all the built-in default behavior.

function useToggle({ reducer = (state, action) => action.changes } = {}) {
  const [state, dispatch] = React.useReducer((state, action) => {
    const changes = { on: !state.on }; // default toggle logic
    return reducer(state, { ...action, changes });
  }, { on: false });

  const toggle = () => dispatch({ type: 'toggle' });
  return { on: state.on, toggle };
}

// Consumer can override: e.g., "never allow toggling off once on"
function App() {
  const { on, toggle } = useToggle({
    reducer: (state, action) => {
      if (state.on && action.type === 'toggle') return state; // block the change
      return action.changes;
    },
  });
  return <button onClick={toggle}>{on ? 'ON' : 'OFF'}</button>;
}

Interview Q&A - Q: When would you reach for the state reducer pattern? A: Building a reusable component library (design system) where you can't predict every edge case a consumer needs, but want to keep sensible defaults — letting advanced consumers customize specific transitions without forking the component.

Quick Revision

  • Compound components: share state via Context, consumer controls composition/layout.
  • Controlled/uncontrolled generalizes beyond forms to any reusable component API.
  • State reducer pattern: expose override hooks into internal logic for advanced library consumers.

25. Common Mistakes & Anti-Patterns

# Mistake Why it's wrong Fix
1 Mutating state directly: state.items.push(x); setState(state) React compares references for change detection — mutating in place means the reference is identical, so React may skip the re-render entirely Always create a new object/array: setState([...state.items, x])
2 Using array index as key in dynamic lists Causes wrong DOM/state reuse on reorder/insert/delete (Section 10) Use a stable unique ID from the data
3 Calling Hooks conditionally or inside loops Breaks React's internal Hook-order tracking, causing subtle bugs or crashes Always call Hooks unconditionally at the top level
4 Missing dependency in useEffect's dependency array Causes stale closures — effect uses outdated props/state Include all referenced reactive values, or use the eslint-plugin-react-hooks exhaustive-deps rule
5 Fetching data directly in the component body (not in useEffect) Causes an infinite loop — fetch triggers setState triggers re-render triggers fetch again Wrap side effects in useEffect with proper dependencies
6 Defining a component inside another component's render function A brand-new component type is created every render, causing the child to fully unmount/remount every time (losing its state, e.g., input focus) Define components outside, at module scope
7 Passing a new inline object/function as a prop to a memo-wrapped child Defeats shallow prop comparison, child re-renders anyway useMemo/useCallback, or hoist static objects outside the component
8 Overusing Context for frequently-changing, high-frequency state Causes broad re-renders across the tree (Section 12) Use Redux/Zustand with selectors, or split into smaller contexts
9 Forgetting e.preventDefault() on form submit Causes full page reload, losing all React state Always call it in the submit handler
10 Not cleaning up subscriptions/timers/listeners in useEffect Memory leaks, "can't perform state update on unmounted component" warnings, race conditions Always return a cleanup function that tears down what was set up
11 Directly comparing objects/arrays for equality (prevProps.data === newProps.data) assuming it reflects "no meaningful change" New references from .map()/.filter()/spread create "different" objects even with identical values Memoize with useMemo, or use deep-equality checks only where truly needed
12 Treating useMemo/useCallback as free — wrapping everything Adds unnecessary complexity & its own comparison overhead for cheap computations Profile first; memoize only proven-expensive computations or to satisfy a memo/dependency-array need

Interview Q&A

Q: "I have an infinite re-render loop — how do you debug it?" A: Look for: (1) setState called unconditionally in the component body (not inside an effect/handler), (2) a useEffect with a dependency that's a new object/array/function every render (creating a new reference each time, re-triggering the effect, which sets state, which re-renders, ad infinitum), (3) a missing or incorrect dependency array causing the effect to always re-run and always update state.

Q: What ESLint rule catches most Hook-related bugs before runtime? A: eslint-plugin-react-hooks, specifically its exhaustive-deps rule, which warns about missing dependencies in useEffect/useMemo/useCallback.

Quick Revision

  • Never mutate state directly — always create new references.
  • Never define components inside other components' render bodies.
  • Always clean up effects; always include exhaustive dependencies (or intentionally justify omissions with a comment).

26. Rapid-Fire Interview Q&A Bank

Use this section for last-minute revision — short, direct answers.

Q: What is the difference between React.PureComponent and React.Component? A: PureComponent implements shouldComponentUpdate with a shallow prop/state comparison automatically; Component re-renders on every parent render/state change regardless (unless you implement shouldComponentUpdate yourself).

Q: What is prop drilling? A: Passing data through multiple layers of components that don't need it themselves, just to reach a deeply nested child — solved by Context or state management libraries.

Q: What is the difference between state and props once more, in one line? A: Props = data passed in from outside (read-only); State = data owned/managed internally (mutable via setter).

Q: Explain the Virtual DOM diffing algorithm's time complexity trick. A: Full generic tree diff is O(n³); React's heuristics (same-type assumption + keys) reduce this to O(n).

Q: What are Fragments and why use them? A: <>...</> (or <React.Fragment>) lets you group multiple children without adding an extra wrapper DOM node — useful to avoid invalid HTML nesting (e.g., inside <table>) or unnecessary div soup.

Q: What is "lifting state up"? A: Moving state from a child to their closest common parent when multiple children need to read/share or stay in sync with that state.

Q: What does React.StrictMode do? A: A development-only tool that intentionally double-invokes certain functions (component render, some lifecycle/effect functions) to help surface side effects that aren't idempotent/pure, plus warns about deprecated APIs — no effect in production builds.

Q: Why does StrictMode double-render/double-invoke effects in dev? A: To help you catch effects/renders that aren't safely resilient to being run twice, which future concurrent React features may rely on (e.g., an interrupted render being retried).

Q: What's the difference between useState initial value as a value vs a function? A: useState(expensiveCompute()) calls expensiveCompute() on every render (the argument is evaluated regardless, then discarded after the first render); useState(() => expensiveCompute()) (lazy initializer) only calls it once, on the first render — important for expensive initial computations.

Q: Can you update state in the render phase (component body) directly? A: Generally no — causes infinite loops/warnings, except in the specific, controlled Ross pattern React officially supports: updating state directly during render to adjust state based on a prop change ("adjusting state when a prop changes," documented as an exception) — but this is rare and usually useEffect or lifting state up is preferred.

Q: What is prop types / TypeScript's role in React? A: PropTypes (runtime prop validation, legacy/JS projects) or TypeScript (compile-time static typing) both catch incorrect prop usage — TypeScript is now the industry standard for larger codebases, catching errors before runtime.

Q: Explain "children as a prop." A: props.children represents whatever is nested between a component's opening/closing tags (<Card>this is children</Card>) — a special, implicit prop enabling composition patterns.

Q: What is the difference between useEffect cleanup running "before every re-run" vs "only on unmount"? A: The cleanup function runs both before the effect re-runs (if dependencies changed) and on final unmount — not just at unmount, a common misconception.

Q: How would you debounce a search input in React? A: A useDebounce custom hook that delays updating a "debounced" state value via setTimeout inside useEffect, clearing the previous timeout on each keystroke (in the cleanup function), so the actual search/API call only fires after the user stops typing for N ms.

function useDebounce(value, delay) {
  const [debounced, setDebounced] = React.useState(value);
  React.useEffect(() => {
    const timer = setTimeout(() => setDebounced(value), delay);
    return () => clearTimeout(timer); // cancels the pending update if value changes again before delay elapses
  }, [value, delay]);
  return debounced;
}

Q: What's the difference between useEffect and useLayoutEffect again, and a rule of thumb? A: Rule of thumb: default to useEffect; only reach for useLayoutEffect if you see a visual flicker because you need to measure/adjust the DOM before the browser paints.

Q: What's a "key" collision issue and how does it manifest? A: If two sibling elements share the same key, React can only use one to disambiguate — you'll see console warnings and potentially incorrect updates/duplicated content.

Q: What does "React batches state updates" mean practically, and how has it changed? A: Multiple setState calls within the same event handler (or, since React 18, even inside promises/timeouts/native event handlers — "automatic batching") are merged into a single re-render rather than one re-render per call, for performance.

Q: Difference between React.Children.map use case? A: A utility for safely iterating over props.children (which can be a single child, an array, or nested) when building components that need to inspect/transform/clone their children, e.g., compound components adding props to each child.

Q: What is the difference between a "presentational" and a "container" component? A: Presentational (aka "dumb") components focus purely on how things look, receiving data via props with no internal data-fetching logic; container ("smart") components handle data-fetching/state and pass data down — a pattern largely superseded by custom Hooks for separating concerns, but still commonly discussed in interviews.

27. System-Design Style React Questions

These are common in senior/experienced-level interviews — open-ended, expect you to reason through trade-offs out loud.

Q: "Design the state management for a large e-commerce checkout flow (cart, shipping, payment, multiple steps)." Key points to mention: - Multi-step form state: useReducer locally, or a dedicated slice in Redux/Zustand if other parts of the app need cart data (e.g., a header cart icon). - Persist partially-filled state to localStorage/sessionStorage so a refresh doesn't lose progress. - Validate each step before allowing "Next"; keep validation logic colocated with each step's component or in shared schema (e.g., Zod/Yup). - Use React Router nested routes for each step, or state-driven step index — discuss trade-off (URL-addressable steps aid back-button/bookmark/analytics vs simpler state-only stepping). - Server round-trip only on final submission, or incrementally per step depending on backend design.

Q: "How would you architect a real-time notifications feature (WebSocket-driven)?" Key points: - A single WebSocket connection managed via a custom hook or Context Provider near the app root (useWebSocket), not per-component connections. - New notifications pushed into a global store (Context+useReducer or Redux/Zustand) so any part of the UI (bell icon, toast, notification center) can subscribe. - Cleanup: close the socket in useEffect's cleanup on unmount/logout. - Consider reconnection/backoff logic and deduplication if the same notification could arrive twice.

Q: "A component tree re-renders way more than expected in production — how do you diagnose and fix it?" Key points: - React DevTools Profiler → record interaction → identify which components re-rendered and why (highlighted with "why did this render" reasons in newer DevTools). - Check for non-memoized objects/arrays/functions passed as props to memo-wrapped children. - Check for Context value objects recreated every render without useMemo. - Consider colocating state closer to where it's used ("state colocation") instead of one large shared state object causing broad subscriptions. - Only then apply memo/useMemo/useCallback to the specific proven offenders.

Q: "How would you handle authentication (protected routes, token refresh) in a React SPA?" Key points: - Store auth state (user, token) in Context or a state library; keep the raw token in memory or an httpOnly cookie (not localStorage, to reduce XSS token-theft risk — a good security-awareness point to mention). - A <ProtectedRoute> wrapper component checks auth state and redirects unauthenticated users to /login, preserving the intended destination for post-login redirect. - An Axios/fetch interceptor to attach the token to requests and handle 401s by attempting a silent token refresh, then retrying the original request or logging out.

Q: "How do you keep a component library consistent and reusable across many teams?" Key points: - Compound components / state reducer pattern for flexible, composable APIs (Section 24). - Design tokens (colors, spacing) rather than hardcoded values. - Storybook for isolated component development/visual documentation. - Strict TypeScript prop typing + automated visual regression testing.

Final One-Page Cheat Sheet (Night-Before-Interview Recap)

  • React = declarative, component-based UI library using a Virtual DOM + diffing (reconciliation, powered by Fiber) to minimize real DOM updates.
  • JSX compiles to React.createElement(); must return a single root/Fragment.
  • Props = read-only, parent→child. State = local, mutable, owned by the component, triggers re-render on change.
  • Hooks Rules: top-level only, React functions only. useState (local value) · useEffect (side effects + cleanup) · useRef (mutable value/DOM ref, no re-render) · useContext (avoid prop drilling) · useMemo/useCallback (referential stability/perf) · useReducer (complex state transitions) · custom hooks (reusable logic, not shared state).
  • Keys: stable + unique + from data, never array index for dynamic lists.
  • Controlled (React-owned via state) vs Uncontrolled (DOM-owned, read via ref) forms; file inputs must be uncontrolled.
  • Context: great for low-frequency global data (theme/auth), but re-renders all consumers on any change — use Redux/Zustand for high-frequency/complex global state (selector-based, no full re-render).
  • Error Boundaries: class-only, catch render errors (not event handlers/async/SSR errors).
  • HOC/Render Props: pre-Hooks reuse patterns, largely replaced by custom Hooks (avoid "wrapper hell").
  • Portals: render into a different DOM location, same React tree (context/events still work normally) — for modals/tooltips.
  • forwardRef + useImperativeHandle: needed to accept/customize refs on custom components (pre React 19).
  • Performance: profile first → memoize the actual bottleneck → virtualize long lists → code-split routes; avoid inline object/function literal props to memoized children.
  • SSR/Next.js: faster first paint + SEO vs CSR; watch for hydration mismatches (no Date.now()/window in render logic without guards).
  • Testing (RTL): query/interact like a user (getByRole/getByText), not implementation details; findBy* for async.
  • Common bugs: mutating state directly, missing useEffect deps, components defined inside render, infinite re-render loops from unguarded setState in render body.
