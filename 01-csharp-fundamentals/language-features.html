Core Language Features

Generics, delegates, lambdas, iterators and pattern matching. LINQ, dependency injection and events are all built on these — so this page unlocks several later sections.

🟢 Beginner 🟡 Intermediate 🔥 Must know
Quick revision
  • Generics — write the algorithm once, keep type safety, avoid boxing. where constraints let you actually use the type.
  • Delegate — a variable that holds a method. Func returns a value, Action doesn't, Predicate returns bool.
  • Event — a delegate with restricted access: outsiders can subscribe, only the owner can raise it.
  • Closure — a lambda that captures a variable. It captures the variable, not the value — that's the classic loop bug.

Generics 🔥 Must know

In simple terms

Generics let you write code that works with any type, while the compiler still knows exactly which type you're using.

You get one implementation, full type safety, and no boxing.

Think of it this way

A generic type is a labelled shipping box. Same box design for anything, but the label says exactly what's inside — so nobody can put a laptop in the box marked "books", and you don't have to unwrap it to find out what it holds.

The non-generic alternative was one unlabelled box for everything: you had to open it and hope ((int)list[0]).

Why they exist — the before and after

var list = new ArrayList();
list.Add(1);
list.Add("oops");                 // compiles fine - no type safety

int first = (int)list[0];         // cast needed, and it boxes/unboxes
int second = (int)list[1];        // InvalidCastException at runtime
var list = new List<int>();
list.Add(1);
list.Add("oops");                 // compile error - caught immediately

int first = list[0];              // no cast, no boxing

Three wins in one change: errors move from runtime to compile time, the casts disappear, and the boxing disappears.

Constraints — how you actually use T

By default T could be anything, so you can barely do anything with it. where tells the compiler more:

where T : classMust be a reference typeYou need to compare to null

where T : new()Has a public no-arg constructorYou need to create one
where T : notnullCannot be a nullable typeDictionary keys
 
// Without a constraint, entity.Id doesn't compile - T might not have an Id.
public sealed class Repository<T> where T : IEntity
{
    public T? Find(IEnumerable<T> items, Guid id) =>
        items.FirstOrDefault(e => e.Id == id);      // works: T is guaranteed to have Id
}
Generics in .NET are real, not erased ⭐ Senior-level

This is a good differentiator if you've used Java. Java erases generics at compile time — at runtime, List<String> is just List.

.NET keeps them at runtime. The CLR generates a specialised version for each value type (List<int> really stores ints, no boxing) and shares one version across reference types. That's why typeof(List<int>) != typeof(List<string>) in C#, and why you can reflect over generic arguments.

Delegates 🔥 Must know

In simple terms

A delegate is a variable that holds a method.

Just as an int variable holds a number, a delegate variable holds "some code I can call later".

Think of it this way

A delegate is a phone number. You're not the plumber, but you can hold their number and call it when needed — and you can swap the number without changing anything about how you make the call.

Func<int, int>        square  = x => x * x;          // takes int, RETURNS int
Action<string>        log     = msg => Console.WriteLine(msg);   // returns NOTHING
Predicate<int>        isEven  = x => x % 2 == 0;      // returns BOOL

Console.WriteLine(square(5));    // 25
log("hello");
Console.WriteLine(isEven(4));    // True
How to remember them

Func = function, so it returns something. The last type parameter is the return type.

Action = an action — it does something and returns nothing.

Why this matters: this is what LINQ is. Where takes a Func<T, bool>; Select takes a Func<T, TResult>. Once delegates click, LINQ stops looking like magic.

// Instead of writing a class per rule, pass the rule in.
public static IEnumerable<Order> Filter(IEnumerable<Order> orders, Func<Order, bool> rule)
{
    foreach (var order in orders)
        if (rule(order)) yield return order;
}

var big = Filter(orders, o => o.Total > 1000);
var recent = Filter(orders, o => o.CreatedUtc > DateTime.UtcNow.AddDays(-7));

That's the Strategy pattern in one line — which is why C# often doesn't need the full interface-based version.

Closures — and the classic bug 🟡 Intermediate

In simple terms

When a lambda uses a variable from outside itself, it captures that variable. The lambda is now a closure.

The key detail: it captures the variable, not the value at that moment.

var actions = new List<Action>();

for (var i = 0; i < 3; i++)
    actions.Add(() => Console.WriteLine(i));

foreach (var a in actions) a();

Most people expect 0 1 2. In a classic for loop it prints 3 3 3.

There is one i for the whole loop. All three lambdas captured that same variable, and by the time they run the loop has finished and i is 3.

for (var i = 0; i < 3; i++)
{
    var copy = i;                                  // new variable each iteration
    actions.Add(() => Console.WriteLine(copy));    // prints 0 1 2
}
The version difference that catches people out

In foreach, this was fixed in C# 5 — the iteration variable became per-iteration, so foreach closures behave as you'd expect.

In a for loop it was never changed, because i is genuinely one variable that the loop mutates. So for still needs the explicit copy.

Knowing that distinction is a good senior-level detail.

Production trap — closures capture more than you think

A closure keeps its captured variables alive. If a lambda captures this — which happens implicitly when you use any instance field — and that lambda is stored in a long-lived place (an event handler, a static cache, a timer), the entire object can't be garbage collected.

That's a common source of slow memory growth in long-running services. See memory & GC.

Events 🟡 Intermediate

In simple terms

An event is a delegate with a lock on it. Outside code can subscribe and unsubscribe, but only the declaring class can raise it or clear it.

public class OrderService
{
    // Without 'event', any caller could do  svc.OrderPlaced = null;
    // and wipe out every other subscriber.
    public event EventHandler<OrderPlacedArgs>? OrderPlaced;

    public void Place(Order order)
    {
        // ... do the work ...
        OrderPlaced?.Invoke(this, new OrderPlacedArgs(order.Id));
    }
}

Note the ?. — if nobody has subscribed, the delegate is null, and invoking it would throw.

Two things to know about events
  • They leak memory if you don't unsubscribe. The publisher holds a strong reference to every subscriber. A long-lived publisher plus short-lived subscribers that never detach means those subscribers can never be collected — the "lapsed listener" problem.
  • One throwing handler stops the rest. Handlers run in subscription order; an exception in the second one means the third never runs.

For in-process decoupling inside a domain model, prefer domain events with an explicit dispatcher — they support async handlers and give you control over failure.

Extension methods 🟢 Beginner

In simple terms

A static method that you can call as if it were an instance method on the type — even a type you don't own.

public static class StringExtensions
{
    // 'this' on the first parameter is what makes it an extension
    public static bool IsValidEmail(this string value) =>
        !string.IsNullOrWhiteSpace(value) && value.Contains('@');
}

// Now it reads like a method on string:
if (email.IsValidEmail()) { /* ... */ }

This is how LINQ works. Where, Select and OrderBy aren't members of IEnumerable<T> — they're extension methods in System.Linq.Enumerable. That's why you need using System.Linq; for them to appear.

Common mistake

Extension methods are resolved at compile time and are not polymorphic — they can't be overridden. They also lose to instance methods: if the type later gains a real method with the same signature, that one wins silently and your extension stops being called.

Also note an extension method can be called on null without throwing, because there's no instance dereference. So validate the parameter.

Iterators and yield return 🟡 Intermediate

In simple terms

yield return lets a method hand back items one at a time, on demand, instead of building a whole list first.

Think of it this way

Without yield, you cook the entire buffet before anyone eats.

With yield, you cook each dish when a guest asks for it. If they leave after two courses, you never cooked the rest.

public static IEnumerable<int> Numbers()
{
    Console.WriteLine("start");
    yield return 1;
    Console.WriteLine("after 1");
    yield return 2;
    Console.WriteLine("after 2");
}

var seq = Numbers();          // prints NOTHING - the method hasn't run yet
foreach (var n in seq)        // now it runs, pausing at each yield
    Console.WriteLine(n);

// Output: start, 1, after 1, 2, after 2

The compiler rewrites that method into a state machine class that remembers where it paused. It's the same machinery async/await uses.

Why it matters: memory. Reading a million-line file with yield holds one line in memory at a time; returning a List<string> holds all million.

Production trap — deferred execution surprises

Because the body doesn't run until enumeration, two things bite:

  • Argument validation is deferred too. A throw for a bad parameter won't fire when the method is called — only when someone enumerates, which may be far away. Validate in a non-iterator wrapper method.
  • Enumerating twice runs it twice. If it hits a database or an API, you've just made two calls. .ToList() once if you need to iterate more than once.

Pattern matching 🟡 Intermediate

In simple terms

Test the shape of a value — its type, its properties, its structure — and pull out the parts you need, in one expression.

if (shape is Circle)
{
    var c = (Circle)shape;
    if (c.Radius > 0) return Math.PI * c.Radius * c.Radius;
}
else if (shape is Rectangle)
{
    var r = (Rectangle)shape;
    return r.Width * r.Height;
}
throw new ArgumentException();
var area = shape switch
{
    Circle { Radius: > 0 } c    => Math.PI * c.Radius * c.Radius,
    Rectangle r                 => r.Width * r.Height,
    null                        => throw new ArgumentNullException(nameof(shape)),
    _                           => throw new ArgumentException($"Unknown shape {shape.GetType().Name}")
};

Notice Circle { Radius: > 0 } — that's a type check, a property check and a variable binding in one pattern.

Why this matters beyond tidiness

Over a sealed hierarchy, the compiler can tell you when a switch expression doesn't handle every case. That turns "someone forgot to update the switch" from a production bug into a build warning.

It's also why the classic argument for polymorphism over switches is weaker in modern C# — see Open/Closed.

Key takeaways
  • Generics = one implementation, compile-time safety, no boxing. Constraints make T usable.
  • .NET generics are preserved at runtime, unlike Java's erased ones.
  • Func returns, Action doesn't. LINQ is just methods taking Func.
  • Closures capture the variable. for loops need an explicit copy; foreach hasn't since C# 5.
  • Events leak if subscribers never detach, and one throwing handler blocks the rest.
  • Extension methods are compile-time and non-polymorphic; instance methods beat them.
  • yield return is lazy — validation is deferred, and enumerating twice executes twice.
  • Pattern matching over a sealed hierarchy gives you exhaustiveness checking.

Common mistakes

  • Capturing the loop variable in a for loop and getting the last value every time.
  • Never unsubscribing from events, so subscribers can't be collected.
  • Enumerating a yield method twice and unknowingly hitting the database twice.
  • Argument validation inside an iterator, so it throws far away from the call.
  • Generic methods with no constraint, then casting T to something — which defeats the point.
  • Extension methods on object or over-broad types, polluting IntelliSense everywhere.
  • Returning IEnumerable<T> from a repository and letting the caller enumerate it after the connection has closed.

Interview questions

Basic

What's the difference between Func, Action and Predicate?
How I'd answer

"They're all built-in delegate types — ways of holding a method in a variable."

"Action returns nothing. Func returns a value, and its last type parameter is the return type — so Func<int, string> takes an int and returns a string. Predicate<T> is really just Func<T, bool> with a more descriptive name."

"In practice I use Func and Action almost exclusively. Predicate mostly survives in older APIs like List<T>.FindAll; LINQ standardised on Func<T, bool>."

"The reason this matters is that it's what LINQ is built on. Where takes a Func<T, bool>, Select takes a Func<T, TResult>. Once you see that, LINQ stops being magic — it's just methods that take behaviour as a parameter."

What they're really checking
  • Do you know which type parameter is the return type?
  • Can you connect delegates to LINQ?
Likely follow-ups
  • What's the difference between Func<T, bool> and Expression<Func<T, bool>>?
  • How is a delegate different from an interface with one method?

Intermediate

What does this print, and why? 🔥 Must know 
var actions = new List<Action>();
for (var i = 0; i < 3; i++)
    actions.Add(() => Console.Write(i));
foreach (var a in actions) a();
How I'd answer

"It prints 333, not 012."

"The lambdas capture the variable i, not its value at the time they were created. In a for loop there's only one i for the whole loop, so all three lambdas close over the same variable. By the time they actually run, the loop has finished and i is 3."

"The fix is to give each iteration its own variable — declare a local copy inside the loop body and capture that instead."

"There's a version detail worth knowing: this was a problem with foreach too, and it was fixed in C# 5 by making the iteration variable per-iteration. It was deliberately not changed for for loops, because there i genuinely is one variable that the loop mutates — changing it would break code that relies on that."

"The related thing I'd mention is that closures keep captured variables alive. If a lambda captures this — which happens implicitly if you touch any instance field — and it's stored somewhere long-lived like an event handler or a static cache, the whole object can't be collected. That's a real source of slow memory growth."

What they're really checking
  • Do you know closures capture variables, not values?
  • Do you know the foreach vs for distinction?
  • Bonus: do you connect closures to memory leaks?
Weak answers
  • Red flag: "012" — the most common wrong answer.
  • Red flag: knowing the answer but not being able to explain why.
Likely follow-ups
  • What does the compiler actually generate for a closure?
  • How could a closure cause a memory leak?
Why would you use yield return instead of returning a list?
How I'd answer

"Mainly memory and responsiveness. With yield, items are produced on demand, so you hold one at a time instead of the whole collection. Reading a million-line file that way uses constant memory; returning a list uses a million strings' worth."

"It also means the caller can stop early. If they only need the first ten matches, only ten get produced — the rest of the work never happens. That composes well with LINQ, where Take(10) genuinely stops the pipeline."

"Under the hood the compiler rewrites the method into a state machine that remembers where it paused. It's the same mechanism async/await uses."

"The two traps I'd flag. First, deferred validation — a guard clause inside an iterator doesn't run when the method is called, only when someone enumerates. So I put validation in a normal wrapper method that then calls the private iterator. Second, enumerating twice runs it twice, which is a real bug if it hits a database or an API. If the caller might iterate more than once, materialise with ToList()."

"That second point is also why I'm careful about returning IEnumerable<T> from a repository — the caller might enumerate it after the connection has been disposed."

What they're really checking
  • Do you understand lazy evaluation, not just the syntax?
  • Do you know the deferred-validation and double-enumeration traps?
Likely follow-ups
  • What's IAsyncEnumerable<T> for?
  • What happens if you yield return inside a try with a finally?

Advanced

Are C# generics erased at runtime? ⭐ Senior-level
How I'd answer

"No — and that's a real difference from Java, which does erase them."

"In .NET, generic type information survives to runtime. The CLR generates a specialised implementation for each value type argument, so List<int> genuinely stores ints inline with no boxing. For reference types it shares a single implementation, because every reference is the same size."

"The practical consequences: typeof(List<int>) and typeof(List<string>) are different types. You can inspect generic arguments via reflection. You can write typeof(T) inside a generic method and get the real type. And default(T) works correctly — zero for value types, null for reference types — because the runtime knows what T is."

"In Java none of that works, which is why you see people passing Class<T> objects around as a workaround."

"The performance angle is the important half. Because value-type generics are specialised, generics in .NET are genuinely zero-cost for value types — no boxing, and the JIT can inline through them. That's why List<int> replaced ArrayList rather than just wrapping it."

What they're really checking
  • Do you know the CLR implementation, not just the syntax?
  • Can you name the observable consequences?
Likely follow-ups
  • What does default(T) return, and how does the runtime know?
  • What are covariance and contravariance — and why is IEnumerable<out T> covariant but List<T> not?
