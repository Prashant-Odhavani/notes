C# Fundamentals

The start of the path. Everything later in this handbook — EF Core, ASP.NET Core, async, architecture — rests on the ideas in this section.

🟢 Beginner 🟡 Intermediate 🔥 Must know
Quick revision
  • C# has two families of type: value types (copied) and reference types (shared). Almost every "why did that change?" bug traces back here.
  • Stack vs heap is an implementation detail, but interviewers ask it — and it explains boxing, which explains a whole class of performance problems.
  • Generics exist so you can write code once without giving up type safety or boxing everything.
  • Delegates are "a variable that holds a method". Events, LINQ and callbacks are all built on them.
  • struct vs class, record vs class, and string being immutable are the three questions that come up most.
  • Nullable reference types turn "it might be null" from a runtime surprise into a compiler warning.

Why this section comes first 🟢 Beginner

In simple terms

Most senior .NET interview questions are framework questions with a C# answer.

Getting the language right first makes every later section easier — and it's the cheapest way to sound genuinely experienced.

C# and .NET — two different things 🟢 Beginner

People use these interchangeably in conversation, but the distinction matters and interviewers occasionally check it.

ThingWhat it is
C#The language. Syntax and rules. Compiled by Roslyn.
IL (Intermediate Language)What C# compiles to. Not machine code yet.
CLR (Common Language Runtime)The runtime that executes IL — JIT compilation, garbage collection, type safety.
BCL / Base Class LibraryThe built-in types: string, List<T>, HttpClient.
.NETThe whole platform: runtime + libraries + SDK + tooling.
Think of it this way

C# is the language you write. IL is the sheet music. The CLR is the orchestra that plays it.

Which is why F# and VB.NET also run on .NET — different languages, same sheet music format.

The runtime side — JIT, AOT, target frameworks, the SDK — is covered in .NET Platform Fundamentals. This section is the language.

How C# is interviewed 🟡 Intermediate

Four levels, and they escalate quickly:

  1. Definitions. "What's the difference between a class and a struct?" Screening only.
  2. Consequences. "So what happens if I put a struct in a List and modify it?" This is where most candidates stop being able to answer.
  3. Read this code. A snippet with a subtle bug — a captured loop variable, a boxed comparison, a mutable struct. You explain what it prints and why.
  4. Design. "Model money in C#." Tests whether you reach for a record struct, whether you validate in the constructor, whether you think about equality.
Senior signal

Answer level 1 in one sentence, then volunteer level 2 without being asked.

"A struct is a value type, so it's copied on assignment — which means if you store one in a collection and modify what you read out, you're modifying a copy. That's the bug people hit."

That single move — definition plus the consequence — is the clearest way to signal you've used this in anger rather than read it.

Warm-up interview questions

How would you describe your level of C# knowledge?
How I'd answer

"I'd describe it in terms of what I can reason about rather than years. I'm comfortable with the type system — value versus reference semantics, where boxing happens, how equality works — and with generics, delegates and expression trees, which matter because they're what LINQ and DI are built on."

"The areas I've had to understand properly because they caused real problems are async and memory. Knowing why .Result deadlocks, what ConfigureAwait actually does, and why a long-lived object holding a short-lived one is a leak — those came from debugging, not reading."

"Where I'd say I'm still deliberately learning is the very low-level performance work — Span<T>, stack allocation, source generators. I know when to reach for them and I've used them in a hot path, but I wouldn't claim to be the person who writes the allocation-free parser."

What they're really checking
  • Can you self-assess honestly? Overclaiming is the fastest way to fail the follow-up.
  • Do you know which parts of the language actually matter in production?
Weak answers
  • Red flag: "expert" or "10 out of 10" — the next question will disprove it.
  • Red flag: listing years of experience instead of capabilities.
Likely follow-ups
  • Tell me about a C#-specific bug you had to debug.
  • What's a C# feature you avoid, and why?
What's a C# feature you think is overused?
How I'd answer

"A few, but the one I'd pick is var for non-obvious types. var is great when the right-hand side names the type — var order = new Order(). It's bad when it hides it: var result = _service.Process(input) tells the reader nothing, and in a review I can't tell whether that's a Task, an IEnumerable or a tuple."

"The other one is exceptions for control flow. Throwing for an expected business outcome — a declined payment, a validation failure — is both slow and misleading. Exceptions should mean something genuinely exceptional; expected outcomes are better as a result type."

"And I'd add dynamic. It exists for real interop reasons, but every use throws away the compiler's help, which is the main thing C# gives you over a dynamic language."

What they're really checking
  • Do you have opinions formed by experience rather than by tutorials?
  • Can you criticise something without being dogmatic?
Likely follow-ups
  • How would you return a "declined payment" without throwing?
  • When is dynamic genuinely the right answer?
