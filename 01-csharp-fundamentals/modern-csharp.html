Modern C# by Version

What changed, why it changed, and which features are worth adopting. Useful context — and a quick way to show you write current C# rather than C# 5.

🟡 Intermediate 💡 Good to know
Quick revision — the ones that actually changed how we write C#
  • C# 8 — nullable reference types. The biggest change to daily C# in a decade.
  • C# 9 — record. Value equality and immutable data without boilerplate.
  • C# 10 — file-scoped namespaces, global usings. Less noise in every file.
  • C# 11 — required members, raw string literals.
  • C# 12 — primary constructors on classes, collection expressions ([1, 2, 3]).
  • C# 13 — incremental: params collections, better lock.

Why this page exists 🟢 Beginner

Nobody will quiz you on which version shipped init accessors. But two things do come up:

  1. "What's new in C# that you like?" — a genuine question, and a weak answer signals you stopped learning a few years ago.
  2. Your code samples date you. Writing new List<string>() where [] works, or a 30-line DTO where a record does, reads as out of date.
In simple terms

The last few C# versions have mostly been about writing less code to say the same thing, plus letting the compiler catch null bugs.

Language version follows the target framework

You don't pick a C# version directly — it's implied by TargetFramework. Roughly: .NET 6 → C# 10, .NET 7 → C# 11, .NET 8 → C# 12, .NET 9 → C# 13.

You can override it with <LangVersion>, but features that need runtime support won't work on an older runtime. Verify against current docs before relying on a specific pairing.

C# 8 — nullable reference types 🔥 Must know

The headline feature, and the one with the most impact on real codebases.

// With <Nullable>enable</Nullable> in the csproj:
string name  = null;      // warning: converting null to non-nullable
string? maybe = null;     // fine, explicitly nullable

Console.WriteLine(maybe.Length);          // warning: possible null dereference
Console.WriteLine(maybe?.Length ?? 0);    // fine

Covered in detail on the type system page — including the important caveat that it's compile-time only.

Also in C# 8, and genuinely useful:

FeatureWhat it does
Switch expressionsvar x = value switch { ... } — an expression, not a statement
using declarationsusing var f = File.Open(...) with no extra braces
IAsyncEnumerable<T>await foreach — streaming async data
Default interface methodsAdd a member to an interface without breaking implementers
Ranges and indicesitems[1..^1], items[^1] for the last item

C# 9 — records 🔥 Must know

Before — and this is the short version

A DTO with value equality meant writing a constructor, properties, Equals, GetHashCode, ToString and a copy method. Around 40 lines for three properties.

After

public record Money(decimal Amount, string Currency);

Records are covered on the type system page. Other C# 9 items:

  • init accessors — settable during construction, read-only afterwards.
  • Top-level statements — no Program class boilerplate.
  • Target-typed new — List<Order> x = new();
  • Pattern matching improvements — is not null, and, or, relational patterns like > 100.

C# 10 — less ceremony per file 🟡 Intermediate

namespace MyApp.Orders;      // note the semicolon - no braces

public sealed class Order
{
    // everything is one indent shallower than it used to be
}
// In a single file, e.g. GlobalUsings.cs
global using System.Collections.Generic;
global using Microsoft.Extensions.Logging;

// Or in the .csproj:
// <ImplicitUsings>enable</ImplicitUsings>

Small changes, but they remove noise from every single file — which is why almost every new project turns both on.

C# 11 — required and raw strings 🟡 Intermediate

public class Order
{
    public required string CustomerId { get; init; }   // must be set
    public string? Notes { get; init; }                 // optional
}

var a = new Order();                          // compile error - CustomerId not set
var b = new Order { CustomerId = "acme" };    // fine

This solves a real problem: object initialisers were convenient but let you forget a mandatory property. Previously your only option was a constructor, which is awkward with many properties.

// Before: every quote escaped, unreadable
var json = "{\"name\": \"Ada\", \"role\": \"engineer\"}";

// After: three or more quotes, and the content is literal
var json = """
    { "name": "Ada", "role": "engineer" }
    """;

Especially good for embedded JSON, SQL and regex — the three places escaping used to hurt most. The closing delimiter's indentation is stripped from every line, so it stays readable in context.

C# 12 — primary constructors and collection expressions 🟡 Intermediate

Primary constructors are the change you'll notice most in a DI-heavy codebase:

public sealed class OrderService
{
    private readonly IOrderRepository _orders;
    private readonly ILogger<OrderService> _log;

    public OrderService(IOrderRepository orders, ILogger<OrderService> log)
    {
        _orders = orders;
        _log = log;
    }
}
public sealed class OrderService(IOrderRepository orders, ILogger<OrderService> log)
{
    // 'orders' and 'log' are usable directly in any member
}

Nine lines become one. This is why most examples in this handbook use that form.

One caveat worth knowing

Primary constructor parameters on a class are mutable within the class — they aren't automatically readonly fields. If that matters, assign them to explicit readonly fields. (On a record, they become public properties instead, which is a different behaviour again.)

int[]        a = [1, 2, 3];
List<string> b = ["x", "y"];
Span<int>    c = [1, 2, 3];

int[] combined = [..a, 4, 5];      // spread operator

One syntax that works across arrays, lists and spans — and it's why you'll see [] instead of new List<T>() throughout this handbook.

C# 13 💡 Good to know

An incremental release. The two most practical items:

  • params collections — params now works with Span<T>, IEnumerable<T> and others, not just arrays. That avoids an array allocation on every call in hot paths.
  • Lock object — a dedicated System.Threading.Lock type that lock recognises, which is faster than locking on a plain object.

Also: field keyword work, implicit index access in initialisers, and more flexible ref struct usage. Verify specifics against current docs — this is the area most likely to have shifted since writing.

Which of these to actually adopt ⭐ Senior-level

FeatureVerdictWhy
Nullable reference typesAlways, on new projectsCatches a whole bug class at compile time. Highest value change available
Records for DTOs and valuesAlwaysCorrect equality and hashing for free — see the GetHashCode trap
File-scoped namespaces, global usingsAlwaysPure noise reduction, zero risk
Primary constructorsYes for DI-heavy classesRemoves real boilerplate; watch the mutability caveat
Collection expressionsYesShorter and works uniformly across collection types
Raw string literalsYes, where escaping hurtEmbedded JSON/SQL/regex become readable
Top-level statementsSparinglyGreat for samples and tiny tools; less clear in a large app's entry point

Senior signal

Adopting a feature because it's new is as bad as refusing to. The strong position is to name what a feature buys you: nullable reference types buy compile-time null safety, records buy correct equality, primary constructors buy less boilerplate.

And be able to name one you'd use carefully. Default interface methods are a good example — they exist for versioning a published interface, and using them as a general design tool leads to confusion about where behaviour lives.

Key takeaways
  • C# version follows TargetFramework; you rarely set it directly.
  • C# 8's nullable reference types are the highest-value setting in a new project.
  • C# 9's records are the default choice for DTOs, events and value objects.
  • C# 12's primary constructors and collection expressions are the two changes most visible in everyday code.
  • Judge features by what they buy you, not by how new they are.

Interview questions

What recent C# features do you like, and which do you avoid?
How I'd answer

"The one I'd turn on in every project is nullable reference types. It converts a whole class of runtime null-reference bugs into compiler warnings. On a legacy codebase it's noisy at first, so I'd enable it per-project and fix as I go rather than all at once."

"Records are my default for DTOs, events and value objects. Partly the brevity, but mainly correctness: you get Equals and GetHashCode that agree with each other, which is something people get wrong by hand — and getting it wrong makes objects vanish from dictionaries."

"Primary constructors in C# 12 remove real boilerplate in DI-heavy classes — nine lines down to one. The caveat is that on a class the parameters aren't automatically readonly, so if immutability matters I still assign to explicit readonly fields."

"Raw string literals for anything with embedded JSON, SQL or regex. That was genuinely painful before."

"What I'd use carefully: default interface methods. They exist so a library author can add a member without breaking implementers, and that's a good reason. Using them as a general design tool gets confusing, because there's still no state and the resolution rules are subtle. I'd also use top-level statements sparingly — fine for tools and samples, less clear as the entry point of a large application."

What they're really checking
  • Are you still learning the language, or did you stop at C# 7?
  • Do you evaluate features on merit rather than novelty?
  • Can you name a caveat? That's the part that shows real use.
Weak answers
  • Red flag: not being able to name anything past C# 7 or 8.
  • Red flag: listing features with no reason why they help.
Likely follow-ups
  • How would you introduce nullable reference types into a large legacy codebase?
  • When is a record the wrong choice?
  • What do default interface methods not give you that an abstract class does?
How would you enable nullable reference types on a 200,000-line legacy codebase?
How I'd answer

"Not all at once. Turning it on globally would produce thousands of warnings, everyone would ignore them, and the feature would be worthless."

"I'd go project by project, starting with the ones where null bugs actually hurt — usually the domain and application layers rather than the outer edges. Enable it in one project, fix that project's warnings, treat them as errors from then on so they can't regress."

"For each project the work is mostly mechanical: mark things ? that genuinely can be null, and add guard clauses where they can't. The interesting part is that it forces you to decide — and that's where you find the real bugs, in places where nobody had ever thought about whether null was possible."

"I'd resist two shortcuts. The null-forgiving operator ! silences the warning without fixing anything, so I'd only use it where I can prove non-null and add a comment saying why. And #nullable disable at the top of a file is a way of pretending you did the work."

"One thing I'd flag to the team: these are compile-time annotations only. A non-nullable string can still be null at runtime — from deserialization, reflection, or a library without annotations. So it doesn't remove the need to validate data at boundaries; it removes the need to defensively null-check your own internal code."

What they're really checking
  • Do you know incremental adoption beats a big-bang change?
  • Do you know the annotations aren't enforced at runtime?
  • Do you recognise ! as a smell rather than a solution?
Likely follow-ups
  • What does the ! operator actually do?
  • How do you handle a third-party library with no annotations?
