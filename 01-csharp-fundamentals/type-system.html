Types & Memory Layout

The single highest-value C# topic for interviews. Almost every "why did that happen?" bug in .NET traces back to something on this page.

🟢 Beginner 🟡 Intermediate 🔥 Must know
Quick revision
  • Value type — assignment copies the data. Reference type — assignment copies the address, so both variables see one object.
  • Value types: int, bool, decimal, DateTime, struct, enum. Reference types: class, interface, string, arrays, delegates.
  • Boxing = putting a value type on the heap so it can be treated as object. Allocates. In a hot loop, it hurts.
  • string is a reference type that behaves like a value — immutable, with value equality.
  • record gives you value equality and a with expression. Use it for data, not for entities with identity.
  • Override Equals? You must override GetHashCode too, or your objects go missing in dictionaries.

Value types vs reference types 🔥 Must know

In simple terms

A value type variable holds the thing itself. Copy it and you get two independent things.

A reference type variable holds directions to the thing. Copy it and you get two sets of directions to one thing.

Think of it this way

Value type = a photocopy. I photocopy a document and hand it to you. You scribble on yours; mine is untouched.

Reference type = a shared Google Doc link. I send you the link. You edit it, and I see the change immediately — because there was only ever one document.

See it happen

public class OrderClass { public int Total; }

var a = new OrderClass { Total = 100 };
var b = a;              // copies the ADDRESS
b.Total = 500;

Console.WriteLine(a.Total);   // 500  <- a changed too
public struct OrderStruct { public int Total; }

var x = new OrderStruct { Total = 100 };
var y = x;              // copies the DATA
y.Total = 500;

Console.WriteLine(x.Total);   // 100  <- x is untouched

Same code shape, opposite result. The only difference is class versus struct.

Common mistake — the one that bites in real code

Passing a List<T> into a method and being surprised that the caller's list changed.

void AddDefaults(List<string> items)
{
    items.Add("default");        // the CALLER's list now has this
}

List<T> is a reference type. You didn't get a copy of the list — you got directions to it. If you want the caller protected, take IReadOnlyList<T> or copy it yourself.

What about ref? 🟡 Intermediate

ref passes the variable itself, not its contents. That lets you reassign what the caller's variable points at:

void Replace(List<string> list)      { list = new List<string> { "new" }; }
void ReplaceRef(ref List<string> list) { list = new List<string> { "new" }; }

var items = new List<string> { "old" };

Replace(items);
Console.WriteLine(items[0]);      // "old"  - reassigned only the local parameter

ReplaceRef(ref items);
Console.WriteLine(items[0]);      // "new"  - reassigned the caller's variable
Remember this

Reference type ≠ passed by reference.

By default C# passes the reference by value. You can change the object's contents, but you can't repoint the caller's variable — unless you use ref.

Stack and heap 🟡 Intermediate

In simple terms

The stack is a small, fast scratchpad tied to the currently running method. It's cleaned up automatically when the method returns.

The heap is a large shared area for objects that must outlive the method. The garbage collector cleans it up later.

Think of it this way

The stack is your desk — you pile things on it while you work, and it's swept clean when you finish the task.

The heap is the warehouse. Things live there long-term, and someone has to come round and clear out what nobody references any more.

StackHeap
HoldsLocals, parameters, and value types declared as localsObjects (all reference types), and value types that are fields of an object
CleanupAutomatic on method returnGarbage collector
SpeedVery fast — just moves a pointerSlower to allocate; costs GC work later
SizeSmall (~1 MB per thread by default)Large
The nuance that impresses ⭐ Senior-level

"Value types live on the stack" is the textbook answer and it's not quite true.

A value type lives wherever its container lives. An int local sits on the stack. An int field inside a class sits on the heap, inside that object. A struct captured by a lambda or held in an async method's state machine also ends up on the heap.

Saying that — and adding that the stack/heap split is a CLR implementation detail, not a language guarantee — is a strong senior answer.

Boxing and unboxing 🔥 Must know

In simple terms

Boxing wraps a value type in an object on the heap, so it can be used where an object is expected.

Unboxing pulls the value back out — and it requires a cast, which can fail.

Think of it this way

You have a £5 note. To post it, you put it in an envelope — that's boxing. The envelope is a new thing that had to be created, and it's not free.

Do that once and nobody cares. Do it a million times in a loop and you've generated a million envelopes for the bin collector to deal with.

int number = 42;

object boxed = number;        // BOXING: allocates on the heap
int unboxed = (int)boxed;     // UNBOXING: copies the value back out

// This throws InvalidCastException - the box holds an int, not a long
long wrong = (long)boxed;

Where boxing hides

Explicit boxing is rare. The problem is the accidental kind:

// 1. Old non-generic collections - boxes every single item
var list = new System.Collections.ArrayList();
for (var i = 0; i < 1_000_000; i++) list.Add(i);      // 1M boxes

// 2. String concatenation with a value type
string s = "Count: " + 42;                             // 42 gets boxed

// 3. Non-generic Equals / interfaces
int x = 5;
bool same = x.Equals((object)5);                        // boxes the argument
// Generic collections are typed - no boxing
var list = new List<int>();
for (var i = 0; i < 1_000_000; i++) list.Add(i);       // zero boxes

// Interpolation with a value type calls the type's own ToString
string s = $"Count: {42}";                              // no boxing in modern .NET
Remember this

Generics exist largely to eliminate boxing.

Before C# 2.0, storing an int in a collection meant boxing it. That's why ArrayList is a museum piece and List<T> is what you use.

Keep it in proportion

Boxing is a hot-path concern. One box in a request handler is irrelevant. A million boxes inside a tight loop shows up in a profiler as GC pressure.

In an interview, say that. "I'd avoid it in a loop over a large collection; I wouldn't restructure readable code to remove a single box" is a better answer than treating all allocation as evil.

class vs struct — how to choose 🔥 Must know

The practical rule: use a class unless all of these are true:

  1. It logically represents a single value (a point, a money amount, a date range).
  2. It's small — roughly 16 bytes or less.
  3. It's immutable.
  4. It won't be boxed frequently.
Production trap — the mutable struct

This is the classic C# gotcha, and it's worth being able to explain:

struct Counter { public int Value; }

var counters = new List<Counter> { new Counter { Value = 0 } };

counters[0].Value = 5;        // won't even compile - "cannot modify the return value"

var c = counters[0];          // this compiles...
c.Value = 5;                  // ...but modifies a COPY
Console.WriteLine(counters[0].Value);   // 0 - the list is unchanged

counters[0] returns a copy of the struct, so you mutate the copy and throw it away. The fix is to make structs readonly so the compiler stops you trying — or use a class.

// readonly: the compiler enforces that nothing can mutate it
public readonly struct Point(double X, double Y)
{
    public double DistanceTo(Point other) =>
        Math.Sqrt(Math.Pow(X - other.X, 2) + Math.Pow(Y - other.Y, 2));
}

Records 🟡 Intermediate

In simple terms

A record is a class (or struct) where the compiler writes the boring parts for you: value equality, a readable ToString, and a with expression for copying.

Use it when the type is data. Use a plain class when the type has identity and behaviour.

public record Money(decimal Amount, string Currency);

var a = new Money(10, "GBP");
var b = new Money(10, "GBP");

Console.WriteLine(a == b);          // True  - value equality, free
Console.WriteLine(a);               // Money { Amount = 10, Currency = GBP }

var c = a with { Amount = 20 };     // copy with one change

Compare that to a plain class, where a == b would be False because they're two different objects.

UseWhenExample
record (class)Data with value semantics, possibly largishDTOs, API requests, events, commands
readonly record structSmall immutable value, avoid heap allocationMoney, Point, an ID wrapper
classHas identity, lifecycle and behaviourOrder, Customer — an entity
Common mistake — with is a shallow copy

If a record holds a List<T>, the copy and the original share the same list. Add to one and it appears in the other.

The record itself is immutable; what it points at may not be. Hold ImmutableArray<T> or expose IReadOnlyList<T> over a defensively copied array if you need it immutable all the way down.

Enums — and the trap when you persist them 🟢 Beginner

In simple terms

An enum is a named set of integer constants. It's a value type.

Its job is to replace magic numbers and loose strings with something the compiler can check.

public enum OrderStatus
{
    Draft = 0,        // assigned explicitly - do this
    Paid = 1,
    Shipped = 2,
    Cancelled = 3
}
Production trap — reordering a persisted enum

By default an enum's members are numbered 0, 1, 2… in declaration order, and databases usually store that number.

So if someone later inserts a value in the middle:

public enum OrderStatus
{
    Draft,            // 0
    PendingPayment,   // 1  <- inserted here
    Paid,             // 2  (was 1)
    Shipped,          // 3  (was 2)
    Cancelled         // 4  (was 3)
}

Every row that stored 1 meaning "Paid" now reads back as "PendingPayment". Nothing errors. Nothing warns. Your data has silently changed meaning.

Two defences: always assign values explicitly and never reuse or reorder them, or persist the enum as a string so the stored value is self-describing. Strings cost a little space and buy you safety and readable data.

Two more things worth knowing:

  • An enum can hold a value that isn't defined. (OrderStatus)99 compiles and runs. So validate input with Enum.IsDefined at boundaries, and always handle the unexpected case in a switch.
  • [Flags] lets you combine values as bits — assign powers of two (1, 2, 4, 8) and use HasFlag or bitwise operators. Useful for permission sets.

Why string is special 🔥 Must know

In simple terms

string is a reference type that behaves like a value type: it's immutable, and == compares the text rather than the address.

var s = "hello";
s.ToUpper();                     // does nothing to s - returns a NEW string
Console.WriteLine(s);            // "hello"

s = s.ToUpper();                 // reassignment is what changes s
Console.WriteLine(s);            // "HELLO"

// Value-style equality, even though string is a reference type
Console.WriteLine("abc" == "abc");   // True

Immutability is why strings are safe to share between threads and safe to use as dictionary keys. It's also why the loop below is a classic performance mistake:

var result = "";
foreach (var line in tenThousandLines)
    result += line;              // ~10,000 string allocations, each copying everything so far
var sb = new StringBuilder();
foreach (var line in tenThousandLines)
    sb.Append(line);
var result = sb.ToString();      // one allocation at the end
Don't over-apply it 💡 Good to know

Concatenating three or four strings is fine — the compiler turns a + b + c into a single String.Concat call. StringBuilder is for loops and unknown-length building, not for every concatenation.

Equality: ==, Equals, and GetHashCode 🟡 Intermediate

ComparisonDefault behaviour
== on a classReference equality — are these the same object?
== on a structDoesn't compile unless the struct defines the operator
== on string / recordValue equality (both override it)
.Equals()Reference equality for classes; field-by-field for structs and records
ReferenceEquals()Always reference equality — can't be overridden
Production trap — the missing GetHashCode

If you override Equals you must override GetHashCode. Here's what happens if you don't:

public class CustomerId
{
    public int Value { get; init; }
    public override bool Equals(object? o) => o is CustomerId c && c.Value == Value;
    // GetHashCode NOT overridden - inherits reference-based hashing
}

var dict = new Dictionary<CustomerId, string>();
dict[new CustomerId { Value = 1 }] = "Ada";

var lookup = new CustomerId { Value = 1 };
Console.WriteLine(dict.ContainsKey(lookup));   // False!

A dictionary finds the bucket using the hash, and only then compares with Equals. Two "equal" objects with different hashes land in different buckets, so the lookup never even gets to the comparison.

The rule: equal objects must have equal hash codes. Using a record gets both right for free — which is the main reason to prefer records for value-like types.

Nullable types 🟡 Intermediate

Two different features share the ? syntax, and mixing them up is common.

Remember this

Nullable reference types are warnings, not guarantees.

A non-nullable string can still be null at runtime — from reflection, deserialization, or a library that doesn't have annotations. So still validate data crossing your boundaries.

// In the .csproj - this is the single highest-value setting in a new project
<Nullable>enable</Nullable>
<TreatWarningsAsErrors>true</TreatWarningsAsErrors>
string name = null;          // warning: cannot convert null to non-nullable
string? maybe = null;        // fine - explicitly nullable

Console.WriteLine(maybe.Length);          // warning: possible null dereference
Console.WriteLine(maybe?.Length ?? 0);    // fine
Key takeaways
  • Value = copied, reference = shared. This one distinction explains most surprise-mutation bugs.
  • Reference types are still passed by value — you need ref to repoint the caller's variable.
  • Value types live wherever their container lives, not "always on the stack".
  • Boxing allocates. It matters in loops, not in one-off code.
  • Prefer class; use struct only for small immutable values.
  • Never write a mutable struct. Mark structs readonly.
  • string is an immutable reference type with value equality — use StringBuilder in loops.
  • Override Equals ⇒ override GetHashCode. Or just use a record.
  • Nullable reference types are compile-time only. Still validate at boundaries.

Common mistakes

  • Assuming a method got a copy of your list. It got the same list.
  • Mutable structs — modifications silently apply to a copy.
  • Overriding Equals without GetHashCode — objects disappear from dictionaries and Distinct() stops working.
  • += on strings inside a loop.
  • Using ArrayList, Hashtable or other non-generic collections — boxing plus no type safety.
  • Treating a non-nullable reference as guaranteed non-null after deserialization.
  • Big structs passed around by value, where the copying costs more than a heap allocation would have.

Interview questions

Basic

What's the difference between a value type and a reference type?
How I'd answer

"A value type variable holds the data itself, so assigning it copies the data — you end up with two independent values. A reference type variable holds a reference to an object, so assigning it copies the reference, and both variables point at the same object."

"The consequence is what actually matters day to day. If I pass a List into a method and it calls Add, the caller's list has changed — because there was only ever one list. If I pass a struct and the method modifies it, the caller sees nothing."

"On memory: value types are typically on the stack and reference types on the heap, but I'd qualify that — a value type lives wherever its container lives. An int field inside a class is on the heap, inside that object. It's also a CLR implementation detail rather than a language guarantee."

"And one thing people get wrong: 'reference type' doesn't mean 'passed by reference'. C# passes the reference by value, so I can change the object's contents but I can't repoint the caller's variable unless I use ref."

What they're really checking
  • Do you go past the definition to the consequence?
  • Do you know the "value types are on the stack" simplification is imprecise?
  • Do you understand pass-by-value of a reference?
Weak answers
  • Red flag: "value types go on the stack, reference types on the heap" and stopping there.
  • Red flag: saying reference types are passed by reference.
Likely follow-ups
  • Is string a value or reference type? Why does it behave the way it does?
  • What's boxing?
  • When would you choose a struct?

Intermediate

What is boxing, and why should you care?
How I'd answer

"Boxing is wrapping a value type in an object on the heap so it can be used where object is expected. Unboxing is casting it back out — and that cast can fail at runtime if the types don't match exactly."

"The reason to care is allocation. Every box is a heap allocation, which means GC pressure. In a loop over a large collection that's measurable; in a one-off call it's irrelevant."

"What matters practically is knowing where it hides, because explicit boxing is rare. The classic sources are non-generic collections like ArrayList, which boxes every item; calling a non-generic Equals or comparing through object; and older string formatting paths."

"That's really what generics were introduced for. List<int> stores ints directly with no boxing, whereas ArrayList boxes a million ints into a million objects. Same for IComparable<T> over the non-generic version."

"I'd keep it proportionate though. I'd remove boxing from a hot path if a profiler pointed at it — I wouldn't make readable code worse to avoid a single box."

What they're really checking
  • Do you know where boxing happens without being told?
  • Do you connect it to generics and to GC pressure?
  • Do you keep performance claims proportionate?
Likely follow-ups
  • Does $"{someInt}" box? Has that changed across .NET versions?
  • What happens when a struct implements an interface and you call through the interface?
  • How would you detect boxing in a running application?
When would you use a struct instead of a class?
How I'd answer

"Rarely — my default is a class, and I'd want a specific reason to deviate."

"I'd use a struct when the type represents a single logical value, it's small — roughly 16 bytes or less — it's immutable, and it won't be boxed a lot. Things like a point, a money amount, a strongly-typed ID wrapper. Framework examples are DateTime, TimeSpan, Guid."

"The payoff is avoiding a heap allocation, which matters if you're creating millions of them. But if it's large, you've replaced one cheap allocation with expensive copying on every assignment and every method call, so you can easily make things worse."

"The rule I hold firmly is: never write a mutable struct. If you put one in a collection, the indexer returns a copy, so modifying what you read out silently does nothing — and it's a genuinely confusing bug because the code looks correct. I mark structs readonly so the compiler enforces it."

"In modern C# I'd usually reach for readonly record struct. It gives me immutability, value equality and a correct GetHashCode without writing any of it."

What they're really checking
  • Do you default to the safe option and justify deviating?
  • Do you know the mutable-struct trap?
  • Do you know large structs can be slower, not faster?
Weak answers
  • Red flag: "structs are faster, so use them for performance."
  • Red flag: not knowing the collection-indexer copy problem.
Likely follow-ups
  • What does readonly struct actually change?
  • What's ref struct for?
  • Can a struct inherit? Can it implement an interface?

Advanced

Why must you override GetHashCode when you override Equals? ⭐ Senior-level
How I'd answer

"Because hash-based collections use the hash code to decide where to look, and only use Equals to confirm once they're in the right bucket."

"So if two objects are equal but return different hash codes, they get put in different buckets. A dictionary lookup computes the hash, goes to that bucket, doesn't find the key there, and reports it isn't present — without ever calling Equals. The object is effectively invisible."

"It breaks more than dictionaries: HashSet, Distinct(), GroupBy and ToDictionary all rely on the same contract."

"The contract itself is: equal objects must have equal hash codes. The reverse isn't required — unequal objects may collide, and the collection handles that by comparing within the bucket."

"There's a second trap worth mentioning: the hash must be stable while the object is in the collection. If you hash on a mutable property and then change it, the object is now in the wrong bucket and you can't find or remove it. That's an argument for hashing only on immutable identity."

"In practice I'd avoid writing either by hand. A record generates both correctly, and if I do need custom logic I'd use HashCode.Combine rather than inventing an arithmetic scheme."

What they're really checking
  • Do you know how a hash table works, not just the rule?
  • Do you know the contract is one-directional?
  • Do you spot the mutable-key problem?
Likely follow-ups
  • What does record generate for equality, exactly?
  • Should GetHashCode be stable across process restarts?
  • How would you implement equality for an entity with a database ID?
Model money in C#. What type do you choose and why?
How I'd answer

"I'd use a readonly record struct Money(decimal Amount, string Currency), and I'd justify each part."

"decimal rather than double, because double is binary floating point and can't represent 0.1 exactly. That produces rounding errors that accumulate, which is unacceptable for money. decimal is base-10 and has the precision for financial values."

"A struct because money is a single small immutable value and there may be a lot of them. readonly so the compiler guarantees immutability and I can't hit the mutable-struct copy trap."

"A record because I want value equality — ten pounds is ten pounds regardless of which instance it is — and records give me correct Equals and GetHashCode without hand-writing them."

"The currency is the important design point. Carrying it in the type means I can reject adding GBP to USD in the Add method rather than silently producing a wrong total. I'd validate in the constructor so an invalid Money can't exist anywhere in the program."

"For storage I'd map amount and currency as two columns with an explicit precision and scale — something like decimal(19,4) — because letting the database pick a default is how you get silent truncation. And if it needed to support many currencies with different minor units, I'd consider storing integer minor units instead of decimals."

What they're really checking
  • Do you know why double is wrong for money? This is close to a required answer.
  • Do you put currency in the type rather than alongside it?
  • Do you think about persistence precision?
Weak answers
  • Red flag: double, or decimal with no reason given.
  • Red flag: a bare decimal with currency tracked separately — that's how mismatched-currency bugs happen.
Likely follow-ups
  • How do you handle dividing money three ways without losing a penny?
  • How would you map this in EF Core?
  • What about currencies with no minor unit, like the yen?
