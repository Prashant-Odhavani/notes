Fundamentals

Keys, queries and indexes. Four concepts, and they determine everything the table can ever do.

🟢 Beginner 🟡 Intermediate 🔥 Must know
Quick revision
  • Partition key decides where the item lives. Sort key decides order within that partition.
  • Query needs the partition key and is efficient. Scan reads the whole table.
  • The sort key is where range queries and hierarchies come from. It's the most underused feature.
  • GSI = a different partition key, eventually consistent, its own capacity. LSI = same partition key, different sort key.
  • Reads are eventually consistent by default. Strongly consistent costs 2×.
  • Conditional writes are how you get atomicity and optimistic concurrency.
  • 400 KB item limit, and 10 GB per partition-key value if you use an LSI.

Partition key and sort key 🔥 Must know

In simple terms

The partition key is hashed to decide which physical partition stores the item. That's how DynamoDB finds data in constant time regardless of table size.

The sort key orders items within a partition. That's what turns a key-value store into something you can range-query.

Key typeStructureCapability
Simple Partition key only Pure key-value. Get one item by key. Nothing else
Composite Partition key + sort key Get one item, or a sorted range within a partition. Far more useful
Remember this

The sort key is where most of DynamoDB's power lives, and it's the part people underuse.

With a composite key you can ask: "all of this user's orders since March, newest first", "the latest version of this document", "all events for this device in this hour" — all as a single efficient query.

A table with only a partition key can answer exactly one question: give me this item.

// Table: PK = "USER#123", SK = "ORDER#2024-06-01#1041"
var request = new QueryRequest
{
    TableName = "app",
    KeyConditionExpression = "PK = :pk AND begins_with(SK, :prefix)",
    ExpressionAttributeValues = new Dictionary<string, AttributeValue>
    {
        [":pk"]     = new AttributeValue { S = "USER#123" },
        [":prefix"] = new AttributeValue { S = "ORDER#2024-06" }
    },
    ScanIndexForward = false,       // descending - newest first
    Limit = 20
};
Sort key conditionMeaning
SK = :vExact match — one item
SK < :v, >, <=, >=Range
SK BETWEEN :a AND :bBounded range
begins_with(SK, :p)Prefix — the hierarchy workhorse
No contains, ends_with, or arbitrary expressions — the sort key is sorted lexicographically, so only prefix and range work
Why sort keys are strings with delimiters

Sort keys are compared lexicographically. So encoding a hierarchy as ORDER#2024-06-01#1041 means begins_with(SK, "ORDER#2024-06") gets that month, and begins_with(SK, "ORDER#") gets all orders.

Two consequences. Use ISO-8601 dates (2024-06-01), because lexicographic order matches chronological order — 01/06/2024 does not. And zero-pad numbers: ITEM#0042 sorts correctly where ITEM#42 sorts after ITEM#300.

That's a small detail that causes genuinely confusing bugs, because the query works and returns the wrong order.

Filter expressions don't reduce cost

This is the most expensive misunderstanding in DynamoDB.

A FilterExpression is applied after items are read and after capacity is consumed. So a scan with a filter returning 10 items out of a million still reads and charges for all one million.

It looks like a WHERE clause and it behaves like filtering in application code — with the network transfer avoided but none of the cost.

Only key conditions reduce what's read. Filters are for trimming results you've already paid for, which is occasionally useful and never an optimisation.

Scan is acceptable when
A one-off migration or backfill
An admin or debugging tool on a small table
Exporting the whole table anyway
A genuinely tiny table — a few hundred config items

Anything else on a request path means the key design doesn't serve that access pattern, and the fix is a GSI or a different key structure — not a faster scan.

GSIs and LSIs 🔥 Must know

Why they exist

The table's key structure supports one access pattern well. A secondary index gives you another one, by maintaining a copy of the data under different keys.

That's the important mental model: a GSI is a managed, automatically-maintained duplicate of your data with different keys. Not a pointer structure like a relational index.

GSI (Global)LSI (Local)
Partition keyCan be differentMust be the same as the table's
Sort keyAny attributeA different attribute
ConsistencyEventually consistent onlyStrongly consistent available
CapacityIts ownShares the table's
Create laterYesNo — only at table creation
Count limit20 (soft)5, fixed
Size constraintNoneImposes a 10 GB limit per partition-key value
Remember this

Use GSIs. Avoid LSIs.

An LSI can only be created with the table — so if you need another one later, that's a table migration. And it imposes a 10 GB ceiling per partition-key value on the whole table, which is a significant constraint accepted for very little benefit.

The only thing an LSI offers that a GSI doesn't is strongly consistent reads on the index. If you need that, use it deliberately — otherwise GSI, always.

GSI throttling is a separate failure mode

A GSI has its own capacity, and writes to the table propagate to it. So if the GSI is under-provisioned, writes to the base table get throttled — because DynamoDB can't accept a write it cannot replicate to the index.

That's a confusing symptom: your table has plenty of capacity, and writes are failing. The cause is an index you weren't monitoring.

Same applies to a hot partition in the GSI. A GSI whose partition key has low cardinality — status, say — creates a hot partition that throttles base-table writes. Worth designing GSI keys as carefully as the table's own.

Index projections

ProjectionCopiesTrade-off
KEYS_ONLYJust the keysCheapest storage; needs a second read for other attributes
INCLUDEKeys plus named attributesUsually right — enough to serve the query
ALLEverythingNo extra read, doubles storage and write cost
Projection is a real cost decision

A GSI with ALL is a full second copy of the table — double the storage, and every write costs capacity on both.

KEYS_ONLY is cheapest but means a follow-up BatchGetItem for the actual attributes, which is an extra round trip and extra capacity.

INCLUDE with exactly the attributes the query needs is normally the right answer — and note that if the projection doesn't cover an attribute you filter on, DynamoDB cannot fetch it from the base table during an index query. The attribute simply isn't there. That surprises people expecting relational index behaviour.

Sparse indexes — the underused trick

Table items:
  { PK: "ORDER#1", status: "shipped" }                        -- not in the GSI
  { PK: "ORDER#2", status: "pending", pendingSince: "2024-06-01" }   -- IS in the GSI

GSI: partition key = pendingSince
  -> contains only pending orders. Tiny index, cheap to query and maintain.
Senior signal — sparse indexes replace the "query by status" problem

"Find all pending orders" is the classic DynamoDB modelling problem. A GSI on status is bad — low cardinality, so one hot partition holds every pending order.

A sparse index solves it elegantly: only write the pendingSince attribute while the order is pending, and remove it when the status changes. Items without the attribute don't appear in the index at all.

So the index contains only the small working set. It's tiny, it fits in cache, it's cheap to maintain, and it shrinks automatically as orders are processed — items leave the index when the attribute is removed.

This is the DynamoDB equivalent of a partial index, and knowing it is a strong signal because it's not obvious from the documentation.

Consistency 🟡 Intermediate

Read typeGuaranteeCost
Eventually consistent (default)May not reflect a very recent write0.5 RCU per 4 KB
Strongly consistentReflects all completed writes1 RCU per 4 KB — 2×
Transactional readSerializable, across items2 RCU per 4 KB — 4×
GSIs are always eventually consistent

There is no strongly-consistent read on a GSI, at any price. The index is updated asynchronously after the base table write.

The lag is normally milliseconds, and it means write-then-query-the-GSI can miss the item you just wrote. That's a read-your-own-writes bug in the same family as replica lag.

If a flow writes an item and immediately needs to find it via a GSI, restructure so it reads by primary key instead — or return the item you already have rather than re-querying.

Conditional writes 🔥 Must know

var request = new UpdateItemRequest
{
    TableName = "inventory",
    Key = new Dictionary<string, AttributeValue> { ["PK"] = new AttributeValue { S = sku } },
    UpdateExpression    = "SET stock = stock - :qty",
    ConditionExpression = "stock >= :qty",          // checked atomically
    ExpressionAttributeValues = new Dictionary<string, AttributeValue>
    {
        [":qty"] = new AttributeValue { N = qty.ToString() }
    }
};

try { await client.UpdateItemAsync(request); }
catch (ConditionalCheckFailedException)
{
    throw new InsufficientStockException(sku);      // condition wasn't met
}
Remember this

Conditional expressions are how DynamoDB gives you correctness without transactions.

The condition is evaluated atomically with the write, so there's no window between checking and changing. That's the same atomic-conditional-update pattern as everywhere else, and here it's the primary tool rather than a nice option.

Two staple uses: attribute_not_exists(PK) for an insert-if-absent, and a version check for optimistic concurrency.

// Optimistic locking on a version attribute
ConditionExpression = "version = :expected",
UpdateExpression    = "SET #s = :status, version = version + :one"

// Idempotent insert - fails if the item already exists
ConditionExpression = "attribute_not_exists(PK)"
// ConditionalCheckFailedException = already processed. The idempotency primitive.
This is the idempotency primitive

attribute_not_exists(PK) plus catching ConditionalCheckFailedException is a complete idempotency key implementation.

Insert succeeds → do the work. Condition fails → already handled, return the previous result. One operation, no race window, no read-then-write gap.

Exactly the same shape as Postgres ON CONFLICT DO NOTHING and a unique-constraint violation in SQL Server. Three databases, one pattern — recognising that is worth more than memorising any of them.

The 1 MB pagination trap

A query stops at 1 MB of data read — before applying a filter expression. So a query with a filter can return zero items and still have more results, because the 1 MB it read all got filtered out.

An empty result set does not mean "no more data". The only end-of-data signal is LastEvaluatedKey being null. Code that stops paginating on an empty page silently misses results, and it's data-dependent so it passes testing.

Same class of bug as Cosmos continuation tokens — check the token, never the result count.

Key takeaways
  • Partition key decides location; sort key decides order within it and enables ranges.
  • Sort keys are lexicographic — use ISO dates and zero-padded numbers.
  • Query needs the partition key; scan reads everything and degrades forever.
  • Filter expressions don't reduce cost — they apply after reading.
  • A GSI is a maintained duplicate under different keys. Use GSIs, avoid LSIs.
  • An under-provisioned or hot GSI throttles base table writes.
  • INCLUDE projections normally; a missing attribute can't be fetched from the base table.
  • Sparse indexes solve "query by status" without a hot partition.
  • GSIs are always eventually consistent — no strongly consistent read exists.
  • Conditional expressions give atomicity and idempotency without transactions.
  • An empty query page doesn't mean end of data — check LastEvaluatedKey.

Common mistakes

  • Believing a filter expression saves capacity.
  • Scans on request paths because the key design doesn't fit.
  • Creating LSIs, accepting the 10 GB limit and immutability for little gain.
  • Not monitoring GSI capacity, so base-table writes throttle inexplicably.
  • A low-cardinality GSI partition key such as status.
  • Expecting strongly consistent GSI reads.
  • Write then immediately query a GSI, missing the item.
  • Non-ISO dates or unpadded numbers in sort keys, giving wrong order.
  • Stopping pagination on an empty page.
  • Read-modify-write instead of a conditional expression.
  • Large blobs in items against the 400 KB limit.

Interview questions

Intermediate

What's the difference between a query and a scan? 🔥 Must know
How I'd answer

"A query requires the partition key. DynamoDB hashes it, goes straight to that partition, and reads only the matching items — optionally narrowed by a sort key condition. The cost is proportional to what you get back, and it stays constant as the table grows."

"A scan reads every item in the table. Cost is proportional to table size, so it degrades linearly forever."

"The thing I'd emphasise, because it's the most expensive misunderstanding in DynamoDB: a filter expression does not reduce cost. It's applied after items are read and after capacity is consumed. So a scan with a filter that returns 10 items out of a million still reads and charges for all million. It looks like a WHERE clause and it's really client-side filtering with the network transfer saved."

"Only key conditions reduce what's read. Filters trim results you've already paid for."

"There's a related trap: a query or scan stops at 1 MB of data read, before filtering. So a filtered query can return zero items and still have more results. An empty result set is not the end of the data — the only signal is LastEvaluatedKey being null. Code that stops paginating on an empty page silently misses results, and it's data-dependent so it passes testing."

"On when a scan is acceptable: one-off migrations, backfills, exports, an admin tool on a genuinely tiny table. Never on a request path."

"And the important framing — if I find myself needing a scan for a normal application feature, that's not a query problem, it's a modelling problem. It means the key structure doesn't serve that access pattern, and the fix is a GSI or a different key design. Optimising the scan — parallel segments, tighter filters — is treating the symptom."

What they're really checking
  • Do you know filters don't reduce cost? That's the discriminating one.
  • Do you know the 1 MB / empty-page trap?
  • Do you treat a needed scan as a modelling failure?
Likely follow-ups
  • How would you find all orders with status "pending"?
  • What's a parallel scan, and when is it justified?
  • How do you paginate correctly?

Advanced / scenario

You need to find all orders with status "pending". How? ⭐ Senior-level
How I'd answer

"This is the classic DynamoDB modelling question, and the two obvious answers are both wrong — which is why it's asked."

"A scan with a filter on status is what people reach for first. It reads the entire table and charges for all of it, then discards the non-pending items. Correct results, cost proportional to table size, and it degrades forever as the table grows."

"A GSI with status as the partition key looks like the proper fix and is arguably worse. status has maybe five distinct values, so every pending order lands in one partition. That partition is capped at 3,000 RCU and 1,000 WCU, so it becomes a hot partition — and because a GSI shares the write path, throttling on that index throttles writes to the base table. You've turned a read problem into a write outage."

"The right answer is a sparse index."

"I'd only write a pendingSince attribute while the order is pending, and REMOVE it when the status changes. Then a GSI partitioned on something high-cardinality — a date bucket, say — with pendingSince as the sort key. Items without the attribute don't appear in the index at all."

"So the index contains only the current working set — maybe a few thousand items rather than the whole table. It's tiny, it stays in cache, it's cheap to maintain, and it shrinks automatically as orders are processed, because removing the attribute removes the index entry. That last property is what makes it elegant: the index is self-cleaning."

"On the partition key for that GSI, I'd avoid a single constant value even though the index is small — that's still one partition and still capped. A date bucket like PENDING#2024-06-01 spreads it while keeping the query targeted, since a worker processing pending orders knows roughly which days to look at."

"I'd use INCLUDE projection with just the attributes the worker needs — order id, customer, total — rather than ALL, since ALL duplicates the whole table and doubles write cost on every order."

"And I'd note the GSI is eventually consistent, always — there's no strongly consistent read on a GSI at any price. For a background worker picking up pending orders, a few milliseconds of lag is irrelevant. If something needed to write an order and immediately find it via this index, that would be a read-your-own-writes bug and I'd restructure to read by primary key instead."

"The general lesson I'd draw: in DynamoDB, 'query by low-cardinality attribute' is always a sparse index question. Same shape for 'unprocessed', 'flagged for review', 'needs retry' — any small working set within a large table. It's the direct equivalent of a partial index in Postgres."

What they're really checking
  • Do you reject both the scan and the naive GSI?
  • Do you know a low-cardinality GSI key creates a hot partition?
  • Do you know GSI throttling affects base-table writes?
  • Do you know the sparse index pattern?
  • Do you think about the GSI's own partition key and projection?
Weak answers
  • Red flag: "scan with a filter."
  • Red flag: "GSI on status" with no cardinality concern.
  • Red flag: no awareness of the GSI-to-base-table write coupling.
Likely follow-ups
  • How do you remove an attribute in an update expression?
  • What if you needed to page through millions of pending items?
  • How does this compare to a Postgres partial index?
