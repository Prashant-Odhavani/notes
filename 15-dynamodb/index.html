DynamoDB

The most constrained database in this handbook, and the most predictable. It forces a design process that other databases let you skip.

🟡 Intermediate ⭐ Senior-level

The fundamental difference 🔥 Must know

In simple terms

Every other database in this handbook lets you store data first and work out queries later. Relational normalisation, MongoDB documents, even Cosmos — you can retrofit a query with an index.

DynamoDB does not. You must enumerate every access pattern before you design the table, because the key structure is the query capability.

The design process, reversed

Relational: model the entities → normalise → write queries → add indexes as needed.

DynamoDB: list every access pattern → design keys that serve them → then see what the data looks like.

If you design a DynamoDB table by thinking about entities, you will build something that can't answer your queries — and the fix is a table migration, not an index.

Think of it this way

A relational database is a library with a catalogue. Any question can be answered by searching, and you can add a new index for a new kind of question.

DynamoDB is a set of pre-sorted shelves. Anything the shelving supports is instant. Anything it doesn't means walking every shelf — or rebuilding the shelving.

Senior signal — why "no query planner" is a feature

Every other database in this handbook has a section on the planner going wrong: stale statistics, parameter sniffing, a plan flip after a failover, cross-partition fan-out that worsens as data grows.

DynamoDB has none of those failure modes, because there is nothing to decide. A query either matches the key structure and is fast, or it doesn't and you can see that in the code.

That's the trade: you give up query flexibility and get predictability. For a system where p99 latency is a product requirement and 3am plan regressions are unacceptable, that's a genuinely good deal — and it's the strongest argument for DynamoDB that isn't about scale.

The honest warning

DynamoDB punishes uncertainty harder than anything else here. If the product is still discovering what it needs, you will design a table, ship it, discover a new access pattern, and face a choice between an expensive scan, a new GSI, or a table migration.

A relational database absorbs that churn — you add an index and move on. DynamoDB makes it structural.

So "we don't know all our queries yet" is a strong argument against DynamoDB, and saying so is better than demonstrating you can do single-table design. The pattern is impressive and it's not free.

The object persistence model fights single-table design

DynamoDBContext maps one POCO to one table with named properties. That's comfortable and it assumes a relational-style layout — one entity type per table.

Single-table design does the opposite: several entity types share a table with overloaded generic key names like PK and SK, whose meaning depends on the item type. The high-level mapper has no good way to express that.

So in practice: low-level API for single-table designs, object persistence only for simple one-entity-per-table models. Choosing the friendly API first and then trying to do single-table design is a common source of pain.

Always log consumed capacity in development
var request = new QueryRequest
{
    TableName = "app",
    ReturnConsumedCapacity = ReturnConsumedCapacity.TOTAL,
    // ...
};
var response = await client.QueryAsync(request);
logger.LogInformation("Consumed {Units} RCU", response.ConsumedCapacity.CapacityUnits);

Same reasoning as logging Cosmos RU charges and EF Core's SQL. Consumed capacity is the signal that tells you whether an operation is a targeted query or an accidental scan — and a scan returns correct results, so nothing else warns you.

One place DynamoDB is more capable than Cosmos

Transactions span partitions. TransactWriteItems handles up to 100 items across different partition keys and even different tables, atomically.

Cosmos has no cross-partition transaction at all — its transactional batch is scoped to one logical partition. So in Cosmos the partition key is your transaction boundary; in DynamoDB it isn't.

That's a genuine and often-overlooked advantage, because DynamoDB is usually characterised as the more restrictive of the two.

When would you choose DynamoDB, and when would you avoid it? 🔥 Must know
How I'd answer

"The deciding question is: do we know all our access patterns, and are they stable? Everything else follows from that."

"DynamoDB is different from every other database in this space because the key structure is the query capability. There's no query planner, so you can't retrofit a query with an index the way you would in Postgres or MongoDB. You enumerate the access patterns first, design keys to serve them, and the data layout falls out of that. If you design by thinking about entities, you'll build something that can't answer your questions."

"So I'd choose it when the access patterns are genuinely known and stable — session stores, shopping carts, user or device state, event ingestion, anything key-based at high volume. Also when predictable latency is a product requirement: single-digit milliseconds whether the table has a thousand items or a trillion, and no plan to regress at 3am. Every other database in this handbook has a failure mode where the planner picks something different after a failover or a statistics update. DynamoDB doesn't have that category of problem, because there's nothing to decide."

"And it's genuinely zero-operations — no instances, no upgrades, no vacuum, no index maintenance. On demand pricing means an idle table costs almost nothing, and you can calculate the bill from the access patterns before writing code."

"I'd avoid it when the queries aren't settled. That's the honest warning: DynamoDB punishes uncertainty harder than anything else. If the product discovers a new access pattern after launch, the options are an expensive scan, a new GSI, or a table migration — where a relational database would absorb it with one index. 'We don't know all our queries yet' is a strong argument against DynamoDB, and I'd rather say that than demonstrate I can do single-table design."

"I'd also avoid it for anything needing aggregation or reporting — there's no GROUP BY, no joins, no aggregate functions at all. You either maintain counters via streams or export to something else. And for relational integrity: no foreign keys, no constraints, so every invariant lives in application code."

"One thing I'd correct if it comes up: DynamoDB is usually described as the most restrictive option, but its transactions span partitions and even tables — up to 100 items atomically. Cosmos has no cross-partition transaction at all. So on that specific axis DynamoDB is the more capable of the two."

"The other practical consideration is team familiarity. Single-table design has a real learning curve, and a team applying relational instincts to DynamoDB tends to produce a table-per-entity layout with scans everywhere — which gets the costs of DynamoDB without the benefits."

What they're really checking
  • Do you lead with access patterns rather than scale?
  • Do you know the design process is reversed?
  • Will you argue against it when appropriate?
  • Do you know what it genuinely can't do — aggregation, joins?
Weak answers
  • Red flag: "it scales infinitely" as the main reason.
  • Red flag: "it's schemaless so it's flexible" — the opposite is true.
  • Red flag: no awareness that new access patterns are expensive.
