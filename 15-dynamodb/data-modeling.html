Single-Table Design

The technique DynamoDB is known for. Genuinely powerful, frequently misapplied, and it starts with a list rather than a diagram.

🔴 Advanced ⭐ Senior-level 🔥 Must know
Quick revision
  • Start with a written list of access patterns. Not an entity diagram.
  • Generic key names — PK, SK — because they hold different things per item type.
  • Prefix key values with the entity type: USER#123, ORDER#1041.
  • The goal is one query per screen, returning several entity types together.
  • Hierarchies go in the sort key, queried with begins_with.
  • Adjacency lists handle many-to-many.
  • Single-table isn't always right. Knowing when to use several tables matters.

Why one table 🔥 Must know

In simple terms

DynamoDB has no joins. So if a screen needs a user, their orders and their addresses, a table-per-entity layout means three round trips.

Put them in one table sharing a partition key, and one query returns all three — because they're physically adjacent, sorted by the sort key.

Think of it this way

Table-per-entity is filing by document type: all invoices in one cabinet, all customers in another. To assemble a customer's file you visit several cabinets.

Single-table is filing by customer: one folder per customer containing their details, their invoices and their addresses, in order. One trip.

BenefitDetail
One query per screenSeveral entity types returned together — the main point
Fewer round tripsLatency is dominated by round trips, not by data volume
CheaperOne table's capacity, and one query's overhead instead of N
Transactional writesRelated items can be written atomically
Less to operateOne table to monitor, back up, and configure

The design process 🔥 Must know

  1. List every access pattern in writing. "Get a user by id." "List a user's orders, newest first." "Get an order with its line items." Be exhaustive — this is the step that determines everything.
  2. Note the cardinality and direction of each relationship, and how often each pattern runs.
  3. Design the primary key to serve the most frequent patterns.
  4. Add GSIs for patterns the primary key can't serve.
  5. Write out the resulting item shapes in a table and check every pattern against it.
  6. Verify no pattern needs a scan. If one does, go back to step 3.
Step 1 is the whole thing

Everyone wants to skip to the key design. Every DynamoDB failure I've seen traces back to an access pattern nobody wrote down.

The reason it matters so much more here than elsewhere: in Postgres, a missed query means adding an index. In DynamoDB it can mean a table migration — because the primary key can't be changed and a new GSI may not have the data it needs in the right shape.

The written list is the design artefact. It should be in the repository, and it should be updated when a new pattern is added — because that's the moment to check whether the table still supports it.

The two conventions that make this work

1. Generic key names. PK and SK, not userId and orderDate — because they hold different things depending on the item type.

2. Type-prefixed values. USER#123 rather than 123, so the key space is unambiguous and begins_with can filter by type.

The # is conventional and any delimiter works, as long as it can't appear in an id.

Why METADATA as a sort key

An entity's own attributes need a sort key value, and it should sort before its children so a single query returns the parent first.

METADATA, #META, or just A — whatever sorts early. Some people use the entity type itself (ORDER#1041 / ORDER#1041) so the item is self-describing.

Practical benefit: querying PK = ORDER#1041 with Limit = 1 gets just the order header cheaply, and without the limit you get the header plus every line in one call.

Hierarchies in the sort key ⭐ Senior-level

PK              SK
--------------- --------------------------------------
STORE           COUNTRY#UK#REGION#SE#CITY#LONDON#S#001
STORE           COUNTRY#UK#REGION#SE#CITY#LONDON#S#002
STORE           COUNTRY#UK#REGION#NW#CITY#MANCH#S#010
STORE           COUNTRY#IE#REGION#L#CITY#DUBLIN#S#020

Queries, all with begins_with on SK:
  All UK stores          -> "COUNTRY#UK"
  All South East stores  -> "COUNTRY#UK#REGION#SE"
  All London stores      -> "COUNTRY#UK#REGION#SE#CITY#LONDON"
Senior signal — one key serves every level

A composite sort key encoding a hierarchy from broadest to narrowest gives you a query at every level of granularity with a single index. In a relational database that's several indexes or a recursive CTE.

The constraint is the same as any prefix: you can only query left to right. "All stores in cities called London, in any country" doesn't work — city isn't a prefix. That's the trade, and it's why the ordering of levels has to match how you'll query.

Being able to explain both the capability and the left-to-right constraint is what distinguishes understanding it from having read about it.

Adjacency lists for many-to-many 🔴 Advanced

PK                SK                Attributes
----------------- ----------------- --------------------
STUDENT#s1        STUDENT#s1        name, email          (the entity itself)
COURSE#c1         COURSE#c1         title, credits       (the entity itself)
STUDENT#s1        COURSE#c1         enrolledAt, grade    (the relationship)
STUDENT#s1        COURSE#c2         enrolledAt, grade
STUDENT#s2        COURSE#c1         enrolledAt, grade

Primary key:  PK = STUDENT#s1  -> that student's courses
GSI (SK, PK): PK = COURSE#c1   -> that course's students
How the inverted GSI works

The relationship item is stored once, with the student as PK and the course as SK.

A GSI with the keys swapped — SK as partition key, PK as sort key — lets you query the relationship from the other direction. Same item, both directions, one extra index.

That inverted GSI is a standard part of the single-table toolkit, and it usually serves several reverse lookups at once rather than just one.

Denormalize onto the relationship item

Querying a student's courses returns relationship items with course ids. Getting the course titles means a second BatchGetItem — the N+1 problem again.

So copy the fields the screen displays — courseTitle, credits — onto the relationship item. One query renders the page.

That's the extended reference pattern, and here it's not optional in the way it is in MongoDB, because there's no $lookup fallback at all. Keep the duplicated fields to ones that rarely change, and use Streams to update them when they do.

GSI overloading 🔴 Advanced

Items carry generic GSI keys whose meaning depends on the item type:

PK            SK          GSI1PK             GSI1SK
------------- ----------- ------------------ ------------------
USER#123      PROFILE     EMAIL#a@x.com      USER#123
ORDER#1041    METADATA    STATUS#pending     2024-06-01#1041
PRODUCT#KB-01 METADATA    CATEGORY#input     KB-01

One GSI on (GSI1PK, GSI1SK) serves:
  - look up a user by email
  - list pending orders by date
  - list products in a category
Senior signal — why overload rather than add indexes

Each GSI is a full maintained copy of the projected attributes, with its own capacity, and every base-table write propagates to every index. So five GSIs means five copies to write.

Overloading one GSI to serve several unrelated patterns keeps that cost down. It works because different item types simply put different things in GSI1PK, and each query knows which prefix it's looking for.

Combined with the sparse index property — items that don't set GSI1PK aren't in the index at all — one GSI can cover a surprising number of patterns.

The honest cost: readability. A table where GSI1PK means four different things is hard for a newcomer to reason about, and impossible to understand without the access-pattern document. That's a real maintenance burden and the main argument for restraint.

Write sharding for hot partitions 🔴 Advanced

Problem: PK = "COUNTER#global" takes all writes -> one partition, 1,000 WCU cap

Solution: add a deterministic or random suffix
  COUNTER#global#0 .. COUNTER#global#9      -> 10 partitions, 10,000 WCU

Reading the total: query all 10 and sum in the application.
Suffix strategyTrade-off
Random (0–N)Even spread; reads must query all N shards
Deterministic — hash(id) % NEven spread, and a single item is still directly addressable
Time-based — an hour bucketNatural for time-series; reads target a window
Prefer deterministic suffixes

A random suffix means you can no longer compute an item's key from its identity — so a point read becomes a query across all N shards, and you've traded a cheap read for a fan-out.

Deriving the suffix from a hash of the item's own id keeps single-item reads direct while still spreading writes. Same reasoning as Cosmos synthetic keys.

Random is only right when you genuinely never read a single item — a pure aggregate counter, where every read sums all shards anyway.

When single-table is the wrong choice ⭐ Senior-level

Use several tables whenWhy
Entities are genuinely unrelated No query ever needs them together, so co-locating buys nothing
Very different access volumes High-volume telemetry alongside low-volume config means one capacity setting serving two incompatible workloads
Different lifecycles One needs TTL expiry, another must be retained for seven years
Different backup or compliance needs Table-level, so mixing forces the strictest policy on everything
Separate services own the data A shared table is a shared database — the coupling microservices exist to avoid
The team is new to DynamoDB A bad single-table design is worse than a straightforward multi-table one
Senior signal — being willing to say no to it

Single-table design is treated as the correct DynamoDB answer, and it's a technique with a purpose: eliminating round trips for entities read together. If nothing is read together, it delivers complexity and no benefit.

The strongest argument against it is the one people don't make: it optimises for access patterns you know today and makes changing them harder. A table where four entity types share overloaded keys is difficult to evolve, and impossible to understand without the design document.

So my position: use it where entities are genuinely accessed together and the patterns are stable. Use separate tables where they aren't. And if the team is new to DynamoDB, a clear multi-table design that works beats a clever single-table design nobody can safely change.

Saying that is a stronger signal than demonstrating the pattern, because the pattern is well documented and the judgement isn't.

Adding an access pattern later 🔴 Advanced

SituationApproach
The data is there, keyed wrong Add a GSI. Online, backfilled automatically, no downtime
Need a new attribute in the key Backfill the attribute onto existing items, then add a GSI on it
The primary key itself is wrong New table plus migration. The expensive case
Adding a GSI is easier than people expect

A new GSI is created and backfilled online — the table stays available throughout. It consumes write capacity during the backfill, so on-demand mode or temporarily raised capacity avoids throttling live traffic.

So "we need a new access pattern" is often a GSI, not a migration. The genuinely expensive case is when the primary key is wrong, because that can't be changed — that's a new table, dual writes, a backfill, and a cutover.

Which is why step 3 of the design process deserves the most scrutiny: GSIs are recoverable, the primary key isn't.

Key takeaways
  • Write the access patterns down first. That list is the design artefact.
  • Generic key names with type-prefixed values.
  • A sort key prefix scheme gives you per-type and per-range queries from one key.
  • Hierarchies encode broadest-to-narrowest, queried left to right only.
  • Adjacency lists plus an inverted GSI handle many-to-many.
  • Denormalize display fields onto relationship items — there's no join fallback.
  • Overload one GSI across item types rather than adding many.
  • Deterministic shard suffixes keep point reads possible.
  • Separate tables when entities aren't read together, or have different volumes or lifecycles.
  • New GSIs are online and cheap; a wrong primary key means a table migration.

Common mistakes

  • Designing from an entity diagram instead of access patterns.
  • Not writing the access patterns down, so nobody can check a change against them.
  • Meaningful key names like userId in a multi-entity table.
  • No type prefixes, making the key space ambiguous.
  • Non-sortable sort keys — unpadded numbers, non-ISO dates.
  • A GSI per access pattern instead of overloading.
  • Random shard suffixes, destroying point reads.
  • Not denormalizing display fields, causing N+1 batch gets.
  • Single-table for unrelated entities, all cost and no benefit.
  • A shared table across services, recreating the shared-database problem.

Interview questions

Advanced / scenario

Design a DynamoDB table for an e-commerce system. 🔥 Must know
How I'd answer

"I'd start by asking for the access patterns, because in DynamoDB you can't design the table without them — the key structure is the query capability, and there's no planner to compensate. If I designed from an entity diagram I'd build something that can't answer the questions."

"Let me assume a reasonable set: get a user's profile; list a user's orders newest first; get an order with its line items; look up a user by email; list products in a category; find pending orders for fulfilment."

"Primary key: generic PK and SK, with type-prefixed values."

"A user's profile is PK = USER#123, SK = PROFILE. Their orders are PK = USER#123, SK = ORDER#2024-06-01#1041. So querying PK = USER#123 with begins_with(SK, "ORDER#") and ScanIndexForward = false gives their orders newest first — and because the date is in the sort key, I also get 'orders in June' for free with a longer prefix. Querying PK = USER#123 with no sort condition returns the profile and the orders in one call."

"Order detail is a separate partition: PK = ORDER#1041 with SK = METADATA for the header and SK = LINE#001 onwards for the items. One query returns the order and every line — which is the main thing single-table design buys you, since there's no join."

"That means the order is stored in two places — as a summary item under the user, and as a full record under its own partition. That's deliberate duplication, and it's correct here: the list view needs a few fields, the detail view needs everything, and both should be single queries."

"For the remaining patterns I'd use one overloaded GSI rather than three separate ones, because each GSI is a full maintained copy with its own capacity and every write propagates to all of them."

"So items carry generic GSI1PK/GSI1SK whose meaning depends on type. The user profile sets GSI1PK = EMAIL#a@x.com for email lookup. Products set GSI1PK = CATEGORY#input. That one index serves both."

"Pending orders I'd do as a sparse index, because that's the trap in this question. A GSI on status would be a hot partition — five distinct values means every pending order in one partition, capped at 1,000 WCU, and since a GSI shares the write path, throttling there throttles base-table writes. Instead I'd write a pendingSince attribute only while the order is pending and remove it when the status changes. Items without the attribute aren't in the index, so it contains just the working set and shrinks automatically as orders are fulfilled."

"For that index's partition key I'd use a date bucket rather than a constant, so it spreads across partitions while a fulfilment worker can still target recent days."

"Denormalization I'd be explicit about. The order summary under the user carries the total and status so the list renders from one query. Line items carry the product name and price as at purchase time — which isn't really denormalization, it's a historical snapshot: an invoice must show what was charged then, not today's price. Joining to the current product would be a genuine bug."

"Projections: INCLUDE with just the attributes each query needs, not ALL — ALL duplicates the whole table and doubles write cost."

"Two things I'd flag. Reporting and analytics don't belong here — no aggregation, no joins — so I'd stream to S3 or a warehouse via DynamoDB Streams for that. And I'd keep the access pattern list in the repository, so when someone adds a feature there's a defined place to check whether the table still supports it."

What they're really checking
  • Do you ask for access patterns before designing?
  • Do you use generic keys with type prefixes?
  • Do you get several entity types from one query?
  • Do you overload a GSI rather than adding several?
  • Do you catch the status hot-partition trap and use a sparse index?
  • Do you distinguish snapshot data from denormalization?
Weak answers
  • Red flag: a table per entity, with joins done in application code.
  • Red flag: a GSI on status.
  • Red flag: designing before asking what the queries are.
Likely follow-ups
  • How would you handle "all orders across all users last month"?
  • How do you keep the duplicated order summary in sync?
  • What if a new access pattern appears after launch?
Is single-table design always the right approach? ⭐ Senior-level
How I'd answer

"No, and I think it's over-applied — largely because it's the impressive-sounding answer."

"It's a technique with a specific purpose: eliminating round trips for entities that are read together. DynamoDB has no joins, so if a screen needs a user plus their orders plus their addresses, co-locating them under one partition key turns three queries into one. That's a real and significant win."

"But the benefit is entirely conditional on being read together. If the entities are never queried in the same request, putting them in one table delivers the complexity and none of the benefit."

"Where I'd use separate tables:"

"Genuinely unrelated entities. No query needs them together, so nothing is gained."

"Very different access volumes. High-volume telemetry alongside low-volume configuration means one capacity configuration serving two incompatible workloads, and a traffic spike in one throttles the other."

"Different lifecycles. TTL is table-level. If one entity type should expire after 30 days and another must be retained for seven years, that's awkward in one table. Same for backup and compliance settings."

"Separate services owning the data. A shared table is a shared database — exactly the coupling microservices exist to avoid. Two services with overloaded keys in one table can't deploy or evolve independently."

"And team familiarity. A poorly-executed single-table design is considerably worse than a straightforward multi-table one — scans everywhere because the keys don't fit, and nobody confident enough to change it. A clear design that works beats a clever one nobody can safely modify."

"The argument against it that I think is underweighted: it optimises for the access patterns you know today, and makes changing them harder. Overloaded keys mean the table's meaning lives in a design document rather than in the schema. Six months later, a new engineer looking at GSI1PK holding four different kinds of value has no way to understand it from the data alone. That's a real maintenance cost, and it's rarely mentioned alongside the performance benefit."

"So my position: single-table where entities are genuinely accessed together and the patterns are stable. Separate tables otherwise. And if the access patterns aren't settled yet, that's an argument against DynamoDB entirely rather than an argument about table count."

What they're really checking
  • Do you know what problem it actually solves?
  • Can you name concrete cases against it?
  • Do you raise the maintainability cost?
  • Do you connect it to service boundaries?
Weak answers
  • Red flag: "yes, it's the DynamoDB way."
  • Red flag: "no, it's too complex" with no analysis.
