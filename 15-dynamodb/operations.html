Capacity, Streams & Operations

Capacity is the cost lever, streams are how you build anything reactive, and hot partitions are the failure mode that survives good capacity planning.

🟡 Intermediate 🔴 Advanced ⭐ Senior-level
Quick revision
  • On-demand for unpredictable load, provisioned + auto scaling for steady. Provisioned is much cheaper at consistent volume.
  • 1 WCU = one 1 KB write. 1 RCU = one 4 KB strongly consistent read, or two eventually consistent.
  • Per-partition caps: 3,000 RCU / 1,000 WCU. The hot-partition ceiling.
  • Adaptive capacity helps automatically but doesn't fix a genuinely skewed key.
  • Transactions span partitions and tables — up to 100 items, at 2× cost.
  • TTL deletion is free and asynchronous, up to 48 hours late.
  • Streams give a 24-hour ordered change log per partition key.

Senior signal — auto scaling doesn't handle spikes

This is the trap. Provisioned auto scaling watches CloudWatch metrics and adjusts — which takes minutes. A traffic spike that arrives in seconds gets throttled while auto scaling catches up.

So auto scaling handles gradual changes — daily cycles, weekly patterns. It does not handle a marketing email going out, or a viral moment.

On-demand absorbs an instant doubling of the previous peak with no throttling. Beyond double, it also needs a moment to adapt — which is why AWS suggests pre-warming by ramping traffic if you know a large spike is coming.

The practical strategy: on-demand while you're learning the traffic shape, then switch to provisioned with reserved capacity once it's predictable. You can change mode once every 24 hours, so this is a reversible decision — unlike most things in DynamoDB.

Item size rounds up, and that matters

A 1.1 KB write costs 2 WCU. A 4.1 KB read costs 2 RCU. Rounding is per operation, so items sitting just over a boundary double their cost.

On a high-volume table, trimming items from 1.1 KB to just under 1 KB halves the write cost. That's a real optimisation and an unusually direct one — shorter attribute names genuinely help, because attribute names are stored with every item.

That's why DynamoDB tables often have terse attribute names. It looks like premature optimisation and it's measurable at scale.

Hot partitions 🔥 Must know

The limit that survives good capacity planning

Each physical partition is capped at 3,000 RCU and 1,000 WCU, regardless of what the table is provisioned for.

So a single partition key taking heavy traffic throttles at those numbers even if the table has 40,000 WCU available.

CauseExample
Low-cardinality partition keystatus, country, tenantType
One dominant valueA tenant that's 60% of your traffic
Time-based keyToday's date takes every write
A hot GSI keyThrottles the index, which throttles base-table writes
Adaptive capacity helps, and isn't a fix

DynamoDB automatically detects imbalance and does two things: it borrows unused capacity from other partitions to serve a hot one, and it can isolate a persistently hot key onto its own partition.

That handles moderate skew transparently, and it's why hot partitions are less catastrophic than they were years ago.

But the hard per-partition ceiling still applies. If a single partition key genuinely needs more than 3,000 RCU or 1,000 WCU, no amount of adaptive capacity helps — you cannot split a single key's traffic, because all items with that key live together by definition.

So the fix is always in the key design: write sharding, a higher-cardinality key, or caching in front.

Finding a hot partition

Enable CloudWatch Contributor Insights on the table. It reports the most frequently accessed and most throttled partition keys directly — which is far better than inferring it from aggregate metrics.

The signature to recognise: throttling while consumed capacity is well below provisioned. Same signature as Cosmos hot partitions, and the same wrong conclusion — raising capacity adds headroom to partitions that weren't busy.

Transactions 🟡 Intermediate

var request = new TransactWriteItemsRequest
{
    TransactItems = new List<TransactWriteItem>
    {
        // Debit - only if sufficient funds
        new() { Update = new Update
        {
            TableName = "accounts",
            Key = Key("ACCOUNT#from"),
            UpdateExpression    = "SET balance = balance - :amt",
            ConditionExpression = "balance >= :amt",
            ExpressionAttributeValues = amounts
        }},
        // Credit
        new() { Update = new Update
        {
            TableName = "accounts",
            Key = Key("ACCOUNT#to"),
            UpdateExpression = "SET balance = balance + :amt",
            ExpressionAttributeValues = amounts
        }},
        // Idempotency guard - fails if this transfer was already recorded
        new() { Put = new Put
        {
            TableName = "transfers",
            Item = transferRecord,
            ConditionExpression = "attribute_not_exists(PK)"
        }}
    },
    ClientRequestToken = idempotencyKey     // safe to retry for ~10 minutes
};
PropertyDetail
ScopeAcross partitions and tables — better than Cosmos
Limit100 items, 4 MB
Cost2× — it's a two-phase commit
ConditionsAny item can carry a condition; one failure aborts everything
Same item twiceNot allowed in one transaction

Senior signal — ClientRequestToken is the detail people miss

The ambiguous timeout problem: a client times out and doesn't know whether the transaction committed. Retrying might apply it twice.

ClientRequestToken makes the transaction idempotent at the service level — the same token within about ten minutes returns the original result rather than re-executing.

That's built-in idempotency for a multi-item write, which is genuinely useful and rarely mentioned. It's the same guarantee you'd otherwise build with an idempotency key table — here the service does it.

Note the window is limited, so it protects against retries, not against a duplicate submission an hour later. For that you still need your own record — which is why the example above also writes a transfer row with attribute_not_exists.

Prefer a conditional write to a transaction

Transactions cost 2× and are slower. A single-item conditional write is atomic on its own and costs 1×.

So "decrement stock if sufficient" needs no transaction — it's one UpdateItem with a ConditionExpression. Reach for a transaction only when several items must change together.

Same principle as everywhere: put the condition in the write before reaching for heavier machinery.

Two TTL traps

Expired items are still readable. Deletion is asynchronous, so an item past its TTL can be returned by a query for hours. If expiry is security-relevant — a session, a token — you must check the timestamp in code. TTL is a storage-cleanup mechanism, not an access control.

Epoch seconds, not milliseconds. Writing milliseconds gives a timestamp roughly fifty thousand years in the future, so nothing ever expires. There's no error and no warning — the table just grows. This is a genuinely common bug because .NET's ToUnixTimeMilliseconds() is right there next to the correct method.

Free deletion makes TTL the right answer for sessions, caches, event data and audit logs — millions of explicit deletes would consume real WCU and can throttle live traffic.

DynamoDB Streams 🔥 Must know

In simple terms

An ordered log of item-level changes, retained for 24 hours. Ordering is guaranteed per partition key, not globally.

Typically consumed by Lambda, which polls the stream and invokes your function in batches.

StreamViewTypeRecord contains
KEYS_ONLYJust the keys
NEW_IMAGEThe item after the change
OLD_IMAGEThe item before
NEW_AND_OLD_IMAGESBoth — needed to know what actually changed
What streams are for
  • Maintaining aggregates — counters and totals, since DynamoDB has no aggregation.
  • Keeping denormalized copies in sync when a duplicated field changes.
  • Publishing domain events — a built-in outbox, no dual write.
  • Feeding a search index or a data warehouse.
  • Cross-region replication — how global tables work internally.
  • Audit trails, using OLD_IMAGE and NEW_IMAGE.
Senior signal — streams are how you get aggregation at all

DynamoDB has no COUNT, no SUM, no GROUP BY. So "how many orders does this customer have?" has no query answer.

The pattern is to maintain the aggregate on write: a stream handler increments a counter item when an order is created. The read becomes a single item get.

Doing it via the stream rather than in application code matters, because the stream sees every write — including from other services, scripts and migrations. Incrementing in the application means any code path that forgets silently corrupts the count.

"DynamoDB can't aggregate, so I'd maintain counters via Streams" is the answer that shows you've actually built on it.

Stream handlers must be idempotent, and the counter case isn't

Lambda retries a failed batch, so at-least-once delivery. A handler that does ADD orderCount 1 will over-count on redelivery.

Two fixes. Record processed sequence numbers and skip duplicates — reliable, more machinery. Or make the operation idempotent by recomputing rather than incrementing where feasible.

Also: a failing batch blocks its shard. Lambda retries the same batch, so one poison record stops everything behind it for up to 24 hours. Configure a failure destination (an SQS dead-letter queue), MaximumRetryAttempts, and BisectBatchOnFunctionError so a single bad record doesn't take out the whole partition's processing. That's the operational detail people discover during an incident.

Streams vs Kinesis Data Streams

DynamoDB can also stream to Kinesis Data Streams, which gives longer retention (up to a year), multiple independent consumers, and the wider Kinesis ecosystem.

The trade: Kinesis does not guarantee ordering or exactly-once, where native Streams guarantee ordering per partition key. So native Streams for anything order-sensitive, Kinesis when you need long retention or fan-out to many consumers.

Global tables 🔴 Advanced

PropertyDetail
ModelMulti-region, multi-active — every region accepts writes
MechanismBuilt on Streams, replicating asynchronously
LagTypically under a second
ConflictsLast writer wins, by timestamp. No alternative
CostReplicated writes are charged in each region
Last writer wins is the only option

Unlike Cosmos, which offers custom merge procedures and a manual conflicts feed, DynamoDB global tables give you last writer wins and nothing else.

Two regions update the same item; the later timestamp wins and the other update is silently discarded. There's no hook, no conflict log, no merge.

So the design has to make conflicts impossible: route each item's writes to one region (region affinity by user or tenant), or model append-only so two regions insert distinct items rather than updating a shared one.

Conditional writes also behave differently than you'd expect — the condition is evaluated locally, so two regions can both satisfy the same condition simultaneously. That breaks the atomicity guarantee people rely on, and it's the detail that makes global tables genuinely harder than they look.

DAX and caching 💡 Good to know

DAXElastiCache / in-process
IntegrationDrop-in — a different client, same APIApplication code changes
InvalidationWrite-through plus TTLYour responsibility
LatencyMicrosecondsSub-millisecond
ConsistencyEventually consistent reads onlyWhatever you build
Best forRead-heavy with hot keys, minimal code changeFine-grained control, non-AWS portability
DAX's real use case is a hot partition you can't redesign

If one item is read enormously — a global config document, a leaderboard, a popular product — you'll hit the 3,000 RCU per-partition cap no matter how the table is keyed, because it's a single item.

DAX absorbs those reads, and it's a client swap rather than an application redesign. That's the situation where it's clearly the right tool.

The caveat: DAX serves eventually consistent reads, and a strongly consistent read bypasses the cache entirely. So code that requests strong consistency gets no benefit — worth checking before concluding DAX will help.

Backup and recovery 🟡 Intermediate

MechanismGives you
Point-in-time recoveryRestore to any second in the last 35 days. Enable this
On-demand backupA named snapshot, retained indefinitely
Export to S3For analytics — no capacity consumed
Deletion protectionPrevents accidental table deletion. Also enable this
Restore always creates a new table

You cannot restore over an existing table. A restore produces a new table, so recovery means restoring, verifying, then repointing the application — which is a deployment, not a database operation.

That's the RTO people underestimate: the restore itself can take a while on a large table, and then there's a cutover.

Also note the restored table has no indexes configured the same way by default — you specify them at restore time. Worth having the restore procedure written down and tested rather than improvised during an incident.

Export to S3 is how you do analytics

DynamoDB has no aggregation, and scanning for reporting consumes real capacity that competes with production traffic.

Export to S3 consumes no table capacity at all — it reads from the continuous backup, not the table. Then query it with Athena, or load it into a warehouse.

That's the structurally correct answer to "how do we report on DynamoDB data?", and it's much better than a scheduled scan. Same reasoning as Cosmos's analytical store.

Key takeaways
  • On-demand for unpredictable load; provisioned plus reserved capacity for steady. Switchable daily.
  • Auto scaling reacts in minutes — it does not handle sudden spikes.
  • Capacity units round up per operation, so item size trimming is a direct saving.
  • 3,000 RCU / 1,000 WCU per partition. Adaptive capacity softens skew, doesn't remove the ceiling.
  • Transactions span partitions and tables at 2× cost; prefer a conditional write for one item.
  • ClientRequestToken gives service-level transaction idempotency for ~10 minutes.
  • TTL is free, up to 48 hours late, epoch seconds, and expired items stay readable.
  • Streams: 24 hours, ordered per partition key, at-least-once, and a failing batch blocks its shard.
  • Streams are how you get aggregation, since DynamoDB has none.
  • Global tables are last-writer-wins only, and conditions evaluate locally.
  • DAX for a hot single item; it only serves eventually consistent reads.
  • Export to S3 for analytics — no capacity consumed.

Common mistakes

  • Relying on auto scaling for spikes, then getting throttled.
  • On-demand at steady high volume, paying several times more than necessary.
  • Ignoring item size rounding on high-volume tables.
  • Raising table capacity to fix a hot partition.
  • Transactions where a conditional write would do, at double the cost.
  • No ClientRequestToken, so a client retry re-applies a transaction.
  • TTL in milliseconds — nothing ever expires, silently.
  • Trusting TTL for security expiry instead of checking in code.
  • Non-idempotent stream handlers that over-count on retry.
  • No dead-letter destination on a stream consumer, so one bad record blocks a shard.
  • Global tables with concurrent same-item writes, silently losing updates.
  • Scanning for reports instead of exporting to S3.
  • PITR not enabled.

Advanced / scenario

You need a count of orders per customer, and DynamoDB has no aggregation. How? ⭐ Senior-level
How I'd answer

"DynamoDB has no COUNT, SUM or GROUP BY, so this has to be maintained on write rather than computed on read."

"The naive option is querying all of a customer's orders and counting them in the application. That works and it's linear in their order count — fine for ten orders, expensive for ten thousand, and the cost grows forever. Worth mentioning that Select = COUNT reduces the data transferred but still consumes the same read capacity, because DynamoDB reads the items to count them. So it's not an optimisation."

"My answer is a counter item maintained by DynamoDB Streams."

"A stream handler on the orders table increments an orderCount attribute on the customer item — or a dedicated counter item — when an order is created, and decrements on delete. Reading the count then becomes a single item get, ~0.5 RCU, constant regardless of order volume."

"Why via the stream rather than in the application code that creates the order: the stream sees every write, including from other services, admin scripts and migrations. If I increment in application code, any path that forgets silently corrupts the count — and you won't notice for months."

"The critical detail: Streams are at-least-once, so the handler is retried, and ADD orderCount 1 is not idempotent. A redelivered batch over-counts. Two ways to handle it. Record the processed sequence number on the counter item and skip duplicates with a conditional write. Or attach the increment to a marker: conditionally write a 'counted' flag on the order item itself, and only increment if that write succeeds — so the increment happens exactly once per order."

"Watch for a hot counter. If this is a global counter rather than per-customer, a single item takes every increment and caps at 1,000 WCU. Per-customer is naturally partitioned so that's fine, but for a global total I'd use write sharding — increment one of N shard items and sum them on read."

"Operational details I'd get right. A failing batch blocks its shard and Lambda retries it, so one poison record stops everything behind it for up to 24 hours. I'd configure a dead-letter destination, MaximumRetryAttempts, and BisectBatchOnFunctionError so a single bad record doesn't halt processing."

"And I'd add a reconciliation job. Derived counters drift — a missed event, a bug, a manual data fix. A periodic job that recomputes and corrects is not optional; without it you have a number nobody trusts, and 'the count is wrong' becomes unfixable because you don't know when it diverged."

"If the requirement were richer than a count — aggregations across customers, arbitrary date ranges — I'd stop trying to do it in DynamoDB and export to S3 and query with Athena. That consumes no table capacity, and DynamoDB is simply the wrong tool for analytical queries."

What they're really checking
  • Do you know there's no aggregation, and that COUNT still costs full reads?
  • Do you maintain the aggregate via Streams rather than application code, and know why?
  • Do you handle at-least-once making increments unsafe?
  • Do you consider a hot counter?
  • Do you add reconciliation?
  • Do you know when to leave DynamoDB for analytics?
Weak answers
  • Red flag: a scan or query-and-count on the request path.
  • Red flag: incrementing in application code with no stream.
  • Red flag: no awareness that retries over-count.
  • Red flag: no reconciliation.
Likely follow-ups
  • Write the conditional expression for the exactly-once increment.
  • How would the reconciliation job work?
  • What if you needed counts by status as well?
