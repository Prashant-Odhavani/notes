.NET Framework & Legacy Modernization

Most .NET jobs involve some legacy. This is what's different about it, and how to migrate without a two-year rewrite that never ships.

🟡 Intermediate ⭐ Senior-level 💡 Good to know
Quick revision
  • .NET Framework is Windows-only and no longer gets new features — 4.8 is the last version. It's supported, not evolving.
  • No built-in DI, no built-in configuration binding, no built-in logging. That's the biggest day-to-day difference.
  • IIS hosts it, not Kestrel. Application pools, recycling and web.config instead of a self-hosted process.
  • HttpContext.Current is a static ambient value — convenient, and the source of many async bugs.
  • WCF has no modern .NET equivalent. gRPC replaces most of it; that's usually the biggest migration blocker.
  • Migrate incrementally with the strangler pattern. A big-bang rewrite is the classic failure.

Why this page exists 🟢 Beginner

In simple terms

A very large amount of working, revenue-generating .NET code runs on .NET Framework.

Interviewers ask about it because they probably have some — and they want to know whether you can work in it and whether you have a realistic view of migrating it.

The two questions that actually come up:

  1. "What's the difference between .NET Framework and .NET?" — a knowledge check.
  2. "How would you migrate this application?" — a judgement check, and the more important one.

The one-line version

.NET Framework is Windows-only and feature-frozen. Modern .NET is cross-platform and actively developed.

Everything else — DI, configuration, logging, hosting — follows from modern .NET being a redesign rather than an update.

The naming history, briefly

.NET Framework 1.0–4.8 → .NET Core 1.0–3.1 → .NET 5 onwards.

"Core" was dropped at 5 to signal that it was now the .NET, and the version skipped 4 to avoid confusion with Framework 4.x. So ".NET 8" is the successor to .NET Core, not to .NET Framework 4.8 — they're different lineages that were merged.

Framework-specific runtime concepts 🟡 Intermediate

ConceptWhat it was forIn modern .NET
AppDomain An isolation boundary inside a process — load assemblies, unload them, sandbox code Gone. Use separate processes, or AssemblyLoadContext for collectible loading
GAC (Global Assembly Cache) Machine-wide shared assemblies, versioned and signed Gone. Dependencies are per-application via NuGet
Binding redirects web.config entries resolving version conflicts Gone. The SDK resolves a single version at build time
Machine-wide install One Framework version per machine, shared by all apps Side-by-side runtimes, or self-contained deployment
Why these disappeared

They all solved the same problem: many applications sharing one machine-wide runtime.

Modern .NET made deployment self-contained and side-by-side instead, so the problems those features solved no longer exist. GAC and binding redirects were symptoms of shared installation.

IIS and the ASP.NET pipeline 🟡 Intermediate

ConceptWhat it means
Application poolThe worker process (w3wp.exe) hosting your app. Isolation and resource limits live here
RecyclingIIS restarts the pool periodically, or on memory limits — which silently masked memory leaks for years
Idle timeoutThe pool shuts down after inactivity. First request afterwards is slow (cold start)
Global.asaxApplication and session lifecycle events — Application_Start, Session_Start
HttpModule / HttpHandlerThe pipeline extension points — the ancestors of middleware
web.configConfiguration and IIS settings in one XML file
Two Framework behaviours that surprise people coming from modern .NET
  • Pool recycling hides leaks. If IIS restarts the process every 29 hours, a slow memory leak never becomes visible. Move that app to a container with no recycling and the leak surfaces immediately — which is why "it was fine before we migrated" sometimes means "the leak was always there".
  • In-process session state is normal. Framework apps commonly use Session, which requires sticky sessions and breaks when you scale out. That's often the real blocker to horizontal scaling, and it has to be addressed during migration.

HttpContext.Current — the async trap 🔴 Advanced

public async Task<ActionResult> Index()
{
    var user = HttpContext.Current.User;          // fine

    await SomeServiceAsync();                      // continuation may resume elsewhere

    var again = HttpContext.Current.User;          // may be NULL
}
Why it breaks

HttpContext.Current is a static, ambient value flowed through the synchronisation context.

After an await, if the context isn't restored — or you used ConfigureAwait(false), or spawned a Task.Run — the ambient value is gone.

This is why ASP.NET Core removed it in favour of injecting IHttpContextAccessor. It's also why ConfigureAwait(false) is dangerous in Framework web code but harmless in ASP.NET Core — there's nothing ambient to lose.

The migration-friendly habit

Even in Framework code, capture what you need from the context at the start of the request and pass it explicitly. Don't reach for HttpContext.Current deep in a service.

That removes a class of async bug immediately, and it's exactly the refactoring migration would require anyway — so it's work you'd have to do regardless.

WCF — the real migration blocker ⭐ Senior-level

In simple terms

WCF was a framework for building services over many transports — HTTP, TCP, named pipes, MSMQ — with configurable security, transactions and reliable messaging.

There is no equivalent in modern .NET. Nothing covers that whole surface.

What you used WCF forModern replacement
Binary RPC between .NET servicesgRPC — contract-first, fast, streaming
SOAP endpoints for external consumersCoreWCF (community port), or expose REST alongside
HTTP servicesASP.NET Core Web API
MSMQ-based reliable messagingA real broker — Service Bus, RabbitMQ
Distributed transactions (MSDTC)No equivalent. Use sagas
netTcpBinding duplex callbacksgRPC bidirectional streaming, or SignalR
The two that have no answer

MSDTC distributed transactions. If the app relies on a two-phase commit across a database and a queue, there is no port. You have to redesign it around eventual consistency — which is a domain-modelling change, not a technical migration. That's often the thing that makes a WCF migration a multi-quarter project rather than a sprint.

WS-* security and complex SOAP interop. If an external partner requires it, CoreWCF is the option, but you're accepting a community-maintained dependency for something Microsoft doesn't ship.

How to actually migrate ⭐ Senior-level

Remember this

Never do a big-bang rewrite.

You get a long period with no delivery, ending in one enormous risky cutover — and you have to catch up with every change made to the legacy system while you were building.

A realistic sequence

  1. Inventory and assess. Run the .NET Upgrade Assistant / API portability analyser. Find what has no modern equivalent — WCF, MSMQ, System.Drawing on Linux, Windows-specific APIs, MSDTC. Those determine whether this is a three-month or two-year project.
  2. Fix the migration blockers in place, on Framework. Remove HttpContext.Current from services. Replace in-process session with a distributed store. Introduce a DI container. Move config out of web.config. All of this can ship incrementally, on the old platform, with no cutover risk.
  3. Extract shared logic to netstandard2.0 so both the old and new app can reference it. That's the one legitimate remaining use for .NET Standard.
  4. Put a reverse proxy in front. YARP or nginx. Everything still routes to the legacy app — nothing has changed functionally, and that's the point.
  5. Move one route at a time. Build the endpoint in a new ASP.NET Core app, route just that path to it, verify, and keep going. Each step is independently shippable and revertible.
  6. Delete the legacy app when nothing routes to it.

That's the strangler fig pattern. Steps 2 and 3 are the ones teams skip, and they're the ones that make the rest low-risk.

The hard part nobody puts in the plan

Shared data. While both apps run, they need the same data. So you're either dual-writing, syncing, or letting the new app read the old database directly.

That decision determines whether the migration takes six months or three years — far more than the code does. Address it explicitly in the plan rather than discovering it in month four.

Authentication is the second one: sessions or auth cookies have to be valid across both apps during the transition, which usually means moving to a shared token-based scheme before you start routing traffic.

Senior signal

Being willing to say "don't migrate this one".

.NET Framework 4.8 is a supported component of Windows and receives security updates. A stable app nobody is changing has no urgent technical reason to move. Migrating it consumes months of capacity for no user-visible benefit.

Interviewers notice the difference between "modernise everything" and "here's how I'd decide which applications justify it".

Key takeaways
  • .NET Framework: Windows-only, feature-frozen at 4.8, still supported.
  • No built-in DI, config binding or logging — that's the biggest daily difference.
  • AppDomains, GAC and binding redirects existed because the runtime was machine-wide. Self-contained deployment removed the need.
  • IIS pool recycling masks memory leaks; in-process session blocks scale-out.
  • HttpContext.Current is ambient and breaks across await. Capture early, pass explicitly.
  • WCF has no full replacement. gRPC covers RPC; MSDTC and WS-* are the real blockers.
  • Migrate with a strangler: fix blockers in place first, then route path by path.
  • Shared data and shared auth decide the timeline, not the code.
  • Sometimes the right answer is not to migrate.

Common mistakes

  • Big-bang rewrite — no delivery for a year, one risky cutover, and a moving target.
  • Not auditing for blockers first, then discovering WCF or MSDTC in month three.
  • Ignoring the shared-data problem until both apps are live.
  • Migrating the code but keeping in-process session, so you still can't scale out.
  • Assuming pool recycling was hiding nothing — leaks appear after migration.
  • ConfigureAwait(false) in Framework web code, losing HttpContext.Current.
  • Targeting netstandard2.0 for new projects that have no Framework consumers.
  • Migrating an app that's being retired anyway.

Interview questions

What's the difference between .NET Framework and .NET? 🔥 Must know
How I'd answer

"The headline is that .NET Framework is Windows-only and feature-frozen — 4.8 is the last version, getting security updates but no new features. Modern .NET is cross-platform and on an annual release cadence."

"But the differences that matter day to day are architectural, because modern .NET was a redesign rather than an update."

"Framework has no built-in dependency injection, so every project picks Autofac or Unity or Ninject and they're all wired differently. No built-in configuration binding — it's web.config XML and ConfigurationManager.AppSettings. No built-in logging abstraction. Modern .NET has all three in the box, which is why codebases look far more consistent."

"Hosting is different too. Framework runs in IIS with System.Web, so you get application pools, recycling and HttpContext.Current. Modern .NET is a self-hosted process with Kestrel, which is what makes containers straightforward."

"Deployment is the other big one. Framework is installed machine-wide, one version, shared by every app — which is why the GAC and binding redirects existed. Modern .NET is side-by-side or entirely self-contained, so those problems just disappeared."

"And performance is a genuine difference, not a marketing claim — newer JIT, better GC, and a lot of allocation removed from the BCL."

"One naming point that trips people up: .NET 5 followed .NET Core 3.1, skipping 4 to avoid confusion with Framework 4.x. So .NET 8 is the successor to .NET Core, not to Framework 4.8 — two lineages that got merged."

What they're really checking
  • Do you know the practical differences, or just "one is cross-platform"?
  • Do you know why the GAC and binding redirects existed?
  • Do you know the naming history?
Likely follow-ups
  • What happened to AppDomains?
  • What's .NET Standard for now?
  • Why is ConfigureAwait(false) more dangerous in Framework?
You've inherited a large .NET Framework application. How would you approach modernising it? ⭐ Senior-level
How I'd answer

"My first question would be whether to migrate at all, and I'd want a business reason before committing capacity. Framework 4.8 is still supported and getting security updates. If the app is stable, rarely changed, and Windows hosting isn't a problem, migrating consumes months for no user-visible benefit."

"Good reasons to do it: we need Linux or containers for cost, performance genuinely matters, it's under active development and the missing features are slowing us down, or we need libraries that have dropped Framework support."

"Assuming there's a reason, I'd start with an assessment — the Upgrade Assistant and portability analyser — specifically hunting for things with no modern equivalent. WCF, MSMQ, MSDTC distributed transactions, Windows-specific APIs. Those determine whether this is three months or two years, and I'd want that answer before promising a timeline."

"Then, and this is the part teams skip: fix the blockers in place, on Framework. Remove HttpContext.Current from service layers and pass context explicitly. Replace in-process session with a distributed store. Introduce a DI container. Move configuration out of web.config. Every one of those ships incrementally on the old platform with no cutover risk — and they're all work the migration would require anyway."

"Then extract the shared domain logic into a netstandard2.0 library so both apps can reference it. That's the one remaining legitimate use for .NET Standard."

"Then a strangler: reverse proxy in front, everything still routing to legacy, and move one route at a time to a new ASP.NET Core app. Each step is shippable and revertible, and we're delivering value throughout rather than going dark for a year."

"The two things I'd put in the plan explicitly because they're what actually determine the timeline: shared data — while both apps run they need the same data, so we're dual-writing or the new app reads the old database — and shared authentication, because sessions or auth cookies have to be valid across both. I'd sort auth out before routing any traffic."

"What I'd refuse to do is a big-bang rewrite. You get a long period with no delivery, one enormous cutover, and you spend the whole time chasing changes being made to the system you're replacing."

What they're really checking
  • Do you question whether migration is justified?
  • Do you assess blockers before committing?
  • Do you know you can do preparatory work on Framework?
  • Do you raise shared data and auth — the things that actually blow up timelines?
Weak answers
  • Red flag: "rewrite it in .NET 9" with no assessment.
  • Red flag: no mention of how the two systems coexist.
  • Red flag: assuming migration is always the right call.
Likely follow-ups
  • What would you do about a WCF service with duplex callbacks?
  • How do you handle the shared database during transition?
  • How would you convince the business to fund this?
