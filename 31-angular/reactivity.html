How change detection works 🔥 Must know

In simple terms

Angular doesn't know when your data changes. So instead it re-checks bindings after anything happens that might have changed something, and updates the DOM where a bound value differs.

Zone.js is how it knows something happened. It patches the browser's async APIs — setTimeout, addEventListener, fetch, promises — so Angular is notified when any of them completes.

Think of it this way

A proofreader who can't be told which page changed. Every time anyone touches the manuscript, they re-read the entire document looking for differences.

Correct, and expensive. OnPush is telling them "only re-read chapters whose cover sheet has been stamped".

StepWhat happens
1. An async event firesClick, HTTP response, timer, keystroke — anything Zone.js patched
2. Zone notifies AngularThe microtask queue drains, then Angular is told the zone is stable
3. Change detection runsWalks the component tree from the root, top to bottom
4. Bindings are comparedEach binding's current value against its previous value
5. DOM is updatedOnly where a value actually differs
The connection to the event loop

Change detection runs when the microtask queue has drained — so it's scheduled off the back of the event loop mechanics, not on a timer.

That's why an await inside a component triggers a cycle when it resumes: the continuation is a microtask, Zone.js sees it complete, and Angular checks.

It's also why work outside Angular's zone — via runOutsideAngular — doesn't trigger change detection at all. Useful for high-frequency things like mouse-move handlers or animation frames that shouldn't cause a full check on every event.

OnPush — what actually triggers it

@Component({
  selector: 'app-order-row',
  changeDetection: ChangeDetectionStrategy.OnPush,   // opt in
  template: `{{ order.reference }} - {{ order.total | currency }}`
})
export class OrderRowComponent {
  @Input() order!: Order;
}
An OnPush component re-checks when
An @Input() changes by reference — a new object, not a mutated one
An event handler fires inside the component or its template
An observable bound with the async pipe emits
A signal read in its template changes
You call markForCheck() explicitly
The mutation trap — why OnPush "doesn't work"
// Parent component
addItem(item: Item) {
  this.items.push(item);        // SAME array reference
}
// An OnPush child bound to [items]="items" sees no change.
// The reference is identical, so Angular skips it entirely.
addItem(item: Item) {
  this.items = [...this.items, item];    // NEW array reference
}

OnPush compares inputs by reference, so mutating an object or array in place is invisible to it. The data is correct, the view is stale, and nothing errors.

This is the single most common OnPush complaint, and it's not a bug — it's the contract. OnPush requires that you treat inputs as immutable.

Which is a good discipline anyway: immutable updates make change tracking predictable and are the same reasoning behind React's state rules. If a codebase mutates state freely, adopting OnPush means fixing that first.

Never call methods from templates 🔥 Must know

<div *ngFor="let item of getFilteredItems()">{{ item.name }}</div>
<span>{{ calculateTotal() }}</span>
<span>{{ formatDate(item.created) }}</span>
export class OrderListComponent {
  readonly items  = signal<Item[]>([]);
  readonly filter = signal('');

  // Recomputes ONLY when items() or filter() actually change
  readonly filteredItems = computed(() =>
    this.items().filter(i => i.name.includes(this.filter())));

  readonly total = computed(() =>
    this.filteredItems().reduce((sum, i) => sum + i.price, 0));
}
@for (item of filteredItems(); track item.id) {
  <div>{{ item.name }}</div>
}
<span>{{ total() }}</span>
Remember this

Angular cannot know whether a method's return value changed, so it must call it every cycle.

A computed signal is memoised — it tracks its dependencies and only recalculates when one of them actually changes. Reading it afterwards is just returning a cached value.

Before signals, the equivalents were a precomputed field updated when data changed, or a pure pipe (which Angular caches by argument). Both still work; computed signals are clearer.

Signals 🔥 Must know

// writable state
const count = signal(0);
count.set(5);
count.update(n => n + 1);
console.log(count());              // read by calling it

// derived state - memoised, recomputes lazily
const doubled = computed(() => count() * 2);

// side effects - runs when dependencies change
effect(() => {
  console.log('count is now', count());   // dependencies tracked automatically
});

The dividing line

Signals for state. Observables for events and async.

"What is the current filter value?" — a signal. It always has a value and you read it synchronously.

"Every keystroke, debounced, cancelling the previous request" — an observable. That's a stream with timing.

They interoperate: toSignal() converts an observable to a signal, toObservable() goes the other way. So you don't have to pick one for the whole application.

export class OrderSearchComponent {
  private readonly http = inject(HttpClient);

  readonly query = signal('');

  // Signal -> observable -> HTTP stream -> back to a signal.
  // toSignal handles subscription AND cleanup automatically.
  readonly results = toSignal(
    toObservable(this.query).pipe(
      debounceTime(300),
      distinctUntilChanged(),
      switchMap(q => q ? this.http.get<Order[]>(`/api/orders?q=${q}`) : of([]))
    ),
    { initialValue: [] }
  );
}
Why this pattern is the modern default

The debouncing and request cancellation genuinely need RxJS — signals have no equivalent to switchMap, and shouldn't.

But the result is state, so exposing it as a signal means the template reads results() with no async pipe, no subscription, and no cleanup code. toSignal unsubscribes when the component is destroyed.

That combination — RxJS for the async pipeline, signals at the boundary — removes the most common source of Angular memory leaks while keeping the operators where they're needed.

effect() is not for deriving values

A common misuse is using effect() to compute one signal from another by calling set() inside it. That works, and it's wrong — it creates a second source of truth that can drift, and Angular actively discourages writing to signals in effects.

computed() is for deriving. effect() is for side effects — logging, analytics, syncing to localStorage, imperatively calling a non-Angular library.

If you find yourself setting a signal inside an effect, the answer is almost always a computed. This is the same distinction as React's "don't use an effect to compute derived state".

Senior signal — the four flattening operators

This is the RxJS question most likely to come up, because choosing wrong causes real bugs rather than just inefficiency.

switchMap — cancels the previous inner observable. For a type-ahead search that's exactly right: you don't want the response for "ab" arriving after the response for "abc" and overwriting it. That's a genuine race condition, not a performance concern.

mergeMap — everything runs concurrently, results arrive in completion order. Fine for independent operations; wrong for search, because out-of-order responses corrupt state.

concatMap — strictly sequential and ordered. Use when order matters, like a queue of writes that must apply in sequence.

exhaustMap — ignores new emissions while one is in flight. The correct answer for a submit button: rapid clicks produce one request, not five. Most people reach for a disabled flag instead; exhaustMap is the declarative version.

Being able to name which bug each one prevents is what distinguishes real usage from memorising a list.

Subscription cleanup 🔥 Must know

export class DashboardComponent implements OnInit {
  ngOnInit() {
    this.service.updates$.subscribe(data => this.data = data);
    // Never unsubscribed. The subject holds a reference to this component
    // forever - so the component, its DOM and its captured scope all leak.
    // And the callback keeps running after the component is destroyed.
  }
}
// Component
readonly data$ = this.service.updates$;

// Template - Angular subscribes AND unsubscribes for you
// {{ data$ | async }}   or   @if (data$ | async; as data) { ... }
export class DashboardComponent {
  private readonly service = inject(DataService);

  constructor() {
    this.service.updates$
      .pipe(takeUntilDestroyed())      // Angular 16+; ties to the injection context
      .subscribe(data => this.handle(data));
  }
}

Which observables genuinely need cleanup

HttpClient observables complete after one emission, so they self-unsubscribe. Not subscribing to those is a leak in principle and harmless in practice.

The ones that leak are those that never complete: subjects, interval, fromEvent, router events, form valueChanges, and anything from a long-lived service. Those hold a reference to your callback — and therefore your component — indefinitely.

valueChanges is the one people miss most, because it looks local to the component.

The safe habit: treat every subscription as needing cleanup rather than reasoning about which ones don't. Same discipline as disposing every IDisposable.

Zoneless Angular 🔴 Advanced

What changes

Zone.js patches every async API to detect that something happened, then Angular checks the tree to find out what.

With signals, Angular is told precisely what changed — so the patching becomes unnecessary. Zoneless mode removes Zone.js entirely and relies on signals and explicit notification.

BenefitDetail
Smaller bundleZone.js is roughly 35KB
Less work per eventNo tree walk to find what changed
Cleaner stack tracesZone.js wraps async calls and obscures them
Better interopThird-party async code no longer triggers spurious cycles
What zoneless requires of your code

Any state the template depends on must be a signal, or you must call markForCheck(). Mutating a plain field and expecting the view to update no longer works — nothing is watching.

So a codebase built on plain properties and default change detection can't simply switch it on. The migration is: adopt OnPush broadly, move template-bound state to signals, then go zoneless.

Stable from v20, and the direction Angular is clearly heading. For an interview, knowing it exists and what it demands is enough unless the role is Angular-focused.

Key takeaways
  • Zone.js patches async APIs so Angular knows to check; change detection walks from the root.
  • OnPush checks on reference-changed inputs, internal events, async pipe emissions and signal changes.
  • Mutating an input in place is invisible to OnPush — treat inputs as immutable.
  • Never call a method from a template binding; use a computed signal.
  • Signals for state, observables for streams; toSignal/toObservable bridge them.
  • computed() derives, effect() is for side effects only.
  • switchMap for search, exhaustMap for submits, concatMap for ordered writes.
  • Async pipe or toSignal first; takeUntilDestroyed when imperative.
  • Observables that never complete are the ones that leak — valueChanges especially.
  • Zoneless requires signals or explicit markForCheck.

Common mistakes

  • Method calls in template bindings.
  • Mutating arrays or objects passed to OnPush children.
  • Subscribing without cleanup.
  • mergeMap for a search, letting stale responses overwrite fresh ones.
  • Nested subscriptions instead of a flattening operator.
  • Using effect() to derive state rather than computed().
  • Manual subscription where the async pipe would do.
  • Missing trackBy / track, recreating every DOM node.
  • Calling detectChanges() to force updates instead of fixing the cause.
  • High-frequency handlers inside the zone — mouse move, scroll, animation frames.

Interview questions

Intermediate

Explain change detection and OnPush. 🔥 Must know
How I'd answer

"Angular has no way to know when your data changes — there's no proxy or setter interception on plain properties. So instead it re-checks bindings after anything happens that might have changed something."

"Zone.js is how it knows something happened. It monkey-patches the browser's async APIs — setTimeout, addEventListener, promises, XHR — so when any of them completes, Angular is notified and runs change detection."

"With the default strategy, that check walks the entire component tree from the root, comparing every binding's current value to its previous value, and updates the DOM where they differ. So on a large application, every click and every HTTP response checks everything."

"OnPush narrows that. An OnPush component is only checked when one of four things happens: an @Input() changes by reference, an event handler fires inside the component or its template, an observable bound with the async pipe emits, or a signal read in its template changes. Otherwise Angular skips the component and its subtree entirely."

"The critical consequence — and the reason people say OnPush is broken — is reference comparison. If a parent does this.items.push(newItem), the array reference hasn't changed, so an OnPush child bound to it sees nothing. The data is right, the view is stale, and there's no error."

"That's not a bug, it's the contract: OnPush requires you to treat inputs as immutable and replace rather than mutate — this.items = [...this.items, newItem]. Which is good discipline regardless, and it's the same reasoning as React's state rules."

"So adopting OnPush in an existing codebase means auditing for in-place mutation first. Turning it on without that produces stale views in hard-to-predict places."

"Worth adding where this is heading: signals make the whole model unnecessary. A signal tells Angular exactly what changed, so it can update precisely what depends on it rather than checking a tree. That's what enables zoneless change detection — Zone.js exists only to detect that something happened, and with signals that's no longer needed."

What they're really checking
  • Do you know Zone.js is the detection mechanism?
  • Can you list what triggers an OnPush check?
  • Do you know the mutation trap and why it's a contract, not a bug?
  • Do you know where signals fit?
Weak answers
  • Red flag: "OnPush makes it faster" with no mechanism.
  • Red flag: not knowing mutation breaks it.
Likely follow-ups
  • How would you force an update under OnPush?
  • What's markForCheck vs detectChanges?

switchMap, mergeMap, concatMap, exhaustMap — when do you use each? 🔥 Must know
How I'd answer

"All four flatten an observable of observables. They differ in what they do with a new emission while a previous inner observable is still running — and I'd frame each by the bug it prevents, because that's what makes the choice obvious."

"switchMap cancels the previous one. That's what you want for a type-ahead search. If the user types 'a', 'ab', 'abc', you fire three requests, and without cancellation the response for 'a' can arrive after the response for 'abc' and overwrite the results with stale data. That's a genuine race condition, not just wasted bandwidth. switchMap cancels the in-flight request so only the latest can land. Same reasoning for route parameter changes."

"mergeMap runs everything concurrently and results arrive in whatever order they complete. Right for independent operations — uploading several files, firing off analytics events. Wrong for search, for exactly the ordering reason above."

"concatMap queues them strictly in order, waiting for each to complete before starting the next. Use it when order matters — a sequence of writes that must apply in sequence, or operations where the second depends on the first having landed. Slower by design."

"exhaustMap ignores new emissions while one is in flight. This is the right answer for a submit button: if the user clicks five times rapidly, you want one request, not five. Most people solve that with a disabled flag and a boolean — exhaustMap is the declarative version and it can't get out of sync."

"The way I keep them straight: switch cancels, merge parallelises, concat queues, exhaust ignores."

"And the related mistake worth mentioning: nested subscriptions. Subscribing inside a subscribe callback is what these operators exist to replace. Nesting means you can't cancel the inner one, error handling doesn't compose, and cleanup becomes manual — so it reintroduces every problem the operators solve."

"If I'm unsure in a review, the question I ask is: what should happen if this fires again before the last one finished? The answer names the operator."

What they're really checking
  • Do you know switchMap prevents a race, not just waste?
  • Do you know exhaustMap for double-submit?
  • Do you recognise nested subscribes as the anti-pattern?
Likely follow-ups
  • What happens to the cancelled HTTP request?
  • How would you retry a failed request?
  • Where does shareReplay fit?

Advanced

Signals or RxJS — how do you decide? ⭐ Senior-level
How I'd answer

"They solve different problems, so mostly it isn't a choice — signals for state, observables for streams and async."

"A signal is a value that changes. It always has a current value, you read it synchronously by calling it, dependencies are tracked automatically, and there's no cleanup. 'What's the current filter?' or 'is the panel open?' — signal."

"An observable is a stream of events over time. It may not have emitted yet, it needs subscription and cleanup, and it has a large operator library for timing and coordination. 'Every keystroke, debounced 300ms, cancelling the previous request' — that's inherently a stream and signals have no equivalent to debounceTime or switchMap, deliberately."

"So in practice they compose, and the pattern I'd reach for is RxJS for the async pipeline, signals at the boundary. Take a query signal, convert with toObservable, debounce and switchMap the HTTP call, then toSignal the result back."

"The payoff is concrete: the template reads results() with no async pipe and no subscription, and toSignal handles unsubscription on destroy. That eliminates the most common source of Angular memory leaks while keeping the operators where they're genuinely needed."

"Where signals are a clear improvement: component state and derived values. A computed is memoised, so the template-method performance problem disappears — and it reads synchronously, so no | async and no BehaviorSubject plumbing for what is really just a value."

"Where I'd stay with RxJS: anything with timing, cancellation, retries, or coordination between streams. And the HttpClient returns observables, so the data layer is naturally RxJS whatever you do at the component boundary."

"One misuse worth calling out: using effect() to derive one signal from another by calling set() inside it. That creates a second source of truth that can drift, and Angular discourages writing to signals in effects. computed() derives; effect() is for genuine side effects — logging, localStorage, calling into a non-Angular library. Same distinction as React's 'don't use an effect to compute derived state'."

"On migration: I wouldn't rewrite working RxJS code. I'd use signals for new component state and for places where a BehaviorSubject was only ever standing in for a value, and leave established streams alone. The two interoperate specifically so this can be incremental."
