Forms, Routing & HTTP

The three subsystems you use on every screen. Interceptors and guards will feel like middleware and filters, because that's what they are.

🟡 Intermediate 🔴 Advanced 🔥 Must know
Quick revision
  • Reactive forms for anything real. Template-driven only for trivial cases.
  • A validator is a function returning errors or null.
  • Async validators need debouncing, or you'll hit the API on every keystroke.
  • Guards are functions now, not classes.
  • Interceptors are middleware — auth headers, retries, error mapping.
  • Lazy load routes with loadComponent — the biggest bundle win.
  • Client validation is UX; the server enforces the rules.

export class OrderFormComponent {
  private readonly fb = inject(NonNullableFormBuilder);

  readonly form = this.fb.group({
    reference: this.fb.control('', [Validators.required, Validators.maxLength(20)]),
    email:     this.fb.control('', [Validators.required, Validators.email]),
    quantity:  this.fb.control(1,  [Validators.required, Validators.min(1)]),
    lines:     this.fb.array<FormGroup>([])
  });

  // form.value is fully typed - no `any`
  submit() {
    if (this.form.invalid) {
      this.form.markAllAsTouched();   // reveal errors the user hasn't visited
      return;
    }
    this.service.save(this.form.getRawValue());
  }
}
NonNullableFormBuilder saves a lot of noise

By default a FormControl is nullable, because reset() sets it to null. So form.value.email is string | null | undefined and every usage needs narrowing.

NonNullableFormBuilder makes reset() restore the initial value instead of null, so the types are simply string. Considerably less friction, and it's what you almost always want.

Also worth knowing: form.value omits disabled controls, which silently drops fields from your payload. getRawValue() includes them. That's a real bug source when a field is conditionally disabled.

Custom and async validators

// Returns null when valid, an error object when not
export function futureDate(control: AbstractControl): ValidationErrors | null {
  if (!control.value) return null;                 // let `required` handle empty
  return new Date(control.value) > new Date()
    ? null
    : { futureDate: { actual: control.value } };
}

// Cross-field validation goes on the GROUP, not a control
export function datesInOrder(group: AbstractControl): ValidationErrors | null {
  const from = group.get('from')?.value;
  const to   = group.get('to')?.value;
  return !from || !to || from <= to ? null : { datesOutOfOrder: true };
}
export function uniqueReference(api: OrderApi): AsyncValidatorFn {
  return (control: AbstractControl): Observable<ValidationErrors | null> =>
    timer(400).pipe(                    // debounce - do NOT hit the API per keystroke
      switchMap(() => api.referenceExists(control.value)),
      map(exists => (exists ? { referenceTaken: true } : null)),
      catchError(() => of(null))        // don't block submission on a failed check
    );
}
Three async validator mistakes

1. No debounce. Async validators run on every value change, so without the timer you issue a request per keystroke. switchMap cancels the previous one, which limits the damage but still floods the server.

2. No error handling. If the check fails — network error, API down — an unhandled error leaves the control in a pending state forever, so the form can never be submitted. Returning null on error fails open, which is correct here because the server validates anyway.

3. Forgetting the pending state. While an async validator runs the control is neither valid nor invalid. A submit button bound only to form.invalid is enabled during that window, so a fast user can submit before validation completes. Bind to form.invalid || form.pending.

Routing 🔥 Must know

export const routes: Routes = [
  { path: '', component: HomeComponent },

  {
    path: 'orders',
    // Lazy: this chunk isn't downloaded until the route is visited
    loadComponent: () => import('./orders/order-list.component')
      .then(m => m.OrderListComponent),
    canActivate: [authGuard]
  },
  {
    path: 'orders/:id',
    loadComponent: () => import('./orders/order-detail.component')
      .then(m => m.OrderDetailComponent),
    canActivate: [authGuard],
    resolve: { order: orderResolver }
  },
  {
    path: 'admin',
    // Lazy-load a whole route subtree
    loadChildren: () => import('./admin/admin.routes').then(m => m.adminRoutes),
    canMatch: [adminGuard]
  },
  { path: '**', component: NotFoundComponent }
];
export const authGuard: CanActivateFn = (route, state) => {
  const auth   = inject(AuthService);
  const router = inject(Router);

  if (auth.isAuthenticated()) return true;

  // Preserve where they were going, so we can return after login
  return router.createUrlTree(['/login'], {
    queryParams: { returnUrl: state.url }
  });
};
GuardRunsUse for
canActivateBefore activating a routeAuthentication, authorisation
canActivateChildBefore any child routeProtecting a whole section
canMatchBefore the route is even matchedPrevents downloading the lazy chunk at all
canDeactivateBefore leavingUnsaved-changes warnings
resolveBefore activation, to fetch dataLoading data before the view shows
Senior signal — canMatch versus canActivate

With canActivate on a lazy route, Angular downloads the chunk first, then runs the guard and rejects. So a non-admin user has still downloaded the entire admin bundle.

canMatch runs before matching, so a failed check means the chunk is never fetched. That's both a bundle-size and a mild information-disclosure improvement — the admin code isn't sitting in a regular user's browser.

It also lets you serve different components for the same path based on a condition, which is a clean way to handle feature flags or role-specific screens.

This is a genuinely useful distinction that most people don't know, and it's a good thing to raise unprompted.

A guard is not security

Route guards run in the browser. Anyone can bypass them — disable JavaScript, call the API directly, edit the bundle.

So a guard is a navigation and UX control: don't show the user a screen they can't use. The actual authorisation must be enforced server-side on every endpoint.

Same reasoning as client-side form validation — the client layer is convenience, the server layer is the control. Stating that unprompted is a good security signal.

Resolvers: useful, with a caveat

A resolver fetches data before the route activates, so the component renders with data already present — no loading spinner, no empty state.

The trade-off: navigation appears frozen while it runs. The old view stays on screen with no feedback until the data arrives, which feels worse than a fast transition with a skeleton if the call is slow.

So resolvers suit fast, essential data. For anything slow, navigate immediately and load in the component with a loading state — the perceived performance is better even though the total time is the same.

HttpClient and interceptors 🔥 Must know

export const authInterceptor: HttpInterceptorFn = (req, next) => {
  const token = inject(AuthService).token();
  if (!token) return next(req);

  // Requests are IMMUTABLE - clone to modify
  return next(req.clone({
    setHeaders: { Authorization: `Bearer ${token}` }
  }));
};

export const errorInterceptor: HttpInterceptorFn = (req, next) => {
  const router = inject(Router);

  return next(req).pipe(
    retry({ count: 2, delay: (_, n) => timer(1000 * 2 ** n) }),  // backoff
    catchError((err: HttpErrorResponse) => {
      if (err.status === 401) router.navigate(['/login']);
      if (err.status === 403) router.navigate(['/forbidden']);
      return throwError(() => err);
    })
  );
};

// Registration - order matters, they run in sequence
provideHttpClient(withInterceptors([authInterceptor, errorInterceptor]));
Don't retry non-idempotent requests

That retry above applies to every request including POST. Retrying a POST can create two orders — and because the first request may have succeeded before the response was lost, you can't tell from the client.

This is exactly the ambiguous timeout problem. Safe retry needs either idempotent methods only, or an idempotency key.

So the interceptor should check: retry GET freely; retry POST or PATCH only if the server supports an idempotency key and you're sending one. A blanket retry in an interceptor is a duplicate-submission bug waiting to happen, and it's a common one because the interceptor looks like infrastructure code.

Interceptors are middleware — the mental model transfers

They form a chain: each one can inspect the request, modify a clone, pass it on, and then operate on the response coming back. Order matters.

That's exactly ASP.NET Core middleware, on the client side. The next(req) call is await _next(context).

One important detail: HttpRequest is immutable. You must clone() to change anything. Mutating and passing the same object doesn't work — a mistake that produces silently missing headers.

The auth-header leak

An interceptor that adds Authorization to every request will attach your bearer token to third-party URLs too — a maps API, an analytics endpoint, a CDN.

That's a genuine credential leak to an external party, and it's easy to introduce because the interceptor is written once and applies globally.

Guard it with a check on the request URL: only attach the token to your own API origin. Allow-list, don't block-list.

Lazy loading ⭐ Senior-level

The highest-leverage bundle optimisation

Without lazy loading, the initial bundle contains every screen in the application — including admin pages, reports and settings the user may never visit.

loadComponent or loadChildren splits each route into its own chunk, downloaded on first visit. The initial load only needs the first screen.

On a large application this is routinely the difference between a multi-megabyte initial bundle and a few hundred kilobytes.

TechniqueEffect
loadComponentOne component per chunk. Finest granularity
loadChildrenA route subtree per chunk
@defer (v17+)Defer part of a template — on viewport, interaction, idle or timer
Preloading strategyFetch likely-next chunks during idle time
 
<!-- The chart library isn't downloaded until the block scrolls into view -->
@defer (on viewport) {
  <app-sales-chart [data]="data()" />
} @placeholder {
  <div class="chart-skeleton"></div>
} @loading (minimum 200ms) {
  <app-spinner />
} @error {
  <p>Chart unavailable.</p>
}
@defer is more granular than route splitting

Route-level lazy loading is coarse — the whole screen or nothing. @defer works within a template, so a heavy charting library on an otherwise-light dashboard loads only when that section is actually reached.

The triggers are genuinely useful: on viewport, on interaction, on hover, on idle, on timer, or when a condition.

@placeholder shows before loading starts and @loading during — with minimum to prevent a spinner flashing for 50ms, which looks worse than no spinner. That's a thoughtful detail worth mentioning.

Key takeaways
  • Reactive forms for anything real; they're testable without the DOM.
  • NonNullableFormBuilder removes null noise; getRawValue() includes disabled controls.
  • Cross-field validation belongs on the group.
  • Async validators need debouncing, error handling, and a pending check on submit.
  • Guards are functions; canMatch avoids downloading a chunk the user can't use.
  • A guard is UX, not security — the server authorises.
  • Resolvers avoid spinners but freeze navigation; use for fast data only.
  • Interceptors are middleware, and requests are immutable — clone to modify.
  • Never blanket-retry POST; and never attach auth tokens to third-party URLs.
  • Lazy-load routes for the biggest bundle win; @defer for granular in-template splitting.

Common mistakes

  • Template-driven forms for complex requirements.
  • form.value silently dropping disabled fields.
  • Async validators with no debounce, hitting the API per keystroke.
  • No catchError in an async validator, leaving the form permanently pending.
  • Submit enabled during pending validation.
  • Cross-field validators on a control instead of the group.
  • canActivate on lazy routes where canMatch avoids the download.
  • Treating guards as authorisation.
  • Mutating an HttpRequest instead of cloning.
  • Blanket retry including POST.
  • Auth headers sent to third-party origins.
  • No lazy loading, shipping every screen in the initial bundle.

Interview questions

Intermediate

How would you implement an "is this username taken?" check on a form? 🔥 Must know
How I'd answer

"An async validator on the control, and there are three details that make the difference between it working and it being a problem."

"Debouncing. Async validators fire on every value change, so without a delay you're issuing an API request per keystroke. I'd start the pipeline with timer(400) so it only runs once the user pauses, and use switchMap so a newer check cancels the in-flight one — otherwise a response for a shorter prefix can arrive later and overwrite the result for what's actually in the box."

"Error handling. If the check fails — API down, network blip — an unhandled error leaves the control stuck in pending forever, so the form can never be submitted. I'd catchError and return null, which fails open. That's the right call because the server validates on submit anyway, so the worst case is the user gets the error a bit later rather than being permanently blocked."

"The pending state. While the validator runs, the control is neither valid nor invalid. So a submit button bound only to form.invalid is enabled during that window and a fast user can submit before the check completes. It needs to be form.invalid || form.pending."

"For the UX I'd also show a spinner on the field while pending, so the user understands why the button is briefly disabled rather than thinking it's broken."

"Then the point I'd make regardless of implementation: this is a convenience, not a guarantee. Even with a perfect check there's a race — two users can both check 'available' and both submit. So the server needs a unique constraint on the column and must handle the violation, returning a field-level error the form can display."

"That's the same reasoning as everywhere else in the handbook: the client check improves the experience, the database constraint is what actually enforces uniqueness. A check-then-insert in application code has a race window; a unique constraint doesn't."

"One implementation note: I'd inject the API service via a factory function returning the AsyncValidatorFn, rather than reaching for a service inside the validator — that keeps it testable, since I can pass a stub."

What they're really checking
  • Do you debounce and cancel?
  • Do you know an unhandled error leaves the form pending forever?
  • Do you handle the pending state on submit?
  • Do you know the client check can't guarantee uniqueness?
Weak answers
  • Red flag: a request per keystroke.
  • Red flag: no server-side constraint mentioned.
Likely follow-ups
  • How does the server report the conflict?
  • How would you test this validator?
  • What if the check needs to exclude the current user's own value on edit?

Advanced

Your Angular bundle is 4MB. How do you reduce it? ⭐ Senior-level
How I'd answer

"I'd measure before changing anything — ng build --stats-json and then source-map-explorer or webpack-bundle-analyzer. That shows what's actually large, and it's frequently not what people assume."

"Then, in the order I'd expect the biggest wins:"

"Lazy loading routes. Usually the largest single improvement. Without it the initial bundle contains every screen — admin, reports, settings — even for a user who only visits the dashboard. loadComponent per route splits each into its own chunk. On a large app this alone can take a multi-megabyte bundle down to a few hundred kilobytes."

"And I'd use canMatch rather than canActivate on role-restricted routes, because canActivate downloads the chunk then rejects. A non-admin shouldn't be downloading the admin bundle at all."

"Third-party libraries. The usual offenders: moment.js, which is large and has no tree-shaking — replace with date-fns or the native Intl APIs. Importing all of lodash rather than specific functions. A full icon set when you use twelve icons. A charting library loaded on every page for one dashboard."

"@defer for heavy in-template content. Route splitting is coarse — the whole screen or nothing. If a dashboard has a light summary and a heavy chart, @defer (on viewport) means the charting library only downloads when the chart scrolls into view. That's finer-grained than routing can achieve."

"Check the build configuration. Production mode, optimisation on, source maps not shipped. It's worth confirming rather than assuming — a misconfigured build can double the output, and it's an embarrassing thing to discover after weeks of optimisation work."

"Standalone components help, because with NgModule importing a shared module pulls in everything it declares whether you use it or not. Standalone components declare exactly what they need, so tree-shaking is more effective."

"Then two things I'd be careful about."

"Don't over-split. Too many tiny chunks means many round trips, and on a high-latency connection that can be slower than one larger bundle. Route-level granularity plus @defer for genuinely heavy components is about right."

"And set a budget so it doesn't regress. Angular supports bundle budgets in angular.json that fail the build past a threshold. Without that, the bundle grows back over six months and you do this exercise again. That's the part people skip, and it's the part that makes the fix durable."

"I'd also add a preloading strategy after splitting — fetching likely-next chunks during idle time gives you small initial load and fast subsequent navigation, which is otherwise the trade-off you accept with lazy loading."

What they're really checking
  • Do you measure first?
  • Do you know lazy loading is the biggest lever?
  • Do you know canMatch avoids the download?
  • Do you know over-splitting is possible?
  • Do you prevent regression with a budget?
Weak answers
  • Red flag: optimising without measuring.
  • Red flag: no mention of lazy loading.
  • Red flag: no plan to stop it regressing.
Likely follow-ups
  • What's the trade-off with preloading?
  • How does @defer differ from lazy routes?
  • How would you measure the real user impact?
