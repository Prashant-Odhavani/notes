Performance, Testing & Security

Three areas where the interview question is usually "how would you find out?" rather than "what's the answer?"

Separate the two problems first

Slow to load is a bundle and network problem — lazy loading, payload size, request count. Covered on the routing page.

Slow to interact is nearly always change detection — method calls in templates, default strategy, missing track.

They have no overlap, so diagnosing which one you have saves most of the work.

The profiler makes this concrete

Angular DevTools shows each change detection cycle as a bar chart, with time attributed per component. So you can see how often cycles run and which component dominates them.

What you're looking for: cycles firing far more often than the user is interacting — that's usually something in the zone triggering constantly, like a setInterval or a mousemove handler. Or one component consuming most of the time, which points at expensive template work.

Guessing at OnPush without this is how people spend a week adding change detection strategies and see no improvement, because the actual cause was a method call in a template.

A table with 5,000 rows and ten columns is 50,000 cells. Even with perfect change detection, that's a large DOM — and browser layout, paint and memory costs scale with node count regardless of framework.

So the answer isn't a better change detection strategy, it's rendering fewer nodes. Virtual scrolling renders perhaps 20 rows and recycles them as you scroll, so the DOM stays constant no matter how long the list is.

The alternative is server-side paging, which is often better still — it also reduces the payload and the query cost. "Do we need 5,000 rows in the browser at all?" is usually the right first question, and it connects to the unbounded query surface problem on the API side.

Component harnesses are the maintainability answer

Tests written against the DOM — fixture.nativeElement.querySelector('.mat-mdc-input-element') — break whenever the component library changes its internal markup. That's happened repeatedly with Angular Material, and it invalidates hundreds of tests at once for no behavioural reason.

A harness is a stable API over a component: setValue(), isDisabled(), click(). The library maintains the harness alongside the markup, so upgrades don't break your tests.

Harnesses also work in both unit tests and Playwright, so the same interaction code is reusable across levels. That's a genuinely strong point to raise, because brittle DOM selectors are the main reason teams abandon component testing.

Test behaviour, not implementation

A test asserting that component.isLoading === true is testing a private field. Rename it and the test fails despite nothing being broken.

A test asserting that a spinner is visible while the request is in flight tests what the user experiences. Refactor freely and it still passes.

That's the difference between a test suite that enables refactoring and one that prevents it — and "our tests break every time we refactor" is a symptom of testing implementation.

Practical version: assert on rendered output and emitted events, mock at the service boundary, and don't reach into component internals.

A note on fakeAsync and waitForAsync

fakeAsync with tick() lets you control time synchronously — useful for testing debounced inputs or timers without actually waiting.

waitForAsync plus fixture.whenStable() waits for real async work to settle.

Modern preference is to await harness methods, which handle stabilisation internally, so you rarely need either explicitly. Knowing they exist matters mostly for maintaining older test suites — and note that fakeAsync depends on Zone.js, so zoneless applications need a different approach.

XSS and sanitization 🔥 Must know

What Angular does for you

Angular treats all interpolated values as untrusted text and escapes them. So {{ userInput }} renders <script> as visible characters, not as a script.

That's the default, it's on everywhere, and it's why XSS in Angular applications is comparatively rare.

BindingAngular's behaviour
{{ value }}Escaped. Always safe
[textContent]Escaped
[innerHTML]Sanitized — strips scripts and event handlers, keeps safe markup
[src], [href]Sanitized against javascript: URLs
[style]Sanitized
bypassSecurityTrustHtmlNo protection at all
 
// Disables Angular's sanitization entirely for this value
this.content = this.sanitizer.bypassSecurityTrustHtml(userSuppliedHtml);
// If userSuppliedHtml contains <img src=x onerror="steal()">, it executes.
bypassSecurityTrust* is a security decision, not a formatting one

The name is deliberately alarming and people use it anyway — usually to render rich text or an embedded SVG that Angular's sanitizer stripped.

The rule: only ever bypass for content you generated or that came from a trusted, controlled source. Never for anything a user supplied, and never for anything from an API you don't control.

If you genuinely need user-supplied rich text, sanitize it with a dedicated library like DOMPurify with an explicit allow-list, and ideally do it server-side on write so the stored data is already safe. Sanitizing on render means every read path has to remember.

In review I'd treat every occurrence of bypassSecurityTrust as requiring a comment explaining why the source is trusted. It's the one Angular API where a mistake is directly exploitable.

Token storage 🔥 Must know

LocationXSS exposureVerdict
localStorageReadable by any scriptAvoid for tokens
sessionStorageSame, scoped to the tabMarginally better, same flaw
In-memory (a service field)Not persisted; lost on refreshGood for access tokens
HttpOnly cookieUnreadable by JavaScriptBest for refresh tokens
The recommended shape

Access token in memory. Refresh token in an HttpOnly, Secure, SameSite cookie.

A short-lived access token in a service field is gone on refresh — so the app silently calls the refresh endpoint, which authenticates via the cookie the browser sends automatically and that JavaScript can't read.

An XSS payload can then use the API while the page is open, which is bad, but it cannot steal a long-lived credential to use later from elsewhere. That's the meaningful difference.

With cookies you need CSRF protection — which Angular's HttpClient supports via XSRF-TOKEN handling.

Content Security Policy is the defence in depth

A strict CSP limits what an injected script can do even if XSS occurs — blocking inline scripts, restricting which origins can be contacted, preventing exfiltration to an attacker's domain.

Angular works with a strict CSP, though it needs configuration for its own inline styles — a nonce, via ngCspNonce.

Worth mentioning because it demonstrates layered thinking: escaping prevents most XSS, CSP limits the damage when something gets through, and HttpOnly cookies limit what can be stolen. No single control is relied upon.

The window problem
ngOnInit() {
  const width = window.innerWidth;        // ReferenceError on the server
  localStorage.getItem('theme');          // same
}
private readonly platformId = inject(PLATFORM_ID);

ngOnInit() {
  if (isPlatformBrowser(this.platformId)) {
    const width = window.innerWidth;
  }
}
// Or move it to ngAfterViewInit, which doesn't run during SSR.

There is no window, document or localStorage in Node. Any code touching them during initialisation crashes the server render — and because the client-side build works fine, this only appears when SSR is enabled.

Third-party libraries are the common culprit, and you often can't fix them — which is why some libraries have to be loaded browser-only.

Non-destructive hydration is the meaningful improvement

Historically Angular's SSR threw away the server-rendered DOM and re-rendered from scratch on the client — so users saw content, then a flicker as it was replaced, and there was a burst of work on load.

Non-destructive hydration (v16+, stable and default in v17+) reuses the existing DOM and only attaches event listeners and state. No flicker, much less work, materially better Core Web Vitals.

It requires the server and client to render the same output. Non-deterministic rendering — Math.random(), Date.now(), anything environment-dependent — causes hydration mismatches, which log warnings and fall back to re-rendering that subtree. That's the practical constraint worth knowing.

Key takeaways
  • Separate slow-to-load from slow-to-interact; they have different causes and fixes.
  • Profile with Angular DevTools before adding OnPush anywhere.
  • Virtual scrolling or server paging for long lists — DOM node count costs regardless of framework.
  • Most tests should be plain unit tests with no TestBed.
  • Component harnesses survive library markup changes; DOM selectors don't.
  • Test rendered behaviour, not internal fields.
  • Angular escapes interpolation and sanitizes innerHTML by default.
  • bypassSecurityTrust* removes that entirely — trusted sources only, sanitize server-side on write.
  • Access token in memory, refresh token in an HttpOnly cookie, plus CSRF protection.
  • CSP limits the damage if XSS still occurs.
  • SSR: guard browser APIs, and keep rendering deterministic for hydration.

Common mistakes

  • Adding OnPush everywhere without profiling first.
  • Rendering thousands of rows instead of virtualising or paging.
  • Tests coupled to component library markup.
  • Asserting on private fields rather than behaviour.
  • Too many E2E tests — slow, flaky, expensive to maintain.
  • bypassSecurityTrustHtml with user content.
  • JWTs in localStorage.
  • Cookies without CSRF protection.
  • window access during SSR initialisation.
  • Non-deterministic rendering breaking hydration.

Interview questions

Intermediate

How does Angular protect against XSS, and where does that protection stop? 🔥 Must know
How I'd answer

"Angular treats every interpolated value as untrusted text and escapes it. So {{ userInput }} containing a script tag renders the tag as visible characters rather than executing it. That's on by default everywhere, which is why XSS in Angular apps is comparatively rare."

"It goes further for specific bindings. [innerHTML] is sanitized — it strips scripts and event handlers while keeping safe markup, so you can render formatted content without opening a hole. [src] and [href] are checked against javascript: URLs, and [style] is sanitized too."

"Where it stops is bypassSecurityTrustHtml and its siblings. Those disable sanitization completely for that value. The name is deliberately alarming and people still reach for it — usually because the sanitizer stripped something they wanted, like an embedded SVG or rich-text markup."

"So my rule is: only bypass for content you generated or that came from a source you control. Never for user input, never for an API you don't own. And in code review I'd treat every occurrence as needing a comment explaining why the source is trusted — it's the one Angular API where a mistake is directly exploitable."

"If the requirement genuinely is user-supplied rich text, the answer is a dedicated sanitizer like DOMPurify with an explicit allow-list, and ideally applied server-side on write so the stored value is already safe. Sanitizing on render means every read path has to remember to do it — and one that forgets is the vulnerability."

"Two adjacent things I'd raise because they're part of the same picture."

"Token storage. Escaping is the primary defence, but if XSS does occur, what can it steal? A JWT in localStorage is readable by any script, so it can be exfiltrated and used later from anywhere. An access token held in memory plus a refresh token in an HttpOnly cookie means the attacker can act while the page is open but can't take a durable credential away. That's a meaningful reduction in impact."

"Content Security Policy as defence in depth — it restricts what an injected script can do even when escaping fails, particularly blocking exfiltration to an attacker's domain. Angular supports a strict CSP with a nonce for its inline styles."

"So the layered view: escaping prevents most XSS, CSP limits what a successful injection can do, and HttpOnly cookies limit what it can steal."

What they're really checking
  • Do you know escaping is the default and sanitization applies to innerHTML?
  • Do you know bypassSecurityTrust* removes it?
  • Do you sanitize server-side on write rather than on render?
  • Do you connect it to token storage and CSP?
Likely follow-ups
  • How would you safely render user-submitted markdown?
  • What's the CSRF risk with cookies?
  • How does the refresh flow work with an in-memory token?

Advanced

How would you test an Angular application? ⭐ Senior-level
How I'd answer

"I'd aim for most of the value at the cheapest level, and be deliberate about what each level is for — because the failure mode is a suite that's slow, flaky and breaks on every refactor."

"Most tests should be plain unit tests with no Angular machinery at all. Services, validators, pipes, pure functions — instantiate the class with stub dependencies and assert. No TestBed, no fixture, milliseconds to run. If a service is hard to test this way it usually means it's doing too much, so the difficulty is useful information."

"Component tests for rendering and interaction logic, with services mocked at the boundary. The key discipline is testing behaviour rather than implementation. Asserting component.isLoading === true tests a private field — rename it and the test fails though nothing broke. Asserting that a spinner is visible while a request is in flight tests what the user experiences, and survives refactoring."

"For interacting with components I'd use component harnesses rather than DOM queries. Tests written against querySelector('.mat-mdc-input-element') break whenever the library changes its internal markup — which Angular Material has done repeatedly, invalidating hundreds of tests for no behavioural reason. A harness is a stable API the library maintains alongside its markup, and the same harness code works in Playwright too."

"A few integration tests where several components and real routing interact — the places where the wiring is the risk rather than any individual piece."

"Few E2E tests, covering critical journeys only: log in, place an order, check out. They're the most valuable tests when they fail legitimately and the most expensive to maintain. A large E2E suite becomes flaky, and a flaky suite gets ignored — at which point it's worse than not having it, because it consumes CI time and trains people to re-run failures."

"Some specifics that matter in practice."

"Mock at the HTTP boundary with HttpTestingController, not by stubbing your own service methods. That way you're testing your service's real logic including error handling, and you can assert the request shape."

"Don't test the framework. A test proving *ngIf hides an element is testing Angular, not your code."

"Async handling — await harness methods where possible, since they stabilise internally. fakeAsync with tick() for time-dependent things like debounced inputs. Worth noting fakeAsync relies on Zone.js, so zoneless apps need a different approach."

"And the honest position on coverage: coverage percentage is a weak signal. 90% coverage of getters and setters tells you nothing. I'd rather have thorough tests on the business rules and the error paths than uniform coverage — and I'd specifically make sure the failure cases are tested, because those are what break in production and what nobody exercises manually."

What they're really checking
  • Do you push most tests to the cheapest level?
  • Do you test behaviour rather than internals?
  • Do you know harnesses and why they matter?
  • Are you realistic about E2E cost and flakiness?
  • Do you have a view on coverage as a metric?
Weak answers
  • Red flag: "aim for 100% coverage."
  • Red flag: mostly E2E tests.
  • Red flag: asserting on component private state.
Likely follow-ups
  • How do you test a component with a signal input?
  • How do you keep E2E tests from being flaky?
  • How would you test an interceptor?
