Angular

The framework most .NET shops chose, and the one whose interview questions are almost entirely about change detection.

Why .NET teams picked Angular 🟡 Intermediate

In simple terms

Angular is opinionated, batteries-included and built around dependency injection and decorators — which is the shape a C# developer already thinks in.

React gives you a rendering library and leaves the architecture to you. Angular gives you the architecture.

The DI similarity is genuinely useful, not superficial

Angular's injector hierarchy behaves like ASP.NET Core's service scopes: a provider on the root injector is effectively a singleton, one on a component is scoped to that component and its children.

So the reasoning you already do about lifetimes transfers — including the failure mode. Injecting something short-lived into something long-lived causes the same captive dependency problem in both.

That's why Angular tends to feel natural to backend developers and React tends to feel foreign at first.

Angular has changed substantially, and most real codebases are a mixture — modules and standalone components side by side, some signals, mostly RxJS.

That's normal and not a problem. Standalone components interoperate with modules deliberately, so migration is incremental.

What matters in an interview is being able to say which patterns you've used and why. "We're on v17, mostly standalone, we introduced signals for component state but our data layer is still RxJS because that's what the HTTP client returns" is a much stronger answer than reciting the newest features — it shows you've worked in a real migration rather than a tutorial.

The three things that decide performance 🔥 Must know

Almost every Angular performance problem is one of these
  1. Change detection running too often, or over too much of the tree. Default strategy plus Zone.js checks everything on every async event.
  2. Expensive work inside a template. A method call or getter in a binding runs on every change detection cycle.
  3. Subscriptions that are never cleaned up, leaking memory and running work for destroyed components.

All three are covered on the reactivity page, which is the highest-value page in this section.

<!-- filteredItems() runs on EVERY change detection cycle,
     which may be hundreds of times per second during scroll or typing -->
<div *ngFor="let item of filteredItems()">{{ item.name }}</div>

<!-- Same problem: a getter doing real work -->
<span>{{ calculateTotal() }}</span>
Why this is worse than it looks

Angular has no way to know whether a method's result changed, so it must call it again every cycle. With the default change detection strategy and Zone.js, a cycle runs after every click, HTTP response, timer tick and keystroke — across the whole component tree.

So a filter over a thousand items, called from a template, can run hundreds of times per second while the user types. The page becomes visibly slow and the cause is invisible in the code — it looks like a normal binding.

The fixes, in order of preference: a computed signal (recalculates only when its inputs change), a precomputed field updated when the data changes, or a pure pipe. Never a method call in a hot binding.

Both are good. The differentiator is what happens as the team grows.

Angular's opinionation means ten developers write similar code, because the framework has already made the routing, HTTP, forms and DI decisions. That's genuinely valuable on a large or rotating team, and it's why enterprises pick it.

React's flexibility means those decisions are yours — which is faster when the team is small and aligned, and produces divergent codebases when it isn't. Two React projects at the same company can look nothing alike.

The answer interviewers respond to: "whichever the team already knows" — because familiarity outweighs the technical differences for almost every real project. Choosing the framework your team doesn't know, on the basis of a benchmark, is the failure mode.

Why is your Angular app slow? 🔥 Must know
How I'd answer

"I'd want to know which kind of slow first, because the causes are unrelated: slow initial load, or sluggish interaction."

"Slow initial load is a bundle problem. I'd check the bundle with source-map-explorer, look for whether routes are lazy-loaded, and look for the usual offenders — moment.js, importing all of lodash rather than specific functions, an icon library pulling in everything. Lazy-loading feature routes is usually the biggest single win, because the initial bundle only needs the first screen."

"Sluggish interaction is almost always change detection, and there are three specific causes I'd look for."

"Method calls in templates. This is the most common by a wide margin. Angular can't know whether a method's result changed, so it calls it on every change detection cycle — and with the default strategy plus Zone.js, that's after every click, HTTP response, timer and keystroke, across the whole tree. A filter over a thousand items in a template can run hundreds of times a second while someone types. It looks like an ordinary binding, which is why it survives review."

"Default change detection everywhere. Without OnPush, every async event anywhere checks every component. Moving to OnPush means a component only re-checks when its inputs change by reference, an event fires inside it, or an observable it subscribes to with the async pipe emits."

"Missing trackBy — or in modern Angular, a track expression on @for. Without it, replacing an array causes Angular to destroy and recreate every DOM node rather than reusing them. On a large list that's very visible."

"To confirm rather than guess, I'd use the Angular DevTools profiler, which shows change detection cycles and how long each component took. That points directly at the component responsible instead of me speculating."

"The modern structural answer is signals. A computed signal recalculates only when its dependencies change, so the template-method problem disappears — and signals enable fine-grained updates where Angular can re-render just what depends on the changed value rather than checking a component tree. Combined with zoneless change detection, that removes the whole 'checks everything on every event' model."

"And I'd check the obvious non-Angular causes too: are we making N+1 API calls, is a single endpoint slow, are we loading far more data than the screen displays? A slow app is often a slow backend, and it's worth ruling that out before profiling the framework."

What they're really checking
  • Do you separate load time from interaction cost?
  • Do you know method-calls-in-templates is the usual culprit?
  • Do you know what triggers change detection under OnPush?
  • Do you profile rather than guess?
Weak answers
  • Red flag: "Angular is just slow."
  • Red flag: adding OnPush everywhere with no diagnosis.
  • Red flag: no mention of the profiler.
Likely follow-ups
  • What exactly triggers change detection?
  • How do signals change this?
  • What does trackBy do?
