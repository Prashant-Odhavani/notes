Components, Modules & DI

The building blocks. Dependency injection will feel familiar; the injector hierarchy is the part worth real attention.

🟢 Beginner 🟡 Intermediate 🔥 Must know
Quick revision
  • Standalone components are the default now. NgModule is legacy but interoperates.
  • Binding syntax: [prop] in, (event) out, [(ngModel)] both.
  • providedIn: 'root' is a singleton and tree-shakeable.
  • A provider on a component gives one instance per component instance.
  • ngOnInit for initialisation, not the constructor.
  • ngOnChanges fires on reference change, not mutation.
  • ng-content projects children — the composition mechanism.

The component model 🔥 Must know

@Component({
  selector: 'app-order-summary',
  standalone: true,                       // implicit in v19+
  imports: [CurrencyPipe, OrderRowComponent],   // what the TEMPLATE needs
  changeDetection: ChangeDetectionStrategy.OnPush,
  template: `
    <h2>{{ title() }}</h2>
    @for (line of order().lines; track line.id) {
      <app-order-row [line]="line" (removed)="remove($event)" />
    } @empty {
      <p>No items.</p>
    }
    <strong>{{ total() | currency }}</strong>
  `
})
export class OrderSummaryComponent {
  // Signal inputs - Angular 17.1+
  readonly order = input.required<Order>();
  readonly title = input('Order summary');

  readonly removed = output<string>();

  readonly total = computed(() =>
    this.order().lines.reduce((s, l) => s + l.price, 0));

  remove(id: string) { this.removed.emit(id); }
}

importsComponents, directives and pipes the template uses. Standalone components declare their own dependencies
templateInline, or templateUrl for a separate file

Signal inputs are a real improvement, not just new syntax

The old @Input() decorator gave you a plain property. To react to a change you needed ngOnChanges and a string-keyed lookup, or a setter.

input() returns a signal, so it composes directly into computed(). Derived values update automatically with no lifecycle hook at all — which removes most legitimate uses of ngOnChanges.

input.required<T>() also gives compile-time enforcement that the input was supplied, replacing the ! non-null assertion that everyone used to write and occasionally got wrong.

Standalone vs NgModule 🔥 Must know

Senior signal — why standalone is genuinely better

The real problem with NgModule wasn't the boilerplate, it was indirection. To know whether a component could use a particular directive, you had to find its module, check the imports, and possibly follow a chain of re-exporting modules.

With standalone, a component's dependencies are declared in the component. What it needs is visible where it's used, and unused imports are a compile error rather than dead weight in a shared module.

It also makes lazy loading finer-grained — you can lazy-load a single component rather than needing a module boundary, so route-level code splitting stops being an architectural decision.

Migration is incremental by design: standalone components can be imported into modules and vice versa, so a mixed codebase is entirely normal and not a problem to apologise for.

Template bindings 🔥 Must know

<!-- Interpolation: value into text -->
<p>{{ order.reference }}</p>

<!-- Property binding: value into a property. Note NOT an attribute -->
<img [src]="imageUrl" [alt]="description">
<button [disabled]="!isValid">Save</button>

<!-- Event binding: DOM or component event out -->
<button (click)="save()">Save</button>
<app-row (removed)="onRemoved($event)" />

<!-- Two-way: shorthand for [value] plus (valueChange) -->
<input [(ngModel)]="searchTerm">
Property versus attribute — the distinction that causes bugs

[disabled]="false" sets the DOM property to false, so the button is enabled. disabled="false" sets the HTML attribute to the string "false" — and the mere presence of the attribute disables the button, so the button is disabled.

Angular binds to properties by default, which is almost always what you want. For genuine attributes there's [attr.aria-label], and that's required for ARIA attributes because they have no corresponding DOM property.

So [attr.aria-expanded]="isOpen" is correct and [aria-expanded]="isOpen" silently does nothing. That's a common accessibility bug in Angular templates.

track is now mandatory, and that's deliberate

The old trackBy was optional, so it was usually omitted — and without it, replacing an array causes Angular to destroy and recreate every DOM node instead of reusing them. On a large list that's a very visible performance problem, and it also loses focus and scroll position.

@for requires a track expression. Making it mandatory removed an entire category of accidental slowness.

Track by a stable unique identifier — usually item.id. Tracking by index defeats the purpose, because the identity of position 3 changes when you insert at position 0.

Dependency injection 🔥 Must know

// Modern: the inject() function
export class OrderComponent {
  private readonly http   = inject(HttpClient);
  private readonly logger = inject(LoggerService);
}

// Traditional: constructor injection - still fully supported
export class OrderComponent {
  constructor(
    private readonly http: HttpClient,
    private readonly logger: LoggerService
  ) {}
}

The injector hierarchy

Angular resolves a dependency by looking at the component's own injector, then its parent's, then upward to the root. The first match wins.

So providing a service on a component gives that component and its children their own instance, shadowing any root-level one.

@Component({
  selector: 'app-wizard',
  standalone: true,
  providers: [WizardStateService],   // a fresh instance per wizard
  template: `<app-step-one /><app-step-two />`
})
export class WizardComponent {}

// Every child step injects the SAME WizardStateService instance -
// the one belonging to this wizard. Two wizards on a page don't share state.
Senior signal — this is how you scope shared state without a global store

A component-level provider is the cleanest way to share state between a component and its descendants without making it application-global.

A multi-step wizard, a data grid with child cells, a form section with several sub-components — all need shared state that is per-instance. Putting it in a root singleton means two wizards on the same page interfere; passing it down through inputs means threading it through every intermediate layer.

A provider on the parent gives every descendant the same instance via injection, and it's destroyed with the parent — so there's no cleanup and no leakage between instances.

That's a pattern worth knowing explicitly, because the instinct from backend DI is to register everything at the root.

The captive dependency problem applies here too

Injecting a component-scoped service into a root singleton doesn't work — the root injector can't see component providers, so you get a NullInjectorError.

The reverse is fine and common: a component-scoped service injecting root singletons.

This is the same reasoning as not injecting a scoped service into a singleton in ASP.NET Core — a longer-lived thing cannot depend on a shorter-lived one. Angular fails loudly at runtime rather than silently capturing, which is arguably better than .NET's behaviour before the validation was added.

HookFiresUse for

ngAfterViewInitAfter the view and children renderDOM measurement, ViewChild access

Why initialisation goes in ngOnInit, not the constructor

The constructor runs before Angular sets the inputs. So reading this.orderId there gives you undefined, and an HTTP call using it requests the wrong thing — or throws.

ngOnInit runs after the first round of inputs is applied, so the values are there.

Keeping the constructor to dependency injection only also makes components far easier to test — you can construct one without triggering side effects, then call ngOnInit when you actually want the initialisation to happen. A constructor that fires HTTP requests makes every test do network work.

ngOnChanges only sees reference changes

It fires when an input is reassigned, not when the object it points at is mutated. So a parent doing this.order.total = 100 does not trigger the child's ngOnChanges.

Same underlying rule as OnPush's reference comparison — and the same fix: replace rather than mutate.

With signal inputs this mostly stops mattering, because a computed() depending on the input signal re-evaluates automatically and there's no hook to get wrong.

Content projection 🟡 Intermediate

@Component({
  selector: 'app-card',
  standalone: true,
  template: `
    <div class="card">
      <header><ng-content select="[card-title]" /></header>
      <div class="body"><ng-content /></div>
      <footer><ng-content select="[card-actions]" /></footer>
    </div>`
})
export class CardComponent {}
<app-card>
  <h3 card-title>Order 1041</h3>
  <p>Placed 12 June. Three items.</p>
  <button card-actions>View</button>
</app-card>
Projection is what makes components composable

Without it, a card component would need an input for every possible piece of content — [title], [body], [buttonText] — and would break the moment someone needed two buttons or an icon.

With projection the card owns the structure and styling, and the consumer owns the content. That's a much better separation, and it's how every component library is built.

Note that projected content belongs to the parent's change detection context, not the card's — which is why projecting into an OnPush component still updates when the parent's data changes.

Key takeaways
  • Standalone components declare their own dependencies — less indirection, finer lazy loading.
  • Signal inputs compose into computed(), removing most uses of ngOnChanges.
  • [prop] binds a property; [attr.x] for real attributes, required for ARIA.
  • @for requires track — track a stable id, never the index.
  • providedIn: 'root' is a singleton; a component provider is one per component instance.
  • Component-level providers are how you scope shared state to a subtree.
  • A singleton can't inject a component-scoped service — the same rule as .NET DI lifetimes.
  • Constructor for DI only; ngOnInit for initialisation.
  • ngOnChanges fires on reassignment, not mutation.
  • ng-content gives structure/content separation; projected content stays in the parent's change detection.

Common mistakes

  • HTTP calls in the constructor, before inputs are set.
  • Mutating an input object and expecting ngOnChanges to fire.
  • [aria-label] instead of [attr.aria-label].
  • disabled="false" as an attribute, which disables the control.
  • Tracking by index in @for.
  • Registering everything in root when per-instance state was needed.
  • Injecting a component-scoped service into a singleton.
  • Not using OnPush as the default for new components.
  • Inputs for content where projection is the right answer.
  • Forgetting to add an import to a standalone component's imports.

Interview questions

Intermediate

Explain Angular's dependency injection and service lifetimes. 🔥 Must know
How I'd answer

"It's close enough to ASP.NET Core's DI that the reasoning transfers directly, which is one reason Angular feels natural coming from .NET."

"Angular has a hierarchy of injectors. When a component asks for a dependency, Angular checks that component's own injector, then its parent's, then upward to the root injector. The first match wins."

"@Injectable({ providedIn: 'root' }) registers on the root injector, so you get one instance for the whole application — effectively a singleton. It's also tree-shakeable: if nothing injects it, it's dropped from the bundle, which the old NgModule providers array couldn't do."

"A providers array on a component creates a new instance per component instance, shared with that component's descendants. That's the closest thing to a scoped lifetime."

"That second one is more useful than people realise. If I have a multi-step wizard where the steps need shared state, providing the state service on the wizard component means every child step injects the same instance — the one belonging to that wizard. Two wizards on a page don't interfere, and it's destroyed with the parent so there's no cleanup and no leakage. A root singleton would make them share state; passing it through inputs would mean threading it through every intermediate component."

"The failure mode is the same as .NET's: a longer-lived service can't depend on a shorter-lived one. Injecting a component-scoped service into a root singleton throws NullInjectorError, because the root injector can't see component providers. The reverse — a component service injecting root singletons — is fine and normal."

"Angular fails loudly there, which is arguably better than the captive-dependency problem in .NET where a singleton holding a scoped service used to just silently misbehave."

"On syntax: inject() is the modern form and constructor injection still works identically. inject() is more convenient for base classes and functional guards and interceptors, where there's no constructor to inject into. It has to be called in an injection context — a field initialiser or constructor — which is the one gotcha."

What they're really checking
  • Do you know the injector hierarchy and first-match resolution?
  • Do you know component providers give per-instance scope?
  • Can you give a real reason to use one?
  • Do you know the lifetime constraint?

  • What does tree-shakeable mean here?
  • How would you provide different implementations per environment?

Why put initialisation in ngOnInit rather than the constructor? 🔥 Must know
How I'd answer

"Because inputs aren't set when the constructor runs. Angular constructs the component first, then applies the bound inputs, then calls ngOnInit."

"So if a component takes an orderId input and the constructor tries to load that order, this.orderId is undefined — and you either throw or request /api/orders/undefined. That's a genuinely common bug and it looks baffling, because the input clearly is bound in the template."

"ngOnInit runs after the first ngOnChanges, so the inputs are populated."

"There's a second reason that matters as much: testability. If the constructor only does dependency injection, I can construct the component in a test without triggering any side effects, set up whatever state I need, then call ngOnInit deliberately. A constructor that fires HTTP requests means every test — including ones that don't care about loading — does network work and needs mocks."

"That's the same principle as keeping .NET constructors cheap and side-effect-free: construction shouldn't do work."

"So the rule I'd state: constructor for DI, ngOnInit for initialisation."

"Worth adding what modern Angular changes here. With signal inputs, a lot of what used to go in ngOnInit or ngOnChanges becomes a computed() that just depends on the input signal — so it re-evaluates when the input changes and there's no lifecycle hook to get wrong. For loading data based on an input, the pattern is toObservable on the input signal piped through switchMap, converted back with toSignal — which also handles the case where the input changes after initialisation, something an ngOnInit-only implementation misses entirely."

"That last point is worth making, because 'load in ngOnInit' quietly assumes the input never changes — and when it does, the component shows stale data."

What they're really checking
  • Do you know inputs aren't available in the constructor?
  • Do you mention testability?
  • Do you know ngOnInit alone misses later input changes?
Likely follow-ups
  • What if the input changes after init?
  • When would you use ngAfterViewInit?
  • How do signal inputs change this?
