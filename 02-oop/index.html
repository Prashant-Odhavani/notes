Object-Oriented Programming

Everyone can name the four pillars. Interviews use them as a door into what you actually understand about design.

🟢 Beginner 🟡 Intermediate 🔥 Must know
Quick revision
  • OOP exists to make change cheap. Data and the rules about it live together, so a change lands in one place.
  • Encapsulation = protect the rules, not just the fields.
  • Abstraction = decide what to expose.
  • Inheritance = "can be used instead of".
  • Polymorphism = same call, different behaviour, picked at runtime.
  • Judge any design by one question: what does this make easy to change, and what does it make hard?

Why interviewers still ask this 🟢 Beginner

"What are the four pillars of OOP?" gets asked constantly. The recited answer is worth nothing — everyone has it memorised.

The question is really a setup. What follows is where the signal is:

  • "Show me encapsulation being broken in code you've seen."
  • "When would inheritance be the wrong choice?"
  • "How does polymorphism actually work at runtime?"

So: know the definitions cold — they take thirty seconds — and spend your prep on the second layer. Invariants, substitutability, coupling, and why designs rot.

Senior signal

Talk about invariants and dependency direction instead of the four words. "Encapsulation means a caller can't put the object into an invalid state" lands much better than "encapsulation means hiding data with private fields".

The four pillars, and what they're actually for 🔥 Must know

PillarTextbook versionWhat it's really for
Encapsulation Bundle data with the methods that use it; restrict access Make it impossible to observe or leave the object in an invalid state
Abstraction Expose the essentials, hide the detail Let callers depend on a stable idea instead of a changing implementation
Inheritance Derive a type from another and gain its members Express real substitutability so polymorphic code works — not code reuse
Polymorphism One interface, many implementations Add behaviour without touching existing callers
Remember this

All four pillars are ways of controlling who depends on what.

That framing turns "define encapsulation" into a design conversation, which is where you want to be.

Think of it this way

A well-designed kitchen. Encapsulation is the cupboard door — you get plates, not the mess. Abstraction is the tap: hot and cold, no plumbing. Inheritance is that any kettle fits the same socket. Polymorphism is that "boil water" works whether it's a kettle or a hob.

Cross-cutting interview questions

Is OOP still the right default, given functional programming and modern C#?
How I'd answer

"I treat them as complementary. Modern C# clearly does too — records, pattern matching, immutable collections and LINQ are functional ideas that landed in an OO language because they solve things OOP handles badly."

"OOP earns its place when something has identity, a lifecycle and rules. An Order has a state machine and things that must always be true about it. Putting that in a type that won't let callers break it is genuinely valuable."

"Functional style wins for transformation and calculation — take data, apply rules, produce a result, no hidden state. Easier to test, easy to parallelise, no temporal coupling."

"So a codebase I'd be happy with is mixed. Entities are encapsulated with behaviour. Values are immutable records. Query and reporting paths are basically functional pipelines with no domain objects at all — which is really the argument for CQRS. The mistake is dogma either way: forcing a rich domain model onto a report, or turning entities into property bags with all the rules in static helpers."

What they're really checking
  • Do you hold a position with reasons, or an allegiance?
  • Do you know modern C# absorbed functional features, and why?
Likely follow-ups
  • What's an anaemic domain model? Is it always wrong?
  • When would you choose a record over a class?
You're reviewing a class with 40 public members and 2,000 lines. What do you do?
How I'd answer

"I wouldn't start by splitting it. Splitting arbitrarily gives you several classes that all depend on each other, which is worse than one honest big class."

"First I'd look for the seams: which methods use which fields. Classes like this almost always have two or three clusters where a group of methods touches a group of fields and nothing else. That clustering is the boundary — it's low cohesion showing itself."

"Then I'd ask what reasons this class has to change. If pricing rules, persistence and notifications all live in it, those change for different reasons on different schedules, so separating them is justified by more than taste. If it's genuinely one cohesive thing that happens to be big — a complex tax calculation, say — I'd leave it. Splitting something cohesive across files makes it harder to follow, not easier."

"And I'd do it incrementally behind tests. Characterisation tests first, extract one cluster at a time, keep the original as a facade delegating to the new types so callers don't all change at once. Every step stays reviewable and revertible."

What they're really checking
  • Can you find real boundaries, or do you split by line count?
  • Do you know cohesion is the underlying concept?
  • Do you refactor safely and incrementally?
Likely follow-ups
  • What if it's a God object referenced from 200 places?
  • How do you decide when a class is "too big"?
