OOP Fundamentals

The four pillars, explained the way you'd want a senior engineer to explain them — plus the C# details interviewers always follow up with.

🟢 Beginner 🟡 Intermediate 🔥 Must know
Quick revision
  • Encapsulation = the object protects its own rules. Public setters give that away.
  • Abstraction = hide what changes, expose what stays the same.
  • Inheritance = "can be used instead of". Not "shares code with".
  • Polymorphism = same call, different behaviour, decided at runtime.
  • virtual+override picks the method by the object's type. new picks it by the variable's type — almost always a bug.

Classes and objects 🟢 Beginner

One line: a class is the blueprint, an object is one thing built from it.

In C#, classes are reference types. A variable holds a reference to the object, not the object itself.

var a = new Order();
var b = a;              // b points at the SAME order
b.Status = OrderStatus.Paid;

Console.WriteLine(a.Status);   // Paid - because a and b are the same object

That single fact causes a lot of real bugs: shared state, accidental mutation, and surprises around equality. The details are in the C# type system.

The design question that actually matters is not "what fields does this hold?" It is:

What rules is this class responsible for keeping true?

If the answer is "none", you've built a data structure. That's fine — just don't call it a domain model.

Encapsulation 🔥 Must know

In simple terms

The object protects its own rules. Nobody outside can put it into a state that shouldn't exist.

It's about protecting rules — not about typing private in front of fields.

Think of it this way

A cash machine. You can withdraw and check your balance, but you can't reach in and set the balance to £1,000,000.

The machine exposes operations, not fields. That's the whole idea.

Start with the broken version

public class Order
{
    public List<OrderLine> Lines { get; set; } = new();
    public decimal Total { get; set; }
    public OrderStatus Status { get; set; }
    public DateTime? ShippedAt { get; set; }
}

Every field is behind a property, so it looks fine. Now watch what any caller can do:

order.Lines.Add(new OrderLine(sku, qty));   // Total is now wrong
order.Status = OrderStatus.Shipped;         // but ShippedAt is still null
order.Total  = -50;                         // a negative total is allowed

The rules exist — total must match the lines, a shipped order must have a shipped date — but the class doesn't own them. So every caller has to remember them. Three callers will, the fourth won't, and that's your production bug.

Common mistake

Exposing a List<T> property. Even with a private setter, the caller can still call .Add() and .Remove(). This is the encapsulation leak people miss most often in C#.

The fixed version

public sealed class Order
{
    private readonly List<OrderLine> _lines = [];

    public OrderStatus Status { get; private set; } = OrderStatus.Draft;
    public DateTime? ShippedAt { get; private set; }

    public IReadOnlyList<OrderLine> Lines => _lines;   // read-only view
    public decimal Total => _lines.Sum(l => l.LineTotal); // derived, can't drift

    public void AddLine(string sku, int quantity, decimal unitPrice)
    {
        if (Status != OrderStatus.Draft)
            throw new InvalidOperationException("Lines can only be added to a draft order.");
        if (quantity <= 0)
            throw new ArgumentOutOfRangeException(nameof(quantity));

        _lines.Add(new OrderLine(sku, quantity, unitPrice));
    }

    public void Ship(DateTime shippedAtUtc)
    {
        if (Status != OrderStatus.Paid)
            throw new InvalidOperationException($"Cannot ship an order in state {Status}.");

        Status = OrderStatus.Shipped;
        ShippedAt = shippedAtUtc;      // both change together, or neither does
    }
}

What changed:

  • Total is calculated, so it can never disagree with the lines.
  • Ship() sets status and date together, so "shipped with no date" is impossible.
  • Illegal transitions throw instead of quietly corrupting data.
  • Callers can read the lines but not modify them.

Notice this isn't more code overall. It's the same validation that would otherwise be copy-pasted across services — moved to the one place that can't be bypassed.

How I'd explain this in an interview

"Encapsulation means the object owns the rules about its own state, so no caller can break them. The access modifiers are just the mechanism."

"The example I use is an Order with a public setter on Total and Status. It looks encapsulated because everything is a property, but the rule 'total equals the sum of the lines' isn't enforced anywhere — so every service has to remember it, and eventually one forgets."

"The fix is to expose operations instead of state. AddLine keeps the total right, Ship sets the status and timestamp together. And in C# I'd watch for the list leak — returning List<T> lets callers mutate it even if the setter is private."

Abstraction 🟢 Beginner

In simple terms

Hide what's likely to change. Expose what won't.

Think of it this way

A car's pedals. "Accelerate" and "brake" haven't changed in a century — but what's behind them went from petrol engine to electric motor without you relearning how to drive.

The pedals are the abstraction. The engine is the implementation.

So the test for a good abstraction is simple: can the implementation change without callers changing?

// Leaky: the caller now knows we use SQL, and knows about offsets and readers.
public interface ICustomerSqlRepository
{
    SqlDataReader ExecuteCustomerQuery(string whereClause, int offset, int fetch);
}
public interface ICustomerRepository
{
    Task<Customer?> FindAsync(CustomerId id, CancellationToken ct);
    Task<IReadOnlyList<Customer>> SearchAsync(CustomerSearch criteria, CancellationToken ct);
}

The second one isn't better because it uses an interface — the first one does too. It's better because it hides a decision that might change (SQL) and exposes a concept that won't (finding a customer).

Common mistake

Creating an interface that mirrors one class method-for-method. That abstracts nothing. You've added a file and an indirection, and the "flexibility" is imaginary.

Inheritance 🔥 Must know

In simple terms

Inheritance means "can be used instead of".

It does not mean "is a kind of", and it definitely doesn't mean "shares some code with".

Think of it this way

A debit card inherits from "payment card" because anywhere a payment card is accepted, a debit card works. That's a safe substitution.

A gift card looks like a payment card — same shape, same magnetic stripe — but it can't be used for a hotel deposit. If you modelled it as a payment card, every deposit flow would break.

So when you inherit, you're making a promise: anywhere the base type works, the derived type works too. Break that promise and correct code starts failing.

Here's the classic example of how it goes wrong.

public class Rectangle
{
    public virtual int Width  { get; set; }
    public virtual int Height { get; set; }
    public int Area => Width * Height;
}

public class Square : Rectangle
{
    public override int Width  { set { base.Width = base.Height = value; } }
    public override int Height { set { base.Width = base.Height = value; } }
}
void Stretch(Rectangle r)
{
    r.Width = 10;
    r.Height = 4;
    Debug.Assert(r.Area == 40);   // fails for Square: area is 16
}

Nothing here is a compile error. The design is wrong. Rectangle implicitly promises that width and height are independent. Square breaks that promise.

This generalises well beyond shapes. The warning signs that inheritance is wrong:

  • A subclass throws from a method it inherited.
  • A subclass makes a rule stricter than the base.
  • Call sites need if (x is SomeSubclass) checks.

How to choose, in plain terms:

  • If two completely unrelated types might want this → interface. (IDisposable, IValidatable, IPaymentGateway.)
  • If there's real shared code and shared state, and the types form a family → abstract class. Example: a message handler base that owns retry bookkeeping while each subclass implements only the handling.
  • Often you use both: an interface for the contract, an abstract base for convenience.
Default interface methods (C# 8+) 💡 Good to know

They exist so library authors can add a method to a published interface without breaking everyone. They are not a replacement for abstract classes — there's still no state, and the resolution rules get subtle fast. Use them for evolving an interface, not as a default design tool.

Polymorphism 🔥 Must know

In simple terms

You call the same method and get different behaviour, decided by what the object actually is at runtime.

The caller doesn't need to know which concrete class it got.

Think of it this way

You press "print" in an application. The same click sends a job to a laser printer, an inkjet, or a PDF writer — and the application has no idea which.

It just calls Print(). Each printer knows how to do its own version.

Two kinds get mixed up in interviews. Being precise here is an easy win.

OverloadingOverriding
What differsThe parametersNothing — same signature
DecidedAt compile timeAt run time
Based onThe argument types you passedThe actual type of the object
KeywordsNonevirtual + override

virtual / override / new — the classic trap 🟡 Intermediate

public class Notifier
{
    public virtual string Send() => "base-virtual";
    public          string Log()  => "base-plain";
}

public class EmailNotifier : Notifier
{
    public override string Send() => "email-override";
    public new      string Log()  => "email-new";      // hides, does not override
}
Notifier n = new EmailNotifier();

n.Send();                     // "email-override"  <- object's type wins
n.Log();                      // "base-plain"      <- variable's type wins
((EmailNotifier)n).Log();     // "email-new"       <- different variable type, different result

Read that last block twice. With new, the behaviour depends on how the variable is declared, not on what the object actually is.

That's why it's dangerous. Two call sites can look identical and behave differently, and nothing in the code looks wrong.

Common mistake

Seeing new on a method in a code review and letting it through. Default assumption: it's a mistake. Either the base method should have been virtual, or the derived method should have a different name.

How the runtime actually picks the method 🔴 Advanced ⭐ Senior-level

Here's the mechanism, step by step:

  1. Every object on the heap has a pointer to its type's method table.
  2. A non-virtual call compiles to a direct call — the target is known at compile time.
  3. A virtual call loads the method table from the object and calls through the slot for that method. So the object's real type decides.
  4. An interface call needs one more lookup, because the runtime has to map the interface slot to the concrete type's implementation.

Two consequences worth knowing:

  • Inlining. The JIT can't inline a call whose target it can't prove. Modern .NET does guarded devirtualization — it speculatively inlines the type it sees most often and adds a type check that falls back if a different type shows up.
  • sealed helps. If a class or override is sealed, the JIT can prove there's no further override and skip the indirection entirely. That's why hot framework types are often sealed.
Keep this in proportion

For normal application code this performance difference is unmeasurable. The real reasons to seal a class are design reasons: you didn't design it for inheritance, and sealing means you can change internals later without breaking someone's override.

Never call a virtual method from a constructor 🔴 Advanced

public abstract class Repository
{
    protected Repository()
    {
        Configure();          // virtual call during BASE construction
    }
    protected virtual void Configure() { }
}

public sealed class SqlRepository : Repository
{
    private readonly string _connection = "Server=...";

    protected override void Configure()
    {
        Console.WriteLine(_connection.Length);   // _connection is still null here
    }
}

Why? Construction order in C# is:

  1. Derived field initialisers run.
  2. Base constructor runs. ← your virtual call happens here, and it dispatches to the derived override
  3. Derived constructor body runs.

So the override executes while the object is only half-built. In this example _connection hasn't been assigned yet.

The rule: don't call virtual members from constructors. If subclasses need to contribute to setup, pass the values in as constructor parameters, or use an explicit init method the caller runs after construction.

Key takeaways
  • Encapsulation is about invariants. Ask "what can a caller break?" not "are my fields private?"
  • A read-only collection property is still mutable if the items themselves are mutable.
  • Inheritance is a promise of substitutability. If a subclass throws or restricts, the design is wrong.
  • Interface = capability, many allowed. Abstract class = family with shared state, one allowed.
  • new makes behaviour depend on the variable's declared type. Treat it as a bug.
  • sealed lets the JIT devirtualize — but seal for design reasons, not performance.
  • Virtual calls in constructors run against a half-initialised object.

Common mistakes

  • Public setters everywhere, then enforcing the rules in services. The object can't defend itself.
  • Exposing List<T> and thinking a private setter protects it.
  • Deep hierarchies (4+ levels). To understand one method you open five files.
  • Inheriting to reuse one helper method. Composition or a static method does it without the substitutability promise.
  • Method hiding with new, giving behaviour that depends on the variable type.
  • Interfaces that exist only to be mocked, mirroring one class exactly.
  • Anaemic entities — properties only, all behaviour in XManager classes.

Best practices

  • Expose behaviour, not state. If two fields must change together, that's one method.
  • Make concrete classes sealed by default. Open them for inheritance deliberately.
  • Construct objects valid — required data in the constructor, no half-built states.
  • Use record with init for value-like types.
  • Keep hierarchies shallow. Two levels is usually plenty.
  • Name types after the domain (PricingPolicy), not after patterns (PricingStrategyImpl).

Interview questions

Basic

Explain encapsulation, and show me where it's commonly violated.
How I'd answer

"Encapsulation means the object owns its own state and the rules that keep it valid. Access modifiers are just how you do it — the point is that no caller can put the object into a state that shouldn't exist."

"The violation I see most is a class that looks encapsulated because everything is a property, but every property has a public setter. Take an Order with a settable Total and Status. Now the rule 'total equals the sum of the lines' lives nowhere. Every service has to re-implement it, and one of them won't."

"The fix is to expose operations. AddLine keeps the total consistent. Ship sets the status and the timestamp together and rejects the transition if the order isn't paid."

"There's a subtler C# one too: if you expose a List<T>, a private setter doesn't help — callers can still add and remove. It needs to be IReadOnlyList<T> over a private backing list."

What they're really checking
  • Do you know the purpose, or just the syntax?
  • Have you hit the mutable-collection leak in real code?
Weak answers
  • Red flag: "make fields private and add getters and setters." That's a data bag, not encapsulation.
Likely follow-ups
  • How do you encapsulate an entity that EF Core has to materialise?
  • Does encapsulation conflict with serialization?

Intermediate

Abstract class or interface — how do you choose?
How I'd answer

"My default is an interface. It keeps the type substitutable, allows multiple implementations, and doesn't use up the single base-class slot."

"I go to an abstract class when there's real shared implementation and shared state. For example a message handler base that owns the retry counting and logging, while each subclass only implements the actual handling."

"The way I think about it: an interface is a capability — something unrelated types might have, like IDisposable. An abstract class is membership in a family that shares mechanics."

"There's also a versioning angle that matters for shared libraries. Adding a member to an abstract class is fine because you provide the implementation. Adding one to an interface breaks every implementer — which is exactly why default interface methods were added in C# 8. In practice I often use both: an interface for the contract, plus an abstract base with the common implementation."

What they're really checking
  • Can you give selection criteria, not just a feature comparison?
  • Do you know the versioning implication? That's the practical difference in library design.
Likely follow-ups
  • What are default interface methods actually for?
  • Can an abstract class implement an interface without implementing its members?
What's the difference between virtual/override and new?
How I'd answer

"virtual plus override is real polymorphism. The method is picked at runtime based on the actual type of the object, so a base-typed variable holding a derived instance calls the derived version."

"new is method hiding. It declares a separate method that happens to share a name, and the call is resolved at compile time from the variable's declared type."

"So with new, the same object behaves differently depending on how the variable is declared. A Notifier variable holding an EmailNotifier calls the base method; cast it to EmailNotifier and you get the derived one. Two call sites that look identical, two different results."

"The only case I'd accept it is deriving from a base class I don't control that exposes a non-virtual member. In a review, if I see new, I assume it's a mistake until someone explains otherwise."

What they're really checking
  • Do you understand compile-time vs runtime resolution?
  • Can you explain why it's dangerous, not just what it does?
Likely follow-ups
  • What does sealed override mean, and why write it?
  • How does the runtime dispatch a virtual call?
  • Why is calling a virtual method from a constructor dangerous?

Advanced

How does virtual dispatch work, and what does sealed have to do with performance? ⭐ Senior-level
How I'd answer

"Every object carries a pointer to its type's method table. A non-virtual call is a direct call because the compiler knows the target. A virtual call has to load that table from the object and call through the right slot, so the object's real type decides which code runs. Interface calls add one more step, because the runtime maps the interface slot onto the concrete type's implementation."

"The performance story is mostly about inlining rather than the extra indirection. The JIT can't inline a call it can't resolve, and inlining is what unlocks most other optimisations. Modern .NET does guarded devirtualization — it inlines the type it sees most often and guards it with a type check that falls back if something else turns up."

"sealed helps because the JIT can prove there's no further override, so it can devirtualize unconditionally. That's why performance-sensitive framework types are often sealed."

"I'd be careful how much weight I put on that though. In normal application code the difference isn't measurable. I seal classes for design reasons — I haven't designed them for inheritance, and sealing lets me change internals later without breaking someone."

What they're really checking
  • Does your knowledge go below the language into the runtime?
  • Do you keep performance claims proportionate, or cargo-cult micro-optimisations?
Likely follow-ups
  • Why aren't struct methods virtual? What happens when a struct implements an interface?
  • What's the boxing cost in that case?
Design a payment system supporting card, bank transfer and wallet.
How I'd answer

"First I'd figure out what actually varies. All three need authorise, capture and refund. But they differ in timing — a card authorisation is immediate, a bank transfer can settle days later, a wallet may need a balance check first. That timing difference is the important constraint and it's easy to miss."

"So I'd define one interface — IPaymentGateway with authorise, capture, refund — and implement it per method. I'd avoid a shared base class at first, because the common parts are usually cross-cutting things like retry, logging and idempotency, and those work better as decorators wrapping each implementation."

"For the async case, I would not hide the waiting inside the method — that gives you a method that sometimes blocks for days. Instead the result type is explicit: Authorized, Pending, Declined, Failed. Pending means the caller stores state and reacts to a webhook later. That way no implementation has to lie to satisfy the interface, which is really the Liskov concern."

"And I'd make sure every call carries an idempotency key. Retries are guaranteed in payments, and double-charging is the failure that actually costs you."

What they're really checking
  • Do you find the real axis of variation, or reach for a hierarchy?
  • Do you notice that async settlement breaks a naive uniform interface?
  • Does idempotency occur to you without being prompted?
Weak answers
  • Red flag: an abstract PaymentBase with three subclasses and no discussion of what varies.
  • Red flag: throwing exceptions for declined payments. A decline is an expected outcome, not an exceptional one.
Likely follow-ups
  • How do you add a fourth method without touching existing code?
  • Where do you enforce idempotency — gateway, your service, or the database?
  • How would you test this without hitting the real providers?
