Advanced OOP & Design Quality

The layer past the four pillars: how objects relate, how designs rot, and what makes code cheap to change.

🟡 Intermediate 🔴 Advanced ⭐ Senior-level
Quick revision
  • Inheritance is fixed at compile time and gives you everything. Composition is chosen at runtime and gives you only what you asked for.
  • Coupling = how much A must know about B. Cohesion = how related the parts inside A are. Want: low coupling, high cohesion.
  • Liskov: a subclass must work anywhere the base works. No stricter inputs, no weaker guarantees, no new exceptions.
  • Immutability kills a whole class of bugs — shared references, ordering bugs, thread safety.
  • Default immutable for values. Entities with a lifecycle stay mutable, but only through methods that enforce the rules.
  • An anaemic domain model is fine for CRUD and a real problem for complex rules. Know which one you're building.

Composition over inheritance 🔥 Must know

In simple terms

Inheritance = "my class is that thing, so it gets everything."

Composition = "my class has that thing, and only uses what it needs."

Think of it this way

Inheritance is being born into a family — you get the whole surname, history and obligations, and you can't pick which parts.

Composition is hiring specialists. You choose exactly who you need, you can swap them, and you can hire two at once.

Remember this

Use inheritance for "can be used instead of". Use composition for "reuses" or "varies".

Everyone repeats the slogan. The reason behind it is what gets tested.

Why inheritance is a heavy commitment:

  • You depend on the whole base class — public members, protected members, state, and its unwritten behavioural rules.
  • That dependency is fixed at compile time. It can't vary per instance.
  • It's transitive. A change three levels up reaches you.

That last point has a name: the fragile base class problem. A change that's correct in isolation breaks subclasses that relied on the old behaviour — including behaviour nobody documented.

Watch inheritance fail

Two report formats, two cross-cutting concerns. With inheritance:

public abstract class ReportGenerator             { public abstract byte[] Generate(); }
public class PdfReport             : ReportGenerator { }
public class CachedPdfReport       : PdfReport       { }   // caching
public class LoggedPdfReport       : PdfReport       { }   // logging
public class CachedLoggedPdfReport : CachedPdfReport { }   // both - logging duplicated
public class ExcelReport           : ReportGenerator { }
public class CachedExcelReport     : ExcelReport     { }   // caching duplicated

Six classes already, with logging written twice and caching written twice. Add a third concern and it's unmanageable.

The root error: you're using a single-axis mechanism to model several independent axes (format × caching × logging).

The composition version

public interface IReportGenerator
{
    Task<byte[]> GenerateAsync(ReportRequest request, CancellationToken ct);
}

public sealed class PdfReportGenerator : IReportGenerator { /* just formatting */ }

public sealed class CachingReportGenerator(IReportGenerator inner, IDistributedCache cache)
    : IReportGenerator
{
    public async Task<byte[]> GenerateAsync(ReportRequest request, CancellationToken ct)
    {
        var key = request.CacheKey();
        if (await cache.GetAsync(key, ct) is { } hit) return hit;

        var bytes = await inner.GenerateAsync(request, ct);
        await cache.SetAsync(key, bytes, ct);
        return bytes;
    }
}

Now caching exists once and wraps anything implementing the interface. Logging is another wrapper. You compose them at registration:

services.AddScoped<IReportGenerator>(sp =>
    new LoggingReportGenerator(
        new CachingReportGenerator(
            new PdfReportGenerator(),
            sp.GetRequiredService<IDistributedCache>()),
        sp.GetRequiredService<ILogger<LoggingReportGenerator>>()));

This is the Decorator pattern, and it's the best concrete answer to "give me an example of composition over inheritance".

You also get something inheritance can't give you: the composition is a runtime decision. Caching in production, none in tests — no new classes.

Trade-off

Composition isn't free. More types, an extra frame in every stack trace, and the wiring lives away from the logic. For a single implementation with no variation, a plain method or a small base class is simpler and clearer.

Association, aggregation, composition 🟢 Beginner 💡 Good to know

These come up in UML-flavoured questions. The thing that actually matters in code is who owns the lifetime.

RelationshipMeansLifetimeExample
Association"uses" / "knows about"IndependentOrder.Customer — the order didn't create the customer
Aggregation"has-a", sharedPart outlives the wholeTeam.Members — deleting the team doesn't delete the people
Composition"owns", exclusivePart dies with the wholeOrder.Lines — a line means nothing without its order

This isn't academic. It maps directly onto aggregate design and onto cascade-delete decisions in your schema. If deleting the parent should delete the child, that's composition — and the child probably shouldn't be reachable from elsewhere in the system.

Coupling and cohesion 🔥 Must know

In simple terms

Coupling is between classes: how much A has to know about B.

Cohesion is inside one class: how well its parts belong together.

You want low coupling, high cohesion.

Think of it this way

Cohesion is how tidy one drawer is — a drawer of only cutlery is cohesive; the "junk drawer" isn't.

Coupling is how many drawers you must open to make one cup of tea. If it's five, something is wrong with the kitchen.

Coupling — worst to best

TypeLooks likeWhy it hurts
ContentOne module reaches into another's internalsNothing is safe to refactor
CommonShared mutable static stateInvisible dependencies, order-dependent bugs, untestable
ControlPassing a flag that switches behaviour: Process(order, isRush: true)Caller must know the callee's branches. Usually two methods in disguise
StampPassing a whole object when two fields would doCouples you to a type you didn't need; harder to test
DataPassing exactly what's neededFine — this is normal collaboration
MessageTalking via events, no direct referenceLoosest — but you pay in indirection and eventual consistency

Two things worth saying in an interview:

  • Coupling isn't the enemy. A system with zero coupling does nothing. The goal is that dependencies point at stable things, not volatile ones.
  • "Loosely coupled" ≠ "has interfaces". If IOrderService has twelve methods and one implementation, you haven't reduced coupling. You've added a file.

Cohesion

Cohesion asks whether the things inside a class belong together. Easy test:

Do the methods use the same fields?

If methods 1–4 touch fields A and B, and methods 5–9 touch C and D, that's two classes sharing a name.

The weakest form you'll meet constantly is the Helpers / Utils / Common class. Its members share nothing but a namespace. It attracts more unrelated code over time, everything ends up depending on it, and it becomes the hardest file in the codebase to change.

Senior signal

Connect cohesion to rate of change: things that change together should live together. That's the real content of SRP, and it's a much more useful test than "does this class do one thing" — which is unfalsifiable, because "one thing" can be defined at any size you like.

Liskov substitution, practically 🔴 Advanced

Formally: a subtype must be usable anywhere the base type is expected. In practice, three rules cover almost every real violation:

  1. Don't make the inputs stricter. If the base accepts any positive quantity, an override that rejects over 100 breaks callers.
  2. Don't weaken the guarantees. If the base promises a saved entity has an ID, an override that sometimes doesn't assign one breaks callers.
  3. Don't add new failure modes. Throwing NotSupportedException from an inherited method is the obvious one.
public class FileStorage
{
    // Contract: returns the stored file's URI. Throws only on IO failure.
    public virtual Task<Uri> SaveAsync(Stream content, string name) => ...;
}

public class ReadOnlyArchiveStorage : FileStorage
{
    public override Task<Uri> SaveAsync(Stream content, string name)
        => throw new NotSupportedException("Archive storage is read-only.");
}

Now correct code written against FileStorage blows up for one subtype — and only when configuration happens to point at it.

The fix is to stop pretending. Split the interface:

public interface IReadableStorage { Task<Stream> ReadAsync(string name, CancellationToken ct); }
public interface IWritableStorage { Task<Uri> SaveAsync(Stream content, string name, CancellationToken ct); }

// The archive implements only IReadableStorage.
// Code that needs to write can only be handed something that can write.

That's Interface Segregation solving a Liskov problem. Worth pointing out in an interview — it shows the SOLID principles interlock instead of being a list.

How to spot LSP violations in review

Look for if (x is SomeSubclass) at call sites, or a try/catch around a polymorphic call. If callers have to know which concrete type they're holding, the abstraction has stopped abstracting.

Immutability 🟡 Intermediate

One line: if it can't change after construction, a whole category of bugs becomes impossible.

What you get:

  • No aliasing surprises — nobody can change your object behind your back.
  • No temporal coupling — no "you must call Initialize() first".
  • Thread-safe for free, no locking.
  • Validate once in the constructor, and an invalid instance can't exist anywhere.
public readonly record struct Money(decimal Amount, string Currency)
{
    public Money
    {
        if (Amount < 0) throw new ArgumentOutOfRangeException(nameof(Amount));
        if (Currency?.Length != 3) throw new ArgumentException("ISO 4217 code required");
    }

    public Money Add(Money other)
    {
        if (other.Currency != Currency)
            throw new InvalidOperationException($"Cannot add {other.Currency} to {Currency}.");
        return this with { Amount = Amount + other.Amount };
    }
}

Three things doing real work here:

  • Validation in the constructor → an invalid Money can't exist.
  • Records give value equality free — two instances of 10 GBP are interchangeable, which is exactly right for a value.
  • Currency mismatch is caught by the type, not by a caller remembering. That bug otherwise reaches production as a silently wrong total.
Trade-off

Every "change" allocates a new object. Trivial for small values — readonly record struct avoids the heap entirely. It can matter for large graphs mutated in a loop; there, use a mutable builder locally and freeze at the end. Entities with a real lifecycle normally stay mutable, but only through methods that enforce the rules.

Object lifetime 🟡 Intermediate

The GC handles memory. What you have to think about is how long an object should be useful — which in ASP.NET Core is the DI lifetime question.

LifetimeMeansThe danger
TransientNew instance every time it's resolvedExpensive if construction is costly
ScopedOne per requestInjecting it into a singleton captures it forever — the captive dependency bug
SingletonOne per applicationMust be thread-safe. Must not hold per-request state

Objects owning scarce resources — file handles, sockets, DB connections — need IDisposable and using, because the GC gives you no timing guarantee. Details in memory & GC and DI lifetimes.

Law of Demeter 💡 Good to know

// Coupled to Order, Customer, Address AND Country - four types in one line.
var rate = TaxTable.For(order.Customer.Address.Country.Code);

// The order answers a question about itself.
var rate = order.TaxRate();

The first version breaks if any link in the chain changes — including one becoming nullable.

The related smell is feature envy: a method that mostly manipulates another object's data probably belongs on that object.

Common mistake

Applying Demeter mechanically by adding wrappers like order.GetCustomerAddressCountryCode(). That just moves the coupling and adds noise. Move the behaviour, not the getters. (And note: LINQ and fluent APIs aren't violations — they operate on values from the same object, not navigation through unrelated types.)

The anaemic domain model debate ⭐ Senior-level

Anaemic = entities are property bags, all the logic sits in service classes. Very common in .NET, partly because ORMs and serializers push you that way.

The honest position: it's a trade-off, not a universal error.

Anaemic is fine when

The logic is validation and mapping. CRUD apps, internal tools, reporting. A rich domain model there is ceremony with no payoff.

Anaemic hurts when

There are real invariants and state machines — pricing, entitlements, policies, order lifecycles. Rules get scattered, implemented three ways, and the entity can always be made invalid.

The tell that you chose wrong: services called OrderManager full of if (order.Status == ...) checks repeated across files — and bugs whose fix is always "we forgot to check X in this one path".

Key takeaways
  • Inheritance for substitutability; composition for reuse and variation.
  • The decorator example is the strongest concrete answer for "composition over inheritance".
  • Coupling should point at stable things. Interfaces alone don't reduce coupling.
  • Cohesion test: do the methods use the same fields? Change-together = live-together.
  • LSP violations announce themselves as type checks and try/catch at call sites.
  • Immutable for values, mutable-but-guarded for entities.
  • Anaemic models are a real choice — judge by how many invariants exist.

Common mistakes

  • Deep hierarchies built for reuse. Understanding one method means opening five files.
  • Utils / Helpers classes. Zero cohesion, maximum inbound coupling.
  • Boolean flag parameters that switch behaviour. Two well-named methods are almost always better.
  • Passing whole entities to methods that need one field, coupling unrelated modules to your model.
  • Shared mutable state across threads with no synchronisation — see concurrency.
  • An interface per class, reflexively, with no second implementation.
  • Overriding Equals without GetHashCode, so objects vanish from dictionaries.

Interview questions

Why prefer composition over inheritance? Give a concrete example.
How I'd answer

"Because inheritance couples you to the whole base type, permanently, along one axis. Composition lets you depend on only what you need and vary it at runtime."

"The failure I've actually hit is the combinatorial one. You have report formats — PDF, Excel, CSV — and cross-cutting concerns like caching, logging and authorisation. With inheritance you get a class per combination, and each concern gets implemented more than once, because a class can only have one base."

"With composition each concern is a decorator implementing the same interface and wrapping an inner instance. Caching is written once. They compose in any order at registration. And I can vary it per environment — caching in production, none in tests — with no new types."

"The other reason is the fragile base class problem. Changing a base can break subclasses in ways the compiler can't catch, because subclasses depend on implicit behaviour — what order methods call each other in, what state is valid when a protected member runs. Composition has no hidden contract; you only depend on the published interface."

"I wouldn't state it as absolute, though. Inheritance is right when you need real substitutability, when a framework requires it, or for template method where a base owns the algorithm. My rule is: inheritance for 'can be used instead of', composition for 'reuses' or 'varies'."

What they're really checking
  • Can you give a concrete example rather than the slogan?
  • Do you know the fragile base class problem by mechanism?
  • Do you still know when inheritance is right?
Weak answers
  • Red flag: "inheritance is bad" with no counter-case.
  • Red flag: "composition is more flexible" with no example of that mattering.
Likely follow-ups
  • How do you register a decorator chain in the built-in .NET DI container?
  • What's the downside of five decorators wrapping one service?
What is tight coupling, and how would you find it in a codebase you just joined?
How I'd answer

"Tight coupling means one component depends on another's details, so changing one forces changing the other. The versions that hurt most are depending on concrete types you can't substitute, shared mutable static state, and reaching through object graphs into things you were never given."

"Joining a codebase, the fastest signal is the tests. If a unit test needs a database or fifteen lines of mock setup to construct one class, that class is tightly coupled — the test is telling you what the real dependencies are."

"Other quick tells: static access to DateTime.Now or a service locator, because those are dependencies that don't appear in any signature. Constructors with more than about five parameters, which usually means several responsibilities. And long navigation chains."

"For fixing it I'd be strategic rather than exhaustive. Coupling only costs you where change happens, so I'd look at which files change most and which areas generate defects, and start there. The first moves are usually safe and mechanical: inject hidden dependencies, replace static state with an abstraction, pass the data a method needs instead of whole objects."

"I'd also avoid over-correcting. Adding an interface for everything isn't decoupling. If there's one implementation and no seam anyone needs, you've added indirection without removing a dependency. My test is whether the abstraction lets something actually vary — a second implementation, a simpler test double, or a boundary you want to defend."

What they're really checking
  • Do you diagnose from evidence, or assert principles?
  • Do you prioritise by change frequency?
  • Do you know interfaces aren't automatically decoupling?
Likely follow-ups
  • How do you make DateTime.Now testable without an interface for everything?
  • Is a shared DTO between two services coupling? Does it matter?
When would you make a type immutable, and when would you not?
How I'd answer

"I default to immutable for anything value-like — money, date ranges, addresses, IDs, config, DTOs, anything crossing a thread boundary."

"The reasons are concrete. Nobody can change it underneath me, which removes a whole class of aliasing bugs. It's thread-safe with no locking. It can be cached and shared safely. And validating in the constructor means an invalid instance can't exist anywhere, so I check once instead of defensively everywhere."

"Where I wouldn't is entities with identity and a lifecycle. An Order exists over time and moves through states. Making a new object per change means updating every reference, and it fights the ORM, which tracks identity and mutation. There I'd keep it mutable but only through methods that enforce the rules."

"I'd also skip it where the cost is real — building a large structure in a loop, or a hot path where per-iteration allocation shows up in a profile. The answer there is a mutable builder that produces an immutable result, or readonly record struct for small values so there's no heap allocation at all."

What they're really checking
  • Can you name the specific bug classes it removes?
  • Do you know its cost and the builder escape hatch?
  • Do you distinguish values from entities?
Likely follow-ups
  • What does with actually do — deep or shallow copy?
  • Is a record with a List<T> property immutable?
  • Why does readonly record struct matter for performance?
Is an anaemic domain model an anti-pattern? ⭐ Senior-level
How I'd answer

"It depends on how much behaviour the domain actually has, and I'd push back on treating it as universally wrong."

"For a system whose logic is validation, mapping and CRUD — a lot of internal tooling is like this — entities as data plus straightforward services is simpler and maps cleanly onto the ORM and the API contracts. Forcing a rich domain model there adds ceremony with no benefit."

"Where it genuinely breaks down is systems with real invariants and state transitions — pricing, entitlements, insurance policies, order lifecycles. Then the rules live in services, so the same rule ends up written three ways with subtle differences, and the entity can always be put into an invalid state because nothing owns its consistency. The bugs have a recognisable shape: 'we forgot to check the status in this one path'."

"So the question I ask is: are there rules that must hold no matter which code path touches this? If yes, they belong on the object, because that's the only place they can't be bypassed. And it's not binary — most real systems are anaemic in the CRUD areas and rich in the two or three places where the actual complexity lives. That's a reasonable outcome, not an inconsistency to fix."

What they're really checking
  • Do you hold nuanced positions, or repeat received opinions?
  • Can you name the specific failure mode instead of saying "it's not OO"?
Weak answers
  • Red flag: "yes, always, you should use DDD" — dogma with no cost analysis.
  • Red flag: not knowing the term.
Likely follow-ups
  • How do you keep a rich domain model working with EF Core?
  • Where does validation live — the entity, the request model, or both?
