Your production debugger. Also, if you're careless with it, one of the larger lines on the bill.

Senior signal — dependencies are the most useful and least used

Most teams look at requests and exceptions. The dependencies table is where the answers usually are.

It records every outgoing call — each SQL query, HTTP request, Service Bus operation and Redis command — with its duration, success and target. Automatically, with no code.

So "the endpoint takes 3 seconds" becomes answerable: one dependency shows 2.8 seconds and it's a specific SQL query, or there are 400 dependency records for one request, which is an N+1.

That second case is the one worth knowing: counting dependencies per operation finds N+1 problems that no single slow query would reveal — each call is 2ms and there are four hundred of them. Nothing in the request telemetry shows that; the dependency count does.

Instrumenting with OpenTelemetry 🔥 Must know

builder.Services.AddOpenTelemetry()
    .UseAzureMonitor(o =>
    {
        o.ConnectionString = builder.Configuration["ApplicationInsights:ConnectionString"];
        o.SamplingRatio = 0.2f;              // 20% - see the cost section
    })
    .WithTracing(t => t
        .AddAspNetCoreInstrumentation()      // incoming requests
        .AddHttpClientInstrumentation()      // outgoing HTTP, with context propagation
        .AddSqlClientInstrumentation(s => s.SetDbStatementForText = true))
    .WithMetrics(m => m
        .AddAspNetCoreInstrumentation()
        .AddRuntimeInstrumentation());       // GC, thread pool, exceptions

// Enrich every telemetry item with the things you'll want to filter by
builder.Services.AddSingleton<ITelemetryInitializer, TenantEnricher>();
Why OpenTelemetry rather than the App Insights SDK

The classic SDK works and couples your instrumentation to Azure. OpenTelemetry is now Microsoft's recommended path, and the reason is portability: you instrument once against a vendor-neutral standard and export to App Insights.

If you later add Grafana, or move to Datadog, or run a service in another cloud, you change the exporter rather than reinstrumenting the application.

It also standardises trace context propagation across languages, which matters in a polyglot estate — a Node service and a .NET service produce traces that join up correctly.

The practical caveat: some App Insights features are still richer through the native SDK, and a few instrumentation libraries lag. So it's worth checking that the specific dependency you care about — a particular Azure SDK, EF Core — is instrumented before assuming full coverage.

Senior signal — enrich telemetry with the dimension you'll filter by

The single highest-value customisation is adding your own dimensions to every telemetry item — most importantly tenant id, and often user id, feature flag state or API version.

Because the first question in any incident is "is this one customer or everyone?", and without a tenant dimension you cannot answer it. You end up correlating timestamps against support tickets.

A telemetry initialiser adds it once, globally, rather than per log statement. Then every request, dependency, exception and trace carries it and every KQL query can filter or group by it.

Do it early. Retrofitting means you can't investigate anything historical by tenant, and it's exactly the dimension you'll want during the first serious incident. Same reasoning as per-tenant observability.

One caution: enrich with identifiers, never with data. A telemetry item containing another customer's record is itself a leak, and telemetry is usually readable by more people than the database.

Cost, and the sampling trade 🔥 Must know

The billing model

You're billed per GB of telemetry ingested. Not per request, not per instance — per gigabyte of data sent.

Which means logging volume is a cost decision, and on a busy application it can exceed what you're paying for the compute that generated it.

Senior signal — sampling keeps traces whole, and that's the important part

Naive sampling would drop individual telemetry items, which would leave you with a request whose dependencies are missing — useless for investigation.

App Insights sampling is consistent across an operation: it hashes the operation_Id, so if a request is sampled in, all its dependencies, traces and exceptions come with it. You get complete traces for a subset of operations rather than fragments of all of them.

Which makes the trade clear: you lose the ability to find a specific individual request, but the ones you keep are fully diagnosable.

Two things to know. Sampling affects counts — App Insights scales them by itemCount to compensate, so aggregate figures remain roughly right, but exact counts and rare events become unreliable. And you can exclude exceptions from sampling, which is usually the right choice: sample the successful requests heavily, keep every failure.

"Sample aggressively on success, never on exceptions" is a good concrete answer.

// A processor drops telemetry client-side, so you don't pay to send it
public sealed class HealthCheckFilter(ITelemetryProcessor next) : ITelemetryProcessor
{
    public void Process(ITelemetry item)
    {
        // Health probes fire constantly and tell you nothing
        if (item is RequestTelemetry r &&
            r.Url?.AbsolutePath.StartsWith("/health", StringComparison.OrdinalIgnoreCase) == true &&
            r.Success == true)
        {
            return;                      // dropped - never transmitted
        }

        next.Process(item);
    }
}
Set a daily cap, and understand what it does

A daily ingestion cap prevents a runaway bill — a logging loop or a traffic spike can otherwise generate an enormous amount of telemetry.

The consequence is blunt: once the cap is hit, telemetry is discarded for the rest of the day. So you're blind exactly when something unusual is happening, which is when you most need visibility.

So a cap is a financial safety net, not a cost strategy. Set it well above normal volume, alert when you approach it, and control cost through log levels, filtering and sampling instead.

The failure mode to avoid: a cap set close to normal usage, hit during an incident, so the incident is undiagnosable.

KQL, practically 🔥 Must know

// Slowest endpoints by p95
requests
| where timestamp > ago(24h)
| summarize p50 = percentile(duration, 50),
            p95 = percentile(duration, 95),
            count() by name
| order by p95 desc

// Failure rate per endpoint
requests
| where timestamp > ago(1h)
| summarize total = count(),
            failed = countif(success == false) by name
| extend failureRate = round(100.0 * failed / total, 2)
| where failureRate > 1
| order by failureRate desc

// N+1 detection: operations making an unusual number of dependency calls
dependencies
| where timestamp > ago(1h)
| summarize calls = count() by operation_Id, operation_Name
| where calls > 50
| summarize operations = count(), avgCalls = avg(calls) by operation_Name
| order by avgCalls desc

// Everything for one trace - the incident-investigation query
union requests, dependencies, exceptions, traces
| where operation_Id == "abc123..."
| project timestamp, itemType, name, message, duration, success
| order by timestamp asc

// Errors grouped by tenant - only possible if you enriched telemetry
exceptions
| where timestamp > ago(6h)
| extend tenant = tostring(customDimensions.TenantId)
| summarize count() by tenant, type
| order by count_ desc
The two queries that earn their keep

The union ... where operation_Id query is the one to remember. Given a trace id from an error response, it returns every request, dependency, exception and log line for that one operation, in order — across services. That's the distributed stack trace you don't otherwise have.

Which is why returning the trace id to the client matters so much: a user quotes a reference and you retrieve the complete picture rather than searching by timestamp.

The dependency-count query finds N+1 problems, which are invisible in request telemetry because each call is fast. An operation making 400 dependency calls is a problem no percentile on requests would reveal.

Both are worth saving as workbook queries so they're available during an incident rather than being written under pressure.

Percentiles, not averages

An average hides the distribution. A 200ms average can be 90% of requests at 50ms and 10% at 1.5 seconds — and the 10% is what users complain about.

So percentile(duration, 95) and percentile(duration, 99) are the numbers that describe experience. p50 alongside them shows the spread.

Same reasoning applies to alerting: alerting on average latency misses the case where a minority of requests are terrible, which is the more common failure shape.

Trace context doesn't cross a message broker by itself

HTTP calls propagate traceparent automatically, so a chain of service calls joins up without effort.

A message publish does not, unless the library adds it. So without handling, the trace ends at "published a message" and the consumer's work appears as an unrelated root trace — and correlating them means matching timestamps and guessing.

That's precisely where the hard bugs live, because asynchronous flows are the ones you can't reason about by reading code.

The Azure SDKs and MassTransit handle this now. It's worth verifying on a real trace rather than assuming: publish a message, consume it, and confirm both appear under one operation_Id. If they don't, put traceparent in the message headers and restore it in the consumer.

Alerting ⭐ Senior-level

Alert onDon't alert on
Failure rate above a threshold — users are affectedEvery individual exception
p95 latency degradationA single slow request

Queue depth or consumer lag growingMomentary queue depth
Dead-letter queue depth > 0—

Senior signal — alert on symptoms, and the business metric is the best one

The failure mode of alerting is volume. Alert on every exception and within a month nobody reads them, so the one that mattered is missed. An ignored alert is worse than no alert, because it creates a false sense of coverage.

So alert on things a user would notice: elevated failure rate, degraded p95, availability tests failing.

The most valuable alert though is usually a business metric that stopped. "No orders completed in the last hour" catches an enormous range of failures — a broken payment integration, a failed deployment, a full database, a certificate expiry — including ones you didn't anticipate and have no specific alert for.

Technical alerts detect known failure modes. A business-metric alert detects unknown ones, which is strictly more valuable and much rarer to find configured.

It needs care with normal variation — quiet periods overnight, weekends — so it's usually a comparison against the same period last week rather than a fixed threshold.

Key takeaways
  • Requests, dependencies, exceptions, traces, custom events — dependencies are the most underused.
  • Counting dependencies per operation is how you find N+1 problems.
  • Instrument with OpenTelemetry and export to App Insights.
  • Enrich every item with tenant id — identifiers only, never data.
  • Billed per GB ingested; log levels, filtering and sampling are cost controls.
  • Sampling is consistent per operation_Id, so traces stay whole.
  • Sample success heavily, keep every exception.
  • A daily cap is a financial safety net that blinds you when it triggers.
  • The union ... operation_Id query is your distributed stack trace.
  • Percentiles, not averages.
  • Trace context doesn't cross a broker automatically — verify it.
  • Alert on user-visible symptoms; a stopped business metric catches unknown failures.

Common mistakes

  • Verbose framework logging in production, dominating ingestion cost.
  • Logging request and response bodies — expensive and a data-protection risk.
  • Health checks recorded as requests, inflating volume and skewing metrics.
  • No tenant enrichment, so incidents can't be scoped to a customer.
  • Sampling exceptions away, losing the rare failures.
  • A daily cap set near normal volume, so it triggers during incidents.
  • Alerting on every exception until nobody reads alerts.
  • Alerting on averages rather than percentiles.
  • Assuming trace context crosses the message broker.
  • No trace id returned to clients, so support tickets can't be correlated.
  • Only looking at requests and exceptions, ignoring dependencies.

Interview questions

Intermediate

An endpoint is slow in production. How do you find out why? 🔥 Must know
How I'd answer

"I'd start in Application Insights and work from the aggregate to the specific, rather than guessing."

"First, confirm and characterise it with a KQL query on requests — percentiles by endpoint name, not averages. An average hides the distribution: 200ms average could be 90% at 50ms and 10% at 1.5 seconds, and the 10% is what users complain about. So p50, p95 and p99, and whether it's all requests or a tail."

"Then I'd look at the dependencies table for that operation, which is where the answer usually is. It records every outgoing call — SQL, HTTP, Service Bus, Redis — with duration and success, automatically."

"Two shapes to look for."

"One slow dependency. If a single SQL query is 2.8 seconds of a 3-second request, that's the answer and I'd take the query to an execution plan."

"Many fast dependencies. This is the one people miss. If there are 400 dependency records for one operation, each 2ms, that's an N+1 — and no percentile on requests would reveal it, because nothing is individually slow. I'd find it by summarising dependency count per operation_Id."

"For a specific slow request I'd use the end-to-end transaction view, or the KQL equivalent — a union across requests, dependencies, exceptions and traces filtered by operation_Id. That gives the full waterfall in order, including across services if it's distributed. That's the distributed stack trace you don't otherwise have."

"If the dependencies don't account for the time, then it's in-process — CPU work, serialisation, or contention. I'd check the runtime metrics for thread pool starvation and GC pressure, both of which produce latency that doesn't appear in any dependency. Thread pool starvation from sync-over-async is a classic cause of exactly this pattern: nothing slow, everything queued."

"I'd also check whether it's always slow or only sometimes, because the causes differ. Intermittent points at cold start, a specific instance, lock contention, or parameter sniffing in SQL. Consistently slow points at the code path itself."

"And I'd scope it by dimension — is it one tenant or everyone? Which is only answerable if telemetry was enriched with tenant id, and is the reason to do that early. One tenant being slow usually means their data volume exposed a missing index."

"One caveat on the data: if sampling is on, a specific request may not have been captured. Sampling is consistent per operation so the ones I do have are complete, but I can't necessarily find one particular user's request from an hour ago. Worth knowing before concluding the telemetry is broken."

What they're really checking
  • Do you use percentiles rather than averages?
  • Do you go to the dependencies table?
  • Do you know how to spot N+1 in telemetry?
  • Do you consider in-process causes when dependencies don't explain it?
  • Do you scope by tenant, and know sampling affects what you can find?
Weak answers
  • Red flag: "add more logging" as the first step.
  • Red flag: looking only at average duration.
  • Red flag: no mention of dependencies.
Likely follow-ups
  • Write the KQL for that.
  • How would you confirm thread pool starvation?
  • What if the slow dependency is a third-party API?

Advanced

Your Application Insights bill is larger than your compute bill. What do you do? ⭐ Senior-level
How I'd answer

"That's common and entirely fixable. App Insights is billed per GB ingested, so this is a volume problem — and I'd find out what's generating the volume before changing anything."

"There's a KQL query for it: group by itemType to see the split between traces, dependencies, requests and exceptions, and then break down the largest category. Usually one thing dominates, and it's usually traces."

"Then, in order of impact and how safe each is:"

"Log levels. The most common cause is Information level for Microsoft.* and System.* categories — EF Core logs every query, ASP.NET Core logs routing details. Setting framework categories to Warning while keeping your own at Information often removes most of the volume immediately, and loses almost nothing you'd actually read."

"Filter obvious noise. Health-check requests firing every few seconds from the load balancer, and any successful high-frequency polling endpoint. A telemetry processor drops these client-side, so you don't even pay to transmit them."

"Sampling. The main lever. And the important property is that App Insights sampling is consistent per operation_Id — it hashes the trace id, so if a request is sampled in, all its dependencies, traces and exceptions come with it. You get complete traces for a subset of operations rather than fragments of everything."

"So I'd sample successful requests aggressively — 10 or 20% is usually plenty for diagnosing patterns — and exclude exceptions from sampling entirely. Failures are rare and individually valuable; successes are numerous and interchangeable. 'Sample success heavily, keep every exception' is the rule."

"The trade to state honestly: I lose the ability to find one specific request from an hour ago. For diagnosing patterns that's fine; for investigating a named customer's specific complaint it's a real loss. And counts become approximate — App Insights scales by itemCount so aggregates stay roughly right, but exact counts and rare-event detection get unreliable."

"Stop logging request and response bodies if that's happening. It's expensive and it's a data-protection problem — telemetry is typically readable by more people than the database."

"For longer-term control: a daily cap as a financial safety net, set well above normal volume with an alert as it's approached. I'd be explicit that a cap is not a cost strategy — once it triggers, telemetry stops for the rest of the day, so you're blind exactly when something unusual is happening. A cap set close to normal usage means undiagnosable incidents."

"And I'd consider retention: the default is 90 days, and shorter retention costs less. If nobody queries beyond 30 days, that's a straightforward saving, with an export to cheaper storage if there's a compliance reason to keep it."

"The framing I'd bring: observability has a price, and the goal isn't minimum cost — it's the right information at a defensible cost. Cutting telemetry until incidents become undiagnosable is a false economy that shows up as longer outages instead of a smaller bill."

What they're really checking
  • Do you measure what's generating volume first?
  • Do you know log levels are usually the biggest win?
  • Do you know sampling is consistent per operation?
  • Do you keep exceptions out of sampling?
  • Do you know a cap blinds you when it fires?
  • Do you frame it as value versus cost, not minimising cost?
Weak answers
  • Red flag: "turn off logging."
  • Red flag: setting a tight daily cap as the solution.
  • Red flag: sampling everything uniformly, including exceptions.
Likely follow-ups
  • What sampling rate would you pick, and how would you validate it?
  • How do you keep exceptions unsampled?
  • What would you export for long-term retention?
