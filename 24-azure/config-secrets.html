Configuration & Secrets

The goal is an application that holds no secrets at all. Managed identity is how you get there, and it's the answer to most questions in this area.

🟡 Intermediate 🔴 Advanced 🔥 Must know
Quick revision
  • Managed identity means no credential exists to leak, rotate or commit.
  • Key Vault for secrets, keys and certificates. App Configuration for settings and feature flags.
  • They're complementary — App Configuration can reference a Key Vault secret.
  • Nothing sensitive in appsettings.json, ever. It's in source control.
  • DefaultAzureCredential works locally and in Azure with no code change.
  • Rotation only works if the app re-reads — caching a secret forever defeats it.
  • Configuration order matters: later providers override earlier ones.

A committed secret is compromised, and rotating it is the only fix

Deleting a secret from a file and committing the deletion does nothing. It remains in the history, in every clone, in every fork and in every CI cache.

So the response to "we accidentally committed a connection string" is always the same: rotate the credential immediately, then clean history if you want to, in that order. History rewriting is cosmetic; rotation is the fix.

Which is the strongest practical argument for managed identity: there is no credential in the first place, so this class of incident cannot happen. You can't leak what doesn't exist.

Worth pairing with secret scanning in CI — push protection and similar — so the mistake is blocked rather than discovered afterwards.

Managed identity 🔥 Must know

What it is

Azure gives your app an identity in Entra ID. You grant that identity permission on the database, the storage account, the Key Vault.

The app asks the platform for a token at runtime. There is no secret anywhere — not in config, not in Key Vault, not in the pipeline.

System-assignedUser-assigned
LifecycleTied to the resource — deleted with itIndependent resource
SharedNo, one per resourceYes, across many resources
Recreating the resourceNew identity, so every grant must be redoneIdentity survives; grants persist
Use forSimple single-resource casesAnything with infrastructure-as-code or many instances
Senior signal — prefer user-assigned once you have IaC

System-assigned is simpler and is what most tutorials show. It has a specific operational problem: the identity dies with the resource.

So if your Terraform or Bicep ever replaces the App Service — a change that forces recreation — you get a brand-new principal id, and every role assignment on every resource it accessed silently stops applying. The app deploys successfully and then can't reach the database.

A user-assigned identity is a separate resource with a stable id, so grants survive recreation. It also lets several apps or instances share one identity, which means one set of role assignments to manage rather than one per resource.

The trade-off is honest: a shared identity is a coarser blast radius, because anything holding it has the same access. So user-assigned per logical service, not one for the whole estate.

// DefaultAzureCredential tries a chain of sources in order:
//   managed identity  ->  environment variables  ->  Azure CLI  ->  Visual Studio
// So the same code authenticates in Azure and on a developer machine.

var credential = new DefaultAzureCredential(new DefaultAzureCredentialOptions
{
    ManagedIdentityClientId = builder.Configuration["Azure:ManagedIdentityClientId"]
    // required when the resource has more than one user-assigned identity
});

builder.Configuration.AddAzureKeyVault(
    new Uri($"https://{builder.Configuration["KeyVault:Name"]}.vault.azure.net/"),
    credential);

// Data plane clients take the same credential - no keys anywhere
builder.Services.AddSingleton(new BlobServiceClient(
    new Uri("https://myaccount.blob.core.windows.net"), credential));

// Even SQL, via Entra authentication - note there is no password in this string
var sqlConnection = "Server=tcp:myserver.database.windows.net;Database=app;"
                  + "Authentication=Active Directory Default;";
Two things that reliably go wrong

Multiple user-assigned identities without specifying which. If a resource has more than one, DefaultAzureCredential cannot choose and fails — with an error that doesn't obviously say that. Set ManagedIdentityClientId explicitly whenever there could be more than one.

The credential chain differs between local and Azure. Locally it falls through to your Azure CLI login, which usually has far more permission than the app's identity. So a role you forgot to grant works on your machine and fails in Azure — the "works locally" of this feature.

The mitigation is to test against a real deployed environment rather than trusting local success, and in production to narrow the chain — disable the interactive and CLI sources so a failure is explicit instead of silently falling back to something unexpected.

Key Vault 🔥 Must know

ConceptDetail
SecretsArbitrary strings — connection strings, API keys
KeysCryptographic keys. Operations happen inside the vault; the key never leaves
CertificatesManaged lifecycle, with auto-renewal from an integrated CA
VersionsEvery update creates a version. Referencing without a version gets the current one
Soft delete + purge protectionOn by default. A deleted vault is recoverable and its name stays reserved
Access modelAzure RBAC — the modern option, over legacy access policies
Managed HSMA separate service, FIPS 140-2 Level 3, for strict compliance
RBAC rather than access policies

Key Vault has two authorisation models. Access policies are the original: vault-specific, invisible to Azure-wide tooling, and coarse — the smallest useful grant tends to be "all secrets".

Azure RBAC is the current recommendation: standard role assignments, visible in access reviews and policy tooling, assignable per individual secret, and inheritable through scope.

Use RBAC with Key Vault Secrets User for applications — read-only on secret values — and keep management roles separate. A common misconfiguration is granting Key Vault Administrator to an application because it was quicker, which lets it write and delete secrets it only needs to read.

Enable diagnostic logging too. Knowing which identity read which secret when is the audit trail you need after an incident, and it isn't on by default.

Key Vault is throttled, so treating it as a config store breaks under load

Key Vault is a secret store, not a high-throughput configuration service. Requests are limited per vault, and it's easier to reach than people expect.

If your app reads a secret per request, you'll get 429s under load — and the failure looks like the app being broken rather than a limit being hit.

The correct pattern is to load secrets at startup into IConfiguration, which caches them in memory. The Key Vault configuration provider does this for you.

That creates the tension with rotation below: caching is required for throughput and is exactly what makes rotation not take effect. Both facts are true, and the resolution is a bounded refresh interval rather than either extreme.

One consequence: a vault outage at startup means the app can't start. That's usually preferable to starting without configuration, but it makes the vault a startup dependency — so enable retry in the provider rather than failing on a transient error.

They're complementary, and the combination is the good pattern

These aren't alternatives. App Configuration can hold a Key Vault reference — the stored value is a pointer, and the .NET provider resolves it from the vault using the app's identity.

So you get one place to look for all configuration, secrets remain stored and access-controlled properly, and no secret value ever sits in App Configuration.

Add labels and one store serves every environment: the same key ConnectionStrings:Default with labels dev, staging and prod, selected by the environment name at startup.

Whether that's worth it depends on scale. For a single application, app settings plus Key Vault is simpler and cheaper. App Configuration earns its cost when several services share configuration, or when you want feature flags and dynamic refresh — that's the honest threshold.

builder.Configuration.AddAzureAppConfiguration(o =>
{
    o.Connect(new Uri(endpoint), credential)
     .Select(KeyFilter.Any, LabelFilter.Null)                      // shared defaults
     .Select(KeyFilter.Any, builder.Environment.EnvironmentName)   // environment overrides
     .ConfigureKeyVault(kv => kv.SetCredential(credential))        // resolve KV references

     // Refresh: watch ONE sentinel key, not every key
     .ConfigureRefresh(r => r
        .Register("Sentinel", refreshAll: true)
        .SetRefreshInterval(TimeSpan.FromMinutes(5)))

     .UseFeatureFlags(f => f.SetRefreshInterval(TimeSpan.FromMinutes(1)));
});

builder.Services.AddAzureAppConfiguration();   // the refresh middleware
builder.Services.AddFeatureManagement();

app.UseAzureAppConfiguration();                // must be in the pipeline or refresh never runs
Senior signal — the sentinel key makes a multi-key change atomic

If you watch every key individually, they refresh independently. So a change that updates three related settings can be observed half-applied — the app briefly runs with the new URL and the old API key.

For related settings that partial state can be worse than either version.

The sentinel pattern fixes it: watch one unrelated key with refreshAll: true. Update all the real keys first, then bump the sentinel last. The app sees a single change and reloads everything together, so the switch is atomic from its point of view.

It also cuts polling cost dramatically, because there's one key to check rather than hundreds. This is one of the details that separates "I've used App Configuration" from "I've operated it."

Rotation ⭐ Senior-level

Rotation only works if the application notices

Rotating a secret in Key Vault changes nothing for a running application that read it at startup and cached it. The app keeps using the old value until it restarts — so the rotation looks successful while the old credential is still in active use.

Worse, if the old value is revoked as part of rotation, the app breaks at an unrelated moment: the deployment weeks later that finally restarts it. That's unpleasant to debug, because nothing changed at the time it failed.

Three workable approaches:

  • Managed identity instead. Nothing to rotate. This is why it's the default answer to secret management.
  • Refresh on an interval. The Key Vault provider supports a reload interval, and App Configuration handles it via the sentinel. Bounded staleness, no restart needed.
  • Two valid credentials during rotation. Most Azure services offer primary and secondary keys precisely for this: point the app at the secondary, regenerate the primary, point back. Both are valid throughout, so no running instance ever holds an invalid credential.

That last one is the general principle and it appears everywhere: overlap the old and new credential rather than cutting over. The same shape as expand-and-contract for schema changes — add, migrate, remove, never replace in one step.

Provider ordering 🟢 Beginner

1  appsettings.json                     committed defaults
2  appsettings.{Environment}.json       committed per-environment
3  User Secrets                         local development only
4  Environment variables                container and App Service settings land here
5  Command-line arguments
6  Azure Key Vault / App Configuration  IF added after the above

   Later providers override earlier ones for the same key.
The ordering bug worth knowing

If Key Vault is added before the environment variables provider, an App Service application setting with the same name silently overrides the Key Vault value.

That produces a genuinely confusing situation: the vault holds the correct secret, the app is using something else, and everything looks correctly configured.

In .NET's default host builder the standard providers are already registered, so anything you add in Program.cs comes last and wins. That's usually what you want — but be deliberate rather than assuming, especially if you clear the sources.

Also note double underscore maps to the section separator in environment variables: ConnectionStrings__Default becomes ConnectionStrings:Default. That's how App Service settings and container environment variables reach nested configuration.

Validate configuration at startup

Bind options with ValidateDataAnnotations() and ValidateOnStart(), so a missing or malformed setting fails the application immediately with a clear message.

Without it, a missing value is null and surfaces later as a NullReferenceException deep in a request — or worse, as silently wrong behaviour, like a timeout of zero or a feature defaulting off.

Failing at startup means the deployment fails visibly, which is exactly when you want to know. Combined with a slot swap's warm-up check, a misconfigured deployment aborts the swap instead of taking the site down.

Key takeaways
  • Managed identity wherever it's supported — no credential to leak or rotate.
  • Prefer user-assigned once you have IaC, so grants survive resource recreation.
  • Specify the client id when a resource has more than one identity.
  • The local credential chain has more permission than the app's — don't trust local success.
  • Key Vault for secrets; Azure RBAC not access policies; enable diagnostic logging.
  • Key Vault is throttled — cache at startup, never read per request.
  • App Configuration for settings and feature flags; it can reference Key Vault secrets.
  • Use a sentinel key so multi-key changes apply atomically.
  • Rotation needs the app to re-read, or two valid credentials during the overlap.
  • Provider order decides who wins; environment variables use double underscore.
  • A committed secret must be rotated — deleting the file is not a fix.
  • ValidateOnStart() so misconfiguration fails the deployment, not a request.

Common mistakes

  • Connection strings in appsettings.json, committed.
  • Deleting a committed secret without rotating it.
  • Reading Key Vault per request, hitting throttling under load.
  • Rotating a secret and assuming the app picked it up.
  • Granting an app Key Vault Administrator when it only reads.
  • System-assigned identity with IaC that can recreate the resource.
  • Not setting the client id with multiple user-assigned identities.
  • Adding Key Vault before environment variables, so app settings override it.
  • Watching every key for refresh instead of a sentinel, causing partial application.
  • No ValidateOnStart(), so missing config fails at request time.
  • Secrets in pipeline variables as plain text rather than a variable group backed by the vault.

Interview questions

Intermediate

How do you manage secrets for a .NET application in Azure? 🔥 Must know
How I'd answer

"The target I'd aim for is that the application holds no secrets at all, and I'd get as close to that as the dependencies allow."

"So the first question for each dependency is: does it support managed identity? Azure SQL, Storage, Service Bus, Cosmos DB, Key Vault and Event Hubs all do. If it does, there's no secret to manage — Azure gives the app an identity, I grant that identity permission on the resource, and the app gets a token at runtime."

"That's not just convenient, it removes a whole class of incident. There's no credential to accidentally commit, no rotation schedule, nothing sitting in a pipeline variable. You can't leak what doesn't exist."

"For what genuinely needs a secret — a third-party API key, a legacy system with password auth — that goes in Key Vault, and the app reads it using its managed identity. So there's still no credential in configuration; the identity is what opens the vault."

"I'd use DefaultAzureCredential, which is what makes this practical day to day: it tries managed identity first and falls back to the developer's Azure CLI login locally, so the same code works in both places with no conditional logic."

"For access control, Azure RBAC rather than the legacy access policies — assignable per secret, visible to Azure-wide access reviews, and I'd give the app Key Vault Secrets User, which is read-only. A common misconfiguration is granting an application Key Vault Administrator because it was faster, which lets it write and delete secrets it only needs to read."

"Two operational points I'd raise, because they're where this goes wrong in practice."

"Key Vault is throttled. It's a secret store, not a config service, so reading a secret per request produces 429s under load. Secrets should load at startup into IConfiguration — the Key Vault configuration provider does that — which caches them in memory. Worth noting that makes the vault a startup dependency, so I'd enable retry in the provider."

"Rotation needs the app to notice. If secrets are cached at startup, rotating in the vault changes nothing until a restart — and if the old value is revoked, the app breaks at an unrelated moment, on some later deployment. Which is horrible to debug because nothing changed when it failed. I'd set a reload interval so staleness is bounded, and where the service offers primary and secondary keys, use both during rotation so there's never a window with an invalid credential."

"For local development, User Secrets — outside the repository, per developer. Never appsettings.json, because that's in source control."

"And if a secret ever does get committed: rotate it immediately. Deleting the file and committing that does nothing — it's in the history, in every clone and every CI cache. History rewriting is cosmetic; rotation is the actual fix. I'd also want secret scanning in CI so it's blocked rather than discovered."

What they're really checking
  • Is managed identity your first instinct rather than Key Vault?
  • Do you know Key Vault is throttled and secrets are cached at startup?
  • Do you understand rotation requires the app to re-read?
  • Do you know RBAC over access policies, and least privilege?
  • Do you know a committed secret must be rotated?
Weak answers
  • Red flag: "environment variables" as the whole answer.
  • Red flag: Key Vault authenticated with a client secret — which just moves the secret somewhere else.
  • Red flag: no mention of rotation or managed identity.
Likely follow-ups
  • How does the app authenticate to Key Vault?
  • How would you rotate a third-party API key with no downtime?
  • System-assigned or user-assigned, and why?

Advanced

You need to change a setting in production without a deployment. How? ⭐ Senior-level
How I'd answer

"It depends on how quickly it has to take effect and whether a restart is acceptable — those two questions decide the mechanism."

"If a restart is fine: change the App Service application setting. That triggers a restart and the new value is picked up. Simple, and adequate for most settings. On a scaled-out app the restart is rolling, so it isn't full downtime, but there is a brief disruption."

"If it must take effect without a restart: IConfiguration supports reloading, and Azure App Configuration is built for this. It polls on a configured interval and updates configuration in place."

"There's a detail that matters here. If you register every key for refresh, they update independently — so a change touching three related settings can be observed half-applied. The app briefly runs with the new URL and the old API key. For related settings that partial state can be worse than either version."

"The fix is the sentinel pattern: register one unrelated key with refreshAll: true. Update all the real keys, then bump the sentinel last. The app sees one change and reloads everything together, so the switch is atomic from its perspective. It also cuts polling cost dramatically, because there's one key to check rather than hundreds."

"On the consumption side, this only works if the code reads it correctly. IOptionsSnapshot or IOptionsMonitor, not IOptions — IOptions is a singleton bound once at startup and will never see the change, however well refresh is configured. That's the most common reason dynamic refresh appears not to work."

"If it's behavioural rather than a value — turning something on or off — then it's a feature flag, and App Configuration handles those first-class, with a shorter refresh interval and filters for percentage rollout or targeting specific users."

"That's genuinely better than a setting for anything risky, because it decouples deployment from release: deploy the code dark, enable it for 1% of users, watch the metrics, expand or turn it off. And turning a flag off is much faster and lower-risk than rolling back a deployment."

"Two things I'd be careful about."

"Changing production configuration outside a deployment loses the audit trail and the review. Nothing in Git says why the timeout is now 90 seconds, and it drifts from what infrastructure-as-code declares — so the next deployment may quietly revert it. I'd want App Configuration changes going through the same pipeline where practical, and at minimum have change logging and Event Grid notifications enabled so changes are visible."

"And not every setting is safe to change live. Something read once at startup — a connection pool size, a registered service, middleware order — won't take effect, or worse will take effect partially and leave the app inconsistent. So I'd be explicit about which settings are designed to be dynamic and treat the rest as deployment-time."

"Feature flags are the case where dynamic change is unambiguously right. Arbitrary configuration hot-reload is a capability worth having and worth using sparingly."

What they're really checking
  • Do you know App Configuration supports dynamic refresh?
  • Do you know the sentinel pattern and why partial application matters?
  • Do you know IOptions won't see changes?
  • Do you reach for feature flags for behavioural changes?
  • Do you raise the audit-trail and IaC-drift concern?
  • Do you know not every setting is safely dynamic?
Weak answers
  • Red flag: "edit the app setting" with no awareness of the restart.
  • Red flag: dynamic refresh with IOptions.
  • Red flag: no mention of feature flags or the governance trade-off.
Likely follow-ups
  • Which options interface, and why does it matter?
  • How do you audit who changed what?
  • How would you roll out a risky change to 5% of users?
