Azure Functions

Excellent for event-driven work, and the hosting plan decision is where most of the real trade-offs live.

🟡 Intermediate 🔴 Advanced 🔥 Must know
Quick revision
  • A trigger starts the function; bindings move data in and out declaratively.
  • Consumption scales to zero and has cold start. That's the whole trade.
  • Use the isolated worker model — in-process is legacy.
  • Consumption has a hard timeout (10 minutes max). Premium and Flex don't.

Triggers and bindings 🔥 Must know

The distinction

A trigger is what causes the function to run — exactly one per function.

A binding is declarative data movement: input bindings fetch something before your code runs, output bindings write something after. Any number, both optional.

public class OrderFunctions(ILogger<OrderFunctions> logger)
{
    [Function(nameof(ProcessOrder))]
    [ServiceBusOutput("notifications", Connection = "ServiceBus")]   // output binding
    public async Task<string> ProcessOrder(
        [ServiceBusTrigger("orders", Connection = "ServiceBus")]      // trigger
        Order order,
        FunctionContext context)
    {
        logger.LogInformation("Processing {OrderId}", order.Id);
        await _handler.HandleAsync(order, context.CancellationToken);

        // The return value is written to the output binding
        return JsonSerializer.Serialize(new OrderProcessed(order.Id));
    }

    [Function(nameof(HttpCreateOrder))]
    public async Task<HttpResponseData> HttpCreateOrder(
        [HttpTrigger(AuthorizationLevel.Function, "post", Route = "orders")]
        HttpRequestData req)
    {
        var order = await req.ReadFromJsonAsync<CreateOrder>();
        // ...
        var response = req.CreateResponse(HttpStatusCode.Created);
        return response;
    }
}

The blob trigger is slower than people expect

On Consumption, the classic blob trigger works by scanning the container's logs, and the delay can be up to ten minutes. It's also unreliable at high volume and can miss blobs.

That surprises teams building "upload a file and process it immediately" — it isn't immediate.

The fix is Event Grid: configure the storage account to publish blob-created events, and trigger the function from Event Grid instead. That's push-based and near-instant. Event-Grid-based blob triggers are now the recommended approach and there's a dedicated [BlobTrigger(Source = BlobTriggerSource.EventGrid)] form.

Knowing this specific limitation is a good practical signal, because the naive approach appears to work in testing with a handful of files.

Senior signal — bindings trade testability for brevity

Output bindings are genuinely convenient: return a value and it lands in a queue, a blob or Cosmos with no client code, no connection management and no retry handling to write.

The cost is testability and control. A function whose output is a binding can't be unit tested without the Functions host, and you can't easily add retry policies, custom serialisation, or conditional logic about whether to write.

So my rule: bindings for the trigger and simple pass-through outputs; inject a client for anything with logic. If the decision about what to publish depends on the result of the work, that belongs in code with an injected ServiceBusClient — which is also then testable with a fake.

That's a more calibrated answer than either "bindings are great" or "always inject clients".

Cold start: what it is and when it matters

On Consumption, an idle function app is deallocated entirely. The next request has to allocate an instance, load the runtime, load your assemblies and run startup — commonly hundreds of milliseconds to several seconds, and worse with a large dependency graph.

So the rule is about who is waiting. For a queue processor, a webhook receiver or a scheduled job, nobody is — a two-second cold start is invisible. For a user-facing HTTP API it's a visible latency spike, intermittently, which is much worse than being uniformly slower.

What makes it worse: large assemblies, heavy DI graphs built at startup, and reading configuration or secrets during initialisation.

What helps: ReadyToRun compilation, trimming dependencies, deferring expensive initialisation out of the startup path, and keeping the app small. What helps most is always-ready instances on Flex or pre-warmed instances on Premium — at which point you're paying for idle capacity, which is exactly what Consumption avoided.

That trade is the honest answer: Premium removes the cold start and the cost advantage together.

Flex Consumption is now the sensible default

Flex Consumption keeps scale-to-zero billing while adding the things Consumption lacked: VNet integration, configurable per-instance concurrency, larger instance sizes, and always-ready instances to eliminate cold start on the paths that need it.

That combination previously forced you onto Premium — you wanted VNet or no cold start, and had to accept paying for idle instances for everything.

With Flex you can keep most functions scaling to zero and mark specific ones always-ready. So the decision becomes per-function rather than per-app.

Worth knowing because a lot of material still presents it as a binary Consumption-versus-Premium choice, and "I'd use Flex Consumption with always-ready instances for the HTTP-triggered functions" is a current, specific answer.

Senior signal — why isolation was the right architectural change

In-process functions ran inside the Functions host, sharing its runtime and assemblies. That caused two persistent problems.

Version coupling. You could only target the .NET version the host supported, so adopting a new .NET release meant waiting for the Functions host to support it.

Assembly conflicts. If the host loaded a different version of a library you also used — Newtonsoft.Json was the classic — you got runtime binding failures that were miserable to diagnose.

The isolated model runs your code in its own process communicating with the host over gRPC. So you choose your .NET version, there are no shared assemblies, and startup looks like a normal Program.cs with familiar DI and middleware.

The cost is a small amount of serialisation overhead across the process boundary, and slightly worse cold start. That's a good trade for the decoupling, and it's why in-process support has ended — this is the only model going forward.

How scaling actually works 🔴 Advanced

Event Hubs and Cosmos triggers are capped by partition count

For queue-based triggers the scale controller adds instances based on backlog, so throughput scales with load.

For partitioned sources it doesn't work that way. A partition is assigned to exactly one instance to preserve ordering — so with four Event Hubs partitions you get at most four concurrently processing instances, however large the backlog.

Which means a Functions app falling behind on an Event Hub cannot be fixed by scaling. The options are making the function faster, increasing batch size, or adding partitions — and adding partitions changes key-to-partition mapping, so it breaks ordering for existing keys.

Same constraint as Kafka consumer groups, because it's the same underlying model. Knowing that scaling has a structural ceiling here is the distinguishing detail.

Functions retry, so idempotency is mandatory

Most triggers retry on failure. A Service Bus trigger abandons the message so it's redelivered; a Cosmos trigger reprocesses from the last checkpoint; a timer trigger can run twice if an instance is replaced mid-execution.

So at-least-once execution is the default, and a handler with side effects will produce duplicates.

Practically: dedupe on a message id or a business key, recorded in the same transaction as the work. If the record commits separately, a crash between them marks the message processed when it wasn't — turning duplicate execution into lost work.

And note the timer trigger is a singleton by default — the host uses a blob lease to ensure one instance runs it. That's usually what you want, and it's the lease that provides it, so it's worth knowing it exists rather than assuming the platform guarantees single execution by magic.

Durable Functions ⭐ Senior-level

What it adds

Ordinary functions are stateless and short-lived. Durable Functions adds stateful orchestration — a workflow that can span hours or months, survive restarts, fan out and fan in, and wait for external events.

The orchestrator's state is persisted after each step, so it resumes rather than restarting.

[Function(nameof(ProcessBatchOrchestrator))]
public async Task<BatchResult> ProcessBatchOrchestrator(
    [OrchestrationTrigger] TaskOrchestrationContext context)
{
    var batch = context.GetInput<Batch>()!;

    // Fan out - these run in parallel across instances
    var tasks = batch.Items
        .Select(item => context.CallActivityAsync<ItemResult>(nameof(ProcessItem), item))
        .ToList();

    var results = await Task.WhenAll(tasks);          // fan in

    // Wait for a human, for up to 3 days - the orchestrator is not running
    // or being billed while it waits
    var approval = await context.WaitForExternalEvent<bool>(
        "Approval", TimeSpan.FromDays(3));

    if (!approval) await context.CallActivityAsync(nameof(RejectBatch), batch.Id);

    return new BatchResult(results);
}

Orchestrator code must be deterministic — it replays

This is the constraint that catches everyone, and the reason matters.

Durable achieves durability by replaying the orchestrator from the beginning each time it resumes, using an event-sourced history to short-circuit work that already completed. So the orchestrator function body runs many times, and it must take the same path every time.

Which forbids:

  • DateTime.UtcNow — use context.CurrentUtcDateTime
  • Guid.NewGuid() — use context.NewGuid()
  • Random, and anything environment-dependent
  • I/O of any kind — no HTTP, no database. That belongs in an activity
  • Task.Delay — use context.CreateTimer
  • Non-durable async — only await Durable APIs

Break determinism and you get baffling behaviour: an orchestration taking a different branch on replay, activities running twice, or a NonDeterministicOrchestrationException.

The mental model: the orchestrator decides what to do; activities do it. All I/O, all non-determinism and all real work goes in activities. There's an analyser that catches most violations — enable it.

Where Durable genuinely wins

The case that's hard to build otherwise is waiting. An orchestration can wait three days for an approval, and while waiting it isn't running and isn't billed — the state is persisted and it resumes on the event.

Building that yourself means a workflow table, a polling job, timeout handling and resumption logic. Durable makes it one await.

It's also the natural fit for a saga: the orchestrator is the coordinator, activities are the steps, and compensation is just more activity calls in a catch. And the state persistence — which is the part teams most often get wrong when hand-rolling a saga — comes free.

The honest costs: the determinism constraint is a real learning curve, debugging a replayed orchestration is unintuitive, and the history in Table Storage needs purging or it grows indefinitely.

Key takeaways
  • One trigger per function; bindings are declarative data movement.
  • Bindings cost testability — inject a client when there's logic about what to write.
  • The blob trigger polls and can lag ten minutes; use Event Grid instead.
  • Consumption trades cold start for scale-to-zero. Flex Consumption is now the sensible default.
  • Premium removes cold start and the cost advantage together.
  • Use the isolated worker model — in-process is end-of-life.
  • Event Hubs and Cosmos triggers are capped by partition count, so scaling has a ceiling.
  • Execution is at-least-once — dedupe in the same transaction as the work.
  • Timer triggers are singletons via a blob lease.
  • Durable orchestrators replay, so they must be deterministic — no I/O, no DateTime.UtcNow, no NewGuid.
  • Durable's real advantage is waiting without running or being billed.

Common mistakes

  • Consumption plan for a latency-sensitive HTTP API, exposing cold start to users.
  • Long-running work on Consumption, hitting the 10-minute timeout.
  • Blob trigger where near-immediate processing was expected.
  • In-process model for new work.
  • Scaling out to fix Event Hubs lag, when partition count is the ceiling.
  • Non-idempotent handlers, so retries duplicate side effects.
  • I/O in a Durable orchestrator.
  • DateTime.UtcNow or Guid.NewGuid() in an orchestrator.
  • Never purging Durable history, so Table Storage grows without limit.
  • Heavy startup work, making cold start worse.
  • Connection strings in app settings rather than managed identity.

Interview questions

Intermediate

Which Functions hosting plan would you choose? 🔥 Must know
How I'd answer

"It depends on whether anyone is waiting, how long the work takes, and whether I need VNet access."

"The core trade is cold start versus paying for idle. On Consumption an idle function app is deallocated entirely, so the next request pays to allocate an instance, load the runtime and load my assemblies — commonly hundreds of milliseconds to several seconds, worse with a big dependency graph."

"So for background and event-driven work — a queue processor, a webhook receiver, a scheduled job — Consumption is ideal. Nobody is waiting, so a two-second cold start is invisible, and I pay essentially nothing when idle."

"For a user-facing HTTP API it's the wrong choice, because cold start becomes an intermittent latency spike — which is worse than being uniformly slower, since it's unpredictable."

"My current default though would be Flex Consumption, because it changed this decision. It keeps scale-to-zero billing while adding VNet integration, configurable per-instance concurrency, and always-ready instances to remove cold start on specific functions."

"Previously wanting either VNet or no cold start forced you onto Premium, which meant paying for idle instances across the whole app. With Flex the decision becomes per-function: most scale to zero, and the HTTP-triggered ones get always-ready instances."

"Premium I'd choose for pre-warmed instances plus unlimited duration and full VNet support — and I'd be honest that it removes the cold start and the cost advantage together. It's billed per instance-hour like an App Service plan. At that point the question is what Functions is buying: if the answer is the triggers and bindings, that's legitimate; if it's 'serverless', you've lost the property that made it serverless."

"The other hard constraint worth naming: Consumption has a 10-minute maximum duration. So anything long-running either needs Premium or Flex, or — better — should be restructured. A function processing 10,000 records in one execution is fragile regardless of the timeout; I'd rather fan out to one execution per record, or use Durable Functions for the orchestration."

"And if I already have an App Service plan with spare capacity, running Functions on it is a reasonable way to avoid a second bill — accepting that it doesn't scale independently."

What they're really checking
  • Do you frame it as cold start versus idle cost?
  • Do you know the 10-minute Consumption timeout?
  • Do you know Flex Consumption exists and what it changes?
  • Do you recognise Premium removes both cold start and the cost benefit?
  • Do you question long-running functions rather than just picking a bigger plan?

  • What actually causes a cold start, and how do you reduce it?
  • How would you handle a 30-minute job?
  • How does Functions decide to scale out?

Advanced

Why must a Durable Functions orchestrator be deterministic? ⭐ Senior-level
How I'd answer

"Because of how Durable achieves durability — and once you know the mechanism the constraint stops feeling arbitrary."

"An orchestration can span hours or months and must survive process restarts. Durable doesn't keep the orchestrator running and waiting. Instead, when it hits an await, it unloads — and when the awaited work completes, it replays the orchestrator function from the very beginning."

"During replay it uses an event-sourced history to short-circuit anything already done: it reaches CallActivityAsync, sees in the history that this activity already returned a value, and hands back the recorded result without re-executing it. It carries on replaying until it reaches work that hasn't happened yet, and then actually does it."

"So the orchestrator body runs many times, and it must take the same path every time — otherwise the history no longer lines up with the code's decisions."

"Which forbids anything non-deterministic. DateTime.UtcNow returns a different value on each replay, so a branch on it can go a different way — you use context.CurrentUtcDateTime, which returns the value recorded in the history. Guid.NewGuid() likewise, so context.NewGuid(). No Random, nothing environment-dependent."

"And no I/O at all — no HTTP calls, no database access. Partly because it's non-deterministic, partly because it would re-execute on every replay. All of that goes in activities, which run once and have their results recorded."

"Also no Task.Delay — use context.CreateTimer, which is durable, so the orchestrator genuinely isn't running or being billed while it waits. And only await Durable APIs, because awaiting an arbitrary task breaks the replay model."

"The mental model I'd give: the orchestrator decides what to do; activities do it. The orchestrator is pure coordination logic."

"What happens if you break it is genuinely confusing — an orchestration taking a different branch on replay, activities appearing to run twice, or a NonDeterministicOrchestrationException that points at a line which looks fine. So I'd enable the Durable analyser, which catches most violations at build time."

"One consequence worth knowing: you can't safely change orchestrator code while orchestrations are in flight, because an in-progress instance will replay against the new code with old history. The mitigation is versioning — deploy a new orchestrator name and let existing instances drain on the old one."

"And the payoff for accepting all this: the orchestration survives restarts and deployments, and it can wait days for a human approval without consuming resources. Building that by hand means a workflow table, a polling job, timeout handling and resumption logic — Durable makes it one await."

What they're really checking
  • Do you know the replay mechanism, not just the rule?
  • Can you list what's forbidden and the Durable alternatives?
  • Do you know the orchestrator/activity division of responsibility?
  • Do you know about versioning in-flight orchestrations?
  • Can you state what the constraint buys you?
Weak answers
  • Red flag: "because the docs say so" with no mechanism.
  • Red flag: putting HTTP calls in an orchestrator.
  • Red flag: no awareness that the body runs repeatedly.
Likely follow-ups
  • How would you implement a saga with Durable?
  • How do you debug a replayed orchestration?
  • What happens to the history data over time?
