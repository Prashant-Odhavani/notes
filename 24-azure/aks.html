AKS

The most capable compute option and the one with the highest operational cost. Knowing when not to pick it is most of the senior signal.

Senior signal — AKS is a platform decision, not a deployment choice

Kubernetes gives you enormous capability, and the price is a permanent operational commitment: cluster upgrades on a schedule, node image patching, capacity planning, networking design, RBAC, admission policy, and the expertise to debug it when a pod won't schedule at 2am.

That's a reasonable trade for a platform team supporting many services. It's a poor one for three microservices, where you'll spend more time on the cluster than on the code — and the cluster becomes a single point of both failure and knowledge.

Azure Container Apps is built for that middle ground: containers, revisions, scale to zero, KEDA-based event scaling, Dapr if you want it, and no cluster. It runs on AKS underneath, which is why it feels similar, without you operating it.

So the calibrated answer is: Container Apps unless you need something only the Kubernetes API provides — custom operators, a service mesh, CRDs, StatefulSets, a large existing Helm estate, or genuine multi-cloud portability. Those are real reasons. "We want containers" is not one.

Saying that out loud is a strong signal, because the failure mode in interviews is treating Kubernetes as the default modern answer. Choosing the simplest thing that meets the requirement is the more senior instinct.

Separate your system and user node pools

If application pods share nodes with kube-system, a memory-hungry workload can starve CoreDNS or metrics-server.

The result is bad in a specific and confusing way: DNS resolution starts failing intermittently across the whole cluster, so every service appears broken while nothing in any application's logs explains it. And metrics-server dying means the HPA stops scaling — so the cluster can't respond to the load that caused it.

A dedicated system node pool with the CriticalAddonsOnly taint keeps application pods off those nodes. It costs a couple of small VMs and removes a whole class of cluster-wide incident.

Same reasoning as keeping reporting off the production database: don't let a workload you can shed compete with infrastructure you can't.

Senior signal — KEDA over HPA for anything queue-driven

CPU is a poor proxy for the work a queue consumer has to do. A pod pulling from Service Bus might sit at 15% CPU while ten thousand messages back up, because it's waiting on I/O — so the HPA sees an idle pod and scales down exactly when there's a backlog.

KEDA scales on the thing that actually matters: queue length, Event Hubs lag, Kafka lag, a Prometheus query, a cron schedule. It's an AKS add-on, so there's no separate installation to maintain.

And it scales to zero, which the HPA cannot. A consumer with no messages costs nothing — that's a real saving for batch and off-peak workloads, and it's the same mechanism Container Apps uses underneath.

The trade to mention: scale-from-zero has a cold start, so a latency-sensitive path needs a minimum replica count. And scaling on queue depth needs a sensible target and cooldown, or you'll thrash — pods starting and stopping faster than they can drain anything.

Requests and limits are the most consequential thing you'll configure

Two numbers per container, and they behave differently:

  • Requests are what the scheduler reserves. They decide where a pod can be placed and how much node capacity is considered used.
  • Limits are the hard ceiling. Exceeding a CPU limit gets you throttled; exceeding a memory limit gets the container OOM-killed — immediately, with no grace.

What goes wrong:

No requests set. The scheduler assumes near-zero, packs the node, and everything degrades together under load. This is the most common one, and it's silent until traffic arrives.

Requests far above real use. The cluster looks full at 20% actual utilisation and the autoscaler adds nodes you don't need. Pure cost.

Memory limit too low. Containers restart under load, which reads as instability rather than configuration. And note that .NET sizes the GC heap from the limit — so a badly-set limit changes runtime behaviour, not just the kill threshold.

The practical advice: set memory request and limit equal, because memory is incompressible and overcommitting it means an OOM kill instead of graceful slowdown. For CPU, set a request and consider leaving the limit off — CPU is compressible, so a burst is better absorbed than throttled. Then derive the numbers from observed usage rather than guessing.

Workload identity 🔥 Must know

apiVersion: v1
kind: ServiceAccount
metadata:
  name: orders-api
  annotations:
    azure.workload.identity/client-id: "00000000-0000-0000-0000-000000000000"
---
apiVersion: apps/v1
kind: Deployment
metadata: { name: orders-api }
spec:
  replicas: 3
  template:
    metadata:
      labels:
        azure.workload.identity/use: "true"     # required, easy to forget
    spec:
      serviceAccountName: orders-api            # federated to the managed identity
      containers:
        - name: api
          image: myacr.azurecr.io/orders-api:1.4.2   # never :latest
          resources:
            requests: { cpu: "200m", memory: "256Mi" }
            limits:   { memory: "256Mi" }        # equal to request; no CPU limit
          readinessProbe:                        # remove from load balancer when not ready
            httpGet: { path: /health/ready, port: 8080 }
            periodSeconds: 5
          livenessProbe:                         # RESTART the container - different job
            httpGet: { path: /health/live, port: 8080 }
            periodSeconds: 15
            failureThreshold: 3
          lifecycle:
            preStop:
              exec: { command: ["sleep", "5"] }  # let endpoints propagate before shutdown
Senior signal — federated credentials mean no secret exists

Workload identity federates a Kubernetes service account to an Entra managed identity. The pod receives a projected service-account token, exchanges it for an Entra token, and calls Azure SQL, Key Vault or Storage with it.

So there's no client secret in a Kubernetes Secret — which matters, because Kubernetes Secrets are base64-encoded, not encrypted, readable by anyone with namespace access, and visible in etcd backups.

It replaces the older pod-managed identity, which is deprecated. Worth knowing that if you meet it in an existing cluster: it relied on intercepting the instance-metadata endpoint, which was slower and more fragile.

Two details that catch people. The azure.workload.identity/use: "true" label is required on the pod template, and without it nothing happens — no error, just failed authentication. And the federated credential must name the exact namespace and service-account, so moving a workload to a different namespace breaks it in a way that looks like a permissions problem.

For genuine secrets that must exist — a third-party key — use the Secrets Store CSI driver to mount them from Key Vault, so they're never Kubernetes objects at all.

Readiness and liveness do different jobs

The distinction is worth being exact about, because getting it wrong causes outages rather than preventing them.

Readiness controls whether the pod receives traffic. Failing it removes the pod from the service endpoints; the container keeps running. That's the right response to "I'm warming up" or "my dependency is briefly unavailable."

Liveness restarts the container. That's only correct for a pod that is genuinely unrecoverable — deadlocked, or in a corrupted state.

The failure mode: a liveness probe that checks the database. When the database has a 30-second blip, every pod fails liveness and every container restarts — simultaneously, cluster-wide. You've converted a brief dependency issue into a full outage, and the restarts add a thundering-herd of reconnections on top.

So liveness checks only what a restart could fix. Readiness may check dependencies. And add a preStop delay, because endpoint removal isn't instantaneous — without it a pod can stop accepting connections while the load balancer is still sending them, which shows up as a handful of 502s on every deployment.

IP exhaustion is the classic AKS design mistake

With traditional Azure CNI, every pod takes a VNet IP address — and IPs are pre-allocated per node based on the maximum pods per node, whether or not pods exist.

So a node configured for 110 pods reserves 110 addresses the moment it joins. Thirty nodes is 3,300 addresses, and a /24 subnet holds 251. Teams routinely discover this when the cluster cannot scale out — the autoscaler adds a node, there are no IPs, and the node never becomes ready.

And a subnet can't be resized in place once it's in use, so the fix is rebuilding the cluster on a bigger subnet. That's why it's a design mistake rather than a configuration one.

Azure CNI Overlay is the answer and the current recommendation: pods get IPs from a separate overlay CIDR, so only nodes consume VNet addresses. You scale to thousands of pods on a small subnet.

The trade: overlay pod IPs aren't directly routable from outside the cluster, so a scenario needing to reach a pod IP directly from elsewhere in the VNet needs the node-subnet model. That's uncommon, and worth confirming rather than assuming.

Upgrades ⭐ Senior-level

ConcernReality
Version supportRoughly a year per minor version. You will upgrade regularly
Skipping versionsNot allowed — one minor version at a time
OrderControl plane first, then node pools
Node upgradesSurge new nodes, cordon, drain, remove old ones
Auto-upgrade channelsPatch, stable, rapid — with maintenance windows
API deprecationsThe actual risk. Removed APIs break manifests
The upgrade risk is deprecated APIs, not the upgrade itself

The mechanics are well handled: AKS surges new nodes, drains the old ones and replaces them. That part rarely surprises anyone.

What breaks is removed API versions. Kubernetes deprecates and then removes API groups, so a manifest or Helm chart referencing a removed version fails to apply after the control plane upgrade — and often only when something next tries to deploy, which can be days later and appears unrelated.

AKS surfaces deprecated API usage in diagnostics, and there are tools like kubent that scan manifests. Checking before upgrading is a five-minute job that prevents the whole problem.

Two operational safeguards. PodDisruptionBudgets so a drain can't take every replica of a service at once — though a PDB that's too strict will block the drain indefinitely, which is its own incident. And maintenance windows, so auto-upgrade doesn't roll nodes during your peak hours.

Because upgrades come round every few months regardless of your roadmap, treat them as scheduled work. Falling out of support is worse: no patches, no support, and eventually a forced multi-version jump — which you can't do in one step, so you're chaining upgrades under pressure.

Key takeaways
  • Container Apps first; AKS when you need the Kubernetes API itself.
  • Microsoft runs the control plane; you own, patch and pay for nodes.
  • Dedicated system node pool with CriticalAddonsOnly.
  • Pods scale with HPA or KEDA; nodes with the cluster autoscaler.
  • KEDA for queue-driven work, and it can scale to zero.
  • Requests decide scheduling; memory limits kill, CPU limits throttle.
  • Memory request equal to limit; consider no CPU limit.
  • Workload identity means no secret exists — the use: "true" label is required.
  • Readiness removes traffic; liveness restarts. Never check dependencies in liveness.
  • Add a preStop delay to avoid 502s on deployment.
  • Azure CNI Overlay avoids VNet IP exhaustion.
  • Upgrade regularly; the real risk is removed APIs.
  • PodDisruptionBudgets and maintenance windows — but a strict PDB blocks drains.

Common mistakes

  • Choosing AKS for three services when Container Apps would do.
  • Application pods on the system node pool, starving CoreDNS.
  • No resource requests, so the scheduler overpacks nodes.
  • Requests far above actual usage, paying for idle nodes.
  • Liveness probes that check the database, restarting every pod during a blip.
  • No preStop hook, dropping in-flight requests on deploy.
  • Secrets in Kubernetes Secrets instead of workload identity or the CSI driver.
  • Missing the workload-identity label and debugging it as a permissions issue.
  • Traditional Azure CNI on a small subnet, hitting IP exhaustion.
  • HPA on CPU for a queue consumer, scaling down under backlog.
  • Falling out of version support, then chaining upgrades under pressure.
  • :latest image tags, so you can't tell what's running or roll back.

Pods are being OOM-killed under load. Walk through it. ⭐ Senior-level
How I'd answer

"First I'd confirm it is an OOM kill rather than something else, because several failures look similar. kubectl describe pod shows the last state with reason OOMKilled and exit code 137. If instead it's exit 143 or a failing liveness probe, that's a different problem — a restart caused by the probe, not by memory."

"Then the question is which of three things is happening, because the fixes are different."

"The limit is simply too low for legitimate usage. The most common case. The number was guessed at, or copied from another service, and real traffic needs more. I'd look at actual working set over time — container memory metrics — and set the limit above observed peak with headroom."

"The .NET-specific detail worth raising: the runtime sizes its GC heap from the container limit. So the limit isn't just a kill threshold, it changes how the GC behaves. A limit set very tight makes the GC run far more aggressively — high CPU, worse latency — and the pod may be spending its time collecting rather than working. Raising the limit can improve CPU as well as stop the kills, which surprises people."

"I'd also check Server GC. It's the default for ASP.NET Core and it's tuned for throughput, so it holds more memory and allocates per-core heaps. In a container with a low memory limit and several visible cores that's a bad fit — Workstation GC, or configuring heap limits, is often the right call for small containers. It's a genuine trade: more memory-efficient, somewhat lower throughput."

"A memory leak. If usage climbs monotonically and never recovers after a GC, that's a leak rather than a sizing problem — and raising the limit only delays it. In .NET the usual suspects are HttpClient instances created per request, static collections that only grow, event handlers never unsubscribed, or IDisposable not disposed. I'd take a dump — dotnet-gcdump — and compare heap contents over time to find what's accumulating."

"A load-proportional spike. If memory tracks concurrency, something is buffering per request: reading an entire upload into memory, materialising a full query result, or building a large response in a string. That's a code fix — stream instead of buffer, page the query — not a limit increase."

"On configuration, two things I'd correct if they're wrong."

"Request and limit for memory should be equal. If the request is lower, the scheduler places pods based on the smaller number and the node is overcommitted — so under load pods compete for memory that was never reserved, and the kernel kills whichever crosses its limit first. Setting them equal gives the pod the Guaranteed QoS class, so it isn't the first eviction candidate when the node comes under pressure."

"Check whether the node itself is under memory pressure, which is a different failure: the kubelet starts evicting pods, and pods with requests below usage go first. kubectl describe node shows the conditions. If that's what's happening, the fix is node sizing and correct requests rather than per-pod limits."

"For mitigation while investigating: raise the limit to stop the restarts, since a restarting pod is worse than a memory-hungry one, and add an alert on container restarts so it doesn't go unnoticed next time. But I'd be clear that's containment, not a fix — if it's a leak, the same thing happens at the higher number."

"The general point: a memory limit is a statement about the application's behaviour, so getting it right means measuring rather than guessing, and it interacts with GC configuration in a way that's specific to .NET and easy to miss."

What they're really checking
  • Do you confirm the failure mode before acting?
  • Do you know .NET sizes the GC heap from the container limit?
  • Do you distinguish a leak from under-sizing from per-request buffering?
  • Do you know why request should equal limit for memory?
  • Do you consider node-level eviction?
Weak answers
  • Red flag: "increase the memory limit" and stop there.
  • Red flag: no awareness of GC interaction with limits.
  • Red flag: not distinguishing a leak from a sizing problem.
Likely follow-ups
  • How do you capture a heap dump from a pod?
  • Server GC or Workstation GC in a container, and why?
  • What QoS class does the pod have, and does it matter?
