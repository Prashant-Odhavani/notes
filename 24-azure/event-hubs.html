Event Hubs

A partitioned log, not a queue. Once that distinction lands, everything else about the service follows from it.

🟡 Intermediate 🔴 Advanced 🔥 Must know
Quick revision
  • It's a log. Reading doesn't remove anything; events expire on retention.
  • Partitions are the unit of ordering and of parallelism.
  • Partition key → hash → partition. Same key, same partition, ordered.
  • Consumer groups are independent cursors over the same data.
  • One active reader per partition per consumer group. That's your parallelism ceiling.
  • Checkpointing is your progress marker — and it's how duplicates happen.
  • Partition count can be increased but not decreased, and increasing changes key mapping.

Senior signal — no per-event state is the whole design trade

Service Bus tracks every message individually: a lock, a delivery count, a dead-letter destination. That's what makes per-message retry and poison-message handling possible, and it's also what caps throughput — that bookkeeping costs something per message.

Event Hubs tracks one number per partition per consumer group: the offset. That's the entire consumer state. Which is why it handles millions of events a second, and why the features you'd expect from a queue simply don't exist.

The consequence people meet in production: you cannot dead-letter a single bad event. If event 5,000 in a partition throws, your options are to skip it, to stop the partition, or to write it somewhere yourself. There's no platform mechanism.

So error handling on Event Hubs is your code: catch, write the failure to a Service Bus queue or blob for later, and carry on. If you stop instead, the partition stalls and lag grows behind one bad event.

"Event Hubs for volume, Service Bus for per-message guarantees" is the summary — and it's the reason many systems use both.

Partitions 🔥 Must know

  Without a partition key:
     round-robin across all partitions

  Consumers:
     partition 0 --+

     partition 3 --+

Choosing the partition key is the decision you can't easily undo

Three things follow from the key, and they pull against each other.

Ordering. Only events with the same key are ordered relative to each other. So if per-device or per-account ordering matters, that has to be the key.

Distribution. A key with skewed values sends most traffic to one partition. One partition becomes the bottleneck while others idle — and adding partitions doesn't help, because the hot key still hashes to a single one. This is exactly the hot partition problem, and it shows up identically in Kafka, Cosmos DB and DynamoDB. Same physics every time.

Parallelism. Ordering within a key means one consumer processes that key's events serially. A coarse key (region, tenant) gives you order at the cost of throughput.

And the trap: if you later increase the partition count, keys remap. Events for one key that were on partition 3 start landing on partition 7 — while partition 3 still holds unprocessed earlier events for that key. Ordering is broken across the boundary, and no amount of consumer care fixes it.

So the practical advice is to provision partitions generously at creation. They're cheap in Standard, the count can't go down, and increasing it later is the operation with real consequences. Choosing 32 when you needed 8 costs nothing; choosing 4 when you needed 32 is a migration.

Do you actually need ordering?

A lot of the difficulty here disappears if the answer is no.

Telemetry, click events, metrics, logs, most audit records — these don't need ordering. Omit the partition key, get round-robin distribution, perfect balance and maximum parallelism.

Ordering matters when events describe transitions of the same entity: created → updated → deleted for one order, or state changes for one device. Processing those out of order produces the wrong final state.

Even then there's often a way out: make the events idempotent and carry a version, and the consumer can discard anything older than what it has already applied. Then order doesn't matter, and you get the distribution benefits back. It's more work in the consumer and usually the better trade at high volume.

Consumer groups and checkpointing 🔥 Must know

// EventProcessorClient does load balancing across instances and stores
// checkpoints in blob storage. Do not hand-roll this.
var processor = new EventProcessorClient(
    checkpointStore: new BlobContainerClient(blobUri, credential),
    consumerGroup: "billing",
    fullyQualifiedNamespace: ns,
    eventHubName: "telemetry",
    credential);

processor.ProcessEventAsync += async args =>
{
    try
    {
        await Handle(args.Data, args.CancellationToken);
    }
    catch (Exception ex)
    {
        // No dead-letter here. Record it yourself and MOVE ON,
        // or this one event stalls the whole partition.
        await _poison.SendAsync(args.Data, ex, args.CancellationToken);
        _log.EventFailed(args.Partition.PartitionId, args.Data.SequenceNumber, ex);
    }

    // Checkpoint periodically, not per event - each one is a storage write
    if (args.Data.SequenceNumber % 100 == 0)
        await args.UpdateCheckpointAsync(args.CancellationToken);
};

processor.ProcessErrorAsync += args =>
{
    _log.ProcessorError(args.Operation, args.PartitionId, args.Exception);
    return Task.CompletedTask;   // the processor recovers on its own
};
Senior signal — checkpoint frequency is a duplicates-versus-cost dial

A checkpoint is "I have processed up to here." On restart or rebalance, processing resumes from the last checkpoint.

Checkpoint per event and duplicates are minimal — but every checkpoint is a write to blob storage, so throughput collapses and you're paying for storage operations at event volume.

Checkpoint every 10,000 events and throughput is excellent, but a crash reprocesses up to 10,000 events.

There is no setting that removes the trade, because Event Hubs is at-least-once, always. Even per-event checkpointing has a window: you process, then checkpoint, and a crash between them replays that event.

Which is why the real answer is the same one that appears throughout the handbook: make the consumer idempotent, then checkpoint on an interval that suits your throughput — every few hundred events or every few seconds — and stop worrying about duplicates.

"At-least-once delivery plus an idempotent consumer gives an exactly-once effect" is the framing that matters, and it's identical to Kafka offset commits and idempotency keys in HTTP.

Consumer groups are cursors, not filters

A consumer group doesn't select a subset of events. Every group sees every event in the hub; the group only tracks where it has read to.

So adding a consumer group for analytics doesn't reduce what the billing group receives, and it doesn't cost extra throughput on the ingress side. Egress does count against your throughput units, though — a second consumer group doubles the read volume.

Two more limits worth knowing. Standard tier allows 20 consumer groups, which is plenty for most designs but not unlimited. And only one active reader per partition per group — a second instance trying to read the same partition in the same group is rejected, which is why the processor client does ownership-based load balancing rather than letting everyone read everything.

If you want filtering, that's Event Grid or a Service Bus topic. Event Hubs delivers everything and expects the consumer to decide.

Auto-inflate goes up and never comes down

Auto-inflate raises throughput units automatically when you exceed the current allocation, up to a limit you set. It's worth enabling, because exceeding your TUs means ingress throttling — producers get 429s and events are rejected, which for telemetry means permanently lost data.

The thing to know: it does not scale back down. A traffic spike that pushes you from 4 TUs to 20 leaves you paying for 20 indefinitely until someone notices.

So enable it as a safety net and alert on the TU count changing, so the scale-up is visible and someone can reduce it deliberately. Treating auto-inflate as fire-and-forget is a recurring source of surprise on the bill.

Premium's processing units behave differently and don't have this shape, which is part of what you're paying for.

Senior signal — Capture is the cheap answer to "we need the history"

Retention is the limit on replay: if you keep one day and a consumer bug is found on Thursday affecting Monday's events, those events are gone.

Extending retention is one answer and it's the expensive one — you're paying streaming-service prices to store cold data.

Capture writes every event to Blob Storage or Data Lake automatically, in Avro, with no code at all. Storage costs a fraction of Event Hubs retention, and you get an indefinite archive that's directly queryable by Synapse, Databricks or Fabric.

So the pattern is: short retention on the hub for live consumers, Capture for history and reprocessing. The hub handles the last few hours; the archive handles everything else.

The trade to state: replaying from Capture isn't the same as resetting an offset — you're reading Avro files from storage, so it's a separate code path you have to write and test. Worth building before you need it, because the day you need it is a bad day to write new code.

The Kafka endpoint 🔴 Advanced

Protocol compatibility, not Kafka

Standard tier and above expose a Kafka-protocol endpoint, so an existing Kafka producer or consumer can point at Event Hubs with a configuration change and no code change.

That's genuinely useful for migration and for reusing Kafka tooling and client libraries. What you get is the protocol — not the ecosystem.

Kafka Streams, ksqlDB, log compaction and transactions are not supported. So if the application depends on those, it isn't a configuration change; it's a redesign.

The honest framing: Event Hubs is a managed streaming service with a Kafka-shaped door. Use it to avoid running Kafka yourself, not to get Kafka's full feature set.

Key takeaways
  • It's a log — reading advances a cursor, events expire on retention.
  • No per-event state, so no per-message retry and no dead-letter. You handle failures.
  • One bad event handled badly stalls a partition.
  • Partition key decides ordering, distribution and parallelism at once.
  • A hot key can't be fixed by adding partitions.
  • Partition count can only go up, and increasing it remaps keys and breaks ordering.
  • Provision partitions generously at creation.
  • Consumer groups are independent cursors over all events, not filters.
  • One active reader per partition per consumer group.
  • Checkpoint frequency trades duplicates against cost; at-least-once always.
  • Idempotent consumers make the duplicate question go away.
  • Auto-inflate scales up and never down — alert on it.
  • Capture gives cheap indefinite history; short retention on the hub.
  • The Kafka endpoint is protocol compatibility, not the Kafka ecosystem.

Common mistakes

  • Using Event Hubs for work that needs per-message retry — that's Service Bus.
  • Throwing on a bad event and stalling the partition.
  • Too few partitions, capping consumer parallelism permanently.
  • A skewed partition key, so one partition carries most traffic.
  • Increasing partition count on a hub where ordering matters.
  • Checkpointing per event, destroying throughput.
  • Assuming exactly-once and building a non-idempotent consumer.
  • Auto-inflate enabled with no alert, leaving TUs high forever.
  • Long retention instead of Capture, paying streaming prices for cold data.
  • Expecting consumer groups to filter events.
  • Assuming the Kafka endpoint means Kafka Streams works.

Interview questions

Intermediate

When would you choose Event Hubs over Service Bus? 🔥 Must know
How I'd answer

"The distinction I'd start from is a queue versus a log, because every other difference follows from it."

"Service Bus is a queue. Reading a message removes it. The broker tracks each message individually — a lock, a delivery count, a dead-letter destination. That per-message bookkeeping is what gives you retry, poison-message handling, sessions and transactions."

"Event Hubs is a log. Reading advances a cursor; the data stays until retention expires. The only consumer state is one offset per partition per consumer group. Which is why it does millions of events a second — there's almost no bookkeeping — and why the queue features simply don't exist."

"So I'd choose by what the message is."

"Service Bus for commands and work — 'process this payment', 'send this email'. Things where each message matters individually, must be retried on failure, and must not be lost. One consumer should handle it, and if it fails repeatedly it needs to go somewhere a human can look."

"Event Hubs for telemetry and event streams — IoT readings, click events, application metrics, audit trails. High volume, individually less important, and often multiple independent consumers want the same data: one writing to a warehouse, one running real-time alerts, one archiving."

"That last point is a real differentiator. With Event Hubs, adding a consumer group is free from the producer's perspective — nobody changes, everyone gets everything. And replay: I can reset an offset and reprocess a day's events, which is invaluable when a consumer had a bug. A queue can't do that; the messages are gone."

"The main thing I'd flag as a trap: Event Hubs has no dead-letter queue. If one event fails to process, there's no platform mechanism. Your options are to skip it, stop the partition, or write it somewhere yourself. And stopping is dangerous — the partition stalls and lag grows behind one bad event."

"So error handling is your code, and it has to be deliberate: catch, record the failure to a Service Bus queue or blob, continue. Teams that pick Event Hubs for throughput and then need per-message reliability end up rebuilding queue semantics badly on top of a log."

"And it's not either/or — a common shape is Event Hubs for ingestion at volume, then a consumer that converts the events that need reliable individual handling into Service Bus messages. Each service does what it's good at."

What they're really checking
  • Do you have the queue-versus-log distinction?
  • Do you connect it to why throughput differs?
  • Do you know Event Hubs has no dead-letter?
  • Do you value replay and multiple consumer groups?
  • Do you see them as complementary?
Weak answers
  • Red flag: "Event Hubs is faster" as the whole answer.
  • Red flag: expecting dead-lettering on Event Hubs.
  • Red flag: no mention of replay or consumer groups.
Likely follow-ups
  • How do you handle a poison event on Event Hubs?
  • How do you get ordering?
  • What if you need both patterns?

Advanced

Consumer lag is growing on one partition only. Diagnose it. ⭐ Senior-level
How I'd answer

"One partition and not the others is a strong signal — it rules out a general capacity problem, because if the consumer were simply too slow every partition would lag. So something is specific to this partition or its reader."

"I'd work through four causes, in the order they're likely."

"Partition key skew. Most likely. If the key is something like tenant id or device id and one value dominates — a large customer, a misbehaving device sending 100× the normal rate — that key hashes to one partition, and that partition receives disproportionate traffic while the others idle."

"I'd confirm it by comparing incoming event counts per partition, which the metrics give directly. And the important consequence: adding partitions doesn't fix this. The hot key still hashes to a single partition. Same physics as a hot partition in DynamoDB or Cosmos, and the fix is the same — change the key so the hot value spreads, typically by adding a suffix, or drop ordering entirely for that traffic and go round-robin."

"A stalled or repeatedly failing reader. If the handler throws on a specific event and the code retries indefinitely or rethrows, that partition makes no progress while every other partition continues. Lag on exactly one partition with normal event rates is the signature."

"I'd look for repeated exceptions with the same sequence number in the logs. This is the Event Hubs failure mode that catches people, because there's no dead-letter to absorb a poison event — a single bad message can hold up a partition indefinitely. The fix is to record the failure elsewhere and move on."

"Ownership churn. If the processor client is rebalancing repeatedly — instances scaling up and down, or checkpoint storage being slow or throttled — a partition can lose and regain ownership constantly and spend its time re-establishing rather than processing. I'd check the error handler's output and the blob checkpoint store for throttling, which is easy to overlook because it's a different resource."

"Slow processing for that partition's data specifically. If one partition happens to carry events that are more expensive to handle — larger payloads, a code path hitting a slower dependency — it processes more slowly with nothing actually broken. Comparing per-event processing duration by partition distinguishes this from the others."

"For diagnosis I'd want lag per partition as a metric, computed as the difference between the last enqueued sequence number and the checkpointed one. That's the number worth alerting on, and per-partition rather than aggregate — an average across 32 partitions hides exactly this situation."

"On mitigation: I'd separate catching up from fixing the cause. If it's a poison event, skipping it restores flow immediately and I can investigate the recorded failure afterwards. If it's skew, catching up may require temporarily throttling the hot producer, because a single reader per partition per consumer group is a hard ceiling — I can't add consumers to drain one partition faster."

"That ceiling is worth saying explicitly, because it's the constraint that makes this different from a queue: with Service Bus I'd add consumers. Here I can't, so the answer is either fewer events on that partition or faster processing per event."

What they're really checking
  • Do you recognise per-partition lag as skew or a stalled reader?
  • Do you know adding partitions doesn't fix a hot key?
  • Do you know a poison event stalls a partition with no dead-letter?
  • Do you consider checkpoint-store throttling?
  • Do you know one reader per partition is a hard ceiling?
Weak answers
  • Red flag: "scale out the consumer" — it can't help one partition.
  • Red flag: "add partitions" for a hot key.
  • Red flag: only monitoring aggregate lag.
Likely follow-ups
  • How would you change the partition key without breaking ordering?
  • How do you compute lag per partition?
  • What if the hot tenant legitimately sends that volume?
