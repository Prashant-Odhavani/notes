App Service

The least fashionable and frequently correct choice for a .NET web application. Slots are the feature worth understanding properly.

🟢 Beginner 🟡 Intermediate 🔥 Must know

Plans and what you're paying for 🔥 Must know

The billing model

You pay for the App Service Plan — a set of VMs — per hour, whether your app is receiving traffic or not.

Multiple apps can run on one plan and share its CPU and memory. So the plan is the unit of both cost and resource contention.

TierGives youUse for
Free / SharedQuotas, no SLA, no custom domain SSLExperiments only
BasicCustom domains, manual scale, no slotsDev and test
StandardSlots (5), autoscale, daily backupsMost production apps
Premium v3More slots, better hardware, zone redundancy, higher scaleProduction needing HA or scale
Isolated v2Dedicated App Service Environment, full VNet isolationStrict compliance or network isolation
Basic has no deployment slots, and that's the tier decision

Slots are the single most valuable App Service feature, and they start at Standard. Choosing Basic to save money means giving up zero-downtime deployment and instant rollback.

That's usually the wrong trade for anything production, because the alternative is deploying over the running app — brief downtime, and a rollback means redeploying the previous build.

Premium v3 also has better price-performance than Standard on newer hardware, so the naive cost comparison can mislead. And zone redundancy — which distributes instances across availability zones — is Premium v3 only, so a Standard plan has no protection against a zone failure however many instances you run.

"Standard as the minimum for production, Premium v3 if we need zone redundancy or the performance" is the calibrated answer.

Scaling out breaks anything holding local state

The moment there's more than one instance, a request can land on any of them. Which breaks four things that work perfectly on a single instance:

  • In-memory session or cache. Instance 2 doesn't have what instance 1 stored.
  • Files written to local disk. Each instance has its own — though note App Service shares /home across instances by default, which surprises people in both directions.
  • In-memory rate limiting or counters. Three instances means three times the limit.
  • Background timers in the web app. Every instance runs them, so a nightly job runs n times.

That last one is the most damaging and the least obvious — a scheduled task inside a web app silently multiplies when you scale out, so an email goes three times.

The fixes: distributed cache and session, blob storage for files, Redis-backed rate limiting, and moving scheduled work out to a Function or a singleton-guarded job. All of which should be done before you need to scale, because discovering them during a traffic spike is the worst time.

ARR affinity: off by default in your head, on by default in Azure

App Service enables ARR affinity (session affinity) by default, which pins a client to one instance using a cookie.

That's there to make legacy stateful apps work when scaled out. For a stateless application it's actively harmful: load distributes unevenly, a scale-out event doesn't relieve existing clients because they stay pinned, and losing an instance drops those users' state.

Turn it off for anything stateless. It's a single setting, and leaving it on is one of the most common reasons scaling out doesn't help as much as expected.

If you genuinely need affinity, that's a signal to fix the state rather than keep the pinning — because affinity also prevents graceful instance replacement during platform maintenance.

Deployment slots 🔥 Must know

What they are

A slot is a separate running instance of your app on the same plan, with its own hostname. You deploy to it, verify it, then swap it with production.

The swap is a routing change — the warmed-up slot becomes production and the old production becomes the staging slot. Which is why rolling back is another swap, and takes seconds.

Swap stepWhat happens
1Production settings are applied to the staging slot
2The slot restarts with those settings
3Azure warms it up — requests the root path, or your configured warm-up paths
4Warm-up must succeed, or the swap is aborted
5Routing switches. The old production becomes staging
Senior signal — step 2 is why "it worked in staging" fails after a swap

The subtlety people miss: slot-specific settings are applied and the slot restarts before the swap.

So the app you verified in staging — with the staging database, the staging API keys — is not the app that goes live. Azure restarts it with production configuration first.

That's correct and necessary, and it means your verification in staging didn't test the production configuration. If a production setting is missing or malformed, you find out during the swap.

Which is why warm-up matters: it's the only check that runs against production settings before traffic switches. Configure WEBSITE_SWAP_WARMUP_PING_PATH to hit a real health endpoint that exercises the database and critical dependencies — then a bad production setting aborts the swap instead of taking the site down.

Mark settings as slot settings (sticky) for anything that must not follow the app — connection strings, environment name, keys. Everything else swaps with the app, which is usually what you want for application configuration.

  WEBSITE_SWAP_WARMUP_PING_PATH   = /health/ready
  WEBSITE_SWAP_WARMUP_PING_STATUSES = 200

  WEBSITE_WARMUP_PATH             = /health/ready   (for scale-out warm-up too)

  Mark as SLOT SETTINGS (do not swap):
    ConnectionStrings__Default
    ASPNETCORE_ENVIRONMENT
    ApplicationInsights__ConnectionString
Slots also give you canary releases

Beyond swapping, you can route a percentage of traffic to a slot — 10% to the new version, watch the metrics, then increase or roll back.

That's a genuine canary deployment with no extra infrastructure, and it's the safest way to release a change you're unsure about. Combine it with per-slot Application Insights and you can compare error rates and latency between versions directly.

One caveat: traffic routing uses a cookie to keep a user on the same version, so a user's experience is consistent — which is what you want, and it means the split isn't perfectly even per request.

Slots share the plan's resources

A slot isn't free capacity. It runs on the same App Service Plan, so a staging slot under load-test consumes the CPU and memory production needs.

Which means: don't run performance tests against a slot on the production plan, and be aware that several active slots on a small plan will contend.

For genuine load testing, use a separate plan. This is the same reasoning as keeping reporting off the production database — shared capacity means one workload can degrade another.

The distinction that gets confused

VNet integration is outbound only. It lets your app call into a virtual network. It does not make your app private — the public endpoint is still there.

To make the app private you need a private endpoint, which is the inbound counterpart.

Teams routinely enable VNet integration, assume the app is now internal, and leave a publicly-reachable endpoint. The two features are frequently used together and they solve opposite problems.

Also worth knowing: outbound IPs change when you scale or change tier, so third parties that allow-list your IP will break. A NAT Gateway gives a stable outbound address, which is the correct fix rather than repeatedly updating an allow-list.

Senior signal — the health check endpoint does real work

Configuring a health-check path isn't documentation. App Service polls it and takes unhealthy instances out of the load balancer, then replaces them if they stay unhealthy.

So a single bad instance — one with a corrupted connection pool, or one that's OOM-thrashing — stops receiving traffic automatically instead of failing a proportion of requests until someone notices.

The design matters though, and it's the same distinction as liveness versus readiness: the check should verify this instance can serve traffic, not that every dependency is up.

If the health check fails whenever the database is briefly unavailable, then every instance reports unhealthy simultaneously and App Service removes them all — turning a 30-second database blip into a full outage that you caused. Check the things specific to the instance; degrade gracefully on shared dependencies.

Always On, and why idle unloading catches people

By default App Service unloads an app after about 20 minutes of no requests. The next request pays a cold start — and any in-process background work simply stops.

So a BackgroundService or a hosted timer in a web app silently stops running on a low-traffic site. That's a genuinely confusing failure: the job worked in testing and mysteriously doesn't run overnight in production.

Always On prevents the unload, and it's available from Basic upward. Enable it for anything with background work or where first-request latency matters.

But the better answer for scheduled work is to move it out of the web app — into a Function with a timer trigger, or a separate worker — because a web app is scaled for request handling and its instance count is the wrong control for background jobs. And as noted above, scaling out makes an in-app timer run on every instance.

Key takeaways
  • You pay for the plan; apps on one plan share its resources.
  • Slots start at Standard — that's the minimum production tier.
  • Zone redundancy is Premium v3 only.
  • Scale out requires a stateless app — session, cache, files and timers all break otherwise.
  • An in-app scheduled job runs once per instance when scaled out.
  • Turn off ARR affinity unless you genuinely need it.
  • A swap applies production settings and restarts before switching — so staging didn't test production config.
  • Configure warm-up to a real health path; a failed warm-up aborts the swap.
  • Mark connection strings and environment as slot settings.
  • Traffic routing to a slot gives you a canary release for free.
  • VNet integration is outbound; a private endpoint is inbound. They're different problems.
  • Health checks remove bad instances — don't fail them on shared dependencies.
  • Always On, or background work stops when the app idles out.

Common mistakes

  • Basic tier in production, so no slots and no autoscale.
  • Scaling out with in-memory session or cache.
  • A background timer inside the web app, multiplying on scale-out.
  • ARR affinity left on for a stateless app.
  • No warm-up configured, so the first users after a swap hit a cold app.
  • Connection strings not marked as slot settings, so staging config swaps into production.
  • Load testing a slot on the production plan.
  • Assuming VNet integration makes the app private.
  • Third parties allow-listing outbound IPs that change on scale.
  • A health check that fails on database unavailability, removing every instance.
  • No Always On, so background work silently stops.

Interview questions

Intermediate

How do you deploy with zero downtime, and how do you roll back? 🔥 Must know
How I'd answer

"Deployment slots. Deploy to a staging slot, verify it, then swap with production."

"The reason this gives zero downtime is that the swap is a routing change, not a redeploy. The staging slot is already running and warmed; swapping just switches which one receives traffic. And the previous production version becomes the staging slot — so rollback is another swap, and it takes seconds."

"That's the key property. Without slots, a rollback means redeploying the previous build, which takes as long as a deployment and involves rebuilding or re-fetching an artefact — during an incident."

"The mechanics worth understanding, because there's a step people miss: when you initiate a swap, Azure applies production settings to the staging slot and restarts it, warms it up, and only then switches routing."

"Which means the app you verified in staging is not the app that goes live — it's restarted with production configuration first. So your staging verification didn't test the production settings. If a production connection string is wrong or missing, you'd find out during the swap."

"That's why warm-up configuration matters. Setting WEBSITE_SWAP_WARMUP_PING_PATH to a real health endpoint — one that exercises the database and critical dependencies — means Azure hits it with production settings applied, and a failure aborts the swap rather than taking the site down. It's the only check that runs against production config before traffic moves."

"I'd also mark the right things as slot settings, which are sticky and don't swap: connection strings, ASPNETCORE_ENVIRONMENT, the Application Insights connection string. Otherwise staging's database connection follows the app into production, which is the classic slot accident."

"Beyond swapping, slots also give canary releases: route 10% of traffic to the new version, watch error rate and latency, then increase or roll back. That's a genuine canary with no extra infrastructure, and it's the safest way to release something uncertain."

"Two caveats. Slots need Standard tier or above — Basic has none, which is the main reason not to run Basic in production. And slots share the plan's resources, so a staging slot under load test consumes CPU production needs; for real load testing I'd use a separate plan."

"One thing I'd add regardless of slots: the deployment has to be backward compatible with the database. Both versions run simultaneously during the swap and during any canary period, so a migration that renames a column breaks whichever version isn't expecting it. That's expand-and-contract across separate releases, and slots don't solve it."

What they're really checking
  • Do you know a swap is a routing change, hence instant rollback?
  • Do you know production settings are applied and the slot restarts first?
  • Do you configure warm-up, and know it can abort the swap?
  • Do you know about slot settings?
  • Do you raise database backward compatibility?
Weak answers
  • Red flag: "use slots" with no mechanism.
  • Red flag: no mention of warm-up or slot settings.
  • Red flag: no awareness that both versions run during the transition.
Likely follow-ups
  • What should the warm-up endpoint check?
  • How do you handle a database migration alongside this?
  • What if the new version is fine but slower?

Advanced

You scale out from one instance to three and things start breaking. Why? ⭐ Senior-level
How I'd answer

"Almost certainly local state — something that worked because there was only ever one instance. I'd check five things, roughly in order of how often they're the cause."

"In-memory session or cache. A request lands on instance 2 and the session stored on instance 1 isn't there, so users appear randomly logged out or lose form data. The fix is a distributed store — Redis — for both session and cache."

"Background timers inside the web app. This is the most damaging one and the least obvious. A BackgroundService or hosted timer runs on every instance, so a nightly job that sends invoices now sends them three times. Nothing errors — the work just happens repeatedly."

"The fix is to move scheduled work out to a Function with a timer trigger, which is a singleton by default, or guard it with a distributed lock. And really it belongs outside the web app anyway, because instance count is scaled for request handling and is the wrong control for background jobs."

"In-memory rate limiting or counters. ASP.NET Core's built-in rate limiter is per-instance, so a 100-per-minute limit becomes 300 across three instances. Same for any in-memory counter or deduplication set. Needs Redis-backed shared state."

"Local file writes. Uploads or generated files written to local disk. Worth knowing that App Service actually shares /home across instances by default, which cuts both ways — it may work, and it's slow and a contention point. Blob storage is the right answer."

"Singleton assumptions more generally — an in-memory queue, a static cache warmed at startup, a lock that only guards within one process."

"There's also an App Service specific thing I'd check: ARR affinity. It's on by default, pinning each client to one instance with a cookie. If that's what was masking the state problem, then turning it off would have surfaced these issues immediately — and leaving it on means scaling out doesn't help much, because existing clients stay pinned to their original instance."

"So for a stateless app I'd turn affinity off, and if the app genuinely needs it, that's a signal to fix the state rather than keep the pinning — affinity also prevents graceful instance replacement during platform maintenance."

"The broader point: these are all the same bug — state that lives in a process rather than a shared store. Which is why 'is this app stateless?' is the question to answer before you need to scale, not during a traffic spike. Running two instances in a test environment from the start surfaces every one of these immediately."

What they're really checking
  • Do you identify local state as the common cause?
  • Do you catch the background-timer multiplication?
  • Do you know in-memory rate limiting doesn't work across instances?
  • Do you know ARR affinity is on by default?
  • Do you suggest running two instances early to surface this?
Weak answers
  • Red flag: "scale back down."
  • Red flag: enabling affinity as the fix rather than a diagnosis.
  • Red flag: no mention of background jobs.
Likely follow-ups
  • How would you make a scheduled job run exactly once?
  • Where should uploaded files go?
  • How do you test for this before scaling?
