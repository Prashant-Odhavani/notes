Event Grid

The push-based one. It's how Azure services tell you something happened, and its routing-and-filtering model is what makes it different from a queue or a log.

🟡 Intermediate 🔴 Advanced 💡 Good to know
Quick revision
  • Push, not pull. Event Grid calls your handler; you don't poll.
  • System topics are free reactive hooks into Azure resource events.
  • Filtering happens in the service, so handlers only receive what they asked for.
  • Retries are built in, with exponential backoff and dead-lettering to blob.
  • At-least-once, unordered. Handlers must be idempotent and order-independent.
  • A webhook must complete the validation handshake before it gets events.
  • Reacting to blob events beats polling — this is the main practical use.

The subscription is where filtering belongs, and it's the feature that makes Event Grid worth using.

Without it, every handler receives every event and immediately discards most of them. On a busy storage account that's a Function invocation — billed, cold-start-prone — for each event you don't care about.

With subject prefix and suffix filters plus advanced filters on the event payload, the service decides. A subscription can say "only .jpg files, only under /uploads/, only where data.contentLength is above a threshold" and the handler is never invoked for anything else.

That's cheaper, simpler and more obvious: the routing rule is visible in the infrastructure definition rather than buried as an early return in a function. Someone reading the Bicep can see what triggers what.

Worth knowing the limits — advanced filters are capped per subscription (25 filters, 5 values each at time of writing), so genuinely complex routing may still need logic in the handler. But the first pass belongs in the subscription.

The distinction that decides it: notification or work?

Event Grid events are notifications. "A blob was created." "A resource was deleted." "An order was placed." The event says what happened, with identifiers — and the handler fetches whatever detail it needs.

Service Bus messages are work. "Process this payment." They're directed at a specific consumer, must not be lost, need retry and dead-letter semantics per message, and often need ordering.

So the question is: if this event is delivered twice, out of order, or 30 seconds late, is that fine? If yes, Event Grid. If it must be handled exactly in sequence with strong guarantees, Service Bus.

A useful sanity check on payload design: an Event Grid event should be small. If you're tempted to put the full order document in it, that's a sign the consumer is doing work rather than reacting to a fact — and it creates a coupling where the publisher must know what every consumer needs.

This is the event-carried state transfer versus event notification trade-off, and Event Grid is firmly on the notification side.

Dead-lettering is off by default, so failed events are silently discarded

This is the single most consequential default in Event Grid. If retries exhaust — the handler was broken for longer than the TTL, or returned 500 every time — the event is dropped, with no record anywhere unless you configured a dead-letter destination.

So a handler that was down for a day loses everything sent during that window, permanently, and nothing in the portal tells you what you lost.

Configure a dead-letter blob container on every subscription. It costs nothing and it's the difference between "we lost some events, we don't know which" and "here they are, we can replay them."

Then alert on that container being non-empty, because a dead-letter store nobody looks at is the same as no dead-letter store. And note the delay — dead-lettering isn't immediate; events land after the retry window closes, so the alert fires late by design.

Same principle as a Service Bus DLQ: the queue is only useful if someone is watching it.

Unordered and at-least-once — plan for it, don't hope

Event Grid makes no ordering promise at all, and it will deliver duplicates. Both are stated guarantees rather than edge cases, so a handler that assumes otherwise is simply wrong.

What that means concretely:

  • Handlers must be idempotent. Use the event id, which is stable across retries of the same event, to detect a repeat.
  • A created and a deleted event can arrive in either order. So processing "deleted" for something you haven't seen created must be handled, not crash.
  • Use the version or timestamp in the payload, not arrival order, to decide which state is newer. Discard anything older than what you've applied.
  • Prefer re-reading current state over trusting the payload. If the event says "blob created", read the blob — that's correct regardless of ordering or duplication.

That last point is why the notification model is robust: an event that just says what changed, with the handler fetching current state, is naturally tolerant of both re-delivery and reordering. An event carrying full state is not.

[Function("OnBlobCreated")]
public async Task Run(
    [EventGridTrigger] CloudEvent evt,
    CancellationToken ct)
{
    // 1. Idempotency: the event id is stable across retries
    if (!await _processed.TryMarkAsync(evt.Id, ct))
    {
        _log.DuplicateEvent(evt.Id);
        return;                          // already handled - return 2xx, do not retry
    }

    var data = evt.Data!.ToObjectFromJson<StorageBlobCreatedEventData>();

    // 2. Read current state rather than trusting the payload.
    //    Correct even if events arrive out of order or twice.
    var blob = _container.GetBlobClient(data.Url);
    if (!await blob.ExistsAsync(ct))
    {
        _log.BlobAlreadyDeleted(data.Url);
        return;                          // deleted since - not an error
    }

    await GenerateThumbnailAsync(blob, ct);

    // 3. Anything that throws returns non-2xx, so Event Grid retries.
    //    Transient failures are handled for you; permanent ones dead-letter.
}

Webhook validation 🔴 Advanced

The handshake, and why your endpoint gets no events

Before Event Grid sends events to an arbitrary HTTPS endpoint, the endpoint must prove it wants them. Otherwise Event Grid could be used to flood a third-party URL — an amplification attack, since anyone could subscribe someone else's endpoint.

So on subscription creation, Event Grid sends a validation event and the endpoint must either echo back the validationCode in its response, or call the validationUrl it was given.

Until that succeeds, the subscription is not active and no events flow. "I created a subscription and nothing arrives" is almost always this.

The practical shortcut: with Azure Functions, Logic Apps, Service Bus, Event Hubs or Storage Queues as the handler, there's no handshake — the platform handles it. It only applies to custom webhooks.

One more thing that catches people: the subscription is disabled if the endpoint stays unreachable for long enough. So an endpoint that was down during a long outage may need re-enabling, not just fixing.

Authenticate the delivery, not just the subscription

A validated webhook is publicly reachable, so anyone who finds the URL can post to it. The handshake proves the endpoint consented to receive events; it doesn't authenticate individual deliveries.

Options, roughly in order of preference: Entra ID authentication on the delivery, so Event Grid presents a token your endpoint validates; delivery with a managed identity to a protected endpoint; or at minimum a shared secret in a query parameter or header — weaker, and it should be stored in Key Vault and rotated.

For internal handlers, prefer Functions, Service Bus or Event Hubs destinations over a webhook entirely. Then delivery is authenticated by the platform and there's no public endpoint to defend.

Both schemas work and Event Grid can translate between them. CloudEvents is the one to pick for new development.

It's a CNCF specification, so the same event format is understood by Knative, Kafka tooling, other clouds and a wide range of libraries. Your event contract stops being Azure-shaped.

That matters more than it sounds: if a consumer ever moves off Azure, or you integrate with a partner who isn't on Azure, a standard envelope is the difference between a configuration change and a translation layer.

The type field is worth designing deliberately — reverse-DNS style, like com.contoso.orders.placed, and versioned, because the event type is a published contract and consumers filter on it. Renaming it later silently breaks every subscription filtering on the old name.

Key takeaways
  • Push-based: Event Grid calls your handler, retries and dead-letters for you.
  • System topics give free reactive hooks into Azure resource events.
  • Filter in the subscription, not the handler — cheaper and visible in IaC.
  • Events are notifications; keep payloads small and let handlers fetch state.
  • At-least-once and unordered, both guaranteed — handlers must be idempotent.
  • Use the event id for deduplication and payload version for ordering.
  • Dead-lettering is off by default; configure it and alert on the container.
  • Webhooks need the validation handshake; Azure-native handlers don't.
  • Authenticate deliveries too — prefer Entra ID over a shared secret.
  • Use CloudEvents for new work, and version the event type.
  • Reacting to blob events beats polling a container.

Common mistakes

  • No dead-letter destination, so exhausted events vanish silently.
  • A dead-letter container nobody monitors.
  • Assuming ordering, so a delete-before-create sequence crashes the handler.
  • A non-idempotent handler, duplicating work on redelivery.
  • Filtering in the handler, paying for invocations you discard.
  • Large payloads, coupling the publisher to consumers' needs.
  • Using Event Grid for work that needs ordering or per-message reliability.
  • Not completing the webhook handshake, then wondering where the events are.
  • An unauthenticated public webhook.
  • The Event Grid schema for new work instead of CloudEvents.
  • Renaming an event type, breaking every subscription filter.

Interview questions

Intermediate

A file lands in blob storage and you need to process it. How do you wire that up? 🔥 Must know
How I'd answer

"Event Grid, with a system topic on the storage account, subscribing a Function to BlobCreated."

"I'd specifically avoid the blob trigger, which is the obvious choice and the wrong one at any scale. The classic blob trigger works by polling and scanning logs, so there can be a delay of minutes on a container with many blobs, and it's unreliable for high volume."

"The Event Grid path is push-based: the storage account raises the event, Event Grid delivers it in seconds, and there's no scanning. Microsoft's own guidance is to use the Event Grid blob trigger rather than the polling one for anything beyond low volume."

"Then I'd do the filtering in the subscription, not in the function. A subject suffix filter for the extension, a prefix filter for the folder, and advanced filters on the payload if needed — so the function is only invoked for blobs it should actually process."

"That matters for two reasons: I'm not paying for invocations that immediately return, and the routing rule is visible in the infrastructure definition rather than hidden as an early return inside the code. Someone reading the Bicep can see what triggers what."

"On the handler, three things I'd get right."

"Idempotency. Event Grid is at-least-once, so the same event will sometimes arrive twice. The event id is stable across retries, so I'd record processed ids and skip repeats — importantly returning 2xx on a duplicate, because a non-2xx tells Event Grid to retry."

"Read the blob rather than trusting the event. The event tells me a URL; the blob is the truth. That's naturally correct even if events arrive out of order or twice — and I'd handle the blob no longer existing as a normal outcome rather than an error, because it may have been deleted since."

"Configure dead-lettering. This is off by default, and it's the important one. If my function is broken for longer than the retry window — 24 hours by default — the events are silently discarded. No record, no way to know what was lost. A dead-letter blob container costs nothing and turns that into a replayable list. Plus an alert on it being non-empty, because a dead-letter store nobody watches is the same as not having one."

"On error handling generally, I don't need retry logic in the function. Throwing returns a non-2xx and Event Grid retries with exponential backoff — so transient failures are handled by the platform. I only need to make sure a permanent failure doesn't retry pointlessly for 24 hours, so for something like a malformed file I'd log it, record it somewhere, and return success."

"If processing is long-running or needs strict per-file ordering, I'd have Event Grid deliver to a Service Bus queue instead of directly to a Function, and consume from there. That gets me the queue semantics — sessions for ordering, delivery count, a proper DLQ — with Event Grid still doing the detection. Event Grid for the trigger, Service Bus for the guarantees."

What they're really checking
  • Do you know the polling blob trigger is the weaker option?
  • Do you filter in the subscription?
  • Do you make the handler idempotent using the event id?
  • Do you know dead-lettering is off by default?
  • Do you know when to insert Service Bus in the path?
Weak answers
  • Red flag: blob trigger with no awareness of the polling delay.
  • Red flag: no mention of duplicates or dead-lettering.
  • Red flag: custom retry logic inside the handler.
Likely follow-ups
  • What happens if the function is down for two days?
  • How do you guarantee each file is processed once?
  • How would you handle a 20-minute processing job?

Advanced

Event Grid, Service Bus or Event Hubs — how do you choose? ⭐ Senior-level
How I'd answer

"I'd decide on what the message is, not on throughput numbers — because the throughput differences follow from the design rather than being the point."

"Service Bus when the message is work that must not be lost. 'Process this payment', 'send this invoice'. It tracks every message individually — a lock, a delivery count, a dead-letter queue — which is what gives you per-message retry, poison handling, sessions for ordering and transactional send. That bookkeeping is also what caps throughput, and it's worth paying for when each message matters."

"Event Hubs when it's a high-volume stream you may want to replay. Telemetry, clicks, metrics. It's a log, so reading advances a cursor rather than removing anything — multiple consumer groups read independently, and I can reset an offset to reprocess. The cost is that there's no per-event state at all, so no dead-letter and no per-message retry. Error handling is my code."

"Event Grid when it's a notification and something needs to react. 'A blob was created', 'a resource was deleted', 'an order was placed'. It's push-based, so no polling infrastructure, and the filtering happens in the service so handlers only get what they subscribed to."

"The clarifying questions I'd actually ask:"

"Does order matter? Event Grid gives none at all — that alone eliminates it for many cases. Service Bus sessions give per-session order. Event Hubs gives per-partition order."

"Do I need to replay? Only Event Hubs. If reprocessing history is a requirement, the decision is made."

"Is a lost message acceptable? With Service Bus, no — it sits in the queue until handled or dead-lettered. With Event Grid, retries exhaust after the TTL and the event is dropped unless dead-lettering is configured, which is off by default. That default has surprised a lot of teams."

"Who consumes it? One known consumer doing work points at Service Bus. Several unknown or evolving consumers reacting points at Event Grid, because adding a subscription changes nothing for the publisher."

"Push or pull? If the handler can't be reached — it's behind a firewall, or it needs to control its own rate — push doesn't work and Event Grid is out, or needs a Service Bus queue as the destination."

"The part I'd emphasise is that these compose, and the good designs usually use more than one. Event Grid detects a blob and delivers to a Service Bus queue so the actual processing gets queue semantics — sessions, delivery count, a real DLQ — with Event Grid doing the detection. Or Event Hubs ingests telemetry at volume and a consumer converts the few events needing reliable handling into Service Bus messages."

"So it's rarely 'pick one'. It's use each where its guarantees match the need, and be able to say what each one is giving you. The failure mode is picking one service for everything and then rebuilding the others' semantics badly on top of it — hand-rolled dead-lettering on Event Hubs, or polling a queue because you needed push."

What they're really checking
  • Do you decide on message semantics rather than throughput?
  • Can you name what each service uniquely provides?
  • Do you know Event Grid has no ordering and drops by default?
  • Do you see them as composable rather than exclusive?
  • Do you ask about consumers, replay and push versus pull?
Weak answers
  • Red flag: choosing purely on throughput figures.
  • Red flag: treating them as interchangeable.
  • Red flag: no mention of ordering or delivery guarantees.
Likely follow-ups
  • Design the pipeline for IoT telemetry that also triggers alerts.
  • How would you get ordered processing from Event Grid?
  • When is Storage Queues good enough?
