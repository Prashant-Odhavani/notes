The pattern in all of them

Every answer is a trade-off, and naming the cost is what distinguishes a good one.

"I'd use AKS" is weak. "I'd use Container Apps because we need scale-to-zero and Dapr but don't have a platform team to run AKS — and we'd lose the fine-grained control if we later need custom scheduling" is the shape they're listening for.

Senior signal — Container Apps changed the default answer

The old choice was App Service for simple things and AKS for anything container-based, which meant teams took on Kubernetes to get containers, service discovery and independent scaling.

Container Apps gives most of that without the cluster. It's Kubernetes underneath — KEDA for event-driven scaling, Envoy for ingress, Dapr available — with none of it exposed. You get containers, revisions, traffic splitting, scale-to-zero and managed certificates, and you never touch a node pool, a cluster upgrade or a networking plugin.

So the honest position now: AKS needs justifying, not assuming. Reach for it when you genuinely need custom scheduling, DaemonSets, operators, GPU workloads, a service mesh you control, or you already have deep Kubernetes expertise and tooling.

"I'd use Container Apps unless we specifically need cluster-level control" is a stronger answer than defaulting to AKS — because it recognises that running Kubernetes is a full-time commitment that many teams take on without accounting for it.

Managed identity 🔥 Must know

The single highest-value Azure practice

A managed identity is an Entra ID identity attached to your Azure resource. The platform issues and rotates the tokens.

Which means there is no secret — nothing in configuration, nothing in Key Vault, nothing to leak in a log or a screenshot or a repository.

// One credential type works locally (your az login) and in Azure (managed identity)
var credential = new DefaultAzureCredential();

builder.Services.AddSingleton(new BlobServiceClient(
    new Uri("https://myaccount.blob.core.windows.net"), credential));

builder.Services.AddSingleton(new ServiceBusClient(
    "mynamespace.servicebus.windows.net", credential));

// Even SQL - no password in the connection string
// "Server=tcp:my.database.windows.net;Database=app;Authentication=Active Directory Default;"
ApproachWhat can leak
Connection string in appsettings.jsonEverything — it's in source control
Connection string in app settingsReadable by anyone with portal access
Secret in Key VaultThe secret still exists, and needs rotating
Managed identityNothing — there is no secret
Senior signal — Key Vault is an improvement, not the answer

"Put the secrets in Key Vault" is the common answer and it's a middle step. You've moved the secret somewhere better and you still have a secret — to store, rotate, audit, and grant access to.

Managed identity removes it entirely. There's no credential to rotate because there's no credential.

So the ordering is: managed identity wherever the service supports it — storage, Service Bus, Key Vault, SQL, Cosmos, Event Hubs all do — and Key Vault only for secrets that genuinely can't be replaced by an identity, typically third-party API keys.

And DefaultAzureCredential is what makes it practical: the same code authenticates via your az login locally and via managed identity in Azure, so there's no "works on my machine" divergence and no local secrets either.

The three costs that surprise teams

Application Insights ingestion. Billed per GB of telemetry. Verbose logging on a high-traffic app can cost more than the compute running it. Sampling and log-level discipline are cost controls, not just tidiness — covered on the App Insights page.

Storage transactions. Everyone budgets for GB stored; few budget for operations. A chatty application doing millions of small blob reads can spend more on transactions than on storage — and the cool and archive tiers have higher transaction costs, so moving data there to save money can increase the bill if it's accessed often.

Cross-region egress. Data leaving a region is charged. A chatty service in one region calling a database in another pays per byte, continuously, and it's invisible until you look at the networking line.

All three share a shape: the obvious dimension is priced sensibly and a second dimension isn't budgeted for. That's the thing to look for on any Azure bill.

Where would you host a new .NET API on Azure? 🔥 Must know
How I'd answer

"I'd ask a few things first, because the answer genuinely depends: is it containerised, does it need to scale to zero, how many services are we running, and do we have anyone to operate Kubernetes?"

"For a single web API with steady traffic, App Service. It's the lowest operational burden, deployment slots give zero-downtime releases and easy rollback, it has built-in authentication, and there's essentially nothing to manage. Not fashionable, and frequently correct."

"For several services, or anything containerised, my default is now Container Apps rather than AKS. That's the answer that's changed in the last few years and it's worth being explicit about."

"Container Apps is Kubernetes underneath — KEDA for event-driven scaling, Envoy for ingress, Dapr available — with none of it exposed. So you get containers, revisions, traffic splitting for canary releases, scale-to-zero, service discovery and managed certificates, and you never touch a node pool, a cluster upgrade, or a CNI plugin."

"Which means AKS now needs justifying rather than assuming. I'd reach for it when there's a genuine need for cluster-level control — custom scheduling, DaemonSets, operators, GPU workloads, a service mesh we configure ourselves — or when the team already has deep Kubernetes expertise and tooling, in which case the familiarity argument is real."

"Running AKS is a standing commitment: node image upgrades, Kubernetes version upgrades every few months, networking, RBAC, cluster autoscaler tuning, and someone on call who understands it. Teams routinely take that on to get containers, which Container Apps now provides without it."

"For event-driven or spiky work — a queue processor, a webhook handler, scheduled jobs — Functions on the Consumption plan, because you pay almost nothing when idle and it scales out automatically. The caveat is cold start, so I wouldn't put a latency-sensitive user-facing API on Consumption; the Premium plan with pre-warmed instances fixes that and costs like an App Service plan, at which point I'd ask what Functions is buying."

"Two things I'd decide regardless of the host."

"Managed identity, not connection strings. Storage, Service Bus, SQL, Cosmos and Key Vault all support it, so there's no secret to store or rotate — and DefaultAzureCredential means the same code works locally via az login. 'Put the secrets in Key Vault' is a middle step; the better answer is not having a secret."

"And Application Insights with OpenTelemetry from the start, because retrofitting observability after the first production incident is much harder than having it — though I'd configure sampling deliberately, since ingestion is billed per GB and verbose logging on a busy app can cost more than the compute."

What they're really checking
  • Do you ask about containers, scale-to-zero, service count and team capability?
  • Do you know Container Apps changed the default?
  • Will you say App Service when it's right?
  • Do you treat AKS as needing justification?
  • Do you know Functions' cold-start caveat?
  • Do you mention managed identity unprompted?
Weak answers
  • Red flag: "AKS, because microservices."
  • Red flag: no mention of operational burden.
  • Red flag: connection strings in configuration.
Likely follow-ups
  • How do deployment slots actually work?
  • What causes a Functions cold start and how do you avoid it?
  • When would AKS genuinely be right?
