Service Bus

The broker with real messaging semantics. Most of what makes it worth choosing is per-message control that Event Hubs and Kafka structurally cannot offer.

🟡 Intermediate 🔴 Advanced 🔥 Must know
Quick revision
  • Queue = one consumer per message. Topic = a copy per subscription.
  • Peek-lock is the default and the right choice — the message returns if you crash.
  • The lock expires. Slow processing means redelivery, so renew or process faster.
  • Dead-lettering is built in, and you must monitor the DLQ.
  • Sessions give ordering — at the cost of one consumer per session.
  • Duplicate detection is by MessageId, within a time window.
  • Scheduled delivery is native — no polling table needed.

// Only high-value orders reach this subscription - filtered at the broker,
// so the consumer never sees or pays for the rest.
await admin.CreateSubscriptionAsync(
    new CreateSubscriptionOptions("orders", "high-value"),
    new CreateRuleOptions("value-filter",
        new SqlRuleFilter("total > 10000 AND region = 'UK'")));

// A correlation filter is cheaper to evaluate than SQL - prefer it when
// you're matching on equality alone.
await admin.CreateSubscriptionAsync(
    new CreateSubscriptionOptions("orders", "uk-only"),
    new CreateRuleOptions("uk", new CorrelationRuleFilter { Subject = "UK" }));
Filter at the broker, not in the consumer

A consumer that receives every message and discards 95% of them still pays for the receive operation, the lock, the network transfer and the completion — for messages it doesn't want.

A subscription filter evaluates at the broker, so those messages never reach you. On a high-volume topic that's a substantial reduction in operations, which on the Standard tier is what you're billed for.

Correlation filters are cheaper than SQL filters because they only do equality matching on system and user properties. So use a correlation filter for "region = UK" and reserve SQL filters for genuine expressions.

One trap: a subscription with no rule receives everything, and creating a subscription adds a default true rule. If you add your own filter without removing the default, you still get everything.

Peek-lock and the lock duration 🔥 Must know

ModeBehaviourOn crash
Peek-lock (default) Message is locked, not removed. You complete, abandon or dead-letter it Lock expires; message returns
Receive-and-delete Removed the moment it's delivered Message is lost 
var processor = client.CreateProcessor("orders", new ServiceBusProcessorOptions
{
    MaxConcurrentCalls = 10,
    // Auto-complete on success, abandon on exception. Usually what you want.
    ReceiveMode = ServiceBusReceiveMode.PeekLock,
    // Renews the lock while the handler runs - critical for slow processing
    MaxAutoLockRenewalDuration = TimeSpan.FromMinutes(10)
});

processor.ProcessMessageAsync += async args =>
{
    var order = args.Message.Body.ToObjectFromJson<Order>();

    try
    {
        await HandleAsync(order, args.CancellationToken);
        // Auto-completed on return
    }
    catch (ValidationException ex)
    {
        // PERMANENT failure - retrying will never work. Dead-letter explicitly.
        await args.DeadLetterMessageAsync(args.Message,
            deadLetterReason: "ValidationFailed",
            deadLetterErrorDescription: ex.Message);
    }
    // Transient exceptions propagate -> message is abandoned -> redelivered
};
Lock expiry is the failure that produces mysterious duplicates

The lock has a duration — 30 seconds by default, maximum 5 minutes. If your handler takes longer and the lock isn't renewed, the broker assumes you died and redelivers the message to another consumer.

So the same message is now being processed twice, concurrently. And when your original handler finishes and tries to complete it, that throws ServiceBusException with MessageLockLost — after the work has already been done.

The symptom is duplicate side effects with no obvious cause: two emails, two charges, two rows. And it only appears under load, when handlers slow down.

Two fixes. MaxAutoLockRenewalDuration on the processor, which renews in the background while your handler runs — this is the one people miss. And make handlers idempotent, because renewal can still fail and delivery is at-least-once regardless.

Also note MaxDeliveryCount, default 10: after that many abandons the message is automatically dead-lettered. So a message failing on a lock timeout ten times disappears into the DLQ, which is another reason to monitor it.

Dead-lettering 🔥 Must know

A message is dead-lettered when
MaxDeliveryCount is exceeded — default 10 abandons
You call DeadLetterMessageAsync explicitly
The message expires (TimeToLive) and dead-lettering on expiry is enabled
It fails a subscription filter evaluation
It exceeds the max size or the session can't be accepted
Senior signal — the DLQ is a real queue, and that has consequences

The dead-letter queue isn't a log — it's a sub-queue you can receive from, at <queue>/$deadletterqueue. Which means replay is a first-class operation: read from the DLQ, fix or resubmit.

Three consequences people miss.

It counts against your quota. DLQ messages consume the entity's storage, so an unattended DLQ can eventually fill the queue and block new messages entirely.

DLQ messages don't expire by default. They accumulate indefinitely unless you handle them.

You need a replay path built in advance. The reason to dead-letter rather than drop is that you can reprocess after a fix — and teams dead-letter diligently for a year then discover during an incident that they have no tooling to resubmit, so they're writing it under pressure.

And the alerting rule: alert on DLQ depth greater than zero, not on a threshold. Any dead-lettered message is by definition unhandled, so a threshold means silently accepting some data loss. An unmonitored DLQ is the quietest form of losing data there is.

Sessions and ordering 🔥 Must know

// Publishing: SessionId groups related messages
await sender.SendMessageAsync(new ServiceBusMessage(payload)
{
    SessionId = order.Id.ToString(),     // all messages for THIS order, in order
    MessageId = eventId.ToString()       // for duplicate detection
});

// Consuming: a session processor locks a whole session to one consumer
var processor = client.CreateSessionProcessor("orders", new ServiceBusSessionProcessorOptions
{
    MaxConcurrentSessions = 20,          // 20 orders in parallel...
    MaxConcurrentCallsPerSession = 1     // ...but strictly ordered within each
});
The trade

A session is locked to a single consumer, and processed one message at a time. That's what guarantees order.

So ordering costs parallelism within a session, and you get parallelism across sessions. With a session per order you can process twenty orders concurrently while each order's messages stay in sequence.

Which means the design question is: what's the smallest scope that genuinely needs ordering? Usually one entity — never the whole queue.

Sessions must be enabled at creation, and they change the failure mode

You cannot enable sessions on an existing queue. It's set at creation, so adding ordering later means creating a new entity and migrating — the same shape as an immutable partition key.

And a session introduces head-of-line blocking: a message that keeps failing blocks its session, because the consumer can't skip it without breaking order. Every subsequent message for that order waits.

Dead-lettering it unblocks the session and breaks ordering for that entity. That's a deliberate choice of availability over ordering, and it should be made consciously rather than discovered.

Sessions also enable session state — a small blob of data associated with the session, which is useful for stateful sequences without an external store.

Duplicate detection 🟡 Intermediate

await admin.CreateQueueAsync(new CreateQueueOptions("orders")
{
    RequiresDuplicateDetection = true,
    DuplicateDetectionHistoryTimeWindow = TimeSpan.FromMinutes(10)
});

// The broker discards a second message with the same MessageId
// inside the window. So MessageId must be DETERMINISTIC.
await sender.SendMessageAsync(new ServiceBusMessage(payload)
{
    MessageId = $"order-placed:{order.Id}"      // NOT Guid.NewGuid()
});
It only works if MessageId is deterministic

Duplicate detection compares MessageId. If you generate a new Guid per send, a retry produces a different id and the duplicate is not detected — you've enabled the feature and it does nothing.

The id must be derived from the event: order-placed:{orderId}, or a business idempotency key. Then a retried publish is recognised as the same message.

Two limits to know. It's publisher-side only — it stops the same message being enqueued twice; it does nothing about a consumer processing one message twice after a lock timeout. So consumers still need to be idempotent.

And the window is bounded — maximum 7 days, and a larger window costs storage and throughput. A retry outside the window isn't detected.

So it's a useful belt alongside consumer idempotency, not a replacement for it.

Scheduled and deferred messages ⭐ Senior-level

// Deliver in 24 hours - no polling table, no timer, no background scanner
long sequenceNumber = await sender.ScheduleMessageAsync(
    new ServiceBusMessage(reminderPayload),
    DateTimeOffset.UtcNow.AddHours(24));

// Cancellable if circumstances change
await sender.CancelScheduledMessageAsync(sequenceNumber);

// Deferral: set aside a message you can't handle yet, keep the sequence number
await args.DeferMessageAsync(args.Message);
var deferred = await receiver.ReceiveDeferredMessageAsync(sequenceNumber);
Senior signal — this is a genuine differentiator against Kafka

Scheduled delivery replaces a whole pattern people otherwise build: a table of pending work, a background service polling it every minute, and the accompanying concerns about missed windows, duplicate scheduling and clock skew.

With Service Bus it's one call, it's durable, and it's cancellable by sequence number.

Kafka has no equivalent. Delayed retry there means tiered retry topics — orders.retry.5m, orders.retry.1h — with consumers that wait, which is real machinery to build and operate, and a message moved to a retry topic loses its ordering relationship with its siblings.

Deferral is the other one with no Kafka analogue: set a message aside without losing it or blocking the queue, and retrieve it later by sequence number. Useful when a message arrives before its prerequisite — you defer rather than abandon-and-retry, so you don't burn delivery attempts.

Naming these as reasons to prefer Service Bus over a log-based broker is a stronger answer than "Service Bus is for lower volume".

Standard is shared capacity, and that means variable latency

Basic and Standard run on multi-tenant infrastructure, so throughput and latency vary with what other tenants are doing. It's fine for most workloads and it isn't predictable.

Premium gives dedicated resources, so latency is consistent — plus VNet integration, private endpoints, geo-disaster-recovery, and 100 MB messages.

The billing difference matters for planning: Standard is per operation, so a chatty low-volume system can be surprisingly expensive; Premium is per messaging unit per hour, so it's a fixed cost regardless of volume. High steady volume is usually cheaper on Premium.

Two things that catch people: Basic has no topics at all, so choosing it forecloses publish-subscribe entirely. And large messages should use the claim-check pattern — store the payload in blob storage, send a reference — rather than reaching for Premium's 100 MB limit, because large messages are slow to move and expensive to retry.

Key takeaways
  • Queue for work (one consumer), topic for events (a copy per subscription).
  • Filter at the broker with subscription rules; correlation filters are cheaper than SQL.
  • A new subscription has a default true rule — remove it or you receive everything.
  • Peek-lock by default. Receive-and-delete loses messages on crash.
  • Lock expiry causes concurrent duplicate processing — set MaxAutoLockRenewalDuration and be idempotent.
  • MaxDeliveryCount (10) auto-dead-letters, so monitor the DLQ.
  • The DLQ is a real queue: it counts against quota, doesn't expire, and needs a replay path.
  • Alert on DLQ depth > 0, not a threshold.
  • Sessions give per-entity ordering, cost intra-session parallelism, and can't be enabled later.
  • Duplicate detection needs a deterministic MessageId and is publisher-side only.
  • Scheduled delivery and deferral are genuine advantages over log-based brokers.
  • Basic has no topics; Standard is shared capacity; Premium is dedicated and fixed-cost.

Common mistakes

  • Receive-and-delete for work that matters.
  • No lock renewal on slow handlers, producing concurrent duplicates.
  • Non-idempotent consumers, so redelivery duplicates side effects.
  • An unmonitored dead-letter queue.
  • No replay tooling for dead-lettered messages.
  • Retrying permanent failures until MaxDeliveryCount instead of dead-lettering explicitly.
  • MessageId = Guid.NewGuid() with duplicate detection enabled.
  • Filtering in the consumer instead of on the subscription.
  • Leaving the default subscription rule alongside a new filter.
  • Choosing Basic then needing topics.
  • Large payloads inline rather than a claim check.
  • Assuming sessions can be added later.

Interview questions

Intermediate

A consumer processes the same message twice. Why, and how do you fix it? 🔥 Must know
How I'd answer

"The most likely cause with Service Bus specifically is lock expiry, and it's worth explaining the mechanism because the symptom looks like a mystery."

"In peek-lock mode the broker locks the message rather than deleting it — 30 seconds by default, maximum five minutes. If my handler takes longer than the lock duration and the lock isn't renewed, the broker assumes the consumer died and redelivers to another consumer. So now the same message is being processed twice, concurrently."

"And when the original handler finishes and tries to complete, it gets a MessageLockLost exception — after the work has already been done. So you see duplicate side effects plus a confusing exception, and only under load when handlers slow down."

"The immediate fix is MaxAutoLockRenewalDuration on the processor, which renews the lock in the background while the handler runs. That's the setting people miss — the default renewal window is short relative to real processing times."

"I'd also look at whether the handler should take that long. If it's doing a synchronous HTTP call or a heavy database operation per message, the better fix may be to make it faster, or to accept the message and queue the slow part."

"But the durable answer is idempotency, because Service Bus is at-least-once by design and no configuration removes that. Renewal can still fail, the process can crash between doing the work and completing the message, and a network blip can lose the completion acknowledgement."

"So I'd implement the inbox pattern: record the MessageId in a table with a unique constraint, in the same database transaction as the work. A duplicate hits the constraint and is skipped."

"The same-transaction detail is the critical one — if I record the id and commit separately from the work, a crash between them means the message is marked processed but the work never happened. That turns duplicate delivery into lost work, which is strictly worse and silent."

"Two other things I'd check. MaxDeliveryCount, default 10 — if the message keeps failing on lock timeout it'll be auto-dead-lettered after ten attempts, so I'd look at the DLQ for evidence. And duplicate detection on the queue, which helps only if MessageId is deterministic — if the publisher generates a fresh Guid per send, a retried publish isn't detected. That's publisher-side anyway, so it wouldn't fix this particular case."

What they're really checking
  • Do you know about lock duration and expiry?
  • Do you know MaxAutoLockRenewalDuration?
  • Do you land on idempotency as the durable fix?
  • Do you know the dedupe record must share the transaction?
  • Do you know duplicate detection is publisher-side?
Weak answers
  • Red flag: "switch to receive-and-delete" — that loses messages instead.
  • Red flag: no mention of idempotency.
  • Red flag: assuming duplicate detection solves consumer-side duplicates.
Likely follow-ups
  • How do you prune the dedupe table?
  • What if the work isn't in a database?
  • How would you detect this happening in production?

Advanced

You need messages for one order processed in order, but high throughput overall. How? ⭐ Senior-level
How I'd answer

"Sessions, with the order id as the SessionId. That gives ordering per order and parallelism across orders, which satisfies both requirements."

"The mechanism: a session is locked to a single consumer and processed one message at a time — that's what guarantees order. So with a session processor I'd set MaxConcurrentSessions to something like 20 and MaxConcurrentCallsPerSession to 1. Twenty orders in flight simultaneously, each internally sequential."

"So throughput scales with the number of distinct orders, not with a single consumer's speed."

"Three things I'd flag."

"Sessions must be enabled when the queue is created. You cannot add them to an existing queue — that's a new entity and a migration. So this is a design-time decision, the same shape as an immutable partition key."

"A failing message blocks its session. Head-of-line blocking: the consumer can't skip it without breaking order, so every subsequent message for that order waits. Dead-lettering it unblocks the session and breaks ordering for that order — which may be fine or may corrupt state, depending on whether the handlers are commutative. That's a deliberate availability-over-ordering choice and it should be made consciously."

"A hot session still serialises. If one order generates most of the traffic, that session is the bottleneck and adding consumers won't help, because a session can only ever be handled by one consumer. Same shape as a hot partition."

"The broader point I'd make though: I'd first try to make ordering unnecessary, because it's expensive beyond the throughput cost — it also creates the head-of-line blocking problem."

"The most useful technique is state-based rather than delta-based messages. 'The order status is now Shipped' is order-independent and idempotent — applying it twice or out of sequence gives the same result. 'Advance the status' is neither. So designing messages as facts about current state rather than increments dissolves the whole problem."

"Alternatively, include a version or sequence number and have the consumer ignore anything older than what it has already applied. That handles out-of-order arrival rather than preventing it, so you keep full parallelism and lose the blocking risk."

"So my order of preference: design so ordering doesn't matter; if it genuinely does, sessions keyed to the smallest scope that needs it — normally one entity, never the whole queue."

"One practical warning: scaling consumers on a non-session queue silently breaks ordering. If a team adds instances to clear a backlog without realising sessions weren't enabled, they've introduced a correctness bug to fix a throughput problem — and it won't be obvious until something processes out of sequence."

What they're really checking
  • Do you know sessions are the mechanism, and how they trade parallelism?
  • Do you know sessions can't be enabled later?
  • Do you know about head-of-line blocking?
  • Do you try to eliminate the ordering requirement first?
  • Do you know state-vs-delta message design?
Weak answers
  • Red flag: "use one consumer" with no session awareness.
  • Red flag: claiming you can have global ordering and high throughput.
  • Red flag: no mention of what happens when a message fails.
Likely follow-ups
  • What happens if one session's message keeps failing?
  • How would you handle a dominant order generating most traffic?
  • What's session state for?
