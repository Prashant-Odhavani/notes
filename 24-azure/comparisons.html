Azure Service Comparisons

If you read one page in this section, read this one. Choosing correctly between similar services is what actually gets tested.

🟡 Intermediate ⭐ Senior-level 🔥 Must know
The decision rules, in one place
  • Service Bus = a message must be processed. Event Hubs = a high-volume stream. Event Grid = something happened.
  • App Service for a web app. Container Apps for containers without a cluster. AKS only when you need cluster control.
  • Functions for event-driven and spiky; watch cold start.
  • Blob for files, Table/Cosmos for structured, Queue only if Service Bus is overkill.
  • App Configuration for settings and flags; Key Vault for secrets — and managed identity instead of secrets where possible.
  • Redis to cache; Cosmos to store globally; SQL for relational.

Messaging: the three-way distinction 🔥 Must know

The framing that makes it obvious

These aren't the same service at different scales. They answer different questions.

Service Bus — "this work must be done." Event Hubs — "here is a firehose of data." Event Grid — "something happened, react if you care."

Senior signal — the questions that separate them

"Must every message be processed, or is it a stream where losing one is acceptable?" Processing → Service Bus. Stream → Event Hubs.

"Do I need to dead-letter, defer or schedule an individual message?" Only Service Bus can. Event Hubs tracks an offset, so acknowledging message 6 acknowledges 0–5 — you cannot skip one without committing past it.

"Do several independent consumers need the same data, possibly replaying it?" Event Hubs. Service Bus deletes on consumption.

"Am I reacting to Azure resource changes?" Event Grid — it's the only one with native publishers for blob-created, resource-modified and similar platform events.

The mistake I'd flag: using Event Hubs for work distribution. It looks like a queue and isn't. You'd have to build dead-lettering yourself, and a poison message blocks its partition indefinitely. That's the same log-versus-queue distinction as Kafka, because Event Hubs is Kafka-compatible.

Event Grid is push, and that changes the design

Service Bus and Event Hubs are pull — your consumer asks for messages, so it controls the rate.

Event Grid pushes to an HTTP endpoint, a Function, a queue. Which means you don't control the arrival rate, so your handler must absorb bursts or you need a queue in front. And it requires an endpoint reachable by Azure, plus subscription validation.

It also has no ordering guarantee at all — events can arrive out of order or more than once, so handlers must be idempotent and order-independent.

The common production pattern is Event Grid to a Service Bus queue: Grid gives you the platform event sources and fan-out filtering, the queue gives you buffering, ordering via sessions, and per-message dead-lettering. Using both deliberately is a good answer.

The decision, in order
  1. One web app or API, steady traffic? App Service. Slots, easy, nothing to manage.
  2. Event-driven, spiky, or glue? Functions — accepting cold start on Consumption.
  3. Several containerised services? Container Apps.
  4. Do you genuinely need cluster-level control? Only then, AKS.

Notice that AKS is last and conditional. That ordering is the answer.

The Functions cold-start trade, stated properly

On the Consumption plan, an idle Function app is deallocated. The next request pays a cold start — commonly hundreds of milliseconds to several seconds, worse for large dependency graphs.

So Consumption is right for background and event-driven work where nobody is waiting: a queue processor, a webhook receiver, a scheduled job. It's wrong for a latency-sensitive user-facing API, where an occasional three-second response is unacceptable.

The Premium plan fixes it with pre-warmed instances and adds VNet integration and no timeout limit — and it costs like an App Service plan, at which point the honest question is what is Functions buying you? If the answer is "the bindings and the triggers", that's legitimate. If it's "serverless", you've lost the property that made it serverless.

Being able to say "Premium removes the cold start and the cost advantage together" is the calibrated answer.

Queue Storage vs Service Bus — the distinction to know

Queue Storage is cheaper and scales enormously, and it's much less capable. No topics, no sessions, no dead-letter queue, no scheduled delivery, no duplicate detection, no transactions, and only at-least-once with a visibility timeout.

So the rule: Queue Storage when you need a simple buffer at very high volume and low cost. Service Bus when you need any of the messaging semantics — which for most business workloads you do, because dead-lettering alone is close to mandatory.

Choosing Queue Storage and then hand-building dead-lettering and scheduling is the failure mode. That work is what you're paying Service Bus for.

Blob access tiers: the transaction-cost inversion

Hot, Cool, Cold and Archive get progressively cheaper to store and progressively more expensive to access.

So moving frequently-read data to Cool to save money can increase the bill, because the transaction and retrieval charges exceed the storage saving. And Archive requires a rehydration of hours before you can read at all — it's genuinely offline.

Lifecycle management policies automate the transitions by age, which is the right mechanism. The judgement is when — and it depends on access frequency, not just age.

This is the same shape as the general Azure cost trap: the obvious dimension is priced sensibly and a second dimension isn't budgeted for.

The ordering

1. Managed identity wherever the target supports it — storage, Service Bus, SQL, Cosmos, Key Vault, Event Hubs all do. No secret exists, so nothing can leak or needs rotating.

2. Key Vault for secrets that genuinely can't be replaced by an identity — typically third-party API keys.

3. App Configuration for non-secret settings and feature flags, especially shared across services.

Never a connection string in appsettings.json.

Two configuration traps

Key Vault charges per operation and adds latency. Reading a secret on every request is slow and costly. The provider caches, and you must set a refresh interval deliberately — too short and you pay, too long and a rotated secret isn't picked up. Neither default is right for every case.

App Configuration doesn't refresh by itself. Registering the provider gets values at startup; picking up changes requires configuring sentinel-key-based refresh. Teams routinely believe they have dynamic configuration and discover on the first attempted change that a restart is needed.

Both failures look like the feature working until you actually rely on it.

Senior signal — instrument with OpenTelemetry, export to App Insights

The older approach was the Application Insights SDK, which works and couples your instrumentation to Azure.

OpenTelemetry is now the recommended path, including by Microsoft. You instrument once against a vendor-neutral standard and export to App Insights — and if you later move to Grafana, Datadog or anything else, you change the exporter rather than the instrumentation.

It also gives consistent tracing across services regardless of language, which matters in a polyglot estate.

And it's the same instrumentation described in microservices observability — so the trace-id propagation, baggage and sampling reasoning carries over directly.

Interview questions

The one that comes up most

Service Bus, Event Hubs or Event Grid — how do you choose? 🔥 Must know
How I'd answer

"They're often presented as three messaging services at different scales, and that framing is what makes the choice confusing. They answer different questions."

"Service Bus is for when a message must be processed. It's a queue or topic — the message is delivered to a consumer, and once completed it's deleted. Critically it has per-message operations: dead-letter this one, defer that one, schedule delivery for later, detect duplicates. That's what you want for business work — placing an order, sending an invoice, charging a card."

"Event Hubs is a high-volume partitioned log. Data is retained after consumption, consumers track their own offset, so many independent consumers can read the same stream and any of them can replay. That's telemetry, IoT, clickstream — millions of events a second where the value is in the aggregate."

"Event Grid is for notifying that something happened, and it's the only one that pushes. It has native publishers for Azure platform events — a blob was created, a resource changed — and it fans out to subscribers with filtering."

"The questions I'd use to decide:"

"Must every message be processed, or is it a stream where losing one doesn't matter? Processing means Service Bus."

"Do I need to dead-letter, defer or schedule an individual message? Only Service Bus can. Event Hubs tracks an offset, which is a position — so acknowledging message 6 implicitly acknowledges everything before it. You cannot skip a bad message without committing past it."

"Do several independent consumers need the same data, possibly replaying history? Event Hubs, because Service Bus deletes on consumption."

"Am I reacting to Azure resource changes? Event Grid."

"The mistake I'd specifically call out is using Event Hubs for work distribution. It looks like a queue and isn't — you'd hand-build dead-lettering, and an unhandled poison message blocks its partition indefinitely because you can't commit past it without acknowledging it. It's exactly the same log-versus-queue distinction as Kafka, which makes sense since Event Hubs is Kafka protocol-compatible."

"Two things about Event Grid that change the design. It's push, so you don't control the arrival rate — your handler has to absorb bursts. And it has no ordering guarantee at all, and can deliver more than once, so handlers must be idempotent and order-independent."

"Which is why the common production pattern is Event Grid into a Service Bus queue: Grid gives you the platform event sources and filtered fan-out, the queue gives you buffering, ordering via sessions, and per-message dead-lettering. Using them together deliberately is usually better than picking one and working around what it lacks."

What they're really checking
  • Do you know they solve different problems, not the same one at different scales?
  • Do you know Service Bus is the only one with per-message operations?
  • Do you know Event Hubs retains and replays?
  • Do you know Event Grid is push, unordered and at-least-once?
  • Do you know the Grid-to-queue pattern?
Weak answers
  • Red flag: "Event Hubs for high volume, Service Bus for low" — the distinction isn't volume.
  • Red flag: treating them as interchangeable.
  • Red flag: no awareness that Event Grid pushes.
Likely follow-ups
  • How would you dead-letter with Event Hubs?
  • How do Event Hubs consumer groups work?
  • What happens if an Event Grid subscriber is down?
