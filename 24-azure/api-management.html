API Management

A programmable gateway in front of your APIs. The policy pipeline is the whole product — almost every question about APIM is really a question about policies.

🟡 Intermediate 🔴 Advanced 💡 Good to know
Quick revision
  • It's a reverse proxy you can program with declarative policies.
  • Four policy scopes: global, product, API, operation — and they nest.
  • Four sections: inbound, backend, outbound, on-error.
  • <base /> controls where the parent scope's policy runs.
  • Validate JWTs at the gateway, so bad tokens never reach your service.
  • Rate limit by key, not by the whole gateway.
  • Products + subscriptions is how you package and meter access.
  • Tier choice is mostly about VNet and multi-region, not throughput.

The honest scope: APIM is for APIs you publish to others

If you have one web API consumed by your own SPA, APIM adds cost, latency and a deployment dependency for very little. App Service plus a WAF via Front Door or Application Gateway covers that case.

APIM earns its place when there's a consumer relationship to manage: third parties, partners, internal teams you don't control, or paid API tiers. Then subscription keys, per-consumer quotas, a self-service portal and the ability to change the exposed contract without touching the backend are all genuinely valuable.

It's also the pragmatic answer for fronting something you can't change — a legacy SOAP service, a vendor API with an awkward shape, a mainframe endpoint. Policies can rewrite the request and response so consumers see a clean modern API while the backend stays untouched.

Being able to say when not to use it is part of a good answer, because "we put APIM in front of everything" is a common and expensive default.

<policies>
  <inbound>
    <base />                          <!-- run global + product policy first -->

    <!-- Reject bad tokens at the edge. The backend never sees them. -->
    <validate-jwt header-name="Authorization"
                  failed-validation-httpcode="401"
                  failed-validation-error-message="Unauthorized">
      <openid-config url="https://login.microsoftonline.com/{tenant}/v2.0/.well-known/openid-configuration" />
      <audiences><audience>api://orders</audience></audiences>
      <required-claims>
        <claim name="scp" match="any"><value>orders.read</value></claim>
      </required-claims>
    </validate-jwt>

    <!-- Per-caller limit. NOT a global one - see the note below. -->
    <rate-limit-by-key calls="100" renewal-period="60"
                       counter-key="@(context.Subscription?.Id ?? context.Request.IpAddress)"
                       remaining-calls-header-name="X-RateLimit-Remaining" />

    <!-- Contract enforcement from the OpenAPI spec -->
    <validate-content unspecified-content-type-action="prevent"
                      max-size="102400" size-exceeded-action="prevent"
                      errors-variable-name="validationErrors">
      <content type="application/json" validate-as="json" action="prevent" />
    </validate-content>

    <!-- Backend auth by managed identity: no key travels anywhere -->
    <authentication-managed-identity resource="api://orders-backend" />
  </inbound>

  <backend>
    <forward-request timeout="30" buffer-request-body="false" />
  </backend>

  <outbound>
    <base />
    <!-- Never leak backend internals -->
    <set-header name="X-Powered-By" exists-action="delete" />
    <set-header name="Server" exists-action="delete" />
  </outbound>

  <on-error>
    <base />
    <!-- Log the real reason, return something safe -->
    <set-body>@{
      return new JObject(
        new JProperty("type", "https://httpstatuses.io/500"),
        new JProperty("title", "Request could not be processed"),
        new JProperty("traceId", context.RequestId)).ToString();
    }</set-body>
  </on-error>
</policies>
Senior signal — <base /> is the detail that separates familiarity from experience

Policies at each scope don't simply concatenate. <base /> is a placeholder for the parent scope's policy at that section, and where you put it decides the order.

So in an inbound section, <base /> first means global and product policies run before yours. Putting it last means yours runs first — which is how you'd skip a global rate limit for a health endpoint, or add a header the parent policy reads.

Omitting <base /> entirely silently discards the parent policy for that section. That's the bug: someone writes an API-scope policy without it, and the global authentication or CORS policy stops applying — with no error, and the API works fine in testing because the token happened to be valid anyway.

Also worth knowing: outbound sections evaluate outward — operation, then API, then product, then global — so the nesting is inverted on the way back out. Which is what you want for response transformation, and confusing the first time you debug it.

The related discipline: put security policies at the global or product scope, so a new API inherits them by default rather than depending on whoever creates it remembering.

rate-limit versus rate-limit-by-key

Plain rate-limit applies per subscription. That sounds right until you consider what happens when many callers share one subscription, or when you want to limit by something else entirely.

rate-limit-by-key lets you choose the counter: subscription id, IP, a JWT claim, a tenant header. That choice is the security decision.

Two traps. Keying on IP alone is wrong behind NAT or a corporate proxy, where thousands of users share an address and throttle each other. Keying on a client-supplied header with no validation is worse — the caller just changes the value to reset their limit, so the limit does nothing.

Key on something the caller cannot forge: a subscription id, or a claim from a token you validated in the same pipeline. And note the ordering matters — validate the JWT before rate limiting by a claim from it, or you're trusting an unverified value.

Also: on multi-region or scaled deployments, rate-limit counters are not perfectly synchronised across gateway units, so treat the limit as approximate rather than exact. Fine for protection, not for billing.

Products, subscriptions and versions 🟡 Intermediate

ConceptIs
ProductA bundle of APIs with its own policy — "Free tier", "Partner tier"
SubscriptionA consumer's access to a product, with keys. The unit of metering
VersionA breaking change, exposed by path, header or query. Consumers choose
RevisionA non-breaking change, staged and tested, then made current
Named valueConfiguration for policies, optionally backed by Key Vault
Versions and revisions solve different problems

The distinction is worth being precise about, because it's the natural interview follow-up.

A version is for a breaking change. v1 and v2 exist simultaneously, consumers move when they're ready, and you retire v1 on a published timeline. That's a consumer-visible decision.

A revision is for a non-breaking change to an existing version. You create it, test it against a separate revision URL, then make it current — and consumers see nothing. It also gives you a change log and a one-click way back to the previous revision.

So: revisions for safe iteration, versions for contract breaks. Teams that create a new version for every change end up maintaining five versions that differ trivially, which is a maintenance burden with no benefit — and each one has to be tested and supported.

The related discipline is knowing who uses what. Subscription-level metrics tell you which consumers are still on v1, which turns "we'd like to retire it" into a specific list of people to contact. Without that you can never safely remove anything.

Subscription keys are not authentication

A subscription key identifies which consumer application is calling. It's an API key: useful for metering, quotas and revoking a specific consumer.

It says nothing about which user is acting, or what they're allowed to do. It travels in a header, appears in logs and configuration, and is shared across everyone using that application.

So user authentication and authorisation is still OAuth 2.0 and JWTs, validated with validate-jwt. The two are complementary — the key says who the integration is, the token says who the user is and what scopes they hold.

Treating a subscription key as authentication is a genuine security mistake, and it's common in internal APIs where "you need the key to call it" gets mistaken for access control. Any leak of the key becomes full access, with no user identity in the audit trail.

The classic tiers take a long time to do anything

Provisioning a classic APIM instance takes 30 to 45 minutes, and so does scaling it or changing its network configuration. That's not a typo and it shapes how you work with it: you can't spin one up per pull request, and an emergency scale-out is not a quick fix.

The v2 tiers exist largely to fix this — provisioning and scaling in minutes — and they're the sensible default for new deployments. Feature parity has been improving, so it's worth checking the current state against what you need rather than relying on an older comparison.

Two other tier facts that decide architectures. VNet injection is Premium on the classic tiers — so "the gateway must sit inside our network and reach private backends" historically forced Premium, which is a large jump in cost. And multi-region deployment is Premium only, which is the answer to global latency and regional failover.

Developer tier has no SLA. It's fully featured, which makes it tempting for production, and it is explicitly not supported for it.

The self-hosted gateway

Premium lets you run the gateway itself as a container — in your own Kubernetes cluster, another cloud, or on-premises — while management, policy authoring and analytics stay in Azure.

Two problems it solves. Data residency: traffic never leaves the jurisdiction, because the gateway is local even though the control plane is in Azure. And latency to local backends: a request from an on-premises client to an on-premises service doesn't make a round trip to Azure and back.

The trade: you're now operating the gateway — upgrades, scaling, monitoring — so it's only worth it when residency or locality genuinely demands it. It also needs connectivity to Azure for configuration, though it keeps serving on cached configuration if that connection drops, which is the property that makes it viable.

Key takeaways
  • APIM is a programmable reverse proxy; policies are the product.
  • Use it when there's a consumer relationship to manage, not for a single internal API.
  • Scopes nest global → product → API → operation; <base /> decides ordering.
  • Omitting <base /> silently drops the parent policy.
  • Outbound evaluates outward — the nesting inverts on the way back.
  • Put security policies at global or product scope so new APIs inherit them.
  • Validate JWTs at the gateway; the backend still shouldn't trust blindly.
  • Rate limit by a key the caller can't forge, and validate the token first.
  • Rate-limit counters are approximate across scale units.
  • Revisions for non-breaking change, versions for contract breaks.
  • Subscription keys identify the application, not the user.
  • Classic tiers take 30–45 minutes to provision or scale; v2 tiers are minutes.
  • VNet injection and multi-region are Premium on classic tiers.
  • Self-hosted gateway for data residency and local latency.

Common mistakes

  • Omitting <base />, silently disabling inherited policy.
  • Security policies at operation scope, so a new API is unprotected by default.
  • Rate limiting on a client-supplied header the caller can change.
  • Rate limiting by IP behind NAT, so users throttle each other.
  • Rate limiting on a claim before validating the token.
  • Treating the subscription key as authentication.
  • Backends reachable directly, so the gateway can be bypassed entirely.
  • Secrets as plain named values instead of Key Vault references.
  • A new version for every non-breaking change.
  • Developer tier in production — no SLA.
  • Assuming you can scale APIM quickly on a classic tier during an incident.
  • Policy edited in the portal and never captured in source control.

Interview questions

Intermediate

What would you put in an APIM policy, and what should stay in the service? 🔥 Must know
How I'd answer

"My dividing line is: cross-cutting concerns that are the same for every API go in the gateway; anything involving business meaning stays in the service."

"So in the gateway: JWT validation, rate limiting and quotas, request size and schema validation against the OpenAPI spec, CORS, response caching, stripping headers that leak backend detail, and obtaining a token for the backend via managed identity."

"The reason those belong there is that they're identical across services and they're cheaper to do early. A request with an invalid token is rejected at the edge and never consumes a backend instance — which matters under attack, because otherwise every bad request costs you compute."

"And putting them at the global or product scope means a newly-added API inherits them automatically, rather than depending on whoever created it remembering. That's a structural guarantee instead of a procedural one, which is the part I care about."

"In the service: authorisation decisions that depend on data — 'can this user see this specific order?' — business validation, and anything needing domain knowledge. The gateway shouldn't know what an order is or query the database to decide."

"The important qualifier: gateway validation doesn't mean the service can stop validating. The service should still validate its own tokens and inputs, because if anything ever reaches it another way — a misconfigured network rule, an internal caller, a private endpoint someone added — it's the last line of defence."

"That's related to something I'd check explicitly: can the backend be reached directly, bypassing the gateway? If yes, every gateway policy is advisory. The backend should only accept traffic from APIM — via VNet, private endpoint, or at minimum a client certificate — otherwise all this is theatre."

"On policy mechanics, the thing I'd be careful about is <base />. It's a placeholder for the parent scope's policy, so where it sits controls ordering — and omitting it silently drops the inherited policy for that section. No error, and the API works fine in testing. That's the APIM bug people hit."

"Two things I'd avoid putting in policies. Complex logic in C# expressions — it's possible, and it becomes untestable, hard to debug and invisible to anyone reading the service code. Once a policy needs real logic, that logic belongs in code."

"And secrets as plain named values. Named values should be Key Vault references so they're not sitting readable in the APIM configuration."

"Last thing: policies belong in source control. They're deployable artefacts. Editing XML in the portal means the running configuration is untracked, unreviewed, and lost on any redeploy from a template — and 'someone changed a policy in the portal' is a genuinely hard incident to diagnose."

What they're really checking
  • Do you have a principled dividing line rather than a list?
  • Do you know policies at global scope make protection the default?
  • Do you keep validation in the service too?
  • Do you check that the gateway can't be bypassed?
  • Do you keep policy in source control?
Weak answers
  • Red flag: putting business logic in policies.
  • Red flag: removing service-side validation because the gateway does it.
  • Red flag: no awareness that the backend may be directly reachable.
Likely follow-ups
  • How do you stop traffic reaching the backend directly?
  • Where would you cache, and how do you avoid serving one user another's data?
  • How do you test a policy change?

Advanced

You're exposing an API to external partners. Design the gateway configuration. ⭐ Senior-level
How I'd answer

"I'd design this around per-partner isolation — the ability to see, limit and revoke each partner independently — because that's the requirement that distinguishes a partner API from an internal one."

"Products and subscriptions give me that. A product per commercial tier — say Standard and Premium partner — with different rate limits and quotas, and a subscription per partner. Then each partner has their own key, their own usage metrics, and I can revoke exactly one without touching anyone else."

"Authentication is OAuth with client credentials, validated by validate-jwt at the gateway — checking signature against the published JWKS, issuer, audience, and the specific scopes required for each operation."

"I'd be explicit that the subscription key is not authentication. It identifies which partner integration is calling, which is what I need for metering and revocation. The token is what establishes authorisation. Both, doing different jobs."

"Rate limiting and quotas keyed on the subscription id — something the partner cannot forge. I'd use rate-limit-by-key for a short window to protect the backend from bursts, and quota-by-key for the monthly volume in the commercial agreement. And I'd return Retry-After and remaining-call headers, because a partner that can see their limit will handle it properly instead of retrying blindly."

"Important ordering detail: validate the JWT before rate limiting on anything from it. Otherwise the counter key comes from an unverified token."

"Contract enforcement with validate-content and validate-headers against the OpenAPI spec, plus a maximum body size. Partner integrations send malformed requests — that's normal — and I'd rather reject them at the edge with a clear message than have them produce obscure backend errors. It also stops a malformed-payload attack reaching my service."

"Backend protection is the part I'd insist on. The backend accepts traffic only from APIM — via VNet integration and private endpoints, or a client certificate if the network can't do it. If partners can reach the backend directly, every policy above is decoration. I'd also use authentication-managed-identity so the gateway gets its own token for the backend and no shared secret exists."

"Versioning: path-based versions, since partners integrate once and change slowly, so the version must be obvious and stable. Revisions for non-breaking changes so I can improve things without asking anyone to do work. And I'd track which subscriptions still call v1, because that turns deprecation from a hope into a list of people to email."

"Onboarding through the developer portal — self-service documentation, a try-it console, key management — with subscription approval required rather than automatic, since these are commercial relationships."

"Resilience: a backend timeout well below the partner's likely client timeout, retry only on genuinely idempotent operations, and a circuit breaker on the backend so a failing service returns fast rather than holding connections. A slow gateway is worse than a failing one, because the partner's connections pile up too."

"Observability per subscription — that's the operational point. When a partner says 'your API is broken', I need to see their traffic, error rates and latency specifically, not an aggregate. I'd also return a correlation id in every response so a support conversation starts with an identifier instead of a timestamp."

"Tier: if the backend is private, that historically means Premium for VNet injection on the classic tiers, or Standard v2 which supports VNet integration — worth checking current parity. Premium also gives multi-region, which matters if partners are geographically spread. Not Developer tier: no SLA."

"And a practical constraint I'd raise early: classic APIM takes 30 to 45 minutes to provision or scale. So capacity planning has to be ahead of time — you cannot scale out during an incident — and the v2 tiers are much better on that, which is a real argument for them."

"Finally, everything in source control — APIs, products, policies — deployed through the pipeline. Portal edits mean untracked production configuration, and with external partners depending on it, an unreviewed policy change is a genuine risk."

What they're really checking
  • Do you use products and subscriptions for per-partner isolation?
  • Do you separate the key from authentication?
  • Do you order JWT validation before claim-based rate limiting?
  • Do you lock the backend to gateway-only traffic?
  • Do you plan deprecation using subscription-level usage?
  • Do you know the provisioning-time constraint?
Weak answers
  • Red flag: API keys as the only security.
  • Red flag: a single shared rate limit for all partners.
  • Red flag: leaving the backend publicly reachable.
Likely follow-ups
  • A partner exceeds their quota mid-month. What happens?
  • How do you deprecate v1 safely?
  • How do you test policy changes before production?
