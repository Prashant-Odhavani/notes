SOLID Principles

Five habits that make C# code cheaper to change. Each one solves a specific, recognisable pain — this page leads with that pain, not the definition.

🟡 Intermediate 🔥 Must know
Quick revision — the five in one line each
  • Single Responsibility — one reason to change. Don't let unrelated jobs share a class.
  • Open/Closed — add, don't edit. New behaviour should mean a new class, not a change to a tested one.
  • Liskov Substitution — a subclass must not surprise you. It has to work anywhere the base works.
  • Interface Segregation — don't force people to depend on what they don't use. Small interfaces beat big ones.
  • Dependency Inversion — depend on abstractions, and own them. Your business logic shouldn't know about SQL Server.

Before the definitions: what problem is this solving? 🟢 Beginner

Think about the last time a change was painful. It usually looked like one of these:

  • You edited one class and something unrelated broke.
  • Adding a new payment provider meant touching seven files.
  • You couldn't write a unit test without spinning up a database.
  • A subclass threw an exception from a method it inherited.
  • You changed an interface and broke five classes that didn't care about the change.

Those five pains are, in order, exactly what SRP, OCP, DIP, LSP and ISP address.

In simple terms

SOLID is five answers to one question: "who depends on whom, and what breaks when this changes?"

That's it. Everything else is detail.

They're habits, not laws. Each one has a cost, and a codebase that maximises all five is usually over-abstracted and unpleasant to read. Knowing when not to apply them matters just as much — there's a section on that at the end.

Senior signal

In an interview, say where each principle earns its keep and where it doesn't. SRP and DIP pay off almost everywhere. OCP pays when variation is real and recurring. ISP matters mainly at published boundaries. LSP isn't a design lever at all — it's a rule you must not break.

S — Single Responsibility 🔥 Must know

In simple terms

A class should have one reason to change.

Not "one method". Not "one thing" — that's too vague to be useful. One reason, meaning one group of people who ask for changes to it.

Think of it this way

A restaurant doesn't have one person who cooks, takes payments and designs the menu. Not because it's impossible — because every time the menu changes, you'd risk breaking the kitchen.

Same code, same logic: separate the jobs that change for different reasons.

The problem

public class InvoiceService
{
    public decimal CalculateTotal(Invoice invoice)   // Finance owns this rule
    {
        var subtotal = invoice.Lines.Sum(l => l.Quantity * l.UnitPrice);
        return subtotal + (subtotal * 0.20m);
    }

    public void Save(Invoice invoice)                // The platform team owns this
    {
        using var conn = new SqlConnection(_connectionString);
        conn.Execute("INSERT INTO Invoices ...", invoice);
    }

    public string RenderHtml(Invoice invoice)        // Marketing owns this
        => $"<h1>Invoice {invoice.Number}</h1>";
}

Ask yourself: who asks for changes to this file? Three different groups. And that causes four concrete problems:

  1. A VAT change, a database change and a template restyle all touch the same file.
  2. They conflict in source control.
  3. Each change risks breaking the other two.
  4. You can't unit test the VAT rule without a database connection.

The fix

// Finance rules. Pure logic, fast tests, no infrastructure.
public sealed class InvoiceCalculator(ITaxPolicy taxPolicy)
{
    public Money CalculateTotal(Invoice invoice) { /* ... */ }
}

// Changes when storage changes.
public sealed class InvoiceRepository(AppDbContext db) : IInvoiceRepository { /* ... */ }

// Changes when the template changes.
public sealed class InvoiceHtmlRenderer(ITemplateEngine templates) : IInvoiceRenderer { /* ... */ }

Now a VAT change touches one small class with fast tests, and nothing else.

How to remember SRP

Ask: "who would ask me to change this?"

Two different answers means two classes.

Common mistake — going too far

Reading "one responsibility" as "one method per class". You end up with OrderValidator, OrderValidatorFactory and OrderValidationResultMapper — ten files where three would do, and following one request means opening all of them.

The test isn't method count. If the same person requests every change to five classes, they were probably one class.

O — Open/Closed 🟡 Intermediate

In simple terms

Add new behaviour by adding code, not by editing code that already works.

"Open" for extension, "closed" for modification.

Think of it this way

A power strip. You add a new device by plugging it in — you don't rewire the strip.

The socket is the abstraction. Each device is a new implementation.

The problem

public decimal CalculateShipping(Order order)
{
    switch (order.ShippingMethod)
    {
        case ShippingMethod.Standard: return 4.99m;
        case ShippingMethod.Express:  return 12.99m;
        case ShippingMethod.NextDay:  return 24.99m;
        default: throw new ArgumentOutOfRangeException();
    }
}

Here's the part that actually hurts. It isn't this one switch — it's that switches on the same enum multiply. You'll find another in the UI, one in reporting, one in the invoice printer.

Add "Locker delivery" and the compiler won't tell you which of the seven you missed. One of them silently falls into default in production.

The fix

public interface IShippingRate
{
    ShippingMethod Method { get; }
    Money RateFor(Order order);
}

public sealed class NextDayRate : IShippingRate
{
    public ShippingMethod Method => ShippingMethod.NextDay;
    public Money RateFor(Order order) => new(24.99m, "GBP");
}

public sealed class ShippingCalculator(IEnumerable<IShippingRate> rates)
{
    public Money For(Order order) =>
        rates.FirstOrDefault(r => r.Method == order.ShippingMethod)?.RateFor(order)
        ?? throw new ShippingUnavailableException(order.ShippingMethod);
}

Adding locker delivery is now one new class plus one registration line. No existing file changes.

Trade-off — be honest about this one

The switch is easier to read. All the rates are in one place. The polymorphic version scatters them across files and you need to understand DI registration.

So OCP is worth it when the set genuinely grows and each variant has real logic. It's not worth it for three constants.

Also: modern C# switch expressions over a sealed hierarchy give you exhaustiveness warnings — the compiler does tell you about the missed case. That weakens the classic argument quite a bit.

How to remember OCP

Use the rule of three. The first time you write the branch, write it. The third time you're editing the same switch to add a case — refactor to polymorphism.

Three edits is evidence. One is a guess.

L — Liskov Substitution 🔴 Advanced

In simple terms

If code works with the base class, it must still work when you hand it a subclass.

A subclass is allowed to do more. It is not allowed to do less, or to break a promise the base class made.

Think of it this way

A rental car agency promises "a car with four wheels and a steering wheel". If they hand you a go-kart, it technically has wheels — but every assumption you made (motorway, passengers, boot space) just broke.

The go-kart is a vehicle. It is not a valid substitute for a car.

Three rules cover almost every real violation

RuleWhat a violation looks like
Don't make the inputs stricterBase accepts any positive amount; the override rejects anything over 1000
Don't weaken the guaranteesBase promises a saved entity has an ID; the override sometimes leaves it null
Don't add new failuresThe override throws NotSupportedException

The problem

public class Employee
{
    public virtual decimal CalculateBonus(decimal salary) => salary * 0.10m;
}

public class Contractor : Employee
{
    // Contractors get no bonus - so this "override" breaks the base's promise.
    public override decimal CalculateBonus(decimal salary)
        => throw new InvalidOperationException("Contractors get no bonus.");
}
var totalBonuses = employees.Sum(e => e.CalculateBonus(e.Salary));

Nothing is wrong with that Sum. It was written against Employee's contract, which says "this returns a number". The subclass broke that contract.

Two ways to fix it

public override decimal CalculateBonus(decimal salary) => 0m;

Simple, and correct if "no bonus" really does mean zero.

public interface IBonusEligible { Money CalculateBonus(); }

public sealed class PermanentEmployee : Worker, IBonusEligible { /* ... */ }
public sealed class Contractor        : Worker { }   // simply doesn't implement it

var totalBonuses = workers.OfType<IBonusEligible>().Sum(w => w.CalculateBonus().Amount);

Option 2 is stronger: the runtime crash becomes impossible to write. Code that needs a bonus can only be handed something that has one.

Notice that fixing an LSP problem here meant splitting an interface — which is ISP. The principles interlock; that's a good thing to point out in an interview.

How to spot LSP violations in review

Look for if (x is SomeSubclass) at call sites, or a try/catch around a polymorphic call.

If callers have to know which concrete type they're holding, the abstraction has stopped abstracting.

I — Interface Segregation 🟡 Intermediate

In simple terms

Don't force a class to depend on methods it never calls.

Several small, focused interfaces beat one big general-purpose one.

Think of it this way

A TV remote with 60 buttons where you only ever use 5. Every extra button is something you have to look past, and every redesign risks moving the ones you actually need.

The problem

public interface IUserService
{
    Task<User> GetAsync(Guid id);
    Task<User> CreateAsync(CreateUser cmd);
    Task DeleteAsync(Guid id);
    Task<byte[]> ExportAllAsync();            // only the admin job needs this
    Task ImportAsync(Stream csv);             // only the migration tool needs this
    Task<bool> ValidatePasswordAsync(Guid id, string password);
}

What this actually costs you:

  • The login controller depends on six members and uses one.
  • Every test double has to stub all six.
  • A read-only implementation has to throw from ImportAsync — so a bad interface just created an LSP violation.

The fix

public interface IUserReader        { Task<User?> GetAsync(Guid id, CancellationToken ct); }
public interface IUserWriter        { Task<User> CreateAsync(CreateUser cmd, CancellationToken ct); }
public interface IUserAuthenticator { Task<bool> ValidatePasswordAsync(Guid id, string pw, CancellationToken ct); }

// One class can still implement all three. That's fine.
public sealed class UserService : IUserReader, IUserWriter, IUserAuthenticator { /* ... */ }
The bit people get wrong

ISP is about the consumer's view, not the implementer's.

One class implementing four interfaces is completely fine. What matters is that the login controller only depends on the one method it uses.

Common mistake

Taking it to one method per interface, everywhere. You get dozens of tiny interfaces and a DI registration file nobody can read. Segregate where clients genuinely differ — especially at boundaries other teams consume — and leave cohesive interfaces alone.

D — Dependency Inversion 🔥 Must know

In simple terms

Your business logic should not know about SQL Server, SMTP or HTTP.

It depends on an interface it owns; the infrastructure implements that interface.

Think of it this way

A wall socket. Your laptop doesn't know or care whether the electricity comes from a coal plant, a wind farm or a generator. It depends on the socket shape — and the power station is the one that had to conform to it.

That last part is the "inversion": the consumer defines the plug, not the supplier.

The problem

public class OrderProcessor
{
    public void Process(Order order)
    {
        using var conn = new SqlConnection("Server=prod;...");    // knows the database
        conn.Execute("INSERT INTO Orders ...", order);

        var client = new SmtpClient("smtp.company.com");          // knows the mail server
        client.Send(new MailMessage(/* ... */));

        File.AppendAllText(@"C:\logs\orders.txt", "...");         // knows the disk
    }
}

You cannot unit test this at all. Running the test would send a real email to a real customer.

The fix

// Defined in the APPLICATION layer, in domain language.
public interface IOrderRepository    { Task AddAsync(Order order, CancellationToken ct); }
public interface INotificationSender { Task OrderReceivedAsync(Order order, CancellationToken ct); }

public sealed class OrderProcessor(
    IOrderRepository orders,
    INotificationSender notifications,
    ILogger<OrderProcessor> log)
{
    public async Task ProcessAsync(Order order, CancellationToken ct)
    {
        await orders.AddAsync(order, ct);
        await notifications.OrderReceivedAsync(order, ct);
        log.LogInformation("Processed order {OrderId}", order.Id);
    }
}
// This project references the application project. Never the reverse.
public sealed class SqlOrderRepository(AppDbContext db) : IOrderRepository { /* ... */ }
Remember this — the one detail that matters

The interface must live with the caller, not the implementer.

IOrderRepository belongs in the Application project. SqlOrderRepository belongs in Infrastructure, and Infrastructure references Application. That flip is the whole point.

DIP vs DI vs IoC — three terms people mix up

TermWhat it actually isExample
Dependency InversionA design principle: which way dependencies point, and who owns the interfaceThe core defines IOrderRepository
Inversion of ControlA general idea: the framework calls you, not the other way roundASP.NET Core calls your controller
Dependency InjectionA technique: pass dependencies in, usually via the constructorOrderProcessor(IOrderRepository orders)
DI containerA tool that automates the injectionservices.AddScoped<...>()
Why the distinction is practical, not pedantic

You can use a DI container everywhere and still fail DIP.

If IOrderRepository is defined in the Infrastructure project and the Application project references Infrastructure to get it, the dependency still points from policy to detail. You have injection without inversion — and your core still can't be compiled or tested without a database.

How the five fit together ⭐ Senior-level

PrincipleMain benefitCost when overdoneWhere it pays most
SRPChange stays local; testableClass explosion, logic scatteredSeparating domain rules from infrastructure
OCPAdd features without editing tested codeIndirection for variation that never arrivesGrowing families: payment methods, exporters
LSPPolymorphism you can trustRarely overdone — it's a constraint, not a leverAny inheritance or shared interface
ISPClients insulated from unrelated changeInterface soup, unreadable DI setupPublished contracts, cross-team boundaries
DIPTestable core, swappable infrastructureInterfaces with one implementation foreverEvery boundary to I/O, time, external systems
One sentence that connects them

SRP decides where the boundaries go. DIP decides which way they point. ISP keeps them small. LSP keeps implementations honest. OCP is what you get in return.

When NOT to apply SOLID

  • Scripts, migrations, one-off tools. Code you'll delete next month doesn't need extension points.
  • Genuinely stable behaviour. If a rule hasn't changed in three years, an abstraction to make it changeable is speculative.
  • Plain CRUD. A controller reading and writing a record doesn't need a service, a repository interface, a mapper and a factory.
  • Before you know what varies. The first implementation can't tell you the axis of variation, so the abstraction you invent is usually the wrong shape.
Production trap

The expensive SOLID failure isn't violating the principles. It's applying them mechanically until every action sits behind three interfaces, stack traces are meaningless, and finding where something happens means chasing DI registrations across four projects.

That codebase isn't "clean" — it traded one difficulty for a worse one. Optimise for the person reading it next.

Key takeaways
  • SRP: split by who asks for the change, not by method count.
  • OCP: refactor on the third edit of the same switch, not the first.
  • LSP: the tell is type checks and try/catch at call sites.
  • ISP: judge from the consumer's side; one class can implement many interfaces.
  • DIP: the interface lives with the caller — otherwise it's DI without inversion.
  • A wrong abstraction costs more than duplication. Duplicate twice, extract on the third.

Interview questions

Basic

Explain the Single Responsibility Principle with a real example.
How I'd answer

"A class should have one reason to change. The framing I find most useful is: it should be answerable to a single group of people who request changes. Otherwise 'one responsibility' is unfalsifiable, because you can define it at any size."

"The example I've hit repeatedly is an invoice service that calculates totals, saves to the database and renders an HTML template. Three different groups drive changes there — finance changes VAT, the platform team changes storage, marketing changes the template."

"So they all edit the same file, they conflict in source control, each change risks the others, and you can't test the VAT rule without a database. Splitting it into a calculator with no infrastructure, a repository and a renderer means a VAT change touches one small class with fast tests."

"Where I'm careful is not reading it as 'one method per class'. I've seen codebases with OrderValidator, OrderValidatorFactory and OrderValidationResultMapper where following one request means opening ten files. That's worse. My test is whether the same person requests all the changes."

What they're really checking
  • Can you define "responsibility" in a way that's actually decidable?
  • Do you recognise the over-application failure mode?
Likely follow-ups
  • Does a controller that validates, calls a service and maps a response violate SRP?
  • How does SRP relate to cohesion?

Intermediate

How do you achieve Open/Closed in C#? Is a switch statement always a violation?
How I'd answer

"The usual mechanism is polymorphism — define an abstraction for what varies, implement it per variant, and let the caller resolve implementations instead of branching. In .NET that often means registering several implementations and injecting IEnumerable<T>, so adding a variant is a new class plus a registration."

"But a switch isn't automatically a violation. The problem with switches isn't the syntax, it's duplication. When the same enum is switched on in seven places, adding a value means finding all seven and the compiler won't tell you which you missed. If there's exactly one switch, close to the type it belongs to, and the set is stable — I'd leave it. It reads better."

"Modern C# also changes the calculus. A switch expression over a sealed hierarchy gives you exhaustiveness warnings, so the compiler does tell you. That weakens the classic argument quite a bit."

"My practical trigger is the rule of three. First time I write the branch. By the third time I'm editing the same switch for a new case, that's real evidence of a growing family, and I refactor. Doing it earlier is guessing at an axis of variation I haven't observed yet."

What they're really checking
  • Do you know the mechanisms — and can you defend not applying them?
  • Do you know modern language features change classic OO advice?
Weak answers
  • Red flag: "switch statements are always bad, use polymorphism."
  • Red flag: claiming OCP means never editing existing code — impossible in practice.
Likely follow-ups
  • How do you register and select among many implementations in ASP.NET Core DI?
  • Does adding a case to a switch expression over a sealed hierarchy break OCP?
Give an example of a Liskov violation you've seen, and how you'd fix it.
How I'd answer

"The clearest one was a storage abstraction with a SaveAsync method, and a read-only archive implementation that threw NotSupportedException from it. Everything compiled. It worked until a code path that legitimately saved files got pointed at archive storage by configuration."

"The tell was already visible before the incident. Call sites had started doing if (storage is not ReadOnlyArchiveStorage), and one had a try/catch around the save. Whenever callers need to know which implementation they're holding, the abstraction has stopped abstracting."

"The fix was to split the interface — readable and writable — with the archive implementing only the readable one. That moves the error from runtime to compile time: code that needs to write can only be given something that can write, so the bad configuration becomes impossible to express."

"There's a subtler variety too — not throwing, but weakening a guarantee. A repository documented as returning a persisted entity with an ID, and a caching implementation returning a stale copy without one. Nothing throws, you just get a null reference somewhere far away. Those argue for contract tests that every implementation has to pass."

What they're really checking
  • Can you recognise LSP violations from symptoms, not theory?
  • Do you know contract tests as a mitigation?
Likely follow-ups
  • How would you write a contract test suite all implementations must pass?
  • Is returning null instead of throwing a Liskov violation?

Advanced

Are dependency inversion, dependency injection and IoC the same thing? ⭐ Senior-level
How I'd answer

"No, and it's worth being precise because they get used interchangeably."

"Dependency inversion is a design principle about which way dependencies point — high-level policy shouldn't depend on low-level detail, and crucially the abstraction is owned by the high-level module. Inversion of control is broader: the framework calls your code rather than the other way round. Dependency injection is one technique for supplying dependencies, usually via the constructor. A container just automates that."

"The reason it's practical rather than pedantic: you can use a container everywhere and still fail DIP. If IOrderRepository lives in the infrastructure project and the application references it, the dependency still points from policy to detail. You have injection without inversion, and your core still can't be tested without infrastructure."

"The inversion happens when the interface lives with the consumer and the implementer depends on it. That's exactly what makes Clean and Hexagonal architectures work — the dependency arrow points inward regardless of which way control flows at runtime."

"And I'd add: not every dependency deserves an abstraction. Depending directly on List<T> or a JSON serializer is fine. I invert at boundaries where I need substitutability — I/O, time, randomness, external services, anything that makes tests slow or non-deterministic."

What they're really checking
  • Conceptual precision — this question is designed to separate memorisation from understanding.
  • Do you know where interfaces should live? That's the operative part of DIP.
  • Do you know when not to abstract?
Weak answers
  • Red flag: "DIP means using a DI container."
  • Red flag: "always program to an interface" with no discussion of ownership or cost.
Likely follow-ups
  • Which project should IOrderRepository live in, and why?
  • How do you handle something the domain needs that's inherently infrastructural, like the current time?
  • When is a concrete dependency acceptable?
A colleague says the codebase should follow SOLID everywhere. How do you respond?
How I'd answer

"I'd agree with the intent and push back on 'everywhere'. The principles exist to make change cheap, so the question for any specific case is whether it makes change cheaper here. Sometimes it demonstrably doesn't."

"An interface with one implementation that will never have another adds a file, an indirection in every stack trace, and a registration to maintain — in exchange for flexibility nobody uses."

"The concrete cost is legibility. In a heavily abstracted codebase, answering 'what happens when this endpoint is called?' means chasing registrations across projects. Everyone pays that, every time. The benefit only arrives if the variation actually materialises. So it's a bet: how likely is this to vary, and what does it cost me until then?"

"What I'd advocate is applying them where evidence supports it. DIP at I/O boundaries almost always pays. SRP between domain rules and infrastructure almost always pays. OCP pays when I've edited the same switch three times — observed variation, not predicted. LSP isn't optional, because breaking it produces real bugs."

"The framing that usually lands is: duplicate twice, abstract on the third. A wrong abstraction is more expensive than duplication, because it's harder to remove and everything gets built on top of it."

What they're really checking
  • Can you hold a nuanced position under mild social pressure?
  • Can you articulate the cost of abstraction concretely?
Likely follow-ups
  • Where would you draw the line on a greenfield service?
  • How do you retrofit DIP into a codebase full of static dependencies?
