Red Flags

Each of these is something you probably already know better. The problem is that the wrong phrasing is what comes out under pressure.

🟡 Intermediate 🔥 Must know
Why this page is worth more than another topic

Most preparation adds knowledge. This page removes a specific liability: answers that are technically adjacent to the truth and reveal that you've read about something rather than run it.

An interviewer hearing "we'd use microservices for scalability" doesn't conclude you know nothing. They conclude you've absorbed the marketing rather than the trade-off — which is a much more damaging inference at seven years than at two.

The fix is cheap, because in almost every case below you already know the correct version. You just need the right sentence to be the one that arrives first.

"Async makes it faster" 🔥 Must know

Red flagWhat it reveals
"We made it async so it's faster"Async is confused with parallelism
"Async improves performance"No model of what it actually does
Say instead

"Async doesn't make a single request faster — it's usually marginally slower because of the state machine. What it does is free the thread while waiting on I/O, so the same server handles far more concurrent requests before it saturates. It's a throughput and scalability property, not a latency one."

Then the consequence that shows you've debugged it: "which is also why sync-over-async is so damaging — a .Result holds a pool thread for the whole I/O, the pool only adds threads at one or two a second, so requests queue and latency climbs while CPU stays low."

That second sentence is what distinguishes the answer, because it's the observable consequence rather than the definition.

"Microservices for scalability" 🔥 Must know

Red flagWhat it reveals
"Microservices so we can scale"You can scale a monolith horizontally too
"Microservices are more maintainable"Distributed systems are harder to maintain, not easier
A service per database tableBoundaries drawn from schema, not from transactions
Services sharing one databaseCoupling without independence — the worst of both
Say instead

"Microservices have exactly one primary benefit: independent deployability. Everything else attributed to them is either narrower than claimed or a liability. Scalability isn't a reason — a monolith scales horizontally perfectly well, and usually more cheaply."

"So the question is whether independent deployability is worth the cost: network calls that fail, no transactions across boundaries, distributed tracing, versioned contracts, and eventual consistency you now have to explain to the business. For one team of eight deploying together, it usually isn't — I'd start with a modular monolith with boundaries enforced mechanically, so splitting later is mechanical rather than archaeological."

And the boundary rule: "I'd draw boundaries from what must be transactional together, not from nouns. The number of sagas in a design is a good proxy for whether the boundaries are right."

"NoSQL is faster" / "NoSQL scales better" 🔥 Must know

Say instead

"NoSQL isn't faster in general — it's faster for the access pattern you designed the key for, and worse for anything else. A point read by partition key is extremely fast; an unanticipated query is expensive or impossible."

"So the trade is that you're moving work from query time to design time. Relational gives you flexible querying and joins after the fact; document stores give you predictable performance if the access patterns are known and stable. That's a genuine trade, not a hierarchy."

The specific thing that shows experience: "and the partition key is usually irreversible, so choosing it before you know the access patterns and the size distribution is the expensive mistake. A very skewed key gives you a hot partition, and adding capacity can't fix it because throughput divides per partition."

Related flag: "NoSQL means no schema" — "there's still a schema, it just lives in the application and in every consumer, unversioned. That's usually harder to change, not easier."

"We'd use a distributed lock" 🔥 Must know

Say instead

"I'd check first whether the store already guarantees it, because a lock elsewhere is weaker. An atomic conditional write — UPDATE ... WHERE Status = 'Available', or a unique constraint, or an ETag check — makes the condition and the effect the same operation, so there's no window."

"A Redis lock can't guarantee anything about a write to SQL. If the lock expires mid-operation, two callers proceed and the invariant breaks with no error at all. So it adds a dependency and edge cases while providing a weaker guarantee than the database already offers."

The principle to state: "enforce an invariant in the store that owns the data. A lock elsewhere is advisory; a constraint in the database is absolute."

Distributed locks are legitimate for coordination — leader election, ensuring one instance runs a scheduled job — where the consequence of a rare overlap is duplicated work rather than corrupted data. And even there: "a lock reduces the probability of concurrent execution; idempotency makes it harmless. If I could only have one, I'd take idempotency."

"We'd scale out" 🔥 Must know

Red flagWhy it's wrong
"Add more instances"Correct for one of the two failure shapes, harmful for the other
"Scale the database tier"Often a missing index, not a capacity problem
"Add more RUs"Cannot fix a hot partition
"Increase the memory limit"Delays a leak rather than fixing it
Say instead

"Before scaling anything I'd want to know whether latency scales with load. If it rises with concurrency, something is queueing — a connection pool, the thread pool, a lock, a CPU limit being throttled. If it's constant regardless of load, it's a slow path — a missing index, an N+1, a slow dependency."

"Those need opposite responses. Scaling out helps the second and can make the first worse, because more instances compete for the same finite database connections — so 'the app is slow' becomes 'the app can't connect', which is worse and looks unrelated."

That single distinction is one of the highest-value things you can say in a scaling question, because it's the opposite of the reflex answer and it's easy to justify.

Also worth having: "scaling out only works if the app is stateless — and the one that does real damage is a background timer inside the web app, which now runs on every instance. A nightly job fires three times and nothing errors."

"We'd add a cache" 🔥 Must know

Say instead

"Caching is usually the right answer at a high read/write ratio, and I'd want to say what's cached, for how long, and how it's invalidated — because those are the parts that go wrong."

Then the three details that show you've operated one:

"Jitter every TTL, because a stampede isn't about misses, it's about simultaneous misses — identical TTLs set at a deployment all expire in the same second."

"Delete on write, don't update — two concurrent writers updating a cache can interleave and leave it permanently wrong, whereas a delete's worst case is a redundant read."

"And a cache failure must never fail the request. If an unhandled Redis exception becomes a 500, we've made the cache a hard dependency and reduced availability below the database alone. Though 'the cache is optional' is only true if the database can survive 100% of the read load — which is worth knowing before it happens."

The security one, if it's multi-tenant: "tenant id in every cache key. Omitting it means serving one customer another's data, which is a breach rather than a bug — and it passes every single-tenant test."

Error handling flags 🟡 Intermediate

Red flagBetter
catch (Exception) { }Catch what you can handle; let the rest reach the boundary handler
"We log and rethrow at every layer"One log at the boundary, with context. Duplicates are noise
throw ex;throw; — the first resets the stack trace
Exceptions for expected outcomesA result type for "not found" or "invalid"; exceptions for the exceptional
"We add retries"Timeout first, then breaker; retry with jitter, never on 4xx
Returning the exception message to the clientA safe message plus a trace id; the detail stays internal
The retry answer is the one that matters most

"Add retries" is the reflex response to any dependency failure, and on its own it makes things worse.

Say instead: "the timeout matters more than the retry, because without one there's no bound on the damage — and HttpClient's default is 100 seconds, which is catastrophic for a service-to-service call. Then a circuit breaker, so I stop paying the timeout on every request once it's clearly down. Then retries with exponential backoff and jitter — without jitter, a thousand clients that failed together all retry together, so the dependency recovers, gets hit by a wall, and falls over again."

"And never retry a 4xx — the request is malformed or unauthorised, so retrying can't succeed and just adds load to something already struggling."

The framing that lands: "my retries are part of the reason it stays down."

Testing flags 🟡 Intermediate

Red flagWhat it reveals
"We aim for 100% coverage"Coverage treated as a goal rather than a diagnostic
"We mock everything"The logic is never tested — only the wiring
"We use the in-memory provider"It doesn't reproduce SQL translation or constraints
"Integration tests are too slow so we skip them"Production failures are mostly integration failures
"Our tests break whenever we refactor"Testing implementation, not behaviour
Say instead

"I'd weight toward integration tests in .NET, because the failures that actually reach production are integration failures — SQL translation, DI registration, serialisation, migrations — and a heavily mocked unit test cannot catch any of them by construction."

"On mocking: mock at boundaries, not at class edges. If every collaborator is a mock, the test asserts that the wiring is as written, which is a tautology — and it breaks on every refactor."

"Coverage is a diagnostic, not a target. 100% coverage with no assertions passes. What I'd actually want is mutation testing, which measures whether the tests would notice a change."

And the counterintuitive point worth making: "the bigger problem is false positives — brittle tests. A suite that breaks on every refactor prevents the thing it was written to enable, so people stop refactoring or start ignoring failures. That's worse than a gap in coverage."

.NET specifics that get stated wrongly 🔴 Advanced

Red flagCorrection
"Dispose HttpClient after each use"That's what causes socket exhaustion. Use IHttpClientFactory
"A singleton HttpClient is the fix"It caches DNS forever — a problem when a dependency fails over
"struct is faster than class"Only when small; copying a large struct costs more
"GC.Collect() to free memory"Almost always counterproductive
"Nullable reference types prevent nulls"Compile-time only; no runtime enforcement
"IEnumerable and IQueryable are interchangeable"The first executes in memory, the second translates to SQL
"Task.Run to make it async"Moves blocking to another pool thread; solves nothing for I/O
"lock works across instances"Process-local only
The HttpClient one is the most common of all

It's worth being precise about, because both the naive answer and the naive fix are wrong and interviewers know it.

"HttpClient implements IDisposable, so disposing it per use looks correct — and it's exactly what causes socket exhaustion. Each disposal leaves a connection in TIME_WAIT, so under load you run out of outbound ports and calls start failing while CPU and memory look completely fine."

"But a static singleton isn't the answer either, because it caches DNS resolution for the lifetime of the process — so when a dependency fails over to a new address, you keep trying the old one."

"IHttpClientFactory solves both: it pools handlers and rotates them on a bounded PooledConnectionLifetime. Which matters especially in Kubernetes, where pods are replaced constantly, so a long-held connection to a deleted pod fails intermittently after every deployment."

Knowing that the obvious fix has its own failure mode is what makes this a strong answer rather than a corrected one.

Senior signal — changing your mind is a positive, not a concession

Interviewers push on decisions, sometimes to test conviction and often because they've spotted a real problem. The strong response engages with the substance:

"You're right that a single writer caps throughput. If we needed more than a few thousand writes a second I'd partition by region — I chose the simpler option because the stated requirement was a few hundred."

That shows you know the boundary of your own decision, which is what judgement actually is. Defending something you can now see is wrong is the worse outcome, because it predicts how you'd behave in a design review.

Equally, "I don't know" with a method is a good answer: "I'd check the documented per-partition throughput before committing to that key." Nobody knows every limit. Inventing one damages everything else you said, because the interviewer usually knows the real number.

And on legacy code: describe it neutrally. "It was built for different constraints, and the cost of changing it had grown" lands very differently from "it was a mess" — and the first is almost always more accurate.

Phrases to retire 🟡 Intermediate

Instead ofSay
"It's best practice""It's usually right because…, and I'd deviate when…"
"For scalability"Name the specific bottleneck it relieves
"It's more maintainable"Name what becomes easier to change, and what becomes harder
"We'd monitor it"Name the metric and the threshold you'd alert on
"We'd add logging"Say what you'd log and which question it answers
"It just works"Explain the mechanism, or say you'd check
"That's an anti-pattern"Say what goes wrong and when it's acceptable anyway
"Best practice" is the weakest phrase available

It signals that a rule was absorbed rather than understood, and it invites the follow-up "why?" — which you then have to answer anyway, from a worse starting position.

Saying "this is usually right because X, and I'd deviate when Y" answers the follow-up pre-emptively and demonstrates the thing "best practice" was standing in for.

Same with "anti-pattern". Most so-called anti-patterns are reasonable in some context — a service locator in a plugin host, a shared database during a migration, a singleton for genuinely global immutable state. Saying "the problem with this is X, though it's defensible when Y" is more useful and more accurate than a label.

The general habit: replace the label with the consequence. It's the same move as choosing the failure mode over the feature description, and it's what makes an answer sound like experience rather than revision.

Key takeaways
  • Async is throughput, not latency — and sync-over-async is the observable consequence.
  • Microservices buy independent deployability; scalability isn't a reason.
  • NoSQL is faster for the pattern you designed the key for, worse for others.
  • Prefer the store's atomic conditional write over a distributed lock.
  • Ask whether latency scales with load before scaling anything.
  • Caching: jitter TTLs, delete on write, never let a cache failure fail the request.
  • Timeout before retry; jitter always; never retry a 4xx.
  • Weight toward integration tests; coverage is a diagnostic, not a target.
  • Brittle tests are a worse problem than coverage gaps.
  • IHttpClientFactory — and know why both disposal and a singleton are wrong.
  • Change your mind when shown a real problem; say "I don't know" with a method.
  • Replace "best practice" and "anti-pattern" with the actual consequence.
