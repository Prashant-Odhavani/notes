How to use this page

Go line by line and try to say the reasoning aloud. Not the fact — the mechanism and its consequence.

"ConfigureAwait(false) in libraries" is recall. "Because a library shouldn't force a context capture the caller may not need, and in a UI app resuming on the captured context is what turns a .Result into a deadlock" is understanding.

Anywhere you can state the fact and not the consequence, open the full page for that topic. That's the whole method: this page finds gaps; the topic pages close them.

C# and the runtime 🔥 Must know

Language
  • Value vs reference type — where it lives matters less than copy-on-assign semantics.
  • struct for small immutable values; copying a large struct costs more than a reference.
  • record gives value equality, with expressions, and a concise constructor. Reference type unless record struct.
  • string is immutable — concatenation in a loop allocates each time; use StringBuilder.
  • Boxing allocates. It's why List<T> beats ArrayList.
  • IDisposable releases unmanaged resources deterministically; the GC won't do it promptly.
  • Nullable reference types are compile-time only — no runtime enforcement.
  • Span<T> for zero-allocation slicing; stack-only, so no async.
  • IEnumerable is lazy — enumerating twice executes twice.
  • Closures capture variables, not values — the classic loop-variable bug (fixed for foreach since C# 5).
Async
  • async is about not blocking threads, not about speed. One request isn't faster; the server handles more.
  • .Result/.Wait() holds a pool thread for the whole I/O. The pool adds threads at ~1–2/sec, so requests queue — latency climbs, CPU stays low.
  • One .Result deep in the chain is enough to starve the pool.
  • async void — exceptions can't be caught by the caller and crash the process. Only for event handlers.
  • ConfigureAwait(false) in libraries: don't force a context capture the caller may not need.
  • Task.WhenAll for parallel I/O; Parallel.ForEach is for CPU work.
  • CancellationToken all the way down, or cancellation does nothing.
  • ValueTask only for hot paths that often complete synchronously; awaiting twice is undefined.
  • IAsyncEnumerable to stream without buffering everything.
GC and memory
  • Generational — Gen0 collections are cheap, Gen2 is expensive.
  • Large Object Heap (85 KB+) isn't compacted by default — fragments.
  • Server GC is the ASP.NET Core default: per-core heaps, holds memory, tuned for throughput.
  • In a container, the GC sizes its heap from the memory limit — so a tight limit means aggressive collection, high CPU, and possibly an OOM anyway. Raising it can reduce CPU.
  • High CPU is often allocation, not computation.
  • Leaks in .NET: unbounded caches and static collections, unsubscribed events, captured scoped services in a singleton, HttpClient per request (sockets, not managed memory).
  • Rising and never recovering after GC = a leak. Tracks concurrency = per-request buffering.

OOP, SOLID and patterns 🔥 Must know

Principles
  • SRP — one reason to change, not "one thing".
  • OCP — extend without modifying; strategy or polymorphism instead of a growing switch.
  • LSP — a subtype must honour the base contract. Throwing NotSupportedException breaks it.
  • ISP — a fat interface forces implementers to stub methods.
  • DIP — depend on abstractions; the concrete type is chosen at composition.
  • Composition over inheritance — inheritance couples you to the base's changes.
  • Idiomatic .NET often is the pattern: constructor injection is Strategy, DbSet is Repository, DbContext is Unit of Work, middleware is Chain of Responsibility.
Patterns worth naming
  • Strategy — replaces a growing switch on type. Loses to a three-case switch.
  • Factory — when construction has rules or dependencies; often just DI.
  • Singleton — almost every criticism is really of static global access. AddSingleton is the answer.
  • Mediator — the real reason is IPipelineBehavior, not controller decoupling. Costs navigability.
  • CQRS comes in levels — separate models on one database is nearly free; separate stores buys eventual consistency. CQRS ≠ event sourcing.
  • Outbox — the only way to make a database write and a publish atomic.
  • Decorator — cross-cutting behaviour without touching the implementation.

ASP.NET Core and APIs 🔥 Must know

Framework
  • Middleware order matters — exception handling first, auth before authorisation, routing before endpoints.
  • Lifetimes: singleton per app, scoped per request, transient per resolution. A scoped service captured by a singleton is a bug — and a real source of cross-request leaks.
  • IOptions is bound once; IOptionsMonitor/Snapshot see changes. Dynamic config with IOptions silently does nothing.
  • IHttpClientFactory — fixes socket exhaustion and DNS caching. Essential in Kubernetes, where pods are replaced constantly.
  • Minimal APIs vs controllers — performance is similar; choose on team and structure.
  • Rate limiting is per-instance — it multiplies on scale-out unless distributed.
  • Health checks: liveness must not check dependencies, or one blip restarts every instance.
HTTP and REST
  • PUT is idempotent, POST isn't. PATCH depends on how you define it.
  • Status codes carry meaning: 400 malformed, 401 unauthenticated, 403 authenticated but not allowed, 404 hides existence, 409 conflict, 422 semantically invalid, 429 throttled.
  • Problem Details (RFC 9457) for machine-readable errors, with a trace id.
  • ETag does two jobs — 304 caching and If-Match optimistic concurrency (412 on conflict).
  • Never Cache-Control: public on an authenticated response — a shared cache can serve one user's data to another.
  • Keyset pagination — offset is slow at depth and silently skips rows during an export.
  • Idempotency keys on POST, enforced by a unique index, not an application check.
  • Version the whole API, additively where possible; track usage per consumer or you can never deprecate.

Data access 🔥 Must know

EF Core
  • Change tracking costs — AsNoTracking() for reads.
  • N+1 — lazy loading in a loop. Fix with Include or a projection; find it by counting dependency calls per operation.
  • Select a projection rather than loading whole entities you won't use.
  • Client-side evaluation is an exception in modern EF Core rather than a silent fallback — good.
  • DbContext is not thread-safe and is scoped per request.
  • Global query filters for tenant isolation — and the filter must read the tenant at query time, or the cached model bakes one tenant's id in for everyone.
  • Filters don't apply to raw SQL or ExecuteUpdate/ExecuteDelete.
  • Never the in-memory provider for testing query behaviour — Testcontainers with real migrations.
  • Migrations run as a Job, not at app startup with multiple replicas.
SQL
  • Clustered index = the physical order; one per table. Non-clustered is a separate structure with a pointer back.
  • Covering index — INCLUDE the columns needed to avoid a key lookup.
  • Index order matters: equality, then range, then sort (ESR).
  • Every index costs on write. Read wins are paid for on write.
  • Gradual slowdown = a scan meeting more rows. Sudden = a plan change.
  • Parameter sniffing — one cached plan compiled for an atypical parameter; the same query is fast for some inputs and slow for others.
  • Query Store shows when a plan regressed and can force the old one.
  • Estimated vs actual rows is the most informative number in a plan.
  • A transaction's cost is its duration — never an HTTP call inside one.
  • Isolation levels: read committed default; snapshot avoids readers blocking writers at the cost of version-store pressure.
  • Deadlocks are usually inconsistent lock ordering; retry the victim.
  • Azure SQL: DTU is a composite — check CPU, data IO and log IO separately. Log write rate throttles writes while CPU looks low.
NoSQL and Redis
  • Partition key is the decision you can't undo — it sets the scale ceiling and which queries are cheap.
  • A hot partition can't be fixed with capacity — throughput divides per partition, so adding RUs gives each one a smaller share. Increase key cardinality.
  • Aggregate RU utilisation hides a hot partition completely — 429s at 15% is the signature.
  • Cosmos consistency: five levels; session is the useful default, and the session token must propagate across instances.
  • Change feed is a built-in outbox in Cosmos and DynamoDB.
  • DynamoDB filter expressions don't reduce cost — you pay for what was read, not returned.
  • Redis is single-threaded per node — one slow command blocks every client. Never KEYS.
  • Cache-aside: delete on write, don't update — two concurrent updates can leave it permanently wrong.
  • Jitter every TTL. A stampede is about simultaneous misses.
  • Cache the absence briefly, or unknown ids bypass the cache entirely.
  • A cache failure must never fail the request — and "the cache is optional" is only true if the database survives 100% of the load.
  • Tenant id in every cache key. Omitting it is a breach.

Distributed systems 🔥 Must know

Messaging
  • Queue vs log: a queue removes on read and tracks each message (retry, DLQ); a log advances a cursor and keeps the data (replay, many consumers).
  • Event Hubs and Kafka have no dead-letter — a poison event stalls a partition unless your code handles it.
  • Exactly-once delivery is impossible; at-least-once + an idempotent consumer gives an exactly-once effect.
  • Deduplicate in the same transaction as the work, or you can do the work and fail to record it.
  • Ordering is per partition at best. Prefer version-based rejection over enforcing order.
  • Design events as state, not deltas, so duplicates and reordering are harmless.
  • Consumer lag: the trend matters, not the depth. One partition lagging = skew or a stall.
  • Consumers can't exceed the partition count.
  • Keep events small — identifiers and the fact, so consumers read current state.
Resilience
  • Slow is worse than dead. A dead dependency fails fast; a slow one exhausts your threads and takes down unrelated endpoints.
  • Timeout first, then circuit breaker, then bulkhead. HttpClient's 100-second default is far too long.
  • Backoff needs jitter, or synchronised retries keep a recovered service down.
  • Never retry a 4xx; don't stack retries at three layers (27 requests for one call).
  • Compensation is not rollback — it's a new business action. Irreversible steps go last.
  • A saga has no isolation — an explicit Pending status is the semantic lock.
  • Every store gives one atomic conditional write — ETag, rowversion, SET NX, condition expressions. Every correct coordination pattern is built on it.
  • Check-then-act is the bug, everywhere.
Architecture
  • Microservices have exactly one primary benefit: independent deployability. Everything else is narrower than claimed or a liability.
  • Modular monolith first, with boundaries enforced mechanically so splitting later is mechanical.
  • "What must be transactional together?" defines service boundaries better than nouns do.
  • The number of sagas is a proxy for whether the boundaries are right.
  • A shared database between services isn't microservices — you have coupling without independence.
  • Return the trace id to the client; it's how a support ticket becomes a distributed trace.

Testing 🟡 Intermediate

Testing
  • False positives (brittle tests) are the bigger problem — a suite that breaks on every refactor prevents the thing it was written to enable.
  • Mock at boundaries, not class edges. Over-mocking tests the wiring, never the logic.
  • Weight toward integration tests in .NET, because the failures that reach production are integration failures — SQL translation, DI registration, serialisation, migrations.
  • Testcontainers, never EF Core's in-memory provider for query or constraint behaviour.
  • Coverage is a diagnostic, not a target. Mutation testing measures what coverage can't.
  • async void tests silently pass — enable xUnit1001 as an error.
  • Test the concurrency case — submit the same operation twice simultaneously. It's the case nobody tests and the one that fails.

Azure and containers 🔥 Must know

Azure
  • Managed identity wherever supported — no credential to leak, rotate or commit.
  • Key Vault is throttled — cache at startup. Which is exactly what makes rotation not take effect, so bound the refresh.
  • A committed secret must be rotated; deleting the file does nothing.
  • App Service: ARR affinity is on by default and defeats scale-out for stateless apps.
  • A slot swap applies production settings and restarts before switching — so staging never tested production config. Configure warm-up.
  • SNAT port exhaustion — outbound calls fail while every normal metric looks fine.
  • Service Bus vs Event Hubs vs Event Grid: work, stream, notification.
  • Event Grid dead-lettering is off by default — failed events are silently discarded.
  • Functions scaling out overwhelms a fixed-capacity database — cap the scale-out.
  • Event Hubs/Cosmos triggers cap instances at the partition count.
  • Storage: redundancy is not backup. Geo-replication is asynchronous, so failover can lose writes. Immutability policies are the ransomware answer.
  • Direct upload via a user delegation SAS — revocable, and no account key.
Containers and Kubernetes
  • A container is a host process with namespaces and cgroups — no guest OS, weaker isolation than a VM.
  • Layer caching: copy project files and restore before copying source.
  • Layers are additive — a deleted secret is still in the image.
  • Requests decide scheduling; memory limits kill, CPU limits throttle.
  • Memory request = limit (incompressible); consider no CPU limit (compressible).
  • CPU throttling hides in average CPU — check throttled seconds.
  • No readiness probe = no safe rollout.
  • Liveness must not check dependencies, or one blip restarts every pod.
  • Endpoint removal races SIGTERM — a preStop sleep is the fix for deploy-time 502s.
  • Secrets are base64, not encrypted. Use workload identity.
  • Container Apps before AKS unless you need the Kubernetes API itself.

Delivery 🟡 Intermediate

Git and CI/CD
  • A commit is an immutable content-addressed snapshot; a branch is a pointer. That's why rebase creates new commits.
  • The reflog is your undo — ~90 days. Nothing committed is really lost.
  • Rebase your own unpushed work; never a shared branch.
  • Reset for local mistakes, revert for public ones. --force-with-lease, never plain force.
  • Build once, deploy that artefact to every environment.
  • OIDC federated on the environment — no stored secret, and bound so a leak is useless.
  • Expand and contract for schema change: both versions run during a rolling deploy.
  • Terraform state holds secrets in plaintext; for_each not count; apply the saved plan.
  • Bicep has no state and no provider lag — but incremental mode never deletes.
  • Read the plan for destroy and replace — the code diff won't show it.

Front-end essentials 🟡 Intermediate

JavaScript, Angular, React
  • The event loop: microtasks drain completely before the next macrotask.
  • Closures capture variables, not values.
  • Angular change detection: OnPush only re-renders on reference change — mutating an object silently does nothing.
  • Four flattening operators: switchMap cancels (typeahead), concatMap queues, mergeMap races, exhaustMap ignores while busy (submit buttons).
  • Unsubscribe or leak — takeUntilDestroyed.
  • React: server state vs client state is the distinction that removes most state-management complexity.
  • useEffect dependencies — a missing one is a stale closure; an object literal re-runs every render.
  • Keys must be stable ids, never the array index.

Method, for the design and diagnosis rounds 🔥 Must know

Production diagnosis
  • Characterise before diagnosing — all requests or a tail? since when? did anything deploy?
  • "Does it scale with load?" splits queueing from a slow path — and they need opposite responses.
  • Percentiles, never averages. The p50–p99 gap is the information.
  • Split by dimension early — instance, partition, tenant. Aggregates reassure while one unit fails.
  • Name the specific metric. That's the line that scores.
  • Label mitigations as mitigations, and capture evidence before restarting anything.
  • Finish with "how would we have known sooner?"
System design
  • Requirements first, and write down the exclusions.
  • "What must be strongly consistent?" is usually the pivotal question — and the answer differs per part of the system.
  • Estimate to reach a decision, then stop. Say when scale is a non-issue.
  • Data model before architecture; the boxes follow from it.
  • Name the trade-off: choice, reason, cost, and when you'd choose differently.
  • Volunteer failure modes — duplicates, slow dependencies, partial failure, schema change.
  • Finish on operability. The best alert is a business metric that stopped.
The eight lines to have ready

If everything else goes, these transfer across almost every question:

  • Slow is worse than dead.
  • At-least-once plus an idempotent consumer gives an exactly-once effect.
  • Adding capacity never fixes a hot key.
  • The aggregate metric is never the one you hit.
  • Check-then-act is a race; one atomic conditional write is the fix.
  • Compensation is not rollback.
  • A control that depends on someone remembering isn't a control.
  • Choose the simplest thing that meets the requirement.

Each is a consequence rather than a fact, which is why they're worth having verbatim. They also each open onto a longer answer if the interviewer follows up — which is exactly what you want.
