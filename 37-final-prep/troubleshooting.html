Six scenarios, said out loud. What's scored is the order you check things in and whether you name the specific metric.

🔴 Advanced ⭐ Senior-level
The four questions that narrow almost anything

Before any hypothesis, these four eliminate most of the possibility space — and asking them out loud is itself most of the score:

1. All requests or a subset? A subset means a specific code path, tenant, or instance. All means something shared.

2. Does it scale with load? Latency rising with concurrency means queueing. Constant latency means a slow path. Those need opposite responses, and this is the single most valuable question.

3. When did it start, and did anything deploy? Gradual means data growth. Sudden with a deploy means a code change. Sudden without one means a plan change, a dependency, or infrastructure.

4. One instance or all of them? One instance is a completely different problem — and aggregate metrics hide it entirely.

Six scenarios 🔥 Must know

Latency is 5 seconds. CPU is 20%. The database says queries take 10ms. 🔥 Must know
How I'd answer

"Those three facts together are diagnostic. The database is fast and the CPU is idle, so the time is spent waiting, and not on the database doing work. Requests are almost certainly queueing before they reach it."

"First hypothesis: thread pool starvation from sync-over-async. A blocking call — .Result, .Wait() — holds a pool thread for the entire I/O. The pool injects new threads at roughly one or two a second, so under load requests arrive faster than threads free up. The 10ms query really is 10ms; the request spent 4.99 seconds waiting for a thread to run it on."

"I'd confirm with dotnet-counters: queue length rising, thread count climbing slowly. And dotnet-stack — if dozens of threads are parked on the same .GetAwaiter().GetResult() frame, that's conclusive."

"Second candidate with the same signature: connection pool exhaustion. The distinguishing detail is that the wait happens before any query executes, and the error mentions the pool — 'timeout period elapsed prior to obtaining a connection'. That also fits 'the database says queries are fast', because the database only sees queries that got a connection."

"Third, if this is a container: CPU throttling. A CPU limit is enforced per 100ms period, so a container consuming its quota is paused for the remainder. Average CPU looks low precisely because it's paused rather than idle — which is why 20% isn't the reassurance it appears to be. I'd check throttled seconds, not CPU percent."

"Fourth: lock contention — a lock serialising requests through a critical section. Also low CPU, also scales with concurrency, and dotnet-stack distinguishes it because the blocked threads share a different frame."

"The question that separates them fastest: does latency scale with concurrency? If yes it's queueing — one of these four. If a single request in isolation is also slow, it's a genuinely slow path and I'd be looking somewhere else entirely."

"On mitigation: ThreadPool.SetMinThreads raises the floor and buys time, and I'd be explicit that it's a workaround — it hides the problem at moderate load and the same wall reappears higher up. The fix is async all the way down, and one .Result deep in the chain is enough, so a fully async controller can still starve. Analyzer rules catch it at build time, which is the structural version."

Memory grows steadily and the pod is OOM-killed every few hours. 🔥 Must know
How I'd answer

"First I'd confirm it is an OOM kill: kubectl describe pod shows last state OOMKilled with exit code 137. If it's exit 143 or a failing liveness probe, that's a different problem — a restart caused by the probe rather than by memory."

"Then the shape of the growth, which distinguishes three causes."

"Rises and never recovers after GC → a leak. Something roots the objects. Raising the limit only delays it."

"Tracks concurrency, falls afterwards → per-request buffering. Reading an entire upload into memory, materialising a whole query result. That's a code fix — stream instead of buffer, page the query."

"Sawtooth with a stable ceiling → normal. That's the GC working."

"For a leak, the technique is two dotnet-gcdumps several minutes apart, compared. What grew between them is the answer, and the retention path shows what's rooting it. Much faster than reasoning about the code."

"The .NET suspects, in order: an unbounded cache or static dictionary that only grows — IMemoryCache with no SizeLimit is the most common by a distance. Event handlers never unsubscribed. A long-lived delegate capturing a scoped service, which keeps a whole DbContext and its change tracker alive. And a DI lifetime mistake — a scoped service captured by a singleton."

"HttpClient per request is worth checking too, though it leaks sockets rather than managed memory, so it presents as connection failures instead."

"The container-specific detail I'd raise: .NET sizes its GC heap from the container memory limit, so the limit is an input to the runtime, not just a kill threshold. A limit set too tight makes the GC run far more aggressively — high CPU, more pause time — and it may still be killed. So raising the limit can reduce CPU, which is genuinely counterintuitive."

"And I'd check Server GC: it's the ASP.NET Core default, allocates per-core heaps and holds memory rather than returning it. In a small container with many visible cores that's a poor fit, and Workstation GC can be measurably better — a real trade between memory efficiency and throughput."

"Also: leave headroom below the limit. The GC heap isn't the only memory the process uses — native allocations, thread stacks and the runtime itself all count against the cgroup — so a heap limit at 100% of the container limit still gets OOM-killed."

A query that took 50ms now takes 8 seconds. Nothing was deployed. 🔥 Must know
How I'd answer

"'Nothing deployed' rules out a code change, so either the data changed or the plan changed. The question that separates them is whether the degradation was gradual or sudden."

"Gradual — slower over weeks — is almost certainly a scan meeting more rows. The query was always doing a scan; it just didn't matter at 50,000 rows and does at five million. Nothing changed except the data, which is why it feels mysterious. The fix is an index, confirmed from the plan showing a scan where a seek should be."

"Sudden, with no deployment, points at a plan change — and specifically parameter sniffing."

"The mechanism: SQL Server compiles a plan for the first parameter values it sees and caches it. If that first execution was for a customer with ten orders, the plan uses nested loops with seeks — perfect for ten rows, catastrophic for a customer with a million. So the same query text is fast for some parameters and slow for others."

"And it flips without warning: a restart, a failover, a statistics update or memory pressure causes a recompile, and whichever parameter arrives first sets the plan for everyone. That's exactly 'it was fine yesterday'."

"Query Store is how I'd confirm it. It keeps plan history per query, so I can see the point the plan changed and compare the two. On Azure SQL it's on by default. It also gives me the fastest mitigation — force the previous plan — which is minutes rather than hours. I'd label that as a mitigation, since a forced plan is a pinned hint that can become wrong as data changes."

"Other candidates. Stale statistics after a large data load — a big gap between estimated and actual rows in the plan is the tell, and it's usually the most informative number in a plan. Blocking, if it's intermittent rather than consistent: wait statistics distinguish it immediately, since LCK_ waits mean blocking rather than a slow plan. And a dropped index if there's been maintenance — cheap to rule out."

"On prevention: an alert on p95 duration per query from Query Store, so a regression is caught in hours rather than when someone complains. Automatic plan correction is worth considering too — Azure SQL can detect a regression and revert the plan without anyone being paged."

One instance out of six is serving errors. The others are fine. ⭐ Senior-level
How I'd answer

"That it's one instance is the most informative fact — it rules out anything shared. The code, the database, the configuration and the dependencies are identical across all six, so the cause is state local to that instance."

"I'd start by noting that aggregate metrics hide this completely: one instance in six failing every request shows as a 17% error rate, which looks like a moderate problem rather than a third of affected users seeing total failure. So the first move is to split every metric by instance."

"The candidates, roughly in order."

"A corrupted or exhausted connection pool. That instance's pool has drained — connections not disposed on some path, or a burst it never recovered from — so every request times out waiting for one. Restarting fixes it, which is why this often looks self-healing and recurs."

"Memory pressure or GC thrashing. That instance has grown, the GC is running constantly, and latency has become timeouts. kubectl top or per-instance memory metrics show it immediately."

"A stale cached value. An in-process cache on that instance holds something wrong — an expired token it isn't refreshing, a cached DNS entry pointing at a replaced pod, a configuration value read before a change. This is where a singleton HttpClient caching DNS bites: the dependency failed over and that instance keeps trying the old address."

"Something local it can't reach. A node-level network problem, a disk that's full, or a mounted secret that failed to refresh."

"A partition or lease it owns. If instances own partitions — an Event Hubs processor, a sharded consumer — then that instance's partition may be the problem rather than the instance."

"How I'd act. Take it out of rotation rather than restarting immediately, so I can capture a dump and stack traces first — a restart destroys exactly the evidence I need, and this will recur. Then replace it, which restores service."

"Prevention is the more interesting half, and it's two things. A readiness probe that would have removed it automatically — that's precisely what health checks are for, and if it kept receiving traffic while broken then the probe isn't checking anything meaningful. And alerting on per-instance error rate, not just the aggregate, so one bad instance surfaces as a specific alert rather than as a slightly elevated overall number."

Intermittent failures, roughly 1% of requests, no pattern anyone can see. ⭐ Senior-level
How I'd answer

"'No pattern' usually means nobody has grouped by the right dimension yet, so that's where I'd start rather than with a hypothesis."

"I'd group the failures by instance, tenant, endpoint, time-of-day, and payload characteristics. One percent spread evenly is a very different problem from one percent concentrated in one tenant or one instance — and it's common for 'random' to become obvious once split by dimension."

"Then I'd look for a correlation in time: does it spike on a schedule? That points at a batch job, a cache expiry, a token refresh, a backup window, or a scaling event. A regular period is a strong clue — a ten-minute rhythm is almost always a cache TTL."

"The candidates that produce genuinely low-rate intermittent failures:"

"A race condition. Small window, so it needs concurrency to hit. Check-then-act is the usual shape — two requests both check, both proceed. It correlates with load and it will look random at low traffic."

"Connection or pod churn. In Kubernetes especially: a pooled connection to a pod that's been replaced fails on next use. That produces exactly this signature — a small percentage, clustered around deployments and scaling events. IHttpClientFactory with a bounded PooledConnectionLifetime is the fix."

"A specific instance, which is why grouping by instance comes first."

"Data-dependent failures. A particular record breaks a code path — a null someone didn't expect, an unusual character, a value out of range. Grouping by the failing entity id usually reveals it."

"Lock or deadlock victims. A deadlock victim is a transient failure by design, so a low rate of them is normal-ish — the question is whether the rate is rising and whether the application retries."

"Retry exhaustion on a marginal dependency. If a dependency fails 5% of the time and you retry twice, you'd see about 0.01% — so 1% suggests either no retries or a worse dependency than assumed."

"What I'd need to make progress, and I'd say this directly: enough telemetry to find a specific failed request and trace it end to end. If sampling is dropping the failures, I'd exclude exceptions from sampling — which is the right configuration anyway, since failures are rare and individually valuable while successes are numerous and interchangeable."

"The framing: intermittent failures are almost never random. They're a pattern in a dimension you haven't looked at. The work is finding the dimension, not guessing the cause."

The database is hammered every ten minutes and requests time out. 🔥 Must know
How I'd answer

"A regular ten-minute period is a very strong signal — that's almost certainly a cache TTL, and I'd expect to find a ten-minute expiry in the code. It's a cache stampede."

"The mechanism: the entries were all populated at roughly the same moment — usually at a deployment, when every instance starts cold — and given identical TTLs. So they all expire in the same second, every concurrent request misses, and hundreds of identical queries hit the database at once."

"Then it sustains itself: the database saturates, queries slow, requests time out before they can repopulate the cache, so the next wave misses too. And the rhythm persists because each repopulation resets the clock in unison."

"The point worth making is that the cache made this worse than having no cache — without it the database would see steady load; with it, the load arrives as synchronised walls."

"Confirming it: correlate database load with cache miss rate. Misses spiking at the same instant as the database spike is conclusive."

"The fix is nearly free: jitter every TTL — randomise by ±15%. One line, and it's the whole fix for the common case, because a stampede is about simultaneous misses rather than misses. Spread the same number across ninety seconds and the database won't notice."

"If it's a single very hot key — a pricing table, a config blob — jitter doesn't help, because it's one key expiring once. There I'd use single-flight: the first caller takes a short lock and repopulates while others wait briefly or serve the stale value. Or serve stale and refresh in the background, which is usually the best user-facing behaviour — a few seconds of staleness in exchange for never having a user-visible miss."

"Cache warming on startup for the deployment trigger, gated behind the readiness probe so an instance doesn't take traffic until it's useful."

"Two adjacent things I'd check while I'm there. Does a cache failure fail the request? If an unhandled Redis exception becomes a 500, we've made the cache a hard dependency and reduced availability below the database alone. And can the database survive losing the cache entirely? If it absorbs 90% of reads, losing it means 10× load — so 'the cache is optional' is only true if the source can take the traffic."

"Prevention: alert on cache miss rate rather than only database load, because the miss spike precedes the symptom. And treat identical TTLs as something to catch in review, since jitter costs nothing."

What these six have in common

Every one is diagnosed by the same two moves: ask whether it scales with load, and split the metric by a dimension.

Queueing versus slow path decides whether scaling out helps or hurts. Splitting by instance, tenant, partition or endpoint turns "no pattern" into a specific cause — because the aggregate is reassuring while a single unit fails.

And three of the six had a symptom that pointed at the wrong subsystem: thread starvation looked like a database problem, CPU throttling looked like idle capacity, and a cache stampede looked like a database capacity issue. So the habit worth having is distrusting the obvious attribution and confirming with a metric that distinguishes.

Finally, in every case the answer ends with how would we have known sooner? — because that's frequently the real question, and it's the part most candidates leave out.

Key takeaways
  • Four narrowing questions: subset or all, scales with load, when and did anything deploy, one instance or all.
  • "Does it scale with load?" separates queueing from a slow path — opposite fixes.
  • Latency with low CPU: thread starvation, pool exhaustion, CPU throttling, or lock contention.
  • CPU percent hides throttling — check throttled seconds.
  • Memory: never recovering is a leak; tracks concurrency is buffering; sawtooth is normal.
  • Compare two gcdumps — what grew is the answer.
  • .NET sizes the GC heap from the container limit, so a tight limit raises CPU.
  • Gradual query slowdown is a scan; sudden is a plan change — Query Store shows which.
  • One instance failing rules out everything shared; aggregates hide it.
  • Capture evidence before restarting — it will recur.
  • Intermittent failures are a pattern in a dimension you haven't grouped by.
  • Never sample exceptions away — failures are rare and individually valuable.
  • A regular period is a cache TTL; jitter is the free fix.
  • Finish with how you'd have detected it sooner.
