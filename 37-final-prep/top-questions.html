The pattern that turns a good answer into a strong one

Every answer below follows the same shape: state the mechanism, then the consequence you've seen in production.

"A struct is a value type, a class is a reference type" is correct and forgettable. Adding "which is why a large struct passed around costs more than a reference, and why List<T> beats ArrayList — boxing allocates" turns recall into understanding.

That's the whole technique, and it works on every question in this handbook. The mechanism gets you a pass; the consequence gets you the role.

C# fundamentals 🔥 Must know

What's the difference between a value type and a reference type? 🔥 Must know
How I'd answer

"A value type holds its data directly; a reference type holds a reference to data elsewhere. So assignment copies the value in one case and copies the reference in the other — which is the behaviour that actually matters."

"I'd avoid saying 'stack versus heap', because it's an implementation detail and often wrong: a value type that's a field of a class lives on the heap with it, and a captured local ends up on the heap too. The copy semantics are the reliable distinction."

"Practical consequences. Passing a large struct copies it, so it can cost more than passing a reference — which is why structs are for small immutable values. Boxing allocates, which is why List<T> beats ArrayList. And mutating a struct in a collection often modifies a copy, which is a genuinely confusing bug."

"record is worth mentioning: value equality without being a value type, unless it's a record struct. That separation of equality from storage is what people find surprising."

Explain async/await. Does it make code faster? 🔥 Must know
How I'd answer

"No — a single request isn't faster, and is marginally slower because of the state machine. What async does is free the thread while waiting on I/O, so the same server handles far more concurrent requests before saturating. It's a throughput property, not a latency one."

"Mechanically: await on an incomplete task returns the thread to the pool and registers a continuation. When the I/O completes, the continuation runs — possibly on a different thread."

"The consequence I'd lead with, because it's the observable one: sync-over-async starves the thread pool. A .Result holds a pool thread for the entire I/O, and the pool only injects new threads at one or two a second — so under load requests queue, latency climbs steeply, and CPU stays low because nothing is computing."

"It typically presents as a database problem when the queries are fine. And one .Result deep in the call chain is enough, so a fully async controller can still starve."

"Two more things I'd get right. async void — exceptions can't be caught by the caller and crash the process; only for event handlers. And ConfigureAwait(false) in libraries, so you don't force a context capture the caller may not need."

What does IDisposable solve, and when do you implement it? 🟡 Intermediate
How I'd answer

"It gives deterministic release of things the GC won't handle promptly — file handles, sockets, database connections, unmanaged memory. The GC will eventually collect the object, but 'eventually' isn't good enough for a connection from a finite pool."

"I implement it when a type owns such a resource, or owns another disposable. And I'd use using or await using so disposal happens even on an exception path."

"Two things worth knowing. A finalizer is a safety net for unmanaged resources and it makes collection more expensive, so it's only warranted when wrapping a raw handle — and SafeHandle usually removes the need. And IAsyncDisposable exists because some cleanup is genuinely I/O — flushing a stream, closing a connection gracefully — and blocking in Dispose is how you deadlock."

"The one that catches people: disposing HttpClient per use is wrong, even though it's disposable. Each disposal leaves a socket in TIME_WAIT, so under load you exhaust outbound ports. IHttpClientFactory is the answer."

ASP.NET Core 🔥 Must know

Explain the DI lifetimes. What goes wrong if you get them wrong? 🔥 Must know
How I'd answer

"Singleton — one instance for the application. Scoped — one per request. Transient — a new one every time it's resolved."

"The failure that matters is a scoped service captured by a singleton. The singleton holds the first request's instance forever — so a DbContext intended to live for one request is shared across every subsequent request. That gives you a growing change tracker, thread-safety violations because DbContext isn't thread-safe, and stale data."

"Worse in multi-tenant systems: if the captured service holds tenant context, one request can serve another tenant's data — intermittently and under load, which is the hardest version of that bug to find."

"The good news is that scope validation catches it at startup in development, so it's usually a build-time failure rather than a production one. Worth enabling in all environments."

"The subtler case is a singleton needing scoped work — a background service wanting a DbContext. There you inject IServiceScopeFactory and create a scope per unit of work, rather than resolving the scoped service once."

"On transient versus scoped: transient is fine for cheap stateless services, and it means two collaborators in one request get different instances — which matters if the service holds any per-request state."

How does middleware work, and does order matter? 🔥 Must know
How I'd answer

"Middleware is a pipeline of components, each holding a reference to the next. A request passes through them in registration order, and the response passes back out through them in reverse — so each one can act before and after the rest of the pipeline. It's the Chain of Responsibility pattern."

"Order matters absolutely, and getting it wrong usually fails silently rather than erroring."

"Exception handling goes first, so it wraps everything after it — registered later and it can't catch what ran before it. Routing before endpoints, obviously. And authentication before authorisation, because authorisation needs an identity to evaluate — reversed, every authenticated request looks anonymous and you get 401s you can't explain."

"CORS before anything that would short-circuit, or the preflight never gets its headers. Response compression and caching need to be positioned to see the response you actually want them to act on."

"The general principle: anything that short-circuits must come after everything that needs to see the request."

Data access 🔥 Must know

What's an N+1 query and how do you find it? 🔥 Must know
How I'd answer

"One query fetches N rows, then iterating them triggers a query per row — so N+1 round trips instead of one or two. Classically caused by lazy loading inside a loop, or by projecting a navigation property that wasn't included."

"The reason it's worth knowing well is how it hides. Each individual query is fast — two milliseconds — so nothing looks slow. There's no slow query to find in the plan cache, and no latency percentile reveals it, because no single operation is slow. It's four hundred fast things."

"So the way I'd find it is by counting dependency calls per operation in Application Insights — grouping the dependencies table by operation_Id and looking for operations making hundreds of calls. That's the query that surfaces it, and it's not one people usually run."

"Fixes: Include when you need the related entities, or better a projection with Select so you fetch only the columns you use. AsSplitQuery if a single joined query produces a cartesian explosion instead."

"And prevention rather than detection: EF Core can be configured to throw on lazy loading, which turns an N+1 into a test failure. That's the structural fix — it can't reach production."

How do indexes work, and when do they not help? 🔥 Must know
How I'd answer

"An index is a sorted structure — a B-tree — that lets the engine seek to matching rows instead of scanning the whole table. A clustered index is the physical row order, so there's one per table; a non-clustered index is a separate structure with a pointer back to the row."

"Column order matters, and it's the thing most often wrong: equality predicates first, then range, then anything you sort by. An index on (Status, CreatedAt) serves WHERE Status = x ORDER BY CreatedAt; reversed, it doesn't."

"Covering the query with INCLUDE columns avoids the key lookup back to the table, which is often where most of the remaining cost is."

"When indexes don't help: low selectivity — an index on a boolean matching half the table is worse than a scan, and the optimiser will correctly ignore it. A function applied to the column — WHERE YEAR(Date) = 2024 isn't sargable, so rewrite it as a range. Leading wildcards in LIKE. And a mismatched data type forcing an implicit conversion, which silently disables the index — that one is genuinely hard to spot."

"The cost side, which is the part people skip: every index is maintained on every write. A table with twelve indexes does thirteen writes per insert. So on a write-heavy table, indexes are a real trade rather than free — and the DMVs will tell you which ones have never been used."

Explain transactions and isolation levels. 🟡 Intermediate
How I'd answer

"A transaction gives ACID — atomicity, consistency, isolation, durability. In practice isolation is the one with choices, and the choices trade correctness against concurrency."

"Read uncommitted allows dirty reads — you can see uncommitted data that may be rolled back. Read committed is the SQL Server default and prevents that. Repeatable read also prevents a row changing under you. Serializable prevents phantoms too, at the cost of range locks and much more blocking."

"Snapshot isolation is the one I'd highlight, because it's often the right answer: readers see a consistent version and don't block writers. The cost is version-store pressure in tempdb and the possibility of update conflicts."

"The practical point I'd make is that a transaction's cost is its duration, not its size. It holds locks until it commits — so the worst thing you can do is put an HTTP call inside a transaction. The lock is then held for however long a third party takes, and under load that cascades into timeouts that look like a database problem."

"Also worth knowing: lock escalation, where a bulk update crossing about 5,000 row locks takes a table lock instead and blocks everything — so batch large updates. And deadlocks, which are usually two paths taking locks in different orders; the fix is consistent ordering plus a retry, since a deadlock victim is a transient failure by design."

APIs and distributed basics 🔥 Must know

What makes an operation idempotent, and why does it matter? 🔥 Must know
How I'd answer

"Idempotent means performing it more than once has the same effect as performing it once. PUT and DELETE are idempotent by definition; POST generally isn't."

"It matters because retries are unavoidable. A response can be lost after the work succeeded — a timeout, a dropped connection, a process dying — and the caller can't tell the difference between 'it failed' and 'it worked and I didn't hear'. So it retries, and without idempotency you get a double charge or a duplicate order."

"The important framing: nothing was broken in that scenario. Both sides behaved correctly and the outcome is still wrong — which is why idempotency is a design requirement rather than a bug fix."

"How I'd implement it. Prefer naturally idempotent operations — 'set status to Shipped' is safe to repeat, 'increment the counter' isn't. Where that's not possible, an idempotency key supplied by the caller, stored with the result, so a repeat returns the original outcome."

"Two details that make or break it. The key must come from the client, because a server-generated key gives every retry a new value and deduplicates nothing. And it must be enforced by a unique index — insert first and treat the constraint violation as a duplicate. An application-level 'have we seen this?' check is check-then-act, which two concurrent callers both pass."

"The principle: make the database the arbiter, not your code."

When would you add a cache, and what goes wrong? 🔥 Must know
How I'd answer

"When reads greatly outnumber writes and the same data is read repeatedly. I'd want the read/write ratio first, because that's what decides whether it's worth the complexity — at 20:1 caching is load-bearing, at 2:1 it's probably not worth the failure modes."

"And I'd be specific about what, for how long, and how it's invalidated, because those are the parts that go wrong. Reference data can cache for hours; an order for a minute with invalidation on write; a permission check barely at all, because stale authorisation is a security issue rather than a stale display."

"What goes wrong, in order of how often I've seen it."

"Stampede. Identical TTLs — typically set when every instance started at a deployment — all expire in the same second, so every request misses simultaneously and the database gets hit by a wall. Jitter every TTL; that's one line and it's the whole fix, because a stampede is about simultaneous misses rather than misses."

"Stale data. I'd invalidate on write rather than waiting for the TTL — and specifically delete rather than update, because two concurrent writers updating a cache can interleave and leave it permanently wrong. A delete's worst case is a redundant database read."

"The cache becoming a hard dependency. If an unhandled Redis exception becomes a 500, we've reduced availability below the database alone. So every access is wrapped and falls through to the source. Though 'the cache is optional' is only true if the database survives 100% of the read load, which is worth knowing before it happens."

"And in a multi-tenant system, tenant id in every key. Omitting it serves one customer another's data — a breach, not a bug, and it passes every single-tenant test."

How do you handle exceptions in a web API? 🟡 Intermediate
How I'd answer

"One handler at the boundary — exception-handling middleware, or IExceptionHandler — that logs with context and maps to a response. Not try/catch in every controller action."

"The response is Problem Details, so it's machine-readable, with a trace id included. That trace id is what turns a support ticket into a distributed trace — the customer quotes a reference and I retrieve the whole request."

"I'd catch only what I can actually handle. Catching broadly and swallowing means a failure becomes a wrong answer instead of an error, which is much harder to diagnose. And throw; rather than throw ex;, since the latter resets the stack trace."

"On what's an exception at all: expected outcomes shouldn't be exceptions. 'Not found' and 'validation failed' are normal results — a result type or a validation response is clearer and much cheaper than throwing on a hot path."

"And never return the exception message to the client. It leaks internal detail — table names, file paths, sometimes connection strings. A safe message plus the trace id; the detail stays in the logs."

"One thing I'd add for a payment or similarly sensitive path: don't log request bodies. A well-meaning debug log can put card data or personal data into a log store that far more people can read."

Design fundamentals 🔥 Must know

Explain SOLID. Which principle do you find most useful? 🔥 Must know
How I'd answer

"I'd go through them quickly and then say which ones actually change my code, because reciting five definitions isn't the interesting part."

"Single responsibility — one reason to change. Not 'one thing', which is too vague to apply; the useful test is whether two different stakeholders would ask you to change the same class for different reasons."

"Open/closed — extend without modifying. In practice that's polymorphism or a strategy instead of a switch that grows every time a case is added."

"Liskov substitution — a subtype must honour the base contract. The clearest violation is overriding a method to throw NotSupportedException: it compiles, satisfies the type system, and breaks callers."

"Interface segregation — a fat interface forces implementers to stub methods they don't support, which is usually the same smell as the LSP violation."

"Dependency inversion — depend on abstractions, with the concrete type chosen at composition. That's what makes testing at boundaries possible."

"Most useful in practice: dependency inversion and single responsibility — those two change how I structure code daily. Open/closed I'd apply when a third case appears, not pre-emptively, because building extensibility for cases that never arrive is its own cost."

"The thing I'd add: in .NET, idiomatic code often is the pattern. Constructor injection is Strategy plus DIP. DbSet is a Repository. DbContext is a Unit of Work. Middleware is Chain of Responsibility. Recognising a principle in ordinary code is more useful than being able to draw the diagram."

REST: what do the status codes mean, and what's the difference between PUT and PATCH? 🟢 Beginner
How I'd answer

"PUT replaces the whole resource and is idempotent — sending it twice leaves the same state. PATCH applies a partial modification, and whether it's idempotent depends on the operations: 'set name to X' is, 'append to a list' isn't."

"That matters for retries. A client can safely retry a PUT after a timeout; retrying a PATCH depends on what the patch does."

"On status codes, the distinctions worth being precise about: 401 is unauthenticated — you haven't proved who you are. 403 is authenticated but not permitted. Confusing them makes clients retry with the same credentials pointlessly."

"404 versus 403 is a design decision: returning 404 for something that exists but isn't yours hides existence, which is often what you want for security."

"400 is malformed, 422 is well-formed but semantically invalid, 409 is a conflict with current state, 412 is a failed precondition — which is what If-Match returns and gives you optimistic concurrency for free. 429 is throttled, and should come with Retry-After."

"202 Accepted is worth mentioning because it's underused: for anything that takes longer than a request should, accept it and return a status URL rather than holding the connection until it times out."

Key takeaways
  • State the mechanism, then the production consequence. That's the whole technique.
  • Async is throughput; sync-over-async starves the pool and looks like a database problem.
  • Copy semantics, not stack-versus-heap, is the value/reference distinction.
  • A scoped service captured by a singleton is the DI bug that matters.
  • Middleware order: exception handling first, authentication before authorisation.
  • N+1 hides because every query is fast — count dependencies per operation.
  • Index column order: equality, range, sort. Every index costs on write.
  • A transaction's cost is its duration — no HTTP calls inside one.
  • Idempotency: client-supplied key, unique index, database as arbiter.
  • Caching: jitter TTLs, delete on write, never a hard dependency, tenant in the key.
  • One exception handler at the boundary, Problem Details, trace id, no leaked detail.
  • In .NET, idiomatic code often is the pattern.
  • 401 vs 403, 400 vs 422, and 202 for anything slow.
