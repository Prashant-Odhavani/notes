Operations & Scaling

Consumer lag is the one number that tells you whether Kafka is healthy. Almost everything operational reduces to keeping it low.

🔴 Advanced ⭐ Senior-level 💡 Good to know
Quick revision
  • Consumer lag is the primary metric. Growing lag means you're falling behind permanently.
  • Slow processing causes rebalance loops via max.poll.interval.ms.
  • Retention is time or size based — and it deletes data regardless of whether it's been read.
  • Log compaction keeps the latest value per key forever. Different from retention.
  • A tombstone is a null value — that's how you delete a key under compaction.
  • Partition count is effectively permanent. Over-provision moderately.
  • Batching and compression are the main producer throughput levers.

Consumer lag 🔥 Must know

In simple terms

Lag is the newest offset in a partition minus the consumer group's committed offset — how many messages behind you are.

Some lag is normal and healthy. Growing lag means consumers can't keep up, and it will never recover on its own.

Lag patternMeans
Flat and lowHealthy
Spiky, returns to baselineHandling bursts fine
Steadily growingUnder-provisioned. Will not self-correct
Growing on one partition onlyA hot key, or a stuck consumer
Sudden jumpA consumer died, or a rebalance
Flat but highKeeping pace but never catching up — a stalled consumer, or offsets reset
Lag plus retention equals silent data loss

This is the failure that surprises people. Retention deletes data on a schedule regardless of whether anyone has consumed it.

So if retention is 7 days and lag grows past 7 days' worth of messages, Kafka deletes messages the consumer has never read. The consumer then jumps forward to the earliest available offset — and the data is gone.

Depending on auto.offset.reset, the consumer either silently skips to the beginning of what's retained (earliest) or to the newest message (latest), losing everything in between. Either way there's no error — just a gap.

So lag must be alerted on before it approaches the retention window, not when it's already there. And the alert should be in time terms, not message count, because "500,000 messages behind" means nothing without knowing the rate.

Fixing growing lagNotes
Make the consumer fasterUsually the best option — batch database writes, remove an N+1, cache a lookup

Rebalancing 🔥 Must know

SettingControlsSymptom if wrong
session.timeout.ms How long without a heartbeat before the consumer is considered dead Too low: spurious rebalances on GC pauses
max.poll.interval.ms Maximum time between poll() calls Too low: rebalance loop when processing is slow
heartbeat.interval.ms Heartbeat frequency Should be roughly a third of the session timeout
max.poll.records Messages returned per poll Too high with slow processing: exceeds the poll interval
The rebalance loop — a classic and confusing failure

Heartbeats run on a background thread, so the consumer looks alive even while your handler is busy. What actually detects a stuck consumer is max.poll.interval.ms — the time between poll() calls.

So if max.poll.records is 500 and each message takes 100ms, one batch takes 50 seconds. With the default 5-minute poll interval that's fine — but at 1,000 records and 500ms each, it's over 8 minutes, the broker declares the consumer dead, and a rebalance starts.

Then the reassigned partition goes to another consumer which also takes too long, and that one is evicted too. The group rebalances continuously and processes almost nothing — while every consumer looks healthy and CPU looks fine.

Two fixes: reduce max.poll.records so a batch completes well inside the interval, or raise max.poll.interval.ms to fit the realistic worst case. Reduce the batch size first, because a long poll interval delays detection of genuinely dead consumers.

Recognising this pattern — continuous rebalancing with no progress and healthy-looking consumers — is one of the most useful diagnostic signals in Kafka operations.

Cooperative and static membership reduce rebalance pain

CooperativeSticky assignment only moves the partitions that need to move, so consumers keep processing the rest. The older eager strategy stops the entire group and reassigns everything — a stop-the-world pause on every deployment.

Static membership (group.instance.id) gives each consumer a stable identity, so a restart within the session timeout doesn't trigger a rebalance at all — the same partitions come back to it.

That's the setting that makes rolling deployments cheap. Without it, a rolling restart of ten consumers causes ten rebalances; with it, none. Worth knowing because deployment-induced rebalancing is a common source of latency spikes that nobody attributes to deployments.

Retention and compaction 🔥 Must know

Retention (delete)Compaction (compact)
Deletes based onAge or sizeSuperseded keys
KeepsEverything within the windowThe latest value per key, forever
Old values for a keyKept until the window expiresRemoved once superseded
Log sizeBounded by time or bytesBounded by distinct key count
Use forEvent streams — "what happened"State/snapshots — "what is it now"
The distinction that matters

Retention is a time window over events. Use it when you care about a stream of things that happened, and old ones stop mattering.

Compaction is a key-value store in a log. It keeps the most recent value for each key indefinitely — so a new consumer can read the whole topic and reconstruct current state for every key.

Senior signal — compaction is what makes a topic a replayable state store

With retention, replaying gives you recent events. If retention is 7 days you cannot rebuild state that depends on older data — the events are gone.

With compaction, the topic always contains at least the latest value for every key. So a brand-new consumer can read from the beginning and end up with complete current state for every entity, however old.

That's what makes compacted topics the foundation for materialised views, caches and lookup tables — you can add a consumer at any time and it bootstraps itself. It's also how Kafka stores its own consumer offsets, in the compacted __consumer_offsets topic.

To delete a key under compaction you publish a tombstone — a message with that key and a null value. Compaction removes the key entirely after delete.retention.ms, giving consumers time to observe the deletion.

Two caveats worth stating: compaction is asynchronous and best-effort, so duplicates for a key can exist transiently; and it only ever compacts inactive segments, so the newest data is never compacted. Consumers must therefore tolerate seeing several values for a key.

  Before compaction:
    (user1, {name:"A"}) (user2, {name:"B"}) (user1, {name:"A2"}) (user2, null)

  After compaction:
    (user1, {name:"A2"})        <- only the latest value survives
                                <- user2 removed by the tombstone
Retention deletes unread data

Retention has no relationship to consumption. It is not "delete once everyone has read it" — it's "delete after this long, regardless".

So a consumer offline longer than the retention window loses data permanently, with no error. That's the lag-plus-retention trap from above, and it's why retention should be set from recovery requirements: how long could a consumer plausibly be down — a long weekend, a bank holiday, an extended incident — plus margin.

Seven days is a common default and it's a decision, not a given. If a consumer could be down over a four-day break plus a day to notice and fix, seven days is uncomfortably tight.

Partition sizing ⭐ Senior-level

The constraint that drives the decision

You can add partitions but not remove them — and adding them breaks key ordering, because partition assignment is hash(key) % count.

So this is effectively a design-time decision. Over-provision moderately, and don't plan to change it.

Too fewToo many
Caps consumer parallelismMore file handles and open files per broker
Can't scale out to clear lagMore memory for producer batching per partition
Hot partitions more likelySlower rebalances and longer leader elections
Adding them later breaks orderingHigher end-to-end latency from smaller batches
A sizing approach

Work from target throughput divided by per-consumer throughput. If you need 100,000 messages a second and one consumer handles 5,000, that's 20 partitions minimum — then add headroom for growth, so perhaps 30.

Sanity-check against key cardinality: partitions beyond the number of distinct keys are guaranteed to sit empty. And against expected consumer count, since that's the ceiling you're buying.

For most systems, tens of partitions is right. Hundreds is unusual and should be justified; thousands per topic causes real operational problems.

A useful reframing: partition count is a capacity decision like sizing a thread pool — you want enough for peak plus headroom, and over-provisioning has a real but modest cost while under-provisioning is expensive to fix.

Producer throughput tuning 🔴 Advanced

var config = new ProducerConfig
{
    BootstrapServers = brokers,
    EnableIdempotence = true,
    Acks = Acks.All,

    // Wait briefly to fill a batch - the single biggest throughput lever
    LingerMs = 10,
    BatchSize = 64 * 1024,               // 64KB batches

    // Compression applies per batch, so bigger batches compress better
    CompressionType = CompressionType.Zstd,

    MaxInFlight = 5                      // <= 5 required with idempotence
};
SettingEffectTrade-off
linger.msWaits to fill a batchLatency for throughput. 0 means send immediately
batch.sizeMaximum batch bytesMemory per partition
compression.typeCompresses each batchCPU for network and disk. zstd or lz4
acksDurabilityall costs latency and is correct
max.in.flightUnacknowledged batchesMust be ≤ 5 with idempotence
linger.ms is counter-intuitive and effective

The default of 0 sends each message as soon as possible, which sounds optimal and produces many small requests.

Setting linger.ms=10 waits up to 10 milliseconds to accumulate a batch. That adds at most 10ms of latency and can multiply throughput several times over, because per-request overhead is amortised across many messages — and larger batches compress far better, so network and disk usage drop too.

For most event-streaming workloads 10ms is imperceptible and the gain is substantial. It's the highest value-to-effort producer setting, and it's frequently left at the default.

Compression matters more than people expect because it applies per batch, not per message — so JSON with repeated field names across a batch compresses very well. zstd generally beats gzip on both ratio and CPU.

Failure and recovery 🔴 Advanced

FailureWhat happensWhat you should have done
A broker dies Leadership moves to an in-sync replica; producers and consumers reconnect replication.factor ≥ 3, min.insync.replicas=2
A consumer dies Rebalance; its partitions move; uncommitted work reprocesses Idempotent consumers
A whole AZ fails Depends on replica placement Rack awareness, so replicas span zones
Disk fills Broker stops accepting writes Retention sized to disk, plus alerting
Consumer offsets lost Restarts per auto.offset.reset — reprocess everything or skip everything Know which reset you've configured, and why
auto.offset.reset has two bad outcomes, so choose deliberately

This applies when a consumer group has no committed offset — a brand-new group, or one whose offsets expired or were deleted.

earliest reprocesses the entire retained topic. For a new analytics consumer that's exactly right. For a consumer that sends emails, it means emailing everyone about every order in the last seven days.

latest skips everything currently in the log. Safe against mass side effects, and it silently loses any backlog — so a consumer that was down and lost its offsets never processes what accumulated.

There is no safe default. The decision follows from what the consumer does: idempotent projections and read models want earliest; anything with external side effects wants latest plus a deliberate backfill if needed.

And this is a strong argument for idempotent consumers beyond duplicate handling — with idempotency, an accidental earliest reprocess is wasteful rather than catastrophic.

Rack awareness is a one-line configuration with real value

Setting broker.rack makes Kafka distribute a partition's replicas across different racks or availability zones.

Without it, all three replicas of a partition can land in the same zone — so a zone failure takes the partition fully offline despite replication factor 3. You've paid for redundancy and got none against the failure mode most likely to occur.

Managed services generally configure this. If you run your own brokers it's worth verifying rather than assuming, because the symptom only appears during the incident you bought replication to survive.

Key takeaways
  • Consumer lag is the primary health metric — alert in time terms, not message counts.
  • Retention deletes unread data, so lag exceeding the retention window loses messages silently.
  • Adding consumers only helps up to the partition count.
  • max.poll.interval.ms plus slow processing causes continuous rebalancing with no progress.
  • Reduce max.poll.records before raising the poll interval.
  • Cooperative assignment and static membership make deployments cheap.
  • Retention is a time window over events; compaction is a key-value store that keeps the latest value forever.
  • Compacted topics let a new consumer bootstrap full current state.
  • A tombstone is a null value; compaction is asynchronous so consumers must tolerate duplicates.
  • Partition count is effectively permanent — size from throughput with headroom.
  • linger.ms plus compression is the biggest producer throughput lever.
  • auto.offset.reset has two bad outcomes; choose from what the consumer does.
  • Rack awareness, or replication factor 3 protects against nothing zone-wide.

Common mistakes

  • Not monitoring consumer lag, or alerting on counts rather than time.
  • Retention shorter than plausible consumer downtime.
  • Adding consumers beyond the partition count to fix lag.
  • max.poll.records too high for the processing time, causing rebalance loops.
  • Raising the poll interval instead of reducing the batch.
  • Eager rebalancing and no static membership, so every deploy stalls the group.
  • Using retention where compaction was needed for a state topic.
  • Assuming compaction removes duplicates immediately.
  • Too many partitions, slowing rebalances for no gain.
  • linger.ms=0 and no compression on a high-volume producer.
  • auto.offset.reset=earliest on a consumer with side effects.
  • No rack awareness, so replicas share a failure domain.

Interview questions

Advanced / scenario

Consumer lag is growing steadily. Walk me through it. 🔥 Must know
How I'd answer

"Growing lag means consumers are slower than producers, and it will not recover on its own — so this needs action rather than observation."

"The first thing I'd establish is how urgent it is relative to retention, because that determines whether this is a performance problem or an imminent data-loss problem. Retention deletes data on a schedule regardless of whether it's been consumed. So if retention is 7 days and lag reaches 7 days' worth, Kafka deletes messages the consumer has never read — and the consumer silently jumps forward. No error, just a gap."

"So I'd convert lag into time rather than message count. '500,000 messages behind' is meaningless; 'four hours behind, on seven-day retention' tells me I have room, and 'five days behind' means I'm about to lose data."

"Then I'd check whether it's all partitions or one."

"One partition growing points at a hot key — a dominant entity sending most of the traffic to one partition — or a stuck consumer on that partition. Adding consumers won't help a hot key, because you can't split a single key across partitions."

"All partitions growing is genuine under-provisioning."

"Before scaling anything I'd check for a rebalance loop, because that presents as growing lag with healthy-looking consumers and it's the most confusing cause. Heartbeats run on a background thread, so a consumer looks alive while its handler is busy — what detects a stuck consumer is max.poll.interval.ms. If a batch takes longer than that, the broker evicts the consumer, the partition moves to another that also takes too long, and the group rebalances continuously while processing almost nothing. I'd look at rebalance frequency in the consumer metrics to rule that in or out."

"If that's the cause, the fix is to reduce max.poll.records so a batch completes well inside the interval — I'd do that before raising the poll interval, because a long interval delays detection of genuinely dead consumers."

"For real under-provisioning, in order of preference:"

"Make the consumer faster. Usually the best option and often the easiest — batch the database writes instead of one per message, remove an N+1, cache a lookup. A consumer doing a synchronous HTTP call per message is the common culprit."

"Add consumers — but only up to the partition count. Beyond that they sit idle, which catches teams mid-incident: they scale from 4 pods to 12, nothing improves, and rebalances get slower."

"Add partitions to raise the ceiling — and this breaks key ordering, because assignment is hash(key) % count, so a key's old and new messages end up in different partitions being processed concurrently. That's a correctness change made under pressure, which is exactly when you don't want to make one."

"Or reduce what's produced — filtering at the source is sometimes the real answer, if a lot of what's flowing through isn't needed."

"For immediate mitigation if retention is closing in, I'd consider temporarily extending retention to buy time. That's a broker config change and it's much cheaper than losing data."

"And afterwards: alert on lag in time terms with a threshold well below retention, so this is caught while it's a capacity conversation rather than an incident."

What they're really checking
  • Do you connect lag to retention and potential data loss?
  • Do you express lag in time rather than count?
  • Do you check per-partition to spot hot keys?
  • Do you know about rebalance loops?
  • Do you know adding consumers is capped, and adding partitions breaks ordering?
Weak answers
  • Red flag: "add more consumers" as the whole answer.
  • Red flag: no awareness that retention deletes unread data.
  • Red flag: adding partitions without mentioning the ordering break.
Likely follow-ups
  • How would you handle a hot key?
  • How do you process concurrently within a partition safely?
  • What would you set retention to, and why?
When would you use log compaction instead of retention? ⭐ Senior-level
How I'd answer

"They answer different questions, so the choice follows from what the topic represents."

"Retention is a time window over a stream of events. It suits topics where the topic means 'these things happened' and old events stop mattering — order placed, payment received, page viewed. Log size is bounded by time or bytes."

"Compaction keeps the latest value per key, indefinitely. So the topic means 'this is the current state of each entity' rather than a history. Log size is bounded by the number of distinct keys, not by time."

"The property that makes compaction powerful: a brand-new consumer can read the topic from the beginning and end up with complete current state for every key, however old. With retention it would only get whatever falls inside the window — so if retention is 7 days, you cannot rebuild state for an entity that hasn't changed in a month, because its last event is gone."

"That's what makes compacted topics the foundation for materialised views, caches and lookup tables — a consumer bootstraps itself with no separate seeding process. It's also how Kafka stores its own consumer offsets, in the compacted __consumer_offsets topic."

"So concretely I'd use compaction for: a customer or product catalogue where I need current details per id; configuration or feature flags; any read model I might need to rebuild; and anything where a new consumer must be able to bootstrap full state."

"And retention for: event streams, audit trails, telemetry — anything where the sequence is the point and old entries expire."

"To delete a key under compaction you publish a tombstone — a message with that key and a null value. Compaction then removes the key entirely after delete.retention.ms, which exists to give consumers time to observe the deletion rather than it vanishing before they see it. That's also how you satisfy a GDPR erasure request against a compacted topic, which is worth knowing because 'the log is immutable' otherwise sounds like a compliance problem."

"Two caveats I'd state, because they cause bugs. Compaction is asynchronous and best-effort, and it only ever compacts inactive segments — so the newest data is never compacted. Which means a consumer can legitimately see several values for the same key and must handle that; treating a compacted topic as guaranteeing one message per key is wrong."

"You can also combine them — cleanup.policy=compact,delete — to keep the latest value per key and eventually expire keys that stop being updated. That's useful for something like session state, where you want current values but don't want dead keys accumulating forever."

What they're really checking
  • Do you frame it as events versus state?
  • Do you know a new consumer can bootstrap from a compacted topic?
  • Do you know about tombstones and delete.retention.ms?
  • Do you know compaction is asynchronous, so duplicates appear?
  • Bonus: do you know the combined policy?
Likely follow-ups
  • How does this relate to event sourcing?
  • How would you handle a GDPR deletion request?
  • What stops a compacted topic growing forever?
