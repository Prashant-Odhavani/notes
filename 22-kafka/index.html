Kafka

Not a message queue. A distributed, replayable log — and that single difference drives everything about when it's the right choice.

🔴 Advanced ⭐ Senior-level

Kafka is not a queue 🔥 Must know

The one difference that matters

A queue deletes a message once it's consumed. The message is a unit of work that gets done and disappears.

Kafka appends to a log and keeps it. Consumers track their own position. Reading doesn't remove anything — so many independent consumers can read the same data, and any of them can rewind.

Think of it this way

A queue is a to-do list. You take an item, do it, cross it off. It's gone.

Kafka is a ledger. Entries are written in order and never removed. Different readers keep bookmarks at different pages, and anyone can go back and re-read from any point.

That's why "replay the last three days of events into a new service" is natural in Kafka and impossible with a queue.

Senior signal — the consequences of an append-only log

Because the log is immutable and consumers only track an offset, Kafka cannot do per-message operations. There's no "dead-letter this one message and carry on", no "defer this for ten minutes", no "complete message 5 but not message 4".

That's not a missing feature — it's inherent to the design. Offsets are positions in a sequence, so acknowledging message 6 implicitly acknowledges everything before it.

Practically that means you build dead-lettering yourself: catch the failure, produce the message to a separate error topic, and commit the offset anyway. And a poison message you don't handle blocks its partition indefinitely, because you can't skip it without committing past it.

Service Bus gives you all of that in the broker. So "Kafka has higher throughput" is true and often irrelevant — the real question is whether you need replay and multiple independent readers enough to give up per-message control.

The deciding question

Do you need to replay, or do you need many independent readers of the same events?

If yes — Kafka's design is genuinely different and worth the operational cost.

If no, and you mainly need reliable work distribution with per-message handling — Azure Service Bus or RabbitMQ is the better tool, and choosing Kafka means taking on complexity for capabilities you won't use.

The operational cost is the part that's understated

Self-hosted Kafka is a genuinely demanding system to run. Broker sizing, partition planning, replication factors, ISR configuration, rebalance tuning, retention and compaction policies, consumer lag monitoring, and — historically — a ZooKeeper cluster alongside it.

Partition count in particular is a decision you largely commit to upfront: you can add partitions, but doing so changes which partition a key maps to, which breaks the ordering guarantee for existing keys. You cannot reduce them at all.

So unless there's a platform team, use a managed service — Confluent Cloud, Azure Event Hubs with the Kafka endpoint, or MSK. The economics change completely: Event Hubs in particular gives you a Kafka-compatible endpoint with none of the broker operations, which for a .NET shop on Azure is frequently the pragmatic answer.

"We'd use Event Hubs rather than running Kafka ourselves" is a strong, practical answer.

Stream processing is where .NET is genuinely behind

Kafka Streams and ksqlDB are JVM-first, and the .NET equivalents are considerably less mature. So windowed aggregations, stream-table joins and stateful stream processing are much harder from .NET than from Java.

That's worth knowing as an honest constraint. If the requirement is heavy stream processing, the options are a JVM service for that part, Azure Stream Analytics, or accepting a less mature library.

For the common case — produce and consume events with partitioned ordering — Confluent.Kafka is entirely solid and there's no gap. It's specifically the processing topology layer that's thin.

Kafka or Azure Service Bus? 🔥 Must know
How I'd answer

"They solve different problems, so I'd start from what the workload actually needs rather than comparing throughput numbers."

"The fundamental difference is that a queue deletes a message when it's consumed, and Kafka keeps it. Kafka is an append-only log where consumers track their own offset — so reading doesn't remove anything, many independent consumers can read the same data, and any of them can rewind."

"So the deciding question is: do I need replay, or many independent readers of the same events?"

"If yes, Kafka's design is genuinely different and worth the cost. Rebuilding a read model from three days of history, onboarding a new consumer that needs to process everything from the beginning, having analytics and search indexing and audit all consume the same stream independently — those are natural in Kafka and impossible with a queue."

"If no, Service Bus is the better tool — and I'd say that plainly rather than defaulting to Kafka because it's the more impressive answer."

"The reason is that Service Bus gives you things Kafka structurally cannot. Per-message operations: dead-letter this one message, defer that one for ten minutes, complete message 5 but not message 4. Kafka can't do any of that, because an offset is a position in a sequence — acknowledging message 6 implicitly acknowledges everything before it."

"So with Kafka you build dead-lettering yourself: catch the failure, produce to an error topic, commit the offset anyway. And an unhandled poison message blocks its partition indefinitely, because you can't skip past it without committing. Service Bus handles all of that in the broker, along with scheduled delivery and duplicate detection."

"For a typical .NET line-of-business system — send this invoice, process this order, notify these services — that per-message control matters far more than throughput. Most systems are nowhere near Kafka's throughput advantage being relevant."

"The operational cost is the other half. Self-hosted Kafka is demanding: broker sizing, partition planning, replication and ISR configuration, rebalance tuning, retention and compaction, lag monitoring. Partition count especially is largely a one-way decision — you can add partitions, but that changes which partition a key maps to and breaks ordering for existing keys, and you can't reduce them at all."

"So unless there's a platform team, I'd use a managed service. For a .NET shop on Azure, Event Hubs with the Kafka endpoint is often the pragmatic answer — Kafka-compatible protocol, no broker operations."

"One honest constraint if the plan involves stream processing: Kafka Streams and ksqlDB are JVM-first and the .NET equivalents are much less mature. So windowed aggregations and stream-table joins are meaningfully harder from .NET. Producing and consuming is fine; it's the processing topology layer that's thin."

"And they're not mutually exclusive — a common shape is Kafka as the event backbone for analytics and integration, with Service Bus for command-style work distribution where per-message handling matters."
