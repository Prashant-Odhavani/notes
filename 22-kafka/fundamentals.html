Architecture & Fundamentals

Partitions are the unit of everything — parallelism, ordering and scaling all follow from them.

🟡 Intermediate 🔴 Advanced 🔥 Must know
Quick revision
  • A topic is split into partitions. A partition is an ordered, append-only log.
  • Ordering is guaranteed within a partition only — never across a topic.
  • Same key → same partition, which is how you get ordering where it matters.
  • Partition count caps consumer parallelism. Extra consumers sit idle.
  • Offsets are per consumer group, so groups are independent.
  • acks=all plus min.insync.replicas=2 is the durable configuration.

Remember this

The partition is the unit of parallelism, ordering and scale — all three.

Ordering exists within a partition. Consumer parallelism is capped by partition count. Distribution across brokers is per partition.

Which means the partition count decision constrains everything downstream, and it's the one you can't easily undo.

Partition keys 🔥 Must know

await producer.ProduceAsync("orders", new Message<string, string>
{

// Same key -> same partition -> ordered relative to each other.
// Null key -> round-robin (or sticky batching) -> NO ordering guarantee.

Adding partitions breaks ordering for existing keys

Partition assignment is hash(key) % partitionCount. Change the count and the modulo changes — so a key that mapped to partition 2 may now map to partition 5.

The consequence: that key's older messages are in the old partition and its new messages are in a different one. Two consumers process them concurrently, and the ordering guarantee you were relying on silently no longer holds — for historical data as well as new.

And you cannot reduce partition count at all.

So partition count is effectively a design-time decision. The usual advice is to over-provision — more partitions than you currently need, since they're relatively cheap — but not excessively, because each one costs file handles, memory and rebalance time.

This is the Kafka equivalent of Cosmos's immutable partition key: the decision you must get right up front.

Consumer groups 🔥 Must know

The mechanism

Consumers with the same group.id form a group, and Kafka assigns each partition to exactly one consumer in that group. So the group collectively processes everything, once.

A different group gets its own assignment and its own offsets — so it reads everything independently, unaffected by the first group.

  Topic: orders (4 partitions)

  Group "fulfilment" (2 consumers)      Group "analytics" (1 consumer)
    Consumer A -> P0, P1                  Consumer X -> P0, P1, P2, P3
    Consumer B -> P2, P3

  Both groups receive EVERY message. Within a group, each partition
  goes to one consumer. The groups' offsets are completely separate.

Partition count is a hard ceiling on consumer parallelism

A partition is only ever assigned to one consumer per group — that's what preserves ordering. So consumers beyond the partition count do nothing at all.

This catches teams during an incident: the queue is backing up, they scale the consumer deployment from 4 to 12 pods, and throughput doesn't change. The extra 8 are idle, and now rebalances are slower.

To increase consumer parallelism you must add partitions — which breaks key ordering, as above. That's the bind, and it's why partition sizing deserves real thought before launch.

If the bottleneck is per-message processing time rather than partition count, the better fix is often to make the consumer faster or to process within a partition concurrently where ordering permits.

Offset management 🔥 Must know

var config = new ConsumerConfig
{
    BootstrapServers = brokers,
    GroupId = "fulfilment",
    EnableAutoCommit = false,                       // commit deliberately
    AutoOffsetReset = AutoOffsetReset.Earliest      // new group starts at the beginning
};

using var consumer = new ConsumerBuilder<string, string>(config).Build();
consumer.Subscribe("orders");

while (!ct.IsCancellationRequested)
{
    var result = consumer.Consume(ct);
    if (result is null) continue;

    await HandleAsync(result.Message, ct);   // process FIRST

    consumer.StoreOffset(result);            // then record progress
}
StrategySemanticsRisk
Auto-commit (periodic) Convenient Can commit before processing completes — message loss on crash
Commit after processing At-least-once Duplicate on crash between processing and commit. The usual choice
Commit before processing At-most-once Message loss on crash. Rarely what you want
Committing an offset acknowledges everything before it

An offset is a position, not a per-message flag. Committing offset 100 says "I have processed everything up to 100" — so it implicitly acknowledges 0–99 whether or not they succeeded.

That has two consequences people trip over.

You cannot acknowledge out of order. If you process messages concurrently within a partition and message 98 fails while 99 and 100 succeed, committing 100 loses 98 permanently. So concurrent processing within a partition requires tracking the lowest un-processed offset and committing only up to there.

Auto-commit can lose messages. It commits on a timer based on what's been fetched, not what's been processed. So a crash after the commit but before processing means those messages are gone — the consumer restarts past them. That's why EnableAutoCommit = false is the default choice for anything that matters.

Replication and durability 🔥 Must know

How it works

Each partition has a leader and some followers. All reads and writes go to the leader; followers copy from it.

Followers that are caught up form the in-sync replica set (ISR). If the leader fails, a new leader is elected from the ISR — so only in-sync replicas can be promoted, which is what prevents data loss.

acksProducer waits forDurability
0Nothing — fire and forgetMessages can vanish. Metrics only
1The leader onlyLost if the leader fails before followers copy it
allAll in-sync replicasDurable. The correct choice for real data
 
var config = new ProducerConfig
{
    BootstrapServers = brokers,
    Acks = Acks.All,                    // wait for all in-sync replicas
    EnableIdempotence = true,           // no duplicates from producer retries
    MessageSendMaxRetries = int.MaxValue,
    MaxInFlight = 5                     // required to be <= 5 for idempotence
};
// Broker side: min.insync.replicas = 2 with replication.factor = 3
Senior signal — acks=all alone is not durable

This is the configuration mistake that looks correct. acks=all means "wait for all in-sync replicas" — and if replicas have fallen behind, the ISR can shrink to just the leader.

At that point acks=all means acknowledgement from one broker, and losing that broker loses the data. You've configured durability and got none.

The fix is the broker-side setting min.insync.replicas=2 with replication.factor=3. Then if the ISR shrinks below 2, the producer receives an error rather than a false acknowledgement — so you fail loudly instead of silently losing data.

The trade-off is explicit: with replication factor 3 and min ISR 2, you tolerate one broker failure and remain available; two failures make the partition unwritable. That's choosing consistency over availability deliberately, which is the correct choice for data you can't lose.

Knowing that acks=all needs min.insync.replicas to mean anything is one of the better Kafka signals — it's a genuine production trap.

The insight worth stating

Kafka is fast because it does less, not because it's cleverer.

A queue must track per-message state — delivered, acknowledged, deferred, dead-lettered — which means random access and bookkeeping. Kafka appends to a file and stores one integer per consumer group.

So the performance advantage and the missing features are the same design decision. You can't have per-message dead-lettering and the throughput of an append-only log.

That framing is much stronger than reciting "zero-copy and sequential I/O", because it explains the trade-off rather than just the optimisation.

ZooKeeper is gone

Kafka historically needed a ZooKeeper cluster for metadata and controller election — a second distributed system to operate, and a common source of problems.

KRaft mode replaced it: Kafka manages its own metadata using a Raft quorum among the brokers. ZooKeeper support was removed entirely in Kafka 4.0.

Worth knowing because older material assumes ZooKeeper, and "you also need to run ZooKeeper" is no longer a valid objection to Kafka. It also means faster failover and a much larger practical partition limit.

Key takeaways
  • The partition is the unit of ordering, parallelism and distribution.
  • Ordering exists within a partition only — never across a topic.
  • Same key means same partition; a null key means no ordering.
  • Adding partitions changes key-to-partition mapping and breaks existing ordering. You can't reduce them.
  • Partition count is a hard ceiling on consumer parallelism — extra consumers idle.
  • Consumer groups are independent; each tracks its own offsets.
  • Committing an offset acknowledges everything before it, so you can't acknowledge out of order.
  • Auto-commit can lose messages — commit after processing.
  • acks=all is meaningless without min.insync.replicas=2.
  • Kafka is fast because it does less — which is why it lacks per-message operations.
  • KRaft removed the ZooKeeper dependency.

Common mistakes

  • Expecting topic-wide ordering.
  • A null key when ordering was required.
  • A low-cardinality key, creating hot partitions.
  • Adding partitions without realising ordering breaks.
  • Scaling consumers past the partition count and expecting more throughput.
  • Auto-commit enabled on a consumer that must not lose messages.
  • Committing before processing.
  • Concurrent processing within a partition then committing the highest offset.
  • acks=1 for data that matters.
  • acks=all without min.insync.replicas.
  • Too many partitions, slowing rebalances and consuming resources.

Interview questions

Intermediate

Explain partitions, consumer groups and how they interact. 🔥 Must know
How I'd answer

"A topic is a logical name; the partition is the real unit. Each partition is an ordered, immutable, append-only log, and partitions can live on different brokers — which is how Kafka scales."

"The critical consequence: ordering is guaranteed within a partition and nowhere else. There is no topic-wide ordering, ever. So if you need messages for one customer processed in order, they must go to the same partition — which you achieve by using the customer id as the key, since Kafka assigns partitions by hashing the key."

"That gives you ordering per entity and parallelism across entities, which is usually exactly what you want."

"A consumer group is a set of consumers sharing a group.id. Kafka assigns each partition to exactly one consumer in the group — that's what preserves ordering. The group collectively processes everything once."

"Different groups are completely independent: each gets its own partition assignment and its own offsets. So a fulfilment group and an analytics group both receive every message and neither affects the other. That's how Kafka supports many independent readers of the same stream, which a queue can't."

"Two consequences that matter practically."

"Partition count is a hard ceiling on consumer parallelism. With four partitions, a fifth consumer in the group does nothing at all. This catches teams during incidents: the lag is growing, they scale from 4 pods to 12, and throughput doesn't move — eight are idle and rebalances are now slower."

"And you can't simply add partitions to fix that, because partition assignment is hash(key) % partitionCount. Change the count and a key that mapped to partition 2 may now map to partition 5 — so that key's old messages are in one partition and its new ones in another, being processed concurrently. The ordering guarantee silently stops holding. And you can't reduce partitions at all."

"So partition count is effectively a design-time decision. I'd over-provision moderately — more than currently needed, since partitions are fairly cheap — but not wildly, because each costs file handles, memory and rebalance time."

"On offsets, the thing to know is that an offset is a position, not a per-message acknowledgement. Committing offset 100 means 'everything up to 100 is done' — so it implicitly acknowledges 0 to 99 whether they succeeded or not. That's why you can't acknowledge out of order, and why processing concurrently within a partition requires tracking the lowest un-processed offset rather than just committing the highest one you finished."

  • Do you know ordering is per-partition only?
  • Do you know the key determines the partition?
  • Do you know partition count caps parallelism?
  • Do you know adding partitions breaks ordering?
  • Do you know offsets are positions, not per-message flags?

Advanced

How do you make sure a message is never lost? ⭐ Senior-level
How I'd answer

"There are three places a message can be lost — producing, in the broker, and consuming — and each needs its own configuration. Getting one right and missing another is the usual failure."

"Producer side: acks=all, so the producer waits for all in-sync replicas rather than just the leader. With acks=1 a message acknowledged by the leader is lost if that leader fails before followers copy it."

"I'd also set enable.idempotence=true, which prevents producer retries creating duplicates — the broker deduplicates using a producer id and sequence number. And unbounded retries, so a transient broker problem doesn't drop the message."

"But here's the trap, and it's the important part: acks=all alone is not durable. It means 'all in-sync replicas' — and if followers fall behind, the ISR can shrink to just the leader. At that point acks=all is acknowledgement from one broker, and losing it loses the data. You've configured durability and got none."

"So the broker needs min.insync.replicas=2 with replication.factor=3. Then if the ISR drops below 2, the producer gets an error instead of a false acknowledgement — you fail loudly rather than losing data silently."

"That's an explicit availability trade: with factor 3 and min ISR 2 you survive one broker failure and stay writable; two failures make the partition unwritable. For data you can't lose, that's the right choice."

"I'd also disable unclean leader election, which would otherwise let an out-of-sync replica become leader — trading data loss for availability."

"Consumer side: enable.auto.commit=false and commit after processing. Auto-commit runs on a timer against what's been fetched, so a crash after the commit but before processing means those messages are gone — the consumer restarts past them."

"Committing after processing gives at-least-once, so the consumer must be idempotent because a crash between processing and commit means redelivery. That's unavoidable, so I'd handle it with a dedupe key rather than pretend it won't happen."

"And the piece outside Kafka: if the message originates from a database change, the outbox pattern. Writing to the database and producing to Kafka aren't atomic — if the produce fails after the commit, the data changed and nothing downstream knows. Writing the event into the same transaction and relaying it afterwards is the only reliable answer."

"So the full chain is: outbox for atomicity with the database; acks=all plus min.insync.replicas plus idempotence for producing; replication for broker durability; and manual commit after processing with idempotent handling for consuming. Missing any one of those leaves a hole, and the min.insync.replicas one is the hole people don't know they have."

What they're really checking
  • Do you cover all three loss points?
  • Do you know acks=all needs min.insync.replicas?
  • Do you know auto-commit can lose messages?
  • Do you require idempotent consumers?
  • Do you connect it to the outbox?
Weak answers
  • Red flag: "acks=all" as the complete answer.
  • Red flag: no mention of the consumer side.
  • Red flag: claiming exactly-once without idempotency.
Likely follow-ups
  • What's unclean leader election and why disable it?
  • How does the idempotent producer actually work?
  • What's the latency cost of acks=all?
