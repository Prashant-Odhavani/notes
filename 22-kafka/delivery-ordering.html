Delivery Semantics & Ordering

Kafka does offer exactly-once — with conditions that are usually not met. Knowing where the boundary sits is the whole topic.

🔴 Advanced ⭐ Senior-level 🔥 Must know
Quick revision
  • At-least-once is the practical default — commit after processing.
  • The idempotent producer removes duplicates from producer retries, not from consumer redelivery.
  • Kafka transactions give exactly-once for Kafka-to-Kafka only.
  • If your consumer writes to a database, transactions don't cover it — you still need idempotency.
  • Ordering is per partition, and a rebalance can still cause reprocessing.
  • Dead-lettering is something you build — Kafka has no equivalent.

The three semantics 🔥 Must know

SemanticHow you get itFailure mode
At-most-once Commit the offset before processing Message loss — a crash after commit skips it forever
At-least-once Commit after processing Duplicates — a crash before commit reprocesses
Exactly-once Transactions, or at-least-once plus idempotent handling Complexity, and narrower applicability than advertised
The practical answer

At-least-once delivery plus idempotent processing. That's what almost every production system uses, and it produces an exactly-once effect.

Kafka's transactional exactly-once is real, and it applies to a narrower case than people assume — which is the distinction worth getting right.

The idempotent producer 🔥 Must know

The problem it solves

A producer sends a message, the broker writes it, and the acknowledgement is lost in transit. The producer retries — and now the message is in the log twice.

The idempotent producer fixes this: each producer gets an id, and each message carries a sequence number per partition. The broker rejects a duplicate sequence number, so retries are safe.

var config = new ProducerConfig
{
    BootstrapServers = brokers,
    EnableIdempotence = true,        // producer id + per-partition sequence numbers
    Acks = Acks.All,                 // implied by idempotence, but be explicit
    MessageSendMaxRetries = int.MaxValue,
    MaxInFlight = 5                  // must be <= 5 for idempotence to hold
};
What it does not cover

This is the distinction that matters. The idempotent producer prevents duplicates caused by producer retries within one session. That's it.

It does not prevent: your application code calling ProduceAsync twice because of a bug or a retry higher up; duplicates after a producer restart, since a new session gets a new producer id; or consumer reprocessing after a crash or rebalance.

So enabling it is correct and free, and it solves one narrow problem. It is not "Kafka has exactly-once now" — and treating it that way is a common misreading.

Kafka transactions ⭐ Senior-level

What they actually do

A transaction lets a producer write to several partitions and commit consumer offsets atomically.

That makes the consume → transform → produce pattern exactly-once: either the output messages and the offset commit both land, or neither does.

producer.InitTransactions(TimeSpan.FromSeconds(10));

while (!ct.IsCancellationRequested)
{
    var result = consumer.Consume(ct);
    if (result is null) continue;

    producer.BeginTransaction();
    try
    {
        var output = Transform(result.Message.Value);
        producer.Produce("orders-enriched", new Message<string, string>
        {
            Key = result.Message.Key, Value = output
        });

        // The offset commit is PART of the transaction
        producer.SendOffsetsToTransaction(
            [new TopicPartitionOffset(result.TopicPartition, result.Offset + 1)],
            consumer.ConsumerGroupMetadata, TimeSpan.FromSeconds(10));

        producer.CommitTransaction();
    }
    catch
    {
        producer.AbortTransaction();
        throw;
    }
}
Transactions only cover Kafka — this is the limit people miss

Kafka transactions are atomic across Kafka partitions and offsets. Nothing else.

So if your consumer writes to SQL Server and then commits the offset, the transaction gives you nothing — the database write is outside its scope. A crash between the database commit and the offset commit means reprocessing, and the database write happens twice.

Which is the overwhelmingly common case: most consumers write to a database, not to another topic.

So the honest position: Kafka's exactly-once applies to stream processing — reading a topic, transforming, writing a topic. For consumers with external side effects you're back to at-least-once plus idempotency, and the transaction machinery buys you nothing while costing throughput.

Being able to state that boundary precisely is one of the strongest Kafka signals available, because "Kafka supports exactly-once" is widely repeated without the qualifier.

Consumers must opt in to see only committed data

Transactional writes are visible to consumers by default, even before commit. To read only committed data you must set isolation.level=read_committed.

With the default read_uncommitted, a consumer sees messages from transactions that later abort — so you get data that was explicitly rolled back.

That's a genuine footgun: the producer side is configured carefully for exactly-once and the consumer quietly reads uncommitted output. Both ends have to be configured.

Making consumers idempotent 🔥 Must know

public async Task ConsumeAsync(ConsumeResult<string, string> result, CancellationToken ct)
{
    // A natural key from the log position - stable across redeliveries
    var messageKey = $"{result.Topic}:{result.Partition.Value}:{result.Offset.Value}";

    await using var tx = await _db.Database.BeginTransactionAsync(ct);

    _db.ProcessedMessages.Add(new ProcessedMessage(messageKey, DateTime.UtcNow));
    try
    {
        await _db.SaveChangesAsync(ct);          // unique constraint on messageKey
    }
    catch (DbUpdateException) when (IsUniqueViolation)
    {
        return;                                  // already processed
    }

    await ApplyAsync(result.Message, ct);        // the actual work
    await _db.SaveChangesAsync(ct);
    await tx.CommitAsync(ct);                    // both commit together
}
Topic-partition-offset is a good dedupe key

Unlike a queue message id, Kafka gives you a naturally stable identifier for free: the combination of topic, partition and offset uniquely identifies a message in the log, and it's identical on every redelivery.

One caveat: it identifies a log position, not a logical event. If the producer published the same logical event twice — at different offsets — dedupe by position won't catch it. For that you need a business key or an event id in the payload.

So: offset-based dedupe protects against redelivery; a payload event id protects against duplicate publication. Which you need depends on whether the producer is idempotent, and knowing the difference is worth stating.

What ordering actually guarantees 🔥 Must know

GuaranteedNot guaranteed
Order within a partitionOrder across partitions
Order for a given key (same partition)Order across a topic
Offsets increase monotonically per partitionThat a message is processed exactly once
A consumer reads a partition in orderThat it won't reprocess after a rebalance
A rebalance can cause reprocessing even with correct code

When a consumer joins, leaves or is deemed dead, Kafka rebalances — reassigning partitions across the group.

If a consumer was mid-batch and hadn't committed, the partition moves to another consumer which starts from the last committed offset — so those messages are processed again, by a different consumer.

That's correct behaviour and unavoidable. It means idempotency isn't only about crashes — routine deployments trigger rebalances, so every rolling deploy is an opportunity for reprocessing.

Two mitigations. Commit more frequently, which narrows the window at the cost of more commit overhead. And handle PartitionsRevoked to commit before releasing the partition, which makes a graceful handover clean.

But the durable answer is idempotency, because an ungraceful failure has no handover at all.

var consumer = new ConsumerBuilder<string, string>(config)
    .SetPartitionsRevokedHandler((c, partitions) =>
    {
        // Losing these partitions - commit what we've finished
        try { c.Commit(); }
        catch (KafkaException ex) { _logger.LogWarning(ex, "Commit on revoke failed"); }
    })
    .Build();
Cooperative rebalancing reduces the disruption

The classic strategy is eager: every consumer stops and gives up all partitions, then everything is reassigned. So adding one consumer briefly halts the entire group — a "stop-the-world" rebalance.

partition.assignment.strategy=CooperativeSticky only moves the partitions that need to move, and consumers keep processing the rest. On a large group that's the difference between a brief hiccup and a multi-second stall on every deployment.

It's the default in newer clients and worth verifying explicitly, because an eager rebalance on a group of thirty consumers during a rolling deploy is a visible latency spike.

Dead-lettering in Kafka ⭐ Senior-level

There is no built-in mechanism

Kafka has no dead-letter queue. An offset is a position, so you cannot mark one message as failed and continue past it — committing past a message acknowledges it.

So dead-lettering is something you implement.

try
{
    await ApplyAsync(result.Message, ct);
}
catch (Exception ex) when (IsPermanent(ex))
{
    // Produce to an error topic WITH enough context to diagnose and replay
    await producer.ProduceAsync("orders.dlq", new Message<string, string>
    {
        Key = result.Message.Key,
        Value = result.Message.Value,
        Headers = new Headers
        {
            { "original-topic",     Encoding.UTF8.GetBytes(result.Topic) },
            { "original-partition", Encoding.UTF8.GetBytes(result.Partition.Value.ToString()) },
            { "original-offset",    Encoding.UTF8.GetBytes(result.Offset.Value.ToString()) },
            { "error",              Encoding.UTF8.GetBytes(ex.Message) },
            { "traceparent",        Encoding.UTF8.GetBytes(Activity.Current?.Id ?? "") },
            { "failed-at",          Encoding.UTF8.GetBytes(DateTime.UtcNow.ToString("O")) }
        }
    }, ct);
}

consumer.StoreOffset(result);   // commit either way, so the partition progresses
Senior signal — the ordering consequence of dead-lettering

Committing past a failed message breaks the ordering guarantee for that key. If message 5 for customer A is dead-lettered and message 6 is processed, then A's events have been applied out of order — and if you later replay message 5, it applies after 6.

That may be fine, or it may corrupt state, depending entirely on whether the handlers are commutative.

So dead-lettering in Kafka is a deliberate choice of availability over ordering, per partition. The alternative — halting the partition until the message is fixed — preserves ordering and stops all progress for every key in that partition.

Knowing that this is a trade-off with no free option, rather than a feature to configure, is the senior answer. And it's a reason to prefer state-based over delta-based messages: if the payload says "quantity is now 5" rather than "add 2", replaying out of order is harmless.

Retry topics, and their cost

A common pattern is tiered retry topics — orders.retry.5m, orders.retry.1h — with a consumer that waits before reprocessing. That gives delayed retry, which Kafka has no native support for.

The cost is that a message moved to a retry topic has left its original partition, so it has lost all ordering relationship with its siblings. And you've added topics and consumers to operate.

It works, and it's a lot of machinery to reproduce something Service Bus does natively with ScheduleMessageAsync. Worth mentioning as a reason the broker choice matters.

Key takeaways
  • At-least-once plus idempotency is the practical answer for almost every consumer.
  • The idempotent producer only prevents duplicates from producer retries in one session.
  • Kafka transactions are atomic across Kafka partitions and offsets — nothing external.
  • If the consumer writes to a database, transactions buy you nothing.
  • Consumers need read_committed or they see aborted transactions.
  • Topic-partition-offset is a good dedupe key for redelivery; a payload event id for duplicate publication.
  • Rebalances cause reprocessing, so every rolling deploy exercises your idempotency.
  • Commit on PartitionsRevoked, and use cooperative rebalancing.
  • Kafka has no dead-letter queue — you build it with an error topic.
  • Dead-lettering trades ordering for availability, per partition.
  • State-based messages make out-of-order replay harmless.

Common mistakes

  • Believing EnableIdempotence gives end-to-end exactly-once.
  • Using transactions with a database consumer and assuming it's covered.
  • Leaving isolation.level at read_uncommitted, so aborted data is read.
  • Non-idempotent consumers, so every rebalance duplicates work.
  • Not committing on partition revocation.
  • Eager rebalancing on a large consumer group.
  • No error topic, so a poison message blocks the partition forever.
  • Dead-lettering without considering the ordering break.
  • Delta-based messages that can't tolerate replay.
  • A dedupe table that's never pruned.

Interview questions

Advanced

Does Kafka support exactly-once delivery? 🔥 Must know
How I'd answer

"Yes, with a significant qualifier that's usually left off: Kafka's exactly-once applies to Kafka-to-Kafka processing, not to your consumer's side effects."

"Let me separate the three things people conflate."

"The idempotent producer — enable.idempotence=true — gives each producer an id and each message a per-partition sequence number, so the broker rejects duplicates. That solves exactly one problem: a producer retry after a lost acknowledgement writing the message twice. It does not cover your application calling produce twice, a producer restart, or any consumer-side reprocessing. It's free and correct and narrow."

"Kafka transactions are the real exactly-once mechanism. A producer can write to several partitions and commit consumer offsets atomically — so for consume, transform, produce, either the output and the offset commit both land or neither does. That genuinely is exactly-once for stream processing."

"But the transaction only spans Kafka. If my consumer reads a topic and writes to SQL Server, the database write is outside the transaction's scope. A crash between the database commit and the offset commit means reprocessing, and the row is written twice. The transaction machinery gives me nothing while costing throughput."

"And that's the overwhelmingly common case — most consumers write to a database or call an API, not to another topic."

"So the practical answer: at-least-once delivery plus idempotent processing, which produces an exactly-once effect. I'd implement that with a dedupe record committed in the same database transaction as the work — if the dedupe record commits separately, a crash between them marks the message processed when it wasn't, turning duplicate delivery into lost work, which is worse."

"Kafka helps here: topic-partition-offset is a naturally stable dedupe key, identical on every redelivery, so you don't need the producer to supply a message id. Though note that identifies a log position — if the producer published the same logical event at two offsets, you'd need a business key in the payload to catch that."

"One configuration detail worth flagging: if you do use transactions, consumers must set isolation.level=read_committed. The default is read_uncommitted, so a consumer will see messages from transactions that later abort — data that was explicitly rolled back. Configuring the producer carefully for exactly-once and leaving the consumer at the default is a real and quiet failure."

"And I'd mention that rebalances cause reprocessing too, not just crashes. Adding a consumer, or a rolling deployment, triggers a rebalance — an uncommitted partition moves to another consumer which restarts from the last committed offset. So every deploy exercises your idempotency, which is a good argument for it being real rather than theoretical."

What they're really checking
  • Do you separate idempotent producer from transactions?
  • Do you know transactions don't cover external writes?
  • Do you land on at-least-once plus idempotency?
  • Do you know the same-transaction dedupe requirement?
  • Do you know about read_committed?
Weak answers
  • Red flag: "yes, just enable idempotence".
  • Red flag: "no, exactly-once is impossible" with no nuance.
  • Red flag: assuming transactions cover a database write.
Likely follow-ups
  • What's the throughput cost of transactions?
  • How would you dedupe if the producer isn't idempotent?
  • How do you prune the dedupe table?
A message keeps failing and it's blocking the partition. What do you do? ⭐ Senior-level
How I'd answer

"This is a structural gap in Kafka rather than a misconfiguration, so I'd start by naming why it happens: an offset is a position, not a per-message acknowledgement. Committing offset 6 implicitly acknowledges everything before it. So there is no way to skip message 5 and continue — committing past it is acknowledging it."

"That's why Kafka has no dead-letter queue. Service Bus can mark one message dead and move on because it tracks per-message state; Kafka tracks one integer per consumer group."

"So the options, and none of them are free."

"1. Halt the partition and alert. Stop consuming, page someone, fix the underlying problem, resume. Preserves ordering perfectly and stops all progress for every key in that partition — so one bad order for one customer blocks thousands of unrelated customers. Rarely acceptable."

"2. Produce to an error topic and commit anyway. This is what most systems do — the hand-built equivalent of dead-lettering. Catch the permanent failure, produce the message to orders.dlq with headers carrying the original topic, partition, offset, the exception and the trace id, then commit the offset so the partition progresses."

"3. Tiered retry topics for delayed retry, since Kafka has no native scheduled delivery. A consumer on orders.retry.5m waits then reprocesses. It works and it's a lot of machinery to reproduce something Service Bus does with one method call."

"The consequence I'd make explicit, because it's the part usually missed: option 2 breaks the ordering guarantee for that key. If message 5 for customer A is dead-lettered and message 6 is processed, A's events have been applied out of order — and replaying 5 later applies it after 6."

"Whether that's acceptable depends entirely on whether the handlers are commutative. Which is a strong argument for state-based rather than delta-based messages: if the payload says 'quantity is now 5', out-of-order replay is harmless. If it says 'add 2', it corrupts the total."

"So dead-lettering in Kafka is choosing availability over ordering, per partition, and that should be a deliberate decision rather than a default someone configured."

"Practically I'd also: validate at the boundary so a message that can't be deserialised goes straight to the error topic on the first attempt rather than being retried three times while blocking; distinguish transient from permanent so I'm not dead-lettering a message that failed because a dependency was briefly down; alert on error-topic depth greater than zero, because an unmonitored error topic is silent data loss; and build the replay tooling up front, since the whole point is reprocessing after a fix and teams discover during an incident that they never wrote it."

What they're really checking
  • Do you know why Kafka can't skip a message?
  • Do you know dead-lettering is something you build?
  • Do you spot the ordering break?
  • Do you connect it to state-vs-delta message design?
  • Do you plan monitoring and replay?
Weak answers
  • Red flag: "use the dead-letter queue" — Kafka has none.
  • Red flag: skipping the message with no ordering discussion.
  • Red flag: retrying forever.
Likely follow-ups
  • How would you replay from the error topic safely?
  • What if the failure is a schema change?
  • Would Service Bus have been a better choice here?
