Data & Consistency

The hardest part of microservices. You gave up transactions across services — this page is about what replaces them.

🔴 Advanced ⭐ Senior-level 🔥 Must know
Quick revision
  • You can't have a transaction across services. Two-phase commit exists and you shouldn't use it.
  • A saga is a sequence of local transactions with compensating actions.
  • Compensation isn't rollback — it's a new action that undoes the effect.
  • Orchestration = a coordinator drives it. Choreography = services react to events.
  • Every consumer must be idempotent. At-least-once delivery guarantees redelivery.
  • "Exactly once" doesn't exist at the transport level — you achieve it with deduplication.
  • Eventual consistency is a product decision, not just a technical one.

Why you can't just use a transaction 🔥 Must know

The problem

Placing an order needs to reserve inventory, charge a card and create a shipment. In a monolith that's one transaction — all of it commits or none of it does.

Across three services with three databases, there is no shared transaction. Each can succeed or fail independently, so partial completion is the normal case, not an edge case.

Two-phase commit: why it's not the answer

2PC does provide atomicity across databases — a coordinator asks everyone to prepare, then tells everyone to commit.

The problems are severe. It's blocking: participants hold locks from prepare until commit, so a slow participant blocks everyone. It has a coordinator single point of failure — if the coordinator dies after prepare, participants are stuck holding locks with no idea what to do. Availability is the product of all participants, so it gets worse with each one. And it's not supported by most modern data stores — Cosmos DB, DynamoDB, most message brokers, and it doesn't work on Linux in .NET via MSDTC.

Most fundamentally, it's the opposite of what microservices are for: you deliberately decoupled services, then reintroduced a runtime dependency where they all have to be available and cooperating for anything to complete.

So the answer isn't a better distributed transaction. It's accepting eventual consistency and designing for it — which is what sagas are.

The Saga pattern 🔥 Must know

In simple terms

Break the distributed operation into a sequence of local transactions, each in one service and each atomic on its own.

If a step fails, run compensating actions for the steps that already succeeded — working backwards.

Think of it this way

Booking a holiday: flight, hotel, car. Three separate companies, no shared transaction.

If the car booking fails, you don't get an atomic rollback — you cancel the hotel and cancel the flight. Those are new actions with their own consequences: a cancellation record, possibly a fee.

That's compensation, and the fact that it leaves a trace is the important difference from rollback.

StepLocal transactionCompensating action
1Create order (Pending)Mark order Failed
2Reserve inventoryRelease reservation
3Charge paymentRefund — a new transaction, not an undo
4Create shipmentCancel shipment
5Mark order Confirmed—
Senior signal — compensation is not rollback, and the difference is visible

A database rollback leaves no trace. It's as if the transaction never happened.

Compensation is a new business action with its own record. A refund isn't an un-charge — the customer sees a charge and a refund on their statement, there may be a fee, and the accounting shows both.

That has real consequences you have to design for. Some steps can't be compensated at all — you can't un-send an email, un-ship a parcel, or un-disclose data. So the ordering matters: put irreversible steps last, after everything that could still fail.

That single rule — irreversible steps last — is one of the most practically useful things about saga design, and it's the part people miss. Sending the confirmation email before charging the card means a failed payment leaves the customer with a confirmation for an order that doesn't exist.

There's also an intermediate-state visibility problem: during the saga, the order exists in a Pending state that other parts of the system and possibly the user can see. That state has to be meaningful in the domain, not an implementation artefact.

  Order Service      --OrderCreated-->
  Inventory Service  --InventoryReserved-->
  Payment Service    --PaymentCharged-->
  Shipping Service   --ShipmentCreated-->
  Order Service      (marks Confirmed)

  On failure, each service publishes a failure event and the
  previous ones subscribe to compensate.
  No component knows the whole flow.
public sealed class PlaceOrderSaga(
    IOrderService orders,
    IInventoryService inventory,
    IPaymentService payments,
    IShippingService shipping,
    ILogger<PlaceOrderSaga> logger)
{
    public async Task<Result> ExecuteAsync(PlaceOrderRequest req, CancellationToken ct)
    {
        // Track what needs undoing, in reverse order
        var compensations = new Stack<Func<Task>>();

        try
        {
            var order = await orders.CreateAsync(req, ct);
            compensations.Push(() => orders.MarkFailedAsync(order.Id));

            var reservation = await inventory.ReserveAsync(order.Lines, ct);
            compensations.Push(() => inventory.ReleaseAsync(reservation.Id));

            var charge = await payments.ChargeAsync(order.Total, req.PaymentToken, ct);
            compensations.Push(() => payments.RefundAsync(charge.Id));

            // Irreversible steps LAST - nothing after this can fail and need undoing
            await shipping.CreateAsync(order.Id, ct);
            await orders.ConfirmAsync(order.Id, ct);

            return Result.Ok(order.Id);
        }
        catch (Exception ex)
        {
            logger.LogError(ex, "Saga failed; compensating {Count} steps", compensations.Count);
            await CompensateAsync(compensations);
            return Result.Fail("Order could not be completed.");
        }
    }

    private static async Task CompensateAsync(Stack<Func<Task>> compensations)
    {
        while (compensations.Count > 0)
        {
            var undo = compensations.Pop();
            try { await undo(); }
            catch (Exception ex)
            {
                // A failed compensation needs a human. Do NOT swallow it.
                // Continue compensating the rest, but raise an alert.
                Alert.CompensationFailed(ex);
            }
        }
    }
}
Senior signal — failed compensation is the case nobody plans for

Every saga example shows the happy path and the compensation path. Almost none address what happens when the compensation itself fails — the refund API is down, the inventory release times out.

You are now in a genuinely inconsistent state that the system cannot resolve on its own. The card is charged and the order is failed.

So a production saga needs: retries with backoff on compensations, because most failures are transient; persistence of saga state so it survives a process restart and can resume; an alert to a human, because some cases require judgement; and often a reconciliation job that finds sagas stuck in an intermediate state past a threshold.

Mentioning that compensation can fail — and that this requires an operational answer rather than a code answer — is one of the strongest signals available on this topic. It's the difference between having read about sagas and having run one.

Which to choose

Orchestration for anything non-trivial. The flow is in one readable method, error handling is explicit, and you can answer "where is this order stuck?" by looking at one place. With choreography, the flow exists only as an emergent property of subscriptions — and reconstructing it means reading five services.

Choreography where the steps are genuinely independent reactions — "when an order is placed, update the search index, send a receipt, award loyalty points". Those don't form a sequence, they're parallel side effects, and each new one should be addable without touching the publisher.

The nuance worth stating: choreography is looser coupling but harder operations. Teams often choose it for the coupling benefit and then can't debug the system. If you can't answer "why did this order never complete?" in under a minute, the coupling you saved wasn't worth it.

In .NET, MassTransit provides both — a state-machine saga for orchestration and event consumers for choreography — with saga state persistence built in, which is the part you don't want to hand-roll.

Idempotency 🔥 Must know

The rule

Message delivery is at-least-once. So every consumer will receive duplicates, and must handle them.

This isn't a rare edge case — it's guaranteed. A consumer that processes a message and crashes before acknowledging will receive it again. That's the broker doing its job correctly.

So "charge the card" must be safe to receive twice.

TechniqueHow
Naturally idempotent operation SET status = 'Shipped' — applying it twice changes nothing. Best where possible
Deduplication table (inbox) Record the message id in the same transaction as the work. A duplicate hits a unique constraint and is skipped
Version check Apply only if the entity's version matches — optimistic concurrency
Idempotency key Caller supplies a key; the service returns the original result for a repeat
State check "Already shipped? Then do nothing." Simple, and racy without a lock or a constraint 
public async Task HandleAsync(OrderPlaced message, CancellationToken ct)
{
    await using var tx = await _db.Database.BeginTransactionAsync(ct);

    // Unique constraint on MessageId is what makes this safe
    _db.ProcessedMessages.Add(new ProcessedMessage(message.MessageId, DateTime.UtcNow));

    try
    {
        await _db.SaveChangesAsync(ct);       // throws if already processed
    }
    catch (DbUpdateException) when (IsUniqueViolation)
    {
        return;                               // duplicate - already handled
    }

    // The work and the dedupe record commit TOGETHER.
    // A crash before commit means neither happened, so redelivery is correct.
    await DoTheWorkAsync(message, ct);
    await _db.SaveChangesAsync(ct);
    await tx.CommitAsync(ct);
}
Senior signal — "exactly once" does not exist

Brokers advertise it and it isn't achievable at the transport level. The reason is the ambiguous timeout: a consumer processes a message and crashes before its acknowledgement lands. The broker cannot distinguish "processed but unacknowledged" from "never processed", so it must redeliver — and if it didn't, it would lose messages instead.

What you can have is at-least-once delivery plus idempotent processing, which produces exactly-once effect. That's the accurate framing, and it's what "exactly-once" always means in practice.

The critical detail in the inbox pattern is that the dedupe record and the work commit in the same transaction. If you record the message id first and commit separately, a crash between them means the message is marked processed but the work never happened — you've turned duplicate delivery into lost work, which is worse.

Being precise about this — rather than accepting "exactly once" as a feature — is a strong distributed systems signal.

Eventual consistency ⭐ Senior-level

In simple terms

Different services hold different views of the same fact, and they converge eventually — usually within milliseconds, occasionally longer.

Which means there is a window where the system is observably inconsistent, and the business has to agree that's acceptable.

Problem it createsHow to handle it
User doesn't see their own change Return the written entity rather than re-reading; or read from the write model briefly after a write
Two services disagree Define one as authoritative; reconcile the others against it
An intermediate state is visible Make it a real domain state — "Pending", "Reserved" — with meaningful UI
Replicas drift A reconciliation job. Not optional
An operation can't be honoured after the fact Semantic locks — reserve up front rather than checking later
Eventual consistency is a product decision, not a technical one

"Your order is confirmed, but the stock count updates in a few seconds" is a business rule, and someone who owns the product needs to agree to it.

The version that goes wrong: engineering adopts microservices, accepts eventual consistency as a technical consequence, and the business discovers later that overselling is now possible. Nobody agreed to that trade — it arrived as a side effect of an architecture decision.

So the conversation to have before building is: which inconsistencies are acceptable, for how long, and what happens when the window is violated? For a retailer, overselling one item and apologising may be entirely fine. For a pharmacy dispensing controlled drugs, it isn't.

Framing it that way — as a requirement to be agreed rather than a constraint to be worked around — is what distinguishes an architect from an implementer on this topic.

Semantic locks: reserve rather than check

The trap with eventual consistency is checking a condition and acting on it later. "Is there stock? Yes. Now charge the card." Between those, someone else took the stock.

The fix is to reserve instead of check. The inventory service atomically decrements available stock and issues a reservation with a TTL. If the saga fails, the reservation is released; if it's abandoned, the TTL expires and the stock returns.

That converts "hope it's still there" into a genuine claim, and it's the same atomic conditional update pattern applied across a service boundary. It also gives you the "held for 10 minutes" checkout behaviour that a plain decrement can't.

Key takeaways
  • There's no transaction across services; 2PC is blocking, fragile and largely unsupported.
  • A saga is local transactions plus compensating actions.
  • Compensation is a new business action, not a rollback — it leaves a trace.
  • Put irreversible steps last. You can't un-send an email.
  • Orchestration for complex flows; choreography for independent reactions.
  • Choreography buys loose coupling and costs debuggability.
  • Plan for compensation itself failing — retries, persisted state, alerts, reconciliation.
  • Delivery is at-least-once, so every consumer must be idempotent.
  • Dedupe record and work must commit in the same transaction.
  • "Exactly once" is at-least-once plus idempotency.
  • Eventual consistency needs business agreement, not just engineering acceptance.
  • Reserve rather than check, and give reservations a TTL.

Common mistakes

  • Reaching for two-phase commit.
  • Treating compensation as rollback, ignoring the trace it leaves.
  • Irreversible steps early in the saga.
  • No plan for failed compensation.
  • Saga state held in memory, lost on restart.
  • Choreography for a complex flow, then being unable to debug it.
  • Non-idempotent consumers.
  • Recording the dedupe key in a separate transaction from the work.
  • Trusting a broker's "exactly once".
  • Check-then-act instead of reserve.
  • No reconciliation job.
  • Accepting eventual consistency without business sign-off.

Interview questions

Advanced / scenario

An order must reserve stock, charge a card and create a shipment across three services. How? 🔥 Must know
How I'd answer

"There's no transaction spanning three services, so this is a saga — a sequence of local transactions, each atomic within its own service, with compensating actions if a later step fails."

"I'd rule out two-phase commit explicitly. It technically provides atomicity, and it's blocking — participants hold locks from prepare until commit — it has a coordinator single point of failure, its availability is the product of all participants, and it isn't supported by most modern stores or by .NET on Linux. More fundamentally it reintroduces exactly the runtime coupling that splitting the services was meant to remove."

"So the steps: create the order as Pending, reserve inventory, charge the card, create the shipment, mark the order Confirmed. Each has a compensation — mark failed, release the reservation, refund the charge, cancel the shipment."

"I'd choose orchestration over choreography here. This is a real sequence with error handling, and with orchestration the whole flow is one readable method — so when an order gets stuck I look in one place. With choreography the flow only exists as an emergent property of five services' subscriptions, and reconstructing it means reading all of them."

"Now the parts that distinguish a working saga from a diagram."

"Compensation is not rollback. A refund isn't an un-charge — the customer sees a charge and a refund on their statement, there may be a fee, and accounting records both. So compensation is a new business action with visible consequences, and the product needs to accept that."

"Order the steps so irreversible ones are last. You can't un-send an email or un-ship a parcel. So the confirmation email goes after the payment succeeds, not before — otherwise a failed charge leaves the customer holding a confirmation for an order that doesn't exist. Getting that ordering right is one of the most useful things in saga design and it's frequently missed."

"Reserve, don't check. The naive version checks stock then charges, and between those someone else takes the stock. Instead inventory atomically decrements and issues a reservation with a TTL — so it's a genuine claim. If the saga fails the reservation is released; if it's abandoned the TTL returns the stock. That also gives you 'held for 10 minutes' at checkout, which a plain check can't."

"Every step must be idempotent, because message delivery is at-least-once and a consumer that crashes before acknowledging will receive the message again. For the charge that means an idempotency key so a retry doesn't double-charge. For the inbox pattern, the critical detail is that the dedupe record and the actual work commit in the same transaction — if you record the message id separately, a crash between them means it's marked processed but never happened, which turns duplicate delivery into lost work."

"And I'd plan for compensation failing, which is the case most designs skip. If the refund API is down, we're in a state the system can't resolve itself — card charged, order failed. That needs retries with backoff, saga state persisted so it survives a restart and can resume, an alert to a human because some cases need judgement, and a reconciliation job that finds sagas stuck past a threshold."

"One thing I'd raise with the business rather than decide alone: the intermediate state is visible. The order exists as Pending for the duration. That has to be a meaningful domain state with sensible UI, not an implementation artefact the user sees by accident."

"In .NET I'd use MassTransit's state-machine saga rather than hand-rolling this, mainly for the state persistence and timeout handling — those are the parts that are tedious and easy to get wrong."
