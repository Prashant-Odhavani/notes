Microservices

The topic where the strongest interview answer is usually an argument against doing it.

🔴 Advanced ⭐ Senior-level 🔥 Must know

What microservices actually buy you 🔥 Must know

In simple terms

There is exactly one primary benefit: independent deployability.

Teams can ship their own service without coordinating a release with everyone else. Every other claimed benefit either follows from that, or isn't real.

Claimed benefitHonest assessment
Independent deployability Real, and the main one. Ship without a coordinated release
Team autonomy Real. A team owns a service end to end and isn't blocked by others
Independent scaling Real but narrower than claimed. Usually one component needs scaling — and you can often scale a monolith horizontally instead
Fault isolation Only if you build for it. Without timeouts, circuit breakers and fallbacks, one slow service takes down everything calling it
Technology diversity Usually a liability. Five languages means five toolchains, five sets of expertise, five security-patch processes
Smaller, simpler codebases Misleading. Each service is smaller; the system is considerably more complex
Better code quality Not a consequence. Service boundaries don't prevent bad code — you get badly coupled services instead
Remember this

Microservices are an organisational solution before they're a technical one.

They solve "forty developers can't ship without tripping over each other". They do not solve "our code is messy" — that's a modularity problem, and you can fix modularity inside one deployable.

Which is why the first question is always how many teams do you have?, not how much traffic do you have?

The failure mode: a distributed monolith

This is what you get when services are split without genuine boundaries: services that must be deployed together because they're too coupled to release independently.

The symptoms are recognisable. A change to one service requires changes to three others. Releases are coordinated across teams anyway. One service being down makes the others useless. Services share a database. Every request fans out through five hops.

You now have every cost of distribution and none of the benefit — the deployability you were buying is exactly what you've lost. It's strictly worse than the monolith you started with, and it's considerably harder to reverse.

Being able to describe this failure mode specifically is one of the better signals in a microservices interview, because it's the outcome most real projects actually reach.

When they're justified ⭐ Senior-level

Genuine reasonsPoor reasons
Many teams blocked by coordinated releases — the primary one "Monoliths are outdated"
One component has genuinely different scaling needs — and scaling the whole thing is proven too expensive "It'll scale better" with no measurement
Different compliance or data-residency requirements per capability "We want to try Go"
Genuinely different availability requirements — checkout must survive reporting being down "The codebase is a mess" — that's a modularity problem
Independent lifecycle — a capability changing weekly next to one changing yearly "It's what everyone does"
Senior signal — the modular monolith is the right default

Most systems that "need microservices" need clear module boundaries inside one deployable.

You get the thing people actually want — separated concerns, independent reasoning, enforced boundaries — while keeping transactions, refactoring, a single stack trace and one deployment.

And crucially, a well-modularised monolith is the cheapest possible path to microservices later, because the boundaries already exist and have been validated by use. Splitting a module that's already independent is mechanical. Splitting a tangled monolith is the project that fails.

So "I'd start with a modular monolith and extract services when a specific boundary proves it needs independent deployment" is the answer that demonstrates judgement. It's also what the migration page covers in detail.

.NET Aspire addresses the genuinely painful part

The daily cost of microservices isn't architecture — it's that running the system locally becomes hard. Eight services, a database, a message broker and a cache, all needing to start in the right order with the right connection strings.

Aspire gives you a C# project describing the whole system — services, dependencies, and the wiring between them — so F5 starts everything with service discovery and configuration handled, plus a dashboard showing traces and logs across all of it.

It also configures OpenTelemetry, health checks and resilience defaults, which are the things teams otherwise reimplement inconsistently per service.

Worth knowing as a current answer to "how do you handle local development with many services?", because the traditional answers — a Compose file everyone maintains, or a shared dev environment people queue for — are both unsatisfying.

Should we move to microservices? 🔥 Must know
How I'd answer

"My default answer is probably not yet, and I'd want to know what problem we're solving before agreeing to it — because microservices solve a fairly narrow problem at considerable cost."

"The question I'd ask first is how many teams do we have, and are they blocked by each other? Not how much traffic — how many teams. Microservices are an organisational solution before a technical one. The primary thing they buy is independent deployability: a team ships without coordinating a release with everyone else. Every other claimed benefit either follows from that or doesn't survive scrutiny."

"So if the answer is 'we have one team of eight', microservices will make things worse. That team now maintains six pipelines, six sets of infrastructure, and pays network cost between components that used to be method calls — for a coordination benefit they didn't need."

"If the reason given is 'the codebase is a mess', I'd push back firmly. That's a modularity problem, and distribution doesn't fix it — you get the same tangle with network calls between the tangles, which is strictly harder to reason about. You can fix modularity inside one deployable, and it's much cheaper."

"If the reason is scaling, I'd want measurements. Usually one component is the bottleneck, and scaling a monolith horizontally is simpler than splitting it. It's also worth noting that the database is frequently the actual constraint, and splitting services doesn't help if they all still hit the same database."

"What I'd propose instead is a modular monolith: clear module boundaries, each owning its data, communicating through explicit interfaces, with the boundaries enforced — by project references or an architecture test that fails the build on a violation."

"That gives the separation people actually want while keeping transactions, refactoring across boundaries, one stack trace and one deployment. And it's the cheapest path to microservices later, because the boundaries already exist and have been validated by real use. Extracting a module that's genuinely independent is mechanical work; splitting a tangled monolith is the project that fails."

"The failure mode I'd name explicitly is the distributed monolith — services split without real boundaries, so they must be deployed together anyway. A change to one needs changes to three others, releases are still coordinated, they share a database, and one being down makes the rest useless. That's every cost of distribution with none of the benefit, and it's much harder to reverse than the monolith you started with."

"Where I would extract a service: a capability with genuinely different availability requirements — checkout must survive reporting being down — different compliance or data-residency rules, a genuinely different scaling profile that's been measured, or a team that owns a capability end to end and is being blocked."

What they're really checking
  • Do you ask about team structure rather than traffic?
  • Do you know independent deployability is the actual benefit?
  • Will you push back on "the codebase is messy"?
  • Do you propose a modular monolith as the default?
  • Can you describe the distributed-monolith failure mode?
Weak answers
  • Red flag: "yes, it scales better" with no measurement.
  • Red flag: listing benefits with no costs.
  • Red flag: treating it as the modern default.
Likely follow-ups
  • How would you find the first service to extract?
  • How do you enforce module boundaries in a monolith?
  • What if one component genuinely needs different scaling?
