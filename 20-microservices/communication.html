Communication

Every synchronous call between services is a coupling you have to pay for at runtime. Choosing where to accept that is the design work.

🔴 Advanced ⭐ Senior-level 🔥 Must know
Quick revision
  • Synchronous = temporal coupling. The callee must be up now.
  • Asynchronous decouples availability at the cost of eventual consistency.
  • Chained synchronous calls multiply failure. Five 99.9% services in series is 99.5%.
  • gRPC for internal service-to-service, REST for public and browser-facing.
  • An API gateway handles cross-cutting concerns; a BFF shapes responses per client.
  • Never break a contract. Add optional fields; version when you must.
  • Contract tests catch breakage that unit tests cannot.

Synchronous or asynchronous 🔥 Must know

The distinction that matters most

Synchronous means the caller waits. So the callee must be available at that moment — that's temporal coupling, and it's the coupling microservices are least good at removing.

Asynchronous means the caller publishes and moves on. The consumer processes when it can, so it can be down without affecting the publisher.

Synchronous (HTTP / gRPC)Asynchronous (messaging)
Caller waitsYesNo
Callee must be upYesNo — the broker holds the message
ConsistencyImmediateEventual
Failure handlingRetry, circuit break, fall backBroker retries; dead-letter queue
DebuggingStraightforward — a request and a responseHarder — needs tracing
BackpressureThe caller absorbs itThe queue absorbs it
Best forQueries, and anything the user waits forCommands with side effects, notifications, fan-out
The rule of thumb

Synchronous when the caller needs the answer to continue. Asynchronous when it just needs the work to happen.

"Is this card valid?" — synchronous; the checkout can't proceed without knowing.

"Send the confirmation email", "update the search index", "recalculate loyalty points" — asynchronous. Nobody is waiting, and doing them synchronously means the order fails if the email service is down.

Chained synchronous calls multiply failure — do the arithmetic
  Gateway ──► Orders ──► Inventory ──► Pricing ──► Tax ──► Payments

  Each service is individually 99.9% available.
  Availability of the chain:  0.999^5 = 99.5%

  99.9% = ~43 minutes of downtime a month
  99.5% = ~3.6 hours a month

  Latency is additive too: five services at 50ms each is 250ms
  before any of them does real work.

Each hop multiplies the failure probability and adds its latency. A chain of well-behaved services is a badly-behaved system.

Worse, a slow dependency is more dangerous than a failed one: without a timeout, threads pile up waiting, the caller's thread pool exhausts, and the caller fails too — then its caller fails. That's a cascading failure, and it's how one slow service takes down a whole system.

Which is why timeouts and circuit breakers aren't optional polish — and why replacing a hop with replicated data or an event is often the better fix than making the hop more resilient.

syntax = "proto3";

service Pricing {
  rpc GetPrice (PriceRequest) returns (PriceResponse);
  rpc StreamPriceUpdates (PriceStreamRequest) returns (stream PriceUpdate);
}

message PriceRequest {
  string sku = 1;
  string currency = 2;
  int32 quantity = 3;
}
Senior signal — the contract, not the performance

gRPC is usually justified on speed. The binary encoding and HTTP/2 multiplexing are real, and for most internal calls the difference is not what matters — a few milliseconds against a database query taking twenty.

The stronger argument is the contract. A .proto file is a real, versioned artefact that generates both client and server. So a breaking change is a compile error in the consumer, not a runtime surprise in production.

With REST, the contract is a document that drifts from the implementation — OpenAPI generated after the fact, or hand-maintained and stale. Renaming a JSON field breaks consumers silently.

So: gRPC internally where both ends are yours and the contract discipline pays; REST at the edge where reach, browser support and debuggability matter more. Mixing them by audience rather than picking one globally is the calibrated answer.

Protobuf field numbers are permanent

The numbers — sku = 1 — are what's on the wire, not the names. So you can rename a field freely, and you must never reuse or renumber one.

Reusing a retired number means old clients interpret new data as the old field: silent data corruption rather than an error. Protobuf provides reserved specifically to prevent this, and using it is the mark of someone who's maintained a proto over time.

Safe evolution: add new fields with new numbers, make them optional, never change a type, never renumber. Same discipline as additive API versioning.

On Kubernetes this is mostly a solved problem

A Kubernetes Service gives you a stable DNS name that resolves to healthy pods, with load balancing included. So http://pricing/api/prices just works, and scaling or replacing pods requires no client change.

That means a dedicated discovery component like Consul is often unnecessary — the platform does it. Bringing in a service registry when you're already on Kubernetes usually adds a moving part for no gain.

.NET Aspire also provides service discovery for local development, so the same logical name works on a developer machine and in the cluster — which removes a common source of environment-specific configuration.

  Browser ──►  Web BFF     ──┐

  Partner ──►  Public API  ──┘

  Gateway: authentication, rate limiting, TLS termination, routing
  BFF:     "the basket screen needs these six fields from three services"
Senior signal — the BFF exists to stop clients being chatty

Without one, a mobile app rendering a basket screen calls Orders, then Pricing, then Inventory — three round trips over a mobile network, where latency is the dominant cost and each request might be 200ms.

A BFF makes one call. It fans out server-side where the calls are fast and parallel, and returns exactly the fields that screen needs.

The reason it's per client is that a mobile screen and a desktop screen genuinely need different data — and a shared aggregation layer becomes a compromise nobody is happy with, then a coordination point between the web and mobile teams. Separate BFFs let each client team change its own without asking anyone.

The trade-off: some duplicated aggregation logic between BFFs. That's usually the right trade, because the alternative is coupling the client teams together — and the duplication is shallow.

This is also the answer to "how do you avoid over-fetching and under-fetching?" without adopting GraphQL.

Don't let the gateway become a monolith

Gateways accumulate. It starts as routing and auth, then someone adds a response transformation, then a business rule, then request enrichment — and now it's a shared component every team must change to ship a feature.

At that point the gateway is the coordination bottleneck the architecture was meant to remove, and it's a single point of failure with business logic in it.

Keep gateways to genuinely cross-cutting infrastructure: authentication, rate limiting, TLS, routing, request logging. Anything client-specific belongs in a BFF; anything domain-specific belongs in a service.

Versioning contracts 🔥 Must know

The rule

You cannot deploy a breaking change to a service and its consumers simultaneously.

During any rolling deployment, old and new versions of both run at once. So every change must be compatible in both directions for the duration.

Which means: add, don't change. New optional fields, new endpoints, new event types. Removing or renaming anything is a multi-step process.

SafeBreaking
Adding an optional fieldRemoving or renaming a field
Adding an endpointChanging a field's type
Adding an enum value if consumers tolerate unknownsMaking an optional field required
Relaxing validationTightening validation
Adding a new event typeChanging an existing event's meaning
The enum trap

Adding an enum value looks additive and frequently isn't. If a consumer has switch (status) with no default case, or deserialises strictly, a new value breaks it — and it breaks at runtime, in production, on data it has never seen.

Two defences. Producers should treat new enum values as a versioned change unless consumers are known to tolerate unknowns. Consumers should always handle the unknown case explicitly — a default branch that logs and degrades rather than throwing.

This is worth raising because it's the most common "but it was only an addition" incident.

How to remove a field safely

  1. Add the replacement alongside the old one. Both are populated.
  2. Migrate consumers to the new field, one at a time, deploying independently.
  3. Verify nothing reads the old field — instrument it and check the telemetry, don't assume.
  4. Stop populating it, and leave it present but empty for a release.
  5. Remove it.
Step 3 is the one people skip

"We told everyone to migrate" is not evidence. Instrument the old field — log or count each read — and remove it only when the count has been zero for long enough to cover monthly jobs and infrequent clients.

Without that, you discover the remaining consumer during an incident, and it's usually something nobody remembered: a reporting job, a partner integration, a mobile app version still in the wild that you can't force-update.

Mobile is the case that makes this non-negotiable — you cannot deprecate a field an old app version still requires, however long ago you announced it.

Contract tests

The gap they fill

Unit tests verify a service against its own expectations. Integration tests need everything running. Neither catches "we renamed a field and a consumer three teams away depends on it".

A consumer-driven contract test has each consumer declare what it needs, and the producer's pipeline verifies it still provides it — without running the consumer.

Senior signal — this is what makes independent deployment safe

Independent deployability is the point of microservices, and it's only genuinely safe if you can tell — before deploying — whether you've broken a consumer.

Contract tests give you that: the producer's build fails if it violates a published expectation. So the feedback arrives in CI rather than in someone else's error logs.

Without them, teams compensate with a coordinated integration environment and a release train — which is exactly the coordination microservices were adopted to remove. So contract testing isn't optional infrastructure; it's what keeps the architecture's central promise true.

Pact is the usual tool. The honest cost is that it requires discipline from both sides and a broker to store the contracts, and teams often abandon it — which is worth acknowledging rather than presenting it as free.

Key takeaways
  • Synchronous calls create temporal coupling — the callee must be up now.
  • Synchronous when the caller needs the answer; asynchronous when it just needs the work done.
  • Chained sync calls multiply failure and add latency — five 99.9% services is 99.5%.
  • A slow dependency is more dangerous than a failed one; timeouts are mandatory.
  • gRPC internally for the contract discipline; REST at the edge for reach and debuggability.
  • Protobuf field numbers are permanent — never reuse, use reserved.
  • On Kubernetes, DNS-based discovery is usually sufficient.
  • Gateway for cross-cutting infrastructure; BFF per client to stop chatty clients.
  • Keep business logic out of the gateway or it becomes the bottleneck.
  • Add, don't change. Removing a field is a five-step process, and step 3 is instrumentation.
  • New enum values are frequently breaking — handle unknowns on the consumer side.
  • Contract tests are what make independent deployment genuinely safe.

Common mistakes

  • Synchronous calls for work nobody is waiting for.
  • Long synchronous chains, multiplying failure and latency.
  • No timeouts, so a slow dependency exhausts the caller's threads.
  • gRPC for browser-facing APIs without considering the proxy requirement.
  • Reusing a protobuf field number.
  • Business logic in the API gateway.
  • One shared aggregation layer instead of a BFF per client.
  • Breaking changes deployed in one step.
  • Removing a field without instrumenting reads first.
  • Adding an enum value assuming it's additive.
  • No contract tests, so breakage is found in production.

Interview questions

Advanced / scenario

Service A needs data from Service B. What are your options? 🔥 Must know
How I'd answer

"Three options, and I'd choose based on whether A can function when B is unavailable — because that's the question that actually decides it."

"1. Synchronous call. A calls B's API when it needs the data. Simple, immediately consistent, easy to debug. The cost is temporal coupling: A is now down whenever B is down, and A's latency includes B's."

"That's fine for a genuine query where the user is waiting and the data must be current — a card authorisation, a stock check at checkout. It's the wrong choice if A's core function shouldn't depend on B being up."

"2. Replicate the data. B publishes events when its data changes; A keeps a local read-only copy of the fields it needs and queries its own store."

"This is usually the right answer when A needs B's data frequently but doesn't need it current to the millisecond. A stays available when B is down, and its reads are local — so no network latency and no cascading failure."

"The costs I'd state rather than gloss over: it's eventually consistent, so A can act on slightly stale data — which needs to be acceptable for that use case. It needs the outbox pattern on B's side, or events get lost when the database commit succeeds and the publish fails. And it needs a reconciliation job, because replicas drift — a missed event, a bug, a manual data fix. Anyone proposing replication without reconciliation hasn't run it in production."

"3. Move the operation. If A needs so much of B's data that replicating it means copying half of B, that's a boundary problem, not a communication problem. Either the logic belongs in B, or A and B should be one service."

"That third option is the one people don't consider, and it's often correct. Chattiness is a boundary smell. If A calls B five times to complete one operation, the seam was cut in the wrong place — and the fix is to move the seam, not to optimise the calls."

"So the decision procedure I'd use: does A need this to answer a request the user is waiting on, and must it be current? Then synchronous, with a timeout, a circuit breaker and a defined fallback. Does A need it often but tolerate staleness? Replicate via events. Does A need so much that replication is absurd? Reconsider the boundary."

"One thing I'd add on the synchronous option, because it's frequently missed: a slow dependency is more dangerous than a failed one. Without a timeout, A's threads accumulate waiting for B, A's thread pool exhausts, and A fails too — then A's callers fail. That's a cascading failure from one slow service. So if I do take a synchronous dependency, the timeout isn't optional polish, and I'd want a circuit breaker so A fails fast rather than queueing."

What they're really checking
  • Do you frame it around availability coupling?
  • Do you know replication via events is an option?
  • Do you state the outbox and reconciliation requirements?
  • Do you consider that it might be a boundary problem?
  • Do you know a slow dependency cascades?
Weak answers
  • Red flag: synchronous HTTP as the only option.
  • Red flag: A reading B's database.
  • Red flag: replication with no consistency discussion.
Likely follow-ups
  • How do you detect and fix a drifted replica?
  • What do you do when the circuit breaker is open?
  • How would you version the events B publishes?
How do you change a service's API without breaking consumers? ⭐ Senior-level
How I'd answer

"The constraint that drives everything: you cannot deploy a breaking change to a service and its consumers at the same moment. During any rolling deployment both old and new versions of both are running, so every change has to be compatible in both directions for the duration."

"So the rule is add, don't change. New optional fields, new endpoints, new event types — all safe. Removing a field, renaming one, changing a type, or making an optional field required are all breaking."

"For a genuine removal it's a multi-step process:"

"Add the replacement alongside the old field and populate both. Migrate consumers one at a time, deploying independently. Verify nothing reads the old field. Stop populating it but leave it present. Then remove it."

"The verification step is the one people skip, and it's the one that matters. 'We announced the deprecation' isn't evidence. I'd instrument the old field — count or log every read — and only remove it once that count has been zero for long enough to cover monthly jobs and infrequent clients."

"Without that you find the last consumer during an incident, and it's always something nobody remembered: a quarterly reporting job, a partner integration, or a mobile app version still in the wild. Mobile is what makes this non-negotiable — you cannot deprecate a field an old app build still requires, no matter how long ago you announced it."

"When a breaking change genuinely can't be avoided, I'd version and run both — /v1 and /v2 side by side, with a stated deprecation window and telemetry per version so I know when v1 is actually unused. Versioning by URL path is the most operationally obvious; header-based versioning is cleaner in theory and harder to debug."

"The trap I'd flag specifically: adding an enum value is frequently breaking even though it looks additive. A consumer with a switch and no default case, or strict deserialisation, fails at runtime on a value it's never seen. So producers should treat it as versioned unless consumers are known to tolerate unknowns, and consumers should always handle the unknown case by degrading rather than throwing."

"And the mechanism that makes all of this safe rather than hopeful: consumer-driven contract tests. Each consumer publishes what it needs; the producer's pipeline verifies it still provides that, without running the consumer. So a breaking change fails my build rather than appearing in someone else's error logs."

"That matters because the alternative is a shared integration environment and a release train — which is precisely the coordination microservices were adopted to eliminate. So contract testing isn't optional tooling; it's what keeps independent deployability true. I'd be honest that it takes discipline from both sides and teams do abandon it."

What they're really checking
  • Do you know both versions run simultaneously during deployment?
  • Do you have the full removal sequence?
  • Do you insist on instrumenting before removing?
  • Do you know the enum trap?
  • Do you connect contract tests to independent deployability?
Weak answers
  • Red flag: "version everything" as the whole answer.
  • Red flag: announcing deprecation and removing on schedule.
  • Red flag: no mention of contract tests.
Likely follow-ups
  • How long do you keep v1 running?
  • How do you version events, as opposed to APIs?
  • How does Pact actually work?
