Migration & Modular Monolith

The most useful page in this section, because the correct answer is usually "build a modular monolith and extract only what proves it needs extracting".

🔴 Advanced ⭐ Senior-level 🔥 Must know
Quick revision
  • A modular monolith gets you most of the benefit with none of the distribution cost.
  • Enforce module boundaries mechanically — an architecture test, not a convention.
  • Never do a big-bang rewrite. Strangle it incrementally.
  • Extract the boundary that's proven itself, not the one that's easiest.
  • The database is the hard part, not the code.
  • Extract code first, then data — in separate, shippable steps.
  • Be willing to say "don't split this".

The modular monolith 🔥 Must know

In simple terms

One deployable, one database server, one process — but internally divided into modules with enforced boundaries, each owning its own data and exposing an explicit interface.

You get separated concerns and independent reasoning. You keep transactions, refactoring, one stack trace and one deployment.

Senior signal — enforce boundaries mechanically or they erode

A documented convention that "Billing must not reference Ordering internals" survives about three months. Someone needs one class, references it directly under deadline pressure, and nobody notices in review.

So the boundary has to be checked by the build. Two ways:

[Fact]
public void Modules_may_only_depend_on_other_modules_Contracts()
{
    var result = Types.InAssembly(typeof(BillingModule).Assembly)
        .Should()
        .NotHaveDependencyOn("Shop.Modules.Ordering.Domain")
        .And().NotHaveDependencyOn("Shop.Modules.Ordering.Infrastructure")
        .GetResult();

    result.IsSuccessful.Should().BeTrue(
        because: string.Join(", ", result.FailingTypeNames ?? []));
}

NetArchTest or ArchUnitNET for this. Or make it structural: separate projects where only Contracts is referenced, so a violation is a compile error rather than a test failure. That's stronger, because it can't be skipped.

This is the single most important practice in a modular monolith. Without enforcement you have a normal monolith with folders — and the whole value proposition, including the cheap path to extraction later, disappears.

Module data ownership, without separate databases

Each module owns its tables. Use schema separation — ordering.Orders, billing.Invoices — with a DbContext per module configured to its own schema.

Then the rule is: no module queries another module's tables. Cross-module data goes through the Contracts interface, same as it would across a service boundary.

That's what makes later extraction tractable: the data boundary already exists and has been respected, so splitting the database is a matter of moving schemas rather than untangling joins.

The pragmatic exception worth being honest about: you can still transact across schemas, and sometimes you should. That's a genuine advantage over microservices — just be aware each cross-module transaction is a coupling you'd have to replace with a saga if you extracted.

When not to split 🔥 Must know

Don't split whenBecause
You have one or two teamsThere's no coordination problem to solve, and you'd pay all the costs
The domain isn't understood yetBoundaries drawn from guesses are the expensive kind of wrong
The motivation is "the code is messy"That's modularity — fixable in one deployable, far cheaper
There's no operational maturityNo CI/CD, no tracing, no on-call — microservices will be unrunnable
The bottleneck is the databaseSplitting services that all hit one database changes nothing
It's mostly CRUDThe distribution cost buys nothing
Splitting before you understand the domain is the expensive mistake

Boundaries are the one decision that's genuinely hard to reverse. Inside a monolith, moving a class between modules is a refactor. Between services it's a data migration, a contract change, a coordinated deployment, and possibly a saga where a transaction used to be.

So splitting a domain you don't yet understand means committing to boundaries at the point of minimum knowledge — and then discovering the seam was in the wrong place, when it's most expensive to move.

That's the strongest argument for monolith-first: build it as modules, let the boundaries be corrected cheaply while you learn, and extract only once a boundary has proven stable under real change. Extracting a module that's already independent is mechanical. Extracting one that isn't is the project that fails.

Pick for learning, not for value, the first time

The first extraction is where you build the machinery — pipelines, tracing, service discovery, contract tests, deployment, on-call. All of that is new, and some of it will be wrong.

So the first candidate should be valuable enough to justify the work but not the most critical path. Notifications, search indexing, reporting, file processing — things that are genuinely separable, tolerate eventual consistency, and where a mistake during the learning phase is recoverable.

Extracting checkout first means learning distributed systems on the flow that generates revenue. Everything you get wrong is an incident.

The sequence

  1. Make it a clean module first. Enforce the boundary inside the monolith, with an architecture test. If you can't do this, you're not ready to extract — the boundary doesn't exist yet.
  2. Separate its data. Move its tables to their own schema, remove cross-module joins and foreign keys, and replace them with calls through the interface. This is the hard part.
  3. Put a facade in front. All access goes through the module's interface. Still in-process, still one deployment.
  4. Deploy it as a service, still calling the same code. Change the facade to make a network call. Nothing else changes.
  5. Move the database. Its schema becomes its own database.
  6. Replace remaining synchronous calls with events where appropriate, to remove temporal coupling.
The order matters

Code first, then data. Each step is independently shippable and revertible.

Step 4 is the key insight: you can deploy something as a separate service while it still shares the database. That proves the deployment, monitoring and network path work before you take on the data migration — so if it goes wrong, you revert a routing change rather than a database split.

Doing both at once means a failure could be either, and reverting means undoing both.

Step 2 is where extractions actually fail

The code separation is usually straightforward — move classes, define an interface. The data is where it gets hard, and teams consistently underestimate it.

Foreign keys across the boundary must go. That means giving up referential integrity the database was enforcing, and replacing it with application-level checks plus a reconciliation job.

Joins across the boundary must be replaced — with a call, replicated data, or a denormalised copy. Every one is a decision, and a report joining six tables across the seam may need a separate reporting store.

Transactions spanning the boundary become sagas. That's the expensive one, and it's why "things that must be atomic together belong in the same service" is worth checking before committing to the split.

If step 2 reveals dozens of cross-boundary joins and transactions, that's not an obstacle to work through — it's evidence the boundary is wrong. The right response is to stop and reconsider, not to push on and build sagas.

The strangler pattern 🔴 Advanced

  Step 1:  Client ──► Proxy ──► Monolith                 (100% legacy)

  Step 2:  Client ──► Proxy ──┬─► Monolith
                              └─► New Service  (5% of traffic, shadow-compared)

  Step 3:  Client ──► Proxy ──┬─► Monolith     (fallback)
                              └─► New Service  (100%)

  Step 4:  Client ──► Proxy ────► New Service  (monolith path deleted)
Shadow traffic de-risks the cutover

Between steps 1 and 2, send requests to both the monolith and the new service, serve the monolith's response, and compare them.

That validates the new implementation against real production traffic — including the edge cases nobody thought to test — with zero user risk, because the monolith's answer is still what's returned.

Discrepancies are exactly the bugs you'd otherwise find after cutover. It's the single most effective de-risking technique for an extraction, and it's underused because it requires the proxy to support it.

Caveat: only safe for reads, or writes you're confident are idempotent — otherwise you're doubling side effects. For write paths, compare what the new service would have done rather than letting it act.

Keep the old path until you're certain

Deleting the monolith's implementation as soon as the new service takes traffic removes your rollback. Keeping it costs a little duplication and buys the ability to flip back in seconds.

Ideally the switch is a feature flag rather than a deployment, so reverting during an incident is a configuration change.

Delete the old path once you've been at 100% for long enough to have covered the monthly and quarterly jobs — those are what surface the paths nobody remembered.

Key takeaways
  • A modular monolith keeps transactions, refactoring and one deployment while giving you real boundaries.
  • Enforce boundaries with an architecture test or project structure — conventions erode.
  • Modules own their schemas; no module queries another's tables.
  • Don't split with one or two teams, an unclear domain, or no operational maturity.
  • Splitting before understanding the domain commits you at minimum knowledge.
  • Extract for learning first — valuable but not the most critical path.
  • Make it a clean module before extracting; if you can't, the boundary doesn't exist.
  • Code first, then data. Deploy as a service while still sharing the database.
  • Data separation is where extractions fail — FKs, joins and transactions across the seam.
  • Many cross-boundary joins means the boundary is wrong, not that you need more sagas.
  • Shadow traffic validates against production reality at no user risk.
  • Keep the old path behind a flag until you're certain.

Common mistakes

  • Big-bang rewrite — no delivery for a year, one risky cutover.
  • Splitting before the domain is understood.
  • Boundaries by convention, with no mechanical enforcement.
  • Extracting the most critical service first.
  • Moving code and data simultaneously, so a failure is ambiguous.
  • Underestimating the data separation.
  • Pushing through dozens of cross-boundary joins instead of questioning the seam.
  • Deleting the old path immediately, losing rollback.
  • Extracting to fix code quality rather than a deployment problem.
  • No tracing or CI/CD in place before the first service.

Interview questions

Advanced / scenario

You have a large monolith and leadership wants microservices. How do you approach it? 🔥 Must know
How I'd answer

"First I'd find out what problem they're trying to solve, because 'we want microservices' is a solution looking for one — and the answer changes the whole approach."

"If it's 'teams are blocked by coordinated releases', that's the genuine case and microservices are the right tool. If it's 'the codebase is a mess', that's a modularity problem and distribution won't fix it — you'll get the same tangle with network calls between the tangles, which is strictly harder. If it's 'it doesn't scale', I'd want measurements first, because the bottleneck is frequently the database, and splitting services that all hit one database changes nothing."

"I'd also check operational readiness honestly. If there's no mature CI/CD, no distributed tracing, no centralised logging and no on-call rotation, microservices will be unrunnable — and the first outage will be unexplainable. Those need to exist first, and building them is a prerequisite rather than a parallel activity."

"What I'd propose is a modular monolith as the first phase, and I'd frame it as progress toward microservices rather than a refusal — because it genuinely is."

"Concretely: identify module boundaries by business capability, move each into its own project, give each its own database schema, and expose a Contracts project as the only thing other modules may reference. Then enforce that with an architecture test that fails the build, or structurally with project references so a violation is a compile error."

"That enforcement is the critical part. A documented convention survives about three months before someone references an internal class under deadline pressure. Without mechanical enforcement you have a normal monolith with folders, and the entire value — including the cheap path to extraction — disappears."

"The reason this is the right first phase: it delivers most of what people actually want — separated concerns, clear ownership, parallel work without merge chaos — while keeping transactions, refactoring with compiler support, one stack trace and one deployment. And it's the cheapest possible path to microservices later, because the boundaries already exist and have been validated by real change. Extracting a module that's genuinely independent is mechanical work; extracting one from a tangle is the project that fails."

"Then extract selectively, when a specific module proves it needs independent deployment. For the first one I'd pick something valuable but not the most critical path — notifications, search indexing, reporting — because the first extraction is where you build the pipelines, tracing, contract tests and on-call, and some of that will be wrong. Learning distributed systems on the checkout flow means every mistake is an incident."

"The sequence for an extraction: make it a clean module with the boundary enforced; separate its data into its own schema, removing cross-boundary joins and foreign keys; put a facade in front; then deploy it as a service while it still shares the database; then move the database last."

"That step-4 ordering is the important one. It proves the deployment, monitoring and network path work before taking on the data migration — so if something's wrong you revert a routing change rather than a database split."

"And I'd set the expectation that step 2 is where this actually gets hard. Foreign keys across the boundary have to go, which means giving up referential integrity and adding reconciliation. Joins become calls or replicated data. Transactions become sagas. If separating the data reveals dozens of cross-boundary joins and transactions, that's not an obstacle to grind through — it's evidence the boundary is wrong, and the right response is to stop and reconsider."

"Throughout, I'd use a strangler approach with a proxy, ideally with shadow traffic — send reads to both, serve the monolith's response, compare them. That validates the new service against real production traffic including the edge cases nobody tested, at zero user risk. And I'd keep the old path behind a feature flag so reverting during an incident is a config change rather than a deployment."

"The message I'd give leadership: we'll get the benefits incrementally and reversibly, rather than committing to an eighteen-month rewrite that delivers nothing until it's finished — and we may well find that after phase one, only two modules genuinely need to be services."

What they're really checking
  • Do you interrogate the motivation?
  • Do you check operational readiness as a prerequisite?
  • Do you propose a modular monolith, and insist on mechanical enforcement?
  • Do you extract code before data, and deploy before migrating?
  • Do you know data separation is the hard part?
  • Can you frame it politically as progress, not refusal?
Weak answers
  • Red flag: a service-by-service rewrite plan with no questions asked.
  • Red flag: boundaries by convention only.
  • Red flag: no mention of the database.
  • Red flag: extracting the most critical service first.
Likely follow-ups
  • How do you handle a report that joins across two modules?
  • What if leadership insists on a timeline for full migration?
  • How would you write the architecture test?
