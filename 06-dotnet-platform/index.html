.NET Platform Fundamentals

The layer between your C# and the operating system: what runs your code, how the app starts up, and how everything gets wired together.

🟡 Intermediate 🔥 Must know
Quick revision
  • C# compiles to IL; the CLR runs it, JIT-compiling to machine code as it goes.
  • One SDK can build for many target frameworks. The SDK version and the runtime version are different things.
  • The generic host is the startup model for everything — web apps, workers, console tools. It owns DI, configuration, logging and shutdown.
  • DI lifetimes: singleton (one per app), scoped (one per request), transient (one per resolve).
  • Injecting a scoped service into a singleton is the captive dependency bug — it's the mistake that comes up most.
  • Configuration is a layered system: later providers override earlier ones.

Why this comes before ASP.NET Core 🟢 Beginner

Most tutorials teach ASP.NET Core and the platform together, which makes it hard to tell what belongs to the web framework and what belongs to .NET itself.

In simple terms

Dependency injection, configuration, logging and the host are not web features.

They're platform features. A background worker or a console app uses exactly the same ones.

Separating them matters practically: it's why a well-structured solution can share the same wiring between an API and a worker service, and it's why an interviewer asking "explain DI lifetimes" isn't asking a web question.

The pieces, from bottom to top 🟢 Beginner

LayerWhat it does
Operating systemThreads, memory, file handles, sockets
CLR (runtime)Loads assemblies, JIT-compiles IL, runs the GC, enforces type safety
BCL (base class library)string, List<T>, HttpClient, File
Generic hostStartup, DI container, configuration, logging, graceful shutdown
Your applicationASP.NET Core, a worker, a console tool
Think of it this way

The CLR is the engine. The BCL is the standard parts catalogue. The generic host is the chassis and wiring harness — it's what makes the engine and parts into a vehicle that starts, runs and stops cleanly.

ASP.NET Core is then just one body you can bolt onto that chassis.

How this area is interviewed 🟡 Intermediate

Three questions dominate, and they're all really the same question in different clothes: do you understand object lifetimes?

QuestionWhat it's testing
"Explain the DI lifetimes."Table stakes. Everyone can list them
"What happens if you inject a scoped service into a singleton?"The real question. Captive dependencies
"How do you use a DbContext in a background service?"Whether you know you need to create a scope manually
"Where does configuration come from, and what wins?"Whether you understand the provider chain
"How do you handle graceful shutdown?"Whether you've operated something in Kubernetes
Senior signal

Connecting DI lifetimes to a failure you've seen. For example:

"We had a singleton cache service that took an IOptions<T> and a DbContext. It worked in development and then started throwing ObjectDisposedException under load, because the context it captured on the first request was disposed at the end of that request. The fix was injecting IServiceScopeFactory and creating a scope per operation."

That's a much stronger answer than reciting the three lifetimes.

A note on versions 💡 Good to know

This area changed shape significantly, and interviewers sometimes probe whether you know the history:

EraStartup model
.NET FrameworkGlobal.asax, web.config, no built-in DI
.NET Core 1–2Startup.cs with ConfigureServices and Configure
.NET Core 3 – .NET 5Generic host + Startup.cs
.NET 6+Minimal hosting — everything in Program.cs, no Startup

Examples in this handbook use the .NET 6+ minimal hosting model. If you've mostly worked with Startup.cs, the concepts map directly — ConfigureServices becomes builder.Services, and Configure becomes the middleware calls on app.
