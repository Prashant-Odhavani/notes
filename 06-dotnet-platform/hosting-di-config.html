Hosting & Dependency Injection

How a .NET app starts, how objects get created for you, and the lifetime mistake that causes more production bugs than any other DI issue.

🟡 Intermediate 🔴 Advanced 🔥 Must know
Quick revision
  • The host owns the DI container, configuration, logging and the shutdown signal. Same model for web apps and workers.
  • Singleton — one per application. Scoped — one per request. Transient — a new one every time it's injected.
  • Captive dependency: a scoped service injected into a singleton is held for the process lifetime. This is the bug.
  • In a BackgroundService you must create a scope yourself — there's no request to give you one.
  • Singletons must be thread-safe. They're shared across every concurrent request by definition.
  • Register in the direction of the dependency: infrastructure implements interfaces the application owns.

The host 🟢 Beginner

In simple terms

The host is the object that starts your app, holds everything it needs, and stops it cleanly.

var builder = WebApplication.CreateBuilder(args);

// 1. Register what the app needs (the DI container)
builder.Services.AddScoped<IOrderRepository, SqlOrderRepository>();
builder.Services.AddSingleton<IPriceCache, PriceCache>();
builder.Services.AddControllers();

var app = builder.Build();

// 2. Configure how requests flow through it
app.UseAuthentication();
app.MapControllers();

app.Run();      // starts listening, and blocks until shutdown is signalled

Four things the host gives you before you write any code:

ServiceWhat you get
DI containerbuilder.Services — register types, get them injected
Configurationbuilder.Configuration — appsettings, env vars, secrets, layered
LoggingILogger<T> injectable anywhere, providers configurable
Lifetime managementStartup ordering, and a cancellation token when shutdown begins
Same model for a worker

A background worker uses Host.CreateApplicationBuilder(args) instead of WebApplication.CreateBuilder. Everything else — DI, configuration, logging — is identical. That's why the same infrastructure registrations can be shared between an API and a worker in the same solution.

The three lifetimes 🔥 Must know

LifetimeOne instance per…Use for
SingletonApplicationCaches, HTTP client factories, config snapshots, anything stateless and expensive to create
ScopedRequest (or explicit scope)DbContext, repositories, unit of work, anything carrying per-request state
TransientInjectionCheap, stateless helpers — validators, mappers
Think of it this way

Singleton = the office coffee machine. One for the building, everyone shares it, and it had better cope with several people at once.

Scoped = your cup for this meeting. Yours for the duration, then washed up.

Transient = a paper napkin. Take a new one whenever you need one.

The rule that decides it

Ask: "does this hold state that belongs to one request?"

Yes → scoped. No, and it's expensive to create → singleton. No, and it's cheap → transient.

The captive dependency bug 🔥 Must know

In simple terms

A singleton is created once. So whatever it captures in its constructor, it holds forever.

If that was a scoped service, you've just given a per-request object the lifetime of the process.

builder.Services.AddDbContext<AppDbContext>(...);        // SCOPED by default
builder.Services.AddSingleton<PriceCache>();             // SINGLETON

public class PriceCache
{
    private readonly AppDbContext _db;                   // captured on first creation

    public PriceCache(AppDbContext db) => _db = db;      // held for the app's lifetime

    public async Task<decimal> GetAsync(int sku) =>
        await _db.Prices.Where(p => p.Sku == sku).Select(p => p.Value).FirstAsync();
}

What actually goes wrong, in the order you'll see it:

  1. The first request creates the singleton, which captures that request's DbContext.
  2. That request ends and its scope is disposed — including the context.
  3. The next request uses the singleton, which uses the disposed context → ObjectDisposedException.
  4. Or, if it survives, the context accumulates every entity it ever tracked and never releases them — a memory leak and stale data.
  5. And because DbContext isn't thread-safe, concurrent requests through one instance give you "a second operation was started on this context".
public class PriceCache(IServiceScopeFactory scopeFactory)
{
    public async Task<decimal> GetAsync(int sku, CancellationToken ct)
    {
        using var scope = scopeFactory.CreateScope();          // a fresh scope
        var db = scope.ServiceProvider.GetRequiredService<AppDbContext>();

        return await db.Prices
            .Where(p => p.Sku == sku)
            .Select(p => p.Value)
            .FirstAsync(ct);
    }                                                          // scope disposed here
}
The container can catch this for you

Scope validation detects captive dependencies at startup and throws instead of failing later. It's on by default in the Development environment, which is why this bug usually escapes to production from a team that only tests in Release.

Turn it on everywhere:

builder.Host.UseDefaultServiceProvider(o =>
{
    o.ValidateScopes = true;       // catch captive dependencies
    o.ValidateOnBuild = true;      // catch missing registrations at startup, not first request
});

What can safely inject what

Consumer ↓ / Dependency →SingletonScopedTransient
Singleton✅ Fine❌ Captive dependency⚠️ Becomes effectively a singleton
Scoped✅ Fine✅ Fine⚠️ Lives as long as the scope
Transient✅ Fine✅ Fine✅ Fine
Remember this

A dependency is held for at least as long as the thing consuming it.

So you can always inject something longer-lived into something shorter-lived. Never the reverse.

Note the transient row: a transient injected into a singleton is created once and held forever. It isn't an error, but it isn't "transient" any more either — and if it holds a resource, that's a leak.

Scoped services in background work 🔥 Must know

A BackgroundService is registered as a singleton. So it hits exactly the problem above — and there's no request to give it a scope.

public class OrderProcessor(AppDbContext db) : BackgroundService   // WRONG
{
    protected override async Task ExecuteAsync(CancellationToken ct)
    {
        while (!ct.IsCancellationRequested)
        {
            var pending = await db.Orders.Where(o => !o.Processed).ToListAsync(ct);
            // one context, held for days, tracking every entity it ever saw
        }
    }
}
public class OrderProcessor(IServiceScopeFactory scopeFactory, ILogger<OrderProcessor> log)
    : BackgroundService
{
    protected override async Task ExecuteAsync(CancellationToken ct)
    {
        while (!ct.IsCancellationRequested)
        {
            try
            {
                // A fresh scope per iteration - fresh DbContext, released afterwards
                using var scope = scopeFactory.CreateScope();
                var db = scope.ServiceProvider.GetRequiredService<AppDbContext>();

                var pending = await db.Orders.Where(o => !o.Processed).Take(50).ToListAsync(ct);
                foreach (var order in pending) { /* ... */ }
                await db.SaveChangesAsync(ct);
            }
            catch (OperationCanceledException) when (ct.IsCancellationRequested)
            {
                break;                            // normal shutdown, not an error
            }
            catch (Exception ex)
            {
                // Swallow-and-continue: an unhandled exception here kills the host
                log.LogError(ex, "Order processing iteration failed");
            }

            await Task.Delay(TimeSpan.FromSeconds(10), ct);
        }
    }
}
Production trap — an unhandled exception stops the whole host

If ExecuteAsync throws, the host shuts down by default (since .NET 6). Your API stops serving traffic because a background job failed once.

So the loop body needs its own try/catch that logs and continues. And note the separate catch for OperationCanceledException — cancellation during shutdown is normal and shouldn't be logged as an error.

Registration patterns 🟡 Intermediate

// Interface to implementation - the common case
services.AddScoped<IOrderRepository, SqlOrderRepository>();

// Concrete type only
services.AddSingleton<PriceCache>();

// Factory - when construction needs logic or config
services.AddSingleton<IPaymentGateway>(sp =>
{
    var options = sp.GetRequiredService<IOptions<PaymentOptions>>().Value;
    return new StripeGateway(options.ApiKey);
});

// Many implementations of one interface - inject IEnumerable<IShippingRate>
services.AddSingleton<IShippingRate, StandardRate>();
services.AddSingleton<IShippingRate, ExpressRate>();

// Keyed services (.NET 8+) - pick by key rather than by type
services.AddKeyedScoped<INotifier, EmailNotifier>("email");
services.AddKeyedScoped<INotifier, SmsNotifier>("sms");
// consume with: [FromKeyedServices("email")] INotifier notifier
MethodBehaviour if already registered
Add*Adds another. Resolving one type gets the last registered; resolving IEnumerable<T> gets all
TryAdd*Only adds if nothing is registered for that type. Use this in library extension methods
ReplaceSwaps the existing registration. Useful in tests
Best practice for tests

Register the real thing in Program.cs, then use services.Replace(...) or RemoveAll in your test host to swap in a fake. That way your test exercises the real wiring, and you only substitute what you deliberately chose to. See testing in .NET.

Graceful shutdown 🔴 Advanced

In simple terms

When the host is asked to stop — SIGTERM from Kubernetes, Ctrl+C, a deployment — it signals a cancellation token and waits for in-flight work to finish.

If your code ignores that token, the platform eventually kills the process and the work is lost.

The sequence:

  1. The platform sends SIGTERM.
  2. The host stops accepting new requests and triggers ApplicationStopping.
  3. StopAsync is called on hosted services, and the CancellationToken passed to ExecuteAsync is cancelled.
  4. The host waits up to the shutdown timeout (default 30 seconds).
  5. Anything still running is killed.
builder.Services.Configure<HostOptions>(o =>
{
    o.ShutdownTimeout = TimeSpan.FromSeconds(25);
});
Production trap — Kubernetes will out-wait you, or won't

Kubernetes sends SIGTERM, waits terminationGracePeriodSeconds (default 30), then SIGKILL.

If your .NET shutdown timeout is longer than that grace period, Kubernetes kills you mid-drain and you lose in-flight requests. Set the .NET timeout below the grace period, and make sure long-running work checks the cancellation token frequently enough to actually stop in time.

Key takeaways
  • The host owns DI, configuration, logging and shutdown — for web apps and workers alike.
  • Singleton = per app, scoped = per request, transient = per injection.
  • You can inject longer-lived into shorter-lived, never the reverse.
  • Scoped into singleton = captive dependency. Enable ValidateScopes everywhere, not just Development.
  • BackgroundService is a singleton — create a scope per unit of work.
  • Catch exceptions inside a background loop, or one failure takes the host down.
  • Singletons must be thread-safe.
  • Keep the .NET shutdown timeout under the platform's grace period.

Common mistakes

  • Injecting DbContext into a singleton — the captive dependency.
  • Injecting DbContext into a BackgroundService — same bug, different disguise.
  • A singleton holding mutable state with no synchronisation.
  • Registering everything as transient "to be safe" — you lose caching and create needless allocation.
  • No try/catch in a background loop, so one transient failure stops the host.
  • Injecting IServiceProvider everywhere — that's service location, and it hides dependencies from the constructor.
  • Not passing the shutdown token into long-running work, so it can't stop cleanly.
  • Relying on Development-only scope validation, so the bug ships.

Interview questions

Basic

Explain the DI lifetimes, and how you choose between them.
How I'd answer

"Singleton is one instance for the whole application. Scoped is one per request — or per explicit scope. Transient is a new one every time it's injected."

"The way I decide is one question: does this hold state that belongs to a single request? If yes, it's scoped — a DbContext is the obvious example, because it tracks the entities for that unit of work. If no, and it's expensive to create or genuinely shared, singleton — a cache, or something holding a pooled connection. If no and it's cheap, transient."

"In practice I lean towards scoped for anything touching data and singleton for infrastructure, and I use transient less than people expect — most stateless helpers are fine as singletons."

"The important consequence is the direction of the dependency. Something is held for at least as long as whatever consumes it, so you can inject longer-lived into shorter-lived but never the reverse. Injecting a scoped service into a singleton means the singleton holds that instance forever — which is the captive dependency problem, and it's the mistake I'd actually watch for in review."

"And a singleton has to be thread-safe, because by definition it's shared across every concurrent request."

What they're really checking
  • Can you go beyond listing them to a decision rule?
  • Do you volunteer the captive dependency problem?
  • Do you mention thread safety?
Likely follow-ups
  • What happens if you inject a scoped service into a singleton?
  • How do you use a DbContext in a background service?
  • Is a transient injected into a singleton still transient?

Intermediate

You need a DbContext in a BackgroundService. How do you do it? 🔥 Must know
How I'd answer

"You can't just inject it, because a BackgroundService is registered as a singleton and DbContext is scoped. That's a captive dependency."

"If you do it, the context lives for the lifetime of the service — days or weeks. It accumulates every entity it has ever tracked, so memory grows and queries get slower. You get stale data because the change tracker keeps returning cached instances. And it isn't thread-safe, so any concurrency gives you 'a second operation was started on this context'."

"So instead I inject IServiceScopeFactory, and create a scope per unit of work — usually per loop iteration or per message. Inside the scope I resolve the context, do the work, and dispose the scope, which disposes the context. That mirrors what a web request does automatically."

"Two other things I'd get right in that loop. Wrap the body in a try/catch, because since .NET 6 an unhandled exception in ExecuteAsync shuts down the host — so a transient database blip would take my API offline. And handle OperationCanceledException separately, so normal shutdown doesn't get logged as an error and page someone."

"I'd also enable ValidateScopes outside Development. It's on by default in Development only, which is exactly why this class of bug ships to production."

What they're really checking
  • Do you know BackgroundService is a singleton?
  • Can you name the specific symptoms, not just "it's wrong"?
  • Bonus: the host-shutdown behaviour and scope validation.
Weak answers
  • Red flag: "register the DbContext as a singleton" — makes it far worse.
  • Red flag: "inject IServiceProvider" without creating a scope.
Likely follow-ups
  • Where exactly does the scope boundary go — per iteration or per item?
  • How do you make the job stop cleanly on shutdown?
  • How would you make the same job safe to run on three instances?

Advanced

Your API throws ObjectDisposedException intermittently after a few minutes of traffic. What would you look at? ⭐ Senior-level
How I'd answer

"That pattern — works at first, then fails intermittently under traffic — points strongly at a lifetime mismatch. Something long-lived is holding something that got disposed."

"My first hypothesis is a captive dependency: a singleton that took a scoped service in its constructor. It captures the first request's instance, that request ends, the scope disposes it, and every subsequent use throws. The intermittency comes from it depending on which code path hits the singleton."

"To confirm it quickly I'd enable ValidateScopes and ValidateOnBuild and start the app. Scope validation throws at startup with the exact chain — 'cannot consume scoped service X from singleton Y' — which usually identifies it in seconds. It's on by default in Development, so if this reached production it's likely nobody ran with it enabled."

"If that comes up clean, the other candidates are: a BackgroundService injecting a scoped service, which is the same bug in a different place; something capturing an HttpContext or a scoped service in a closure and using it after the request ended — fire-and-forget work is the classic; or a manually created scope disposed while an async operation is still using it, which happens if you don't await inside the using."

"That last one is worth calling out because it's easy to write: if you create a scope, start an async operation without awaiting it, and let the using block exit, the scope is disposed while the work is still running."

"For prevention I'd turn on both validation flags in every environment, and treat the exception type as a signal to check lifetimes first rather than adding a null check or a retry — which is what people reach for and which hides the real problem."

What they're really checking
  • Do you recognise the symptom pattern as a lifetime issue?
  • Do you know scope validation exists and that it's Development-only by default?
  • Can you list other realistic causes, including the async-scope one?
Weak answers
  • Red flag: "add a try/catch and retry."
  • Red flag: "register everything as transient."
Likely follow-ups
  • Why is scope validation off outside Development?
  • How do you do fire-and-forget work safely in ASP.NET Core?
  • What's the difference between this and "a second operation started on this context"?
