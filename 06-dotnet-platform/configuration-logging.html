Configuration, Options & Logging

Where settings come from, how to consume them without string keys everywhere, and how to log so the logs are actually useful at 3am.

🟢 Beginner 🟡 Intermediate 🔥 Must know
Quick revision
  • Configuration is layered. Providers are added in order and later ones override earlier ones.
  • Environment variables beat appsettings.json — that's how containers and CI inject settings.
  • The options pattern turns config into a strongly-typed class you inject, instead of magic string lookups.
  • IOptions = read once. IOptionsSnapshot = per request. IOptionsMonitor = live reload, safe in singletons.
  • Structured logging: log with named placeholders, never string interpolation. You can then query on the values.
  • Never put secrets in appsettings.json. Use user secrets locally, a secret store in production.

The configuration chain 🔥 Must know

In simple terms

Configuration isn't one file. It's a stack of sources merged into a single key/value lookup.

If two sources define the same key, the one added later wins.

Think of it this way

Sheets of tracing paper stacked on a lightbox. Each one can overwrite what's underneath.

appsettings.json is the bottom sheet. Environment variables go on top. Whatever's on the topmost sheet is what you read.

The default order in CreateBuilder, from lowest priority to highest:

#SourceTypical use
1appsettings.jsonDefaults, committed to source control
2appsettings.{Environment}.jsonPer-environment overrides
3User secrets (Development only)Local secrets, stored outside the repo
4Environment variablesHow containers and CI inject settings
5Command-line argumentsHighest priority — one-off overrides
 
// appsettings.json
// { "Database": { "ConnectionString": "Server=dev;..." , "CommandTimeout": 30 } }

var cs = builder.Configuration["Database:ConnectionString"];
var timeout = builder.Configuration.GetValue<int>("Database:CommandTimeout");
The double-underscore convention

Many platforms don't allow : in environment variable names, so .NET also accepts double underscore as the separator:

Database__ConnectionString=Server=prod;...

That's the mechanism behind almost all container configuration — and it's worth knowing, because it's how you override a nested setting from a Kubernetes manifest or a Docker -e flag without touching a file.

The options pattern 🔥 Must know

In simple terms

Instead of reading Configuration["Database:CommandTimeout"] wherever you need it, bind that section to a class once, and inject the class.

Why bother? Three concrete reasons:

  • Typos become compile errors, not silent nulls at runtime.
  • Types are checked — you get an int, not a string you have to parse.
  • You can validate at startup, so a misconfigured deployment fails immediately rather than on the first request that needs the setting.
public sealed class DatabaseOptions
{
    public const string Section = "Database";

    [Required]
    public string ConnectionString { get; init; } = "";

    [Range(1, 300)]
    public int CommandTimeoutSeconds { get; init; } = 30;
}

// Program.cs
builder.Services
    .AddOptions<DatabaseOptions>()
    .Bind(builder.Configuration.GetSection(DatabaseOptions.Section))
    .ValidateDataAnnotations()
    .ValidateOnStart();          // fail at startup, not on first use
public sealed class OrderRepository(IOptions<DatabaseOptions> options)
{
    private readonly DatabaseOptions _config = options.Value;
    // strongly typed, validated, no magic strings
}
Why ValidateOnStart() matters

Without it, validation runs the first time something resolves the options — which might be an endpoint nobody hits for an hour. With it, a bad deployment fails at startup, the container never becomes healthy, and your rollout stops automatically.

That turns a mysterious runtime error into a clean deployment failure, which is exactly what you want in a pipeline.

The three options interfaces 🟡 Intermediate

A common interview question, because choosing wrong causes subtle bugs.

Reads configReload on change?Injectable into
IOptions<T>Once, at first resolveNoAnything, including singletons
IOptionsSnapshot<T>Once per scope/requestYes, per requestScoped only
IOptionsMonitor<T>Live, with change notificationsYes, immediatelyAnything, including singletons
How to choose

Default to IOptions. Most settings don't change while the app runs.

Need to pick up changes without a restart? Use IOptionsMonitor — and note it's the only one safe in a singleton.

IOptionsSnapshot is scoped, so injecting it into a singleton is a captive dependency.

public sealed class FeatureGate
{
    private FeatureOptions _current;

    public FeatureGate(IOptionsMonitor<FeatureOptions> monitor)
    {
        _current = monitor.CurrentValue;
        monitor.OnChange(updated => _current = updated);   // hot reload
    }

    public bool IsEnabled(string name) => _current.Enabled.Contains(name);
}

Secrets 🔥 Must know

Never commit a secret to appsettings.json

It ends up in source control, in every clone, in every branch, and in the git history forever — deleting it in a later commit doesn't remove it.

If it happens, the only real remediation is to rotate the credential. Rewriting history helps but you must assume it was already read.

WhereUse
Local developmentdotnet user-secrets set "Db:ConnectionString" "..." — stored in your user profile, outside the repo
CI/CDPipeline secrets injected as environment variables
AzureKey Vault with managed identity — no credential to store at all
KubernetesSecrets as env vars, or a CSI driver mounting from a vault

Managed identity is the one worth understanding: the app authenticates to Key Vault using an identity the platform assigns it, so there's no secret needed to fetch the secrets. That removes the bootstrapping problem entirely. Covered in App Configuration & Key Vault.

Structured logging 🔥 Must know

In simple terms

Log with named placeholders, not string interpolation.

The logging system then stores the values as separate fields — so you can search and filter on them rather than grepping text.

_logger.LogInformation($"Order {orderId} shipped to {country}");
_logger.LogInformation("Order {OrderId} shipped to {Country}", orderId, country);

They look almost identical. The difference at 3am is enormous:

With interpolationWith structured logging
Stored as one flat stringStored as a template plus OrderId and Country fields
Find one order by substring searchwhere OrderId == "abc-123"
Can't group or aggregate"Count shipments by country" is a query
Formatting cost paid even if the level is offNo formatting if the level is disabled

That last row is a real performance point: with interpolation the string is built before the call, so you pay for it even when Information logging is switched off.

Log levels — and what they should mean

LevelUse forProduction?
TraceExtremely detailed diagnosticsNever — may contain sensitive data
DebugDeveloper diagnosticsOff, enabled temporarily to investigate
InformationNotable business events: order placed, user registeredYes, but be selective
WarningSomething unexpected that was handled — a retry, a fallbackYes
ErrorAn operation failed and a user is affectedYes — should be alertable
CriticalThe application or a subsystem is downYes — should page someone
Common mistake — everything at Information

Two costs. The signal gets buried: real errors scroll past in a flood of routine chatter. And the bill — log ingestion is usually charged by volume, and verbose Information logging is one of the most common sources of surprise observability spend.

The test for Information: would I want to see this for every single request in production? Usually the answer is no, and it belongs at Debug.

Scopes and correlation 🟡 Intermediate

using (_logger.BeginScope("Processing order {OrderId} for {TenantId}", order.Id, tenantId))
{
    _logger.LogInformation("Validating");     // both fields attached automatically
    await _validator.ValidateAsync(order, ct);

    _logger.LogInformation("Charging card");  // and here
    await _payments.ChargeAsync(order, ct);
}

Without a scope you'd repeat orderId in every call and inevitably forget somewhere. With one, every log inside carries the context — so filtering by order ID gives you the whole story of that operation.

The single most valuable thing to add

A correlation ID that flows through every log line and across service boundaries. ASP.NET Core gives you Activity.Current.TraceId automatically with OpenTelemetry-style tracing.

Without it, debugging a request that touched four services means guessing from timestamps. With it, one query returns the whole path. It's cheap to add and transformative during an incident — see observability.

Production trap — logging sensitive data

Logging a whole request object is convenient and dangerous. Passwords, tokens, card numbers and personal data end up in your log store, which usually has broader access and longer retention than your database.

That's a data-protection incident created by the observability system. Log identifiers, not payloads — and never log an entire exception's request context without checking what's in it.

Key takeaways
  • Configuration is layered; later providers win. Environment variables override files.
  • Database__ConnectionString — double underscore for nested keys in env vars.
  • Bind config to a class, validate it, and ValidateOnStart() so bad deploys fail fast.
  • IOptions by default; IOptionsMonitor for reload and for singletons; IOptionsSnapshot is scoped only.
  • Never commit secrets. User secrets locally, managed identity in Azure.
  • Structured logging with named placeholders — queryable, and cheaper when the level is off.
  • Don't log everything at Information. It buries the signal and costs money.
  • A correlation ID is the highest-value logging investment you can make.

Common mistakes

  • Secrets in appsettings.json — permanent, once committed.
  • Magic string config lookups scattered through the codebase instead of bound options.
  • No validation, so a missing setting fails on the first request that needs it.
  • IOptionsSnapshot in a singleton — captive dependency.
  • String interpolation in log calls, losing structure and paying formatting cost when disabled.
  • Everything at Information, drowning real errors and inflating the bill.
  • Logging whole request or entity objects, leaking personal data into the log store.
  • No correlation ID, making cross-service debugging guesswork.

What is structured logging and why does it matter? 🔥 Must know
How I'd answer

"It means logging with named placeholders and passing the values as arguments, rather than building a string. So LogInformation("Order {OrderId} shipped", orderId) rather than interpolating the ID into the message."

"They look nearly identical in code, and the difference only shows up when you need the logs. With interpolation you get one flat string, so finding a specific order means a substring search, and you can't aggregate at all. With structured logging the provider stores the template plus OrderId as a separate field, so it's a query — and I can group, count and alert on field values."

"There's also a performance angle. With interpolation the string is built before the call, so you pay the formatting cost even when Information logging is switched off. With the template form, nothing is formatted if the level is disabled."

"Two things I'd add on top. Scopes, so context like the order ID and tenant ID attaches to every log inside a block rather than being repeated and forgotten. And a correlation ID flowing across service boundaries — that's the difference between one query returning a request's whole journey and guessing from timestamps across four services."

"The discipline part is levels. If everything is Information, real errors get buried and the ingestion bill balloons. My test is: would I want this for every request in production? If not, it's Debug. And I'd be careful never to log whole request objects, because that's how tokens and personal data end up in a log store with broader access than the database."

What they're really checking
  • Do you know the mechanism, and why the two forms differ?
  • Do you mention correlation IDs unprompted?
  • Do you think about cost and about leaking sensitive data?
Weak answers
  • Red flag: not knowing the difference from interpolation.
  • Red flag: "log everything so you have it if you need it."
