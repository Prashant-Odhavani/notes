Runtime, SDK & Project System

What happens between "I press F5" and "my code executes" — and the version concepts that confuse everyone at least once.

Quick revision
  • C# → IL (portable bytecode) → JIT → machine code, at runtime.
  • Tiered compilation: the JIT compiles quickly first, then recompiles hot methods with full optimisation.

How your code actually runs 🟢 Beginner

In simple terms

C# isn't compiled to machine code when you build. It's compiled to IL — a portable instruction set.

The CLR then compiles IL to real machine code while the program runs. That's the JIT.

Think of it this way

IL is a recipe written in a universal notation. It doesn't assume a particular kitchen.

The JIT is the chef reading it in your kitchen and adapting to the equipment you actually have — this CPU, these instruction sets.

  1. Build. Roslyn compiles your C# to IL, packaged in an assembly (a .dll).
  2. Load. The CLR loads the assembly and its dependencies.
  3. JIT. The first time a method is called, the JIT compiles that method to machine code for your CPU.
  4. Execute. Subsequent calls run the compiled code directly.

This is why the first request to a freshly started .NET app is slower — it's paying JIT costs. And it's why .NET can take advantage of CPU features that didn't exist when your code was written: the JIT knows what hardware it's on.

Tiered compilation 🟡 Intermediate

There's a tension: compiling well takes time, but you want to start fast. .NET resolves it by doing both.

TierWhenOptimisation
Tier 0First call to a methodMinimal — compile fast, run slower
Tier 1After a method is called enough timesFull — recompiled with inlining and everything else

So a method that runs once stays cheaply compiled; a hot loop gets promoted and optimised properly. The runtime also uses profile data gathered at tier 0 to make better decisions at tier 1 — including the guarded devirtualization mentioned in virtual dispatch.

Why this matters for benchmarks

If you time a method's first few calls, you're measuring tier 0 plus JIT time, not your code. That's the main reason a Stopwatch loop misleads and BenchmarkDotNet warms up first — see measuring properly.

When AOT is worth it

Serverless functions and CLI tools — anywhere startup time dominates and the process is short-lived.

Not for a long-running web app: it starts once, then the JIT's CPU-specific optimisation wins.

What AOT breaks

AOT requires the compiler to see all the code that will run, so anything resolved dynamically is a problem: reflection over types the trimmer removed, runtime code generation (Expression.Compile), and reflection-based serialization.

That's the reason source generators exist — see source generators. If you're targeting AOT, use the source-generated modes of System.Text.Json and friends.

Three version numbers that get confused constantly.

The relationship

One SDK can build for many target frameworks. The .NET 9 SDK happily builds a net6.0 project.

But the runtime on the machine must support the target framework you built for.

{
  "sdk": {
    "version": "8.0.400",
    "rollForward": "latestFeature"
  }
}

Worth having in a team repo: it stops "works on my machine" problems caused by two developers on different SDK versions producing different build behaviour.

What about .NET Standard? 💡 Good to know

In simple terms

netstandard was a contract, not a runtime — a set of APIs that .NET Framework, .NET Core, Xamarin and Mono all promised to provide.

It existed so one library could work everywhere. Since .NET 5 unified the platforms, it's mostly unnecessary.

When you'd still use it: a library that must be consumable from .NET Framework 4.x. Target netstandard2.0 for that. Otherwise target the .NET version you need.

The project file 🟢 Beginner

<Project Sdk="Microsoft.NET.Sdk.Web">

  <PropertyGroup>
    <TargetFramework>net9.0</TargetFramework>

    <!-- Turn null-reference bugs into compiler errors -->
    <Nullable>enable</Nullable>
    <TreatWarningsAsErrors>true</TreatWarningsAsErrors>

    <!-- Common namespaces added automatically -->
    <ImplicitUsings>enable</ImplicitUsings>

    <!-- Deterministic builds: same input, same binary -->
    <Deterministic>true</Deterministic>
  </PropertyGroup>

  <ItemGroup>
    <PackageReference Include="Microsoft.EntityFrameworkCore.SqlServer" Version="9.0.0" />
  </ItemGroup>

  <ItemGroup>
    <ProjectReference Include="..\MyApp.Application\MyApp.Application.csproj" />
  </ItemGroup>

</Project>

Two properties worth arguing for on any new project:

  • Nullable + TreatWarningsAsErrors — the highest-value settings available. Covered in nullable reference types.
  • ImplicitUsings — removes a block of using lines from every file.
Directory.Build.props

Repeating those properties in twelve project files means they'll drift. Put shared settings in a single Directory.Build.props at the solution root — MSBuild applies it to every project underneath automatically.

Same idea for package versions: Directory.Packages.props with ManagePackageVersionsCentrally means you upgrade a package in one place instead of fifteen.

The security implication people miss

Self-contained deployment means you own runtime patching. When a .NET security fix ships, a framework-dependent app gets it by updating the base image or host. A self-contained app keeps running the vulnerable runtime until someone rebuilds it.

That's a real operational trade-off, not just a size question — and it's the kind of detail that reads as production experience.

Trimming

PublishTrimmed removes unused code to shrink the output. It works well for self-contained apps, but it's the same hazard as AOT: the trimmer can only remove what it can prove is unused, and reflection defeats that proof. A type used only via reflection looks unused, gets removed, and you get a runtime failure that didn't occur in a normal build.

Test a trimmed build properly before shipping one — the failures appear at runtime, not at build time.

Key takeaways
  • C# → IL → JIT → machine code. The JIT can optimise for the actual CPU.
  • Tiered compilation trades startup speed for eventual peak performance — and it's why benchmarks need warm-up.
  • Native AOT for short-lived processes; JIT for long-running services.
  • SDK, runtime and target framework are three different versions. One SDK builds many targets.
  • netstandard is legacy — use it only to support .NET Framework consumers.
  • Put shared build settings in Directory.Build.props, not in every csproj.
  • Self-contained means you own runtime security patching.
  • Trimming and AOT both break reflection. Test those builds specifically.

Common mistakes

  • Confusing SDK and runtime versions when diagnosing a build or deploy problem.
  • Targeting netstandard2.0 for a new project that has no .NET Framework consumers — you lose access to modern APIs for nothing.
  • Duplicating build properties across many csproj files so they drift.
  • Shipping self-contained without a patching plan.
  • Enabling trimming or AOT without testing the published output.
  • Benchmarking in Debug, or without warm-up, and drawing conclusions from tier 0.
  • No global.json on a team repo, so builds differ per machine.

Interview questions

What happens when you build and run a .NET application?
How I'd answer

"The C# compiler produces IL rather than machine code — a portable instruction set packaged into an assembly. So the build output isn't native to any particular CPU."

"At runtime the CLR loads the assembly and its dependencies, and the JIT compiles each method to machine code the first time it's called. That's why the first request to a freshly started app is slower — you're paying JIT cost — and it's also why .NET can use CPU instructions that didn't exist when the code was written, because the JIT knows what hardware it's actually on."

"There's a refinement called tiered compilation. Tier 0 compiles quickly with minimal optimisation so startup is fast. Methods that get called a lot are recompiled at tier 1 with full optimisation, using profile data gathered from tier 0. So you get fast startup and good steady-state throughput rather than choosing between them."

"The alternatives are ReadyToRun, which pre-compiles ahead of time but keeps the JIT available, and Native AOT, which compiles fully ahead of time. AOT gives you millisecond startup and a small footprint, which is ideal for serverless or CLI tools — but it restricts reflection and runtime code generation, because the compiler has to see everything statically."

"For a long-running web service I'd stay with the JIT. It starts once, and after that the CPU-specific optimisation is worth more than the startup saving."

What they're really checking
  • Do you know it's IL and JIT, not direct native compilation?
  • Do you know tiered compilation, and can you explain why it exists?
  • Bonus: when AOT is and isn't appropriate.
Likely follow-ups
  • What does AOT break, and why?
  • How does this affect benchmarking?
  • What's the difference between the SDK and the runtime?
Framework-dependent or self-contained deployment — how do you choose?
How I'd answer

"It comes down to who controls the target machine and who owns runtime patching."

"Framework-dependent needs the matching runtime installed. The output is small — a few megabytes — and when a .NET security patch ships, updating the host or the container base image fixes every app at once. That's my default for anything I deploy to infrastructure I control, including containers using a runtime base image."

"Self-contained bundles the runtime, so it runs anywhere without prerequisites. That's right for a CLI tool users download, or a machine I don't control."

"The trade-off people underweight is patching responsibility. With self-contained, a runtime CVE means I have to rebuild and redeploy every app to get the fix. Framework-dependent, I update the base image. That's an operational commitment, not just a size difference."

"Size can be reduced with trimming, but that brings its own risk: the trimmer removes what it can't see being used, and reflection defeats that analysis. So a trimmed build can fail at runtime in a way the untrimmed build doesn't — which means you have to test the actual published artifact, not just the debug build."

"For containers specifically I'd usually go framework-dependent on a runtime base image. You get layer caching, small deltas per deploy, and centralised patching."

What they're really checking
  • Do you think about patching, not just file size?
  • Do you know trimming's failure mode?
  • Have you thought about the container case specifically?
Likely follow-ups
  • Which base image would you choose for a container, and why?
  • How would you test that a trimmed build still works?
