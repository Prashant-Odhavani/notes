Fundamentals & Test Doubles

The pyramid is a useful lie. What to mock is the decision that determines whether your suite helps or hinders.

🟡 Intermediate 🔴 Advanced 🔥 Must know
Quick revision
  • The pyramid is about cost and speed, not about what's valuable.
  • Arrange, Act, Assert — one action per test.
  • Stub provides input. Mock verifies interaction. Fake is a working implementation.
  • Mock at boundaries — network, clock, file system. Not at class edges.
  • Verifying interactions couples you to implementation. Prefer asserting state.
  • Never use DateTime.Now in testable code — inject TimeProvider.
  • Builders beat shared fixtures for readable, independent tests.

The pyramid, honestly 🔥 Must know

What it actually says

Many fast cheap tests at the bottom, few slow expensive ones at the top. It's a statement about cost and feedback speed, not about where value lives.

Which matters, because the value is often higher up — an integration test that exercises real SQL catches things no unit test can.

LevelSpeedCatchesMisses
Unit Milliseconds Logic, branches, edge cases, calculations Everything about integration — SQL translation, serialisation, config, wiring
Integration Seconds Real queries, migrations, DI wiring, serialisation Cross-service behaviour; browser behaviour
End-to-end Minutes The system genuinely works together Nothing — but slowly, flakily, and ambiguously
Senior signal — where the pyramid misleads in .NET

Taken literally, the pyramid pushes you toward maximising unit tests. In a .NET codebase that produces a specific pathology: heavily mocked unit tests that pass while the application is broken.

Because the things that actually fail are frequently at the seams — an EF Core query that can't translate to SQL and throws at runtime, a missing DI registration, a JSON property name mismatch, a migration that fails on real data, a nullable reference the in-memory provider tolerated.

None of those are catchable by a unit test with mocked dependencies, by construction.

Which is why the "testing trophy" framing is a better fit for modern .NET: fewer heavily-mocked unit tests, substantially more integration tests — real database via Testcontainers, real DI container, real serialisation — and a handful of end-to-end tests. Integration tests are slower and they catch a qualitatively different class of bug.

Being able to say "I'd weight toward integration tests because the failures that reach production are integration failures" is a stronger answer than reciting the pyramid.

Arrange, Act, Assert 🔥 Must know

[Fact]
public async Task Discount_applies_above_the_volume_threshold()
{
    // Arrange - set up the world
    var customer = ACustomer.OnPlan(CustomerTier.Standard);
    var order = AnOrder.For(customer).WithSubtotal(1_200m);
    var sut = new PricingService(_policies);

    // Act - exactly ONE action
    var price = await sut.PriceAsync(order);

    // Assert - the observable outcome
    price.Amount.Should().Be(1_140m);      // 5% off above 1000
}

The name is the documentation

A good test name means a CI failure is diagnosable from the report alone, without opening the file.

Placing_an_order_with_insufficient_stock_is_rejected tells you what broke. TestPlaceOrder_2 tells you to go and read it.

The useful pattern is scenario and expected outcome: what's the situation, what should happen. Some teams use Method_Scenario_Expectation; the specific convention matters much less than whether the name states the behaviour.

A related benefit: if you can't name the test clearly, the test is usually doing too much — the difficulty naming it is the signal.

// STUB - supplies input so the code under test can run
_rates.Setup(r => r.GetAsync("USD")).ReturnsAsync(1.27m);

// MOCK - asserts that an interaction happened. Couples to implementation.
_publisher.Verify(p => p.Publish(It.IsAny<OrderPlaced>()), Times.Once);

// FAKE - a real implementation, simplified
public sealed class InMemoryOrderRepository : IOrderRepository
{
    private readonly Dictionary<Guid, Order> _orders = new();

    public Task<Order?> GetAsync(Guid id, CancellationToken ct) =>
        Task.FromResult(_orders.GetValueOrDefault(id));

    public Task AddAsync(Order order, CancellationToken ct)
    {
        _orders[order.Id] = order;      // actually works
        return Task.CompletedTask;
    }
}
The distinction that matters

A stub answers a question. A mock is an assertion.

Stubbing GetAsync to return a value is arranging the world — it doesn't constrain how your code works.

Verifying that Publish was called once is a test assertion about the implementation. It fails if you achieve the same outcome differently.

Which is why "stub liberally, mock sparingly" is a good default.

Fakes are underused and often the best option

A fake repository is more work to write once and then dramatically better than mocks across dozens of tests.

With mocks, each test sets up its own Setup calls describing exactly which methods are called with what — so the test knows the implementation. With a fake, the test stores an order and later reads it back, and asserts on state rather than interactions.

That makes tests read like the behaviour they describe, and it means refactoring the code under test doesn't touch the tests.

The caveat: a fake must be faithful. An in-memory repository that doesn't enforce a unique constraint the real database does will let bugs through. So a fake is right for straightforward collection semantics and wrong when the real thing's behaviour is subtle — which is exactly why EF Core's in-memory provider is a poor substitute for a real database.

Senior signal — over-mocking produces tests that verify nothing

This is the most consequential testing mistake in .NET, and it's easy to make because mocking every constructor parameter feels rigorous.

Two problems. The tests are welded to the current structure, so extracting a class breaks a dozen passing tests that were all still correct — which is the false-positive tax that eventually kills the suite.

And more seriously: if you mock the pricing calculator, the pricing logic is never tested. The test asserts that the service called a mock that returned a value you specified. It would pass if the real calculator were completely wrong.

So a suite can have high coverage, all green, and verify very little — because every interesting computation was mocked away and only the wiring was exercised.

The fix is to define the unit as a behaviour rather than a class, let internal collaborators be real, and double only at genuine boundaries. Then the test exercises the actual logic and survives restructuring.

Never mock what you don't own

Mocking a third-party client directly — Mock<SqlConnection>, Mock<HttpClient>, a cloud SDK type — bakes your assumptions about that library's behaviour into the test.

If the assumption is wrong, the test passes and production fails. And when the library updates, the mock still reflects the old behaviour, so the test keeps passing while the real integration breaks.

Wrap it in your own interface and mock that instead. Then the interface expresses what you need, the wrapper is thin enough to verify by integration test, and library changes surface in one place.

For HttpClient specifically the right seam is a custom HttpMessageHandler — you're then testing against real HTTP semantics with a controlled response, rather than mocking a class that wasn't designed to be mocked.

Time, randomness and other non-determinism 🔥 Must know

public bool IsExpired() => DateTime.UtcNow > ExpiresAt;

// The test can only pass by also calling DateTime.UtcNow, so it either
// tests nothing meaningful or fails at midnight / in another timezone /
// on the last day of the month.
public sealed class Subscription(TimeProvider clock)
{
    public DateTimeOffset ExpiresAt { get; init; }
    public bool IsExpired() => clock.GetUtcNow() > ExpiresAt;
}

// In the test - control time exactly
var clock = new FakeTimeProvider(new DateTimeOffset(2024, 6, 1, 12, 0, 0, TimeSpan.Zero));
var sub = new Subscription(clock) { ExpiresAt = new DateTimeOffset(2024, 6, 2, 0, 0, 0, TimeSpan.Zero) };

sub.IsExpired().Should().BeFalse();

clock.Advance(TimeSpan.FromDays(2));        // move time forward deliberately
sub.IsExpired().Should().BeTrue();

Senior signal — TimeProvider also fixes slow tests

TimeProvider abstracts timers and delays, not just the current time. So TimeProvider.Delay and timer callbacks can be advanced instantly in a test.

That turns a test of retry-with-backoff — which would genuinely wait thirty seconds — into one that runs in milliseconds by calling clock.Advance(TimeSpan.FromSeconds(30)).

Which matters because tests involving Thread.Sleep or real delays are the ones that make a suite slow enough to skip, and they're frequently the flakiest — a five-second wait that's occasionally not long enough on a loaded CI machine.

So "inject TimeProvider" isn't only about determinism; it's how you test time-dependent behaviour — expiry, backoff, scheduling, debouncing — at all, without waiting.

Test data 🟡 Intermediate

// Every test uses this. Nobody knows which fields their test depends on.
private static readonly Order StandardOrder = new()
{
    Id = Guid.Parse("..."), CustomerId = Guid.Parse("..."),
    Subtotal = 100m, Status = OrderStatus.Draft, /* 20 more fields */
};

// Changing Subtotal to 150 breaks four unrelated tests, and it's not obvious why.
public sealed class AnOrder
{
    private decimal _subtotal = 100m;               // sensible defaults
    private CustomerTier _tier = CustomerTier.Standard;

    public static AnOrder Default => new();
    public static AnOrder WithSubtotal(decimal v) => new AnOrder { _subtotal = v };

    public AnOrder ForTier(CustomerTier t) { _tier = t; return this; }

    public Order Build() => new() { Subtotal = _subtotal, /* ... */ };
    public static implicit operator Order(AnOrder b) => b.Build();
}

// The test states ONLY what it cares about. Everything else is a default.
var order = AnOrder.WithSubtotal(1_200m).ForTier(CustomerTier.Gold);
Builders make tests self-documenting

The value isn't saving keystrokes. It's that the test states exactly which values are relevant to it and hides the rest.

Reading AnOrder.WithSubtotal(1_200m) in a discount test tells you the subtotal is what matters. Reading StandardOrder tells you nothing, so you have to go and look — and when someone changes a field in the shared fixture, unrelated tests break for reasons nobody can see.

Builders also keep tests independent, since each constructs its own data rather than sharing mutable state. That removes order-dependent failures, which are among the most frustrating to debug.

AutoFixture does something similar by generating values automatically. It's useful and I'd be careful with it in assertions — generated values make failures harder to read, and a test asserting on an autogenerated string tells you little when it fails.

Key takeaways
  • The pyramid describes cost and speed, not value. In .NET, weight toward integration tests.
  • The failures that reach production are integration failures — SQL translation, DI, serialisation, migrations.
  • One action per test; name it as a behaviour; no logic in the test.
  • Stub to provide input; mock to verify interaction. Stub liberally, mock sparingly.
  • Fakes are underused — they let you assert state instead of interactions.
  • Mock at genuine boundaries: network, clock, file system, brokers. Not at class edges.
  • Over-mocking means the logic is never tested — only the wiring.
  • Never mock a type you don't own; wrap it in your own interface.
  • Inject TimeProvider — it makes time-dependent behaviour testable and fast.
  • Builders over shared fixtures: tests state only what matters and stay independent.

Common mistakes

  • Mocking every constructor parameter, welding tests to the current structure.
  • Mocking the class that contains the logic, so the logic is never exercised.
  • Verifying interactions where asserting state would do.
  • Mocking HttpClient or an SDK type directly.
  • DateTime.UtcNow in testable code.
  • Thread.Sleep in tests — slow and flaky.
  • Shared mutable fixtures, causing order-dependent failures.
  • Several actions in one test, so failures are ambiguous.
  • Logic in the test — an if or a loop that can itself be wrong.
  • Names like Test1, so CI failures require opening the file.
  • Asserting on autogenerated values.

Interview questions

Intermediate

What's the difference between a mock, a stub and a fake — and when do you use each? 🔥 Must know
How I'd answer

"They're all test doubles, and the distinction that matters practically is whether it's part of the arrangement or part of the assertion."

"A stub provides canned input so the code under test can run. Setting an exchange-rate service to return 1.27 is arranging the world — it doesn't constrain how my code works."

"A mock verifies that an interaction happened. Verify(p => p.Publish(...), Times.Once) is a test assertion, and specifically an assertion about the implementation."

"A fake is a working lightweight implementation — an in-memory repository that genuinely stores and retrieves."

"The other two are less commonly discussed: a dummy just fills a parameter that's never used, and a spy records calls for later inspection rather than asserting up front."

"My default is stub liberally, mock sparingly, and reach for fakes more than most people do."

"The reason to be sparing with mocks is that verifying an interaction couples the test to the implementation. If I assert that the repository was called and then the publisher was called, I have documented the current implementation — and that test fails when I achieve the same outcome a different way, including a legitimate improvement. So I'd rather assert on the outcome: what state resulted, what was returned."

"I'd use a mock where the interaction is the observable behaviour and there's no state to check — 'an email was sent', 'the payment gateway was charged exactly once'. There the call crossing the boundary is genuinely what I care about, so verifying it is asserting behaviour rather than implementation."

"Fakes are underused. A fake repository is more work to write once and dramatically better across dozens of tests, because each test stores something and reads it back — asserting state rather than interactions. That makes tests read like the behaviour they describe, and refactoring the code under test doesn't touch them."

"The caveat is that a fake must be faithful. An in-memory repository that doesn't enforce a unique constraint the real database does will let bugs through. Which is exactly why EF Core's in-memory provider is a poor substitute for a real database — it doesn't enforce constraints, doesn't translate LINQ to SQL, and happily accepts queries that fail against SQL Server. I'd use Testcontainers for a real database instead."

"And one rule regardless: never mock a type you don't own. Mocking HttpClient or a cloud SDK type bakes my assumptions about that library into the test — if the assumption is wrong the test passes and production fails, and when the library updates the mock still reflects the old behaviour. I'd wrap it in my own interface and mock that. For HttpClient specifically the right seam is a custom HttpMessageHandler, so I'm testing real HTTP semantics with a controlled response."

What they're really checking
  • Can you state the distinction usefully rather than by definition?
  • Do you know mocks couple you to implementation?
  • Do you know when a mock is right?
  • Do you consider fakes?
  • Do you know not to mock what you don't own?
Likely follow-ups
  • How would you test something that sends an email?
  • Why not use EF Core's in-memory provider?
  • How do you test HttpClient code?

Advanced

A team's tests break on every refactor. What's wrong and how do you fix it? ⭐ Senior-level
How I'd answer

"That's a diagnosis, not an annoyance: the tests are coupled to implementation rather than behaviour. And it matters because it means the suite is actively preventing the thing it was written to enable."

"I'd look for three specific causes, in the order I'd expect to find them."

"One — interaction verification everywhere. Tests full of Verify calls asserting that the repository was called, then the publisher, then the logger. Each of those is an assertion about how the code works, so any change to how breaks them even when what it does is identical."

"Two — mocking every constructor parameter. This is the root cause in most .NET codebases. If every class is treated as a unit and every collaborator is mocked, each test is welded to one class's exact dependency list. So extracting a helper — the most ordinary refactor there is — breaks a dozen tests that were all passing and all still correct."

"Three — asserting on internal state rather than observable outcomes. Reflecting into private fields, or asserting on a property that exists only to make the test pass."

"There's a worse consequence of the second one that I'd raise, because it usually hasn't been noticed: if you mock the class that contains the logic, the logic is never tested. A test that mocks the pricing calculator asserts that the service called a mock which returned the value you specified. It would pass if the real calculator were completely wrong. So the suite can be green with high coverage and verify almost nothing — only the wiring."

"For the fix, I wouldn't propose rewriting the suite — that's a large project with no visible deliverable and it won't get funded. I'd do it incrementally."

"Change the default for new tests first: define the unit as a behaviour exercised through a stable entry point — an application service or handler — with real internal collaborators and doubles only at genuine boundaries: network, clock, file system, brokers. Write one exemplar test that demonstrates the pattern, because a concrete example moves a team more than a guideline."

"Then use failures as the trigger. When a brittle test breaks during a refactor, don't just fix it — replace it with a behavioural one at the right level. The pain is already there, so the work is already justified, and over a few months the worst tests get replaced by attrition."

"And add integration tests, because the over-mocked suite almost certainly isn't catching the failures that reach production — EF Core queries that can't translate to SQL, missing DI registrations, serialisation mismatches, migrations failing on real data. None of those are catchable by a mocked unit test, by construction. Testcontainers with a real database plus WebApplicationFactory catches a class of bug the existing suite can't see, so it adds value immediately rather than duplicating coverage."

"The test I'd give the team as a rule of thumb: if I restructure the internals without changing what the system does, should this test fail? If yes, it's the wrong test. That's a question anyone can apply in review without needing to remember a taxonomy."

"And I'd be honest that some churn is legitimate — if you change a public contract, tests should break. The problem is specifically tests breaking on changes that don't alter behaviour."

What they're really checking
  • Do you identify implementation coupling as the cause?
  • Do you spot that over-mocking means the logic isn't tested?
  • Do you propose incremental change rather than a rewrite?
  • Do you add integration tests to cover the real gap?
  • Do you give the team a usable rule?
Weak answers
  • Red flag: "write better tests" with no mechanism.
  • Red flag: proposing a full rewrite of the suite.
  • Red flag: no recognition that the suite may be verifying nothing.
Likely follow-ups
  • How would you convince the team the current tests are weak?
  • Where exactly do you draw the unit boundary?
  • How do you keep integration tests fast enough for CI?
