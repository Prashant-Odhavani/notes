Testing in .NET

The tooling is good. The traps are the in-memory provider, async misuse, and integration tests that share state.

🟡 Intermediate 🔴 Advanced 🔥 Must know
Quick revision
  • xUnit creates a new class instance per test — that's your isolation.
  • [Theory] with [InlineData] for the same behaviour across inputs.
  • Never async void in a test — failures are silently swallowed.
  • Don't use EF Core's in-memory provider to test queries.
  • WebApplicationFactory for real end-to-end API tests in-process.
  • Testcontainers for a real database in CI, per test run.
  • Reset state between integration tests, or they interfere.

Why xUnit's design nudges you toward better tests

xUnit constructs a new instance of the test class for every test, and has no [SetUp] attribute — you use the constructor.

That's a deliberate constraint: it makes shared mutable state between tests structurally awkward, which is the main cause of order-dependent, intermittently-failing suites.

It also runs test classes in parallel by default, so tests that quietly depended on shared state fail immediately rather than after six months of growth.

When you genuinely need expensive shared setup — a database container, a WebApplicationFactory — that's an explicit IClassFixture or ICollectionFixture, so sharing is a visible decision rather than the default.

[Theory]
[InlineData(999, 999)]        // below threshold - no discount
[InlineData(1000, 1000)]      // at the boundary - no discount
[InlineData(1001, 950.95)]    // just above - 5% applies
[InlineData(5000, 4750)]
public void Volume_discount_applies_above_1000(decimal subtotal, decimal expected)
{
    new StandardDiscount().Apply(Money.Of(subtotal)).Amount
        .Should().Be(expected);
}

// MemberData for cases you can't express as constants
[Theory]
[MemberData(nameof(ExpiryCases))]
public void Expiry_is_calculated_correctly(DateTime start, int days, DateTime expected) { }

public static TheoryData<DateTime, int, DateTime> ExpiryCases => new()
{
    { new DateTime(2024, 1, 31), 1, new DateTime(2024, 2, 1) },
    { new DateTime(2024, 2, 28), 1, new DateTime(2024, 2, 29) },   // leap year
    { new DateTime(2024, 12, 31), 1, new DateTime(2025, 1, 1) }
};
Theories are where boundary conditions belong

The value isn't avoiding duplication — it's that a theory makes the boundary explicit and visible.

Writing 999, 1000 and 1001 as three cases documents where the threshold is and proves which side it falls on. That's exactly the off-by-one that ships, and a single test with one representative value doesn't catch it.

Same for dates: month ends, leap years, year boundaries. Those are the cases that break in production, and they're trivial to add as theory rows.

One caution: keep the test body logic-free. If a theory needs an if to handle different cases, it's really two tests wearing one name.

Loose mocking hides bugs, and it's the default

By default both libraries return default for anything you didn't stub — so an unstubbed method returning a reference type gives null.

That's convenient and it means a test can pass while silently exercising a null path you never intended. You stub two of five methods, the other three return null, and the code under test happens not to dereference them today. Then a refactor makes it dereference one, and the test fails for a reason that looks unrelated.

MockBehavior.Strict throws on any unstubbed call, which surfaces this — at the cost of tests that break whenever the code calls something new, even harmlessly.

My preference is loose mocking plus fewer mocks overall. If you're stubbing five methods on one dependency, the more useful signal is that the test is over-mocked — a fake would be clearer and wouldn't have null holes.

Async testing pitfalls 🔥 Must know

[Fact]
public async void Order_is_saved()          // async VOID
{
    await _sut.PlaceAsync(order);
    Assert.True(false);                     // this test PASSES
}
// The test runner cannot await async void. The exception is raised on a
// different context, after the test has already been reported as passed.
// Worst case: it crashes the test host with no attribution.
[Fact]
public async Task Order_is_saved()          // async Task - awaited properly
{
    await _sut.PlaceAsync(order);
    (await _db.Orders.SingleAsync()).Should().NotBeNull();
}
MistakeConsequence
async void testFailures silently pass. The worst bug in a test suite
.Result or .Wait()Can deadlock; wraps exceptions in AggregateException

Thread.Sleep to "wait for" async workSlow and flaky — use TimeProvider or a proper wait
async void is the most dangerous mistake in a test suite

Everything else on this page makes tests worse. This one makes them lie.

An async void test cannot be awaited by the runner, so the runner reports it as passed the moment it hits the first await. Any assertion after that point — and any exception — happens after the result was recorded.

So you can have a suite of green tests that assert nothing, and nobody notices because green is green.

Enable the analyser: xUnit1001 flags this, and it should be an error rather than a warning. It's one of the few analyser rules that catches a correctness problem in the tests themselves.

Related: an async void event handler in production code has the same unobservable-exception problem, which is why it's only acceptable at genuine event-handler boundaries.

// The async overload matters - the sync one won't observe the exception
var act = async () => await _sut.PlaceAsync(invalidOrder);

await act.Should().ThrowAsync<ValidationException>()
         .WithMessage("*quantity*");

// xUnit's built-in equivalent
await Assert.ThrowsAsync<ValidationException>(() => _sut.PlaceAsync(invalidOrder));

Testing EF Core 🔥 Must know

Don't use the in-memory provider to test queries

It's the most common .NET testing mistake, because it's convenient and Microsoft's own docs now advise against it.

The in-memory provider is not a relational database. It has no SQL, so:

  • It doesn't enforce constraints — unique indexes, foreign keys, required columns, max lengths. So a test passes and production throws a constraint violation.
  • It doesn't translate LINQ. Queries that cannot be translated to SQL run happily in memory — so your test passes and the real query throws InvalidOperationException at runtime.
  • Case sensitivity, collation and null ordering differ, so string comparisons and ORDER BY behave differently.
  • No transactions, no concurrency tokens behaving realistically.
  • Migrations aren't exercised at all.

The result is a suite that's green while the application is broken — a false negative, which is precisely what tests exist to prevent.

Use a real database. Testcontainers makes it straightforward, and SQLite is a middle option — closer to real SQL, still not identical to SQL Server on collation, date handling or schema features.

public sealed class DatabaseFixture : IAsyncLifetime
{
    private readonly MsSqlContainer _container = new MsSqlBuilder()
        .WithImage("mcr.microsoft.com/mssql/server:2022-latest")
        .Build();

    public string ConnectionString => _container.GetConnectionString();

    public async Task InitializeAsync()
    {
        await _container.StartAsync();

        // Run the REAL migrations - so migrations are tested too
        await using var db = new AppDbContext(
            new DbContextOptionsBuilder<AppDbContext>()
                .UseSqlServer(ConnectionString).Options);
        await db.Database.MigrateAsync();
    }

    public Task DisposeAsync() => _container.DisposeAsync().AsTask();
}

// One container shared across a collection - starting it is the expensive part
[CollectionDefinition(nameof(DatabaseCollection))]
public sealed class DatabaseCollection : ICollectionFixture<DatabaseFixture> { }
Senior signal — running real migrations is the underrated benefit

Calling MigrateAsync() in the fixture rather than EnsureCreated() means every test run exercises your migration chain against a real database engine.

That catches a class of failure nothing else does: a migration that fails on a real provider, two migrations that conflict, a migration that works on an empty database and breaks with data present, or a model that has drifted from the migrations so the schema doesn't match the code.

Migration failures are among the worst production incidents because they happen during deployment — so the application is already down and the rollback is a database operation. Catching them in CI is disproportionately valuable.

EnsureCreated() builds the schema from the model and bypasses migrations entirely, so it specifically doesn't test the thing that breaks.

// Respawn deletes all data while preserving the schema - much faster than
// recreating the database, and it respects foreign-key order automatically.
public sealed class IntegrationTestBase : IAsyncLifetime
{
    private static Respawner? _respawner;
    protected AppDbContext Db = null!;

    public async Task InitializeAsync()
    {
        _respawner ??= await Respawner.CreateAsync(_connectionString, new RespawnerOptions
        {
            TablesToIgnore = ["__EFMigrationsHistory"],
            DbAdapter = DbAdapter.SqlServer
        });

        await _respawner.ResetAsync(_connectionString);   // clean slate per test
        Db = CreateContext();
    }
}
Shared state is what makes integration suites flaky

Integration tests share a database, so without isolation they interfere: one test's data makes another's count assertion wrong, and failures become order-dependent — passing locally, failing in CI where the order differs.

Three options, in order of preference. Respawn between tests — deletes data, keeps schema, fast, and handles foreign-key ordering for you. A transaction per test, rolled back — very fast, and it breaks if the code under test manages its own transactions, which is common. A database per test — perfect isolation, far too slow.

And be careful with parallelism: xUnit runs collections in parallel by default, so tests in different collections sharing one database will interfere. Either put all database tests in one collection (serialising them) or give each collection its own database.

That's a real trade — serialising integration tests makes them slower, and it's usually the right choice over intermittent failures nobody can reproduce.

Testing the whole API 🔥 Must know

public sealed class ApiFactory : WebApplicationFactory<Program>
{
    private readonly string _connectionString;

    protected override void ConfigureWebHost(IWebHostBuilder builder)
    {
        builder.UseEnvironment("Testing");

        builder.ConfigureTestServices(services =>
        {
            // Point at the test database
            services.RemoveAll<DbContextOptions<AppDbContext>>();
            services.AddDbContext<AppDbContext>(o => o.UseSqlServer(_connectionString));

            // Replace ONLY genuine external boundaries
            services.RemoveAll<IPaymentGateway>();
            services.AddSingleton<IPaymentGateway, FakePaymentGateway>();

            services.RemoveAll<IEmailSender>();
            services.AddSingleton<IEmailSender, RecordingEmailSender>();

            // Bypass auth so tests don't need real tokens
            services.AddAuthentication("Test")
                    .AddScheme<AuthenticationSchemeOptions, TestAuthHandler>("Test", _ => { });
        });
    }
}

[Fact]
public async Task Posting_a_valid_order_returns_201_and_persists_it()
{
    var client = _factory.CreateClient();

    var response = await client.PostAsJsonAsync("/api/orders",
        new { customerId = _customerId, lines = new[] { new { sku = "KB-01", qty = 2 } } });

    response.StatusCode.Should().Be(HttpStatusCode.Created);

    // Real routing, model binding, validation, filters, EF Core, SQL, serialisation
    var saved = await _db.Orders.SingleAsync();
    saved.Status.Should().Be(OrderStatus.Placed);
}
Senior signal — this is the highest value-per-test in .NET

WebApplicationFactory starts your actual application in-process — real Program.cs, real middleware pipeline, real DI container, real model binding, real filters, real serialisation — and gives you an HttpClient that talks to it without a network hop.

So one test covers routing, binding, validation, authorisation, the handler, EF Core, real SQL and JSON serialisation. That's the entire class of integration failure that mocked unit tests cannot catch — a missing DI registration, a JSON property name mismatch, a filter not applied, a query that won't translate.

And it's fast, because there's no network and no process start.

The discipline that matters: replace only genuine external boundaries. Payment gateway, email, third-party APIs — yes. Your own services, the database, the DI container — no, because replacing those is exactly what stops the test catching integration problems. The temptation is to stub more and more until it's a unit test with extra ceremony.

If I could have only one kind of test in a .NET API, it would be this.

Testing outbound HTTP calls
// Don't mock HttpClient. Substitute the handler - you keep real HTTP semantics.
public sealed class StubHandler(HttpStatusCode code, string body) : HttpMessageHandler
{
    protected override Task<HttpResponseMessage> SendAsync(
        HttpRequestMessage request, CancellationToken ct) =>
        Task.FromResult(new HttpResponseMessage(code)
        {
            Content = new StringContent(body, Encoding.UTF8, "application/json")
        });
}

services.AddHttpClient<PricingClient>()
        .ConfigurePrimaryHttpMessageHandler(() => new StubHandler(HttpStatusCode.OK, json));

This tests your real client code — serialisation, status handling, retry policies, EnsureSuccessStatusCode — against a controlled response.

Mocking HttpClient itself skips all of that and bakes in assumptions about a class you don't own. For richer scenarios, WireMock.Net gives you a real local HTTP server with request matching and verification.

Assertions 🟡 Intermediate

// Built-in xUnit
Assert.Equal(OrderStatus.Placed, order.Status);
// Failure: "Assert.Equal() Failure: Expected: Placed, Actual: Draft"

// FluentAssertions - reads as a sentence, richer failures
order.Status.Should().Be(OrderStatus.Placed, "because a valid order is placed immediately");

order.Lines.Should().HaveCount(2)
     .And.OnlyContain(l => l.Quantity > 0);

// Object graph comparison, ignoring generated values
actual.Should().BeEquivalentTo(expected, o => o.Excluding(x => x.Id)
                                              .Excluding(x => x.CreatedUtc));
A licensing note worth knowing

FluentAssertions changed to a commercial licence from version 8 for non-open-source use. Version 7 remains free under the old terms.

So for a new commercial project the realistic options are: stay on version 7, pay, use Shouldly, or use xUnit's built-in assertions with Assert.Multiple. AwesomeAssertions is a community fork of the version 7 API.

Worth mentioning because it's recent and a lot of existing material assumes FluentAssertions is simply free — and it's the kind of thing that surfaces during a licence audit rather than at adoption.

Key takeaways
  • xUnit's instance-per-test and default parallelism make shared state structurally awkward — that's a feature.
  • Use theories for boundary conditions; keep the body logic-free.
  • async void tests silently pass. Enable xUnit1001 as an error.
  • Loose mocking returns nulls for unstubbed calls — a sign you're over-mocking.
  • Don't test queries against EF Core's in-memory provider — no constraints, no SQL translation.
  • Testcontainers gives a real database in CI; run real MigrateAsync so migrations are tested.
  • Reset state between integration tests with Respawn, and mind xUnit parallelism.
  • WebApplicationFactory is the highest value-per-test in .NET — replace only external boundaries.
  • Test outbound HTTP by substituting HttpMessageHandler, not by mocking HttpClient.
  • FluentAssertions v8 is commercially licensed; v7, Shouldly or built-ins are the alternatives.

Common mistakes

  • async void tests that pass regardless of assertions.
  • .Result or .Wait() instead of awaiting.
  • EF Core in-memory provider for query or constraint testing.
  • EnsureCreated instead of MigrateAsync, so migrations are never exercised.
  • No state reset between integration tests, causing order-dependent failures.
  • Parallel collections sharing one database.
  • Stubbing your own services in WebApplicationFactory, defeating the point.
  • Mocking HttpClient rather than the handler.
  • Five Setup calls on one mock — use a fake instead.
  • Thread.Sleep to wait for async work.
  • Logic inside a theory body.

Interview questions

Intermediate

How would you test a service that uses EF Core? 🔥 Must know
How I'd answer

"I'd use a real database, via Testcontainers — and I'd start by explaining why not the in-memory provider, because that's the common answer and it's actively harmful."

"The in-memory provider isn't a relational database. There's no SQL underneath, so it doesn't enforce unique indexes, foreign keys, required columns or max lengths — a test passes and production throws a constraint violation. And it doesn't translate LINQ, so a query that cannot be translated to SQL runs happily in memory and then throws InvalidOperationException at runtime against the real provider."

"So it produces the worst kind of test: green while the application is broken. That's a false negative, which is precisely what tests exist to prevent. Microsoft's own guidance now advises against it for this reason."

"With Testcontainers I start a real SQL Server in Docker for the test run. One container shared across a test collection, since starting it is the expensive part — a few seconds once, not per test."

"The detail I'd highlight: run MigrateAsync() rather than EnsureCreated(). That means every test run exercises the real migration chain against a real engine — so it catches a migration that fails on the real provider, two migrations that conflict, or a model that's drifted from the migrations. Migration failures are among the worst production incidents because they happen during deployment, so the app is already down. EnsureCreated builds the schema from the model and bypasses migrations entirely, so it specifically doesn't test the thing that breaks."

"For isolation between tests I'd use Respawn — it deletes all data while keeping the schema, respects foreign-key ordering, and is much faster than recreating the database. Without a reset, one test's data breaks another's count assertion and failures become order-dependent: passing locally, failing in CI."

"A transaction per test rolled back is faster still, and it breaks if the code under test manages its own transactions — which is common — so I'd default to Respawn."

"And I'd be careful with xUnit parallelism: collections run in parallel by default, so database tests in different collections will interfere. Either put them all in one collection, which serialises them, or give each collection its own database. Serialising is slower and better than intermittent failures nobody can reproduce."

"Where SQLite fits: it's a reasonable middle option — real SQL, real constraints, in-memory and fast — and it isn't SQL Server. Collation, date handling, and some schema features differ, so it catches more than the in-memory provider and less than the real thing. I'd use it if Docker weren't available in CI."

"For anything above the repository, I'd go further and use WebApplicationFactory with the real database — that covers routing, binding, validation, DI, EF Core, SQL and serialisation in one test, which is the whole class of failure that mocked unit tests can't reach."

  • Do you reject the in-memory provider, with specific reasons?
  • Do you know Testcontainers?
  • Do you run real migrations?
  • Do you handle state isolation and parallelism?
  • Do you know where SQLite sits?

How would you write an integration test for an ASP.NET Core API? ⭐ Senior-level
How I'd answer

"WebApplicationFactory<Program> with a real database from Testcontainers. I'd argue that's the highest value-per-test available in .NET."

"It starts the actual application in-process — real Program.cs, real middleware pipeline, real DI container, real model binding, real filters, real serialisation — and gives me an HttpClient that talks to it with no network hop."

"So one test exercises routing, binding, validation, authorisation, the handler, EF Core, real SQL and JSON serialisation. That's exactly the class of failure a mocked unit test cannot catch: a missing DI registration, a JSON property name mismatch, a filter not applied, a query that won't translate to SQL, a migration that fails. And it's fast, because there's no process start and no network."

"The important discipline is replacing only genuine external boundaries. The payment gateway, the email sender, third-party HTTP APIs — those get fakes, and I'd use a recording fake for email so I can assert what would have been sent. But not my own services, not the database, not the DI container — replacing those is precisely what stops the test catching integration problems."

"There's a real temptation to keep stubbing until the test is easy, and at that point it's a unit test with extra ceremony and none of the value."

"For authentication I'd register a test authentication handler so tests don't need real tokens, with a way to vary the claims per test — because authorisation logic is exactly the thing worth testing here, and I want to assert that a user without a role gets 403 rather than bypassing auth entirely."

"For configuration, UseEnvironment("Testing") plus ConfigureTestServices, which runs after the app's own registrations so my replacements win. Using ConfigureServices instead is a common mistake — the app's registrations run after and overwrite yours."

"State isolation as before: Respawn between tests, and all database tests in one xUnit collection so they don't run in parallel against a shared database."

"I'd assert on both the response and the persisted state — status code, response body shape, and then query the database to confirm what was actually written. Checking only the status code misses a handler that returns 201 without saving."

"What I'd not do is push everything to this level. These are slower than unit tests, so I'd use them for the main path through each endpoint plus its important failure cases — validation rejection, not found, unauthorised, conflict — and keep detailed branch coverage of calculations in fast unit tests where they belong."

"One practical caveat: WebApplicationFactory requires the app's Program.cs to be reachable, which with top-level statements means either making the assembly's internals visible to the test project or having a partial Program class. That's a small friction people hit on first setup."

What they're really checking
  • Do you know WebApplicationFactory runs the real pipeline?
  • Do you replace only external boundaries?
  • Do you know ConfigureTestServices vs ConfigureServices?
  • Do you test authorisation rather than bypassing it?
  • Do you assert on persisted state, not just the status code?
  • Are you deliberate about what belongs at this level?
Weak answers
  • Red flag: stubbing the database and internal services.
