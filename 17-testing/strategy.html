Strategy, Coverage & CI

Where to spend testing effort, which metrics are honest, and how to stop a suite rotting once it exists.

🟡 Intermediate ⭐ Senior-level 🔥 Must know
Quick revision
  • Invest by risk, not uniformly. Test what would hurt most if wrong.
  • Coverage measures execution, not verification. Useful as a diagnostic, harmful as a target.
  • Mutation testing measures whether tests actually catch bugs.
  • A flaky test is worse than no test — it trains people to ignore failures.
  • Quarantine flaky tests immediately, then fix or delete them.
  • Fast tests on every commit, slower ones on merge or a schedule.
  • For legacy code, write tests at the boundary first, then refactor.

Where to invest 🔥 Must know

The principle

Testing effort should follow risk: how likely something is to be wrong, multiplied by how much it costs if it is.

Uniform coverage across a codebase spends the same effort on a payment calculation and a ToString() override, which is obviously wrong when stated plainly and is what a coverage target encourages.

Test heavilyTest lightly
Money, pricing, tax, billing — wrong answers cost real moneyGetters, setters, simple mappers
Authorisation and tenant isolation — a bug here is a breachFramework behaviour you didn't write
State machines and workflow transitionsGenerated code
Anything with a compliance or audit requirementLogging statements
Concurrency and idempotencyConfiguration wiring — covered by one integration test
Code that has broken beforeThrowaway or spike code
Boundaries and error pathsThe happy path alone
Senior signal — error paths are under-tested and over-represented in incidents

Most suites test the happy path thoroughly and the failure paths barely at all, because the happy path is easier to write and feels like the point.

But the happy path is also what gets exercised constantly in manual testing, in staging, and by every user every day. The failure paths are the ones nobody exercises until production does.

What happens when the payment gateway times out mid-transaction? When the message is a duplicate? When the database rejects a constraint? When the input is null, empty, enormous, or a different tenant's id?

That's where incidents come from, and it's where a test has the highest marginal value — because it's the only thing exercising that branch.

"I'd prioritise the error paths and boundaries over adding more happy-path coverage" is a strong answer, because it reflects where defects actually live rather than where tests are easy to write.

Coverage 🔥 Must know

What it does and doesn't tell you

Coverage says a line was executed. It says nothing about whether a test would notice if that line were wrong.

So you can reach 90% with tests that assert almost nothing — and that's exactly what happens when coverage becomes a target rather than a signal.

[Fact]
public void CalculateTotal_does_not_throw()
{
    var result = _calculator.CalculateTotal(order);   // every line executed
    Assert.NotNull(result);                            // asserts essentially nothing
}
// Change the tax rate, the discount logic, or the rounding - this still passes.
Coverage as a…Verdict
Diagnostic — "what isn't tested at all?"Genuinely useful. Zero coverage on the pricing engine is a real finding
Trend — "is it falling?"Useful, especially on new code
Target — "we require 80%"Harmful. Produces tests written for the number
Quality measureMeaningless. It measures execution, not verification
If you must have a gate, gate on new code

A global threshold on a legacy codebase either blocks all work or gets set so low it means nothing. And retrofitting tests purely to reach a number produces the worst tests in the codebase.

Coverage on the diff is a more defensible gate: new and changed lines must be covered, and the existing figure is left alone. That stops decline without demanding a retrospective project, and it puts the requirement where the author has context.

I'd still treat it as a prompt for discussion rather than a hard block — because there are legitimate exceptions, and a gate that can't be overridden gets gamed rather than respected.

Mutation testing ⭐ Senior-level

The idea

Deliberately introduce bugs into the code — flip a > to >=, negate a condition, change a constant, remove a statement — and check whether any test fails.

A mutation that survives means no test would have caught that bug. Which is the question coverage can't answer.

  Original:   if (subtotal > 1000) discount = 0.05m;

  Mutants:
    if (subtotal >= 1000)     KILLED    <- a test caught the boundary change
    if (subtotal < 1000)      KILLED
    if (true)                 SURVIVED  <- nothing tests the below-threshold case
    discount = 0.0m;          SURVIVED  <- nothing asserts the discount VALUE

  Line coverage: 100%.  Mutation score: 50%.
  Two real bugs would ship undetected.
Senior signal — this is the metric that measures what you care about

Coverage answers "did a test run this line?". Mutation testing answers "would a test catch a bug in this line?" — which is the actual question.

It reliably finds two things coverage hides: missing assertions, where the code runs and nothing checks the result, and untested boundaries, where you test 500 and 2000 but never 999, 1000 and 1001.

In .NET the tool is Stryker.NET. The honest caveat is that it's slow — it re-runs your tests once per mutant, so a full run on a large codebase takes a long time.

Which makes the practical use targeted rather than universal: run it on the genuinely critical modules — pricing, tax, authorisation, anything financial — rather than the whole solution, and run it on a schedule rather than per commit.

Even one run on your most important module is usually revealing, and it's a much better use of effort than pushing coverage from 78% to 85%.

Flaky tests 🔥 Must know

A flaky test is worse than no test

Not merely annoying — actively harmful, because of what it does to the team's behaviour.

It trains people to ignore failures. Once "just re-run it" becomes normal, a genuine failure gets re-run too, and eventually merged. The suite has stopped functioning as a gate while still consuming CI time and appearing to work.

It also destroys the signal you need most: when everything is occasionally red, nobody can tell whether today's red is real.

So flakiness is a reliability problem to be fixed with urgency, not a known inconvenience. A suite that's 99% reliable across 500 tests fails somewhere on most runs.

CauseFix
Shared state between testsReset between tests; construct data per test
Order dependencyRandomise order locally to surface it, then remove the coupling
Real time and timingTimeProvider; never Thread.Sleep
Fixed waits for async workPoll for the condition with a timeout, don't sleep a guess
Test parallelismIsolate resources, or serialise the affected collection
External dependenciesStub them — a test hitting a real API is flaky by definition
Culture and timezoneSet both explicitly in the test
Unordered results asserted as orderedAssert set equality, or order explicitly
Quarantine immediately, then fix or delete

The instinct is to add a retry attribute and move on. That hides the flakiness and keeps the false confidence.

Better: quarantine it — move it out of the blocking suite into a separately-reported set — so the main pipeline is trustworthy again immediately. Then it's a tracked item with an owner.

And apply a deadline: fixed or deleted within a sprint. A quarantine with no expiry becomes a graveyard of tests nobody looks at, which is the same problem with extra process.

Deleting a flaky test is a legitimate outcome. A test that can't be made reliable provides no signal, and removing it is honest about that — whereas leaving it retrying pretends coverage exists that doesn't.

Being willing to say "I'd delete it" is a good senior signal, because most people won't.

// Flaky: 500ms is a guess. Too short on loaded CI, wasteful when fast.
await Task.Delay(500);
(await _db.Orders.CountAsync()).Should().Be(1);

// Reliable: wait for the CONDITION, with a timeout
await Assert.EventuallyAsync(
    async () => await _db.Orders.CountAsync() == 1,
    timeout: TimeSpan.FromSeconds(5),
    pollInterval: TimeSpan.FromMilliseconds(50));
// Fast when the work is fast; tolerant when CI is slow.

What belongs in the pipeline 🔥 Must know

StageRunsBudgetBlocking?
On every commitBuild, analysers, unit testsUnder 5 minutesYes
On pull requestThe above plus integration testsUnder 15 minutesYes
On merge to mainPlus contract tests, a smoke E2E setUnder 30 minutesYes
NightlyFull E2E, mutation testing, performance, security scansHours are fineNo — reported
Senior signal — the commit-stage budget is the constraint that matters

If the fast feedback loop takes twenty minutes, developers stop waiting for it. They push and context-switch, so a failure arrives after they've moved on — and the cost of fixing it has gone up several times because they've lost the context.

So under five minutes for the commit stage is a real engineering requirement, not an aspiration. It's what keeps the loop tight enough that people act on results.

Which forces useful discipline: unit tests must be genuinely fast, so no database and no network. Integration tests go to a later stage. And when the commit stage creeps past the budget, that's a signal to investigate — usually a test that quietly acquired an I/O dependency.

The corollary: put slow-but-valuable things in a non-blocking nightly stage rather than dropping them. Full E2E, mutation testing and performance tests are worth running; they aren't worth blocking every commit on.

Tests that fail only in CI

Almost always one of four causes, and worth checking in this order.

Parallelism — CI may run with different concurrency, so shared-state coupling surfaces there and not locally. Order — a different execution order exposes a dependency between tests. Environment — culture, timezone, locale or line endings differ from your machine. Timing — CI machines are slower and noisier, so fixed waits that pass locally time out.

The diagnostic that finds most of these quickly: run locally with randomised order and the same parallelism as CI. If it fails, it was never a CI problem — it was a latent bug your local run happened to hide.

Testing legacy code ⭐ Senior-level

The bind

The code has no tests because it's hard to test — static dependencies, no interfaces, DateTime.Now everywhere, a 900-line method.

And you can't safely refactor it to be testable, because there are no tests. That circle is the actual problem.

  1. Find the widest seam you can reach — an API endpoint, a public method, a message handler. Not the class you want to change.
  2. Write characterisation tests there — capture what it currently does, including behaviour that looks wrong.
  3. Refactor toward testability, with those tests as the safety net.
  4. Add focused tests to the newly-testable units.
  5. Then change the behaviour — and now the characterisation test failing is informative.
Senior signal — characterisation tests capture current behaviour, not correct behaviour

This is the key distinction, and it's counter-intuitive.

A characterisation test asserts what the code does today, bugs included. If it rounds incorrectly, you assert the incorrect rounding.

The purpose isn't to validate correctness — it's to detect change. So when you refactor, any difference in behaviour shows up immediately, including differences you didn't intend. That's what makes the refactor safe.

Fixing the bug is a separate, deliberate step: change the code, watch the characterisation test fail, and update it consciously with a note explaining why the behaviour changed. That gives you an audit trail of intentional changes rather than accidental ones.

Trying to fix bugs while refactoring means you can't tell which change caused a difference — and that's how a refactor becomes an incident.

Approval tests are well suited to this: capture the entire output as a snapshot and diff against it, rather than hand-writing assertions for behaviour you don't yet understand.

Test at the widest seam, not the narrowest

The instinct is to unit test the class you're about to change. In legacy code that's usually the hardest place to start — it's the one with the static calls and the tangled dependencies.

Go wider. An HTTP endpoint or a message handler is often testable as-is with WebApplicationFactory and a real database, without touching the code at all. That gives you a safety net immediately, at the cost of a slower test.

Then refactor inward with that net in place, and add fast focused tests to the pieces as they become testable.

That sequencing — coarse test first, then refactor, then fine tests — is what makes legacy work tractable. Starting with the unit test means changing untested code, which is the thing you were trying to avoid.

What not to test 🟡 Intermediate

Don't testWhy
The frameworkA test proving [Required] rejects null tests ASP.NET Core, not you
Third-party librariesTest your usage of them, at the integration level
Trivial propertiesA getter returning a field has no logic to be wrong
Private methods directlyTest them through the public behaviour that uses them
Generated codeTest the generator, or the behaviour it produces
Log messagesUnless a log is the deliverable, as in audit
Implementation structure"This class has three dependencies" isn't behaviour
Testing private methods is a design signal

If a private method feels like it needs its own test, that usually means it contains enough logic to be its own concept — and the right response is to extract it into a class with a public interface, then test it directly.

Making it internal plus InternalsVisibleTo is the common workaround. It works, and it locks the test to the current structure — so the test breaks when you reorganise, which is the brittleness problem again.

So: the difficulty testing a private method is information. Either it's simple enough to be covered through the public behaviour, or it's substantial enough to deserve extraction. Reaching for reflection or InternalsVisibleTo skips that decision.

Key takeaways
  • Invest by risk — likelihood of being wrong times cost if it is.
  • Error paths and boundaries are under-tested and over-represented in incidents.
  • Coverage measures execution, not verification. Diagnostic yes, target no.
  • If you gate, gate on the diff rather than the whole codebase.
  • Mutation testing measures whether tests would catch a bug — run it on critical modules, on a schedule.
  • A flaky test trains people to ignore failures, which is worse than no test.
  • Quarantine flaky tests immediately; fix or delete within a sprint.
  • Poll for conditions with a timeout; never sleep a guess.
  • Commit stage under five minutes, or people stop waiting for it.
  • Slow-but-valuable tests go in a non-blocking nightly stage.
  • CI-only failures are usually parallelism, order, environment or timing.
  • For legacy code: characterisation tests at the widest seam, then refactor, then fine tests.
  • Difficulty testing a private method means it should be extracted.

Common mistakes

  • A mandated coverage percentage, producing tests written for the number.
  • Uniform coverage across trivial and critical code alike.
  • Only happy-path tests.
  • Retry attributes on flaky tests instead of fixing them.
  • Tolerating flakiness until nobody trusts the suite.
  • Thread.Sleep to wait for async work.
  • A commit stage over ten minutes, so developers stop waiting.
  • Full E2E on every commit, making the pipeline slow and flaky.
  • Refactoring legacy code before writing a characterisation test.
  • Fixing bugs while refactoring, so differences can't be attributed.
  • Testing private methods via reflection.
  • Testing the framework rather than your own logic.

Interview questions

Intermediate

What code coverage should a project aim for? 🔥 Must know
How I'd answer

"I'd push back on the framing, because a coverage target is the wrong instrument — and I'd explain why rather than just refusing the number."

"Coverage measures whether a line was executed by a test. It says nothing about whether the test would notice if that line were wrong. So you can reach 90% with tests that assert almost nothing — call the method, assert not-null — and that's precisely what happens when the percentage becomes a target. People write tests to satisfy the number, and the worst tests in a codebase are usually the ones added to hit a coverage gate."

"Meanwhile the things that break in production — error paths, boundary conditions, concurrent access, malformed input — tend to be the uncovered parts, because they're harder to write tests for. So the metric actively points effort away from where the risk is."

"What I'd use instead is risk-based investment: test heavily where being wrong is expensive. Money, pricing and tax. Authorisation and tenant isolation, where a bug is a breach. State machines. Anything with a compliance requirement. Anything that has broken before. And test lightly the getters, the mappers, and the framework behaviour I didn't write."

"Where coverage is useful is as a diagnostic rather than a goal. 'The pricing engine has zero coverage' is a real finding worth acting on. And as a trend, especially on new code — a sudden drop is worth a conversation."

"If an organisation insists on a gate, I'd argue for coverage on the diff rather than globally: new and changed lines must be covered, the existing figure is left alone. That stops decline without demanding a retrospective testing project, and it puts the requirement where the author has context. I'd still make it a prompt rather than a hard block, because a gate that can't be overridden gets gamed."

"And the metric I'd actually reach for if I wanted to know whether tests verify anything is mutation testing. It changes the code — flips a comparison, negates a condition, alters a constant — and checks whether any test fails. A surviving mutant means no test would catch that bug, which is the question coverage can't answer."

"In .NET that's Stryker.NET. It's slow, because it re-runs the suite per mutant, so I'd run it on the genuinely critical modules on a schedule rather than the whole solution per commit. One run on the pricing engine is usually more revealing than pushing coverage from 78% to 85%."

What they're really checking
  • Do you know coverage measures execution, not verification?
  • Can you explain why a target is counterproductive?
  • Do you propose risk-based investment instead?
  • Do you know about mutation testing?
  • Can you offer a workable compromise if a gate is mandated?
Weak answers
  • Red flag: "80%" with no reasoning.
  • Red flag: "100%, always."
  • Red flag: treating coverage as a quality measure.
Likely follow-ups
  • How do you decide what's high risk?
  • How does mutation testing work?
  • What if management mandates a number?

Advanced / scenario

Your CI suite fails intermittently and the team re-runs until green. What do you do? 🔥 Must know
How I'd answer

"I'd treat this as urgent, because the suite has already stopped working as a gate. Once 'just re-run it' is normal, a genuine failure gets re-run too and eventually merged — so the tests are consuming CI time while providing false confidence. That's worse than having no suite, because nobody realises the protection is gone."

"First, measure it. I'd collect per-test pass/fail history across runs so I know which tests are flaky and how often. Most CI systems can report this. Without data it's anecdote, and the team will disagree about which tests are the problem."

"Then restore trust immediately by quarantining. Move the flaky tests out of the blocking suite into a separately-reported set. That makes the main pipeline trustworthy again today rather than after the fixes land — which matters, because the behaviour of ignoring failures is what you're trying to stop."

"What I'd not do is add retry attributes. That hides the flakiness and keeps the false confidence — you've made the symptom invisible while the cause remains."

"Then fix by cause, and they cluster into a few categories."

"Shared state and order dependency — the most common. One test's data affects another's assertion, so failures depend on execution order. I'd surface these deliberately by running locally with randomised order, then fix by resetting state between tests and constructing data per test rather than sharing fixtures."

"Timing. Fixed waits — Task.Delay(500) — that pass locally and time out on a loaded CI machine. The fix is to poll for the condition with a timeout, so it's fast when the work is fast and tolerant when CI is slow. And TimeProvider for anything time-dependent, which also makes those tests instant."

"Parallelism. CI may run different concurrency to local, so tests sharing a database interfere there and not locally. Either isolate the resource per collection or serialise the affected ones — slower, and better than intermittent failures."

"Environment — culture, timezone, line endings differing from developer machines. Set them explicitly in the test."

"External dependencies. A test calling a real API is flaky by definition. Stub it."

"The diagnostic I'd emphasise: run locally with randomised order and CI's parallelism. If it fails, it was never a CI problem — it was a latent bug that your local run happened to hide. That reframing matters, because teams often treat these as infrastructure issues when they're test defects."

"Then a policy so it doesn't return: a quarantined test is fixed or deleted within a sprint, with a named owner. A quarantine with no expiry becomes a graveyard, which is the same problem with extra process."

"And I'd be explicit that deleting is a legitimate outcome. A test that can't be made reliable provides no signal — removing it is honest, whereas leaving it retrying pretends coverage exists that doesn't. Most teams won't delete a test, and that reluctance is how the graveyard forms."

What they're really checking
  • Do you recognise the suite has already failed as a gate?
  • Do you quarantine to restore trust immediately?
  • Do you refuse retry attributes as the fix?
  • Can you enumerate the causes and their fixes?
  • Do you know the randomised-order diagnostic?
  • Will you delete a test?
Weak answers
  • Red flag: adding automatic retries.
  • Red flag: "CI machines are just slower" as the explanation.
  • Red flag: no plan to prevent recurrence.
Likely follow-ups
  • How do you detect order dependency systematically?
  • How would you get the team to agree to delete tests?
  • What do you do about a flaky E2E test that covers a critical journey?
