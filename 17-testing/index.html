Testing

The point of a test suite is that you can change the code with confidence. Most suites fail at exactly that.

🟡 Intermediate 🔥 Must know

What tests are actually for 🔥 Must know

In simple terms

Tests exist so you can change the code without being afraid.

Everything else — catching bugs, documenting behaviour, driving design — follows from that or is a secondary benefit. If a test suite makes change harder rather than easier, it has failed at its primary job however green it is.

A test earns its place if itA test costs you if it
Fails when behaviour breaksPasses while behaviour is broken
Passes through a refactorFails on every refactor
Tells you what broke, quicklyFails ambiguously, or intermittently
Documents an intended behaviourDocuments an implementation detail
Runs fast enough to run oftenIs slow enough that people skip it
The two failure modes, and the second is more common

False negatives — the test passes while the code is broken. Obvious, and what everyone worries about.

False positives — the test fails when nothing is broken. This is the one that destroys suites, and it's more common.

A test that fails every time you rename a private method, extract a class, or change how something is implemented internally isn't protecting you. It's taxing every change. And the predictable response is that people stop trusting failures, start re-running until green, and eventually delete or disable the suite.

So "our tests break every time we refactor" isn't a minor annoyance — it's a diagnosis. It means the tests are coupled to implementation rather than behaviour, and the suite is actively preventing the thing it was written to enable.

Behaviour, not implementation 🔥 Must know

[Fact]
public void PlaceOrder_calls_repository_then_publishes()
{
    _sut.PlaceOrder(order);

    // Asserting HOW it works. Every one of these breaks on refactor.
    _repository.Verify(r => r.Add(It.IsAny<Order>()), Times.Once);
    _repository.Verify(r => r.SaveChanges(), Times.Once);
    _publisher.Verify(p => p.Publish(It.IsAny<OrderPlaced>()), Times.Once);
    _logger.Verify(l => l.LogInformation(It.IsAny<string>()), Times.Once);
}
[Fact]
public async Task Placing_an_order_reserves_stock_and_confirms_it()
{
    var result = await _sut.PlaceOrderAsync(AnOrder.With(quantity: 2));

    result.IsSuccess.Should().BeTrue();

    var saved = await _db.Orders.SingleAsync();
    saved.Status.Should().Be(OrderStatus.Confirmed);

    (await _db.Inventory.SingleAsync()).Available.Should().Be(8);   // was 10
}
The test to apply

If I restructure the internals without changing what the system does, should this test fail?

If yes, the test is coupled to implementation and will cost you on every change.

Assert on return values, observable state, and messages that cross a boundary. Not on which internal collaborators were called in what order.

Senior signal — where the boundary sits determines everything

The reason most .NET test suites are brittle is that they treat every class as a unit and mock every collaborator. So each test is welded to one class's exact dependencies, and extracting a helper breaks a dozen tests.

A more useful notion of a unit is a behaviour, exercised through a stable entry point — typically an application-service or handler method — with mocks only at genuine boundaries: the network, the clock, the file system, a third-party API.

Internal collaborators are implementation detail and should be real. If a handler uses three domain services, let it use them; the test asserts the outcome. Then extracting a fourth service breaks nothing.

That single shift — mock at boundaries, not at class edges — is the difference between a suite that enables refactoring and one that prevents it. It's covered in detail on the fundamentals page.

On coverage ⭐ Senior-level

Coverage measures execution, not verification

A line is covered if a test executed it. Nothing about whether the test would notice if that line were wrong.

Which means you can reach 90% coverage with tests that assert almost nothing — and this happens routinely when coverage becomes a target. Auto-generated tests, tests that call a method and assert it doesn't throw, tests over getters and setters.

Meanwhile the things that break in production — error paths, boundary conditions, concurrent access, malformed input — are frequently the uncovered parts, because they're harder to write tests for.

Coverage is useful as a diagnostic and harmful as a target. Low coverage in an important area is a real signal worth investigating. A mandated percentage produces tests written to satisfy the number.

If you want to know whether tests actually verify anything, mutation testing measures that directly — it changes the code and checks whether a test notices.

How I'd answer

"I'd start from what tests are for: being able to change the code without being afraid. So a good test is one that fails when behaviour breaks and survives a refactor."

"That second half is the part people underweight. Everyone worries about tests that pass while the code is broken — false negatives. But false positives destroy suites: a test that fails every time you rename a private method or extract a class isn't protecting you, it's taxing every change. And the predictable outcome is that people stop trusting failures, re-run until green, and eventually disable the suite."

"So the question I apply is: if I restructure the internals without changing what the system does, should this test fail? If yes, it's coupled to implementation."

"Concretely that means asserting on return values, observable state, and messages crossing a boundary — not on which internal collaborators were called in what order. A test with four Verify calls checking that the repository was called then the publisher was called is documenting the current implementation, and it will break the moment that implementation changes for any reason, including a legitimate improvement."

"The related decision is where the boundary sits, and I think that's the root cause of most brittle .NET suites. If you treat every class as a unit and mock every collaborator, each test is welded to one class's exact dependencies — so extracting a helper breaks a dozen tests that were all passing and all still correct."

"I'd rather define a unit as a behaviour, exercised through a stable entry point like an application service or handler, with test doubles only at genuine boundaries: the network, the clock, the file system, a third-party API. Internal collaborators are implementation detail and should be real."

"Beyond that, the practical properties: fast enough that people run it — a suite taking twenty minutes gets skipped; deterministic, because a flaky test is worse than no test since it trains people to ignore failures; independent, so tests can run in any order without shared state; and clear on failure, so the name and assertion tell you what broke without opening the file."

"And I'd name what I don't use as a quality measure: coverage. It measures whether a line was executed, not whether a test would notice if it were wrong. You can hit 90% with tests that assert nothing, and that's exactly what happens when coverage becomes a target. It's a useful diagnostic — low coverage somewhere important is worth investigating — and a harmful goal. If I wanted to know whether tests genuinely verify behaviour, mutation testing measures that directly."

What they're really checking
  • Do you know false positives are the bigger problem?
  • Do you distinguish behaviour from implementation, with a usable test for it?
  • Do you have a view on where the unit boundary sits?
  • Are you sceptical of coverage as a target?
Weak answers
  • Red flag: "high coverage and one assertion per test."
  • Red flag: mocking every dependency as a default.
  • Red flag: no acknowledgement that tests can make change harder.
