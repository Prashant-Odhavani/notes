Enterprise Patterns

The patterns that shape whole applications. CQRS is the one worth understanding properly, because it exists at several levels and people conflate them.

🟡 Intermediate 🔴 Advanced 🔥 Must know
Quick revision
  • Repository — abstracts data access. DbSet is already one, so a thin wrapper adds little.
  • Unit of Work — one transaction across several changes. SaveChanges is this.
  • Specification — a reusable, composable query predicate.
  • Dependency Injection — depend on abstractions, supplied from outside.
  • CQRS — separate models for reading and writing. Comes in levels.
  • Event Sourcing — store the events, derive the state. Powerful and expensive.
  • CQRS ≠ Event Sourcing. Conflating them is the most common error here.

Repository 🔥 Must know

In simple terms

A repository gives the domain a collection-like way to reach persistence, so business logic doesn't contain queries.

The interesting question in .NET isn't what it is — it's whether you need one on top of EF Core.

The generic repository is the anti-pattern
public interface IRepository<T> where T : class
{
    Task<T?> GetByIdAsync(int id);
    Task<IEnumerable<T>> GetAllAsync();          // loads the entire table
    Task<IEnumerable<T>> FindAsync(Expression<Func<T, bool>> predicate);
    Task AddAsync(T entity);
    Task UpdateAsync(T entity);
    Task DeleteAsync(T entity);
}

This is DbSet<T> with fewer capabilities. It adds a layer and removes the ability to project, include, or compose — so callers either fetch whole entities they don't need, or the interface grows an escape hatch returning IQueryable, at which point it's abstracting nothing.

GetAllAsync is the tell: it invites loading a whole table into memory, and it appears in nearly every generic repository.

And the usual justification — "we could swap the database" — almost never happens, and wouldn't work anyway, because provider differences leak through regardless.

public interface IOrderRepository
{
    Task<Order?> GetForFulfilmentAsync(Guid id, CancellationToken ct);
    Task<IReadOnlyList<Order>> GetOverdueAsync(DateOnly asOf, CancellationToken ct);
    Task AddAsync(Order order, CancellationToken ct);
}

public sealed class OrderRepository(AppDbContext db) : IOrderRepository
{
    // The AGGREGATE is loaded correctly - the caller can't forget an Include
    public Task<Order?> GetForFulfilmentAsync(Guid id, CancellationToken ct) =>
        db.Orders
          .Include(o => o.Lines)
          .Include(o => o.ShippingAddress)
          .FirstOrDefaultAsync(o => o.Id == id, ct);
}
Senior signal — what a repository is actually for

Not database swapping. Two real things:

1. Guarding the aggregate boundary. GetForFulfilmentAsync guarantees the order arrives with its lines and address loaded. A caller using DbSet directly can forget an Include, then hit a lazy-load or a null reference at the point the domain method needs it. That's the strongest argument, and it's about correctness, not abstraction.

2. Naming the query in domain terms. GetOverdueAsync puts "what overdue means" in one place instead of the predicate being re-derived slightly differently in three services.

So: a repository per aggregate with named methods, on the write side. For reads, query DbContext directly with a projection — wrapping that in a repository only costs you EF's capabilities. That's also why the same codebase legitimately has repositories for commands and none for queries, which is CQRS at its simplest.

Unit of Work 🟡 Intermediate

You already have one

DbContext is a Unit of Work. It tracks changes and SaveChanges commits them in a single transaction.

So wrapping it in an IUnitOfWork that calls SaveChanges is usually a pass-through with extra indirection.

public interface IUnitOfWork
{
    Task<int> SaveChangesAsync(CancellationToken ct = default);
}
// Justification: the domain layer can commit without referencing DbContext,
// so it doesn't take a dependency on EF Core. That's an architecture
// decision, not a technical necessity - and it is a thin one.
The real pitfall: multiple SaveChanges calls

One SaveChanges is one transaction. Two calls are two transactions, so a failure between them leaves the first committed.

That's how you get an order with no stock deduction. Covered in detail on the EF Core transactions page, and it's a more practically important thing to know than whether to wrap DbContext in an interface.

Specification 🟡 Intermediate

// OrderService
var active = db.Orders.Where(o => !o.IsDeleted && o.Status != OrderStatus.Cancelled);

// ReportService - subtly different, and now the numbers disagree
var active = db.Orders.Where(o => o.Status != OrderStatus.Cancelled);

// ExportService - a third variation
var active = db.Orders.Where(o => !o.IsDeleted && o.Status == OrderStatus.Placed);
public static class OrderSpecs
{
    public static Expression<Func<Order, bool>> Active =>
        o => !o.IsDeleted && o.Status != OrderStatus.Cancelled;

    public static Expression<Func<Order, bool>> PlacedAfter(DateTime utc) =>
        o => o.CreatedUtc > utc;
}

// Composable, and still translated to SQL
var recent = db.Orders.Where(OrderSpecs.Active)
                      .Where(OrderSpecs.PlacedAfter(cutoff));
When it's worth it — and the simpler alternative

The value is a single definition of a business concept used in several places. "Active", "overdue", "eligible for refund" — where the definition drifting causes reports to disagree with the application.

It must be an Expression<Func<T, bool>>, not a Func<T, bool>. A plain delegate can't be translated to SQL, so EF would load the table and filter in memory — the client-evaluation trap.

For soft delete and tenancy specifically, a global query filter is better — it applies automatically so nobody can forget it, where a specification still has to be remembered at each call site.

The full GoF Specification with And/Or/Not combinators and expression rewriting is usually more machinery than the problem justifies. Static expression properties get most of the benefit.

Dependency Injection 🔥 Must know

The distinction worth being precise about

Dependency Inversion is the principle: depend on abstractions, and let the high-level policy define the abstraction rather than the low-level detail.

Dependency Injection is the technique: supply dependencies from outside instead of constructing them internally.

An IoC container is the tool that automates the wiring. You can do DI without one.

public class OrderService
{
    private readonly SqlOrderRepository _repo = new(
        new SqlConnection("Server=prod;..."));            // hard-coded, untestable
    private readonly SmtpEmailSender _email = new("smtp.corp.local");

    // Cannot test without a database and an SMTP server.
    // Cannot change either without editing this class.
}
public class OrderService(IOrderRepository repo, IEmailSender email)
{
    // Dependencies are visible in the signature and substitutable in tests.
    // This class no longer knows SQL Server or SMTP exist.
}
Senior signal — where the interface should live

Dependency inversion is about more than using an interface. It's about who owns it.

If IEmailSender lives in the infrastructure project alongside SmtpEmailSender, the domain still points at infrastructure — you've added an interface without inverting anything.

If IEmailSender lives in the domain or application layer, defined in terms the domain cares about, and infrastructure implements it, then the dependency arrow points inward. That's the inversion, and it's what makes Clean Architecture work.

The practical test: can the domain project compile with no reference to the infrastructure project? If not, you have DI but not inversion.

CQRS 🔥 Must know

In simple terms

Use a different model for reading than for writing.

That's the whole idea. Everything else — separate handlers, separate databases, event sourcing — is an implementation choice layered on top, and conflating those with the principle is where confusion starts.

Think of it this way

A restaurant kitchen and its menu describe the same food differently.

The kitchen needs recipes, quantities, allergen rules and process order — everything needed to make it correctly. The menu needs a name, a description and a price.

Printing the recipe on the menu would be absurd. So would asking the chef to cook from the menu.

Why one model serves both badly

Write sideRead side
Cares aboutInvariants, validation, transactionsShape, speed, joining across aggregates
Natural modelRich domain objects, one aggregate at a timeFlat DTOs, denormalized, whatever the screen needs
VolumeUsually lowerUsually 10–100× higher
Consistency needStrongOften "a few seconds stale is fine"
Shape stabilityChanges with business rulesChanges with every UI redesign
 
// A "get order summary" that goes through the domain model
public async Task<OrderSummaryDto> GetSummaryAsync(Guid id)
{
    // Loads the full aggregate - lines, address, payments, history -
    // because the repository guarantees a complete aggregate.
    var order = await _orderRepository.GetByIdAsync(id);

    // ...to display four fields.
    return new OrderSummaryDto(
        order.Id,
        order.Customer.Name,           // another join, or a lazy load
        order.Lines.Count,             // loaded 200 lines to count them
        order.Lines.Sum(l => l.Total)  // and to add them up in memory
    );
}
What's wrong with it
Loads far more than it needs — the whole aggregate for four fields
Aggregates in memory that the database would compute in one pass
Change tracking overhead on entities nobody will modify
Cross-aggregate reads fight the boundary. "Orders with customer name and latest payment" spans three aggregates, so either you load three or you break the boundary
The domain model gets distorted by read requirements — navigation properties added purely so a screen can display something

CQRS comes in levels ⭐ Senior-level

LevelWhat it meansCost
1. Separate models, one database Writes go through the domain; reads project directly to DTOs Nearly none. Start here
2. Separate read store Denormalized tables or views, updated from the write side Eventual consistency, sync mechanism
3. Separate database or service Read store is a different technology — Elasticsearch, a replica Real operational complexity
4. Plus event sourcing Events are the source of truth; read models are projections High. A different way of building software

public async Task<Result> Handle(ShipOrder cmd, CancellationToken ct)
{
    var order = await _orders.GetForFulfilmentAsync(cmd.OrderId, ct);
    if (order is null) return Result.NotFound();

    order.Ship(cmd.ShippedAtUtc);          // the rules live in the aggregate
    await _uow.SaveChangesAsync(ct);

// READ: skips the domain entirely. Projects exactly what the screen needs.
public Task<OrderSummaryDto?> Handle(GetOrderSummary q, CancellationToken ct) =>
    _db.Orders
       .AsNoTracking()                      // no change tracking
       .Where(o => o.Id == q.OrderId)
       .Select(o => new OrderSummaryDto(    // SQL computes the aggregates
           o.Id,
           o.Customer.Name,                 // one JOIN, one column
           o.Lines.Count(),                 // COUNT in the database
           o.Lines.Sum(l => l.Total)))      // SUM in the database
       .FirstOrDefaultAsync(ct);
Senior signal — level 1 is free, and it's what CQRS usually means

Level 1 needs no extra infrastructure, no eventual consistency, and no new technology. It's one database and two code paths.

The write path uses repositories and the domain model, so invariants are enforced in one place. The read path queries DbContext directly with a projection, so it fetches four columns instead of an object graph and lets SQL do the aggregation.

That's the version I'd apply by default, and it captures most of the benefit. It's also why the same codebase legitimately has repositories for writes and none for reads — that isn't inconsistency, it's the pattern.

Levels 2 and above buy read scalability at the cost of eventual consistency, and that's a genuine architectural commitment. Being able to separate "CQRS the principle" from "CQRS with a separate event-sourced read store" is the discriminating answer, because a lot of people believe CQRS requires the whole apparatus and dismiss it as over-engineering on that basis.

What level 2+ actually costs

Once the read store is separate, it's updated after the write — so a user can save something and not see it in a list. That's a UX problem, not just a technical one, and it needs deliberate handling: return the written entity rather than re-reading, or read from the write model immediately after a write. Same read-your-own-writes problem as a replica.

You also need a sync mechanism that's reliable — a change feed or outbox, not a dual write — plus a way to rebuild the read model when it drifts or its shape changes. Teams routinely forget the rebuild path and then can't change the read model shape.

So the honest position: go to level 2 when reads genuinely can't be served from the write model, not because CQRS is supposed to look like that.

Event Sourcing 🔴 Advanced

In simple terms

Instead of storing current state, store every change as an immutable event. Current state is derived by replaying them.

A bank statement rather than just a balance — and the balance is computed from the statement.

public sealed class Account
{
    public Money Balance { get; private set; } = Money.Zero;

    // State is derived, never stored
    public static Account From(IEnumerable<IAccountEvent> history)
    {
        var account = new Account();
        foreach (var e in history) account.Apply(e);
        return account;
    }

    private void Apply(IAccountEvent e) => Balance = e switch
    {
        Deposited d  => Balance + d.Amount,
        Withdrawn w  => Balance - w.Amount,
        _ => Balance
    };
}
GainsCosts
Complete audit trail — by construction, not by adding loggingQuerying is hard — you need projections for everything
Time travel — reconstruct any past stateEvent schema versioning is permanent; old events must stay readable forever
New read models from history — answer questions you hadn't thought ofEventual consistency throughout
Natural fit for event-driven integrationSteep learning curve; unfamiliar to most teams
Concurrency via expected-version checksSnapshots needed once streams get long
CQRS is not Event Sourcing — the most common conflation

CQRS means separate read and write models. You can do it with one SQL database and two LINQ queries.

Event Sourcing means events are the source of truth. It's a persistence strategy.

They're frequently used together — event sourcing makes querying hard, so you need CQRS read models to make it usable. But CQRS does not require event sourcing, and treating them as one thing is why people believe CQRS is inherently heavy.

If someone proposes "CQRS" and means event sourcing with separate stores and eventual consistency, that's a much bigger commitment than level 1 — and worth separating explicitly before the team agrees to it.

My default: CQRS at level 1 freely; event sourcing only where the audit trail or temporal queries are a genuine domain requirement — finance, compliance, anything where "what did it look like on the 14th?" is a real question. Not as a general architecture.

Key takeaways
  • Generic IRepository<T> is DbSet with fewer features. Use intention-revealing methods per aggregate.
  • A repository's real value is guarding the aggregate boundary, not swapping databases.
  • DbContext is already a Unit of Work; two SaveChanges calls are two transactions.
  • Specifications must be Expression<Func<T,bool>> to reach SQL; query filters are better for soft delete and tenancy.
  • DI without inversion is just constructor parameters — the interface must live with the high-level policy.
  • CQRS means separate read and write models. Level 1 is one database, two code paths, and nearly free.
  • Level 2+ buys read scale at the cost of eventual consistency and a rebuild path you must build.
  • Event sourcing gives audit and time travel; it costs querying, versioning and team familiarity.
  • CQRS ≠ Event Sourcing. Separate them explicitly in any design conversation.

Common mistakes

  • Generic repository over EF Core, losing projection and composition.
  • GetAllAsync inviting whole-table loads.
  • Repositories on the read side, blocking projections.
  • Two SaveChanges calls where atomicity was required.
  • Func<T,bool> instead of Expression, forcing client evaluation.
  • Interfaces in the infrastructure layer — DI without inversion.
  • Believing CQRS requires separate databases.
  • Jumping to level 2 CQRS without needing read scale.
  • No rebuild path for a read model.
  • Event sourcing as a default architecture.
  • Conflating CQRS with Event Sourcing.

Interview questions

Intermediate

Do you need a repository if you're using EF Core? 🔥 Must know
How I'd answer

"Sometimes, and not the generic kind."

"DbSet<T> is already a repository and DbContext is already a unit of work, so a generic IRepository<T> with GetById/GetAll/Add/Update/Delete is strictly less capable than what it wraps. It removes projection, Include, and composition — so callers either fetch whole entities they don't need, or you add an escape hatch returning IQueryable, and then it's abstracting nothing."

"GetAllAsync is the tell. It invites loading an entire table into memory, and it appears in almost every generic repository I've seen."

"The usual justification is 'we could swap the database'. That almost never happens, and it wouldn't work anyway — provider differences leak through, and a generic interface doesn't hide them."

"What I would use is a repository per aggregate with intention-revealing methods. IOrderRepository with GetForFulfilmentAsync and GetOverdueAsync."

"Two genuine reasons for that."

"Guarding the aggregate boundary. GetForFulfilmentAsync guarantees the order comes back with its lines and address loaded. Using DbSet directly, a caller can forget an Include and then hit a null reference where the domain method needed the lines. That's a correctness argument, not an abstraction one, and it's the strongest reason."

"Naming the query in domain language. GetOverdueAsync puts the definition of 'overdue' in one place, rather than three services each deriving a slightly different predicate and the reports disagreeing."

"The important qualifier: this is for the write side. For reads I'd query DbContext directly with a projection — AsNoTracking, Select into a DTO — because wrapping that in a repository only costs me EF's capabilities."

"And that asymmetry is deliberate rather than inconsistent. Repositories for commands, direct queries for reads, is CQRS at its simplest level — separate models for reading and writing, one database, no extra infrastructure."

What they're really checking
  • Do you know DbSet is already a repository?
  • Can you explain what a generic repository removes?
  • Do you dismiss the database-swapping justification?
  • Do you know the aggregate-boundary argument?
  • Do you connect write/read asymmetry to CQRS?
Weak answers
  • Red flag: "yes, for testability" — EF has an in-memory provider and you can substitute at a higher level.
  • Red flag: "to swap the database" as the main reason.
Likely follow-ups
  • How would you test code that uses DbContext directly?
  • Where does the Specification pattern fit?
  • Would you have a repository for reads?

Advanced

Explain CQRS. When would you use it? 🔥 Must know
How I'd answer

"CQRS is using a different model for reading than for writing. That's the entire principle — everything else is an implementation choice."

"I'd start there deliberately, because the most common confusion is thinking CQRS requires separate databases and event sourcing. It doesn't, and that belief is why people dismiss it as over-engineering."

"Why it exists: the two sides have genuinely different needs. The write side cares about invariants, validation and transactions — so a rich domain model, one aggregate at a time. The read side cares about shape and speed, and frequently needs data joined across aggregates. Read volume is typically ten to a hundred times higher, and the read shape changes with every UI redesign while the write model changes with business rules."

"Forcing both through one model gives you the worst of each: loading a full aggregate with two hundred lines to display four fields and count them in memory, and read queries that fight the aggregate boundary because the screen needs data from three of them."

"The part I'd emphasise is that CQRS comes in levels, and they have wildly different costs."

"Level 1 — separate models, one database. Writes go through repositories and the domain model. Reads query DbContext directly with AsNoTracking and a projection into a DTO, so SQL does the counting and summing. That's free — no new infrastructure, no eventual consistency, no new technology. Just two code paths. This is what I'd apply by default, and it captures most of the benefit."

"Level 2 — a separate read store. Denormalized tables updated from the write side. Now you have eventual consistency, which is a real commitment: a user can save something and not see it in a list. That needs handling deliberately — return the written entity rather than re-reading, or read from the write model right after a write. It's the same read-your-own-writes problem as a database replica."

"Level 3 — a different technology, like Elasticsearch for search. Real operational complexity."

"Level 4 — plus event sourcing. A different way of building software."

"So my answer on when: level 1 almost always, because it costs nothing and the projection is simply better code. Level 2 when reads genuinely can't be served from the write model — a dashboard aggregating across many aggregates, or read volume that needs its own scaling. Not because CQRS is supposed to look like that."

"Two things I'd insist on before agreeing to level 2 or above. A reliable sync mechanism — a change feed or an outbox, never a dual write, because that's the classic way the two stores silently diverge. And a rebuild path, so the read model can be regenerated from the source of truth when it drifts or its shape changes. Teams forget the rebuild and then can't change the read model without a migration nobody wants to attempt."

"And to be explicit: CQRS is not Event Sourcing. They pair well — event sourcing makes querying hard, so it needs CQRS projections to be usable — but CQRS needs one SQL database and two queries. If someone says CQRS and means event sourcing, that's worth separating before the team commits to it."

What they're really checking
  • Do you state the principle without the apparatus?
  • Do you know it has levels with different costs?
  • Do you know level 1 is essentially free?
  • Do you raise eventual consistency and read-your-own-writes?
  • Do you require a sync mechanism and a rebuild path?
  • Do you separate it from event sourcing?
Weak answers
  • Red flag: "CQRS means two databases".
  • Red flag: conflating it with event sourcing.
  • Red flag: recommending it universally, or dismissing it entirely.
Likely follow-ups
  • How do you keep the read model in sync?
  • How do you handle a user not seeing their own write?
  • When is event sourcing actually justified?
