Creational Patterns

Patterns about how objects get made. In .NET, the DI container already does most of this — so the useful skill is knowing which ones it replaces.

🟡 Intermediate 🔥 Must know
Quick revision
  • Factory Method — one place decides which implementation you get.
  • Abstract Factory — creates a family of related objects that must match.
  • Builder — step-by-step construction when there are many optional parts.
  • Singleton — one instance. In .NET, use AddSingleton, not a static property.
  • Prototype — copy an existing object instead of building a new one.
  • The container replaces most of these. Reach for a pattern when the decision is runtime data, not a type.

Factory Method 🔥 Must know

In simple terms

You need one of several implementations, and which one depends on runtime data — an enum, a country code, a customer tier.

A factory puts that decision in one place, so callers ask for "the right one for this payment method" instead of knowing all the options themselves.

Think of it this way

A hotel concierge. You say "I need to get to the airport"; they decide whether that's a taxi, a shuttle or the train.

You don't need to know which transport companies exist, and when a new option appears, only the concierge learns about it.

The problem it solves

public class CheckoutService
{
    public async Task<Result> PayAsync(Order order)
    {
        // This switch is about to appear in RefundService, SubscriptionService,
        // and anywhere else that touches payments.
        IPaymentGateway gateway;
        switch (order.PaymentMethod)
        {
            case PaymentMethod.Card:
                gateway = new StripeGateway(
                    new HttpClient(), _config["Stripe:Key"], _logger);   // caller builds it
                break;
            case PaymentMethod.BankTransfer:
                gateway = new OpenBankingGateway(new HttpClient(), _config["OB:Cert"]);
                break;
            case PaymentMethod.Wallet:
                gateway = new WalletGateway(_walletDb);
                break;
            default:
                throw new NotSupportedException();
        }
        return await gateway.AuthorizeAsync(order.ToRequest());
    }
}
What's wrong with it
The rule is duplicated. Add a payment method and you hunt for every switch
Every caller knows every implementation, so it references all of them
The caller constructs dependencies — HTTP clients, config, loggers. It shouldn't know Stripe needs an API key
Untestable. You cannot substitute a fake gateway without changing this code

The pattern applied

public interface IPaymentGatewayFactory
{
    IPaymentGateway For(PaymentMethod method);
}

public sealed class PaymentGatewayFactory(IServiceProvider services) : IPaymentGatewayFactory
{
    public IPaymentGateway For(PaymentMethod method) => method switch
    {
        PaymentMethod.Card         => services.GetRequiredService<StripeGateway>(),
        PaymentMethod.BankTransfer => services.GetRequiredService<OpenBankingGateway>(),
        PaymentMethod.Wallet       => services.GetRequiredService<WalletGateway>(),
        _ => throw new NotSupportedException($"No gateway for {method}.")
    };
}

// The caller now knows nothing about gateways
public class CheckoutService(IPaymentGatewayFactory factory)
{
    public Task<Result> PayAsync(Order order) =>
        factory.For(order.PaymentMethod).AuthorizeAsync(order.ToRequest());
}
// Each gateway keeps its OWN dependencies and lifetime
services.AddHttpClient<StripeGateway>();
services.AddHttpClient<OpenBankingGateway>();
services.AddScoped<WalletGateway>();
services.AddSingleton<IPaymentGatewayFactory, PaymentGatewayFactory>();
The key detail: resolve, don't new

The factory calls GetRequiredService rather than a constructor. That's what keeps it a routing decision instead of a construction procedure.

Each gateway declares its own dependencies and lifetime in the container. StripeGateway gets a typed HttpClient with its own retry policy; WalletGateway is scoped because it touches the database. The factory never learns any of that.

A factory full of new StripeGateway(new HttpClient(), ...) has just moved the problem into one file. It's still constructing, and it still breaks when a gateway gains a dependency.

In .NET you often don't need a factory at all ⭐ Senior-level

public interface IPaymentGateway
{
    PaymentMethod Method { get; }                     // self-describing
    Task<Result> AuthorizeAsync(PaymentRequest r, CancellationToken ct);
}

public sealed class StripeGateway : IPaymentGateway
{
    public PaymentMethod Method => PaymentMethod.Card;
    // ...
}

// The container injects EVERY registered implementation
public sealed class PaymentService(IEnumerable<IPaymentGateway> gateways)
{
    private readonly Dictionary<PaymentMethod, IPaymentGateway> _byMethod =
        gateways.ToDictionary(g => g.Method);

    public Task<Result> AuthorizeAsync(PaymentRequest r, CancellationToken ct) =>
        _byMethod.TryGetValue(r.Method, out var gateway)
            ? gateway.AuthorizeAsync(r, ct)
            : throw new NotSupportedException($"No gateway for {r.Method}.");
}
services.AddKeyedScoped<IPaymentGateway, StripeGateway>(PaymentMethod.Card);
services.AddKeyedScoped<IPaymentGateway, WalletGateway>(PaymentMethod.Wallet);

// Resolve by key - no factory class needed
public class CheckoutService(IServiceProvider sp)
{
    public Task<Result> PayAsync(Order o) =>
        sp.GetRequiredKeyedService<IPaymentGateway>(o.PaymentMethod)
          .AuthorizeAsync(o.ToRequest(), default);
}
Senior signal — why the self-describing version is usually better

With a switch-based factory, adding a payment method means editing two places: the registration and the factory's switch. Forget the switch and you get a runtime NotSupportedException that compiles perfectly.

With IEnumerable<IPaymentGateway>, adding a gateway means one line of registration. The dictionary builds itself. That's the open/closed principle actually working rather than being asserted.

Keyed services achieve the same thing with less code, though you lose the compile-time visibility of what's registered.

Being able to say "the classic Factory Method is largely replaced by IEnumerable<T> injection or keyed services in .NET" is the answer that shows you know the pattern and the platform — rather than reciting the GoF version.

Abstract Factory 🟡 Intermediate

In simple terms

Factory Method makes one thing. Abstract Factory makes a family of related things that must be consistent with each other.

The point isn't creating several objects — it's guaranteeing they match.

public interface IStorageFactory
{
    IBlobStore   CreateBlobStore();
    IQueueClient CreateQueue();
    ISecretStore CreateSecrets();
}

public sealed class AzureStorageFactory : IStorageFactory
{
    public IBlobStore   CreateBlobStore() => new AzureBlobStore(...);
    public IQueueClient CreateQueue()     => new ServiceBusQueue(...);
    public ISecretStore CreateSecrets()   => new KeyVaultSecrets(...);
}

public sealed class AwsStorageFactory : IStorageFactory
{
    public IBlobStore   CreateBlobStore() => new S3BlobStore(...);
    public IQueueClient CreateQueue()     => new SqsQueue(...);
    public ISecretStore CreateSecrets()   => new SecretsManagerSecrets(...);
}
Where the value is — and why it's rare

The guarantee is that you can't accidentally get an Azure blob store with an AWS queue. One factory choice fixes the whole family, so mismatched combinations are unrepresentable.

Genuinely useful for cloud abstraction, database provider families, and cross-platform UI toolkits.

But it's rare in application code, because DI registration already achieves it: register the Azure implementations in one if block at startup and the whole graph is consistent. The factory class earns its place mainly when the choice must be made per request rather than per deployment — a multi-cloud SaaS where the tenant decides.

It's also the pattern most likely to be over-applied: three factories to abstract something that only ever has one implementation.

Builder 🔥 Must know

In simple terms

When an object has many optional parts, a constructor becomes unusable — you get six overloads and parameter lists nobody can read.

A builder lets you name the parts you care about and ignore the rest.

// Which one do I call? What is `null, null, true, false, 30`?
var report = new Report("Sales", null, null, true, false, 30, null, "USD");

public Report(string title) { }
public Report(string title, DateRange? range) { }
public Report(string title, DateRange? range, string[]? columns) { }
public Report(string title, DateRange? range, string[]? columns, bool grouped) { }
// ... and it keeps growing
var report = new ReportBuilder("Sales")
    .ForPeriod(lastQuarter)
    .WithColumns("Region", "Revenue")
    .GroupedBy("Region")
    .InCurrency("USD")
    .Build();
Modern C# removes most of the need
public sealed record ReportRequest
{
    public required string Title { get; init; }
    public DateRange? Period { get; init; }
    public string[] Columns { get; init; } = [];
    public string Currency { get; init; } = "GBP";
}

var report = new ReportRequest
{
    Title = "Sales",              // `required` - compile error if omitted
    Period = lastQuarter,
    Columns = ["Region", "Revenue"]
};

Named, optional, immutable, and the compiler enforces the mandatory parts. No builder class to maintain.

A builder still earns its place when construction involves validation between steps, ordering rules, or non-trivial assembly — which is exactly why WebApplicationBuilder, HostBuilder and EF Core's ModelBuilder exist. Those aren't just setting properties; each call registers behaviour and the final Build() validates the whole configuration.

Singleton 🔥 Must know

In simple terms

Exactly one instance exists, and everything shares it.

Asked constantly in interviews — and the interesting part is that the classic implementation is the wrong answer in modern .NET.

The version that's broken

public sealed class Cache
{
    private static Cache? _instance;

    public static Cache Instance => _instance ??= new Cache();
    // Thread A checks _instance: null. Thread B checks: also null.
    // Both construct. Both assign. Two "singletons" exist, and each
    // caller has whichever one won the race.
}

static readonly fieldYesSimplest correct option

public sealed class Cache
{
    private static readonly Cache _instance = new();
    private Cache() { }
    public static Cache Instance => _instance;
}
// The CLR guarantees static initialization runs exactly once, thread-safely.
// There is no lock to write and therefore none to get wrong.
public sealed class Cache
{
    private static readonly Lazy<Cache> _lazy =
        new(() => new Cache(), LazyThreadSafetyMode.ExecutionAndPublication);

    private Cache() { }
    public static Cache Instance => _lazy.Value;
}

What you should actually do

// Registration
services.AddSingleton<ICache, MemoryCache>();

// Consumption - the dependency is visible in the signature
public class ProductService(ICache cache)
{
    // ...
}

Remember this

Almost every criticism of "Singleton" is really a criticism of static global access, not of having one instance.

One instance is often exactly right — a connection multiplexer, an in-memory cache, an HttpClient factory.

What causes the pain is Cache.Instance called from deep inside a method: an invisible dependency you can't substitute, so any class touching it becomes untestable without also constructing its cache.

A DI singleton gives you the same single instance with visible, replaceable dependencies.

A singleton must be thread-safe — and this catches people out

A singleton is shared by definition, so every member is potentially called concurrently. A Dictionary<K,V> field will corrupt under concurrent writes; ConcurrentDictionary won't.

The specific .NET trap: injecting a scoped service into a singleton. The singleton captures that instance for the application's lifetime, so a DbContext intended to live for one request lives forever — accumulating tracked entities and being used concurrently by every request. That's the captive dependency problem, and it produces the "second operation started on this context" error.

The fix is to inject IServiceScopeFactory and create a scope per unit of work — the same reasoning as using IDbContextFactory in a background service.

Prototype 💡 Good to know

In simple terms

Copy an existing object rather than constructing a new one — useful when construction is expensive or the configuration is complex and you want a variant of it.

public sealed record SearchCriteria(string Term, int Page, int PageSize, string Sort);

var baseline = new SearchCriteria("laptop", 1, 20, "relevance");

// `with` produces a copy with specific changes - shallow, by design
var pageTwo   = baseline with { Page = 2 };
var byPrice   = baseline with { Sort = "price", Page = 1 };
Shallow versus deep copy is the thing to know

with and MemberwiseClone both produce a shallow copy: reference-type fields are shared between the original and the copy.

So a copied object holding a List<T> shares that list — mutate it through either reference and both see the change. That's a genuinely surprising bug when the copy was made specifically to avoid interference.

For value-like records of primitives, shallow is fine and cheap. If the object holds mutable collections you need an explicit deep copy, and the cleanest way is usually to make the nested types immutable too so the question stops mattering.

Serialize-and-deserialize as a deep-copy mechanism works and is slow — acceptable for a one-off, not on a hot path.

Key takeaways
  • Factory Method centralises "which implementation?" when the answer is runtime data.
  • A factory should resolve from the container, not new things up.
  • IEnumerable<T> injection or keyed services usually beat a switch-based factory — one place to change instead of two.
  • Abstract Factory guarantees a consistent family; DI registration often achieves the same thing.
  • Builder is largely replaced by required and init — unless construction has real logic, as in WebApplicationBuilder.
  • _instance ??= new() is not thread-safe. static readonly is.
  • Prefer AddSingleton to a static Instance: same guarantee, visible and substitutable dependencies.
  • Singletons must be thread-safe, and must never capture a scoped dependency.
  • with is a shallow copy — shared references surprise people.

Common mistakes

  • A factory that calls new, so it still knows every dependency.
  • A switch-based factory where IEnumerable<T> would be self-extending.
  • Forgetting to update the factory switch after registering a new implementation.
  • Abstract Factory for something with one implementation.
  • A builder for a simple data object that init properties would cover.
  • _instance ??= new() presented as a correct singleton.
  • Static Instance access hiding dependencies and blocking tests.
  • A non-thread-safe collection inside a singleton.
  • A scoped service injected into a singleton.
  • Assuming with deep-copies.

Interview questions

Intermediate

Implement a thread-safe Singleton. Would you actually use it? 🔥 Must know
How I'd answer

"I'd write it, then argue against it — because in modern .NET the pattern is usually the wrong tool."

"The version people write first is private static Cache? _instance; with public static Cache Instance => _instance ??= new Cache();. That's not thread-safe. Two threads can both find _instance null, both construct, and both assign — so you get two instances, and each caller holds whichever won the race. On a web server that's not theoretical."

"The simplest correct version is a static readonly field with a private constructor. The CLR guarantees static initialisation runs exactly once, thread-safely — so there's no lock to write and therefore none to get wrong."

"If construction is expensive or must be deferred, Lazy<T> with LazyThreadSafetyMode.ExecutionAndPublication. I'd mention double-checked locking exists and I wouldn't hand-write it — it needs volatile and it's easy to get subtly wrong for no benefit over Lazy<T>."

"But the answer I'd actually give for production code is services.AddSingleton<ICache, MemoryCache>()."

"The reasoning: almost every criticism of Singleton is really a criticism of static global access, not of having one instance. One instance is frequently correct — a Redis multiplexer, an in-memory cache, an options object."

"What causes the pain is Cache.Instance called from inside a method. That's an invisible dependency — you can't see it in the constructor, you can't substitute it in a test, and any class touching it drags the real cache into every test that exercises it. It also makes the singleton's own dependencies awkward, because it has to reach for them statically too."

"A DI singleton gives the identical single-instance guarantee, with the dependency visible in the constructor and replaceable with a fake. And the lifetime decision moves to the composition root where it belongs, so the class doesn't have an opinion about how many of itself should exist."

"Two things I'd add unprompted. A singleton must be thread-safe — every member is potentially concurrent, so a plain Dictionary field will corrupt and needs to be ConcurrentDictionary. And never inject a scoped service into a singleton: it captures that instance forever, so a per-request DbContext ends up shared across every request. The fix is IServiceScopeFactory and a scope per unit of work."

  • Do you know static readonly is thread-safe by CLR guarantee?
  • Can you separate "one instance" from "static global access"?
  • Do you raise thread safety and captive dependencies?

  • Red flag: ??= presented as thread-safe.
  • Red flag: "Singleton is an anti-pattern" with no distinction.
  • Red flag: hand-rolled double-checked locking without volatile.

You need a different payment gateway per payment method. How do you wire that up? 🔥 Must know
How I'd answer

"The naive version is a switch at the call site, and I'd name what's wrong with it before offering an alternative: the rule gets duplicated in every service that touches payments, every caller ends up referencing every gateway, and the caller has to know how to construct them — that Stripe needs an HTTP client and an API key. That last part is what makes it untestable."

"The textbook answer is a factory: one class with the switch, returning IPaymentGateway. The important detail is that it should resolve from the container rather than call new — GetRequiredService<StripeGateway>() not new StripeGateway(...). That keeps it a routing decision, so each gateway declares its own dependencies and lifetime in registration. A factory full of constructor calls has just moved the problem into one file."

"But in .NET I'd usually do something better: let the implementations declare what they handle."

"Each gateway exposes a Method property. The consumer injects IEnumerable<IPaymentGateway> — the container supplies every registered implementation — and builds a dictionary keyed by method."

"The reason that's better is concrete: with a switch-based factory, adding a payment method means editing two places, the registration and the switch. Miss the switch and you get a runtime NotSupportedException from code that compiled fine. With IEnumerable<T>, adding a gateway is one line of registration and the dictionary builds itself. That's open/closed actually working rather than being claimed."

"Since .NET 8 there's a third option — keyed services. AddKeyedScoped<IPaymentGateway, StripeGateway>(PaymentMethod.Card) and resolve with GetRequiredKeyedService. Least code, though you lose the compile-time visibility of what's registered and it couples the consumer to IServiceProvider."

"Which I'd pick depends on the shape. If the set of gateways is stable and small, keyed services are fine. If new gateways get added regularly — which is typical for payments — the self-registering IEnumerable version, because it's the one where adding an implementation can't be done half-way."

"One design point worth raising: if the gateways differ in behaviour rather than just identity — different retry policies, different idempotency requirements — that's Strategy rather than Factory, and the distinction matters for where the logic lives. Factory answers 'which object?'; Strategy answers 'which algorithm?'. Here it's genuinely a factory, because the caller just wants the right gateway."

What they're really checking
  • Can you name what's wrong with the inline switch?
  • Do you know a factory should resolve, not construct?
  • Do you know the IEnumerable<T> and keyed-service alternatives?
  • Can you articulate the two-places-to-change argument?
Likely follow-ups
  • How would you test the routing?
  • What if a gateway needs per-tenant configuration?
  • How is this different from Strategy?
