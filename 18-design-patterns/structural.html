Structural Patterns

How objects get composed — wrapping, bridging and simplifying — without changing what they already do.

🟡 Intermediate 🔥 Must know
Quick revision
  • Adapter — makes an incompatible interface fit. Changes the shape, not the behaviour.
  • Decorator — same interface, adds behaviour around the inner object. Stackable.
  • Proxy — same interface, controls access: laziness, caching, permissions, remoting.
  • Decorator vs Proxy: same structure, different intent. Decorator adds, Proxy governs (and often skips the call entirely).
  • Facade — one simple entry point over a complicated subsystem.
  • Composite — treat a tree and its leaves the same way. Bridge — two things vary independently.

Adapter 🔥 Must know

One line: translate someone else's interface into yours.

The problem: a vendor SDK does what you need but in the wrong shape — wrong names, wrong types, its own exception hierarchy. Use it directly and vendor types spread through your codebase, so replacing it becomes a rewrite.

public interface ISmsSender
{
    Task<SmsResult> SendAsync(PhoneNumber to, string message, CancellationToken ct);
}
public sealed class TwilioSmsAdapter(ITwilioRestClient client) : ISmsSender
{
    public async Task<SmsResult> SendAsync(PhoneNumber to, string message, CancellationToken ct)
    {
        try
        {
            var response = await MessageResource.CreateAsync(
                to: new Twilio.Types.PhoneNumber(to.E164),
                body: message,
                client: client);

            // 2. translate their vocabulary into ours
            return response.Status switch
            {
                MessageResource.StatusEnum.Queued or MessageResource.StatusEnum.Sent
                    => SmsResult.Accepted(response.Sid),
                _   => SmsResult.Rejected(response.ErrorMessage ?? "unknown")
            };
        }
        catch (ApiException ex) when (ex.Status == 429)
        {
            // 3. translate their failures into ours
            throw new TransientMessagingException("SMS provider throttled us.", ex);
        }
    }
}

An adapter does three jobs. Notice the third one especially:

  1. Convert types — our PhoneNumber into theirs.
  2. Convert vocabulary — their status enum into our result.
  3. Convert failures — their exceptions into ours.

People skip the third one, and it's the one that leaks hardest. Once callers start catching ApiException, swapping vendors breaks code everywhere.

Best practice

This is the tactical version of an anti-corruption layer in DDD — see domain-driven design. Every external integration deserves one: it keeps foreign concepts out of your domain, and gives you one place to put retry, timeout and logging.

Decorator 🔥 Must know

One line: same interface, wraps an inner instance, adds behaviour around it.

The problem: you want caching, retry, logging or metrics on an existing component without modifying it — and you want to combine them freely.

public sealed class RetryingPriceFeed(IPriceFeed inner, ILogger<RetryingPriceFeed> log)
    : IPriceFeed
{
    public async Task<Price> GetAsync(string symbol, CancellationToken ct)
    {
        for (var attempt = 1; ; attempt++)
        {
            try
            {
                return await inner.GetAsync(symbol, ct);
            }
            catch (TransientFeedException ex) when (attempt < 3)
            {
                // Jitter matters: without it every caller retries in lockstep
                // and recreates the exact spike you're recovering from.
                var delay = TimeSpan.FromMilliseconds(
                    Math.Pow(2, attempt) * 100 + Random.Shared.Next(0, 100));

                log.LogWarning(ex, "Attempt {Attempt} failed for {Symbol}", attempt, symbol);
                await Task.Delay(delay, ct);
            }
        }
    }
}

Then you compose them at registration:

// Explicit factory - no extra package, completely clear.
services.AddSingleton<HttpPriceFeed>();
services.AddSingleton<IPriceFeed>(sp =>
    new CachingPriceFeed(
        new RetryingPriceFeed(sp.GetRequiredService<HttpPriceFeed>(),
                              sp.GetRequiredService<ILogger<RetryingPriceFeed>>()),
        sp.GetRequiredService<IMemoryCache>()));

// Or with Scrutor:
services.AddSingleton<IPriceFeed, HttpPriceFeed>();
services.Decorate<IPriceFeed, RetryingPriceFeed>();
services.Decorate<IPriceFeed, CachingPriceFeed>();   // outermost registered last
Common mistake — order

Caching outside retry means a cache hit skips the retry logic entirely. That's usually what you want.

Retry outside caching means every retry re-checks the cache, which is pointless — and worse, a failure gets retried before the cache can serve a value.

Logging outermost if you want to measure total time including retries. Decide deliberately and leave a comment saying why.

For HTTP, .NET already gives you this: DelegatingHandler instances registered through IHttpClientFactory form a decorator chain around the transport. That's where Polly policies live — see performance & resilience.

Decorator vs Proxy — the classic question

DecoratorProxy
StructureImplements the interface, holds an inner instanceIdentical
IntentAdd behaviourControl access
Stacked?Usually severalUsually one
Who supplies the inner object?Injected from outsideOften created or found by the proxy itself
Might skip the call?Rarely — it delegatesOften — cache hit or denied permission short-circuits

The honest summary: structurally identical, distinguished by intent. Say that plainly and then give the last two rows — that's a better answer than inventing a structural difference.

Facade 🟢 Beginner

One line: one simple method over a subsystem that needs several calls in a specific order.
public sealed class OnboardingFacade(
    ITenantProvisioner provisioner,
    IIdentityService identity,
    IBillingClient billing,
    ISeedDataLoader seeder)
{
    public async Task<Tenant> OnboardAsync(OnboardingRequest request, CancellationToken ct)
    {
        var tenant = await provisioner.CreateAsync(request.Name, request.Region, ct);
        await identity.CreateAdminAsync(tenant.Id, request.AdminEmail, ct);
        await billing.CreateSubscriptionAsync(tenant.Id, request.Plan, ct);
        await seeder.SeedDefaultsAsync(tenant.Id, ct);
        return tenant;
    }
}

What a facade does not solve — worth noticing: those are four steps across four systems with no transaction. If step three fails, you have a half-provisioned tenant. That's a saga / compensation problem, not a facade problem.

Common mistake

Letting the facade grow. Callers keep asking for "just one more method" until it's the whole application. Past a handful of coherent operations, split it by use case.

Composite 🟡 Intermediate 💡 Good to know

One line: treat a single item and a group of items through the same interface.
public interface IPricedItem { Money Price(); }

public sealed record Product(string Sku, Money UnitPrice, int Quantity) : IPricedItem
{
    public Money Price() => UnitPrice * Quantity;
}

public sealed class Bundle(decimal discountRate) : IPricedItem
{
    private readonly List<IPricedItem> _items = [];
    public Bundle Add(IPricedItem item) { _items.Add(item); return this; }

    public Money Price()
    {
        var gross = _items.Aggregate(Money.Zero("GBP"), (sum, i) => sum.Add(i.Price()));
        return gross * (1 - discountRate);
    }
}

The client calls Price() and never knows whether it's holding one product or a nested tree.

Production trap

Composite is a great in-memory pattern and a performance trap when the tree is in a database. If each node lazily loads its children, you get an N+1 query storm. Load the whole tree in one query — recursive CTE, closure table, or materialised path — rather than walking it node by node. Also watch for unbounded recursion on deep or cyclic data.

Bridge 🔴 Advanced 💡 Good to know

One line: two things vary independently, so don't model them with one inheritance tree.

Classic case: notification types (alert, reminder, digest) × delivery channels (email, SMS, push). Inheritance gives you 9 classes. Bridge gives you 3 + 3.

public interface IMessageChannel
{
    Task DeliverAsync(string to, string subject, string body, CancellationToken ct);
}

public abstract class Notification(IMessageChannel channel)
{
    protected IMessageChannel Channel { get; } = channel;
    public abstract Task SendAsync(User user, CancellationToken ct);
}

In practice Bridge is rare in application code, because dependency injection produces the same structure naturally. The moment you inject an interface instead of inheriting an implementation, you have a bridge. Saying that is more useful than memorising the diagram.

Key takeaways
  • Adapter must also translate exceptions, not just types and names.
  • Decorator order changes behaviour — cache outside retry, logging outermost.
  • Decorator and Proxy have the same shape; intent is what differs.
  • A facade simplifies calls but doesn't give you transactions across systems.
  • Composite over a database tree = N+1 unless you load it in one query.
  • DI already gives you Bridge without calling it that.

Common mistakes

  • Vendor types leaking through an adapter — especially exceptions and enums.
  • Decorator chains ordered by accident, so caching sits inside retry or metrics exclude retries.
  • A facade that grows until it's the application.
  • Composite over a database-backed tree, producing an N+1 storm.
  • Calling a decorator a proxy (or vice versa) — harmless in code, but it reads as imprecision in an interview.
  • Wrapping everything "for flexibility" until a request passes through five wrappers that each do nothing.

Interview questions

What's the difference between Decorator and Proxy?
How I'd answer

"Structurally they're the same — both implement the interface of the thing they wrap and hold a reference to it. The difference is intent, and it shows up in a few concrete behaviours."

"A decorator adds behaviour around the call — logging, retry, caching, metrics — and it's designed to be stacked. It almost always delegates, because augmenting is its job. And the inner instance is injected from outside, so the decorator doesn't choose what it wraps."

"A proxy controls access. It frequently doesn't call through: a protection proxy denies the call, a caching proxy returns a stored result, a virtual proxy defers creating the real object until it's needed. Proxies also often create or locate their target rather than receiving it — that's what makes lazy loading and remote proxies possible."

"In practice the line blurs. A caching wrapper can be described either way. What I'd take from the distinction is the design question: am I augmenting behaviour, in which case I should expect to stack these and think about ordering? Or am I governing access, in which case there's probably one and it needs to be impossible to bypass?"

What they're really checking
  • Can you discuss intent, not just structure?
  • Are you comfortable saying two patterns overlap, rather than inventing a difference?
Likely follow-ups
  • How does EF Core's lazy loading proxy work, and what problems does it cause?
  • Where does DelegatingHandler fit?
Add caching and retry to an existing service without changing it. How? ⭐ Senior-level
How I'd answer

"Decorators. Two classes implementing the same interface, each wrapping an inner instance, composed at registration. The original class stays untouched, each concern lives in one place, and I can vary the composition per environment — caching in production, none in integration tests."

"Ordering is the part I'd think about explicitly. Caching on the outside, so a cache hit skips the retry logic entirely and costs nothing. Retry inside it, so a transient failure gets retried before anything is cached. And I'd make sure failures aren't cached, or are cached with a very short TTL — caching an error for ten minutes turns a blip into an outage."

"For the retry itself I'd use Polly rather than hand-rolling it. The details are easy to get wrong: exponential backoff with jitter so callers don't retry in lockstep, a cap on attempts, and only retrying genuinely transient failures — retrying a 400 is pointless load. I'd pair it with a circuit breaker so we stop hammering a dependency that's properly down, and a timeout so a hung call can't hold a request thread forever."

"If it's an HTTP dependency, all of that belongs in a DelegatingHandler through IHttpClientFactory — same pattern, at the transport level."

"One caution I'd raise unprompted: retry must be safe. If the operation isn't idempotent — a payment authorisation, an order submission — retrying can duplicate the effect. The fix is an idempotency key, not removing the retry."

What they're really checking
  • Do you know the pattern and the ordering consequences?
  • Does idempotency occur to you when discussing retry?
  • Do you use the platform rather than reimplementing it?
Weak answers
  • Red flag: modifying the original class to add try/catch and a cache lookup.
  • Red flag: retry with no backoff, no cap, or on non-idempotent operations.
Likely follow-ups
  • How do you register that chain in the built-in DI container?
  • What if the cache and retry both have a 30s timeout and the caller has 10s?
  • How would you invalidate the cache when the underlying data changes?
