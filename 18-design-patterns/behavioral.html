Behavioural Patterns

Patterns about how objects interact. Strategy and Mediator are the two that come up constantly — and Mediator is the one where having an opinion matters.

🟡 Intermediate 🔴 Advanced 🔥 Must know
Quick revision
  • Strategy — one interface, a class per algorithm, chosen at runtime. Replaces a growing switch.
  • Observer — publishers notify subscribers without knowing them.
  • Command — an action as an object, so it can be queued, logged or undone.
  • Chain of Responsibility — ASP.NET Core middleware is exactly this.
  • Template Method — a base class fixes the steps, subclasses fill them in.
  • State — behaviour changes with state. Start with a transition table.
  • Mediator — components talk through a hub. Real benefits, real costs.

Strategy 🔥 Must know

In simple terms

You have several ways of doing the same job, and which one applies depends on runtime data.

Strategy puts each variant in its own class behind one interface, so the caller picks one instead of branching through all of them.

Think of it this way

A navigation app. "Fastest route", "avoid motorways", "walking" are different algorithms producing the same shape of answer.

The app doesn't contain one enormous routing function with modes bolted on. It has interchangeable routing engines, and you select one.

The problem it solves

public decimal CalculateDiscount(Order order, Customer customer)
{
    decimal discount = 0;

    switch (customer.Tier)
    {
        case CustomerTier.Standard:
            if (order.Subtotal > 1000) discount = order.Subtotal * 0.05m;
            break;

        case CustomerTier.Gold:
            discount = order.Subtotal * 0.10m;
            if (order.Subtotal > 5000) discount = order.Subtotal * 0.15m;
            break;

        case CustomerTier.Partner:
            // Partner discounts come from a contract in the database...
            var contract = _db.Contracts.FirstOrDefault(c => c.CustomerId == customer.Id);
            discount = order.Subtotal * (contract?.Rate ?? 0.12m);
            break;

        // Six months later: Seasonal, Employee, Volume, FirstOrder...
    }

    return discount;
}
What's wrong with it
Every new rule means editing this method — so every change risks the existing rules
The method accumulates dependencies. Partner needs the database; the next one needs an HTTP call. Now this class depends on everything
Testing one rule requires satisfying all of them. To test Gold you still construct the database dependency Partner needs
It grows without limit. Discount logic is the classic example — it never stops accumulating cases

The pattern applied

public interface IDiscountPolicy
{
    CustomerTier AppliesTo { get; }
    Money Apply(Money subtotal, Customer customer);
}

public sealed class StandardDiscount : IDiscountPolicy
{
    public CustomerTier AppliesTo => CustomerTier.Standard;

    public Money Apply(Money subtotal, Customer customer) =>
        subtotal.Amount > 1000 ? subtotal * 0.95m : subtotal;
}

public sealed class GoldDiscount : IDiscountPolicy
{
    public CustomerTier AppliesTo => CustomerTier.Gold;

    public Money Apply(Money subtotal, Customer customer) =>
        subtotal.Amount > 5000 ? subtotal * 0.85m : subtotal * 0.90m;
}

// This one needs the database - and ONLY this one does
public sealed class PartnerDiscount(IContractRepository contracts) : IDiscountPolicy
{
    public CustomerTier AppliesTo => CustomerTier.Partner;

    public Money Apply(Money subtotal, Customer customer)
    {
        var rate = contracts.RateFor(customer.Id) ?? 0.12m;
        return subtotal * (1 - rate);
    }
}
public sealed class PricingService(IEnumerable<IDiscountPolicy> policies)
{
    private readonly Dictionary<CustomerTier, IDiscountPolicy> _byTier =
        policies.ToDictionary(p => p.AppliesTo);

    public Money PriceFor(Order order, Customer customer) =>
        _byTier.TryGetValue(customer.Tier, out var policy)
            ? policy.Apply(order.Subtotal, customer)
            : order.Subtotal;          // no policy = no discount
}
services.AddScoped<IDiscountPolicy, StandardDiscount>();
services.AddScoped<IDiscountPolicy, GoldDiscount>();
services.AddScoped<IDiscountPolicy, PartnerDiscount>();
services.AddScoped<PricingService>();

// Or scan the assembly, so adding a class is genuinely zero configuration:
// services.Scan(s => s.FromAssemblyOf<IDiscountPolicy>()
//     .AddClasses(c => c.AssignableTo<IDiscountPolicy>()).AsImplementedInterfaces());

Each rule is its own classA new rule is a new file, not an edit to working code

Senior signal — Strategy in .NET is usually just an injected interface

The GoF diagram has a Context class holding a strategy and a setter to swap it. You almost never write that in .NET, because constructor injection is the strategy pattern — the container supplies the implementation and the consumer never knows which one.

So if a class takes IDiscountPolicy in its constructor, you've already applied Strategy without naming it. Saying that shows you recognise the pattern in idiomatic code rather than only in its textbook shape.

And for a genuinely simple stateless algorithm, you may not need the interface at all. A Func<Money, Customer, Money> or a dictionary of delegates is less ceremony:

private static readonly Dictionary<CustomerTier, Func<Money, Money>> Rules = new()
{
    [CustomerTier.Standard] = s => s.Amount > 1000 ? s * 0.95m : s,
    [CustomerTier.Gold]     = s => s * 0.90m
};

Reach for the interface when a strategy needs its own dependencies (like PartnerDiscount), needs a name for registration, or has more than one method.

The honest trade-off

Strategy exchanges a visible conditional for invisible indirection.

With three simple cases, the switch is genuinely easier to read and debug — everything is on one screen. Strategy scatters that logic across four files and a registration, and finding "what actually runs for a Gold customer" now requires knowing the pattern.

It wins when the variants have real logic, their own dependencies, or the set keeps growing. Discount rules, payment providers, export formats, notification channels — all yes. A three-case switch over an enum that hasn't changed in two years — no.

Strategy vs Factory: a factory answers "which object do I need?" and hands it back. Strategy answers "which algorithm should run?" and the caller just invokes it. They're often used together — a factory selecting a strategy.

Observer 🟡 Intermediate

In simple terms

Something happened, and an unknown number of interested parties should react — without the publisher knowing who they are.

public sealed record OrderPlaced(Guid OrderId, Guid CustomerId, Money Total);

// Several independent handlers, none known to the publisher
public sealed class SendConfirmationEmail : INotificationHandler<OrderPlaced>
{
    public Task Handle(OrderPlaced e, CancellationToken ct) => /* ... */;
}

public sealed class UpdateSalesFigures : INotificationHandler<OrderPlaced>
{
    public Task Handle(OrderPlaced e, CancellationToken ct) => /* ... */;
}
Two decisions people skip

1. Before or after commit? Handlers running inside the transaction can roll it back — correct for maintaining an invariant, wrong for sending an email, because a later failure has already sent it. Handlers running after commit can't affect the transaction but may fail with the data already saved.

2. Anything with an external side effect belongs in an outbox. Write the intent in the same transaction, publish after commit. Otherwise you get the dual-write problem: the order saved and the email didn't, or vice versa.

And with plain C# event handlers, a subscriber that never unsubscribes is a memory leak — the publisher holds a reference to it indefinitely. Same shape as unremoved DOM listeners.

Command 🟡 Intermediate

In simple terms

Wrap "do this thing" in an object, so the action can be passed around, queued, logged, retried or undone rather than being a method call that happens immediately.

public sealed record CancelOrder(Guid OrderId, string Reason) : IRequest<Result>;

public sealed class CancelOrderHandler(IOrderRepository orders)
    : IRequestHandler<CancelOrder, Result>
{
    public async Task<Result> Handle(CancelOrder cmd, CancellationToken ct)
    {
        var order = await orders.GetAsync(cmd.OrderId, ct);
        order.Cancel(cmd.Reason);
        return Result.Ok();
    }
}
Why turning an action into data is powerful

Once the request is an object, things become possible that a method call can't offer: serialise it to a queue for later processing, log it as an audit record of intent, validate it generically before any handler runs, retry it after a failure, or store a sequence of them for undo.

That's why Command underpins CQRS, message queues and event sourcing — they all depend on the operation being representable as data.

The cost is a class per operation, which is real ceremony for simple CRUD.

Chain of Responsibility 🔥 Must know

You already use this every day

ASP.NET Core middleware is Chain of Responsibility. Each component gets the request, decides whether to handle it or pass it on, and can act on the response coming back.

So is Angular's HttpInterceptor, and DelegatingHandler in HttpClient.

app.UseExceptionHandler();     // outermost - catches everything below
app.UseHttpsRedirection();
app.UseAuthentication();       // must precede authorisation
app.UseAuthorization();
app.MapControllers();          // the endpoint - the end of the chain
The pipeline is bidirectional, so order matters twice

Each middleware runs code before calling next() and can run more after it returns. So the first registered component is the outermost — first to see the request and last to see the response.

That's why exception handling goes first (it must wrap everything) and why authentication must precede authorisation (you can't authorise an unidentified user).

Registering middleware in the wrong order produces failures that look inexplicable — authorisation rejecting a valid user because authentication hasn't run yet. Covered in detail on the ASP.NET Core pipeline page.

Template Method 💡 Good to know

public abstract class ImportJob
{
    // The algorithm's shape is fixed here and cannot be reordered
    public async Task<ImportResult> RunAsync(CancellationToken ct)
    {
        var raw = await FetchAsync(ct);           // subclass supplies
        var valid = Validate(raw);                // subclass may override
        await PersistAsync(valid, ct);            // subclass supplies
        await NotifyAsync(valid.Count, ct);       // shared default
        return new ImportResult(valid.Count);
    }

    protected abstract Task<IReadOnlyList<Row>> FetchAsync(CancellationToken ct);
    protected abstract Task PersistAsync(IReadOnlyList<Row> rows, CancellationToken ct);
    protected virtual IReadOnlyList<Row> Validate(IReadOnlyList<Row> rows) => rows;
    protected virtual Task NotifyAsync(int count, CancellationToken ct) => Task.CompletedTask;
}
Prefer composition unless the sequence is genuinely fixed

Template Method uses inheritance, so it inherits inheritance's problems: a subclass is coupled to the base's protected surface, and changing that base breaks every subclass at once.

The composition alternative is to inject an IFetcher and an IPersister into one concrete ImportJob. More flexible, more testable, and each part is substitutable independently.

Template Method still earns its place when the ordering is the invariant you're protecting — when it must be fetch, then validate, then persist, and a subclass getting that wrong would be a bug. The base class makes the order unrepresentable-wrong, which composition doesn't.

State 🟡 Intermediate

private static readonly Dictionary<(OrderStatus From, OrderTrigger On), OrderStatus>
    Transitions = new()
{
    [(OrderStatus.Draft,    OrderTrigger.Submit)]  = OrderStatus.Placed,
    [(OrderStatus.Placed,   OrderTrigger.Pay)]     = OrderStatus.Paid,
    [(OrderStatus.Placed,   OrderTrigger.Cancel)]  = OrderStatus.Cancelled,
    [(OrderStatus.Paid,     OrderTrigger.Ship)]    = OrderStatus.Shipped,
    [(OrderStatus.Shipped,  OrderTrigger.Deliver)] = OrderStatus.Delivered
    // Anything absent is an invalid transition - by construction
};

public void Apply(OrderTrigger trigger)
{
    if (!Transitions.TryGetValue((Status, trigger), out var next))
        throw new InvalidOperationException($"Cannot {trigger} an order that is {Status}.");
    Status = next;
}
Why a table beats a class-per-state at first

The full State pattern gives each state its own class implementing the operations. That's right when each state has substantial distinct behaviour.

But a transition table is exhaustively testable — you can assert every state-trigger combination in a loop, and invalid transitions are simply absent from the table rather than requiring a check in each state class. It's also readable as a specification: someone can see the whole lifecycle in one place.

So start with the table. Move to class-per-state when the behaviour in each state diverges enough that the table's value objects get complicated.

The alternative people reach for — a pile of if (status == X && ...) checks scattered across services — is what both approaches exist to prevent, because invalid transitions become possible wherever someone forgets a check.

Mediator 🔥 Must know

In simple terms

Instead of components calling each other directly, they send messages to a hub which routes them to whatever handles them.

In .NET this almost always means MediatR or a similar library: a controller sends a request object, and a handler elsewhere processes it.

Think of it this way

An air traffic controller. Aircraft don't negotiate with each other directly — they all talk to the tower.

That removes N-to-N coordination. It also means the tower is now essential, and you can't tell which aircraft is talking to which by looking at the aircraft.

The problem it solves

public class OrdersController(
    IOrderRepository orders,
    IInventoryService inventory,
    IPaymentGateway payments,
    IEmailSender email,
    IAuditLogger audit,
    IValidator<PlaceOrderDto> validator,
    IUnitOfWork uow,
    ILogger<OrdersController> logger) : ControllerBase
{
    [HttpPost]
    public async Task<IActionResult> Place(PlaceOrderDto dto)
    {
        // Validation, logging and transaction handling repeated in EVERY action
        var result = await validator.ValidateAsync(dto);
        if (!result.IsValid) return BadRequest(result.Errors);

        logger.LogInformation("Placing order for {Customer}", dto.CustomerId);
        using var tx = await uow.BeginAsync();
        try
        {
            // ... orchestration ...
            await tx.CommitAsync();
            return Ok();
        }
        catch (Exception ex)
        {
            logger.LogError(ex, "Failed to place order");
            throw;
        }
    }
}
What's wrong with it
Eight constructor dependencies, and the controller grows one per feature
Validation, logging and transaction code repeated in every action — copy-paste that drifts
Orchestration logic lives in the HTTP layer, so it can't be reused from a background job or a message consumer
Hard to test — eight mocks to exercise one path

The pattern applied

public class OrdersController(IMediator mediator) : ControllerBase
{
    [HttpPost]
    public async Task<IActionResult> Place(PlaceOrder command, CancellationToken ct)
    {
        var result = await mediator.Send(command, ct);
        return result.IsSuccess ? Ok(result.Value) : BadRequest(result.Error);
    }
}
public sealed record PlaceOrder(Guid CustomerId, OrderLine[] Lines) : IRequest<Result<Guid>>;

public sealed class PlaceOrderHandler(
    IOrderRepository orders,
    IInventoryService inventory) : IRequestHandler<PlaceOrder, Result<Guid>>
{
    public async Task<Result<Guid>> Handle(PlaceOrder cmd, CancellationToken ct)
    {
        if (!await inventory.CanFulfilAsync(cmd.Lines, ct))
            return Result.Fail<Guid>("Insufficient stock");

        var order = Order.Place(cmd.CustomerId, cmd.Lines);
        await orders.AddAsync(order, ct);
        return Result.Ok(order.Id);
    }
}
// Applies to EVERY request passing through the mediator
public sealed class ValidationBehaviour<TRequest, TResponse>(
    IEnumerable<IValidator<TRequest>> validators)
    : IPipelineBehavior<TRequest, TResponse> where TRequest : notnull
{
    public async Task<TResponse> Handle(
        TRequest request, RequestHandlerDelegate<TResponse> next, CancellationToken ct)
    {
        var failures = validators
            .Select(v => v.Validate(request))
            .SelectMany(r => r.Errors)
            .Where(f => f is not null)
            .ToList();

        if (failures.Count > 0) throw new ValidationException(failures);

        return await next();
    }
}

// One registration; every command is now validated, logged and transactional
services.AddTransient(typeof(IPipelineBehavior<,>), typeof(ValidationBehaviour<,>));
services.AddTransient(typeof(IPipelineBehavior<,>), typeof(LoggingBehaviour<,>));
services.AddTransient(typeof(IPipelineBehavior<,>), typeof(TransactionBehaviour<,>));
Senior signal — the pipeline is the actual reason to adopt Mediator

People justify MediatR with "it decouples the controller from the handler". That's true and it's a weak benefit — the controller was already only calling one service.

The real value is IPipelineBehavior. Validation, logging, transaction management, retry, caching and authorisation get written once and apply uniformly to every request. Without it, each of those is copy-pasted into every handler and drifts — one endpoint forgets the transaction, another logs differently.

It's the same mechanism as ASP.NET Core middleware, applied at the application layer instead of the HTTP layer — which matters because it also covers requests that didn't arrive over HTTP, like a message consumer or a scheduled job.

Leading with the pipeline rather than the decoupling is what shows you've used it in anger.

The costs — have an opinion on these

Navigability suffers. "Go to definition" on mediator.Send(command) takes you into the library, not the handler. You find handlers by naming convention or by searching for the request type. On a large codebase that's a genuine daily friction, and it's the complaint experienced teams raise most.

Weaker compile-time safety. A missing or duplicate handler is a runtime failure, not a build error. Deleting a handler still compiles.

Indirection for its own sake in small services. In a three-endpoint API, mediator.Send is an extra hop to reach a class the controller could have injected directly. You get the ceremony and none of the benefit.

Debugging is harder. A stack trace through four pipeline behaviours and a dispatcher is considerably less readable than a direct call.

My position: adopt it when you have enough use cases that uniform cross-cutting behaviour is worth the indirection — and note you can get most of the benefit without the library by injecting handlers directly and using decorators for the cross-cutting parts.

Key takeaways
  • Strategy replaces a growing switch; each variant gets its own class and its own dependencies.
  • In .NET, constructor injection is Strategy — and a Func<> often suffices.
  • Strategy trades a visible conditional for invisible indirection. Three simple cases don't need it.
  • Observer: decide before-commit vs after-commit deliberately, and use an outbox for external effects.
  • C# event subscribers that never unsubscribe leak.
  • Command turns an action into data, which is what makes queueing, retry, audit and undo possible.
  • Middleware is Chain of Responsibility, and it's bidirectional — order matters twice.
  • For state machines, start with an exhaustively-testable transition table.
  • Mediator's real payoff is IPipelineBehavior, not controller decoupling.
  • Mediator costs navigability and compile-time safety. Don't adopt it reflexively in a small service.

Common mistakes

  • Strategy for a two-case switch — indirection with no benefit.
  • A strategy interface where a Func<> would do.
  • One class accumulating every rule's dependencies because the switch stayed.
  • Domain event handlers sending email inside the transaction.
  • Event subscribers never unsubscribed.
  • Middleware registered in the wrong order — authorisation before authentication.
  • Status checks scattered across services instead of one transition table.
  • Adopting MediatR for the decoupling without using pipeline behaviours.
  • MediatR in a three-endpoint service.
  • Business logic in the controller, so it can't be reused by a job or consumer.

Interview questions

Intermediate

You have a discount calculation with a growing switch on customer tier. How would you restructure it? 🔥 Must know
How I'd answer

"That's Strategy, and I'd start by naming why the switch is a problem, because that determines whether the pattern is worth it."

"Three specific problems. Every new rule means editing working code, so each change risks the existing tiers. The method accumulates dependencies — the Partner tier needs a contract from the database, the next one needs an HTTP call, and now this one class depends on everything. And testing one rule requires satisfying all of them: to test the Gold calculation I still have to construct whatever the Partner branch needs."

"So I'd extract an IDiscountPolicy interface with an Apply method, and one class per tier. PartnerDiscount takes IContractRepository in its constructor; the others take nothing. Each is testable in two lines with no mocks."

"For selection, rather than a factory with its own switch, I'd have each policy declare what it applies to and inject IEnumerable<IDiscountPolicy> into the pricing service, building a dictionary keyed by tier. That way adding a rule is one registration line — there's no switch left to forget to update. With assembly scanning it's zero configuration."

"Now the honest part: Strategy trades a visible conditional for invisible indirection. The switch had everything on one screen. After this, answering 'what runs for a Gold customer?' means knowing the pattern and finding the right file."

"So I'd apply it here because discount logic is the classic never-stops-growing case and the rules have genuinely different dependencies. I would not apply it to a three-case switch over a stable enum — there the switch is easier to read and debug, and extracting it is over-engineering."

"Two .NET-specific points. Constructor injection already is Strategy — if a class takes IDiscountPolicy, the pattern is applied whether or not anyone called it that. And for genuinely simple stateless rules, a dictionary of Func<> delegates is less ceremony than an interface and four classes. I'd reach for the interface specifically because PartnerDiscount needs its own dependency, which a lambda can't carry cleanly."

What they're really checking
  • Can you name what's actually wrong with the switch?
  • Do you notice the dependency-accumulation problem?
  • Do you use self-selection rather than another switch in a factory?
  • Will you say when Strategy is not worth it?
  • Do you know DI already is Strategy?
Weak answers
  • Red flag: applying it with no cost analysis.
  • Red flag: replacing the switch with another switch in a factory and calling it decoupled.
Likely follow-ups
  • What if two discounts can apply at once?
  • How would you test the selection logic?
  • When would a Func<> be enough?

Advanced

Would you use MediatR in a new project? ⭐ Senior-level
How I'd answer

"It depends on size, and I'd be specific about what the benefit actually is — because the usual justification is the weak one."

"People say it decouples the controller from the handler. That's true and it's not worth much: the controller was already just calling one service, and swapping IOrderService for IMediator hasn't bought much decoupling."

"The real value is IPipelineBehavior. Validation, logging, transaction management, retry and authorisation get written once and apply to every request automatically. Without it, each handler repeats that plumbing — and it drifts. One endpoint forgets to wrap in a transaction, another logs a different shape, and you find out during an incident."

"It's the same mechanism as ASP.NET Core middleware, but at the application layer — which matters because it also covers requests that didn't arrive over HTTP. A message consumer or a scheduled job sending the same command gets the same validation and transaction handling for free. That's the argument I'd lead with."

"It also gives you a natural unit of work per use case: one request type, one handler, one thing that class does. That tends to keep handlers small in a way that service classes with fifteen methods don't."

"Now the costs, which I think are understated."

"Navigability. 'Go to definition' on mediator.Send(command) takes you into the library. You find handlers by convention or by searching the request type. On a large codebase that's daily friction, and it's the thing teams who've lived with it complain about most."

"Weaker compile-time safety. A missing handler is a runtime failure. Deleting one still compiles."

"Harder debugging. A stack trace through four behaviours and a dispatcher is much less readable than a direct call."

"And in a small service it's pure overhead — an extra hop to reach a class you could have injected."

"So: for a substantial application with many use cases, yes, because uniform cross-cutting behaviour is worth the indirection. For a service with a handful of endpoints, no — inject the handler directly."

"The middle option worth mentioning: you can get most of the benefit without the library. Inject handler interfaces directly, and use decorators — which Scrutor makes easy — for the cross-cutting concerns. You keep 'go to definition' working and compile-time checking, and you lose the generic dispatch. For teams that find the indirection painful, that's often the better trade."

"One thing I'd flag regardless: MediatR is now commercially licensed for larger organisations. That doesn't change the design argument, but it's a real consideration for a new project and worth raising rather than discovering later."

What they're really checking
  • Do you identify pipeline behaviours as the real benefit?
  • Do you know it covers non-HTTP entry points?
  • Are you honest about navigability and debugging costs?
  • Do you scale the answer to project size?
  • Do you know the decorator alternative?
Weak answers
  • Red flag: "yes, it's clean architecture" with no analysis.
  • Red flag: leading with controller decoupling.
  • Red flag: no awareness of the navigability cost.
Likely follow-ups
  • Write a transaction pipeline behaviour.
  • How would you handle a command that must not be transactional?
